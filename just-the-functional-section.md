### The functional angle: all four can sort by a derived key, and exactly one decided that means caching it

Drawn from today's Rust tip, which is this problem, and today's C++ tip, whose
projection-based `ranges::sort` carries the identical hazard. F# is here as the
control: the language where this shape is the idiom, to settle whether the cost
belongs to functional style or to the languages charging for it.

The shape is "order these by something derived from each element". Every one of
the four can say it. What differs is whether saying it implies that the derived
value is computed once.

```fsharp
// F# 8, FSharp.Core 8.0.0.0, .NET 8.0.8. Every *By function caches the key,
// including the one that mutates in place. Counted, not assumed:
let words = [ for i in 0 .. 63 -> sprintf "w%03d" ((i * 37) % 64) ]
words |> List.sortBy (fun s -> s.ToLowerInvariant())            // 64 calls
words |> List.toArray |> Array.sortInPlaceBy (fun s -> s.ToLowerInvariant())  // 64
// Drop to a raw comparator and the caching goes with it, because there is no
// longer a key for the library to hold on to:
words |> List.sortWith (fun a b -> compare (a.ToLowerInvariant()) (b.ToLowerInvariant()))  // 900
```

The other three, same input, same key, counted the same way: Rust's
`sort_by_key` 834 and `sort_by_cached_key` 64, C++'s
`ranges::sort(v, {}, proj)` 960 on libstdc++ (854 on libc++), and JS
`sort(cmp)` 598.

| Language | The functional form | Key calls, n=64 | What it costs |
| --- | --- | --- | --- |
| F# | `List.sortBy`, `Array.sortInPlaceBy` | 64 | Nothing at the call site. The library caches whether or not you allocate a new list. |
| Rust | `sort_by_cached_key` | 64 | A `(K, u32)` side table per element, and you must know the longer name exists. |
| Rust | `sort_by_key` | 834 | The shorter, more obvious name is the expensive one. |
| C++ | `ranges::sort(v, {}, proj)` | 960 (libstdc++), 854 (libc++) | Not expressible. The projection is a call, not a value, and std has no cached form to reach for. |
| TypeScript | `sort(cmp)` | 598 | Not expressible. There is no key parameter at all, so the comparator extracts twice per comparison. |

So the cost is not the price of functional style. It is a library policy
decision, made once per language, that you inherit. F# decided a key is a value
worth keeping; C++ decided a projection is a call to be repeated; Rust decided
both and made the cheap one longer to type; JS never had the concept.

The mutability angle points the other way from the usual expectation.
`Array.sortInPlaceBy` is the impure, mutating F# function, and it still caches,
so in F# you do not trade purity for the cheap key. Rust does not make you
trade either, but it makes you know a name. The one place today where purity did
buy something is in the TypeScript tip: `.map` builds a fresh array and
therefore silently repairs a holey elements kind, while `.fill` mutates in place
and leaves it holey forever. The version that constructs a new value is the one
that could afford to be correct, and nobody wrote that down as the reason.

If a `*By` function in your codebase takes a closure, do you know whether it
holds the result or re-runs it? And when a language gives you both, as Rust
does, which one did the API author make easier to type?

**Sources**

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-listmodule.html#sortBy
- https://doc.rust-lang.org/std/primitive.slice.html#method.sort_by_cached_key
- https://en.cppreference.com/w/cpp/algorithm/ranges/sort

**Verified**

All counts were measured on Debian 13 (arm64): `dotnet fsi` on .NET 10.0.402
SDK (64, 64, 900), rustc 1.99.1 (834, 64), GCC 14.2 with libstdc++ (960), and
Node 22.23.4 (299 comparisons, 598 extractions). As a separate confirmation, on
macOS `dotnet fsi` on .NET 8.0.8 with FSharp.Core 8.0.0.0, rustc 1.95.0 and
Node 22.17.1 gave the same counts, and Apple clang 21 with libc++ gave 854.
Exact comparison counts are implementation-defined in all four languages, so
treat the numbers as the shape of the difference rather than as constants.

### The functional angle: all four languages let a closure outlive what it captured, and only one of them lets it dangle

Draws on today's C++ tip, which is entirely about what a capture list actually
stores, and on the F# tip, which is about what wrapping a value costs. The shape
is the smallest interesting closure there is: build one over a local, return it,
call it after the local is gone.

C++ is the baseline here, not because it is the odd one out but because it is
the only one of the four where the *capture mode is written down by the
programmer* and can therefore be written down wrongly.

```cpp
// C++: [=] over a member captures `this` by pointer, not the member by value.
struct Widget { int n = 7; std::function<int()> make() { return [=] { return n; }; } };
// ASan: stack-use-after-scope, READ of size 4, in the lambda's operator()
```

```rust
// Rust: the borrow checker refuses before you can run it. Note that the
// diagnostic names `w.n`, not `w` -- edition 2021 captures disjoint fields.
fn make() -> Box<dyn Fn() -> u32> {
    let w = Widget { n: 7 };
    Box::new(|| w.n)        // error[E0373]: closure may outlive the current
}                           // function, but it borrows `w.n`
// Box::new(move || w.n)    // compiles, prints 7: the closure OWNS w
```

```fsharp
// F#: no capture syntax exists, and no lifetime error is possible. The CLR
// lifts `w` into a heap display class, so the closure cannot outlive it.
let make () : unit -> int =
    let w = { n = 7 }
    fun () -> w.n
printfn "%d" (make () ())        // 7
```

```ts
// TS/JS: captures the BINDING, not the value. Nothing dangles, but the closure
// sees writes that happened after it was built.
function make() { let n = 7; const f = () => n; n = 99; return f; }
make()();                        // 99, not 7
// And the loop case, which is the same fact wearing a hat:
for (let i = 0; i < 3; i++) withLet.push(() => i);   // [0, 1, 2]
for (var j = 0; j < 3; j++) withVar.push(() => j);   // [3, 3, 3]
```

| Language | What "capture" stores | Measured | What it costs |
| --- | --- | --- | --- |
| C++ | whatever the capture list says; `[=]` over a member stores `this`, a raw pointer | ASan `stack-use-after-scope` at the call | correctness. `[=, this]` or `[*this]` are silent; a deprecation warning is the only guard, and only since C++20 |
| Rust | the fields actually used, by the weakest mode that works; `move` forces ownership | `error[E0373]` naming `w.n` | nothing at runtime. You pay by having to decide `move` or not, and the decision is in the type |
| F# | a compiler-generated heap object holding the captured values | 24 bytes per iteration for a record capture; ~0 for a bare `int`, because escape analysis erased it | an allocation per closure, in principle. In practice the optimizer often takes it back, which makes it unpredictable rather than free |
| TypeScript | a reference to the enclosing binding, per `let` iteration or once per `var` | `99` instead of `7`; `[3,3,3]` for `var` | nothing dangles, and nothing is a snapshot either. Immutability is the only way to make a capture mean what it looks like |

The asymmetry worth keeping is not "Rust is safe". It is that **C++ is the only
one of the four that asks you to name the capture mode, and the shorthand
everybody types names the wrong one.** `[=]` is spelled as a by-value default
and behaves as by-pointer for the members you most want to read. Rust removed
the question by inferring the mode and putting the failure in the type system;
F# and TypeScript removed it by making the environment reachable forever.

Immutability outranks purity here, and TypeScript is where you can see it: its
closure is not wrong so much as *not a snapshot*, and the only fix that makes
`() => n` mean 7 forever is never writing to `n`. F# gets that for free by
default and needed `let mutable` only to hold the benchmark's sink, which is the
measurement's problem rather than the shape's.

Left hanging: `[*this]` copies the whole object, which is the honest
by-value capture and also a copy constructor call you did not write. On a type
with a `vector` member, in a lambda built per request, which of the two bugs
would you rather have - and how would you notice the second one?

### The functional angle: three of these four languages decide a fold's accumulator type from the fold, and only C++ lets the seed decide it

Draws on the C++ tip. Same shape everywhere: a left fold with an explicit seed.

F# is the baseline here because `List.fold` is generic in `'State` and `'T` separately and inference must unify `'State` with the folder's result, so a mismatch is a type error by construction.

```fsharp
let xs = [1.5; 2.5; 3.25]
let bad  = List.fold (+) 0   xs   // error FS0001: 'float' does not match 'int'
let good = List.fold (+) 0.0 xs   // 7.25
```

```rust
let v: Vec<f64> = vec![1.5, 2.5, 3.25];
let bad  = v.iter().fold(0,   |a, b| a + b);  // error[E0277]: cannot add `&f64` to `{integer}`
let good = v.iter().fold(0.0, |a, b| a + b);  // 7.25
```

```cpp
auto bad  = std::accumulate(v.begin(), v.end(), 0);   // 6, silently, T == int
auto good = std::ranges::fold_left(v, 0, std::plus{}); // 7.25, even with the int seed
```

```ts
const s: string[] = ["a", "b"];
const bad = s.reduce((a, b) => a + b, 0);   // error TS2769: No overload matches
// number[] with seed 0 is fine: there is no integer type to truncate into.
```

| Language | Where the accumulator type comes from | Seed/element mismatch |
| --- | --- | --- |
| F# | `'State`, unified with the folder's result | FS0001 at compile time |
| Rust | closure's inferred parameter and return | E0277 at compile time |
| TypeScript | `U` on `reduce<U>`, bound by the seed | TS2769; no integer type exists |
| C++ `accumulate` | `T`, from `init` alone | none; 6 instead of 7.25 |
| C++ `ranges::fold_left` | `decay_t<invoke_result_t<F&, T, range_reference_t<R>>>` | none needed: result widens to `double` |

C++23 did not add a check; it moved the accumulator's type from the seed to the folder, which is what the other three always did. `std::reduce` is the other std answer and the thread left hanging: it may reorder, so it needs an associativity that `double` addition does not have, and the fastest of the three std folds is the one whose preconditions your data violates.

### The functional angle: every language here type-erases a closure, and only C++ lets a copy constructor's noexcept decide whether that allocates

Draws on the C++ tip. The shape is the same in all four: take a closure, forget its concrete type, store it behind one uniform callable type.

```rust
let x = 7;
let f: Box<dyn Fn() -> i32> = Box::new(move || x);   // 1 allocation once it captures
let g: Box<dyn Fn() -> i32> = Box::new(|| 1);        // 0: a non-capturing closure is zero-sized
fn take(h: impl Fn() -> i32) -> i32 { h() }          // no erasure, no allocation, one copy of code per closure
```

```cpp
std::function<long()> f = [p = Plain{}] { return p.a; };        // 0: fits 16 bytes, nothrow copy
std::function<long()> g = [h = Handwritten{}] { return h.a; };  // 1: same size, copy ctor not noexcept
```

```fsharp
let make (i: int) = fun () -> i + 1                          // 24 bytes: an FSharpFunc subclass instance
let asDelegate (i: int) = System.Func<int>(fun () -> i + 1)  // 88 bytes: closure plus delegate
```

```ts
const make = (i: number) => () => i + 1;   // a heap-allocated closure object in V8; not measured here
```

| Language | Erased form | Allocation, measured | What it costs |
| --- | --- | --- | --- |
| F# | `unit -> int` closure / `Func<int>` | 24 B / 88 B per capturing closure | always a GC object; crossing into a .NET delegate nearly quadruples it |
| Rust | `Box<dyn Fn>` / `impl Fn` | 1 alloc capturing, 0 non-capturing / none | erasure is opt-in and priced at the type; `impl Fn` pays in code size instead |
| C++ | `std::function` | 0 up to 16 B with nothrow copy, else 1 | the price depends on a property of the captured type that the call site never shows |
| TypeScript | any function value | not measured | every closure is a heap object; there is no unboxed form to choose |

F# is the baseline because the functional form is its default, and it still charges for the capturing closure every time: the cost is intrinsic to erasing a closure, not to any one language. What sets C++ apart is not the price but where the decision comes from. Rust and F# price the type you chose; C++ prices the captured type's copy constructor. Left hanging: which of your .NET interop boundaries converts an F# closure into a delegate on every request?

### The functional angle: "give me the last one" is O(1) only where the language never promised to run the skipped elements

Draws on the Rust tip, with a measured row from each other language. Same problem everywhere: map a 1,000-element array with a counting function, take the last result.

```rust
v.iter().map(f).last()        // 1000 calls: last() is a consuming fold
v.iter().map(f).next_back()   // 1 call
```

```cpp
auto t = v | std::views::transform(f);
t.back();                     // 1 call: a view evaluates on access, never on skip
```

```fsharp
arr |> Seq.map f |> Seq.last      // 1000 calls
arr |> Array.map f |> Array.last  // 1000 calls: eager, and it allocates the whole result
```

```ts
v.map(f).at(-1)                          // 1000 calls: Array.prototype.map is eager
for (const x of v.values().map(f)) {}    // 1000 calls: iterator helpers have no last/back
```

| Language | Functional form | Calls, n=1000 | What it costs |
| --- | --- | --- | --- |
| F# | `Seq.map >> Seq.last` | 1000 | the baseline here since `Seq` is the lazy default; laziness buys nothing when the consumer walks forward |
| Rust | `map(..).last()` / `.next_back()` | 1000 / 1 | the O(1) path exists but you must name it; the default is the fold |
| C++ | `views::transform(..).back()` | 1 | free, because views never promised side effects on skipped elements |
| TypeScript | `map(..).at(-1)` | 1000 | no lazy backwards path at all; eager `map` also allocates n results |

The asymmetry worth noticing: C++ gets O(1) *because* its view is allowed to skip your function, and Rust cannot *because* its `last` is not. Neither needs `mut` to express the fast version; the cost is entirely in what the consumer is allowed to skip.

Left hanging: if a function you pass to `map` should be pure, should a language be allowed to call it fewer times than you wrote, and would you notice if it did?

### The functional angle: the additive identity of floating point is -0, and only two of the folds you write know it

Draws on the TypeScript tip (`Math.sumPrecise([])` is `-0`), with a measured row from each other language. The shape: sum a sequence of `f64`, starting from the fold's identity element. For `+` on IEEE-754, that element is `-0.0`, because `-0.0 + x == x` for every `x`, including `x = -0.0`. `+0.0 + -0.0` is `+0.0`, so starting from `+0` changes the result for an all-negative-zero input.

```rust
let s: f64 = [-0.0f64].iter().sum();                 // -0.0: std's Sum folds from -0.0
let f: f64 = [-0.0f64].iter().fold(0.0, |a, b| a + b); // +0.0: your fold does not
```

```cpp
std::accumulate(v.begin(), v.end(), 0.0);   // +0.0 for {-0.0}: your init
std::reduce(v.begin(), v.end());            // +0.0 for {-0.0}: init is T{}, which is +0.0
```

```fsharp
List.sum [-0.0]            // +0.0: GenericZero is +0.0
List.fold (+) 0.0 [-0.0]   // +0.0
```

```ts
[-0].reduce((a, b) => a + b, 0);   // +0
Math.sumPrecise([-0]);             // -0 (and [] gives -0 too)
```

| Language | Functional form | Sign for `[-0.0]` | What it costs |
| --- | --- | --- | --- |
| F# | `List.sum` | +0 | the baseline, since it is the idiomatic `sum`; `GenericZero` picks +0, so the identity law is broken by the stdlib itself |
| Rust | `Iterator::sum` / `fold(0.0, ..)` | -0 / +0 | std gets it right (`core/src/iter/traits/accum.rs` folds from `-0.0`); the hand-written fold, which is what most people write, does not |
| C++ | `accumulate(.., 0.0)` / `reduce` | +0 / +0 | no std sum knows; `reduce` also may reorder, so it is not even the same rounding |
| TypeScript | `reduce(.., 0)` / `sumPrecise` | +0 / -0 | the new builtin is the only precise sum in any of the four stdlibs, and the runtime lag is the cost |

The asymmetry worth noticing: none of these needs `mut`, and every one is a "pure" fold. The bug is in the identity element, not in the style. A fold is only lawful if its seed is the operator's identity, and three of four standard libraries chose the seed that reads nicest instead.

Left hanging: does any code of yours branch on the sign of zero (`1 / x`, `Math.sign`, `atan2`, a serializer that writes `-0`), and if so, which of your sums feed it?

### The functional angle: every run-once cell has to decide whether a failure is remembered, and the standard libraries split three ways

Draws on the TypeScript tip, with a measured row from each language. The shape: a lazy, run-once value whose initializer fails the first time and would succeed the second time. Purity says evaluating the same thunk twice gives the same answer, so caching the failure is the "functional" choice. Operations says a 503 is not a value.

```rust
static L: LazyLock<u32> = LazyLock::new(flaky);   // 2nd access: panics "previously been poisoned"
static O: OnceLock<u32> = OnceLock::new();
O.get_or_init(flaky);                             // 2nd call: runs flaky again, Ok(2)
```

```cpp
int get() { static int v = flaky(); return v; }  // throw on 1st call: 2nd call re-runs, 2
std::call_once(flag, [&] { out = flaky(); });    // same: an exceptional call does not set the flag
```

```fsharp
let l = lazy (flaky ())   // l.Force() twice: Error "503", Error "503", calls = 1
```

| Language | Run-once form | After a failed first run | What it costs |
| --- | --- | --- | --- |
| F# | `lazy` / `Lazy<T>` | the same exception, forever | the baseline, since `lazy` is F#'s built-in thunk; recovery means a new `Lazy`, so the binding cannot be a plain `let` |
| Rust | `LazyLock` / `OnceLock::get_or_init` | poisoned forever / retried | two cells, two policies; `LazyLock` poisoning is a *different* panic than the one that caused it |
| C++ | function-local `static` / `call_once` | retried / retried | the language chose retry, so a failing initializer runs on every call until it succeeds, with no backoff |
| TypeScript | memoized Promise / `Effect.cached` | the same rejection / the same `Exit`, forever | recovery is manual: rebuild the Promise, or `cachedInvalidateWithTTL` plus an explicit `invalidate` |

The asymmetry: none of these needs `mut` in user code, and the "pure" answer (remember the failure) is what F#, Promise, and Effect give you, while C++ gives the retry answer and Rust ships both. The cost is not in the style, it is in who has to write the retry policy.

Left hanging: for each run-once value in your services, which policy did you actually want, and which one did the cell you picked give you?

### The functional angle: only TypeScript lets `filter` change the element type, so only TypeScript has to prove an "if and only if"

Draws on the TypeScript tip. The shape: drop the missing values from a list of optionals and end up with a list of the values. Every language can do it; they disagree on whether a *filter* is allowed to do it.

```rust
let kept:    Vec<Option<i32>> = readings.iter().copied().filter(|reading| reading.is_some()).collect(); // type unchanged
let present: Vec<i32>         = readings.iter().copied().flatten().collect();                        // [0, 3]
```

```cpp
auto present = readings
    | std::views::filter([](auto& maybe) { return maybe.has_value(); })
    | std::views::transform([](auto& maybe) { return *maybe; });  // *maybe unchecked, trusts the filter
```

```fsharp
List.filter Option.isSome readings   // [Some 0; Some 3]  still options
List.choose id readings              // [0; 3]
```

| Language | Functional form | What it costs |
| --- | --- | --- |
| F# | `List.choose` | nothing extra: filter-and-unwrap is one function, so there is no predicate to trust (the baseline because `choose` is the idiomatic spelling) |
| Rust | `filter_map` / `flatten` | nothing extra; `filter` cannot change the type, so the change is always a different, named adaptor |
| C++ | `views::filter` then `views::transform(deref)` | two adaptors and an unchecked `*maybe` whose safety lives in the other lambda; no `choose` in std |
| TypeScript | `filter` with an inferred predicate | one function that sometimes changes the type: only when the predicate is an iff, and a hand-written predicate is trusted without a check |

The asymmetry: F# and Rust made "refine the type" a constructor-driven operation (`Some value` is the proof), so the question never arises. TypeScript made it predicate-driven, which is the only way a structural type system can express it, and paid for that with an inference rule readers have to learn. C++ pays in a different coin: the proof and its use sit in two lambdas that can drift apart.

Left hanging: in your own pipelines, where does "this value is present" get proved, and how far away is the line that relies on it?

### The functional angle: returning the input untouched when nothing changed is free only where identity is visible

Draws on the Rust tip, with F# and C++ as rows. The shape: a transformation that usually changes nothing, and whether it can hand back the original instead of a copy.

```rust
// from_utf8_lossy(&[u8]) -> Cow<str>: Borrowed when clean, Owned when it replaced something.
// from_utf8_lossy_owned(Vec<u8>) is that Cow with the Borrowed arm turned back into your Vec.
```

```fsharp
let original = "hello world"
obj.ReferenceEquals(original.Replace("zzz", "y"), original)    // true: nothing matched, same instance
let words = [ "a"; "b" ]
obj.ReferenceEquals(List.filter (fun _ -> true) words, words)  // false: always a new list
```

| Language | Functional form | What it costs |
| --- | --- | --- |
| F# / .NET | `String.Replace` returns `this` on no match (measured); `List.filter` keeping everything still copies (measured) | sharing is free under a GC, but each function decides; the type does not tell you which you got |
| Rust | `Cow<'a, str>` | the "maybe unchanged" outcome is in the type, so the caller sees it and pays a lifetime for it |
| C++ | none in std | `std::string` copy-on-write was removed: C++11's rules for `operator[]` and invalidation forced libstdc++ off its COW string in GCC 5 (documentation, not run) |
| TypeScript | none needed for strings | strings have no observable identity, so "same instance" is not a question; arrays always copy |

The asymmetry: F# gets sharing for free from immutability and a GC, but cannot say in a type whether it happened. Rust says it in the type and makes you carry a lifetime for the borrowed arm. C++ tried implicit sharing and the standard took it away.

Left hanging: in your hot paths, which "transform" calls usually return their input unchanged, and are you paying for a copy each time anyway?

### The functional angle: lookahead is free where reading and advancing are two calls, and costs a buffer where they are one

Draws on the Rust tip. The shape: "take the prefix that matches, then hand the rest to someone else", over one single-pass source.

F# is the baseline here for a different reason than usual: its `seq` sidesteps the problem by not having a shared cursor at all, which turns out to be the most expensive answer.

```fsharp
// F#: no shared cursor; takeWhile and skipWhile each enumerate from the start.
let mutable reads = 0
let records = seq { for value in [1; 2; 3; 10; 11; 4] do reads <- reads + 1; yield value }
let small = records |> Seq.takeWhile (fun value -> value < 10) |> List.ofSeq
let rest  = records |> Seq.skipWhile (fun value -> value < 10) |> List.ofSeq
// [1; 2; 3] [10; 11; 4] reads=10   <- correct, but a 6-element source was read 10 times
```

```cpp
// C++23: *cursor reads, ++cursor advances, so stopping costs nothing...
auto stream = std::views::istream<int>(input);   // "1 2 3 10 11 4"
auto cursor = stream.begin();
for (; cursor != stream.end() && *cursor < 10; ++cursor) { /* 1 2 3 */ }
for (; cursor != stream.end(); ++cursor) { /* 10 11 4 */ }
// ...but `stream | views::take_while(...)` followed by a second range-for over
// `stream` prints "11 4": istream_view::begin() reads ahead, so re-entering drops 10.
```

```typescript
// TypeScript: next() is fused like Rust's, and there is no Peekable in the language.
function* take_while<T>(source: Iterator<T>, keep: (item: T) => boolean): Generator<T> {
    for (let step = source.next(); !step.done; step = source.next()) {
        if (!keep(step.value)) return;   // step.value is dropped here
        yield step.value;
    }
}
// small [1, 2, 3], rest [11, 4]
```

| Language | Functional form | Element 10 survives? | What it costs |
| --- | --- | --- | --- |
| F# | `Seq.takeWhile` + `Seq.skipWhile` | yes | the source is enumerated twice: 10 reads for 6 elements, and every side effect runs twice |
| Rust | `by_ref().take_while` | no | free, and wrong; the fix `Peekable::next_if` stores an `Option<Option<T>>` lookahead |
| C++ | explicit iterator loop | yes | free, because `*it` and `++it` are separate; lost again if you re-enter an `istream_view` via `begin()` |
| C++ | `views::take_while`, then re-iterate the view | no | `begin()` on a single-pass view performs a read |
| TypeScript | generator over `Iterator.next()` | no | free, and wrong; the fix is a hand-written peek buffer, std has none |

The asymmetry worth noticing: the two languages with a fused `next()` (Rust, TypeScript) need a mutable one-slot buffer to get it right, and only Rust ships that buffer. ### The functional angle: a persistent map is only as cheap as the comparator it is handed, and F# hands it the slow one for tuples

Draws on the F# tip, with Rust and C++ as the contrast. The functional data structure here is the ordered tree map: `Map` in F#, `BTreeMap` in Rust, `std::map` in C++. ## [2026-10-05.md](entries/2026-10-05.md)

### The functional angle: a stable sort is free in every language here, as long as you picked the right name, and F# hands it to you by module

Draws on the F# tip, with Rust, C++, TypeScript and Go measured on the same data: 1000 `(priority, arrival)` pairs, `priority = arrival % 3`, sorted by priority only.

A functional pipeline treats a sort as a pure function from a list to a list, and assumes the result is fully determined by the input. With equal keys, that holds only if the sort is stable. Otherwise the output depends on the algorithm, and here on whether the input has more than 16 elements. So stability is what makes `sortBy` the pure function a pipeline expects.

```rust
// Rust: the name carries the guarantee.
orders.sort_by_key(|order| order.0);          // stable  (driftsort)
orders.sort_unstable_by_key(|order| order.0); // unstable (ipnsort), measured stable=false
```

```cpp
// C++20 ranges: same split as Rust, but the unstable one has the short name.
std::ranges::sort(orders, {}, &Order::first);        // measured stable=0
std::ranges::stable_sort(orders, {}, &Order::first); // stable=1, may allocate a buffer
```

```typescript
// TypeScript: one function, required to be stable since ES2019.
const sorted = [...orders].sort((left, right) => left[0] - right[0]); // stable=true
```

| Language | Functional form | Stable at n=1000? | What it costs |
| --- | --- | --- | --- |
| F# | `List.sortBy` / `Seq.sortBy` | yes | a full copy, plus list nodes; `Array.sortBy` is the cheap one and is not stable |
| Rust | `sort_by_key` | yes | `&mut` in place, plus a scratch allocation; you have to opt in to unstable |
| C++ | `ranges::stable_sort` | yes (`ranges::sort`: no) | a temporary buffer, falling back to O(n log^2 n) if allocation fails |
| TypeScript | `Array.prototype.sort` | yes | mutates in place, so the pure form needs `[...orders]` or `toSorted` (ES2023) |
| Go | `sort.SliceStable` | yes (`sort.Slice`: no) | an index-based `less` closure that captures the slice it sorts |

The difference is in what the short name gets you. In Rust and TypeScript the short name is stable. In C++ and Go the short name is unstable, and stable costs one more word. F# is the only one where the same short name, `sortBy`, means both, and the collection module picks. It is also the only language here where the unstable choice is the one the performance refactor reaches for.

Left open: if a pure pipeline wants determinism, should it ask for stability, or for a total key like `(priority, arrival)` that makes the question disappear? Which one survives a teammate changing the key?

### The functional angle: a value that holds work is either a recipe or a receipt, and only F# lets you pick with one keyword

Draws on the F# tip (`async` against `task`), with the other three languages measured on the same question. Run the same "charge once" computation through each one's deferred value. Then ask two things: did binding it run anything, and does a second consumer run it again?

```rust

block_on(pending);               // runs, -> 1
// block_on(pending);            // error[E0382]: use of moved value: `pending`
```

```cpp
// C++23: std::async picks by launch policy, and get() is single-use.
auto hot  = std::async(std::launch::async, charge);    // has run (count 1)
auto lazy = std::async(std::launch::deferred, charge); // has not run
hot.get(); lazy.get();                                 // 1, 2
hot.get();  // valid() == false. The standard leaves this undefined.
            // libstdc++ 14 (GCC 14.2, Debian 13): throws future_error "No associated state".
            // libc++ 19 (Debian clang 19) and libc++ 22 (Apple clang 21): segfault, exit 139.
auto shared = std::async(std::launch::deferred, charge).share();
shared.get(); shared.get();                            // 3, 3: now a receipt
```

```typescript
// effect 4.0.1, Node 22.17.1.
const promise = new Promise((resolve) => resolve(++charge_count)); // ran: 1
const effect = Effect.sync(() => ++charge_count);                 // did not run
await promise; await promise;                                      // 1, 1
Effect.runSync(effect); Effect.runSync(effect);                    // 2, 3
const cached = Effect.runSync(Effect.cached(effect));
Effect.runSync(cached); Effect.runSync(cached);                    // 4, 4
```

| Language | Recipe (cold) | Receipt (hot) | Second consumer, measured | What it costs |
| --- | --- | --- | --- | --- |
| F# | `async { }` | `task { }` | async: runs again. task: same result | one keyword; same `let!` for both, so a swap does not show at the use site |
| Rust | every `Future` | none in std; `futures::FutureExt::shared` | compile error E0382 | no silent repeat; sharing needs a crate and `Clone` output |
| C++ | `launch::deferred` | `launch::async`, `.share()` | `get()` twice: throws on libstdc++, segfaults on libc++ | UB, not a type error; `shared_future` is the opt-in receipt |
| TypeScript | `Effect` | `Promise` | Effect: runs again. Promise: same result | two libraries, two vocabularies; `Effect.cached` converts |

The asymmetry worth noticing is in the Rust row. It is the only language here where "run it again" cannot happen by accident, because the type system makes the recipe single-use. The cost is that making a receipt is a deliberate act with a dependency attached. F# is the other end: both shapes are built in, and the only clue to which one you have is a word in the binding.

If a recipe that runs twice and a receipt that runs once are both correct, depending on the caller, whose job is it to say which one a function returns: its type, its name, or its docs?

### The functional angle: Rust's old range is its own cursor, so a drained range is a leftover value you can still read


```typescript
const numbers = inclusive(1, 3);           // a generator: value and cursor in one object

```

| --- | --- | --- |

Draws on the Rust tip (`let _ = payload` in a `move` closure). The question is what a closure holds when its body names a variable but does nothing with it.

## [2026-10-13.md](entries/2026-10-13.md)

### The functional angle: memoizing a thunk forces you to decide whether failure is a value, and Rust is the only one that ships both answers as separate types

Draws on the F# tip. The shape is "a thunk evaluated at most once": `lazy`, a function-local `static`, a memoized promise. It is pure only while the thunk succeeds. When it fails, the cache has to choose between remembering the failure, which makes it a referentially transparent value, and retrying, which makes it a side effect with a cache in front.

Same probe in each language: a loader that fails on the first call and succeeds on the second, accessed twice.

| Language | Memoized form | Load calls | Second access | What it costs |
| --- | --- | --- | --- | --- |
| F# | `lazy (load ())` | 1 | same exception object | permanent failure; `PublicationOnly` retries but lets threads race the factory |
| Rust | `LazyLock::new(load)` | 1 | panics (poisoned, unrecoverable) | permanent; no `into_inner` recovery on stable |
| Rust | `OnceLock::get_or_init(load)` | 2 | `"connection=prod"` | retries; the closure is passed at each call site, not once at the declaration |
| C++ | `static const auto config = load();` | 2 | `"connection=prod"` | retries; the standard requires a throwing initializer to be attempted again |
| TypeScript | `cached ??= load()` (a promise) | 1 | same rejection | permanent; retrying means clearing `cached` in a `.catch`, by hand |

The C++ row was run on Linux (GCC 14.2, Debian 13, `-std=c++20`): 2 load calls, second access `"connection=prod"`. The Rust, F# and TypeScript rows are language semantics, the same on Linux and macOS. As a separate confirmation, all five rows were run on macOS on 2026-10-13: rustc 1.95.0, Apple clang 21 `-std=c++20`, Node 22.17.1, .NET 8.0.8.

The asymmetry worth noticing is Rust's. `LazyLock` and `OnceLock` are the same machinery, and the only difference is *where the closure lives*. Bind the computation to the declaration and you get a value, which can only be poisoned. Pass it at the call site and you get a procedure, which can be tried again. F# and TypeScript give you the value form by default; C++ gives you only the procedure form, with no way to ask for a remembered failure except by catching and storing it yourself. The immutable, declaration-bound form is the one that pins a transient error forever.

The open thread: if a cached failure is the honest, pure answer, and a retry is the practical one, where should the retry policy live? Inside the cell, at the call site, or in a supervisor that throws the whole cell away?

### The functional angle: max is a fold only when its operator is associative, and NaN makes every language's default max depend on where the NaN sits

Draws on the F# tip (NaN equality) and the C++ tip (argument order deciding the answer). The functional claim "a max is `reduce max`, so order does not matter" holds only if the binary operator is associative and commutative. Under IEEE NaN, most defaults are neither. Each row below was run on the inputs `[1, NaN, 2]`, `[NaN, 1, 2]` and `[1, 2, NaN]`, on Linux (GCC 14.2, rustc 1.99.1, .NET 10.0.13, Node 22.23.4), with the same results on macOS as a separate confirmation.

```fsharp
List.max [nan; 1.0; 2.0]          // nan   (NaN wins only when it is first)
List.reduce max [1.0; nan; 2.0]   // nan   (max itself propagates NaN, either side)
```

```rust
readings.iter().copied().fold(f64::NEG_INFINITY, f64::max)  // 2 for all three orders: f64::max drops NaN
readings.iter().copied().max_by(f64::total_cmp)             // NaN for all three: total order, +NaN is largest
// readings.iter().max() does not compile: f64 is not Ord.
```

```cpp
std::ranges::max(readings);  // 2, nan, 2: < on NaN is not a strict weak order (a precondition violation)

```

```typescript
Math.max(...readings);                                          // NaN for all three
readings.reduce((best, value) => (value > best ? value : best)); // 2, NaN, 2
```

| Language | Functional form | Result on the three orders | What it costs |
| --- | --- | --- | --- |
| F# | `List.max` vs `List.reduce max` | 2, NaN, 2 vs NaN, NaN, NaN | the two "same" spellings disagree; neither is documented for NaN |

### The functional angle: taking a prefix of a lazy sequence decides who owns the rest, and four languages give four answers

Draws on the TypeScript tip (`take` closes) and the F# tip only for its baseline row. The functional claim is "`take n` is a pure prefix". That holds only when the source is a value. When the source is a stateful iterator, `take` has to decide what happens to the elements it did not take. Each row was run on a source of `1..6`, taking 2 and then reading the rest.

```fsharp
let numbers = seq { try (for step in 1 .. 6 do yield step) finally printfn "finally ran" }
numbers |> Seq.take 2 |> Seq.toList   // [1; 2], "finally ran"
numbers |> Seq.take 2 |> Seq.toList   // [1; 2] again: a seq is a recipe, every read restarts
```

```rust
let mut batches = 1..=6;
let head: Vec<i32> = batches.by_ref().take(2).collect();   // [1, 2]
let rest: Vec<i32> = batches.collect();                    // [3, 4, 5, 6]
```

```cpp
std::istringstream input{"1 2 3 4 5 6"};
auto batches = std::views::istream<int>(input);
for (int batch : batches | std::views::take(2)) {}   // 1 2
for (int batch : batches) {}                          // 4 5 6 : 3 is gone
```

```typescript
const source = read_batches();
[...source.take(2)];   // [1, 2], generator closed
[...source];           // []
```

| Language | Prefix form | Rest after taking 2 | What it costs |
| --- | --- | --- | --- |
| F# | `Seq.take 2` | the sequence restarts at 1 | the baseline here, since a `seq` is a value and the purity is real: there is no "rest" to own. Continuing needs a hand-held `IEnumerator`, and `Seq.take` disposes its own one |
| Rust | `by_ref().take(2)` | `[3, 4, 5, 6]` | opt-in: plain `take` consumes the iterator by value, so you must ask to keep it |
| C++ | `views::take(2)` over `views::istream` | `4 5 6`, element 3 lost | nothing closes, but the view reads ahead: the iterator's last `++` pulls 3 into the view's cache, and the next `begin()` reads again and overwrites it |
| TypeScript | `iterator.take(2)` | `[]` | closes by spec; lending needs a wrapper with no `return()` |

The C++ row is the one to remember: no error, no close, just one element that nobody received. That is the cost of the view caching a lookahead value it does not own.

Rust is the only row that can lend without allocating or wrapping, and it pays for that with `&mut` in the signature, which is exactly what makes the borrow visible. So which of these is the "functional" answer: F#'s restart, which is pure because it refuses to share state, or Rust's lend, which shares state and says so in the type?

What differs is what each one gives you to build it from:

| Language   | Building block                                    | Total form                                                         | What it costs                                                                       |
| ---------- | ------------------------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| F#         | `Checked.int` raises `OverflowException`          | `try Some (Checked.int amount) with :? OverflowException -> None`  | an exception on every failure, about 18 microseconds each against 0.01 for a success (measured); still no `tryInt` in FSharp.Core |
| Rust       | none: `i32::try_from(f64)` does not exist (E0277) | `is_finite()` plus a bounds check, then `then_some(scaled as i64)` | the bounds are yours to get exactly right (`< i64::MAX as f64`, not `<=`)           |
| C++        | none, and the unchecked cast is UB                | `std::optional` plus a negated `>= && <` check before the cast     | the check's form decides whether `NaN` reaches the UB                               |
| TypeScript | `Number.isSafeInteger`                            | `Math.round`, then `isSafeInteger ? scaled : undefined`            | cheapest of the four; "safe" means below 2^53, not "fits in an int32"               |

No row needs mutation: every total form is one expression over the input. F# is the only language with a primitive that refuses, and even it reports refusal through an exception, so the `Option` still comes from a wrapper.

Gotchas, all measured:

- Rust's `bool::then_some` evaluates its argument even when the condition is false; only `then(|| ...)` is lazy. The cast in `in_range.then_some(scaled as i64)` therefore always runs, which is harmless only because Rust's `as` is defined on every input. The same eager shape in C++ would run the undefined cast.
- The upper bound has to be `<`, not `<=`: `i64::MAX as f64` is exactly 2^63, one past the largest `i64`, and `9223372036854775808.0_f64 as i64` quietly saturates to `i64::MAX`. With `<=`, that input passes the check and comes back as the wrong value.
- F#'s exception-based `Option` is cheap when inputs are valid and expensive when they are not: about 0.01 microseconds per accepted value against about 18 microseconds per rejected one. A bad batch of input is roughly 1800 times slower, which matters when the bad input is what an attacker sends.
- In C++, an `std::optional<std::int64_t>` holding 0 is truthy: `if (auto cents = to_cents_checked(0.001))` takes the branch with `cents` equal to 0, because the test asks "is there a value", not "is it nonzero".
- TS `Number.isSafeInteger(-0)` is true, so `to_cents_checked(-0.004)` returns `-0` rather than `0` or `undefined`, and the `-0` from the FAQ reaches the ledger.

Should the conversion return `None`, or the reason (`NaN`, overflow, negative) it refused?

## [2026-10-20.md](entries/2026-10-20.md)

### The functional angle: grouping comes in two shapes, and only the adjacent one can stream

Draws on the Rust and F# tips; C++ and TypeScript rows added as comparisons.

"Group by" is two different functions. The **run** shape looks at neighbours and yields as it goes, but needs sorted input and can drift (Rust tip). The **bucket** shape is a real GROUP BY, but must see every element before yielding the first group (F# tip). No language here gives you both from one call.

```rust
// Run shape: lazy, zero-alloc, slice-only.
let runs = sorted_keys.chunk_by(|earlier, later| earlier == later);
// Bucket shape: std has no groupBy, so it is a HashMap fold, and the fold needs `mut`.
let buckets = keys.iter().fold(HashMap::new(), |mut buckets_so_far, key| { buckets_so_far.entry(*key).or_insert_with(Vec::new).push(*key); buckets_so_far });
```

```fsharp
// Bucket shape is the only one shipped; a run shape is a hand-written seq { } with state.
let buckets = keys |> Seq.groupBy id   // eager on first MoveNext, re-run per enumeration
```

| Language | Run shape (adjacent) | Bucket shape (hash) | What it costs |
| --- | --- | --- | --- |
| F# | not in FSharp.Core (8, 10, 11 checked) | `Seq/List/Array.groupBy` | bucket buffers all input, 16.6 MB per pass over 1M ints; `Seq` re-runs it per consumer |
| Rust | `slice::chunk_by` (1.77) | no std function | run is free but slice-only; bucket is a `HashMap` fold with a `mut` accumulator |
| C++ | `views::chunk_by` (C++23, libstdc++ 14 and libc++ 22 checked) | no std function | run is lazy and drifts the same way; bucket is a hand-rolled `unordered_map` loop |
| TypeScript | no std function | `Map.groupBy` / `Object.groupBy` (ES2024) | bucket drains the iterable (1M pulled for 3 groups, Node 26); run is hand-written |

The asymmetry worth noticing: Rust's bucket shape is the one place the immutability rule bends, because the accumulator is the data structure. F# hides the same mutation inside `groupBy`, which is why its version is a one-liner and also why it is eager.

Left hanging: if your input arrives sorted by key (a log by timestamp, a DB cursor with `ORDER BY`), which of your groupings are paying the bucket shape's memory for a run shape's problem?

### The functional angle: "add a month" is a partial function, and only C++ refuses to make it total

Draws on all four tips. The shape: `add_months: date -> int -> date option`, returning nothing when the target day does not exist, instead of clamping or overflowing.

F# is the baseline here because .NET `AddMonths` is the documented clamp the other libraries copy, so the strict version is a filter on top of it:

```fsharp
// F#
let add_months_strict (start: DateOnly) (month_count: int) : DateOnly option =
    let moved = start.AddMonths month_count
    if moved.Day = start.Day then Some moved else None // AddMonths clamped
// add_months_strict (DateOnly(2026, 1, 31)) 1 -> None; ... 2 -> Some 3/31/2026
```

Rust and `jiff` 0.2.38 are the same shape, with `?` and `then_some` doing the `Option` plumbing:

```rust
// Rust (jiff 0.2.38)
fn add_months_strict(start: Date, month_count: i32) -> Option<Date> {
    let moved = start.checked_add(month_count.months()).ok()?;
    (moved.day() == start.day()).then_some(moved) // jiff clamped
}
```

C++ needs no detection at all, because the invalid value is itself the signal:

```cpp
// C++20
std::optional<year_month_day> add_months_strict(year_month_day start, months count) {
    year_month_day moved = start + count;
    return moved.ok() ? std::optional{moved} : std::nullopt; // the invalid value is the signal
}
```

TypeScript has no immutable date, so the strict version starts with a defensive copy:

```typescript
// TypeScript
const add_months_strict = (start: Date, month_count: number): Date | undefined => {
    const moved = new Date(start.getTime());
    moved.setUTCMonth(moved.getUTCMonth() + month_count);
    return moved.getUTCDate() === start.getUTCDate() ? moved : undefined; // overflowed past month end
};
```

| Language | Built-in month add | Associative? (Jan 31: +1+1 vs +2) | What the strict form costs |
| --- | --- | --- | --- |
| F# / .NET | clamp, total | No: Mar 28 vs Mar 31 | a day comparison after the fact |
| Rust (`jiff`) | clamp, `Result` only for range | No: Mar 28 vs Mar 31 | the same comparison, plus `?` on the range error |
| C++20 | keeps Feb 31, `!ok()` | **Yes**: Mar 31 vs Mar 31 | nothing: `ok()` is the check |
| TypeScript | overflow, mutating | No: Mar 3, then Apr 3 | a copy before every add, since `setUTCMonth` mutates |

The clamp makes the function total and loses information: once Jan 31 has become Feb 28, no later step knows it was ever the 31st. C++ keeps the information by allowing a value that is not a date, which is the only reason its addition stays associative. Immutability is where TypeScript pays: it is the one language here where the strict form needs a copy, because the built-in mutates the caller's object.

Is "a date that is not a date" a type-system failure, or the honest representation of a question the caller has not answered yet?

## [2026-10-21-extra-2-of-13.md](entries/2026-10-21-extra-2-of-13.md)

### The functional angle: a schedule is a lazy infinite sequence, and `take_while` is only correct if it is sorted

Draws on the Rust tip, with the other three written against the same data. The shape: "every run before the deadline" over a lazy, possibly infinite schedule. Rust `take_while` (F# `Seq.takeWhile`, C++ `views::take_while`) is the natural fold for that, because it stops at the first run past the deadline instead of searching forever. It also silently assumes the sequence is sorted.

The Rust `cron` crate's every-30-minutes iterator across the fall-back hour yields 06:00Z, 07:00Z, 06:30Z, 07:30Z. With a 07:00Z deadline:

```rust
// Rust (cron 0.17.0, chrono-tz 0.10.4)
let schedule = cron::Schedule::from_str("0 */30 * * * *").unwrap();
let start = Chicago.with_ymd_and_hms(2026, 11, 1, 0, 50, 0).unwrap();
let deadline = Utc.with_ymd_and_hms(2026, 11, 1, 7, 0, 0).unwrap(); // 01:00 CST
let by_take_while: Vec<_> = schedule.after(&start).take_while(|run| *run < deadline).collect();
let by_filter: Vec<_> = schedule.after(&start).take(4).filter(|run| *run < deadline).collect();
println!("{} vs {}", by_take_while.len(), by_filter.len()); // 1 vs 2
```

F# is the baseline since F# `Seq.takeWhile` is the same lazy combinator in the language where laziness is idiomatic:

```fsharp
// F#
let runs = [ 6, 0; 7, 0; 6, 30; 7, 30 ] |> Seq.map (fun (hour, minute) -> DateTimeOffset(2026, 11, 1, hour, minute, 0, TimeSpan.Zero))
let deadline = DateTimeOffset(2026, 11, 1, 7, 0, 0, TimeSpan.Zero)
printfn "%d vs %d" (runs |> Seq.takeWhile (fun run -> run < deadline) |> Seq.length) (runs |> Seq.filter (fun run -> run < deadline) |> Seq.length) // 1 vs 2
```

C++20 ranges, same answer:

```cpp
// C++20
auto fn_before_deadline = [deadline](sys_time<minutes> run) { return run < deadline; };
std::cout << std::ranges::distance(runs | std::views::take_while(fn_before_deadline)) << " vs "
          << std::ranges::distance(runs | std::views::filter(fn_before_deadline)) << "\n"; // 1 vs 2
```

TypeScript has iterator helpers but no `takeWhile`, so it is a hand-written generator:

```typescript
// TypeScript
const take_while = function* <T>(source: Iterable<T>, keep: (item: T) => boolean): Generator<T> {
    for (const item of source) { if (!keep(item)) return; yield item; }
};
console.log([...take_while(runs, (run) => run < deadline)].length, runs.filter((run) => run < deadline).length); // 1 2
```

| Language | Lazy "runs before deadline" | Result on the fall-back sequence | What it costs |
| --- | --- | --- | --- |
| F# | `Seq.takeWhile` | 1 of 2 runs | nothing to write; the sortedness assumption is invisible |
| Rust | `Iterator::take_while` | 1 of 2 runs | same; `filter` needs a `take(n)` bound or it never ends |
| C++20 | `views::take_while` | 1 of 2 runs | same, plus the lambda's capture |
| TypeScript | no std `takeWhile`; a generator | 1 of 2 runs | a generator function of your own |

The four agree, which is the point: the bug is not in any combinator, it is in the sequence's contract. `filter` is correct on unsorted input but, over an infinite lazy source (Rust iterators, F# `Seq`, C++ views), never terminates; TypeScript's `Array.prototype.filter` is eager and cannot take an infinite source at all. `take_while` terminates but is only correct on sorted input. A schedule iterator that is "sorted by wall clock" is not sorted by instant across a fall-back hour, and Rust `croner` documents that it chose instant order precisely so that a forward search never goes backwards.

What would it take for a type to say "this iterator is sorted", and would you trust a library that claimed it?

## [2026-10-21-extra-3-of-13.md](entries/2026-10-21-extra-3-of-13.md)

### The functional angle: elapsed time on a wrapping counter is a pure function mod 2^32, and ordering is not

Draws on the Rust and TypeScript tips, with C++ and F# measured on the same numbers: a `u32` tick started at `2^32 - 5`, read again at `5`, 10 ms later.

Subtraction modulo 2^32 is total and exact: it never fails and always gives 10. Comparison is not a function of the two readings at all, because "is 5 after 4294967291?" depends on how many wraps happened in between, which the values do not carry. Each language below gets the subtraction right in one expression; none of them can make `<` right.

F# is the baseline here because its default arithmetic is already the unchecked modular kind, so the pure form is just `-`:

```fsharp
// F#: uint32 arithmetic is unchecked by default, so `-` is already modular
let started = UInt32.MaxValue - 4u
let now = 5u
printfn "%d" (now - started) // 10
```

Rust makes the modular intent explicit in the name, because plain `-` panics in debug builds:

```rust
// Rust: wrapping_sub is the total, profile-independent form
assert_eq!(5_u32.wrapping_sub(u32::MAX - 4), 10);
```

C++ gives the same answer for unsigned types and undefined behaviour for signed ones:

```cpp
// C++: modulo 2^32 for uint32_t, by the standard
std::uint32_t started = std::numeric_limits<std::uint32_t>::max() - 4, now = 5;
std::uint32_t elapsed = now - started;           // 10
// The same arithmetic on int32_t is UB; clang -fsanitize=signed-integer-overflow reports
// "signed integer overflow: 2147483643 + 10 cannot be represented in type 'int'"
```

TypeScript has no 32-bit type, so it opts in with an operator:

```typescript
// TypeScript: >>> 0 reinterprets the double as an unsigned 32-bit integer
const started = 2 ** 32 - 5;
const now = 5;
console.log((now - started) >>> 0); // 10; without >>> 0 it is -4294967286
```

| Language | Modular elapsed | Cost of the pure form | Ordering (`now > deadline`) |
| --- | --- | --- | --- |
| F# | `now - started` on `uint32` | none: unchecked is the default; `Checked` would throw | wrong across the wrap |
| Rust | `wrapping_sub` | a method name; plain `-` panics in debug | wrong across the wrap |
| C++ | `now - started` on `uint32_t` | none for unsigned; UB for `int32_t` | wrong across the wrap |
| TypeScript | `(now - started) >>> 0` | an operator, and only for 32 bits | wrong across the wrap |

The four agree on both halves, which says the problem is the representation, not the language. A wrapping counter is an element of a cyclic group: differences are meaningful, positions are not. The kernel's `time_after()` recovers an ordering only by assuming the two readings are less than half the cycle apart, which is a precondition no type here can state.


```ts
// TypeScript: no maxBy in the standard library; the comparison you write is the policy.
const first_max = bids.reduce((best, bid) => (bid.amount > best.amount ? bid : best))   // bob

```

### The functional angle: `add` is not invertible, so `until` is a separate function with its own answers

Draws on all four tips. If `add(date, span)` were a bijection, `until(a, b)` would be defined as the `span` with `add(a, span) == b`. It is not a bijection: Jan 28, 29, 30 and 31 all map to Feb 28 under `add(_, P1M)`. So there are four inputs for one output, and no inverse exists. Every library had to define `until` separately, and the definitions do not round-trip.

```text
// Measured, Rust jiff and TypeScript Temporal agree on every line:
// add(Jan 31, P1M)          = Feb 28
// until(Jan 31, Feb 28)     = P28D          (not P1M)
// sub(Feb 28, P1M)          = Jan 28        (not Jan 31)
// add(Feb 29 2004, P22Y)    = Feb 28 2026
// until(Feb 29 2004, Feb 28 2026).years = 21 (not 22)
```

| Language | `add` of a calendar span | `until` / difference | Round trip `add` then `until` | What it costs |
| --- | --- | --- | --- | --- |
| Rust (`jiff`) | clamps | calendar span, days by default | not identity | name the largest unit every time |
| C++ | refuses (`ok()` false) | days only, or `year_month` boundaries | nothing to round-trip | you write both directions, and pick the clamping |

### The functional angle: equality has to agree with ordering, and only Rust makes it a contract

Draws on all four tips. A sort, a dedupe and a set are three functions built on two relations, `eq` and `lt`. They only compose when "neither is less" means "equal". Rust's `Ord` documentation makes that a requirement: an `Ord` implementation must be consistent with `PartialEq`. That is why `jiff`'s `Zoned` gave up zone-aware equality.

The same strings through a plain string sort, measured in each language:

```text
// Rust Vec::sort, C++ std::ranges::sort, F# List.sort, JS Array.prototype.sort: identical result
2026-10-22T07:30:00-05:00   <- actually 12:30:00Z, the LATEST
2026-10-22T11:59:59+00:00
2026-10-22T12:00:00.5Z      <- '.' (0x2E) sorts before 'Z' (0x5A)
2026-10-22T12:00:00Z
// Sorted by instant (JS Temporal.Instant.compare): 11:59:59Z, 12:00:00Z, 12:00:00.5Z, 07:30:00-05:00
```

| Language | Type | `eq` | `lt` | Agree? | What it costs |
| --- | --- | --- | --- | --- | --- |
| Rust | `jiff::Zoned` | instant | instant | yes, required by `Ord` | zone-aware equality is a hand-written `a == b && a.time_zone() == b.time_zone()` |
| C++ | `zoned_time` | zone and instant | none | nothing to agree with | every sort needs a projection; `std::set` needs a comparator |
| F# | `DateTimeOffset` | instant | instant | yes | the offset is silently dropped by any keyed collection |
| TypeScript | `Temporal.ZonedDateTime` | `equals`: zone, calendar, instant | `compare`: instant | **no** | code must pick per call; `Set` uses references, which is a third relation |
| all four | ISO 8601 strings | bytes | bytes | yes, and both wrong | sort by a parsed key: Rust `sort_by_cached_key`, F# `List.sortBy`, C++ a projection, TS a comparator that parses twice per compare |

## [2026-10-22-extra-6-of-13.md](entries/2026-10-22-extra-6-of-13.md)

### The functional angle: converting to a coarser unit is a function with a rounding mode, and below zero the libraries disagree

Draws on the C++ and F# tips, with Rust `jiff` and JS as peer rows. `to_millis: micros -> millis` looks total and obvious. It is a choice between truncating toward zero and flooring toward negative infinity, and the two only differ for values before 1970.

```text
// -500 microseconds (1969-12-31T23:59:59.9995Z) converted to milliseconds, measured
// Rust jiff 0.2.38: Timestamp::from_microsecond(-500)?.as_millisecond()   ->  0
// C++20:            duration_cast<milliseconds>(-500us)                   ->  0
// C++20:            floor<milliseconds>(-500us)                           -> -1
// F# / .NET:        ToUnixTimeMilliseconds()                              -> -1
// JS:               Date.parse("1969-12-31T23:59:59.9995Z")               -> -1
```

| Language | Function | Rounds | What it costs |
| --- | --- | --- | --- |
| Rust | `jiff` `as_millisecond` | toward zero | a pre-1970 instant moves later, into the next millisecond |
| C++ | `duration_cast` / `floor` / `round` | toward zero / down / half-even | the only one that names all three; the default spelling is the truncating one |
| F# / .NET | `ToUnixTimeMilliseconds` | down | consistent with the calendar: 23:59:59.9995 stays in 1969 |
| TypeScript | `Date.parse` | down | the same; and `Math.trunc` vs `Math.floor` at your own call sites decides the rest |

Truncation toward zero is not monotonic in the useful sense: -0.5 ms and +0.5 ms both become 0, so two distinct instants a millisecond apart collapse into one, and the one before 1970 now sorts as if it were in 1970. Flooring keeps the order. No row needs `mut`; the asymmetry is that only C++ makes you see that a choice exists.

## [2026-10-22-extra-7-of-13.md](entries/2026-10-22-extra-7-of-13.md)

### The functional angle: a schedule is a function from "the last deadline and now" to "the next deadline", and there are exactly three of them

Draws on all four tips. Strip the APIs away and every periodic timer computes `next_deadline(previous, now, period)`. The three policies are three different pure functions:

```text
// Pseudocode for the three policies, then which API implements which (all measured above)
burst(previous, now, period)    = previous + period                                  // may be in the past
delay(previous, now, period)    = now + period                                       // forgets the grid
skip(previous, now, period)     = previous + period * (1 + floor((now - previous) / period))  // next grid point after now
```

| Language | Burst | Skip | Delay (drift) | What choosing costs |
| --- | --- | --- | --- | --- |
| Rust (`tokio`) | `MissedTickBehavior::Burst` (default) | `Skip` | `Delay` | one setter; the default is the one that floods |
| C++ | `sleep_until(next += period)` | the `while` loop in the C++ tip | `sleep_for(period)` | you write the function, and nobody reviewing sees its name |
| F# / .NET | not offered | `PeriodicTimer` | not offered | `Threading.Timer` is none of the three: it does not wait, so it overlaps |
| TypeScript | not offered | not offered | `setInterval` | anything else is hand-written from the start time |

All three are pure: only `now` comes from outside. That makes them easy to test with a fake clock and impossible to test without one, which is why the default is usually discovered in production. No row needs `mut` beyond the stored `next`. The asymmetry is that Rust names all three, and every other row offers one or none.

## [2026-10-23.md](entries/2026-10-23.md)

### The functional angle: a count each thread folds and returns needs no padding at all

Draws on the C++ tip. Padding exists because threads share mutable slots; the functional shape, where each thread
folds its own count and the results are reduced after the join, removes the sharing instead of spacing it out.

```cpp
// C++20: one future per worker, each folding into a local, reduced once at the end
std::vector<std::future<long>> partials(thread_count);
std::ranges::generate(partials, [] {
    return std::async(std::launch::async, [] {
        long hits = 0; // local to this thread: nothing to share, nothing to pad
        for (long step = 0; step < steps; ++step) { hits = hits + 1; asm volatile("" : "+r"(hits)); } // barrier stops the optimizer folding the loop
        return hits;
    });
});
const long total = std::transform_reduce(partials.begin(), partials.end(), 0L, std::plus<>{},
                                         [](std::future<long>& partial) { return partial.get(); });
```

```rust
// Rust: scoped threads, each a fold, summed on join
let total: u64 = thread::scope(|scope| {
    let workers: Vec<_> = (0..4).map(|_| scope.spawn(|| (0..STEPS).fold(0u64, |hits, _| black_box(hits + 1)))).collect();
    workers.into_iter().map(|worker| worker.join().unwrap()).sum()
});
```

```fsharp
// F#: Array.Parallel.init runs the folds, Array.sum reduces
let rec fnCountUp step hits = if step = steps then hits else fnCountUp (step + 1L) (hits + 1L)
let total = Array.Parallel.init 4 (fun _ -> fnCountUp 0L 0L) |> Array.sum
```

| Language | Functional form | Fold, 4 x 50M (Debian / macOS) | Shared adjacent slots, 4 x 50M (Debian / macOS) | What it costs |
| --- | --- | --- | --- | --- |
| F# | `Array.Parallel.init` + `Array.sum` | 14 / 13-15 ms | 721-966 / 1960-2144 ms (`Interlocked.Increment`) | nothing extra; it is the idiom, and a tail-recursive `fnCountUp` compiles to a loop |
| Rust | `thread::scope` + `fold` + `sum` | 88-89 / 97-127 ms | 1341-1361 / 383 ms (`AtomicU64`, relaxed) | a `Vec` of join handles; `black_box` per step inflates the fold here |
| C++ | `std::async` + `transform_reduce` | 14 / 25-32 ms | 425-1338 / 1505-1581 ms (8-byte spacing), 98 / 97 ms padded | a `std::future` per worker, and no fold primitive for "a thread's result" |

The numbers compare a fold with shared slots inside one language, not one language with another: each row used a
different barrier to stop the optimizer deleting the loop. Debian is Debian 13 in Docker on an M3 Pro (g++ 14.2,
rustc 1.99.1, .NET 10), and its shared-slot numbers swing widely between runs, while the fold numbers do not; macOS
is native on the same M3 Pro (Apple clang 21, rustc 1.95, .NET 8). TypeScript has no row: workers share memory only through a
`SharedArrayBuffer`, and that was not measured. The asymmetry worth noticing is mutability: the fold needs no `let mut`
in Rust or `mutable` in F#, while C++ keeps a mutable local because `std::async` hands it a lambda, not a fold, and
`ranges::fold_left` has no parallel overload.

the join. Where is the line in your services between a count you could fold and one you really must share?

## [2026-10-26.md](entries/2026-10-26.md)

### The functional angle: a derived ordering is a declaration-order decision, and only TypeScript makes you write it down

This draws on the Rust tip, with F# as the baseline row because structural comparison is the default there. The functional shape is "compare by the structure, derive the function": `compare` is not written, it falls out of the type. Each language derives it, and each one decides the order differently.

```fsharp
// F#: records compare field by field in declaration order, like Rust and C++.
type JobByPriority = { priority: int; name: string }
type JobByName = { name: string; priority: int }
type Severity = Low = 30 | Medium = 20 | High = 10 // .NET enum: by value
type Level = Low | Medium | High                    // union: by case order
// Set.minElement of the same two jobs: "zulu" vs "alpha"
// Severity.High < Severity.Low = true;  High < Low (Level) = false
```

```cpp
// C++20: a defaulted <=> is the derived ordering, lexicographic in declaration order.
struct JobByName { std::string name; int priority; auto operator<=>(const JobByName&) const = default; };
enum class Severity { Low = 30, Medium = 20, High = 10 }; // built-in < compares the values
```

```typescript
// TypeScript: nothing is derived. The comparator is the ordering, written by hand.
const byPriority = jobs.toSorted((left, right) => left.priority - right.priority || left.name.localeCompare(right.name));
[{ priority: 2 }, { priority: 1 }].toSorted(); // [2, 1]: every element is "[object Object]"
```

| Language | Derived form | `High < Low` with `Low = 30, High = 10` | What it costs |
| --- | --- | --- | --- |
| F# | structural `compare` on records and unions | `true` for an enum, `false` for a plain union (case order) | two rules in one language: the enum follows values, the union follows lines |
| Rust | `#[derive(PartialOrd, Ord)]` | `true` (discriminant value) | a field reorder or a discriminant change re-sorts everything, silently |
| C++20 | `operator<=> = default` | `true` (`enum class` compares underlying values) | same as Rust, and the default must be written per type |
| TypeScript | none | `true` (a numeric enum is a number) | the comparator is explicit, so it cannot drift, but it can be forgotten; `toSorted()` with none keeps the input order for objects |

Measured: rustc 1.99.1, g++ 16.2.0 `-std=c++20`, `dotnet fsi` on SDK 10.0.402, tsc 6.0.3 on Node 22.17.1. All three derived orderings agreed on "zulu" versus "alpha" for the reordered fields.

The derived version is the functional ideal (no code, no drift between type and function) and the explicit version is the safe one. Which of the two would you want for a type whose order is persisted on disk?

### The functional angle: you can only schedule a description, and half of these languages hand you a receipt

Draws on the F# tip (`Task.parallelLimit`), with the same question asked of Rust, C++ and TypeScript. The functional shape is "a computation as a value you can pass around before it runs". Whether a language's default async value is that, or a handle to work already in progress, decides whether a limiter, a retry or a timeout can wrap it after the fact.

```fsharp

let cold = [ for report_id in 1..6 -> async { return report_id } ]        // nothing runs yet
let hot = [ for report_id in 1..6 -> task { return report_id } ]          // all six already ran
```

```rust
// Rust: an async fn call builds an inert future; nothing runs until it is polled.
let pending: Vec<_> = (1..=6).map(work).collect();   // measured: started 0
```

```ts

const effects = job_ids.map((job_id) => Effect.promise(() => work(job_id))); // measured: started 0
await Effect.runPromise(Effect.all(effects, { concurrency: 2 }));           // peak 2, 315 ms
```

```cpp

std::async(std::launch::async, work, job_id);     // measured: 6 of 6 started before any get()
std::async(std::launch::deferred, work, job_id);  // measured: 0 of 6 started
```

| Language | Cold form (a description) | Hot form (a receipt) | Pre-started work under a limit of 2 |
| --- | --- | --- | --- |
| F# | `Async<'T>`, or a `CancellationToken -> Task<'T>` factory | `Task<'T>` | peak 6 (`Task.parallelLimit`, rewrapped tasks) |

If cold is what makes work schedulable, what is the cost of the cold default that F# and TypeScript programmers keep avoiding, and is Rust paying it somewhere you have not looked?

## [2026-10-30.md](entries/2026-10-30.md)

### The functional angle: no standard heap is FIFO for ties, so arrival order has to become part of the key, and that key is state

Draws on the F# tip, with Rust and C++ rows measured the same way and TypeScript as the sort-based contrast.

A heap is the functional programmer's favourite "pure" structure until ties appear: the dequeue order of equal keys is an artifact of the sift algorithm, and every standard library here documents it as unspecified. The only portable fix is decorate-with-sequence, the same move as the Schwartzian transform: widen the key to `(priority, arrival)`.

```rust
// Rust 1.99.1: BinaryHeap is a max-heap, so Reverse turns it into a min-heap over (priority, arrival)
use std::cmp::Reverse;
use std::collections::BinaryHeap;
let mut with_sequence = BinaryHeap::new();
for job in 0..10u64 {
    with_sequence.push(Reverse((0u8, job)));
}
// pops 0, 1, 2, ... 9
```

```cpp
// C++ (libstdc++, GCC 16.2): greater<> turns the default max-heap into a min-heap over (priority, arrival)
std::priority_queue<std::pair<int, int>, std::vector<std::pair<int, int>>, std::greater<>> with_sequence;
for (int id = 0; id < 10; ++id) with_sequence.push({0, id});
// tops 0, 1, 2, ... 9
```

The asymmetry worth leading with: the arrival number is a counter, so the "functional" fix needs mutable state somewhere. A single producer can fold an index in (`for job in 0 .. 9` above); two producers need a shared atomic or a timestamp, which is exactly the state a pure queue was supposed to avoid. F# is the baseline here only because its row costs the same as everyone else's, which says the cost belongs to the heap, not to the language.

| Language | Functional form | 10 ties, no sequence | What it costs |
| --- | --- | --- | --- |
| F# (.NET 11 rc.3) | `PriorityQueue<_, struct (int * int64)>` | 0 9 8 7 6 5 4 3 2 1 | 8 more bytes per entry and a counter you thread yourself |
| Rust 1.99.1 | `BinaryHeap<Reverse<(u8, u64)>>` | 0 2 6 9 8 5 7 4 1 3 | same counter, plus `Reverse` because std's heap is max-first |
| C++ (GCC 16.2) | `priority_queue<pair<int, int>, ..., greater<>>` | 0 2 6 9 8 5 7 4 1 3 | same counter, plus `greater<>` because the default is max-first |
| TypeScript (Node 26.12.1) | `toSorted((left, right) => left.priority - right.priority)` | 0 1 2 ... 9 | no heap in std; stable by spec since ES2019, so FIFO is free but every re-sort is O(n log n) |

Rust's `BinaryHeap` and C++'s `std::priority_queue` produced the identical scramble, which is what two textbook binary heaps with the same sift rule should do; .NET's quaternary heap produced a different one. If the order you need is "arrival", is a priority queue still the structure you want, or is it a list of FIFO queues indexed by priority?

```cpp
// C++20: check before the cast, written as acceptance; NaN fails it.

    if (!(const_horizontal_bias_double > -32769.0 && const_horizontal_bias_double < 32768.0)) return std::nullopt;
    return static_cast<std::int16_t>(const_horizontal_bias_double);  // now in range: defined
}
// 40000 -> nullopt, NaN -> nullopt, 32767.9 -> 32767, -32768.5 -> -32768
```

## [2026-11-02-extra-4-of-15.md](entries/2026-11-02-extra-4-of-15.md)

### The functional angle: an event is a value with a time, and dropping the time is what lets an old one look new

Draws on all four tips. Every mechanism above passes the reading on without the moment it was taken, so the listener cannot tell "before I was enabled" from "after". The functional fix is to carry the time, or an epoch, in the value, and filter on it.

```rust
// Rust, edition 2021 or later: tag each reading with the epoch it belongs to, and drop older epochs.
#[derive(Clone, Copy)]
struct Reading { epoch: u32, altitude_m: u32 }

fn first_touchdown_altitude_m(readings: impl Iterator<Item = Reading>, enabled_epoch: u32) -> Option<u32> {
    readings.filter(|reading| reading.epoch >= enabled_epoch).map(|reading| reading.altitude_m).next()
}
// first_touchdown_altitude_m([Reading { epoch: 0, altitude_m: 1500 }, Reading { epoch: 1, altitude_m: 0 }].into_iter(), 1) == Some(0)
```

```ts
// TypeScript: the same filter over timestamped readings.
type Reading = { taken_at_ms: number; altitude_m: number }
const const_fn_first_touchdown_altitude_m = (readings: Reading[], enabled_at_ms: number): number | undefined =>
    readings.find((reading) => reading.taken_at_ms >= enabled_at_ms)?.altitude_m
```

| Language | Keeps the early event | Drops it | What carries the time |
| --- | --- | --- | --- |
| Rust | `mpsc::channel`, `sync_channel(1)` | `sync_channel(0)` | nothing; add an epoch to the message |
| C++ | a predicate `wait` on a flag | a plain `wait` (the notify is lost) | nothing; the flag is a bool |
| F# | `MailboxProcessor` | `Event` | nothing; add it to the message type |
| TypeScript | `Promise`, `AbortSignal.aborted` | `EventEmitter`, `events.once` | nothing; resolve with a timestamped value |

F# is the baseline here because it is the one row that ships both policies in its own core library, which shows the choice is about the mechanism, not the language. In every row the fix is the same shape: a value that carries when it happened, filtered against when listening began.

The snippets in this section were run: the Rust `first_touchdown_altitude_m` returned `Some(0)` for the commented input, and the TypeScript version returned the same for the equivalent array on Node 26.13.0.

## [2026-11-02-extra-5-of-15.md](entries/2026-11-02-extra-5-of-15.md)

### The functional angle: an update that is one value replacing another has no window

Draws on all four tips. Every window above exists because the update is two steps on shared state. The functional form builds the new state as a value and publishes it in one step, so there is no moment when `in_service_count` and `in_service_switch_names` disagree.

```fsharp
// F#: an immutable record and a function that returns the next one.
type LinkStatus = { in_service_switch_names: string list; in_service_count: int }
let fn_with_call_attempt (previous_link_status: LinkStatus) (switch_name: string) : LinkStatus =
    { in_service_switch_names = switch_name :: previous_link_status.in_service_switch_names; in_service_count = previous_link_status.in_service_count + 1 }
let current_link_status = fn_with_call_attempt { in_service_switch_names = []; in_service_count = 0 } "new-york"
printfn "%A" current_link_status
```

```rust
// Rust: build the next link status as a value, then replace the shared one in one assignment under the lock.
use std::sync::{Arc, Mutex};
#[derive(Clone, Debug)]
struct LinkStatus { in_service_switch_names: Vec<String>, in_service_count: usize }
fn with_call_attempt(previous_link_status: &LinkStatus, switch_name: &str) -> LinkStatus {
    let mut mut_next_in_service_switch_names = previous_link_status.in_service_switch_names.clone(); // the copy is local until it is complete
    mut_next_in_service_switch_names.push(switch_name.to_string());
    LinkStatus { in_service_switch_names: mut_next_in_service_switch_names, in_service_count: previous_link_status.in_service_count + 1 }
}
fn main() {
    let shared_link_status = Arc::new(Mutex::new(LinkStatus { in_service_switch_names: Vec::new(), in_service_count: 0 }));
    let next_link_status = with_call_attempt(&shared_link_status.lock().unwrap(), "new-york");
    *shared_link_status.lock().unwrap() = next_link_status; // one assignment: readers see the old value or the new one
    println!("{:?}", shared_link_status.lock().unwrap());
}
```

```cpp
// C++20: publish an immutable snapshot through std::atomic<std::shared_ptr<T>>.

#include <cstdio>
#include <memory>
#include <string>
#include <vector>

std::atomic<std::shared_ptr<const LinkStatus>> shared_link_status_snapshot{std::make_shared<const LinkStatus>()};  // mutable: store() publishes into it
std::shared_ptr<const LinkStatus> with_call_attempt(const LinkStatus& const_previous_link_status, const std::string& const_switch_name) {
    LinkStatus next_link_status = const_previous_link_status;          // a private copy, invisible until published; mutable: filled in, then moved
    next_link_status.in_service_switch_names.push_back(const_switch_name);
    next_link_status.in_service_count += 1;
    return std::make_shared<const LinkStatus>(std::move(next_link_status));
}
int main() {
    shared_link_status_snapshot.store(with_call_attempt(*shared_link_status_snapshot.load(), "new-york"));  // one store: readers see old or new
    const std::shared_ptr<const LinkStatus> const_observed_link_status = shared_link_status_snapshot.load();
    std::printf("size %zu count %zu lock_free %d\n", const_observed_link_status->in_service_switch_names.size(), const_observed_link_status->in_service_count, shared_link_status_snapshot.is_lock_free());
}
```

```ts
// TypeScript: build the next state, then replace the reference once.

let current_link_status: LinkStatus = { in_service_switch_names: [], in_service_count: 0 } // mutable: replaced by one assignment below
const const_fn_with_call_attempt = (previous_link_status: LinkStatus, switch_name: string): LinkStatus =>
    ({ in_service_switch_names: [...previous_link_status.in_service_switch_names, switch_name], in_service_count: previous_link_status.in_service_count + 1 })

```

| Language | Two-step update window | Functional form, run here | What it still needs |
| --- | --- | --- | --- |
| F# | open on a shared mutable collection | an immutable record and a function returning the next one: printed as a record with `in_service_switch_names = ["new-york"]` and `in_service_count = 1` | one owner, such as a `MailboxProcessor`, that applies updates in order |
| Rust | refused at runtime by `RefCell` or `Mutex` | build the next value, then one assignment under the `Mutex`: `LinkStatus { in_service_switch_names: ["new-york"], in_service_count: 1 }` | the lock around the assignment |
| C++ | open: `recursive_mutex` admits re-entry | `std::atomic<std::shared_ptr<const T>>` store of a private copy: `size 1 count 1` on GCC 16.2 and Debian clang 19.1.7 (`is_lock_free()` 0) | a standard library that has it: libstdc++ (GCC 16.2 and Debian clang 19.1.7 default) accepted it; Debian clang 19.1.7 with `-stdlib=libc++` rejected `std::atomic<std::shared_ptr>` (error "_Atomic cannot be applied to type ... which is not trivially copyable"), as did Apple clang 21 libc++ (static assertion) |
| TypeScript | open at every `await` | spread into a new object, assign once | the assignment after the last `await`, not before it |

F# is the baseline here because its default data types are already the functional form; the window opens when F# code shares mutable state, such as a .NET collection, a `ref` cell or a captured `mutable`. All four snippets were run: F# on .NET 10.0.403, Rust on rustc 1.99.1, C++ on GCC 16.2.0 and Debian clang 19.1.7 (Docker), TypeScript on Node 26.13.0.

AT&T's report says the flaw was in all the switches and that the duplicated mate was hit during the same vulnerable period; this part infers that the mate failed the same way because it ran the same code. A pure update function shares that property: two replicas fed the same messages fail identically.

### The functional angle: a lookup is a partial function, and the default is a decision made far from the data

Draws on all four tips. A table is a function from keys to values that is undefined for some keys. Each language gives the lookup a total form (`Option`, `at()`, `tryFind`, `| undefined`), and each tip's bug is the same step: collapsing "undefined here" into a value with a default.

```fsharp
// F#: match on the option, and make "missing" a case the caller must handle.
let fn_quotient_digit_of (quotient_digit_table: Map<int * int, int>) (divisor_remainder_key: int * int) : Result<int, string> =
    match Map.tryFind divisor_remainder_key quotient_digit_table with
    | Some found_digit -> Ok found_digit
    | None -> Error (sprintf "no table entry for %A" divisor_remainder_key)
let quotient_digit_table = Map.ofList [ ((1, 12), 2) ]
printfn "%A %A" (fn_quotient_digit_of quotient_digit_table (1, 12)) (fn_quotient_digit_of quotient_digit_table (7, 12))
```

```rust

}
fn main() {
    let quotient_digit_table = HashMap::from([((1, 12), 2)]);

}
```

| --- | --- | --- | --- |

## [2026-11-02.md](entries/2026-11-02.md)

### The functional angle: an error value keeps where it was made, and an exception keeps where it was last thrown

Draws on the F# tip. The functional move is to make the failure a value. A value carries whatever it recorded when it was created, and no amount of passing it along can lose that.

```rust
// Rust, rustc 1.99.1: the trace lives in the error value, so `?` cannot drop it.
use std::backtrace::Backtrace;

struct OrderError {
    message: String,
    trace: Backtrace, // captured once, where the failure happened
}

#[inline(never)]
fn parse_order(payload: &str) -> Result<i32, OrderError> {
    Err(OrderError { message: format!("bad order {payload}"), trace: Backtrace::force_capture() })
}

fn load(payload: &str) -> Result<i32, OrderError> {
    let parsed = parse_order(payload)?; // moves the value up; the trace goes with it
    Ok(parsed)
}
// load("x").unwrap_err().trace names parse_order: true in debug and in -O.
```

```ts
// TypeScript, Node 22.17.1: an Error's stack is fixed when it is constructed.
function parse_order(payload: string): never { throw new Error("bad order " + payload) }
function load(payload: string): number {
    try { return parse_order(payload) } catch (caught) { throw caught } // stack still names parse_order
}
```

| Language | How the failure travels | Where the trace comes from | What it costs |
| --- | --- | --- | --- |
| F# | exception through `task` / `async` | the last `raise` in `task`; the saved original in `async` | `ExceptionDispatchInfo.Capture(e).Throw()` today, preview `reraise ()` in F# 11; a `Result` carries no trace unless you store one |
| Rust | `Result<T, E>` through `?` | wherever the error value captured a `Backtrace` | opt-in, one capture per error value; `?` moves it and kept the origin in debug and `-O` |
| TypeScript | thrown `Error` | the `new Error(...)` call | nothing: `throw caught` kept `parse_order` |
| C++ | `throw;` or `throw caught;` | none: `std::exception` holds no trace | C++23 `std::stacktrace::current()` captured by hand (not measured) |

### The functional angle: a delete that returns which of three things happened, instead of a `bool` or an exception that means two of them

```rust
// Rust: remove_dir's io::ErrorKind mapped to an enum.
```

## [2026-11-03-extra-13-of-15.md](entries/2026-11-03-extra-13-of-15.md)

### The functional angle: a retransmission timer is a fold over packets, and the Solaris bug is one arm that returns the initial state

Draws on all four tips. A timer that learns is a pure step function, `next_state = send_packet(state)`, folded over the packets of a connection. Paxson's description pins down the shape of the Solaris arm: on a timeout the RTO doubles, and on the acknowledgement that follows it is "restored to its erroneously small value", which the model represents as its first guess. The model below runs 10 packets over a 680 ms path with a 300 ms first guess, once with that reset and once with RFC 6298's rules: keep the backed-off timer, take no sample from a retransmitted packet (Karn), and smooth clean samples with alpha 1/8 and beta 1/4. It leaves out RFC 6298's 1-second minimum RTO and its clock-granularity term (the RFC writes `RTO <- SRTT + max (G, K*RTTVAR)` with K = 4).

```rust
// Rust: the timer folded over 10 packets.
const PATH_RTT_MS: f64 = 680.0;
const INITIAL_RTO_MS: f64 = 300.0;
#[derive(Clone, Copy, Debug)]
struct TimerState { rto_ms: f64, smoothed_rtt_ms: Option<f64>, rtt_variance_ms: f64, retransmission_count: u32 }
fn send_packet(timer_state: TimerState, resets_on_ambiguous_ack: bool) -> TimerState {
    if PATH_RTT_MS > timer_state.rto_ms {
        // the timer fires first: retransmit, double the RTO; the ack that follows is ambiguous (Karn), so no sample
        let backed_off_rto_ms = if resets_on_ambiguous_ack { INITIAL_RTO_MS } else { timer_state.rto_ms * 2.0 };
        TimerState { rto_ms: backed_off_rto_ms, retransmission_count: timer_state.retransmission_count + 1, ..timer_state }
    } else {
        // a clean sample: RFC 6298 smoothing, alpha 1/8 and beta 1/4
        let (smoothed_rtt_ms, rtt_variance_ms) = match timer_state.smoothed_rtt_ms {
            None => (PATH_RTT_MS, PATH_RTT_MS / 2.0),
            Some(previous_srtt_ms) => (0.875 * previous_srtt_ms + 0.125 * PATH_RTT_MS,
                                       0.75 * timer_state.rtt_variance_ms + 0.25 * (previous_srtt_ms - PATH_RTT_MS).abs()),
        };
        TimerState { rto_ms: smoothed_rtt_ms + 4.0 * rtt_variance_ms, smoothed_rtt_ms: Some(smoothed_rtt_ms), rtt_variance_ms, ..timer_state }
    }
}
fn main() {
    let initial_state = TimerState { rto_ms: INITIAL_RTO_MS, smoothed_rtt_ms: None, rtt_variance_ms: 0.0, retransmission_count: 0 };
    for resets_on_ambiguous_ack in [true, false] {
        let final_state = (0..10).fold(initial_state, |timer_state, _packet_index| send_packet(timer_state, resets_on_ambiguous_ack));
        println!("resets={resets_on_ambiguous_ack} retransmitted {} of 10, final RTO {:.0} ms", final_state.retransmission_count, final_state.rto_ms);
    }
}
// resets=true retransmitted 10 of 10, final RTO 300 ms
// resets=false retransmitted 2 of 10, final RTO 862 ms
```

### The functional angle: when the checks are a list, a duplicated line repeats a check instead of skipping the next one

Draws on all four tips. In goto fail, copying one line skipped every check after it. When the steps are values in a list and a fold runs them, copying an entry only runs that check twice: the signature check at the end still runs and still refuses.

### The functional angle: bind the verdict into the error channel, and "the call worked" starts to mean "it matched"

Draws on all four tips. Each language already has the operation that removes the third state: a bind that turns `Ok(false)` into an error. After it, `is_ok()`, `?`, `if (const_require_match_result)` and a failed effect all mean the same thing as "matched".

```rust
// Rust: and_then moves Ok(false) into the error channel.
#[derive(Debug)]
enum LoginError { Directory, Mismatch }
fn verify_password(stored_password_hash: &str, provided_password: &str) -> Result<bool, LoginError> {
    if stored_password_hash.is_empty() { Err(LoginError::Directory) } else { Ok(stored_password_hash == provided_password) }
}
fn require_match(stored_password_hash: &str, provided_password: &str) -> Result<(), LoginError> {
    verify_password(stored_password_hash, provided_password)
        .and_then(|password_matched| if password_matched { Ok(()) } else { Err(LoginError::Mismatch) })
}
fn main() {
    println!("{:?} {}", require_match("legacy-hash", "guess"), require_match("legacy-hash", "guess").is_ok()); // Err(Mismatch) false
}
```

```fsharp

    if stored_password_hash = "" then Error Directory else Ok (stored_password_hash = provided_password)
```

### The functional angle: head-and-rest recursion is cheap only where the rest is a view, and only F# lists give it to you without asking

Draws on the F# tip (array slices) and the Rust tip (borrowed buffers), with C++ and TypeScript as the other rows. F# is the baseline because its list is the one structure where "the rest" is shared by construction.

One shape, "sum a sequence by taking the first element and recursing on the rest", over 4,000 integers:

| Language | Functional form | Bytes allocated, n=4000 | What it costs |
| --- | --- | --- | --- |
| F# | `head :: tail` on a list | 32 | tail shared; no copy at all |

### The functional angle: a standard's constants are inputs, and an unexplained input is a hidden parameter

## [2026-11-04-extra-13-of-15.md](entries/2026-11-04-extra-13-of-15.md)

### The functional angle: a key is a function of the entropy given to it, and the type should carry that provenance

Draws on all four tips. The Heninger failure was `generate_key(state) -> (p, q)` called with a state that was the same on every device. In a pure view, the function is deterministic and the weakness is in the argument. A type that only a secure source could construct would have forced the choice at the call site:

```rust
// Rust: a seed type that cannot be built from a constant, only from the operating system
pub struct SecureSeed([u8; 32]);
impl SecureSeed {
    pub fn from_os() -> Result<SecureSeed, getrandom::Error> { let mut seed = [0u8; 32]; getrandom::fill(&mut seed)?; Ok(SecureSeed(seed)) }
}
// fn generate_rsa_key(seed: SecureSeed) -> RsaKey   // a boot-time call must handle the error, not skip it
```

This sketch was not compiled; `getrandom::fill` is the crate's documented call, which I did not check in this session. The point is the shape: failing to get entropy becomes a value the caller must handle.

| --- | --- | --- |
| Rust | take a `Result` from the OS source (sketch above) | 226 of 2,000 toy devices factored when it did not |
| C++ | call `getrandom` with `GRND_NONBLOCK` and look at the result | 32 bytes returned at once here |

## [2026-11-04-extra-2-of-15.md](entries/2026-11-04-extra-2-of-15.md)

### The functional angle: a range is a total function only if you decide what happens at the edges

Draws on all four tips. Turning a random integer into "one of n" is a function from a large domain onto a small codomain. A total version says what happens to the inputs that do not fit evenly, and the four tips show each language's default.

```rust
// Rust: make the fit an explicit, total function. Reject the tail so every residue gets equal inputs.
fn fn_unbiased_below(range_size: u32, mut mut_next_raw: impl FnMut() -> u32) -> u32 {
    let reject_from: u32 = u32::MAX - (u32::MAX % range_size); // first input that would favor low residues
    loop {
        let raw_value: u32 = mut_next_raw();
        if raw_value < reject_from {
            return raw_value % range_size;
        }
    }
}
```

| Language | Default squeeze | What the default silently does | Total form |
| --- | --- | --- | --- |
| Rust | `raw % n`, or `ratio * n` as `usize` | bias that grows with `n`; index `n` once in 2^25 draws | rejection loop, or `random_range` |
| C++ | `generate_canonical` | returns 1.0 (libc++), or clamps, or re-draws (libstdc++) | nothing portable: pick one library |
| F# | `hash % n` | negative index in about 42 percent of cases | `rem_euclid`-style fix, or `GetInt32` |
| TypeScript | `Math.round(random * (n - 1))` | end values at half probability | `Math.floor(random * n)` |

C++ is the one row where the standard itself shipped the partial function, and the fix took eight years. The rejection loop above is total only if the generator varies: with a constant generator it never returns, which is exactly what GCC 16.2 did in the C++ tip.


## [2026-11-04-extra-3-of-15.md](entries/2026-11-04-extra-3-of-15.md)

### The functional angle: a comparator is an effect, a key is a value, and only the second is a shuffle

Draws on all four tips. The ballot's bug, Rust's panic, C++'s corrupted heap and the TypeScript bias are one mistake: using a function that returns a different answer every call where the algorithm assumes a pure function. A comparator is called many times per pair. A key drawn once per element is a value, and sorting by values is correct.

## [2026-11-04-extra-4-of-15.md](entries/2026-11-04-extra-4-of-15.md)

### The functional angle: a seed is an argument, and the argument's type decides how much randomness the function can express

Draws on all four tips. A seeded generator is a function from a seed to a stream. Its image can be no larger than its domain, so a function over a 15-bit domain has at most 32,768 streams, whatever the state size. The measurements show it in each language:

```rust
// Rust: the type says how many streams exist. A u16 seed means at most 65,536 streams, however large the state.

}
```

| Rust | `u64` here, a 15-bit pid in the example | 32,768 distinct keys, measured | none; recovered in 10 ms |
| C++ | `result_type` (32 bits) | at most 2^32, by the type | two `time()` seeds, same stream |

### The functional angle: share nothing, and make the stream a value passed in

## [2026-11-04-extra-7-of-15.md](entries/2026-11-04-extra-7-of-15.md)

### The functional angle: if the generator is state, a copy of the world is a copy of the state

Draws on the F# tip and all four measurements. Fork, snapshot and checkpoint copy the world. A pure generator makes the copy explicit: `let child = parent`. An impure one makes it implicit, and the implicit copy is the hazard.

## [2026-11-04-extra-9-of-15.md](entries/2026-11-04-extra-9-of-15.md)

### The functional angle: a generator is a function from state to state, and its cycle structure is a property you can compute

Draws on all four tips. Each generator here is a pure function `state -> (value, state)`. For a pure function over a finite state space the whole behavior is the functional graph: cycles with trees leading into them. A cycle length, a number of unreachable states and a linear relation are all facts about that graph, and a short program finds them exactly.

```fsharp
// F#: the cycle length of any pure generator step function over a small state, by walking until a state repeats
let fn_cycle_length (fn_step: uint32 -> uint32) (start_state: uint32) : int =
    let seen: System.Collections.Generic.HashSet<uint32> = System.Collections.Generic.HashSet<uint32>()
    let mutable mut_state: uint32 = start_state
    while seen.Add mut_state do
        mut_state <- fn_step mut_state
    seen.Count
printfn "%d" (fn_cycle_length (fun state -> (state * 9301u + 49297u) % 233280u) 1u)
```

This sample ran and printed `233280`, the same as the TypeScript tip.

| C++ | RANDU recurrence | one linear relation, 15 planes |
| F# | ANSI C sample LCG | low k bits have period 2^k |

## [2026-11-04.md](entries/2026-11-04.md)

### The functional angle: a generic call finds its extension in a different place in each language, and F# and C++ both stop at the definition for a type you do not own

Draws on the F# tip (SRTP and extensions) and the C++ tip (binding a callable at compile time). The shape is ad-hoc polymorphism: a generic function calls `shout(value)`, and someone else supplies `shout` for a type neither of them owns.

```rust
// Rust 1.99.1: an impl is global to the crate; where it is written does not matter
fn shout_all<T: loud::Shout>(value: &T) -> String { value.shout() }
mod loud { pub trait Shout { fn shout(&self) -> String; } }
mod hidden_impls { // private, written after shout_all, never imported anywhere
    impl crate::loud::Shout for String {
        fn shout(&self) -> String { format!("{}!", self.to_uppercase()) }
    }
}
// shout_all(&String::from("hello")) -> HELLO!
```

```cpp
// C++20, GCC 16.2 and Debian clang 19.1.7: the same unqualified call, looked up twice
template <class T> std::string shout_all(const T& value) { return shout(value); }
namespace loud {
    struct Reading { double degrees; };
    std::string shout(const Reading& reading) { return std::to_string(reading.degrees) + " C!"; }
}
std::string shout(const std::string& text) { return text + "!"; } // after the template, global namespace
// shout_all(loud::Reading{21.5})     -> 21.500000 C!   (argument-dependent lookup at instantiation)
// shout_all(std::string("hello"))    -> GCC: "'shout' was not declared in this scope, and no declarations
//    were found by argument-dependent lookup at the point of instantiation"; clang: "neither visible in the
//    template definition nor found by argument-dependent lookup"
```

```fsharp
// F# 11 RC 3 with --langversion:preview: the extension must be in scope where shout is defined
type System.String with
    member text.Shout() = text.ToUpperInvariant() + "!"
let inline shout (value: ^T) = (^T : (member Shout : unit -> string) value)
// shout "hello" -> HELLO!  ; move the extension below shout, or open it only at the call: FS0001
```

| Language | Where the extension must be | What it costs |
| --- | --- | --- |
| F# 11 preview | in scope at the `inline` function's definition | measured: a call-site `open` or a later declaration gives FS0001; the helper's file must open the extension |
| Rust | anywhere in the crate (impls are global), but only your own trait or your own type (orphan rule) | measured: the impl in a private module written later worked; for a foreign trait and a foreign type you need a newtype |
| C++ | an associated namespace of the argument (found at instantiation), or declared before the template | measured: `shout(const std::string&)` in the global namespace is invisible to the template, because ADL for `std::string` searches `std` only |
| TypeScript | not expressible: types are erased, so no call is chosen by type | you pass the implementation as a value (a dictionary of functions), which is the hand-written form of what the other three do |

F# and C++ fail on the same shape for different reasons: F# records the extensions in scope when the constraint is asserted in the function body, and C++ splits the lookup in two and gives the second half only to ADL. Rust avoids the scope question altogether, and pays with the orphan rule. Which of the costs in the third column would you rather your library's users discover the hard way?
