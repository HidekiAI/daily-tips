<!-- special-nav -->

Not part of the rotation. Part 6 of the fourteen-part special on real incidents: the [Pentium floating-point divide flaw](https://www.ardent-tool.com/CPU/Intel/fdiv/white11.pdf), described in Intel's white paper of 1994-11-30. Each tip below is a lookup that finds nothing and returns a value anyway.

# What happened

**Bug class:** Bohrbug (it fails the same way every time its trigger appears) in this special's classification (inferred from the lookup mechanism: a divisor/remainder pair that hits a missing entry reads the same wrong digit every time); Intel puts the chance for random inputs at 1 in 9 billion. The anti-pattern is a generated table whose missing entries read as a valid value.

**The story, in plain words:**

Intel called the Pentium the "next generation" after the i486, and one of its goals was faster floating-point arithmetic (the way a processor handles numbers with decimal points). The i486 divided with the classic shift-and-subtract method, which produces one bit of the answer per clock tick. For the Pentium, Intel chose a method called radix-4 SRT, which produces two bits per tick and roughly doubles the speed of division.

SRT works by looking things up. At each step the chip takes the top digits of the divisor and of the remainder so far, uses them as an address in a table, and reads back a guess for the next piece of the answer: -2, -1, 0, +1 or +2. It then multiplies, subtracts, shifts and repeats.

Intel generated that table numerically, then a script copied its entries into the chip's hardware, a programmable lookup array. The table was right. The script had an error, and 5 entries went missing. A missing entry did not look missing: it read as a quotient digit of 0, where the table should have said +2.

The damage was small and strange. Only divisors that start with one of five bit patterns, followed by a long run of 1s, can hit those entries, so a division goes wrong in about 1 of every 9 billion random divides, according to Intel. When it does, the error lands far down the answer, in the worst case in the 4th significant decimal digit. Intel says it found the flaw itself, in its own testing, which by then had covered seven trillion computer cycles.

Intel put numbers on how rare that is. For a spreadsheet user doing 1,000 divides a day, its paper gives one failure in 27,000 years. Its paper concluded the flaw was of no concern to the vast majority of users, and told the few who run millions of divides a day to get an updated processor or a software workaround.

The point for the tips below: a missing entry silently became a normal-looking value. Intel's own words follow.

From "Statistical Analysis of Floating Point Flaw in the Pentium Processor (1994)", Intel Corporation, H. P. Sharangpani and M. L. Barton, November 30th 1994:

```text
The cause of the problem traces itself to a few missing entries in a lookup table
used in the hardware implementation algorithm for the divide operation.
```

```text
After the quantized P-D plot (lookup table) was numerically generated as in Figure
4-1, a script was written to download the entries into a hardware PLA (Programmable
Lookup Array). An error was made in this script that resulted in a few lookup entries
(belonging to the positive plane of the P-D plot) being omitted from the PLA. The 5
critical entries are shown in Figure 4-3 as the shaded regions. As a result of the
omission, a divisor/remainder pair that hits these entries during the lookup phase of
the SRT algorithm will incorrectly read a quotient digit value of 0 instead of +2.
```

Intel's own estimate: "1 in 9 billion randomly fed divide or remainder instructions will produce inaccurate results." The table itself was computed correctly. The step that copied it into hardware dropped five entries, and an empty slot read as a legal digit, 0, so nothing downstream could tell. The white paper is read here from a third-party mirror; Intel's own page linked it at www.intel.com/procs/support/pentium/fdiv/white11/index.htm.

## Rust: `map[&key]` panics on a missing entry, and the `unwrap_or_default()` you write to avoid the panic is the FDIV digit

*Idioms and antipatterns*

**Did you know**

`HashMap::get` returns `Option`, so a Rust table can say "not here": `get(&(7, 12))` on a table missing that entry returned `None`. Indexing with `map[&key]` refuses outright and panics with "no entry found for key". The common way to silence both is `.get(&key).copied().unwrap_or_default()`, which returned 0 for the missing entry: exactly the Pentium's quotient digit of 0 instead of +2. Measured on rustc 1.99.1.

**Show me**

```rust
// rustc 1.99.1, Debian.
use std::collections::HashMap;

fn main() {
    // A quotient-digit table generated by a script; the (7, 12) entry was dropped.
    let quotient_digit_table: HashMap<(u8, u8), i8> = HashMap::from([((1, 12), 2), ((4, 12), 2)]);
    let dropped_table_key: (u8, u8) = (7, 12);

    println!("{:?}", quotient_digit_table.get(&dropped_table_key)); // None: the table can say "not here"
    println!("{}", quotient_digit_table.get(&dropped_table_key).copied().unwrap_or_default()); // 0: the FDIV digit

    // Indexing refuses instead of inventing a value.
    let indexing_catch_result = std::panic::catch_unwind(|| quotient_digit_table[&dropped_table_key]);
    println!("{}", indexing_catch_result.is_err()); // true: panicked with "no entry found for key"
}
```

**Why it matters**

The type system did its part: `Option<&i8>` forces a decision. The defect is the decision, made in one call chained onto the lookup, where a reviewer reads it as tidy code rather than as "a missing entry means zero". A generated table should treat a missing key as a build error, not a runtime default.

**Chew on this**

Which of your lookups end in `unwrap_or_default()`, `unwrap_or(0)` or `unwrap_or("")`, and which of those tables could be missing an entry because a generator or a migration skipped it? Would your tests ever look up a key the generator dropped?

**Sources**

- https://doc.rust-lang.org/std/collections/struct.HashMap.html#method.get
- https://doc.rust-lang.org/std/collections/struct.HashMap.html#impl-Index%3C%26Q%3E-for-HashMap%3CK,+V,+S%3E

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1.

**Gotchas**

- `entry(key).or_default()` does the same as `unwrap_or_default()` and also writes it: reading the missing entry returned 0 and grew the map from 1 entry to 2, so the next `get` finds a real-looking 0.
- `catch_unwind` around the indexing is only for the demonstration; in a service, the panic from `map[&key]` would take down the handler, which for a generated table is the honest outcome.

## C++: reading a missing key with `std::map::operator[]` inserts a 0, so the dropped entry now exists and says zero

*Idioms and antipatterns*

**Did you know**

`std::map::operator[]` returns a reference to the mapped value, and when the key is absent it first inserts a value-initialized one. Reading `quotient_digit_table[{7, 12}]` from a 2-entry table returned 0 and left the table with 3 entries. `at()` throws `std::out_of_range` instead, and `contains()` (C++20) asks without inserting. Measured on Debian clang 19.1.7 and GCC 16.2 in Docker (C++20); Apple clang 21 gave the same result.

**Show me**

```cpp
// C++20, Debian clang 19.1.7 and GCC 16.2 (Docker).
#include <cstdio>
#include <map>
#include <stdexcept>
#include <utility>

int main() {
    // A quotient-digit table generated by a script; the {7, 12} entry was dropped.
    std::map<std::pair<int, int>, int> quotient_digit_table{{{1, 12}, 2}, {{4, 12}, 2}};  // mutable: operator[] below inserts into it

    std::printf("%zu\n", quotient_digit_table.size());     // 2
    const int const_dropped_entry_digit = quotient_digit_table[{7, 12}];              // a read, which inserts a value-initialized 0
    std::printf("%d %zu\n", const_dropped_entry_digit, quotient_digit_table.size());  // 0 3: the missing entry now exists, as 0

    try {
        std::printf("%d\n", quotient_digit_table.at({10, 12}));
    } catch (const std::out_of_range& const_out_of_range_failure) {
        std::printf("at() threw: %s\n", const_out_of_range_failure.what());  // libstdc++: "map::at"; libc++: "map::at:  key not found"
    }
}
```

**Why it matters**

The PLA's empty slots read as 0; `operator[]` makes the same thing happen in software and then makes it permanent, so a later audit of the table finds an entry that looks generated. Rust's `HashMap` has no inserting index operator at all, as the Rust tip showed: `map[&key]` panics instead.

**Chew on this**

How many of your `operator[]` calls on a map are reads? If each read had to be `at()`, `find()` or `contains()`, which ones would you have to decide what "missing" means for?

**Sources**

- https://en.cppreference.com/w/cpp/container/map/operator_at
- https://en.cppreference.com/w/cpp/container/map/at
- https://en.cppreference.com/w/cpp/container/map/contains

**Verified**

Compiled with `-std=c++20 -Wall -Wextra` on Debian clang 19.1.7 (`debian-clang:trixie`; libstdc++ by default, and again with `-stdlib=libc++`) and GCC 16.2.0 (`gcc:latest`), both in Docker; no warnings. The two standard libraries word the `at()` message differently, as the comment shows: libstdc++ (GCC and Debian clang default) printed `map::at`, Debian clang with `-stdlib=libc++` printed `map::at:  key not found`. Additionally checked on macOS (Apple clang 21.0.0, arm64, libc++): no warnings, same libc++ wording.

**Gotchas**

- Making the table `const` turns the accidental insert into a compile error: `operator[]` on a `const std::map` failed on GCC 16.2 with "discards qualifiers" and on Debian clang 19.1.7 with "no viable overloaded operator[]", while `contains()` compiled on both.
- Neither compiler warned about using `operator[]` for a read, with `-Wall -Wextra`.

**Related**

- [2026-09-21](2026-09-21.md) - C++, "One defaulted move constructor decides whether your type works with `map::operator[]`". The same operator's other requirement: it can only insert a type it can default-construct.

## F#: a table made with `Array2D.zeroCreate` cannot tell a dropped entry from a real 0, and an `option` table can

*Idioms and antipatterns*

**Did you know**

Filling a lookup table into `Array2D.zeroCreate<int> 16 16` leaves every cell the generator did not write as 0, which is also a legal digit: the dropped `(7, 12)` cell and a genuine zero cell both read 0. That is the PLA in F#: absence and zero share one representation. Building the table as `Array2D.create<int option> 16 16 None` instead gives `None` for the dropped cell and `Some 2` for a filled one. Measured on .NET 10.0.403.

**Show me**

```fsharp
// SDK 10.0.403 (F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14).
// A quotient-digit table generated by a script; the (7, 12) entry was dropped.
let generated_table_entries = [ (1, 12, 2); (4, 12, 2) ]

// A zero-filled table cannot tell "missing" from "the digit is 0".
let zero_filled_digit_table = Array2D.zeroCreate<int> 16 16
for (divisor_bits, remainder_bits, entry_digit) in generated_table_entries do
    zero_filled_digit_table.[divisor_bits, remainder_bits] <- entry_digit
printfn "%d %d" zero_filled_digit_table.[7, 12] zero_filled_digit_table.[0, 0]       // 0 0: dropped entry and real zero look the same

// An option table can.
let option_digit_table = Array2D.create<int option> 16 16 None
for (divisor_bits, remainder_bits, entry_digit) in generated_table_entries do
    option_digit_table.[divisor_bits, remainder_bits] <- Some entry_digit
printfn "%A %A" option_digit_table.[7, 12] option_digit_table.[1, 12]   // None Some 2
```

**Why it matters**

Dense arrays are the natural representation for a hardware-style table, and their default value is the problem: the representation has no slot for "not generated". An `option` per cell costs a check on every read, which is exactly the check the Pentium's PLA could not make. A `Map` makes the same distinction, with `Map.tryFind` returning `None`, and then `Option.defaultValue 0` throws it away again.

**Chew on this**

Which of your arrays or structs use their zero value to mean both "nothing here" and "the value is zero"? If a generator dropped one entry, which of your checks would notice?

**Sources**

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-array2dmodule.html
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-mapmodule.html#tryFind

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0` (Ubuntu 24.04, not Debian).

**Gotchas**

- `Array2D.zeroCreate<int option>` is already a table of `None`: every cell read `None`, so zero-creating an option table is safe where zero-creating an `int` table is not. The reason is that `None` is null at runtime, covered in [part 1 of the FP special](2026-10-27-extra-1-of-12.md#f-none-is-a-literal-null-at-runtime-so-nonetostring-throws-and-string-none-prints-nothing).
- `Map.find` and `dict.[key]` throw `KeyNotFoundException` on the missing key, and `Map.tryFind (7, 12) |> Option.defaultValue 0` returned 0, the same default the Rust tip measured.

- [2026-10-07](2026-10-07.md) - F#, "A `[<Struct>]` single-case union hides its constructor, and `Array.zeroCreate` still makes one with null inside". The other way a zero-filled array lies about what it holds.

## TypeScript: a `Record<string, number>` lookup of a missing key is typed `number` and is `undefined`, and `?? 0` turns it into the FDIV digit

*Idioms and antipatterns*

**Did you know**

Under `--strict`, indexing a `Record<string, number>` with a key that is not there type-checks as `number` and evaluates to `undefined`. The usual repair, `?? 0`, returns 0 for the missing entry, and plain arithmetic gives `NaN`. Only `--noUncheckedIndexedAccess`, which `--strict` does not include, types the lookup as `number | undefined` (TS2322 on assigning it to `number`). Measured on Node 26.13.0 with tsc 7.0.2.

**Show me**

```ts
// TypeScript, Node 26.13.0 (LTS, strips types natively), tsc 7.0.2 --strict.
// A quotient-digit table generated by a script; the "7,12" entry was dropped.
const const_quotient_digit_by_key: Record<string, number> = { "1,12": 2, "4,12": 2 }

const const_dropped_entry_digit: number = const_quotient_digit_by_key["7,12"] // tsc --strict: no error, the type says number
console.log(const_dropped_entry_digit)                           // undefined
console.log(const_quotient_digit_by_key["7,12"] ?? 0)     // 0: the usual "fix" is the FDIV digit
console.log(const_quotient_digit_by_key["7,12"] * 3)      // NaN
// With --noUncheckedIndexedAccess the first line is TS2322: 'number | undefined' is not assignable to 'number'.
```

**Why it matters**

The type claims every key exists, which is true of `Record<K, V>` only when `K` is a closed set; with `string` keys it is a promise nobody can keep. A generated table indexed by string is the PLA case exactly: the type says "a digit is here", the runtime says nothing is, and `?? 0` decides the answer is zero.

**Chew on this**

Is `noUncheckedIndexedAccess` on in your projects, and if you turned it on today, how many errors would you get? For each, would the fix be a real check or another `?? 0`?

**Sources**

- https://www.typescriptlang.org/tsconfig/#noUncheckedIndexedAccess
- https://www.typescriptlang.org/docs/handbook/utility-types.html#recordkeys-type

**Verified**

Run on Node 26.13.0, the current LTS (`node:lts-trixie`, Debian), and type-checked with tsc 7.0.2 with and without `--noUncheckedIndexedAccess`.

**Gotchas**

- A `Map<string, number>` does not have the hole: `map.get(key)` is typed `number | undefined` without any flag, and assigning it to `number` was TS2322.
- `const_quotient_digit_by_key["7,12"] | 0` also gave 0: every coercion to a number that does not produce `NaN` produces the FDIV digit instead.

# The functional angle: a lookup is a partial function, and the default is a decision made far from the data

Draws on all four tips. A table is a function from keys to values that is undefined for some keys. Each language gives the lookup a total form (`Option`, `at()`, `tryFind`, `| undefined`), and each tip's bug is the same step: collapsing "undefined here" into a value with a default.

```fsharp
// F#: match on the option, and make "missing" a case the caller must handle.
let fn_quotient_digit_of (quotient_digit_table: Map<int * int, int>) (divisor_remainder_key: int * int) : Result<int, string> =
    match Map.tryFind divisor_remainder_key quotient_digit_table with
    | Some found_digit -> Ok found_digit
    | None -> Error (sprintf "no table entry for %A" divisor_remainder_key)
let quotient_digit_table = Map.ofList [ ((1, 12), 2) ]
printfn "%A %A" (fn_quotient_digit_of quotient_digit_table (1, 12)) (fn_quotient_digit_of quotient_digit_table (7, 12))
```

```rust
// Rust: a missing entry is an error the caller has to handle, not a digit.
use std::collections::HashMap;
fn quotient_digit_of(quotient_digit_table: &HashMap<(u8, u8), i8>, divisor_remainder_key: (u8, u8)) -> Result<i8, String> {
    quotient_digit_table.get(&divisor_remainder_key).copied().ok_or(format!("no table entry for {divisor_remainder_key:?}"))
}
fn main() {
    let quotient_digit_table = HashMap::from([((1, 12), 2)]);
    println!("{:?} {:?}", quotient_digit_of(&quotient_digit_table, (1, 12)), quotient_digit_of(&quotient_digit_table, (7, 12)));
}
```

```cpp
// C++23: std::expected says "missing" in the type; find() never inserts.
#include <cstdio>
#include <expected>
#include <map>
#include <utility>
std::expected<int, const char*> quotient_digit_of(const std::map<std::pair<int, int>, int>& const_quotient_digit_table, const std::pair<int, int> const_divisor_remainder_key) {
    const std::map<std::pair<int, int>, int>::const_iterator const_found_entry = const_quotient_digit_table.find(const_divisor_remainder_key);
    return const_found_entry == const_quotient_digit_table.end() ? std::expected<int, const char*>(std::unexpect, "no table entry") : const_found_entry->second;
}
int main() {
    const std::map<std::pair<int, int>, int> const_quotient_digit_table{{{1, 12}, 2}};
    const std::expected<int, const char*> const_present_key_expected = quotient_digit_of(const_quotient_digit_table, {1, 12});
    const std::expected<int, const char*> const_missing_key_expected = quotient_digit_of(const_quotient_digit_table, {7, 12});
    std::printf("%d %s\n", const_present_key_expected.value(), const_missing_key_expected.has_value() ? "value" : const_missing_key_expected.error());
}
```

```ts
// TypeScript: Map.get plus an explicit check, returned as a tagged result.
type DigitResult = { ok: true; digit: number } | { ok: false; reason: string }
const const_fn_quotient_digit_of = (quotient_digit_table: Map<string, number>, table_key: string): DigitResult => {
    const const_found_digit = quotient_digit_table.get(table_key)
    return const_found_digit === undefined ? { ok: false, reason: `no table entry for ${table_key}` } : { ok: true, digit: const_found_digit }
}
const const_quotient_digit_table = new Map<string, number>([["1,12", 2]])
console.log(const_fn_quotient_digit_of(const_quotient_digit_table, "1,12"), const_fn_quotient_digit_of(const_quotient_digit_table, "7,12"))
```

Each was run: F# printed `Ok 2 Error "no table entry for (7, 12)"` (.NET 10.0.403), Rust `Ok(2) Err("no table entry for (7, 12)")` (rustc 1.99.1), C++ `2 no table entry` (GCC 16.2 and Debian clang 19.1.7, `-std=c++23`, no warnings), and TypeScript the two tagged results (Node 26.13.0, tsc 7.0.2 `--strict` clean).

| Language | Total lookup | Collapse that hides the gap | Measured |
| --- | --- | --- | --- |
| F# | `Map.tryFind`, an `option` cell | `Option.defaultValue 0` | `None` became 0 |
| Rust | `HashMap::get` returns `Option` | `.copied().unwrap_or_default()` | `None` became 0 |
| C++ | `at()`, `find()`, `contains()` | `operator[]`, which also inserts | 0, and size 2 to 3 |
| TypeScript | `Map.get`, or `--noUncheckedIndexedAccess` | `?? 0`, `| 0` | `undefined` became 0 |

F# is the baseline because its idiomatic lookup is already total and its dense-array default is the one place the gap opens. The functional fix is to keep the `Option` to the edge, where a missing entry is either a reported error or a documented choice, and never a silent 0 in the middle.

Where in your code is the line that turns "not found" into a number, and who would you ask before changing it?

# The security angle: a default that grants

Draws on the C++ and TypeScript tips, with Rust and F# as controls. Runs in both directions: every language here offers a lookup that reports absence, and every one also offers a one-call default that erases it.

```ts
// TypeScript. Looks like a permissions table. A missing role reads as level 0, and 0 is "admin".
const const_role_access_level: Record<string, number> = { auditor: 2, viewer: 3 } // lower is more privileged; admin is 0
const const_fn_can_delete = (role: string): boolean => (const_role_access_level[role] ?? 0) <= 1
console.log(const_fn_can_delete("viewer"), const_fn_can_delete("contractor")) // false true: an unknown role can delete
```

The class is [CWE-453](https://cwe.mitre.org/data/definitions/453.html), insecure default variable initialization: the value used for "not in the table" is the most privileged one there is. The sample was run on Node 26.13.0.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | a missing key typed as present, then defaulted | nothing under `--strict` alone | `noUncheckedIndexedAccess`, and a default that denies |
| C++ | `operator[]` inserts the zero value on read | `at()` and `contains()` exist | use them for reads; make tables `const` |
| Rust | `unwrap_or_default()` picks `0` | `get` returns `Option` | choose the default deliberately, or refuse |
| F# | `Option.defaultValue` after `tryFind` | `tryFind` returns `option` | the same |

TypeScript is the baseline because its index type is the only row where the compiler, in its strict mode, says the missing value is present.

Which of your lookup defaults is the most permissive value of its type?
