# Daily Tips: 2026-09-03

## Rust: select_nth_unstable is std's quickselect, and it always panics on an empty slice

*Stdlib and ecosystem gems*

**Did you know**

`slice::select_nth_unstable` (stable since 1.49.0) reorders a slice in place so
that position `index` holds the element that would be there after a full sort,
and returns a triple: the unsorted `<=` subslice, `&mut` the element itself, and
the unsorted `>=` subslice. The docs commit to *O(n)*, not just amortized: the
implementation is introselect over ipnsort with a Median of Medians (Tukey's
Ninther) fallback that "guarantees linear runtime for all inputs". So computing
p50 and p99 over a latency buffer never needs a sort, never allocates, and the
second percentile only has to search the subslice the first one handed back. The
sharp edge is in the Panics section: it panics when `index >= len()`, "and so
always panics on empty slices".

**Show me**

```rust
// Latency percentiles without sorting. Reverse-sorted input on purpose:
// that is the shape that punishes a naive quicksort.
let mut lat: Vec<u32> = (0..1000).rev().collect();

let n = lat.len();
let (p50, p99) = (n * 50 / 100, n * 99 / 100);

// First select partitions around p50 and hands back both halves.
// `greater` is a &mut subslice of `lat` already known to hold every
// element >= the median, so the p99 select searches ~50% of the data.
let (_lesser, median, greater) = lat.select_nth_unstable(p50);
let median = *median;                       // copy out; `median` borrows `lat`

// Index is relative to `greater`, and `greater` excludes the median element,
// hence the -1. Absolute position lands back on 990.
let (_, p99v, _) = greater.select_nth_unstable(p99 - p50 - 1);

println!("p50={median} p99={p99v}");        // p50=500 p99=990

// And the trap: an empty request window is not "no percentile", it is a panic.
// let empty: &mut [u32] = &mut [];
// empty.select_nth_unstable(0);            // panics: index >= len()
```

**Why it matters**

A metrics endpoint that sorts a per-interval sample buffer to answer p50/p95/p99
does *k* sorts, or one sort plus index math, where *k* selects would do. The real
bite is the other end: the empty-window case is not rare on a fresh process or a
quiet shard, and it reaches you as a panic in whatever task is serving `/metrics`
rather than as a `None`.

**Chew on this**

Where in your code do you sort a whole collection to read one position out of it,
and how many of those positions do you actually need? And when your service
reports a percentile over a window that received zero requests, what does it
currently return, and did anyone choose that?

**Sources**

- https://doc.rust-lang.org/std/primitive.slice.html#method.select_nth_unstable
- Local std source: `library/core/src/slice/mod.rs` (rustc 1.95.0), lines 3460-3520

## C++: Range-for over a temporary's subobject was a use-after-free until C++23

*Idioms and antipatterns*

**Did you know**

In a range-based `for`, the range-initializer is bound to a hidden
`auto&& __range`, and that binding lifetime-extends the temporary *only when the
initializer is the temporary itself*. Write `for (x : make_thing())` and you are
fine. Write `for (x : make_thing().items())` and, before C++23, the `Thing`
temporary was destroyed at the end of the initializer while `__range` kept a
reference into it, for every iteration of the loop. P2718R0 (wording for
P2644R1) fixed this by extending *all* temporaries in the for-range-initializer
to the end of the loop. Standard: C++23. Support: GCC 15 onward, Clang 19 onward.
MSVC status not confirmed.

**Show me**

```cpp
struct Config {
    std::vector<std::string> names{"alpha", "beta"};
    ~Config() { std::puts("Config destroyed"); }
    const std::vector<std::string>& items() const { return names; }
};
Config load() { return Config{}; }          // returns by value

int main() {
    // The for-range-initializer is `load().items()`.
    // Pre-C++23: only the final expression's result is bound to __range.
    // The Config temporary dies at the end of the init, so the vector
    // reference dangles for the whole loop. Nothing warns by default.
    for (const auto& n : load().items())
        std::printf("%s\n", n.c_str());
}
```

Measured on Apple clang 21.0.0 / libc++, `-fsanitize=address`:

| Mode | Result |
| --- | --- |
| `-std=c++20` | `ERROR: AddressSanitizer: stack-use-after-scope`, READ of size 8 in `vector::begin`, inside `'ref.tmp'` |
| `-std=c++23` | prints `alpha`, `beta`, then `Config destroyed` after the loop |

The ordering in the C++23 run is the proof: the destructor now runs *after* the
loop body, not before it.

**Why it matters**

This is the antipattern that reads correctly. `load().items()` is the obvious way
to write it, the compiler is silent, and on a small `Config` the freed stack slot
is usually still intact, so the loop produces right answers in dev and garbage
under load or under a different inlining decision. Three languages, one mistake,
three personalities: Rust rejects the equivalent at compile time (and edition
2024 moved the goalposts again on exactly which temporaries live how long), C++
compiled it silently for a decade and reads freed memory, and JS/TS cannot
express the bug at all because the GC keeps the intermediate object alive.

**Chew on this**

Grep your codebase for a range-for whose initializer contains a `.` or `->` after
a call. Which of those calls return by value? And if your build is still on
C++17 or C++20, what is currently keeping those loops correct: the standard, the
optimizer, or luck?

**Sources**

- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2718r0.html
- https://gcc.gnu.org/projects/cxx-status.html
- https://releases.llvm.org/19.1.0/tools/clang/docs/ReleaseNotes.html

**Verified**

Both modes compiled and run locally under Apple clang 21.0.0 with ASan. GCC 15
and Clang 19 versions come from the GCC C++ status page and the Clang 19 release
notes, not from a local run; no GCC on this host. MSVC support could not be
confirmed from a primary source, so it is stated as unknown rather than absent.

## TypeScript: TypeScript 7.0 stopped splitting surrogate pairs in template literal inference

*New discoveries and currently popular patterns*

**Did you know**

Until 7.0, `${infer Head}${infer Tail}` split a string literal type by UTF-16
*code unit*, so an astral-plane character came apart into its two surrogate
halves and `Head` was an unpaired surrogate: a string literal type that no
meaningful string is ever equal to. TypeScript 7.0 (GA 2026-07-08) infers by
code point instead. The release notes list it as a breaking change and name the
casualties directly: "type-level string manipulation that intentionally modeled
UTF-16 code units, such as some string `Length` utilities."

**Show me**

```ts
type Head<S> = S extends `${infer H}${string}` ? H : never;

// Measured on tsc 6.0.3, --strict:
declare const h: Head<"\u{1F600}abc">;   // U+1F600, one code point, two units
const lone: "\uD83D" = h;                // OK      <- head is the high surrogate
const whole: "\u{1F600}" = h;            // error TS2322

type Chars<S extends string, Acc extends string[] = []> =
  S extends `${infer H}${infer T}` ? Chars<T, [...Acc, H]> : Acc;
type Len<S extends string> = Chars<S>["length"];

// tsc 6.0.3:  Len<"ok"> = 2   Len<"\u{1F600}"> = 2   Len<"\u{1F600}ok"> = 4
// tsc 7.0:    the emoji counts once, per the 7.0 release notes
```

The release-notes example, stated in their terms:

```ts
type HeadTail<S> = S extends `${infer Head}${infer Tail}` ? [Head, Tail] : never;
type Result = HeadTail<"\u{1F600}abc">;
// 7.0:        ["\u{1F600}", "abc"]
// previously: ["\uD83D", "\uDE00abc"]
```

**Why it matters**

Anything that validates a shape at the type level and re-implements it at
runtime now has two possible disagreements instead of one: a `Len<S>` guarding a
fixed-width column, a branded-string type checking a prefix, a route-parameter
parser. `"x".length` in JS still counts code units, so the type level and the
runtime level have moved apart on exactly the inputs users paste in from a phone.
The compiler upgrade does not tell you which of your literal types shifted; it
just starts agreeing with `[...str]` and `for...of` instead of with `str[0]`.

**Chew on this**

Do you have any type-level string arithmetic whose runtime counterpart uses
`.length` or `.slice()`? Which of the two is the one your users' data actually
cares about, and were you ever picking, or just inheriting whichever the compiler
happened to do?

**Sources**

- https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/
- https://devblogs.microsoft.com/typescript/announcing-typescript-7-0-rc/

**Verified**

The tsc 6.0.3 numbers above were measured locally with `tsc --noEmit --strict`
on this host. The 7.0 behavior rests on the official release notes only; no TS
7.0 toolchain is installed here, so the code-point results were not executed.
