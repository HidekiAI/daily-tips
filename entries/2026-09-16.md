# Daily Tips: 2026-09-16

## Rust: A `for` loop cannot reach Chain's `fold` specialization, and pays 3x for it

*Perf and memory model*

**Did you know**

`Iterator` has two iteration protocols, not one. External iteration is `next()`,
which a `for` loop desugars to. Internal iteration is `fold` / `try_fold`, where
the iterator drives the whole traversal itself. Adapters are free to specialize
the internal one, and `Chain` does: its `next()` must ask "am I still on `a`?"
once per element, while its `fold` runs `a.fold(...)` then `b.fold(...)` with no
per-element check at all. The std docs say this outright under `for_each`: "In
some cases `for_each` may also be faster than a loop, because it will use
internal iteration on adapters like `Chain`."

**Show me**

```rust
fn external(a: &[u64], b: &[u64]) -> u64 {
    let mut acc = 0u64;                 // the `mut` is forced by the loop shape
    for x in a.iter().chain(b.iter()) { // desugars to repeated Chain::next()
        acc += *x;                      // one Option check per element, no autovec
    }
    acc
}

fn internal(a: &[u64], b: &[u64]) -> u64 {
    // dispatches to Chain::fold, which folds a, then folds b.
    // Each half is a plain slice fold, so each half autovectorizes.
    a.iter().chain(b.iter()).fold(0u64, |acc, x| acc + *x)
}

// rustc 1.95.0 -O, 2 x 4M u64, arm64: 3.46ms external vs 1.12ms internal (3.1x).
// .sum(), .for_each(), .find(), .any(), .position() all route through
// fold/try_fold, so they get the fast path too. A `for` loop with `break`
// does not: `break` is external iteration by construction.
```

**Why it matters**

Anywhere you chain two buffers and walk them (header slab plus body slab,
ring buffer wrapped at the end, two arenas of the same record type), the
idiomatic `for` loop is the slow spelling. This is also the rare case where the
immutable form wins twice: no `let mut`, and 3x the throughput.

**Chew on this**

Which of your hot loops iterate a `chain`, `flat_map`, or `zip` with a `for`
rather than a fold, and would you even notice if you flipped one? And the
uncomfortable version: if `break` forces you back onto `next()`, what does that
say about every early-exit loop you have written over an adapter?

**Sources**

- https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.for_each
- https://doc.rust-lang.org/src/core/iter/adapters/chain.rs.html
- https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.try_fold

**Verified**

Benchmarked locally on rustc 1.95.0, arm64-apple-darwin, `-O`. The 3.1x is this
machine's number; the direction is structural but the magnitude is not portable.

## C++: `std::flat_map` is two vectors, so `auto&` on its elements will not compile

*Stdlib and ecosystem gems*

**Did you know**

C++23's `std::flat_map` is not the `boost::container::flat_map` you have been
using. Boost stores one `vector<std::pair<Key, T>>`, so its iterator hands back
a real `pair&`. The standard one is a container adaptor over **two parallel
containers**, `vector<Key>` and `vector<T>`, so there is no `pair` object in
memory to take a reference to. Its `reference` type is a proxy,
`pair<const Key&, T&>`, materialized on dereference. The consequence inverts
everyone's instinct: `for (auto& [k, v] : fm)` is a compile error and
`for (auto [k, v] : fm)` mutates the map.

**Show me**

```cpp
#include <flat_map>
std::flat_map<int, double> fm{{3, 3.5}, {1, 1.5}, {2, 2.5}};

// for (auto& [k, v] : fm) { v *= 2; }
//   error: non-const lvalue reference cannot bind to a temporary
//   The "temporary" is the proxy pair<const int&, double&>.

for (auto [k, v] : fm) { v *= 2; }   // by value, and it MUTATES: v is a double&
                                     // (the pair is copied; the references are not)

fm.keys().data();                    // const vector<int>&    -- keys are contiguous
fm.values().data();                  // const vector<double>& -- separate allocation
// &keys()[1] - &keys()[0] == 4, not 16: no pair padding, because there is no pair.

auto [k, v] = std::move(fm).extract();  // steals both vectors; fm is left empty
```

**Why it matters**

Swapping `boost::container::flat_map` for `std::flat_map` looks like a header
change and is silently an AoS-to-SoA layout change. Key-only scans get denser
(no interleaved values, no pair padding), value-heavy iteration gets a second
cache stream, and any code that took `pair&` or passed `&*it` to something
expecting a real object stops compiling. Insert and erase are linear, same as
boost. Rust never grew this container because `BTreeMap` is already a
cache-friendly B-tree, and its iterator yields an honest `(&K, &V)` tuple, so
destructuring by reference just works there.

**Chew on this**

If your lookups only ever compare keys, is the SoA split a free win or does the
second stream cost you more on the values pass than the denser key scan saves?
And where else in your codebase does a proxy reference hide behind `auto&`
(`vector<bool>`, `zip_view`) waiting to fail the same way?

**Sources**

- https://en.cppreference.com/w/cpp/container/flat_map
- https://github.com/boostorg/container/blob/boost-1.88.0/include/boost/container/flat_map.hpp
- https://gcc.gnu.org/bugzilla/show_bug.cgi?id=107759

**Verified**

C++23, `__cpp_lib_flat_map` >= 202207L. Compiled and run here on Apple clang
21.0.0 with libc++ 22.1 (macro reports 202511L). libstdc++ support is GCC 15
onward per PR 107759, documentation only: no GCC on this host to confirm. MSVC
state not checked.

  about the layout you actually got.

## TypeScript: TS4104 is keyed on array types, so a readonly array launders through an index signature

*Type system deep cuts*

**Did you know**

The handbook admits the first half: "TypeScript doesn't factor in whether
properties on two types are `readonly` when checking whether those types are
compatible." Arrays look like the exception, because `readonly number[]` to
`number[]` gets its own error, TS4104. But TS4104 is a **special case keyed on
array and tuple types**, not a structural consequence. Describe the same array
with an index signature and the check is simply not reached.

**Show me**

```typescript
declare const roa: readonly number[];

type MutIdx = { length: number; [n: number]: number };
const laundered: MutIdx = roa;   // no TS4104: the target is not an array type
laundered[0] = 999;              // compiles clean under --strict

// The same erasure, three ways, all accepted:
type RoIdx = { readonly [k: string]: number };
declare const ri: RoIdx;
const m1: { [k: string]: number } = ri;        // index signature: erased
declare const d: { readonly inner: { a: number } };
d.inner.a = 5;                                 // readonly is one level deep
class C { readonly a = 1 }
const m2: { a: number } = new C();             // class field: erased too

// Only these two fire TS4104: readonly T[] -> T[], and readonly [A,B] -> [A,B].
// Runtime is a third answer again: on a frozen array the laundered write
// throws TypeError in a module (always strict) and silently no-ops in sloppy CJS.
```

**Why it matters**

A readonly-everything discipline at your API boundary is documentation, not a
guarantee: `Readonly<T>` survives exactly as long as nobody annotates the other
side. Rust puts this in the type and enforces it transitively, `&T` versus
`&mut T`, so there is no laundering move. C++ `const` is shallower than people
claim but still refuses to bind `T&` to a `const T&` source, so it catches the
direct case TypeScript waves through. TypeScript is the only one of the three
where the erasure is deliberate policy rather than a gap.

**Chew on this**

If `readonly` is unenforced on properties, what is your `Readonly<T>` actually
buying at a boundary a caller can annotate around, and would `Object.freeze`
plus a runtime check be the honest version? And for the FP angle: does a
readonly-everything codebase make you *more* likely to skip the defensive copy
that would have actually held?

**Sources**

- https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties
- https://github.com/microsoft/TypeScript/blob/main/src/compiler/diagnosticMessages.json

**Verified**

Every snippet above checked with `tsc --noEmit --strict`, tsc 6.0.3. The
laundering case produced zero errors; runtime behavior confirmed under node
22.17.1 in both `.mjs` and sloppy CJS.

**Related**

- [2026-09-15](2026-09-15.md) - TypeScript, "`void` in return position is the

# FAQ

**Which other Rust adapters specialize `fold`?** Nearly all of them:
`Chain`, `Flatten` / `FlatMap`, `Filter`, `FilterMap`, `Enumerate`, `Rev`,
`Copied` / `Cloned`, `Skip`, `Take`, `StepBy`, `Peekable`, `Scan`, `Cycle`.
`flat_map` is the biggest win after `chain`, because its `next()` carries the
inner-iterator state machine. One asymmetry worth knowing: `Zip` specializes
`fold` but not `try_fold`, so `zip.sum()` takes the fast path and
`zip.any()` does not.

**Does this apply to `async` streams?** No. `futures::Stream` has only
`poll_next`, the external protocol. `StreamExt::fold` is a combinator built on
top of `poll_next`, not a specialization hook an adapter can override.

**Is `std::flat_map` usable in a `constexpr` variable?** No, even in C++26
where its members became `constexpr`: the backing vectors allocate, so a
`constexpr flat_map` variable is still ill-formed. The `constexpr` is for use
inside constant evaluation, not for storage.

**Can I get AoS layout back from `std::flat_map`?** No. The two-container split
is in the class template's parameter list (`KeyContainer`, `MappedContainer`),
so there is no instantiation that interleaves them. If you need AoS, you need
boost or your own sorted vector.

**Does `satisfies` fix the readonly erasure?** No. `satisfies` changes which
type is inferred, not which assignability rules run. The property-modifier
erasure happens in the relation check itself.

**Is TS4104 in the compiler or in a lint?** Compiler. It is a diagnostic in
`diagnosticMessages.json`, emitted from the array and tuple assignability path,
which is precisely why an index-signature target never reaches it.

# Appendix A: which languages actually have two iteration protocols?

Not part of the tip rotation. Written 2026-09-16 to back the Rust tip, because
"internal iteration" sounds like a design-pattern word and is in fact a
concrete second set of trait methods. Snippets below were compiled on this host
where a toolchain existed (rustc 1.95.0, Apple clang 21, tsc 6.0.3); the C# and
Java lines are from documentation and are marked as such.

## A.1 What "internal" means mechanically

External iteration: the caller owns the loop and the iterator owns a cursor.
Internal iteration: the caller hands over a closure and the iterator owns the
loop. The second form is faster for composed adapters for one reason only, and
it is not inlining: the adapter can flatten its own state machine into straight
line code because nothing outside it can observe a partially advanced cursor.

```rust
// Both of these produce the same answer. Only the second lets Chain
// decide the traversal order and drop its per-element branch.
let mut n = 0;                                     // external: caller's loop
for x in a.iter().chain(b.iter()) { n += x; }
let n = a.iter().chain(b.iter()).sum::<u64>();     // internal: Chain's loop
```

## A.2 Why the name misleads a C++ reader

In C++, `std::for_each` and `std::ranges::for_each` read like internal
iteration, and they are not. Both are written as a loop over `first != last`
calling `*it` and `++it`. The algorithm owns a loop, but the *view* does not,
so a composed view's iterator still pays its per-element state check. C++23
`ranges::fold_left` is the same story: an algorithm over iterators, not a
customization point a view can specialize.

```cpp
// C++23. Reads like Rust's fold. Is not: this drives view::iterator externally,
// so join_view's inner/outer bookkeeping runs per element either way.
auto n = std::ranges::fold_left(v | std::views::join, 0, std::plus{});
```

## A.3 The mapping

| Language | External protocol | Second, specializable protocol | Adapter can flatten its own loop? |
| --- | --- | --- | --- |
| Rust | `Iterator::next` | Yes: `fold`, `try_fold`, `for_each` are trait methods with default bodies an impl may override | Yes. This is the whole point of the design |
| C++ | iterator `++` / `*` / `!=` | No. `for_each` and `fold_left` are algorithms, not customization points on the view | No. A view's iterator is the only entry point |
| C# | `IEnumerator.MoveNext` | No. LINQ operators are external; `List<T>.ForEach` is one type's method, not a protocol | No |
| Java | `Iterator.next` | Yes: `Spliterator.forEachRemaining` and the `Stream` pipeline, per the `Spliterator` docs | Yes, and this is what powers parallel streams |
| TypeScript | `Symbol.iterator` then `next()` | No. `Array.prototype.forEach` is one type's method; a generator has only `next()` | No. Every `next()` also returns a fresh `{value, done}` object |

## A.4 Back to the tip

The Rust tip is not "prefer functional style". It is that Rust shipped a second
protocol *specifically so adapters could opt out of per-element bookkeeping*,
`for` can only reach the first one, and nothing in the type signature tells you
which one you picked. Java made the same call with `Spliterator`. C++, C#, and
JavaScript did not, so in those three languages the choice does not exist and
`for_each` versus a loop is a style question. In Rust it is a codegen question.
