## Rust: `.map(f).last()` calls `f` on every element even when the iterator can run backwards

*Idioms and antipatterns*

**Did you know**

`Iterator::last` has a default body that folds forward through the whole iterator, and `Map`, `Filter` and friends do not override it, even when they implement `DoubleEndedIterator`. So `v.iter().map(f).last()` runs `f` 1,000 times on a 1,000-element slice, while `.next_back()` (or `.rev().next()`) runs it once. The bare `slice::Iter` *does* override `last` to call `next_back`, which is why the cheap case you tested once feels safe. Default clippy (0.1.95) flags none of the `.last()` calls; it only suggests `rfind` for `filter(..).next_back()`.

**Show me**

```rust
use std::cell::Cell;

fn main() {
    let calls = Cell::new(0u32);
    let v: Vec<u32> = (0..1_000).collect();

    // Default Iterator::last: a forward fold, so the closure runs n times.
    let a = v.iter().map(|x| { calls.set(calls.get() + 1); x * 2 }).last();
    println!("last()      {:?} calls={}", a, calls.get()); // Some(1998) calls=1000

    calls.set(0);
    // Map forwards next_back to the inner slice iterator: one call.
    let b = v.iter().map(|x| { calls.set(calls.get() + 1); x * 2 }).next_back();
    println!("next_back() {:?} calls={}", b, calls.get()); // Some(1998) calls=1

    calls.set(0);
    // Filter: next_back walks from the end until the predicate holds.
    let f = v.iter().filter(|x| { calls.set(calls.get() + 1); **x % 7 == 0 }).next_back();
    println!("filter      {:?} calls={}", f, calls.get()); // Some(994) calls=6
}
```

**Why it matters**

Why can't `Map` just forward `last` to `next_back`? Because `last` promises to consume the iterator, and the closure may have side effects (the counter above is one); skipping 999 calls would be observable. So the library cannot pick the fast path for you. On a request path where `f` parses, allocates or takes a lock, "get the last one" is O(n) work hiding behind a name that reads O(1). C++ makes the opposite choice: `views::transform(...).back()` on a bidirectional common range calls the function once (measured below), because a view never promised to evaluate the elements you skip.

**Chew on this**

Where in your code does `.last()` sit on an adaptor chain rather than on a bare slice or `Vec` iterator? If an iterator's laziness is supposed to be invisible, why is the number of times your closure runs part of the observable contract at all?

**Sources**

- https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.last
- https://doc.rust-lang.org/std/iter/trait.DoubleEndedIterator.html#tymethod.next_back
- core source: `library/core/src/iter/traits/iterator.rs` (default `last` via `fold`), `library/core/src/slice/iter/macros.rs` (slice override)

## C++: CTAD through an alias template rewrites the class's guides and bolts on a hidden `is_deducible` constraint

*Type system deep cuts*

**Did you know**

Since C++20 (P1814) `Vec v{1, 2}` works when `Vec` is `template<class T> using Vec = std::vector<T>`. The compiler does not deduce "through" the alias: it takes every guide of `std::vector`, rewrites each one's return type in terms of the alias's parameters, and adds a constraint that the result must actually be expressible as the alias. Clang 21 prints that constraint verbatim: `requires __is_deducible(PtrVec, vector<T *, _Allocator>)`. So an alias like `PtrVec = std::vector<T*>` *refuses* `PtrVec iv{1, 2}` instead of quietly producing `vector<int>`. Support: GCC 10, Clang 19, MSVC 19.27; Apple clang 21 accepts it under `-std=c++20` but still reports `__cpp_deduction_guides` as `201703L`, not the C++20 value `201907L`.

**Show me**

```cpp
// clang++ -std=c++20 ctad.cpp   (Apple clang 21)
#include <vector>
#include <string>
#include <type_traits>

template <class T> using PtrVec = std::vector<T*>;

template <class K, class V> struct Pair { K k; V v; };   // aggregate, no guide written
template <class V> using Named = Pair<std::string, V>;

int main() {
    int a = 1, b = 2;
    PtrVec pv{&a, &b};                       // vector's guide gives vector<int*>; T = int
    static_assert(std::is_same_v<decltype(pv), std::vector<int*>>);

    Named n{std::string("x"), 42};           // aggregate CTAD (P1816) through an alias
    static_assert(std::is_same_v<decltype(n), Pair<std::string, int>>);

    // PtrVec iv{1, 2};
    // error: no viable constructor or deduction guide for deduction of
    //        template arguments of 'PtrVec'
    // note: implicit deduction guide declared as '... requires
    //        __is_deducible(PtrVec, vector<T *, _Allocator>) ...'
}
```

**Why it matters**

An alias is now a type *filter* at the construction site, not just a spelling: a codebase-wide `template<class T> using Handle = std::shared_ptr<const T>` rejects a CTAD construction that would have produced a mutable pointee, with no guide written. Under `-std=c++17` Clang accepts the same alias CTAD as an extension with a warning, but aggregate CTAD fails outright, so a build flag decides which half of this works. Rust has no analogue: a `type` alias is purely a spelling and inference never runs "through" it with an extra check.

**Chew on this**

Which of your aliases are written as a "shorter name" but actually encode a constraint (`const`, a pointer, a fixed allocator) that CTAD will now enforce, or that a feature-test guard keyed on `__cpp_deduction_guides` would turn off on Apple clang? When a hidden constraint rejects a construction, should that error land at the alias or at the class?

**Sources**

- https://wg21.link/p1814 (CTAD for alias templates)
- https://wg21.link/p1816 (CTAD for aggregates)
- https://en.cppreference.com/w/cpp/language/class_template_argument_deduction
- https://en.cppreference.com/cpp/compiler_support/20

**Verified**

Apple clang 21 only (the `g++` on this host is the same clang); GCC 10 and MSVC 19.27 support rests on the cppreference table.

**Related**

- [2026-09-02](2026-09-02.md) - C++, "Two textually identical requires clauses are two different constraints". The `__is_deducible` constraint is one more compiler-synthesized `requires` you never wrote.

## F#: F# 11 record spreads are last-writer-wins, and a spread after an explicit field overwrites it with only a warning

*New discoveries and currently popular patterns*

**Did you know**

.NET 11 RC 1 (September 2026) made F# 11 the default and stabilized record spreads (dotnet/fsharp #18927, merged 2026-08-01): `{ ...r1; ...r2; E = 5 }` builds a record from other records' fields, for named and anonymous records alike. The composition is ordered and rightmost wins, including over an explicit field: `{ A = 0; ...r1 }` keeps `r1.A` and raises warning FS3898 ("Spread field 'A: int' shadows an explicitly declared field with the same name"), not an error. Fields the target type lacks are dropped silently: `let r2 : R2 = { ...r1 }` from a three-field `r1` typechecks.

**Show me**

```fsharp
// F# 11 (.NET 11 SDK, RC 1+). Shapes taken from the compiler's own test suite.
type R1 = { A : int; B : int }
type R2 = { C : int; D : int }
type R3 = { ...R1; ...R2; E : int }      // type spread: A; B; C; D; E

let r1 = { A = 1; B = 2 }
let r2 = { C = 3; D = 4 }
let r3 = { ...r1; ...r2; E = 5 }         // A=1 B=2 C=3 D=4 E=5

let r4 : R1 = { ...r3; B = 99 }          // C, D, E dropped without a diagnostic
let ok  = { ...r1; A = 99 }              // explicit after spread: A = 99
let bad = { A = 99; ...r1 }              // spread after explicit: A = 1, FS3898 warning

// Compare the old copy-and-update, which has one source and no ordering:
let old = { r1 with A = 99 }             // A = 99, always
```

**Why it matters**

`with` had exactly one source and every listed field won, so it could not express "later overrides earlier" and could not get it backwards. Spreads bring JavaScript's object-spread semantics, ordering hazard included, into a language whose record update never had that hazard; the difference from JS is a warning, and a warning is only as good as your `TreatWarningsAsErrors`. For a server that builds a response DTO from a domain record, silently dropping extra fields is the useful half; letting a spread quietly undo an explicit override is the half to watch.

**Chew on this**

If you adopt spreads for DTO mapping, does FS3898 get promoted to an error in your build, or does it join the warnings nobody reads? Now that two records can be merged in one expression, which of your record types would you rather keep on `with` precisely because it only takes one source?

**Sources**

- https://github.com/dotnet/core/blob/main/release-notes/11.0/preview/rc1/fsharp.md
- https://github.com/dotnet/fsharp/pull/18927
- https://github.com/dotnet/fsharp/blob/1bc322b6b82630810bed09dcc89e28109935840e/tests/FSharp.Compiler.ComponentTests/Language/RecordSpreadsTests.fs (Algebra module: FS3898 test, "Extra fields are ignored" test)
- https://github.com/fsharp/fslang-design/pull/805 (RFC)

**Verified**

Not run: this host has .NET SDK 8.0.401 (F# 8). Every behavior above is quoted from the RC 1 release notes, the PR description, and the compiler tests at commit 1bc322b.

**Related**

- [2026-09-24](2026-09-24.md) - F#, "A record expression takes the most recently declared type with those labels". Spreads are one more way a record expression's target type comes from inference rather than from you.

## TypeScript: a 16-character `slice` of a 1 MiB string keeps the whole 1 MiB alive, and a 12-character one does not

*Perf and memory model*

**Did you know**

V8 implements `slice`/`substring` of a flat string as a *SlicedString*: a pointer to the parent plus an offset and length, with no copy. V8 only does this when the result is at least 13 characters (`SlicedString::kMinLength = 13` in `src/objects/string.h`); shorter results are copied. Measured on Node 22.17.1 (V8 12.4): keeping a 16-char slice of each of 200 one-MiB strings holds heapUsed at 203.6 MiB, while a 12-char slice of the same strings holds 6.6 MiB. The type is `string` in both cases.

**Show me**

```ts
// node --expose-gc slice.mjs   (Node 22.17.1)
const mib = () => (process.memoryUsage().heapUsed / 1048576).toFixed(1);
const make = (i: number) => "x".repeat(1 << 20) + "-" + i; // fresh 1 MiB string
const kept: string[] = [];

for (let i = 0; i < 200; i++) kept.push(make(i).slice(0, 16));
(globalThis as any).gc(); console.log(mib()); // ~203.6: every parent is pinned

kept.length = 0;
for (let i = 0; i < 200; i++) kept.push(make(i).slice(0, 12));
(globalThis as any).gc(); console.log(mib()); // ~6.6: under 13 chars, V8 copies

kept.length = 0;
// Forcing a copy of a long slice: rebuild it from characters.
for (let i = 0; i < 200; i++) kept.push([...make(i).slice(0, 16)].join(""));
(globalThis as any).gc(); console.log(mib()); // ~5.6
```

**Why it matters**

The classic server shape is "read a big payload, keep a small token from it": a request ID from a log line, a key from a JSON body, a header value cached in a `Map`. Each cached slice of 13+ characters pins its whole source until the slice dies, and heap snapshots show the retention under `(sliced string)` rather than under your cache. Rust makes the same trade visible: `&big[0..16]` borrows and the borrow checker stops you from storing it past `big`, so you write `.to_owned()`; C++ `std::string_view` has Rust's representation with none of the enforcement; Go's substrings share the backing array exactly like V8's, with `strings.Clone` (Go 1.20+) as the explicit copy.

**Chew on this**

Which long-lived `Map` or LRU in your services is keyed or valued by a string that was sliced out of a request body? The 13-character threshold is an engine constant, not a language rule, so what would you want to measure before relying on any copy idiom to stay a copy in the next V8?

**Sources**

- https://github.com/v8/v8/blob/main/src/objects/string.h (`SlicedString::kMinLength = 13`)
- https://nodejs.org/api/process.html#processmemoryusage
- https://pkg.go.dev/strings#Clone

**Verified**

Node 22.17.1 / V8 12.4.254.21, run as plain `.mjs` (the snippet above is the same code with type annotations). The `[...s].join("")` copy is an observed behavior of this V8, not a documented guarantee.

**Related**

- [2026-09-02](2026-09-02.md) - TypeScript, "A 16-byte Buffer.allocUnsafe pins 8 KiB". Same retention shape, one layer down: a small view keeps a large backing store alive.

# The functional angle: "give me the last one" is O(1) only where the language never promised to run the skipped elements

Draws on the Rust tip, with a measured row from each other language. Same problem everywhere: map a 1,000-element array with a counting function, take the last result.

```rust
v.iter().map(f).last()        // 1000 calls: last() is a consuming fold
v.iter().map(f).next_back()   // 1 call
```

```cpp
auto t = v | std::views::transform(f);
t.back();                     // 1 call: a view evaluates on access, never on skip
```

```fsharp
arr |> Seq.map f |> Seq.last      // 1000 calls
arr |> Array.map f |> Array.last  // 1000 calls: eager, and it allocates the whole result
```

```ts
v.map(f).at(-1)                          // 1000 calls: Array.prototype.map is eager
for (const x of v.values().map(f)) {}    // 1000 calls: iterator helpers have no last/back
```

| Language | Functional form | Calls, n=1000 | What it costs |
| --- | --- | --- | --- |
| F# | `Seq.map >> Seq.last` | 1000 | the baseline here since `Seq` is the lazy default; laziness buys nothing when the consumer walks forward |
| Rust | `map(..).last()` / `.next_back()` | 1000 / 1 | the O(1) path exists but you must name it; the default is the fold |
| C++ | `views::transform(..).back()` | 1 | free, because views never promised side effects on skipped elements |
| TypeScript | `map(..).at(-1)` | 1000 | no lazy backwards path at all; eager `map` also allocates n results |

The asymmetry worth noticing: C++ gets O(1) *because* its view is allowed to skip your function, and Rust cannot *because* its `last` is not. Neither needs `mut` to express the fast version; the cost is entirely in what the consumer is allowed to skip.

Left hanging: if a function you pass to `map` should be pure, should a language be allowed to call it fewer times than you wrote, and would you notice if it did?

# The security angle: in both F# 11 and TypeScript, putting the spread last can quietly undo a revocation

Draws on the F# tip (Mode B: record spreads are convenient, but are they *secure*?), with TypeScript as the comparison. Direction: the languages partly prevent it, and the part they do not prevent is where it goes wrong.

The insecure sample looks like a style choice, "defaults first, then the incoming object":

```fsharp
// F# 11: meant to revoke. The spread comes last, so session.Status wins.
let revoked = { Status = Revoked; ...session }   // warning FS3898, still compiles
```

```ts
type Session = { user: string; status: "active" | "revoked" };
type Loose   = { user: string; status?: "active" | "revoked" };

const a = { status: "revoked" as const, ...s };   // s: Session -> error TS2783
const b = { status: "revoked" as const, ...l };   // l: Loose   -> no diagnostic
const c = { status: "revoked" as const, ...r };   // r: Record<string,string> -> no diagnostic
```

Measured on tsc 6.0.3 `--strict`: only `a` errors (TS2783, "'status' is specified more than once, so this usage will be overwritten"). Once the spread source's field is optional, or comes from an index signature, as it does after a loose `JSON.parse` or a partial-update DTO, the check has nothing to prove and stays silent. At runtime every one of them keeps whatever `status` the source carried.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| F# 11 | explicit field before a spread is overwritten | warning FS3898 on every such case | make FS3898 an error; put overrides after spreads |
| TypeScript | property before a spread is overwritten | error TS2783, but only when the spread's property is required | optional and index-signature sources get no check; order overrides last |
| Rust | n/a: struct update `..base` must come last and fills only unnamed fields | the ordering hazard cannot be written | nothing for ordering; `..base` still copies every field you forgot to name |
| C++ | n/a: designated initializers have no spread | no hazard, no feature | the hand-written copy is where you forget a field |

Rust is the control for this class: `S { status: Revoked, ..session }` is the only legal order, so the explicit field always wins. The failure class is CWE-863 (Incorrect Authorization) when the field gates access: a revocation that compiles, passes a happy-path test that starts from an already-revoked session, and never takes effect.

Left hanging: in your update paths, is the incoming object spread before or after the fields you mean to force, and what type does that incoming object have by the time it reaches the spread?

Sources: https://cwe.mitre.org/data/definitions/863.html , https://github.com/dotnet/fsharp/pull/18927 , https://github.com/microsoft/TypeScript/issues/37559 (TS2783, shipped in 3.9).
