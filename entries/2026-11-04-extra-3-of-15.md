# Daily Tips special, part 3 of 15: random numbers, or a shuffle that was never a shuffle

<!-- special-nav -->
**Specials:** [<- previous: random numbers, part 2 of 15](2026-11-04-extra-2-of-15.md) | [next: random numbers, part 4 of 15 ->](2026-11-04-extra-4-of-15.md)

Not part of the rotation. Part 2 squeezed one random number into a range. This part shuffles a whole list, which looks like a one-liner in every language and is where two famous bugs lived: a sort with a random comparator, and a swap loop that picks its partner from the wrong range. Both produce output that looks shuffled. Neither is uniform.

# What happened

**Bug class:** a plausible algorithm that is not a uniform shuffle, found only by counting (a Bohrbug with a statistical signature, invisible to any single run).

**The story, in plain words:**

In early 2010 Microsoft shipped a "browser ballot" for Windows users in Europe: a screen that offered five web browsers, as a concession to the European Union. The screen was supposed to put the browsers in a random order each time, so that no browser got the best spot. The order was decided by a few lines of JavaScript on the page.

A Slovak technology site, DSL.sk, tried it and noticed something odd: the order was not random. Rob Weir then copied the page's function into a test file and ran it 10,000 times in Internet Explorer. He found that Internet Explorer itself landed in the last position 5,034 times out of 10,000, about half the time. Chrome landed third 3,679 times, over a third. The browser the screen was supposed to treat evenly was being pushed to the end, and nobody had meant it to be.

The cause was one line. To shuffle five browsers the page sorted them with a comparator that ignores its arguments: `function RandomSort (a,b) { return (0.5 - Math.random()); }`. A sort assumes that if a is before b then b is after a, and that the answers agree with each other. A comparator that flips a coin on every call breaks both, so what the sort algorithm does with the answers depends on the algorithm, not on chance. Weir called it "a rookie mistake in the code, but it is an interesting mistake that we can learn from". By 6 March Weir added a note that Microsoft appeared to have updated the page and corrected the error.

The quotes, from Rob Weir, "Doing the Microsoft Shuffle: Algorithm Fail in Browser Ballot" (An Antic Disposition, 27 February 2010):

- "It was a Microsoft concession to the EU, to provide a randomized ballot screen for users to select a browser."
- "Internet Explorer showed up 50% of the time in the last position."
- "In the end it is a rookie mistake in the code, but it is an interesting mistake that we can learn from, so I'll examine it in some depth."
- "Microsoft used none of these well-known solutions in their random solution. Instead they fell for the well-known trap."
- "Sorting requires a self-consistent definition of ordering."

Appendix A shows the other classic, from a study that broke a real online poker shuffle. Appendix B is a lottery that was not mixed enough.

## Rust: `sort_by` with a random `Ordering` compiles, does not panic up to 20 items and is biased at 5, and panics from 21

*Stdlib and ecosystem gems*

**Did you know**

On rustc 1.99.1, `items.sort_by(|_, _| random Less or Greater)` is a legal program. For five items over a million runs, item 0 ended in position 0 about 30.7 percent of the time and in position 4 about 6.3 percent, not 20 percent each. At 20 items nothing panicked in 200 runs. At 21 items 196 of 200 runs panicked with "user-provided comparison function does not correctly implement a total order", and the cliff between 20 and 21 suggests the sort uses a different algorithm above 20 elements, one that checks (I did not read the source to confirm).

**Show me**

```rust
// rustc 1.99.1, std only: a random comparator, counted
use std::cmp::Ordering;
use std::panic;

struct XorShift64 {
    state: u64,
}
impl XorShift64 {
    fn next_u64(&mut self) -> u64 {
        self.state ^= self.state << 13;
        self.state ^= self.state >> 7;
        self.state ^= self.state << 17;
        self.state
    }
}

fn main() {
    panic::set_hook(Box::new(|_| {})); // keep the output to one line per size
    let mut mut_rng = XorShift64 { state: 0x9E3779B97F4A7C15 };
    for item_count in [20usize, 21] {
        let mut mut_panic_count: u32 = 0;
        for _ in 0..200 {
            let mut mut_items: Vec<usize> = (0..item_count).collect();
            let sort_attempt_result = panic::catch_unwind(panic::AssertUnwindSafe(|| {
                mut_items.sort_by(|_, _| if mut_rng.next_u64() & 1 == 0 { Ordering::Less } else { Ordering::Greater });
            }));
            if sort_attempt_result.is_err() {
                mut_panic_count += 1;
            }
        }
        println!("{} items: {} of 200 runs panicked", item_count, mut_panic_count);
    }

    let mut mut_position_counts: [u32; 5] = [0; 5];
    for _ in 0..1_000_000 {
        let mut mut_items: Vec<usize> = (0..5).collect();
        mut_items.sort_by(|_, _| if mut_rng.next_u64() & 1 == 0 { Ordering::Less } else { Ordering::Greater });
        mut_position_counts[mut_items.iter().position(|&item| item == 0).unwrap()] += 1;
    }
    println!("item 0 final position counts (sort_by shuffle): {:?}", mut_position_counts);
}
```

Output: `20 items: 0 of 200 runs panicked`, `21 items: 196 of 200 runs panicked` (the exact number varies with the generator), and `item 0 final position counts (sort_by shuffle): [307306, 307772, 204804, 117341, 62777]`. A bad comparator is detected, but only on the code path that can detect it.

**Why it matters**

A test with ten items passes forever, and the same code panics in production at 21. The tip is not that the panic exists, it is the cliff: a shuffle written this way is biased from the first element and loud only past 20. `slice::shuffle` from the `rand` crate is the intended tool, and a sort by a random key drawn once per element is correct (see the functional angle).

**Chew on this**

Does your test data ever exceed 20 elements? If a sort of 21 panics and a sort of 20 does not, which of them tested your comparator?

**Sources**

- https://doc.rust-lang.org/std/primitive.slice.html#method.sort_by (the documented total-order requirement and panic)
- https://docs.rs/rand/latest/rand/seq/trait.SliceRandom.html

**Verified**

Measured on rustc 1.99.1, std only, release build. The 20/21 boundary was bracketed with sizes 20, 21, 24, 32, 33, 40, 64, 65 and 100: 0 of 200 panicked at 20, 196 to 200 at 21 and above. Why the algorithm changes at 21 I did not trace in the source.

**Gotchas**

- The panic message is only promised as "may panic" in the documentation; the bias, not the panic, is the dependable part.
- `sort_by_cached_key` with a random key gave `[199907, 199936, 200193, 200361, 199603]` over a million runs: uniform, because each key is drawn once.

## C++: `std::sort` with a coin-flip comparator is undefined behavior, and GCC 16.2 aborted with "double free or corruption" while libc++ returned a biased order

*Stdlib and ecosystem gems*

**Did you know**

`std::sort` requires a strict weak ordering, and a comparator that returns `engine() & 1` violates it, which is undefined behavior. On GCC 16.2 (libstdc++), sorting five items a million times with such a comparator aborted the process with `double free or corruption (out)`, exit status 134: the allocator detected heap corruption (I did not trace which libstdc++ function caused it). On clang 19.1.7 with libc++ the same program finished and gave a biased order, item 0 landing first 30.7 percent of the time. And `std::shuffle(items, mt19937(42))` of ten items gave `1 6 7 0 5 9 8 2 3 4` on libstdc++ (GCC 16.2 and the 14.2 that ships with clang) and `6 4 0 9 2 3 1 5 7 8` on libc++, which is part 1's point again.

**Show me**

```cpp
// g++ -std=c++23 -O2 sortshuf.cpp        (GCC 16.2)
// clang++ -std=c++23 -stdlib=libc++ -O2 sortshuf.cpp   (clang 19.1.7)
#include <algorithm>
#include <array>
#include <cstdio>
#include <numeric>
#include <random>
#include <vector>

int main() {
    std::vector<int> shuffled(10);
    std::iota(shuffled.begin(), shuffled.end(), 0);
    std::mt19937 shuffle_engine(42);
    std::shuffle(shuffled.begin(), shuffled.end(), shuffle_engine);
    for (int item : shuffled) std::fprintf(stderr, "%d ", item);
    std::fprintf(stderr, "\n");

    std::mt19937 engine(42);
    std::array<int, 5> position_counts{};
    for (int run = 0; run < 1000000; ++run) {
        std::vector<int> items(5);
        std::iota(items.begin(), items.end(), 0);
        std::sort(items.begin(), items.end(), [&](int, int) { return (engine() & 1u) == 0; }); // undefined behavior
        position_counts[std::find(items.begin(), items.end(), 0) - items.begin()]++;
    }
    for (int count : position_counts) std::fprintf(stderr, "%d ", count);
    std::fprintf(stderr, "\n");
}
```

Measured: GCC 16.2 printed the shuffle line and then `double free or corruption (out)` and aborted. libc++ printed `6 4 0 9 2 3 1 5 7 8` then `307062 226299 216985 155809 93845`. Sorting 100, 1000 and 100000 items with the same comparator, in a variant that takes the item count from the command line, returned normally on both: the crash is not triggered by size.

**Why it matters**

Undefined behavior means the failure is not a property of the comparator but of the library, the input size and the optimizer. A corrupted heap that appears only on one standard library, with five elements and a million repetitions, is exactly the kind of failure that survives review. The browser ballot got off lightly: a wrong order. In C++ the same line can write outside your vector. (`std::random_shuffle`, the older shuffle, was removed in C++17, per the standard draft: not run here.)

**Chew on this**

How many comparators in your code have been checked for strict weak ordering, as opposed to checked for "returns a bool"? Would a bad one fail on your platform, or only on the one you ship to?

**Sources**

- https://eel.is/c++draft/alg.sorting#alg.sorting.general (the strict weak ordering requirement)
- https://eel.is/c++draft/alg.random.shuffle

**Verified**

GCC 16.2.0 and clang 19.1.7 with libc++, `-O2`. The shuffle line was also run on clang with libstdc++ 14.2 and matched GCC. The standard citations are from the draft; the crash message is verbatim from the run, and I did not investigate which libstdc++ function wrote out of bounds.

**Gotchas**

- Output goes to stderr in the probe because stdout is block-buffered when piped and the abort would lose it.
- The same comparator did not crash at 100, 1000 or 100000 items. Do not read that as safe.

## F#: the poker shuffle, "swap each position with any position", turns 3 cards into 27 equally likely paths over 6 orderings, so some orderings come up 5 times in 27 and some 4

*Idioms and antipatterns*

**Did you know**

The shuffle in Appendix A swaps every position with a random position anywhere in the deck. For three cards that is 3 x 3 x 3 = 27 equally likely paths, and 27 does not divide evenly into 6 orderings. Exact enumeration in F# on .NET 10 gave `123: 4, 132: 5, 213: 5, 231: 5, 312: 4, 321: 4`. Fisher-Yates, which swaps position i with a position from i to the end, has 3 x 2 x 1 = 6 paths and gives each ordering exactly once. For 52 cards the gap is 52^52 paths over 52! orderings, and it can never be even.

**Show me**

```fsharp
// .NET 10.0.14, dotnet fsi: exact enumeration, no randomness involved
let card_count: int = 3
let fn_apply_swaps (swap_targets: int list) : string =
    let deck: int[] = Array.init card_count (fun position -> position + 1)
    swap_targets |> List.iteri (fun position target ->
        let held_card: int = deck.[target]
        deck.[target] <- deck.[position]
        deck.[position] <- held_card)
    deck |> Array.map string |> String.concat ""

let naive_paths: int list list =
    [ for first in 0 .. 2 do
        for second in 0 .. 2 do
            for third in 0 .. 2 -> [ first; second; third ] ]
printfn "naive swap-with-any, %d paths: %A" naive_paths.Length
    (naive_paths |> List.map fn_apply_swaps |> List.countBy id |> List.sortBy fst)

let fisher_yates_paths: int list list =
    [ for first in 0 .. 2 do
        for second in 1 .. 2 do
            for third in 2 .. 2 -> [ first; second; third ] ]
printfn "fisher-yates, %d paths: %A" fisher_yates_paths.Length
    (fisher_yates_paths |> List.map fn_apply_swaps |> List.countBy id |> List.sortBy fst)
```

Output: `naive swap-with-any, 27 paths: [("123", 4); ("132", 5); ("213", 5); ("231", 5); ("312", 4); ("321", 4)]`, then `fisher-yates, 6 paths: [("123", 1); ("132", 1); ("213", 1); ("231", 1); ("312", 1); ("321", 1)]`. `Random.Shuffle` (a documented method, .NET 8 and later): `Random(42).Shuffle(Array.init 10 id)` gave `[6; 2; 3; 0; 5; 1; 8; 4; 7; 9]`, a third answer for the same seed and size that the C++ libraries gave.

**Why it matters**

Counting paths is a proof, not a statistical test: no sample size can find a bias this small by luck, and an enumeration cannot be argued with. The same trick scales to any shuffle you can run with an injected choice function, which is also how you would test your own. The bias at three cards is 5 to 4. At 52 it is still tiny per ordering, and a poker player does not need all orderings to be skewed, only a few common ones.

**Chew on this**

If a shuffle takes its choices from a function you can replace with a list, how many orderings of three items can you enumerate before you trust it? Which of the shuffles in your code have ever been run that way?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.random.shuffle
- https://web.archive.org/web/20131021130406/http://www.cigital.com/papers/download/developer_gambling.pdf (the poker paper)

**Verified**

.NET SDK 10.0, `dotnet fsi`. `Random(42).Shuffle` ran on the same image. Also measured, not shown: `List.sortWith` with a random comparator on five items put item 0 in positions `[307624; 307285; 204466; 117421; 63204]` over a million runs, and `Array.Sort` with a random `Comparison` on 100 items returned normally.

**Gotchas**

- A sort by a random key drawn once per element, `List.sortBy (fun _ -> rnd.Next())`, gave `[199907; 199581; 199291; 200806; 200415]`: uniform to within noise. Ties in the keys are the only remaining bias.
- `Array.Sort` did not throw on a random comparison of 100 items, unlike Rust's panic.

## TypeScript: `array.sort(() => 0.5 - Math.random())` on Node 26 gives item 0 the first or second slot 49 percent of the time, and the answer depends on the engine

*Idioms and antipatterns*

**Did you know**

The line Microsoft's ballot used is still the most-copied JavaScript shuffle. On Node 26.13 (V8), over a million runs on five items, item 0 landed in positions 0 to 4 `246260 245365 195502 172283 140590` times: 24.6 percent first and 14.1 percent last, not 20 percent each. Weir measured Internet Explorer landing last about half the time in its own engine. Different engines sort differently, so the bias is different, and the specification does not promise anything about it.

**Show me**

```ts
// Node 26.13.0 (runs the types as-is), tsc 7.0.2
const const_run_count: number = 1_000_000
const const_item_count: number = 5

const const_fn_item_zero_positions = (const_fn_shuffle: (items: number[]) => number[]): number[] => {
    const const_counts: number[] = new Array<number>(const_item_count).fill(0)
    for (let run_index: number = 0; run_index < const_run_count; run_index++) {
        const_counts[const_fn_shuffle([0, 1, 2, 3, 4]).indexOf(0)]++
    }
    return const_counts
}

const const_fn_comparator_shuffle = (items: number[]): number[] => items.sort(() => 0.5 - Math.random())

const const_fn_fisher_yates = (items: number[]): number[] => {
    for (let position: number = items.length - 1; position > 0; position--) {
        const swap_with: number = Math.floor(Math.random() * (position + 1))
        ;[items[position], items[swap_with]] = [items[swap_with], items[position]]
    }
    return items
}

console.log("sort(() => 0.5 - Math.random()), item 0 position counts:", const_fn_item_zero_positions(const_fn_comparator_shuffle).join(" "))
console.log("Fisher-Yates, item 0 position counts:                   ", const_fn_item_zero_positions(const_fn_fisher_yates).join(" "))
```

Output: `246260 245365 195502 172283 140590` for the comparator shuffle and `199319 199800 200047 200113 200721` for Fisher-Yates. The counts vary by run; the shape does not.

**Why it matters**

The comparator shuffle works well enough that nobody notices: every output is a permutation, none repeats the same order twice, and a casual test shows variety. The bias lives in the counts, which only a measurement shows, and in a position that matters (the first slot of a ballot, a playlist, a card deal). No exception and no type error warns you, which is why this shape survived to a European ballot.

**Chew on this**

Which of your shuffles have you counted instead of eyeballed? If the engine decides how wrong the shuffle is, which engine did you test on, and which does your user run?

**Sources**

- https://www.robweir.com/blog/2010/02/microsoft-random-browser-ballot.html
- https://tc39.es/ecma262/#sec-array.prototype.sort (the comparator contract)

**Verified**

Node v26.13.0 in the `node:lts` image, a million runs per line. ECMAScript says the sort order is implementation-defined if the comparator is not consistent (read in the spec text); the bias numbers are measured, the engine-dependence claim rests on Weir's Internet Explorer numbers against mine.

**Gotchas**

- `toSorted` takes the same comparator and would have the same problem; I did not measure it.

# The functional angle: a comparator is an effect, a key is a value, and only the second is a shuffle

Draws on all four tips. The ballot's bug, Rust's panic, C++'s corrupted heap and the TypeScript bias are one mistake: using a function that returns a different answer every call where the algorithm assumes a pure function. A comparator is called many times per pair. A key drawn once per element is a value, and sorting by values is correct.

```rust
// Rust: decorate with one random key per item (drawn once), then sort by the key. Uniform up to key ties.
items.sort_by_cached_key(|_| mut_rng.next_u64());
```

| Language | Comparator shuffle, measured | Key shuffle, measured | What decides when it fails |
| --- | --- | --- | --- |
| Rust | item 0 `[307306 ... 62777]`, panics from 21 items | `sort_by_cached_key` `[199907 ... 199603]` | a checked total order, on one path |
| C++ | `[307062 ... 93845]` on libc++, abort on GCC 16.2 | not measured | undefined behavior, library by library |
| F# | `[307624 ... 63204]`, no throw at 100 | `List.sortBy` `[199907 ... 200415]` | nothing: it just stays wrong |
| TypeScript | `[246260 ... 140590]` | not measured | the engine's sort algorithm |

Rust is the baseline because its type system could not stop the bug and its runtime half-did: a panic, on some inputs. Which of those is better for a shuffle: a panic at 21 or a wrong answer at five?

# The security angle: a biased shuffle is a predictable deck

Draws on the F# tip (and Appendix A). Mode B: what the language does not prevent. Bug classes: CWE-330 (Use of Insufficiently Random Values) and CWE-338 (Use of Cryptographically Weak PRNG), the second because a game or a lottery needs a source an opponent cannot predict.

```fsharp
// F#: shuffle a deck for a game that pays money. Fisher-Yates over a cryptographic source, not Random(seed).
let fn_secure_shuffle (items: 'item[]) : unit =
    for position in items.Length - 1 .. -1 .. 1 do
        let swap_with: int = System.Security.Cryptography.RandomNumberGenerator.GetInt32(position + 1)
        let held_item: 'item = items.[position]
        items.[position] <- items.[swap_with]
        items.[swap_with] <- held_item
```

This sample ran on .NET 10 and returned a permutation of 0 to 9; it is the standard algorithm over `RandomNumberGenerator.GetInt32`, which part 2 measured as uniform for one range.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| F# | `Random(seed)` shuffles are reproducible from the seed | `Random.Shuffle` is documented for general use, not secrets (documentation) | use a cryptographic source for anything with money on it |
| Rust | `rand`'s `shuffle` is only as strong as the generator behind it | `thread_rng` is OS-seeded (documentation) | say which generator when a shuffle matters |
| C++ | `std::shuffle` takes any engine, including a predictable one | nothing | the engine is the design decision |
| TypeScript | `Math.random` is documented by V8 as not cryptographically secure | nothing | `crypto.getRandomValues` for a fair deal |

C++ is the baseline: it is the language that lets you hand any engine to `std::shuffle` and never asks whether it was a fair one. What would you check first in a card game: the shuffle, the seed or the engine?

# FAQ

**Is a sort by random key a perfect shuffle?**
Not quite: if two random keys tie, the stable sort leaves those items in their original order, a small bias. With 64-bit keys the chance is negligible; with `rnd.Next()` (31 bits) two given keys tie with probability 2^-31, about one in two billion, by arithmetic; I did not measure the tie rate.

**Why did the ballot's Internet Explorer land last and my Node counts put item 0 first?**
Different engines run different sort algorithms over the same incoherent comparator. Weir's table is from Internet Explorer's engine, mine from V8. Nothing in the language fixes either.

**Does Fisher-Yates need a perfect random source?**
Its fairness depends on drawing each swap partner uniformly from the right range (part 2's modulo bias applies to that one draw). With an unbiased draw, every ordering is reachable exactly once per path.

# Appendix A: An online poker shuffle swapped each card with a random one anywhere in the deck, and seeded from the clock

Researchers at Reliable Software Technologies wrote "How we Learned to Cheat in Online Poker: A Study in Software Security" about the PlanetPoker card room, whose software vendor, ASF Software, had published its shuffling code (I read the Internet Archive's 2013 copy of a 2006 re-issue; the text refers to January 1999 in the past tense, and I did not verify the original date). The shuffle in their Figure 1, in Pascal, filled the deck with the cards 1 to 52, called `randomize`, then for each position `ctr` swapped card `ctr` with the card at `random(51)+1`. They name two flaws in it:

- The swap partner was chosen from the whole deck, not from the cards not yet placed: "regardless of the off-by-one problem, it doesn't return an even distribution of decks". That is the F# tip's 27-paths-over-6 argument, at 52 cards.
- The off-by-one: with `random(51)+1` the swap partner is never position 52, so the last card is swapped with something else and "this shuffling algorithm never allows the 52nd card to end up in the 52nd place".

The third flaw is the seed. The paper says `randomize` chose the seed from "the number of milliseconds since midnight", so "There are a mere 86,400,000 milliseconds in a day", and that a 32-bit generator can only start from "just over 4 billion possible seeds" against 52! (they write about 2^226) possible orderings. By synchronizing with the server's clock they cut the candidates "down to a number on the order of 200,000". Their program needed five known cards: the cheating player's two plus the three-card flop. From those it searched the few hundred thousand possible shuffles "in real time, during play", and found the exact shuffle: "We know who holds what cards, what the rest of the flop looks, and who is going to win like in advance."

The paper's own fix is the algorithm in this part: "X = RANDOM NUMBER BETWEEN CT AND 52 INCLUSIVE", a Fisher-Yates shuffle, with a real seed. The lesson for this part is the first flaw. The lesson for part 4 is the third.

# Appendix B: The 1969 draft lottery loaded its capsules month by month, and the mixing did not undo the order

The United States held a lottery to rank birth dates for the draft on 1 December 1969 (a date from the secondary source below). Two papers in Science (22 January 1971) record what followed. Stephen Fienberg's "Randomization and social affairs: the 1970 draft lottery" opens its abstract by noting that "several young men have filed suit in federal court, seeking to void the 1970 drawing and to force a new lottery" on "the lack of proper randomization", and that "The 1917 and 1940 Selective Service draft lotteries have served in the past as indications that the commonly held notion of 'randomness' is often at variance with the strict statistical meaning". Rosenblatt and Filliben's "Randomization and the draft lottery" describes the replacement: for the 1 July 1970 lottery, "Fifty 'random permutations' were prepared for use by the Selective Service System as a basis for a two-stage randomization".

The specifics of what went wrong in 1969 I read only in a secondary source, Wikipedia's article on the lottery (the Internet Archive's snapshot of 18 September 2026), which I did not check against the papers. It says the capsules were "put in a box month by month, January through December", that "subsequent mixing efforts were insufficient to overcome this sequencing", that the rank of the average draft number by month ran 5, 4, 1, 3, 2, 6, 8, 9, 10, 7, 11, 12 from January to December, and that a Monte Carlo simulation put the chance of a random order of months being that close to 1 to 12 at 0.09 percent. Treat those figures as Wikipedia's. The mechanism is the same as the ballot's: a procedure that looks mixed, whose output was never counted against the uniform case.
