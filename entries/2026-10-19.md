## Rust: Adding impl Drop breaks every ..Default::default() that still takes a String from the base, and the base was built and dropped in full anyway

*Idioms and antipatterns*

**Did you know**

Functional record update, `Session { token, ..Default::default() }`, builds the base as a whole temporary value, moves or copies the fields you did not name out of it, and drops the rest at the end of the statement. So `Default::default()` runs in full (every `String`, every `Vec::with_capacity`), and if the type implements `Drop`, that `drop` runs on a value no one ever named. Add `impl Drop` to a struct later (to wipe a token, say) and each update site that takes a non-`Copy` field from the base stops compiling with `E0509`. A site that only takes `Copy` fields from the base still compiles, so the breakage is spread across the codebase in a way that looks random.

**Show me**

```rust
// rustc 1.95.0, any edition.
#[derive(Default)]
struct Session {
    token: String,
    user: String,
    retries: u32,
}

impl Drop for Session {
    // Added later, to wipe the token on the way out.
    fn drop(&mut self) {
        println!("drop user={:?}", self.user);
        self.token.clear();
    }
}

fn main() {
    // Only `retries` (Copy) comes from the base, so this still compiles.
    // The base is a whole Session: built by Default, then dropped right here.
    let copy_only = Session { token: "t".into(), user: "alice".into(), ..Default::default() };

    // `user` (a String) would be moved out of the base:
    // let moved = Session { token: "t".into(), retries: 1, ..Default::default() };
    //   error[E0509]: cannot move out of type `Session`, which implements the `Drop` trait

    // Compiles: name every field, so nothing is moved out of a Drop type.
    let spelled_out = Session { token: "t".into(), user: String::new(), retries: 1 };

    println!("built {} {}", copy_only.retries, spelled_out.retries);
}
// Output:
//   drop user=""        <- the anonymous base, dropped before the next line runs
//   built 0 1
//   drop user=""
//   drop user="alice"
```

**Why it matters**

`..Default::default()` is how config and request-option structs get built across a service, so adding a `Drop` impl ends up as a refactor that touches many files. It also shows that the "immutable" update syntax was never free: each use builds and throws away a full default, allocations included. C++20 designated initializers have no base value at all, so this problem cannot arise there. F#'s `{ s with ... }` copies references to every field, so an `IDisposable` field is now shared by two records with no compiler complaint. TypeScript's `{ ...base }` copies own enumerable properties and quietly drops the prototype.

**Chew on this**

The ways out of `E0509` are to spell out every field, to use `let mut` and assign, or to `mem::take` from a base you own. Which of those still says "everything else is the default" to the next person who adds a field? And if `Drop` exists to clear a secret, how many unnamed copies of that struct did your `..Default::default()` sites already create and drop?

- https://doc.rust-lang.org/error_codes/E0509.html

## C++: set_option(key, "false") picks the bool overload and stores true, and only std::variant was fixed

*Type system deep cuts*

**Did you know**

A string literal reaches `bool` through standard conversions only (array-to-pointer, then boolean conversion). It reaches `std::string` or `std::string_view` only through a user-defined conversion. Overload resolution always ranks a standard conversion sequence above a user-defined one, so `f(key, bool)` beats `f(key, std::string)` for `"false"`, and the non-null pointer becomes `true`. This holds in every standard from C++98 to C++26. The library fixed it for one type only. P0608R3 (a defect report back to C++17) makes `std::variant`'s converting constructor ignore any alternative that would be a narrowing conversion, and P1957R2 (a defect report in C++20) made pointer-to-`bool` count as narrowing. Library support for P0608R3: libstdc++ 10, libc++ 9, MSVC STL 19.29. Compiler support for P1957R2: GCC 10/11, Clang 11, MSVC 19.27.

**Show me**

```cpp
// GCC 14.2 (libstdc++) and Apple clang 21 (libc++ 22.1); same output under -std=c++17, c++20 and c++23.
#include <cstdio>
#include <string>
#include <string_view>
#include <variant>

// Two overloads that look like they cover "a flag" and "a text value".
void set_option(std::string_view key, bool enabled)       { std::printf("%.*s = bool %d\n", (int)key.size(), key.data(), enabled); }
void set_option(std::string_view key, std::string value)  { std::printf("%.*s = string %s\n", (int)key.size(), key.data(), value.c_str()); }

int main() {
    // const char[6] -> const char* -> bool is a standard conversion;
    // const char* -> std::string is user-defined, so bool ranks higher and wins.
    set_option("require_tls", "false");             // prints: bool 1
    set_option("require_tls", std::string("false")); // prints: string false

    // std::variant fixed exactly this in C++20 (P0608 + P1957): the converting
    // constructor now refuses narrowing and pointer-to-bool, so string wins.
    std::variant<bool, std::string> setting = "false";
    std::printf("variant index = %zu (1 means std::string)\n", setting.index());
}
```

**Why it matters**

`-Wall -Wextra` print nothing for this code. Clang's `-Wstring-conversion` ("implicit conversion turns string literal into bool") is the warning that catches it, and it is not part of either group. A settings API with a `bool` overload and a string overload therefore stores `true` for every literal anyone ever passed as text. Rust has no implicit conversions and no overloading, so the same API is a trait (`impl Into<Value>`) chosen by the argument's exact type. F# and C# have no implicit conversion from `string` to `bool`. TypeScript overloads exist only at the type level: at runtime there is one function, and `if (value)` treats `"false"` as true.

**Chew on this**

The committee fixed `variant` by redefining narrowing, not by changing overload resolution, because changing the core rule would silently change which function existing code calls. Is that the same trade-off you would make for your own overload sets, or is a `bool` overload next to a string one a design that should not compile at all? Which of your APIs takes a `bool` and could also be handed a string?

**Sources**

- https://en.cppreference.com/w/cpp/language/overload_resolution
- https://en.cppreference.com/w/cpp/utility/variant/variant
- https://wg21.link/P0608R3
- https://wg21.link/P1957R2
- https://en.cppreference.com/w/cpp/compiler_support/20

**Verified**

GCC 14.2 / libstdc++ on Debian 13, `-std=c++17`, `c++20` and `c++23` with `-Wall -Wextra`: no warnings, and all three print `bool 1`, `string false`, `variant index = 1`. As a separate confirmation, Apple clang 21 with libc++ 22.1 on macOS prints the same.

## F#: F# 11 lets a plain let hold a let!, and it compiles that let into a hidden nested task

*New discoveries and currently popular patterns*

**Did you know**

Through F# 10, a `let!` inside the body of a plain `let` in a computation expression is `FS0750` ("This construct may only be used within computation expressions"). dotnet/fsharp#19868 (merged 2026-07-24, shipped in .NET 11 Preview 7 in August 2026, part of F# 11, the default language version since RC1 in September) accepts it. It does so by rewriting `let port = <body with a bang>` into `let! port = builder { <body> }`, a nested computation of the same builder. So a binding without a `!` now suspends, and for `task` it allocates a second task. The PR's first version lifted the bang straight out of the body, and review found it silently miscompiled shadowing (`(42, 42)` returned instead of `(42, 999)`). `use`, a bang inside `try`, and a bang that is not at the head of the chain are still `FS0750`. The PR adds no language-version switch that I could find.

**Show me**

```fsharp
// F# 11 / .NET 11 SDK accepts this. F# 8 (SDK 8.0.401) rejects it:
//   nested.fsx(10,13): error FS0750: This construct may only be used within computation expressions
open System.Threading.Tasks

let load_port (seed: int) = Task.FromResult (8080 + (seed &&& 1))

let written (seed: int) =
    task {
        let port =                     // no `!`, yet this line now awaits
            let! raw = load_port seed
            raw + 1000
        return port
    }

// What the compiler generates for it, per the PR. Release build, .NET 8:
//   flat   (let! raw = ...; let port = raw + 1000)   144.0 bytes/call
//   nested (this shape)                              216.0 bytes/call
let generated (seed: int) =
    task {
        let! port = task {
            let! raw = load_port seed
            return raw + 1000 }
        return port
    }
```

**Why it matters**

Reviewers find suspension points by scanning for `!`, and that habit is now wrong for one shape of code: a `let` whose body contains a bang is an await, plus one extra task (72 bytes per call here) on every pass through a hot handler. Rust needed no such rewrite, because a block is an expression: `let port = { let raw = load_port().await; raw + 1 };` stays inside the one state machine (that whole future measured 2 bytes). TypeScript has no statement blocks in expression position, so the same shape is an async IIFE, which creates a new Promise every time it runs.

**Chew on this**

The nested form is the one F# already let you write by hand, so the feature adds no expressive power, only a shape where the cost is hidden. Would you allow it in a hot path, or does your review checklist now need a rule for "a bang inside a let"? And for a builder you wrote yourself, is "nested computation of the same builder" even what that body means?

**Sources**

- https://github.com/dotnet/fsharp/pull/19868
- https://github.com/dotnet/core/blob/main/release-notes/11.0/preview/preview7/fsharp.md
- https://www.infoq.com/news/2026/09/dotnet-11-rc-1-release/

**Verified**

Only the .NET 8 SDK (FSharp.Core 8.0.0.0, .NET 8.0.8) is installed here. The `FS0750` text is quoted from it, and the byte counts measure the hand-written nested form in a Release build, not F# 11 compiler output. The F# 11 behavior rests on the PR and the release notes.

## TypeScript: One null in a number[] boxes every double in it, and popping the null does not undo it

*Perf and memory model*

**Did you know**

V8 stores an array of non-integer numbers as `PACKED_DOUBLE_ELEMENTS`: raw 8-byte floats, back to back. Push a single `null` (or `undefined`, or a string) and the array moves to `PACKED_ELEMENTS`, where each slot is a pointer and each double becomes its own `HeapNumber` object. A million readings went from 10.0 MiB to 25.2 MiB here. Elements-kind transitions are one-way, so removing the `null` with `pop()` leaves the array boxed for as long as it lives. A `NaN` sentinel is itself a double, so it keeps the flat layout. None of this appears in the type: `(number | null)[]` and `number[]` compile to the same JavaScript.

**Show me**

```typescript
// tsc 6.0.3 --strict; Node 22.17.1 (V8 12.4). Measured with --expose-gc and
// heapUsed: 10.0 MiB flat, 25.2 MiB after one null, 10.0 MiB with NaN.
// %DebugPrint (--allow-natives-syntax) shows PACKED_ELEMENTS after the pop().
const gap_marked: (number | null)[] = [];
const nan_marked: number[] = [];

for (let sample = 0; sample < 1_000_000; sample++) {
    const reading: number = sample * 0.5 + 0.25;
    gap_marked.push(reading);
    nan_marked.push(reading);
}

gap_marked.push(null); // every double above is now a separate 16-byte heap object
nan_marked.push(NaN);  // still a flat array of 8-byte doubles
gap_marked.pop();      // too late: the array never goes back to unboxed doubles

const total_valid = nan_marked.filter((reading) => !Number.isNaN(reading)).length;
console.log(gap_marked.length, total_valid);
```

**Why it matters**

A metrics buffer or time series typed `(number | null)[]` "to be honest about gaps" pays 2.5x the heap and gives the GC a million extra objects to trace, and the first gap in a long-lived buffer makes that permanent. `Float64Array` cannot change kind at all, and it is the only way to get a type that guarantees the layout. The other languages force the choice into the type. A Rust `Vec<Option<f64>>` and a C++ `std::vector<std::optional<double>>` both cost 16 bytes per element, decided at compile time, because `f64` has no spare bit pattern for `None` to use.

**Chew on this**

`NaN` as "missing" keeps the layout but brings back the sentinel problem `Option` exists to remove: an upstream `0 / 0` now looks exactly like a gap. Where is the boundary in your code that could hold `Float64Array` plus a separate validity bitmap, and who would notice if a `null` slipped into a buffer in production?

**Sources**

- https://v8.dev/blog/elements-kinds
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Float64Array

**Verified**

The `null` transition is measured with `%DebugPrint`, not quoted: the V8 post documents the one-way rule and the string case but does not mention `null`.

# The functional angle: "absent" costs a full word per element in every language here, and only V8 decides that cost for you

This draws on the TypeScript tip. The other rows are the same shape: a million doubles, some of which may be missing.

F# is the baseline here because `option` is the idiomatic way to say "missing" there, so its rows show what the idiom costs in a language built around it:

```fsharp
// dotnet fsi, FSharp.Core 8.0.0.0; GC.GetAllocatedBytesForCurrentThread, 1M elements.
let plain    = Array.init count (fun index -> float index * 0.5 + 0.25)             //  7.6 MiB
let value    = Array.init count (fun index -> ValueSome (float index * 0.5 + 0.25)) // 15.3 MiB
let boxed    = Array.init count (fun index -> Some (float index * 0.5 + 0.25))      // 30.5 MiB
```

```rust
// rustc 1.95.0
size_of::<f64>()          // 8
size_of::<Option<f64>>()  // 16: f64 has no niche, so the tag gets its own word after padding
```

```cpp
// GCC 14.2 (libstdc++) and Apple clang 21 (libc++)
sizeof(double)                 // 8
sizeof(std::optional<double>)  // 16
```

| Language | Functional form | 1M elements | What it costs |
| --- | --- | --- | --- |
| F# | `float option[]` | 30.5 MiB | one 24-byte heap box per `Some`, plus an 8-byte reference |
| F# | `float voption[]` | 15.3 MiB | tag plus padding, 16 bytes inline, no allocation |
| Rust | `Vec<Option<f64>>` | 16 B/elem, not run at 1M | the same 16 bytes, fixed by the type |
| C++ | `vector<optional<double>>` | 16 B/elem, not run at 1M | the same 16 bytes, fixed by the type |
| TypeScript | `(number \| null)[]` | 25.2 MiB | 10.0 until the first `null`, then a `HeapNumber` per element, permanently |

The asymmetry is where the decision is made. Rust, C++ and F# each make it at compile time: you pick `Option`, `optional` or `voption` and pay a known price. TypeScript's type picks nothing. The runtime picks at the first non-number value, and nothing in the source shows that it happened. Every compiled language here ends up spending a word on the tag, so the cheaper option in all four is the same non-functional one: a dense array of values plus a separate bitmap of which ones are valid.

Is a bitmap beside a `Float64Array` a step back from `Option`, or is it the same sum type, stored one column at a time?

# The security angle: the string "false" turns a flag on in two of the four languages

This draws on the C++ tip, and runs in the direction where the language does not protect you. A string that reaches a `bool` without being parsed is CWE-704 (Incorrect Type Conversion or Cast), and the dangerous form is a flag whose `true` value loosens security.

The insecure sample, in C++: two overloads that pass review, and a config loader that forwards a value it read as text.

```cpp
void set_option(std::string_view key, bool enabled);
void set_option(std::string_view key, std::string value);

set_option("allow_anonymous", "false");   // binds to bool, stores true
```

The same failure in TypeScript, where the conversion happens at runtime instead of in overload resolution:

```typescript
// ALLOW_ANONYMOUS=false node app.js
const allow_anonymous: boolean = Boolean(process.env.ALLOW_ANONYMOUS); // true: any non-empty string is truthy
```

The parse functions in the other two languages disagree with each other, which matters as soon as two services read the same environment file:

```text
                 "false"      "False"               " false "
Rust parse::<bool>  Ok(false)    Err(ParseBoolError)   Err(ParseBoolError)
.NET Boolean.Parse  false        false                 false   (case-insensitive, trims)
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | a `"false"` literal binds to the `bool` overload as `true` | nothing in `-Wall -Wextra`. clang `-Wstring-conversion` warns. `std::variant` refuses it since the C++20 DRs | enable `-Wstring-conversion`, or delete the overload: `void set_option(std::string_view, const char*) = delete;` |
| TypeScript | `Boolean("false")` and `if (env.FLAG)` are `true` | nothing. The `boolean` annotation describes the result of the conversion, not a parse | compare against an exact token, and decide what happens on anything else |
| Rust | nothing implicit; `parse::<bool>` is exact-match | refuses `"False"` and `" false"` with an `Err` | handle the `Err`. `unwrap_or(true)` puts the bug back in |
| F# / C# | nothing implicit; `Boolean.Parse` is lenient | accepts case and whitespace variants, throws on anything else | the leniency differs from Rust's: the same `.env` file can parse differently in each service |

Rust is the baseline row here because it is the only one that turns both halves into code you have to write: there is no conversion to fall into, and the parse failure is a value you must handle. The table's last column is the point: in every language, someone has to decide what an unparseable flag means.

When your service reads a security flag it cannot parse, does it fail closed, fail open, or crash, and is that choice written down anywhere other than in a default argument?
