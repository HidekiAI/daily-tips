# Daily Tips: 2026-10-02

## Rust: `take_while` eats the element that stopped it, because `next()` reads and advances in one call

*Idioms and antipatterns*

**Did you know**

`stream.by_ref().take_while(pred)` looks like "consume the prefix, leave the rest". It is not: to learn that it should stop, `take_while` has to call `next()` on the element that fails the predicate, and `Iterator` has no way to put an element back. That element is simply dropped. The fix in std is `Peekable::next_if` (Rust 1.51), driven by `iter::from_fn`, which only advances when the predicate holds.

**Show me**

```rust
// rustc 1.95.0, --edition 2024. Printed values are from that run.
fn main() {
    let records = [1, 2, 3, 10, 11, 4];

    // The trap: by_ref() lets us keep using `stream` afterwards, which makes
    // it look like take_while stopped *before* 10. It stopped *after* it.
    let mut stream = records.iter();
    let small: Vec<&i32> = stream.by_ref().take_while(|value| **value < 10).collect();
    let rest: Vec<&i32> = stream.collect();
    println!("{small:?} {rest:?}");
    // [1, 2, 3] [11, 4]        <- 10 is gone, no warning anywhere

    // The fix: a one-element lookahead buffer. next_if peeks, and only
    // calls next() when the predicate says yes.
    let mut stream = records.iter().peekable();
    let small: Vec<&i32> = std::iter::from_fn(|| stream.next_if(|value| **value < 10)).collect();
    let rest: Vec<&i32> = stream.collect();
    println!("{small:?} {rest:?}");
    // [1, 2, 3] [10, 11, 4]
}
```

**Why it matters**

The classic case is a line-based protocol parsed off one shared iterator: headers with `take_while(|line| !line.is_empty())` is fine because the blank line is meant to vanish, and then someone reuses the same shape for "records until the next section marker" and the marker line silently disappears. It is a property of the `Iterator` contract, not of `take_while`: `next()` is the only way to look, so every look is a consume. C++ splits reading (`*it`) from advancing (`++it`), so a hand-written loop can stop without consuming; TypeScript's `Iterator.next()` is fused exactly like Rust's and loses the element the same way.

**Chew on this**

Where in your code does one iterator get passed to two consumers in sequence? Does the second one ever need the element the first one stopped on?

## C++: `Port() = delete` stopped `Port{70000}` only in C++20; in C++17 the struct was still an aggregate

*Type system deep cuts*

**Did you know**

In C++17, a struct whose constructors are all deleted or defaulted on their first declaration is still an *aggregate*, because those constructors are not "user-provided". Brace initialization of an aggregate never calls a constructor, so `Port{70000}` compiled straight past `Port() = delete` and past the factory the author meant to be the only way in. C++20 (P1008R1) changed the rule to "no user-*declared* constructors", which closes it: GCC 9, Clang 8, MSVC 19.20, Apple Clang 10.0.1 onward, under `-std=c++20`. Under `-std=c++17` the hole is still open today, and `-Wall -Wextra` does not mention it; only `-Wc++20-compat` does.

**Show me**

```cpp
// Apple clang 21. -std=c++17: compiles. -std=c++20: error on bypass().
#include <type_traits>

// The author's intent: "a Port only comes from Port::parse".
struct Port {
    Port() = delete;               // no default construction
    static Port parse(int raw);    // the sanctioned way in, validates 1..65535
    int value;                     // public so callers can read it
};

// C++17: true. A deleted ctor is user-declared but not user-provided.
// C++20: false. Any user-declared ctor removes aggregate status.
static_assert(std::is_aggregate_v<Port> == (__cplusplus < 202002L));

// C++17: aggregate init, no constructor runs, 70000 is not a port.
// C++20: "no matching constructor for initialization of 'Port'".
Port bypass() { return Port{70000}; }

// The fix that works in both: make the data private and the ctor private
// (and explicit). Then Port{70000} is "calling a private constructor".
```

**Why it matters**

A codebase pinned to C++17 for one old toolchain can carry "validated" types that any call site can forge with braces, and the review that approved `= delete` believed the opposite. Moving to C++20 turns those forgeries into compile errors, which is the rare standard upgrade that breaks only code that was already wrong. Rust has no such gap because construction is controlled by field privacy, not by constructors: a struct literal with a private field does not compile outside its module (E0451). F#'s `type Port = private { value: int }` does the same job (FS1093).

**Chew on this**

How many of your "only via the factory" types rely on a deleted or defaulted constructor rather than on private data? If one translation unit still builds as C++17, which of them can it forge?

**Sources**

- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2018/p1008r1.pdf
- https://en.cppreference.com/w/cpp/language/aggregate_initialization
- https://en.cppreference.com/w/cpp/compiler_support/20

**Verified**

Apple clang 21 only, `-std=c++17` and `-std=c++20`; GCC and MSVC rows are from the cppreference support table, not run.

## F#: F# 11 made `$"{price}"` culture-invariant, so a German server's logs switch from `1.234,5` to `1,234.5` on upgrade

*New discoveries and currently popular patterns*

**Did you know**

In .NET 11 RC 1 (September 2026, F# 11 default), string-typed interpolated strings lower to `String.Concat` instead of the reflection-based printf engine (dotnet/fsharp #19971, merged 2026-08-01). The side effect is a behavior change: plain holes and .NET-format holes now format through the F# `string` operator, which is invariant, instead of the current thread culture. Measured under `de-DE`: `$"{1234.5:N1}"` was `1.234,5` on F# 8 and is `1,234.5` on F# 11, and a `DateTime` hole moved from `02.10.2026` to `10/02/2026`. `--langversion:10.0` on the 11 SDK did not bring the old output back. And the change is per *type*, not per syntax: the same `$"{price:N1}"` handed directly to `printfn` is a `PrintfFormat`, and it still prints `1.234,5`.

**Show me**

```fsharp
// dotnet fsi on SDK 8.0.401 (FSharp.Core 8) and 11.0.100-rc.1 (FSharp.Core 11).
open System
open System.Globalization

CultureInfo.CurrentCulture <- CultureInfo("de-DE")
let price = 1234.5
let when_utc = DateTime(2026, 10, 2, 13, 5, 0, DateTimeKind.Utc)

printfn "%s" $"{price}"         // F# 8: 1234,5              F# 11: 1234.5
printfn "%s" $"{price:N1}"      // F# 8: 1.234,5             F# 11: 1,234.5
printfn "%s" $"{when_utc}"      // F# 8: 02.10.2026 13:05:00 F# 11: 10/02/2026 13:05:00
printfn "%s" $"%f{price}"       // both: 1234.500000  (printf holes were always invariant)
printfn "%s" (price.ToString()) // both: 1234,5       (ToString still follows the culture)
printfn "%s" (String.Format("{0}", price)) // both: 1234,5

// The same interpolation passed straight to printfn is a PrintfFormat, not a
// string, so it never reaches String.Concat and keeps the old culture rule:
printfn $"{price:N1}"         // F# 8: 1.234,5             F# 11: 1.234,5
```

**Why it matters**

Anything that parses its own interpolated output, or that a human reads in a non-English locale, changes on SDK upgrade with no compiler warning: a CSV row built with `$"{amount}"`, a date in an email body, a log line a downstream parser splits on commas. The F# 11 behavior is the one Rust's `format!`, C++'s `std::format` (without `{:L}`), Go's `fmt` and TypeScript's template literals already had; C# is now the outlier, since `$"{price}"` in C# is still `1234,5` under `de-DE` unless wrapped in `string.Create(CultureInfo.InvariantCulture, ...)`. A mixed F#/C# solution now formats the same expression two ways.

**Chew on this**

Which of your interpolated strings were *meant* to be localized, and which only happened to be? Once the two languages in your solution disagree, which one do you want your tests to pin?

**Sources**

- https://github.com/dotnet/core/blob/main/release-notes/11.0/preview/rc1/fsharp.md
- https://github.com/dotnet/fsharp/pull/19971
- https://devblogs.microsoft.com/dotnet/dotnet-11-rc-1/

**Verified**

Measured in `dotnet fsi` only (SDK 8.0.401 and 11.0.100-rc.1.26425.128); a compiled project build was not run. The C# line was run on .NET 8. RC behavior may still change before the November GA.

## TypeScript: A closure that never mentions your 64 MiB buffer keeps it alive if any closure in the same scope does, even one in a branch that never ran

*Perf and memory model*

**Did you know**

V8 decides at parse time which variables live in a function's heap *context*, and every closure created in that scope points at the same context. So if one inner function mentions `payload`, every sibling closure retains `payload`, including one that only returns `200`. The scope analysis is static: a closure inside an `if (debug)` that never executed still forces `payload` into the context. Measured on Node 22.17.1 with `--expose-gc`.

**Show me**

```typescript
// tsc 6.0.3 --strict --target es2022; node --expose-gc. Output is from that run.
declare const gc: () => void;
type Made = { handler: () => number; probe: WeakRef<object> };

function handler_alone(): Made {
    const payload: Uint8Array = new Uint8Array(64 * 1024 * 1024); // 64 MiB body
    const handler = (): number => 200;                             // never mentions payload
    return { handler, probe: new WeakRef(payload) };
}

function handler_dead_branch(debug: boolean): Made {
    const payload: Uint8Array = new Uint8Array(64 * 1024 * 1024);
    if (debug) {
        // Never created when debug is false. Still puts payload in the context.
        const log_size = (): number => payload.byteLength;
        void log_size;
    }
    const handler = (): number => 200;                             // same body as above
    return { handler, probe: new WeakRef(payload) };
}

const made: Array<[string, Made]> = [["alone", handler_alone()], ["dead branch", handler_dead_branch(false)]];
// A WeakRef target is kept until the current job ends, so look on a later turn.
setTimeout(() => {
    gc();
    for (const [label, entry] of made) console.log(label, entry.probe.deref() !== undefined);
    // alone false          <- collected
    // dead branch true     <- 64 MiB held by a handler that returns 200
}, 0);
```

**Why it matters**

A long-lived handler, timer or event listener registered from a request-scoped function holds every request-scoped value that *any* sibling closure mentions, for as long as the handler lives. The type of the handler says `() => number`; the heap says 64 MiB. Rust and C++ do not have this shape at all: each closure is its own struct holding exactly what it captures (`size_of_val` of the Rust `|| 200` closure is 0, the one capturing a `Vec` is 8 here). F# compiles each lambda to its own class with only its free variables as fields (checked by reflection: `Byte[]` on one, `Int32` on the other).

**Chew on this**

Which of your long-lived callbacks are created inside a function that also allocates something large? If you hoisted the callback out, what would it lose access to that it actually needs?

**Sources**

- https://v8.dev/blog/preparser
- https://blog.meteor.com/an-interesting-kind-of-javascript-memory-leak-8b47d2e7f156

**Verified**

V8 behavior measured on Node 22.17.1 only; other engines (JavaScriptCore, SpiderMonkey) were not checked, and V8 may change its context allocation.

# The functional angle: lookahead is free where reading and advancing are two calls, and costs a buffer where they are one

Draws on the Rust tip. The shape: "take the prefix that matches, then hand the rest to someone else", over one single-pass source.

F# is the baseline here for a different reason than usual: its `seq` sidesteps the problem by not having a shared cursor at all, which turns out to be the most expensive answer.

```fsharp
// F#: no shared cursor; takeWhile and skipWhile each enumerate from the start.
let mutable reads = 0
let records = seq { for value in [1; 2; 3; 10; 11; 4] do reads <- reads + 1; yield value }
let small = records |> Seq.takeWhile (fun value -> value < 10) |> List.ofSeq
let rest  = records |> Seq.skipWhile (fun value -> value < 10) |> List.ofSeq
// [1; 2; 3] [10; 11; 4] reads=10   <- correct, but a 6-element source was read 10 times
```

```cpp
// C++23: *cursor reads, ++cursor advances, so stopping costs nothing...
auto stream = std::views::istream<int>(input);   // "1 2 3 10 11 4"
auto cursor = stream.begin();
for (; cursor != stream.end() && *cursor < 10; ++cursor) { /* 1 2 3 */ }
for (; cursor != stream.end(); ++cursor) { /* 10 11 4 */ }
// ...but `stream | views::take_while(...)` followed by a second range-for over
// `stream` prints "11 4": istream_view::begin() reads ahead, so re-entering drops 10.
```

```typescript
// TypeScript: next() is fused like Rust's, and there is no Peekable in the language.
function* take_while<T>(source: Iterator<T>, keep: (item: T) => boolean): Generator<T> {
    for (let step = source.next(); !step.done; step = source.next()) {
        if (!keep(step.value)) return;   // step.value is dropped here
        yield step.value;
    }
}
// small [1, 2, 3], rest [11, 4]
```

| Language | Functional form | Element 10 survives? | What it costs |
| --- | --- | --- | --- |
| F# | `Seq.takeWhile` + `Seq.skipWhile` | yes | the source is enumerated twice: 10 reads for 6 elements, and every side effect runs twice |
| Rust | `by_ref().take_while` | no | free, and wrong; the fix `Peekable::next_if` stores an `Option<Option<T>>` lookahead |
| C++ | explicit iterator loop | yes | free, because `*it` and `++it` are separate; lost again if you re-enter an `istream_view` via `begin()` |
| C++ | `views::take_while`, then re-iterate the view | no | `begin()` on a single-pass view performs a read |
| TypeScript | generator over `Iterator.next()` | no | free, and wrong; the fix is a hand-written peek buffer, std has none |

The asymmetry worth noticing: the two languages with a fused `next()` (Rust, TypeScript) need a mutable one-slot buffer to get it right, and only Rust ships that buffer. F# avoids the mutable buffer by paying in re-reads instead, which is the purely functional answer and the most expensive one on a socket.

Which of your "parse a prefix" functions take a reusable collection, and which take a stream that can only be read once?

# The security angle: a constructor is only a gate if the language forbids walking around it

Draws on the C++ tip, and runs in the "the language does not prevent it" direction for C++17 and TypeScript, and the "it does" direction for Rust, C++20 and F#. Mode D: the validated type is supposed to make an out-of-range port unrepresentable, and in two of these languages it does not. Rust is the control, because construction there is governed by field visibility and nothing else.

The insecure samples, both measured:

```cpp
// C++17: looks like a sealed value type, is a public struct.
struct Port { Port() = delete; static Port parse(int raw); int value; };
Port forged = Port{70000};   // compiles under -std=c++17, no warning with -Wall -Wextra
```

```typescript
// TypeScript: a private constructor is not a member, so it does not make the
// type nominal. Anything shaped like { value: number } is a Port.
class Port {
    private constructor(readonly value: number) {}
    static parse(raw: number): Port | undefined {
        return Number.isInteger(raw) && raw > 0 && raw < 65536 ? new Port(raw) : undefined;
    }
}
const forged: Port = { value: 70000 };   // tsc --strict: no error
```

The TypeScript fix is a member the outside cannot produce: `readonly #checked = true;` turns the same line into TS2741 ("Property '#checked' is missing").

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | nothing, for this shape | a struct literal with a private field fails outside its module (E0451) | `#[derive(Deserialize)]` builds the struct without calling `parse`, so serde input bypasses it |
| C++17 | `Port{70000}` skips every constructor | treats a deleted-only ctor type as an aggregate | private data, or build as C++20; `-Wc++20-compat` finds the sites |
| C++20 | nothing, for this shape | any user-declared ctor removes aggregate status (P1008) | a type with *no* declared ctor and public fields is still forgeable by design |
| F# | nothing, for this shape | `private` record representation rejects `{ value = 70000 }` (FS1093) | reflection and serializers that set fields directly |
| TypeScript | an object literal satisfies the class type | checks shape only; `private constructor` is not part of the shape | add an ES `#private` field or a brand; and `as Port` still forges anything |

Classes: CWE-20 (Improper Input Validation), and CWE-1284 (Improper Validation of Specified Quantity in Input) for the out-of-range value itself.

Every row's "Still on you" has the same entry in a different costume: the deserializer. Which of your validated types can be produced by your JSON layer without passing through the function that validates them?

# FAQ

**Does `skip_while` lose an element too?** No. `skip_while` yields the first failing element as its first output, so nothing is dropped. Only the adaptors that *stop* on a failing element (`take_while`, `map_while`) discard it.

**Does `Peekable` plus `take_while` fix the Rust tip?** No. `peekable.by_ref().take_while(...)` still calls `next()` on the stopping element. Only `next_if` / `next_if_eq` peek before advancing.

**Does the F# 11 change affect `sprintf` and `printfn`?** No. Printf formatting was already invariant; the measured `%f{price}` hole is identical on F# 8 and F# 11. Only plain `{x}` and .NET-format `{x:N1}` holes in string-typed interpolations changed.

**Is an F# interpolated string passed to `printfn` affected?** No, measured: `printfn $"{price:N1}"` prints `1.234,5` under `de-DE` on both F# 8 and F# 11, because that form is a `PrintfFormat<...>` and only string-typed interpolations lower to `String.Concat`.

**Does `"use strict"` or an ES module change the V8 closure retention?** Not measured. The mechanism is scope analysis, which runs in both modes, but the claim above rests on a script-mode run only.

**Is C++17 aggregate forgery a GCC or Clang bug?** No. It is the C++17 rule as written; P1008R1 cites exactly this `= delete` example as motivation.
