## Rust: thread_local!'s const { } deletes the init branch, and in a Linux executable what is left is a single `%fs:` instruction

*Perf and memory model*

**Did you know**

A plain `thread_local! { static HITS: Cell<u64> = Cell::new(0); }` is lazy: every `.with()` first reads a per-thread state byte and branches on "initialized yet?". Writing the initializer as `const { Cell::new(0) }` bakes the value into the TLS image, and for a type with no `Drop` the std docs say it "does not need to track any additional state". On x86_64 Linux (rustc 1.99.1) the lazy accessor is `cmpb $1, %fs:...+8; jne` and then a load, increment and store; the const one is the one instruction `incq %fs:...`. On arm64 Linux the lazy one has `ldrb w9, [x8, #8]; cbz` and the const one has none of it. The branch is perfectly predicted, though, so the timed gain on arm64 Linux was small: 0.761 vs 0.756 ns per access. As a separate confirmation, macOS (rustc 1.95.0, aarch64) removes the same branch, but both forms there start with `blr x8`, a call through the Mach-O TLV descriptor, and timed 1.30 vs 1.26 ns.

**Show me**

```rust
use std::cell::{Cell, RefCell};

thread_local! {
    // Lazy form: built on first access, so every .with() first reads a
    // per-thread state byte ("initialized? destroyed?") and branches on it.
    static LAZY_HITS: Cell<u64> = Cell::new(0);

    // const form: the initial value lives in the TLS image. Cell<u64> has no
    // Drop, so there is no state byte at all: the access is just the load.
    static CONST_HITS: Cell<u64> = const { Cell::new(0) };

    // const also works for a type that needs Drop (Vec::new is a const fn);
    // the state then exists only to register the destructor, not to init.
    static SCRATCH: RefCell<Vec<u8>> = const { RefCell::new(Vec::new()) };
}

#[inline(never)]
fn bump_lazy() { LAZY_HITS.with(|hits| hits.set(hits.get() + 1)); }

#[inline(never)]
fn bump_const() { CONST_HITS.with(|hits| hits.set(hits.get() + 1)); }

fn main() {
    bump_lazy();
    bump_const();
    SCRATCH.with_borrow_mut(|buffer| buffer.push(1)); // 1.73+: no .with(|cell| cell.borrow_mut())
    println!("{} {}", LAZY_HITS.get(), CONST_HITS.get());
}
```

**Why it matters**

Per-thread counters, arenas and request ids sit on the hottest path of a server, and the `const` form is free to adopt: it is one keyword and it does not change the API. The surprise is the size of the win. It depends on the platform's TLS model more than on Rust. A Linux executable uses the local-exec model, a thread-pointer-relative access with no call, so the removed branch is most of the instructions but, being predicted, little of the time. A Linux shared library (`cdylib`) pays a `callq __tls_get_addr@PLT` before either form (measured in the x86_64 asm), and so does every access on macOS, where a Mach-O TLV access is always a call. C++ has the same split, with a sharper edge: an `extern thread_local` whose initializer the compiler cannot see is accessed through a wrapper on every use, and C++20 `constinit` is what removes it. On Linux, GCC 14.2 compiles `++request_count` on an `extern thread_local int` to a check of the weak `_ZTH13request_count` and a `bl _ZTH13request_count` before the `tpidr_el0` access (arm64), and Clang 21 to `callq _ZTH13request_count@PLT` before the `%fs:` access (x86_64); the `constinit` version is the bare thread-pointer load on both. As a separate confirmation, on macOS Clang 21 emits `bl __ZTW13request_count`, and `constinit` leaves the bare TLV call.

**Chew on this**

Which of your thread locals is `Cell::new(0)` written without `const`, purely because the docs example you copied predates it? And if the remaining cost on your production OS is the TLS model rather than the branch, is a thread local even the right tool for a counter that a sharded atomic could hold?

## C++: std::midpoint rounds toward its first argument, so midpoint(high, low) is the overflow-free round-up a last-true search needs

*Stdlib and ecosystem gems*

**Did you know**

`std::midpoint` (C++20, `<numeric>`) is not symmetric. For integers, cppreference: "if the sum is odd, the result is rounded towards `a`", so `midpoint(2, 5)` is 3 and `midpoint(5, 2)` is 4. The pointer overload follows the same rule. That asymmetry is a feature. A binary search for the *last* index where a predicate holds keeps `mid` in the surviving half (`low = mid`), so `mid` must round up or the loop stops making progress. `midpoint(high, low)` rounds up, and unlike the hand-rolled `(low + high + 1) / 2` it cannot wrap. Rust's `u32::midpoint` (1.85) and `i32::midpoint` (1.87) are symmetric and always round toward zero, so Rust has no argument-order spelling of a round-up at all. Support: libstdc++ 9, libc++ 9, MSVC STL 19.28; feature macro `__cpp_lib_interpolate` 201902.

**Show me**

```cpp
#include <cstdint>
#include <cstdio>
#include <initializer_list>  // GCC needs it for the range-for over {7u, 9u, ...}; Apple clang did not
#include <numeric>

// Largest index in [low, high] where is_ok holds; is_ok(low) is known true.
// The kept half includes mid, so mid has to round UP or low stops moving.
template <class Pred>
std::uint32_t last_ok(std::uint32_t low, std::uint32_t high, Pred is_ok, bool round_up) {
    int steps = 0;
    while (low < high) {
        if (++steps > 64) return UINT32_MAX;  // demo tripwire: a u32 range needs at most 32 steps
        // midpoint rounds toward its FIRST argument, so argument order picks the direction.
        std::uint32_t mid = round_up ? std::midpoint(high, low) : std::midpoint(low, high);
        if (is_ok(mid)) low = mid; else high = mid - 1;
    }
    return low;
}

int main() {
    for (std::uint32_t threshold : {7u, 9u, 4'294'967'000u}) {
        auto at_most = [threshold](std::uint32_t value) { return value <= threshold; };
        std::uint32_t upper = threshold < 100 ? 10u : UINT32_MAX;
        std::printf("threshold %u: midpoint(high, low) -> %u, midpoint(low, high) -> %u\n",
                    threshold, last_ok(0, upper, at_most, true), last_ok(0, upper, at_most, false));
    }
    // Output: 7 -> 7 / 7, 9 -> 9 / 4294967295 (tripwire), 4294967000 -> 4294967000 / tripwire.
    // The hand-rolled round-up wraps near the top; midpoint does not.
    std::uint32_t low = 4'000'000'000u, high = UINT32_MAX;
    std::printf("(low + high + 1) / 2 = %u, midpoint(high, low) = %u\n",   // 2000000000 vs 4147483648
                (low + high + 1) / 2, std::midpoint(high, low));
}
```

**Why it matters**

The `midpoint(low, high)` bug is position-dependent. Threshold 7 terminates and threshold 9 spins forever, so a test suite with a few happy values passes and a production input that lands on `low + 1 == high` with `is_ok(low + 1)` true pins a core. In Rust the same search needs `low.midpoint(high) + 1` or a different loop invariant, and the type system cannot tell you which one you needed. F# and C# have no library midpoint; `(low + high) / 2` there wraps silently on `int` unless the arithmetic is `Checked`.

**Chew on this**

Every binary search you own picks an invariant, `[low, high)` or `[low, high]`, keep-mid-low or keep-mid-high. How many of them chose it on purpose, and how many inherited it from whichever spelling of the midpoint was typed first?

## F#: = says two NaN records differ and .Equals says they match, so List.distinct and HashSet dedupe the same list differently

*Idioms and antipatterns*

**Did you know**

F# runs two equalities at once. The `=` operator uses PER semantics, where `nan <> nan`, and structural equality carries that into every record, tuple and list that contains a float. `.Equals` and `compare` use ER semantics, where NaN matches NaN. FSharp.Core says so in its own comparer names (`fsEqualityComparerUnlimitedHashingPER` / `...ER`). So the collection you choose picks the semantics for you. `List.distinct` is built on `HashIdentity.Structural` (PER) and keeps both NaN readings. `HashSet<_>()` and `Dictionary<_,_>()` use `EqualityComparer.Default`, which calls `.Equals` (ER), and keep one. `Set` uses `compare` and also keeps one.

**Show me**

```fsharp
open System.Collections.Generic

type Reading = { sensor: string; value: float }

// Two readings from a sensor that reports "no value" as NaN.
let first = { sensor = "temp"; value = nan }
let second = { sensor = "temp"; value = nan }

// The = operator uses PER semantics: NaN is not equal to itself, so neither is the record.
printfn "first = second       %b" (first = second)            // false
// .Equals uses ER semantics: NaN equals NaN, so the record does too.
printfn "first.Equals second  %b" (first.Equals second)       // true
printfn "compare              %d" (compare first second)      // 0

// Three "remove duplicates" spellings, three comparers:
let by_distinct = List.distinct [first; second]               // HashIdentity.Structural (PER)
let by_hashset = HashSet<Reading>([first; second])            // EqualityComparer.Default -> .Equals (ER)
let by_set = Set.ofList [first; second]                       // compare (ER for NaN)
printfn "distinct %d, HashSet %d, Set %d"
    by_distinct.Length by_hashset.Count by_set.Count          // 2, 1, 1

// The same split in lookups: contains says no, a Dictionary key says yes.
printfn "List.contains        %b" (List.contains first [second])   // false
let last_seen = Dictionary<Reading, int>()
last_seen[first] <- 1
printfn "ContainsKey second   %b" (last_seen.ContainsKey second)   // true
```

**Why it matters**

A refactor that swaps `List.distinct` for a `HashSet`, or `List.contains` for a `Dictionary` lookup "for speed", changes the answer for every record holding a NaN. No type changes, no warning appears, and a test without NaN fixtures never sees it. The other languages each pick one side. Rust refuses: `f64` is not `Eq`, so `HashSet<Reading>` with an `f64` field does not compile until you choose `total_cmp` or a wrapper. JavaScript mixes them per method: `[NaN].includes(NaN)` is true (SameValueZero) while `[NaN].indexOf(NaN)` is -1 (strict equality), measured on Node 22.23.4 on Linux (and Node 22.17.1 on macOS).

**Chew on this**

Which of your records holds a float that can be NaN, such as a missing sensor value, a 0/0 ratio or a parsed "NaN" string, and which equality does each place that compares it actually use? Would you rather NaN rows merge or multiply?

## TypeScript: ReturnType and Parameters read only the last overload, so a generic wrapper silently drops every other one

*Type system deep cuts*

**Did you know**

The handbook states it in one sentence: "When inferring from a type with multiple call signatures (such as the type of an overloaded function), inferences are made from the *last* signature." `Parameters<typeof load_user>`, `ReturnType<typeof load_user>`, and any generic `<Args, Result>(target: (...args: Args) => Result)` wrapper all see one signature, the last one. Wrap an overloaded function in a timing, retry or logging helper, and every overload but the last disappears from the wrapper's type. Overload *order* is therefore part of the public type: swapping two declarations flips what `ReturnType` reports, with no change to the implementation.

**Show me**

```typescript
// Overloads: a single id gets one row, an array of ids gets many.
function load_user(user_id: string): { name: string };
function load_user(user_ids: readonly string[]): { name: string }[];
function load_user(arg: string | readonly string[]): { name: string } | { name: string }[] {
    return typeof arg === "string" ? { name: arg } : arg.map((user_id) => ({ name: user_id }));
}

// Inference from an overloaded function's type uses the LAST signature only.
type LoadArgs = Parameters<typeof load_user>;      // [user_ids: readonly string[]]
type LoadResult = ReturnType<typeof load_user>;    // { name: string }[]

// A generic "add timing" wrapper built the usual way silently drops the string form.
function timed<Args extends unknown[], Result>(
    target: (...args: Args) => Result,
): (...args: Args) => Result {
    return (...args) => {
        const started = performance.now();
        try { return target(...args); }
        finally { console.log(`took ${performance.now() - started} ms`); }
    };
}

const timed_load = timed(load_user);
const many = timed_load(["ada", "linus"]);   // fine: matches the last overload
const one = timed_load("ada");               // error TS2345: 'string' is not assignable to 'readonly string[]'
```

**Why it matters**

The failure is loud here only because the dropped overload is the one a caller uses. If the last overload is a catch-all union (the shape the handbook calls "presumably the most permissive"), the wrapper compiles everywhere and quietly widens every return to the union, so callers start narrowing values the original API typed precisely. Elsewhere it plays out differently. C++ refuses to pick one: `decltype(&load_user)` on an overload set is ill-formed, so you must `static_cast` to a specific signature, which makes the choice visible. Rust has no overloading at all. F# allows overloads only on methods, and passing one as a function value needs an annotation to choose.

**Chew on this**

Which of your helpers (`retry`, `memoize`, `withSpan`, a mocked `jest.fn` typed off `typeof real`) wraps something with overloads? Does the catch-all you put last exist for callers, or only so the implementation type-checks?

**Sources**

- https://www.typescriptlang.org/docs/handbook/2/conditional-types.html (Inferring Within Conditional Types)
- https://www.typescriptlang.org/docs/handbook/2/functions.html#function-overloads

# The functional angle: max is a fold only when its operator is associative, and NaN makes every language's default max depend on where the NaN sits

Draws on the F# tip (NaN equality) and the C++ tip (argument order deciding the answer). The functional claim "a max is `reduce max`, so order does not matter" holds only if the binary operator is associative and commutative. Under IEEE NaN, most defaults are neither. Each row below was run on the inputs `[1, NaN, 2]`, `[NaN, 1, 2]` and `[1, 2, NaN]`, on Linux (GCC 14.2, rustc 1.99.1, .NET 10.0.13, Node 22.23.4), with the same results on macOS as a separate confirmation.

```fsharp
List.max [1.0; nan; 2.0]          // 2.0
List.max [nan; 1.0; 2.0]          // nan   (NaN wins only when it is first)
List.reduce max [1.0; nan; 2.0]   // nan   (max itself propagates NaN, either side)
```

```rust
readings.iter().copied().fold(f64::NEG_INFINITY, f64::max)  // 2 for all three orders: f64::max drops NaN
readings.iter().copied().max_by(f64::total_cmp)             // NaN for all three: total order, +NaN is largest
// readings.iter().max() does not compile: f64 is not Ord.
```

```cpp
std::ranges::max(readings);  // 2, nan, 2: < on NaN is not a strict weak order (a precondition violation)
std::accumulate(begin, end, -INFINITY, [](double acc, double value) { return std::fmax(acc, value); });  // 2 always
```

```typescript
Math.max(...readings);                                          // NaN for all three
readings.reduce((best, value) => (value > best ? value : best)); // 2, NaN, 2
```

| Language | Functional form | Result on the three orders | What it costs |
| --- | --- | --- | --- |
| F# | `List.max` vs `List.reduce max` | 2, NaN, 2 vs NaN, NaN, NaN | the two "same" spellings disagree; neither is documented for NaN |
| Rust | `fold(f64::max)` / `max_by(total_cmp)` | 2, 2, 2 / NaN, NaN, NaN | nothing hidden: you must pick one, because `max()` will not compile |
| C++ | `ranges::max` / `fold(fmax)` | 2, nan, 2 / 2, 2, 2 | the default is a precondition violation; `fmax` is the lawful one |
| TypeScript | `Math.max` / `reduce(>)` | NaN, NaN, NaN / 2, NaN, 2 | the built-in is lawful (NaN-absorbing); the hand-written reduce is not |

Rust is the only row where the order-dependent version cannot be typed by accident. Everywhere else, the lawful operator exists (`fmax`, `Math.max`, `max` as a reducer in F#) and the default spelling is not it. Parallelism is where this stops being academic. `std::reduce` with an execution policy, PLINQ `Aggregate` and a chunked `rayon` fold all regroup the operands, and that is exactly what a non-associative operator cannot tolerate.

Left open: when your aggregate is "max latency over the window", is a NaN sample the answer, noise to skip, or an alarm? And does the spelling you used encode that choice, or only happen to?

# The security angle: the midpoint is attacker-chosen arithmetic, and the two classic failures are a wrapped index and a loop that never exits

Mode B, interrogating the C++ tip. It runs in both directions: `std::midpoint` prevents one failure class and its argument order creates another.

The insecure sample is ordinary code that passes review:

```cpp
// "Standard" binary search over a sorted index of record offsets.
std::uint32_t mid = (low + high) / 2;   // CWE-190: wraps once low + high > UINT32_MAX
// for a last-true search:
std::uint32_t mid = std::midpoint(low, high);  // CWE-835: never advances when high == low + 1 and is_ok(mid)
```

The first is the bug Google reported in 2006 in nearly every textbook binary search, Java's `Arrays.binarySearch` included. Measured on Linux (re-run 2026-10-23, same numbers as the original macOS run), with `low = 4000000000`, `high = 4200000000`: C++ `uint32_t` gives 1952516352, a wrapped index. Rust release gives the same 1952516352 silently, and Rust debug panics with "attempt to add with overflow". F# `int` gives -97483648 unless `Checked.(+)` is used, which throws `OverflowException`. JavaScript cannot overflow a double, but the idiom `(low + high) >>> 1` truncates to 32 bits: with `low = 3e9`, `high = 3.2e9` it returned 952516352 where `Math.floor` gives 3100000000. Past 2^53, `Math.floor((low + high) / 2)` is off by one (9007199254740990 vs the exact ...989), the same rounding the 2026-10-13 TypeScript tip found in 64-bit ids.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | unsigned wrap (signed overflow is UB) | `std::midpoint` cannot overflow | its argument order; a spin is a DoS when the search key is a request field |
| Rust | wrap in release, panic in debug | `midpoint` (1.85 / 1.87) cannot overflow | `overflow-checks = true` in the release profile if a panic beats a wrong index |
| F# | silent `int` wrap | `open Checked` makes `+` throw | choosing checked arithmetic per module; no library midpoint |
| TypeScript | `>>> 1` truncation; imprecision above 2^53 | none, numbers are doubles | `Math.floor`, or `BigInt` for offsets that can exceed 2^53 |

The control here is Rust's debug build: it is the only row where the wrapped index cannot reach the array access unnoticed. The rest of the table is about how far the bad index travels before something notices. A wrapped `mid` in C++ reads the wrong record, and a bounds-checked access in Rust or .NET turns it into a crash. Both outcomes are worse than a wrong answer when the search key comes from a client.

Left open: which of your binary searches runs over a range sized by the input (a file length, a byte offset, a timestamp) rather than by an in-memory array's length, which keeps `low + high` safe by accident?
