## Rust: `collect::<Rc<[T]>>()` allocates once only when the iterator knows its exact length, and a `filter` goes through a `Vec` that peaks at 2.5x

*Perf and memory model*

**Did you know**

`Rc<[T]>` and `Arc<[T]>` need room for two counters in front of the elements, so they can never adopt a `Vec`'s buffer. When the iterator implements the unstable `TrustedLen` trait (ranges, `slice::iter`, `map` and `chain` over those), std allocates the `Rc` once and writes the elements straight in. Anything else, `filter` included, is collected into a `Vec` first and then copied. With 100,000 `u64`s filtered down to 85,714, that cost 2 allocations, 15 reallocations and a peak of 1,734,304 live bytes for a result that keeps 685,728.

**Show me**

```rust
// rustc 1.99.1, Debian. Counts below come from a counting #[global_allocator]
// (not shown); n = 100_000 u64 is 800,000 bytes, and Rc adds a 16-byte header.
use std::rc::Rc;

fn main() {
    let count: u64 = 100_000;
    let readings: Vec<u64> = (0..count).collect();

    // Exact length known up front (TrustedLen): std allocates the Rc once
    // and writes the elements straight into it.
    let doubled: Rc<[u64]> = (0..count).map(|id| id * 2).collect(); // 1 alloc, 800,016 B
    let copied: Rc<[u64]> = readings.iter().copied().collect(); // 1 alloc, 800,016 B
    let joined: Rc<[u64]> = (0..count / 2).chain(count / 2..count).collect(); // 1 alloc

    // filter cannot know its length, so std collects into a Vec first:
    // 15 reallocs while the Vec doubles to 131,072 slots (1 MiB), then a
    // second allocation for the Rc (685,728 B for 85,714 kept) and a copy.
    // Peak live: 1,734,304 B, 2.5x what the Rc keeps.
    let kept: Rc<[u64]> = (0..count).filter(|reading| reading % 7 != 3).collect();

    println!("{} {} {} {}", doubled.len(), copied.len(), joined.len(), kept.len());
}
```

**Why it matters**

A common way to publish a read-only snapshot to many tasks is to filter rows into an `Arc<[Row]>`, and `Arc` measured the same as `Rc` in the keep-all case: 2 allocations, 15 reallocations, a 1,848,592-byte peak. Under a container memory limit the snapshot builder briefly needs room for the doubling `Vec` and the final copy at once. C++ has no collect step to compare against: C++20's `std::make_shared<T[]>(n)` takes the element count before it allocates, so working out the filtered length is your job there.

**Chew on this**

Which of your shared snapshots are built from a `filter`, and how large is the biggest one at the moment it is rebuilt? If you counted the survivors first and then filled an exact-size allocation, would the second pass over the source cost more than the copy it saves?

**Sources**

- https://doc.rust-lang.org/std/rc/struct.Rc.html#impl-FromIterator%3CT%3E-for-Rc%3C%5BT%5D%3E
- https://doc.rust-lang.org/std/sync/struct.Arc.html#impl-FromIterator%3CT%3E-for-Arc%3C%5BT%5D%3E
- https://doc.rust-lang.org/std/iter/trait.TrustedLen.html

**Verified**

The doc passages were read through a page summary because the fetched text was truncated, and the measurements agree with them. The C++ `make_shared<T[]>` remark is from documentation and was not run.

**Gotchas**

- A filter that keeps everything still goes through the `Vec`: `(0..n).filter(|_| true)` measured 2 allocations, 15 reallocations and a 1,848,592-byte peak for 800,016 bytes kept.
- `Rc::from(vec)` is never a move, even when the `Vec`'s capacity is exact. The buffer has no room for the counters, so it is a new allocation plus a copy (`Rc::from(readings.clone())` measured 2 allocations and 1,600,016 bytes, one of them the clone).
- Debug and `-O` builds gave identical counts. The choice happens inside std's `FromIterator` impl, so the optimizer cannot remove the `Vec`.

## C++: a `double` template argument is compared by identity, not by `==`, so `amplifier<0.0>` and `amplifier<-0.0>` are two types, and a NaN matches only a NaN with the same bits

*Type system deep cuts*

**Did you know**

C++20 (P1907R1) allows floating-point non-type template parameters, and two arguments name the same specialization only when their "values are identical" ([temp.type]/2.2), not when they compare equal. `0.0 == -0.0` is true, yet `amplifier<0.0>` and `amplifier<-0.0>` are two types, each with its own statics. `NaN == NaN` is false, yet naming the same NaN twice gives one type, while a NaN with a different payload or sign bit gives another. Apple clang 21 and GCC 16.2.0 agree on every line.

**Show me**

```cpp
// C++20 (P1907R1). Apple clang 21 and GCC 16.2 agree on every line.
#include <cstdio>
#include <limits>
#include <type_traits>

template <double gain>
struct amplifier {
    static inline int instances = 0;  // one counter per specialization
    amplifier() { ++instances; }
};

int main() {
    constexpr double positive_zero = 0.0;
    constexpr double negative_zero = -0.0;
    constexpr double quiet_nan = std::numeric_limits<double>::quiet_NaN();

    std::printf("%d\n", positive_zero == negative_zero);  // 1: equal values
    std::printf("%d\n", std::is_same_v<amplifier<positive_zero>,
                                       amplifier<negative_zero>>);  // 0: two types

    std::printf("%d\n", quiet_nan == quiet_nan);  // 0: NaN is unequal to itself
    std::printf("%d\n", std::is_same_v<amplifier<quiet_nan>,
                                       amplifier<quiet_nan>>);  // 1: one type

    amplifier<positive_zero> left_channel;
    amplifier<negative_zero> right_channel;  // a second static counter
    std::printf("%d %d\n", amplifier<positive_zero>::instances,
                amplifier<negative_zero>::instances);  // 1 1, not 2

    // Rust has no analogue: a const generic may only be an integer, char or
    // bool, so `struct Amplifier<const GAIN: f64>;` is rejected outright.
}
```

**Why it matters**

A template keyed on a tuning constant (a gain, a threshold, a rate) turns every distinct bit pattern into a separate type with its own registry, cache or singleton. A `-0.0` from `-1.0 * 0.0` in a `constexpr` config silently gets a second copy of all of them (measured: it names the same type as `amplifier<-0.0>`, not `amplifier<0.0>`). Rust avoids the question by refusing `f64` const generics (`` `f64` is forbidden as the type of a const generic parameter ``, rustc 1.99.1). TypeScript's `Object.is` uses the same identity: `Object.is(0, -0)` is false and `Object.is(NaN, NaN)` is true.

**Chew on this**

Which of your templates take a value that started life as arithmetic rather than as a literal? If two translation units compute the "same" constant along different paths, how would you notice that they instantiated different types?

**Sources**

- https://eel.is/c++draft/temp.type#2.2
- https://en.cppreference.com/w/cpp/language/template_parameters
- https://en.cppreference.com/w/cpp/compiler_support/20
- https://doc.rust-lang.org/reference/items/generics.html#const-generics

**Verified**

cppreference lists GCC 11, Clang 18 (partial) and MSVC 19.26 for P1907R1; only clang 21 and GCC 16.2 were run, and GCC with `-std=c++17` rejects a `double` parameter outright. The NaN payload and sign cases used `std::bit_cast` from `0x7ff8000000000001` and `0xfff8000000000000`. The TypeScript `Object.is` values were run on Node 22.17.1.

**Gotchas**

- `amplifier<1>` and `amplifier<1.5f>` do not compile. A template argument is a converted constant expression, and both compilers refused `int` to `double` and `float` to `double` with `-std=c++20`, `c++23` and `c++26` alike ("conversion from 'float' to 'double' is not allowed in a converted constant expression"). Write `1.0`.
- `amplifier<0.1 + 0.2>` and `amplifier<0.3>` are different types, because the two values differ in the last bit.
- `template <auto>` makes the argument's type part of its identity too: `bounded<1>`, `bounded<1u>` and `bounded<1L>` are three different types.

## F#: `raise caught` drops the throw site inside `task { }` and keeps it inside `async { }`, and F# 11's preview finally accepts `reraise ()` in both

*New discoveries and currently popular patterns*

**Did you know**

`reraise ()` in a computation expression handler is error FS0413 in F# 10, because the `with` block is a lambda handed to the builder, not a real .NET handler, so people write `raise caught`. Inside `task { }` that restarts the stack trace at the `raise` line, and the frame that threw is gone. Inside `async { }` the frame survives, because FSharp.Core keeps a `ConditionalWeakTable` from each exception to its saved `ExceptionDispatchInfo` and restores it on the rethrow. [dotnet/fsharp#20405](https://github.com/dotnet/fsharp/pull/20405), merged 2026-09-21 and in the .NET 11 RC 2 release notes, lowers `reraise ()` there to `ExceptionDispatchInfo.Capture(e).Throw()` behind `--langversion:preview`.

**Show me**

```fsharp
// SDK 10.0.403 (F# 10, FSharp.Core 10.1.0.0) and SDK 11.0.100-rc.3 (F# 11)
open System
open System.Runtime.CompilerServices
open System.Runtime.ExceptionServices

[<MethodImpl(MethodImplOptions.NoInlining)>]
let parse_order (payload: string) : int =
    raise (FormatException("bad order " + payload)) // the frame you want in the log

let load_task (payload: string) =
    task {
        try
            return parse_order payload
        with caught ->
            return raise caught // trace restarts here: parse_order is gone
    }

let load_task_kept (payload: string) =
    task {
        try
            return parse_order payload
        with caught ->
            ExceptionDispatchInfo.Capture(caught).Throw() // F# 10 workaround: kept
            return 0
    }

let load_async (payload: string) =
    async {
        try
            return parse_order payload
        with caught ->
            return raise caught // kept: FSharp.Core restores the saved trace
    }

// `return reraise ()` in any handler above: F# 10 says FS0413, F# 11 says
// FS3350 unless --langversion:preview, which compiles it to the
// ExceptionDispatchInfo line and keeps parse_order in task and async alike.
```

**Why it matters**

The usual pattern in a service is to log and rethrow in a handler, and the log that matters is the one that names the function that failed. Moving a handler from `async { }` to `task { }` (a common migration for throughput) silently removes that frame if the handler used `raise caught`. C# draws the same line with `throw;` against `throw ex;`. TypeScript does not have the problem at all, because an `Error`'s `stack` is captured when it is constructed: a rethrown error kept its original function on Node 22.

**Chew on this**

How many `with ex -> ... raise ex` handlers sit inside `task { }` in your codebase, and would any of your logs tell you the frame was missing? Once `reraise ()` works everywhere, is the explicit `ExceptionDispatchInfo` call still worth keeping for readers who do not know about the lowering?

**Sources**

- https://github.com/dotnet/fsharp/pull/20405
- https://github.com/dotnet/core/blob/main/release-notes/11.0/preview/rc2/fsharp.md
- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/async.fs
- https://learn.microsoft.com/en-us/dotnet/api/system.runtime.exceptionservices.exceptiondispatchinfo

**Verified**

Versions: F# 10, FSharp.Core 10.1.0.0, SDK 10.0.403 (.NET 10.0.14); F# 11, FSharp.Core 11.0.0.0, SDK 11.0.100-rc.3. Run with `dotnet fsi` on SDK 8.0.401 (macOS), on `mcr.microsoft.com/dotnet/sdk:10.0` (Ubuntu 24.04, not Debian), and on `mcr.microsoft.com/dotnet/nightly/sdk:11.0` (Ubuntu 26.04, a release candidate rather than a GA runtime). The C# statement is from documentation and was not run.

**Gotchas**

- On the F# 11 SDK without preview, the error is no longer FS0413 but FS3350 ("Feature 'calls to 'reraise' in a computation expression handler' is not available in F# 11.0"), so a build log on the new SDK names a different code.
- Outside any computation expression, `raise caught` drops the frame too (measured on all three SDKs). Only `reraise ()` keeps it there.
- A throwing function that ends in `failwithf` may leave no frame of its own, which makes every case look broken. With `failwithf`, even plain `reraise ()` gave a trace starting in FSharp.Core's printf closure, `NoInlining` or not. Only `raise (FormatException ...)` put `parse_order` in the trace. Whether the call was inlined or tail-called was not determined.

## TypeScript: `template.replace("{name}", display_name)` expands `$&`, `` $` `` and `$'` inside `display_name`, and only a function replacement is literal

*Idioms and antipatterns*

**Did you know**

The second argument of `String.prototype.replace` is a replacement template even when the pattern is a plain string. `$$` becomes `$`, `$&` becomes the matched text, `` $` `` the text before the match, and `$'` the text after it. So filling a placeholder with a user's display name lets the name rewrite the result: `"$'"` copies the rest of the template into the slot. A function in that position has its return value inserted as-is. `replaceAll` takes the same templates. tsc 7.0.2 with `--strict` reports nothing, because the parameter is just `string`.

**Show me**

```ts
// Node 26.13.0 and 22.17.1, tsc 7.0.2 --strict: no diagnostic on any line.
const greeting_template: string = "Hello {name}, your order is ready."

// The second argument is a replacement TEMPLATE, even when the pattern is a
// plain string: $$, $&, $` and $' are expanded inside display_name.
const fn_render = (display_name: string): string =>
    greeting_template.replace("{name}", display_name)

console.log(fn_render("Ann"))   // Hello Ann, your order is ready.
console.log(fn_render("Ann$$")) // Hello Ann$, your order is ready.
console.log(fn_render("$&"))    // Hello {name}, your order is ready.
console.log(fn_render("$`"))    // Hello Hello , your order is ready.
console.log(fn_render("$'"))    // Hello , your order is ready., your order is ready.

// A function's return value is inserted as-is: no pattern is expanded.
const fn_render_literal = (display_name: string): string =>
    greeting_template.replace("{name}", () => display_name)

console.log(fn_render_literal("$'")) // Hello $', your order is ready.
```

**Why it matters**

Hand-rolled templates for emails, notifications and log lines are usually exactly this one `replace` call, and the data that fills them is often user-supplied. Nothing crashes. The message just stops saying what the code says, and `Ann$$` quietly becomes `Ann$`. Rust's `str::replace` and .NET's `String.Replace` are literal. Their regex replace functions template the replacement like JavaScript's does, with different syntax for it (see the security angle below).

**Chew on this**

Where in your code does a value you do not control reach the second argument of `replace` or `replaceAll`? If a wrapper that always passes a function is the fix, what stops the next person from calling `replace` directly?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/replace
- https://tc39.es/ecma262/multipage/text-processing.html#sec-getsubstitution

**Verified**

The tc39 `GetSubstitution` text was too large to fetch, so the behavior rests on MDN and on the runs above.

**Gotchas**

- `$1` and `$<who>` stay literal when the pattern is a string, because there are no capture groups. With a RegExp pattern they expand: `/\{(?<who>name)\}/` with `"[$1|$<who>]"` gave `[name|name]`.
- `replaceAll` expands too: `"a.b.c".replaceAll(".", "$&$&")` is `"a..b..c"`.
- `split` then `join` is literal: `template.split("{name}").join("$&")` gave `Hello $&, your order is ready.`

**Related**

# The functional angle: an error value keeps where it was made, and an exception keeps where it was last thrown

Draws on the F# tip. The functional move is to make the failure a value. A value carries whatever it recorded when it was created, and no amount of passing it along can lose that.

```rust
// Rust, rustc 1.99.1: the trace lives in the error value, so `?` cannot drop it.
use std::backtrace::Backtrace;

struct OrderError {
    message: String,
    trace: Backtrace, // captured once, where the failure happened
}

#[inline(never)]
fn parse_order(payload: &str) -> Result<i32, OrderError> {
    Err(OrderError { message: format!("bad order {payload}"), trace: Backtrace::force_capture() })
}

fn load(payload: &str) -> Result<i32, OrderError> {
    let parsed = parse_order(payload)?; // moves the value up; the trace goes with it
    Ok(parsed)
}
// load("x").unwrap_err().trace names parse_order: true in debug and in -O.
```

```ts
// TypeScript, Node 22.17.1: an Error's stack is fixed when it is constructed.
function parse_order(payload: string): never { throw new Error("bad order " + payload) }
function load(payload: string): number {
    try { return parse_order(payload) } catch (caught) { throw caught } // stack still names parse_order
}
```

| Language | How the failure travels | Where the trace comes from | What it costs |
| --- | --- | --- | --- |
| F# | exception through `task` / `async` | the last `raise` in `task`; the saved original in `async` | `ExceptionDispatchInfo.Capture(e).Throw()` today, preview `reraise ()` in F# 11; a `Result` carries no trace unless you store one |
| Rust | `Result<T, E>` through `?` | wherever the error value captured a `Backtrace` | opt-in, one capture per error value; `?` moves it and kept the origin in debug and `-O` |
| TypeScript | thrown `Error` | the `new Error(...)` call | nothing: `throw caught` kept `parse_order` |
| C++ | `throw;` or `throw caught;` | none: `std::exception` holds no trace | C++23 `std::stacktrace::current()` captured by hand (not measured) |

Only F#'s `task` loses an origin it had, because the trace belongs to the throw and not to the value. The Rust row keeps it by construction, which is the case for returning a `Result` from your own code in F# too.

Which failures in your services are exceptions only because a library threw them, and which ones would read better as values you return?

# The security angle: a replacement string is a template, so a chosen name can erase itself from an audit line

Draws on the TypeScript tip. It runs in the "does not prevent" direction: none of the four languages stops user text from reaching a templated replacement, and only some offer a literal form at all.

```ts
// TypeScript, Node 22.17.1. Looks like a log formatter. The actor controls a template.
const fn_audit_line = (actor: string, target: string): string =>
    "{actor} deleted {target}".replace("{actor}", actor).replace("{target}", target)

fn_audit_line("mallory", "post-42") // "mallory deleted post-42"
fn_audit_line("$&", "post-42")      // "{actor} deleted post-42": nobody did it
fn_audit_line("$'", "post-42")      // " deleted post-42 deleted {target}"

// Literal: a function's return value is never expanded.
const fn_audit_line_literal = (actor: string, target: string): string =>
    "{actor} deleted {target}".replace("{actor}", () => actor).replace("{target}", () => target)

fn_audit_line_literal("$&", "post-42") // "$& deleted post-42"
```

The defect is log integrity: [CWE-117](https://cwe.mitre.org/data/definitions/117.html) (improper output neutralization for logs), a child of [CWE-116](https://cwe.mitre.org/data/definitions/116.html) (improper encoding or escaping of output). The line still parses and still looks like a template bug, which is why it survives review.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | `replace` / `replaceAll` with a string replacement expand `$&`, `` $` ``, `$'`, `$$`, even with a string pattern | nothing: the parameter is `string`, tsc 7.0.2 `--strict` is silent | pass `() => value` |
| Rust | `regex` 1.13.1 `Regex::replace` expands `$0` and `$name`; `$&` stays literal | `str::replace` is literal; `NoExpand(...)` and a closure replacer are literal | wrap user text in `NoExpand` |
| C++ | `std::regex_replace` expanded `$&` on libc++ (clang 21) and libstdc++ (GCC 16) | std has no literal flag: `format_literal` is Boost's, and both compilers rejected it | `std::string::find` plus `replace`, or a `regex_iterator` loop |
| F# / .NET | `Regex.Replace` expands `$&` | `String.Replace` is literal, a `MatchEvaluator` is literal | a `MatchEvaluator`, or escape `$` as `$$` first |

The baseline for this class is C++, because it is the one row with no literal mode in its standard regex API. Every other language at least ships the safe spelling.

Which of your log, email and notification formatters fill a placeholder with something a user typed, and how many of them call a regex API?
