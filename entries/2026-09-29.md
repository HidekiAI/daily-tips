## Rust: two captureless closures unify to a `fn` pointer, and capturing one `()` breaks the whole array

*Type system deep cuts*

**Did you know**

Every closure has its own anonymous type, yet `[|x: i32| x + 1, |x: i32| x * 2]` compiles, and its type is `[fn(i32) -> i32; 2]`. Array literals, `if`/`else`, and `match` arms run a least-upper-bound coercion, and closures that capture nothing coerce to a function pointer as part of it. Capture anything in one element and the coercion is off for all of them: E0308, "no two closures, even if identical, have the same type". Size does not matter. A closure capturing a zero-sized `()` is 0 bytes and still refuses to become a `fn`.

**Show me**

```rust
// rustc 1.95.0, --edition 2024
fn pick(flag: bool) -> fn(i32) -> i32 {
    // Two distinct closure types. The if/else LUB coerces both to fn(i32) -> i32.
    if flag { |x| x + 1 } else { |x| x * 2 }
}

fn main() {
    let ops = [|x: i32| x + 1, |x: i32| x * 2, |x: i32| x - 3];
    // type_name_of_val(&ops)       -> [fn(i32) -> i32; 3]
    let v = vec![|x: i32| x + 1, |x: i32| x * 2];
    // type_name_of_val(&v)         -> Vec<fn(i32) -> i32>
    println!("{} {} {}", pick(true)(10), ops[2](10), v[1](10)); // 11 7 20

    let k = 5;
    // let bad = [|x: i32| x + 1, |x: i32| x * k];
    //   error[E0308]: expected closure, found a different closure
    //   note: no two closures, even if identical, have the same type

    let unit = ();
    let z = move |x: i32| { let u = unit; let _ = u; x };
    // size_of_val(&z) == 0, and still:
    // let f: fn(i32) -> i32 = z;   // E0308: expected fn pointer, found closure
    let _ = (k, z);
}
```

**Why it matters**

A dispatch table of handlers written as closures is a `fn`-pointer table by accident, and the first refactor that makes one handler read a config value or a metrics handle breaks the table's type, with the error pointing at the literal rather than the new capture. C++ agrees on half of this: Apple clang 21 accepts `cond ? [](int x){...} : [](int x){...}` through the built-in conditional-operator candidates, but `auto il = {lambda1, lambda2}` fails with "deduced conflicting types", so the braced list needs the pointer type spelled out. F# never has the problem: every closure is an `FSharpFunc<int, int>` subclass, so a list mixing capturing and captureless lambdas is one type and every call is a virtual `Invoke`.

**Chew on this**

When one handler needs context, do you box the whole table into `Box<dyn Fn>`, or change the `fn` signature so the context is a parameter and the table stays captureless? Which of your tables are `fn` pointers today without anyone having chosen it?

**Sources**

- https://doc.rust-lang.org/reference/type-coercions.html#least-upper-bound-coercions
- https://doc.rust-lang.org/reference/types/closure.html
- https://eel.is/c++draft/expr.prim.lambda.closure

## C++: libc++ 22 made `multimap::find` return any equal element, and for four months `extract(k)` followed it off the standard

*New discoveries and currently popular patterns*

**Did you know**

Since LLVM 22.1.0 (2026-02-24), libc++'s `__tree::find` stops at the first equal node it meets on the way down (PR #152370), instead of walking to the lower bound. For `map` and `set` nothing changes. For `multimap` and `multiset`, `find(k)` now returns whichever equal element sits highest in the red-black tree: the 2nd of 7, the 32nd of 100. The standard allows it: `find` returns "an element with the key equivalent to k". It broke Qt 6's `QMultiMap::value` anyway (issue #193311, 2026-04-21, closed "this is a Qt bug"). `extract(k)` is different: the standard says "removes the **first** element", but libc++ 22.1.0 through 22.1.6 routed it through the same `find`. Fixed in PR #199703, backported to 22.1.7 (2026-06-02). libstdc++ and MSVC STL still implement `find` as lower bound plus compare.

**Show me**

```cpp
// clang++ -std=c++23 -O2  (Apple clang 21, libc++ 220106)
#include <cstdio>
#include <map>

int main() {
    std::multimap<int, int> mm;
    for (int i = 0; i < 7; ++i) mm.emplace(5, i);  // equal keys keep insertion order

    std::printf("find=%d lower_bound=%d\n",
                mm.find(5)->second,                 // 1 on libc++ 22, 0 on libstdc++/MSVC
                mm.lower_bound(5)->second);         // 0 everywhere: this is "the first"

    auto nh = mm.extract(5);
    std::printf("extract=%d\n", nh.mapped());       // 1 here: this SDK's libc++ has the bug
                                                    // 0 on libc++ >= 22.1.7, as the standard says
    // As n grows, find picks: n=3 -> 1, n=8 -> 3, n=100 -> 31
}
```

**Why it matters**

"The first value for this key" is a common reading of `multimap::find` in dedupe, priority, and first-writer-wins code, and it was true on every major implementation until February. It is still true on libstdc++ and MSVC, so the same code gives different answers per platform and nothing warns. Apple's SDK header on this host (dated 2026-08-08) still has the `extract` bug, so "upstream fixed it in June" does not mean your macOS build has it. Rust's `BTreeMap` has no multimap and makes you pick the value container. F#'s `Map` is unique-key only.

**Chew on this**

Which `multimap::find` in your code is really asking for `lower_bound` or `equal_range().first`, and would your tests catch it, given the answer only changes once three or more equal keys exist? How far behind upstream libc++ is the toolchain you ship with?

**Sources**

- https://github.com/llvm/llvm-project/pull/152370
- https://github.com/llvm/llvm-project/issues/193311
- https://github.com/llvm/llvm-project/pull/199703
- https://releases.llvm.org/22.1.0/projects/libcxx/docs/ReleaseNotes.html
- https://eel.is/c++draft/associative.reqmts.general

**Verified**

Run on Apple clang 21 with libc++ 220106 only. libstdc++ (`stl_tree.h`, `_Rb_tree::find`) and MSVC STL (`xtree`, `_Find` via `_Find_lower_bound`) were read from current upstream source, not run. The 22.1.7 fix was read from `release/23.x` and PR #200270, not run.

## F#: a `MailboxProcessor` whose body throws keeps accepting mail, and nothing hears it die

*Stdlib and ecosystem gems*

**Did you know**

`MailboxProcessor` is an actor in FSharp.Core: a private queue, one async loop, no dependency. If the body throws, the exception goes to the agent's `Error` event, and with no subscriber it goes nowhere. The agent is dead, but `Post` still succeeds, the queue grows without limit, and `PostAndReply` blocks forever. Measured: 100,000 posts after the crash, all queued, about 58 bytes each; `TryPostAndReply(..., 500)` returns `None`. The queue has no capacity option at all. Measured on F# 8, FSharp.Core 8.0.0, .NET 8.0.8.

**Show me**

```fsharp
// dotnet fsi (F# 8, FSharp.Core 8.0.0, .NET 8.0.8)
type Msg =
    | Add of int
    | Get of AsyncReplyChannel<int>

let agent =
    MailboxProcessor<Msg>.Start(fun inbox ->
        let rec loop (total: int) = async {
            match! inbox.Receive() with
            | Add n when n < 0 -> return failwith "negative"   // one bad message
            | Add n -> return! loop (total + n)
            | Get ch -> ch.Reply total; return! loop total }
        loop 0)

agent.Post (Add 1)
agent.TryPostAndReply(Get, timeout = 500)   // Some 1
agent.Post (Add -1)                         // agent is now dead; nothing printed
for i in 1 .. 100_000 do agent.Post (Add i) // no exception, no warning
agent.CurrentQueueLength                    // 100000  (about 5.8 MB retained)
agent.TryPostAndReply(Get, timeout = 500)   // None; PostAndReply would hang

// The one line that makes death visible:
// agent.Error.Add(fun e -> log.Error(e, "agent died"))
```

**Why it matters**

An in-process actor is exactly what a long-running service reaches for to serialize access to a cache or a connection, and this one fails like a memory leak rather than a crash. Rust's `std::sync::mpsc` makes the same death loud: when the worker panics its `Receiver` drops, and the next `send` returns `Err(SendError)`, measured. Go and Node go further and take the whole process down on the unrecovered panic or unhandled rejection. C++ ships no channel, so the answer is whatever your library chose.

**Chew on this**

For each agent you run, is the right reaction to a body exception to restart the loop, fail every pending `PostAndReply`, or crash the process? And who is supposed to notice today?

**Sources**

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-control-fsharpmailboxprocessor-1.html
- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/mailbox.fs
- https://doc.rust-lang.org/std/sync/mpsc/struct.Sender.html#method.send

**Verified**

Measured in `dotnet fsi` on .NET 8 only; the byte count is from `GC.GetTotalMemory true` around the posts, one run. Rust row on rustc 1.95.0, Go on 1.24.2, Node on 22.17.1.

## TypeScript: `Effect.cached` memoizes the `Exit`, so a failed first call is the answer forever

*Idioms and antipatterns*

**Did you know**

A `const fetchToken: Effect<...>` is a recipe: `yield*` it twice and the request runs twice. The usual fix is `Effect.cached(fetchToken)`, which gives you an inner effect that runs once and replays. It replays the whole `Exit`, though, not only a success. It stores a `Deferred<A, E>`, so if the first call fails with a 503, every later read fails with that same 503 and the request never runs again. `cachedWithTTL` keeps the failure until the TTL expires. `cachedInvalidateWithTTL` hands you an `invalidate` effect, which is the only way to throw out a cached failure early. The docs do not mention failures at all. Measured on effect 3.22.2.

**Show me**

```ts
// effect 3.22.2, Node 22.17.1
import { Effect } from "effect";

let calls = 0;
const fetchToken: Effect.Effect<string, string> = Effect.suspend(() =>
    ++calls === 1 ? Effect.fail("503") : Effect.succeed(`tok-${calls}`));

// Plain: runs each time.                    -> Failure, Success   calls=2
// Effect.cached: the 503 is memoized.       -> Failure, Failure   calls=1
const cachedRun = Effect.gen(function* () {
    const token = yield* Effect.cached(fetchToken);
    const a = yield* Effect.exit(token);
    const b = yield* Effect.exit(token);   // never re-runs fetchToken
    return [a._tag, b._tag];
});

// cachedWithTTL(fetchToken, "50 millis"): Failure, Failure, then Success after 80 ms.
// cachedInvalidateWithTTL: the escape hatch.
const recoverable = Effect.gen(function* () {
    const [token, invalidate] = yield* Effect.cachedInvalidateWithTTL(fetchToken, "1 hour");
    // This read still fails, but the failure is evicted, so the next read re-runs.
    return yield* token.pipe(Effect.tapError(() => invalidate));
});

// A memoized Promise has the same trap: const p = fetchP(); both awaits reject, calls=1.
```

**Why it matters**

Token fetches, config loads, and connection handshakes are what people cache, and they are also what fails transiently at boot. With `Effect.cached`, one bad second at startup turns into a service that fails every request until restart, and `Effect.retry` around the *inner* effect does nothing, because the retry reads the cache. Put the retry inside the cached effect, or invalidate on failure. F#'s `lazy` has the same default (it rethrows the first exception forever); Rust's `OnceLock::get_or_init` and C++'s `std::call_once` go the other way and retry.

**Chew on this**

Is there an `Effect.cached` or a memoized Promise in your boot path, and does its failure mean "retry later" or "this process is broken"? If a failure should never be cached, is `Effect.cached` still the right tool, or is it a `Ref` with a policy?

**Sources**

- https://effect.website/docs/caching/caching-effects/
- https://github.com/Effect-TS/effect/blob/main/packages/effect/src/internal/effect/circular.ts

**Related**

- [2026-09-24](2026-09-24.md) - TypeScript, "`Effect.all` is sequential unless you say otherwise, and by default it stops starting effects at the first failure". Another Effect default about what happens after the first failure, and another one that runs opposite to the Promise habit.

# The functional angle: every run-once cell has to decide whether a failure is remembered, and the standard libraries split three ways

Draws on the TypeScript tip, with a measured row from each language. The shape: a lazy, run-once value whose initializer fails the first time and would succeed the second time. Purity says evaluating the same thunk twice gives the same answer, so caching the failure is the "functional" choice. Operations says a 503 is not a value.

```rust
static L: LazyLock<u32> = LazyLock::new(flaky);   // 2nd access: panics "previously been poisoned"
static O: OnceLock<u32> = OnceLock::new();
O.get_or_init(flaky);                             // 2nd call: runs flaky again, Ok(2)
```

```cpp
int get() { static int v = flaky(); return v; }  // throw on 1st call: 2nd call re-runs, 2
std::call_once(flag, [&] { out = flaky(); });    // same: an exceptional call does not set the flag
```

```fsharp
let l = lazy (flaky ())   // l.Force() twice: Error "503", Error "503", calls = 1
```

| Language | Run-once form | After a failed first run | What it costs |
| --- | --- | --- | --- |
| F# | `lazy` / `Lazy<T>` | the same exception, forever | the baseline, since `lazy` is F#'s built-in thunk; recovery means a new `Lazy`, so the binding cannot be a plain `let` |
| Rust | `LazyLock` / `OnceLock::get_or_init` | poisoned forever / retried | two cells, two policies; `LazyLock` poisoning is a *different* panic than the one that caused it |
| C++ | function-local `static` / `call_once` | retried / retried | the language chose retry, so a failing initializer runs on every call until it succeeds, with no backoff |
| TypeScript | memoized Promise / `Effect.cached` | the same rejection / the same `Exit`, forever | recovery is manual: rebuild the Promise, or `cachedInvalidateWithTTL` plus an explicit `invalidate` |

The asymmetry: none of these needs `mut` in user code, and the "pure" answer (remember the failure) is what F#, Promise, and Effect give you, while C++ gives the retry answer and Rust ships both. The cost is not in the style, it is in who has to write the retry policy.

Left hanging: for each run-once value in your services, which policy did you actually want, and which one did the cell you picked give you?

# The security angle: a dead consumer with an unbounded queue is an allocator anyone can feed

Draws on the F# tip, and runs in the direction the language does **not** prevent. A crashed `MailboxProcessor` keeps taking `Post`, so every message a client can cause becomes retained memory, and the service fails later and elsewhere, as an out-of-memory. Class: CWE-770 (Allocation of Resources Without Limits or Throttling), with CWE-400 (Uncontrolled Resource Consumption) as the outcome, and CWE-755 (Improper Handling of Exceptional Conditions) as the cause.

```fsharp
// Looks like a rate-limit agent. One malformed request kills the loop;
// every later request is queued and never answered, and the queue has no cap.
// (sketch, not compiled: Request and check stand for your own types)
let limiter = MailboxProcessor<Request>.Start(fun inbox -> async {
    while true do
        let! req = inbox.Receive()
        check req })            // a throw here ends the while loop, silently
// handler: limiter.Post req   // still succeeds after the crash
```

```fsharp
// What was meant: make death visible, and make the caller see it too.
limiter.Error.Add(fun e -> log.Fatal(e, "limiter died"); exit 1)
// and on the request path: TryPostAndReply with a timeout, never PostAndReply
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| F# | agent body throws; `Post` still queues | `Error` event, silent if unsubscribed; no queue bound | subscribe `Error` on every agent; use `TryPostAndReply` with a timeout on request paths |
| Rust | worker panics while senders live | `send` returns `Err(SendError)` once the `Receiver` drops | handle the `Err` instead of `let _ =`; `mpsc::channel` is unbounded, `sync_channel(n)` is not |
| Go | consumer goroutine panics | the unrecovered panic exits the whole process | decide whether that crash is what you want, or `recover` and restart the consumer on purpose |
| TypeScript | un-awaited async worker throws | Node exits on the unhandled rejection by default | an array used as a queue has no bound either; cap it and reject at the edge |

The control here is Rust: its channel ties the consumer's death to the sender's return type, so the failure shows up on the producer's own path. F# is the odd one: its actor is the only one of the four whose death is silent by default.

Left hanging: which of your in-process queues can a client grow, and what happens to the queue after its consumer dies?

# FAQ

**Does the closure LUB coercion work for `Vec::push` one element at a time?** No. It happens where the compiler sees several expressions at once (array and `vec!` literals, `if`/`else`, `match` arms). Pushing a second closure into a `Vec` already inferred as the first closure's type is a plain E0308.

**Does libc++ 22's `find` change affect `count` or `equal_range`?** No. Both still walk to the full equal range, and `equal_range(k).first` is the portable "first element" spelling.

**Does `Effect.cached` cache defects from `Effect.die` too?** Yes, measured: a first-run `Effect.die` replays as a `Failure` on the second read, and the initializer ran once.

**Where does `Effect.retry` go with `Effect.cached`?** Inside. `Effect.cached(fetchToken.pipe(Effect.retry({ times: 3 })))` succeeded after 2 calls; `token.pipe(Effect.retry(...))` on the cached effect failed after 1 call, because every retry read the cache.

**Can I see a dead `MailboxProcessor` from outside?** Not directly. There is no `IsAlive`; `CurrentQueueLength` growing while `TryPostAndReply` times out is the only symptom without an `Error` subscriber.
