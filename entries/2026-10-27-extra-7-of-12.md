**The thesis of this part: a lazy pipeline runs each step as many times as its consumer asks, and the consumer, not the pipeline, decides the count.** "Lazy" is usually sold as "does less work", and it can: a Rust `len()` ran the `map` closure zero times. The same laziness made a C++ `transform` run 9 times for 6 items, made F#'s `Seq.item` in a loop evaluate 500,500 elements to read 1,000, and let a TypeScript debug line drain a generator so the real loop saw nothing. Nothing in any pipeline's type says how many times its steps will run.

Every value below was printed by the snippet beside it, on Linux: a Debian 13.7 container with rustc 1.99.1, g++ 14.2.0 and .NET SDK 10.0.402 (runtime 10.0.13, FSharp.Core 10.1.0.0), the `gcc:16` image with g++ 16.2.0, and the `node:22-trixie` image with Node 22.23.4 and tsc 7.0.2.

| Language | Pipeline | How many times the expensive step ran |
| --- | --- | --- |
| Rust | `map(f)` over 5 items | 0 for `len()`, 1 for `rev().next()`, 4 for `nth(3)`, 5 for `count()` and `last()` |
| C++ | `transform(f) \| filter(p)` over 6 items, 3 passing | 9 on the first pass, 5 on the second |
| F# | `Seq.item index` for each of 1,000 positions | 500,500 element evaluations |
| TypeScript | a generator read after a debug `console.log([...queue])` | all 3 items consumed by the log, 0 left for the loop |

## Rust: the consumer decides how often a map closure runs, so len() ran it 0 times and step_by(2) ran it 5 times for 3 results

*Perf and memory model*

**Did you know**

A `map` adaptor runs its closure only when something calls `next` (or `next_back`) on it, and each consumer asks a different number of times. Over five items, `len()` ran the closure 0 times (it is answered from `ExactSizeIterator`), `rev().next()` ran it once, `nth(3)` four times (every skipped element is still mapped), and `count()`, `last()` and `step_by(2).count()` five times each, the last one for three results. The counts were identical at `opt-level` 0 and 3. The std docs warn about the zero case ("iterators are lazy and do nothing unless consumed"); the in-between counts are the part nobody writes down.

**Show me**

```rust
// rustc 1.99.1, edition 2021; same counts at opt-level 0 and 3.
use std::cell::Cell;

fn main() {
    let ports: Vec<u16> = vec![80, 443, 8080, 8443, 9000];
    let closure_calls = Cell::new(0u32);
    let next_port = |port: &u16| { closure_calls.set(closure_calls.get() + 1); *port + 1 };
    let fn_report = |label: &str, consume: &dyn Fn() -> String| {
        closure_calls.set(0);
        let shown = consume();
        println!("{label:<16} {shown:<10} map closure ran {} times", closure_calls.get());
    };
    fn_report("len()", &|| ports.iter().map(next_port).len().to_string());                    // 0
    fn_report("count()", &|| ports.iter().map(next_port).count().to_string());                // 5
    fn_report("last()", &|| format!("{:?}", ports.iter().map(next_port).last()));             // 5
    fn_report("rev().next()", &|| format!("{:?}", ports.iter().map(next_port).rev().next())); // 1
    fn_report("nth(3)", &|| format!("{:?}", ports.iter().map(next_port).nth(3)));             // 4
    fn_report("step_by(2)", &|| ports.iter().map(next_port).step_by(2).count().to_string());  // 5, for 3 results
}
```

**Why it matters**

When the closure is cheap, none of this matters. When it parses, allocates, looks something up or has a side effect, the consumer silently picks the cost: `last()` and `rev().next()` return the same element and differ fivefold in work, and `nth` pays for everything it skips. The rule that predicts it is mechanical: the closure runs once per `next` or `next_back` call, and only `len()` and `size_hint()` avoid calling either. C++ `views::transform` has the same "per dereference" rule with a twist, measured next. F# `Seq.map` follows the same rule, and JavaScript iterator helpers do too.

**Chew on this**

Which of your iterator chains end in `last()`, `nth()` or `skip(..).next()` over a `map` that does real work, and would the reverse iterator or an index into the source give the same answer for less?

**Sources**

- https://doc.rust-lang.org/std/iter/index.html#laziness ("iterators are lazy and do nothing unless consumed")
- https://doc.rust-lang.org/std/iter/trait.ExactSizeIterator.html
- https://doc.rust-lang.org/std/iter/trait.DoubleEndedIterator.html

**Gotchas**

- `step_by(2)` still maps the elements it steps over: 5 closure calls for 3 results, because stepping is done by calling `next` on the mapped iterator.
- `len()` exists only while the chain is `ExactSizeIterator`: after a `filter` it is "E0599: no method named `len` found for struct `Filter<I, P>`", and `count()` runs everything.

## C++: transform before filter runs the transform again for every element that passes, so 6 items cost 9 lookups

*Perf and memory model*

**Did you know**

`views::transform` computes its value on every dereference, and `views::filter` dereferences each element once to test it, then the loop dereferences each passing element again to read it. So `skus | views::transform(price_of) | views::filter(...)` called `price_of` 9 times for 6 items with 3 passing. A second pass called it 5 times, not 9, because `filter_view` "caches the result" of `begin()" within the `filter_view` object for use on subsequent calls": the first match is not searched for again. Putting the filter first (on the SKU) cut it to 3. Same counts on g++ 14.2 and g++ 16.2.

**Show me**

```cpp
// C++20 ranges, g++ 14.2 -O2 and g++ 16.2 -std=c++26: same counts.
#include <cstdio>
#include <ranges>
#include <vector>

int lookups = 0;
int price_of(int sku) { ++lookups; return sku * 10; } // stands in for an expensive lookup

int main() {
    std::vector<int> skus{1, 2, 3, 4, 5, 6};
    auto pricey = skus | std::views::transform(price_of)
                       | std::views::filter([](int price) { return price >= 40; });
    int total = 0;
    for (int price : pricey) total += price;
    std::printf("total=%d lookups=%d\n", total, lookups); // total=150 lookups=9: 6 to filter, 3 again to read

    lookups = 0;
    for (int price : pricey) total += price;
    std::printf("second pass lookups=%d\n", lookups);    // 5: begin() was cached, so the first match is not searched again

    lookups = 0;
    auto filter_first = skus | std::views::filter([](int sku) { return sku >= 4; })
                             | std::views::transform(price_of);
    for (int price : filter_first) total += price;
    std::printf("filter first lookups=%d\n", lookups);   // 3

    // const auto& frozen = pricey; for (int price : frozen) {}
    //   error: passing 'const std::ranges::filter_view<...>' as 'this' argument discards qualifiers
}
```

**Why it matters**

"Transform, then keep the expensive ones" is the natural way to write a pricing, scoring or permission pipeline, and it pays the transform twice for every element that survives. The cached `begin()` adds a second surprise: the same view does different amounts of work on its first and second traversal, and it cannot be iterated through a `const&` at all, because `begin()` writes the cache. Rust's `map(..).filter(..)` computes each mapped value once, because `filter` receives the value `map` already produced; F# `Seq.map >> Seq.filter` behaves like Rust. C++26 adds `views::cache_latest` for exactly this case: on g++ 16.2, `transform(price_of) | views::cache_latest | filter(...)` made 6 lookups on each pass instead of 9 and 5.

**Chew on this**

In your range pipelines, which `transform` sits in front of a `filter`, and is the transformed value something you would be willing to compute twice for every element that survives?

**Sources**

- https://en.cppreference.com/w/cpp/ranges/filter_view ("caches the result within the `filter_view` object for use on subsequent calls")
- https://en.cppreference.com/w/cpp/ranges/transform_view
- https://en.cppreference.com/w/cpp/ranges/cache_latest_view (C++26, "caches the last-accessed element ... so that the element does not have to be recomputed")

**Verified**

g++ 14.2 and 16.2 (libstdc++) only; libc++ and MSVC STL not checked. `views::cache_latest` on g++ 16.2 only.

**Gotchas**

- A `filter_view` cannot be iterated as `const`: its `begin()` is not `const`-qualified because it writes the cache, so passing one by `const auto&` fails with "discards qualifiers".
- The cache goes stale if the underlying vector changes between passes. With `prices{10, 50, 20, 60}` filtered to `>= 40`, setting `prices[1] = 5` after the first pass made the second pass begin at `5` and print `5 60`: an element that fails the predicate came out of the filter.
- Moving the predicate to the source (`filter` on the SKU, then `transform`) works only when the predicate does not need the transformed value; when it does, materialize once into a vector.

## F#: Seq.item restarts the sequence every time, so reading 1,000 positions by index evaluated 500,500 elements

*Perf and memory model*

**Did you know**

A `seq<'T>` has no position: `Seq.item position` starts a fresh enumeration and walks to `position`, so reading every position of a 1,000-element `seq` in a loop evaluated its body 500,500 times, 1 + 2 + ... + 1000. `Seq.sum` over the same sequence evaluated 1,000. Asking three cheap-looking questions, `Seq.length`, `Seq.head` and `Seq.isEmpty`, enumerated it three times (1,002 evaluations). `Seq.cache` made the indexed loop cost 1,000 evaluations, because it remembers what it has already produced.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, dotnet fsi.
let mutable element_evaluations = 0 // counts how often the seq body produced an element
let readings : seq<int> = seq {
    for index in 1 .. 1000 do
        element_evaluations <- element_evaluations + 1
        yield index }

let total_by_index = List.sum [ for position in 0 .. 999 -> Seq.item position readings ]
printfn "Seq.item in a loop: %d evaluations" element_evaluations    // 500500

element_evaluations <- 0
printfn "Seq.sum once: %d, %d evaluations" (Seq.sum readings) element_evaluations // 500500, 1000

element_evaluations <- 0
let summary = (Seq.length readings, Seq.head readings, Seq.isEmpty readings)
printfn "length, head, isEmpty: %A, %d evaluations" summary element_evaluations // (1000, 1, false), 1002

element_evaluations <- 0
let cached = Seq.cache readings
let cached_total = List.sum [ for position in 0 .. 999 -> Seq.item position cached ]
printfn "Seq.cache then item: %d evaluations" element_evaluations    // 1000
```

**Why it matters**

`Seq.item`, `Seq.length` and `Seq.head` read like constant-time accessors, and on a `seq` each one is a new enumeration, so an index loop is quadratic and every "is it empty, then how long, then the first one" sequence re-runs the source three times. When the source is a query, a file read or a computation with side effects (part 6 measured one that reopened a file), each enumeration repeats it. Rust's iterators are single-pass, so `nth` consumes and the next `nth` continues from there; C++ ranges re-walk like F# does; a JavaScript generator, like Rust, can be walked only once.

**Chew on this**

Which of your functions take `seq<'T>` and then call more than one of `Seq.length`, `Seq.head`, `Seq.isEmpty` or `Seq.item` on it, and what is behind the sequences their callers pass?

**Sources**

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-seqmodule.html#item
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-seqmodule.html#cache
- https://learn.microsoft.com/dotnet/fsharp/language-reference/sequences

**Gotchas**

- `List.ofSeq` once and then `List.item` evaluates the source only once, but `List.item` is itself a walk down a linked list, so the index loop is still quadratic in list cells; use `Array.ofSeq` for indexing.
- `Seq.cache` keeps every produced element alive for as long as the cached sequence is reachable.
- `Seq.isEmpty` produced exactly one element (the 1,002 is 1,000 for `length`, 1 for `head`, 1 for `isEmpty`), so it is cheap; it is repeating it per call that is not.

## TypeScript: a debug line that spreads a generator drains it, so the real loop processed 0 of 3 jobs

*Idioms and antipatterns*

**Did you know**

A generator object can be walked once. `console.log("queued:", [...queue])` is a natural debug line, and the spread consumes every item, so the `for...of` that follows processed 0 of 3 jobs. Printing the generator object itself does not drain it, and does not help either: `console.log(queue_again)` printed `Object [Generator] {}`, and spreading afterwards still found all 3. ES2025's iterator helpers keep the same single-pass laziness: `pending_jobs().map(...)` ran its callback 0 times until the first `next()`.

**Show me**

```typescript
// TypeScript, tsc 7.0.2 --strict, Node 22.23.4 (Iterator helpers: ES2025).
function* pending_jobs(): Generator<string> {
    yield "resize-1"
    yield "resize-2"
    yield "resize-3"
}

const processed_clean: string[] = []
for (const job of pending_jobs()) processed_clean.push(job)
console.log(processed_clean.length) // 3

const queue = pending_jobs()
console.log("queued:", [...queue]) // a debug line someone added: spreading drains the generator
const processed: string[] = []
for (const job of queue) processed.push(job)
console.log(processed.length)       // 0

const queue_again = pending_jobs()
console.log(queue_again)            // Object [Generator] {}: printing the object does not drain it
console.log([...queue_again].length) // 3

let mapped_calls = 0
const upper_jobs = pending_jobs().map((job) => { mapped_calls += 1; return job.toUpperCase() })
console.log(mapped_calls)                          // 0: Iterator.prototype.map is lazy
console.log(upper_jobs.next().value, mapped_calls) // RESIZE-1 1
```

**Why it matters**

This is a Heisenbug in the literal sense: the act of looking at the value changes what the program does next, so the bug appears when someone adds logging to investigate, or disappears when they remove it. The type `Generator<string>` says nothing about single use, and `Iterable<string>` parameters hide it further, since an array passed to the same function can be walked any number of times. Rust iterators are single-pass too, but a debug print of an iterator needs it by value or by `&mut`, so the consumption is visible in the code; F#'s `seq` re-runs instead of draining, which is part 6's and the F# tip's problem.

**Chew on this**

Which of your functions take an `Iterable<T>` and walk it more than once (a `length` check, then a loop), and what happens when a caller passes a generator instead of an array?

**Sources**

- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/Generator
- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/Iterator/map
- https://tc39.es/ecma262/#sec-%iterator.prototype%.map

**Gotchas**

- `Array.from(queue)` drains it the same way as the spread (0 items left afterwards); `structuredClone` cannot copy a generator at all and throws `DataCloneError`.
- Iterator helpers need `lib: es2025` (or newer) in tsc and Node 22 or later at runtime; the snippet compiled with `--lib es2025,dom`.
- A generator that is partly consumed by a debug `queue.next()` loses exactly that item: after one `next()`, spreading gave `[ 2, 3 ]`.

# The functional angle: a lazy step runs once per request from downstream, and only Rust's adaptors make the count predictable from the code

_Draws on all four tips. The shape: an expensive step in a lazy pipeline, consumed in two different ways. Every count was measured._

| Language | Expensive step | Consumed one way | Consumed another way | What decides the count |
| --- | --- | --- | --- | --- |
| F# | `seq` body | `Seq.sum`: 1,000 | `Seq.item` per index: 500,500 | each `Seq.*` call starts a new enumeration |
| Rust | `map` closure, 5 items | `rev().next()`: 1 | `last()`: 5 | one call per `next`/`next_back`; `len()` makes none |
| C++ | `transform`, 6 items, 3 kept | `filter` first: 3 | `transform` first: 9 (then 5 on a second pass) | one call per dereference, and `filter` dereferences twice |
| TypeScript | generator body, 3 items | one `for...of`: 3 | debug spread, then `for...of`: 3 then 0 | single pass: whoever reads first gets everything |

F# is the baseline because `seq` is its default lazy shape and it has the simplest rule: every consumer re-runs the whole source. Rust's rule is just as simple once you know it, and the only one of the four where the count can be read off the adaptor chain without knowing the consumer's internals. C++ needs one extra fact (how many times `filter` dereferences), and TypeScript's generators turn a second reader into a silent empty one.

Left open: when you hand a lazy pipeline to code you did not write, do you materialize it first, or document how many times it may be walked?

# The security angle: the debug line that made validation pass

_Draws on the TypeScript tip, Mode B: the tip shows a debug log draining a generator. When the generator yields validation failures, draining it turns "there are violations" into "there are none". Direction: nothing in the language or the type checker prevents it._

```typescript
// TypeScript, tsc 7.0.2, Node 22.23.4
type Upload = { readonly name: string; readonly size_bytes: number }
function* find_violations(uploads: ReadonlyArray<Upload>): Generator<string> {
    for (const upload of uploads) if (upload.size_bytes > 10_000_000) yield `${upload.name} too large`
}
const is_allowed = (uploads: ReadonlyArray<Upload>, debug: boolean): boolean => {
    const violations = find_violations(uploads)
    if (debug) console.log("violations:", [...violations]) // the debug line
    return violations.next().done === true                 // "no violations left" reads as allowed
}
is_allowed([{ name: "dump.sql", size_bytes: 50_000_000 }], false) // false
is_allowed([{ name: "dump.sql", size_bytes: 50_000_000 }], true)  // true: the log consumed the violation
```

With debugging off the 50 MB upload is rejected; with it on, the log prints the violation and then the check allows the upload. That is CWE-489 (Active Debug Code): a diagnostic left in, or switched on in production to investigate an incident, changes a security decision. It is also a fail-open check, part 3's CWE-636, reached by a different route.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | a debug spread drains the violations generator | nothing; `Generator` does not say "single use" | materialize once (`const violations = [...find_violations(uploads)]`), then log and decide on the array |
| Rust | a debug `for` over an iterator of violations consumes it | the consumption needs the iterator by value or `&mut`, visible in the code | collect into a `Vec` before logging and deciding |
| F# | a debug `Seq.toList` re-runs the source instead of draining it | the decision sees the same violations, at the cost of a second run | nothing for this shape; the cost is part 6's repeated effect |
| C++ | a range over a generator-like view can be single-pass (`std::generator`, C++23) | C++23 `std::generator` is an input range, consumed once | same as TypeScript; not measured here |

Left open: which of your validation or permission checks consume a lazy source, and what would a debug line in front of them do?

# FAQ

**Does Rust's `map` closure run when I call `size_hint()`?**
No. `len()` ran it 0 times, and `len()` is built on the same exact size information; only `next` and `next_back` run the closure.

**Is the 9-lookup C++ result an optimization level thing?**
No. The count was 9 at `-O2` on both g++ 14.2 and g++ 16.2. It is the view's specified behaviour: one transform call per dereference, and the filter dereferences each passing element twice.

**Does `Seq.cache` make an F# `seq` safe to index?**
It makes repeated enumeration cheap in evaluations: the indexed loop dropped to 1,000. It does not turn the sequence into an array, so for heavy random access `Array.ofSeq` once is the direct answer (the per-call cost of `Seq.item` on a cached sequence was not measured here).

**Does `console.log(generator)` in Node drain it?**
No. It printed `Object [Generator] {}` and the generator still yielded all 3 items afterwards. Only code that iterates (a spread, `Array.from`, `for...of`) consumes it.
