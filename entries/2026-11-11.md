## Rust: `"".split(',')` yields one empty string, so an unset `ALLOWED_ROLES` becomes a list that allows the empty role

*Idioms and antipatterns*

**Did you know**

`str::split` always yields at least one item, so `"".split(',')` is `[""]`, not `[]`: one element, and `is_empty()` on the collected `Vec` is `false`. An allow-list parsed from an unset or empty environment variable therefore contains the empty string, and a request whose role header was missing (read with `unwrap_or_default()`) matches it. `split_whitespace` and `lines` behave the other way and yield nothing for `""`, which is why the mistake reads as correct in review. Measured on rustc 1.99.1 on Debian 13.7; this is documented, stable behaviour since 1.0.

**Show me**

```rust
// Rust, edition 2024, rustc 1.99.1
fn parse_allowed_roles(raw: &str) -> Vec<&str> {
    raw.split(',').map(str::trim).collect()
}

fn main() {
    // ALLOWED_ROLES unset, read with env::var(..).unwrap_or_default(): ""
    let allowed_roles = parse_allowed_roles("");
    assert_eq!(allowed_roles, [""]); // one item, not zero
    assert!(!allowed_roles.is_empty()); // so "nothing configured" reads as configured
    let request_role = ""; // role header missing, defaulted the same way
    assert!(allowed_roles.contains(&request_role)); // and the empty role is allowed

    // A trailing comma adds an empty item; split_terminator drops only that one.
    assert_eq!("admin,".split(',').collect::<Vec<_>>(), ["admin", ""]);
    assert_eq!("admin,".split_terminator(',').collect::<Vec<_>>(), ["admin"]);
    assert_eq!(",".split_terminator(',').collect::<Vec<_>>(), [""]); // still one
}
```

The functional fix is one adaptor after the trim, `.filter(|role| !role.is_empty())`, which makes `""`, `" , "` and `"admin,"` agree; the security angle below adds the check that should follow it.

**Why it matters**

A comma list in config is the usual way to say who may do something, and the empty case is the one nobody writes a test for: the deployment that forgot the variable gets a rule instead of a refusal. JavaScript's `"".split(",")` and .NET's `"".Split(',')` build the same one-element list (measured: `[""]` and `[|""|]`), while C++20's `std::views::split` over an empty `string_view` yields zero pieces on libstdc++, so a port from C++ is the one that quietly changes meaning.

**Chew on this**

Which of your config parsers can tell "variable unset" from "variable set to empty", and should the two mean the same thing?

**Sources**

- https://doc.rust-lang.org/std/primitive.str.html#method.split
- https://doc.rust-lang.org/std/primitive.str.html#method.split_terminator
- https://doc.rust-lang.org/std/primitive.str.html#method.split_whitespace

**Verified**

rustc 1.99.1 on Debian 13.7. The JavaScript `[""]` ran on Node 26.13 and the .NET `[|""|]` on .NET 10 in the SDK image (Ubuntu 24.04). The C++ zero pieces ran on GCC 16.2.0 and Debian clang 19.1.7, both with libstdc++ 14; libc++ and MSVC were not checked.

**Gotchas**

- An empty pattern matches at both ends: `"ab".split("")` is `["", "a", "b", ""]` and `"".split("")` is `["", ""]`. JavaScript's `"ab".split("")` is `["a", "b"]` and its `"".split("")` is `[]`.
- `"".splitn(2, ',')` is `[""]` as well: the count is a maximum, and the minimum is still one.
- `split_terminator` drops one trailing empty item only, so `",".split_terminator(',')` is still `[""]`.
- `"".lines().count()` and `"   ".split_whitespace().count()` are both 0, so code that moves from `lines()` to `split('\n')` gains an empty item on empty input.

## C++: `std::stacktrace` links only with `-lstdc++exp`, and at `-O2 -g` it names the inlined function and drops the one whose frame is on the stack

*Stdlib and ecosystem gems*

**Did you know**

C++23's `<stacktrace>` lets a server attach `std::stacktrace::current()` to an error with no third-party library, but on libstdc++ it still lives in the experimental archive: without `-lstdc++exp` the code compiles and then fails to link (`undefined reference to std::stacktrace_entry::_Info::_M_populate`), on GCC 16.2 and on Debian clang 19.1.7 with libstdc++ 14 alike. Apple's libc++ has no `<stacktrace>` header at all. Once it links, the trace depends on the build: with `-O2 -g` GCC 16 reports the inlined `load_user()` and omits `handle_request()`, the function whose frame is actually on the stack; without `-g` it is the other way round; Debian clang at `-O2` dropped both, because it inlined one and turned the other into a tail call; and a stripped binary reports empty names.

**Show me**

```cpp
// C++23. g++ -std=c++23 -O2 -g trace.cpp -lstdc++exp   (GCC 16.2.0)
#include <cstdio>
#include <stacktrace>

[[gnu::noinline]] std::stacktrace query_db() { return std::stacktrace::current(); }
inline std::stacktrace load_user() { return query_db(); } // gets inlined at -O2
[[gnu::noinline]] std::stacktrace handle_request() { return load_user(); }

int main() {
    for (const std::stacktrace_entry& const_frame : handle_request()) {
        std::printf("%s line %u\n", const_frame.description().c_str(), const_frame.source_line());
    }
}
// Frames up to main, as printed (the trailing libc frames are left out):
// GCC 16    -O2 -g : query_db() line 5 | load_user() line 6 | main line 10
// GCC 16    -O2    : query_db()        | handle_request()     | main   (no lines)
// clang 19  -O2 -g : query_db() line 5 | main line 10
// both      -O0 -g : query_db | load_user | handle_request | main
// both      -O2 -g, then strip: every name empty except __libc_start_main
```

**Why it matters**

A trace on an error is only as good as the build that produced it: the usual release container, `-O2` and stripped, logs a stack of empty strings, and an unstripped `-O2 -g` build logs names that are each true yet skip the frame you would search for. Capturing is cheap, about 1.4 to 2 microseconds for six frames in three separate runs on both compilers, while capture plus `std::to_string` took about 2.3 to 4.5 microseconds, so the price is in rendering. Rust makes the opposite default: `std::backtrace::Backtrace::capture()` returns a disabled backtrace unless `RUST_BACKTRACE` or `RUST_LIB_BACKTRACE` is set, while C++ always captures.

**Chew on this**

When an incident trace names a function that is not on the call path you expected, which do you trust first: the trace, or your reading of the source?

**Sources**

- https://en.cppreference.com/w/cpp/utility/basic_stacktrace
- https://en.cppreference.com/w/cpp/compiler_support/23
- https://doc.rust-lang.org/std/backtrace/struct.Backtrace.html#method.capture

**Verified**

GCC 16.2.0 (`gcc:latest`) and Debian clang 19.1.7 with libstdc++ 14, both on Debian 13.7; MSVC not checked. Additionally checked on macOS (Apple clang): `<stacktrace>` file not found.

**Gotchas**

- `std::stacktrace::size_type` is `unsigned short` in libstdc++ 14 and 16 (the standard says only "implementation-defined unsigned integer type"), so clang `-Wformat` warns on `%zu` for `size()`, and a `max_depth` of 100000 passed to `current(skip, max_depth)` converts to 34464.
- At `-O0` every frame appears in both compilers, so a test of the trace in a debug build passes and the release trace differs.
- The file name is whatever the compiler recorded: clang compiling `/work/st.cpp` from `/tmp` reported `/tmp//work/st.cpp`, a build-machine path that ends up in your logs.

## F#: A caught `failwith` cost 1.4 microseconds and 296 bytes at the throw site and 6.5 microseconds and 2,376 bytes fifty frames up, while `Error` allocated nothing

*Perf and memory model*

**Did you know**

On .NET 10.0.14 with FSharp.Core 10.1, a `try ... with` around a `failwith` measured 1,449 ns and 296 bytes per call when caught in the same function (on a cold run; warmed up, the bytes fell to 192), 3,951 ns and 1,148 bytes ten frames up, and 6,500 ns and 2,376 bytes fifty frames up: the price is the unwind, and it grows with the distance between the throw and the `with`. F#'s `Result` is a `[<Struct>]` union, so returning `Error "negative amount"` through the same fifty frames allocated 0 bytes and took 11 to 57 ns. .NET 11.0.0 with FSharp.Core 11 (RC SDK) was faster at the throw site (1,028 ns) but allocated the same per frame.

**Show me**

```fsharp
// F# 10 / FSharp.Core 10.1.0 / .NET 10.0.14, dotnet fsi --optimize+
let rec validate_or_throw (depth: int) (amount_cents: int64) : int64 =
    if depth = 0 then
        if amount_cents < 0L then failwith "negative amount" else amount_cents
    else
        let checked_cents = validate_or_throw (depth - 1) amount_cents
        checked_cents + 1L // not a tail call, so every level is a real frame

let rec validate_result (depth: int) (amount_cents: int64) : Result<int64, string> =
    if depth = 0 then
        if amount_cents < 0L then Error "negative amount" else Ok amount_cents
    else
        match validate_result (depth - 1) amount_cents with
        | Ok checked_cents -> Ok (checked_cents + 1L)
        | Error reason -> Error reason // a struct copied up, nothing on the heap

// Per call, Stopwatch plus GC.GetAllocatedBytesForCurrentThread, caught at the top:
// depth   failwith caught          Result Error
//   0     1,449 ns    296 bytes    11 ns   0 bytes
//  10     3,951 ns  1,148 bytes    11 ns   0 bytes
//  50     6,500 ns  2,376 bytes    57 ns   0 bytes
```

**Why it matters**

A validator that rejects bad input by throwing turns every rejected request into microseconds of unwinding and kilobytes of garbage, and a burst of bad requests is exactly when you want neither. The bytes appear to be the stack trace being recorded frame by frame as the exception passes (an inference from how they grow with depth, not measured directly), so the cost lands even when nobody reads `.StackTrace`. Reading it is extra: the first read of a trace in a process took milliseconds in two separate runs (4,062 and 1,624 microseconds).

**Chew on this**

Which of your `failwith` calls can a client reach with its own input, and how many frames separate each one from the `with` that catches it?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/results
- https://learn.microsoft.com/en-us/dotnet/standard/exceptions/best-practices-for-exceptions
- https://learn.microsoft.com/en-us/dotnet/api/system.gc.getallocatedbytesforcurrentthread

**Verified**

Measured in the official .NET SDK images, which are Ubuntu (24.04 for .NET 10, 26.04 for .NET 11), not Debian, on an arm64 Docker VM. One run each for the table, so the timings are magnitudes. The byte counts depend on JIT warm-up and on the harness, which is not shown here: two later checks with their own harnesses gave 192 to 296 bytes at depth 0, 760 to 1,312 at depth 10, and 2,376 to 4,464 at depth 50.

**Gotchas**

- Throwing one preallocated exception does not avoid the allocation: a shared `InvalidOperationException` raised ten frames up still allocated 1,192 bytes and took 3,944 ns per call in one run, which fits the trace being recorded per throw rather than per object (inferred, not measured directly).
- That shared instance has one `StackTrace`, overwritten by the latest throw: after a throw from three frames deep and then one from one frame deep, the object reported the trace of the second throw. Under concurrency a log can attach another request's trace.
- `with :? Exception -> ...` compiles with warning FS0067, "This type test or downcast will always hold"; catch a specific type or write `with _ ->`.

## TypeScript: TypeScript 7.0.2 and the 7.1 beta compile `obj[++key]! ||= 1` for ES2020 so that `++key` runs twice, and the fix landed on 2026-11-04

*New discoveries and currently popular patterns*

**Did you know**

When `||=`, `&&=` or `??=` is lowered for `--target es2020` or older (and `**=` for ES2015), the compiler normally stores a computed key or receiver in a temporary so it is evaluated once. A type-only wrapper on the target defeated that: with `!`, `as` or `satisfies` around it, `obj[++key]! ||= 1` was emitted as `obj[++key] || (obj[++key] = 1)`, which reads one property and writes another. Measured: TypeScript 6.0.3, 7.0.2 and 7.1.0-beta all emit that and print `2 {"2":1}`, where Node 26.13's own type stripping prints `1 {"1":1}`. It was reported as microsoft/TypeScript#65287 on 2026-11-03 (the reporter found it in every version back to 4.0.2), fixed by PR #65297 on 2026-11-04, and the `7.1.0-dev.20261111.1` nightly emits `obj[_a = ++key] || (obj[_a] = 1)`, though the fix is on `main` and not in a stable release yet.

**Show me**

```ts
// tsc --target es2020 --strict input.ts   (TypeScript 7.0.2, Node 26.13.0)
let load_count = 0
type Config = { retry_count?: number }
const const_shared_config: Config = {}
const const_fn_load_config = (): Config => { load_count += 1; return const_shared_config }

// The `as` is type-only, yet it changes what the emitted JavaScript evaluates:
;(const_fn_load_config().retry_count as number | undefined) ??= 3
// 6.0.3, 7.0.2, 7.1.0-beta: const_fn_load_config().retry_count ?? (const_fn_load_config().retry_count = 3)
//                          -> load_count is 2
// 7.1.0-dev.20261111.1:    (_a = const_fn_load_config()).retry_count ?? (_a.retry_count = 3)
//                          -> load_count is 1

let plain_key = 0
const const_plain_obj: Record<number, number> = {}
const_plain_obj[++plain_key] ||= 1 // no wrapper: every version caches the key, plain_key is 1
```

Here the loader returns the same object, so only the side effect doubles. A loader that returned a fresh copy on each call would also send the write to a copy nobody keeps.

**Why it matters**

The bug sits exactly where TypeScript and its output part ways: tests run under Node's type stripping pass, and the `tsc` build you deploy does something else. The trigger is a shape people write defensively around indexed access, a `!` or an `as` on the target, although `counts[++key] ||= 1` itself compiled cleanly under `--strict --noUncheckedIndexedAccess` on 7.0.2 without one; it needs only a target below ES2021. At `--target es2021` 7.0.2 keeps `obj[++key] ||= 1` as written and prints `1 {"1":1}`, so a Node 26 server can step out of the bug by raising its target.

**Chew on this**

Which of your build targets are older than the runtime they ship to, and what else is that gap rewriting for you?

**Sources**

- https://github.com/microsoft/TypeScript/issues/65287
- https://github.com/microsoft/TypeScript/pull/65297
- https://github.com/microsoft/TypeScript/releases/tag/v7.1-beta

**Verified**

Measured in `node:lts` (Node 26.13.0, Debian 13) with 6.0.3, 7.0.2, 7.1.0-beta and the 2026-11-11 nightly; the 4.0.2-and-later history is the reporter's, not re-run here.

**Gotchas**

- `??` is itself ES2020, so at `--target es2020` the plain `??` is kept and only `??=` is lowered; the `**=` case needs `--target es2015` or older.
- A target without a wrapper was always fine: `const_plain_obj[++plain_key] ||= 1` became `const_plain_obj[_a = ++plain_key] || (const_plain_obj[_a] = 1)` in the three released versions, and the same with `_b` in the nightly, whose fixed line above it takes `_a`.
- `tsc` gives no error and no warning on any of these lines; only the emitted JavaScript shows it.

# The functional angle: failure as a value costs nanoseconds everywhere, and the exception it replaces costs microseconds that grow with the stack, except in JavaScript

Draws on the F# tip only. The Rust, C++ and TypeScript rows were measured for this section, not taken from those tips, with the same shape: a check at the bottom of a call chain, failing, caught or matched at the top.

The functional form is the same in all four: the failure is an ordinary return value, and each level passes it up with one branch.

```rust
// Rust 1.99.1: ? is the branch, Result<i64, &str> is two words on the stack
fn validate_result(depth: u32, amount_cents: i64) -> Result<i64, &'static str> {
    if depth == 0 {
        return if amount_cents < 0 { Err("negative amount") } else { Ok(amount_cents) };
    }
    Ok(validate_result(depth - 1, amount_cents)? + 1)
}
```

```cpp
// C++23 (GCC 16.2): std::expected, with transform as the map over the success side
std::expected<long, const char*> validate_expected(const int const_depth, const long const_amount_cents) {
    if (const_depth == 0) {
        return const_amount_cents < 0 ? std::expected<long, const char*>{std::unexpect, "negative amount"}
                                      : std::expected<long, const char*>{const_amount_cents};
    }
    return validate_expected(const_depth - 1, const_amount_cents)
        .transform([](const long const_checked_cents) { return const_checked_cents + 1; });
}
```

```ts
// TypeScript (Node 26.13): no Result in the language, so a discriminated union object
type Checked = { ok: true; value: number } | { ok: false; reason: string }
const const_fn_validate_result = (depth: number, amount_cents: number): Checked => {
  if (depth === 0) return amount_cents < 0 ? { ok: false, reason: "negative amount" } : { ok: true, value: amount_cents }
  const const_checked = const_fn_validate_result(depth - 1, amount_cents)
  return const_checked.ok ? { ok: true, value: const_checked.value + 1 } : const_checked
}
```

F# is the baseline row because it is the only one of the four where both forms are everyday idiom: `failwith` and `Result` sit side by side in ordinary F# code, so its row compares two things a reader would actually write.

| Language | Functional form | Thrown, caught at depth 0 / 10 / 50 | As a value, depth 0 / 10 / 50 | What it costs |
| --- | --- | --- | --- | --- |
| F# (.NET 10) | `Result`, a `[<Struct>]` union | 1,449 / 3,951 / 6,500 ns | 11 / 11 / 57 ns | a struct copy per level, 0 bytes; the throw allocates 296 to 2,376 bytes |
| Rust 1.99.1 | `Result` with `?` | `panic!` + `catch_unwind`: 3,412 / 5,896 / 17,032 ns | 1 / 10 / 299 ns | one branch per level; and under `panic = "abort"` there is nothing to catch |
| C++ (GCC 16.2, `-O2`) | `std::expected` + `transform` | 1,436 / 4,712 / 18,807 ns | 1 / 13 / 317 ns | one branch per level; the throw also allocates the exception object on the heap (Itanium C++ ABI, as on Linux) |
| TypeScript (Node 26.13) | union object `{ ok, ... }` | 1,565 / 1,950 / 2,838 ns | 57 / 36 / 180 ns | one object per level; the throw grows the least, partly because V8 records only `Error.stackTraceLimit` = 10 frames by default |

One run each on an arm64 Docker VM, so read the columns as magnitudes; none of the harnesses behind this paragraph are shown in the entry. The recursion has to stay un-foldable for them to mean anything: in a second harness whose compiler folded the chain, the Rust throw measured flat (5.2, 4.9 and 5.0 microseconds at depth 0, 10 and 50), and with a volatile write after each call it grew again (Rust 5.4, 10.0 and 30.6; C++ 2.3, 8.9 and 33.1 microseconds).

The asymmetry worth leading with is JavaScript's: its throw grew the least with depth. Part of that is the trace. V8, the JavaScript engine in Node.js, records only ten frames by default, and in that second harness a depth-50 throw cost 4,703 ns with `Error.stackTraceLimit` at 0, 5,847 ns at the default 10 and 11,436 ns at 100. Unwinding is not free either: with no trace at all, depth 50 still cost 80% of the default. The trace is part of an exception's price, and the only runtime here that caps it by default is the one where the trace is shortest when you need it.

None of the four value forms, in Rust, C++, F# or TypeScript, needed `mut`, a mutable accumulator or a `let mutable`; the imperative cost here is all on the throwing side.

Left open: if the trace is part of what makes the exception expensive, which of your errors would lose nothing if they carried no trace at all, and which would lose everything?

# The security angle: an empty setting becomes a rule that matches an empty request, in three of the four languages

Draws on the Rust tip (Mode C, the missing check) and on the C++ and F# tips (Mode B). It runs in the insecure direction: none of the four languages prevents any of this.

## The empty allow-list

This is the line that ships, in plausible TypeScript:

```ts
// TypeScript (Node 26.13): looks like a normal allow-list
const const_allowed_roles: string[] = (process.env.ALLOWED_ROLES ?? "").split(",").map((role) => role.trim())
const const_fn_is_allowed = (request_role: string): boolean => const_allowed_roles.includes(request_role)
// ALLOWED_ROLES unset -> const_allowed_roles is [""] -> const_fn_is_allowed("") is true
// for any request whose role header was missing and defaulted to ""
```

And the check it is missing, in Rust, for an allow-list: drop empty items, then make the empty case explicit, here as an error rather than a rule. Whether unset and set-to-empty should both land there is the Rust tip's open question, and this sketch does not settle it.

```rust
// Rust 1.99.1: compiled and asserted with the tip's snippet
fn parse_allowed_roles_strict(raw: &str) -> Result<Vec<&str>, String> {
    let allowed_roles: Vec<&str> = raw
        .split(',')
        .map(str::trim)
        .filter(|role| !role.is_empty())
        .collect();
    if allowed_roles.is_empty() {
        Err(format!("ALLOWED_ROLES has no roles: {raw:?}"))
    } else {
        Ok(allowed_roles)
    }
}
// parse_allowed_roles_strict(" , admin ,") == Ok(vec!["admin"]); "" and " , " are Err
```

C++ is the control here, and it fails the other way: C++20's `std::views::split` over an empty `string_view` yields zero pieces on libstdc++, so the C++ port reads "unset" as "nobody", which is safe for an allow-list and unsafe for a deny-list.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `"".split(',')` is `[""]` | documents it; `split_whitespace` and `lines` yield nothing for `""` | filter empty items after the trim, and decide explicitly what an empty list means |
| C++20 (libstdc++) | `views::split` over `""` yields zero pieces | gives an empty list, which an allow-list reads as allow nobody | decide what empty means; a deny-list built this way denies nothing |
| F# (.NET 10) | `"".Split(',')` is `[\|""\|]` | `RemoveEmptyEntries \|\|\| TrimEntries` gives `[\|\|]`, but `RemoveEmptyEntries` alone kept `" "` and `" admin "` | pass both flags, then check the length |
| TypeScript | `"".split(",")` is `[""]` | nothing; `.filter(Boolean)` gives `[]` | the same filter and the same explicit decision |

Classes: CWE-183 (Permissive List of Allowed Inputs) and CWE-1188 (Initialization of a Resource with an Insecure Default).

## The trace in the response

The C++ and F# tips both produce text that describes your build: clang recorded `/tmp//work/st.cpp`, a build-machine path, and a .NET `StackTrace` names every method between the throw and the catch. Returned to a client, that is CWE-209 (Generation of Error Message Containing Sensitive Information). The F# gotcha adds a second class: one shared exception object thrown by two requests carries whichever trace was written last, so a log line, or an error body, can describe another request (CWE-488, Exposure of Data Element to Wrong Session).

| F# (.NET) | `.StackTrace` on a shared exception is the last thrower's | records a fresh trace on every throw into the same object | never share a thrown exception instance across requests |
