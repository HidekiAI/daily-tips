**The thesis of this part: an exhaustive match is a promise about the cases the compiler can see, and each language breaks it at a different seam.** "Sum types plus exhaustive match" is the textbook argument for typed FP, and it is true inside the compiler's view. Rust stops looking behind a reference, C++ lets a new alternative convert itself into an old handler, F# makes the gap a warning and makes enums impossible to cover, and TypeScript's proof never reaches the JSON that arrives at runtime. The interesting day is not the day the match is written. It is the day someone adds a case.

## Rust: since 1.82 an Err(Infallible) arm can be left out, but only by value, so the same match behind a reference needs it back

*Type system deep cuts*

**Did you know**

Rust 1.82 stabilized omitting patterns for uninhabited types. A `Result<T, Infallible>` has no `Err` values, so `let Ok(value) = result;` is irrefutable and a `match` needs only the `Ok` arm. The release notes carve out one exception, "for reasons related to uninitialized values and unsafe code": the omission is not allowed "if the empty type is accessed through a reference, pointer, or union field". Borrow the same `Result`, or box the error, and E0004 is back. And the day the error type stops being `Infallible`, every irrefutable `let Ok(..)` becomes E0005, which is exactly the "a variant was added" alarm you want.

**Show me**

```rust
// rustc 1.99.1, edition 2021. Uninhabited-error patterns: Rust 1.82 (min_exhaustive_patterns).
use std::convert::Infallible;

fn main() {
    // String's FromStr error type is Infallible: turning text into a String cannot fail.
    let parsed: Result<String, Infallible> = "eu-west-1".parse::<String>();
    let Ok(region) = parsed; // irrefutable since 1.82: Err(Infallible) has no values
    println!("{region}"); // eu-west-1

    let parsed_again: Result<String, Infallible> = "us-east-2".parse();
    let label = match parsed_again { Ok(text) => text.to_uppercase() }; // no Err arm needed
    println!("{label}"); // US-EAST-2

    // The exemption stops at indirection: behind & or Box the compiler wants the arm back.
    let borrowed: &Result<String, Infallible> = &"ap-south-1".parse();
    match borrowed {
        Ok(text) => println!("{text}"), // ap-south-1
        Err(never) => match *never {},  // without this arm: E0004, `&Err(_)` not covered
    }
}
```

Change the first parse to `"8080".parse::<u16>()` (error type `ParseIntError`) and the build stops at `let Ok(region)`: "E0005: refutable pattern in local binding, pattern `Err(_)` not covered".

**Why it matters**

Infallible errors are common in generic code: `FromStr for String`, `TryFrom` blanket impls, a trait whose error type a concrete implementation fills with `Infallible`. Writing `let Ok(..)` instead of `unwrap()` turns "this cannot fail today" into a compile error the day it can, with no panic path in between. C++ has no uninhabited type, so `std::expected<T, E>` always has an error state to handle. F# cannot express it either: a union needs at least one case, and nothing tells the compiler a case is empty. TypeScript can (`Result<T, never>`), but narrowing is about types, not patterns, so there is no arm to omit.

**Chew on this**

- https://doc.rust-lang.org/std/convert/enum.Infallible.html ("The error type for errors that can never happen")

**Gotchas**

- `Box<Infallible>` counts as indirection too: `match boxed { Ok(value) => .. }` on a `Result<u16, Box<Infallible>>` is E0004, `Err(_)` not covered.
- The arm you may now omit is not reported as dead if you keep it. The release notes say empty-pattern arms "are not yet reported as unreachable code", to avoid breaking crates that support older compilers.
- It does not apply to `#[non_exhaustive]` types: the release notes limit it to empty types "and no `#[non_exhaustive]` attribute".

## C++: std::visit picks a handler by overload resolution, so a new double alternative lands in the int handler as 2 with no warning

*Idioms and antipatterns*

**Did you know**

The usual `overloaded{...}` visitor is not a match. It is an overload set, and `std::visit` calls it with each alternative like any function call, so implicit conversions apply. Add `double` to a `std::variant<int, std::string>` and forget its handler, and `2.5` goes to `[](int)` as `2`. g++ 14.2 said nothing with `-Wall -Wextra -Wconversion`; adding `bool` does the same. The guard is a deleted template `operator()` in the set: an exact match beats every conversion, so an alternative without its own handler becomes a compile error. The `overloaded{...}` spelling without a deduction guide needs C++20 (aggregate CTAD); g++ 14.2 at `-std=c++17` reports "class template argument deduction failed".

**Show me**

```cpp
// C++20 (aggregate CTAD for overloaded{...}); std::variant and std::visit are C++17. g++ 14.2.
#include <cstdio>
#include <string>
#include <variant>

template <class... Handlers> struct overloaded : Handlers... { using Handlers::operator()...; };

// v1 was std::variant<int, std::string>. Someone adds double for fractional timeouts.
using setting_value = std::variant<int, std::string, double>;

const char* describe(const setting_value& value) {
    return std::visit(overloaded{
        [](int seconds) { std::printf("int %d -> ", seconds); return "int handler"; },
        [](const std::string&) { return "string handler"; },
        // No double handler, and no diagnostic: double converts to int, so visit still compiles.
    }, value);
}

// Guard: an exact-match catch-all that cannot be called. It beats every conversion,
// so an alternative without its own handler becomes a compile error instead.
struct no_implicit_conversion {
    template <class Unhandled> const char* operator()(const Unhandled&) const = delete;
};

int main() {
    std::printf("%s\n", describe(setting_value{2.5})); // int 2 -> int handler
    // Adding no_implicit_conversion{} to the overloaded{...} above turns that into:
    // error: no type named 'type' in 'struct std::invoke_result<overloaded<...>, const double&>'
}
```

**Why it matters**

A variant is how C++ spells a sum type, and adding an alternative is how a config format, a message protocol or an AST grows. The visitor then routes the new case to whichever old handler it converts to: a fractional timeout truncated to whole seconds, a `bool` flag treated as a count. With the guard in place the existing alternatives still pick their own handlers (`42` still reached the `int` one), because a non-template exact match wins a tie with a template. Rust and F# have no conversions in a `match`, so a new variant is either a missing arm or a compile error, never a different arm.

**Chew on this**

How many of your visitors would still compile if the variant gained an alternative tomorrow, and would you find out from the compiler, from a test, or from a truncated value in production?

**Sources**

- https://en.cppreference.com/w/cpp/utility/variant/visit (the `overloaded` helper is the page's own example)
- https://en.cppreference.com/w/cpp/language/overload_resolution
- https://en.cppreference.com/w/cpp/language/class_template_argument_deduction

**Verified**

g++ 14.2 (libstdc++) only; Clang and MSVC not checked.

**Gotchas**

- A generic `[](const auto&)` catch-all hides the gap the same way: with `[](int)` and `[](const auto&)`, the string and the `2.5` both printed "generic handler", with no warning.
- The guard's error message is not friendly: g++ reports it inside `<type_traits>` as "no type named 'type' in 'struct std::invoke_result<...>'", followed by "'constexpr' call flows off the end of the function". The alternative's type is in the `invoke_result` arguments.
- `bool` converts too: after adding `bool` to the variant, `setting_value{true}` printed "int handler".

## F#: a complete match on an enum still warns FS0104, and the `_` that silences it swallows every member added later

*Idioms and antipatterns*

**Did you know**

A .NET enum can hold any value of its underlying type, so F# warns FS0104, "Enums may take values outside known cases", on a match that covers every named member. In a build with `TreatWarningsAsErrors=true` that is an error, so the usual fix is a `_` arm, and that `_` then takes every member added later without any diagnostic. The F# enum docs suggest the other fix: `#nowarn "104"` makes the compiler treat only the declared members as valid, so a complete match builds clean and a newly added member fails the build with FS0025, the same as a discriminated union. An undefined value like `enum<Region> 7` still throws `MatchFailureException` at runtime.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, dotnet build with TreatWarningsAsErrors=true.
type Region =
    | Europe = 0
    | America = 1
    // | Asia = 2   <- the day someone adds a member

// Every member is covered, yet FS0104 fires ("Enums may take values outside known cases"),
// so a warnings-as-errors build forces the wildcard below onto a complete match.
let datacenter_of (region: Region) =
    match region with
    | Region.Europe -> "fra"
    | Region.America -> "iad"
    | _ -> "fra" // required by FS0104 as an error; it also catches every member added later

printfn "%s" (datacenter_of Region.America)   // iad
printfn "%s" (datacenter_of (enum<Region> 7)) // fra: an undefined value, silently routed
// With Asia added: datacenter_of Region.Asia is "fra", and the build succeeds with no warning.

// The alternative: put #nowarn "104" at the top of the file and drop the `_` arm.
// The complete match then builds clean; adding Asia fails the build with
// error FS0025: ... the value 'Region.Asia' may indicate a case not covered,
// and enum<Region> 7 throws MatchFailureException at runtime.
```

**Why it matters**

Enums show up in F# wherever .NET does: `HttpStatusCode`, `FileAccess`, an EF Core column, a C# library's options. A team that turns on warnings-as-errors to catch FS0025 on unions gets a `_` on every enum match as a side effect, which is the opposite of what they wanted. C# has the same split: a complete `switch` expression over an enum drew "warning CS8524: ... involving an unnamed enum value. For example, the pattern '(Region)2' is not covered" on .NET SDK 10.0.402. Rust has no such gap: an `enum` cannot hold an undeclared value in safe code, `7u8 as Region` is "E0605: non-primitive cast", and a `_` on a complete match draws "warning: unreachable pattern".

**Chew on this**

Which of your `_` arms on enum matches were written to handle a real unknown value, and which were written to make FS0104 go away?

**Sources**

- https://learn.microsoft.com/dotnet/fsharp/language-reference/enumerations ("you can suppress warning FS0104 using the directive `#nowarn "104"`")
- https://learn.microsoft.com/dotnet/fsharp/language-reference/pattern-matching
- https://learn.microsoft.com/dotnet/fsharp/language-reference/compiler-options

**Gotchas**

- `WarningsAsErrors=FS0025` (or `25`) makes only the union warning an error and leaves FS0104 a warning; `TreatWarningsAsErrors=true` makes both errors. Check with `--no-incremental`: an up-to-date build printed "Build succeeded" without recompiling.
- `#nowarn "104"` is a promise, not a check: `enum<Region> 7` still compiles, and the match throws `MatchFailureException` on it.
- `dotnet fsi` runs the script despite FS0025 and FS0104; only a build with warnings as errors stops.

## TypeScript: `satisfies never` proves the switch is complete for the types, and the default arm's return value decides what an unknown tag from JSON gets

*Idioms and antipatterns*

**Did you know**

`session satisfies never` in a `default` arm (TypeScript 4.9 and later) is an exhaustiveness check that exists only at compile time. Add a case to the union and tsc stops with TS1360, "does not satisfy the expected type 'never'", which is the point. At runtime the check is gone, and the arm's next statement decides what an unknown tag gets: a `{"kind":"admin"}` from `JSON.parse` (typed `any`, so assignable to `Session` with no cast) reached `default` and returned `false`. Effect's `Match.exhaustive` gives the same compile-time error (TS2345 when a case is added) and also throws at runtime on an unmatched value: `Error: effect/match/Match/exhaustive: absurd`.

**Show me**

```typescript
// TypeScript, tsc 7.0.2 --strict, effect 4.0.6, Node 22.23.4.
import { Match } from "effect"

type Session =
    | { readonly kind: "anonymous" }
    | { readonly kind: "member"; readonly user_id: string }

const can_post = (session: Session): boolean => {
    switch (session.kind) {
        case "anonymous": return false
        case "member": return true
        default: session satisfies never; return false // compile-time proof only; this line is the runtime policy
    }
}

const can_post_strict = Match.type<Session>().pipe(
    Match.when({ kind: "anonymous" }, () => false),
    Match.when({ kind: "member" }, () => true),
    Match.exhaustive) // also compile-time checked, and it throws at runtime on anything else

// JSON.parse returns any, so it is assignable to Session without a cast or a check.
const from_wire: Session = JSON.parse('{"kind":"admin","user_id":"u9"}')
console.log(can_post(from_wire)) // false: the fallback decided, not the type
try { can_post_strict(from_wire) } catch (thrown) { console.log(String(thrown)) }
// Error: effect/match/Match/exhaustive: absurd
```

**Why it matters**

The never check is the best tool TypeScript has for the day a variant is added: both forms above turned an added `admin` case into a compile error (TS1360 for the switch, TS2345 on the `Match.exhaustive` line). But the value that reaches the function at runtime was never checked against the union, so "exhaustive" covers the code paths, not the data. Rust checks both: an enum value cannot exist unless something constructed it as the type, and serde's derived `Deserialize` rejects an unknown tag as "unknown variant". In TypeScript that check is a separate step you write, with a schema at the boundary.

**Chew on this**

For each union you switch on, where does the value come from, and was it parsed against the union at that point, or only declared to be one?

**Sources**

- https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html (the `satisfies` operator)
- https://www.typescriptlang.org/docs/handbook/2/narrowing.html (exhaustiveness checking with `never`)
- https://effect.website/docs/code-style/pattern-matching/
- https://github.com/tc39/proposal-pattern-matching (Stage 1)
- https://doc.rust-lang.org/reference/statements.html#let-else-statements

**Gotchas**

- `const unhandled: never = session; throw new Error(...)` gives the same compile-time check and fails loudly at runtime: it threw `unhandled session {"kind":"admin","user_id":"u9"}`.
- `Match.exhaustive`'s runtime message changed path between versions: "effect/Match/exhaustive: absurd" on 3.22.4, "effect/match/Match/exhaustive: absurd" on 4.0.6. Do not match on that string.
- When a case is added, the `Match.exhaustive` error is long (a full `Matcher<...>` type) and a second one appears at the call site, TS2349 "This expression is not callable", because the matcher's type became `never`.

# The functional angle: adding a case is a compile error in three of the four, and C++ is the one where it is a different arm

_Draws on all four tips. The shape is "add one case to a sum type that existing code matches on", and the question is what the existing match does about it._

| Language | Construct | New case with no handler | What it costs |
| --- | --- | --- | --- |
| F# | discriminated union | FS0025 warning; an error only with warnings as errors | the default build succeeds and throws `MatchFailureException` on the new case |
| F# | .NET enum | caught by `_`, silently, if FS0104 was silenced with a wildcard | `#nowarn "104"` restores FS0025 and gives up the runtime-value warning |
| Rust | `enum` | E0004 unless a `_` arm exists; a `_` on a complete match draws "unreachable pattern" | nothing by default; `_` is the opt-out, and it warns while it is redundant |
| C++ | `std::variant` + `overloaded` | routed to whichever handler the new type converts to, with no diagnostic | a deleted template catch-all in every visitor |
| TypeScript | tagged union + `satisfies never` | TS1360 | runtime data is unchecked; the `default` arm is the runtime answer |

F# is the baseline here for a mechanical reason: it is the only one of the four with both a real sum type (the union) and a type that looks like one but is not (the enum), in the same `match` syntax. The two rows show that what makes an exhaustive match safe is that the type cannot hold an undeclared value, not the `match` keyword. Rust's enums have that property, C++'s variant has it for values but not for overload resolution, and TypeScript has it only up to the first `JSON.parse`.

Left open: if exhaustiveness is a property of the type rather than of the match, which of your "enums" are really sum types, and which are integers with names?

# The security angle: an unknown tag takes whatever path the fallback chose, so a boolean shortcut fails open

_Draws on the TypeScript tip, Mode D: make the insecure state unrepresentable, and see what happens where it cannot be. Direction: the type system prevents the bug in the code it sees and permits it in the data it does not._

The insecure sample is a shortcut that looks equivalent to the exhaustive switch:

```typescript
// TypeScript (run as JS on Node 22.23.4): "everyone who is not anonymous may post"
const can_post_shortcut = (session: Session): boolean => session.kind !== "anonymous"
// {"kind":"admin"}     -> true   (a tag the union never declared)
// {"kind":"anonymus"}  -> true   (a typo from another service)
```

It compiles against the same `Session` type, and it fails open: every value that is not literally `"anonymous"` is allowed, including tags the code has never seen. The exhaustive switch in the tip fails closed only because its `default` arm happens to return `false`. That is CWE-863 (Incorrect Authorization), reached through CWE-1287 (Improper Validation of Specified Type of Input): the type said `Session`, and nothing checked it.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | a wire tag outside the union reaches a permission check (CWE-863) | nothing at runtime; `JSON.parse` is `any` | parse at the boundary (a schema decode), and write permission checks as an allow-list switch whose `default` denies |
| C++ | a new variant alternative is routed to an existing handler by conversion | nothing; overload resolution is working as designed | a deleted template catch-all in every visitor that makes a decision |
| F# | an enum value with no name (`enum<Region> 7`) reaches a match | `_` takes it silently; without `_`, `MatchFailureException` | decide per match: route unknowns explicitly, or `#nowarn "104"` and let it throw |
| Rust | nothing at the language level: `7u8 as Region` does not compile | an enum cannot hold an undeclared value in safe code | the conversion from the wire (`TryFrom`, a deserializer) is where unknown values must be rejected |

Left open: which of your permission checks is written as "not the forbidden case" rather than "one of the allowed cases"?

# FAQ

**What is Rust's `Infallible` actually for, and where does it show up?**
It is an enum with no variants, stable since Rust 1.34 (it arrived with `TryFrom`), and the docs call it "the error type for errors that can never happen". Its job is to fill the `E` slot of a generic API whose concrete implementation cannot fail, "to indicate that the result is always `Ok`". Where it shows up, measured on rustc 1.99.1:

- **std's blanket `TryFrom`**: every `From` conversion is also a `TryFrom` with `Error = Infallible`, so `i64::try_from(5i32)` has error type `core::convert::Infallible`, while the lossy `u8::try_from(300i32)` has `TryFromIntError`.
- **`FromStr for String`**: `"x".parse::<String>()` has error type `Infallible`, which is why the Rust tip above could write `let Ok(region) = ...`.
- **Service traits that demand an error type**: hyper's own hello-world handler returns `Result<Response<Full<Bytes>>, Infallible>` because it never fails (from hyper's guide; not compiled here).

It costs nothing: `size_of::<Result<u32, Infallible>>()` is 4, the same as `u32` (`Result<u32, String>` is 24). It implements `Error`, so `?` lifts it into a `Box<dyn Error>` signature with no conversion to write. The docs also call it a stand-in: once the never type `!` is stable, the plan is `pub type Infallible = !;` and, eventually, deprecating the name. C++ and F# have no equivalent; TypeScript's `never` plays the same role in a type parameter (`Result<T, never>`).

**F#'s `let datacenter = match region with ...` binds the result of a match. What is the equivalent in the other three?**
It works in F# because `match` is an expression, so `let` can bind whatever the chosen arm returns. Rust is the only other one of the four where that is true as written. Every snippet below ran:

```fsharp
// F# 10
let datacenter = match region with | "eu" -> "fra" | "us" -> "iad" | _ -> "sin" // fra
```

```rust
// Rust 1.99.1, edition 2024
let datacenter = match port { 8000..=8999 => "fra", _ => "iad" };          // the same shape as F#
let Some(port) = port_for(service) else { return format!("{service}: no port") }; // let-else, Rust 1.65
if let Some(admin_port) = port_for("api") && admin_port == port { /* .. */ }      // let chains, edition 2024
```

Rust adds two forms F# does not have. `let ... else` binds on a match and requires the `else` to leave the scope: an `else` that only prints is "E0308: `else` clause of `let...else` does not diverge". Let chains (`if let ... && ...`) need edition 2024.

```cpp
// C++23, g++ 14.2: no match expression; an immediately invoked lambda turns statements into a value
const char* const datacenter = [&] {
    if (region == "eu") return "fra";
    if (region == "us") return "iad";
    return "sin";
}();                                                                          // fra
const char* const by_ternary = region == "eu" ? "fra" : region == "us" ? "iad" : "sin"; // fra
```

C++ has no match expression yet, so the idioms are the immediately invoked lambda (`[&] { ... }()`), which also lets the result be `const`, and a ternary chain. For a `std::variant`, `std::visit` returning a value is the closest thing to a typed match (part 2's C++ tip shows where it differs).

```typescript
// TypeScript, tsc 7.0.2, effect 4.0.6
const by_ternary = region === "eu" ? "fra" : region === "us" ? "iad" : "sin" // fra
const by_match = Match.value(region).pipe(
    Match.when("eu", () => "fra"),
    Match.when("us", () => "iad"),
    Match.orElse(() => "sin"))                                                // fra
```

TypeScript's expression forms are the nested ternary and Effect's `Match`, which with `Match.exhaustive` instead of `Match.orElse` is the only one of the TypeScript forms that checks coverage. A native `match (x) { when ...: ...; default: ... }` expression is a TC39 proposal at Stage 1, so not in the language.

**Isn't a catch-all that asserts "Unhandled match case {value}" the safe default everywhere?**
It is the right move where the compiler cannot see the cases, and it costs you the compile-time check where it can. Measured, after adding an `Asia` member that no arm handles:

| Where | With the catch-all assert | Without it |
| --- | --- | --- |
| Rust, your own `enum` | `other => unreachable!("Unhandled match case {other:?}")` compiles and panics at runtime | "E0004: non-exhaustive patterns: `Region::Asia` not covered" at build time |
| F#, your own union | an asserting `_` compiles, and the build stays green | FS0025 (an error with warnings as errors) |
| C++, `switch` on an `enum class` | any `default:` silences `-Wswitch`: g++ 14.2 `-Wall` printed nothing; `-Wswitch-enum` brings it back ("enumeration value 'asia' not handled") | `-Wall` warns: "enumeration value 'asia' not handled in switch [-Wswitch]" |
| C++, `assert` in `default:` | under `-DNDEBUG` (release) the assert is gone and the function falls off its end: "control reaches end of non-void function [-Wreturn-type]", and the call printed an empty string, which is undefined behaviour | |
| TypeScript, `switch` on a union | `const unhandled: never = value; throw new Error(...)` keeps both: TS1360/TS2322 at build time and a throw at runtime | |
| Wire tags, .NET enums, `#[non_exhaustive]`, ints cast to C++ enums | the assert is the only check there is | no compile-time check exists to lose |

So: no catch-all on a sum type you own (let the compiler fail the build), an asserting catch-all on values from outside, and in C++ a check that survives release builds (a throw or `std::abort`, not `assert`). On a request path, prefer returning an error to panicking; part 1's [Cloudflare appendix](2026-10-27-extra-1-of-12.md#appendix-a-cloudflare-2025-11-18-a-failure-value-unwrapped-on-the-request-path) is what a panic on outside input costs.

**Does a `_` arm in Rust warn when every variant is already covered?**
Yes: rustc 1.99.1 printed "warning: unreachable pattern" for `_` after `Region::Europe` and `Region::America`. The warning goes away the day a variant is added, which is exactly when the `_` starts hiding it.

**Does a generic `[](const auto&)` handler in a C++ visitor count as handling the new alternative?**
For the compiler, yes: it is an exact match for every type. With `[](int)` and `[](const auto&)`, the string and the `2.5` both went to the generic handler, and nothing warned. The deleted-template guard is the inverse of that handler.

**Does `#nowarn "104"` in F# make undefined enum values safe?**
No. It tells the compiler to check matches against the declared members only. `enum<Region> 7` still compiles, and the match throws `MatchFailureException` on it at runtime.

**Is `satisfies never` new?**
`satisfies` arrived in TypeScript 4.9. The older form, `const unhandled: never = value`, works in any version with `never` and is what the handbook's narrowing page shows.

# Appendix A: Knight Capital, 2012-08-01, a reused flag value reached the one server where it still meant the old case

_Not part of the tip rotation. Written 2026-10-27; backs the thesis of this part (exhaustive only over the cases the code can see) and the C++ tip (a new value routed to an old handler). A real incident, quoted from the SEC's order; the reproduction is illustrative code, run on rustc 1.99.1 (Debian 13.7)._

**Bug class:** Bohrbug, deployment-triggered: solid on the one server that kept the old code. Anti-pattern: reusing a retired flag's value for a new meaning while code that handles the old meaning still exists somewhere.

## A.1 What happened

Quoted from the SEC order (Release No. 34-70694, October 16, 2013):

- "The new RLP code also repurposed a flag that was formerly used to activate the Power Peg code." Power Peg was functionality Knight "had discontinued using many years earlier", yet it "remained present and callable".
- During the staged deployment, "one of Knight's technicians did not copy the new code to one of the eight SMARS computer servers".
- On August 1, "orders sent with the repurposed flag to the eighth server triggered the defective Power Peg code still present on that server".
- "For the 212 incoming parent orders that were processed by the defective Power Peg code, SMARS sent millions of child orders, resulting in 4 million executions in 154 stocks for more than 397 million shares in approximately 45 minutes." Knight "realized a $460 million loss on these positions".

## A.2 The shape, reproduced

Knight's source is not public, so this is the shape, not the code: two builds decode the same flag byte, and only the old one still has an arm for the old meaning.

```rust
// Rust, rustc 1.99.1. Illustrative shape, not Knight's code (SMARS's source is not public).
mod old_build {
    // The eighth server: flag value 1 still means Power Peg.
    #[derive(Debug)]
    pub enum RoutingMode { Standard, PowerPeg }
    pub fn decode(wire_flag: u8) -> Result<RoutingMode, u8> {
        match wire_flag { 0 => Ok(RoutingMode::Standard), 1 => Ok(RoutingMode::PowerPeg), unknown => Err(unknown) }
    }
}
mod new_build {
    #[derive(Debug)]
    pub enum RoutingMode { Standard, RetailLiquidity }
    pub fn decode_reused(wire_flag: u8) -> Result<RoutingMode, u8> { // RLP reuses value 1
        match wire_flag { 0 => Ok(RoutingMode::Standard), 1 => Ok(RoutingMode::RetailLiquidity), unknown => Err(unknown) }
    }
}
fn main() {
    let rlp_order_flag_reused: u8 = 1; // the repurposed flag
    let rlp_order_flag_fresh: u8 = 2;  // a value the old build has never seen
    println!("new build, reused 1 -> {:?}", new_build::decode_reused(rlp_order_flag_reused));
    println!("old build, reused 1 -> {:?}", old_build::decode(rlp_order_flag_reused));
    println!("old build, fresh 2  -> {:?}", old_build::decode(rlp_order_flag_fresh));
}
```

Printed:

```text
new build, reused 1 -> Ok(RetailLiquidity)
old build, reused 1 -> Ok(PowerPeg)
old build, fresh 2  -> Err(2)
```

Both builds are exhaustive over their own enum, and both compile clean. The match cannot help, because the bug is in what the byte means, not in which arms exist. A fresh value would have reached the old build's `unknown` arm and been rejected. The reused one reached an arm that was correct, for the meaning it used to have.

The SEC's numbers, recomputed (from the same Rust program; "4 million" and "$460 million" are the order's rounded figures, so these are approximate):

```text
executions per parent order ~ 18868
executions per second       ~ 1481
loss per minute             ~ $10.2 million
servers on the old build    = 1 of 8 (12.5%)
```

## A.3 Would a stricter enum type have caught it?

The flag in A.2 is a small integer with names, which is what an enum is. C# is known for refusing the implicit enum-int conversions that C and C++ allow, and the F# tip above showed a .NET enum holding a value no member declares (`enum<Region> 7`). So would C#-style enum rules have stopped a bug like this one? No, and they stop less than their reputation suggests. Measured on .NET SDK 10.0.402, g++ 14.2 and gcc 14.2 (`-std=c17`):

| Conversion | C# | C++ unscoped `enum` | C++ `enum class` (C++11) | C |
| --- | --- | --- | --- | --- |
| enum to int, implicit | CS0266 "Cannot implicitly convert type 'Region' to 'int'" | allowed | "cannot convert 'region_scoped' to 'int'" | allowed |
| int to enum, implicit | CS0266, except the literal `0` | "invalid conversion from 'int' to 'region_plain'" | error | allowed, no warning with `-Wall -Wextra` |
| `(Region)7` by explicit cast | compiles; prints `7`; `Enum.IsDefined` is `false` | compiles | compiles | |

What the C# rule prevents is *accidental mixing*: passing a count where a region was expected, or doing arithmetic on a region. What it does not prevent is an *undeclared value*: an explicit cast still accepts any integer, because at runtime a .NET enum is its underlying integer. That is exactly why F#'s FS0104 and C#'s CS8524 exist, even on a match that names every member. And this incident was neither case: the flag was a declared, valid value whose meaning had changed, which no conversion rule can catch. The design history (whether C# 1.0's rule was a reaction to C++ practice) is not checked here; the table is what today's compilers do.

## A.4 Back to the tips

- **C++:** the visitor tip is the same failure inside one process: a new alternative reaches an existing handler because the old handler accepts it. The deleted-template guard is the in-process version of "use a fresh value".
- **F#:** an enum value is the wire format of this incident. `#nowarn "104"` plus a complete match makes a *new* member a build error, but a *reused* value is not new, so nothing fires.
- **Rust:** the E0005 trick in the Rust tip works because the type changed. Here the type stayed `u8`, so no pattern could notice.
- **TypeScript:** an allow-list switch with a denying `default` handles a fresh tag correctly; it handles a reused tag exactly like the old one.

The SEC order also names a control that would have caught it before the open: an internal system sent "97 of these e-mail messages" reading "Power Peg disabled" before 9:30 a.m., and they "were not acted upon".
