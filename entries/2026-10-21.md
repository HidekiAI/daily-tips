## Rust: max_by_key hands back the last of equal maxima and min_by_key the first, so a ported argmax picks a different winner

*Stdlib and ecosystem gems*

**Did you know**

`Iterator::max_by_key` (and `max`, `max_by`) returns the **last** element when several are equally maximum, while `min_by_key` (and `min`, `min_by`) returns the **first** element when several are equally minimum. Both are documented guarantees, not accidents of the implementation. An argmax written as `enumerate().max_by_key(...)` therefore returns the highest tied index. C++'s `std::max_element` and F#'s `List.maxBy` both return the first.

**Show me**

```rust
use std::cmp::Reverse;

struct Bid {
    bidder: &'static str,
    amount_cents: u64,
}

fn main() {
    let bids = [
        Bid { bidder: "alice", amount_cents: 500 },
        Bid { bidder: "bob", amount_cents: 700 },   // first to bid 700
        Bid { bidder: "carol", amount_cents: 700 }, // second to bid 700
        Bid { bidder: "dave", amount_cents: 300 },
        Bid { bidder: "erin", amount_cents: 300 },
    ];

    // Documented: on a tie for the maximum, the LAST element is returned.
    let winner = bids.iter().max_by_key(|bid| bid.amount_cents).unwrap();
    assert_eq!(winner.bidder, "carol");

    // Documented the other way round: on a tie for the minimum, the FIRST is returned.
    let lowest = bids.iter().min_by_key(|bid| bid.amount_cents).unwrap();
    assert_eq!(lowest.bidder, "dave");

    // An argmax built on enumerate() inherits it: index 2, not 1.
    let (winning_index, _) = bids
        .iter()
        .enumerate()
        .max_by_key(|(_, bid)| bid.amount_cents)
        .unwrap();
    assert_eq!(winning_index, 2);

    // Say the tie-break in the key instead of inheriting it from std:
    // higher amount first, then the EARLIER index (Reverse flips its order).
    let (first_index, first_to_bid) = bids
        .iter()
        .enumerate()
        .max_by_key(|(index, bid)| (bid.amount_cents, Reverse(*index)))
        .unwrap();
    assert_eq!((first_index, first_to_bid.bidder), (1, "bob"));
    println!("ok");
}
```

**Why it matters**

Any "pick the best" over data with ties, such as the highest bid, the least-loaded worker or the newest version, carries a tie-break policy whether anyone wrote one or not. Port the same line from C++ (`max_element`), F# (`List.maxBy`) or a NumPy-style `argmax`, and the first tie becomes the last: carol wins instead of bob, and no compiler or test with distinct values notices. The `(key, Reverse(index))` tuple costs nothing and makes the policy part of the code.

**Chew on this**

Which of your `max_by_key` calls run over data where ties are normal, and does anyone downstream depend on which one wins? If the rule is "first come, first served", where in your code is that written down today?

## C++: const auto& shortest = std::min(load(), fallback) dangles, and wrapping std::min in your own template silences clang's only warning

*Idioms and antipatterns*

**Did you know**

The two-argument `std::min`, `std::max` and `std::clamp` return `const T&`, so binding the result to a reference dangles when the chosen argument was a temporary. This is true in every standard since C++98. On Linux, GCC 14.2's `-Wdangling-reference` (in `-Wall`) warns on the direct call and on a wrapper alike, because it guesses from the call shape. Clang warns (`-Wdangling`, on by default) only because libc++ tags those parameters with `_LIBCPP_LIFETIMEBOUND`: with libstdc++, the Linux default, Debian clang 19 warns on neither. A one-line template wrapper of your own drops the attribute, and under clang the identical bug then compiles with zero warnings. The `std::min({a, b})` initializer_list overload returns `T` by value and cannot dangle.

**Show me**

```cpp
#include <algorithm>
#include <string>

std::string load_display_name();  // returns by value: a temporary at every call site

template <class T>
const T& pick_smaller(const T& left, const T& right) {  // no [[clang::lifetimebound]] here
    return std::min(left, right);
}

void render(const std::string& fallback) {
    // 1. GCC 14.2 -Wall: "possibly dangling reference to a temporary [-Wdangling-reference]".
    //    libc++ marks std::min's parameters lifetimebound, so clang with libc++ says:
    //    "temporary bound to local reference 'direct' will be destroyed at the
    //     end of the full-expression [-Wdangling]"
    const std::string& direct = std::min(load_display_name(), fallback);

    // 2. The same dangling reference through a one-line wrapper: zero warnings from clang.
    //    GCC 14.2 still warns here, exactly as on line 1.
    //    The attribute is on std::min's parameters, not on yours.
    const std::string& wrapped = pick_smaller(load_display_name(), fallback);

    // 3. The fix std already ships: the initializer_list overload returns T by value.
    const std::string copied = std::min({load_display_name(), fallback});

    // 4. Or bind by value; the copy is what the reference was pretending to avoid.
    const std::string by_value = std::min(load_display_name(), fallback);

    (void)direct; (void)wrapped; (void)copied; (void)by_value;
}
```

**Why it matters**

`const auto&` on a call result is a habit people pick up to "avoid a copy", and lifetime extension makes it safe for functions that return by value. It is not safe for functions that return one of their reference parameters. The bug only fires on the call where the temporary wins the comparison, so it passes most tests. Under ASan (GCC 14.2 on Debian 13, and Apple clang 21), reading `wrapped` was reported as `stack-use-after-scope`. Rust rejects the same shape at compile time: a `fn min<'a>(left: &'a T, right: &'a T) -> &'a T` cannot outlive a temporary argument.

**Chew on this**

How many of your own helpers return a `const T&` taken from a parameter, and do any of them carry `[[clang::lifetimebound]]`? Would a code reviewer catch `const auto& limit = std::clamp(requested * 2, low, high);`?

**Sources**

- https://en.cppreference.com/w/cpp/algorithm/min
- https://en.cppreference.com/w/cpp/algorithm/clamp
- https://github.com/llvm/llvm-project/blob/main/libcxx/include/__algorithm/min.h

**Verified**

GCC 14.2 on Debian 13, `-std=c++20 -Wall -Wextra`: `-Wdangling-reference` on lines 1 and 2, nothing on lines 3 and 4; with `-fsanitize=address` and a `main` that reads `wrapped`, ASan reported `stack-use-after-scope`. Debian clang 19: with libc++ 19, `-Wdangling` on line 1 only; with libstdc++, no warning on any line. As a separate confirmation, Apple clang 21 with libc++: the `-Wdangling` warning on line 1 and its absence on line 2 were observed, and ASan reported the dangling read.

## F#: Map.Count walks the whole tree on every call, so if prices.Count > 0 costs about 1 ms at a million entries

*Stdlib and ecosystem gems*

**Did you know**

An F# `Map` node stores its key, value, height and children, but not a size. `Map.Count`, `Map.count`, `Set.Count` and `Set.count` all recount by walking every node (`MapTree.size` calls `sizeAux` recursively), so they are O(n) per call. `Map.isEmpty` only looks at the root. Measured in `dotnet fsi` (F# 8, FSharp.Core 8.0.0, .NET 8.0.8), over 1000 calls each:

| Entries | `m.Count` per call | `Map.isEmpty` per call | `Dictionary.Count` per call |
| --- | --- | --- | --- |
| 1,000 | 2.3 us | 0.08 us | 0.02 us |
| 100,000 | 199 us | 0.02 us | 0.3 us |
| 1,000,000 | 1.07 ms | 0.06 us | 0.04 us |

**Show me**

```fsharp
// F# 8, FSharp.Core 8.0.0, .NET 8.0.8 (dotnet fsi)
let prices = Map.ofSeq (Seq.init 1_000_000 (fun index -> index, index * 2))

// Reads like a field. It is MapTree.size: a recursive walk of every node.
let has_prices_slow = prices.Count > 0      // ~1.07 ms per call at 1,000,000 entries

// The same question answered from the root alone.
let has_prices = not (Map.isEmpty prices)    // ~0.06 microseconds per call

// Set.Count is the same walk (~0.93 ms at 1,000,000). When the size is needed
// often, carry it beside the map; the immutable update keeps both in step.
type PriceBook = { entries: Map<int, int>; entry_count: int }

let add_price (book: PriceBook) (sku: int) (price: int) : PriceBook =
    let already_listed = Map.containsKey sku book.entries
    { entries = Map.add sku price book.entries
      entry_count = if already_listed then book.entry_count else book.entry_count + 1 }

let book = add_price (add_price { entries = Map.empty; entry_count = 0 } 7 100) 7 120
printfn "%b %b %d %d" has_prices_slow has_prices book.entry_count book.entries.[7]
```

**Why it matters**

`Count` is a property, and on every BCL collection a property read is O(1), so nobody looks twice at `while queue.Count > 0` or a `Count` in a log line on a hot path. On a `Map` holding a large in-memory cache, that line is a full tree walk per request, and inside a loop that shrinks the map it turns O(n log n) work into O(n^2). Rust's `BTreeMap::len` and C++'s `std::map::size` are O(1) because they keep a counter. F# chose not to, which keeps every node small and every `Map.add` free of bookkeeping.

**Chew on this**

Where does your code ask a `Map` or `Set` for its `Count` just to compare it with zero? If you carried the count yourself as in `PriceBook`, which code path would be the first to update the map and forget the counter?

**Sources**

- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/map.fs
- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/set.fs
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/fsharp-collection-types

**Verified**

The timings are FSharp.Core 8.0.0. The O(n) `sizeAux` walk was confirmed in `main`'s `map.fs`, but newer FSharp.Core versions were not timed. `Set.count` is listed as O(N) in the Learn collection table, but `Map.count` has no row there, and `set.fs` was not opened.

## TypeScript: TypeScript 6.0 defaults types to [], so process and describe vanish until you list @types/node yourself

*New discoveries and currently popular patterns*

**Did you know**

Before 6.0, leaving `compilerOptions.types` unset meant "load every visible `node_modules/@types/*` package", including those in parent folders. From TypeScript 6.0 the default is `[]`, so an unchanged tsconfig suddenly stops seeing globals such as `process`, `Buffer`, `describe` and `expect`. tsc 6.0.3 reports `error TS2591: Cannot find name 'process'` and tells you to add `node` to `types`. Setting `"types": ["*"]` brings back the old load-everything behaviour (measured with a stand-in `@types` package).

**Show me**

```ts
// tsconfig.json, unchanged across the upgrade:
//   { "compilerOptions": { "noEmit": true, "strict": true }, "include": ["src"] }
//
// src/main.ts
export const port: number = Number(process.env.PORT ?? 8080)
// tsc 5.x: compiles, @types/node was picked up implicitly.
// tsc 6.0.3: error TS2591: Cannot find name 'process'. Do you need to install type
//   definitions for node? Try `npm i --save-dev @types/node` and then add 'node'
//   to the types field in your tsconfig.

// Fix, stated per project instead of inherited from whatever is in node_modules:
//   "types": ["node"]                 // server package
//   "types": ["node", "jest"]         // its test tsconfig only
//   "types": ["*"]                    // the pre-6.0 behaviour, if you must
```

**Why it matters**

In a monorepo, the old default made globals leak in from whatever `@types` package any workspace hoisted, so a browser package could typecheck `process.env` and then crash at runtime, and test globals like `expect` showed up in production code. The new default turns that leak into a compile error, at the price of an upgrade that fails across every package at once. Rust and F# never had this ambient mode, because a crate or assembly reaches your code only through an explicit dependency.

**Chew on this**

If you set `types` package by package, which of your packages turn out to depend on a global they never declared? Is `["*"]` a migration step for you, or does it quietly become the permanent setting?

**Sources**

- https://www.typescriptlang.org/tsconfig/#types

**Verified**

Run on tsc 6.0.3 only. The pre-6.0 behaviour is taken from the tsconfig reference ("For versions below TypeScript 6.0 ...") and was not run on a 5.x compiler. The `["*"]` behaviour was measured, but its documentation was not found on typescriptlang.org.

# The functional angle: "pick the best" is a fold, and each standard library hides a different tie-break inside it

Draws on the Rust tip (`max_by_key`), with F# and C++ as peer rows and TypeScript written by hand.

The shape is a fold that keeps the current best: `fold (fun best item -> if better item best then item else best)`. Whether "better" means `>` or `>=` is the whole tie-break, and every library picked one for you:

```fsharp
// F#: List.maxBy keeps the FIRST of equal maxima (dotnet fsi, FSharp.Core 8.0.0)
let bids = [ "alice", 500; "bob", 700; "carol", 700; "dave", 300; "erin", 300 ]
List.maxBy snd bids |> fst   // "bob"
List.minBy snd bids |> fst   // "dave"
```

```ts
// TypeScript: no maxBy in the standard library; the comparison you write is the policy.
const first_max = bids.reduce((best, bid) => (bid.amount > best.amount ? bid : best))   // bob
const last_max = bids.reduce((best, bid) => (bid.amount >= best.amount ? bid : best))   // carol
```

| Language | Functional form | Tie on the maximum | What it costs |
| --- | --- | --- | --- |
| F# | `List.maxBy` / `Seq.maxBy` / `Array.maxBy` | first (`bob`), measured | nothing to write, and nothing in the name says which tie wins |
| Rust | `max_by_key` | last (`carol`), documented and measured | the opposite of `min_by_key`; a `(key, Reverse(index))` tuple restores first |
| C++ | `std::ranges::max_element` | first, documented | `std::minmax_element` returns the LAST max, measured: three answers in one header |
| TypeScript | `reduce` with `>` or `>=` | whichever operator you typed | no hidden policy, so one character is the whole policy |

No row needs a `mut`: the policy lives entirely in the comparison. The asymmetry is that only TypeScript makes you write it.

Which "best" in your code would change its answer if the comparison flipped from `>` to `>=`?

# The security angle: an implicit tie-break is a policy an attacker can pick their side of

Draws on the Rust tip (in Mode B: is "which tie wins" safe?) and on the C++ tip (Mode C: the check the wrapper dropped). In the Rust case the language prevents nothing. In the C++ case the library's warning prevents the bug only until someone wraps the call.

**Tie-break as a lever (CWE-697, incorrect comparison).** When the inputs can be chosen, so can the tie. An auction that runs `max_by_key` over bids lets a late bidder who matches the top amount take it from the earlier one. A scheduler that runs `min_by_key` over load scores keeps choosing the same first-listed host, which a tenant can arrange to be one they control or starve.

```rust
// Looks like "highest bid wins". Is actually "the LAST of the highest bids wins".
// A bidder who sees the top amount and matches it, rather than beats it, takes the lot.
let winner = bids.iter().max_by_key(|bid| bid.amount_cents);
```

**Dangling through a wrapper (CWE-825, expired pointer dereference; CWE-416 when the buffer is heap).** Line 2 of the C++ snippet compiles cleanly under clang (GCC 14.2 warns), and the ASan runs reported a read after the temporary's scope ended. The bytes read come from a destroyed `std::string`, and the next allocation may already own them.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | ties resolve to the last maximum | documents it; nothing more | put the tie-break in the key whenever the inputs are untrusted |
| C++ | `const T&` from `std::min` outlives its temporary | GCC warns on both, by heuristic; clang + libc++ warn on direct calls only | `[[clang::lifetimebound]]` on your own wrappers, or return by value |
| F# | ties resolve to the first maximum | documents nothing in the name | the same explicit key, e.g. `List.maxBy (fun bid -> amount bid, -index bid)` |
| TypeScript | `>` vs `>=` in a hand-written `reduce` | nothing, and no dangling-reference class exists | a test with deliberate ties |

Rust is the control row for the memory half: the C++ wrapper's signature cannot be written in safe Rust without tying the result's lifetime to both arguments. Nobody is a control row for the tie-break half.

Which of your "pick one" functions gets its input from a party that benefits from winning the tie?
