## Rust: Vec::into_parts hands you a pointer even for an empty Vec, and it is 0x8, which is not null and not something free accepts

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.99.0 (released 2026-10-01) stabilized `Vec::into_parts` and `Vec::from_parts`. They are the `NonNull` twins of `into_raw_parts` (1.93) and `from_raw_parts`: the Vec comes apart into `(NonNull<T>, length, capacity)` and the destructor no longer runs. The part that surprises is what an empty Vec gives you. It owns no allocation, so the "pointer" is a dangling address equal to the element alignment (`0x8` for `u64`), non-null by construction and never something an allocator handed out. A `Vec<()>` reports a capacity of `usize::MAX`.

**Show me**

```rust
use std::ptr::NonNull;

fn main() {
    // An empty Vec owns no allocation: the pointer is a dangling, aligned address.
    let never_allocated: Vec<u64> = Vec::new();
    let (empty_start, empty_len, empty_capacity) = never_allocated.into_parts();
    println!("empty: addr={:#x} len={empty_len} cap={empty_capacity}", empty_start.as_ptr() as usize);

    // A zero-sized element type reports capacity usize::MAX and never allocates.
    let unit_items: Vec<()> = vec![(), (), ()];
    let (_, unit_len, unit_capacity) = unit_items.into_parts();
    println!("Vec<()>: len={unit_len} cap={unit_capacity}");

    // A real allocation round-trips, and the spare capacity travels with the pointer.
    let mut vec_with_spare_capacity: Vec<u64> = Vec::with_capacity(10);
    vec_with_spare_capacity.extend([7, 8, 9]);
    let (buffer_start, buffer_length, buffer_capacity): (NonNull<u64>, usize, usize) = vec_with_spare_capacity.into_parts();
    // SAFETY: the three values come unchanged from into_parts of a global-allocator Vec<u64>.
    let rebuilt_vec: Vec<u64> = unsafe { Vec::from_parts(buffer_start, buffer_length, buffer_capacity) };
    println!("rebuilt_vec={rebuilt_vec:?} cap={}", rebuilt_vec.capacity());
}
```

C++ comparison: `std::vector` has no way to give up ownership at all. `items.release()` does not exist (g++ 16.2, `-std=c++23`: "no member named 'release'"), so handing a buffer to another owner means a custom allocator or a copy. F# has no raw buffer to hand over, and TypeScript's nearest thing is transferring an `ArrayBuffer`, which detaches the sender.

**Why it matters**

The tuple is how a buffer crosses an FFI boundary or an arena without a copy, and `NonNull` means the callee never has to ask "is it null". The cost is that "non-null" now reads as "allocated", and for a Vec with capacity 0 it is not.

**Chew on this**

Where does a buffer from one of your Vecs end up being freed by a rule other than Rust's? Would that code know a capacity-0 Vec arrived there as `0x8`?

**Sources**

- https://doc.rust-lang.org/std/vec/struct.Vec.html#method.into_parts
- https://releases.rs/docs/1.99.0/
- https://blog.rust-lang.org/2026/10/01/Rust-1.99.0/
- https://releases.rs/docs/1.98.0/ (for the 1.98 lint)

**Gotchas**

- Passing an empty Vec's pointer (`0x8`) to C `free` crashed the probe: `Segmentation fault`, exit 139 (rustc 1.99.1, glibc, Debian trixie).
- `into_parts` does not shrink: a Vec with capacity 1000 and one element came back as `len=1 cap=1000`, and the spare room travels with the pointer.
- rustc 1.99.1 warns `suspicious_runtime_symbol_definitions` (added in 1.98) when your own `extern "C"` block declares `free` with `*mut u8` instead of `*mut c_void`.
- Dropping the three values without calling `from_parts` leaks the buffer, per the documentation: only `from_parts` lets the destructor clean up.

## C++: std::inplace_vector throws bad_alloc when it is full, although nothing was allocated, and only GCC 16 ships it

*Stdlib and ecosystem gems*

**Did you know**

`std::inplace_vector<T, N>` is C++26 (P0843): a vector whose elements live inside the object, with a hard capacity of `N`. Its `push_back` on a full container throws `std::bad_alloc`, even though no allocation was attempted. `try_push_back` is the non-throwing form and returns `std::optional<T&>` (empty when full), and `unchecked_push_back` is a precondition: `size() < capacity()`. Support is thin: the cppreference C++26 table lists libstdc++ 16 and nothing for libc++ or MSVC STL.

**Show me**

```cpp
// C++26 <inplace_vector>; GCC 16 only at the time of writing
#include <inplace_vector>
#include <iostream>
#include <new>
#include <string>
#include <type_traits>

int main() {
    std::inplace_vector<int, 4> fixed_items{};
    for (int pushed_value = 1; pushed_value <= 4; ++pushed_value) fixed_items.push_back(pushed_value);

    // Full: push_back throws bad_alloc, although nothing tried to allocate.
    try { fixed_items.push_back(5); }
    catch (const std::bad_alloc& bad_alloc_error) { std::cout << "push_back: " << bad_alloc_error.what() << '\n'; }

    // Full: try_push_back returns std::optional<int&>, empty here; size stays 4.
    auto optional_pushed_ref = fixed_items.try_push_back(5);
    std::cout << "try_push_back: " << (optional_pushed_ref.has_value() ? "placed" : "nullopt")
              << " size=" << fixed_items.size() << '\n';

    // The elements live inside the object, so there is no buffer for a move to steal.
    std::inplace_vector<std::string, 2> source_names{};
    source_names.push_back(std::string(40, 'a'));
    auto destination_names = std::move(source_names);
    std::cout << "after move: source size=" << source_names.size()
              << " source[0].size=" << source_names[0].size() << '\n';
    std::cout << "sizeof=" << sizeof(fixed_items) << " trivially_copyable="
              << std::is_trivially_copyable_v<std::inplace_vector<int, 4>> << '\n';
}
```

Rust comparison: Rust std has no fixed-capacity vector; the `arrayvec` and `heapless` crates provide one (documentation only, not run here). Where `push` on a full `heapless::Vec` returns an `Err` carrying the element back, the C++ default is an exception.

**Why it matters**

It removes the allocator from a latency-sensitive path (no malloc, so no lock and no fragmentation), and makes the array-plus-count pattern a type. What you have to decide is the full case, and the default arm of that decision is an exception.

**Chew on this**

Which of your bounded buffers should throw, return empty, or abort when full? Does the code on that path even build with exceptions on?

**Sources**

- https://en.cppreference.com/cpp/compiler_support/26
- https://eel.is/c++draft/inplace.vector.modifiers
- https://wg21.link/p0843

**Verified**

Debian 13.7 `gcc:latest`, g++ (GCC) 16.2.0, `-std=c++26 -Wall -Wextra`, warning-free. Not verified: Clang with libc++ and MSVC STL (Debian clang 19.1.7 on `debian:stable` had no `<inplace_vector>` header with either Debian's libstdc++ or libc++; the MSVC state rests on the cppreference table).

**Gotchas**

- `-std=c++23` on g++ 16.2 fails with `'inplace_vector' is not a member of 'std'`, and g++ 15.3.0 fails with `fatal error: inplace_vector: No such file or directory`. GCC 16's `bits/version.h` defines `__glibcxx_inplace_vector` as `202603L`.
- `sizeof(std::inplace_vector<int,4>)` is 20 against 24 for a `std::vector<int>`, and `sizeof(std::inplace_vector<int,0>)` is 1.
- It is trivially copyable for `int` (1) and not for `std::string` (0), so only the first can be `memcpy`ed.
- Moving does not steal anything: after the move the source still reported `size=1`, and its string was emptied (`source[0].size=0`).

## F#: readings[1..] copies the rest of the array on every call, so head-and-rest recursion over an array allocated 8 MB for 2,000 numbers

*Perf and memory model*

**Did you know**

On an F# list, `head :: tail` shares the tail and costs nothing, so recursing on "the rest" is the idiom. An array has no shared tail: `readings[1..]` allocates and copies a new array, so the same recursion is quadratic in bytes. Doubling the array from 2,000 to 4,000 elements grew the allocation from 8,048,008 to 32,096,008 bytes. A `ReadOnlySpan<int>` slice, a view over the same memory, allocated 32 bytes for the whole walk. (F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14.)

**Show me**

```fsharp
open System

let readings: int[] = Array.init 2_000 id

// Array slice: readings[1..] allocates and copies a new array on every call.
let rec sum_by_array_slice (remaining_readings: int[]) : int64 =
    if remaining_readings.Length = 0 then 0L else int64 remaining_readings[0] + sum_by_array_slice remaining_readings[1..]

// ReadOnlySpan slice: a view over the same memory, no copy.
let rec sum_by_span (remaining_readings: ReadOnlySpan<int>) : int64 =
    if remaining_readings.Length = 0 then 0L else int64 remaining_readings[0] + sum_by_span (remaining_readings.Slice 1)

let measure_allocated_bytes (sum_action: unit -> int64) : int64 * int64 =
    sum_action () |> ignore // warm up
    let allocated_bytes_before = GC.GetAllocatedBytesForCurrentThread()
    let sum_of_readings = sum_action ()
    sum_of_readings, GC.GetAllocatedBytesForCurrentThread() - allocated_bytes_before

printfn "array [1..]: %A" (measure_allocated_bytes (fun () -> sum_by_array_slice readings))
printfn "span Slice : %A" (measure_allocated_bytes (fun () -> sum_by_span (ReadOnlySpan<int> readings)))
```

Rust and C++ comparison: Rust's `&readings[1..]` and C++20's `span::subspan` are views, so the same shape allocated 0 bytes in both, and copying the tail (`to_vec()`, a new `std::vector`) allocated about 32 MB each (see "The functional angle").

**Why it matters**

A head-and-rest function that is fine on a 10-element list becomes a memory-bandwidth problem when the input is an array of 100,000 rows from a request, and the code does not look any different.

**Chew on this**

Which of your recursive functions were written head-and-rest because that read well on a list, and later got an array passed in? Would you notice, given that the answers are identical?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/arrays
- https://learn.microsoft.com/en-us/dotnet/api/system.readonlyspan-1.slice

**Verified**

`dotnet fsi --optimize+` on the `mcr.microsoft.com/dotnet/sdk:10.0` image, which is Ubuntu 24.04 (no Debian image exists for the .NET SDK). Allocation is `GC.GetAllocatedBytesForCurrentThread()` after one warm-up call.

**Gotchas**

- `list[1..]` is not quadratic: it allocated 48,032 bytes for 2,000 elements and 96,032 for 4,000, about 24 bytes per call, because it shares the tail.
- Out-of-range array slices return an empty array: `readings[5000..]` on 2,000 elements had length 0. `Array.sub readings 5000 1` and `ReadOnlySpan.Slice 5000` both threw.
- The slice is a copy: after `let sliced = readings[1..3]` and `sliced[0] <- -1`, `readings[1]` was still 1.

## TypeScript: NoInfer<T> stops the fallback voting for T, but with an inline array literal it changed nothing and the typo compiled

*Type system deep cuts*

**Did you know**

`NoInfer<T>` (TypeScript 5.4) marks a parameter position that must be checked against `T` but may not contribute to inferring it. Without it, `pick_loose(status_options, 'activ')` infers `T` as `"activ" | Status`, so the typo widens the type instead of failing. With it, `T` comes from `allowed_options` only and the typo is error TS2345. The catch is the inline literal: when `allowed_options` is `['active', 'suspended']`, `T` is already `string`, and `NoInfer` has nothing to protect. (tsc 7.0.2, `--strict`.)

**Show me**

```typescript
type Status = 'active' | 'suspended'

function pick_loose<T>(allowed_options: T[], fallback_status: T): T { return allowed_options[0] ?? fallback_status }
function pick_strict<T>(allowed_options: T[], fallback_status: NoInfer<T>): T { return allowed_options[0] ?? fallback_status }

const status_options: Status[] = ['active', 'suspended']

// Every position votes for T, so the typo joins the union: T = "activ" | Status.
const picked_loose = pick_loose(status_options, 'activ')
// NoInfer removes the fallback's vote: T = Status, and the typo is TS2345.
// const picked_strict = pick_strict(status_options, 'activ')
const picked_strict = pick_strict(status_options, 'active')

// Only with an inline literal array does it quietly do nothing: both T candidates are string.
const picked_from_inline_literal = pick_strict(['active', 'suspended'], 'activ') // T = string, compiles
console.log(picked_loose, picked_strict, picked_from_inline_literal)
```

C++ and Rust comparison: C++ has the same switch as `std::type_identity_t<Item>` (C++20): without it `pick_loose(vector<string>, "typo")` is "no matching function" (deduction conflict, g++ 16.2), with it the call compiles and the argument converts. Rust has no inference voting problem to switch off: `pick_or_default(&names, "typo")` is E0308, expected `String`, found `&str` (rustc 1.99.1).

**Why it matters**

A default or fallback argument is where a typo in a status, role, or permission name gets in. TypeScript is the one of the three where the typo can silently become part of the type, and `NoInfer` works only when the real type was written down somewhere.

**Chew on this**

Which of your generic functions have a parameter that is only meant to be checked against another one, never to add a type to it? Which of their callers pass an inline literal?

**Sources**

- https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-4.html#the-noinfer-utility-type
- https://en.cppreference.com/cpp/types/type_identity

**Gotchas**

- A function where the only parameter is `NoInfer<T>` is unusable: `only_no_infer(5)` failed with TS2345, "'5' is not assignable to parameter of type 'never'".

# The functional angle: head-and-rest recursion is cheap only where the rest is a view, and only F# lists give it to you without asking

Draws on the F# tip (array slices) and the Rust tip (borrowed buffers), with C++ and TypeScript as the other rows. F# is the baseline because its list is the one structure where "the rest" is shared by construction.

One shape, "sum a sequence by taking the first element and recursing on the rest", over 4,000 integers:

| Language | Functional form | Bytes allocated, n=4000 | What it costs |
| --- | --- | --- | --- |
| F# | `head :: tail` on a list | 32 | tail shared; no copy at all |
| F# | `remaining[1..]` on an array | 32,096,008 | a full copy per call; quadratic |
| F# | `ReadOnlySpan.Slice 1` | 32 | a view (the 32 bytes are measured; that a span cannot be captured by a closure is the documented rule, not measured) |
| Rust | `[head, tail @ ..]` on `&[i32]` | 0 | borrow only; the tail cannot outlive the buffer |
| Rust | `split_first` then `tail.to_vec()` | 32,008,000 | an owned copy per call; quadratic |
| C++ | `std::span::subspan(1)` (C++20) | 0 | view; dangles if the vector reallocates |
| C++ | `std::vector(first + 1, last)` | 31,992,000 | a copy per call; quadratic |
| TypeScript | `remaining.slice(1)` on a plain `Array`, in a loop | not counted; 245.8 ms at 20,000, 3,756.6 ms at 40,000, 15,289.8 ms at 80,000 | a plain Array has no view; an index loop took 0.73, 4.52 and 4.56 ms |
| TypeScript | `Int32Array.subarray(1)` | not counted | a view: `.buffer` is the same object and a write through the base showed in the view; index-parameter recursion (`sum(readings, position + 1)`) summed to 1,008, no mutation |

Measured with rustc 1.99.1 (counting global allocator, `-C opt-level=0`), g++ 16.2.0 (replaced `operator new`, `-O0`), F# 10 on .NET 10.0.14 and Node 26.13.0, all in Docker (F# on Ubuntu 24.04, the rest Debian trixie, aarch64). The TypeScript timings are not an exact 4x per doubling (the first doubling was 15x), so read them as "much worse than linear", not as a fit.

The asymmetry to lead with: the functional form stays immutable in every row. A plain TypeScript `Array` has no view, so `slice(1)` copies, but typed arrays do (`subarray`, measured sharing the buffer), and an index parameter keeps the recursion free of mutation on either. What differs is which type gives you the view by default: F# list, Rust slice and C++ span do, a TypeScript `Array` does not.

Hanging thread: if a language gives you a view that is free, but one that can dangle (C++) or be forbidden from escaping (Rust, F#), which of the three failures would you rather find in review?

# The security angle: a fixed capacity and a dangling-but-valid pointer turn a count somebody else chose into a write or a free you did not intend

Draws on the Rust tip (`into_parts`), the C++ tip (`inplace_vector`) and the F# tip (array slices), by Mode B: each tip taught a mechanism, and each is asked "is this secure?". It runs in the direction where the language does not prevent the bug. The question is asked, not answered.

```cpp
// C++26: looks like a bounded buffer, and the loop count comes from the request.
std::inplace_vector<int, 4> fixed_items{};
for (int pushed_value = 0; pushed_value < attacker_chosen_count; ++pushed_value)
    fixed_items.unchecked_push_back(pushed_value);   // precondition: size() < capacity()
```

With a count of 7 the outcome depends on the build, read from the program's own exit code (g++ 16.2.0, `-std=c++26`, `gcc:latest`): at `-O0` it aborted by default with `Assertion '_M_size < _Nm' failed` (exit 134); at `-O1` and `-O2` it printed `size=7` and exited 0, with no diagnostic; at `-O1 -fsanitize=address` it reported `stack-buffer-overflow ... WRITE of size 4` at `unchecked_emplace_back` (exit 1); at `-O2 -D_GLIBCXX_ASSERTIONS` it aborted again (exit 134). That is CWE-787 (out-of-bounds write).

```rust
// Rust: the Vec was empty, the pointer was handed to C, and C frees it.
let (buffer_start, _, _) = never_allocated.into_parts();
unsafe { free(buffer_start.as_ptr().cast::<u8>()) };   // 0x8 was never malloc'd
```

The probe printed `handing 0x8 to C free` and died with `Segmentation fault` (exit 139): CWE-590 (free of memory not on the heap). Nothing in the type said the Vec was empty, because `NonNull` only promises non-null.

```fsharp
// F#: reads like a recursive walk over the request body.
let rec sum_rows (remaining_rows: int[]) = ... sum_rows remaining_rows[1..]
```

A body of 2,000 rows allocated 8,048,008 bytes and 4,000 rows 32,096,008, so a client that sends twice the rows costs the server four times the allocation: CWE-400 (uncontrolled resource consumption). This is the least dramatic row and the most likely one to be in your service.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | `unchecked_push_back` past `N` writes beyond the object | nothing at `-O1` and `-O2` (exit 0, `size=7`); aborts at `-O0` or with `_GLIBCXX_ASSERTIONS` | pick `try_push_back` or check the count before the loop; run ASan in CI |
| Rust | an empty Vec's `0x8` reaches a foreign `free` | `from_parts` is `unsafe`; the pointer is never null | handle `capacity == 0` before the pointer leaves Rust |
| F# | `array[1..]` per step makes cost quadratic in a client-chosen count | nothing; the code is memory safe and slow | cap the count, or slice with `ReadOnlySpan` |
| TypeScript | `NoInfer` is silent when `T` was already `string`, so a typo in a status compiles (type safety, not a CWE class) | nothing beyond the type system | write the status type down, so the typo has something to fail against |

Baselines: for the C++ row, a bounded container where "full" is a returned value (`try_push_back` here); the Rust row has none, because the hazard sits inside an `unsafe` block the author wrote, so no other language is a fair comparison. For the F# row the control is the .NET runtime: it is memory safe and the bug is still a denial of service.
