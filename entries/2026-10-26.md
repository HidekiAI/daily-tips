## Rust: derive(Ord) compares fields top to bottom and variants by discriminant value, so moving a field or renumbering a variant re-sorts everything

*Idioms and antipatterns*

**Did you know**

A derived `PartialOrd`/`Ord` on a struct is lexicographic in *declaration order*: swap two field lines and every `BTreeMap`, `sort()` and `binary_search` keyed by that type now orders differently, with no diagnostic. On an enum, variants are ordered by their **discriminant value**, not by where they are written: with `enum Severity { Low = 30, Medium = 20, High = 10 }`, `High < Low` is `true` and `max()` returns `Low`. Measured on rustc 1.99.1, edition 2024.

**Show me**

```rust
use std::collections::BTreeSet;

// Same two fields, declared in a different order. derive(Ord) follows the
// declaration, so these two types sort the same data differently.
#[derive(PartialEq, Eq, PartialOrd, Ord, Debug)]
struct JobByPriority { priority: u8, name: &'static str }

#[derive(PartialEq, Eq, PartialOrd, Ord, Debug)]
struct JobByName { name: &'static str, priority: u8 }

// Explicit discriminants, e.g. to match a wire or database code. The derived
// order now follows these numbers, not the line each variant sits on.
#[derive(PartialEq, Eq, PartialOrd, Ord, Debug, Clone, Copy)]
enum Severity { Low = 30, Medium = 20, High = 10 }

fn main() {
    let by_priority: BTreeSet<JobByPriority> = [
        JobByPriority { priority: 2, name: "alpha" },
        JobByPriority { priority: 1, name: "zulu" },
    ].into_iter().collect();
    let by_name: BTreeSet<JobByName> = [
        JobByName { name: "alpha", priority: 2 },
        JobByName { name: "zulu", priority: 1 },
    ].into_iter().collect();

    println!("{:?}", by_priority.first().map(|job| job.name)); // Some("zulu")
    println!("{:?}", by_name.first().map(|job| job.name));     // Some("alpha")
    println!("{}", Severity::High < Severity::Low);            // true
    println!("{:?}", [Severity::Low, Severity::High, Severity::Medium].iter().max()); // Some(Low)
}
```

**Why it matters**

A field reorder looks like a cosmetic diff ("group the strings together") and a discriminant change looks like a wire-format fix, yet both silently change every derived order in the service: a `Vec` that was kept sorted and persisted, then searched with `binary_search` after the upgrade, returns wrong answers rather than failing. C++20's `auto operator<=>(const T&) const = default` has exactly the same rule (declaration order, measured below), so the trap ports both ways; F# record comparison does too. TypeScript has no derived ordering at all, so its version of the bug is a comparator someone forgot to update.

**Chew on this**

Which of your types derive `Ord` only because a `BTreeMap` needed a key, and does anything in your code depend on the *order* that derive happened to produce? If a reviewer moved one field line in that struct, what test would turn red?

**Sources**

- https://doc.rust-lang.org/std/cmp/trait.PartialOrd.html#derivable
- https://doc.rust-lang.org/std/cmp/trait.Ord.html#derivable

**Gotchas**

- Memory layout does not drive the order. `struct Packet { flag: u8, sequence: u64, kind: u8 }` is laid out with `sequence` at offset 0 and `flag` at offset 8 (`offset_of!`, rustc 1.99.1), but the derived comparison still compares `flag` first.
- The discriminant decides before any field is read. With `enum Reading { Missing, Value(f64) }`, `Missing.partial_cmp(&Value(f64::NAN))` is `Some(Less)`, while `Value(NAN).partial_cmp(&Value(1.0))` is `None`. Whether a NaN makes a comparison fail depends on which variants meet.
- Appending a variant is not neutral when the code compares with `>=`. See the security angle below: a `Guest` added at the end of `Role` passes `role >= Role::Editor`.

## C++: GCC 16 ships C++26 contracts, and -std=c++26 alone compiles them but does not link

*New discoveries and currently popular patterns*

**Did you know**

GCC 16 is the first shipping compiler with C++26 contracts (P2900R14: `pre`, `post`, `contract_assert`). `-std=c++26` turns the syntax on and defines `__cpp_contracts` as `202502L`, but on g++ 16.2.0 the link then fails with `undefined reference to handle_contract_violation(std::contracts::contract_violation const&)`. The default violation handler lives in the static `libstdc++exp.a`, and the driver adds that library only when it also sees `-fcontracts`. As of cppreference's C++26 support table only GCC 16 implements P2900; Apple clang 21 has no `<contracts>` header at all, and MSVC has no support listed.

**Show me**

```cpp
// C++26, g++ 16.2.0 (gcc:16 image, Debian-based).
//   g++ -std=c++26 contracts.cpp             -> link error, handler missing
//   g++ -std=c++26 -fcontracts contracts.cpp -> links (adds -lstdc++exp)
#include <contracts>
#include <cstdio>

static int checks_run = 0;
static bool positive(int amount) { ++checks_run; return amount > 0; }

int withdraw(int balance, int amount)
    pre(positive(amount))              // a precondition the caller must meet
    post(remaining: remaining >= 0)    // names the return value "remaining"
{
    return balance - amount;
}

int main() {
    std::printf("%d\n", withdraw(100, 30)); // 70, checks_run == 1
    int after = withdraw(10, -5);           // violates pre
    // enforce (the default): prints the violation, then std::terminate, exit 134
    // observe: prints the violation and keeps going, after == 15
    // ignore:  positive() is never called, checks_run stays 0
    std::printf("%d %d\n", after, checks_run);
}
```

**Why it matters**

The default build command in a Makefile or CMake preset that only bumps `-std` breaks at link time, not compile time, and only in the translation units that contain a contract, so it surfaces late. More importantly, the evaluation semantic is a build flag (`-fcontract-evaluation-semantic=ignore|observe|enforce|quick_enforce`, default `enforce`), so the same source is a hard stop in one build and a log line in another. Rust's nearest relative is `debug_assert!`, which `-C debug-assertions` switches on or off, but it has only two outcomes, panic or skip, and no observe mode; `assert!` cannot be switched off at all. F# and TypeScript have no contract syntax at all.

**Chew on this**

If your release build used `observe` to keep a new contract from taking production down, how would you know when it is safe to switch to `enforce`? And which of your preconditions call something with a side effect that `ignore` would quietly skip?

**Sources**

- https://gcc.gnu.org/gcc-16/changes.html (P2900R14, PR119061)
- https://wg21.link/p2900r14
- https://en.cppreference.com/w/cpp/compiler_support/26
- https://patchwork.sourceware.org/project/gcc/patch/20221104144026.2311096-1-jason@redhat.com/ (why the handler sits in `libstdc++exp`)

**Verified**

Measured on g++ 16.2.0 in the official `gcc:16` Docker image only. The MSVC state comes from the cppreference table, not from a compiler.

**Gotchas**

- `quick_enforce` links without `-fcontracts`, because it never calls the handler. It also prints nothing: the only output is `terminate called without an active exception`, exit 134. A crash with no message can be a contract.
- `ignore` links too, and it does not evaluate the predicate: `checks_run` stays 0. A predicate with a side effect behaves differently in every semantic.
- Your own `void handle_contract_violation(const std::contracts::contract_violation&)` replaces the default and links without `-fcontracts`. Under `enforce` the program still terminates after it returns, and output written with `printf` to a piped stdout is lost by the abort. Write the handler's log to stderr. `violation.comment()` gives the predicate text, `"even % 2 == 0"`.
- `-std=c++23 -fcontracts` does not give you the C++26 feature: `contract_assert` is "not declared in this scope".

## F#: A struct union keeps every case's fields side by side unless they share a name and a type, so naming each case's float differently doubles its size

*Perf and memory model*

**Did you know**

A `[<Struct>]` discriminated union is laid out as one flat struct holding the fields of *every* case plus an `int` tag. There is no overlap between cases. Three cases that each carry a `float` under different names (`celsius`, `fahrenheit`, `kelvin`) measure 32 bytes. Since F# 9, cases may reuse a field name, and fields with the same name and type share one slot: the same three cases written `of degrees: float` measure 16 bytes. Measured with `Unsafe.SizeOf` on .NET SDK 10.0.402 (F# 10), FSharp.Core 10.1.0.0, .NET 10.0.13.

**Show me**

```fsharp
// dotnet fsi, SDK 10.0.402 on Debian 13.
open System.Runtime.CompilerServices

[<Struct>]
type SeparateFields =                 // the only legal shape before F# 9
    | Celsius of celsius: float
    | Fahrenheit of fahrenheit: float
    | Kelvin of kelvin: float

[<Struct>]
type SharedField =                    // F# 9+: same name, same type, one slot
    | CelsiusShared of degrees: float
    | FahrenheitShared of degrees: float
    | KelvinShared of degrees: float

[<Struct>]
type Unnamed =                        // unnamed fields are all called "Item",
    | CelsiusUnnamed of float         // so they share a slot too
    | FahrenheitUnnamed of float
    | KelvinUnnamed of float

printfn "%d" (Unsafe.SizeOf<SeparateFields>()) // 32: three doubles + tag, padded
printfn "%d" (Unsafe.SizeOf<SharedField>())    // 16: one double + tag
printfn "%d" (Unsafe.SizeOf<Unnamed>())        // 16

// Reflection shows the backing fields the compiler generated:
//   SeparateFields: _celsius, _fahrenheit, _kelvin, _tag
//   SharedField:    _degrees, _tag
```

**Why it matters**

The usual reason to make a union a struct is to put a million of them in an array without a million heap objects. Naming each case's field for readability, which F# style encourages, quietly doubles that array and its cache misses; F#'s own release notes show seven `int64` cases going from 60 bytes to 16. Rust's `enum` and C++'s `std::variant` overlap their cases automatically (the size is the largest case plus the tag), so neither has this trap. The CLR refuses to overlap a reference field with a value field, because the GC must know which slots hold pointers; F# is stricter still and shares only fields of an identical type, even two 8-byte value types such as `int64` and `float`. TypeScript has no value types, so every union member is a separate object anyway.

**Chew on this**

Which of your struct unions have cases that carry the same kind of value under different names, and is that name doing work a case name already does? When two cases genuinely need different types, is a struct union still cheaper than a reference one?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/whats-new/fsharp-9#field-sharing-for-struct-discriminated-unions
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/discriminated-unions#struct-discriminated-unions

**Gotchas**

- Same name, different type is a compile error, not a separate slot: `| Whole of amount: int64 | Fraction of amount: float` gives FS3585, "all fields with the same name must be of the same type". The same holds for unnamed fields, because they are all `Item`: `| WholeUnnamed of int64 | FractionUnnamed of float` is also FS3585.
- Before F# 9 shared names were rejected outright. Under `--langversion:8.0` the `SharedField` type fails with FS3204, "all union cases must have unique names". So this is not a layout change for existing code: nothing compiled before used a shared name.
- Units of measure share too, because they are erased: the release notes' example puts `int64<meter>` and `int64<second>` in one slot. The type system keeps them apart, but the memory does not.
- Sharing works per field in a tuple: `| Point of row: int * col: int | Span of row: int * width: int` is 16 bytes, so `row` is shared and `col` and `width` each get their own slot.

## TypeScript: readonly on a property is ignored by assignability, so a Readonly<T> passes straight into a function that mutates it

*Type system deep cuts*

**Did you know**

`readonly` on an object property only blocks a *direct* write through that type (TS2540). It is not part of assignability: `Readonly<RetryPolicy>` is assignable to `RetryPolicy`, so any function that takes the mutable type can change the object, and so can a plain `const aliased: RetryPolicy = shared`. Arrays are the exception: `readonly number[]` to `number[]` is TS4104. Measured on tsc 6.0.3 and 7.0.2 with `--strict`. The opt-in fix, `--enforceReadonly` (PR #58296), was closed unmerged on 2026-03-24, when 6.0 became the last release of the JavaScript codebase. The issue it answered, #13347, has been open since January 2017.

**Show me**

```typescript
// tsc 6.0.3 and 7.0.2, --strict: this whole file type-checks with exit 0.
interface RetryPolicy { maxAttempts: number; backoffMs: number }

const fnTighten = (policy: RetryPolicy): void => {
    policy.maxAttempts = 0; // mutates whatever the caller passed in
};

const shared: Readonly<RetryPolicy> = { maxAttempts: 5, backoffMs: 200 };
// shared.maxAttempts = 1;          // TS2540: the direct write IS caught
fnTighten(shared);                   // accepted: readonly is not part of assignability
const aliased: RetryPolicy = shared; // accepted too
aliased.backoffMs = 0;               // and now shared.backoffMs is 0

const limits: readonly number[] = [1, 2, 3];
// const mutableLimits: number[] = limits; // TS4104: arrays ARE checked

// Object.freeze returns Readonly<...>, and that is accepted as well. This line
// is where the program dies at runtime (TypeError in strict mode code).
const frozen = Object.freeze({ maxAttempts: 3, backoffMs: 50 });
fnTighten(frozen);
```

**Why it matters**

`Readonly<Config>` handed to a plugin, a request handler or a helper library reads as a promise that the callee cannot change shared state, and the compiler does not keep that promise as soon as the callee's parameter type is the plain one. With `Object.freeze` underneath, the mistake becomes a runtime `TypeError` ("Cannot assign to read only property 'maxAttempts'") that no type ever predicted. Rust is the opposite: `&T` to `&mut T` does not exist without `unsafe`. C++ is in between, since `const T&` to `T&` needs a `const_cast`, which at least shows up in a grep. F# records are immutable by construction, so there is no mutable type to convert to.

**Chew on this**

Where in your code does `Readonly<...>` cross a function boundary into code you do not own? If you deep-freeze that object in tests only, would you rather the tests throw or production stay quiet?

**Sources**

- https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties
- https://github.com/microsoft/TypeScript/issues/13347
- https://github.com/microsoft/TypeScript/pull/58296

**Gotchas**

- The runtime `TypeError` from writing to a frozen object needs strict mode code. ES modules and TypeScript's emitted CommonJS (which starts with `"use strict"`) throw; a sloppy-mode script ignores the write silently and keeps the old value.
- `Object.freeze` is shallow and so is `Readonly<T>`: a nested object under a `readonly` property is fully mutable, both in the type and at runtime.
- Neither tsc 6.0.3 nor 7.0.2 has any compiler option that changes this (`tsc --help --all` lists no readonly-related flag). A lint rule or a branded type is the only way to make the conversion visible.

# The functional angle: a derived ordering is a declaration-order decision, and only TypeScript makes you write it down

This draws on the Rust tip, with F# as the baseline row because structural comparison is the default there. The functional shape is "compare by the structure, derive the function": `compare` is not written, it falls out of the type. Each language derives it, and each one decides the order differently.

```fsharp
// F#: records compare field by field in declaration order, like Rust and C++.
type JobByPriority = { priority: int; name: string }
type JobByName = { name: string; priority: int }
type Severity = Low = 30 | Medium = 20 | High = 10 // .NET enum: by value
type Level = Low | Medium | High                    // union: by case order
// Set.minElement of the same two jobs: "zulu" vs "alpha"
// Severity.High < Severity.Low = true;  High < Low (Level) = false
```

```cpp
// C++20: a defaulted <=> is the derived ordering, lexicographic in declaration order.
struct JobByName { std::string name; int priority; auto operator<=>(const JobByName&) const = default; };
enum class Severity { Low = 30, Medium = 20, High = 10 }; // built-in < compares the values
```

```typescript
// TypeScript: nothing is derived. The comparator is the ordering, written by hand.
const byPriority = jobs.toSorted((left, right) => left.priority - right.priority || left.name.localeCompare(right.name));
[{ priority: 2 }, { priority: 1 }].toSorted(); // [2, 1]: every element is "[object Object]"
```

| Language | Derived form | `High < Low` with `Low = 30, High = 10` | What it costs |
| --- | --- | --- | --- |
| F# | structural `compare` on records and unions | `true` for an enum, `false` for a plain union (case order) | two rules in one language: the enum follows values, the union follows lines |
| Rust | `#[derive(PartialOrd, Ord)]` | `true` (discriminant value) | a field reorder or a discriminant change re-sorts everything, silently |
| C++20 | `operator<=> = default` | `true` (`enum class` compares underlying values) | same as Rust, and the default must be written per type |
| TypeScript | none | `true` (a numeric enum is a number) | the comparator is explicit, so it cannot drift, but it can be forgotten; `toSorted()` with none keeps the input order for objects |

Measured: rustc 1.99.1, g++ 16.2.0 `-std=c++20`, `dotnet fsi` on SDK 10.0.402, tsc 6.0.3 on Node 22.17.1. All three derived orderings agreed on "zulu" versus "alpha" for the reordered fields.

The derived version is the functional ideal (no code, no drift between type and function) and the explicit version is the safe one. Which of the two would you want for a type whose order is persisted on disk?

# The security angle: an authorization check written as an ordering is rewritten by the next enum edit

This runs Mode D on the Rust tip and Mode B on the C++ and TypeScript tips. The direction is the insecure one: each language lets the check compile, and each one changes what the check means without touching the line that contains it.

```rust
// Rust, rustc 1.99.1. Looks like a tidy role hierarchy.
#[derive(PartialEq, Eq, PartialOrd, Ord, Debug, Clone, Copy)]
enum Role { Viewer, Editor, Admin, Guest } // Guest appended in a later release

fn can_edit(role: Role) -> bool { role >= Role::Editor } // Guest -> true

// The version that survives the edit: adding Guest makes this match fail to
// compile until someone decides what Guest may do.
fn can_edit_explicit(role: Role) -> bool {
    match role {
        Role::Editor | Role::Admin => true,
        Role::Viewer | Role::Guest => false,
    }
}
```

Measured: `can_edit(Role::Guest)` is `true`, `can_edit_explicit(Role::Guest)` is `false`. Appending is the natural place to add a variant, and with a derived order it is the most privileged position.

```cpp
// C++26, g++ 16.2.0. A precondition used as the only guard on a withdrawal.
int withdraw(int balance, int amount) pre(amount > 0) { return balance - amount; }
// With -fcontract-evaluation-semantic=observe, withdraw(10, -5) returns 15:
// the violation is printed and the negative amount goes through.
```

```typescript
// TypeScript, tsc 6.0.3. Readonly is a hint to the caller, not a guarantee.
const fnApplyPlugin = (plugin: (config: AppConfig) => void, config: Readonly<AppConfig>) =>
    plugin(config); // accepted: the plugin's AppConfig parameter may mutate it
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `role >= Role::Editor` admits a newly appended variant (CWE-863, incorrect authorization) | derives the order from declaration and discriminants, with no warning on a new variant | write permission checks as an exhaustive `match`, so a new variant is a compile error |
| C++26 | a `pre` used as input validation is skipped (`ignore`) or only logged (`observe`) by a build flag (CWE-20) | lets the build, not the source, pick the semantic | keep the real check as code, and treat the contract as a second line that may be off |
| TypeScript | a `Readonly<T>` config is mutated by code typed against `T` (CWE-471, modification of assumed-immutable data) | checks direct writes only, never the conversion | freeze at runtime, or pass a copy, at every boundary into code you do not own |
| F# | the same ordered-`Role` check compiles, since a plain union compares by case order | gives exhaustive `match` with warning FS0025 on a missing case | the same as Rust; turn FS0025 into an error (`--warnaserror:25`) |

The Rust row is the baseline here because it is the one where the fix is mechanical: the compiler already refuses an incomplete `match`, it just cannot refuse a `>=`. Which of your `if role >= ...` checks would still be correct if a variant were added tomorrow, and who would notice if it were not?
