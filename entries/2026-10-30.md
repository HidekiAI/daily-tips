# Daily Tips: 2026-10-30

## Rust: Since 1.98 a derived PartialOrd beside a derived Ord calls your fields' cmp, so a field whose two orders disagree flipped 9 < 10 to false

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.98.0 (2026-08-20) added a fast path: when a non-generic type derives both `PartialOrd` and `Ord`, the derived `partial_cmp` is now generated as `Some(self.cmp(other))` instead of walking each field's `partial_cmp` ([rust-lang/rust#155598](https://github.com/rust-lang/rust/pull/155598), merged 2026-05-24, listed under the 1.98 compatibility notes). For any field whose `PartialOrd` and `Ord` agree, nothing changes. For a field whose two orders disagree, every `<`, `>`, `sort()` and `max()` on the outer type silently switched from the field's `partial_cmp` to its `cmp` on upgrade. Generic types are excluded, so `Tagged<Version>` kept the old answer while `Release` flipped.

**Show me**

```rust
// Rust 1.98+; measured on rustc 1.97.1 and 1.99.1 (Debian trixie containers)
use std::cmp::Ordering;

#[derive(PartialEq, Eq)]
struct Version {
    raw: String,
}

impl Version {
    fn numeric(&self) -> u32 {
        self.raw.parse().unwrap_or(0)
    }
}

// `<` is numeric: "9" < "10".
impl PartialOrd for Version {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
        Some(self.numeric().cmp(&other.numeric()))
    }
}

// cmp is lexical: "10" < "9". The two disagree, which the PartialOrd docs call a logic error.
impl Ord for Version {
    fn cmp(&self, other: &Self) -> Ordering {
        self.raw.cmp(&other.raw)
    }
}

// Non-generic, both derived: since 1.98 partial_cmp is generated as Some(self.cmp(other)).
#[derive(PartialEq, Eq, PartialOrd, Ord)]
struct Release {
    version: Version,
}

// Generic: no fast path (the bounds on T would be wrong), so partial_cmp still walks the fields.
#[derive(PartialEq, Eq, PartialOrd, Ord)]
struct Tagged<T> {
    version: T,
}

fn version(raw: &str) -> Version {
    Version { raw: raw.to_string() }
}

fn main() {
    let older = Release { version: version("9") };
    let newer = Release { version: version("10") };
    println!("Release 9 < 10: {}", older < newer); // 1.97.1: true   1.99.1: false

    let tagged_older = Tagged { version: version("9") };
    let tagged_newer = Tagged { version: version("10") };
    println!("Tagged  9 < 10: {}", tagged_older < tagged_newer); // true on both

    let mut releases = vec![newer, older];
    releases.sort(); // sort() compares with `<`, so it moved with the derive
    let order: Vec<&str> = releases.iter().map(|release| release.version.raw.as_str()).collect();
    println!("sorted: {order:?}"); // 1.97.1: ["9", "10"]   1.99.1: ["10", "9"]
}
```

**Why it matters**

A hand-written field type with "smart" `<` and a plain `cmp` (versions, case-insensitive names, money with a currency tie-break) is exactly the type that ends up inside a derived struct, and the upgrade to 1.98 re-sorted it with no warning and no clippy lint at the derive site. C++ has nothing to split, since `operator<=>` is one function and a defaulted one on the outer type calls the member's `<=>`; F# has one `compare` per type, so the same two-orders bug cannot be written there without overriding `IComparable` and `CompareTo` separately.

**Chew on this**

Which of your types implement `PartialOrd` by hand next to a derived or hand-written `Ord`, and would anything in your test suite have noticed the day the outer struct's `<` changed meaning? If the two orders were deliberate, what should the type have been instead?

- https://github.com/rust-lang/rust/blob/main/RELEASES.md (1.98.0, Compatibility Notes)

**Verified**

rustc 1.97.1 and 1.99.1 in `rust:*-slim-trixie`; the two-attribute-lines case below is measured only, and is the derive-order gap the PR itself points at ([rust-lang/rust#124794](https://github.com/rust-lang/rust/issues/124794)).

**Gotchas**

- `slice::sort` and `sort_unstable` compare with `<` (`PartialOrd::lt`), not `cmp`: on `Version` itself they gave `["9", "10"]` while `sort_by(Ord::cmp)` gave `["10", "9"]` (1.99.1).
- A `BTreeSet<Version>` built with `collect()` came out `["9", "10"]` and one built with `insert` came out `["10", "9"]`: `collect` sorts with `<` first, `insert` and `contains` use `cmp`.
- `Iterator::max` returned `"9"` (uses `cmp`) while `version("10").max(version("9"))` returned `"10"` (the `Ord::max` default compares with `<`), on the same two values.
- The fast path depends on attribute order: `#[derive(Ord)]` on a line above `#[derive(PartialOrd)]` got it (`false`), `#[derive(PartialOrd)]` above `#[derive(Ord)]` did not (`true`), on 1.99.1.

## C++: A string_view into a moved std::string survives if the string was long and breaks if it was short, because SSO bytes cannot be stolen

*Perf and memory model*

**Did you know**

Moving a `std::vector` keeps every pointer into it valid, now pointing into the new owner. Moving a `std::string` does not, because a short string's characters live inside the string object itself (the small string optimization), so the move constructor copies them and empties the source. libstdc++ (GCC 16.2) keeps up to 15 characters inline in a 32-byte `std::string`; libc++ (clang 19.1.7) keeps up to 22 in a 24-byte one. The standard allows this by letting any library function that takes a non-const `basic_string` reference invalidate views into it, so even the long case that happens to work is not promised. `std::string_view` is C++17; both libraries behave as measured on Debian trixie.

**Show me**

```cpp
// C++17 (string_view); measured with -std=c++23 on GCC 16.2 (libstdc++) and clang 19.1.7 (libc++), Debian trixie
#include <cstdio>
#include <string>
#include <string_view>
#include <utility>
#include <vector>

int main() {
    // Inline (SSO) buffer: libstdc++ 15 chars in a 32-byte string, libc++ 22 chars in a 24-byte one.
    std::printf("sizeof=%zu inline capacity=%zu\n", sizeof(std::string), std::string{}.capacity());

    std::string short_owner = "hello";                // fits inline: the bytes live inside short_owner
    std::string_view short_view = short_owner;
    std::string short_moved = std::move(short_owner); // copies the 5 bytes, then empties the source
    std::printf("short: view follows? %d, still hello? %d\n",
                short_view.data() == short_moved.data(), short_view == "hello"); // 0, 0 on both

    std::string long_owner = "hello, this sentence is longer than any small string buffer";
    std::string_view long_view = long_owner;          // points at a heap block
    std::string long_moved = std::move(long_owner);   // steals the heap pointer
    std::printf("long:  view follows? %d\n", long_view.data() == long_moved.data()); // 1 on both, by luck

    std::vector<int> numbers{1, 2, 3};
    const int* first = numbers.data();
    std::vector<int> numbers_moved = std::move(numbers); // vector has no inline buffer
    std::printf("vector: pointer follows? %d\n", first == numbers_moved.data()); // 1, and guaranteed
}
```

**Why it matters**

The pattern that bites a server is a `string_view` index (a parsed header map, a tokenizer's output) built over strings that are later moved into a container or a request object: every value over the SSO limit keeps working, every short one silently reads an emptied buffer, and the 16 to 22 character keys behave differently on GCC and clang builds. Rust rejects the same three lines outright (`E0505: cannot move out of owner because it is borrowed`, measured on rustc 1.99.1), and its `String` has no inline buffer to begin with; F# and TypeScript strings are immutable values the runtime keeps alive, so a view can never outlive its bytes there.

**Chew on this**

Where in your code does a `string_view` (or a `std::span` over a `std::string`) get built before its owner is moved into its final home, and what length are the strings your tests feed it? Would you rather fix that by changing the order, or by changing the owner?

**Sources**

- https://en.cppreference.com/w/cpp/string/basic_string.html (Iterator invalidation)
- https://en.cppreference.com/w/cpp/named_req/Container.html
- https://en.cppreference.com/w/cpp/string/basic_string_view.html

**Gotchas**

- AddressSanitizer plus UBSan (GCC 16.2, `-fsanitize=address,undefined`) reported nothing and exited 0: the emptied bytes still belong to a live object, so there is no freed memory to catch.
- The moved-from short string is not garbage but empty: the first byte the view reads is `0` on both libraries, so the bug shows up as a missing value, not a crash.
- The threshold is per library: a 20-character key is on the heap with libstdc++ (view follows the move) and inline with libc++ (view breaks), so the same test can pass on a GCC build and fail on a clang one.
- `-Wall -Wextra` on GCC 16.2 and `-Wall -Wextra -Wdangling` on clang 19.1.7 printed no warning for any of the three moves.

## F#: .NET's PriorityQueue served ten equal-priority jobs as 0, 9, 8, ... 1, so a FIFO at one priority turns LIFO after the first

*Stdlib and ecosystem gems*

**Did you know**

FSharp.Core has no priority queue, so F# reaches for the BCL's `System.Collections.Generic.PriorityQueue<TElement, TPriority>` (.NET 6+), an array-backed quaternary min-heap whose docs say it "does not guarantee first-in-first-out semantics for elements of equal priority". In practice it is worse than "unordered": ten jobs enqueued at priority 0 came out as job-0, then job-9 down to job-1, because every dequeue moves the last array slot to the root and an equal child never displaces it. Measured on F# 11 with FSharp.Core 11.0.0 and .NET 11.0.0-rc.3.

**Show me**

```fsharp
// F# 11, FSharp.Core 11.0.0, .NET 11.0.0-rc.3 (dotnet/nightly/sdk:11.0 container, Ubuntu 26.04)
open System.Collections.Generic

let same_priority = PriorityQueue<string, int>()
for job in 0 .. 9 do
    same_priority.Enqueue(sprintf "job-%d" job, 0)

// ["job-0"; "job-9"; "job-8"; "job-7"; "job-6"; "job-5"; "job-4"; "job-3"; "job-2"; "job-1"]
printfn "%A" [ while same_priority.Count > 0 do yield same_priority.Dequeue() ]

// The fix: make arrival part of the priority. Struct tuples compare left to right.
let with_sequence = PriorityQueue<string, struct (int * int64)>()
for job in 0 .. 9 do
    with_sequence.Enqueue(sprintf "job-%d" job, struct (0, int64 job))

// ["job-0"; "job-1"; "job-2"; ... "job-9"]
printfn "%A" [ while with_sequence.Count > 0 do yield with_sequence.Dequeue() ]
```

**Why it matters**

A work queue with a handful of priority levels is mostly ties, so "jobs at the same priority run in arrival order" is the assumption that holds in a demo and inverts under load: the oldest request at a level waits behind every newer one. Rust's `BinaryHeap` and C++'s `std::priority_queue` are binary max-heaps with the same property but a different scramble (`0 2 6 9 8 5 7 4 1 3` on both, see the functional angle below); TypeScript has no heap in its standard library at all.

**Chew on this**

Which of your queues assume that equal priorities drain in arrival order, and where would the sequence number come from if two producers enqueue concurrently? Is a monotonic counter enough, or does the order you actually need live outside the process?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.priorityqueue-2
- https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.priorityqueue-2.unordereditems

**Verified**

Run with `dotnet fsi` in the `mcr.microsoft.com/dotnet/nightly/sdk:11.0` image, which is Ubuntu 26.04, not Debian, and a release candidate rather than a GA runtime.

**Gotchas**

- It is a min-heap: `"urgent"` at priority 1 dequeued before `"background"` at 9. A max-first queue needs `PriorityQueue<string, int>(Comparer<int>.Create(fun left right -> compare right left))`, which then dequeued `"background"` first.
- `UnorderedItems` is the raw heap array: priorities 5, 1, 4, 2, 3 enqueued in that order enumerate as `["p1"; "p5"; "p4"; "p2"; "p3"]`, neither insertion nor priority order.
- Three ties already came out `["job-0"; "job-2"; "job-1"]`, so a unit test with two jobs at one priority is the only size that looks FIFO.

**Related**

- [2026-10-05](2026-10-05.md) - F#, "Array.sortBy is not stable and List.sortBy is". The same tie-order assumption, met in a sort instead of a heap.

## TypeScript: A const type parameter makes object properties readonly but copies your constraint's mutability onto arrays, and before 5.3 one string[] erased every literal

*Type system deep cuts*

**Did you know**

`<const T>` (TypeScript 5.0) infers as if the call-site literal were written `as const`, but not uniformly: object properties always come back `readonly`, while array literals come back as a `readonly` tuple only if the constraint allows it and as a mutable tuple if the constraint says `string[]`. That mutable-tuple behaviour is TypeScript 5.3's ([microsoft/TypeScript#55229](https://github.com/microsoft/TypeScript/pull/55229), merged 2023-08-26). On 5.2.2 a mutable `string[]` anywhere in the constraint threw away every literal, including the unrelated `path: "/health"` next to it. And `const` only reaches literals written at the call: the same array passed through a variable is plain `string[]`.

**Show me**

```ts
// TypeScript 5.3+; measured on tsc 7.0.2 (Node 26.12.1, Debian trixie), contrasted with 5.2.2
declare function routes_mutable<const T extends string[]>(paths: T): T;
declare function routes_readonly<const T extends readonly string[]>(paths: T): T;
declare function route_object<const T extends { path: string; methods: string[] }>(route: T): T;

const mutable_result = routes_mutable(["/health", "/metrics"]);   // ["/health", "/metrics"]
const readonly_result = routes_readonly(["/health", "/metrics"]); // readonly ["/health", "/metrics"]

const variable_input = ["/health", "/metrics"];
const through_variable = routes_readonly(variable_input);         // string[]: const sees only call-site literals

const object_result = route_object({ path: "/health", methods: ["GET"] });
// tsc 7.0.2: { readonly path: "/health"; readonly methods: ["GET"] }
// tsc 5.2.2: { path: string; methods: string[] }   -- one mutable array erased everything

object_result.path = "/ready"; // TS2540: Cannot assign to 'path' because it is a read-only property.
```

**Why it matters**

`const` type parameters are how route tables, event-name registries and config builders keep their literal keys without asking every caller for `as const`, so whether a property ends up `readonly`, literal, or widened decides which typos the builder still catches. Rust and C++ have no literal types to infer, so the closest relative is C++'s `auto list = {1, 2}` deducing `std::initializer_list<int>`: deduction picking a shape the author did not write. F# has no literal types either; the comparison stops there.

**Chew on this**

Which of your `const T` helpers are called with a variable at least as often as with a literal, and what does their result type become for those callers? If the constraint's `readonly` decides the result's, which one did you actually mean to promise?

**Sources**

- https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#const-type-parameters
- https://github.com/microsoft/TypeScript/pull/55229

**Verified**

tsc 7.0.2, 5.3.3 and 5.2.2 via `npx -p typescript@<version>` in `node:26`; the 5.3 change is not described in the 5.3 release notes, so it rests on the PR and the measurement.

**Gotchas**

- The `readonly` on object properties is only as strong as TypeScript's `readonly`: it blocked `object_result.path = "/ready"` with TS2540, but assignability ignores it, so the result still passes into a function that mutates it.
- The inner tuple is mutable and fixed-length at once: `object_result.methods.push("GET")` compiles and `const method_count: 1 = object_result.methods.length` still compiles after it (tsc 7.0.2 exit 0), while the array now holds 2 elements.
- `push("POST")` on the same tuple is TS2345 (`"POST"` is not assignable to `"GET"`), so a mutable constraint gives you a tuple you can grow only with values it already has.

**Related**

- [2026-10-26](2026-10-26.md) - TypeScript, "readonly on a property is ignored by assignability". The `readonly` that `const T` hands you is that same property modifier.

# The functional angle: no standard heap is FIFO for ties, so arrival order has to become part of the key, and that key is state

Draws on the F# tip, with Rust and C++ rows measured the same way and TypeScript as the sort-based contrast.

A heap is the functional programmer's favourite "pure" structure until ties appear: the dequeue order of equal keys is an artifact of the sift algorithm, and every standard library here documents it as unspecified. The only portable fix is decorate-with-sequence, the same move as the Schwartzian transform: widen the key to `(priority, arrival)`.

```rust
// Rust 1.99.1: BinaryHeap is a max-heap, so Reverse turns it into a min-heap over (priority, arrival)
use std::cmp::Reverse;
use std::collections::BinaryHeap;
let mut with_sequence = BinaryHeap::new();
for job in 0..10u64 {
    with_sequence.push(Reverse((0u8, job)));
}
// pops 0, 1, 2, ... 9
```

```cpp
// C++ (libstdc++, GCC 16.2): greater<> turns the default max-heap into a min-heap over (priority, arrival)
std::priority_queue<std::pair<int, int>, std::vector<std::pair<int, int>>, std::greater<>> with_sequence;
for (int id = 0; id < 10; ++id) with_sequence.push({0, id});
// tops 0, 1, 2, ... 9
```

The asymmetry worth leading with: the arrival number is a counter, so the "functional" fix needs mutable state somewhere. A single producer can fold an index in (`for job in 0 .. 9` above); two producers need a shared atomic or a timestamp, which is exactly the state a pure queue was supposed to avoid. F# is the baseline here only because its row costs the same as everyone else's, which says the cost belongs to the heap, not to the language.

| Language | Functional form | 10 ties, no sequence | What it costs |
| --- | --- | --- | --- |
| F# (.NET 11 rc.3) | `PriorityQueue<_, struct (int * int64)>` | 0 9 8 7 6 5 4 3 2 1 | 8 more bytes per entry and a counter you thread yourself |
| Rust 1.99.1 | `BinaryHeap<Reverse<(u8, u64)>>` | 0 2 6 9 8 5 7 4 1 3 | same counter, plus `Reverse` because std's heap is max-first |
| C++ (GCC 16.2) | `priority_queue<pair<int, int>, ..., greater<>>` | 0 2 6 9 8 5 7 4 1 3 | same counter, plus `greater<>` because the default is max-first |
| TypeScript (Node 26.12.1) | `toSorted((left, right) => left.priority - right.priority)` | 0 1 2 ... 9 | no heap in std; stable by spec since ES2019, so FIFO is free but every re-sort is O(n log n) |

Rust's `BinaryHeap` and C++'s `std::priority_queue` produced the identical scramble, which is what two textbook binary heaps with the same sift rule should do; .NET's quaternary heap produced a different one. If the order you need is "arrival", is a priority queue still the structure you want, or is it a list of FIFO queues indexed by priority?

# The security angle: a BTreeSet denylist built with collect() blocked 1, 2 and 20, and let 10 and 100 through

Draws on the Rust tip (Mode B, the insecure direction): the Gotchas showed `collect()` sorting with `<` and `contains` searching with `cmp`. Ask whether that is secure, not just surprising. It is not: a set whose layout and lookups disagree answers membership questions wrong, which is CWE-697 (Incorrect Comparison).

```rust
// Rust 1.99.1, Version as in the Rust tip: `<` numeric, cmp lexical
use std::collections::BTreeSet;
let blocked: BTreeSet<Version> = ["1", "2", "10", "20", "100"].into_iter().map(version).collect();
blocked.contains(&version("1"));   // true
blocked.contains(&version("10"));  // false: looks like a denylist, lets a blocked version through
blocked.contains(&version("100")); // false
// The same five added with insert(): contains(&version("100")) is true.
```

Nothing here is `unsafe`, nothing panics, and the standard library documents the outcome as unspecified rather than undefined, which is why no tool flags it. The C++ tip has the same shape in a different coat: a `string_view` read after its short owner was moved returns an empty value with ASan silent, an expired-pointer read (CWE-825) that looks like "the header was absent".

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | two traits, two orders: `collect` lays out by `<`, `contains` searches by `cmp` | calls the mismatch a logic error; memory stays safe | keep `partial_cmp` as `Some(self.cmp(other))`, or never derive the two separately |
| C++ | `std::set` uses one `Compare` for layout and lookup, so it cannot split; a non-strict-weak `Compare` is undefined behaviour instead | nothing at compile time | a comparator that is a strict weak order (the `<=` comparator bug in [2026-10-20](2026-10-20.md)) |
| F# | `Set<'T>` and `SortedSet<T>` each use one comparison | one order per collection, so no split | a `CompareTo` that agrees with `=` if you override either |
| TypeScript | no ordered set in std; `Set` uses SameValueZero | nothing to split | the same check on any third-party sorted container |

Rust is the control for this failure class precisely because it is the only one of the four that gives a type two orders. Which of your allowlists and denylists are ordered collections, and do you know which trait built them?
