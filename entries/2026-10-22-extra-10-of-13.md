**The thesis: adding a calendar span is a partial function, so subtracting one cannot be its inverse.** Part 1 showed that Jan 31 + 1 month has to clamp to Feb 28. That means the way back, from Feb 28 to Jan 31, is not "1 month". Every library has to pick an answer for "how many months between", and for "how old is someone born on Feb 29", and they pick differently.

## Rust: `jiff` adds a month to Jan 31 and gets Feb 28, and the difference back is P28D, not P1M

*Type system deep cuts*

**Did you know**

In Rust `jiff` (0.2.38), `date(2026, 1, 31) + 1.month()` is 2026-02-28, clamped to the month's last day. Asking how far apart they are, even with months allowed (`until((Unit::Month, feb28))`), gives **P28D**, not P1M: a whole month did not pass, because Feb 28 is not Jan 31's day of the month. Subtracting the month again gives **2026-01-28**, three days short of where you started. And `until` measures in days unless told otherwise: Jan 1 to Mar 1 is P59D by default and P2M with `Unit::Month`.

**Show me**

```rust
// Rust: jiff 0.2.38, rustc 1.95.0
use jiff::{civil::date, ToSpan, Unit};

fn main() {
    let jan31 = date(2026, 1, 31);
    let feb28 = jan31.checked_add(1.month()).unwrap();
    println!("{feb28}");                                          // 2026-02-28: clamped to the month's last day

    // The difference back is not the span you added:
    println!("{}", jan31.until((Unit::Month, feb28)).unwrap());   // P28D: not P1M, even when months are allowed
    // And subtracting the same span does not return you to the start:
    println!("{}", feb28.checked_sub(1.month()).unwrap());        // 2026-01-28: three days short of Jan 31

    // until() defaults to days as the largest unit:
    println!("{}", date(2026, 1, 1).until(date(2026, 3, 1)).unwrap());              // P59D
    println!("{}", date(2026, 1, 1).until((Unit::Month, date(2026, 3, 1))).unwrap()); // P2M
    println!("{}", jan31.until((Unit::Month, date(2026, 3, 1))).unwrap());            // P1M1D
}
```

**Why it matters**

Subscription and billing code is full of "the next date is the last date plus one period" and "the period that has passed is the difference". With month-end start dates those two lines disagree, and the error compounds: Jan 31, +1 month = Feb 28, +1 month = Mar 28, and the customer has drifted three days off their billing day by March. Store the anchor date and add `n` months to it, rather than adding one month to the previous result. `jiff` and Temporal give identical answers here (TypeScript tip), because `jiff` follows Temporal's arithmetic. C++ refuses to clamp at all.

**Chew on this**

Which of your recurring dates are computed from the previous occurrence instead of from the original anchor? When a customer on the 31st asks "how long have I been subscribed", which unit does your code answer in?

**Sources**

- https://docs.rs/jiff/0.2.38/jiff/civil/struct.Date.html#method.until
- https://docs.rs/jiff/0.2.38/jiff/struct.Span.html

**Gotchas**

- `jan31.until(feb28)` with no unit and with `Unit::Month` both print `P28D` (measured): allowing months does not force them.
- Jan 31 to Mar 1 with `Unit::Month` is `P1M1D` (measured): one month gets you to Feb 28 (clamped), and one day to Mar 1. So `P1M1D` here is 29 days, not 32.
- Rust and its crates evolve: this is `jiff` 0.2.38. Rust `chrono` has `checked_add_months` with the same clamping (`Some(2026-02-28)`, measured), and no span type with months, so its "difference" is a `TimeDelta` of days.

## C++: `year_month` subtraction counts two months between Jan 31 and Mar 1, which are 29 days apart

*Type system deep cuts*

**Did you know**

C++20 calendar types answer "how many months" by counting month boundaries. `(2026y/March) - (2026y/January)` is `months{2}`, whatever the days were, so Jan 31 and Mar 1 are "2 months" apart while `sys_days` says 29 days. The other direction is just as literal: `2004y/February/29 + years{22}` is 2026-02-29, which is not `ok()`. Converting it through `sys_days` silently rolls it to 2026-03-01. `floor<years>` on the elapsed days uses the *average* year (`years{1}` is 365.2425 days), which gives 21 on 2026-02-28. Measured on Apple clang 21 (libc++) and GCC 16.2 (libstdc++).

**Show me**

```cpp
// C++20: Apple clang 21 (libc++ 22) and GCC 16.2 (libstdc++)
#include <chrono>
#include <cstdio>
using namespace std::chrono;

int main() {
    // Calendar months between two year_month values count month boundaries, not elapsed time:
    const months between = (2026y/March) - (2026y/January);
    const days elapsed = sys_days{2026y/March/1} - sys_days{2026y/January/31};
    std::printf("%d months, %d days\n", (int)between.count(), (int)elapsed.count()); // 2 months, 29 days

    // An anniversary of Feb 29 does not exist in most years, and the type tells you:
    const year_month_day birth = 2004y/February/29;
    const year_month_day anniversary = birth + years{22};
    std::printf("2026-02-29 ok(): %d\n", (int)anniversary.ok());                     // 0
    // What sys_days makes of it, and what the average-year duration says:
    const year_month_day rolled{sys_days{anniversary}};
    std::printf("as sys_days: %d-%02u-%02u\n", (int)rolled.year(), (unsigned)rolled.month(), (unsigned)rolled.day()); // 2026-03-01
    const auto lived = sys_days{2026y/February/28} - sys_days{birth};
    std::printf("floor<years>: %d\n", (int)floor<years>(lived).count());           // 21: years{1} is 365.2425 days
}
```

**Why it matters**

C++ is the only one of the four with no "until" at all, so each codebase writes its own, and the `year_month` subtraction is the tempting one-liner for "months of tenure" or "months overdue". It is right for "how many statements were issued" and wrong for "how much time has passed". And `floor<years>(lived)` looks like an age, but it agrees with a calendar age only by luck. Around a birthday, the 0.2425-day average and the real calendar diverge by up to a day. Rust `jiff` and Temporal compute calendar spans for you. .NET leaves you to hand-roll ages too (F# tip).

**Chew on this**

Which of your "months between" calculations subtract `year_month` values, and would a customer on the 31st agree with them? Where you compute an age, which of the three answers here does your formula produce?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/year_month/operator_arith
- https://en.cppreference.com/w/cpp/chrono/year_month_day/ok
- https://en.cppreference.com/w/cpp/chrono/duration (the `years` and `months` typedefs)

**Verified**

Apple clang 21 on this host and `docker run gcc:16`; identical output. MSVC not tested.

**Gotchas**

- `2026y/January/31 + months{1}` is 2026-02-31, `ok() == false`, and converting it through `sys_days` gives 2026-03-03 (both measured).
- A hand-rolled age, "subtract years, minus one if the month and day have not come yet", gives 21 on 2026-02-28 and 22 on 2026-03-01 for a Feb 29 birthday (measured). It is the Mar 1 convention, chosen by accident.
- `months{1}` as a duration is 2629746 s, 30.436875 days (measured), which is a third meaning of "a month" next to the calendar one and the `year_month` one.

## F#: the two usual age formulas disagree on Feb 28, so an "18 or older" check passes with one and fails with the other

*Idioms and antipatterns*

**Did you know**

.NET has no "age" or "years between" API, so two formulas are everywhere. One builds the birthday with `AddYears` and compares it to today. The other compares (month, day) pairs. For someone born on 2008-02-29, on 2026-02-28 the first says **18** and the second says **17**, because `AddYears` clamps Feb 29 to Feb 28 and so puts the birthday on Feb 28 in common years. On Mar 1 both say 18. Measured on FSharp.Core 8.0 / .NET 8.0.8 and FSharp.Core 10.1 / .NET 10.0.13.

**Show me**

```fsharp
// F#: FSharp.Core 8.0 / .NET 8.0.8 (DateOnly is .NET 6+)
open System

let birth = DateOnly(2008, 2, 29)

// The two age formulas found in most codebases:
let fn_age_by_addyears (today: DateOnly) =
    let years = today.Year - birth.Year
    if birth.AddYears years > today then years - 1 else years   // AddYears clamps Feb 29 to Feb 28
let fn_age_by_month_day (today: DateOnly) =
    let years = today.Year - birth.Year
    if (today.Month, today.Day) < (birth.Month, birth.Day) then years - 1 else years

for today in [ DateOnly(2026, 2, 28); DateOnly(2026, 3, 1) ] do
    printfn "%s: %d vs %d" (today.ToString "yyyy-MM-dd") (fn_age_by_addyears today) (fn_age_by_month_day today)
// 2026-02-28: 18 vs 17   <- an "18 or older" check passes with one and fails with the other
// 2026-03-01: 18 vs 18

printfn "%s" ((birth.AddYears 18).ToString "yyyy-MM-dd")  // 2026-02-28: where AddYears puts the birthday
```

**Why it matters**

Both formulas are correct code, and they encode different answers to a legal question: does a Feb 29 birthday fall on Feb 28 or on Mar 1 in a common year? Jurisdictions answer that differently, and no library knows which one applies to your users. When two services each pick a formula, the same person is 17 in one and 18 in the other for a day every three years out of four. Rust `jiff` and Temporal both say 21 on Feb 28 for a 2004 birth, the Mar 1 convention. C++ gives whatever the hand-rolled formula does.

**Chew on this**

Which jurisdiction's rule does your age check follow, and is that written anywhere next to the formula? If two of your services compute ages, do they use the same one?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.dateonly.addyears
- https://learn.microsoft.com/en-us/dotnet/api/system.dateonly

**Gotchas**

- `DateOnly(2026, 1, 31).AddMonths(1).AddMonths(-1)` is 2026-01-28 (measured): the same lost three days as Rust's round trip.
- `DateTime(2026, 3, 1) - DateTime(2026, 1, 31)` is a `TimeSpan` of 29 days, and `TimeSpan` has no months or years at all (measured). "Months between" is always hand-written in .NET.
- `floor((today.DayNumber - birth.DayNumber) / 365.25)` gives 21 on 2026-02-28 for a 2004 birth (measured), the Mar 1 answer, but it is an approximation that can be off by a day near any birthday.

## TypeScript: Temporal's `add` puts a Feb 29 birthday on Feb 28, and its `until` says the person is not that age yet

*Stdlib and ecosystem gems*

**Did you know**

`Temporal.PlainDate.from("2004-02-29").add({ years: 22 })` is 2026-02-28. Yet `birth.until("2026-02-28", { largestUnit: "year" }).years` is **21**, and it becomes 22 on 2026-03-01. So within one API, `add` says the 22nd birthday is Feb 28, and `until` says the 22nd year is complete on Mar 1. Also, `until` defaults to days: Jan 1 to Mar 1 is `P59D` unless you pass `largestUnit: "month"`, which gives `P2M`. And "one month" in days depends on where it starts: 31 from Jan 1, 28 from Feb 1. Measured on Node 26.12.1.

**Show me**

```ts
// TypeScript 6.0.3 (lib esnext, which carries Temporal), run on Node 26.12.1
const birth = Temporal.PlainDate.from("2004-02-29")

// add() and until() disagree about when a Feb 29 baby turns 22:
console.log(birth.add({ years: 22 }).toString())                                      // 2026-02-28
console.log(birth.until(Temporal.PlainDate.from("2026-02-28"), { largestUnit: "year" }).years) // 21
console.log(birth.until(Temporal.PlainDate.from("2026-03-01"), { largestUnit: "year" }).years) // 22

// until() measures in days unless told otherwise:
const new_year = Temporal.PlainDate.from("2026-01-01")
console.log(new_year.until(Temporal.PlainDate.from("2026-03-01")).toString())                         // P59D
console.log(new_year.until(Temporal.PlainDate.from("2026-03-01"), { largestUnit: "month" }).toString()) // P2M

// And "one month" is a different number of days depending on where it starts:
const one_month = Temporal.Duration.from("P1M")
console.log(one_month.total({ unit: "day", relativeTo: new_year }))                              // 31
console.log(one_month.total({ unit: "day", relativeTo: Temporal.PlainDate.from("2026-02-01") })) // 28
```

**Why it matters**

This is the F# tip's disagreement inside one well-designed API, which shows it is not a bug in either function. `add` has to land somewhere in a year without Feb 29, and it clamps. `until` counts a year as complete only when the date reaches or passes Feb 29's position, which in a common year is Mar 1. Code that sends a "happy birthday" with `add` and checks an age limit with `until` will greet someone a day before it lets them in. Rust `jiff` matches Temporal on all of these numbers. .NET's `AddYears` makes the `add` choice.

**Chew on this**

Do your birthday emails and your age checks use the same function? For the Feb 29 users in your database, which day does each of them happen on?

**Sources**

- https://tc39.es/proposal-temporal/docs/plaindate.html#until
- https://tc39.es/proposal-temporal/docs/plaindate.html#add
- https://tc39.es/proposal-temporal/docs/duration.html#total

**Verified**

`console` typed with a one-line `declare` instead of `@types/node`. Run in `docker run node:26`.

**Gotchas**

- `Temporal.PlainDate.from("2026-01-31").until("2026-02-28", { largestUnit: "month" })` is `P28D` (measured), the same as Rust: allowing months does not produce one.
- A `Date`-based "months between", `(year2 - year1) * 12 + (month2 - month1)`, says 2 for Jan 31 to Mar 1 (measured), the C++ `year_month` answer.
- `Math.floor(milliseconds / (365.25 * 86400000))` gave 21 on both 2026-02-27 and 2026-02-28 (measured): it happens to match here, and it drifts near birthdays.

# The functional angle: `add` is not invertible, so `until` is a separate function with its own answers

Draws on all four tips. If `add(date, span)` were a bijection, `until(a, b)` would be defined as the `span` with `add(a, span) == b`. It is not a bijection: Jan 28, 29, 30 and 31 all map to Feb 28 under `add(_, P1M)`. So there are four inputs for one output, and no inverse exists. Every library had to define `until` separately, and the definitions do not round-trip.

```text
// Measured, Rust jiff and TypeScript Temporal agree on every line:
// add(Jan 31, P1M)          = Feb 28
// until(Jan 31, Feb 28)     = P28D          (not P1M)
// sub(Feb 28, P1M)          = Jan 28        (not Jan 31)
// add(Feb 29 2004, P22Y)    = Feb 28 2026
// until(Feb 29 2004, Feb 28 2026).years = 21 (not 22)
```

| Language | `add` of a calendar span | `until` / difference | Round trip `add` then `until` | What it costs |
| --- | --- | --- | --- | --- |
| Rust (`jiff`) | clamps | calendar span, days by default | not identity | name the largest unit every time |
| C++ | refuses (`ok()` false) | days only, or `year_month` boundaries | nothing to round-trip | you write both directions, and pick the clamping |
| F# / .NET | clamps (`AddMonths`, `AddYears`) | `TimeSpan` days only | not identity | age and "months between" are hand-rolled, two ways |
| TypeScript (`Temporal`) | clamps | calendar span, days by default | not identity | same as Rust: name the largest unit |

The asymmetry: C++'s refusal to clamp is the only design where `add` stays honest, at the price of making every caller choose what Feb 31 means. The clamping libraries are convenient one way and surprising the other.

# The security angle: an age gate is a date difference, and two correct formulas disagree for one day

Draws on the F# tip (Mode B: is either formula wrong?) and the TypeScript tip. Neither formula is buggy. The vulnerability is two services choosing differently, or a check using the server's date instead of the user's.

**Inconsistent age verification (CWE-682, incorrect calculation, when the policy is "the law's 18" and the code picked a different day).** The sample is ordinary code from the F# tip: `fn_age_by_addyears` says 18 on 2026-02-28 for a 2008-02-29 birth, and `fn_age_by_month_day` says 17 (measured). If sign-up uses one and checkout uses the other, the account exists but cannot pay, or the reverse. The date itself is also an input. The same check run at 23:30 in Chicago on Feb 28 and on a UTC server, where it is already Mar 1, answers differently (part 1's "once per day" problem).

```fsharp
// F#, illustrative (fn_age_by_addyears is the F# tip's function; this line was not run).
// Looks like "is the user 18?". Is "is the user 18 on the server's calendar, by this formula's leap-day rule?".
let fn_is_adult (birth: DateOnly) = fn_age_by_addyears (DateOnly.FromDateTime DateTime.UtcNow) >= 18
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| F# / .NET | `AddYears` vs month/day formulas: 18 vs 17 (measured) | no age API | one shared function, the jurisdiction's rule written beside it, and the user's local date |
| TypeScript | `add` and `until` disagree on the Feb 28 birthday (measured) | documents both | use `until` for eligibility, and say so |
| Rust (`jiff`) | same as Temporal | documents both | same |
| C++ | the hand-rolled formula's choice is implicit | `ok()` flags the missing Feb 29 | handle `!ok()` explicitly instead of rolling through `sys_days` |

No language is the control. Which day a Feb 29 birthday falls on in a common year is a legal rule that varies by jurisdiction, and no library encodes it. The entry does not state which jurisdictions choose which day, because no primary source for that was checked here.

# FAQ

**Is there an incident appendix for this part?** No. No public post-mortem of a date-difference or age-calculation bug with first-hand detail was found. Part 1's Azure 2012 story is the nearest: it was "add one year" built by hand, the forward half of this part's problem.

**So which answer is right for a Feb 29 birthday?** That is a legal question for each jurisdiction, not a library question. The libraries measured here give both answers: `AddYears`, `jiff`'s `add` and Temporal's `add` put the birthday on Feb 28, while `jiff`'s and Temporal's `until` and the month/day comparison complete the year on Mar 1. Pick one, write down why, and use the same function everywhere.
