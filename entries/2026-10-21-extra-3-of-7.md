## Rust: a `u32` millisecond tick wraps every 49.7 days, `now - start` panics in debug, and `now > deadline` is wrong in both

_Idioms and antipatterns_

**Did you know**

`Instant` is 64-bit and never wraps in practice, but `u32` millisecond counters are everywhere it is not available: embedded HALs, protocol headers, 32-bit uptime fields. Such a counter wraps after 2^32 ms, 49.71 days. Plain `later - started` across the wrap panics in a debug build ("attempt to subtract with overflow") and silently gives the correct 10 in `--release`, because overflow checks are a profile setting. `wrapping_sub` is correct in both. Comparing instants is worse: once the deadline itself has wrapped, `now > deadline` reports "expired" 2 ms after the start. The fix is the one the Linux kernel's `time_after()` macro uses: subtract first, then read the difference as signed.

**Show me**

```rust
use std::hint::black_box;

const TIMEOUT_MS: u32 = 100;
const MS_PER_DAY: f64 = 86_400_000.0;

fn main() {
    // A u32 millisecond tick (an embedded HAL, a protocol header, a 32-bit uptime counter).
    let started_ms: u32 = black_box(u32::MAX - 4);         // 4 ms before the wrap
    let deadline_ms = started_ms.wrapping_add(TIMEOUT_MS); // 95: the deadline already wrapped

    // 2 ms later nothing has expired, yet the naive comparison says it has.
    let early_ms: u32 = black_box(u32::MAX - 2);
    assert!(early_ms > deadline_ms);                       // WRONG: reads as "expired"
    assert!(early_ms.wrapping_sub(started_ms) < TIMEOUT_MS); // right: 2 ms elapsed

    // 10 ms later, after the wrap: plain `-` panics in debug and wraps in release.
    let later_ms: u32 = black_box(5);
    assert_eq!(later_ms.checked_sub(started_ms), None);    // what the debug `-` trips on
    assert_eq!(later_ms.wrapping_sub(started_ms), 10);     // correct in both profiles

    // The Linux time_after() trick: subtract, then read the difference as signed.
    let fn_deadline_passed = |now_ms: u32| (now_ms.wrapping_sub(deadline_ms) as i32) >= 0; // valid while |gap| < 2^31 ms
    assert!(!fn_deadline_passed(early_ms) && !fn_deadline_passed(later_ms) && fn_deadline_passed(95));

    let wrap_days = (u64::from(u32::MAX) + 1) as f64 / MS_PER_DAY;
    println!("wraps every {wrap_days:.2} days"); // 49.71
}
```

**Why it matters**

A device or service that resets every few weeks never sees the wrap in testing; one that stays up for 50 days does, and the symptom is a timeout that fires immediately or never. Because plain `-` panics only in debug, the test build crashes where production silently does the right thing, or the reverse when someone "fixes" the panic with `checked_sub(...).unwrap_or(0)`, which turns 10 ms into 0. C++ gets the same wrap for free on `uint32_t` (unsigned overflow is defined) but undefined behaviour on `int32_t`; .NET's `int` wraps silently unless the code is `checked`; JS has to ask for 32-bit arithmetic with `>>> 0`.

**Chew on this**

Which of your counters is 32 bits wide because a wire format or a C API said so, and what is the longest your process has ever stayed up? Where a `checked_sub` returns `None`, what does your code do with it?

**Sources**

- https://doc.rust-lang.org/std/primitive.u32.html#method.wrapping_sub
- https://doc.rust-lang.org/cargo/reference/profiles.html#overflow-checks
- https://github.com/torvalds/linux/blob/master/include/linux/jiffies.h (`time_after`, `INITIAL_JIFFIES`)

**Verified**

Run under the default debug profile (panic at the plain subtraction, measured) and `--release` (prints 10). `clippy` reported nothing.

**Gotchas**

- `black_box` matters in a demo like this: with constants, rustc rejects `5_u32 - (u32::MAX - 4)` at compile time ("this arithmetic operation will overflow"), so the debug-versus-release difference never shows.
- `checked_sub` is the wrong tool for a wrapping counter: `None` there means "the counter wrapped", which is normal, not an error.
- The signed-difference trick only works while the two readings are less than 2^31 ms (24.86 days) apart. Past that it reports the wrong order, so it bounds timeouts, not dates.
- `u32::MAX as f64 / MS_PER_DAY` is 49.71 too, but it is off by one tick: the counter has 2^32 values, and `u32::MAX + 1` overflows `u32`, so widen first (`u64::from`).
- The Linux kernel starts its 32-bit jiffies counter 5 minutes before the wrap on purpose (`INITIAL_JIFFIES`, "so jiffies wrap bugs show up earlier"). A test that starts a fake clock at `u32::MAX - 300_000` does the same for your code.

## C++: `parse("%m/%d/%y")` reads `68` as 2068 and `69` as 1969, and Apple's libc++ has no `parse` at all

_Idioms and antipatterns_

**Did you know**

C++20 `std::chrono::parse` follows the POSIX rule for `%y`: "values in the range [69,99] shall refer to years 1969 to 1999 inclusive and values in the range [00,68] shall refer to years 2000 to 2068". So `"01/01/50"` is 2050 here and 1950 in .NET and JS. `strptime` and `std::get_time` give the same years on glibc. Unlike the JS `Date` parsers, `parse` refuses a day that does not exist: `"02/30/26"` sets `failbit`. The catch is availability: `parse` is part of P0355R7, which GCC 14's libstdc++ implements and Apple clang 21's libc++ does not (`use of undeclared identifier 'parse'`), so this snippet only builds on GCC here. The only fix for the pivot is a four-digit field; no format flag moves it.

**Show me**

```cpp
#include <chrono>
#include <ctime>
#include <iostream>
#include <sstream>
#include <string>
using namespace std::chrono;

// chrono::parse is C++20 but absent from Apple's libc++; this runs on GCC 14.
year_month_day parse_us_date(const std::string& text) {
    std::istringstream input{text};
    year_month_day parsed{};
    input >> parse("%m/%d/%y", parsed);
    return input.fail() ? year_month_day{} : parsed; // a default ymd is 0-00-00, !ok()
}

int main() {
    // %y follows POSIX: 69-99 is 1969-1999, 00-68 is 2000-2068.
    std::cout << parse_us_date("01/01/68") << " " << parse_us_date("01/01/69") << "\n"; // 2068-01-01 1969-01-01
    std::cout << parse_us_date("01/01/50") << "\n";                                    // 2050-01-01

    // strptime and std::get_time read the same digits the same way on glibc:
    std::tm via_strptime{};
    strptime("01/01/68", "%m/%d/%y", &via_strptime);
    constexpr int TM_YEAR_BASE = 1900;                                                 // tm_year counts from 1900
    std::cout << TM_YEAR_BASE + via_strptime.tm_year << "\n";                          // 2068

    // Unlike the Date parsers in JS, parse refuses a day that does not exist:
    std::cout << parse_us_date("02/30/26").ok() << "\n";                               // 0

    // The pivot is fixed by the format, so the only fix is a 4-digit field:
    std::istringstream four_digits{"01/01/1950"};
    year_month_day explicit_year{};
    four_digits >> parse("%m/%d/%Y", explicit_year);
    std::cout << explicit_year << "\n";                                                // 1950-01-01
}
```

**Why it matters**

A CSV export from a .NET or JS service that writes `MM/dd/yy`, read by a C++ or Go importer, moves every year from 1950 to 1968 forward by a century, and the result is a valid date that passes every check. Birth dates are where this hurts: `01/01/55` is a 71-year-old in .NET and a person born in 2055 in C++. The same bytes, two correct parsers, two answers. Rust `chrono` adds a third pivot (69/70), so even two Rust crates disagree.

**Chew on this**

Which of your inputs still arrive with a two-digit year, and which side of the pivot does its oldest legitimate value fall on? If you cannot change the format, where in the pipeline would you rather fail: at parse time, or at the first age check?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/parse
- https://pubs.opengroup.org/onlinepubs/9799919799/functions/strptime.html (`%y`)
- https://en.cppreference.com/w/cpp/compiler_support/20 (P0355R7 row)

**Verified**

The snippet ran on GCC 14.4.0 only; Apple clang 21 rejects `parse` at compile time. The C++ `get_time` result (same years as `strptime`) is from a separate probe on GCC 14.

**Gotchas**

- `%y` also accepts a single digit: glibc `strptime` reads `"1/1/5"` as 2005 and reports success, so the field width is not a validation.
- A failed `parse` leaves the `year_month_day` untouched, so the result is whatever it was initialised to. Initialise to a known invalid value (`year_month_day{}`) and check `ok()`, or check the stream's `failbit`.
- 2100 is not a leap year: `year{2100}.is_leap()` is false while `2100 % 4 == 0` is true. A hand-rolled leap test breaks 79 years from now, inside the lifetime of a 30-year mortgage written in 2071.
- macOS `date -j -f "%m/%d/%y" 01/01/68 +%Y` prints 2068 and `69` prints 1969: the BSD libc uses the same POSIX window.

## F#: `"1/1/49"` is 2049 and `"1/1/50"` is 1950, and the window is a mutable property of the culture's calendar

_Idioms and antipatterns_

**Did you know**

`DateTime.Parse` resolves a two-digit year through `Calendar.TwoDigitYearMax`, which is 2049 for en-US, en-GB, de-DE, ja-JP and the invariant culture on .NET 8: years 50 to 99 are 1950 to 1999 and 00 to 49 are 2000 to 2049. It is a settable property, so a cloned culture can move the window per call site (`TwoDigitYearMax <- 2029` makes `"1/1/30"` 1930). The Japanese calendar has no window at all: its `TwoDigitYearMax` is 99, because a two-digit Japanese year is already the era year. And a Japanese date built without an era means the current era, so year 64 is Reiwa 64 (2082), not the famous Showa 64 (1989). Measured on F# 8, FSharp.Core 8.0.0.0, .NET 8.0.8.

**Show me**

```fsharp
open System
open System.Globalization

// The pivot is Calendar.TwoDigitYearMax: 2049 in every culture measured here.
let en_us = CultureInfo "en-US"
printfn "%d" en_us.Calendar.TwoDigitYearMax                                  // 2049
let fn_parse_year (culture: CultureInfo) (text: string) : int = DateTime.Parse(text, culture).Year
printfn "%d %d" (fn_parse_year en_us "1/1/49") (fn_parse_year en_us "1/1/50") // 2049 1950

// It is a mutable property on a cloned culture, so the window can move per call site:
let billing_culture = en_us.Clone() :?> CultureInfo
billing_culture.Calendar.TwoDigitYearMax <- 2029
printfn "%d" (fn_parse_year billing_culture "1/1/30")                        // 1930

// The Japanese calendar has no two-digit window at all: the year IS the era year.
let japanese = JapaneseCalendar()
printfn "%d %d" japanese.TwoDigitYearMax (japanese.ToFourDigitYear 99)      // 99 99
// And a year without an era means the CURRENT era: year 64 is Reiwa 64, not Showa 64.
printfn "%s" ((DateTime(64, 1, 7, japanese)).ToString "yyyy-MM-dd")         // 2082-01-07
let showa = 3                                                                 // era number, from JapaneseCalendar.Eras
printfn "%s" ((japanese.ToDateTime(64, 1, 7, 0, 0, 0, 0, showa)).ToString "yyyy-MM-dd")  // 1989-01-07
```

**Why it matters**

The 2049 window is a default somebody chose in another decade, and it can move under you. Measured: a fresh `CultureInfo "en-US"` is its own copy (mutating one left another at 2049), and the cached `CultureInfo.GetCultureInfo "en-US"` is read-only (`InvalidOperationException`), but setting `CultureInfo.CurrentCulture.Calendar.TwoDigitYearMax <- 2029` changed every `DateTime.Parse` that omits a culture: `"1/1/30"` became 1930 for all of them. A record keyed on a Japanese date that was stored as era year only ("64/01/07") silently becomes a 2082 date the day it is read back without the era. C++ and Go fix the window in the format spec (POSIX 68/69), and Rust `chrono` and `jiff` fix it in the crate, so none of those three can be changed by configuration.

**Chew on this**

Is there any two-digit year in your system whose meaning depends on a culture object, and do you know every place that object is mutated? For a Japanese-calendar date, where is the era stored, and what reads it?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.globalization.calendar.twodigityearmax
- https://learn.microsoft.com/en-us/dotnet/api/system.globalization.japanesecalendar
- https://en.wikipedia.org/wiki/Time_formatting_and_storage_bugs (Showa 100)

**Verified**

Everything printed ran on .NET 8.0.8 on macOS; whether a Windows host's regional settings change the default 2049 was not checked.

**Gotchas**

- `"1/1/05"` parses as 2005, so a two-digit birth year of a 121-year-old reads as a newborn.
- `japanese.ToDateTime(100, 1, 1, 0, 0, 0, 0, 3)` (Showa 100) does not throw: it returns 2025-01-01. .NET keeps counting an era past its end, which is the same behaviour as the legacy systems that showed "Showa 100" in 2025.
- `DateTime(64, 1, 7, 0, 0, 0, 0, 3, japanese, DateTimeKind.Unspecified)` compiles, but the `3` is microseconds (an overload added in .NET 7), not the era; it still gives 2082. The era goes through `Calendar.ToDateTime`.
- `Environment.TickCount` is an `int` of milliseconds since boot: it goes negative after 24.86 days and wraps after 49.71. `TickCount64` does not. Unchecked F# subtraction across the wrap still gives the right elapsed time (10), and `Checked.(+)` throws `OverflowException`.
- `TimeSpan.FromMilliseconds` of a negative tick count is a negative `TimeSpan` (`-24.20:31:23.643`), which a "time since boot" display will happily print.
- `Threading.Timer` accepts a due time of 4,294,967,294 ms and throws at 4,294,967,295; `Task.Delay` accepts 30 days and throws at 50.
- `IsLeapYear 2100` is `false`, matching C++ `year::is_leap`.

## TypeScript: `setTimeout(fn, 30 days)` fires after 1 ms, and `NaN` does the same without a warning

_Idioms and antipatterns_

**Did you know**

Node stores a timer delay as a signed 32-bit integer, so the longest delay is 2^31 - 1 ms, 24.86 days. Anything longer, 30 days or `Infinity`, prints a `TimeoutOverflowWarning` to stderr and is set to 1 ms: the timer fires immediately. `NaN` and negative delays also become 1 ms, with no warning at all. `setInterval` overflows the same way, and then repeats every millisecond: an interval of 2^31 ms fired 89 times in 100 ms. TypeScript types `delay` as `number`, so none of this is visible at compile time. A long delay has to be a chain of shorter timers against a monotonic due time, or not a timer at all (see the security angle).

**Show me**

```typescript
// Node 22. Each comment is what a run printed; the 1 ms timers printed 1 to 3 ms across runs.
const DAY_MS = 86_400_000;
const MAX_TIMER_MS = 2 ** 31 - 1; // the delay is stored as a signed 32-bit integer
const started = performance.now();
const fn_elapsed = (): number => Math.round(performance.now() - started);

// 30 days does not fit, so Node warns on stderr and fires after 1 ms.
setTimeout(() => console.log("30-day timer fired at", fn_elapsed(), "ms"), 30 * DAY_MS); // 1 ms
// NaN and negative delays become 1 ms with no warning at all.
setTimeout(() => console.log("NaN timer fired at", fn_elapsed(), "ms"), Number("not a number")); // 1 ms

// A long timer is a chain of short ones against a monotonic due time.
const set_long_timeout = (callback: () => void, delay_ms: number, max_chunk_ms: number = MAX_TIMER_MS): void => {
    const due_at = performance.now() + delay_ms;
    const fn_arm = (): void => {
        const remaining_ms = due_at - performance.now();
        if (remaining_ms <= 0) return callback();
        setTimeout(fn_arm, Math.min(remaining_ms, max_chunk_ms));
    };
    fn_arm();
};
// Shrink the chunk to 40 ms to watch the chain work on a 200 ms delay:
set_long_timeout(() => console.log("chained timer fired at", fn_elapsed(), "ms"), 200, 40); // 201 ms
```

**Why it matters**

A "send the renewal reminder in 30 days" or "retry in a month" timer in a long-running Node service runs at once, and the only trace is one warning line in stderr that log shipping often drops. The `NaN` case is quieter still: a delay computed from a missing config value (`Number(undefined)`) fires immediately with nothing logged. .NET fails loudly at the same boundary (`Task.Delay` throws at 50 days, `Threading.Timer` past 4,294,967,294 ms); Rust `std::thread::sleep` and C++ `sleep_for` take a 64-bit duration and have no such limit (by their signatures, not measured at 30 days).

**Chew on this**

Which of your timers has a delay that comes from configuration or arithmetic rather than a literal, and what would it do with `NaN`? Should anything longer than a few minutes be a timer in your process at all, or a row with a due time?

**Sources**

- https://nodejs.org/api/timers.html#settimeoutcallback-delay-args
- https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout#maximum_delay_value

**Verified**

Node 22.17.1 only; the same overflow warning appeared on Node 26.12.1. Browser behaviour is cited from MDN, not run.

**Gotchas**

- A string delay is coerced like `Number()`: `"1000"` fired after 1001 ms, `"1e3"` after 1003 ms, and `" 1000 "` after 1007 ms.
- `setInterval(fn, 2 ** 31)` does not throw; it becomes a 1 ms interval and fired 89 times in 100 ms.
- `node --no-warnings` hides the overflow warning completely: a 2^31 ms timer printed only its callback's output.
- `performance.now()` is milliseconds since process start (`performance.timeOrigin` was 1792619994400.572 here), so a due time computed from it does not survive a restart. Persist a wall-clock instant instead.
- `performance.now()` advanced by 0.000041 ms at its smallest step here, so it is fine for durations; `Date.now()` has 1 ms resolution and can jump.
- For a 32-bit wrapping counter from a device or protocol, `(now - started) >>> 0` is the JS form of `wrapping_sub`: it gave 10 across the wrap, where `now - started` gave -4294967286.
- `Date.UTC(2100, 1, 29)` is 2100-03-01: 2100 is not a leap year, and `Date` overflows instead of failing (part 1).

# The functional angle: elapsed time on a wrapping counter is a pure function mod 2^32, and ordering is not

Draws on the Rust and TypeScript tips, with C++ and F# measured on the same numbers: a `u32` tick started at `2^32 - 5`, read again at `5`, 10 ms later.

Subtraction modulo 2^32 is total and exact: it never fails and always gives 10. Comparison is not a function of the two readings at all, because "is 5 after 4294967291?" depends on how many wraps happened in between, which the values do not carry. Each language below gets the subtraction right in one expression; none of them can make `<` right.

F# is the baseline here because its default arithmetic is already the unchecked modular kind, so the pure form is just `-`:

```fsharp
// F#: uint32 arithmetic is unchecked by default, so `-` is already modular
let started = UInt32.MaxValue - 4u
let now = 5u
printfn "%d" (now - started) // 10
```

Rust makes the modular intent explicit in the name, because plain `-` panics in debug builds:

```rust
// Rust: wrapping_sub is the total, profile-independent form
assert_eq!(5_u32.wrapping_sub(u32::MAX - 4), 10);
```

C++ gives the same answer for unsigned types and undefined behaviour for signed ones:

```cpp
// C++: modulo 2^32 for uint32_t, by the standard
std::uint32_t started = std::numeric_limits<std::uint32_t>::max() - 4, now = 5;
std::uint32_t elapsed = now - started;           // 10
// The same arithmetic on int32_t is UB; clang -fsanitize=signed-integer-overflow reports
// "signed integer overflow: 2147483643 + 10 cannot be represented in type 'int'"
```

TypeScript has no 32-bit type, so it opts in with an operator:

```typescript
// TypeScript: >>> 0 reinterprets the double as an unsigned 32-bit integer
const started = 2 ** 32 - 5;
const now = 5;
console.log((now - started) >>> 0); // 10; without >>> 0 it is -4294967286
```

| Language | Modular elapsed | Cost of the pure form | Ordering (`now > deadline`) |
| --- | --- | --- | --- |
| F# | `now - started` on `uint32` | none: unchecked is the default; `Checked` would throw | wrong across the wrap |
| Rust | `wrapping_sub` | a method name; plain `-` panics in debug | wrong across the wrap |
| C++ | `now - started` on `uint32_t` | none for unsigned; UB for `int32_t` | wrong across the wrap |
| TypeScript | `(now - started) >>> 0` | an operator, and only for 32 bits | wrong across the wrap |

The four agree on both halves, which says the problem is the representation, not the language. A wrapping counter is an element of a cyclic group: differences are meaningful, positions are not. The kernel's `time_after()` recovers an ordering only by assuming the two readings are less than half the cycle apart, which is a precondition no type here can state.

Is "these two readings are within 24 days of each other" a fact your types could carry, or only your tests?

# The security angle: a ban implemented as a timer ends when the timer overflows

Mode C on the TypeScript tip, in the direction the languages do not help: nothing in any of the four type systems distinguishes "a delay my runtime can hold" from "a number". Leave out the bound and a 30-day ban becomes a 1 ms ban:

```typescript
// TypeScript
const DAY_MS = 86_400_000;
// INSECURE: the ban is a timer. 30 days overflows the timer, so the ban lifts after 1 ms.
const banned = new Set<string>();
const ban_insecure = (account_id: string, ban_ms: number): void => {
    banned.add(account_id);
    setTimeout(() => banned.delete(account_id), ban_ms);
};
// FIXED: the ban is data, an expiry instant checked on every request (and it survives a restart).
const banned_until = new Map<string, number>();
const ban = (account_id: string, ban_ms: number): void => { banned_until.set(account_id, Date.now() + ban_ms); };
const is_banned = (account_id: string, now_ms: number = Date.now()): boolean => (banned_until.get(account_id) ?? 0) > now_ms;

ban_insecure("acct-1", 30 * DAY_MS);
ban("acct-1", 30 * DAY_MS);
setTimeout(() => console.log(banned.has("acct-1"), is_banned("acct-1")), 20); // false true
```

The fixed version also removes a second problem the timer had in every language: a process restart drops all pending timers, so a timer-based ban, lockout or token revocation ends at the next deploy.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | Node `setTimeout` over 2^31 - 1 ms, or `NaN`, fires in 1 ms | a stderr warning for overflow, nothing for `NaN` | store the expiry instant; validate computed delays |
| F# / .NET | `Task.Delay` over the limit throws; `TickCount` goes negative at 24.86 days | throws `ArgumentOutOfRangeException`, so the failure is loud | catch it, or store the instant; use `TickCount64` |
| Rust | a `u32` tick deadline compared with `>` expires early or late | debug builds panic on `-`; release wraps silently | `wrapping_sub` plus a bounded window, or 64-bit `Instant` |
| C++ | `int32_t` tick arithmetic across the wrap | undefined behaviour; the optimizer may assume it never happens | `uint32_t` or `steady_clock`; `-fsanitize=signed-integer-overflow` in tests |

.NET is the control for the timer half, since it is the only one of the four that refuses an out-of-range delay instead of reinterpreting it. Class: CWE-190 (Integer Overflow or Wraparound) for the delay and the tick counter, and CWE-613 (Insufficient Session Expiration) when the timer was what ended a session or a ban.

Which of your security decisions, a lockout, a ban, a token's death, is enforced by something that only exists in memory?

# FAQ

**Does a monotonic clock keep counting while the machine sleeps?**
On Linux, not by default. Debian 13's clock_gettime(2) says `CLOCK_MONOTONIC` "does not count time that the system is suspended", while `CLOCK_BOOTTIME` "also includes any time that the system is suspended". Rust `Instant` documents `CLOCK_MONOTONIC` on Unix, so a Rust `Instant`-based timeout on a laptop that slept for an hour has not seen that hour. Whether C++ `steady_clock` on libstdc++ and Node `performance.now()` use the same clock was not checked.

**What is leap smearing, and why can two servers disagree?**
Instead of inserting `23:59:60`, a smearing NTP server stretches seconds so the extra one is absorbed gradually. Google's published standard is "a 24-hour linear smear from noon to noon UTC". Computed from that: each smeared second is 1/86400 s (11.6 microseconds) longer, and at the leap instant a smeared clock is 0.5 s behind true UTC. A fleet that mixes smeared and unsmeared NTP sources therefore disagrees by up to half a second around the leap, more than enough to reorder log lines or fail a token's `nbf` check. Smearing is irrelevant until the next leap second, and the CGPM decided in 2022 to stop adding them by 2035 (part 1).

**Is 2100 a leap year?**
No: divisible by 100 and not by 400. Measured: C++ `year{2100}.is_leap()` false, .NET `DateTime.IsLeapYear 2100` false, JS `Date.UTC(2100, 1, 29)` rolls to 2100-03-01, while the hand-rolled `2100 % 4 == 0` is true. The 2000 test passes either way, which is why the bug survives: 2000 is divisible by 400.

**What happened with "Showa 100"?**
Showa ended in its 64th year (1989), but some Japanese systems never learned the later eras and kept counting, so 2025 became Showa 100, a three-digit year in fields sized for two (Wikipedia's time bugs list). .NET `JapaneseCalendar.ToDateTime(100, 1, 1, 0, 0, 0, 0, 3)` accepts Showa 100 and returns 2025-01-01, so .NET would read such a record back without complaint.

**Why does the Linux kernel start its tick counter near the wrap?**
So wrap bugs show up in minutes instead of 49 days. `include/linux/jiffies.h` sets `INITIAL_JIFFIES` to `-300*HZ` cast to 32 bits, "so jiffies wrap bugs show up earlier", and compares ticks with `time_after(a, b)`, defined as `((long)((b) - (a)) < 0)`: the same subtract-then-sign test as the Rust tip.

**Can I just use 4-digit years everywhere and forget the pivots?**
For anything you write, yes: every parser measured here reads `%Y` / `yyyy` without a window. For anything you read, no: the pivot belongs to whoever wrote the file, and the opening table shows that .NET, JS, POSIX C and C++, Go, and both Rust crates would read the same `68` as two different centuries.

# Appendix A: the Patriot clock at Dhahran, a counter that was fine and a conversion that was not

_Not part of the tip rotation. Added 2026-10-22, backing this part's thesis that small fields run out. A real incident, not folklore: every fact below is quoted from the GAO report or the Wikipedia article in A.6, and every number in A.2 and A.3 was printed by a real run of the snippets in Rust (rustc 1.95.0), C++20 (Apple clang 21), F# (.NET 8.0.8) and TypeScript (Node 22.17.1)._

**Bug class:** Aging-related bug (Grottke and Trivedi's term, cited by Wikipedia's Heisenbug article): a deterministic Bohrbug whose error grows with uptime and resets on reboot. Root-cause anti-pattern: multiplying an integer tick count by a constant that binary cannot represent exactly (0.1).

## A.1 What happened

On February 25, 1991, a Patriot battery at Dhahran, Saudi Arabia, failed to track an incoming Scud. GAO: the Scud "hit an Army barracks, killing 28 Americans." The battery "had been operating continuously for over 100 hours." Time was "kept continuously by the system's internal clock in tenths of seconds", as an integer, and converted to a real number in registers "only 24 bits long", so the converted time drifted further from the truth the longer the system ran. Two weeks earlier, Israeli data had shown "a 20 percent shift in the Patriot system's radar range gate after the system had been running for 8 consecutive hours". The corrected software was released on February 16 and reached Dhahran on February 26, the day after the attack. The workaround needed no new software at all: rebooting "every few hours", which "takes about 60 to 90 seconds" and sets the clock back to zero.

## A.2 The arithmetic, reproduced

The counter itself never overflowed. The bug is the constant 0.1, which has no exact binary form, chopped to the register's 23 fractional bits:

```rust
// Rust: 0.1 chopped to 23 fractional bits, then multiplied by the tick count
const FRACTION_BITS: u32 = 23;
let scale = (1u64 << FRACTION_BITS) as f64;
let chopped_tenth = (0.1 * scale).floor() / scale;  // 0.0999999046325684
let error_per_tick = 0.1 - chopped_tenth;           // 9.537e-8 s per tenth of a second
let drift_secs = (100 * 3600 * 10) as f64 * error_per_tick; // 100 h of ticks: 0.3433 s
```

| Uptime | GAO's "inaccuracy" column | Recomputed (Rust, C++, F# and TypeScript all agree) | GAO's range-gate shift |
| --- | --- | --- | --- |
| 1 h | 0.0034 s | 0.0034 s | 7 m |
| 8 h | 0.0275 s | 0.0275 s | 55 m |
| 20 h | 0.0687 s | 0.0687 s | 137 m (target outside the gate) |
| 48 h | 0.1648 s | 0.1648 s | 330 m |
| 72 h | 0.2472 s | 0.2472 s | 494 m |
| 100 h | 0.3433 s | 0.3433 s | 687 m |

The model matches all six of GAO's rows to four decimals. The bit-level detail (23 fractional bits, chopped rather than rounded) is this appendix's reconstruction; GAO says only "24 bits". Wikipedia rounds the miss to "600 meters", and GAO's own table says 687.

## A.3 The same bug in today's code

Nobody writes 24-bit fixed point now, but `f32` has a 24-bit significand, and adding 0.1 on every tick is the common modern form:

| Language | 100 h of `elapsed += 0.1` in 32-bit float | Same loop in 64-bit float |
| --- | --- | --- |
| Rust (`f32`) | 347024.78, off by 12975.2 s (3.6 hours) | 359999.999987987, off by 1.2e-5 s |
| C++ (`float`) | 347024.8 | not run |
| F# (`float32`) | 347024.8 | not run |
| TypeScript (`Math.fround` each step) | 347024.8 | 359999.999987987 |

The 32-bit sum also stops moving altogether: at 2097152 (2^21), after 18,073,720 ticks (502 hours), adding 0.1 rounds back to the same value, so the clock freezes (measured in Rust). The repair is the one Rust's `Duration` and C++'s `std::chrono::duration<int64_t, std::deci>` already make: count integer ticks, and convert to seconds once, at the edge.

## A.4 Why it looked intermittent

The error depended on how long the battery had been up, not on anything in the input. A freshly rebooted battery was accurate, and Army officials "assumed other Patriot users were not running their systems for 8 or more hours at a time" (GAO). That is an uptime bug rather than a true Heisenbug: it was fully deterministic, but nobody's test ran 100 hours.

## A.5 Back to the tips

The `u32` tick tip wraps at 49.7 days. The Patriot counter never wrapped: its field was big enough, and the constant it was multiplied by was too small. "Count in integers, convert once" fixes both. A reboot schedule only hides them, and GAO notes the system was designed "to operate for only a few hours at one location".
