## Rust: `Arc<str>::from(String)` copies the whole string into a new block, and `Arc::new(String)` allocates 40 bytes

*Perf and memory model*

**Did you know**

An `Arc<str>` keeps its two reference counts in the same heap block as the bytes, right in front of them. A `String`'s buffer has no room for those 16 bytes, so `Arc::<str>::from(string)` cannot adopt it. It allocates a new block of `len + 16` bytes, copies every byte, and frees the old buffer. The doc says so in one line: "Allocates a reference-counted `str` and copies `v` into it." Going through `into_boxed_str()` first does not help, because `From<Box<str>>` copies too. `Arc::new(string)` is the opposite trade. It allocates 40 bytes (16 for the counts, 24 for the `String` header), keeps the original buffer, and costs a second pointer hop on every read.

**Show me**

```rust
// rustc 1.95.0, -O. A counting #[global_allocator] (not shown, 15 lines)
// adds up layout.size() for every alloc. The numbers in comments are from that run.
use std::rc::Rc;
use std::sync::Arc;

fn main() {
    const PAYLOAD_LEN: usize = 1 << 20; // 1 MiB request body

    let body = "a".repeat(PAYLOAD_LEN);
    let body_ptr = body.as_ptr();
    // 1048592 bytes allocated = 1 MiB + 16 for strong and weak counts.
    let shared: Arc<str> = Arc::from(body);
    assert!(!std::ptr::eq(shared.as_ptr(), body_ptr)); // a new buffer

    let body = "b".repeat(PAYLOAD_LEN);
    let body_ptr = body.as_ptr();
    // 40 bytes allocated. The 1 MiB buffer is kept, one pointer hop deeper.
    let wrapped: Arc<String> = Arc::new(body);
    assert!(std::ptr::eq(wrapped.as_ptr(), body_ptr));

    // Rc<str>::from(String): 1048592 again. Same layout, same copy.
    // Arc<str>::from(Box<str>): 1048592 too, even with an exact-fit box.
    let local: Rc<str> = Rc::from("c".repeat(PAYLOAD_LEN));

    // Arc<str> is a fat pointer (16 bytes), Arc<String> a thin one (8).
    println!("{} {} {}", shared.len(), wrapped.len(), local.len());
}
```

**Why it matters**

`Arc<str>` is the usual answer to "share this immutable string across tasks", and that is right for small keys and config values. On a request path that turns a freshly read body into `Arc<str>`, it doubles peak memory for that body for a moment and adds a full `memcpy`. C++ makes the same choice in plain sight. `std::make_shared<std::string>(std::move(body))` is the `Arc<String>` shape: one control block, the buffer moved in, not copied. Nothing in std gives you a `shared_ptr<char[]>` that adopts a `std::string`'s buffer. F# and TypeScript strings are already shared, immutable, GC-managed objects. Their cost is the reverse: you cannot build one in place without a copy at the end (`StringBuilder.ToString()`, `Buffer.toString()`).

**Chew on this**

Where in your services does a `String` become an `Arc<str>` exactly once, on a hot path, and how big is it when it does? If you switched that one to `Arc<String>`, which readers would pay the extra hop, and would any of them notice?

## C++: C++26 made `std::to_string(0.1)` return `"0.1"`, and only libstdc++ ships it

*Stdlib and ecosystem gems*

**Did you know**

Up to C++23, `std::to_string(double)` is defined as `sprintf("%f")`. That means six digits after the point, always. So `to_string(1e-7)` is `"0.000000"`, and `to_string(1e300)` is a 308-character string of digits. C++26 (P2587R3, voted in June 2023) redefines it as `std::format("{}", value)`, the shortest string that reads back to the same double: `"0.1"`, `"1e-07"`, `"1e+300"`. libstdc++ has shipped this since GCC 14, under `-std=c++26` only. libc++ has not. Its `<version>` header still has `__cpp_lib_to_string` commented out, and upstream lists the paper as not started (llvm/llvm-project#105359). MSVC's STL has no entry for it either. So the same line logs a different string depending on the platform and the `-std` flag.

**Show me**

```cpp
// Run 2026-10-06. Outputs in comments are from those runs.
//   GCC 14.4.0 (docker gcc:14), libstdc++: -std=c++23 and -std=c++26
//   Apple clang 21, libc++ 22.1 (_LIBCPP_VERSION 220106): -std=c++23 and -std=c++2c
#include <charconv>
#include <cstdio>
#include <string>
#include <version>

int main() {
#ifdef __cpp_lib_to_string                 // 202306L on GCC 14 + c++26 only
    std::puts("to_string uses format");
#endif
    const double samples[] = {0.1, 1e-7, 3.14159265358979};
    for (double sample : samples) {
        char shortest[64];
        auto converted = std::to_chars(shortest, shortest + sizeof shortest, sample);
        *converted.ptr = '\0';
        std::printf("%s | %s\n", std::to_string(sample).c_str(), shortest);
    }
    // libc++ (any -std), libstdc++ c++23:
    //   0.100000 | 0.1
    //   0.000000 | 1e-07          <- a nonzero value printed as zero
    //   3.141593 | 3.14159265358979
    // libstdc++ c++26:
    //   0.1 | 0.1
    //   1e-07 | 1e-07
    //   3.14159265358979 | 3.14159265358979
}
```

**Why it matters**

Any string that `to_string` builds and something else compares changes on a GCC 14 build that moves to `-std=c++26`. That includes golden-file tests, cache keys, metric labels, and a hash or signature over a string. The new output is the better one, but it is not the old one. Code built with libc++ on macOS keeps the old form, so the CI machine and the dev laptop now disagree. Spelling it `std::to_chars` (C++17; floating point complete since GCC 11, and present in the libc++ 22 used here) gives the shortest form today, on both toolchains tested. Rust's `f64::to_string()` has always been shortest round-trip, so `0.1` prints as `0.1`. TypeScript's `String(0.1)` is shortest round-trip by spec. In both, there was never a `%f` era to migrate away from.

**Chew on this**

Which of your `to_string` calls on a `double` feed something that compares bytes, not numbers? When you move one build to C++26, which of your test baselines change on Linux and stay the same on macOS?

- https://wg21.link/P2587R3
- https://en.cppreference.com/w/cpp/compiler_support/26

## F#: A `task { }` bound with `let` has already run, and an `async { }` runs again every time you start it

*Idioms and antipatterns*

**Did you know**

`async { ... }` is a recipe. Binding it runs nothing. Each `Async.RunSynchronously` or `let!` starts a fresh run of the body. `task { ... }` is a receipt. The docs say "the task is started immediately after this code is executed". So `let charge = task { ... }` has already run the body by the next line, and every later `.Result` or `let!` reads the same stored result. The two look alike and have the same `let!` syntax. A retry helper that is handed a `Task<'T>` value, not a `unit -> Task<'T>`, retries nothing. It awaits the same finished task each time.

**Show me**

```fsharp
// dotnet fsi, .NET 8.0.8, FSharp.Core 8.0.0.0. Output in comments is from that run.
open System.Threading.Tasks

let mutable charge_count = 0   // stands in for "the card was charged"

let charge_async : Async<int> = async { charge_count <- charge_count + 1; return charge_count }
let charge_task  : Task<int>  = task  { charge_count <- charge_count + 1; return charge_count }
printfn "after binding both: %d" charge_count            // 1: the task already ran

printfn "async: %d %d" (Async.RunSynchronously charge_async)
                       (Async.RunSynchronously charge_async)   // 2 3: runs per start
printfn "task:  %d %d" charge_task.Result charge_task.Result   // 1 1: one result, read twice

// The retry trap. The helper wants something it can call again.
let retry_twice (attempt: unit -> Task<int>) = task {
    let! first = attempt ()
    let! second = attempt ()
    return first, second }

let already_started = task { charge_count <- charge_count + 1; return charge_count }
retry_twice (fun () -> already_started) |> ignore   // (4, 4): one side effect, not two
retry_twice (fun () -> task { charge_count <- charge_count + 1; return charge_count })
|> ignore                                           // (5, 6): a fresh task per attempt
```

**Why it matters**

Moving a code base from `async` to `task` for speed or .NET interop changes when code runs, with no compile error. A value that used to be re-run on every retry, poll, or `Async.Parallel` branch is now run once, at the binding. If that binding is at module level, it runs once at startup. The reverse move hurts too: an `async` passed around as "the result" runs its HTTP call again at every consumer. TypeScript has the same split, but split across libraries: a `Promise` is a receipt and an Effect `Effect` is a recipe. Rust futures are recipes that cannot be run twice. Awaiting one consumes it, so a second `.await` is a move error (E0382), not a silent repeat.

**Chew on this**

In your F# services, which module-level `let` bindings are `task { }` expressions, and did their authors know those run during module initialization? Where you pass work into a retry or timeout wrapper, does its signature take the work or a function that makes the work?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/task-expressions
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/async-expressions
- https://github.com/fsharp/fslang-design/blob/main/FSharp-6.0/FS-1097-task-builder.md

**Verified**

`dotnet fsi` emitted FS3511 ("state machine is not statically compilable") for the two module-level `task` expressions that capture a module-level `mutable`. That is a script-hosting artifact. It does not change when the body runs. It was not checked in a compiled project.

## TypeScript: An untagged union accepts an object with both members' fields, and `in` picks whichever branch you test first

*Type system deep cuts*

**Did you know**

Excess property checking on a union that has no discriminant only asks one question: does each property belong to *some* member, with the right type? TypeScript 3.5 added that much and stopped there. The 3.5 release notes say "partial overlap is still permitted." So `{ subject_id, group_id, scope }` is a valid `GrantBySubject | GrantByGroup`, even though it is neither one. A misspelled key is still caught, which is why this hole goes unnoticed. Add a literal `kind` field and the checker narrows to one member before it checks, so the same extra field becomes TS2353. Adding `group_id?: never` to the subject member does the same without a tag.

**Show me**

```typescript
// tsc 6.0.3 --strict. Errors in comments are from that run; the runtime line ran on Node 22.17.1.
type GrantBySubject = { subject_id: string; scope: string };
type GrantByGroup = { group_id: string; scope: string };
type Grant = GrantBySubject | GrantByGroup;

// Compiles. Every property exists in some member.
const ambiguous: Grant = { subject_id: "u-17", group_id: "admins", scope: "read" };

// error TS2561: 'scpoe' does not exist in type 'Grant'. Did you mean 'scope'?
// const typo: Grant = { subject_id: "u-17", scope: "read", scpoe: "write" };

function describe(grant: Grant): string {
    if ("subject_id" in grant) return `subject ${grant.subject_id}`;
    return `group ${grant.group_id}`;
}
describe(ambiguous); // "subject u-17": the group half is ignored, silently

// Fix 1, tag it: error TS2353: 'group_id' does not exist in type
//   '{ kind: "subject"; subject_id: string; scope: string; }'
type TaggedGrant =
    | { kind: "subject"; subject_id: string; scope: string }
    | { kind: "group"; group_id: string; scope: string };

// Fix 2, forbid the other member's key: error TS2322 on the same literal.
type ExclusiveGrant =
    | { subject_id: string; group_id?: never; scope: string }
    | { group_id: string; subject_id?: never; scope: string };
```

**Why it matters**

Grants, payment targets, and "by id or by email" lookups are exactly the shapes people write as untagged unions, and these are the places where "both" is not a valid state. Any two functions that narrow in a different order then disagree about what the value is. One checks `"subject_id" in grant` and the other checks `"group_id" in grant`. Rust and F# cannot hold the ambiguous value at all: an enum or DU value is one case, and the compiler knows which one. C++ `std::variant` is the same, since `index()` is one number. The gap only reopens there at a parser that has to choose a case from loose input. In TypeScript the choice happens in each `if`, every time someone narrows.

**Chew on this**

Which of your unions are "one of these id shapes" with no `kind` field, and how many places narrow them? If two of those places test the fields in a different order, which one is the authorization check?

# The functional angle: a value that holds work is either a recipe or a receipt, and only F# lets you pick with one keyword

Draws on the F# tip (`async` against `task`), with the other three languages measured on the same question. Run the same "charge once" computation through each one's deferred value. Then ask two things: did binding it run anything, and does a second consumer run it again?

```rust
// Rust 1.95: a future is a recipe that can be used once.
let pending = charge();          // nothing ran: CHARGE_COUNT == 0
block_on(pending);               // runs, -> 1
// block_on(pending);            // error[E0382]: use of moved value: `pending`
```

```cpp
// C++23: std::async picks by launch policy, and get() is single-use.
auto hot  = std::async(std::launch::async, charge);    // has run (count 1)
auto lazy = std::async(std::launch::deferred, charge); // has not run
hot.get(); lazy.get();                                 // 1, 2
hot.get();  // valid() == false. The standard leaves this undefined.
            // libstdc++ 14: throws future_error "No associated state".
            // libc++ 22 (Apple clang 21): segfault, exit 139.
auto shared = std::async(std::launch::deferred, charge).share();
shared.get(); shared.get();                            // 3, 3: now a receipt
```

```typescript
// effect 4.0.1, Node 22.17.1.
const promise = new Promise((resolve) => resolve(++charge_count)); // ran: 1
const effect = Effect.sync(() => ++charge_count);                 // did not run
await promise; await promise;                                      // 1, 1
Effect.runSync(effect); Effect.runSync(effect);                    // 2, 3
const cached = Effect.runSync(Effect.cached(effect));
Effect.runSync(cached); Effect.runSync(cached);                    // 4, 4
```

| Language | Recipe (cold) | Receipt (hot) | Second consumer, measured | What it costs |
| --- | --- | --- | --- | --- |
| F# | `async { }` | `task { }` | async: runs again. task: same result | one keyword; same `let!` for both, so a swap does not show at the use site |
| Rust | every `Future` | none in std; `futures::FutureExt::shared` | compile error E0382 | no silent repeat; sharing needs a crate and `Clone` output |
| C++ | `launch::deferred` | `launch::async`, `.share()` | `get()` twice: throws on libstdc++, segfaults on libc++ | UB, not a type error; `shared_future` is the opt-in receipt |
| TypeScript | `Effect` | `Promise` | Effect: runs again. Promise: same result | two libraries, two vocabularies; `Effect.cached` converts |

The asymmetry worth noticing is in the Rust row. It is the only language here where "run it again" cannot happen by accident, because the type system makes the recipe single-use. The cost is that making a receipt is a deliberate act with a dependency attached. F# is the other end: both shapes are built in, and the only clue to which one you have is a word in the binding.

If a recipe that runs twice and a receipt that runs once are both correct, depending on the caller, whose job is it to say which one a function returns: its type, its name, or its docs?

# The security angle: a value two readers can interpret two ways is an authorization bug waiting for a second reader

Draws on the TypeScript tip (Mode D: make the state impossible to represent) and the C++ tip (Mode B: is this secure, not just correct?). Both run in the "the language lets it through" direction.

**The ambiguous grant.** The compiler accepts the literal, and a cast at the JSON boundary accepts anything. So the ambiguous state arrives from a request body without anyone writing it on purpose:

```typescript
// tsc 6.0.3 --strict: compiles, even with the ExclusiveGrant fix in place,
// because `as` asserts and does not check.
const grant = JSON.parse(request_body) as ExclusiveGrant;
// Reader 1, the permission check:
const allowed = "group_id" in grant ? group_may(grant.group_id) : subject_may(grant.subject_id);
// Reader 2, the audit log:
const actor = "subject_id" in grant ? grant.subject_id : grant.group_id;
// A body with both ids is checked as the group and logged as the subject.
```

This is CWE-436 (Interpretation Conflict): two components read the same input and reach different conclusions. The `?: never` and `kind` fixes protect values the compiler sees being built. They do nothing for a value that was cast, so the runtime decoder has to reject "both" too (an Effect `Schema` union, or a hand-written check that exactly one id key is present).

**The zero that was not zero.** `std::to_string(1e-7)` is `"0.000000"` under every libc++ build and every pre-C++26 libstdc++ build. A rate limit, fee, or threshold that goes through `to_string` into a config file, query string, or signed message reaches the other side as zero. This is CWE-681 (Incorrect Conversion between Numeric Types). The C++26 fix arrives on one standard library only, so a mixed fleet produces both strings from the same source line.

```cpp
// Looks like serialization. On libc++ it rounds 1e-7 down to 0.
std::string encode_fee_rate(double fee_rate) { return "fee=" + std::to_string(fee_rate); }
// Spell it so every toolchain gives the same, exact answer:
//   char text[32]; auto converted = std::to_chars(text, text + sizeof text, fee_rate);
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | an untagged union holds both cases; readers narrow differently (CWE-436) | literal checks with a tag or `?: never`; nothing at an `as` cast | a runtime decoder that rejects "both"; one narrowing function, not many |
| Rust | the same grant as an `enum` | cannot hold both; one variant, checked by `match` | whatever deserializer picks the variant: check what it does with the other id (not measured here) |
| F# / C# | the same grant as a DU | cannot hold both | same as Rust, at the JSON converter |
| C++ (libc++, libstdc++ before c++26) | `to_string` turns a small nonzero double into `"0.000000"` (CWE-681) | defines it as `%f`; C++26 fixes it on libstdc++ only | `std::to_chars` for anything that is parsed back or compared |

Rust is the baseline for the grant row, because there the failure is about which values a type can hold, and an enum value is one case. For the float row the baseline is TypeScript. Its `String(number)` was always shortest round-trip, so the bug cannot exist there, and the C++ row is all cost.

Which of your request types are cast at the boundary rather than decoded, and does any of them have two ways to say who the caller is?

# FAQ

**Does `Arc<[T]>::from(Vec<T>)` reuse the buffer?** No, for the same reason as `str`: the counts must sit in front of the elements. It allocates and moves the elements. `Arc<Vec<T>>` keeps the buffer.

**Can I get the C++26 `to_string` on clang today?** Only by building against libstdc++ (`-stdlib=libstdc++` on Linux, GCC 14 or newer) with `-std=c++26`. libc++ has no implementation as of 22.1.

**Does `backgroundTask { }` change the hot/cold behavior?** No. It changes where the task runs (it skips the `SynchronizationContext`). It still starts when the expression is evaluated.

**Is `ValueTask` a recipe?** No. It is a receipt that may be read only once, which is stricter than `Task`. Awaiting the same `ValueTask` twice is not supported.

**Does `exactOptionalPropertyTypes` close the union hole?** No. The ambiguous literal still compiles with it on (tsc 6.0.3). The fix is the `?: never` field.
