<!-- special-nav -->
**Specials:** [<- previous: small bugs that exploded, part 4 of 13](2026-11-02-extra-4-of-13.md) | (last special)

Not part of the rotation. Part 5 of the thirteen-part special on real incidents: the [AT&T long-distance network slowdown](https://catless.ncl.ac.uk/Risks/9/63/) of 1990-01-15. Each tip below is a second event that arrives while an update is half done, and what the language does about it.

# What happened

**Bug class:** Bohrbug in this special's classification: AT&T describes it as reproducible once two call attempts arrive inside the vulnerable window. The anti-pattern is state that is inconsistent for a moment, reachable by the next message.

From AT&T's "Technical background on AT&T's network slowdown, January 15, 1990", reprinted in RISKS Digest 9.63 from TELECOM Digest (28 January 1990; dashes normalized to ASCII):

```text
As the result of a software flaw, this DLN processor was left vulnerable to
disruption for several seconds. During this vulnerable time, the receipt of two
call attempts from the New York switch -- within an interval of 1/100th of a
second -- caused some data to become damaged. The DLN processor was then taken
out of service to be reinitialized.
```

```text
Since the DLN processor is duplicated, its mate took over the traffic load.
However, a second couplet of closely spaced new call messages from the New York
4ESS switch hit the mate processor during the vulnerable period, causing it to
be removed from service and temporarily isolating the switch from the CCS7
signaling network.
```

The flaw "was inadvertently introduced into all the 4ESS switches in the AT&T network as part of a mid-December software update", so every switch carried it and the effect "cascaded through the network". The often-told version, a C `break` inside an `if` inside a `switch` that left the `switch` instead of the `if`, comes from a forwarded email from a DEC address dated 19 January 1990, quoted secondhand in [RISKS Digest 9.69](https://catless.ncl.ac.uk/Risks/9/69/). AT&T's report does not mention it, so this part does not rest on it.

## Rust: `RefCell` turns a second update during the window into a refusal or a panic, never into damaged data

*Stdlib and ecosystem gems*

**Did you know**

`RefCell<T>` tracks its one mutable borrow at runtime, so a second `borrow_mut` while the first is still alive is refused: `try_borrow_mut` returns `Err`, and `borrow_mut` panics with "RefCell already borrowed". That is the AT&T window turned into an error: the second call attempt cannot reach the half-updated map at all. The cost is that a re-entrant path the design did not foresee now crashes the handler instead of corrupting it. Measured on rustc 1.99.1.

**Show me**

```rust
// rustc 1.99.1, Debian.
use std::cell::RefCell;
use std::collections::HashMap;

fn main() {
    let status_map: RefCell<HashMap<&str, bool>> = RefCell::new(HashMap::new());

    let mut in_update = status_map.borrow_mut(); // the update window opens
    in_update.insert("new-york", true);

    // A second call attempt arrives while the window is open.
    println!("{}", status_map.try_borrow_mut().is_err()); // true: refused, nothing damaged
    // status_map.borrow_mut() here panics with "RefCell already borrowed".

    drop(in_update); // the window closes
    println!("{}", status_map.try_borrow_mut().is_ok()); // true
}
```

**Why it matters**

A refused update is a design decision you can see and handle: queue the message, drop it, or retry. Damaged data is a decision nobody made. The trade is availability: a panic in a handler is a crash of that handler, which in a duplicated pair can repeat the AT&T outcome (inferred: two halves running the same code fail the same way).

**Chew on this**

Which of your `RefCell` or `Mutex` borrows are held across a call that can deliver another message? If a borrow failure meant "try again in a moment", where would you put the retry?

**Sources**

- https://doc.rust-lang.org/std/cell/struct.RefCell.html#method.try_borrow_mut
- https://doc.rust-lang.org/std/sync/struct.Mutex.html#method.lock

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1.

**Gotchas**

- `std::sync::Mutex` is not re-entrant either: a second `try_lock` from the thread that already holds it returned `WouldBlock`. The docs say a second `lock` from the same thread "will not return" and "might panic or deadlock".
- The refusal happens only while the first borrow is alive: after `drop(in_update)`, `try_borrow_mut` succeeded. A borrow that ends before an `await` or a callback no longer protects what happens there.

## C++: `std::recursive_mutex` lets the second call attempt in while the invariant is broken, and the state looks right again afterwards

*Idioms and antipatterns*

**Did you know**

A `std::recursive_mutex` lets the thread that holds it lock it again, which is the usual fix for "my handler calls itself and deadlocks". The second entry then runs in the middle of the first one's update: in the measured program the nested call saw `size 2 count 1`, an invariant that never holds between updates. When the outer call finished, the state read `size 2 count 2`, so any check made after the update passes. Measured on GCC 16.2 and Apple clang 21 (C++20).

**Show me**

```cpp
// C++20, GCC 16.2 (Debian) and Apple clang 21: same output.
#include <cstdio>
#include <mutex>
#include <string>
#include <vector>

struct link_status {
    std::vector<std::string> in_service;
    std::size_t count = 0;  // invariant: count == in_service.size()
};
std::recursive_mutex status_lock;
link_status status;

void on_call_attempt(const std::string& switch_name, bool deliver_nested) {
    std::lock_guard<std::recursive_mutex> guard(status_lock);  // the same thread may enter again
    status.in_service.push_back(switch_name);                   // invariant broken here...
    if (deliver_nested) on_call_attempt(switch_name, false);    // ...when the second attempt arrives
    status.count += 1;                                          // ...and restored here
    std::printf("%s: size %zu count %zu\n", deliver_nested ? "outer" : "inner",
                status.in_service.size(), status.count);
}

int main() { on_call_attempt("new-york", true); }
// inner: size 2 count 1   <- the nested call ran on a broken invariant
// outer: size 2 count 2   <- and the state looks right again afterwards
```

**Why it matters**

A recursive mutex protects against other threads, not against your own call stack, and re-entry from your own stack is exactly the second message arriving mid-update. Rust's `RefCell` and `Mutex` refuse the same re-entry, as the Rust tip measured. In C++ the choice between deadlock (`std::mutex`) and a silent broken invariant (`std::recursive_mutex`) is the programmer's, and neither one reports it.

**Chew on this**

Where in your code is a `recursive_mutex` hiding a call path that re-enters an update? If each such path had to be written as "queue this until the current update is done", how many would you find you never meant to allow?

**Sources**

- https://en.cppreference.com/w/cpp/thread/recursive_mutex
- https://en.cppreference.com/w/cpp/thread/mutex/lock

**Verified**

Compiled with `-std=c++20 -Wall -Wextra` on GCC 16.2.0 (`gcc:latest`, Debian) and Apple clang 21.0.0 (Apple's vendor build, macOS arm64); no warnings, same output.

**Gotchas**

- Neither compiler warned about the re-entrant call: with `-Wall -Wextra` both compiled the program silently.
- The final state is consistent, so an assertion placed after `on_call_attempt` returns would pass; only an assertion inside the nested call sees `count 1` against `size 2`.

## F#: a `Dictionary` written from 8 threads threw "corrupted its state" only after losing most of 1,600,008 entries

*Stdlib and ecosystem gems*

**Did you know**

.NET's `Dictionary` is not safe for concurrent writes, and on .NET 10 it detects some of them: 8 threads writing 200,001 keys each ended with `InvalidOperationException`, whose message says "A concurrent update was performed on this collection and corrupted its state". By then it held 731 entries in one run and 34,743 to 235,597 in others, out of 1,600,008. A `ConcurrentDictionary` given the same writes held all 1,600,008. Measured on .NET 10.0.403.

**Show me**

```fsharp
// SDK 10.0.403 (F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14).
open System.Collections.Concurrent
open System.Collections.Generic
open System.Threading.Tasks

let fn_fill_from_8_threads (write: int -> unit) : string =
    let workers =
        [| for worker_index in 0 .. 7 ->
            Task.Run(fun () -> for call_index in 0 .. 200000 do write (worker_index * 1000000 + call_index)) |]
    try Task.WaitAll workers; "no exception"
    with failure -> failure.InnerException.GetType().Name

let status_map = Dictionary<int, bool>()
let outcome = fn_fill_from_8_threads (fun key -> status_map.[key] <- true)
printfn "Dictionary: %s, Count %d of %d" outcome status_map.Count (8 * 200001)
// Dictionary: InvalidOperationException, Count 731 of 1600008 (34743 to 235597 in other runs)

let safe_map = ConcurrentDictionary<int, bool>()
printfn "ConcurrentDictionary: %s, Count %d" (fn_fill_from_8_threads (fun key -> safe_map.[key] <- true)) safe_map.Count
// ConcurrentDictionary: no exception, Count 1600008
```

**Why it matters**

The exception is a detector, not a guard: it fires after the damage, which is the AT&T order of events ("caused some data to become damaged. The DLN processor was then taken out of service"). F#'s own answer to a shared status map is usually to stop sharing it: a `MailboxProcessor` given 1,000 posts processed them one at a time in a separate run, so the second message waits instead of arriving mid-update. The C++ tip above showed the same window opened by one thread re-entering itself.

**Chew on this**

Which of your F# services share a mutable .NET collection between threads because it looked read-mostly? If that collection threw tomorrow, would the exception tell you which write lost which entry?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.dictionary-2#thread-safety
- https://learn.microsoft.com/en-us/dotnet/api/system.collections.concurrent.concurrentdictionary-2

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0` (Ubuntu 24.04, not Debian), four runs of the `Dictionary` case; every run threw, and the surviving count varied each time.

**Gotchas**

- The count left behind is not stable: 731, 34,743, 45,596 and 235,597 in four runs of the same program, so a test that checks for "some loss" or a particular number is checking luck.
- The documentation leaves concurrent writes to your own synchronization; the exception is a check the runtime happened to make here, so code must not rely on it firing.

## TypeScript: one thread does not mean one update at a time, because every `await` is a window the next message walks into

*Idioms and antipatterns*

**Did you know**

Node runs your code on one thread, but an `async` function gives the event loop back at every `await`, so another call can run in the middle of an update. A status update that pushes a switch, awaits, then increments a count left `size 1 count 0` visible to a second call attempt 1 ms later, inside the 10 ms window. Chaining updates through one promise serializes them: each one finished on a consistent state (`size 1 count 1`, then `size 2 count 2`). Measured on Node 26.13.0.

**Show me**

```ts
// TypeScript, Node 26.13.0 (LTS, strips types natively), tsc 7.0.2 --strict.
const status: { in_service: string[]; count: number } = { in_service: [], count: 0 } // invariant: count === in_service.length
const fn_sleep = (delay_ms: number): Promise<void> => new Promise((resolve) => setTimeout(resolve, delay_ms))

const fn_on_call_attempt = async (switch_name: string): Promise<void> => {
    status.in_service.push(switch_name) // invariant broken...
    await fn_sleep(10)                  // the update window: the event loop runs other work here
    status.count += 1                   // ...restored
}

const first = fn_on_call_attempt("new-york-1")
await fn_sleep(1) // a second call attempt within 1/100 s
console.log(status.in_service.length, status.count) // 1 0: the second arrival sees a half-done update
await Promise.all([first, fn_on_call_attempt("new-york-2")])
console.log(status.in_service.length, status.count) // 2 2
```

**Why it matters**

"JavaScript has no data races" is true of memory and false of invariants: the window between two statements of one async function is as open as AT&T's few seconds. Rust's `RefCell` refuses the second entry and F#'s `MailboxProcessor` queues it, as measured above; TypeScript does neither unless you build the queue.

**Chew on this**

Which of your async handlers update two related pieces of state with an `await` between them? If you moved every such `await` to the end of the handler, which ones could not move?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/await
- https://nodejs.org/en/learn/asynchronous-work/event-loop-timers-and-nexttick

**Verified**

Run on Node 26.13.0, the current LTS (`node:lts-trixie`, Debian), and type-checked with tsc 7.0.2 `--strict` and `@types/node` 26.6.6. The serialized version was run separately with the same timings.

**Gotchas**

- Serializing the updates does not hide the intermediate state from an observer: with the promise-chain queue, a read 1 ms into the first update still saw `size 1 count 0`. The queue protects the next update, not the next reader.
- `Promise.all([first, fn_on_call_attempt(...)])` does not serialize anything: it starts the second update immediately and only waits for both at the end.

# The functional angle: an update that is one value replacing another has no window

Draws on all four tips. Every window above exists because the update is two steps on shared state. The functional form builds the new state as a value and publishes it in one step, so there is no moment when `count` and `in_service` disagree.

```fsharp
// F#: an immutable record and a function that returns the next one.
type LinkStatus = { in_service: string list; count: int }
let fn_with_call_attempt (status: LinkStatus) (switch_name: string) : LinkStatus =
    { in_service = switch_name :: status.in_service; count = status.count + 1 }
let current = fn_with_call_attempt { in_service = []; count = 0 } "new-york"
printfn "%A" current
```

```rust
// Rust: build the next state as a value, then replace the shared one in one assignment under the lock.
use std::sync::{Arc, Mutex};
#[derive(Clone, Debug)]
struct LinkStatus { in_service: Vec<String>, count: usize }
fn with_call_attempt(status: &LinkStatus, switch_name: &str) -> LinkStatus {
    let mut in_service = status.in_service.clone(); // the copy is local until it is complete
    in_service.push(switch_name.to_string());
    LinkStatus { in_service, count: status.count + 1 }
}
fn main() {
    let current = Arc::new(Mutex::new(LinkStatus { in_service: Vec::new(), count: 0 }));
    let next = with_call_attempt(&current.lock().unwrap(), "new-york");
    *current.lock().unwrap() = next; // one assignment: readers see the old value or the new one
    println!("{:?}", current.lock().unwrap());
}
```

```cpp
// C++20: publish an immutable snapshot through std::atomic<std::shared_ptr<T>>.
#include <atomic>
#include <cstdio>
#include <memory>
#include <string>
#include <vector>
struct link_status { std::vector<std::string> in_service; std::size_t count = 0; };
std::atomic<std::shared_ptr<const link_status>> current{std::make_shared<const link_status>()};
std::shared_ptr<const link_status> with_call_attempt(const link_status& status, const std::string& switch_name) {
    link_status next = status;          // a private copy, invisible until published
    next.in_service.push_back(switch_name);
    next.count += 1;
    return std::make_shared<const link_status>(std::move(next));
}
int main() {
    current.store(with_call_attempt(*current.load(), "new-york"));  // one store: readers see old or new
    std::shared_ptr<const link_status> seen = current.load();
    std::printf("size %zu count %zu lock_free %d\n", seen->in_service.size(), seen->count, current.is_lock_free());
}
```

```ts
// TypeScript: build the next state, then replace the reference once.
type LinkStatus = { readonly in_service: readonly string[]; readonly count: number }
let current: LinkStatus = { in_service: [], count: 0 }
const fn_with_call_attempt = (status: LinkStatus, switch_name: string): LinkStatus =>
    ({ in_service: [...status.in_service, switch_name], count: status.count + 1 })
current = fn_with_call_attempt(current, "new-york") // any reader sees the old value or the new one, never half
```

| Language | Two-step update window | Functional form, run here | What it still needs |
| --- | --- | --- | --- |
| F# | open on a shared mutable collection | an immutable record and a function returning the next one: `{ in_service = ["new-york"]; count = 1 }` | one owner, such as a `MailboxProcessor`, that applies updates in order |
| Rust | refused at runtime by `RefCell` or `Mutex` | build the next value, then one assignment under the `Mutex`: `LinkStatus { in_service: ["new-york"], count: 1 }` | the lock around the assignment |
| C++ | open: `recursive_mutex` admits re-entry | `std::atomic<std::shared_ptr<const T>>` store of a private copy: `size 1 count 1` on GCC 16.2 (`is_lock_free()` 0) | a standard library that has it: Apple clang 21 libc++ rejected `std::atomic<std::shared_ptr>` with a static assertion |
| TypeScript | open at every `await` | spread into a new object, assign once | the assignment after the last `await`, not before it |

F# is the baseline here because its default data types are already the functional form; the window opens when F# code shares mutable state, such as a .NET collection, a `ref` cell or a captured `mutable`. All four snippets were run: F# on .NET 10.0.403, Rust on rustc 1.99.1, C++ on GCC 16.2.0, TypeScript on Node 26.13.0.

AT&T's report says the flaw was in all the switches and that the duplicated mate was hit during the same vulnerable period; this part infers that the mate failed the same way because it ran the same code. A pure update function shares that property: two replicas fed the same messages fail identically.

Which of your redundant pairs would survive a bug in the code they share?

# The security angle: the window is where a check and its action disagree

Draws on the TypeScript and C++ tips, with Rust and F# as controls. Runs in both directions: Rust refuses the second entry and F#'s agent queues it; C++ and TypeScript leave the window open by default.

```ts
// TypeScript. Looks like a balance check. The await between check and debit is the window.
const account = { balance_cents: 100 }
const fn_sleep = (delay_ms: number): Promise<void> => new Promise((resolve) => setTimeout(resolve, delay_ms))
const fn_withdraw = async (amount_cents: number): Promise<boolean> => {
    if (account.balance_cents < amount_cents) return false
    await fn_sleep(10)                       // e.g. a fraud-check call
    account.balance_cents -= amount_cents
    return true
}
console.log(await Promise.all([fn_withdraw(100), fn_withdraw(100)]), account.balance_cents) // [ true, true ] -100
```

The class is [CWE-367](https://cwe.mitre.org/data/definitions/367.html), time-of-check time-of-use race condition: both withdrawals passed the check before either debited.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | an `await` between check and act lets a second request pass the same check | nothing: one thread, many interleavings | do the check and the act with no `await` between, or serialize per account |
| C++ | a re-entrant or concurrent path runs between check and act | `std::mutex` blocks other threads, `recursive_mutex` admits re-entry | hold one lock across check and act, without re-entry |
| Rust | the same two-step update | `RefCell` and `Mutex` refuse a second borrow during the first | keep the borrow across check and act |
| F# | the same, on shared mutable state | `MailboxProcessor` applies one message at a time | route both requests through one agent |

TypeScript is the baseline because the window there is created by an ordinary `await`, which code review rarely reads as a concurrency boundary. The [2026-09-24 entry](2026-09-24.md#the-security-angle-adding-concurrency-to-effectall-turns-an-authorization-check-into-a-race-with-the-action-it-guards) met the same check-then-act race through `Effect.all` concurrency. The sample was run on Node 26.13.0.

Which of your handlers check a limit, await something, and then act on the limit they checked?
