**The thesis: a duration has no display format of its own, so every library borrows one, usually a clock's.** A clock face stops at 23:59. A duration does not. The bugs below are where a 25-hour shift, a 90-minute delay or a negative offset is pushed through a format built for a time of day.

## Rust: `std::time::Duration` has no `Display`, prints 25 hours as `90000s`, and `{:.1?}` rounds half to even

*Stdlib and ecosystem gems*

**Did you know**

`std::time::Duration` implements `Debug` and deliberately not `Display`: `println!("{}", duration)` is `error[E0277]`. `Debug` prints the total in the largest unit that keeps it readable as seconds, so 25 hours is `90000s` and 90 minutes is `5400s`. With a precision, `{:.1?}`, it rounds half to even: 1.25 s prints `1.2s` and 1.35 s prints `1.4s`. Rust `jiff`'s `Span` and `SignedDuration` print ISO 8601 (`PT25H`) by default and a friendly form with `{:#}` (`25h`), and a negative friendly duration reads `1h 30m ago`.

**Show me**

```rust
// Rust: std and jiff 0.2.38, rustc 1.95.0
use jiff::{SignedDuration, ToSpan};
use std::time::Duration;

fn main() {
    // std's Duration has Debug and no Display: the only built-in rendering is total seconds.
    println!("{:?}", Duration::from_secs(25 * 3600));   // 90000s
    println!("{:?}", Duration::from_secs(90 * 60));     // 5400s
    // println!("{}", Duration::from_secs(1));          // error[E0277]: `Duration` doesn't implement `std::fmt::Display`

    // Precision on Debug rounds half to even:
    println!("{:.1?} {:.1?}", Duration::from_millis(1250), Duration::from_millis(1350)); // 1.2s 1.4s

    // jiff ships two renderings: ISO 8601 by default, a friendly one with {:#}.
    let span = 25.hours();
    println!("{span} | {span:#}");                       // PT25H | 25h
    let behind = SignedDuration::from_mins(-90);
    println!("{behind} | {behind:#}");                   // -PT1H30M | 1h 30m ago
}
```

**Why it matters**

Logs and metrics in Rust services often print `{:?}` of a `Duration`, because it is the only thing that compiles. That is fine for a request taking `12.3ms`, and unreadable for a job that has been running `90000s`. The rounding is a quieter trap. A latency printed with `{:.1?}` as `1.2s` was 1.25 s, so a threshold check done by reading logs is off by the rounding. C++ and .NET both have an "hh:mm:ss" format, and both of their versions can wrap at 24 hours. Rust's std simply has none.

**Chew on this**

**Sources**

- https://doc.rust-lang.org/std/time/struct.Duration.html (implements `Debug`, not `Display`)
- https://docs.rs/jiff/0.2.38/jiff/struct.Span.html (the `Display` and alternate `{:#}` formats)

**Gotchas**

- 1.05 s prints `1.0s` and 1.15 s prints `1.2s` with `{:.1?}` (measured): half to even, not half away from zero (compare part 6's rounding table).
- `jiff`'s `{:#}` writes a negative `SignedDuration` as `1h 30m ago`, with no minus sign (measured), so it reads as English, not as a number.
- Rust and its crates evolve: this is `jiff` 0.2.38. Balancing `25.hours()` to days needs `days_are_24_hours()` in `SpanRound`, and then it prints `P1DT1H` / `1d 1h` (measured).

## C++: `std::format("{:%T}", 25h)` is `01:00:00` on libc++ and `25:00:00` on libstdc++, and libc++ throws for `hh_mm_ss{25h}`

*Stdlib and ecosystem gems*

**Did you know**

C++20 lets `std::format` print a `duration` with clock specifiers, and the two standard libraries read "hours" differently. With Apple clang 21 (libc++ 22), `{:%T}` of `25h` is **`01:00:00`**: the hours wrap at 24. With GCC 16.2 (libstdc++) it is **`25:00:00`**. `hh_mm_ss` splits a duration into hours, minutes and seconds, so its hours can exceed 23, and formatting `hh_mm_ss{25h}` throws `std::format_error: Formatting a hour needs a valid value` on libc++ while libstdc++ prints `25:00:00`. The plain `{}` agrees on both: `25h`.

**Show me**

```cpp
// C++20: Apple clang 21 (libc++ 22) and GCC 16.2 (libstdc++)
#include <chrono>
#include <cstdio>
#include <format>
#include <string>
using namespace std::chrono;

int main() {
    const auto shift = 25h;
    std::printf("%s\n", std::format("{}", shift).c_str());          // 25h, both libraries
    std::printf("%s\n", std::format("{:%T}", shift).c_str());       // libc++: 01:00:00   libstdc++: 25:00:00
    std::printf("%s\n", std::format("{:%Q %q}", 90min).c_str());    // 90 min: the count and the unit, nothing else

    // hh_mm_ss splits a duration, so its hours() can exceed 23, and the two libraries still disagree:
    try {
        std::printf("%s\n", std::format("{}", hh_mm_ss{shift}).c_str()); // libstdc++: 25:00:00
    } catch (const std::format_error& error) {
        std::printf("format_error: %s\n", error.what());                // libc++: Formatting a hour needs a valid value
    }

    // Portable: format the parts yourself.
    const auto whole_hours = duration_cast<hours>(shift);
    std::printf("%s\n", std::format("{}:{:%M:%S}", whole_hours.count(), shift - whole_hours).c_str()); // 25:00:00
}
```

**Why it matters**

The same source compiled on a Mac and on a Linux CI runner prints different numbers for the same shift length, uptime or SLA breach. One of the two is off by a day, and nothing warns. On libc++ a value that formats fine in tests (under 24 hours) throws in production the first time it exceeds a day. cppreference describes the duration formatter's input as "interpreted as the time of day since midnight", which is libc++'s reading. libstdc++ reads it as elapsed hours. Neither library documents the other's behaviour as wrong, so do not rely on `%H` for anything that can pass 24 hours.

**Chew on this**

Which of your C++ durations can exceed a day, and how are they formatted in logs and UIs? If your binaries are built with both standard libraries, which output do your dashboards parse?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/duration/formatter
- https://en.cppreference.com/w/cpp/chrono/hh_mm_ss

**Verified**

Apple clang 21 on this host and `docker run gcc:16`. MSVC not tested. Whether the standard requires wrapping is not settled here: no LWG issue was found, and cppreference does not say.

**Gotchas**

- `{:%T}` of `-90min` is `-01:30:00` on both libraries (measured): unlike .NET's custom format, the sign survives.
- `{:%j}` of `49h` is `2` on both (measured): for a duration it is a count of whole days, not a day of the year.
- The portable form is to split the hours yourself: `std::format("{}:{:%M:%S}", whole_hours.count(), shift - whole_hours)` printed `25:00:00` on both (measured).

## F#: `TimeSpan.ToString(@"hh\:mm\:ss")` prints 25 hours as `01:00:00`, because `hh` is the `Hours` property, not the total

*Idioms and antipatterns*

**Did you know**

.NET's default `TimeSpan` format is `[-][d.]hh:mm:ss[.fffffff]`, so 25 hours prints as `1.01:00:00`. The custom format everyone writes for "hours and minutes", `@"hh\:mm"`, takes `hh` from the `Hours` property, which is 1 for a 25-hour span (`TotalHours` is 25). So it prints **`01:00`** and the day is silently dropped. A negative span loses its sign too: `-90 min` with `@"hh\:mm"` is `01:30`. And the serializers disagree: System.Text.Json writes `"1.01:00:00"`, `XmlConvert` writes ISO 8601 `P1DT1H`. Measured on FSharp.Core 8.0 / .NET 8.0.8 and FSharp.Core 10.1 / .NET 10.0.13.

**Show me**

```fsharp
// F#: FSharp.Core 8.0 / .NET 8.0.8
open System

let shift = TimeSpan.FromHours 25.0
printfn "%s" (shift.ToString())             // 1.01:00:00: days.hours:minutes:seconds
printfn "%s" (shift.ToString @"hh\:mm\:ss") // 01:00:00: hh is the Hours PROPERTY (1), the day is gone
printfn "%d %g" shift.Hours shift.TotalHours  // 1 25: two different "hours"

// Negative spans lose their sign in a custom format:
let late = TimeSpan.FromMinutes -90.0
printfn "%s | %s" (late.ToString()) (late.ToString @"hh\:mm") // -01:30:00 | 01:30

// Each serializer picks its own wire form:
printfn "%s" (Text.Json.JsonSerializer.Serialize shift)  // "1.01:00:00"
printfn "%s" (Xml.XmlConvert.ToString shift)             // P1DT1H: ISO 8601

// What you probably meant, spelled out:
printfn "%d:%s" (int shift.TotalHours) (shift.ToString @"mm\:ss") // 25:00:00
```

**Why it matters**

`hh\:mm` is the format that passes every test written with a shift of eight hours, and starts reporting a 25-hour outage as one hour on the first real incident. The sign loss is worse: a delay of -90 minutes (early) and +90 minutes (late) print the same `01:30`. Rust has no clock format to misuse. C++ wraps or not depending on the library. JS has the same wrap in its most common shortcut (TypeScript tip). .NET's `TotalHours` exists, but nothing in the format strings uses it.

**Chew on this**

Which of your `TimeSpan` displays use `hh`, and what is the longest span they will ever see? Where a negative span can occur, does anything in the output say so?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/standard/base-types/custom-timespan-format-strings
- https://learn.microsoft.com/en-us/dotnet/standard/base-types/standard-timespan-format-strings

**Gotchas**

- `"g"` gives `1:1:00:00` and `"G"` gives `1:01:00:00.0000000` (measured): the general formats put the days first, with a colon, not a dot.
- `(DateTime.MinValue + span).ToString "HH:mm"` is `01:00` (measured): the "add it to a date and format the time" trick drops the day the same way.
- `String.Format("{0:hh\\:mm}", span)` is `01:00` (measured), so the problem follows the format string into interpolation and logging templates.

## TypeScript: `new Date(ms).toISOString().slice(11, 19)` prints 25 hours as `01:00:00`, and only Node 26 has a real duration formatter

*Stdlib and ecosystem gems*

**Did you know**

The common JS way to turn milliseconds into `hh:mm:ss`, `new Date(ms).toISOString().slice(11, 19)`, treats the duration as a time of day on 1970-01-01, so 25 hours prints **`01:00:00`** on every Node version. Node 26 adds `Intl.DurationFormat`, whose `digital` style prints `25:00:00` and whose `long` style prints `25 hours`, and `Temporal.Duration`, which prints and serializes as ISO 8601 `PT25H`. Node 22 has neither. `Intl.RelativeTimeFormat` formats whatever number you pass: `1.5` days is `in 1.5 days`, and `1` day with `numeric: "auto"` is `tomorrow`. Measured on Node 22.17.1 and 26.12.1.

**Show me**

```ts
// TypeScript 6.0.3 (lib esnext), run on Node 22.17.1 and Node 26.12.1
const twenty_five_hours_ms = 25 * 3600 * 1000

// The classic shortcut: format the duration as if it were a time of day. It wraps at 24 h.
console.log(new Date(twenty_five_hours_ms).toISOString().slice(11, 19)) // 01:00:00, on every Node

// Node 26 has the real tools; Node 22 has neither Intl.DurationFormat nor Temporal.
if (typeof Intl.DurationFormat === "function") {
    console.log(new Intl.DurationFormat("en", { style: "digital" }).format({ hours: 25 })) // 25:00:00
    console.log(new Intl.DurationFormat("en", { style: "long" }).format({ hours: 25 }))    // 25 hours
}
if (typeof Temporal === "object") {
    const shift = Temporal.Duration.from({ hours: 25 })
    console.log(shift.toString(), shift.round({ largestUnit: "day" }).toString()) // PT25H P1DT1H
    console.log(JSON.stringify({ shift }))                                       // {"shift":"PT25H"}
}

// RelativeTimeFormat formats the number you give it; rounding is yours:
const relative = new Intl.RelativeTimeFormat("en", { numeric: "auto" })
console.log(relative.format(1.5, "day"), "|", relative.format(1, "day")) // in 1.5 days | tomorrow
```

**Why it matters**

The `toISOString` trick appears in timers, upload estimates, video players and uptime badges. It is right until the first value over 24 hours, then silently wrong by whole days, which is when the number matters. `Intl.DurationFormat` is the fix on Node 26 and modern browsers, and it is locale-aware (`25 Stunden, 30 Minuten` in German, measured). On Node 22 the only correct option is to divide by hand. .NET and C++ fail the same way with their clock-style formats.

**Chew on this**

Which of your UIs format a duration through a `Date`, and what is the longest duration they display? When you move to `Intl.DurationFormat`, which style and locale should each of them use?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DurationFormat
- https://tc39.es/proposal-temporal/docs/duration.html
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/RelativeTimeFormat

**Verified**

`console` typed with a one-line `declare` instead of `@types/node`. Node 22 on the host, Node 26 in `docker run node:26`.

**Gotchas**

- `typeof Intl.DurationFormat` is `"undefined"` on Node 22.17.1 and `"function"` on Node 26.12.1 (measured), so feature-detect before using it.
- `Temporal.Duration.from({ hours: 25 }).toLocaleString("en")` is `25 hr` (measured), a third spelling next to `25 hours` and `25:00:00`.
- `relative.format(Math.round(36 / 24), "day")` is `in 2 days` (measured): rounding 36 hours to days is your decision, and `Math.round` made it "2".

# The functional angle: formatting is a function from a duration to text, and "hh:mm:ss" is only total for durations under a day

Draws on all four tips. A duration is a number of seconds. A clock format is a function on `[0, 86400)` seconds. Applying the second to the first silently restricts the input to one day, then wraps or throws outside it. The correct functions split the total explicitly:

```text
// Measured: what each library's clock-style format does with 90000 s (25 h)
// C++ libc++ {:%T}           -> 01:00:00   (wraps: value mod 86400)
// C++ libstdc++ {:%T}        -> 25:00:00   (total hours)
// .NET @"hh\:mm\:ss"         -> 01:00:00   (the Hours property, which is value mod 86400 / 3600)
// JS toISOString().slice     -> 01:00:00   (a time of day on 1970-01-01)
// The total function, in any language: hours = total / 3600, minutes = total % 3600 / 60, seconds = total % 60
```

| Language | Total formatter in the standard library | Clock-style formatter | What it costs |
| --- | --- | --- | --- |
| Rust | none (`Debug` only: `90000s`) | none | `jiff`'s `{:#}` (`25h`) or hand-written |
| C++ | `{}` (`25h`), `{:%Q %q}` (`90 min`) | `{:%T}`, library-dependent | pick `{}` or split the hours yourself |
| F# / .NET | `TotalHours` (a number, not a format) | `hh` custom formats wrap and drop the sign | concatenate `int TotalHours` with `mm\:ss` |
| TypeScript | Node 26 `Intl.DurationFormat`, `Temporal` | the `Date` trick | feature-detect, or divide by hand on Node 22 |

No row needs `mut`. The asymmetry: the clock-style formatter is the easy one in every language that has one, and the total one is either missing or a different API.

# The security angle: a wrapped duration is a monitoring blind spot

Draws on the C++ and F# tips (Mode B: the format is fine for display, but is the displayed number used for anything?). The language prevents nothing here.

**Values that wrap in a report (CWE-778, insufficient logging, when the logged value misstates the event; closest class, not a named advisory).** A session that has been open for 25 hours shows as `01:00:00` in a .NET admin page built on `hh\:mm\:ss` (measured), and so does a certificate that expired 25 hours ago if its "time since expiry" uses the same format. An alert rule that parses the formatted log line, rather than the raw number, inherits the wrap:

```fsharp
// F#, illustrative (log and the 24 h rule stand for your own code).
// Looks like "log how long the session has been open". Logs the hours modulo 24.
log (sprintf "session %s open for %s" id (open_for.ToString @"hh\:mm\:ss"))   // 25 h prints as 01:00:00
```

| Language | What goes wrong | What the library does | Still on you |
| --- | --- | --- | --- |
| F# / .NET | `hh` drops whole days and the sign (measured) | documents `hh` as the `Hours` component | log `TotalSeconds` as a number; format only for humans |
| C++ | `%T` wraps on libc++, throws on `hh_mm_ss` (measured) | library-dependent | log `.count()` with a unit; never parse `%T` back |
| TypeScript | the `Date` trick wraps (measured) | nothing | log milliseconds; use `DurationFormat` for display |
| Rust | `90000s` is unambiguous but unfriendly | `Debug` only | nothing hidden: the number is all there |

Rust is the control: its only built-in output is the total, which is ugly and correct. The rule for the others is to keep the machine-readable value a number and to format only at the edge where a person reads it.

# FAQ

**Is there an incident appendix for this part?** No. No public post-mortem blaming a wrapped duration format with first-hand detail was found.

**Why do so many libraries treat a duration as a time of day?** Because the format strings came first. `%H:%M:%S` was designed for `strftime` on a clock reading, and `hh:mm:ss` in .NET's `TimeSpan` mirrors a clock face. ISO 8601 has a real duration format (`PT25H`, `P1DT1H`), and the libraries that implement it, Rust `jiff`, `Temporal` and .NET's `XmlConvert`, print 25 hours without losing a day.
