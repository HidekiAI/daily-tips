# Daily Tips special, part 8 of 15: random numbers, or the one character a random value was missing

<!-- special-nav -->
**Specials:** [<- previous: random numbers, part 7 of 15](2026-11-04-extra-7-of-15.md) | [next: random numbers, part 9 of 15 ->](2026-11-04-extra-9-of-15.md)

Not part of the rotation. Part 7 copied a generator and got repeated numbers. This part is about random values used as names and one-time values: identifiers, nonces, challenge tokens. Two things go wrong with them. They repeat sooner than people expect, because of the birthday arithmetic. And a value that was random enough can still be used in a form that breaks the rule it was supposed to satisfy.

# What happened

**Bug class:** a correct random value placed in an incorrect form. The generator was not at fault. It was a missing prefix on a value that proves control of a domain (CWE-345, insufficient verification of data authenticity; a compliance defect before it was an exploit).

**The story, in plain words:**

A certificate authority only issues a certificate for `example.com` to someone who controls `example.com`. One way to prove control is to ask the applicant to put a secret random value into the domain's DNS records, and then look. DigiCert, one of the largest authorities, offered several such methods. In one of them the applicant creates a CNAME record whose host name is the random value itself.

The industry rules for that method say the random value must not be the bare name of a host. It has to start with an underscore: `_abc123` and not `abc123`. The reason is spelled out in the bug thread by an outside engineer: services that let users create records at arbitrary subdomains, dynamic DNS for instance, can refuse any name that starts with an underscore and so can never be tricked into helping someone pass the check. A name without the underscore is a name a stranger might legitimately register.

DigiCert's code, in one validation path, did not add the underscore. The random value was fine. A DigiCert statement quoted in the bug thread says the value had "at least 150 bits of entropy", and about 83,000 certificates had been issued through the path. The missing character was one `_`.

Nobody noticed for a long time, and then the fix happened by accident. On 6 June 2024 DigiCert's engineers merged several services that generated random values into one that always put an underscore in front, "whether they require one or not". The old bug disappeared. On 3 July a researcher wrote to DigiCert asking whether certificates validated without the underscore needed to be revoked. DigiCert's own timeline says the question was read as being about documentation, and the answers went on for weeks. On 27 July a code review of the old version found the path. On 29 July DigiCert filed the report.

Under the rules governing public certificates, a certificate validated incorrectly has to be revoked within 24 hours. DigiCert had 83,267 of them, belonging to 6,807 customers, and DigiCert's update says many customers could not reissue in time. It took five days: all 83,267 were revoked by 3 August. A further 1,308 S/MIME certificates were found affected and scheduled for 9 August.

The quotes, from Mozilla's Bugzilla, bug 1910322 (DigiCert, filed 29 July 2024) and bug 1910805 (the delayed-revocation report):

- "The code review found one path where a certificate could issue when the random value was used as the host in a CNAME resource record without first pre-appending an underscore." (DigiCert, 1910322)
- "This service began including an underscore prefix before each random value, regardless of which validation method the user chose." (DigiCert, 1910322)
- "The root causes were siloing between engineering and compliance, a failure to take CPRs seriously if they did not include serial numbers, and a lack of engineering rigor." (DigiCert's incident report; CPR is a certificate problem report)
- "Although the chance of a collision is extremely low because the random value has at least 150 bits of entropy, there is still a chance." (DigiCert's stated rationale, quoted in the thread)
- "DigiCert revoked 83,267 certificates in 5 days, instead of 24 hours as required by the current Baseline Requirements." (a summary in 1910805)

The measurements below are about the other half: how fast random identifiers collide, in four languages.

## Rust: 32-bit random ids repeat after about 83,571 draws on average, and that is the formula, not bad luck

*Stdlib and ecosystem gems*

**Did you know**

Draw random ids from a space of 2^n values and the first repeat arrives after about the square root of (pi/2 times 2^n) draws. Measured over 400 trials each in Rust 1.99.1: 20-bit ids repeated after 1,259 draws on average (formula 1,283), 24-bit ids after 5,117 (formula 5,134) and 32-bit ids after 83,571 (formula 82,137). A 32-bit id looks like a four-billion-value space and is a repeat every 80 thousand draws.

**Show me**

```rust
// rand 0.9.5, rustc 1.99.1, release build
use rand::Rng;
use std::collections::HashSet;

fn fn_draws_until_first_repeat(id_bits: u32) -> u64 {
    let mut mut_rng = rand::rng();
    let id_mask: u64 = (1u64 << id_bits) - 1;
    let mut mut_seen: HashSet<u64> = HashSet::new();
    let mut mut_draw_count: u64 = 0;
    loop {
        mut_draw_count += 1;
        if !mut_seen.insert(mut_rng.random::<u64>() & id_mask) {
            return mut_draw_count;
        }
    }
}

fn main() {
    const TRIAL_COUNT: u64 = 400;
    for id_bits in [20u32, 24, 32] {
        let total: u64 = (0..TRIAL_COUNT).map(|_| fn_draws_until_first_repeat(id_bits)).sum();
        let measured_mean: f64 = total as f64 / TRIAL_COUNT as f64;
        let expected_mean: f64 = (std::f64::consts::PI / 2.0 * (1u64 << id_bits) as f64).sqrt();
        println!("{} bit ids: mean draws until the first repeat {:.0}, formula sqrt(pi/2 * 2^bits) {:.0}", id_bits, measured_mean, expected_mean);
    }
}
```

Output (one run): `20 bit ids: mean draws until the first repeat 1259, formula sqrt(pi/2 * 2^bits) 1283`, then `24 bit ids: ... 5117 ... 5134`, then `32 bit ids: ... 83571 ... 82137`. The measured means move by a few percent between runs (a second run: 1,333, 4,964 and 81,680).

**Why it matters**

A random identifier needs a bit width chosen for the number of ids it will ever make, not for the size of the space it sits in. The square-root rule says a space of 2^n is safe for roughly 2^(n/2) draws, and much less for a collision probability you can live with. 128 bits give a trillion trillion draws before the first repeat; 32 bits give a hundred thousand.

**Chew on this**

For each random id your service makes, how many will it ever make, and how many bits does it have? Which of them is only as wide as someone could remember?

**Sources**

- https://en.wikipedia.org/wiki/Birthday_problem (the approximation)
- https://cwe.mitre.org/data/definitions/330.html

**Verified**

rustc 1.99.1, rand 0.9.5, release build, 400 trials per width, one run. The formula is the standard birthday approximation; the measurements agreed with it within about 4 percent in two runs.

**Gotchas**

- Ids truncated to `id_bits` from a 64-bit draw are uniform, so the measurement is of the arithmetic and not of the generator.
- A collision is a repeat of any two, not of one particular id, which is why the number is the square root.

## C++: the birthday probability `1 - exp(-x)` prints `0` for 96-bit and 128-bit ids, and `-expm1(-x)` prints the true `6.9e-18` and `1.6e-27`

*Idioms and antipatterns*

**Did you know**

The probability of at least one repeat among n random values from a space of N is about 1 - exp(-n^2 / 2N). Computing it that way in double precision gives exactly `0` when the answer is smaller than about 1e-16, because `exp(-tiny)` rounds to 1 and `1 - 1` is 0. For a million draws over a 96-bit space the naive formula printed `0` and `std::expm1` printed `6.93889e-18`; over a 128-bit space `0` against `1.61559e-27`. This is the same family as part 2's float rounding: a correct input, a correct formula, a wrong answer from the representation.

**Show me**

```cpp
// g++ -std=c++23 -O2 birthday.cpp   (and clang++ -std=c++23 -stdlib=libc++ -O2 birthday.cpp)
#include <cmath>
#include <cstdio>
#include <initializer_list>

// chance of at least one repeat among draw_count random values from 2^id_bits possibilities
double fn_naive(double draw_count, double id_bits) {
    return 1.0 - std::exp(-draw_count * draw_count / (2.0 * std::exp2(id_bits)));
}
double fn_stable(double draw_count, double id_bits) {
    return -std::expm1(-draw_count * draw_count / (2.0 * std::exp2(id_bits)));
}

int main() {
    std::printf("%-26s %-14s %-14s\n", "draws, id bits", "1 - exp(-x)", "-expm1(-x)");
    for (double id_bits : {32.0, 64.0, 96.0, 128.0}) {
        const double draw_count = std::exp2(20.0); // a million draws
        std::printf("2^20 draws, %3.0f bit ids    %-14.6g %-14.6g\n", id_bits, fn_naive(draw_count, id_bits), fn_stable(draw_count, id_bits));
    }
}
```

Output (identical on GCC 16.2 and libc++): 32 bits `1` and `1`; 64 bits `2.98023e-08` and `2.98023e-08`; 96 bits `0` and `6.93889e-18`; 128 bits `0` and `1.61559e-27`. (On GCC 16.2 the `<initializer_list>` include is required for the braced list; the first draft of this probe failed to compile without it.)

**Why it matters**

A capacity plan that prints `0` for a collision risk is not evidence of safety, it is evidence that the computation ran out of digits. The numbers matter in the small cases: the usual advice on random nonces (a width, and a limit on messages per key) comes from this arithmetic, which I did not check against a standard here, and the decision to accept a risk of 2^-32 or 2^-60 is only possible if the number can be printed.

**Chew on this**

Where in your capacity or risk calculations does a probability get rounded to zero? Would you have noticed that the zero was an artifact?

**Sources**

- https://en.cppreference.com/w/cpp/numeric/math/expm1
- https://en.wikipedia.org/wiki/Birthday_problem

**Verified**

GCC 16.2.0 and Debian clang 19.1.7 with libc++, `-O2`. The nonce advice in "Why it matters" is general knowledge and is not checked here; do not rely on it from this entry.

**Gotchas**

- The formula is an approximation that is accurate when n is far below the square root of N.
- `long double` would postpone the zero, not remove it.

## F#: `Guid.NewGuid()` is version 4 with 122 random bits, `Guid.CreateVersion7()` starts with a millisecond timestamp, and a million v7 ids shared 277 timestamp prefixes

*Stdlib and ecosystem gems*

**Did you know**

.NET 9 added `Guid.CreateVersion7()`. Its output starts with a 48-bit Unix millisecond timestamp, which makes v7 ids sort by creation time and also means that ids created in the same millisecond share their first 12 hex digits. On .NET 10, a million `CreateVersion7()` calls fell into 277 distinct millisecond prefixes, all one million ids were distinct, and the version nibble printed `7` where `NewGuid()` printed `4`. A v7 id has fewer random bits than a v4: the UUID specification (RFC 9562) gives 74, against 122 for version 4. That is plenty against the birthday bound within a millisecond, and the timestamp is visible to anyone who sees the id.

**Show me**

```fsharp
// .NET 10.0.14, dotnet fsi
open System

let fn_version_nibble (identifier: Guid) : char = (identifier.ToString("N")).[12]
let first_v4: Guid = Guid.NewGuid()
let first_v7: Guid = Guid.CreateVersion7()
printfn "NewGuid()         %O version nibble %c" first_v4 (fn_version_nibble first_v4)
printfn "CreateVersion7()  %O version nibble %c" first_v7 (fn_version_nibble first_v7)

let batch: Guid[] = Array.init 1000000 (fun _ -> Guid.CreateVersion7())
let distinct_time_prefixes: int = batch |> Array.map (fun identifier -> identifier.ToString("N").Substring(0, 12)) |> Array.distinct |> Array.length
printfn "1,000,000 v7 ids: %d distinct 48-bit timestamp prefixes, %d distinct ids" distinct_time_prefixes (Array.distinct batch).Length
```

Output (one run): `NewGuid()         aa602fd0-f998-4b06-9f80-ff234bb69637 version nibble 4`, `CreateVersion7()  01a1a873-8fef-7a2f-a221-1b00619fac19 version nibble 7`, `1,000,000 v7 ids: 277 distinct 48-bit timestamp prefixes, 1000000 distinct ids`. The ids and the 277 change every run.

**Why it matters**

An id's fields tell you what an attacker can predict. A v7 id leaks when it was made, to the millisecond, and 74 random bits are still far beyond the Rust tip's thresholds. A v4 id for an access token is 122 bits drawn from the platform's generator (per the documentation: `Guid.NewGuid` uses the operating system's secure source, which I did not verify). Choosing v7 for database locality is a sound trade, and choosing it for an unguessable token is the mistake.

**Chew on this**

Which of your ids are used as secrets, and which as keys? Does either one reveal when it was created?

**Sources**

- https://www.rfc-editor.org/rfc/rfc9562
- https://learn.microsoft.com/en-us/dotnet/api/system.guid.createversion7

**Verified**

.NET SDK 10.0 image (Ubuntu), `dotnet fsi`, one run. The 74 and 122 bit counts are RFC 9562's layout, which I did not recount from the bytes here; the version nibbles and the timestamp prefixes are measured.

**Gotchas**

- The 277 depends on how fast the machine generates ids; a faster machine puts more ids in each millisecond.
- v7 ids created in the same millisecond are ordered by the random bits (or by a counter, if the implementation uses one); I did not check which .NET does.

## TypeScript: eight base-36 characters from `Math.random().toString(36)` repeat after 2,111,863 ids on average, which is the 41-bit birthday bound

*Idioms and antipatterns*

**Did you know**

The common snippet `Math.random().toString(36).slice(2, 10)` makes an eight-character base-36 id: 36^8 is about 2.8 trillion values, about 41 bits. The first repeat is expected after sqrt(pi/2 times 36^8), 2,105,086 ids. Twenty trials on Node 26.13 averaged 2,111,863 in one run and 2,381,527 in another (20 trials are noisy). At a million new ids per day the id repeats within a couple of days, and the second million is the dangerous one.

**Show me**

```ts
// Node 26.13.0: save as ids.mts, run with node ids.mts
const const_trial_count: number = 20
const const_fn_draws_until_repeat = (fn_make_id: () => string): number => {
    const seen_ids: Set<string> = new Set()
    for (let draw_count: number = 1; ; draw_count++) {
        const new_id: string = fn_make_id()
        if (seen_ids.has(new_id)) return draw_count
        seen_ids.add(new_id)
    }
}
const const_fn_mean = (fn_make_id: () => string): number =>
    Array.from({ length: const_trial_count }, () => const_fn_draws_until_repeat(fn_make_id)).reduce((sum, draws) => sum + draws, 0) / const_trial_count

const const_base36_chars: number = 8
const const_space: number = 36 ** const_base36_chars
console.log("8 base-36 chars from Math.random: mean draws until first repeat",
    Math.round(const_fn_mean(() => Math.random().toString(36).slice(2, 2 + const_base36_chars))),
    " formula", Math.round(Math.sqrt(Math.PI / 2 * const_space)))
```

Output (one run): `8 base-36 chars from Math.random: mean draws until first repeat 2111863  formula 2105086`.

**Why it matters**

The same arithmetic as the Rust tip, with a different generator and a width nobody chose on purpose: eight characters was a style decision. `crypto.randomUUID()` gives 122 random bits and would take about 2^61 draws to repeat (arithmetic from 122 bits, not measured). The id also comes from `Math.random`, which V8's own blog says is "still not cryptographically secure", so shortness is not the only problem.

**Chew on this**

Where does your code build an id by slicing a random string? Who chose the length?

**Sources**

- https://nodejs.org/api/crypto.html#cryptorandomuuidoptions
- https://en.wikipedia.org/wiki/Birthday_problem

**Verified**

Node v26.13.0 in the `node:lts` image, 20 trials, one run. The formula is the standard approximation. The claim about `crypto.randomUUID()` is arithmetic from 122 bits, not a measurement.

**Gotchas**

- 20 trials make the mean noisy: the two runs were 0.3 percent and 13 percent from the formula.
- `Math.random().toString(36)` can return fewer than ten characters after `slice(2)`; the probe slices exactly eight and the mean assumes all eight are present.

# The functional angle: an identifier is a value in a type, and its width is the type's job

Draws on all four tips. The DigiCert failure was a value of the right content in the wrong format; the birthday failures are a value of the right format in too small a space. A type can carry both facts: the prefix rule and the bit width.

```rust
// Rust: make "has the required prefix" and "is wide enough" unrepresentable to get wrong
pub struct DomainValidationToken(String); // always starts with '_', always 150+ bits of randomness behind it
impl DomainValidationToken {
    pub fn new(random_bytes: [u8; 24]) -> Self {
        let hex_digits: String = random_bytes.iter().map(|byte| format!("{:02x}", byte)).collect();
        DomainValidationToken(format!("_{}", hex_digits))
    }
    pub fn as_host_label(&self) -> &str { &self.0 }
}
```

This sample compiled and ran; it is a sketch of the type, not DigiCert's design. 24 bytes is 192 bits.

| Language | How a type could carry the rule | What it cannot say |
| --- | --- | --- |
| Rust | a newtype with a private constructor (above) | that the 24 bytes were random |
| C++ | a class with a private constructor | the same |
| F# | a single-case union with a private constructor | the same |
| TypeScript | a branded string type | the brand is erased at runtime |

F# is the baseline because a single-case union with a private constructor is the idiom its programmers reach for first. The question for all four rows is the same: who is allowed to build the value, and does the constructor check the prefix?

# The security angle: a nonce that repeats is a key that leaks

Draws on all four tips and Appendix A. Mode B (what the language does not prevent). Bug classes: CWE-323 (Reusing a Nonce, Key Pair in Encryption), CWE-330 and CWE-345.

```fsharp
// F#: a 96-bit random nonce is safe for about 2^32 messages under one key, by the birthday bound, and not beyond
let random_nonce: byte[] = System.Security.Cryptography.RandomNumberGenerator.GetBytes(12)
```

The DigiCert story shows the compliance side: the cost of a form error is revocation of everything issued through it, on a clock the rules set. Appendix A shows the cryptographic side: one repeated value reveals a private key.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | 32-bit ids repeat after 83,571 draws (measured) | nothing | choose widths by the birthday bound |
| C++ | collision risk printed as `0` (measured) | `expm1` exists | use it, and keep the unrounded number |
| F# | v7 ids reveal creation time (measured prefixes) | `NewGuid()` is v4 | do not use v7 as a secret |
| TypeScript | 41-bit ids repeat after about 2.1 million (measured) | `crypto.randomUUID()` exists | never build ids from `Math.random` |

TypeScript is the baseline because the snippet that makes the shortest id is the one people copy. What does your id generator's documentation promise about uniqueness, and who checked?

# FAQ

**Was DigiCert's random value weak?**
DigiCert says it had at least 150 bits of entropy. The defect was that it was used as a bare host name; the underscore is a naming convention that lets other services refuse it.

**Why 5 days and not 24 hours?**
DigiCert's delayed-revocation report and the discussion in the bug explain the customers' constraints; I did not verify those claims beyond the summary quoted above.

**Is the birthday formula exact?**
No, it is an approximation that is accurate for n much smaller than N, as the three rows of the Rust output show.

# Appendix A: Two signatures with one secret value hand over a private key (the 2010 console talk)

At the 27th Chaos Communication Congress in December 2010, the group fail0verflow (the slides name bushing, marcan, segher and sven) presented "Console Hacking 2010". Two slides state the cryptographic fact in four lines. Their ECDSA slide lists the public values and the private ones: "m = random", "k = private key". The next slide says: "It is imperative to have a random m for every signature: from a pair of signatures that use the same m, we can compute m and k." The following slide shows the algebra: with "R = (mG)x" and "S = (e + kR) / m", two signatures with the same m share R, so subtracting the two S values gives m and then the private key. A later slide, titled "Sony's ECDSA code", shows the vendor's implementation as an image that I could not read as text, so I cannot quote what it did. The widely repeated summary is that the value did not change; I did not verify that here. The part this entry rests on is the algebra, which the slides state plainly.

The relation to this part is the DigiCert lesson read backward. A random value is a promise about every use, not about one. A 150-bit value in the wrong form broke a rule; the same bits used twice break a key.

# Appendix B: Venona, or about 35,000 pages of one-time pad that were printed twice

The one-time pad is the one cipher that is unbreakable if the key is random and used once. The Soviet pads that the American program VENONA later read were neither. NSA's overview of the program (read through a public copy of its Freedom of Information Act release, because the NSA's own address refused me) says the messages "were encrypted using a complicated code that was then superenciphered by adding a numeric key stream from a one-time pad to the code", and that "properly used, a one-time pad is virtually unbreakable". Then it gives the mistake: the pad factory "produced about 35,000 pages of duplicate key as a result of pressures brought by the German advance on Moscow during World War II". "The duplicate pages were sent to distant entities in an attempt to lessen the impact of this weakness."

A repeated page is a repeated nonce (Appendix A of this part states the same rule for signatures): two messages enciphered with the same key pages can be combined to cancel the key. The overview adds that, although the Army "had been collecting VENONA messages since 1939, there was no serious effort against the traffic until 1 February 1943."

Quotes (NSA, "VENONA: An Overview"): "properly used, a one-time pad is virtually unbreakable." and "pads produced about 35,000 pages of duplicate key as a result of pressures brought by the German advance on Moscow during World War II." Source: https://documents.theblackvault.com/documents/nsa/cryptoalmanac/VENONA_An_Overview.pdf (read; the NSA's own URL returned 403 twice).

# Appendix C: Lorenz "Tunny", a retransmitted message that gave away 3,976 characters of key

On 30 August 1941, according to John Tiltman's own account, "two very long messages were intercepted from Vienna to Athens with the same indicator HQIBPEXEZMUG." One had 3,976 symbols of ciphertext and the other was about 500 symbols longer. Two messages with the same indicator were enciphered with the same key, so adding them cancelled it. The plaintext proved to be a report for the German military attache in Athens, and the sending operator had made mistakes that needed "long stretches of corrections and repetitions" (Tiltman's phrase), which is what a hurried resend looks like.

Tiltman wrote: "In the course of the next ten days or so I succeeded in carrying recovery to the end of the shorter of the two messages, thereby recovering 3976 consecutive symbols of key." That run of key, with no machine in sight, was the raw material from which the structure of the Lorenz cipher was worked out. Why the message was sent twice (a garbled first reception, in the usual telling) is not something I could read cleanly in the two-column scan, so I do not claim it.

Source: John Tiltman, "The Tunny Machine and Its Solution" (1960), https://www.cryptocellar.org/Lorenz/Tunny_Machine_Tiltman.pdf (read).
