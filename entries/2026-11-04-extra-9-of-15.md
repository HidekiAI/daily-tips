# Daily Tips special, part 9 of 15: random numbers, or a board that was random in the way a clock is random

<!-- special-nav -->
**Specials:** [<- previous: random numbers, part 8 of 15](2026-11-04-extra-8-of-15.md) | [next: random numbers, part 10 of 15 ->](2026-11-04-extra-10-of-15.md)

Not part of the rotation. Parts 1 to 8 asked whether the generator, its seed, its copies and its ids were handled correctly. This part asks something older: is the generator itself random in any way a person can notice? Some generators pass the simple test (the numbers look scattered) and fail the next one (a pattern appears when you look at them in pairs, triples, or bit by bit). A pattern is a gift to anyone who finds it.

# What happened

**Bug class:** a "random" sequence that is a small fixed set of patterns, noticed by an observer with a recorder and patience (CWE-330, insufficient randomness; found by observation, not by attack code).

**The story, in plain words:**

In 1983 CBS began airing Press Your Luck, a game show whose centerpiece was a "Big Board" of 18 lit squares. The squares flashed in what looked like a random order, and a contestant pressed a button to stop the lights. Each square hid a prize, a sum of money, an extra spin, or a cartoon creature called the Whammy that took away everything you had won.

Michael Larson, an unemployed ice cream truck driver from Ohio, saw it in November 1983, bought a video recorder, and watched the board frame by frame. According to Wikipedia's account, which I read but did not check against its sources, he found that the lights followed only five fixed patterns, not a random sequence, and that two squares, the fourth and the eighth, always held cash and an extra spin. He practised with the pause button for months, flew to Los Angeles and auditioned.

On 19 May 1984 he played. His first spin landed on a Whammy, which he used to calibrate his timing. Then he went 45 spins in a row without another one, and the game ran so long that CBS split the broadcast over 8 and 11 June. He left with $110,237. The network suspected him of cheating, went through the footage, found nothing that broke a rule, and mailed him the check. The board was then reprogrammed with more patterns: 27 more according to the scandal article, "over 30" according to the show article.

The show's designers had made a board that looked random and was a clock. No code was broken. Someone watched long enough to see the cycle.

The quotes, from Wikipedia's "Press Your Luck" and "Press Your Luck scandal" articles (secondary sources, read, not checked against their references):

- "By recording episodes at home on a videocassette recorder and playing them back frame-by-frame, Larson discovered that the presumed random patterns of the game board were not actually random and he was able to memorize the sequences."
- "...discovered that its ostensibly randomized game board was actually only five different patterns of lights."
- "Network executives pored over the footage but found no evidence of malfeasance."

The measurements below find the same kind of structure in four generators that were all used for real: a game's, a famous 1960s one, the C library's textbook one, and a JavaScript snippet.

## Rust: Super Mario 64's `random_u16` visits 65,114 of the 65,536 possible values and then repeats, and 422 values can never come out

*Type system deep cuts*

**Did you know**

The decompilation project `n64decomp/sm64` contains the game's `random_u16` in `src/engine/behavior_script.c`: a 16-bit state, a swap of its two bytes, some shifts and xors, and a special case for the value 22026. Ported to Rust and started from seed 0, it produced 65,114 distinct outputs and then repeated an earlier one (57,460) on call 65,115. So 422 of the 65,536 possible 16-bit values never came out on that walk, and a loop that waits for one of those 422 values, starting from seed 0, waits forever.

**Show me**

```rust
// rustc 1.99.1, std only: a port of random_u16 from n64decomp/sm64 src/engine/behavior_script.c
fn fn_random_u16(mut_seed: &mut u16) -> u16 {
    if *mut_seed == 22026 {
        *mut_seed = 0;
    }
    let mut mixed: u16 = (*mut_seed & 0x00FF) << 8;
    mixed ^= *mut_seed;
    *mut_seed = ((mixed & 0x00FF) << 8).wrapping_add((mixed & 0xFF00) >> 8);
    mixed = ((mixed & 0x00FF) << 1) ^ *mut_seed;
    let shifted: u16 = (mixed >> 1) ^ 0xFF80;
    if mixed & 1 == 0 {
        *mut_seed = if shifted == 43605 { 0 } else { shifted ^ 0x1FF4 };
    } else {
        *mut_seed = shifted ^ 0x8180;
    }
    *mut_seed
}

fn main() {
    let mut mut_seed: u16 = 0;
    let mut mut_visited: Vec<bool> = vec![false; 65536];
    let mut mut_step_count: u32 = 0;
    loop {
        let generated_output: u16 = fn_random_u16(&mut mut_seed);
        mut_step_count += 1;
        if mut_visited[generated_output as usize] {
            println!("first repeated output {} after {} calls", generated_output, mut_step_count);
            break;
        }
        mut_visited[generated_output as usize] = true;
    }
    println!("distinct outputs reached from seed 0: {} of 65536", mut_visited.iter().filter(|visited| **visited).count());
    let unreachable_values: u32 = mut_visited.iter().filter(|visited| !**visited).count() as u32;
    println!("values never produced: {}", unreachable_values);
}
```

Output: `first repeated output 57460 after 65115 calls`, `distinct outputs reached from seed 0: 65114 of 65536`, `values never produced: 422`.

**Why it matters**

A 16-bit state can have at most 65,536 outputs, and a good 16-bit generator would cycle through all of them. This one cycles through 65,114. The loss is small and measurable, and a full-cycle 16-bit state is the most such a generator can offer. The port is mine; I did not compare it with the game's behavior.

**Chew on this**

How big is the state of each generator in your game, test or simulation, and how long is its cycle? Does any code branch on a value that cannot occur?

**Sources**

- https://github.com/n64decomp/sm64/blob/master/src/engine/behavior_script.c (`random_u16`, read)
- https://doc.rust-lang.org/std/primitive.u16.html#method.wrapping_add

**Verified**

rustc 1.99.1, std only, release build. The Rust port is a transcription of the C in the repository, not run against the game. That the original returns the same sequence relies on my port being faithful, which I checked by reading, not by a test vector.

**Gotchas**

- In Rust `<<` on a `u16` drops the high bits without a panic (only the shift amount is checked), which matches the C code storing into `u16` variables.
- The decompilation is a community project and not an official source; it is a primary source for the code, not for the game's documentation.

## C++: the 65539 multiplier makes every consecutive triple satisfy `x3 = 6*x2 - 9*x1 (mod 2^31)`, so ten million triples fell on exactly 15 planes

*Idioms and antipatterns*

**Did you know**

A linear congruential generator with multiplier 65539 and modulus 2^31 (commonly called RANDU; I did not source that name) has `65539 = 2^16 + 3`, so squaring the multiplier gives `65539^2 = 2^32 + 6 * 65539 - 9`, and modulo 2^31 that is `6 * 65539 - 9`. Every output therefore equals `6 * previous - 9 * the one before`, modulo 2^31. Over 10,000,000 consecutive triples that relation failed 0 times, and the integer `(x3 - 6*x2 + 9*x1) / 2^31` took exactly 15 distinct values, from -5 to 9. Plot the triples as points in a cube and they lie on 15 parallel planes. George Marsaglia's 1968 paper in the Proceedings of the National Academy of Sciences is titled "Random numbers fall mainly in the planes".

**Show me**

```cpp
// g++ -std=c++23 -O2 randu.cpp   (and clang++ -std=c++23 -stdlib=libc++ -O2 randu.cpp)
#include <cstdint>
#include <cstdio>
#include <set>

int main() {
    constexpr std::uint64_t MODULUS = 1ULL << 31;
    constexpr std::uint64_t TRIPLE_COUNT = 10000000;
    std::uint64_t first = 1; // x(n+1) = 65539 * x(n) mod 2^31, seeded with an odd number
    std::uint64_t second = (65539 * first) % MODULUS;
    std::uint64_t violations = 0;
    std::set<std::int64_t> plane_numbers;
    for (std::uint64_t triple_index = 0; triple_index < TRIPLE_COUNT; ++triple_index) {
        const std::uint64_t third = (65539 * second) % MODULUS;
        // 65539 = 2^16 + 3, so 65539^2 = 6 * 65539 - 9 (mod 2^31): third = 6 * second - 9 * first (mod 2^31)
        const std::int64_t combination = static_cast<std::int64_t>(third) - 6 * static_cast<std::int64_t>(second) + 9 * static_cast<std::int64_t>(first);
        if (combination % static_cast<std::int64_t>(MODULUS) != 0) ++violations;
        plane_numbers.insert(combination / static_cast<std::int64_t>(MODULUS)); // which plane of the unit cube this triple is on
        first = second;
        second = third;
    }
    std::printf("triples checked: %llu, breaking x3 = 6*x2 - 9*x1 (mod 2^31): %llu\n", static_cast<unsigned long long>(TRIPLE_COUNT), static_cast<unsigned long long>(violations));
    std::printf("distinct planes visited by (x1, x2, x3)/2^31: %zu (lowest %lld, highest %lld)\n", plane_numbers.size(),
                static_cast<long long>(*plane_numbers.begin()), static_cast<long long>(*plane_numbers.rbegin()));
}
```

Output (identical on GCC 16.2 and libc++): `triples checked: 10000000, breaking x3 = 6*x2 - 9*x1 (mod 2^31): 0` and `distinct planes visited by (x1, x2, x3)/2^31: 15 (lowest -5, highest 9)`.

**Why it matters**

A generator whose single values look uniform can have all of its pairs, triples or quadruples in a lattice, and any simulation that uses three consecutive values as a point in space (a random direction, a random color, a random position) samples only the lattice. The check is exact and cheap: a linear relation between consecutive outputs is a proof, and no statistical test is needed. Part 1's `mt19937` and the standard library's `minstd_rand` are different generators and I did not test them for this.

**Chew on this**

Which of your code draws two or three consecutive values and treats them as coordinates? If the generator was a linear congruential one, what would it say about the points?

**Sources**

- https://pubmed.ncbi.nlm.nih.gov/16591687/ (Marsaglia, PNAS 61:25, 1968: the title and record; I could not retrieve the paper's text)
- https://eel.is/c++draft/rand.predef (the standard's own `minstd_rand0` and `minstd_rand`)

**Verified**

GCC 16.2.0 and clang 19.1.7 with libc++, `-O2`. The relation and the 15 planes are exact computations on this recurrence. I did not read Marsaglia's paper, only its record, so I attribute to it only its title.

**Gotchas**

- The seed 1 is arbitrary; any odd seed gives the same relation and the same set of planes.
- The 15 is a bound from the integer range of `u3 - 6*u2 + 9*u1`; the measurement shows all 15 occur.

## F#: the ANSI C sample generator's lowest k bits repeat with period exactly 2^k, so `rand() % 2` alternates and `rand() % 256` has period 256

*Idioms and antipatterns*

**Did you know**

The linear congruential generator `x = 1103515245 * x + 12345 (mod 2^31)` is the example generator in the ANSI C standard's discussion of `rand`. Its modulus is a power of two, so its lowest k bits depend only on the previous lowest k bits, and they cycle with period at most 2^k. On .NET 10 the measured period of the lowest 1 through 8 bits was exactly 2, 4, 8, 16, 32, 64, 128 and 256. `x % 2` is `0, 1, 0, 1, ...` and `x % 256` repeats every 256 calls.

**Show me**

```fsharp
// .NET 10.0.14, dotnet fsi
// the ANSI C sample generator: x(n+1) = 1103515245 * x(n) + 12345 (mod 2^31)
let fn_next (state: uint64) : uint64 = (1103515245UL * state + 12345UL) % (1UL <<< 31)
let fn_period_of_low_bits (bit_count: int) : int =
    let mask: uint64 = (1UL <<< bit_count) - 1UL
    let start: uint64 = 12345UL
    let mutable mut_state: uint64 = fn_next start
    let mutable mut_period: int = 1
    while (mut_state &&& mask) <> (start &&& mask) || (fn_next mut_state &&& mask) <> (fn_next start &&& mask) do
        mut_state <- fn_next mut_state
        mut_period <- mut_period + 1
    mut_period
for bit_count in 1 .. 8 do
    printfn "lowest %d bit(s) repeat with period %d (2^%d)" bit_count (fn_period_of_low_bits bit_count) bit_count
```

Output: eight lines, `lowest 1 bit(s) repeat with period 2 (2^1)` up to `lowest 8 bit(s) repeat with period 256 (2^8)`.

**Why it matters**

The classic bug is `rand() % 6` on a power-of-two-modulus generator: the low bits are the weakest ones, so a die made from them is not a die. That is why generators of this family were advised to be used through their high bits, and why part 2's `%` was bad twice. The measurement is of the textbook constants; a given C library's `rand` may differ, and I did not test one.

**Chew on this**

Which of your random integers come from the low bits of a generator? How would you know if the generator's modulus was a power of two?

**Sources**

- https://en.wikipedia.org/wiki/Linear_congruential_generator (the low-bit property of power-of-two moduli)

**Verified**

.NET SDK 10.0, `dotnet fsi`. The constants are the ones I remember from the sample implementation in the C standard; I did not check them against the standard text, so the claim is about these constants, not about the standard.

**Gotchas**

- `fn_period_of_low_bits` checks that two consecutive values of the low bits repeat, which is enough for a first-order generator: the next state depends only on the current one.
- The loop terminates because the low bits form a permutation of themselves, which the measurement confirms.

## TypeScript: the snippet `seed = (seed * 9301 + 49297) % 233280` visits every one of its 233,280 values once, and its parity flips on all 1,000,000 of 1,000,000 steps

*Idioms and antipatterns*

**Did you know**

A three-line seeded random function is a staple of JavaScript answers: `seed = (seed * 9301 + 49297) % 233280; return seed / 233280`. On Node 26.13 it has a full period: 233,280 distinct values before the first repeat, as many as the modulus allows. That sounds like a good property and is the pattern: it is a permutation of the integers below 233,280, so the whole "random" stream is one fixed ring, the same for every seed, entered at a different point. The modulus is even and the multiplier and increment are odd, so the parity flips on every step: it alternated on 1,000,000 of 1,000,000 consecutive steps.

**Show me**

```ts
// Node 26.13.0: save as snippet.mts, run with node snippet.mts
const const_modulus: number = 233280
const const_fn_next = (seed: number): number => (seed * 9301 + 49297) % const_modulus

const const_start: number = 1
let seed: number = const_fn_next(const_start)
let period: number = 1
const visited: Set<number> = new Set([const_start])
while (!visited.has(seed)) {
    visited.add(seed)
    seed = const_fn_next(seed)
    period++
}
console.log("outputs before the first repeat:", visited.size, "of", const_modulus, "possible values")

let alternations: number = 0
let previous: number = const_start
for (let step_index = 0; step_index < 1000000; step_index++) {
    const current: number = const_fn_next(previous)
    if (current % 2 !== previous % 2) alternations++
    previous = current
}
console.log("steps where the parity changed, out of 1000000:", alternations)
```

Output: `outputs before the first repeat: 233280 of 233280 possible values` and `steps where the parity changed, out of 1000000: 1000000`.

**Why it matters**

The ring is the Press Your Luck board: a fixed cycle that someone can learn from a short run. Seeded with the clock, the first output tells you where in the ring you are, and the rest follows. The generator is fine for shuffling a slideshow and wrong for anything an adversary or a long-running simulation depends on. `Math.random` is a stronger generator, but the V8 blog post in part 2's appendix shows it has been through the same kind of weakness.

**Chew on this**

Where did your seeded-random helper come from, and has anyone checked its period? If your tests use it, how many different sequences can they ever see?

**Sources**

- https://en.wikipedia.org/wiki/Linear_congruential_generator (the full-period conditions)
- https://v8.dev/blog/math-random

**Verified**

Node v26.13.0 in the `node:lts` image, exact enumeration. I did not trace where the snippet came from; it is widely copied, and the three constants are the ones I remembered.

**Gotchas**

- Full period is the maximum for this modulus; "good" generators have much larger state.
- `% 2` of the integer state is not the same as the low bit of `seed / 233280`; the parity claim is about the integer state.

# The functional angle: a generator is a function from state to state, and its cycle structure is a property you can compute

Draws on all four tips. Each generator here is a pure function `state -> (value, state)`. For a pure function over a finite state space the whole behavior is the functional graph: cycles with trees leading into them. A cycle length, a number of unreachable states and a linear relation are all facts about that graph, and a short program finds them exactly.

```fsharp
// F#: the cycle length of any pure generator step function over a small state, by walking until a state repeats
let fn_cycle_length (fn_step: uint32 -> uint32) (start_state: uint32) : int =
    let seen: System.Collections.Generic.HashSet<uint32> = System.Collections.Generic.HashSet<uint32>()
    let mutable mut_state: uint32 = start_state
    while seen.Add mut_state do
        mut_state <- fn_step mut_state
    seen.Count
printfn "%d" (fn_cycle_length (fun state -> (state * 9301u + 49297u) % 233280u) 1u)
```

This sample ran and printed `233280`, the same as the TypeScript tip.

| Language | Generator | Exact fact found by enumeration |
| --- | --- | --- |
| Rust | SM64 `random_u16` | 65,114 of 65,536 values reached, 422 never |
| C++ | RANDU recurrence | one linear relation, 15 planes |
| F# | ANSI C sample LCG | low k bits have period 2^k |
| TypeScript | the 233,280 snippet | one ring of 233,280, parity alternates |

F# is the baseline because the graph-walking sample above is what its immutable style makes shortest. What is the largest generator state you could enumerate this way before it took too long, and what does that say about 32-bit seeds from part 4?

# The security angle: structure is leakage

Draws on all four tips. Mode B (what the language does not prevent). Bug classes: CWE-330 and CWE-338, with CWE-334 (Small Space of Random Values) for the small rings.

```ts
// TypeScript: with the 233,280 generator, one observed value is the whole state, so the next output is known
const const_fn_next_from_observed = (observed_seed: number): number => (observed_seed * 9301 + 49297) % 233280
```

A generator of 233,280 states can be recovered from one output, and one of 65,114 from one output of a 16-bit value. This part's measurements show it without an attack: the state is the output, so the future is a function of the last value. Part 10 does the same for generators whose state is larger than their output.

| Language | Structure found | What an observer gets |
| --- | --- | --- |
| Rust | cycle of 65,114 | the next value after seeing one |
| C++ | 15 planes | a 3D point's likely plane |
| F# | low-bit period 2^k | the low bits are predictable |
| TypeScript | one ring | the next value after seeing one |

C++ is the baseline because the plane structure is the subtlest: nothing about any single value reveals it. What would your simulation look like if every consecutive triple of its random values lay on fifteen sheets of paper?

# FAQ

**Did Larson cheat?**
CBS decided he had not (per Wikipedia): there was no rule against memorizing the board. The show's designers had shipped five patterns where the rules assumed randomness.

**Is C++ `std::mt19937` free of this kind of structure?**
Its structure is different: part 10 shows it can be recovered from outputs, and a lattice test would not find the same thing. I did not test it for planes.

**Why does the Rust port count 65,114?**
Because the function skips some states and sends one (22026) back to 0, so the walk from 0 reached 65,114 distinct outputs; I did not analyze which 422 are missing, or whether other starting seeds reach them.

# Appendix A: A console role-playing game whose battles were decided by a table and a sum

The Rust tip in this part found a 16-bit generator with a short cycle. A different kind of "random" is a fixed table indexed by a counter, as Doom's in part 1. A TASVideos submission for the NES game Final Fantasy II (submission #7170, "game end glitch") documents one. Its notes say: "The basis of the random number is the sum of the zeropage data and carry bit when switching from the overworld to battle." That sum sets the number of monsters in an encounter, whether a pre-emptive attack is available, the monster's first action, and which of two RNG tables is used: "The random value is determined by the table address + index, but the contents of the table depend on bit 1 of the sum." After initialization, the sum becomes the index into the table, and each random calculation advances it. The notes list the table's location in the console's memory (addresses $7a48 to $7b47, 256 bytes) and its first 32 bytes.

The speedrunners' reading is the same as Larson's on Press Your Luck (part 9's story): the outcome is a function of values the player can influence. Here the zero-page sum depends on inputs just before the battle (the notes say the input keys and the A and B button counters during movement matter), so a tool-assisted run chooses the inputs that make the first monster action come out as wanted. I read the submission's notes, not the game's code, and did not reproduce any of it.

Source: https://tasvideos.org/7170S (read).
