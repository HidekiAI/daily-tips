## Rust: Since 1.86 &*boxed upcasts a Box<dyn Plugin> to &dyn Any, and &boxed also compiles but downcasts to None

*Type system deep cuts*

**Did you know**

Since Rust 1.86 a trait object whose trait has `Any` as a supertrait coerces straight to `&dyn Any`, so the hand-written `fn as_any(&self) -> &dyn Any` method every plugin registry used to carry is no longer needed. The trap is the receiver. `&*boxed` upcasts the trait object; `&boxed` coerces the `Box<dyn Plugin>` itself, which is also a `'static` type and therefore also an `Any`. Both compile. On rustc 1.100.0 the first downcast to `AuditPlugin` gave `Some(3)` and the second gave `None`, and Rust 1.85 rejected only the correct one (E0658, "trait upcasting coercion is experimental") while accepting the wrong one.

**Show me**

```rust
// Rust 1.86+ (trait upcasting coercion)
use std::any::{Any, TypeId};

trait Plugin: Any {
    fn name(&self) -> &str;
}

struct AuditPlugin {
    event_count: u32,
}

impl Plugin for AuditPlugin {
    fn name(&self) -> &str {
        "audit"
    }
}

fn main() {
    let boxed: Box<dyn Plugin> = Box::new(AuditPlugin { event_count: 3 });
    println!("{}", boxed.name()); // audit

    // Deref first: this upcasts dyn Plugin -> dyn Any (E0658 on 1.85)
    let plugin_as_any: &dyn Any = &*boxed;
    let found = plugin_as_any.downcast_ref::<AuditPlugin>().map(|plugin| plugin.event_count);
    println!("{found:?}"); // Some(3)

    // No deref: the Box itself is the Any, so its concrete type is Box<dyn Plugin>
    let box_as_any: &dyn Any = &boxed; // compiles on 1.85 and 1.100 alike
    let missed = box_as_any.downcast_ref::<AuditPlugin>().map(|plugin| plugin.event_count);
    println!("{missed:?}"); // None
    println!("{}", box_as_any.downcast_ref::<Box<dyn Plugin>>().is_some()); // true

    // Method syntax hits the same wall: autoref finds Any::type_id on the Box first
    println!("{}", boxed.type_id() == TypeId::of::<AuditPlugin>()); // false
    println!("{}", (*boxed).type_id() == TypeId::of::<AuditPlugin>()); // true
}
```

**Why it matters**

A typed extension map or plugin registry treats `None` as "not the type I asked for" and takes its fallback branch, so the wrong receiver is not a crash, it is a lookup that quietly never matches. C++ has had implicit derived-to-base conversion since the beginning and asks the same question at runtime with `dynamic_cast`, but there the pointer you pass is the object; in Rust a `Box<dyn Trait>` is a value with its own type, and `Any` is happy to describe that value instead of the one inside it.

**Chew on this**

Which of your `downcast_ref` calls return `None` for a reason nobody ever logged? When a field changes from `Arc<dyn Trait>` to `Box<dyn Trait>`, which `TypeId` keys in your code silently change with it?

**Sources**

- https://doc.rust-lang.org/std/any/trait.Any.html
- https://github.com/rust-lang/rust/issues/65991 (trait upcasting tracking issue, cited by rustc 1.85 in its E0658 note)

**Verified**

rustc 1.100.0, 1.86 and 1.85 in the official Docker images (1.100 on Debian 13.7, aarch64). The 1.86 boundary is measured (1.85 rejects, 1.86 compiles); the release notes page itself could not be read (HTTP 503).

**Gotchas**

- `boxed.type_id()` on a `Box<dyn Plugin>` is the Box's `TypeId`: compared with `TypeId::of::<AuditPlugin>()` it printed `false`, and `(*boxed).type_id()` printed `true`. Clippy 0.1.100 warns about this one by default (`type_id_on_box`), but says nothing about `let box_as_any: &dyn Any = &boxed;`.
- The owning form upcasts too: `let owned_any: Box<dyn Any> = boxed;` then `owned_any.downcast::<AuditPlugin>()` gave back the plugin, `Some(3)`. It is also rejected by 1.85 with the same E0658.
- The wrong receiver does not lose the value, it files it under the wrapper: `box_as_any.downcast_ref::<Box<dyn Plugin>>()` printed `true`.

**Related**

- [2026-09-15](2026-09-15.md) - Rust, "A trait object's elided lifetime comes from the containing type, not the use site". The hidden `+ 'static` on `Box<dyn Plugin>` is exactly why the Box qualifies as an `Any` here.

## C++: std::stable_sort asks nothrow new for a buffer, and when refused it halves the request 20 times and sorts 3.3x slower with no error

*Perf and memory model*

**Did you know**

`std::stable_sort` is the standard algorithm that allocates behind your back, and it asks through the nothrow `operator new`, so a refusal never reaches you. Sorting 1,000,000 `uint32_t` (4,000,000 bytes) with g++ 16.2.0 made one request of 2,000,000 bytes, half the input; libc++ (Debian clang 19.1.7) asked for all 4,000,000. With every request refused, both libraries retried 20 times, halving down to 4 bytes, then sorted in place: still correct, but 52.1 ms became 173.0 ms on libstdc++ and 40.0 ms became 228.5 ms on libc++. No exception, no return value, nothing in a log. The permission is in the standard's complexity clause, O(N log N) comparisons "if enough extra memory is available", O(N log² N) otherwise, unchanged since C++98; `std::ranges::stable_sort` (C++20) made the same single request, and overloads (1) and (2) become `constexpr` in C++26.

**Show me**

```cpp
// C++20; g++ 16.2.0 and Debian clang 19.1.7 (libstdc++ and libc++) on Debian 13.7
#include <algorithm>
#include <cstdint>
#include <cstdlib>
#include <new>
#include <vector>

static std::size_t nothrow_calls = 0;
static std::size_t refuse_above_bytes = SIZE_MAX; // set to 0 to simulate memory pressure

// stable_sort's buffer comes through THIS overload, not the throwing one
void* operator new(std::size_t size, const std::nothrow_t&) noexcept {
    ++nothrow_calls;
    if (size > refuse_above_bytes) return nullptr; // the library treats nullptr as "try half"
    return std::malloc(size);
}
void* operator new(std::size_t size) {
    if (void* block = std::malloc(size)) return block;
    throw std::bad_alloc();
}
void operator delete(void* block) noexcept { std::free(block); }
void operator delete(void* block, std::size_t) noexcept { std::free(block); }

void sort_readings(std::vector<std::uint32_t>& readings) {
    std::sort(readings.begin(), readings.end());        // 0 allocations
    std::stable_sort(readings.begin(), readings.end()); // 1 request: 2,000,000 B (libstdc++)
    refuse_above_bytes = 0;
    std::stable_sort(readings.begin(), readings.end()); // 20 requests, 4 B last, in-place merge
}
```

**Why it matters**

Under a container memory limit or a fragmented heap, the sort your request handler depends on does not fail, it gets three to six times slower, which shows up as a latency regression with no error attached. Rust makes the opposite trade: `slice::sort` made one allocation of 4,000,000 bytes for the same million `u32` (`sort_unstable` made none), and the documented behaviour of a failed allocation through the global allocator is to call `handle_alloc_error`, which aborts by default rather than degrading. F# and TypeScript sit with Rust in hiding the buffer entirely, without exposing a way to watch or refuse it.

**Chew on this**

Which of your sorts would you rather see fail loudly than finish four times later? If a sort on your hot path dropped to O(N log² N) during the last memory incident, which of your metrics would have shown it?

**Sources**

- https://en.cppreference.com/w/cpp/algorithm/stable_sort
- https://en.cppreference.com/w/cpp/memory/get_temporary_buffer

**Verified**

Measured in Docker on Debian 13.7 (aarch64), one run per row, input from `std::mt19937` seed 42. The Rust abort-on-failure path rests on documentation; it was not provoked.

**Gotchas**

- Capping the buffer barely hurts, only having none does: refusing anything over 64 KiB gave 6 requests (last 62,500 B) and 53.2 ms against 52.1 ms on libstdc++, and 7 requests and 53.6 ms against 40.0 ms on libc++.
- An allocation tracker that replaces only the throwing `operator new` never sees this buffer: the throwing count stayed at 0 in every run.
- The two standard libraries differ by 2x in peak memory for the same call: libstdc++ asks for half the range, libc++ for the whole range.
- `std::get_temporary_buffer`, the public face of this mechanism, was deprecated in C++17 and removed in C++20, while the algorithm keeps doing it internally.
- The execution-policy overloads (C++17) behave differently: cppreference says they throw `std::bad_alloc` when temporary memory for parallelization is unavailable. Not measured here.

**Related**

- [2026-10-05](2026-10-05.md) - F#, "Array.sortBy is not stable and List.sortBy is". Stability was the free-looking choice there; this is its bill.
- [2026-10-15](2026-10-15.md) - C++, "A pmr::vector growing inside a monotonic_buffer_resource keeps every buffer it outgrew". Another place where the allocator, not the algorithm, decides the cost.

## F#: FSharp.Core 11 hands back one shared empty array from Array.map, collect, sub and zeroCreate 0, so a lock on one empty result blocks every other

*New discoveries and currently popular patterns*

**Did you know**

FSharp.Core 11, which shipped with .NET 11 on 2026-11-10, returns the single `Array.Empty<'T>()` instance for zero-length results across most `Array` and `Array.Parallel` functions (dotnet/fsharp PR #20388, merged 2026-09-16, to save the allocations). Measured with `dotnet fsi`: on FSharp.Core 10.1, `Array.map` over `[||]`, an all-empty `Array.collect`, `Array.sub arr 0 0`, `Array.zeroCreate 0` and `List.toArray []` each gave a fresh array; on FSharp.Core 11 all five are `obj.ReferenceEquals` to `Array.empty<int>`. Values did not change, identity did, so every API that works by identity now sees two unrelated empty results as one object.

**Show me**

```fsharp
// F# 11, FSharp.Core 11.0.0.0, .NET 11.0.0 (same script on FSharp.Core 10.1 for the contrast)
open System.Threading
open System.Runtime.CompilerServices

let east_batches: int[][] = [| [||]; [||] |]
let west_batches: int[][] = [| [||] |]
let east_pending = east_batches |> Array.collect id // empty result
let west_pending = west_batches |> Array.collect id // another empty result, another job

// Job A guards "its own" pending array
let lock_holder = Thread(fun () -> lock east_pending (fun () -> Thread.Sleep 500))
lock_holder.Start()
Thread.Sleep 100

// Job B tries to take "its own" lock
let west_lock_free = Monitor.TryEnter(west_pending, 50)
printfn "%b" west_lock_free // FSharp.Core 10.1: true   FSharp.Core 11: false
if west_lock_free then Monitor.Exit west_pending
lock_holder.Join()

// Metadata attached by identity leaks across results the same way
let result_tags = ConditionalWeakTable<int[], string>()
result_tags.Add(east_pending, "region east")
match result_tags.TryGetValue west_pending with
| true, tag -> printfn "west carries %s" tag // FSharp.Core 11: "region east"
| _ -> printfn "west has no tag"             // FSharp.Core 10.1
```

**Why it matters**

The .NET `Monitor` documentation says "you should lock only on private or internal objects", and a result array stops being private the moment the library may hand the same instance to everyone. It is the same class of bug as C#'s `lock` on a string literal, which is shared through interning: no exception, just contention or a deadlock between code that never shared anything on purpose. Rust has the shared identity too (`Vec::new()` and `Vec::with_capacity(0)` both pointed at `0x4`) but no API to take a lock or a weak-table entry by an object's address, because `Mutex<T>` owns its data; C++ gave both empty `std::vector`s a `data()` of `nullptr` and keeps `std::mutex` a separate object.

**Chew on this**

Which of your locks, weak tables or reference-keyed caches key on an object that came back from a library call rather than one you allocated yourself? When an upgrade changes identity but not values, which of your tests would even notice?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/whats-new/fsharp-11 (section "Avoid callback and empty-result allocation overhead")
- https://github.com/dotnet/fsharp/pull/20388
- https://learn.microsoft.com/en-us/dotnet/api/system.threading.monitor

**Verified**

`dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:11.0` (.NET 11.0.0, FSharp.Core 11.0.0.0) and `sdk:10.0` (.NET 10.0.15, FSharp.Core 10.1.0.0); those images are Ubuntu, not Debian. The PR details (author, merge date, function list) come from reading the PR page.

**Gotchas**

- The sharing is not entirely new: `Array.filter`, `Array.choose`, `Array.truncate 0` and `Array.skip` of the whole array already returned the shared empty array on FSharp.Core 10.1. Code that locked on a filtered result was exposed before the upgrade; FSharp.Core 11 widened it to `map`, `collect`, `sub`, `zeroCreate 0` and `List.toArray`.
- The `[||]` literal was the shared instance on both versions.
- The assembly reports version `11.0.0.0` while the package that shipped with the .NET 11.0.0 SDK is FSharp.Core 11.0.101: check the package version, not `GetName().Version`, when you need to know which behaviour you have.
- The F# 11 page is explicit: "Don't rely on separate empty results having distinct reference identities." Nothing in 10.1 promised distinct identities either.
- Lists are unaffected: per the PR discussion, the empty F# list was already a single shared value.

**Related**

- [2026-11-17](2026-11-17.md) - F#, "F#'s lock takes a System.Threading.Lock and uses Monitor on it". Same `Monitor`, other half of the question: what you lock on decides who you exclude.

## TypeScript: instanceof Error said false for an error from vm.runInNewContext and true for Object.create(Error.prototype), and Error.isError got both right

*Stdlib and ecosystem gems*

**Did you know**

`Error.isError` (ES2026, TC39 stage 4) checks the internal slot every genuine error object carries, not the prototype chain, and Node 26 ships it. Measured on Node 26.13.1: an error created in another realm with `vm.runInNewContext` gave `instanceof Error` `false` and `Error.isError` `true`; `Object.create(Error.prototype)` gave `instanceof` `true` and `isError` `false`. A subclass, a `structuredClone`d `TypeError` and a `DOMException` were `true` on both. tsc 7.0.2 knows the function only under `lib: esnext` (with `es2025` it reports TS2550), and there it narrows `unknown` to `Error`.

**Show me**

```typescript
// TypeScript 7.0.2 (lib: esnext), Node 26.13.1
import vm from "node:vm";

const fn_error_message = (caught: unknown): string =>
    caught instanceof Error ? caught.message : "non-error value thrown";

const fn_error_message_checked = (caught: unknown): string =>
    Error.isError(caught) ? caught.message : "non-error value thrown"; // narrows unknown to Error

// An error built by code running in another realm (a vm context, as test runners use)
const realm_error: unknown = vm.runInNewContext("new Error(\"disk full\")");

console.log(fn_error_message(realm_error));         // non-error value thrown
console.log(fn_error_message_checked(realm_error)); // disk full

// The prototype chain can also say yes to something that was never an error
const impostor: unknown = Object.create(Error.prototype);
console.log(impostor instanceof Error, Error.isError(impostor)); // true false
```

**Why it matters**

Jest runs each test file in a `vm` context, and its issue #2549, "Jest globals differ from Node globals", has been open since January 2017 with `instanceof Error` among its casualties: the same error handler can classify the same failure differently under test than in production, and in the probe the real message "disk full" was replaced by a generic string. The shape matches today's Rust tip: `instanceof` answers about the object's prototype in this realm, `downcast_ref` answers about the value you passed, and in both cases the check is honest about a question you did not mean to ask.

**Chew on this**

Where does your code decide "this is not an error" and continue down a success path? Which of your dependencies create errors in a different realm, a `vm` context, a worker, an iframe, and hand them to your `catch`?

**Sources**

- https://github.com/tc39/proposal-is-error
- https://github.com/jestjs/jest/issues/2549

**Verified**

Node 26.13.1 (`node:lts`) and tsc 7.0.2 with `@types/node`, in Docker on Debian 13.7, aarch64.

**Gotchas**

- `Object.prototype.toString.call` is not a substitute: it printed `[object Error]` for the cross-realm error but `[object DOMException]` for the `DOMException`, which `Error.isError` still accepted.
- `structuredClone` re-creates the error in the current realm: the cloned `TypeError` passed `instanceof Error`, so a clone hides the realm problem rather than exposing it.
- `Object.create(Error.prototype)` has no message and no stack, and still passes `instanceof Error`; a plain look-alike object `{ name, message, stack }` fails both checks.
- Under `--lib es2024` or `es2025` the call is TS2550, and the `unknown` is then left un-narrowed (TS18046 on `.message`): the fix is `esnext` in `lib`, not a cast.

**Related**

- [2026-10-23](2026-10-23.md) - TypeScript, "Array.isArray turns a readonly string[] into any[]". `Array.isArray` is the realm-safe check arrays always had; `Error.isError` is its long-missing sibling.

# The functional angle: a type test that returns an Option is the safe shape in all four languages, and it still answers about the value you passed, not the one you meant

Draws on the Rust and TypeScript tips; the C++ and F# rows were measured for this section (g++ 16.2.0, `dotnet fsi` on .NET 11.0.0).

Each language has a type test shaped like a function to an optional value, and each one keeps a throwing twin beside it. The Option-shaped form is the functional one: absence is a value you must handle, not an exception you might not catch. What none of them can do is know which value you meant to ask about.

```fsharp
// F#: tryUnbox returns an Option; unbox throws
let holder: obj = box 42u
tryUnbox<uint32> holder // Some 42u
tryUnbox<string> holder // None
// unbox<string> holder  -> InvalidCastException
```

```rust
// Rust: downcast_ref returns an Option; there is no throwing form in std
let holder: Box<dyn std::any::Any> = Box::new(42u32);
holder.downcast_ref::<u32>(); // Some(42)
holder.downcast_ref::<String>(); // None
```

```cpp
// C++17: the pointer form of any_cast is the optional-shaped one
std::any holder = 42u;
std::any_cast<unsigned>(&holder);     // non-null
std::any_cast<std::string>(&holder);  // nullptr
// std::any_cast<std::string>(holder) -> throws std::bad_any_cast ("bad any_cast")
```

```typescript
// TypeScript: a type predicate narrows instead of returning a wrapper
const fn_message_or_none = (caught: unknown): string | undefined =>
    Error.isError(caught) ? caught.message : undefined;
```

| Language | Option-shaped test | Throwing twin | What it actually compares |
| --- | --- | --- | --- |
| F# | `tryUnbox<string>` gave `None` | `unbox<string>` threw `InvalidCastException` | the runtime type of the boxed object; the default shape since the `:?` pattern is the same test |
| Rust | `downcast_ref::<String>()` gave `None` | none in std; any `unwrap` is yours | the `TypeId` of the concrete type behind the `dyn Any`, which for `&boxed` is the Box |
| C++ | `any_cast<std::string>(&holder)` gave `nullptr` | `any_cast<std::string>(holder)` threw `bad_any_cast` | the stored type of the `std::any` |
| TypeScript | `Error.isError`, a `value is Error` predicate | none; `instanceof` never throws either | an internal slot, while `instanceof` compares the prototype chain of this realm |

No language here needs `mut` for any of it, and none of the four Option-shaped forms allocates; the cost is entirely in the meaning. An Option makes absence explicit, but in the Rust tip and the TypeScript tip the `None` and the `false` were correct answers to the wrong question, and nothing about the return type can say so.

If every one of these tests is honest, where in your code would you put the check that you asked about the right value?

# The security angle: a check that answers about an object you did not create trusts whoever else holds it

Draws on the F#, TypeScript and Rust tips, Mode B: each tip taught a mechanism that works as specified, and the question here is what it does when the code around it fails open. It runs in the "does not prevent" direction for all three.

```typescript
// TypeScript: classification that fails open (CWE-697, incorrect comparison)
const fn_settle = (outcome: unknown): "rejected" | "approved" =>
    outcome instanceof Error ? "rejected" : "approved";
// A failure thrown from a vm context is not instanceof Error here (measured above),
// so it is "approved". Error.isError, or treating "unknown shape" as rejected, closes it.
```

```fsharp
// F#: "my own" lock that is everyone's (CWE-667, improper locking)
let pending = batches |> Array.collect id   // empty -> the shared Array.Empty<int>() on FSharp.Core 11
lock pending (fun () -> flush pending)      // any other code locking any empty result now waits here
// Lock on a private object instead: let pending_gate = obj ()
```

```rust
// Rust: the wrong receiver turns a policy check into its default (CWE-697)
fn policy_allows(policy: &Box<dyn Plugin>) -> bool {
    let as_any: &dyn Any = policy; // coerces the Box, not the plugin inside it
    as_any.downcast_ref::<DenyAll>().is_none() // never Some, so every request is allowed
}
// &**policy upcasts the plugin itself; a None that means "deny" is safer than one that means "allow"
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | a cross-realm error or a prototype impostor is misclassified | `instanceof` checks the prototype chain; `Error.isError` (ES2026) checks the slot | use `isError` with `lib: esnext`, and make "not recognisably an error" a failure branch, never a success |
| F# | two unrelated jobs contend on, or deadlock over, the same shared empty array | `Monitor` accepts any object; FSharp.Core 11 shares empty results by design | lock only on objects you allocated and never return, as the `Monitor` docs say |
| Rust | a downcast on the wrong receiver silently yields `None` | the compiler accepts both coercions; clippy flags only the `.type_id()` form | deref explicitly (`&*boxed`), and make `None` fail closed |
| C++ | an attacker who controls input size under memory pressure gets a 3x to 6x slower sort | the standard allows the O(N log² N) fallback without a signal | a latency budget or a metric around large sorts (CWE-407) |

There is no control language for this class: in TypeScript, F# and Rust alike the check itself is correct and both the safe and the unsafe call type-check, so the only fix that survives the next maintainer is a check whose failure branch is the safe one.

Which of your checks return "no" for an object you never created, and what does your code do next when they do?
