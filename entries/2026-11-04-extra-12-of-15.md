Not part of the rotation. Parts 4 to 11 had generators broken by mistake or by neglect. This part has a generator that was published as a standard, and whose problem was not a bug at all. The algorithm contained two constants, and anyone who knew a relation between them could read its output like plain text. Nobody outside could tell whether anyone did.

# What happened

**Bug class:** a standardized generator with a possible back door in its constants (CWE-338 for the weak generator, and CWE-327 for a risky cryptographic algorithm in a standard). The finding was a possibility, shown mathematically in 2007, and treated as one for six more years.

**The story, in plain words:**

The United States standards body NIST published a guide to random number generators, Special Publication 800-90. It specified four generators. Three were built from a hash function or a block cipher. The fourth, Dual_EC_DRBG, was built from elliptic-curve arithmetic,, and it was listed alongside the others as a choice.

At a conference rump session in 2007, two Microsoft engineers, Dan Shumow and Niels Ferguson, presented a short talk titled "On the Possibility of a Back Door in the NIST SP800-90 Dual Ec Prng". Their point was a single observation about the algorithm's two fixed points on the curve, P and Q. P is the standard generator point. Q is "a specified constant. It is not stated how it was derived." NIST's curves have prime order, so there is a number e such that e times Q equals P. Whoever chose Q might know e. And if they do, one output block lets them list about 2^15 candidates for the generator's internal state, and a second block picks the right one. The talk's own words for the finding: "If an attacker knows d such that d*P = Q then they can easily compute e such that e*Q = P."

In September 2013 news reports revived the question. NIST says it "immediately recommended against the use of the algorithm" and reissued the document for public comment. In April 2014 NIST announced that it had removed the algorithm from its draft. The final revision, SP 800-90A Rev. 1, says plainly: "The Dual_EC_DRBG has been removed, and section numbers adjusted accordingly."

The quotes:

- "Point Q is a specified constant. It is not stated how it was derived." (Shumow and Ferguson, rump session slides, 2007)
- "NIST prime curves have prime order. So there exists e such that Qe = P." (same)
- "In September 2013, news reports prompted public concern about the trustworthiness of Dual_EC_DRBG. As a result, NIST immediately recommended against the use of the algorithm and reissued SP 800-90A for public comment." (NIST news item, 21 April 2014)
- "NIST recommends that current users of Dual_EC_DRBG transition to one of the three remaining approved algorithms as quickly as possible." (same)
- "The Dual_EC_DRBG has been removed, and section numbers adjusted accordingly." (SP 800-90A Rev. 1, list of changes)

I did not read the later academic analysis of whether deployed products had the back door: its host refused automated access, so I make no claim about who knew what. The measurement below is the 2007 observation, reproduced.

## Rust: with a self-chosen Q = d * P, one 30-byte output of a Dual_EC-style generator gave 32,766 candidates, and a second output chose the right state, which then predicted the next five outputs

*Stdlib and ecosystem gems*

**Did you know**

Dual_EC_DRBG on NIST P-256 outputs the low 240 bits of the x coordinate of `s * Q`, hiding only 16 bits. The attacker adds back each of the 65,536 possible 16-bit prefixes, keeps those that are x coordinates of curve points (32,766 of 65,536 here, the talk's "about 2^15"), multiplies each by `e` where `e * Q = P`, and one of the results is the generator's next state. A second output identifies which. In Rust with the `p256` crate, this took 6 seconds on release build, recovered the state, and predicted the next five outputs exactly. The back door in this demonstration is my own: I chose Q as `d * P` with a `d` I know, which is what the 2007 talk did in its own verification.

**Show me**

```rust
// p256 0.13, elliptic-curve 0.13, rustc 1.99.1, release build: Dual_EC_DRBG on NIST P-256 with a toy Q = d * P chosen by the attacker
use elliptic_curve::ops::Reduce;
use elliptic_curve::sec1::{FromEncodedPoint, ToEncodedPoint};
use p256::{AffinePoint, EncodedPoint, FieldBytes, ProjectivePoint, Scalar, U256};
use std::time::Instant;

const TRUNCATED_BYTES: usize = 2; // the standard drops the 16 most significant bits of each x coordinate

fn fn_x_coordinate(point: &ProjectivePoint) -> FieldBytes {
    let encoded: EncodedPoint = point.to_affine().to_encoded_point(false);
    *FieldBytes::from_slice(encoded.x().expect("not the point at infinity"))
}
fn fn_scalar_from_x(x_coordinate: &FieldBytes) -> Scalar {
    <Scalar as Reduce<U256>>::reduce_bytes(x_coordinate)
}

struct DualEc { state: Scalar, point_q: ProjectivePoint }
impl DualEc {
    // one step: state' = x(state * P); output = the low 240 bits of x(state' * Q)
    fn fn_next_output(&mut self) -> [u8; 32 - TRUNCATED_BYTES] {
        let next_state_x: FieldBytes = fn_x_coordinate(&(ProjectivePoint::GENERATOR * self.state));
        self.state = fn_scalar_from_x(&next_state_x);
        let output_x: FieldBytes = fn_x_coordinate(&(self.point_q * self.state));
        output_x[TRUNCATED_BYTES..].try_into().unwrap()
    }
}

fn main() {
    let secret_d: Scalar = Scalar::from(0x1234_5678_9abc_def0u64) * Scalar::from(0xfedc_ba98_7654_3210u64); // the attacker's knowledge
    let point_q: ProjectivePoint = ProjectivePoint::GENERATOR * secret_d; // Q = d * P
    let secret_e: Scalar = Option::<Scalar>::from(secret_d.invert()).expect("d is invertible"); // e * Q = P
    let mut mut_victim: DualEc = DualEc { state: Scalar::from(0xdead_beef_cafe_f00du64) * Scalar::from(0x0123_4567_89ab_cdefu64), point_q };

    let first_output: [u8; 30] = mut_victim.fn_next_output();
    let second_output: [u8; 30] = mut_victim.fn_next_output();

    let started: Instant = Instant::now();
    let mut mut_on_curve: u32 = 0;
    let mut mut_recovered_state: Option<Scalar> = None;
    for missing_prefix in 0..=u16::MAX {
        let mut candidate_x: [u8; 32] = [0; 32];
        candidate_x[..2].copy_from_slice(&missing_prefix.to_be_bytes());
        candidate_x[2..].copy_from_slice(&first_output);
        let mut compressed: [u8; 33] = [0; 33];
        compressed[0] = 0x02;
        compressed[1..].copy_from_slice(&candidate_x);
        let encoded: EncodedPoint = EncodedPoint::from_bytes(compressed).unwrap();
        let candidate_point: Option<AffinePoint> = AffinePoint::from_encoded_point(&encoded).into();
        let Some(candidate_point) = candidate_point else { continue };
        mut_on_curve += 1;
        // if candidate_point = state' * Q, then e * candidate_point = state' * P, whose x is the next state
        let next_state: Scalar = fn_scalar_from_x(&fn_x_coordinate(&(ProjectivePoint::from(candidate_point) * secret_e)));
        let predicted_second: FieldBytes = fn_x_coordinate(&(point_q * next_state)); // the second output is x(state2 * Q)
        if predicted_second[TRUNCATED_BYTES..] == second_output[..] {
            mut_recovered_state = Some(next_state);
        }
    }
    println!("candidates on the curve: {} of 65536 (took {:?})", mut_on_curve, started.elapsed());
    match mut_recovered_state {
        None => println!("no candidate matched the second output"),
        Some(state) => {
            let mut mut_clone: DualEc = DualEc { state, point_q };
            let predicted: Vec<[u8; 30]> = (0..5).map(|_| mut_clone.fn_next_output()).collect();
            let actual: Vec<[u8; 30]> = (0..5).map(|_| mut_victim.fn_next_output()).collect();
            println!("next five 30-byte outputs predicted: {}", predicted.iter().zip(actual.iter()).filter(|(left, right)| left == right).count());
        }
    }
}
```

Output: `candidates on the curve: 32766 of 65536 (took 6.127315125s)` and `next five 30-byte outputs predicted: 5`. The compiler warns that `FieldBytes::from_slice` is deprecated; it still works.

**Why it matters**

The attack never needs the victim's state or seed, only one 30-byte block of output and a number that the algorithm's author is the only one who could have known. That is why "there is no known attack" was not an answer in 2007: the weakness depended on who held a secret, not on an algorithm anyone could test. The measurement also shows the cost is nothing: six seconds for a search a lab could run on a phone.

**Chew on this**

Which constants in your cryptographic code came from someone else with no explanation of how they were chosen? Who would know if they had a relation you cannot see?

**Sources**

- https://rump2007.cr.yp.to/15-shumow.pdf (Shumow and Ferguson, read)
- https://docs.rs/p256/0.13.2/p256/

**Verified**

rustc 1.99.1, p256 0.13 and elliptic-curve 0.13 from crates.io, release build in the `rust:1` image's cargo; one run. The generator in the code follows the structure on the 2007 slides (state x(s*P), output the low bits of x(state*Q)); I did not check it against the SP 800-90 text, and my `Q` is not NIST's. Whether NIST's own `Q` has a known `d` is not something this measurement shows.

**Gotchas**

- A real implementation also has the reseed and additional-input steps; this toy has neither.
- The 6 seconds cover 65,536 scalar multiplications (32,766 of them reached); the attack's cost depends on the curve library.

## C++: `std::random_device` takes a token naming its source; on GCC 16.2 `default`, `/dev/urandom`, `/dev/random` and `getentropy` work, `rdrand`, `rdseed` and `mt19937` throw, and libc++ accepts only file paths

*Idioms and antipatterns*

**Did you know**

The standard says the constructor argument is implementation-defined. On GCC 16.2 (libstdc++, aarch64 Linux) the tokens `default`, `/dev/urandom`, `/dev/random` and `getentropy` constructed a device with entropy 32; `rdrand`, `rdseed` and `mt19937` threw "unsupported token" (on an x86 machine `rdrand` would be a candidate; I did not test one). On Debian clang 19.1.7 with libc++, only `/dev/urandom` and `/dev/random` worked: `default`, `getentropy`, `rdrand`, `rdseed` and `mt19937` all threw "failed to open ...", because libc++ treats the token as a file name. The portable call `std::random_device()` with no argument uses each library's default.

**Show me**

```cpp
// g++ -std=c++23 -O2 tokens.cpp   (and clang++ -std=c++23 -stdlib=libc++ -O2 tokens.cpp)
#include <iostream>
#include <random>
#include <string>

int main() {
    for (const std::string token : {"default", "/dev/urandom", "/dev/random", "getentropy", "rdrand", "rdseed", "mt19937", "bogus"}) {
        try {
            std::random_device first_device(token);
            std::random_device second_device(token);
            std::cout << token << ": ok, entropy " << first_device.entropy() << ", first words of two instances " << first_device() << " " << second_device() << "\n";
        } catch (const std::exception& problem) {
            std::cout << token << ": throws " << problem.what() << "\n";
        }
    }
}
```

Output on GCC 16.2: four `ok` lines (the words differ between the two instances and between runs) and four `throws random_device::random_device(const std::string&): unsupported token: Invalid argument`. On libc++: `ok` for the two device files and six `throws random_device failed to open ...: No such file or directory`.

**Why it matters**

A portable program has no portable way to ask for a particular source, and a program that passes a token to pick the hardware generator may silently depend on a platform. The Dual EC story is about not being able to see inside a generator; this is the smaller version, a source you cannot even name consistently. If a standard cannot say what `random_device` draws from, a reader cannot audit it.

**Chew on this**

Does your code pass a token to `random_device`? Which platform's behavior does it assume?

**Sources**

- https://eel.is/c++draft/rand.device
- https://gcc.gnu.org/onlinedocs/libstdc++/manual/ (the libstdc++ manual, which documents the tokens it accepts; I did not read it, the behavior above is measured)

**Verified**

GCC 16.2.0 and Debian clang 19.1.7 with libc++, `-O2`, Linux aarch64 containers. Whether `rdrand` is accepted on x86 is not measured.

**Gotchas**

- `entropy()` printed 32 for every accepted token on both libraries, so it does not tell the sources apart.
- Constructing two devices from the same token gave different words, as it should for an operating-system source.

## F#: `RandomNumberGenerator.Create()` is `RandomNumberGeneratorImplementation`, and on Linux the process maps `libcrypto.so.3` and `libssl.so.3`

*Stdlib and ecosystem gems*

**Did you know**

.NET's `RandomNumberGenerator` is documented as the cryptographic source, with the algorithm up to the platform. On .NET 10 in the Ubuntu SDK container `RandomNumberGenerator.Create()` returned an instance of `System.Security.Cryptography.RandomNumberGeneratorImplementation`, and after one call the process had mapped `libcrypto.so.3`, `libssl.so.3` and `libSystem.Security.Cryptography.Native.OpenSsl.so`: the managed call goes to OpenSSL 3. Which generator OpenSSL runs inside is a choice made two layers down (the TypeScript tip lists the families the OpenSSL command line offers; which one is the default I did not check).

**Show me**

```fsharp
// .NET 10.0.14, dotnet fsi
open System
open System.Security.Cryptography

let generator: RandomNumberGenerator = RandomNumberGenerator.Create()
printfn "RandomNumberGenerator.Create() is a %s" (generator.GetType().FullName)
let _filled: byte[] = RandomNumberGenerator.GetBytes(16) // make sure the native layer is loaded
let loaded_libraries: string list =
    IO.File.ReadAllLines("/proc/self/maps")
    |> Array.choose (fun line -> match line.LastIndexOf('/') with | -1 -> None | slash -> Some (line.Substring(slash + 1)))
    |> Array.filter (fun file_name -> file_name.Contains "crypto" || file_name.Contains "ssl" || file_name.Contains "Cryptography")
    |> Array.distinct |> Array.toList
printfn "native libraries mapped: %A" loaded_libraries
```

Output: `RandomNumberGenerator.Create() is a System.Security.Cryptography.RandomNumberGeneratorImplementation` and `native libraries mapped: ["libcrypto.so.3"; "System.Security.Cryptography.dll"; "libssl.so.3"; "libSystem.Security.Cryptography.Native.OpenSsl.so"]`.

**Why it matters**

The trust in `RandomNumberGenerator` is trust in a chain: the .NET shim, the OpenSSL version the distribution installed, its default generator, and the kernel under it. A program cannot see the chain from inside. This is the opposite of Dual EC's problem: the algorithm is not in doubt, but who built each link is not the application's decision.

**Chew on this**

Which version of OpenSSL does your container ship, and who updates it? Would you know if a link in the chain changed?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.randomnumbergenerator

**Verified**

.NET SDK 10.0 image (Ubuntu), `dotnet fsi`. The `/proc/self/maps` list is Linux only.

**Gotchas**

- On Windows the same call goes to the operating system's own API, not to OpenSSL; I did not measure it.
- Mapped libraries show what is loaded, not which of them produced the bytes.

## TypeScript: Node 26.13 bundles OpenSSL 3.5.9 and reports FIPS off, and the OpenSSL command line in the same image lists three generators and no Dual EC

*Idioms and antipatterns*

**Did you know**

`process.versions.openssl` printed `3.5.9` and `crypto.getFips()` returned `0` on Node 26.13. In the same container, the system `openssl` command line (3.5.7, a separate build) listed its random generators: `CTR-DRBG`, `HASH-DRBG` and `HMAC-DRBG`, plus a seed source and a test generator. Dual_EC_DRBG is not among them. That list describes the Debian package, not Node's bundled copy, so it is evidence about the ecosystem, not about Node.

**Show me**

```sh
# node:lts image (Node 26.13.0, Debian)
node -e 'console.log("node", process.version, "openssl", process.versions.openssl, "fips", require("crypto").getFips())'
openssl version
openssl list -random-generators
```

Output: `node v26.13.0 openssl 3.5.9 fips 0`, `OpenSSL 3.5.7 9 Jun 2026 (Library: OpenSSL 3.5.7 9 Jun 2026)`, then `Provided RNGs and seed sources:` with `CTR-DRBG @ default`, `HASH-DRBG @ default`, `HMAC-DRBG @ default`, `SEED-SRC @ default` and `TEST-RAND @ default`.

**Why it matters**

Dual EC is gone from the list that users see, and the NIST document that carried it was revised to remove it. A gap in tooling remains: nothing in `crypto.randomBytes` lets a program ask which generator it got, so "which DRBG" is only knowable from the build. In a regulated setting that is what FIPS mode, `getFips()`, is for.

**Chew on this**

Is your Node build the one the CLI describes? Where in your deployment is the OpenSSL version written down?

**Sources**

- https://nodejs.org/api/crypto.html#cryptogetfips
- https://docs.openssl.org/3.5/man1/openssl-list/ (the `-random-generators` option)

**Verified**

Node v26.13.0 in the `node:lts` image, and the image's own `openssl` 3.5.7. The two OpenSSL builds differ (3.5.9 and 3.5.7); I did not list Node's bundled generators, which `node` does not expose.

**Gotchas**

- `crypto.getFips()` is 0 because the build is not in FIPS mode, which says nothing about quality.
- The list shows available families; the default used by `RAND_bytes` is the documentation's claim and I did not trace it.

# The functional angle: a standard's constants are inputs, and an unexplained input is a hidden parameter

Draws on the Rust tip and the 2007 slides. A pure function `output = f(state, P, Q)` takes `Q` as an argument. A standard that fixes `Q` hides an argument, and the attack is a function of that hidden argument: `attack(e, output) -> candidate states`. Making `Q` an explicit, derived value (hash a public string to a point) removes the hidden parameter.

```rust
// Rust: the toy generator takes Q as a parameter; the attack function takes e as a parameter
// fn fn_next_output(state: Scalar, point_p: ProjectivePoint, point_q: ProjectivePoint) -> (Scalar, [u8; 30])
// fn fn_recover_state(secret_e: Scalar, first_output: [u8; 30], second_output: [u8; 30]) -> Option<Scalar>
```

| Language | Where the hidden choice lives | Measured |
| --- | --- | --- |
| Rust | the `Q` in the generator | 6 s to recover the state with `e` |
| C++ | the token to `random_device` | four accepted tokens on one library, two on another |
| F# | the OpenSSL under `RandomNumberGenerator` | `libcrypto.so.3` mapped |
| TypeScript | the OpenSSL bundled with Node | 3.5.9, FIPS off |

Rust is the baseline because it is the row where the hidden parameter is a number you can hold. If the parameter were visible and derived, would the attack still be a possibility?

# The security angle: an unexplained constant is a trust decision

Draws on the Rust tip. Mode B (what the language does not prevent). Bug classes: CWE-327 and CWE-338.

```rust
// Rust: if a standard hands you a constant, derive your own from a public string instead
// let point_q = hash_to_curve(b"my-application dual-ec point");   // sketch: nothing hidden, nobody knows d
```

This sketch was not run. The defense that matters is not in a language: do not use Dual_EC_DRBG, which NIST no longer lists; use one of the remaining generators (the NIST news item names three); and read where a generator's constants came from.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | a hidden `d` recovers the state from one block (measured) | nothing: constants are values | derive or audit constants |
| C++ | a token chooses the source unportably (measured) | nothing | do not pass tokens in portable code |
| F# | the chain below the API is not visible (measured) | documented as platform-defined | pin and record the OpenSSL version |
| TypeScript | the generator behind `randomBytes` is a build fact | `getFips()` | record the build |

F# is the baseline: it is the only row with nothing to configure and a whole chain to trust. If you had to prove that no hidden constant sits in your stack, where would you start?

# FAQ

**Was Dual_EC_DRBG actually backdoored?**
The 2007 slides show a back door is possible if its authors knew a relation between P and Q. NIST's 2014 item says news reports in September 2013 prompted public concern and that it recommended against use. I did not read the later papers on deployed software and make no claim about who held a relation.

**Why did the first output block give 32,766 candidates, not 32,768?**
About half of all 16-bit prefixes give an x coordinate on the curve; 32,766 is a count from this run, close to 2^15 as the slides say.

**Is this attack practical today?**
For a generator with a known back door, six seconds in Rust here. For a generator without one, no: the attack needs `e`.
