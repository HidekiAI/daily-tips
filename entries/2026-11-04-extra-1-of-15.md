Not part of the rotation. A fifteen-part special on random numbers, each mechanism measured in Rust, C++, F# and TypeScript, with real incidents quoted from primary sources. This part's claim: a seed fixes the raw stream, and almost nothing above it. The engine underneath is usually stable. The step that turns its output into a die roll, a float or a range is where libraries and versions part ways.

# What happened

**Bug class:** Bohrbug (it fails the same way whenever its trigger appears), triggered by any code path that draws a random number on one machine and not on another; the anti-pattern is a random call whose count depends on something local.

**The story, in plain words:**

In 1997 Ensemble Studios was building Age of Empires, a strategy game where each player could command hundreds of units at once. The target machine was a Pentium 90 with 16 MB of memory, connected over a 28.8 kbit/s modem. A modem that slow cannot carry the position of every archer on the map, so the team did something cleverer: they sent only the players' commands, and every computer ran the entire battle itself.

That only works if every computer computes exactly the same battle. The random numbers that decide whether a spear hits were seeded identically on every machine, so each machine drew the same sequence. When any machine's world drifted from the others, the game declared the session "out of sync" and stopped.

Early in the project, Microsoft's product manager predicted that out-of-sync would be the one bug that lasted until the very end. He was right. The cause was rarely a wrong number. It was a different *count* of numbers: one machine drew one extra random value, for a terrain sound, say, and from then on every draw on that machine was shifted by one. The team's paper describes how small the first difference could be. A deer slightly out of place when the map was generated would forage a little differently. Minutes later a villager missed with his spear, and the bug finally surfaced as a mismatch in how much food two players had.

The fix for sounds was to save the generator's state, draw whatever the sound needed, and put the state back. The lesson the team recorded was not about randomness at all. It was about bookkeeping: everyone had to write code that made the same number of calls to random, in the same order, on every machine.

The quotes, from Paul Bettner's paper with Mark Terrano, "1500 Archers on a 28.8: Network Programming in Age of Empires and Beyond" (Game Developer, March 22, 2001):

- "Tim Znamenacek, told Mark early on, 'In every project, there is one stubborn bug that goes all the way to the wire -- I think out-of-sync is going to be it.' He was right."
- "A deer slightly out of alignment when the random map was created would forage slightly differently -- and minutes later a villager would path a tiny bit off, or miss with his spear and take home no meat."
- "programmers were not used to having to write code that used the same number of calls to random within the simulation (yes, the random numbers were seeded and synchronized as well)."
- "having random terrain sounds inside the simulation would cause the games to behave differently (saving and re-seeding the pseudo-random number generator with the last random number took care of things inside the simulation that we needed to be random but not change the simulation."

Appendix A measures the same failure in Doom's source code, where one extra draw changed every shot that followed it.

## Rust: rand 0.9 kept StdRng's raw stream and changed what random_range(1..=6) returns, so a seed-42 test written on 0.8 rolls [1, 4, 2, 4, 6] instead of [4, 2, 4, 6, 3]

*Stdlib and ecosystem gems*

**Did you know**

`StdRng::seed_from_u64(42).next_u32()` returned `572990626` on rand 0.8.8, 0.9.5 and 0.10.3. The engine did not change. Five rolls of `1..=6` from that seed did change: `[4, 2, 4, 6, 3]` on 0.8.8 and `[1, 4, 2, 4, 6]` on 0.9.5 and 0.10.3. The rand 0.9.0 changelog lists the cause under "Reproducibility-breaking optimisations": `Uniform` switched to Canon's and Lemire's methods, which "breaks value stability". The `StdRng` docs warn about the rest: "even with a fixed seed, output is not portable."

**Show me**

```rust
// rand 0.9.5 (and 0.10.3), rustc 1.99.1
use rand::rngs::StdRng;
use rand::{Rng, RngCore, SeedableRng}; // on rand 0.10: use rand::{Rng, RngExt, SeedableRng};

fn main() {
    let mut mut_raw_rng = StdRng::seed_from_u64(42);
    println!("raw next_u32: {}", mut_raw_rng.next_u32()); // 572990626 on 0.8.8, 0.9.5 and 0.10.3

    let mut mut_dice_rng = StdRng::seed_from_u64(42);
    let rolls: Vec<u32> = (0..5).map(|_| mut_dice_rng.random_range(1..=6)).collect();
    println!("five d6 rolls: {:?}", rolls); // [1, 4, 2, 4, 6]; 0.8.8's gen_range gave [4, 2, 4, 6, 3]
}
```

The rename from `gen_range` to `random_range` (rand PR 1505) means a 0.8 test does not even compile on 0.9, so you notice the upgrade. You do not notice that the numbers changed underneath it. C++ has the same split between engine and distribution, and there it is in the standard itself (see the C++ tip).

**Why it matters**

A golden-file test, a replay log or a fixture built from a seed has a silent dependency on the exact distribution code of the crate version in `Cargo.lock`. A `cargo update` across a minor version that is allowed to break values turns every one of those into a failing test, or worse, into a replay that runs differently without failing.

**Chew on this**

Which of your tests assert a value produced from a seed, and is the crate version that produced it written anywhere other than the lock file? When a seeded replay must survive a library upgrade, does it belong to the library's distribution at all?

**Sources**

- https://github.com/rust-random/rand/blob/master/CHANGELOG.md (0.9.0, "Reproducibility-breaking optimisations", PR 1287; rename, PR 1505)
- https://docs.rs/rand/latest/rand/rngs/struct.StdRng.html

**Gotchas**

- On this seed 0.9's `[1, 4, 2, 4, 6]` is a new first value followed by 0.8's first four (`4, 2, 4, 6`), shifted one place. I did not trace why from the source; do not rely on the pattern.
- `ChaCha12Rng::seed_from_u64(42).next_u32()` from `rand_chacha` also gave `572990626`, on 0.3.1 and 0.9.0. The `StdRng` docs recommend the `chacha20` crate directly when you need a portable stream.
- 0.10 renamed traits again: `random_range` needs `rand::RngExt` in scope, and `next_u32` comes from `rand::Rng`.

## C++: mt19937's 10000th output is fixed by the standard and uniform_int_distribution is not, so the same seed rolls 3 5 6 2 5 on libstdc++ and 4 5 3 5 5 on libc++

*Stdlib and ecosystem gems*

**Did you know**

The C++ standard pins the engine exactly: a default-constructed `std::mt19937` must produce 4123659995 as its 10000th value, and it did on GCC 16.2, clang 19.1.7 with libstdc++, and the same clang with libc++ 19.1.7. The distributions are specified only by the probabilities they must produce, not by the algorithm. So `uniform_int_distribution<int>(1, 6)` on `mt19937(42)` rolled `3 5 6 2 5` with libstdc++ and `4 5 3 5 5` with libc++. `normal_distribution` differed too: -0.550234 against 0.515433 (the last digits of the libstdc++ value also changed with `-O2`). `uniform_real_distribution` happened to agree. This has been true since C++11, and it applies to every standard library.

**Show me**

```cpp
// C++20; g++ 16.2 and clang++ 19.1.7 (-stdlib=libstdc++ and -stdlib=libc++)
#include <cstdio>
#include <random>

int main() {
    std::mt19937 engine_for_check;               // default seed 5489
    engine_for_check.discard(9999);
    std::printf("10000th output: %u\n", static_cast<unsigned>(engine_for_check())); // 4123659995 everywhere

    std::mt19937 engine_seeded(42);
    std::uniform_int_distribution<int> die_roll(1, 6);
    for (int roll_index = 0; roll_index < 5; ++roll_index) std::printf("%d ", die_roll(engine_seeded));
    std::printf("\n");                           // libstdc++: 3 5 6 2 5   libc++: 4 5 3 5 5

    std::mt19937 engine_for_normal(42);
    std::normal_distribution<double> bell_curve(0.0, 1.0);
    std::printf("%.6f\n", bell_curve(engine_for_normal)); // libstdc++: -0.550234   libc++: 0.515433
}
```

Rust's rand shows the same split, between crate versions instead of between vendors.

**Why it matters**

A simulation or game server that records seeds for replay is portable only as far as its engine. Build the replay tool with a different standard library, a developer's libc++ build against a server built with libstdc++, and every distribution-shaped value differs while every raw engine value matches. That makes the bug look like it is in your code.

**Chew on this**

Which of your binaries share seeds across platforms: a server, a client, a test harness? If the answer is "all of them", which layer owns the mapping from raw bits to the values you store?

**Sources**

- https://eel.is/c++draft/rand.predef (the required 10000th values)
- https://eel.is/c++draft/rand.dist.general (distributions specified by their probabilities)
- https://en.cppreference.com/w/cpp/numeric/random/uniform_int_distribution

**Gotchas**

- clang uses libstdc++ by default, so it rolled exactly what GCC rolled. The libc++ result needed `apt install libc++-dev libc++abi-dev` and `-stdlib=libc++`.
- `uniform_real_distribution<double>(0, 1)` agreed on both libraries (`0.79654298428784598`) for this seed. That is a fact about this case, not a guarantee.
- `engine.discard(n)` advances the engine, but there is no standard way to save and restore a distribution's internal state except `operator<<` and `operator>>`. `normal_distribution` may cache a second value between calls.

## F#: Random(42) still runs the .NET Framework algorithm, the 21 a bug report called a typo included, while the docs tell you not to rely on it

*Type system deep cuts*

**Did you know**

Since .NET 6, `System.Random` picks its algorithm by how you construct it. `Random()` with no seed uses xoshiro (`XoshiroImpl`, checked by reflection), but `Random(42)` uses `CompatSeedImpl`. That class's source says it exists "for compatibility with cases where a seed is specified and thus the sequence produced historically could have been relied upon". It rolled `[5; 1; 1; 4; 2]` on .NET 10.0.14 and on .NET 11.0.0. It also keeps `_inextp = 21`, the value a bug report (dotnet/runtime issue 23198, "Random deviates from standard algorithm") says was mistyped from Knuth's 24. Meanwhile the documentation says you "shouldn't assume that the same seed will result in the same pseudo-random sequence in different versions of .NET".

**Show me**

```fsharp
// dotnet fsi, .NET 10.0.14 and .NET 11.0.0 (FSharp.Core 10.1 and 11.0)
let fn_impl_name (generator: System.Random) =
    // the private _impl field holds the algorithm Random delegates to
    let impl_field = typeof<System.Random>.GetField("_impl", System.Reflection.BindingFlags.NonPublic ||| System.Reflection.BindingFlags.Instance)
    impl_field.GetValue(generator).GetType().Name

let seeded = System.Random(42)
printfn "Random(42): %s" (fn_impl_name seeded)                     // CompatSeedImpl
printfn "five d6: %A" [ for _ in 1 .. 5 -> seeded.Next(1, 7) ]     // [5; 1; 1; 4; 2] on .NET 10 and 11
printfn "Random(): %s" (fn_impl_name (System.Random()))            // XoshiroImpl
printfn "Random.Shared: %s" (System.Random.Shared.GetType().Name)  // ThreadSafeRandom
```

This is the opposite of Rust's rand and C++'s two libraries: .NET kept the seeded sequence, typo included, even as it modernised everything else. It only promises less than it delivers.

**Why it matters**

The type you hold is `Random` either way, so nothing in an F# signature tells you whether a value comes from the legacy generator or from xoshiro. A seeded `Random` in a test or a procedural-generation tool is reproducible today on the strength of an implementation choice that the docs explicitly do not promise.

**Chew on this**

You now hold two contradictory sources: the runtime's source code keeps the sequence on purpose, and the documentation says not to count on it. Which one do your replays rely on, and what would tell you on the day it changes?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fundamentals/runtime-libraries/system-random ("Notes to Callers")
- https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/System/Random.CompatImpl.cs
- https://github.com/dotnet/runtime/issues/23198

**Verified**

.NET 11 was a release candidate (SDK 11.0.100-rc.3). The `_impl` field is private and could be renamed in any release.

**Gotchas**

- A class derived from `Random` gets a third algorithm, `CompatDerivedImpl`, so that its overrides are still called. Subclassing to add a helper method changes which generator runs.
- `Random.Shared` is a `ThreadSafeRandom` and cannot be seeded. Code that switches a test from `Random.Shared` to `Random(seed)` for reproducibility also switches algorithm.
- `Next(1, 7)` excludes 7. `Next(minValue, maxValue)` is half-open, unlike Effect 4's `nextIntBetween` in the TypeScript tip.

## TypeScript: Effect 4's Random.nextIntBetween(1, 7) can return 7 and Effect 3's never did, and Math.random repeats only under a V8 flag

*Stdlib and ecosystem gems*

**Did you know**

`Math.random()` cannot be seeded from JavaScript. Node 26.13 accepts V8's `--random-seed=42` on the command line, and two runs then printed the same `0.6159659788862542`. Effect does have a seedable service, and it moved between major versions. In Effect 3.22.4, `Random.nextIntBetween(1, 7)` is half-open: 60,000 draws gave only 1 to 6. In Effect 4.1.2, the bound is inclusive unless you pass `{ halfOpen: true }`, so `(1, 7)` returns 7s, and `Random.withSeed(42)` rolls `2,6,2,3,2` where Effect 3's `Random.make(42)` rolled `1,3,1,3,5`. The v3-to-v4 migration guide lists the module only as `effect/Random -> effect/Random`.

**Show me**

```ts
// Effect 4.1.2, Node v26.13.0
import { Effect, Random } from "effect";

const const_five_rolls = Effect.all(Array.from({ length: 5 }, () => Random.nextIntBetween(1, 7)));

// the same seed, run twice, gives the same rolls
console.log(await Effect.runPromise(const_five_rolls.pipe(Random.withSeed(42)))); // [ 2, 6, 2, 3, 2 ] both times
console.log(await Effect.runPromise(const_five_rolls.pipe(Random.withSeed("42")))); // [ 7, 6, 5, 7, 6 ]: 7 is in range now
// Effect 3.22.4, same intent:
//   const_five_rolls.pipe(Effect.withRandom(Random.make(42)))  -> 1,3,1,3,5, and never a 7 in 60,000 draws
// a d6 in Effect 4 is nextIntBetween(1, 6), or nextIntBetween(1, 7, { halfOpen: true })
```

```bash
# Math.random repeats only when V8 itself is seeded, on the command line
node --random-seed=42 -e 'console.log(Math.random())'   # 0.6159659788862542, every run
NODE_OPTIONS=--random-seed=42 node -e 'console.log(Math.random())'
# node: --random-seed= is not allowed in NODE_OPTIONS
```

The F# tip's `Random.Next(1, 7)` is half-open, like Effect 3. A port from .NET to Effect 4 or from Effect 3 to 4 keeps compiling and starts rolling sevens.

**Why it matters**

The type of `nextIntBetween(1, 7)` is `Effect<number>` in both versions, so tsc has nothing to say about the bound moving. A loot table, a retry jitter or a shard picker built on `(0, shardCount)` reaches one index past the end after the upgrade.

**Chew on this**

Every `nextIntBetween` call in an Effect 3 codebase is a bound that silently widens by one on upgrade. Would you rewrite each call site, or wrap the old meaning in one helper, and which of the two would a reviewer of the migration actually check?

**Sources**

- https://github.com/Effect-TS/effect-smol/blob/main/packages/effect/src/Random.ts (`nextIntBetween`, `halfOpen`, `withSeed`)
- https://github.com/Effect-TS/effect-smol/blob/main/migration/v3-to-v4.md
- https://nodejs.org/api/cli.html#node_optionsoptions (the options NODE_OPTIONS accepts)

**Gotchas**

- Effect 4's implementation is `Math.floor(r.nextDoubleUnsafe() * (maxInt - minInt + extra)) + minInt`, where `extra` is 1 unless `halfOpen`. The bounds pass through `Math.ceil` and `Math.floor` first, so `nextIntBetween(1.5, 6.5)` is 2 to 6.
- `Random.withSeed("42")` and `Random.withSeed(42)` are different streams: the string rolled `7,6,5,7,6` and the number `2,6,2,3,2`.
- Under `--random-seed=42`, a `worker_threads` worker's first `Math.random()` was the same `0.6159659788862542` as the main thread's. The flag seeds every isolate the same way.
- Without a seed, Effect's default `Random` service rolled differently on every run (`4,2,4,5,1` on one).

# The functional angle: a seeded generator is a pure function from seed to stream, and every library breaks that purity at the distribution, not at the engine

Draws on all four tips. A seed is meant to make randomness a value: same input, same output, as with any pure function. The four measurements show where that holds and where it stops.

```rust
// Rust, rand 0.9.5: the pure part, and the part a version bump may change
let raw_value = StdRng::seed_from_u64(42).next_u32();                  // 572990626 on 0.8.8, 0.9.5, 0.10.3
let first_roll = StdRng::seed_from_u64(42).random_range(1..=6_u32);    // 1 on 0.9.5, 4 on 0.8.8
```

| Language | Pure part, measured | Where purity stopped | What it costs to keep it |
| --- | --- | --- | --- |
| F# (.NET `Random(seed)`) | `[5; 1; 1; 4; 2]` on .NET 10 and 11, legacy algorithm kept on purpose | nowhere measured, but the docs disclaim it | nothing today; a documented risk on every major upgrade |
| Rust (`rand`) | engine stream `572990626` on three versions | `random_range`, between 0.8 and 0.9 | pin the crate, or map bits to values with your own code |
| C++ (`<random>`) | engine, by the standard (4123659995) | every distribution, between libstdc++ and libc++ | ship your own distribution, or one library everywhere |
| TypeScript (Effect) | `withSeed(42)` repeats within a version | the seeded stream and the bound, between Effect 3 and 4 | pin Effect; `Math.random` needs a V8 flag to be pure at all |

F# is the baseline here because it is the only one whose seeded values survived the upgrades I measured. And it is the only one that says it might not. The other three are honest that the mapping can move. Which is worse for a long-lived replay format: a guarantee nobody made, or a change that is clearly documented and still lands without a compile error?

# The security angle: a reproducible stream is a predictable stream, and a test seed is one flag away from production

Draws on the TypeScript and F# tips and runs in the "does not prevent" direction (Mode B): seeding is fine for replays, but is it secure? Bug classes: CWE-337 (Predictable Seed in Pseudo-Random Number Generator) and CWE-338 (Use of Cryptographically Weak PRNG).

```ts
// TypeScript, Node 26.13: a session id from Math.random, looks fine, is predictable when the process is seeded
const const_fn_session_id = (): string => Math.random().toString(36).slice(2);
// node --random-seed=42 server.js   (left in from a test script)
// -> the first id is the same on every restart, and every worker thread hands out the same first id as the main thread
```

The fix is not a better seed: identifiers and tokens come from a cryptographic source (`crypto.randomUUID()` or `crypto.getRandomValues` in Node), which `--random-seed` does not touch. The measured part here is `Math.random` under the flag. The claim that `crypto` ignores the flag rests on Node's documentation, not on a measurement.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript (Node) | `--random-seed` makes `Math.random` repeat across restarts and across worker threads (measured) | refuses the flag in `NODE_OPTIONS` (measured) | keep the flag out of start scripts; never draw tokens from `Math.random` |
| F# (.NET) | `Random(seed)` is the legacy algorithm, reproducible from the seed (measured) | `RandomNumberGenerator` exists for secrets (documentation) | grep for `Random(` with an argument in non-test code |
| Rust (`rand`) | a `StdRng` seeded from a constant gives the same stream every run (measured) | `ThreadRng` seeds itself from the OS (documentation) | `seed_from_u64` belongs in tests and replays only |
| C++ | `mt19937` from a fixed seed is the same stream on every library (measured) | nothing: no cryptographic generator in std | use the OS (`getrandom`) or a vetted library for anything secret |

TypeScript is the baseline for this class because its predictable mode is switched on by a deployment flag rather than by code, which no code review sees. Which of your services would you know were started with a debugging flag?

# FAQ

**Is `mt19937` itself portable across compilers?**
Yes, measured: the default engine's 10000th value was 4123659995 on GCC 16.2 and on clang 19.1.7 with either library, as the standard requires. Only the distributions differed.

**Does rand's `StdRng` promise a fixed algorithm?**
No. Its docs say its algorithm may change and its output is not portable even with a fixed seed. The engine matched across the three versions measured here; the docs do not promise that it will next time.

**Can I seed `Random.Shared` in .NET?**
No. It has no constructor you can call, and its type is `ThreadSafeRandom`. A reproducible run needs a `Random(seed)` instance passed in explicitly.

**Does `--random-seed` affect `crypto.getRandomValues` in Node?**
Not measured today. Node's crypto functions draw from the operating system's generator through OpenSSL, not from V8's `Math.random` state, per Node's crypto documentation.

# Appendix A: Doom's random numbers are a 256-byte table, and one extra draw changed every shot after it

Not part of the rotation. A real codebase that backs the opening story: id Software released Doom's source in 1997, later under the GPL, and its random number generator fits in 76 lines. The snippets below port it to Rust. The values are read from the original file, not recalled.

**Bug class:** Bohrbug, triggered by a change in the number of draws; the anti-pattern is gameplay and cosmetics sharing one sequence.

## A.1 The table

`linuxdoom-1.10/m_random.c` holds one array, `unsigned char rndtable[256]`, and two indexes into it. Measured from the file: 256 entries, but only 166 distinct values. 90 of the numbers 0 to 255 never appear (1, 5, 6, 9 and 10 among them), and 145 appears five times. The two functions are the same code over two indexes, and the original comment above them asks the question this special is about:

```c
// C, linuxdoom-1.10/m_random.c, quoted
// Which one is deterministic?
int P_Random (void)
{
    prndindex = (prndindex+1)&0xff;
    return rndtable[prndindex];
}

int M_Random (void)
{
    rndindex = (rndindex+1)&0xff;
    return rndtable[rndindex];
}
```

`P_Random` drives gameplay; `M_Random` drives things that must not affect it. `M_ClearRandom` resets both indexes to 0 when a level starts (`G_InitNew` in `g_game.c`).

## A.2 Why demos replay

A Doom demo does not store positions or random numbers. `G_WriteDemoTiccmd` stores four bytes per game tick: `forwardmove`, `sidemove`, `angleturn` and `buttons`. Replaying works only because the game then draws the same `P_Random` values in the same order, which is the Age of Empires design on one machine.

Doom Wiki's page on the random number generator (read through the Internet Archive, snapshot of 2022-04-30, because doomwiki.org itself refuses automated access) agrees with the table counts above: 0 appears twice, 1 not at all, 145 five times, mean 128.852. It adds two things the source alone does not say plainly. `M_Random` is the same table with its own independent index, used for things like sound pitch, "to maintain multiplayer synchronisation": two players may not hear the same sound, so a shared index would desynchronise them. That is the Age of Empires "save and re-seed" fix, built in as a second index. The wiki also notes the same table appears in the Hovertank 3D and Catacomb 3D code bases, and speculates (its words: "suggests") that it was the serialized output of an earlier lagged Fibonacci generator. I did not verify that speculation.

## A.3 One extra draw

`P_GunShot` in `p_pspr.c` computes pistol damage as `damage = 5*(P_Random ()%3+1);`. The Rust port below fires ten shots from a freshly cleared index, then fires them again in a build that adds one more `P_Random` call before the fourth shot, as a new cosmetic effect written against the wrong function would.

```rust
// Rust 1.99.1, reading rndtable from the original m_random.c
struct PlayRandom<'table> { table: &'table [u8], index: usize }
impl PlayRandom<'_> {
    fn next(&mut self) -> u8 { self.index = (self.index + 1) & 0xff; self.table[self.index] } // P_Random
}

fn pistol_damages(table: &[u8], shot_count: usize, extra_draw_before_shot: Option<usize>) -> Vec<u32> {
    let mut mut_random = PlayRandom { table, index: 0 }; // M_ClearRandom at level start
    (0..shot_count).map(|shot_index| {
        if extra_draw_before_shot == Some(shot_index) { mut_random.next(); } // the one new call
        5 * (u32::from(mut_random.next()) % 3 + 1)                            // damage = 5*(P_Random ()%3+1);
    }).collect()
}
// recorded build: [15, 10, 10, 5, 10, 15, 15, 5, 15, 15] total 115
// one extra draw: [15, 10, 10, 10, 15, 15, 5, 15, 15, 15] total 125, first different shot: the fourth
```

The first three shots match, and from the fourth on the two builds diverge for good: 115 points of damage against 125. In a demo, that difference decides whether a monster dies, so every later tick replays a different game. This is a Bohrbug, not a Heisenbug: nothing hides when observed. But it has the same feel, because the "harmless" edit that adds one draw also changes what happens.

## A.4 Back to the tips

All four tips are this appendix again, in library form. A seed fixes `rndindex`, and the code that turns `rndtable[rndindex]` into damage is the part that changes: `random_range` between rand versions, `uniform_int_distribution` between libstdc++ and libc++, `nextIntBetween` between Effect 3 and 4. Doom's answer was to own both the table and the mapping. Age of Empires' answer was to count the draws.
