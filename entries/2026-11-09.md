## Rust: A Relaxed fetch_add is the same lock xadd as SeqCst on x86-64, and only a SeqCst store changes the code

*Perf and memory model*

**Did you know**

On x86-64, `fetch_add(1, Relaxed)` and `fetch_add(1, SeqCst)` compile to the
same instruction, `lock xaddq`. Every load ordering is a plain `movq`. The only
place the ordering changes x86-64 code is a `SeqCst` store, which becomes
`xchgq` instead of `movq`. On `aarch64-unknown-linux-gnu`, the orderings do pick
different code, but by default both are a call: `bl __aarch64_ldadd8_relax` and
`bl __aarch64_ldadd8_acq_rel`, which are helpers that choose the LSE instruction
or an LL/SC loop at run time. Timed on arm64, the two orderings cost the same:
1.76 ns and 1.75 ns per uncontended `fetch_add`.

**Show me**

```rust
// Rust 1.99.1. Read the assembly instead of guessing it:
//   rustc -O --crate-type lib --target x86_64-unknown-linux-gnu --emit asm orderings.rs
use std::sync::atomic::{AtomicU64, Ordering};

#[no_mangle] pub fn add_relaxed(counter: &AtomicU64) -> u64 { counter.fetch_add(1, Ordering::Relaxed) }
#[no_mangle] pub fn add_seqcst(counter: &AtomicU64) -> u64 { counter.fetch_add(1, Ordering::SeqCst) }
#[no_mangle] pub fn load_seqcst(counter: &AtomicU64) -> u64 { counter.load(Ordering::SeqCst) }
#[no_mangle] pub fn store_release(counter: &AtomicU64) { counter.store(1, Ordering::Release) }
#[no_mangle] pub fn store_seqcst(counter: &AtomicU64) { counter.store(1, Ordering::SeqCst) }

// x86-64                      aarch64-unknown-linux-gnu      aarch64-apple-darwin
// add_relaxed   lock xaddq    bl __aarch64_ldadd8_relax      ldadd   (inline)
// add_seqcst    lock xaddq    bl __aarch64_ldadd8_acq_rel    ldaddal (inline)
// load_seqcst   movq          ldar (same as Acquire)         ldar
// store_release movq          stlr                           stlr
// store_seqcst  xchgq         stlr (same as Release)         stlr
```

Timed with 200 million uncontended operations each, `-O`, on arm64 (Debian in
Docker on an M-series Mac, 12 cores):

| Build | fetch_add Relaxed | fetch_add SeqCst | store Relaxed | store SeqCst |
| --- | --- | --- | --- | --- |
| Linux default (helper call) | 1.76 ns | 1.75 ns | 0.31 ns | 0.26 ns |
| Linux, `-C target-feature=+lse` (inline) | 1.75 ns | 1.74 ns | 0.32 ns | 0.28 ns |
| macOS native, rustc 1.95.0 | 1.85 ns | 1.82 ns | 0.31 ns | 0.27 ns |

**Why it matters**

`Relaxed` on a counter does not make the counter faster on x86-64, because there
is no faster read-modify-write to pick. What it does change is what the compiler
and an arm64 CPU are allowed to reorder around it. x86-64 is strongly ordered, so
an ordering that is too weak usually goes unnoticed there and only fails on arm64
servers. A benchmark on an x86-64 laptop cannot show you either the speed-up you
were hoping for or the bug.

**Chew on this**

Which `Relaxed` in your code was chosen for speed, and was it ever measured
against `SeqCst` on the CPU it actually runs on? If an ordering is wrong but
x86-64 hides it, which test of yours would ever run on arm64?

**Sources**

- https://doc.rust-lang.org/std/sync/atomic/enum.Ordering.html
- https://doc.rust-lang.org/nomicon/atomics.html
- https://doc.rust-lang.org/rustc/platform-support/aarch64-unknown-linux-gnu.html

**Verified**

The x86-64 code is assembly emitted by rustc 1.99.1 for that target and was not
run. All the timings are from arm64. The `std` docs do not say which instruction
each ordering becomes: the table above is the emitted assembly, not a promise.

**Gotchas**

- A `SeqCst` load is not dearer than an `Acquire` load on either target: both
  are `movq` on x86-64 and `ldar` on arm64.
- On arm64, a `SeqCst` store is the same `stlr` as a `Release` store. On x86-64
  it is `xchgq`, a locked instruction, and that is the one ordering cost x86-64
  actually charges you.
- The helper call is only on `aarch64-unknown-linux-gnu`. `aarch64-apple-darwin`
  inlines `ldadd`, so reading the assembly on a Mac shows you code that your
  Linux arm64 build does not have.
- Turning on LSE changed nothing measurable here (1.75 ns against 1.76 ns): the
  helper is a call with a branch that is always predicted, and the atomic itself
  costs far more. Under contention, the cache line moving between cores is the
  cost, not the ordering.

## C++: C++26 template for walks a struct's members without reflection, and its binding pack is refused outside a template

*New discoveries and currently popular patterns*

**Did you know**

C++26's expansion statement, `template for`, accepts any value that a structured
binding can take apart, an aggregate struct included. It stamps out one copy of
the loop body per member. You need no `-freflection`, but you only get the
values, not the member names. C++26 also lets a structured binding introduce a
pack, `auto [first, ...rest] = value;`, but P1061R10 only allows that inside a
templated entity, so a plain `main` cannot hold one. GCC 16.1 (2026-04-30) is the
first GCC with both; 16.2 shipped on 2026-08-07. Clang lists P1061R10 as Clang 21
and P1306R5 as Clang 23 "(Partial)". Debian's clang 19.1.7 has neither.

**Show me**

```cpp
// C++26, GCC 16.1 or later: g++ -std=c++26 walk.cpp
#include <cstdio>
#include <string>
#include <tuple>

struct Account { int id; double balance; std::string owner; };

// A binding pack has to live in a templated entity, so this needs to be a template.
template <class T>
std::size_t count_members(const T& value) {
    const auto& [...const_members] = value;
    return sizeof...(const_members);
}

int main() {
    const Account const_account{42, 99.5, "ada"};
    // Destructuring expansion: one copy of the body per member, and no reflection.
    template for (const auto& const_member : const_account)
        std::printf("member of %zu bytes\n", sizeof(const_member));    // 4, 8, 32
    std::printf("members=%zu\n", count_members(const_account));      // 3

    // Written directly in main, GCC 16 rejects this with
    // "structured binding pack outside of template":
    //   auto [first_value, ...rest_values] = std::tuple{1, 2, 3};
    // A generic lambda is a template, so the same line compiles inside one:
    const int const_sum = [](const auto& packed) {
        const auto& [const_first_value, ...const_rest_values] = packed;
        return const_first_value + (const_rest_values + ... + 0);
    }(std::tuple{1, 2, 3});
    std::printf("sum=%d\n", const_sum);                              // 6
}
```

**Why it matters**

The usual C++17 tools for code that touches every field (logging, hashing,
comparing a DTO) were `std::apply` with a fold, which works only on tuple-like
types, or a hand-written `tie()` member. With `template for`, a plain aggregate
works with no boilerplate in the struct. The template-only rule decides where
that code has to live: in a header template, or in a generic lambda.

**Chew on this**

`template for` gives you a struct's values but not their names. Which of your
per-field functions would still be right without names, and which ones would
quietly depend on the order the members are declared in?

**Sources**

- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p1306r5.html
- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2024/p1061r10.html
- https://gcc.gnu.org/gcc-16/changes.html
- https://clang.llvm.org/cxx_status.html

**Verified**

Run only on GCC 16.2.0 (`gcc:latest`). Debian 13.7's clang 19.1.7 rejects both
features, so a second compiler was not available. Clang 21 and 23 were not
checked.

**Gotchas**

- `break` works in a `template for` body and skips the remaining copies. Over
  `std::tuple{7, 3.5, "eight"}`, breaking at the `double` made two visits, not
  three.
- The rule is "templated entity", not "the initializer depends on a template
  parameter". Inside a function template, a binding pack over a local
  `std::tuple<int, int, int>` compiled and summed to 6.
- A generic lambda counts only if the pack binds its own parameter. Binding a
  captured outer `triple` failed with "'triple' is not captured", and once that
  was fixed by binding the parameter, it compiled.
- A braced list expands too, one type per element: `template for (auto literal :
  {1, 'x', 2.5})` gave `sizeof` 4, 1 and 8, so it is not an `initializer_list`.
- With `-Wall -Wextra`, GCC 16.2 warns "unused structured binding declaration" on
  `const auto& [...const_members] = value;`, although `sizeof...(const_members)`
  reads it on the next line.

**Related**

- [2026-10-31](2026-10-31.md) - C++, "C++26 reflection sees only what the
  calling code may access". There, `template for` walked reflected members with
  their names; this one walks the values without them.

## F#: int converts to float where the parameter type is known, so take_ratio 1 compiles and 1 |> take_ratio does not

*Type system deep cuts*

**Did you know**

Since F# 6, an `int32` widens to `float` (and to `int64` and `nativeint`) "when
both source and destination type are known during type inference". `take_ratio 1`,
`let ratio: float = 1`, `[1; 2; 3] : float list` and `Some 1 : float option` all
compile, without a warning by default. The pipe breaks it: `1 |> take_ratio` is
FS0001, because `|>` is a generic function, and its `'a` is already fixed to
`int` before `take_ratio`'s `float` is seen. Only `int32` widens: `take_ratio 5L`
and an `int` into a `float32` are still errors.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10, .NET 10, SDK 10.0.403): dotnet fsi convert.fsx
let take_ratio (ratio: float) = ratio

let direct = take_ratio 1                        // 1.0, no warning by default
let from_binding = let count = 7 in take_ratio count   // 7.0: a binding converts too
let as_option: float option = Some 1             // Some 1.0
let as_list: float list = [1; 2; 3]              // [1.0; 2.0; 3.0]
// let piped = 1 |> take_ratio      // FS0001: Expecting a 'int -> 'a' but given a 'float -> float'
// let halved = take_ratio (7 / 2)  // FS0001: The type 'int' does not match the type 'float'
// let from_long = take_ratio 5L    // FS0001: only int32 widens
printfn "%g %g %A %A" direct from_binding as_option as_list
```

**Why it matters**

The conversion makes calling a .NET API with integer literals less noisy, but
whether it applies now depends on how the call is written, not on the types. A
refactor from `f x` to `x |> f` can stop compiling. A function that used to take
`int` and now takes `float` keeps every call site compiling silently, so nothing
points you at the callers whose meaning changed.

**Chew on this**

If one of your domain functions changed a parameter from `int` to `float`, which
call sites would you want the compiler to flag, and would you turn on
`--warnon:3389` to get them flagged?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/whats-new/fsharp-6
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/casting-and-conversions

**Verified**

Run in the `mcr.microsoft.com/dotnet/sdk:10.0` image, which is Ubuntu, not Debian.

**Gotchas**

- `take_ratio (7 / 2)` is not converted to 3.0: it is FS0001. The expected
  `float` reaches the `/` operator, and the `int` literals do not match it, so
  integer division cannot silently become a float.
- The warnings are opt-in: `--warnon:3388,3389` reports each int-to-float use,
  and there is no warning at all without it.
- An `op_Implicit` conversion is not silent: `take_decimal 1` and an `int` into
  `Nullable<int>` both warn FS3391 by default, unlike the built-in widening.
- A two-branch `if` with `1` and `2.5` compiles when the target is annotated
  `float`, so the branches no longer have to agree with each other, only with
  the annotation.

## TypeScript: Promise.race([]) never settles, so "first replica wins" over an empty list hangs and Node exits with code 0

*Idioms and antipatterns*

**Did you know**

`Promise.race` over an empty array returns a promise that "remains pending
forever" (MDN). TypeScript types it `Promise<never>`, and `never` is assignable
to anything, so `const reply: Reply = await Promise.race([])` compiles under
`--strict`. Inside an async function, neither `.then` callback ever runs. When
nothing else keeps the event loop alive, Node 26 simply exits with code 0 and
prints nothing. Only a top-level `await` gets a diagnostic: "Detected unsettled
top-level await" and exit code 13.

**Show me**

```ts
// TypeScript 7.0.2 --strict, Node 26.13.0, run as an ES module
type Reply = { replica: string; body: string };

const const_fetch_from = (replica: string, delay_in_msec: number): Promise<Reply> =>
    new Promise((resolve) => setTimeout(() => resolve({ replica, body: "ok" }), delay_in_msec));

// "first replica to answer wins": reads well and type-checks
const const_fn_first_reply = (replicas: readonly string[]): Promise<Reply> =>
    Promise.race(replicas.map((replica, index) => const_fetch_from(replica, 10 * (index + 1))));

const const_handle_request = async (): Promise<string> => {
    const const_reply: Reply = await const_fn_first_reply([]);  // a config reload emptied the list
    return const_reply.body;
};
const_handle_request().then(() => console.log("handled"), () => console.log("failed"));
console.log("scheduled");
// Prints only "scheduled", exit code 0. The race never settles, so neither
// callback runs, and with no timer left Node has nothing to wait for and exits.
```

**Why it matters**

In a server, the event loop never runs out of work, so the process does not exit.
The request just waits forever and holds its socket, and its memory is never
freed. There is no exception, no log line and no timeout, unless someone added a
timeout outside the race. The bug only appears once the list is empty, which is
the state a test suite with a fixed replica list never reaches.

**Chew on this**

Which `Promise.race` or `Promise.any` in your code is built from a list that
comes from configuration, discovery or a filter, and which layer decides what
"no candidates" should mean?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/race
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/any
- https://tc39.es/ecma262/#sec-promise.race

**Gotchas**

- The empty-list behaviour is different for each combinator: `Promise.all([])`
  and `Promise.allSettled([])` resolve to `[]`, `Promise.any([])` rejects with an
  `AggregateError` whose `errors` is `[]`, and `Promise.race([])` never settles.
- `Promise.any([])` is "already rejected" when it is created. Created before the
  `try` that awaits it, it crashed Node 26 with an unhandled rejection and exit
  code 1 before the `await` was reached.
- `AbortSignal.any([])` is the same shape as `race`: it never aborts
  (`aborted` stayed `false`), so a combined cancel signal built from zero
  sources does not cancel anything.

# The functional angle: walking a mixed tuple is a fold that can stop only in C++, and the other three each give up something different

Draws on the C++ tip (`template for`). F# is the baseline here not because it is
functional, but because it is the one language whose answer is reflection.

The shape, in C++, F#, Rust and TypeScript alike: visit each element of
`(7, 3.5, "eight")` and stop at the first `double`.

```cpp
// C++17: a fold over && short-circuits, so the step has to return a bool to stop.
std::apply([&](const auto&... elements) {
    ((++fold_visits, !std::is_same_v<std::decay_t<decltype(elements)>, double>) && ...);
}, const_mixed);
// C++26: an expansion statement says the same with a plain break.
template for (const auto& const_element : const_mixed) {
    ++loop_visits;
    if constexpr (std::is_same_v<std::decay_t<decltype(const_element)>, double>) break;
}
// both: 2 visits
```

```fsharp
// F#: tuples do not iterate; reflection hands back obj[]
let fields = Microsoft.FSharp.Reflection.FSharpValue.GetTupleFields(box (7, 3.5, "eight"))
// Object[] holding Int32, Double, String: every field boxed
```

| Language | Functional form | Stops after the double? | What it costs |
| --- | --- | --- | --- |
| F# | `FSharpValue.GetTupleFields` | yes, as an `obj[]` loop | every field boxed into an `Object[]`, and the static types are gone |
| C++17 | `std::apply` plus a fold over `&&` | yes, 2 visits | the stop condition has to be the fold's `bool` value |
| C++26 | `template for` plus `break` | yes, 2 visits | one instantiated body per element; GCC 16 only, here |
| Rust | `for element in (7, 3.5, "eight")` | not expressible | E0277, "is not an iterator"; a `macro_rules!` per arity |
| TypeScript | `for (const element of mixed)` | yes | the element is `string \| number`, so per-position types are lost (TS2322) |

No language made the stop free and kept each element's own type, except C++ at
compile time. What would a step that needs the previous element's type, not just
its own, look like in the C++ fold, and in the `template for` loop?

# The security angle: an empty candidate list turns "first one wins" into a hang, an exception or a panic, depending on the language

Draws on the TypeScript tip, Mode C (the missing check). It runs in the insecure
direction: no language here makes the empty list a compile error.

```ts
// TypeScript: the missing check is one line, and nothing reminds you to write it
const const_fn_first_reply_checked = (replicas: readonly string[]): Promise<Reply> =>
    replicas.length === 0
        ? Promise.reject(new Error("no replicas configured"))
        : Promise.race(replicas.map((replica, index) => const_fetch_from(replica, 10 * (index + 1))));
```

Without it, every request that reaches an emptied list keeps a socket and its
memory forever: CWE-400 (uncontrolled resource consumption), with no error to
alert on.

| Language | What goes wrong on an empty list | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | `Promise.race([])` never settles | nothing: typed `Promise<never>`, so it fits any type | the `length === 0` check, and a timeout outside the race |
| F# | `Task.WhenAny([||])` | throws `ArgumentException`, "The tasks argument contains no tasks." | catching it at the request boundary instead of letting it 500 |
| Rust | `futures` 0.3.34 `select_all(empty)` | panics, "assertion failed: !ret.inner.is_empty()" | a panic in a request handler is a DoS; check before calling it |

C++ has no standard `when_any` to put in the table (from the docs, not checked
further). F# is the baseline because it fails at the call, loudly, where the
empty list is. Which of your fan-out calls would you rather have hang, throw or
panic, and is that what it does today?
