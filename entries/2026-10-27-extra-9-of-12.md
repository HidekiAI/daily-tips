**The thesis of this part: recursion instead of a loop is only safe where something guarantees the tail call, and in all four languages that guarantee depends on the build, a keyword or a runtime, never on the code alone.** The same 10-million-deep tail-recursive count ran or crashed depending on whether it was a debug or release build (Rust, C++), on whether the recursion was direct or mutual (F#), on a compiler version (C++'s `musttail`), and on which JavaScript engine ran it. A recursion that works in production and overflows in the debugger is the inverse of the usual Heisenbug, and three of the four languages produced one.

Every value below was printed by the snippet beside it, on Linux with the default 8 MiB main-thread stack: a Debian 13.7 container with rustc 1.99.1, g++ 14.2.0 and .NET SDK 10.0.402 (runtime 10.0.13, FSharp.Core 10.1.0.0, console projects), the `gcc:16` image with g++ 16.2.0, and the `node:22-trixie` image with Node 22.23.4 and effect 4.0.6.

## Rust: nothing promises a tail call, so a 10-million-deep count overflowed in debug, ran in release, and overflowed again once a Drop value was in scope

*Perf and memory model*

**Did you know**

Rust has no guaranteed tail-call elimination. A plain tail-recursive `count_down(remaining - 1, steps + 1)`, 10 million deep, aborted a debug build with "fatal runtime error: stack overflow, aborting" and completed in a release build, because LLVM turned it into a loop. Add one value with a `Drop` impl that has a visible effect (a guard that updates a counter) and the recursive call is no longer the last thing the frame does: the release build ran 10,000 deep and overflowed at 10 million. Explicit tail calls with the `become` keyword exist only as the unstable `explicit_tail_calls` feature, tracked as an experiment whose RFC is not accepted.

**Show me**

```rust
// rustc 1.99.1, edition 2021, -O (release). 8 MiB main-thread stack.
use std::sync::atomic::{AtomicU64, Ordering};

static RELEASED: AtomicU64 = AtomicU64::new(0);

struct Permit;
impl Drop for Permit {
    fn drop(&mut self) { RELEASED.fetch_add(1, Ordering::Relaxed); } // runs after the recursive call returns
}

fn count_down_holding(remaining: u64, steps: u64) -> u64 {
    let _permit = Permit; // held across the call, so the call is no longer the last thing this frame does
    if remaining == 0 { steps } else { count_down_holding(remaining - 1, steps + 1) }
}

fn main() {
    let depth: u64 = std::env::args().nth(1).and_then(|text| text.parse().ok()).unwrap_or(10_000_000);
    println!("depth {depth}: {} (released {})", count_down_holding(depth, 0), RELEASED.load(Ordering::Relaxed));
}
// release, depth 10000:    depth 10000: 10000 (released 10001)
// release, depth 10000000: fatal runtime error: stack overflow, aborting
// Without the Permit (fn count_down(remaining, steps) with the same tail call):
//   debug:   fatal runtime error: stack overflow, aborting
//   release: depth 10000000: 10000000
```

**Why it matters**

Writing a loop as recursion is a common FP move in Rust (parsers, tree walks, state machines), and it is correct exactly as long as the optimizer cooperates. The debug build is the one that overflows, so the failure shows up in tests and local runs, and the release build hides it until a refactor adds a guard, a `String` that outlives the call or a `MutexGuard`, and the elimination silently stops. F# is the language here that promises tail calls (in Release, with a caveat measured below); C++ added an opt-in guarantee; JavaScript specified one and most engines did not ship it.

**Chew on this**

Which recursive functions in your Rust code would run fine at 10 levels and overflow at 10 million, and does anything in your tests ever reach the second number?

**Sources**

- https://github.com/rust-lang/rust/issues/112788 ("Tracking Issue for Explicit Tail Calls", `#![feature(explicit_tail_calls)]`)
- https://doc.rust-lang.org/reference/destructors.html (when locals are dropped)
- https://doc.rust-lang.org/std/thread/index.html#stack-size

**Gotchas**

- A plain `String` local did not break the release elimination: the optimizer removed the allocation, so the recursion still ran 10 million deep. Only a `Drop` with an effect it could not remove (the atomic counter) did.
- Non-tail recursion can be eliminated too: `1 + nesting_depth(&text[1..])` completed 10 million deep in release, because LLVM rewrote the accumulation into a loop. That is an optimization, not a rule you can rely on.
- Spawned threads get a smaller default stack than the main thread (the `std::thread` docs give 2 MiB on Tier-1 platforms, subject to change), so the same depth overflows sooner off the main thread.

## C++: [[gnu::musttail]] made a 10-million-deep recursion run at -O0 on GCC 16, refused a destructor in scope, and GCC 14 ignored it with a warning

*New discoveries and currently popular patterns*

**Did you know**

GCC 15 added "a musttail statement attribute ... to enforce tail calls", the same contract Clang has offered as `[[clang::musttail]]`. On g++ 16.2, `[[gnu::musttail]] return count_down(remaining - 1, steps + 1);` ran 10 million deep at `-O0`, where the same code without the attribute crashed with SIGSEGV (exit 139). With a local whose destructor must run after the call, the attribute turned the silent loss of the optimization into a compile error: "cannot tail-call: other reasons". On g++ 14.2 the attribute is not known: "warning: attributes at the beginning of statement are ignored [-Wattributes]", and the `-O0` build crashed exactly as before.

**Show me**

```cpp
// C++20, g++ 16.2 (gcc:16 image). [[gnu::musttail]]: GCC 15 and later.
#include <cstdio>

struct permit { ~permit() { std::fflush(nullptr); } }; // a destructor that must run after the call

long count_down(long remaining, long steps) {
#ifdef GUARD
    permit held;
#endif
    if (remaining == 0) return steps;
#ifdef MUSTTAIL
    [[gnu::musttail]] return count_down(remaining - 1, steps + 1);
#else
    return count_down(remaining - 1, steps + 1);
#endif
}

int main() { std::printf("depth 10000000: %ld\n", count_down(10'000'000, 0)); }
// -O0:                   Segmentation fault (exit 139)
// -O2:                   depth 10000000: 10000000
// -O0 -DMUSTTAIL:        depth 10000000: 10000000
// -O0 -DMUSTTAIL -DGUARD: error: cannot tail-call: other reasons
// g++ 14.2 -DMUSTTAIL:   warning: attributes at the beginning of statement are ignored; -O0 still crashes
```

**Why it matters**

`musttail` is the first portable-ish way in C++ to write recursion that is correct at every optimization level, and the compile error on a destructor in scope is the feature, not a limitation: it catches exactly the change that broke Rust's release build above. The trap is the version split. On a compiler that does not know the attribute it degrades to a warning, so a codebase built with g++ 14 somewhere in CI keeps compiling, without the guarantee, unless `-Werror=attributes` is on. Interpreter loops and parsers written as tail-calling functions (one function per opcode) are the main users.

**Chew on this**

If a recursion in your C++ code depends on the optimizer today, would you rather mark it `musttail` and fix whatever stops compiling, or rewrite it as a loop, and does the oldest compiler in your CI matrix know the attribute?

**Sources**

- https://gcc.gnu.org/gcc-15/changes.html ("A musttail statement attribute was added to enforce tail calls")
- https://clang.llvm.org/docs/AttributeReference.html#musttail
- https://gcc.gnu.org/onlinedocs/gcc/Statement-Attributes.html

**Verified**

g++ 14.2 and 16.2 only. Clang's `[[clang::musttail]]` was not compiled (no clang in either image).

**Gotchas**

- `-O2` without the attribute also completed: the optimization exists either way, and only the guarantee is new.
- The error message for the destructor case is "cannot tail-call: other reasons", which does not name the destructor; look for any object with a non-trivial destructor alive at the call.
- `-Werror=attributes` turns the g++ 14.2 warning into a build failure ("error: attributes at the beginning of statement are ignored [-Werror=attributes]"), so an old compiler in CI cannot silently drop the guarantee.

## F#: Debug builds turn tail calls off, so a mutually recursive pair overflowed in Debug and ran in Release, while direct recursion survived both

*Perf and memory model*

**Did you know**

An F# console project's `Tailcalls` property is `false` in Debug and `true` in Release. Direct self-recursion does not need it: the compiler turns `count_down` into a loop itself, and it ran 10 million deep in both configurations. Mutual recursion does need it, because `is_even` calling `is_odd` is a call to a different function that only the runtime's `tail.` call can drop from the stack. The same `is_even 10_000_000L` printed `true` in Release and died in Debug with "Stack overflow. Repeated 130951 times". The `[<TailCall>]` attribute (FSharp.Core 8 and later) checks the other half: in a project build it warned FS3569 on `1L + count_requests (remaining - 1L)`, "has the 'TailCallAttribute' attribute, but is not being used in a tail recursive way".

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, console project; dotnet run -c Debug and -c Release.
let rec count_down (remaining: int64) (steps: int64) : int64 =
    if remaining = 0L then steps else count_down (remaining - 1L) (steps + 1L)

// Mutually recursive pair: is_even / is_odd call each other in tail position.
let rec is_even (number: int64) : bool = if number = 0L then true else is_odd (number - 1L)
and is_odd (number: int64) : bool = if number = 0L then false else is_even (number - 1L)

printfn "count_down depth 10000000: %d" (count_down 10_000_000L 0L) // Debug and Release: 10000000
printfn "is_even depth 10000000: %b" (is_even 10_000_000L)
// Release: true
// Debug:   Stack overflow. Repeated 130951 times: ...   (Tailcalls is false in Debug)

// [<TailCall>] makes the compiler check the recursion (FSharp.Core 8+):
// [<TailCall>]
// let rec count_requests (remaining: int64) : int64 =
//     if remaining = 0L then 0L else 1L + count_requests (remaining - 1L)
// warning FS3569: The member or function 'count_requests' has the 'TailCallAttribute' attribute,
//                 but is not being used in a tail recursive way.
```

**Why it matters**

This is the inverse Heisenbug: the program works in production and crashes when a developer runs it under the debugger, which is exactly when someone is trying to understand it. Debug turns tail calls off on purpose, so that every frame stays visible in the call stack, and the cost lands only on code whose stack safety depends on the runtime: mutual recursion, continuation-passing style, recursion through a function value. Rust and C++ have the same debug/release split for the opposite reason (the optimizer is off), and C++'s `musttail` is the only one of the three that removes it.

**Chew on this**

Which of your F# recursions are mutual, or recurse through a function argument, and have they ever run deep under a Debug build?

**Sources**

- https://learn.microsoft.com/dotnet/fsharp/language-reference/compiler-options (`--tailcalls[+|-]`)
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-core-tailcallattribute.html
- https://learn.microsoft.com/dotnet/api/system.reflection.emit.opcodes.tailcall

**Gotchas**

- `dotnet msbuild -getProperty:Tailcalls` printed `false` for Debug and `true` for Release on a fresh `dotnet new console -lang F#` project. Building Debug with `-p:Tailcalls=true` made `is_even 10_000_000L` print `true`.
- FS3569 is a warning; it does not stop the build and it fired in a project build. An earlier entry in this archive observed that `dotnet fsi` did not report it.
- A .NET stack overflow cannot be caught: wrapping the Debug call in `try ... with` still ended the process with "Stack overflow." and exit code 134 (see the security angle).

## TypeScript: ES2015 specified proper tail calls and V8 never shipped them, so Node threw RangeError at 6,906 frames while Effect.suspend ran a million deep

*Stdlib and ecosystem gems*

**Did you know**

ECMAScript 2015 made tail calls in strict-mode code "proper": a call in tail position must not grow the stack. WebKit's JavaScriptCore implemented it ("PTC is only available in strict mode and only for calls made from tail position", 2016); V8, and therefore Node, did not. A tail-recursive `count_down` completed 6,905 frames deep and threw at 6,906 under `node -e` on Node 22.23.4: "RangeError: Maximum call stack size exceeded". In an ES module the doubling probe passed 4,000 and failed at 8,000, and `--stack-size=4000` moved the failure to 64,000, so the limit depends on frame size and flags, not on the code. Effect's `Effect.suspend` recursion runs on Effect's own loop instead of the JavaScript stack, and counted down from 1,000,000.

**Show me**

```javascript
// JavaScript, Node 22.23.4 (V8), effect 4.0.6, ES module (strict mode).
import { Effect } from "effect"

const count_down = (remaining, steps) => remaining === 0 ? steps : count_down(remaining - 1, steps + 1) // a tail call

try { count_down(10_000, 0) }
catch (thrown) { console.log(`${thrown.constructor.name}: ${thrown.message}`) } // RangeError: Maximum call stack size exceeded
// node -e binary search: deepest that completed 6905, first that threw 6906

// The same recursion through Effect.suspend runs on Effect's run loop, not the JS stack.
const count_down_effect = (remaining, steps) =>
    remaining === 0 ? Effect.succeed(steps) : Effect.suspend(() => count_down_effect(remaining - 1, steps + 1))
console.log(Effect.runSync(count_down_effect(1_000_000, 0))) // 1000000
```

**Why it matters**

TypeScript compiles to whatever the engine runs, so "tail-recursive" in TypeScript means "fine for a few thousand levels on Node". Recursion over user-shaped data (nested JSON, a comment thread, a dependency graph) reaches that in one request. The good news compared with the other three: the failure is a catchable `RangeError`, so a server survives it (measured below). An `Effect.suspend` recursion is the stack-safe form. Rust and C++ get elimination from the optimizer, F# from the runtime in Release.

**Chew on this**

Which of your recursive TypeScript functions walk data that a client shapes, and what is the deepest input your validation lets through before the walk starts?

**Sources**

- https://tc39.es/ecma262/#sec-tail-position-calls
- https://webkit.org/blog/6240/ecmascript-6-proper-tail-calls-in-webkit/ (May 23, 2016)
- https://nodejs.org/api/cli.html (the V8 options section; `--stack-size` is a V8 flag)

**Verified**

JavaScriptCore's proper tail calls are from WebKit's documentation; Safari and `jsc` were not run here.

**Gotchas**

- `--stack-size` raises V8's limit without growing the OS thread stack: `--stack-size=60000` with a 2,000,000-deep recursion crashed Node with a segmentation fault (exit 139) instead of throwing `RangeError`.
- A recursive `Effect.flatMap` chain (each step returning the next `flatMap`) also completed 100,000 deep, because the recursion happens inside callbacks that Effect's loop calls one at a time.
- Arrow functions and `function` declarations behave the same here; strict mode is required for proper tail calls by the spec, and ES modules are always strict.

# The functional angle: the only stack-safe recursion is one whose guarantee you can name, and only F# and Effect give you one without a flag

_Draws on all four tips. The shape: a tail-recursive function run 10 million (or 1 million) deep, and the question of what guarantees it does not grow the stack._

| Language | Form | Guarantee | Where the guarantee is off |
| --- | --- | --- | --- |
| F# | direct `let rec` tail recursion | the compiler emits a loop | nowhere: 10 million deep in Debug and Release |
| F# | mutual `let rec ... and ...` | the runtime's `tail.` calls | Debug, where `Tailcalls` is `false` |
| Rust | tail recursion | none; LLVM may do it | debug builds, and any frame holding a value with a `Drop` effect |
| C++ | `[[gnu::musttail]] return ...` | the attribute, on GCC 15+ (and Clang) | GCC 14 and older, which ignore it with a warning |
| TypeScript | `Effect.suspend` recursion | Effect's run loop | nowhere measured: 1,000,000 deep |
| TypeScript | plain recursion | ES2015 says yes; V8 says no | Node, Chrome, anything V8: about 6,900 frames |

F# is the baseline because tail calls are a first-class part of its compilation model: direct recursion is free in every build, and the one place it is not (mutual recursion in Debug) is a documented build setting. The other rows show the guarantee moving outward: from the compiler (F#) to an attribute (C++), to a library's interpreter (Effect), to nothing at all (Rust, V8).

Left open: when you choose recursion over a loop for readability, how do you record which guarantee you are relying on, so the next refactor does not remove it?

# The security angle: a stack overflow from client-shaped input ends the whole process in three of the four

_Draws on all four tips, Mode A: one failure class across the languages. A recursive walk over nested input (`[[[[...`, ten million deep, one request) runs out of stack. The question is what the overflow takes down with it._

```rust
// Rust, rustc 1.99.1: the walk runs on a worker thread, so a failure should stay there
fn nesting_depth(text: &[u8]) -> usize {
    match text.first() { Some(b'[') => 1 + nesting_depth(&text[1..]), _ => 0 } // not a tail call
}
let request_body: Vec<u8> = vec![b'['; 10_000_000];
let worker = std::thread::spawn(move || nesting_depth(&request_body));
match worker.join() { Ok(depth) => println!("depth {depth}"), Err(_) => println!("worker panicked; server keeps running") }
// debug build:   thread '<unknown>' has overflowed its stack
//                fatal runtime error: stack overflow, aborting   (exit 134; the Err branch never runs)
// release build: depth 10000000 (LLVM turned this one into a loop; with a Drop guard in the frame it aborted the same way)
```

A stack overflow in Rust is not a panic: it aborts the process, so `join` never returns an `Err` and every other request on the server dies with it. That is CWE-674 (Uncontrolled Recursion) leading to a whole-service denial of service.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | deep recursion on input overflows a worker thread | aborts the whole process (exit 134), not catchable | a depth limit before recursing, or an explicit stack (`Vec`) instead of recursion |
| F# | the same in a Debug build, or any non-eliminated recursion | .NET ends the process: "Stack overflow.", exit 134, `try ... with` does not catch it | the same depth limit; do not count on Release tail calls for input-shaped recursion |
| C++ | the same | SIGSEGV (exit 139) | a depth limit; `musttail` helps only for true tail calls, and a depth walk like this one is not one |
| TypeScript | the same | throws a catchable `RangeError` ("caught RangeError", then "still alive") | catch it per request, and still limit depth, since the frames before the throw cost CPU |

Left open: which of your parsers or tree walks recurse on depth a client controls, and what is the deepest input they accept before refusing?

# FAQ

**Does Rust's release build always eliminate tail calls?**
No guarantee exists. It did here for a plain tail call and even for a non-tail `1 + f(..)`, and stopped doing it as soon as a value with an observable `Drop` was in the frame.

**Is `[[gnu::musttail]]` the same as `[[clang::musttail]]`?**
They express the same contract ("this call must be a tail call, or fail to compile"), under each compiler's own attribute namespace; only the GCC spelling was compiled here.

**Can I make an F# Debug build keep tail calls?**
Yes: `-p:Tailcalls=true` (or `<Tailcalls>true</Tailcalls>` in the project file) made the Debug build run `is_even 10_000_000L` to `true`. The cost is frames disappearing from the debugger's call stack.

**Does Safari run the plain `count_down` 10 million deep?**
That is what JavaScriptCore's proper tail calls promise in strict mode, per WebKit's 2016 post; it was not run here.
