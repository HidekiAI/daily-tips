# Daily Tips special, part 4 of 15: random numbers, or a key that could only be one of 32,767

<!-- special-nav -->
**Specials:** [<- previous: random numbers, part 3 of 15](2026-11-04-extra-3-of-15.md) | [next: random numbers, part 5 of 15 ->](2026-11-04-extra-5-of-15.md)

Not part of the rotation. Parts 1 to 3 asked whether a number lands where it should. This part asks where the generator started. A generator can be perfect and still produce one of only a few thousand possible streams, because the seed that picks the stream was small. The key looks 256 bits long, and the attacker needs fifteen.

# What happened

**Bug class:** a seed with far less entropy than the state it feeds. The code was deliberately edited, passed review, and shipped; the only symptom was that two machines generated the same keys.

**The story, in plain words:**

In 2006 a Debian maintainer was debugging programs that use OpenSSL. Valgrind, a memory checker, kept warning that OpenSSL read memory it had never written. The warnings came from code in OpenSSL's random number generator, in a file called `md_rand.c`. The maintainer asked the OpenSSL developers whether the lines could be removed and, according to the Debian wiki's own account, no objection came back. In September 2006 two lines that looked like they used uninitialised memory were commented out.

One of the two was harmless. It mixed the output buffer back into the pool, which the generator does not depend on. The other was in the function that adds entropy to the pool: it was the line that mixed in the incoming seed material. With it gone, the pool never received what was meant for it. What was left was the process ID. The process ID, per the Debian wiki, had a ceiling of 32768, so every key, on every Debian and Ubuntu machine running the changed package, was one of about thirty-two thousand.

Nothing failed. Keys were generated, certificates were signed, SSH logins worked. For almost twenty months. In May 2008 Luciano Bello found that the generator was predictable, and Debian published a security advisory on 13 May. The advisory told everyone who had generated an SSH key, an OpenVPN key, a DNSSEC key or an X.509 certificate key on an affected system to throw it away, and told them to consider every DSA key ever used on such a system compromised, because DSA needs a fresh secret random value for every signature.

The quotes, from Debian Security Advisory DSA-1571-1 (13 May 2008) and the Debian wiki page "SSLkeys" (a community page, written by the people on #debian):

- "Luciano Bello discovered that the random number generator in Debian's openssl package is predictable. This is caused by an incorrect Debian-specific change to the openssl package (CVE-2008-0166). As a result, cryptographic key material may be guessable." (DSA-1571-1)
- "all DSA keys ever used on affected Debian systems for signing or authentication purposes should be considered compromised; the Digital Signature Algorithm relies on a secret random value used during signature generation." (DSA-1571-1)
- "The broken version of OpenSSL was being seeded only by process ID." (Debian wiki)
- "PID 0 is the kernel and PID_MAX (32768) is not reached when wrapping, so there were 32767 possible random number streams per architecture." (Debian wiki)
- "Failing to call MD_Update there means that the pool will never actually get the entropy intended for it." (Debian wiki)

The wiki also says the output differed by architecture (little-endian 32-bit, little-endian 64-bit, big-endian 32-bit), so the whole set of weak keys is about 98,301 per key type and size. This part reproduces the arithmetic in four languages and shows the smaller versions of the same mistake: a seed that is the clock, a seed that has a hidden twin, and a seed that is silently cut to 32 bits. Appendix A is the same mistake from the mid-1990s.

## Rust: a 256-bit key from `StdRng::seed_from_u64(process_id)` is one of 32,768, and one key is enough to recover the pid in 10 milliseconds

*Stdlib and ecosystem gems*

**Did you know**

Seed a `StdRng` with a 15-bit process id and ask it for 32 bytes. Over all 32,768 pids the generator produced 32,768 distinct keys, so nothing collided and nothing looked wrong. Given one such key, a brute-force search over the pids found the secret pid in 10.4 ms on one release run and 4.4 ms on another. The state of `StdRng` is large. The seed you gave it decides how many different keys it can ever make.

**Show me**

```rust
// rand 0.9.5, rustc 1.99.1, release build
use rand::rngs::StdRng;
use rand::{RngCore, SeedableRng};
use std::collections::HashSet;
use std::time::Instant;

const PID_COUNT: u64 = 32768; // a 15-bit process id

fn fn_key_from_pid(process_id: u64) -> [u8; 32] {
    let mut mut_rng = StdRng::seed_from_u64(process_id);
    let mut mut_key: [u8; 32] = [0; 32];
    mut_rng.fill_bytes(&mut mut_key);
    mut_key
}

fn main() {
    let secret_pid: u64 = 20_567; // the victim
    let victim_key: [u8; 32] = fn_key_from_pid(secret_pid);

    let all_keys: HashSet<[u8; 32]> = (0..PID_COUNT).map(fn_key_from_pid).collect();
    println!("distinct 256-bit keys over all {} pids: {}", PID_COUNT, all_keys.len());

    let start: Instant = Instant::now();
    let recovered_pid: Option<u64> = (0..PID_COUNT).find(|candidate_pid| fn_key_from_pid(*candidate_pid) == victim_key);
    println!("recovered pid {:?} from the key in {:?}", recovered_pid, start.elapsed());
}
```

Output: `distinct 256-bit keys over all 32768 pids: 32768`, then `recovered pid Some(20567) from the key in 10.394875ms` (the time varies: 4.35 ms on a second run).

**Why it matters**

The distinct-key count is the trap: a test that generates a hundred keys and checks they differ passes, because 100 draws from 32,768 almost never collide. What matters is the size of the set the key came from, which no output reveals. `seed_from_u64` is the documented convenience for tests; a key goes through `rand::rng()` or the operating system, not through a number you chose.

**Chew on this**

For each key, token or nonce your service makes, can you name the size of the set it was drawn from? Which of them is seeded from something you could write down in a few digits?

**Sources**

- https://www.debian.org/security/2008/dsa-1571
- https://wiki.debian.org/SSLkeys
- https://docs.rs/rand/latest/rand/trait.SeedableRng.html

**Verified**

Measured on rustc 1.99.1 with rand 0.9.5, `cargo run --release`. The elapsed time is one run on one machine.

**Gotchas**

- `seed_from_u64` expands the 64-bit seed into the generator's seed bytes; the key stays one of at most 2^64 however many bytes you ask for, and here only 2^15 were possible.
- The 98,301 figure is the Debian wiki's arithmetic (32,767 streams times three architectures), not something I measured.

## C++: two `std::mt19937` engines seeded with `time(nullptr)` in the same second produce the same stream, and `random_device::entropy()` printed 32 on both libraries

*Idioms and antipatterns*

**Did you know**

`std::mt19937` has 19,937 bits of state and the one-argument constructor takes a single `result_type`, so the seed is one number of at most 32 bits whatever the state size. Seeded with `time(nullptr)`, two engines created in the same second gave the same first output, `2338432862` twice. `std::random_device::entropy()` returned `32` on GCC 16.2 and on libc++ 19.1.7, which is a report about the source, not a measurement of how random the next value is. Needs C++11; `std::seed_seq` accepts any number of words.

**Show me**

```cpp
// g++ -std=c++23 -O2 seeds.cpp          (GCC 16.2)
// clang++ -std=c++23 -stdlib=libc++ -O2 seeds.cpp   (clang 19.1.7)
#include <ctime>
#include <iostream>
#include <random>

int main() {
    const std::time_t clock_seconds = std::time(nullptr);
    std::mt19937 first_engine(static_cast<unsigned>(clock_seconds));
    std::mt19937 second_engine(static_cast<unsigned>(clock_seconds)); // a second start in the same second
    std::cout << "two engines seeded with time(): " << first_engine() << " " << second_engine() << "\n";

    std::random_device entropy_source;
    std::cout << "random_device::entropy() = " << entropy_source.entropy() << "\n";

    std::seed_seq eight_words{entropy_source(), entropy_source(), entropy_source(), entropy_source(),
                              entropy_source(), entropy_source(), entropy_source(), entropy_source()};
    std::mt19937 seq_engine(eight_words); // 256 bits of seed material instead of 32
    std::cout << "engine seeded from 8 words: " << seq_engine() << "\n";
}
```

Output: `two engines seeded with time(): 2338432862 2338432862` (the number depends on the second you run it), `random_device::entropy() = 32`, then a different number on every run.

**Why it matters**

The same-second collision is the classic "restart a worker in a loop" bug: two processes or two retries get identical "random" data, and the second one looks like a replay. The deeper limit is the seed's width. Even with a perfect source, `mt19937(entropy_source())` can reach at most 2^32 of the engine's possible states, so it is wrong for keys; `seed_seq` widens the input and does not make the engine cryptographic (part 5).

**Chew on this**

How many of your services start, fail and restart within a second? What did they seed with, and does the log show two of them producing the same ids?

**Sources**

- https://eel.is/c++draft/rand.eng.mers (constructor takes `result_type`)
- https://eel.is/c++draft/rand.device (`entropy()`)
- https://eel.is/c++draft/rand.util.seedseq

**Verified**

GCC 16.2.0 and clang 19.1.7 with libc++, `-O2`. The `entropy()` value is the library's return value here; I did not read the libraries to see where 32 comes from, and the C++ draft's description of `entropy()` is the cited behavior. The claim that the one-argument constructor takes a single `result_type` is the draft's.

**Gotchas**

- The 2338432862 differs every second; two engines created in the same second agree, which is the property being shown.
- `std::random_device` is allowed to be deterministic on some platforms; that is why `entropy()` exists. I did not test another platform.

## F#: `Random(1)` and `Random(-1)` give the same stream, `Random(Int32.MinValue)` equals `Random(Int32.MaxValue)`, and two `Random(Environment.TickCount)` agree

*Stdlib and ecosystem gems*

**Did you know**

On .NET 10 `Random(seed)` accepts any `int`, which is 2^32 values, but the first `Next()` was `534011718` for both `Random(1)` and `Random(-1)`, and `1559595546` for both `Random(Int32.MinValue)` and `Random(Int32.MaxValue)`. The seeded generator is the legacy one from part 1, and the constructor documents that "If a negative seed number is specified, the absolute value of the number is used", so a negative seed and its positive twin are one stream, and the most negative seed wraps onto the most positive. Two `Random(Environment.TickCount)` created in the same millisecond were identical, while two `Random()` created back to back differed.

**Show me**

```fsharp
// .NET 10.0.14, dotnet fsi
open System

let tick_seed: int = Environment.TickCount
let first_tick_random: Random = Random(tick_seed)
let second_tick_random: Random = Random(tick_seed) // a second start inside the same millisecond
printfn "Random(TickCount) twice: %d %d" (first_tick_random.Next()) (second_tick_random.Next())

let first_default_random: Random = Random()
let second_default_random: Random = Random()
printfn "Random() twice: %d %d" (first_default_random.Next()) (second_default_random.Next())

printfn "seed 1 and seed -1: %d %d" (Random(1).Next()) (Random(-1).Next())
printfn "Random(Int32.MinValue) vs Random(Int32.MaxValue): %d %d" (Random(Int32.MinValue).Next()) (Random(Int32.MaxValue).Next())
```

Output: the first two lines print equal numbers for `TickCount` and different numbers for `Random()` (the values change on every run), then `seed 1 and seed -1: 534011718 534011718` and `Random(Int32.MinValue) vs Random(Int32.MaxValue): 1559595546 1559595546`.

**Why it matters**

The seed space is 2^31 - 1 streams, not 2^32, and a negative seed from a hash or a subtraction duplicates a positive one without a warning. The default constructor is fine: .NET seeds it itself. The trap is the habit of passing a seed "to be safe", which turns a good default into a guessable one. It is also not a source for secrets: `RandomNumberGenerator` is the documented API (part 2).

**Chew on this**

Where does your code pass a value to `Random(...)`? Is it a test, or a "unique" id that is really a timestamp?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.random.-ctor
- https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/System/Random.CompatImpl.cs

**Verified**

.NET SDK 10.0, `dotnet fsi`. The absolute-value rule is the XML documentation on the `Random(int Seed)` constructor in `Random.cs` (read from the runtime repository); the collisions are measured. That `Int32.MinValue` lands on the same stream as `Int32.MaxValue` is measured; I did not read the code that makes it so.

**Gotchas**

- `Environment.TickCount` wraps and has a resolution of about 10 to 16 milliseconds on some platforms, so "the same millisecond" is a wider window than it sounds; I did not measure the resolution here.
- `Random.Shared` takes no seed (part 1).

## TypeScript: Effect's `Random.withSeed(1)` and `withSeed(4294967297)` give the same stream, and so do `1.5` and `1.9`

*Stdlib and ecosystem gems*

**Did you know**

Effect 4.1.2's `Random.withSeed` takes a number or a string and provides an ISAAC generator. Seeding with `1`, `4294967297` (2^32 + 1), `1.5` and `1.9` gave the same first three values, `335948,981815,616586`. `-1` and `2` gave different ones, as did the strings `"1"`, `"a"` and `"b"`. A millisecond timestamp seed (`Date.now()`) and the next millisecond gave different streams, so the clock is a distinct seed per millisecond, and a guessable one. The library's own doc says to "Use an unpredictable seed when uniqueness or unpredictability matters."

**Show me**

```ts
// Effect 4.1.2, Node 26.13.0: save as seeds.mts, run with node seeds.mts (types are stripped, ES module)
import { Effect, Random } from "effect"

const const_fn_first_values = async (seed: number | string): Promise<string> =>
    (await Effect.runPromise(
        Effect.all(Array.from({ length: 3 }, () => Random.nextIntBetween(1, 1000000))).pipe(Random.withSeed(seed))
    )).join(",")

for (const seed of [1, 2, 4294967297, 1.5, 1.9, -1, "1", "a", Date.now(), Date.now() + 1]) {
    console.log(JSON.stringify(seed).padEnd(16), await const_fn_first_values(seed))
}
```

Output: `1`, `4294967297`, `1.5` and `1.9` print `335948,981815,616586`; `2` prints `992593,478372,412785`; `-1` prints `712635,120646,969387`; the strings and the two timestamps print other values, the timestamps differing from each other.

**Why it matters**

A test that seeds with a large integer expecting more variety, say a 40-bit id or a database key, collapses to its low 32 bits as far as these four measurements show, and a fractional seed collapses to its integer part. Two different test cases then replay the same stream, and nothing says so. For anything unpredictable, Effect's seeded generator is the wrong service: use the platform's secure source.

**Chew on this**

Which of your fixtures derive a seed from an id larger than 32 bits? Do any two of them replay the same sequence?

**Sources**

- https://github.com/Effect-TS/effect-smol/blob/main/packages/effect/src/Random.ts
- https://en.wikipedia.org/wiki/ISAAC_(cipher)

**Verified**

Effect 4.1.2 on Node 26.13.0. The `ISAAC_CSPRNG(seed)` call was read in the installed package's `Random.js`; the mechanism that makes `1`, `2^32 + 1` and `1.5` agree (a cut to 32 bits, then an integer) is my reading of the four measurements, and I did not read the seeding code.

**Gotchas**

- The timestamp rows differ per run; only the pair's inequality is the claim.
- The name `ISAAC_CSPRNG` describes the generator family in the library, not a promise that a seed you chose is safe to use for secrets.

# The functional angle: a seed is an argument, and the argument's type decides how much randomness the function can express

Draws on all four tips. A seeded generator is a function from a seed to a stream. Its image can be no larger than its domain, so a function over a 15-bit domain has at most 32,768 streams, whatever the state size. The measurements show it in each language:

```rust
// Rust: the type says how many streams exist. A u16 seed means at most 65,536 streams, however large the state.
fn fn_stream_from_seed(seed_value: u16) -> StdRng {
    StdRng::seed_from_u64(u64::from(seed_value))
}
```

| Language | Seed type | Distinct streams reachable (measured or by the type) | Collision seen |
| --- | --- | --- | --- |
| Rust | `u64` here, a 15-bit pid in the example | 32,768 distinct keys, measured | none; recovered in 10 ms |
| C++ | `result_type` (32 bits) | at most 2^32, by the type | two `time()` seeds, same stream |
| F# | `int` | 2^31 - 1, since `-s` equals `s` | `1` and `-1`; `MinValue` and `MaxValue` |
| TypeScript | `number` or `string` | 32 bits plus integer part, by four measurements | `1`, `2^32 + 1`, `1.5`, `1.9` |

F# is the baseline because it is the only one whose seed type is a plain `int` and still collides inside its own range. If the domain of a seed function is the thing that matters, which of your seed parameters has a type narrower than the state it feeds?

# The security angle: a seed is a key, and a key's strength is the size of its smallest source

Draws on the Rust tip and the Debian incident. Mode B (what the language does not prevent). Bug classes: CWE-335 (Incorrect Usage of Seeds in Pseudo-Random Number Generator), CWE-337 (Predictable Seed in Pseudo-Random Number Generator, the clock and pid cases) and CWE-338.

```rust
// Rust: do not do this for a key
let mut mut_rng = StdRng::seed_from_u64(u64::from(std::process::id()));
// a pid is a small number: the key is one of at most as many values as there are pids
```

The Debian advisory is the field evidence: "cryptographic key material may be guessable", for keys that looked fine to every consumer. The defense is the source, not the algorithm.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `seed_from_u64` with a small value yields a small keyspace (measured) | the docs call it a convenience for tests (documentation) | use `rand::rng()` or `OsRng` for keys |
| C++ | one-word seeding caps at 2^32; `time()` repeats within a second (measured) | `seed_seq` widens the input | `std::random_device` words, or the OS directly |
| F# | `Random(seed)` collides for `s` and `-s` (measured) | `Random()` seeds itself; `RandomNumberGenerator` exists | do not seed anything secret |
| TypeScript | `withSeed` truncates, per the four measurements | the docs warn about unpredictability | `crypto.getRandomValues` for secrets |

Rust is the baseline because the incident it reproduces is the cleanest: the only change from a good key was one small seed. What is the smallest set any of your keys could have come from, and who would find it first?

# FAQ

**Was the Debian bug in OpenSSL?**
The advisory calls it "an incorrect Debian-specific change to the openssl package" and says the vulnerability "does not affect other operating systems which are not based on Debian", while noting that weak keys imported elsewhere still weaken those systems.

**Does a bigger PRNG state fix a small seed?**
No. The state is expanded from the seed, so the number of streams is at most the number of seeds, as the Rust measurement shows for 32,768 pids.

**Is `random_device` safe for seeds?**
It is the right input for a seed, which is its purpose; whether a given platform's implementation is random is what `entropy()` is for. Neither library reported 0 here.

# Appendix A: Netscape 1.1 seeded its generator from the time, the pid and the parent pid

Ian Goldberg and David Wagner, then PhD students at Berkeley, published "Randomness and the Netscape Browser" in Dr. Dobb's Journal in January 1996. They studied Netscape's SSL implementation and found that the seed for the random number generator that made the session's secret key depended on just three quantities: "the time of day, the process ID, and the parent process ID", with the time taken as seconds and microseconds. The paper gives the seeding pseudocode and says the pid and ppid "are 15bit quantities on most UNIX machines". An attacker with an account on the same machine knew the pid and ppid and could read the seconds off a packet capture, which left only the microseconds: "there are only one million possible values for it", and "Testing all one million possibilities takes about 25 seconds on an HP 712/80."

The paper's summary of the effect: "Both the international version (with 40-bit keys) and the domestic version (with 128-bit keys) are vulnerable." The attack needed no cryptanalysis of the cipher: "trying only the keys generated by the possible seed values", and they estimate "even a remote attacker" could break the encryption "in a matter of minutes". The paper reports that Netscape "responded with a new version of the browser, which uses more randomness in producing the encryption keys." This is the Debian bug a dozen years earlier, with a clock in place of a missing line.

# Appendix B: Enigma's operators typed their message key twice, and some typed "aaa"

A different "seed", from 1932. A German Enigma operator picked a three-letter message setting for each message, and the procedure then required it to be enciphered twice at the start of the message, producing a six-letter indicator. A paper on cryptocellar.org that sets out the method of the Polish mathematician Marian Rejewski (I did not identify its author) puts the procedure like this: "the German Enigma operational procedure was to prescribe for each day a set of rotor starting positions to be used by all operators to doubly encipher their own message settings (resulting in six-letter indicators)". Repeating a short value is a redundancy, and Rejewski used it: he treated the machine's six successive positions as six permutations and wrote equations for them.

The same paper records an operator habit that is the human version of part 4's weak seed. On a particular day, it says, "the indicator letter sequence syx scw occurred five times and Rejewski guessed (correctly) that these were the result of the repeated use by the operators of 'aaa' as message settings". A secret chosen by a person who finds the rule tiresome is a seed with one value.

I did not find a source in this session for the British word "cillies" for such lazy settings, so I make no claim about it.

Source: https://www.cryptocellar.org/enigma/files/rejewski-paper.pdf (read; ten pages).

# Appendix C: Pokemon Emerald seeds a 16-bit generator from a timer, and the clock-based seed is compiled out

The community decompilation of the Game Boy Advance game Pokemon Emerald (the `pret/pokeemerald` repository on GitHub) shows the game's random number generator in plain C. `Random()` is a 32-bit linear congruential step, `gRngValue = 1103515245 * gRngValue + 24691` (the macro `ISO_RANDOMIZE1`), returning the high 16 bits. `SeedRng(u16 seed)` takes a 16-bit seed. At start-up `SeedRngAndSetTrainerId` reads `REG_TM1CNT_L`, a 16-bit hardware timer counter, seeds the generator with it, and also stores it as the trainer id. So the seed is whatever the timer shows when the program reads it.

There is also a function `SeedRngWithRtc` that would seed from the cartridge clock's minute count, folded to 16 bits. In this repository it sits inside `#ifdef BUGFIX`, under the comment "FRLG commented this out to remove RTC, however Emerald didn't undo this!". I did not run the game and make no claim about what the original cartridge calls; the code shows what the decompilation builds by default.

I counted what a 16-bit seed buys, with the same step function in Rust:

```rust
// rustc 1.99.1, std only: the Pokemon Emerald Random() as in pret/pokeemerald
use std::collections::HashSet;
fn fn_next(state: &mut u32) -> u16 {
    *state = state.wrapping_mul(1103515245).wrapping_add(24691);
    (*state >> 16) as u16
}
fn main() {
    let mut first_three: HashSet<(u16, u16, u16)> = HashSet::new();
    let mut first_one: HashSet<u16> = HashSet::new();
    for seed in 0u32..=0xFFFF {
        let mut mut_state: u32 = seed;
        let triple = (fn_next(&mut mut_state), fn_next(&mut mut_state), fn_next(&mut mut_state));
        first_one.insert(triple.0);
        first_three.insert(triple);
    }
    println!("65536 possible 16-bit seeds: {} distinct first outputs, {} distinct first-three-output sequences", first_one.len(), first_three.len());
}
```

Output: `65536 possible 16-bit seeds: 45880 distinct first outputs, 65536 distinct first-three-output sequences`. Every seed gives a different sequence, so the whole game's luck is one of 65,536 streams: the same small-seed arithmetic as the Rust tip in this part, in a game people play by timing a button press.

Sources: https://github.com/pret/pokeemerald (`src/main.c`, `src/random.c`, `include/random.h`, `src/rtc.c`, read).
