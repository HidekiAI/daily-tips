**The thesis: time is a global input, and every fake clock replaces only some of the globals.** A test that "advances an hour" advanced one clock. The code under test may read a different one, and then the test passes while asserting nothing. Each tool also starts its fake time somewhere, and none of them starts at today.

| Language and tool | Fakes | Leaves real | Starts at |
| --- | --- | --- | --- |
| Rust `tokio` paused time (`start_paused`) | `tokio::time` (`Instant`, `sleep`, `timeout`, `interval`) | `std::time::Instant`, `SystemTime` | wherever the real clock was |
| C++ (no standard fake) | only code templated on your clock type | `system_clock`, `steady_clock`, and the waits inside the library | whatever you write |
| F# / .NET `FakeTimeProvider` | code that takes a `TimeProvider` | `DateTime.UtcNow`, `Stopwatch`, `Task.Delay` without the provider | **2000-01-01T00:00:00Z**, zone UTC |
| TypeScript `node:test` `mock.timers` | the `apis` you list (`setTimeout`, `Date`, ...) | `performance.now()`, `AbortSignal.timeout`, unlisted timers | **1970-01-01T00:00:00Z** for `Date` |

## Rust: tokio's paused time sleeps an hour in microseconds, and `std::time` never notices

*Stdlib and ecosystem gems*

**Did you know**

With tokio's paused time (`#[tokio::test(start_paused = true)]`, or `start_paused = true` on `#[tokio::main]`, feature `test-util`), `tokio::time::sleep(1h).await` returns at once and `tokio::time::Instant` reports 3600 s elapsed. `std::time::Instant` and `SystemTime` measured about 50 microseconds over the same "hour". So any code under test that checks expiry with `SystemTime::now()` or `std::time::Instant` sees no time pass at all, while the test believes an hour went by. Measured with tokio 1.54.1.

**Show me**

```rust
// Rust: tokio 1.54.1 (features rt, time, macros, test-util), rustc 1.95.0
use std::time::{Duration, SystemTime};

#[tokio::main(flavor = "current_thread", start_paused = true)] // the same switch #[tokio::test(start_paused = true)] uses
async fn main() {
    let tokio_start = tokio::time::Instant::now();
    let std_start = std::time::Instant::now();
    let wall_start = SystemTime::now();

    tokio::time::sleep(Duration::from_secs(3600)).await; // returns at once: paused time auto-advances

    println!("{:?}", tokio_start.elapsed());              // 3600s: tokio's clock jumped an hour
    println!("{:?}", std_start.elapsed());                // ~50us: std's monotonic clock did not
    println!("{:?}", wall_start.elapsed().unwrap());      // ~51us: neither did the wall clock

    // Code under test that reads std::time or SystemTime sees no time pass at all:
    let fn_is_expired = |issued: SystemTime| issued.elapsed().unwrap() > Duration::from_secs(1800);
    println!("{}", fn_is_expired(wall_start));            // false, "an hour" after issue
}
```

**Why it matters**

Paused time is the best tool in this table, because it makes `sleep`, `timeout` and `interval` deterministic and instant. Its edge is exact: it covers `tokio::time` and nothing else. A cache TTL written with `std::time::Instant`, a token check with `SystemTime`, or a dependency that calls either one is invisible to it, so the "expires after an hour" test passes without ever testing expiry. .NET draws the same line at "code that takes a `TimeProvider`". JS draws it at "the APIs you listed".

**Chew on this**

Which of your time checks read `std::time` directly, and which take a clock you could pause? If a test advances an hour, how would you know the code under test noticed?

**Sources**

- https://docs.rs/tokio/1.54.1/tokio/time/fn.pause.html
- https://docs.rs/tokio/1.54.1/tokio/attr.test.html (the `start_paused` option)

**Gotchas**

- `tokio::time::timeout(5s, pending())` also completes at once, as an error, with tokio's clock now at 3605 s (measured): auto-advance jumps to the next timer whenever the runtime has nothing else to do.
- `std::thread::sleep(200ms)` inside a paused runtime does not advance tokio's clock: it stayed at 3605 s (measured). Blocking time is real time.
- Rust and its crates evolve: `start_paused` needs the `test-util` feature and a `current_thread` runtime in tokio 1.54.1.

## C++: a frozen test clock passed to `condition_variable::wait_until` still waits in real time, then reports `no_timeout`

*Type system deep cuts*

**Did you know**

C++20 lets you write your own clock, and `std::chrono::is_clock_v` checks that it has the right shape. Pass a deadline on a frozen test clock to `condition_variable::wait_until`, and both libc++ and libstdc++ turn it into a real-time delta (deadline minus `frozen_clock::now()`), wait that long on a real clock, then ask your clock whether the deadline has passed. It has not, because your clock is frozen, so the call returns `cv_status::no_timeout` after 200 ms of real time. The predicate form keeps going: it re-checked every 100 real milliseconds and never timed out by itself. Measured on Apple clang 21 (libc++) and GCC 16.2 (libstdc++).

**Show me**

```cpp
// C++20: Apple clang 21 (libc++ 22) and GCC 16.2 (libstdc++)
#include <chrono>
#include <condition_variable>
#include <cstdio>
#include <mutex>
using namespace std::chrono;

// A test clock that only moves when the test moves it.
struct frozen_clock {
    using rep = long long;
    using period = std::milli;
    using duration = std::chrono::duration<rep, period>; // must be exactly duration<rep, period>
    using time_point = std::chrono::time_point<frozen_clock>;
    static constexpr bool is_steady = true;
    static inline time_point current{};
    static time_point now() noexcept { return current; }
};
static_assert(is_clock_v<frozen_clock>);

int main() {
    std::mutex gate;
    std::condition_variable signal;
    std::unique_lock lock(gate);

    const auto real_start = steady_clock::now();
    std::cv_status status = signal.wait_until(lock, frozen_clock::now() + 200ms);
    std::printf("waited %lld ms of REAL time, status %s\n",
        (long long)duration_cast<milliseconds>(steady_clock::now() - real_start).count(),
        status == std::cv_status::timeout ? "timeout" : "no_timeout");
    // waited 203 ms of REAL time, status no_timeout
    // The library turned the deadline into a real-time delta, waited it out, then asked the
    // frozen clock whether the deadline had passed. It had not, so: no_timeout.
}
```

**Why it matters**

A custom clock looks like the C++ answer to `FakeTimeProvider`, and for your own code it is: template a component on `Clock` and the test controls it. The standard library's blocking waits are not your code. They need a real clock underneath, so a fake clock makes them slower and wrong, not faster. A test of "times out after 30 s" either waits 30 real seconds or, with the predicate form, hangs. Rust's tokio fakes the waits themselves, which is the one thing a C++ clock type cannot do.

**Chew on this**

Where your C++ code waits with a deadline, which clock does the test control, and which one actually blocks? Would advancing the fake clock wake a thread that is already waiting?

**Sources**

- https://en.cppreference.com/w/cpp/thread/condition_variable/wait_until
- https://en.cppreference.com/w/cpp/chrono/is_clock

**Verified**

Apple clang 21 on this host and `docker run gcc:16`. MSVC was not tested. The "re-checked every 100 real milliseconds" claim comes from a second probe whose predicate became true after 1 s: it was evaluated 11 times on both libraries.

**Gotchas**

- `using duration = milliseconds;` with `rep = long long` passes `is_clock_v` on macOS and fails on Linux (measured: "static assertion failed"), because `milliseconds`' own `rep` is `long long` on one and `long` on the other. Spell `duration<rep, period>`.
- Advancing the frozen clock by an hour from another thread, 50 ms into the wait, did not wake the waiter early: it still returned after 205 real ms, then reported `timeout` because the fake clock had passed the deadline by then (measured on both libraries).
- `std::this_thread::sleep_until(frozen_clock + 200ms)` differs by library: libstdc++ returned after 201 real ms, and libc++ never returned, killed by a 5 s alarm (measured). libc++ keeps sleeping until your clock says the deadline has passed, and a frozen clock never says so.

## F#: `FakeTimeProvider` starts on 2000-01-01 in UTC, and `DateTime.UtcNow` never asks it

*Stdlib and ecosystem gems*

**Did you know**

.NET 8 added `TimeProvider`, and the `Microsoft.Extensions.TimeProvider.Testing` package supplies `FakeTimeProvider`. A new one reports `2000-01-01T00:00:00+00:00`, and its `LocalTimeZone` is UTC even on a machine in Chicago. `Advance(5 h)` completes a `Task.Delay(1 h, fake)` instantly. A `Task.Delay(300 ms)` without the provider was still waiting afterwards, and `DateTime.UtcNow` still read today. Only code that was handed the provider lives in fake time. Measured with package 10.11 on .NET 8.0.8.

**Show me**

```fsharp
// F#: Microsoft.Extensions.TimeProvider.Testing 10.11 on FSharp.Core 8.0 / .NET 8.0.8
#r "nuget: Microsoft.Extensions.TimeProvider.Testing"
open System
open System.Threading.Tasks
open Microsoft.Extensions.Time.Testing

let fake = FakeTimeProvider()
printfn "%s" (fake.GetUtcNow().ToString "o")   // 2000-01-01T00:00:00.0000000+00:00, not today
printfn "%s" fake.LocalTimeZone.Id             // UTC, whatever the machine's zone is

// Only code that was handed the provider sees fake time:
let with_provider = Task.Delay(TimeSpan.FromHours 1.0, fake)
let without_provider = Task.Delay(TimeSpan.FromMilliseconds 300.0)
fake.Advance(TimeSpan.FromHours 5.0)
printfn "%b" with_provider.IsCompleted     // true: an hour passed in no time
printfn "%b" without_provider.IsCompleted  // false: still waiting on the real clock
printfn "%s" (DateTime.UtcNow.ToString "o") // today: DateTime.UtcNow never asks the provider
```

**Why it matters**

The two defaults are the traps. A start date of 2000-01-01 means every certificate, token and license valid "from 2020" is not yet valid in the test, and every "older than 30 days" check is false. A UTC local zone means every DST test passes without DST: part 1's spring-forward gap and part 5's fall-back ordering never happen. Set both explicitly: `new FakeTimeProvider(startDateTime)`, then `SetLocalTimeZone`. And `TimeProvider` is opt-in per call site, so one leftover `DateTime.UtcNow` splits the code under test across two clocks.

**Chew on this**

Which of your services take a `TimeProvider`, and how many `DateTime.UtcNow` calls remain beside it? Which of your tests would change result if the fake clock started in a DST zone instead of UTC?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.timeprovider
- https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.time.testing.faketimeprovider

**Gotchas**

- `CancellationTokenSource(TimeSpan.FromSeconds 10.0, fake)` is cancelled by `Advance(10 s)` (measured): the `TimeProvider` overloads exist for timeouts too, and the parameterless constructor stays on real time.
- `fake.GetElapsedTime(start)` after `Advance(2 s)` is exactly `00:00:02` (measured), so it replaces `Stopwatch` in code that takes the provider.
- `TimeProvider.System.LocalTimeZone` was `America/Chicago` on the same run (measured), so code moved from `System` to the fake changes zone as well as clock.

## TypeScript: `mock.timers` with `Date` starts at 1970, and `performance.now()` and `AbortSignal.timeout` keep real time

*Stdlib and ecosystem gems*

**Did you know**

Node's built-in test runner has `mock.timers` (`node:test`). Enabling it with `apis: ["setTimeout", "Date"]` sets `Date.now()` to **0**, 1970-01-01T00:00:00Z, unless you pass `now`. `tick(1 h)` fires a one-hour `setTimeout` and moves `Date` to 01:00. `performance.now()` is not faked (it moved 1 real ms), `AbortSignal.timeout(1 s)` did not abort after `tick(2 s)`, and `setInterval` is not faked unless listed. Measured on Node 22.17.1.

**Show me**

```ts
// TypeScript 6.0.3 types, node:test on Node 22.17.1 (run with: node --test)
import { test, mock } from "node:test"

test("what mock.timers fakes", () => {
    const real_start = performance.now()
    mock.timers.enable({ apis: ["setTimeout", "Date"] })

    console.log(new Date().toISOString())   // 1970-01-01T00:00:00.000Z: Date starts at the epoch, not now

    let fired = false
    setTimeout(() => { fired = true }, 60 * 60 * 1000)
    mock.timers.tick(60 * 60 * 1000)
    console.log(fired, new Date().toISOString())          // true 1970-01-01T01:00:00.000Z

    console.log(Math.round(performance.now() - real_start)) // ~1: performance.now() is not faked

    const signal = AbortSignal.timeout(1000)
    mock.timers.tick(2000)
    console.log(signal.aborted)                           // false: AbortSignal.timeout is not faked either

    mock.timers.reset()
})
```

**Why it matters**

A 1970 clock is the same trap as .NET's 2000 one, one level worse: it is also part 6's "Dec 31, 1969" bug waiting for anyone who prints a date in a zone west of UTC. Worse, the faked set is a list you type. Leave out `"Date"` and a library that reads `Date.now()` stays on real time while your timers fly (the security angle below shows a JWT surviving that way). A fetch with `AbortSignal.timeout` never times out under `tick`. Pass `now: Date.now()` or a fixed date, and list every API the code under test touches.

**Chew on this**

Which time sources does your code under test read: `Date`, `performance.now()`, `AbortSignal.timeout`, a library's own clock? Does your `mock.timers.enable` call list all of them?

**Sources**

- https://nodejs.org/api/test.html#class-mocktimers
- https://nodejs.org/api/test.html#timersenableenableoptions

**Verified**

`node:test` typed with a one-line `declare module` instead of `@types/node`. Run with `node --test` on Node 22.17.1.

**Gotchas**

- `mock.timers.enable({ apis: ["Date"], now: new Date("2026-10-22T12:00:00Z") })` starts the fake clock there instead (measured).
- `setInterval` not listed in `apis` did not fire at all during `tick(5000)` (measured), because the real timer had not reached its first period yet.
- `mock.timers.reset()` restores the real functions. A test that throws before calling it leaves later tests in fake time unless it runs in a `finally` or an `afterEach`.

# The functional angle: a clock is a parameter, and every fake works only as far as the parameter was passed

Draws on all four tips. Code that reads `now()` from a global is a function with a hidden input. Each test tool either replaces the global (JS `mock.timers`, tokio paused time) or requires the input to be passed explicitly (.NET `TimeProvider`, a C++ `Clock` template parameter). The first reaches code you did not change, and leaks wherever the global is a different one. The second reaches only code you changed, but fails loudly instead of silently.

```text
// The same check written both ways, in each language's spelling (pseudocode shape, measured behaviour above)
// hidden input:   is_expired(token)        = now() - token.issued > ttl   // which now()? whichever global
// explicit input: is_expired(token, clock) = clock.now() - token.issued > ttl
// Rust: fn is_expired(token: &Token, clock: &impl Fn() -> Instant)    // or tokio::time::Instant under pause
// C++:  template <class Clock> bool is_expired(const Token&)          // Clock::now()
// F#:   let is_expired (provider: TimeProvider) token = ...           // provider.GetUtcNow()
// TS:   const fn_is_expired = (token: Token, now: () => number) => ...
```

| Language | Replaces a global | Passes a parameter | What it costs |
| --- | --- | --- | --- |
| Rust | tokio paused time (`tokio::time` only) | an `impl Fn() -> Instant` or a trait | `std::time` callers are untouched, silently |
| C++ | nothing | a `Clock` template parameter | library waits still need a real clock (C++ tip) |
| F# / .NET | nothing | `TimeProvider` | every call site must take it; a leftover `DateTime.UtcNow` splits the clock |
| TypeScript | `mock.timers` (listed APIs only) | a `now` function argument | unlisted sources keep real time, silently |

No row needs `mut` except the fake clock's own state. The asymmetry: the global-replacing tools are easier to adopt and fail silently, and the parameter-passing ones are harder to adopt and fail loudly.

Which of your expiry and timeout checks take their clock as a parameter, and which ones would a test have to replace a global to reach?

# The security angle: a test that advanced the wrong clock proves the expiry check works when it never ran

Draws on the TypeScript tip (Mode B: `mock.timers` is fine for timers, but is the expiry test it supports real?) and the F# tip's start date. The test tools work as documented. The hole is a security test that passes without testing.

**An untested expiry branch (CWE-613, insufficient session expiration, left unverified by its test).** Measured with npm `jsonwebtoken` 9.0.3 on Node 22.17.1:

```ts
// TypeScript: looks like "tokens expire after an hour, proven by a test". Proves nothing.
mock.timers.enable({ apis: ["setTimeout"] })        // Date is not listed
const token = jwt.sign({ sub: "alice" }, secret, { expiresIn: "1h" })
mock.timers.tick(2 * 60 * 60 * 1000)                // "two hours later"
jwt.verify(token, secret)                           // ACCEPTED: jsonwebtoken read the real Date.now()
// With apis ["setTimeout", "Date"] and now: Date.now(), the same test gets TokenExpiredError.
```

A test written to assert rejection fails here, and the tempting "fix" is to change the assertion rather than the mock. A test written to assert acceptance "within the hour" passes for the wrong reason forever.

| Language | What goes wrong | What the tool does | Still on you |
| --- | --- | --- | --- |
| TypeScript | `Date` not in `apis`: JWT expiry reads real time (measured) | fakes exactly the listed APIs | list `"Date"`, pass `now`, and assert the rejection case too |
| F# / .NET | fake time starts in 2000: "not yet valid" everywhere | documents the default | construct with a realistic start; test both sides of every expiry |
| Rust | a `SystemTime` expiry check under tokio pause never expires | fakes `tokio::time` only | pass the clock in, or use `tokio::time::Instant` in the check |
| C++ | a frozen clock makes library waits report `no_timeout` | nothing to fake | template the check on `Clock`, and keep library waits on real clocks |

No language is the control here, because the gap is between the test and the code, not inside either. The control is a habit: every expiry test asserts both "accepted just before" and "rejected just after", so a clock that did not move fails one of them.

Which of your security tests assert only the accepting side of an expiry, and which clock did they actually advance?

# FAQ

**Is there an incident appendix for this part?** No. Test-clock mistakes are found in review and CI, and none found has a public post-mortem with first-hand detail. The incidents in parts 1 to 3 (Azure, Cloudflare, Patriot) are the kind of bug these tools exist to catch: each one needed a date or an uptime that no ordinary test run reaches.

**Why do the fake clocks start in 1970 and 2000?** Both are "zero" for their designers: Node's `Date` mock starts at Unix time 0, the epoch from part 6's FAQ, and .NET's `FakeTimeProvider` starts at its documented default, 2000-01-01 UTC. Neither is today, and both are before most real certificates, tokens and data. Treat the start date as a test input and set it.
