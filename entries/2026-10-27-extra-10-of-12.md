**The thesis of this part: an immutable update says what changes, and the language decides what happens to everything else, including fields that did not exist when the update was written.** "Copy this, but with a different email" is the core move of immutable data, and its danger is the part you did not write. Rust's `..template` copies every unnamed field, so a field added next quarter is inherited from the template. C++'s designated initializers do the opposite and reset unnamed fields, and the compiler warns only until someone gives the field a default. F#'s anonymous-record `with` turns a misspelled field into a new field. A TypeScript spread copies the *value* of a getter, so a computed field stops being computed.

Every value below was printed by the snippet beside it, on Linux: a Debian 13.7 container with rustc 1.99.1, g++ 14.2.0 and .NET SDK 10.0.402 (runtime 10.0.13, FSharp.Core 10.1.0.0), the `gcc:16` image with g++ 16.2.0, and the `node:22-trixie` image with Node 22.23.4 and tsc 7.0.2.

| Language | Partial-update form | An unmentioned field... |
| --- | --- | --- |
| Rust | `Account { email, ..template }` | is copied (or moved) from the template, including fields added later |
| C++ | `account{.email = ...}` | is value-initialized or defaulted; `-Wextra` warns only while it has no default member initializer |
| F# | `{| session with emial = ... |}` | stays as it was, and the misspelled one is added as a new field |
| TypeScript | `{ ...session, user_id: "u2" }` | is copied as a value, so a getter becomes frozen, writable data |

## Rust: ..template copies every field you did not name, so a can_export flag added in v2 is inherited by every user built from the ops account

*Idioms and antipatterns*

**Did you know**

Struct update syntax, `Account { email: ..., ..admin_template }`, fills every field you did not write from the base value. That includes fields added to the struct after the line was written: when `can_export: bool` was added, `new_user` built from the ops account's template came out with `can_export: true`, and nothing warned. The update also moves: without `.clone()`, the non-`Copy` fields move out of the base, so `admin_template.email` is "E0382: borrow of moved value", while the `Copy` field `quota_mb` stays readable. `..Default::default()` is the other choice of base, and it gave the new field `false`.

**Show me**

```rust
// Rust, rustc 1.99.1: struct update syntax from a template.
#[derive(Debug, Clone)]
struct Account {
    email: String,
    can_export: bool, // added in v2; every `..template` site picks it up without a word
    quota_mb: u32,
}

fn main() {
    let admin_template = Account { email: String::from("ops@example.com"), can_export: true, quota_mb: 10_000 };
    // v1 code: "new users look like the ops account, with their own email"
    let new_user = Account { email: String::from("guest@example.com"), ..admin_template.clone() };
    println!("{new_user:?}"); // Account { email: "guest@example.com", can_export: true, quota_mb: 10000 }
    // The moved-from case: without clone(), only the non-Copy fields actually move.
    let partial = Account { quota_mb: 1, ..admin_template };
    println!("{:?} {}", partial.email, admin_template.quota_mb); // "ops@example.com" 10000: quota_mb is Copy
    // println!("{}", admin_template.email); // E0382: borrow of moved value: `admin_template.email`
}
```

**Why it matters**

The base of a struct update is a policy decision that the syntax hides: `..Default::default()` says "new fields start safe", `..some_existing_value` says "new fields copy whatever that value has". The second is the one that bites when the struct grows, because the compile is clean and the field is correct for the template, just not for the copy. C++'s designated initializers reset instead of copying, which fails the other way; F# nominal records reject an unknown label at compile time, which is the strictest of the four.

**Chew on this**

Which of your `..something` struct updates use a live value as the base rather than `Default::default()`, and which fields of that value would you not want copied if they were added tomorrow?

**Sources**

- https://doc.rust-lang.org/reference/expressions/struct-expr.html#functional-update-syntax
- https://doc.rust-lang.org/book/ch05-01-defining-structs.html#creating-instances-from-other-instances-with-struct-update-syntax
- https://doc.rust-lang.org/error_codes/E0382.html

**Gotchas**

- `..Default::default()` gave `Account { email: "guest@example.com", can_export: false, quota_mb: 0 }`: the new field took its default, which is the safer base for anything permission-shaped.
- rustc printed "warning: field `can_export` is never read" for this snippet, because a derived `Debug` does not count as a read; it is unrelated to the update.
- The partial move is per field: reading `admin_template.quota_mb` after the move compiled, reading `admin_template.email` did not, and using `admin_template` as a whole is also a moved-value error.

## C++: designated initializers reset the fields you leave out, and -Wextra stops warning the moment the field gets a default

*Idioms and antipatterns*

**Did you know**

A C++20 designated initializer does not copy anything from anywhere: an omitted member is value-initialized, or takes its default member initializer. g++ 14.2 and g++ 16.2 with `-Wall -Wextra` warned "missing initializer for member 'account::can_export' [-Wmissing-field-initializers]" when the field had no default. Give the struct defaults (`bool can_export = false;`), and the same omission compiled with no warning at all. The other C++ partial update, copy-then-modify (`account copied = admin_template; copied.email = ...;`), behaves like Rust's `..template`: it kept `can_export` as `1`. Designators must also follow declaration order: `{.quota_mb = 5, .email = "x"}` is an error in C++, though not in C.

**Show me**

```cpp
// C++20 designated initializers, g++ 14.2 -Wall -Wextra (g++ 16.2: same).
#include <cstdio>
#include <string>

struct account {             // v1 had only email and quota_mb
    std::string email;
    bool can_export;         // added in v2, no default
    unsigned quota_mb;
};

struct account_v3 {          // the same struct after someone added defaults
    std::string email;
    bool can_export = false;
    unsigned quota_mb = 100;
};

int main() {
    const account admin_template{.email = "ops@example.com", .can_export = true, .quota_mb = 10000};

    // A designated initializer does not copy omitted fields from anywhere: they are value-initialized.
    account new_user{.email = "guest@example.com", .quota_mb = admin_template.quota_mb};
    std::printf("%d %u\n", new_user.can_export, new_user.quota_mb); // 0 10000, with a -Wextra warning

    // Give the fields defaults, and the warning is gone.
    account_v3 new_user_v3{.email = "guest@example.com"};
    std::printf("%d %u\n", new_user_v3.can_export, new_user_v3.quota_mb); // 0 100, no warning

    // Copy-then-modify is the other partial update: it keeps every field, including new ones.
    account copied = admin_template;
    copied.email = "guest@example.com";
    std::printf("%d\n", copied.can_export); // 1
}
```

**Why it matters**

C++ gives you both failure modes of a partial update and lets you pick by syntax: designated initializers forget the unmentioned fields, copy-then-modify remembers all of them. The warning that protects the first form is tied to the absence of a default, so the routine cleanup "give every member a default" switches off the one diagnostic that would have pointed at each update site when a field was added. Rust has no equivalent of the "reset" form except `..Default::default()`, which says so in the source; F#'s record `with` and TypeScript's spread both copy.

**Chew on this**

Which of your structs got default member initializers recently, and how many designated-initializer sites lost their "missing initializer" warning on that day?

**Sources**

- https://en.cppreference.com/w/cpp/language/aggregate_initialization (designated initializers, C++20)
- https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html#index-Wmissing-field-initializers
- https://en.cppreference.com/w/cpp/language/data_members#Member_initialization

**Verified**

g++ 14.2 and 16.2 only; Clang's `-Wmissing-field-initializers` rules for designated initializers were not checked.

**Gotchas**

- The positional form warns the same way: `account positional{"guest@example.com", true};` printed `quota_mb=0` with the same `-Wmissing-field-initializers` warning.
- Out-of-order designators fail: "designator order for field 'account::email' does not match declaration order in 'account'", so reordering struct members breaks every designated initializer that named both.
- `const account admin_template` cannot be updated in place, which is what pushes code toward the copy-then-modify form and its "keep everything" behaviour.

## F#: a misspelled field in an anonymous record's `with` adds a new field instead of failing, and the email you meant to change stays as it was

*Type system deep cuts*

**Did you know**

A nominal record update with a typo fails: `{ account with emial = "new@example.com" }` is "FS1129: The record type 'Account' does not contain a label 'emial'". The anonymous-record form is designed to extend records, so the same typo compiles: `{| session with emial = "new@example.com" |}` produced `{| email = "old@example.com"; emial = "new@example.com"; is_admin = false |}`, and `updated.email` was still the old address. It is caught only when the result meets a type that names the exact fields: passing it to a function taking `{| email: string; is_admin: bool |}` is "FS0001: This anonymous record has an extra field. Remove field 'emial'". F# 8's nested update, `{ tenant with limits.max_upload_mb = 50 }`, copied the inner record and shared the untouched outer fields.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, dotnet fsi.
type Account = { email: string; is_admin: bool }
let account = { email = "old@example.com"; is_admin = false }
// let renamed_typo = { account with emial = "new@example.com" }
//   error FS1129: The record type 'Account' does not contain a label 'emial'.

let session = {| email = "old@example.com"; is_admin = false |}
let updated = {| session with emial = "new@example.com" |}   // anonymous record: the typo ADDS a field
printfn "%A" updated              // {| email = "old@example.com"; emial = "new@example.com"; is_admin = false |}
printfn "email still: %s" updated.email // email still: old@example.com

// Nested copy-and-update (F# 8): one expression updates a field two levels down.
type Limits = { max_upload_mb: int; max_requests: int }
type Tenant = { name: string; limits: Limits }
let tenant = { name = "acme"; limits = { max_upload_mb = 10; max_requests = 100 } }
let raised = { tenant with limits.max_upload_mb = 50 }
printfn "limits shared? %b" (obj.ReferenceEquals(tenant.limits, raised.limits)) // false: a new Limits
printfn "name shared? %b" (obj.ReferenceEquals(tenant.name, raised.name))       // true: the string is reused
```

**Why it matters**

F# is the language whose nominal records already solved the misspelled-update problem (FS1129), which makes the anonymous-record exception easy to miss: anonymous records are common at boundaries (JSON shaping, ad-hoc DTOs, test data), and their copy-and-update is specified to add fields, so a typo is a legal extension. Inference carries the extra field along until something annotated rejects it, which may be the serializer, or nothing. TypeScript's object spread has the same "typo adds a property" behaviour, measured in this archive's security lens; Rust struct updates and C++ designated initializers reject unknown field names.

**Chew on this**

Where do your anonymous records flow after a `with`: into a function with an annotated parameter that would reject an extra field, or into a serializer that would happily write it?

**Sources**

- https://learn.microsoft.com/dotnet/fsharp/language-reference/anonymous-records ("unlike named records, anonymous records allow you to construct entirely different forms with copy and update expressions")
- https://learn.microsoft.com/dotnet/fsharp/language-reference/copy-and-update-record-expressions
- https://learn.microsoft.com/dotnet/fsharp/whats-new/fsharp-8 (nested record field copy and update; design note FS-1049 in fslang-design)

**Gotchas**

- The nominal-record error lists suggestions ("Maybe you want one of the following:"), so the typo is cheap to fix there; the anonymous form never gets that far.
- Nested copy-and-update allocates a new record at every level it passes through: `raised.limits` was a new object, while `raised.name` was the same string instance.
- An anonymous record with an extra field is a different type, so two values that look alike in `%A` output can fail to compare or to unify.

## TypeScript: spreading an object calls its getters once and copies the results, so a computed is_expired froze at false and became writable

*Idioms and antipatterns*

**Did you know**

Object spread copies own enumerable properties by reading them, so a getter is called once and its result is stored as plain data. After `const renamed = { ...session, user_id: "u2" }` and ten seconds of clock movement, `session.is_expired` was `true` and `renamed.is_expired` was still `false`. The property descriptor on the copy was `{"value":false,"writable":true,...}`, and tsc 7.0.2 accepted `renamed.is_expired = true`, while the same assignment on the original object is "TS2540: Cannot assign to 'is_expired' because it is a read-only property". Spreading a class instance drops its prototype the same way: `instanceof` was `false` and the method was `undefined`.

**Show me**

```typescript
// TypeScript, tsc 7.0.2 --strict, Node 22.23.4.
let clock_ms = 1_000
const session = {
    user_id: "u1",
    issued_at_ms: 0,
    get is_expired(): boolean { return clock_ms - this.issued_at_ms > 5_000 }, // computed on every read
}
const renamed = { ...session, user_id: "u2" }   // the getter is CALLED here, and its result copied as plain data
clock_ms = 10_000
console.log("original is_expired:", session.is_expired)   // true: recomputed
console.log("spread copy is_expired:", renamed.is_expired) // false: frozen at copy time
console.log("descriptor:", JSON.stringify(Object.getOwnPropertyDescriptor(renamed, "is_expired")))
// descriptor: {"value":false,"writable":true,"enumerable":true,"configurable":true}
renamed.is_expired = true                                  // and it is writable now; on session this is TS2540
console.log("assignable after spread:", renamed.is_expired) // true

class Quota { constructor(readonly used_mb: number, readonly limit_mb: number) {} remaining_mb(): number { return this.limit_mb - this.used_mb } }
const quota = new Quota(10, 100)
const bumped = { ...quota, used_mb: 20 }
console.log("instanceof after spread:", bumped instanceof Quota, "| has method:", typeof (bumped as { remaining_mb?: unknown }).remaining_mb)
// instanceof after spread: false | has method: undefined
```

**Why it matters**

Spread is the standard immutable update in TypeScript, and it is a snapshot of *values*: anything an object computes (an expiry, a derived total, a lazily loaded field) stops being computed in the copy, and the type system follows the runtime by dropping `readonly` from what used to be a getter. F# records have no getters in the data (members are recomputed on the copy), Rust struct updates copy fields and leave methods on the type, and C++ copy-then-modify copies members and keeps member functions. Only the JavaScript object model mixes data and computation in the thing being copied.

**Chew on this**

Which objects in your code are both updated by spread and carry a getter, and does any caller of the copy depend on that getter still being live?

**Sources**

- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Operators/Spread_syntax#spread_in_object_literals
- https://tc39.es/ecma262/#sec-copydataproperties
- https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties

**Gotchas**

- Spread is shallow: after `const raised = { ...tenant, name: "acme-2" }`, setting `raised.limits.max_upload_mb = 50` changed `tenant.limits` too (`shared: true`).
- The `(bumped as { remaining_mb?: unknown })` cast in the snippet exists only to probe the missing method; without it tsc reports "TS2339: Property 'remaining_mb' does not exist on type '{ limit_mb: number; used_mb: number; }'", because spread types exclude class methods.
- Copying the property descriptors instead, `Object.create(Object.getPrototypeOf(session), Object.getOwnPropertyDescriptors(session))`, keeps the getter itself: that copy read `is_expired` as `true` after the clock moved.

# The functional angle: every partial update needs a rule for the fields it does not name, and only F# nominal records refuse to guess

_Draws on all four tips. The shape: copy a value, change one field, and ask what happened to a field that was added to the type after the update was written, and to a field whose name was mistyped._

| Language | Update form | Field added later | Misspelled field |
| --- | --- | --- | --- |
| F# | `{ account with ... }` (nominal) | copied from the original | FS1129 at compile time |
| F# | `{| session with ... |}` (anonymous) | copied from the original | added as a new field; caught only by an annotated type (FS0001) |
| Rust | `Account { ..template }` | copied (or moved) from the template, silently | compile error: no such field |
| Rust | `Account { ..Default::default() }` | takes its `Default` | compile error |
| C++ | designated initializer | value-initialized or defaulted; warns only without a default member initializer | compile error |
| C++ | copy-then-modify | copied | compile error |
| TypeScript | `{ ...value, field: x }` | copied, getters as frozen values | added as a new property; caught only by an annotated target |

F# nominal records are the baseline because they are the one form that is strict in both columns that can be checked: a misspelled label does not compile, and the copy is explicit about its source. Every other row makes one choice silently. The useful asymmetry: "copy the rest" (Rust template, C++ copy, F#, TypeScript) fails by inheriting something you did not want, while "reset the rest" (C++ designated) fails by forgetting something you did, and only the second has a warning, which defaults turn off.

Left open: for a type that gains a permission-like field, which default is safer at your update sites, "copy from the original" or "reset to the type's default", and does your syntax let you choose?

# The security angle: the fields a partial update did not mention are where permissions leak and expiries stop

_Draws on the Rust and TypeScript tips, Mode B: both tips show an update that keeps a field the author never thought about. When the field is a permission or an expiry, "kept" means "granted" or "never expires"._

```rust
// Rust, rustc 1.99.1: v2 added can_export; the v1 onboarding code was never touched
let new_user = Account { email: String::from("guest@example.com"), ..admin_template.clone() };
// Account { email: "guest@example.com", can_export: true, quota_mb: 10000 }: the guest can export
```

```typescript
// TypeScript, Node 22.23.4: a session copied with spread to change one field
const renamed = { ...session, user_id: "u2" }
clock_ms = 10_000
renamed.is_expired // false, forever: the expiry check was a getter, and the copy holds its old value
```

The Rust case is CWE-269 (Improper Privilege Management): a privilege added to the type flows to every account built from a privileged template, and the compiler has no way to know that is wrong. The TypeScript case is CWE-613 (Insufficient Session Expiration): the copy carries a snapshot of "not expired" taken when it was made.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `..template` grants a new permission field to every copy (CWE-269) | copies it; no lint | build from `Default::default()` (or a constructor) and name every permission explicitly |
| TypeScript | a spread freezes an expiry getter (CWE-613) | copies the value; drops `readonly` | compute expiry from a stored timestamp at the check, never from a copied derived field |
| C++ | copy-then-modify from an admin object keeps its flags | copies every member | construct from defaults with designated initializers, and keep the `-Wextra` warning by not defaulting permission fields |
| F# | an anonymous-record typo leaves the old value in place (the update silently did not happen) | adds a field; FS0001 only at an annotated boundary | annotate the types of security-relevant anonymous records |

Left open: which of your "create from template" paths would hand a new permission to every account they create, and who would notice?

# FAQ

**Does `..Default::default()` in Rust have the same inheritance problem?**
No: with `#[derive(Default)]`, the new `can_export` field came out `false` and `quota_mb` came out `0`. The base you name decides what new fields get.

**Is a TypeScript spread a deep copy?**
No. Nested objects are shared: changing `raised.limits.max_upload_mb` on the copy changed `tenant.limits` on the original as well.

**Does F#'s nested `{ tenant with limits.max_upload_mb = 50 }` copy the whole tree?**
It copies each record on the path it updates and shares the rest: `limits` was a new object, `name` was the same instance.

**Why did g++ warn about the omitted field in one struct and not the other?**
`-Wmissing-field-initializers` (enabled by `-Wextra`) reports members with no initializer at all; a member with a default member initializer has one, so omitting it is not reported.
