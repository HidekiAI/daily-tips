# Daily Tips special, part 7 of 15: random numbers, or two copies of one generator

<!-- special-nav -->
**Specials:** [<- previous: random numbers, part 6 of 15](2026-11-04-extra-6-of-15.md) | [next: random numbers, part 8 of 15 ->](2026-11-04-extra-8-of-15.md)

Not part of the rotation. Part 6 had several threads share one generator. This part has several processes, or several restores of one machine, each with their own copy of the same generator state. A copy of a generator is a generator that will say exactly what the original says next, and the program has no way to notice.

# What happened

**Bug class:** reused generator state after a copy of the process or machine (fork, VM snapshot, container checkpoint). The code is correct in isolation; the environment copied it (CWE-336, same seed in a PRNG, and CWE-323, reusing a nonce).

**The story, in plain words:**

In 2010 two researchers at the University of California, San Diego, Thomas Ristenpart and Scott Yilek, asked a question about virtual machines. A VM snapshot saves the whole state of a running machine and can bring it back later, as many times as you like. Software tends to assume its state moves only forward. A random number generator is exactly such state. If you restore a snapshot twice, does the software draw the same "random" numbers both times?

They tried it with web browsers. They started a browser, took a snapshot of the VM, and then did the same thing twice: reset the VM, open a secure connection to one server; reset the VM again, open one to a second server. During a TLS connection the browser picks a secret number, the premaster secret, that protects the whole session. Firefox on both Windows and Linux sent the same premaster secret to both servers in all three trials. The only thing that changed the result was the user moving the mouse: Firefox mixes in new entropy "every 100 mouse events", and with a hundred events between reset and connection, the secrets differed. Chrome on Linux repeated the secret too, if the browser had already made one secure connection before the snapshot was taken.

Then they tried servers. An Apache server using OpenSSL seeds its generator once in the parent process, then forks child processes to handle requests, and each child adds only "the time, process ID, and some of the runtime stack". Restored from the same snapshot, with the same clock, those are the same. The paper shows how repeated randomness in the server's digital signature scheme (DSA) lets an attacker who sees two signatures extract the server's private signing key. The server never knew it had been rewound.

The same hazard exists without a hypervisor. The OpenSSL wiki says it in two sentences: "One of the most important issues in the proper cryptographic use of random numbers is that random numbers must not be reused. Since the UNIX fork() system call duplicates the entire process state, a random number generator which does not take this issue into account will produce the same sequence of random numbers in both the parent and the child (or in multiple children), leading to cryptographic disaster."

The quotes:

- "We exhibit such VM reset vulnerabilities in widely-used TLS clients and servers: the attacker takes advantage of (or forces) snapshot replay to compromise sessions or even expose a server's DSA signing key." (Ristenpart and Yilek, NDSS 2010)
- "For Firefox on Windows or Linux, the same PMS was sent to both servers in all 3 trials." (same; PMS is the premaster secret)
- "This is because Firefox folds new entropy into the RNG every 100 mouse events." (same)
- "At this point each child process has its own copy of the now-initialized RNG state." (same, on Apache)
- "OpenSSL cannot fix the fork-safety problem because its not in a position to do so." (OpenSSL wiki, "Random fork-safety", a read-only archive)

The measurements below show the copy in four languages, including a library whose fork protection was removed on purpose.

## Rust: after `fork()` a `rand` 0.9 `ThreadRng` repeats the parent's next 300 draws, while 0.8.8 repeated 63

*Stdlib and ecosystem gems*

**Did you know**

rand 0.8 registered a fork handler so that a forked child's `thread_rng()` reseeds itself. The handler only takes effect when the generator's buffered block of random words runs out, so the child still repeated the parent's next 63 draws. rand 0.9 removed the protection: its changelog says "Remove fork-protection from `ReseedingRng` and `ThreadRng`. Instead, it is recommended to call `ThreadRng::reseed` on fork." Measured on 0.9.5, the child and the parent agreed on all 300 of the 300 draws taken after the fork. A `StdRng` copied across the fork agreed on all 300 in both versions, as it must.

**Show me**

```rust
// rand 0.9.5 (and 0.8.8 with thread_rng), libc 0.2, rustc 1.99.1
use rand::{RngCore, SeedableRng};
use std::fs;

const DRAW_COUNT: usize = 300;

fn main() {
    let mut mut_seeded = rand::rngs::StdRng::seed_from_u64(42);
    let mut mut_thread_rng = rand::rng(); // rand 0.8: rand::thread_rng()
    mut_seeded.next_u32();
    mut_thread_rng.next_u32(); // initialize the thread generator before the fork
    let child_pid: libc::pid_t = unsafe { libc::fork() };
    let seeded_draws: Vec<u32> = (0..DRAW_COUNT).map(|_| mut_seeded.next_u32()).collect();
    let thread_draws: Vec<u32> = (0..DRAW_COUNT).map(|_| mut_thread_rng.next_u32()).collect();
    if child_pid == 0 {
        fs::write("/tmp/child_draws.txt", format!("{:?}\n{:?}", seeded_draws, thread_draws)).unwrap();
        std::process::exit(0);
    }
    unsafe { libc::waitpid(child_pid, std::ptr::null_mut(), 0) };
    let child_text: String = fs::read_to_string("/tmp/child_draws.txt").unwrap();
    let mut child_lines = child_text.lines();
    let fn_equal_prefix = |parent_draws: &Vec<u32>, child_line: &str| -> usize {
        let child_draws: Vec<u32> = child_line.trim_matches(|bracket| bracket == '[' || bracket == ']').split(", ").map(|word| word.parse().unwrap()).collect();
        parent_draws.iter().zip(child_draws.iter()).take_while(|(parent_value, child_value)| parent_value == child_value).count()
    };
    println!("StdRng      parent and child agree on the first {} of {} draws", fn_equal_prefix(&seeded_draws, child_lines.next().unwrap()), DRAW_COUNT);
    println!("thread rng  parent and child agree on the first {} of {} draws", fn_equal_prefix(&thread_draws, child_lines.next().unwrap()), DRAW_COUNT);
}
```

Output on rand 0.9.5: `StdRng      parent and child agree on the first 300 of 300 draws`, `thread rng  parent and child agree on the first 300 of 300 draws`. On rand 0.8.8: the `StdRng` line the same and `thread rng  parent and child agree on the first 63 of 300 draws`.

**Why it matters**

The 63 is the useful number: fork protection that fires at the next refill is not protection for the draws already buffered, so a child that draws one nonce right after the fork can repeat its parent's. The 0.9 change turns a partial guard into none and moves the duty to the caller. A pre-fork server, a job runner that forks workers, and a test harness that forks per case all hold the parent's generator in the child.

**Chew on this**

After your service forks, what does the child do first: draw a random value, or reseed? Where in your code is the call that reseeds?

**Sources**

- https://github.com/rust-random/rand/blob/master/CHANGELOG.md (0.9.0, "Remove fork-protection", PR 1379)
- https://wiki.openssl.org/index.php/Random_fork-safety

**Verified**

rand 0.9.5 and 0.8.8, libc 0.2, in the `rust:1` Docker image (rustc 1.99.1). The explanation that 0.8's fork check fires at the next buffer refill is my reading of the 63-draw result, and I did not read the rand source.

**Gotchas**

- `libc::fork` is `unsafe` and unsound in a multithreaded Rust program; the probe is single-threaded on purpose.
- The exact number of agreeing draws depends on how much of the buffered block was used before the fork.

## C++: `fork()` copies a seeded `std::mt19937` exactly, so parent and child both print `3421126067`, while `std::random_device` differs

*Idioms and antipatterns*

**Did you know**

`fork()` duplicates the process, including the engine's 2.5 KB of state. After seeding `mt19937` with 42 and drawing once, the child and the parent each drew `3421126067` next, on GCC 16.2 and on libc++ 19.1.7. A `std::random_device` read in the same two processes returned different values each time, because it asks the operating system, which keeps its own state.

**Show me**

```cpp
// g++ -std=c++23 -O2 forked.cpp   (and clang++ -std=c++23 -stdlib=libc++ -O2 forked.cpp)
#include <iostream>
#include <random>
#include <sys/wait.h>
#include <unistd.h>

int main() {
    std::mt19937 engine(42);
    engine(); // advance once so the state is not the fresh seed
    std::random_device entropy_source;
    pid_t child_pid = fork();
    if (child_pid == 0) {
        std::cout << "child : engine " << engine() << "  random_device " << entropy_source() << std::endl;
        _exit(0);
    }
    waitpid(child_pid, nullptr, 0);
    std::cout << "parent: engine " << engine() << "  random_device " << entropy_source() << std::endl;
}
```

Output (GCC 16.2): `child : engine 3421126067  random_device 3229268048`, `parent: engine 3421126067  random_device 3032291014`. The engine value is the same on both lines and on libc++; the `random_device` values change on every run.

**Why it matters**

The engine copy is the point of the test, and nothing in the language says a copy happened: the state is plain memory. The same property makes `mt19937` reproducible and makes a forked worker a duplicate. `random_device` is the fix for a child that needs a fresh seed, at the cost measured in part 5.

**Chew on this**

Which of your forks or `clone`s happen after an engine is constructed? Is the engine seeded again in the child, or does the child continue the parent's sequence?

**Sources**

- https://pubs.opengroup.org/onlinepubs/9799919799/functions/fork.html (the child is a copy of the parent's address space)
- https://eel.is/c++draft/rand.eng.mers

**Verified**

GCC 16.2.0 and clang 19.1.7 with libc++, `-O2`. The POSIX statement about fork is the cited standard, not run.

**Gotchas**

- The child exits with `_exit` so that no destructors or flushes run twice.
- The 3421126067 is for seed 42 after one draw; it is the second value of that stream.

## F#: a generator kept as a value copies for free and replays exactly, and `System.Random` has no member that can copy it

*Type system deep cuts*

**Did you know**

.NET has no `fork`, so the exact bug does not arise inside a .NET process. The same replay does: copy a generator's state and the copy says the same next thing. With the generator written as an immutable record, "fork" is `let snapshot = state`, free and exact, and parent and child's second draws were both `7273575876580499574`. `System.Random` is a class with hidden state, and a search of its public members for `Clone`, `Copy` or `Snapshot` returned an empty list on .NET 10. So you can reproduce a state only by seeding, and never branch off a running one.

**Show me**

```fsharp
// .NET 10.0.14, dotnet fsi
open System

// a generator as a value: its whole state is one uint64
type XorShiftState = { word: uint64 }
let fn_next (state: XorShiftState) : uint64 * XorShiftState =
    let step_1: uint64 = state.word ^^^ (state.word <<< 13)
    let step_2: uint64 = step_1 ^^^ (step_1 >>> 7)
    let step_3: uint64 = step_2 ^^^ (step_2 <<< 17)
    step_3, { word = step_3 }

let start_state: XorShiftState = { word = 0x9E3779B97F4A7C15UL }
let first_value, after_first = fn_next start_state
let snapshot: XorShiftState = after_first // "fork": a copy is free and exact
let parent_second, _ = fn_next after_first
let child_second, _ = fn_next snapshot
printfn "parent and child second draw: %d %d (equal: %b)" parent_second child_second (parent_second = child_second)

// System.Random has no copy: look for a public member that could snapshot it
let copy_like_members: string list =
    typeof<Random>.GetMembers() |> Array.map (fun member_info -> member_info.Name)
    |> Array.filter (fun member_name -> member_name.Contains "Clone" || member_name.Contains "Copy" || member_name.Contains "Snapshot")
    |> Array.toList
printfn "Random members named Clone, Copy or Snapshot: %A" copy_like_members
```

Output: `parent and child second draw: 7273575876580499574 7273575876580499574 (equal: true)` and `Random members named Clone, Copy or Snapshot: []`.

**Why it matters**

A value generator makes the copy visible: to have a child with a different stream you must write the line that makes it different (seed it, or split it). A mutable generator makes the copy invisible, which is how forks, VM snapshots and containers' checkpoints produce duplicates. The purity here costs one allocation-free record copy per draw; the hand-rolled xorshift is a demonstration and not a recommendation for production randomness.

**Chew on this**

If every generator in your system were a value you had to pass and return, where would a "fork" become a visible line in the code? Which of your processes can be snapshotted and restored, and does any code run before it that draws a number?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.random
- https://www.ndss-symposium.org/ndss2010/when-good-randomness-goes-bad-virtual-machine-reset-vulnerabilities-and-hedging-deployed

**Verified**

.NET SDK 10.0, `dotnet fsi`. The reflection search is over public members only; a private or internal way to copy the state may exist. That .NET has no `fork` is from its API surface: I did not search for a P/Invoke route.

**Gotchas**

- `7273575876580499574` is for this seed and one prior draw; it is deterministic.
- `Process.Start` launches a fresh process that seeds itself; I did not measure that here.

## TypeScript: a value drawn before a Node startup snapshot is identical in every process restored from it, `0.3510755767124506` three times, while `Math.random` after the restore differs

*Stdlib and ecosystem gems*

**Did you know**

Node 26 can build a startup snapshot of a script's heap and start later processes from it. Anything the script computed before the snapshot is frozen into the blob. In the test, a `Math.random()` taken at build time printed `0.3510755767124506` in all three processes started from the blob, while a `Math.random()` drawn after the restore printed three different values (`0.8018`, `0.5177`, `0.7134`). V8 reseeded its generator on restore, but the program's own earlier draw is a copy.

**Show me**

```js
// Node 26.13.0: save as entry.cjs; node --snapshot-blob snap.blob --build-snapshot entry.cjs
// then run node --snapshot-blob snap.blob three times
const { startupSnapshot } = require("node:v8")
const const_value_at_build = Math.random()
startupSnapshot.setDeserializeMainFunction(() => {
    console.log("captured at build:", const_value_at_build, " Math.random after restore:", Math.random())
})
```

Output: three lines, each starting `captured at build: 0.3510755767124506` (the number differs between builds) and ending with a different `Math.random` value.

**Why it matters**

This is the VM-snapshot bug in miniature, and a safer one: the runtime did the right thing for its own generator and the application did the wrong thing with its own earlier value. A session id, a nonce or a cache key created during start-up and kept in the snapshot is the same in every process: the Firefox result from the paper, in JavaScript.

**Chew on this**

What does your service compute at start-up that would be wrong if two copies of it ran? Which of those values come from a random source?

**Sources**

- https://nodejs.org/api/v8.html#startup-snapshot-api
- https://nodejs.org/api/cli.html#--build-snapshot

**Verified**

Node v26.13.0 in the `node:lts` image, three restores from one blob. The reseeding on restore is what the three different `Math.random` values show; I did not read V8's code. I did not test `crypto` after a restore.

**Gotchas**

- A snapshot entry must be a CommonJS file, not an ES module (the first attempt failed with "Cannot use import statement outside a module").
- User-land snapshots are a documented Node feature but the API is versioned and experimental; I did not check its stability level for 26.

# The functional angle: if the generator is state, a copy of the world is a copy of the state

Draws on the F# tip and all four measurements. Fork, snapshot and checkpoint copy the world. A pure generator makes the copy explicit: `let child = parent`. An impure one makes it implicit, and the implicit copy is the hazard.

```fsharp
// F#: splitting the stream is one visible line, instead of an invisible copy
let fn_split (state: XorShiftState) : XorShiftState * XorShiftState =
    let _, next_state = fn_next state
    { word = next_state.word ^^^ 0xD1B54A32D192ED03UL }, next_state // the child is not the parent
```

This sample ran (child and parent states differ), but it is a sketch of the splitting idea, not a vetted splittable generator. Real splittable generators (SplitMix, for one) have proofs of independence, and Rust's `rand_chacha` offers streams.

| Language | What a copy of the world does to the generator | Measured | The fix is |
| --- | --- | --- | --- |
| Rust | `ThreadRng` repeats after fork in 0.9, partly in 0.8 | 300 of 300 vs 63 of 300 draws | `ThreadRng::reseed` after fork |
| C++ | the engine is plain memory, copied exactly | same 3421126067 in both | seed in the child from `random_device` |
| F# | a value copy is exact; `Random` has no copy | equal draws; no member | split explicitly |
| TypeScript | the runtime reseeds its own, not yours | 3 identical build-time values | draw after restore, not before |

Rust is the baseline: the only row where a maintainer decided, and wrote down in a changelog, to leave the duty with the caller. Which would you want from a library, the warning or the guard?

# The security angle: a repeated draw is a repeated nonce

Draws on the Rust and TypeScript tips and the paper. Mode B (what the language does not prevent). Bug classes: CWE-336 (Same Seed in Pseudo-Random Number Generator), CWE-323 (Reusing a Nonce, Key Pair in Encryption) and CWE-330.

```rust
// Rust: a worker forked from a parent that already drew from ThreadRng
// child: let nonce: u64 = rand::rng().next_u64();   // may equal the parent's next nonce (0.9 measured: 300 of 300)
```

The paper's server result is the consequence: with DSA, two signatures made with the same secret per-signature value let a third party compute the private key. The defense in each language is the same: reseed from the operating system in the child, and treat any value drawn before a copy as shared.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | forked child repeats `ThreadRng` (0.9 measured) | nothing; the changelog says to reseed | call the reseed after fork |
| C++ | forked child repeats `mt19937` (measured) | nothing | reseed from `random_device` after fork |
| F# | a restored snapshot repeats any generator (paper's setting) | no `fork` in .NET | use `RandomNumberGenerator` for secrets |
| TypeScript | build-time values are frozen (measured) | V8 reseeds `Math.random` on restore | generate secrets after start, never at build |

TypeScript is the baseline because its runtime already did the hard half. What in your deployment copies a machine or a process, and which draws happen before the copy?

# FAQ

**Did OpenSSL fix this?**
The wiki says OpenSSL 1.1.1 "completely rewrote RNG" and that "the concerns below do not really apply any more". I did not test a current OpenSSL.

**Is a PID mixed in enough?**
The wiki says OpenSSL mixed the PID in, "which provides a certain degree of fork safety", and that when PIDs wrap, new children can repeat an earlier child's sequence. That is the same mechanism as part 5's Android story, as the wiki's own links show.

**Does `getrandom` have this problem?**
It asks the kernel, which keeps its own state; the C++ `random_device` result is the evidence here. Kernel behavior after a VM restore is a separate question that I did not test.
