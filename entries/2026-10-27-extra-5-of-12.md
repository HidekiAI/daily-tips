**The thesis of this part: composition, currying and point-free style all pass a function where a lambda would have adapted the arguments, and each language does something different with the arguments that do not fit.** Writing `map(format_port)` instead of `map((port) => format_port(port))` is the whole appeal: no lambda, the name says what happens. But the lambda was doing a job, choosing which arguments go where, and without it the language decides. Rust refuses to compile. C++'s `std::bind` evaluates the extras and throws them away. TypeScript forwards them. F# curries them into a function value, which the type checker catches, and charges for when a curried function does work between its arguments.

## Rust: a closure auto-derefs its argument and a point-free path does not, so .map(str::len) on &String is E0631

*Idioms and antipatterns*

**Did you know**

Method calls auto-deref, so inside `|host| host.len()` a `&String` finds `str::len` through `Deref`. A path passed by name gets no such help: `hosts.iter().map(str::len)` is "E0631: type mismatch in function arguments", "expected function signature `fn(&String) -> _`, found function signature `fn(&str) -> _`". `map(String::len)` compiles because its signature matches exactly. The same rule bites on references the adaptor adds: `filter` passes `&char`, so `.filter(char::is_alphanumeric)`, which takes `char` by value, is also E0631.

**Show me**

```rust
// rustc 1.99.1, edition 2021.
fn main() {
    let hosts: Vec<String> = vec!["eu-1".to_string(), "us-east-2".to_string()];

    // A closure gets auto-deref: host is &String, and .len() finds str::len through Deref.
    let lengths: Vec<usize> = hosts.iter().map(|host| host.len()).collect();
    // A path whose signature matches exactly is fine: String::len takes &String.
    let lengths_by_path: Vec<usize> = hosts.iter().map(String::len).collect();
    println!("{lengths:?} {lengths_by_path:?}"); // [4, 9] [4, 9]

    // The point-free path does not coerce its argument:
    // hosts.iter().map(str::len)
    //   E0631: type mismatch in function arguments
    //   expected function signature `fn(&String) -> _`, found `fn(&str) -> _`
    // "eu-1".chars().filter(char::is_alphanumeric)
    //   E0631: expected `for<'a> fn(&'a _) -> _`, found `fn(_) -> _` (filter passes &char)

    let alphanumeric: String = "eu-1".chars().filter(|symbol| symbol.is_alphanumeric()).collect();
    println!("{alphanumeric}"); // eu1
}
```

**Why it matters**

Point-free style in Rust is all-or-nothing: the path's signature must be exactly what the adaptor passes, references and all, so the fix is either the matching path (`String::len`) or the lambda you were trying to avoid. That is the safe failure of the four: nothing runs with the wrong argument. TypeScript's `map(format_port)` below has the opposite problem, an argument that fits the type and not the meaning, and C++'s `std::bind` accepts arguments it then ignores.

**Chew on this**

When a point-free `map(SomeType::method)` fails to compile and you switch to the lambda, is the lambda adapting a reference, or is it hiding that the iterator yields a type you did not expect?

**Sources**

- https://doc.rust-lang.org/error_codes/E0631.html
- https://doc.rust-lang.org/reference/expressions/method-call-expr.html (auto-deref applies to method-call receivers)
- https://doc.rust-lang.org/reference/type-coercions.html

**Gotchas**

- `String::len` works and `str::len` does not, though they return the same number: the path names a function with a fixed parameter type, and only method-call syntax walks `Deref`.
- `filter` always passes a reference to the item, so any `fn(T) -> bool` path fails there even when the item type is right; `map` passes the item itself.
- The error lands on the adaptor call, not on the path, and names a signature, not your variable, which makes it read like an iterator problem.

## C++: std::bind evaluates and discards any extra arguments, so a callback that gains a parameter keeps compiling; bind_front refuses

*Stdlib and ecosystem gems*

**Did you know**

The standard says so outright: "If some of the arguments that are supplied in the call to `g()` are not matched by any placeholders stored in `g`, the unused arguments are evaluated and discarded." `std::bind(scale_port, 8000, _1)` called as `(80, 443, 9)` returned 8080 with no warning on g++ 14.2. C++20's `std::bind_front` and a plain lambda both reject the extra arguments at compile time. `bind` also copies its bound arguments: binding `base`, then setting `base = 9000`, still gave 8080.

**Show me**

```cpp
// C++20 (std::bind_front), g++ 14.2 -Wall -Wextra: no warnings.
#include <cstdio>
#include <functional>

int scale_port(int base, int offset) { return base + offset; }

int main() {
    using namespace std::placeholders;
    auto with_bind = std::bind(scale_port, 8000, _1);
    std::printf("%d\n", with_bind(80));         // 8080
    std::printf("%d\n", with_bind(80, 443, 9)); // 8080: 443 and 9 are evaluated and discarded

    auto with_front = std::bind_front(scale_port, 8000);
    std::printf("%d\n", with_front(80));        // 8080
    // with_front(80, 443);  // error: use of deleted function '..._Bind_front<...>::operator()(...)'

    auto with_lambda = [](int offset) { return scale_port(8000, offset); };
    // with_lambda(80, 443); // error: no match for call to '(main()::<lambda(int)>) (int, int)'

    int base = 8000;
    auto bound_copy = std::bind(scale_port, base, _1); // bound arguments are copied
    base = 9000;
    std::printf("%d\n", bound_copy(80));        // 8080, not 9080

    std::printf("sizeof bind=%zu bind_front=%zu lambda=%zu\n",
                sizeof(with_bind), sizeof(with_front), sizeof(with_lambda)); // 16 16 1
}
```

**Why it matters**

Discarding is what lets a `bind` expression satisfy a `std::function` with more parameters than the target uses, which is exactly how a callback signature grows without its handlers noticing (the security angle below measures one). It also costs: the `bind` object stores a function pointer and the bound `int` (16 bytes) and calls through the pointer, while the captureless lambda is 1 byte and names `scale_port` directly. Rust has no `bind`, and a closure with the wrong arity does not type-check against an `Fn(A, B)` bound. F# partial application is the language's own currying, checked by the type system.

**Chew on this**

Which `std::bind` expressions in your code would still compile if the callback type they are assigned to gained a parameter tomorrow, and would you want them to?

**Sources**

- https://en.cppreference.com/w/cpp/utility/functional/bind ("the unused arguments are evaluated and discarded")
- https://en.cppreference.com/w/cpp/utility/functional/bind_front
- https://en.cppreference.com/w/cpp/language/lambda

**Verified**

g++ 14.2 (libstdc++) only; Clang and MSVC not checked.

**Gotchas**

- "Evaluated and discarded" means the extra argument expressions still run, side effects included; only their values are dropped.
- `bind` copies bound arguments unless they are wrapped: cppreference says they "are never passed by reference unless wrapped in `std::ref` or `std::cref`". `bind_front` copies too.
- `bind_front` (C++20) and `bind_back` (C++23) bind only the leading or trailing arguments and have no placeholders, so they cannot reorder arguments the way `bind(f, _2, _1)` can.

## F#: calling a curried function value costs nothing, until the function does work between its arguments, and then each call allocated 24 bytes

*Perf and memory model*

**Did you know**

F# compiles `fun left right -> ...`, and even `fun first -> fun second -> ...`, into one closure that can take both arguments at once, so calling it with two arguments through a function value allocated nothing per call. Partial application (`add_three 5`) allocated nothing per call either. Put a `let` between the two lambdas, `fun first -> let doubled = first * 2 in fun second -> doubled + second`, and the two lambdas can no longer merge: every two-argument call first builds the inner closure, which measured 24.0 bytes per call over a million calls in a Release build. The source of the two versions differs by one line, and their types are the same.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, Release build.
open System.Runtime.CompilerServices

let ports = Array.init 1_000_000 id

[<MethodImpl(MethodImplOptions.NoInlining)>]
let opaque (combine: int -> int -> int) = combine // keeps the optimizer from seeing the lambda

[<MethodImpl(MethodImplOptions.NoInlining)>]
let apply_pair (combine: int -> int -> int) = Array.fold (fun total port -> total + combine port 1) 0 ports

let measure_bytes (label: string) (run: unit -> int) =
    run () |> ignore
    let before = System.GC.GetAllocatedBytesForCurrentThread()
    run () |> ignore
    printfn "%-28s %.1f bytes per call" label (float (System.GC.GetAllocatedBytesForCurrentThread() - before) / 1e6)

let add_three (first: int) (second: int) (third: int) = first + second + third
let staged = fun (first: int) -> (fun (second: int) -> first + second)
let staged_with_work = fun (first: int) -> let doubled = first * 2 in (fun (second: int) -> doubled + second)

measure_bytes "fun left right -> .." (fun () -> apply_pair (opaque (fun left right -> left + right))) // 0.0
measure_bytes "partial add_three 5" (fun () -> apply_pair (opaque (add_three 5)))                    // 0.0
measure_bytes "fun first -> fun second" (fun () -> apply_pair (opaque staged))                         // 0.0
measure_bytes "same, with a let between" (fun () -> apply_pair (opaque staged_with_work))              // 24.0
```

**Why it matters**

Currying is F#'s default, and most of the time it is free because the compiler merges the lambdas. The staged form, "do some work with the first argument, return a function for the second", is a legitimate pattern (precompute a lookup once, apply it many times), and it pays off only when the caller really calls it in two steps. Called with both arguments every time, it allocates the intermediate closure every time. Rust and C++ have no currying, so the staged form is always an explicit closure-returning function and its cost is visible in the signature (`impl Fn`, `Box<dyn Fn>`). In TypeScript, an arrow function returning an arrow function creates a new inner function object on every outer call; that is the language semantics, and whether V8 elides it was not measured.

**Chew on this**

Which of your F# functions are written `fun config -> let prepared = ... in fun request -> ...`, and does every caller apply `config` once and reuse the result, or both arguments every time?

**Sources**

- https://learn.microsoft.com/dotnet/fsharp/language-reference/functions/#partial-application-of-arguments
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-core-optimizedclosures.html
- https://learn.microsoft.com/dotnet/api/system.gc.getallocatedbytesforcurrentthread

**Gotchas**

- The `NoInlining` helpers keep the optimizer from specializing the call. Without them the result was the same: the first three allocated nothing per call, and the staged version with the `let` still allocated 24.0 bytes per call.
- Passing a two-argument function where one is expected is a type error, not a silent bug: `let results : int list = List.map add_ports [ 1; 2 ]` is FS0001, because the result is a list of functions.
- 24 bytes per call is the size of one small object holding one `int` on 64-bit .NET, which fits the inner closure capturing `doubled` (inferred from the size; the object was not inspected).

## TypeScript: map(format_port) passes the index as the second argument, and tsc accepts it because one overload takes fewer parameters

*Type system deep cuts*

**Did you know**

`Array.prototype.map` calls its callback with `(value, index, array)`. Passing a function by name forwards all three, and TypeScript allows a callback with fewer parameters than the caller supplies, so `[80, 443].map(format_port)` type-checks against `format_port`'s one-argument overload. At runtime the implementation received the index as `host` and returned `['0:80', '1:443']`. The standard library version is the same trap: `["10", "10", "10"].map(Number.parseInt)` compiled under `--strict` and returned `[10, NaN, 2]`, because the index became the radix. And `bind` on an overloaded function sees only the last overload: `format_port.bind(null, 8080)` is `(host: string) => string`, so calling it with no arguments is TS2554.

**Show me**

```typescript
// TypeScript, tsc 7.0.2 --strict, Node 22.23.4.
function format_port(port: number): string
function format_port(port: number, host: string): string
function format_port(port: number, host?: string): string {
    return host === undefined ? `:${port}` : `${host}:${port}`
}

console.log(format_port(8080)) // :8080

// Point-free: map calls its callback with (value, index, array). tsc checks format_port against
// the one-argument overload, which accepts fewer parameters, and says nothing.
console.log([80, 443].map(format_port)) // [ '0:80', '1:443' ]: the index arrived as host

// The same trap with a standard function: the index arrives as the radix.
const ids: string[] = ["10", "10", "10"]
console.log(ids.map(Number.parseInt))                        // [ 10, NaN, 2 ]
console.log(ids.map((text) => Number.parseInt(text, 10)))    // [ 10, 10, 10 ]

// bind sees only the last overload: the result is (host: string) => string.
const bound_to_port = format_port.bind(null, 8080)
console.log(bound_to_port("eu")) // eu:8080
// bound_to_port()  // TS2554: Expected 1 arguments, but got 0 (the 1-argument overload is gone)
```

**Why it matters**

"A function with fewer parameters is assignable" is what makes `items.forEach(console.log)`-style code type-check, and it is unsound exactly when the function's later parameters are optional: the caller's extra arguments fill them. Overloads hide it further, because tsc picks the overload that fits and the implementation receives what the caller actually passed. Rust's `map` passes one argument and `str::len` must match it exactly; F#'s `List.map` with a two-argument function produces a list of functions, a type error; C++'s `std::transform` passes one argument, though `std::bind` would discard extras rather than forward them.

**Chew on this**

Which of your point-free callbacks (`.map(parse)`, `.filter(is_valid)`, `.forEach(handle)`) point at a function whose second parameter is optional, and has anyone added that optional parameter since the callback was written?

**Sources**

- https://www.typescriptlang.org/docs/handbook/type-compatibility.html#comparing-two-functions ("ignoring extra function parameters is actually quite common in JavaScript")
- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/Array/map
- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/parseInt

**Gotchas**

- Binding five arguments is typed precisely in tsc 7.0.2: `scale_port.bind(null, 8000, 80, "eu", true, 1)` is `() => string`. The old "`bind` is only typed for four arguments" belief is out of date.
- `pipe(8080, format_port)` from effect passes exactly one argument and gave `:8080`; it is `map` and friends that pass extras.
- `Number.parseInt` with radix `0` behaves as if the radix were omitted, which is why the first element still came out as `10`.

# The functional angle: only F# makes "one argument too many" a type, and it is also the only one that charges for currying

_Draws on all four tips. The shape: pass a function by name to something that calls it with a different number of arguments than the function was written for._

| Language | Extra or mismatched arguments | When you find out | What point-free costs |
| --- | --- | --- | --- |
| F# | become partial application: `List.map add_ports [1; 2]` is a list of functions | compile time, FS0001 at the use | nothing, unless a curried function does work between its arguments (24 bytes per call measured) |
| Rust | must match the adaptor's signature exactly, references included | compile time, E0631 | nothing; no currying, no deref through a path |
| C++ | `std::bind` evaluates and discards them | never | an indirect call through a stored pointer (16-byte `bind` object vs a 1-byte lambda) |
| TypeScript | forwarded into the function's optional parameters | runtime, as a wrong value (`[10, NaN, 2]`) | nothing at runtime; the cost is correctness |

F# is the baseline because currying is its native composition, so every function already has an answer for "what if I get only some of my arguments": a function value. That is what turns the mismatch into a type error. Rust gets there by having no currying at all and exact signatures; C++ and TypeScript both accept the mismatch, one by dropping arguments and one by forwarding them.

Left open: if your style guide prefers point-free calls, which of the four languages would you exempt, and for which kind of function?

# The security angle: a callback that gains a parameter, and a bind that throws it away

_Draws on the C++ tip, Mode C: the missing check. A router's callback type grows a `caller` parameter so handlers can authorize; a handler registered through `std::bind` keeps compiling and never sees it. Direction: the language accepts it by design._

```cpp
// C++20, g++ 14.2 -Wall -Wextra: no warnings
struct request { std::string path; };
struct caller { std::string user; bool is_admin; };
void serve(const request& incoming) { std::printf("serving %s\n", incoming.path.c_str()); } // v1 handler

// v2: the router now passes who is calling, so handlers can authorize.
std::function<void(const request&, const caller&)> on_request = std::bind(serve, _1);
on_request(request{"/admin/export"}, caller{"guest", false}); // serving /admin/export: caller dropped
```

The router authors added the parameter so that every handler would make an authorization decision. The `bind` expression satisfied the new type and discarded the `caller`, so the old handler serves `/admin/export` to a guest without ever being asked. That is CWE-862 (Missing Authorization), reached through CWE-628 (Function Call with Incorrectly Specified Arguments). The same registration written as a lambda that takes only the request fails to compile: "conversion from 'main()::<lambda(const request&)>' to non-scalar type 'std::function<void(const request&, const caller&)>' requested".

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | `bind` discards a new security-relevant argument | accepts it, by specification | register handlers as lambdas or `bind_front`, which reject the arity change |
| TypeScript | a handler with fewer parameters is assignable to the new callback type | accepts it: the handbook allows "discarding" parameters because "ignoring extra function parameters is actually quite common in JavaScript" | make the new parameter part of an object the handler must destructure, or a required first parameter |
| Rust | a closure of the wrong arity does not satisfy `Fn(&Request, &Caller)` | compile error | nothing for this shape |
| F# | a one-argument handler is not a `Request -> Caller -> unit` | compile error | nothing for this shape |

Left open: when you add a parameter to a callback type so that handlers can make a decision, how do you find every handler that will compile without making it?

# FAQ

**Is `std::bind` deprecated?**
No. It is still in C++23; `bind_front` (C++20) and `bind_back` (C++23) are additions for the common cases, and lambdas cover the rest. The difference measured here is behavioural: only `bind` discards extra arguments.

**Does Rust have currying at all?**
No language-level currying: a function takes all its arguments at once. Partial application is a closure (`move |offset| scale_port(8000, offset)`), and a function that returns a closure (`fn scale_from(base: i32) -> impl Fn(i32) -> i32`) is the staged form, with its cost in the return type.

**Does F#'s pipe operator `|>` allocate a closure?**
No: `port |> add_offset 8000` inside the same million-iteration fold allocated 0.0 bytes per call in a Release build. The allocation in the F# tip came from calling a function *value* whose two lambdas could not be merged.

**Why does `["10","10","10"].map(Number.parseInt)` give `10` first and not `NaN`?**
The first call gets index `0` as the radix, and radix `0` means "not specified", so the string is read as decimal. Index `1` is an invalid radix (`NaN`), and index `2` reads `"10"` in base 2, which is `2`.
