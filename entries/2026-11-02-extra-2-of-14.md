# What happened

**Bug class:** Bohrbug, triggered by the new rocket's trajectory; the anti-pattern is code reused unchanged from a system whose input range it was proven against.

From "ARIANE 5 Flight 501 Failure, Report by the Inquiry Board" (Paris, 19 July 1996). The report is a scanned document; the quotes below are transcribed from its page images.

```text
The internal SRI software exception was caused during execution of a data conversion
from 64-bit floating point to 16-bit signed integer value. The floating point number
which was converted had a value greater than what could be represented by a 16-bit
signed integer. This resulted in an Operand Error. The data conversion instructions
(in Ada code) were not protected from causing an Operand Error, although other
conversions of comparable variables in the same place in the code were protected.
```

```text
The value of BH was much higher than expected because the early part of the trajectory
of Ariane 5 differs from that of Ariane 4 and results in considerably higher horizontal
velocity values.
```

The two Inertial Reference Systems ran "identical hardware and software", so the back-up "had already ceased to function during the previous data cycle (72 milliseconds period) for the same reason". Of seven conversions at risk, "protection being added to four of the variables ... However, three of the variables were left unprotected", and "it was jointly agreed not to include the Ariane 5 trajectory data in the SRI requirements and specification". The code that failed was an alignment function that "serves no purpose" after lift-off and kept running for about 40 seconds of flight, a time sequence the report says "is based on a requirement of Ariane 4 and is not required for Ariane 5".

The report is as direct about the response to the exception as about the exception: the specification said that on any exception "the SRI processor should be shut down", and "It was the decision to cease the processor operation which finally proved fatal." It adds that "the computers within the SRIs could have continued to provide their best estimates of the required attitude information."

## Rust: `as i16` keeps running on 32767 where the Ariane 5 code raised, and nothing records the clamp

*Idioms and antipatterns*

**Did you know**

The 1996 conversion raised an Operand Error and the processor shut down. Rust's `as` does the opposite by design: it saturates, so `40000.0 as i16` is 32767 and the program keeps running on that value. That resembles the continue-running mitigation the board described, though the board spoke of attitude estimates, not of clamping, and nothing records that the value was clamped. The checked conversion the three unprotected variables lacked is code you write, as the [float to integer special](2026-10-20-extra.md) showed for `i32`.

**Show me**

```rust
// rustc 1.99.1, Debian.
// std has no TryFrom<f64> for any integer, so the checked path is hand-written.
fn checked_bias_to_i16(candidate_horizontal_bias_f64: f64) -> Result<i16, f64> {
    let is_representable_as_i16 = candidate_horizontal_bias_f64.trunc() >= i16::MIN as f64 && candidate_horizontal_bias_f64.trunc() <= i16::MAX as f64;
    if is_representable_as_i16 { Ok(candidate_horizontal_bias_f64 as i16) } else { Err(candidate_horizontal_bias_f64) } // NaN fails both tests
}

fn main() {
    let horizontal_bias_f64: f64 = 40000.0; // Ariane 5's BH was "much higher than expected"

    // `as` never fails: it saturates, so the unit keeps flying on 32767.
    println!("{}", horizontal_bias_f64 as i16); // 32767
    println!("{}", f64::INFINITY as i16); // 32767
    println!("{}", (-40000.0_f64) as i16); // -32768

    // The 1996 Ada conversion raised instead. Writing that by hand:
    println!("{:?}", checked_bias_to_i16(horizontal_bias_f64)); // Err(40000.0)
    println!("{:?}", checked_bias_to_i16(f64::NAN)); // Err(NaN)
    println!("{:?}", checked_bias_to_i16(32767.9)); // Ok(32767)

    // let refused_conversion = i16::try_from(horizontal_bias_f64); // E0277, as in the 2026-10-20 special
}
```

**Why it matters**

Halting and clamping are both policies, and the board's point was that the 1996 policy was chosen without asking whether a software error could hit both units at once. A service that clamps a rate or a size keeps serving, and a service that panics drops the request; neither tells you the input was outside the range you designed for unless you log it.

**Chew on this**

Which of your numeric conversions would you rather halt on and which would you rather clamp, and is that choice written down anywhere a reviewer would see it? If a clamped value reached a log, would anyone be looking for 32767?

**Sources**

- https://doc.rust-lang.org/reference/expressions/operator-expr.html#numeric-cast
- https://esamultimedia.esa.int/docs/esa-x-1819eng.pdf

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1.

**Gotchas**

- `f64::INFINITY as i16` is 32767 and `f64::NEG_INFINITY as i16` is -32768, so an infinity from a division by zero arrives as a believable maximum, not as an error.
- The obvious range check `candidate_horizontal_bias_f64 >= -32768.0 && candidate_horizontal_bias_f64 <= 32767.0` rejects 32767.9, which `as` would truncate to the valid 32767. Comparing `candidate_horizontal_bias_f64.trunc()` instead accepts every value that truncates into range.

## C++: an out-of-range `static_cast<int16_t>` is undefined, so Debian clang and GCC print -25536 while Apple clang kept an `int16_t` of 40000 that is not greater than 32767

*Type system deep cuts*

**Did you know**

Converting 40000.0 to `int16_t` is undefined behaviour, and the optimizer is allowed to assume it never happens. On Linux (Debian clang 19.1.7 and GCC 16.2, Docker, aarch64) the program printed -25536 at every level from `-O0` to `-O3`, with both compilers: the narrowing happened and the comparison saw the real value. The impossible result appeared only on macOS: under Apple clang 21 on arm64 at `-O1` and above, the function's result was 40000 when widened to `int`, while `widened > 32767` printed 0 on the same line. That compiler skipped the narrowing and also folded the comparison, because an `int16_t` "cannot" exceed 32767. Undefined behaviour permits both outcomes: a check written after the cast survived on Debian clang and GCC and was silently removed by Apple clang.

**Show me**

```cpp
// C++20. Debian clang 19.1.7 and GCC 16.2 (Docker): -25536 at -O0 to -O3.
// Additionally checked on macOS arm64: Apple clang 21 at -O1 and above gives 40000.
#include <cstdint>
#include <cstdio>

[[gnu::noinline]] std::int16_t fn_narrow_bias_to_int16(double horizontal_bias_double) {
    return static_cast<std::int16_t>(horizontal_bias_double);  // UB when value does not fit
}

int main(int argument_count, char**) {
    double horizontal_bias_double = 40000.0 * argument_count;  // not a constant the compiler can see
    std::int16_t stored_bias_int16 = fn_narrow_bias_to_int16(horizontal_bias_double);
    int widened_bias_int = stored_bias_int16;

    // macOS, Apple clang -O0:  stored=-25536 widened=-25536 above_max=0
    // macOS, Apple clang -O2:  stored=40000  widened=40000  above_max=0
    // Debian clang 19.1.7 and GCC 16.2, -O0 to -O3: stored=-25536 widened=-25536 above_max=0
    std::printf("stored=%d widened=%d above_max=%d\n", stored_bias_int16, widened_bias_int, widened_bias_int > 32767);
    // On macOS at -O2 (Apple clang only) the program prints 40000 and, on the same line, says it is not above 32767:
    // an int16_t cannot exceed 32767, so the comparison was folded to false.
}
```

**Why it matters**

A range check written after the conversion, `if (stored_bias_int16 > 32767) alarm();`, is the one check Apple clang's optimizer removed (Debian clang 19.1.7 and GCC 16.2 kept it), so on that compiler the "defensive" version of the code is the one that loses the alarm. Rust's `as` gives a defined value here, wrong but documented. C++ gives a value that depends on the compiler, the flags and the target, and the Ariane 5 board's request for "best estimates" has no meaning when the estimate changes with `-O2`.

**Chew on this**

How many of your conversions from a floating-point value to a narrow integer are checked before the cast rather than after it? If the same source gives different results at `-O0` and `-O2`, which build did your tests run?

**Sources**

- https://en.cppreference.com/w/cpp/language/implicit_conversion
- https://en.cppreference.com/w/cpp/utility/in_range
- https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html

**Verified**

Debian clang 19.1.7 (`debian-clang:trixie`) and GCC 16.2.0 (`gcc:latest`), both in Docker on Debian aarch64, `-std=c++20`, `-O0`, `-O1`, `-O2` and `-O3`: both printed `stored=-25536 widened=-25536 above_max=0` at every level. The same on Debian x86_64 (Debian clang 19.1.7 and Debian GCC 14.2.0, `debian:trixie` under `--platform linux/amd64`). With `-fsanitize=float-cast-overflow` GCC 16.2 reported "40000 is outside the range of representable values of type short int" (the Debian clang image has no UBSan runtime, so that was not run there). Additionally checked on macOS (Apple clang 21.0.0, arm64, `-O0` to `-O3`): the 40000 result appears only there, at `-O1` and above.

**Gotchas**

- C++20's `std::in_range<std::int16_t>(40000.0)` does not compile on Debian clang 19.1.7 or GCC 16.2 (also not on Apple clang 21): `in_range` accepts integer types only, so the standard's own range helper cannot check a `double`.
- UBSan's `-fsanitize=float-cast-overflow` catches this one too, as the [float to integer special](2026-10-20-extra.md) showed for `int`.
- Infinity is undefined too. Debian clang 19.1.7 and GCC 16.2 gave -1 for `int16_t` and 2147483647 for `int` at every level from `-O0` to `-O3`; under Apple clang the wrong value differed by level (additionally checked on macOS: -1 at `-O0`, 2147483647 at `-O2`).

**Related**

## F#: `int16 infinity` is -1, because .NET 10 saturates to `int` first and then keeps the low 16 bits

*Stdlib and ecosystem gems*

**Did you know**

F#'s unchecked `int16` on .NET 10 (Arm64 and x64) neither saturates nor raises: it converts to a saturated `int32` and then discards the high bits. So `int16 40000.0` is -25536, `int16 65578.0` is 42, and `int16 infinity` is -1, because `Int32.MaxValue` is `0x7FFFFFFF` and its low 16 bits are `0xFFFF`. Microsoft's .NET 11 breaking-change notice describes that two-step path as the common CoreCLR sequence in .NET 9 and .NET 10, "not a guaranteed contract", and makes .NET 11's unchecked conversion saturate at `short`'s own bounds. `Checked.int16` raises `OverflowException`, which is the Ariane 5 behaviour.

**Show me**

```fsharp
// SDK 10.0.403 (F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14), Arm64.
let horizontal_bias_float = 40000.0

// Unchecked int16: saturate to int32 first, then keep the low 16 bits.
printfn "%d" (int16 horizontal_bias_float)   // -25536
printfn "%d" (int16 infinity)          // -1: Int32.MaxValue is 0x7FFFFFFF, low 16 bits 0xFFFF
printfn "%d" (int16 65578.0)           // 42: Microsoft's own example of the old behaviour
printfn "%d" (int16 nan)               // 0

// Checked.int16 is the Ariane 5 behaviour: it raises.
let fn_checked_bias_to_int16 (horizontal_bias_float: float) : Result<int16, string> =
    try Ok (Checked.int16 horizontal_bias_float) with :? System.OverflowException -> Error (sprintf "out of range: %g" horizontal_bias_float)
printfn "%A" (fn_checked_bias_to_int16 horizontal_bias_float)   // Error "out of range: 40000"
printfn "%A" (fn_checked_bias_to_int16 infinity)          // Error "out of range: Infinity"
```

**Why it matters**

The same F# line gives -1 on .NET 10 and, per Microsoft's notice, 32767 on .NET 11, so a runtime upgrade changes a number your code computes without a compiler warning. That is the Ariane 5 pattern in miniature: code proven on one platform, reused on another whose range behaviour differs. Rust's `as` has one documented rule; C++ leaves it undefined.

**Chew on this**

Which of your services will move from .NET 10 to .NET 11, and do any of them convert a `float` to a type narrower than `int`? Would any test you have notice -1 turning into 32767?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/core/compatibility/jit/11/fp-to-small-integer
- https://learn.microsoft.com/en-us/dotnet/core/compatibility/jit/9.0/fp-to-integer
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/casting-and-conversions

**Verified**

Run on .NET 10.0.14 Arm64 (`mcr.microsoft.com/dotnet/sdk:10.0`, Ubuntu 24.04, not Debian), on the same image as x64 under emulation (`--platform linux/amd64`); both gave the same values. The .NET 11 result (32767) comes from Microsoft's notice and was not measured here, since .NET 11 is not yet a stable release.

**Gotchas**

- The .NET 9 change that made `int` conversions saturating on x86 and x64 lists `int`, `long`, `uint` and `ulong` only. `short`, `byte`, `sbyte`, `ushort` and `char` were not part of it.
- Microsoft's .NET 11 notice says the new rule covers CoreCLR and Native AOT, and that "Mono is not included in this change".
- `Checked.int16 32767.9` is 32767, not an exception: the checked conversion truncates first, then checks the range.

## TypeScript: the range guard before an `Int16Array` store lets `NaN` through, and the store turns it into 0

*Idioms and antipatterns*

**Did you know**

The usual way to "protect" a conversion, as Ariane 5 did for four of its seven variables, is a range check: `if (candidate_horizontal_bias > 32767 || candidate_horizontal_bias < -32768) throw`. Every comparison with `NaN` is false, so `NaN` passes the guard, and the `Int16Array` store then converts it to 0 without an error. `0 / 0` and `Math.sqrt(-1)` both reached the array as 0. tsc 7.0.2 `--strict` reports nothing, because `NaN` is a `number`.

**Show me**

```ts
// TypeScript, Node 26.13.0 (LTS), tsc 7.0.2 --strict: no diagnostic.
const fn_store_horizontal_bias = (target_bias_store: Int16Array, candidate_horizontal_bias: number): void => {
    if (candidate_horizontal_bias > 32767 || candidate_horizontal_bias < -32768) throw new RangeError(`horizontal bias ${candidate_horizontal_bias} out of range`)
    target_bias_store[0] = candidate_horizontal_bias
}
const bias_store_int16 = new Int16Array(1)
for (const candidate_horizontal_bias of [40000, Number.NaN, 0 / 0, Math.sqrt(-1)]) {
    try { fn_store_horizontal_bias(bias_store_int16, candidate_horizontal_bias); console.log(candidate_horizontal_bias, "-> stored", bias_store_int16[0]) }
    catch (range_error) { console.log(candidate_horizontal_bias, "->", (range_error as Error).message) }
}
// 40000 -> horizontal bias 40000 out of range
// NaN -> stored 0      (three times: NaN, 0 / 0, Math.sqrt(-1))
```

**Why it matters**

The `Int16Array` store is what makes the open guard expensive: it does not raise on `NaN`, it stores a plausible 0. A guard written as "reject what is out of range" fails open for `NaN`, the only `number` that is not ordered; the accept-only form, `if (!(value >= -32768 && value <= 32767)) throw`, is the one the [float to integer special](2026-10-20-extra.md) used in C++. Rust's `checked_bias_to_i16` above uses it too, and the C++ tip shows why a check written after the conversion is worse still.

**Chew on this**

How many of your range guards are written as a rejection of what is too big or too small, rather than an acceptance of what fits? Where could a `NaN` come from in your inputs: a parse, a division, a missing field?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/TypedArray
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number

**Verified**

Run on Node 26.13.0, the current LTS (`node:lts-trixie`, Debian). MDN documents the truncate-then-low-bits rule; the results for `NaN` and `Infinity` were measured, and the specification's `ToInt16` text was not fetched.

**Gotchas**

- An `Int16Array` store wraps modulo 2^16 rather than saturating: 40000 becomes -25536, -40000 becomes 25536, and 65541 becomes 5.
- `Infinity` is stored as 0 as well, so a guard that rejects `Infinity` (it is greater than 32767) is the only thing standing between a division by zero and a silent 0.
- `DataView.setInt16(0, 40000)` follows the same rule: reading it back gives -25536.

# The functional angle: a narrowing conversion is a partial function, and the fix is to say what happens outside its domain

Draws on all four tips. The [float to integer special](2026-10-20-extra.md) already made the case for `float -> int option`; this part adds the narrow width and the guard.

```rust
// Rust, from the tip above: compare the truncated value, so NaN fails both tests.
fn checked_bias_to_i16(candidate_horizontal_bias_f64: f64) -> Result<i16, f64> {
    let is_representable_as_i16 = candidate_horizontal_bias_f64.trunc() >= i16::MIN as f64 && candidate_horizontal_bias_f64.trunc() <= i16::MAX as f64;
    if is_representable_as_i16 { Ok(candidate_horizontal_bias_f64 as i16) } else { Err(candidate_horizontal_bias_f64) }
}
```

```cpp
// C++20: check before the cast, written as acceptance; NaN fails it.
std::optional<std::int16_t> checked_bias_to_int16(double horizontal_bias_double) {
    if (!(horizontal_bias_double > -32769.0 && horizontal_bias_double < 32768.0)) return std::nullopt;
    return static_cast<std::int16_t>(horizontal_bias_double);  // now in range: defined
}
// 40000 -> nullopt, NaN -> nullopt, 32767.9 -> 32767, -32768.5 -> -32768
```

```fsharp
// F#, from the tip above: the checked conversion, turned into a Result.
let fn_checked_bias_to_int16 (horizontal_bias_float: float) : Result<int16, string> =
    try Ok (Checked.int16 horizontal_bias_float) with :? System.OverflowException -> Error (sprintf "out of range: %g" horizontal_bias_float)
```

```ts
// TypeScript: return undefined instead of storing a wrapped value.
const fn_checked_bias_to_int16 = (horizontal_bias_number: number): number | undefined =>
    horizontal_bias_number > -32769 && horizontal_bias_number < 32768 ? Math.trunc(horizontal_bias_number) : undefined // NaN fails the test
// [40000, NaN, 32767.9, -32768.5] -> [undefined, undefined, 32767, -32768]
```

The C++ and TypeScript versions were run with Debian clang 19.1.7, GCC 16.2 (Docker; additionally Apple clang 21 on macOS), Node 26.13.0 (LTS) and tsc 7.0.2 `--strict`. The bounds are open, -32769 and 32768, because the conversion truncates toward zero: -32768.5 becomes -32768, which fits.

| Language | 40000.0 to a 16-bit integer | `NaN` | `infinity` | The total version |
| --- | --- | --- | --- | --- |
| Rust | 32767 (saturates) | 0 | 32767 | hand-written `Result<i16, f64>` (no `TryFrom<f64>`) |
| C++ | undefined: -25536 on Debian clang and GCC at every level, 40000 on Apple clang at -O1 and above | undefined | -1 (`int16_t`) on Debian clang and GCC; Apple clang differed by level | hand-written check before the cast; `in_range` refuses `double` |
| F# (.NET 10) | -25536 (int32 then low bits) | 0 | -1 | `Checked.int16` in a `try`, to a `Result` |
| TypeScript (`Int16Array`) | -25536 (low bits) | 0 | 0 | a guard written as acceptance, not rejection |

The F# row is the baseline here because it is the only language with both a checked and an unchecked conversion built in, and its unchecked one still changes between .NET 10 and .NET 11. In every row the total version is a function from `float` to a result type, the equivalent of the protection the 1996 code gave four variables and not the other three.

If every narrowing conversion in your code had to return a result type, which of them would you find you had never decided how to handle?

# The security angle: the guard that fails open

Draws on the TypeScript and C++ tips, with Rust and F# as control rows. Runs in both directions: each language does make the conversion itself defined or detectable somewhere, and none of them stops a guard from being written so that `NaN` gets past it.

```ts
// TypeScript. Looks like input validation for a requests-per-minute quota field.
const fn_parse_quota = (raw_quota_text: string): number => {
    const parsed_quota_requests_per_minute = Number(raw_quota_text)
    if (parsed_quota_requests_per_minute < 0 || parsed_quota_requests_per_minute > 1000) throw new RangeError("quota out of range")
    return parsed_quota_requests_per_minute
}
fn_parse_quota("abc") // NaN: passes the guard, and NaN > used is false for every check after it
```

The class is [CWE-1284](https://cwe.mitre.org/data/definitions/1284.html), improper validation of specified quantity in input, with the conversion itself under [CWE-681](https://cwe.mitre.org/data/definitions/681.html), incorrect conversion between numeric types.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `as` clamps silently | defines the result, never undefined | `Result` for the checked path, and a log for the clamped one |
| C++ | the cast is undefined; a check after it can be folded away (seen on Apple clang only; Debian clang and GCC kept it) | `-fsanitize=float-cast-overflow` reports it at runtime | check before the cast |
| F# | unchecked `int16` gives a runtime-version-dependent value | `Checked.int16` raises | use `Checked` at boundaries |
| TypeScript | a rejecting guard passes `NaN` | nothing: `NaN` is a `number` | write guards as acceptance, or test `Number.isFinite` first |

TypeScript is the baseline for this class because it is the one row with no checked conversion at all, so the guard is the whole defense.

Which of your validation functions would accept `NaN`, and what does the code after them do with it?
