# Daily Tips: 2026-09-02

## Rust: `if let` and `match` stopped agreeing about temporary scope in edition 2024

*Idioms and antipatterns*

**Did you know**

Everyone reads `if let` as sugar for a two-arm `match`. As of edition 2024 that
is false for drop timing. The temporaries produced by an `if let` scrutinee are
now dropped before control enters the `else` branch; the temporaries of a
`match` scrutinee still live to the end of the whole `match` statement, exactly
as before. So the classic "lock in the scrutinee, re-lock in the fallback arm"
deadlock is fixed in `if let` and untouched in `match`. Requires edition 2024
(Rust 1.85+ to select it); the behavior is per-edition, not per-compiler.

**Show me**

```rust
use std::sync::Mutex;

// try_lock() instead of lock() so the demo reports the deadlock
// rather than becoming one.
fn probe(m: &Mutex<Vec<i32>>) -> &'static str {
    if m.try_lock().is_ok() { "lock FREE" } else { "lock HELD" }
}

fn via_if_let(m: &Mutex<Vec<i32>>) {
    // The MutexGuard is a temporary of the scrutinee. Nobody named it.
    if let Some(_) = m.lock().unwrap().first() {
    } else {
        // 2021: guard alive here. 2024: guard already dropped.
        println!("  if let else -> {}", probe(m));
    }
}

fn via_match(m: &Mutex<Vec<i32>>) {
    match m.lock().unwrap().first() {
        Some(_) => {}
        // Same shape, same guard, but match scrutinee temporaries are
        // NOT rescoped. Both editions still hold the lock here.
        None => println!("  match  arm -> {}", probe(m)),
    }
}

fn main() {
    let m = Mutex::new(Vec::new());
    via_if_let(&m);
    via_match(&m);
}
```

Measured on rustc 1.95.0, same source, only `--edition` differing:

| edition | `if let ... else` | `match` fallback arm |
| --- | --- | --- |
| 2021 | lock HELD | lock HELD |
| 2024 | lock FREE | lock HELD |

**Why it matters**

Two consequences, and they pull in opposite directions. First, migrating a
crate to edition 2024 silently changes destructor timing in every `if let`
with a non-trivial temporary in the scrutinee, which is a behavior change to
guards, spans, transaction handles, and anything whose `Drop` is load-bearing.
Second, the edition guide's own recommended migration for a *borrow* error
("it is always safe to rewrite `if let` with a `match`") reintroduces the long
temporary scope by design, so a mechanical `if let` to `match` refactor on a
2024 crate can hand you back a deadlock that the edition had just removed.

**Chew on this**

Which of your `if let` scrutinees evaluate to something with a non-trivial
`Drop` that you never named, and would you notice if it started dropping one
statement earlier? And in the other direction: the C++ cousin of this pattern,
`if (auto g = m.lock(); pred(g))`, scopes the guard across both branches with
no edition dial to turn and no diagnostic; TypeScript's `using` scopes disposal
to the enclosing block, not the taken branch. If three languages disagree about
when an unnamed guard dies, which one is actually wrong?

**Sources**

- https://doc.rust-lang.org/edition-guide/rust-2024/temporary-if-let-scope.html
- https://doc.rust-lang.org/reference/destructors.html#temporary-scopes

**Verified**

Snippet compiled and run under rustc 1.95.0 at both editions; the table is
measured output. The `if_let_rescope` lint name is accepted by rustc 1.95 but
did not fire on this snippet, so treat the lint as a partial safety net rather
than a migration guarantee.

## C++: Two textually identical `requires` clauses are two different constraints

*Type system deep cuts*

**Did you know**

Constraint subsumption is decided by *identity* of atomic constraints, not by
what they mean, and two atomic constraints are identical only when they come
from the same source-level expression. Write `requires (sizeof(T) > 1)` on two
different overloads and those are two unrelated constraints. Neither overload
is more constrained than the other, so a call that satisfies both is ambiguous,
even though one clause is visibly a superset of the other. Factoring the
predicate into a named `concept` gives both overloads the same expression, and
subsumption then works. C++20; available in GCC 10+, Clang 10+ (concepts as
shipped), MSVC 19.28+.

**Show me**

```cpp
#include <cstddef>

// BROKEN: the two `sizeof(T) > 1` expressions are distinct atomic
// constraints because they originate from distinct declarations.
template <class T> void f(T) requires (sizeof(T) > 1) { }
template <class T> void f(T) requires (sizeof(T) > 1) && (alignof(T) > 1) { }
// f(short{}) -> error: call to 'f' is ambiguous

// FIXED: one expression, referenced twice. Subsumption sees the same
// atomic constraint on both sides, so the second overload wins.
template <class T> concept Wide = sizeof(T) > 1;
template <class T> void g(T) requires Wide<T> { }
template <class T> void g(T) requires Wide<T> && (alignof(T) > 1) { }

int main() { g(short{}); }   // picks the second overload, no ambiguity
```

Clang is unusually forthcoming about the rule when it rejects the first pair:

```
note: similar constraint expressions not considered equivalent;
      constraint expressions cannot be considered equivalent unless
      they originate from the same concept
```

**Why it matters**

This is why every mature concepts-based library defines named concepts for
everything, including one-line predicates that look too small to deserve a
name. It is not style. An inline `requires` clause is a subsumption dead end,
and the failure shows up later as an ambiguity at a call site far from the
declarations, at which point the fix looks like a refactor rather than a
one-word change. The corollary is a review rule with teeth: an inline
`requires` clause is fine on a *single* overload and a latent bug the moment a
second overload wants to refine it.

**Chew on this**

Your constrained overload sets: how many of them refine an inline `requires`
clause rather than a named concept, and are they unambiguous today only because
nobody has added the third overload yet? Note where the sibling languages put
this decision. Rust does not rank `where` clauses at all; it forbids the
overlapping impls outright via coherence, so the ambiguity is a compile error
at the definition rather than at the call. TypeScript ranks overloads by
declaration order and will happily pick the first match without telling you
there was a better one. Is a syntactic identity rule a bug in C++, or the price
of being the only one of the three that tries to rank partial specificity at
all?

**Sources**

- https://en.cppreference.com/w/cpp/language/constraints
- https://eel.is/c++draft/temp.constr.atomic

**Verified**

Both snippets checked with `clang++ -std=c++20 -fsyntax-only` (Apple clang
21.0.0): the first pair errors as ambiguous, the second compiles clean. Not
cross-checked against real GCC or MSVC on this machine, since `g++` here is a
symlink to Apple clang. The GCC/Clang/MSVC support versions above come from the
cppreference compiler support table, not from local compilation.

## TypeScript: A 16-byte `Buffer.allocUnsafe` pins 8 KiB, and `Buffer.alloc` does not

*Perf and memory model*

**Did you know**

`Buffer.allocUnsafe(n)` for any `n` strictly less than `Buffer.poolSize >>> 1`
(4096 by default) does not allocate. It hands back a view into a shared,
pre-allocated 8 KiB `ArrayBuffer`. Retaining that 16-byte header therefore
retains all 8192 bytes, plus every unrelated small buffer that happened to be
carved from the same slab. `Buffer.alloc(n)` is *not* pooled, so the "safe,
slower, zero-filled" allocator is the one that cannot leak this way, and the
"fast" one is the one that can. Node 22.17.1 verified; the pool has behaved
this way since the `Uint8Array`-backed rewrite in Node 4.

**Show me**

```ts
// .buffer.byteLength is the giveaway: it reports the backing ArrayBuffer,
// not the Buffer's own length.
const header = Buffer.allocUnsafe(16);
console.log(header.length, header.buffer.byteLength, header.byteOffset);
// 16 8192 3400   <- a 16-byte view at offset 3400 into the shared slab

console.log(Buffer.alloc(16).buffer.byteLength);           // 16   (unpooled)
console.log(Buffer.allocUnsafeSlow(16).buffer.byteLength); // 16   (unpooled)
console.log(Buffer.allocUnsafe(4096).buffer.byteLength);   // 4096 (at threshold, unpooled)

// The leak shape: slice a small field out of a pooled chunk and keep it.
const chunk = Buffer.allocUnsafe(1024);
const kept  = chunk.subarray(0, 4);
console.log(kept.length, kept.buffer.byteLength);          // 4 8192
// 4 reachable bytes; 8192 unreclaimable. Ratio 2048:1.
```

The Node source is a single line, `lib/buffer.js`:
`if (size < (Buffer.poolSize >>> 1)) { ... }` -- strictly less than, which is
why 4096 escapes the pool even though two places in the API docs describe the
threshold as "less than or equal to half".

**Why it matters**

This is a long-running-server leak with no allocation growth to point at.
Parse a protocol header out of a socket chunk, cache the 4-byte connection id
in a `Map`, and the heap snapshot shows kilobytes of `Buffer` while RSS climbs
by 8 KiB per retained entry. `Buffer.concat` and `Buffer.from(string)` pool on
the same rule, so the same trap sits behind them. The fix is one word if you
know it exists: `Buffer.allocUnsafeSlow`, or copy the bytes out with
`Buffer.from(kept)` before storing.

**Chew on this**

Audit the buffers your service retains past the request that produced them:
which are views, and what is `.buffer.byteLength` on each? Then consider how
the other two languages present the same sharing. Rust's `Bytes` shares a
refcounted slab too, but the sharing is in the type and the `Arc` count is
inspectable, so retention is a fact you can query. C++ `string_view` into a
pooled chunk does not retain anything at all; it dangles, and you get garbage
or a crash instead of a leak. Node retains silently and correctly. Ranked by
how fast you find the bug at 3am, is the leak really the worst of the three
behaviors?

**Sources**

- https://nodejs.org/api/buffer.html#static-method-bufferallocunsafesize
- https://nodejs.org/api/buffer.html#static-method-bufferallocunsafeslowsize
- https://github.com/nodejs/node/blob/v22.17.1/lib/buffer.js#L436

**Verified**

Snippet ran under Node 22.17.1 (all printed values above are measured, offset
3400 being run-dependent) and type-checks clean under `tsc 6.0.3 --strict` with
`@types/node`. The strict-less-than threshold was read from the v22.17.1 source
line cited above, which contradicts two paragraphs of the prose docs; trust the
source. The "since Node 4" claim rests on documentation and changelog only.
