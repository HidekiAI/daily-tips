## Rust: `HashMap::get_disjoint_mut` panics on a repeated key, while the slice version hands you an `Err`

*Stdlib and ecosystem gems*

**Did you know**

Rust 1.86 (April 2025) stabilized `get_disjoint_mut` on both slices and `HashMap`, which is the std answer to "I need two `&mut` into the same collection" that people used to solve with `split_at_mut`, a `remove`/`insert` dance, or `unsafe`. The two versions disagree on what overlap means. The slice version returns `Result<[&mut T; N], GetDisjointMutError>`, so `[0, 0]` is a value you match on. The `HashMap` version returns `[Option<&mut V>; N]`: a *missing* key is `None`, but an *overlapping* key panics with `duplicate keys found`. Its docs also say the duplicate check is O(N^2) in the number of keys asked for.

**Show me**

```rust
// rustc 1.95.0, --edition 2024. Printed values are from that run.
use std::collections::HashMap;

fn main() {
    let mut balances: HashMap<&str, i64> = HashMap::from([("ann", 100), ("bob", 50)]);

    // Slice: overlap is data. You get Err(OverlappingIndices) and carry on.
    let mut slots = [100_i64, 50];
    match slots.get_disjoint_mut([0, 0]) {
        Ok([from, to]) => { *from -= 10; *to += 10; }
        Err(reason) => println!("slice refused: {reason:?}"),
    }
    // slice refused: OverlappingIndices

    // HashMap: a missing key is data (None)...
    let [from, to] = balances.get_disjoint_mut(["ann", "carol"]);
    println!("ann={from:?} carol={to:?}");
    // ann=Some(100) carol=None

    // ...but the same key twice is a panic, from inside hashbrown.
    let outcome = std::panic::catch_unwind(move || {
        let [from, to] = balances.get_disjoint_mut(["ann", "ann"]);
        println!("unreachable {from:?} {to:?}");
    });
    println!("same key twice panicked: {}", outcome.is_err());
    // panicked at .../hashbrown-0.16.1/src/raw/mod.rs:1323:21: duplicate keys found
}
```

**Why it matters**

The textbook use is a transfer: `get_disjoint_mut([from_account, to_account])`. Both ids come off the request, and "transfer from ann to ann" is a request a client can send. On a slice that is an `Err` you turn into a 400; on a `HashMap` it is a panic in the handler, which kills the task and, if the map sat behind a `Mutex`, poisons the lock for every request after it. The check has to happen before the call, as `if from_account == to_account`. The other languages fail more quietly. In C++ there is no such API, so two `find` iterators into one `unordered_map` just point at the same value. In F#, a `Map` transfer that reads both balances and then calls `Map.add` twice, with `"ann"` as both accounts, returned `ann = 110`: the second write wins, and the account gains the amount.

**Chew on this**

Where does your code take two keys from one request and look both up in the same map? Is "the same key twice" rejected before the lookup, or are you relying on the lookup to reject it?

## C++: `map.emplace(key, std::move(value))` eats your value when the key exists, but only if the key needs converting

*Idioms and antipatterns*

**Did you know**

The standard says `emplace` *may* construct the element even when the key is already present, and destroy it at once. `try_emplace` (C++17) promises the opposite: it does not move from its arguments if nothing is inserted. libc++ narrows the gap with a shortcut. When the first argument already has type `key_type`, it looks the key up before building a node, so `emplace(std::string, std::move(v))` leaves `v` alone. Pass a `const char*` for a `std::string` key and that shortcut does not apply. The node is built, `v` is moved into it, and then the node is thrown away. The call site looks the same in both cases. `try_emplace` is available from GCC 6 (libstdc++), Clang 3.7 (libc++) and MSVC 19.0 onward.

**Show me**

```cpp
// Apple clang 21, libc++, -std=c++20 -O2 -Wall -Wextra: no warnings.
// Also compiles under -std=c++17. Printed sizes are from that run.
#include <cstdio>
#include <map>
#include <string>
#include <vector>

int main() {
    std::map<std::string, std::vector<int>> cache{{"hot", {}}};  // key already present

    std::vector<int> payload(1000, 7);
    cache.emplace(std::string("hot"), std::move(payload));
    std::printf("%zu\n", payload.size());  // 1000: key is key_type, lookup came first

    cache.emplace("hot", std::move(payload));  // const char*, not std::string
    std::printf("%zu\n", payload.size());  // 0: node built, payload moved in, node destroyed

    std::vector<int> retry(1000, 7);
    cache.try_emplace("hot", std::move(retry));
    std::printf("%zu\n", retry.size());  // 1000: guaranteed by the standard
}
// std::unordered_map printed the same three numbers.
```

**Why it matters**

The usual pattern is "insert if absent, otherwise keep the value for a retry or a log line". It works in testing, because the test passes a `std::string`. Then someone passes a string literal or a `string_view` and the "kept" value is quietly empty. `-Wall -Wextra` says nothing. Rust has the same loss, but you can see it: `entry(key).or_insert(value)` moves `value` whether or not it is inserted, and reading `value` afterwards is E0382 at compile time. To keep it, you match on `Entry::Vacant` and only then hand it over.

**Chew on this**

How many of your `emplace` calls pass a `std::move`d value and then read that variable again? Which of their key arguments are a literal or a view rather than exactly `key_type`?

**Sources**

- https://en.cppreference.com/w/cpp/container/map/emplace
- https://en.cppreference.com/w/cpp/container/map/try_emplace
- https://en.cppreference.com/w/cpp/compiler_support/17

**Verified**

Measured on Apple clang 21 with libc++ only. GCC is not on this host, so libstdc++ is not measured; the standard permits it to move in both cases.

## F#: a `Map` keyed by a tuple allocates about 1.1 KB per lookup, and the same `compare` in your own code allocates nothing

*Perf and memory model*

**Did you know**

`Map` and `Set` are generic code compiled inside FSharp.Core, so they cannot use the type-specialized comparison that `compare` gets at your call site. They get a comparer from `FastGenericComparerTable<'T>`, which has fast entries for primitives and `string` only. Everything else falls back to the object-based generic comparison. For a `System.Tuple`, that path calls `IStructuralComparable.CompareTo(obj, comparer)`, which boxes each element it compares. A `Map` with 90,000 `int * int` keys spends about 17 comparisons per lookup and allocated **1118 bytes per lookup**. A `struct (int * int)` key is worse, at about 1.9 KB per lookup, because the struct itself gets boxed as well. A record key with the same two `int` fields allocated only the 24 bytes of the key itself. The compiler-generated `CompareTo` on a record compares the fields directly.

**Show me**

```fsharp
// dotnet fsi --optimize+, .NET 8.0.8, FSharp.Core 8.0.0.0. Numbers from that run.
type CellKey = { row: int; col: int }

let size = 300  // 90,000 keys, so a lookup does about 17 comparisons
let cells = [ for row in 0 .. size - 1 do for col in 0 .. size - 1 -> row, col ]
let by_tuple  = cells |> List.map (fun (row, col) -> (row, col), row + col) |> Map.ofList
let by_record = cells |> List.map (fun (row, col) -> { row = row; col = col }, row + col) |> Map.ofList

// Bytes allocated per lookup, measured with GC.GetAllocatedBytesForCurrentThread:
//   Map<int, _>              0      (Int32Comparer from the fast table)
//   Map<CellKey, _>         24      (just the key record you allocate)
//   Map<int * int, _>     1118      (keys built in advance, so this is all comparison)
//   Map<struct(int*int),_> 1864     (boxes the struct, then its items)
//
// The same tuple comparison in your own code is specialized at compile time:
//   compare (3, 4) (150, 150)    -> 0 bytes
// The difference is where the code is compiled, not the tuple.
let hit = by_tuple.[(3, 4)] + by_record.[{ row = 3; col = 4 }]
```

**Why it matters**

A grid, a `(tenant, id)` cache, or a `(from, to)` edge map is exactly the shape that makes people reach for a tuple key. At 20,000 lookups a second that is over a gigabyte of gen-0 garbage a minute, with about 7x the latency of an `int` key (939 ns against 135 ns per lookup here). The fix needs no new library: declare a two-field record, or pack the pair into an `int64`. Rust's `BTreeMap<(u32, u32), _>` allocated 0 bytes over 100,000 lookups, because `Ord` for a tuple is monomorphized into the map's code. C++'s `std::map<std::pair<int,int>, _>` is the same template story.

**Chew on this**

Which of your `Map` or `Set` keys are tuples because a record felt like ceremony? Would your allocation profiler point at `Map.find`, or at the GC it causes?

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-core-languageprimitives.html
- https://learn.microsoft.com/en-us/dotnet/api/system.gc.getallocatedbytesforcurrentthread

## TypeScript: Effect 4.0 swapped `partition` to `[passes, fails]`, and when both halves have one type, tsc accepts the old destructuring

*New discoveries and currently popular patterns*

**Did you know**

Effect 4.0.0 shipped on 2026-10-01. Among its breaking changes: the `partition` functions in `Array`, `Chunk`, `Effect` and `Record` now return successes before failures. In 3.x the order was `[failures, successes]`. The type parameters swap along with the values, so the compiler catches the change only when your error type and success type differ. A check that fails *with the id* and succeeds *with the id* has `E = A = string`. The 3.x line `const [denied, allowed] = yield* Effect.partition(ids, check)` still type-checks on 4.0 with no errors, and now `denied` holds the admins. Separately, v4's `Array.partition` no longer takes a boolean predicate; it takes a filter that returns a `Result`.

**Show me**

```typescript
// tsc 6.0.3 --strict, Node 22.17.1. Same file run against effect 3.22.2 and 4.0.0.
import { Effect } from "effect"

// Fail with the id when access is denied, succeed with it when allowed.
const check_access = (user_id: string): Effect.Effect<string, string> =>
  user_id.startsWith("admin") ? Effect.succeed(user_id) : Effect.fail(user_id)

const program = Effect.gen(function* () {
  // Written against 3.x, where the order was [failures, successes].
  const [denied, allowed] = yield* Effect.partition(["admin-ann", "bob", "cy"], check_access)
  console.log("denied:", denied, "allowed:", allowed)
})

Effect.runPromise(program)
// effect 3.22.2: tsc clean. denied: [ 'bob', 'cy' ]  allowed: [ 'admin-ann' ]
// effect 4.0.0:  tsc clean. denied: [ 'admin-ann' ]  allowed: [ 'bob', 'cy' ]
```

**Why it matters**

Effect's v4 messaging is about the migration guide and the coding agent that will "do most of the work", and an automated migration is exactly the pass that leaves a type-clean swap behind. The values move but the types do not, so `tsc` gives no help. The guard is to give the halves different types: a tagged error such as `{ _tag: "Denied", user_id }` turns the swapped destructuring into a type error at its first use. F#'s `List.partition` and Rust's `Iterator::partition` both return `(matching, rest)` by position too, and neither has ever changed its order. That stability is the only thing protecting a same-typed tuple in those languages.

**Chew on this**

How many of your `partition` calls have the same type in both halves? If one of them flipped tomorrow, which test would fail: one that checks the contents, or only one that checks the counts?

# The functional angle: a persistent map is only as cheap as the comparator it is handed, and F# hands it the slow one for tuples

Draws on the F# tip, with Rust and C++ as the contrast. The functional data structure here is the ordered tree map: `Map` in F#, `BTreeMap` in Rust, `std::map` in C++. The comparator is a function value the tree calls on every step down. The question is whether that function gets specialized for the key type or reached through an interface.

```rust
// Rust: Ord for (u32, u32) is monomorphized into BTreeMap's search loop.
// A counting global allocator saw 0 bytes over 100,000 lookups (rustc 1.95.0 -O).
let total: u64 = (0..100_000_u32)
    .map(|step| u64::from(by_tuple[&(step % size, (step * 7) % size)]))
    .sum();
```

```typescript
// TypeScript has no ordered map, and Map compares keys with SameValueZero,
// so a tuple key does not work at all (Node 22.17.1):
new Map([[[1, 2], "x"]]).has([1, 2])        // false: arrays compare by reference
new Map([["1,2", "x"]]).has(`${1},${2}`)    // true, at the cost of a string per lookup
```

| Language | Functional form | Bytes per lookup, 90,000 keys | What it costs |
| --- | --- | --- | --- |
| F# | `Map<int * int, _>` | 1118 | runtime comparer via `IStructuralComparable`, boxing every element compared |
| F# | `Map<CellKey, _>` (record) | 24 | only the key; the generated `CompareTo` compares fields directly |
| Rust | `BTreeMap<(u32, u32), _>` | 0 | nothing; `Ord` is monomorphized into the map's code |
| C++ | `std::map<std::pair<int,int>, _>` | not measured | `std::less<pair>` is template code inlined into `find` |
| TypeScript | `Map<string, _>` with `` `${row},${col}` `` | not measured | no tuple key at all; one string built per lookup |

The interesting row is F# with a record key. It is the same persistent tree, through the same interface, and it costs nothing extra. So functional style is not the cost. The cost comes from `System.Tuple` being a BCL type that only knows how to compare `obj`, while the record's comparison is generated by the F# compiler. Note also that Rust and C++ pay with code size, one tree search per key type, to get the zero. Which of your hot maps would you rather pay for in binary size than in GC?

# The security angle: a same-typed pair is an authorization decision that no type checks

Draws on the TypeScript and Rust tips. This runs the "language does not prevent it" direction. Both tips show a two-element result where position alone decides which half gets permission. One position flipped with a library upgrade. The other position is the same key twice.

**Mode B, applied to the TypeScript tip.** The partition swap is CWE-863 (incorrect authorization) once the halves gate access. The code that looks fine:

```typescript
// Looks like a filter step. After an upgrade it grants the denied list.
const [denied, allowed] = yield* Effect.partition(requests, authorize)
yield* Effect.forEach(allowed, grant)
```

**Mode D, the fix that survives the next upgrade.** Make the halves different types, so the destructuring cannot type-check in the wrong order:

```typescript
class Denied { readonly _tag = "Denied"; constructor(readonly user_id: string) {} }
const authorize = (user_id: string): Effect.Effect<string, Denied> =>
  user_id.startsWith("admin") ? Effect.succeed(user_id) : Effect.fail(new Denied(user_id))
// Now `grant(allowed_item)` with a Denied in hand is a type error, in either Effect version.
```

**Mode C, applied to the Rust tip.** Leave out the `from == to` check before `HashMap::get_disjoint_mut` and a self-transfer request is a reachable panic. That is CWE-617 (reachable assertion), and it becomes a denial of service (CWE-400 class) once a poisoned `Mutex` makes every later `lock().unwrap()` panic too.

```rust
// Missing check: the request picks both keys.
let [from, to] = accounts.get_disjoint_mut([&request.from, &request.to]);
// The check that belongs before it:
if request.from == request.to { return Err(TransferError::SameAccount); }
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | same-typed tuple halves swap with an upgrade | nothing; `[A[], A[]]` is symmetric | distinct types per half (tagged error), content-checking tests |
| Rust | duplicate key in `get_disjoint_mut` | panics rather than aliasing, so memory is safe | reject `from == to` before the call; `catch_unwind` is not a request guard |
| C++ | two `find`s into one map alias the same value | nothing; both iterators are valid | the same `from == to` check |
| F# | self-transfer on a `Map` with two `Map.add`s | nothing; the second write wins (measured: `ann` 100 -> 110) | the same `from == to` check |

Rust is the baseline row for the duplicate-key class, because it is the only one of the four where the duplicate key fails loudly. The others write the wrong balance without any error. TypeScript is the baseline for the swap class, because its types are the only check there is and they cannot see a symmetric swap. Which of your authorization steps take their answer from a tuple position?
