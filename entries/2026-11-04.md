## Rust: A forgotten Vec::drain(2..4) loses six of eight elements, the tail included, while a forgotten String::drain removes nothing

*Perf and memory model*

**Did you know**

`Vec::drain(range)` hands back a guard, and that guard's `Drop` puts the tail back. Forget the guard with `mem::forget` and the `Vec` is left at the start of the range. On rustc 1.99.1 a forgotten `drain(2..4)` on eight connections left `len() == 2`: elements 2 and 3 were taken, and 4 through 7 were lost with them. Six of the eight values never ran `Drop`. The documentation warns of this: the vector "may have lost and leaked elements arbitrarily, including elements outside the range". `VecDeque::drain` behaves the same. `String::drain` is the opposite: a forgotten `drain(2..4)` left `"abcdefgh"` untouched.

**Show me**

```rust
// rustc 1.99.1, edition 2021
use std::cell::Cell;
use std::mem;

thread_local! { static DROPS: Cell<usize> = const { Cell::new(0) }; }

struct Connection { id: u32 }
impl Drop for Connection {
    // in real code this would close a socket; here it only counts
    fn drop(&mut self) { DROPS.with(|drops| drops.set(drops.get() + 1)); }
}

fn main() {
    let mut mut_pool: Vec<Connection> = (0..8).map(|id| Connection { id }).collect();
    let drain_guard = mut_pool.drain(2..4); // meant to remove ids 2 and 3
    mem::forget(drain_guard);               // the guard's Drop, which moves the tail back, never runs
    println!("pool.len() after forgotten drain(2..4) = {}", mut_pool.len()); // 2
    println!("ids left: {:?}", mut_pool.iter().map(|connection| connection.id).collect::<Vec<_>>()); // [0, 1]
    drop(mut_pool);
    println!("Connection drops counted = {} of 8", DROPS.with(Cell::get)); // 2 of 8
}
```

C++'s `vector::erase(first, last)` has nothing to forget: it is eager, and the tail has moved before the call returns. TypeScript's `splice` is eager too. Rust's `drain` is lazy, so the clean-up is deferred to a guard, and deferred work can be skipped.

**Why it matters**

The `Vec` shortens itself to the range start before it hands out the guard, so a lost guard can never expose a slot whose value was already moved out. That keeps it memory safe. The Rustonomicon's name for "leaks causing more leaks" is leak amplification. In a server the lost elements are resources, not bytes: sockets, file handles and pooled buffers that are never closed. A guard does not have to be forgotten on purpose to be lost. Keeping it inside an `Rc` cycle or in a `ManuallyDrop` loses it the same way.

**Chew on this**

Which of your types keep a guard whose `Drop` is what restores the container's invariant, and can anything that owns them leak? For a pool of live connections, is "memory safe, but the tail is gone" the failure you would have picked?

**Sources**

- https://doc.rust-lang.org/std/vec/struct.Vec.html#method.drain
- https://doc.rust-lang.org/std/collections/struct.VecDeque.html#method.drain
- https://doc.rust-lang.org/std/string/struct.String.html#method.drain
- https://doc.rust-lang.org/std/mem/fn.forget.html
- https://doc.rust-lang.org/nomicon/leaking.html (the Drain example and "leak amplification")

**Gotchas**

- The buffer itself is not leaked: after the forget, `capacity()` was still 8 and the allocation was freed when the `Vec` dropped. Only the six elements' `Drop` never ran.
- A drain that is partly consumed and then dropped still removes the whole range. `next()` returned `Some(2)`, the guard was dropped, and the `Vec` read `[0, 1, 4, 5, 6, 7]`: element 3 was dropped unseen.
- A panic does not trigger this: unwinding runs the guard's `Drop`. Only a guard that is never dropped (`mem::forget`, an `Rc` cycle, `ManuallyDrop`) loses the tail.
- The three std drains do not agree. Measured on 1.99.1: a forgotten `Vec` drain gave `len 2`, a forgotten `VecDeque` drain gave `len 2` and `[0, 1]`, and a forgotten `String` drain kept all 8 bytes.

## C++: C++26 dropped std::nontype in March 2026, so function_ref binds a compile-time callable with std::cw and refuses the call move_only_function answers differently

*New discoveries and currently popular patterns*

**Did you know**

`std::function_ref` (C++26) used to take a compile-time callable through `std::nontype<f>`, which a later draft renamed `std::constant_arg`. P3948R1, dated 2026-03-24, removed both. The constructor now takes the general-purpose `std::constant_wrapper`, spelled `std::cw<f>`. GCC 16.2 ships the new form and reports `__cpp_lib_function_ref` as `202603`. Code written to the older draft now fails with `'nontype' is not a member of 'std'; did you mean 'ctype'?`. Support state: C++26, libstdc++ in GCC 16 only. Debian clang 19.1.7 uses libstdc++ 14.2 and has no `function_ref` at all. libc++ and MSVC were not checked.

**Show me**

```cpp
// C++26, GCC 16.2: g++ -std=c++26 -O2 -Wall -Wextra
#include <functional>
#include <utility>
#include <cstdio>

struct Counter {
    int hits = 0;
    int bump(int step) { hits += step; return hits; }
};

int twice(int amount) { return amount * 2; }

int run_with(std::function_ref<int(int)> callback, int amount) { return callback(amount); }

int main() {
    Counter counter;
    // a member function plus the object it acts on, bound without writing a lambda
    const std::function_ref<int(int)> const_bump_ref(std::cw<&Counter::bump>, counter);
    const_bump_ref(3);
    const_bump_ref(4);
    std::printf("counter.hits=%d\n", counter.hits);              // 7: the ref writes through to counter
    std::printf("cw<twice>: %d\n", run_with(std::cw<twice>, 21));  // 42, the function is a template argument
    std::printf("plain twice: %d\n", run_with(twice, 21));         // 42, through a function pointer
    std::printf("sizeof=%zu\n", sizeof(std::function_ref<int(int)>)); // 16 either way
    // std::function_ref<int(int)> old_ref(std::nontype<twice>); // error: 'nontype' is not a member of 'std'
}
```

**Why it matters**

`function_ref` is the non-owning, never-allocating callback type, the one you put on a hot path. P3948R1 says `cw<f>` lets an optimized build call `f` directly instead of through the stored pointer (not measured here). Any code that adopted the 2025 drafts or an early GCC 16 snapshot has to change `nontype` or `constant_arg` to `cw`. That edit is mechanical, but it is a compile break in code that already shipped.

**Chew on this**

The same `std::cw<f>` argument is now accepted by `function_ref`, `move_only_function`, `copyable_function` and `function`, but only `function_ref` unwraps it. If you swap one wrapper for another during a refactor, which of your callables would answer differently, and would anything tell you?

**Sources**

- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p3948r1.pdf (P3948R1, "constant_wrapper is the only tool needed for passing constant expressions via function arguments", 2026-03-24)
- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3792r0.html (P3792R0, the objection it answers)
- https://cpprefjp.github.io/reference/functional/function_ref.html (in Japanese)

**Gotchas**

- The two wrappers do disagree, and GCC 16.2 catches only one side. Take a callable that counts its arguments unless they are integers, and a `Tag` type with `static constexpr int value = 42`. Then `move_only_function<int(Tag)>(std::cw<sum_all>)(Tag{})` returned 42, because `cw`'s own `operator()` unwrapped `Tag::value`. `sum_all(Tag{})` called directly returned 1. The same `cw` passed to `function_ref` failed to compile: `static assertion failed: cw<fn>(args...) should be equivalent to fn(args...)`. That is the rejection P3948R1's wording mandates.
- Binding at compile time does not shrink the ref: `sizeof` is 16 with `cw<twice>` and with `twice`. The paper says a non-null pointer is stored anyway.
- P3948R1 lists `f1(std::cw<[](int) { return 1; }>)` as ill-formed because of a language limitation. GCC 16.2 compiled `run_with(std::cw<[](int amount) { return amount * 2; }>, 21)` and returned 42. I did not find out which later change allows it, so do not depend on it across compilers.
- `constant_arg` is gone as well, not only `nontype`: `'constant_arg' is not a member of 'std'`.

**Related**

- [2026-10-31](2026-10-31.md) - the functional angle, "passing a function is free only where the compiler can see its body". `cw<f>` is C++26's way of handing it that body.

## F#: F# 11's preview lets an SRTP constraint use an extension member, but only one in scope where the inline function was written

*Type system deep cuts*

**Did you know**

Until now, a statically resolved member constraint (`^T : (member Shout : ...)`) ignored extension members. An extension on `System.String` cannot satisfy it, even though `"hello".Shout()` compiles. RFC FS-1043 changes that. Its implementation (dotnet/fsharp PR 19602) merged on 2026-08-21, and with .NET 11 RC 3 (SDK 11.0.100-rc.3, FSharp.Core 11.0.0.0) it works under `--langversion:preview`. The scope is narrow: it found the extension only when the extension was in scope where `shout` itself was defined. An extension declared after `shout`, or opened only at the call site, still failed.

**Show me**

```fsharp
// dotnet fsi --langversion:preview, .NET SDK 11.0.100-rc.3, FSharp.Core 11.0.0.0
type System.String with                       // optional extension: String is not our type
    member text.Shout() = text.ToUpperInvariant() + "!"

type Celsius = { Degrees: float }
type Celsius with                             // intrinsic extension: same file as the type
    member reading.Shout() = sprintf "%.1f C!" reading.Degrees

let inline shout (value: ^T) = (^T : (member Shout : unit -> string) value)

printfn "%s" (shout { Degrees = 21.5 })       // 21.5 C!  on F# 10 and F# 11
printfn "%s" (shout "hello")                  // HELLO!   only with F# 11 preview
// F# 10 (SDK 10.0.403), even with --langversion:preview:
//   error FS0001: The type 'string' does not support the operator 'Shout'
```

**Why it matters**

Generic numeric and formatting helpers written with `inline` could not take a BCL type you do not own, unless you wrapped it. FS-1043 removes the wrapper, but resolution is fixed by the extension modules in scope where the generic helper is written, not where it is called. A helper in a shared library cannot see an extension the caller opened. To use one, the helper's own file must open the extension module.

**Chew on this**

If a library's `inline` helper captures whatever extensions were in scope when the library was compiled, which module of yours now decides how your type is printed, compared or added? Would you rather the caller's `open` won?

**Sources**

- https://github.com/fsharp/fslang-design/blob/main/RFCs/FS-1043-extension-members-for-operators-and-srtp-constraints.md
- https://github.com/dotnet/fsharp/pull/19602 (merged 2026-08-21)
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/generics/statically-resolved-type-parameters

**Verified**

Both .NET SDK images (`mcr.microsoft.com/dotnet/sdk:10.0` and `mcr.microsoft.com/dotnet/nightly/sdk:11.0`) are Ubuntu, not Debian; .NET publishes no Debian SDK image. F# 11 is a release candidate, so the preview behaviour may change before it ships.

**Gotchas**

- The error calls a method an operator. F# 10 reports `The type 'string' does not support the operator 'Shout'` for a plain named member.
- On F# 10, `--langversion:preview` does nothing for this: SDK 10.0.403 failed the same way. The feature needs the F# 11 compiler and the preview flag together. With the F# 11 RC's default language version it still fails.
- Where the extension is written matters, even with the preview flag. Three layouts still failed on F# 11 RC 3: the extension declared after `shout`, the extension in a module opened only at the call site, and a later function calling `shout "hello"`.
- An intrinsic extension (same file and namespace as the type) always satisfied the constraint, on F# 10 as well. Only the optional extension on a type you do not own needed the preview.

- [2026-10-31](2026-10-31.md) - F#, "InlineIfLambda changed nothing for a one-line lambda". The same `inline` machinery: it decides what is resolved at the definition and what is copied to the call.

## TypeScript: Buffer.from(text, "base64") skips a * and trailing junk and still returns hello, while Uint8Array.fromBase64 throws, and only strict mode refuses aGVsbG9=

*Stdlib and ecosystem gems*

**Did you know**

Node 26.13 (the current LTS) has the TC39 base64 methods: `Uint8Array.fromBase64` and `toBase64`. The proposal is at stage 4. They are stricter than the `Buffer.from(text, "base64")` everyone uses. Measured: `Buffer` decoded `"aGV*sbG8="` and `"aGVsbG8=junk!"` to `hello` without a word. `fromBase64` threw `SyntaxError: Found a character that cannot be part of a valid base64 string.` Its default, `lastChunkHandling: "loose"`, still accepts a missing `=` and non-zero padding bits. Only `"strict"` refuses `aGVsbG9=`, a second spelling of `hello`.

**Show me**

```ts
// Node v26.13.0; tsc 7.0.2 needs --lib esnext (es2024 reports TS2550)
const const_fn_decode_bytes = (label: string, fn_attempt: () => Uint8Array): void => {
    try { console.log(label.padEnd(40), Array.from(fn_attempt()).join(",")); }
    catch (decode_error) { console.log(label.padEnd(40), "throws", String(decode_error)); }
};
const_fn_decode_bytes("Buffer, a * inside",        () => Buffer.from("aGV*sbG8=", "base64"));      // 104,101,108,108,111
const_fn_decode_bytes("Buffer, junk after the =",  () => Buffer.from("aGVsbG8=junk!", "base64"));  // 104,101,108,108,111
const_fn_decode_bytes("fromBase64, a * inside",    () => Uint8Array.fromBase64("aGV*sbG8="));      // throws SyntaxError
const_fn_decode_bytes("fromBase64, no padding",    () => Uint8Array.fromBase64("aGVsbG8"));        // hello: loose is the default
const_fn_decode_bytes("fromBase64, pad bits set",  () => Uint8Array.fromBase64("aGVsbG9="));       // hello again
const_fn_decode_bytes("strict, pad bits set",      () =>
    Uint8Array.fromBase64("aGVsbG9=", { lastChunkHandling: "strict" }));                           // throws: non-zero padding bits
```

The same split runs across the other three languages. .NET's `Convert.FromBase64String` (seen from F#) threw `FormatException` on the `*` and on the missing padding, and accepted `aGVsbG9=`. The Rust `base64` crate 0.22.1 `STANDARD` engine refused all four variants, `InvalidLastSymbol(6, 57)` for the padding bits included. C++ has no base64 in std.

**Why it matters**

A decoder that drops characters it does not understand turns "malformed input" into "valid input with different bytes", and nobody upstream finds out. That matters when the bytes are a token, a signature or a key. Two different strings decoding to the same bytes matters whenever something caches, deduplicates or blocks on the string rather than on the bytes.

**Chew on this**

Every base64 input you decode either comes from your own encoder or arrives over the wire, and the two deserve different modes. Where in your services is the decode mode chosen, and does anything compare the strings before decoding them?

**Sources**

- https://github.com/tc39/proposal-arraybuffer-base64 (stage 4; `lastChunkHandling` loose, strict and stop-before-partial)
- https://nodejs.org/api/buffer.html#buffers-and-character-encodings
- https://datatracker.ietf.org/doc/html/rfc4648#section-3.5

**Gotchas**

- `fromBase64` skips whitespace as well: `"aGVs bG8="` decoded to `hello`. Node's Buffer docs say whitespace is ignored there too. The documentation does not say that `Buffer` skips characters such as `*`; I measured it.
- `Buffer`'s `"base64"` accepts both alphabets in one string: `"-_8"` and `"+/8="` both gave `251,255`. `fromBase64` throws on `-` unless you pass `{ alphabet: "base64url" }`.
- Strict also refuses a missing `=`: `"aGVsbG8"` threw `The base64 input terminates with a single character, excluding padding (=).` The message is V8's, and the input is 7 characters, not 1 extra.
- tsc 7.0.2 declares the methods only under `--lib esnext`; there is no `es2026` lib option yet. With `es2024` you get TS2550, `Property 'fromBase64' does not exist on type 'Uint8ArrayConstructor'`.
- `atob("aGV*sbG8=")` throws (`DOMException: Invalid character`), so `atob` is stricter than `Buffer`. It returns a binary string, not bytes.

# The functional angle: a generic call finds its extension in a different place in each language, and F# and C++ both stop at the definition for a type you do not own

Draws on the F# tip (SRTP and extensions) and the C++ tip (binding a callable at compile time). The shape is ad-hoc polymorphism: a generic function calls `shout(value)`, and someone else supplies `shout` for a type neither of them owns.

```rust
// Rust 1.99.1: an impl is global to the crate; where it is written does not matter
fn shout_all<T: loud::Shout>(value: &T) -> String { value.shout() }
mod loud { pub trait Shout { fn shout(&self) -> String; } }
mod hidden_impls { // private, written after shout_all, never imported anywhere
    impl crate::loud::Shout for String {
        fn shout(&self) -> String { format!("{}!", self.to_uppercase()) }
    }
}
// shout_all(&String::from("hello")) -> HELLO!
```

```cpp
// C++20, GCC 16.2 and Debian clang 19.1.7: the same unqualified call, looked up twice
template <class T> std::string shout_all(const T& value) { return shout(value); }
namespace loud {
    struct Reading { double degrees; };
    std::string shout(const Reading& reading) { return std::to_string(reading.degrees) + " C!"; }
}
std::string shout(const std::string& text) { return text + "!"; } // after the template, global namespace
// shout_all(loud::Reading{21.5})     -> 21.500000 C!   (argument-dependent lookup at instantiation)
// shout_all(std::string("hello"))    -> GCC: "'shout' was not declared in this scope, and no declarations
//    were found by argument-dependent lookup at the point of instantiation"; clang: "neither visible in the
//    template definition nor found by argument-dependent lookup"
```

```fsharp
// F# 11 RC 3 with --langversion:preview: the extension must be in scope where shout is defined
type System.String with
    member text.Shout() = text.ToUpperInvariant() + "!"
let inline shout (value: ^T) = (^T : (member Shout : unit -> string) value)
// shout "hello" -> HELLO!  ; move the extension below shout, or open it only at the call: FS0001
```

| Language | Where the extension must be | What it costs |
| --- | --- | --- |
| F# 11 preview | in scope at the `inline` function's definition | measured: a call-site `open` or a later declaration gives FS0001; the helper's file must open the extension |
| Rust | anywhere in the crate (impls are global), but only your own trait or your own type (orphan rule) | measured: the impl in a private module written later worked; for a foreign trait and a foreign type you need a newtype |
| C++ | an associated namespace of the argument (found at instantiation), or declared before the template | measured: `shout(const std::string&)` in the global namespace is invisible to the template, because ADL for `std::string` searches `std` only |
| TypeScript | not expressible: types are erased, so no call is chosen by type | you pass the implementation as a value (a dictionary of functions), which is the hand-written form of what the other three do |

F# and C++ fail on the same shape for different reasons: F# records the extensions in scope when the constraint is asserted in the function body, and C++ splits the lookup in two and gives the second half only to ADL. Rust avoids the scope question altogether, and pays with the orphan rule. Which of the costs in the third column would you rather your library's users discover the hard way?

# The security angle: a lenient decoder makes two different strings mean the same bytes, and anything keyed on the string can be walked around

Draws on the TypeScript tip and runs in the "does not prevent" direction (Mode B): `Buffer.from(text, "base64")` is fine for decoding what your own encoder wrote, but is it secure to use on input? Bug class: CWE-1289, Improper Validation of Unsafe Equivalence in Input.

```ts
// TypeScript, Node 26.13: a revocation list keyed on the token string, decoded leniently
const const_revoked_tokens: ReadonlySet<string> = new Set(["aGVsbG8="]);
const const_fn_session_key = (presented_token: string): Uint8Array | undefined =>
    const_revoked_tokens.has(presented_token) ? undefined : Buffer.from(presented_token, "base64");
// const_fn_session_key("aGVsbG8=")  -> undefined (revoked)
// const_fn_session_key("aGVsbG9=")  -> bytes of hello: a different string, the same key
// const_fn_session_key("aGV*sbG8=") -> bytes of hello again: Buffer skipped the *
```

The fix is to make the string canonical before it is checked, or to key the check on the decoded bytes. `Uint8Array.fromBase64(presented_token, { lastChunkHandling: "strict" })` threw on both variants above.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript (Node) | `Buffer` skips stray characters, mixes both alphabets, accepts any padding bits | `fromBase64` throws on stray characters; `strict` also refuses missing `=` and set padding bits | pick `strict` for input; compare bytes, not strings |
| F# (.NET 10 `Convert`) | `aGVsbG9=` decodes to `hello`, whitespace is skipped | `FormatException` on `*` and on missing padding | non-canonical padding bits still pass; re-encode and compare if the string is a key |
| Rust (`base64` 0.22.1 `STANDARD`) | nothing measured: all four variants were refused | `InvalidByte`, `InvalidLastSymbol`, `InvalidPadding` as values in a `Result` | an engine with a lenient config (it can be configured) is a review item |
| C++ | no std base64, so you pick a library | nothing | check what your vendored decoder does with `aGVsbG9=` before trusting it |

Rust is the baseline here only by accident of its crate's default: the strictness lives in a configuration, not in the language. Which of your caches, deny-lists or idempotency keys are keyed on a string that some decoder treats as equal to another one?

# FAQ

**Does `mem::forget` on a `Drain` count as unsafe code?**
No. `mem::forget` is a safe function, and the forgotten `Vec::drain` compiled with no `unsafe` block. Leaking is not undefined behaviour in Rust, which is why `Vec` shortens itself before it hands out the guard.

**Can I write `std::cw<f>` in place of `nontype<f>` and keep the old behaviour?**
For a plain function or member pointer, yes: `cw<&Counter::bump>` with an object, and `cw<twice>`, both ran as expected on GCC 16.2. The exception is a callable that can also be called on `constant_wrapper` values: `function_ref` refuses those with a static assertion.

**Does the F# preview change existing code that compiled before?**
The RFC says weak resolution is turned off for inline code where real overload resolution is involved, and that this can change inference. I did not measure an existing program changing; treat any diff in inferred types after enabling preview as this.

**Is `Buffer.from(text, "base64url")` stricter?**
No. On Node 26.13 `"base64url"` decoded `"aGV*sbG8="` to `hello` too, and accepted the standard alphabet (`"+/8="` gave `251,255`): both names were equally lenient.
