**The thesis: a timestamp can now say which zone it was written in, and that makes it possible for the string to disagree with itself.** RFC 9557 (April 2024) appends the zone ID to an RFC 3339 timestamp: `2026-10-22T12:00:00-05:00[America/Chicago]`. The new libraries read it and check the offset against the zone. The old ones either refuse the whole string or read the part they understand and ignore the rest.

| `2026-10-22T12:00:00-05:00[America/Chicago]` | Reads it? | Writes it? | Stale offset (`-05:00` for a zone now at `-06:00`) |
| --- | --- | --- | --- |
| Rust `jiff` 0.2.38 `Zoned` | yes | yes (`Display`) | **rejected** by default |
| Rust `chrono` 0.4.45 `parse_from_rfc3339` | no: `Err("trailing input")` | no | not reached |
| C++20 `chrono::parse("%FT%T%Ez")` | reads the instant, leaves `[...]` unread, reports success | only by hand | never checked |
| F# / .NET 8 and 10 `DateTimeOffset.Parse`, System.Text.Json | no: `FormatException`, `JsonException` | no | not reached |
| TypeScript `Temporal.ZonedDateTime` (Node 26) | yes | yes, also into JSON | **rejected** by default |
| TypeScript `Date` (Node 22 and 26) | no: `NaN` | no | not reached |

## Rust: `jiff` refuses a stored timestamp whose offset no longer matches its zone, and `chrono` refuses the bracket entirely

*Stdlib and ecosystem gems*

**Did you know**

Rust `jiff` (0.2.38) parses and prints RFC 9557 strings, and it checks the offset against the zone's current rules. `2023-07-01T12:00:00-05:00[America/Mexico_City]` was correct under the rules of 2021. Mexico abolished DST in October 2022, so today's tzdata says July 2023 there is `-06:00`, and `jiff` rejects the string by default ("`reject` conflict resolution was chosen ... `America/Mexico_City` ... unambiguously has offset `-06`"). Rust `chrono` (0.4.45) never gets that far: `parse_from_rfc3339` stops at the bracket with `Err("trailing input")`.

**Show me**

```rust
// Rust: jiff 0.2.38 and chrono 0.4.45, rustc 1.95.0
use jiff::{fmt::temporal::DateTimeParser, tz::OffsetConflict, Zoned};

fn main() {
    // RFC 9557: an RFC 3339 timestamp plus the zone it was written in.
    let bracketed = "2026-10-22T12:00:00-05:00[America/Chicago]";
    let zoned: Zoned = bracketed.parse().unwrap();
    println!("{zoned}"); // jiff writes the same form back
    println!("{:?}", chrono::DateTime::parse_from_rfc3339(bracketed).map_err(|error| error.to_string()));
    // Err("trailing input"): chrono's RFC 3339 parser stops at the bracket

    // Written under Mexico City's old rules (CDT, -05:00). Mexico abolished DST in October 2022,
    // so today's tzdata says July 2023 there is -06:00. The string now disagrees with itself.
    let stale = "2023-07-01T12:00:00-05:00[America/Mexico_City]";
    println!("{}", stale.parse::<Zoned>().is_err()); // true: the default is Reject

    let fn_resolve = |conflict: OffsetConflict| {
        DateTimeParser::new().offset_conflict(conflict).parse_zoned(stale).unwrap().to_string()
    };
    println!("{}", fn_resolve(OffsetConflict::AlwaysTimeZone)); // 2023-07-01T12:00:00-06:00[...]: keep the wall clock
    println!("{}", fn_resolve(OffsetConflict::AlwaysOffset));   // 2023-07-01T11:00:00-06:00[...]: keep the instant
}
```

**Why it matters**

The rejection is the feature: it is the only place a program finds out that a government changed the rules after the value was stored. The two repairs are a business decision, not a parsing one. Keep the wall clock (`AlwaysTimeZone`, and `PreferOffset` here) and a 12:00 meeting stays at 12:00 local, an hour later in UTC. Keep the offset (`AlwaysOffset`) and it keeps its instant, now at 11:00 local. Temporal offers the same four choices under other names (TypeScript tip below). .NET and `chrono` cannot see the conflict, because they cannot read the zone.

**Chew on this**

When a stored future time stops matching its zone, should your system move the event in UTC or on the wall clock? Who in your organization would get to decide, and does the code say which they decided?

**Sources**

- https://www.rfc-editor.org/rfc/rfc9557.html
- https://docs.rs/jiff/0.2.38/jiff/fmt/temporal/struct.DateTimeParser.html#method.offset_conflict
- https://docs.rs/jiff/0.2.38/jiff/tz/enum.OffsetConflict.html

**Gotchas**

- `"...-05:00[America/Chicago]".parse::<jiff::Timestamp>()` succeeds and ignores the zone (`2026-10-22T17:00:00Z`, measured): only `Zoned` checks the annotation.
- An annotation with the critical flag, `[!x-foo=bar]`, is rejected ("unsupported RFC 9557 annotation with the critical flag (`!`) set"), while `[u-ca=japanese]` is accepted and dropped from the output (both measured).
- Rust and its crates evolve: this is `jiff` 0.2.38 and `chrono` 0.4.45. A `chrono` user who wants the bracket form has to split it off by hand, as the F# tip does.

## C++: `chrono::parse` reads an RFC 9557 string up to the bracket and reports success, so the zone is silently ignored

*Idioms and antipatterns*

**Did you know**

C++20's `std::chrono::parse("%FT%T%Ez")` reads `2026-10-22T12:00:00-05:00[Asia/Tokyo]` as 17:00Z, sets no `failbit`, and leaves `[Asia/Tokyo]` unread in the stream. The zone in the string is not even consistent with the offset, and nothing notices. Writing the format is no better: `%Z` is the abbreviation (`CDT`), not the zone ID, so `"{:%FT%T%Ez}[{:%Z}]"` produces `...-05:00[CDT]`, which is not RFC 9557 at all. The ID has to come from `get_time_zone()->name()`. Measured with GCC 16.2 (libstdc++). Apple's libc++ has neither `parse` nor a tzdb.

**Show me**

```cpp
// C++20: GCC 16.2 (libstdc++), tzdata 2026c on Debian 13
#include <chrono>
#include <cstdio>
#include <format>
#include <sstream>
#include <string>
using namespace std::chrono;

int main() {
    // An RFC 9557 string, as Temporal, Rust jiff and Java write it.
    std::istringstream stream("2026-10-22T12:00:00-05:00[Asia/Tokyo]"); // the zone even disagrees with the offset
    sys_seconds instant;
    stream >> parse("%FT%T%Ez", instant);
    std::string rest;
    std::getline(stream, rest);
    std::printf("fail=%d instant=%s unread=\"%s\"\n", (int)stream.fail(),
        std::format("{:%FT%TZ}", instant).c_str(), rest.c_str());
    // fail=0 instant=2026-10-22T17:00:00Z unread="[Asia/Tokyo]": success, zone never looked at

    // Writing it: %Z is the abbreviation, not the zone ID, so the bracket has to be built by hand.
    zoned_time chicago{"America/Chicago", sys_days{2026y/October/22} + 17h};
    std::printf("%s\n", std::format("{:%FT%T%Ez}[{:%Z}]", chicago, chicago).c_str());     // ...-05:00[CDT]: wrong
    std::printf("%s[%s]\n", std::format("{:%FT%T%Ez}", chicago).c_str(),
        std::string(chicago.get_time_zone()->name()).c_str());                            // ...-05:00[America/Chicago]
}
```

**Why it matters**

Stream extraction stops at the first character it does not need, and that is correct stream behaviour. It means the usual "did it parse?" check (`if (stream)`) passes for a string with arbitrary text after the offset, including a zone that contradicts it. Rust `jiff` and Temporal reject the same string. .NET rejects it for the opposite reason, because it cannot read brackets at all. C++ is the only one of the four that accepts it, and only because it never reads that far.

**Chew on this**

Where you parse timestamps from a stream, do you check that the stream is at its end afterwards? If a producer starts sending the bracket form, would your parser notice, or quietly keep only the offset?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/parse
- https://www.rfc-editor.org/rfc/rfc9557.html

**Verified**

`docker run gcc:16`. Not buildable on this host's Apple clang (no `chrono::parse`, no tzdb). MSVC not tested.

**Gotchas**

- The safe check is `(stream >> parse(...)) && (stream >> std::ws).eof()`: parsed, and nothing but whitespace left. It accepted the plain string and rejected the bracketed one (measured).
- `%Ez` writes `+00:00` for UTC, never `Z`, on both `sys_time` and a UTC `zoned_time` (measured). Under RFC 9557 that is the right spelling for "UTC is the reference" (FAQ).
- `locate_zone("America/Ciudad_Juarez")` works only with tzdata 2022g or later, because that zone ID did not exist before 2022-11-29 (Appendix A).

## F#: .NET cannot read an RFC 9557 string, so one Temporal field in a JSON request fails the whole bind

*Stdlib and ecosystem gems*

**Did you know**

Neither .NET 8 nor .NET 10 reads the bracket suffix. `DateTimeOffset.Parse("2026-10-22T12:00:00-05:00[America/Chicago]")` throws `FormatException`, and System.Text.Json throws `JsonException` for a `DateTimeOffset` field holding it. JS `Temporal.ZonedDateTime` writes exactly that string into `JSON.stringify` (TypeScript tip below), so a JS front end that moves to Temporal breaks a .NET API on its first request. The workaround is to split the annotation off: parse the RFC 3339 part as a `DateTimeOffset`, and look the zone ID up with `TimeZoneInfo.FindSystemTimeZoneById`. Measured on FSharp.Core 8.0 / .NET 8.0.8 and FSharp.Core 10.1 / .NET 10.0.13.

**Show me**

```fsharp
// F#: FSharp.Core 8.0 / .NET 8.0.8 and FSharp.Core 10.1 / .NET 10.0.13
open System
open System.Globalization
open System.Text.Json

// What a JS service using Temporal puts in its JSON:
let from_temporal = "{\"due\":\"2026-10-22T12:00:00-05:00[America/Chicago]\"}"

type Invoice = { due: DateTimeOffset }

let fn_attempt (label: string) (work: unit -> string) =
    printfn "%-28s %s" label (try work () with error -> error.GetType().Name)

fn_attempt "JsonSerializer" (fun () -> (JsonSerializer.Deserialize<Invoice> from_temporal).due.ToString "o")
// JsonException: the whole request fails to bind
fn_attempt "DateTimeOffset.Parse" (fun () ->
    DateTimeOffset.Parse("2026-10-22T12:00:00-05:00[America/Chicago]", CultureInfo.InvariantCulture).ToString "o")
// FormatException

// Splitting the annotation off by hand works, and keeps the zone ID for TimeZoneInfo:
let fn_split (text: string) =
    let bracket = text.IndexOf '['
    let instant = DateTimeOffset.Parse(text.Substring(0, bracket), CultureInfo.InvariantCulture)
    let zone = TimeZoneInfo.FindSystemTimeZoneById(text.Substring(bracket + 1).TrimEnd ']')
    instant, zone
let instant, zone = fn_split "2026-10-22T12:00:00-05:00[America/Chicago]"
printfn "%s in %s (offset now %O)" (instant.ToString "o") zone.Id (zone.GetUtcOffset instant)
```

**Why it matters**

The failure is loud, which is better than C++'s silence, but it is also total: the whole request is rejected over one field, often with a model-binding error that does not name the format. `DateTimeOffset` has no slot for a zone ID, so even a parser that accepted the bracket would have nowhere to keep it. That is the deeper gap: .NET's types hold an offset, and RFC 9557 exists because an offset is not enough to recompute a future local time after a rule change. Rust `jiff` and Temporal hold both.

**Chew on this**

Which of your .NET APIs accept timestamps from a JS client, and what happens to them the day that client adopts Temporal? If you split the annotation off, where would you keep the zone ID?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.datetimeoffset.parse
- https://learn.microsoft.com/en-us/dotnet/standard/datetime/system-text-json-support
- https://www.rfc-editor.org/rfc/rfc9557.html

**Gotchas**

- `fn_split` above handles exactly one annotation. RFC 9557 allows several (`[America/Chicago][u-ca=japanese]`) and a critical flag (`[!America/Chicago]`), which this code would pass to `FindSystemTimeZoneById` as part of the ID. A real splitter has to parse the suffix grammar.
- `DateTime` with `Kind=Utc` serializes as `...Z`, and `DateTimeOffset` at offset zero as `...+00:00` (measured). Under RFC 9557 those now mean different things (FAQ).
- The same string without the bracket deserializes fine (`2026-10-22T12:00:00.0000000-05:00`, measured), so a test fixture written by hand will not reproduce the failure.

## TypeScript: Temporal writes the bracket into JSON, `Date` reads it as `NaN`, and a stale offset throws unless you choose who moves

*Stdlib and ecosystem gems*

**Did you know**

`JSON.stringify` of a `Temporal.ZonedDateTime` writes the RFC 9557 string, `"2026-10-22T12:00:00-05:00[America/Chicago]"`, and `new Date()` of that string is `NaN` on Node 22 and Node 26. The stored Mexico City string from the Rust tip throws `RangeError` by default, because `offset: "reject"` is Temporal's default for `ZonedDateTime.from`. The two repairs move the meeting in opposite directions. `offset: "prefer"` keeps 12:00 on the wall clock, an hour later in UTC. `offset: "use"` keeps the instant, which is now 11:00 on the wall. Measured on Node 26.12.1, the first Node here with `Temporal`.

**Show me**

```ts
// TypeScript 6.0.3 (lib esnext, which carries Temporal), run on Node 26.12.1
const meeting = Temporal.ZonedDateTime.from("2026-10-22T12:00:00-05:00[America/Chicago]")
const wire = JSON.stringify({ meeting })
console.log(wire)                                  // {"meeting":"2026-10-22T12:00:00-05:00[America/Chicago]"}
console.log(new Date(JSON.parse(wire).meeting).getTime()) // NaN: every Date-based consumer gets Invalid Date

// Stored in 2021 under Mexico City's old rules; Mexico abolished DST in 2022.
const stale = "2023-07-01T12:00:00-05:00[America/Mexico_City]"
try { Temporal.ZonedDateTime.from(stale) }
catch (error) { console.log((error as Error).name) }          // RangeError: the default is offset "reject"

// Two ways to repair it, and they move the meeting in different directions:
console.log(Temporal.ZonedDateTime.from(stale, { offset: "prefer" }).toString()) // 12:00-06:00: same wall clock, an hour later in UTC
console.log(Temporal.ZonedDateTime.from(stale, { offset: "use" }).toString())    // 11:00-06:00: same instant, an hour earlier on the wall
```

**Why it matters**

Moving from `Date` to `Temporal` changes the wire format. Every consumer still on `Date`, and every .NET or `chrono` service (F# and Rust tips), now receives a string it cannot parse. The usual fix is to serialize `toInstant().toString()` for anything that only needs the instant. Then the zone is lost again, and so is the ability to detect a rule change. The rejection on read is how Temporal tells you the rules changed. Silencing it with `"ignore"` or `"use"` across the board turns that warning into a quiet one-hour move.

**Chew on this**

Which of your JSON consumers would receive a `ZonedDateTime` if one were stored in a field today, and which of them could parse it? For stored future events, which `offset` option matches what your users would expect after a rule change?

**Sources**

- https://tc39.es/proposal-temporal/docs/zoneddatetime.html#from
- https://tc39.es/proposal-temporal/docs/zoneddatetime.html#toJSON
- https://www.rfc-editor.org/rfc/rfc9557.html

**Verified**

`console` typed with a one-line `declare` instead of `@types/node`. Run in `docker run node:26`.

**Gotchas**

- `Temporal.Instant.from("...-05:00[America/Chicago]")` succeeds and drops the zone (`2026-10-22T17:00:00Z`, measured), so the check only happens on `ZonedDateTime`.
- `[!America/Chicago]` (critical flag) parses and prints back as `[America/Chicago]`, and an unknown critical key `[!x-foo=bar]` throws `RangeError`, while `[x-foo=bar]` without the `!` is dropped silently (all measured).
- `offset: "ignore"` gave the same result as `"prefer"` here (`12:00-06:00`, measured). They differ only when the stored offset is still valid for the zone, which a stale string by definition is not.

# The functional angle: resolving a stale offset is a choice of four functions, and two libraries gave them different names

Draws on the Rust and TypeScript tips. Parsing `local_time + offset + zone` when the offset and the zone disagree is a function with no single correct answer. Rust `jiff` and Temporal both ship all four answers, with the same results and different names. The other two languages cannot express the question.

```text
// One stale input, all four policies, measured in both libraries:
// 2023-07-01T12:00:00-05:00[America/Mexico_City]   (the zone's rules now say -06:00)
// reject          -> error                                           (default in both)
// keep wall clock -> 2023-07-01T12:00:00-06:00[America/Mexico_City]  (instant moves +1 h)
// keep instant    -> 2023-07-01T11:00:00-06:00[America/Mexico_City]  (wall clock moves -1 h)
```

| Policy | Rust `jiff` `OffsetConflict` | TypeScript Temporal `offset` | C++ | F# / .NET |
| --- | --- | --- | --- | --- |
| refuse | `Reject` (default) | `"reject"` (default) | cannot see the zone | cannot read the string |
| offset if still valid, else the wall clock | `PreferOffset` | `"prefer"` | not expressible | not expressible |
| always the offset (keep the instant) | `AlwaysOffset` | `"use"` | the only behaviour, by accident | the only behaviour, after a hand split |
| always the zone (keep the wall clock) | `AlwaysTimeZone` | `"ignore"` | not expressible | not expressible |

Both defaults refuse, and the result is the point. A pure function cannot know whether the meeting was "12:00 in Mexico City" or "17:00 UTC", so the API makes the caller say so. C++ and .NET fall back to keeping the instant, without saying that is what they chose.

Which of your stored future times are wall-clock promises and which are instants, and does the type you store them in know the difference?

# The security angle: a parser that ignores the annotation lets the string carry two answers

Draws on the C++ tip (Mode C: the missing end-of-input check) and the Rust and TypeScript tips (the rejecting control). Here a language does prevent the bug: `jiff` and Temporal refuse a string whose zone contradicts its offset.

**Unread input accepted as parsed (CWE-20, improper input validation; CWE-1286, improper validation of syntactic correctness of input).** The ordinary C++ code:

```cpp
// C++20, illustrative and not compiled (request, reject and schedule stand for your own code).
// Looks like "parse an ISO timestamp, reject garbage". Accepts anything after the offset.
std::istringstream stream(request.header("X-Scheduled-At"));       // "...-05:00[Asia/Tokyo]"
sys_seconds when;
if (!(stream >> parse("%FT%T%Ez", when))) return reject();        // passes: [Asia/Tokyo] is never read
schedule(when);                                                     // and the Tokyo service shows Tokyo wall time
```

Two systems now read one value two ways. The C++ scheduler uses `-05:00`, and a Temporal or `jiff` reader of the same string either rejects it or, with a permissive `offset` option, honours `Asia/Tokyo`. That is a parser-differential bug: whoever writes the string chooses which reader is right.

| Language | What goes wrong | What the library does | Still on you |
| --- | --- | --- | --- |
| C++ | trailing `[...]` accepted unread (measured) | stops at the first unneeded character, by design | check end-of-input; reject what you do not parse |
| F# / .NET | the whole string refused | `FormatException` / `JsonException` | a real suffix parser if you accept RFC 9557 |
| Rust `jiff` | none here: offset/zone mismatch rejected (measured) | `Reject` by default | keep the default at trust boundaries |
| TypeScript Temporal | none here: mismatch rejected (measured) | `offset: "reject"` by default | do not pass `"ignore"` or `"use"` on untrusted input |

Rust `jiff` and Temporal are the control: they read the whole string and refuse a contradiction. C++ shows what it costs to accept the prefix you understand.

Which of your parsers would accept a timestamp with something after it, and which systems downstream read that something?

# Appendix A: Mexico 2022, the rule change that RFC 9557's offset check exists for

_Not part of the tip rotation. Added 2026-10-22, backing this part's thesis. A real event, not folklore: the facts below are quoted from the tzdata source file `northamerica`, its `NEWS` file and Wikipedia (A.4). The `-06:00` offsets in A.2 were printed by Rust `jiff` 0.2.38 and Temporal on Node 26._

**Bug class:** Not a code bug: a rule change, the second one with about a day's notice. Root-cause anti-pattern: storing a future local time as an offset alone, which keeps the instant and loses the meaning the moment the rules move.

## A.1 What happened

Paul Eggert, the tz maintainer, 2022-10-28: "The new Mexican law was published today ... This abolishes DST except where US DST rules are observed, and in addition changes all of Chihuahua to -06 with no DST." A month later the northern border municipalities asked to match their US neighbours again. From the same file (Heitor David Pinto, 2022-11-28): "the president authorized the publication of the decree for November 29, so the time change would occur on November 30 at 0:00." tzdata's `NEWS` records "Release 2022g - 2022-11-29", "The northern edge of Chihuahua changes to US timekeeping", and "A new Zone America/Ciudad_Juarez splits from America/Ojinaga". So the release that knew about the change shipped the day before it took effect, with a zone ID that had not existed the day before.

## A.2 What the stored strings say now

A booking system that stored `2023-07-01T12:00:00-05:00[America/Mexico_City]` in 2021 wrote what was correct then. Under today's rules Mexico City is `-06:00` in July 2023, and both `jiff` and Temporal reject the string by default (the Rust and TypeScript tips). A system that stored only `2023-07-01T12:00:00-05:00` has a valid instant, 17:00Z, which is now 11:00 local. Nothing in the data says the customer meant 12:00.

## A.3 Back to the tips

This is part 4's Turkey story with one difference. In 2016 nothing in a stored timestamp could notice the change. An RFC 9557 string can, because it carries the zone the time was meant in, and the libraries that read it refuse to guess which half to believe.

- tzdata `northamerica`, the Mexico section (the quotes in A.1): https://github.com/eggert/tz/blob/main/northamerica
- tzdata `NEWS`, "Release 2022g": https://github.com/eggert/tz/blob/main/NEWS

# FAQ

**Is the bracket form ISO 8601?** No. RFC 9557, "Date and Time on the Internet: Timestamps with Additional Information" (IETF, Standards Track, April 2024), extends RFC 3339, which is itself a profile of ISO 8601. The part before the bracket is valid ISO 8601. The `[America/Chicago]` suffix is not, because ISO 8601 has no IANA zone names. The RFC's promise runs the other way: "The extension suffix is completely optional, making existing RFC 3339 timestamps compatible with this format." Its syntax follows Java: the RFC cites it "for backwards compatibility with `java.time.ZonedDateTime`".

**Does RFC 9557 change anything for strings without brackets?** Yes, one thing: "It updates RFC 3339 in the specific interpretation of the local offset `Z`". `Z` now means the same as `-00:00`, "the time in UTC is known, but the offset to local time is unknown", while `+00:00` says UTC is the preferred reference. Rust `jiff` and Temporal already write it that way: an instant prints `...Z`, and a value zoned to UTC prints `...+00:00[UTC]`. Rust `chrono`'s `to_rfc3339` and C++'s `%Ez` always write `+00:00`. .NET `DateTime` writes `Z` and `DateTimeOffset` writes `+00:00` (all measured).
