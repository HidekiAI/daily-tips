# Daily Tips: 2026-08-31

## Rust: In-place `collect` inherits the source Vec's capacity, not the result's length

*Perf and memory model*

**Did you know**

`vec.into_iter().map(..).collect::<Vec<U>>()` is specialized to write results back
over the source buffer instead of allocating (rust-lang/rust#70793). The reuse is
real, but so is its accounting: the result keeps the *source* allocation's byte
capacity. Collect a `Vec<[u64; 8]>` into a `Vec<u64>` and you get
`capacity == 8 * len`. Drop 999_990 of a million elements with `filter` and the
survivor `Vec` still owns the original 8 MB. Conditions: consuming iterator
(`Vec`, `Box<[T]>`, `BinaryHeap`), every adapter `InPlaceIterable`, destination
alignment no larger than the source's, neither side a ZST.

**Show me**

```rust
// Verified: rustc 1.95.0, `rustc -O`, aarch64-apple-darwin. All asserts pass.

// Same alignment (8), dest size divides src size -> buffer reused as-is and the
// capacity is scaled by the size ratio, so it tracks bytes, not elements.
let src: Vec<[u64; 8]> = (0..1024u64).map(|i| [i; 8]).collect();
let dst: Vec<u64> = src.into_iter().map(|a| a[0]).collect();
assert_eq!((dst.len(), dst.capacity()), (1024, 8192));   // 8x overshoot, held forever

// The nastier shape: `filter` is InPlaceIterable too, so a 1M source that yields
// 10 survivors hands you a Vec<u64> that still owns the whole 8 MB.
let src: Vec<u64> = (0..1_000_000u64).collect();
let dst: Vec<u64> = src.into_iter().filter(|x| *x < 10).collect();
assert_eq!((dst.len(), dst.capacity()), (10, 1_000_000));

// Alignment mismatch (8 vs 1) disqualifies reuse, so this one allocates fresh.
// This case used to overshoot too; rust-lang/rust#120091 closed it in 1.76.
let src: Vec<u64> = (0..1024u64).collect();
let dst: Vec<u8> = src.into_iter().map(|x| x as u8).collect();
assert_eq!((dst.len(), dst.capacity()), (1024, 1024));

// Borrowing instead of consuming opts out entirely: `.iter()`, not `.into_iter()`.
```

**Why it matters**

A service that builds a filtered index per refresh and keeps it resident is
holding the pre-filter allocation for the life of the index. RSS looks like a
leak and the allocator profile blames `Vec`, correctly: the capacity is genuinely
owned, not fragmentation. `shrink_to_fit()` or `into_boxed_slice()` on anything
you intend to retain costs one memcpy and hands the rest back. Note this is an
optimization, not a documented guarantee, and the std source itself calls it
"fickle" (rust-lang/rust#79308), so do not build a capacity assumption on it in
either direction.

**Chew on this**

Which of your long-lived `Vec`s were built by a consuming `filter` or `flat_map`
chain, and what is their `capacity() / len()` ratio right now? If you added
`shrink_to_fit` everywhere, where would that extra memcpy land on a path that
rebuilds per request?

**Sources**

- https://doc.rust-lang.org/stable/src/alloc/vec/in_place_collect.rs.html
- https://github.com/rust-lang/rust/issues/120091
- https://github.com/rust-lang/rust/pull/70793

## C++: `std::atomic<T>` has a futex built in, and it compares your padding bytes

*Stdlib and ecosystem gems*

**Did you know**

C++20 gave every `std::atomic` and `std::atomic_flag` blocking members:
`wait(old)`, `notify_one()`, `notify_all()`. On Linux they lower to `futex`, on
macOS to `__ulock`, on Windows to `WaitOnAddress`. No mutex, no condition
variable, no Folly, no Boost. The catch is *what* `wait` compares: the value
representation, memcmp-style, not `operator==`. So `-0.0` never satisfies a wait
on `+0.0`, same-payload NaNs always do, and for a struct with padding you are
comparing uninitialized bytes.

Support: `__cpp_lib_atomic_wait >= 201907L`; libstdc++ 11 onward, libc++ 14
onward, MSVC 19.28 (VS 2019 16.8) onward.

**Show me**

```cpp
// C++20. Verified: Apple clang 21 / libc++ 210106, arm64. __cpp_lib_atomic_wait == 201907.
struct Pad { char a; int b; };             // 1 byte, 3 bytes padding, 4 bytes

std::atomic<Pad> x{Pad{1, 2}};
Pad old;
std::memset(&old, 0xAA, sizeof old);       // dirty the padding on purpose
old.a = 1; old.b = 2;                      // now value-equal to what is stored
std::thread t([&]{ x.wait(old); });        // nobody will ever notify
// Returns immediately. 8 runs out of 8. [atomics.types.operations] says padding
// "that never participates in the object's value representation" is ignored;
// libc++ 21 compares all 8 bytes regardless, so the waiter never blocks.

// The shape that actually works: an integral generation counter (an eventcount).
std::atomic<std::uint64_t> gen{0};
// consumer:
std::uint64_t seen = gen.load(std::memory_order_acquire);
while (!work_available()) {
    gen.wait(seen, std::memory_order_acquire);   // may still return spuriously,
    seen = gen.load(std::memory_order_acquire);  // so the predicate loop is mandatory
}
// producer:
gen.fetch_add(1, std::memory_order_release);
gen.notify_one();                                // notify takes no memory order
```

**Why it matters**

An eventcount over a lock-free queue is exactly this primitive, and most
codebases either grow a `mutex` plus `condition_variable` beside a queue that had
no other reason to touch a mutex, or vendor Folly for it. Two `std::atomic`
members replace both. The trap is one failure mode with three personalities:
Rust's `AtomicU64` exposes no `wait` at all, so you reach for `parking_lot` or
raw futex deliberately and the padding question never arises; C++ silently
accepts `std::atomic<Pad>` and turns your waiter into a spin loop with no
diagnostic; JS `Atomics.wait` only ever addresses `Int32Array` or
`BigInt64Array` elements of a `SharedArrayBuffer`, so padding cannot exist to be
compared. Only the middle one lets you write the bug.

**Chew on this**

If your service already has a lock-free queue with a `condition_variable` bolted
on, what is that mutex actually protecting once the queue itself is lock-free?
What would you have to prove about spurious wakeups and lost notifications before
you deleted it?

**Sources**

- https://eel.is/c++draft/atomics.types.operations
- https://developers.redhat.com/articles/2022/12/06/implementing-c20-atomic-waiting-libstdc
- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/p2616r3.html

**Verified**

Compiled and run on Apple clang 21 / libc++ 210106 (arm64 macOS) only. The
padding behavior on libstdc++ and MSVC was not tested, and the library version
support numbers rest on documentation rather than a local build.

## TypeScript: `stableTypeOrdering` exists because the Go compiler checks types in parallel

*New discoveries and currently popular patterns*

**Did you know**

TypeScript 7.0 shipped 8 July 2026 as a native Go binary that parses, checks and
emits in parallel (`--checkers`, `--builders`, `--singleThreaded`). Parallelism
cost it something the old compiler got for free: union constituent order. TS has
always ordered union members by internal type id, which follows declaration
order; a parallel checker cannot promise that, so TS 7 orders types by *content*
and the behavior is mandatory, not a flag. TypeScript 6.0 (23 March 2026) shipped
the same ordering behind `stableTypeOrdering` for exactly one purpose: so you can
diff the two before migrating. It costs up to 25% compile time, which is why it
is off by default.

**Show me**

```ts
// ord.ts -- declaration order is Zebra, then Apple.
interface Zebra { kind: "zebra" }
interface Apple { kind: "apple" }

// Inference builds the union, so the compiler picks the printed order, not you.
export const pick = <T,>(xs: T[]): T[] => xs;
export const mixed = pick([{} as Zebra, {} as Apple]);
```

```
# tsc 6.0.3, declaration emit, identical input, one flag apart:
"stableTypeOrdering": false  ->  export declare const mixed: (Zebra | Apple)[];
"stableTypeOrdering": true   ->  export declare const mixed: (Apple | Zebra)[];
```

**Why it matters**

That diff lands in a published `.d.ts`. If you gate a package on API surface
(api-extractor, `tsd`, a committed `.d.ts`, golden-file error-message tests),
migrating to TS 7 rewrites those files with zero semantic change, and the noise
arrives in the same PR as the real breakage. Flip `stableTypeOrdering` on under
TS 6 and land the churn by itself first. While you are in that tsconfig: TS 6.0
also changed `types` to default to `[]` instead of "every `@types` package in
`node_modules`", so ambient globals from `@types/node` and `@types/jest`
disappear unless you name them or write `"types": ["*"]`.

**Chew on this**

Does anything you ship depend on union order at runtime, a `switch` over a
discriminant derived from `keyof`, a Zod or effect-TS schema built by mapping a
union, a serializer that walks constituents in order? If you cannot answer that
from memory, what would you actually grep for?

- https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/
- https://github.com/microsoft/TypeScript/pull/63054
