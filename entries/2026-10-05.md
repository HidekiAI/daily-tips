# Daily Tips: 2026-10-05

## Rust: In edition 2024 a returned `impl Trait` borrows every argument, and `use<>` can drop a lifetime but never a type parameter

*Type system deep cuts*

**Did you know**

Edition 2024 (Rust 1.85) changed what a return-position `impl Trait` captures. In 2021, a free function's opaque type captured its type parameters but not its lifetimes, so `fn even_indices(prices: &[u64]) -> impl Iterator<Item = usize>` returned something that did not borrow `prices`. In 2024 it captures every lifetime in scope, so the same signature now holds the borrow for as long as the iterator lives, even when the body never touches `prices` again. The way out is precise capturing, `+ use<>` (stable since 1.82). It is lopsided on purpose: you may leave lifetimes out of `use<..>`, but rustc 1.95 still rejects a list that leaves out a type parameter.

**Show me**

```rust
// rustc 1.95.0. Same file, two editions. Output and errors are from those runs.

// Returns indices only. The iterator reads prices.len() once and keeps nothing.
fn even_indices(prices: &[u64]) -> impl Iterator<Item = usize> {
    (0..prices.len()).step_by(2)
}

// The 2024 fix: an empty capture list says "borrows nothing".
fn even_indices_owned(prices: &[u64]) -> impl Iterator<Item = usize> + use<> {
    (0..prices.len()).step_by(2)
}

fn main() {
    let mut prices: Vec<u64> = vec![10, 20, 30, 40];
    for position in even_indices(&prices) {
        // --edition 2021: compiles, prints [11, 20, 31, 40]
        // --edition 2024: error[E0502]: cannot borrow `prices` as mutable
        //   note: this call may capture more lifetimes than intended, because
        //   Rust 2024 has adjusted the `impl Trait` lifetime capture rules
        prices[position] += 1;
    }
    for position in even_indices_owned(&prices) {
        prices[position] += 1; // compiles in 2024
    }
    println!("{prices:?}");
}

// Not allowed, even in 2024:
// fn lengths<T: AsRef<str>>(names: &[T]) -> impl Iterator<Item = usize> + use<> { .. }
// error: `impl Trait` must mention all type parameters in scope in `use<...>`
```

**Why it matters**

The error shows up in the caller, but the change that caused it is in the callee's signature. Edition is per crate, so a library that bumps its own edition by hand, without `cargo fix --edition` (whose `impl_trait_overcaptures` lint inserts `use<..>` for you), has quietly widened its public API. Downstream code that held such an iterator while mutating the source stops compiling, and nobody touched that code. C++ has nothing like it: a returned range adaptor holds whatever it holds, and if it outlives the vector it dangles, with no diagnostic in either direction. TypeScript's inferred return types have no lifetimes to capture at all.

**Chew on this**

Which of your public `-> impl Iterator` functions really need to borrow their arguments, and which only borrow now because the edition changed? Also, since `use<T>` is mandatory, what happens to your "borrows nothing" promise when a caller passes `T = &'a str`?

## C++: C++26 added `span`'s `initializer_list` constructor, made `span{ptrs, 0}.size()` equal 2, and was taken back out in April 2026

*New discoveries and currently popular patterns*

**Did you know**

P2447R6, adopted for C++26 in March 2024, gave `std::span<const T>` a constructor from `initializer_list<value_type>`. Braced initialization prefers an `initializer_list` constructor, so `span<void* const>{slots, 0}` stopped meaning "pointer plus count". It became a two-element list `{slots, nullptr}`, and `size()` went from 0 to 2 without a diagnostic. With `bool` the same rule turns `span<const bool>{ptr, count}` into a narrowing error. P4144R1 removed the constructor and its feature macro `__cpp_lib_span_initializer_list` (LEWG poll 16/14/2/0/0 on 2026-03-25; merged into the C++26 working draft in early April 2026). Support state: libc++ shipped the constructor (Apple clang 21 has it) and libc++ 23 (LLVM 23, Homebrew clang 23.1.1) has removed it. libstdc++ added it in December 2024, so GCC 15 has it. I could not confirm whether GCC 16 or MSVC have removed it.

**Show me**

```cpp
// Same file, -std=c++26, two standard libraries. Output is from those runs.
//   Apple clang 21 (libc++ 21):        macro=202311 size=2
//   Homebrew clang 23.1.1 (libc++ 23): macro=0      size=0
// Under -std=c++23 both print size=0.
#include <cstdio>
#include <span>
#include <version>

int main() {
    void* slots[10] = {};
    // Intended: an empty view of slots. Under P2447 this is the
    // two-element initializer_list {slots, nullptr}: 0 converts to void*.
    std::span<void* const> handles{slots, 0};
#ifdef __cpp_lib_span_initializer_list
    long macro = __cpp_lib_span_initializer_list;
#else
    long macro = 0;
#endif
    std::printf("macro=%ld size=%zu\n", macro, handles.size());

    // Same rule, loud version. With libc++ 21 and -std=c++26 this fails:
    //   error: type 'bool *' cannot be narrowed to 'value_type' (aka 'bool')
    // bool flags[4] = {}; bool* first = flags; std::size_t count = 4;
    // std::span<const bool> flag_view{first, count};
}
```

**Why it matters**

The loud case, `bool`, is what made the committee act. The quiet case is the dangerous one: any element type that converts from both a pointer and an integer (`void*`, `const void*`, `std::any`, a type with a converting constructor) silently gets a different span with the same source text. Parentheses, `span<void* const>(slots, 0)`, never had this problem, because `initializer_list` constructors only win with braces. Rust has no braced-init overload set, so `&slots[..0]` and `vec![slots_ptr, null]` cannot be mistaken for each other. TypeScript has no counted view at all: `slots.slice(0, 0)` is an empty copy, not a view.

**Chew on this**

You have a toolchain shipping a C++26 rule that the C++26 standard no longer has. How would your build notice that `-std=c++26` means different things on two machines? And how many of your braced `span{pointer, count}` calls are written with braces only because a style guide says "prefer braces"?

## F#: `Array.sortBy` is not stable and `List.sortBy` is, and your tests won't notice below 17 elements

*Stdlib and ecosystem gems*

**Did you know**

FSharp.Core documents every `Array.sort*` function as "not a stable sort", and every `List.sort*` and `Seq.sort*` function as stable. `Array.sortBy` computes each key once and then calls .NET's `Array.Sort(keys, items)`, and `Array.sortWith` also calls `Array.Sort`. `Array.Sort` is an introsort. Introsort uses insertion sort for 16 elements or fewer, and insertion sort happens to be stable. So an `Array.sortBy` on a 16-element fixture keeps equal keys in their original order, and the same code at 17 elements does not. Measured on FSharp.Core 8 (SDK 8.0.401, .NET 8.0.8).

**Show me**

```fsharp
// dotnet fsi, FSharp.Core 8, .NET 8.0.8. Output is from that run.
// Orders arrive in sequence. Sort by priority, expecting arrival order kept within a priority.
let orders count = Array.init count (fun arrival -> (arrival % 3, arrival))

let keptArrivalOrder (sorted: (int * int) array) =
    sorted
    |> Array.pairwise
    |> Array.forall (fun ((prio_a, seq_a), (prio_b, seq_b)) -> prio_a <> prio_b || seq_a < seq_b)

let check label (sorted: (int * int) array) =
    printfn "%-18s stable=%b %A" label (keptArrivalOrder sorted) (Array.truncate 4 sorted)

check "Array.sortBy 16"   (orders 16   |> Array.sortBy fst)  // stable=true   <- the unit test
check "Array.sortBy 17"   (orders 17   |> Array.sortBy fst)  // stable=false  (0,0); (0,12); (0,3)
check "Array.sortBy 1000" (orders 1000 |> Array.sortBy fst)  // stable=false  (0,0); (0,525); (0,522)
check "Array.sortWith"    (orders 1000 |> Array.sortWith (fun (left, _) (right, _) -> compare left right)) // false
check "List.sortBy"       (orders 1000 |> List.ofArray |> List.sortBy fst |> Array.ofList)  // true
check "Seq.sortBy"        (orders 1000 |> Seq.sortBy fst |> Array.ofSeq)                    // true

// Stable and still an array: make the tie-breaker explicit.
let stableByPriority (items: (int * int) array) =
    items |> Array.indexed |> Array.sortBy (fun (index, (prio, _)) -> (prio, index)) |> Array.map snd
check "indexed sortBy"    (orders 1000 |> stableByPriority)  // true
```

**Why it matters**

The bug arrives through a performance refactor: "switch this `List` to an array for speed" swaps `List.sortBy` for `Array.sortBy`, the signatures match, and the 10-row test fixture still passes. In production, a second sort that relied on the first ("sort by time, then by priority") reorders records with equal priority, so a paging cursor or a "first matching rule wins" pass changes its answer from run to run. Rust and Go put the word in the name (`sort_by_key` against `sort_unstable_by_key`; `sort.SliceStable` against `sort.Slice`). C++ does the same (`stable_sort` against `sort`). F# keeps one name and lets the module decide.

**Chew on this**

Where in your code does a sort's correctness depend on an earlier sort, without saying so? If you found one, would you rather make it stable, or make the key total so stability stops mattering?

**Sources**

- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/xmldoc/sort.xml
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-arraymodule.html
- https://learn.microsoft.com/en-us/dotnet/api/system.array.sort

**Verified**

The 16-element cut-off is measured, and matches .NET's introsort threshold. FSharp.Core and .NET treat it as an implementation detail, not a documented guarantee.

**Related**

- [2026-09-18](2026-09-18.md) - Rust, "sort_by_key calls the key function once per comparison". `List.sortBy` was the baseline row there for key caching. Today it is the baseline for stability.

## TypeScript: `try/catch` gives you `unknown`, but `.catch(err => ...)` still gives you `any` under `strict`

*Idioms and antipatterns*

**Did you know**

`strict` turns on `useUnknownInCatchVariables` (TypeScript 4.4), so the binding in `catch (failure)` has type `unknown`. That flag only covers the `catch` clause. The callback form is typed by `lib.es5.d.ts`, which still declares `catch(onrejected?: (reason: any) => ...)`, and `then`'s second argument the same way. `Promise.allSettled`'s `PromiseRejectedResult.reason` is `any` too. Because the parameter is typed by context, `noImplicitAny` stays quiet. The same failure handled two ways gets two different types, and the version that looks more functional is the one with no type checking. Checked on tsc 6.0.3, `strict: true`.

**Show me**

```typescript
// tsc 6.0.3 --strict, Node 22.17.1. Output is from that run.
async function fetchQuote(): Promise<number> {
    throw "upstream timeout"; // a string, not an Error
}

async function viaTryCatch(): Promise<string> {
    try {
        return String(await fetchQuote());
    } catch (failure) {
        // failure: unknown. `failure.message` here is TS18046.
        return failure instanceof Error ? failure.message : String(failure);
    }
}

function viaCatchCallback(): Promise<string> {
    return fetchQuote()
        .then(String)
        // failure: any. No annotation, no diagnostic.
        .catch((failure) => failure.message.toUpperCase());
}

const settled = await Promise.allSettled([fetchQuote()]);
for (const outcome of settled) {
    if (outcome.status === "rejected") {
        const code: number = outcome.reason.code; // compiles; code is undefined
    }
}

console.log(await viaTryCatch());       // upstream timeout
console.log(await viaCatchCallback().catch(String));
// TypeError: Cannot read properties of undefined (reading 'toUpperCase')
```

**Why it matters**

A `.catch` handler that throws turns the error into a new, different rejection. Your log then shows a `TypeError` from the error handler, not the upstream timeout, and the actual cause is gone. Annotating `(failure: unknown) =>` fixes the type, because a parameter typed `unknown` is accepted where `any` is expected. typescript-eslint's `use-unknown-in-catch-callback-variable` rule enforces that. Effect 4.0.1's `Effect.tryPromise` puts the rejection in `UnknownError` with `cause: unknown`, so it has no `any` path at all. Rust's `Result<T, E>` names `E`. C++ `catch (...)` gives you nothing to read, and `std::current_exception` gives you an `exception_ptr` you have to rethrow to inspect.

**Chew on this**

How many `.catch` handlers in your services read a property off the rejection reason? Which of them would throw if a dependency rejected with a string?

# The functional angle: a stable sort is free in every language here, as long as you picked the right name, and F# hands it to you by module

Draws on the F# tip, with Rust, C++, TypeScript and Go measured on the same data: 1000 `(priority, arrival)` pairs, `priority = arrival % 3`, sorted by priority only.

A functional pipeline treats a sort as a pure function from a list to a list, and assumes the result is fully determined by the input. With equal keys, that holds only if the sort is stable. Otherwise the output depends on the algorithm, and here on whether the input has more than 16 elements. So stability is what makes `sortBy` the pure function a pipeline expects.

```rust
// Rust: the name carries the guarantee.
orders.sort_by_key(|order| order.0);          // stable  (driftsort)
orders.sort_unstable_by_key(|order| order.0); // unstable (ipnsort), measured stable=false
```

```cpp
// C++20 ranges: same split as Rust, but the unstable one has the short name.
std::ranges::sort(orders, {}, &Order::first);        // measured stable=0
std::ranges::stable_sort(orders, {}, &Order::first); // stable=1, may allocate a buffer
```

```typescript
// TypeScript: one function, required to be stable since ES2019.
const sorted = [...orders].sort((left, right) => left[0] - right[0]); // stable=true
```

| Language | Functional form | Stable at n=1000? | What it costs |
| --- | --- | --- | --- |
| F# | `List.sortBy` / `Seq.sortBy` | yes | a full copy, plus list nodes; `Array.sortBy` is the cheap one and is not stable |
| Rust | `sort_by_key` | yes | `&mut` in place, plus a scratch allocation; you have to opt in to unstable |
| C++ | `ranges::stable_sort` | yes (`ranges::sort`: no) | a temporary buffer, falling back to O(n log^2 n) if allocation fails |
| TypeScript | `Array.prototype.sort` | yes | mutates in place, so the pure form needs `[...orders]` or `toSorted` (ES2023) |
| Go | `sort.SliceStable` | yes (`sort.Slice`: no) | an index-based `less` closure that captures the slice it sorts |

The difference is in what the short name gets you. In Rust and TypeScript the short name is stable. In C++ and Go the short name is unstable, and stable costs one more word. F# is the only one where the same short name, `sortBy`, means both, and the collection module picks. It is also the only language here where the unstable choice is the one the performance refactor reaches for.

Left open: if a pure pipeline wants determinism, should it ask for stability, or for a total key like `(priority, arrival)` that makes the question disappear? Which one survives a teammate changing the key?

# The security angle: the C++26 `span{ptrs, 0}` is not just the wrong size, it is a dangling view, and `-Wall -Wextra` says nothing

Draws on the C++ tip (Mode B, asking "is this secure?" of what the tip taught), plus the TypeScript tip (Mode C, the missing check). Both run in the "the language lets it through" direction.

**The span.** The `initializer_list` constructor does not only change `size()`. The list `{slots, nullptr}` is a temporary whose backing array dies at the end of the full expression. `handles` was meant to point into `slots`. It points at that dead array instead.

```cpp
// Apple clang 21, -std=c++26 -Wall -Wextra: no warnings.
// With -fsanitize=address:
//   size=2 points_into_slots=0
//   ERROR: AddressSanitizer: stack-use-after-scope ... dangle.cpp:7
void* slots[10] = {};
std::span<void* const> handles{slots, 0};   // looks like an empty view of slots
for (void* const handle : handles) use(handle); // reads 2 pointers from a dead temporary
```

Code that looked like it read nothing now reads two pointer-sized values from stack memory that is no longer in scope. Whatever the compiler has since stored there is now treated as a handle. The fix is not a check, it is a different spelling: `std::span<void* const>(slots, 0)`, or `std::span(slots).first(0)`.

**The catch callback.** A `.catch((failure) => failure.message)` handler has no type checking on the rejection, so the usual failure is a crash inside the handler. The worse one is what the handler sends back:

```typescript
// Compiles under strict. failure: any.
app.get("/quote", (request, response) =>
    loadQuote(request.query.id).catch((failure) =>
        response.status(500).json({ error: failure.message, detail: failure.response?.data })));
// Illustrative, not run. If a dependency rejects with an HTTP-client error that
// carries the upstream response, `detail` sends that upstream body to the caller.
```

With `(failure: unknown)`, every one of those property reads is a compile error until you narrow it, and narrowing is where you decide what may leave the process.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ (libc++ 21, `-std=c++26`) | braced `span{ptr, n}` binds to a temporary list (CWE-416, CWE-125) | nothing at `-Wall -Wextra`; ASan catches it at runtime | parentheses for pointer+count spans; ASan in CI on every `-std` you ship |
| Rust | the same intent, `&slots[..0]` | cannot dangle; a slice borrows `slots` | nothing, this one is handled |
| TypeScript | `any` reason reaches a response body (CWE-209) | erases types; `strict` does not cover the callback | `(failure: unknown)` plus the lint rule; an allowlist of fields that leave |
| F# / C# | exception message sent to a client | `exn` is typed, but `.Message` and `.Data` are still free text | same allowlist; typed exceptions don't make the message safe to send |

The baseline for the span row is Rust, since the failure is memory safety. The baseline for the catch row is F#, since there the value is typed and the problem is purely what you choose to send.

Left open: which of your error handlers serialize a caught value directly into a response? Would your CI catch a dangling span that only exists under one `-std` flag on one standard library?

# FAQ

**Does the Rust 2024 capture change affect trait methods?** No. Return-position `impl Trait` in trait methods (stable since 1.75) has always captured every lifetime in scope, in every edition. 2024 brought free functions and inherent methods in line with that.

**Does `cargo fix --edition` change behavior?** No. It adds `use<..>` lists that keep the 2021 capture set, so the API stays as it was. Hand-editing `edition = "2024"` is what widens it.

**Is `std::span<const int> view = {1, 2, 3};` gone too?** Yes, on a library that implements P4144. That was the use P2447 was added for, mainly as a function argument: `process({1, 2, 3})`.

**Is F#'s `Array.sortInPlace` stable?** No. It is documented as "not a stable sort", and it has the same introsort cut-off.

**Does `Array.prototype.toSorted` keep stability?** Yes. ES2023 specifies it with the same algorithm requirements as `sort`, so it is stable, and it returns a copy.
