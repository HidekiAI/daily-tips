This part: the first day of the week, and the numbers each library gives to weekdays and weeks. Part 1 covered the ISO week-year; this part is about the locale._

**The thesis: "Sunday" has at least four numbers and "week 1" has at least three definitions, and the locale picks one of each.** ISO 8601 says weeks start on Monday and Sunday is 7. C, JS `Date` and .NET say Sunday is 0. The US starts its weeks on Sunday, most of Europe on Monday, and much of the Middle East on Saturday. A date on New Year's Day can be week 0, 1, 53 or 41 depending on who is asked.

| Friday 2027-01-01 | Week number | First day of the week |
| --- | --- | --- |
| ISO 8601 (`%V`, .NET `ISOWeek`, Temporal `weekOfYear`) | **53** of 2026 | Monday |
| `%U` (Sunday-first, C, C++ and Rust `jiff` `strftime`) | **00** | Sunday |
| `%W` (Monday-first) | **00** | Monday |
| .NET `en-US` (`FirstDay`, Sunday) | **1** | Sunday |
| .NET `en-GB`, `de-DE` (`FirstFourDayWeek`, Monday) | **53** | Monday |
| .NET `ar-EG` | **1** | Saturday |
| .NET `fa-IR` (`PersianCalendar`) | **41** | Saturday |

All values measured on 2026-10-22.

## Rust: `jiff` gives Sunday four numbers, 0, 1, 6 and 7, and only some wrong conversions are caught

*Type system deep cuts*

**Did you know**

Rust `jiff` (0.2.38) makes the weekday numbering explicit by naming every convention: `to_sunday_zero_offset` (0, as in C, JS `Date.getDay` and .NET `DayOfWeek`), `to_sunday_one_offset` (1), `to_monday_zero_offset` (6) and `to_monday_one_offset` (7, ISO 8601 and Temporal). Converting back with the wrong one is caught only if the number is out of range. `from_sunday_zero_offset(7)` is an error ("not in the required range of 0..=6"), while `from_sunday_zero_offset(1)` returns Monday, even when the 1 came from a Sunday-is-1 source. `strftime` offers three week numbers: `%U`, `%W` and `%V` give `00`, `00` and `53` for 2027-01-01.

**Show me**

```rust
// Rust: jiff 0.2.38 and chrono 0.4.45, rustc 1.95.0
use jiff::civil::{date, Weekday};

fn main() {
    // One Sunday, four numbers, all from jiff:
    let sunday = Weekday::Sunday;
    println!("{} {} {} {}",
        sunday.to_sunday_zero_offset(),  // 0  (C, JS Date.getDay, .NET DayOfWeek)
        sunday.to_sunday_one_offset(),   // 1
        sunday.to_monday_zero_offset(),  // 6
        sunday.to_monday_one_offset());  // 7  (ISO 8601, Temporal dayOfWeek)
    // ...and chrono has its own names for two of them:
    println!("{} {}", chrono::Weekday::Sun.num_days_from_sunday(), chrono::Weekday::Sun.number_from_monday()); // 0 7

    // Converting back with the wrong convention is caught, in one direction only:
    println!("{:?}", Weekday::from_monday_one_offset(7).map(|day| format!("{day:?}"))); // Ok("Sunday")
    println!("{}", Weekday::from_sunday_zero_offset(7).is_err());                      // true: 0..=6 only
    println!("{:?}", Weekday::from_sunday_zero_offset(1).map(|day| format!("{day:?}"))); // Ok("Monday"), when 1 meant Sunday

    // Week numbers: %U (Sunday-first), %W (Monday-first) and %V (ISO) for the same Friday.
    let new_year = date(2027, 1, 1);
    println!("{} {} {} {}", new_year.strftime("%U"), new_year.strftime("%W"), new_year.strftime("%V"), new_year.strftime("%G"));
    // 00 00 53 2026: two schemes say week 0 of 2027, ISO says week 53 of 2026
}
```

**Why it matters**

Weekday numbers cross every boundary as plain integers: a cron field (Sunday is 0 and 7), a SQL `EXTRACT(DOW)` (0) or `ISODOW` (7), a JS `getDay()` (0), an ISO week date (7). An off-by-one between conventions shifts every weekly job by a day, and only the out-of-range direction fails loudly. `jiff` and Rust `chrono` (`num_days_from_sunday` 0, `number_from_monday` 7) at least make you type the convention. C++ accepts both 0 and 7 as Sunday (C++ tip). JS and .NET give you a bare 0.

**Chew on this**

Which integer weekdays enter your services, and from which convention? Where one convention is converted to another, would a test with a Sunday catch an error?

**Sources**

- https://docs.rs/jiff/0.2.38/jiff/civil/enum.Weekday.html
- https://docs.rs/jiff/0.2.38/jiff/fmt/strtime/index.html (the `%U`, `%W`, `%V` and `%G` directives)

**Gotchas**

- `date(2027, 1, 1).iso_week_date()` is 2026-W53 Friday (measured): the ISO week-year differs from the calendar year at both ends of most years (part 1).
- Rust `chrono`'s `Weekday::Sun.num_days_from_monday()` is 6 and `number_from_monday()` is 7 (measured): one counts from 0, the other from 1, in the same direction.
- Rust and its crates evolve: these method names are `jiff` 0.2.38's. Neither crate has locale week data; that needs ICU4X.

## C++: `weekday{7}` and `weekday{0}` are both Sunday, and weekday subtraction is "days since", always 0 to 6

*Type system deep cuts*

**Did you know**

C++20's `weekday` takes both conventions: `weekday{0} == Sunday` and `weekday{7} == Sunday` are both true, `c_encoding()` gives 0 and `iso_encoding()` gives 7. Subtracting weekdays is modular, so the result is "days since" and never negative: `Sunday - Monday` is 6 days and `Monday - Sunday` is 1. So "days back to the start of this week" is `today - Sunday` in the US and `today - Monday` in Germany: for Friday, 5 and 4. `std::format` gives three week numbers, `%U`, `%W` and `%V`: `00`, `00` and `53` for 2027-01-01 (`%G` 2026). C++ has no locale "first day of week" at all. Measured on Apple clang 21 (libc++) and GCC 16.2 (libstdc++).

**Show me**

```cpp
// C++20: Apple clang 21 (libc++ 22) and GCC 16.2 (libstdc++)
#include <chrono>
#include <cstdio>
#include <format>
using namespace std::chrono;

int main() {
    // weekday accepts both conventions: 0 and 7 are both Sunday.
    std::printf("%d %d\n", (int)(weekday{0} == Sunday), (int)(weekday{7} == Sunday));   // 1 1
    std::printf("%u %u\n", Sunday.c_encoding(), Sunday.iso_encoding());                  // 0 7

    // Weekday subtraction is modular: "days since", always 0 to 6.
    std::printf("%d %d\n", (int)(Sunday - Monday).count(), (int)(Monday - Sunday).count()); // 6 1
    // So "how many days until the start of the week" depends on which day you call the start:
    const weekday friday{sys_days{2027y/January/1}};
    std::printf("%d %d\n", (int)(friday - Sunday).count(), (int)(friday - Monday).count()); // 5 4

    // Three week numbers for the same Friday:
    const sys_days new_year = 2027y/January/1;
    std::printf("%s\n", std::format("{:%U} {:%W} {:%V} {:%G}", new_year, new_year, new_year, new_year).c_str());
    // 00 00 53 2026: Sunday-first and Monday-first call it week 0 of 2027; ISO calls it week 53 of 2026
}
```

**Why it matters**

The modular subtraction is the right primitive for "start of the week", and it puts the locale decision in one visible place: which weekday you subtract. Accepting both 0 and 7 as Sunday removes one off-by-one, and hides it in data. A value that round-trips through `c_encoding()` comes back as 0 even if it went in as 7. .NET and JS carry the locale's first day as data (F# and TypeScript tips). C++ and Rust make the caller supply it.

**Chew on this**

In your C++ code, which weekday does "start of week" subtract, and is that the right one for every market you serve? Where do weekday integers leave your process, and in which encoding?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/weekday
- https://en.cppreference.com/w/cpp/chrono/weekday/operator_arith
- https://en.cppreference.com/w/cpp/chrono/system_clock/formatter (the `%U`, `%W`, `%V` and `%G` specifiers)

**Verified**

Apple clang 21 on this host and `docker run gcc:16`, with identical output. MSVC not tested.

**Gotchas**

- `weekday{8}` is not `ok()`, but `weekday{7}` is (it is Sunday). Validity is 0 to 7, not 0 to 6.
- `%U` and `%W` number the days before the first Sunday or Monday of the year as week `00` (measured for 2027-01-01). That is a week 0, which neither ISO nor .NET has.
- 2026-12-31 is `%U` 52, `%W` 52 and `%V` 53 (measured): the three agree on nothing at the turn of the year.

## F#: 2027-01-01 is week 1 in `en-US`, week 53 in `en-GB` and week 41 in `fa-IR`, and a container's culture is invariant

*Stdlib and ecosystem gems*

**Did you know**

.NET's `Calendar.GetWeekOfYear` takes a `CalendarWeekRule` and a first day, and each culture supplies its own. `en-US` is `FirstDay` plus Sunday, so Friday 2027-01-01 is week 1. `en-GB` and `de-DE` are `FirstFourDayWeek` plus Monday, so it is week 53. `ar-EG` starts on Saturday (week 1). `fa-IR`'s culture calendar is `PersianCalendar`, so the same date is week **41** of a Persian year. `ISOWeek` says 2026-W53. In the .NET 10 Linux container the current culture was the invariant one (Sunday, `FirstDay`). Measured on .NET 8.0.8 (macOS) and .NET 10.0.13 (Linux).

**Show me**

```fsharp
// F#: FSharp.Core 8.0 / .NET 8.0.8 (macOS) and FSharp.Core 10.1 / .NET 10.0.13 (Linux, Docker)
open System
open System.Globalization

let new_year = DateTime(2027, 1, 1)   // a Friday

let fn_culture_week (tag: string) =
    let culture = CultureInfo tag
    let format = culture.DateTimeFormat
    format.FirstDayOfWeek, culture.Calendar.GetWeekOfYear(new_year, format.CalendarWeekRule, format.FirstDayOfWeek)

for tag in [ "en-US"; "en-GB"; "ar-EG"; "fa-IR" ] do
    let first_day, week = fn_culture_week tag
    printfn "%-6s first day %-9O week %d" tag first_day week
// en-US  first day Sunday    week 1
// en-GB  first day Monday    week 53
// ar-EG  first day Saturday  week 1
// fa-IR  first day Saturday  week 41   <- the culture's calendar is PersianCalendar

printfn "ISO: %d-W%d" (ISOWeek.GetYear new_year) (ISOWeek.GetWeekOfYear new_year) // ISO: 2026-W53

// The server's answer depends on its culture, and a container's culture is often invariant (Sunday, FirstDay):
printfn "%s / %O" (if CultureInfo.CurrentCulture.Name = "" then "(invariant)" else CultureInfo.CurrentCulture.Name) CultureInfo.CurrentCulture.DateTimeFormat.FirstDayOfWeek
```

**Why it matters**

"Week 53" on a German report and "week 1" on an American one are the same week. A dashboard that groups by `GetWeekOfYear` with `CurrentCulture` changes its grouping when the server's culture changes, and containers default to the invariant culture. Use `ISOWeek` for anything stored or compared, and a culture only for display. Rust `jiff` and C++ have no culture data, so they cannot do this by accident. JS has the data, behind an API that changed between Node versions (TypeScript tip).

**Chew on this**

Which of your reports group by week, and which culture's rule do they use on the server that runs them? Would a user in Tehran see their week numbers in the Persian calendar, and should they?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.globalization.calendar.getweekofyear
- https://learn.microsoft.com/en-us/dotnet/api/system.globalization.isoweek
- https://learn.microsoft.com/en-us/dotnet/api/system.globalization.calendarweekrule

**Gotchas**

- `int DayOfWeek.Sunday` is 0 and `Monday` is 1 (measured): the enum is Sunday-first whatever the culture's `FirstDayOfWeek` says.
- `CultureInfo.InvariantCulture` is Sunday and `FirstDay` (measured), which matches `en-US` and not ISO 8601.
- The macOS host's current culture was `en-US` and the container's was invariant (measured), so the same code printed different "current" cultures on the two hosts.

## TypeScript: Node 22's `locale.weekInfo` became Node 26's `locale.getWeekInfo()`, and `minimalDays` disappeared on the way

*Stdlib and ecosystem gems*

**Did you know**

`Intl.Locale` exposes the locale's week data: `firstDay` (ISO numbered, so Sunday is 7) and `weekend`. On Node 22.17.1 it is a getter, `locale.weekInfo`, and it also has `minimalDays`. On Node 26.12.1 it is a method, `locale.getWeekInfo()`. `weekInfo` is `undefined` there, and the result has no `minimalDays`. So `new Intl.Locale("en-US").weekInfo.firstDay` works on Node 22 and throws a `TypeError` on Node 26. The numbering also differs from `Date`: `firstDay` 7 is Sunday, while `Date.getDay()` gives Sunday as 0. `ar-EG` starts on Saturday (`firstDay` 6). Measured on both versions.

**Show me**

```ts
// TypeScript 6.0.3 types, run on Node 22.17.1 and Node 26.12.1
const us = new Intl.Locale("en-US")

// The same question, asked the Node 22 way and the Node 26 way:
const fn_week_info = (locale: Intl.Locale): unknown => {
    const shapes = locale as unknown as { weekInfo?: unknown; getWeekInfo?: () => unknown }
    if (typeof shapes.getWeekInfo === "function") return shapes.getWeekInfo()  // Node 26: a method
    return shapes.weekInfo                                                     // Node 22: a getter
}
console.log(JSON.stringify(fn_week_info(us)))
// Node 22: {"firstDay":7,"weekend":[6,7],"minimalDays":1}
// Node 26: {"firstDay":7,"weekend":[6,7]}            <- minimalDays is gone
console.log(typeof (us as unknown as { weekInfo?: unknown }).weekInfo)
// Node 22: object   Node 26: undefined, so `us.weekInfo.firstDay` throws a TypeError on Node 26

// firstDay is ISO-numbered (Sunday is 7), and Date.getDay() is not (Sunday is 0):
console.log(new Date(Date.UTC(2026, 9, 25)).getUTCDay()) // 0: the Sunday 2026-10-25
console.log(JSON.stringify(fn_week_info(new Intl.Locale("ar-EG")))) // firstDay 6: Saturday
```

**Why it matters**

Calendar UIs read `firstDay` to decide which column comes first, and the upgrade from Node 22 to 26 (or an older browser to a newer one) breaks code written against the getter. The two numberings in one standard library are the other trap: using `firstDay` (1 to 7) as an index into an array built from `getDay()` (0 to 6) shifts the week by one, except for Monday-first locales, where 1 happens to match. .NET exposes the same locale data as a stable enum (F# tip), and C++ and Rust have none.

**Chew on this**

Which of your front-end or server code reads `weekInfo`, and does it run on both Node versions? Where `firstDay` meets `getDay()`, which numbering does the array index use?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Locale/getWeekInfo
- https://github.com/tc39/proposal-intl-locale-info

**Verified**

`console` typed with a one-line `declare`. The `weekInfo` and `getWeekInfo` shapes are cast through `unknown`, because TypeScript 6.0.3's `es2022.intl` lib declares neither, and `lib: esnext` declares `getWeekInfo()` but not `weekInfo` (both checked with `tsc`). Run on Node 22.17.1 and in `docker run node:26`.

**Gotchas**

- `minimalDays` (the ISO-style "how many days make week 1") is `1` for `en-US` and `4` for `en-GB` on Node 22, and absent on Node 26 (measured). Code that computed week numbers from it has nothing to read after the upgrade.
- Temporal's `dayOfWeek` is ISO numbered (Sunday is 7), and `weekOfYear` for 2027-01-01 is 53 with `yearOfWeek` 2026 (measured on Node 26), so Temporal agrees with `firstDay`'s numbering and not with `Date`'s.
- `fa-IR` reports `weekend: [5]`, a one-day weekend (measured), so code that assumes two weekend days breaks there too.

# The functional angle: "start of the week" is `date - (weekday - first_day) mod 7`, and the locale supplies one argument

Draws on all four tips. Every "start of week" in every language is the same pure function. Only `first_day` and the weekday encoding change, and both are inputs that look like constants:

```text
// start_of_week(date, first_day) = date - ((weekday(date) - first_day) mod 7) days
// Friday 2027-01-01, measured weekday arithmetic:
//   first_day = Sunday   -> 5 days back -> 2026-12-27
//   first_day = Monday   -> 4 days back -> 2026-12-28
//   first_day = Saturday -> 6 days back -> 2026-12-26
// C++ writes (date_weekday - first_day) directly, since weekday subtraction is already mod 7.
```

| Language | `weekday(date)` encoding | `first_day` source | `mod 7` | What it costs |
| --- | --- | --- | --- | --- |
| Rust (`jiff`) | named per convention | you supply it | `to_*_offset` arithmetic | no locale data; explicit everywhere |
| C++ | `c_encoding` 0 / `iso_encoding` 7 | you supply it | built into `weekday - weekday` | no locale data; the subtraction is free |
| F# / .NET | `DayOfWeek` 0 to 6 | `CultureInfo.DateTimeFormat.FirstDayOfWeek` | `(7 + int day - int first) % 7` by hand | the culture is implicit unless you pass one |
| TypeScript | `getDay()` 0 to 6, Temporal 1 to 7 | `getWeekInfo().firstDay` (1 to 7) | by hand, across two numberings | the data's shape changed between Node versions |

The function needs no `mut`. The asymmetry: the two languages without locale data make `first_day` a visible argument, and the two with it hide the argument in ambient state, the current culture or the default locale.

Where does your "start of week" get its `first_day`, and would you see it change?

# The security angle: a weekly limit keyed on a locale's week resets on different days for different users

Draws on the F# tip (Mode B: the week number is fine for display, but is it fine as a key?). The language prevents nothing here. Part 1's security angle made the same point for "once per day".

**A reset boundary the user can choose (CWE-840, business logic errors; closest class).** A "3 free exports per week" counter keyed on `(user, GetWeekOfYear(date, culture rule))` resets on Sunday for `en-US` users, Monday for `en-GB` users and Saturday for `ar-EG` users. If the culture comes from the request (`Accept-Language`), a user who switches it at the right moment starts a new week a day early:

```fsharp
// F#, illustrative (request and the quota store stand for your own code).
// Looks like "a weekly quota". The week's boundary is whatever culture the request claims.
let week_key = CultureInfo(request.Headers.AcceptLanguage).Calendar.GetWeekOfYear(today, rule, first_day)
```

| Language | What goes wrong | What the library does | Still on you |
| --- | --- | --- | --- |
| F# / .NET | culture-dependent week numbers (1 / 53 / 41, measured) | uses the culture you pass or the current one | key quotas by `ISOWeek` or a rolling 7-day window |
| TypeScript | `firstDay` from the request's locale | gives the locale's data | never take the boundary from the client |
| Rust (`jiff`) | none by default: no locale data | ISO week dates | keep it that way for keys |
| C++ | none by default: no locale data | `%V` ISO weeks | same |

Rust and C++ are the control: without locale data, the only week they compute by default is ISO's, which is the same for everyone.
