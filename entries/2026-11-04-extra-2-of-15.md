# Daily Tips special, part 2 of 15: random numbers, or the number that was never supposed to be 1.0

<!-- special-nav -->
**Specials:** [<- previous: random numbers, part 1 of 15](2026-11-04-extra-1-of-15.md) | [next: random numbers, part 3 of 15 ->](2026-11-04-extra-3-of-15.md)

Not part of the rotation. Part 1 said a seed fixes the raw stream and little above it. This part is about that "above it": the step that squeezes a random integer into a range or a float. Two squeezes fail in ways that look like nothing. One makes the top of the range unreachable or doubled. The other returns a value the specification says is impossible.

# What happened

**Bug class:** a specified algorithm that violates its own range, caught by a downstream function (an exponential distribution turned into infinity). Rounding, not the engine, is the cause. It fires rarely and identically, so it is a Bohrbug that behaves like a Heisenbug.

**The story, in plain words:**

In August 2015 someone filed a bug against the C++ standard library. Their program drew exponentially distributed floats from a 64-bit Mersenne Twister, and every so often it printed `inf`. Not a wrong number: infinity, which then flowed into whatever came next.

The cause was one step earlier than they thought. An exponential value is computed as `-log(1 - x)`, where `x` is a random float in the half-open range from 0 up to but not including 1. If `x` were ever exactly 1, then `1 - x` is 0, `log(0)` is minus infinity, and the result is infinity. The standard promises `x < 1`. The standard's own recipe for making that float, `generate_canonical`, computes a large integer divided by a power of two, and a large integer divided by a power of two can round to exactly 1.0 when the answer has to fit in 24 bits. The committee's own minutes show it printing `0x1p+0`, which is 1.0, from a function defined to return less than 1.

The library working group discussed it in Kona in October 2015, and the record shows people who were uneasy about every fix on the table. One member said "The one thing we cannot tolerate is any output range other than [0, 1)." Another worried that nudging the top value down "will introduce a subtle bias". A third summed up the real problem: "The problem is that the standard specifies the implementation, and the implementation doesn't work." In 2017 they chose to re-run the algorithm when it returns 1.0. A paper, P0952, carried that through, and the issue was marked resolved on 2 April 2024, eight and a half years after it was filed.

The quotes, from the C++ Library Working Group issue list, LWG 2524 ("generate_canonical can occasionally return 1.0"):

- "For float on the average 1 out of 2^24 (~10^7) draws returns 'inf', which is easily confirmed." (the submitter, for their 64-bit engine)
- "The one thing we cannot tolerate is any output range other than [0, 1)."
- "I'm not sure if nudging it down will introduce a subtle bias."
- "The problem is that the standard specifies the implementation, and the implementation doesn't work."
- "Choice: Rerun the algorithm if it gets 1.0." (Albuquerque, November 2017)

This part measures the same rounding in Rust and TypeScript, shows the three different fixes shipping in three C++ library versions, and measures the sibling failure: the modulo operator, which keeps its sign in .NET and its bias everywhere.

## Rust: `(raw as f32) / (u32::MAX as f32)` is exactly 1.0 for 128 of the 2^32 inputs, and `raw % n` favors the low residues by an exact, countable amount

*Stdlib and ecosystem gems*

**Did you know**

Enumerating every `u32`, the division `raw as f32 / u32::MAX as f32` is 1.0 or more for 128 inputs, the first being `4294967168`. A float has 24 bits of precision, so the 128 largest integers all round up to 2^32, and `u32::MAX as f32` is also 2^32. Code that then writes `(ratio * count as f32) as usize` gets `count`, one past the last valid index, about once per 33.5 million draws. The other classic squeeze, `raw % n`, is not uniform either: for `n = 3_000_000_000` the first 1,294,967,296 residues are exactly twice as likely as the rest.

**Show me**

```rust
// rustc 1.99.1, no crates: an exact count over every u32 input, about 4 seconds at -O
fn main() {
    let divisor_from_u32_max: f32 = u32::MAX as f32; // rounds up to 2^32
    let mut mut_count_one: u64 = 0;
    let mut mut_first_one: Option<u32> = None;
    for raw_value in 0..=u32::MAX {
        if (raw_value as f32) / divisor_from_u32_max >= 1.0 {
            mut_count_one += 1;
            if mut_first_one.is_none() {
                mut_first_one = Some(raw_value);
            }
        }
    }
    println!("f32 ratio >= 1.0: {} of 2^32 inputs, first at {:?}", mut_count_one, mut_first_one);

    for range_size in [6u64, 3_000_000_000u64] {
        let total_inputs: u64 = 1u64 << 32;
        let wide_residue_count: u64 = total_inputs % range_size; // residues that get one extra input
        let base_hits: u64 = total_inputs / range_size;
        println!(
            "n={} each residue {} times, first {} residues get {} (ratio {:.6})",
            range_size, base_hits, wide_residue_count, base_hits + 1, (base_hits + 1) as f64 / base_hits as f64
        );
    }
}
```

Output: `f32 ratio >= 1.0: 128 of 2^32 inputs, first at Some(4294967168)`, then `n=6 each residue 715827882 times, first 4 residues get 715827883 (ratio 1.000000)`, then `n=3000000000 each residue 1 times, first 1294967296 residues get 2 (ratio 2.000000)`. For a die the bias is one part in 700 million, invisible. For a range near the top of the integer, it is a factor of two.

**Why it matters**

Both squeezes are everywhere because they are one line. The float one fails once in tens of millions of draws and fails by one index, which is exactly the shape that survives every test and then pages someone after a week of traffic. The modulo one fails smoothly: the bias grows with `n` and nothing ever throws. `rand`'s `random_range` does the integer part with a rejection or multiplication method (part 1 showed its 0.9 change); this tip is for the code that does it by hand.

**Chew on this**

Where in your code does a random float meet an array index, and is there a clamp or a `min(count - 1, ...)` there? Which of your range sizes are large enough that `% n` stops being harmless, and who checked?

**Sources**

- https://cplusplus.github.io/LWG/issue2524 (the same rounding, in C++)
- https://doc.rust-lang.org/reference/expressions/operator-expr.html#numeric-cast (int to float casts round to nearest)

**Verified**

Exact enumeration of all 2^32 inputs, rustc 1.99.1, release build. The `%` residue counts are arithmetic (2^32 divided by n), not sampled.

**Gotchas**

- `u32::MAX as f32` is 4294967296.0, not 4294967295.0, which is why the ratio can reach 1.0 at all. Dividing by `u32::MAX as f64` does not have this problem for 32-bit inputs, because `f64` holds every `u32`; it does for 64-bit inputs.
- 128 of 2^32 is 2^-25, one draw in 33,554,432, for this particular conversion. A different engine width or float type changes the rate.

## C++: `generate_canonical` is specified to return a value below 1, and three library versions do three different things at 4294967168

*Stdlib and ecosystem gems*

**Did you know**

Give `std::generate_canonical<float, 24>` an engine whose output is 4294967168 (the first value whose float ratio rounds to 1.0) and it returns: `1` on libc++ 19.1.7, `0.99999994` on libstdc++ 14.2 (clamped with `nextafter`), and on libstdc++ from GCC 16.2 it never returns for a constant engine, because it re-draws until the result is below 1. That is the P0952 resolution of LWG 2524, shipped in one library and absent from another. Needs C++11 for the function. The fix is P0952R2; which compiler releases carry it is what the table measures.

**Show me**

```cpp
// g++ -std=c++23 -DSKIP_ROUNDING_CASES canon.cpp   (GCC 16.2: the constant engine would re-draw forever)
// clang++ -std=c++23 -stdlib=libc++ canon.cpp      (Debian clang 19.1.7 with libc++)
// clang++ -std=c++23 canon.cpp                     (the same compiler with libstdc++ 14.2)
#include <cstdint>
#include <cstdio>
#include <random>

template <std::uint32_t FIXED_OUTPUT>
struct FixedEngine { // an engine whose every output is FIXED_OUTPUT, to probe the edge of the range
    using result_type = std::uint32_t;
    static constexpr result_type min() { return 0; }
    static constexpr result_type max() { return 0xFFFFFFFFu; }
    result_type operator()() { return FIXED_OUTPUT; }
};

template <std::uint32_t FIXED_OUTPUT>
void report_float_edge() {
    FixedEngine<FIXED_OUTPUT> engine;
    const float canonical_float = std::generate_canonical<float, 24>(engine);
    std::printf("engine output %10u -> generate_canonical<float,24> = %.9g  is_one=%d\n",
                static_cast<unsigned>(FIXED_OUTPUT), canonical_float, canonical_float == 1.0f);
}

int main() {
    report_float_edge<0xFFFFFF7Fu>(); // 4294967167: rounds to just under 1.0f
#ifndef SKIP_ROUNDING_CASES
    report_float_edge<0xFFFFFF80u>(); // 4294967168: first value whose float ratio is 1.0f
    report_float_edge<0xFFFFFFFFu>(); // the engine maximum
#endif
}
```

Measured:

| Library | 4294967167 | 4294967168 | 4294967295 |
| --- | --- | --- | --- |
| libc++ 19.1.7 (Debian clang 19.1.7) | 0.99999994 | 1 | 1 |
| libstdc++ 14.2.0 (Debian clang 19.1.7) | 0.99999994 | 0.99999994 | 0.99999994 |
| libstdc++ from GCC 16.2 | 0.99999994 | does not return | does not return |

The 16.2 row is not a bug in the library: a constant engine can never produce a different draw, so a re-draw loop cannot end. A real engine would simply draw again. In the library source, `random.tcc` has a `__generate_canonical_pow2` path with `while (true)` that returns only when the result is below 1.0, and the older path ends with `nextafter(1, 0)`.

**Why it matters**

An engine value of 4294967168 is one in 2^25 for `mt19937` (the same arithmetic as the Rust tip; I measured the boundary, not a run of 33 million draws). Code downstream that divides by `1 - x`, takes `log(1 - x)`, or indexes by `x * n` meets the boundary at the same rate the LWG submitter did. Three ways to repair one specification means a seeded run can also differ across libraries in the rare draws where the fix triggers, a second reason not to treat distribution output as portable (part 1).

**Chew on this**

Which of your numeric routines have a precondition of "strictly less than 1", and which of them would you trust a library version to uphold? If the committee needed eight years to pick a fix, what does that say about picking your own?

**Sources**

- https://cplusplus.github.io/LWG/issue2524
- https://wg21.link/P0952

**Verified**

GCC 16.2.0 (`gcc:latest`), Debian clang 19.1.7 with libstdc++ 14.2.0 and with libc++, all `-std=c++23 -O2`. The GCC hang was located in `std::__generate_canonical_pow2` with gdb. The P0952 link is cited from the issue page; I did not open the paper.

**Gotchas**

- The `-DSKIP_ROUNDING_CASES` switch exists only because of the infinite loop. Remove it on libc++ or libstdc++ 14.
- I did not test MSVC's STL.

## F#: `abs Int32.MinValue` throws, `x % n` keeps the sign of `x`, and 41,584 of 100,000 string hashes were negative modulo 6

*Idioms and antipatterns*

**Did you know**

On .NET 10, `abs Int32.MinValue` raises `OverflowException`, because there is no positive 32-bit `-2147483648`. And `%` keeps the sign of its left operand (`-7 % 3 = -1`), so the usual `hash % bucket_count` is negative for about 42 percent of string hashes (half the hashes are negative, and five in six of those leave a nonzero remainder): 41,584 of 100,000 keys, measured. Two ways people patch the negative (`abs`, or `& 0x7FFFFFFF`) each have their own cost. `RandomNumberGenerator.GetInt32(6)` exists to skip the question; 600,000 draws gave `[100167; 99964; 100171; 99903; 99814; 99981]`.

**Show me**

```fsharp
// .NET 10.0.14, dotnet fsi
open System
open System.Security.Cryptography

printfn "abs Int32.MinValue: %s" (try string (abs Int32.MinValue) with ex -> ex.GetType().Name)

let bucket_count: int = 6
let negative_bucket_count: int =
    Seq.init 100000 (fun item_index -> (string item_index).GetHashCode() % bucket_count)
    |> Seq.filter (fun bucket -> bucket < 0)
    |> Seq.length
printfn "String.GetHashCode() %% 6 negative for %d of 100000 keys" negative_bucket_count

let bucket_counts: int[] = Array.zeroCreate<int> bucket_count
for _ in 1 .. 600000 do
    let bucket: int = RandomNumberGenerator.GetInt32(bucket_count)
    bucket_counts.[bucket] <- bucket_counts.[bucket] + 1
printfn "RandomNumberGenerator.GetInt32(6) x 600000: %A" bucket_counts
```

Output: `abs Int32.MinValue: OverflowException`, then `String.GetHashCode() % 6 negative for 41584 of 100000 keys` (the count varies per run, because .NET randomizes string hashes per process), then the six counts above. The 41,584 will not match your run; the roughly 42 percent will.

**Why it matters**

A negative array index is the loud failure and `abs` is the quiet one: it repairs every negative input but one and throws on that one, which a uniform 32-bit input reaches once in 4.3 billion draws. `& 0x7FFFFFFF` never throws but keeps 31 of 32 bits. `GetInt32` is the documented unbiased choice for secrets, and it is slower than `Random.Next`. In Rust `-7 % 3` is also `-1` (`rem_euclid` gives the always-nonnegative one), and in C++ `%` truncates toward zero since C++11, so all three languages share the sign trap.

**Chew on this**

Where is a hash or a random int used as an index in your code, and which of `abs`, `&` or `rem_euclid` did it choose? Does that choice still hold when the input is the one value nobody thought to try?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.randomnumbergenerator.getint32
- https://learn.microsoft.com/en-us/dotnet/api/system.math.abs

**Verified**

.NET SDK 10.0 image (Ubuntu), `dotnet fsi`. Claims about C++ truncation and Rust `rem_euclid` are from language documentation; I did not run them today. That `GetInt32` is unbiased rests on its documentation; the six counts are consistent with that and prove nothing alone.

**Gotchas**

- `Math.Abs Int32.MinValue` throws the same way as F# `abs` (measured separately).
- Comparing `GetHashCode` across runs is meaningless on .NET Core: string hashes are randomized per process, which is why the 41,584 moves.

## TypeScript: `Math.round(Math.random() * (n - 1))` gives the two end values half the probability of the rest

*Idioms and antipatterns*

**Did you know**

On Node 26.13 with 6,000,000 draws over six sides, `Math.round(Math.random() * 5)` produced `599791 1199720 1199318 1200449 1200621 600101`: the first and last sides got half the hits. `Math.floor(Math.random() * 6)` gave `999330 1000842 999647 1000123 998907 1001151`. Rounding gives value 0 only the interval below 0.5 and value 5 only the interval above 4.5, each half as wide as the others. And `Math.fround((2 ** 32 - 1) / 2 ** 32)` is `1`, the same rounding as the Rust tip.

**Show me**

```ts
// Node 26.13.0 (runs the types as-is), tsc 7.0.2
const const_draw_count: number = 6_000_000
const const_side_count: number = 6

const const_fn_count_by_side = (const_fn_pick_side: () => number): number[] => {
    const const_counts: number[] = new Array<number>(const_side_count).fill(0)
    for (let step_index: number = 0; step_index < const_draw_count; step_index++) {
        const_counts[const_fn_pick_side()]++
    }
    return const_counts
}

console.log("Math.round(random * 5):", const_fn_count_by_side(() => Math.round(Math.random() * (const_side_count - 1))).join(" "))
console.log("Math.floor(random * 6):", const_fn_count_by_side(() => Math.floor(Math.random() * const_side_count)).join(" "))
console.log("fround((2**32-1)/2**32):", Math.fround((2 ** 32 - 1) / 2 ** 32))

// the % bias, exactly: a random byte mapped onto a 62-character alphabet
const const_alphabet_size: number = 62
const const_byte_counts: number[] = new Array<number>(const_alphabet_size).fill(0)
for (let byte_value: number = 0; byte_value < 256; byte_value++) {
    const_byte_counts[byte_value % const_alphabet_size]++
}
console.log("byte % 62: symbols hit 5 times:", const_byte_counts.filter((hit_count: number) => hit_count === 5).length,
    "hit 4 times:", const_byte_counts.filter((hit_count: number) => hit_count === 4).length)
```

The counts vary slightly per run; the halves do not. The last line is exact arithmetic: 256 = 4 * 62 + 8, so 8 of 62 symbols are 25 percent more likely than the other 54.

**Why it matters**

`Math.round` is the idiom people reach for to include the upper bound, and it produces the fairness bug that no unit test with one draw can see. The byte-to-alphabet mapping is the security-shaped version: a token generator with 62 symbols from one random byte is slightly biased by construction, which is a weakened token, not a broken one. The fix for both is the same: draw a wider integer and reject the leftover, or use a library function that does.

**Chew on this**

Which of your helpers named `randomInt`, `randomChoice` or `pick` use `round`, and which use `% length` on a byte? How would you notice? The counts above needed a million draws to see.

**Sources**

- https://tc39.es/ecma262/#sec-math.random
- https://v8.dev/blog/math-random (what V8's generator is, and why it changed in 2015)

**Verified**

Node v26.13.0, 6,000,000 draws. The `Math.fround` line ran in the same Node 26.13 process; the 128-input count comes from the Rust enumeration.

**Gotchas**

- Effect's `Random.nextIntBetween` is inclusive in version 4 (part 1), so its mapping is a different question from this one.
- `crypto.randomInt(max)` in Node is documented for this use; I did not measure it today.

**Related**

- 2026-10-20, TypeScript: "Math.round(-2.5) is -2, x | 0 wraps modulo 2^32, and parseInt(0.0000005) is 5" (the rounding rule behind the end-value halving).

# The functional angle: a range is a total function only if you decide what happens at the edges

Draws on all four tips. Turning a random integer into "one of n" is a function from a large domain onto a small codomain. A total version says what happens to the inputs that do not fit evenly, and the four tips show each language's default.

```rust
// Rust: make the fit an explicit, total function. Reject the tail so every residue gets equal inputs.
fn fn_unbiased_below(range_size: u32, mut mut_next_raw: impl FnMut() -> u32) -> u32 {
    let reject_from: u32 = u32::MAX - (u32::MAX % range_size); // first input that would favor low residues
    loop {
        let raw_value: u32 = mut_next_raw();
        if raw_value < reject_from {
            return raw_value % range_size;
        }
    }
}
```

| Language | Default squeeze | What the default silently does | Total form |
| --- | --- | --- | --- |
| Rust | `raw % n`, or `ratio * n` as `usize` | bias that grows with `n`; index `n` once in 2^25 draws | rejection loop, or `random_range` |
| C++ | `generate_canonical` | returns 1.0 (libc++), or clamps, or re-draws (libstdc++) | nothing portable: pick one library |
| F# | `hash % n` | negative index in about 42 percent of cases | `rem_euclid`-style fix, or `GetInt32` |
| TypeScript | `Math.round(random * (n - 1))` | end values at half probability | `Math.floor(random * n)` |

C++ is the one row where the standard itself shipped the partial function, and the fix took eight years. The rejection loop above is total only if the generator varies: with a constant generator it never returns, which is exactly what GCC 16.2 did in the C++ tip.

# The security angle: a bias is a loss of entropy, and an out-of-range value is an input nobody validated

Draws on the Rust and TypeScript tips; Mode B (what the language does not prevent). Bug class: CWE-330 (Use of Insufficiently Random Values). The measured fact here is bias, not a short seed.

```ts
// TypeScript: a 16-character token from one byte per character over 62 symbols
const const_token_alphabet: string = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789"
const const_fn_biased_token = (const_random_bytes: Uint8Array): string =>
    Array.from(const_random_bytes, (byte_value: number) => const_token_alphabet[byte_value % const_token_alphabet.length]).join("")
// symbols 0..7 of the alphabet are 25 percent more likely than the others, per character
```

The loss per character is small (a slightly uneven alphabet, not a guessable token). The point is the habit, not this token.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | `byte % 62` biases 8 of 62 symbols (arithmetic) | nothing | `crypto.randomInt` or a rejection loop |
| Rust | `raw % n` bias; `ratio * n` index overflow | bounds-checked indexing turns the overflow into a panic, not a read | a panic on a request path is a denial of service |
| F# | negative index, or `OverflowException` on `abs` | an exception, not a wrong read | catch at the boundary, or use an unbiased API |
| C++ | an unchecked `v[n]` from `x * n` reading past the end | nothing | clamp, or `.at()` |

Rust is the baseline: it is the one where the range bug at least stops the program. Which would you rather debug at three in the morning, a panic with a line number or a token that is 25 percent likelier to start with a capital letter?

# FAQ

**Is `random_range` in Rust unbiased?**
Per rand's changelog it uses Lemire's method (part 1 cites it), which corrects the modulo bias; this part did not re-measure it.

**Does `Math.random()` ever return exactly 1?**
The language specification says no (greater than or equal to 0 and less than 1). I did not measure a run long enough to say anything about the boundary.

**Why did the 128 inputs round to 1.0?**
A 32-bit float keeps 24 bits of precision. Integers above 2^32 - 128 are closer to 2^32 than to the next float below it, so they round up.

# Appendix A: V8's Math.random could produce only 2^32 of the 2^52 values a double can hold, until December 2015

V8's blog post "There's Math.random(), and then there's Math.random()" (17 December 2015) says that up to version 4.9.40 V8 used MWC1616, a multiply-with-carry generator with 64 bits of internal state, and lists its problems in plain terms:

- "The number of random values it can generate is limited to 2^32 as opposed to the 2^52 numbers between 0 and 1 that double precision floating point can represent."
- "The more significant upper half of the result is almost entirely dependent on the value of state0."
- "With a badly chosen initial state, the cycle length could be less than 40 million."
- "It fails many statistical tests in the TestU01 suite."

The replacement, xorshift128+, landed in V8 v4.9.41.0 and shipped in Chrome 49; the post says Firefox and Safari also switched. The same post says even xorshift128+ "is still not cryptographically secure" and points to `getRandomValues`. Part 10 comes back to why that matters. I did not read the secondary account of one company's ID collisions that is often cited with this story: its host refused automated access, so it is not used here.

# Appendix B: Excel 2003's RAND could return negative numbers

Microsoft Knowledge Base article 834520, "The RAND function returns negative numbers in Excel 2003" (read through the Internet Archive's 2012 copy, because Microsoft's current site no longer serves it), says: "When you use the RAND function in Microsoft Office Excel 2003, the RAND function may return negative numbers." Its cause: "This problem may occur when you try to use many random numbers, and you update the RAND function multiple times. For example, this problem may occur when you update your Excel worksheet by pressing F9 ten times or more." The article states it was fixed in the Excel 2003 hotfix package dated 29 February 2004, and does not explain the mechanism. A function documented to return a value from 0 up to 1 returned one below 0: the same broken range as LWG 2524, in a spreadsheet.
