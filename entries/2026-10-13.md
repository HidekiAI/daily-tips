## Rust: A default type parameter never helps inference, which is why HashMap::new is only defined for RandomState

*Type system deep cuts*

**Did you know**

A default on a type parameter (`struct Labelled<Tag = String>`) is used only where you *write the type*: `let annotated: Labelled` means `Labelled<String>`. In expression position the default does nothing. `Labelled::default()` with no annotation is error E0283, "type annotations needed for `Labelled<_>`", even though a default is sitting right there. This is why std puts `HashMap::new` in `impl<K, V> HashMap<K, V, RandomState>`: the impl block pins the hasher, because the `S = RandomState` default cannot. `HashMap::default()` lives in `impl<K, V, S: Default>`, so `S` stays free and the same E0283 fires (measured, rustc 1.95.0). `Vec::new` and `A = Global` are the same trick.

**Show me**

```rust
use std::collections::HashMap;

#[derive(Debug, Default)]
struct Labelled<Tag = String> {
    tag: Tag,
}

impl<Tag> Labelled<Tag> {
    fn new(tag: Tag) -> Self { Labelled { tag } }
}

fn main() {
    // TYPE position: the default fills the hole, so this is Labelled<String>.
    let annotated: Labelled = Labelled::default();

    // EXPRESSION position: the default is ignored and the argument decides.
    let from_value = Labelled::new(7_u8); // Labelled<u8>, no error, no String

    // let inferred = Labelled::default();
    //     ^ E0283: type annotations needed for `Labelled<_>`

    // HashMap::new is defined only in `impl<K, V> HashMap<K, V, RandomState>`,
    // so the impl, not the default, chooses the hasher. This compiles:
    let mut by_name = HashMap::new();
    by_name.insert("alpha", 1);

    // let mut by_name = HashMap::default(); by_name.insert("alpha", 1);
    //     ^ E0283: type annotations needed for `HashMap<&str, i32, _>`

    println!("{} {:?} {}", annotated.tag.len(), from_value, by_name.len());
}
```

**Why it matters**

Adding a defaulted parameter to a public type (`Client<T>` becomes `Client<T, R = DefaultRetry>`) looks backward compatible, and it is in every signature that names the type. It is not in every caller that wrote `Client::default()` or `Client::builder()` and let inference finish the job: those stop compiling, unless you pin the new parameter in a separate impl block the way std does. C++ and TypeScript both do the opposite, and both were checked here: `template <class Tag = int> std::vector<Tag> make_empty(); auto empty = make_empty();` deduces `vector<int>` (clang 21, `-std=c++17`), and `function make_empty<Tag = string>(): Tag[]` makes `make_empty()` a `string[]` (tsc 6.0.3). F# has no type-parameter defaults at all, so the question never comes up there.

**Chew on this**

Which of your public types has a defaulted parameter, and is there a constructor callers reach for that lives in the generic `impl<T>` block instead of the pinned one? If you added a second parameter tomorrow, would you know which call sites in other crates break?

## C++: #embed hands you the file's bytes and no NUL, and suffix(, 0) is how you get one back

*New discoveries and currently popular patterns*

**Did you know**

C++26's `#embed` (P1967R14) expands a file into a comma-separated list of integer constants, one per byte, and nothing else. A `char` array initialised from it is exactly the file's size: `sizeof` is 5 for a 5-byte file, with no terminator. So `strlen`, `printf("%s")`, or a `std::string_view` built from `const char*` reads past the end. The standard gives you parameters for this: `suffix(, 0)` appends a NUL but only when the file is non-empty, and `if_empty(0)` covers the empty case. One more trap measured here: `__has_embed` is legal only inside `#if`; using it in an expression is a hard error. Support, as of Sandor Dargo's 2026-08-05 survey and the cppreference C++26 table: GCC 15 with `-std=c++26`; Clang 19 onward, accepted in C++ mode as a C23 extension with a `-Wc23-extensions` warning; MSVC not yet, and cppreference lists no MSVC entry.

**Show me**

```cpp
// g++ -std=c++26 embed.cpp                            (GCC 16.2; GCC 14.2 has no #embed)
// clang++ -std=c++2c -Wno-c23-extensions embed.cpp   (Apple clang 21)
#include <cstdio>
#include <cstring>

// greeting.txt holds the 5 bytes "hello", no trailing newline.
static const char raw_text[] = {
#embed "greeting.txt"
};                                  // sizeof == 5: bytes only, no terminator

static const char terminated_text[] = {
#embed "greeting.txt" suffix(, 0)
};                                  // sizeof == 6: suffix adds the NUL

// empty.txt exists with 0 bytes; suffix is skipped and if_empty supplies one.
static const char empty_text[] = {
#embed "empty.txt" suffix(, 0) if_empty(0)
};                                  // sizeof == 1

#if __has_embed("empty.txt") == __STDC_EMBED_EMPTY__   // only valid in #if
static_assert(sizeof empty_text == 1);
#endif

int main() {
    std::printf("%zu %zu %zu\n", sizeof raw_text, sizeof terminated_text, sizeof empty_text);
    std::printf("%zu\n", std::strlen(terminated_text));  // 5
    // std::strlen(raw_text) is an out-of-bounds read; ASan reports it below.
}
```

**Why it matters**

The first real use of `#embed` in a service is baking in a SQL migration, a default config, or a certificate bundle, and all three end up handed to an API that takes `const char*`. The bug never shows in a test, because the bytes after the array happen to be zero often enough. With `-fsanitize=address`, `strlen` over a 3-byte embed was reported as `global-buffer-overflow ... 0 bytes after global variable 'banner' ... of size 3`. Rust's `include_str!` returns a `&'static str` that carries its length, so the question cannot arise. Go's `//go:embed` into a `string` is the same: length-carrying. C++ gets bytes because `#embed` is a preprocessor feature shared with C, and C has no length-carrying string.

**Chew on this**

If you replaced an `xxd -i` build step with `#embed` tomorrow, would every consumer see the same bytes? `xxd -i` also gives you no NUL, but it emits a `_len` variable that people learned to use. Who in your codebase is depending on a terminator that was never there?

**Sources**

- https://wg21.link/P1967R14
- https://en.cppreference.com/w/cpp/preprocessor/embed
- https://en.cppreference.com/w/cpp/compiler_support/26
- https://sandordargo.com/blog/2026/08/05/cpp26-embed

**Verified**

Compiled and run with GCC 16.2.0 (`docker run gcc:16`, Debian, aarch64), `-std=c++26 -Wall -Wextra`: prints `5 6 1` and `5`; `__has_embed` in an expression is "used outside of preprocessing directive"; the ASan run reports the same `global-buffer-overflow ... 0 bytes after global variable 'banner' ... of size 3`, and GCC 16 also warns at compile time that the `strlen` argument is "missing terminating nul" (`-Wstringop-overread`). ## F#: lazy remembers the exception, so a config load that failed once at boot fails until the process restarts

*Stdlib and ecosystem gems*

**Did you know**

F#'s `lazy (...)` builds a .NET `Lazy<T>` in `ExecutionAndPublication` mode with a factory, and that mode caches exceptions. If the first `Force()` throws, every later `Force()` rethrows *the same exception object*, and the factory never runs again. Measured: one call to the loader, two identical `TimeoutException`s, and `ReferenceEquals` on the two caught exceptions is `true`. The flag a health check might read, `IsValueCreated`, stays `false` the whole time, so it cannot tell "not loaded yet" from "failed for good". The BCL ships the retrying variant: `Lazy<T>(factory, LazyThreadSafetyMode.PublicationOnly)` does not cache exceptions. The price is that several threads may run the factory concurrently, and only one result wins.

**Show me**

```fsharp
open System
open System.Threading

let mutable load_attempts = 0   // the probe's own counter, not part of the idiom

// The config server is unreachable on the first call only, like a DNS blip at boot.
let load_config () =
    load_attempts <- load_attempts + 1
    if load_attempts = 1 then raise (TimeoutException "config server timed out")
    "connection=prod"

let cached_config = lazy (load_config ())
// Force() twice: TimeoutException, TimeoutException. load_attempts = 1.
// cached_config.IsValueCreated = false, even though the failure is permanent.

// The BCL's retrying mode: exceptions are not cached, the factory runs again.
let retrying_config = Lazy<string>(load_config, LazyThreadSafetyMode.PublicationOnly)
// .Value twice (after resetting the counter): TimeoutException, then "connection=prod".
// Cost: concurrent first callers may each run load_config; one result is kept.
```

**Why it matters**

`let config = lazy (loadFromVault ())` at module level is the obvious way to defer a slow startup call, and it turns one transient network failure into a process that answers every request with the same exception until someone restarts it. Retry wrappers do not help, because they retry `Force()`, and `Force()` never calls the factory again. Rust makes the same split visible in two types (`LazyLock` poisons forever, `OnceLock::get_or_init` retries), and C++ retries a function-local `static` whose initializer threw, per the standard's static-initialization rule. See "The functional angle" below for the measured table.

**Chew on this**

Which of your module-level `lazy` values wrap something that can fail transiently: a secret store, a DNS lookup, a schema fetch? If one of them failed at 3 a.m., what in your service would notice, given that `IsValueCreated` says "not yet" rather than "broken"?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/framework/performance/lazy-initialization#exceptions-in-lazy-objects
- https://learn.microsoft.com/en-us/dotnet/api/system.threading.lazythreadsafetymode
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/lazy-expressions

**Verified**

Run with `dotnet fsi` on .NET 8.0.8, FSharp.Core assembly version 8.0.0.0. That `lazy` maps to `ExecutionAndPublication` is inferred from the measured behaviour plus the BCL table; the F# docs page does not name the mode.

## TypeScript: JSON.parse rounds a 64-bit id before your reviver sees it, and only the ES2025 context.source has the real digits

*Idioms and antipatterns*

**Did you know**

`const parsed: Ownership = JSON.parse(body)` with `owner_id: number` is the everyday idiom, and for a BIGINT id above 2^53 it silently gives you a different id. `{"owner_id": 9007199254740993}` parses to `9007199254740992`. The reviver does not help: it receives the value after it was already converted to a double, so it also sees `...992`. The fix is the ES2025 "JSON.parse source text access" feature: the reviver gets a third `context` argument whose `source` holds the raw text, for primitive values only. Node 22 ships it (measured: `BigInt(context.source)` gives `9007199254740993n`). TypeScript 6.0.3's `lib.es5.d.ts` still declares a two-argument reviver, and the typings are slated for a `lib.es2026.json.d.ts`. A three-argument arrow with an optional `context` still type-checks under `--strict`.

**Show me**

```typescript
const wire_body: string = '{"owner_id": 9007199254740993}';

type Ownership = { owner_id: number };

// The idiom: parse, then claim the type. tsc is satisfied; the value is wrong.
const parsed: Ownership = JSON.parse(wire_body);
console.log(parsed.owner_id);              // 9007199254740992: another user's row

// A reviver runs after number conversion, so it cannot undo the rounding.
JSON.parse(wire_body, (key: string, value: unknown) => {
    if (key === "owner_id") console.log(value); // 9007199254740992
    return value;
});

// ES2025: context.source is the raw text of a primitive. Not in TS 6.0.3's lib,
// so declare the parameter yourself; an optional third parameter still type-checks.
const exact = JSON.parse(wire_body, (key: string, value: unknown, context?: { source?: string }) =>
    key === "owner_id" && context?.source !== undefined ? BigInt(context.source) : value);
console.log(exact.owner_id);               // 9007199254740993n
```

**Why it matters**

Postgres `bigserial`, Snowflake-style ids, and Discord or Twitter ids all pass 2^53. Nothing throws: the wrong number is a valid number, so it goes into the next query and returns a neighbour's row. Every sibling here parses the integer exactly by default: `serde_json` keeps a `u64` as a `u64`, `System.Text.Json` reads an `Int64` from the digits, and nlohmann::json stores a `uint64_t`. JavaScript is the one runtime in the comparison that converts every JSON number to a double. Go is the instructive side note: `encoding/json` into `interface{}` makes a `float64` and loses digits the same way, unless you call `UseNumber()`.

**Chew on this**

Where in your services does an id cross a JSON boundary into Node, and is it a string on the wire or a number? If it is a number, which of your tests uses an id large enough to fail, as opposed to `1`, `2` and `42`?

# The functional angle: memoizing a thunk forces you to decide whether failure is a value, and Rust is the only one that ships both answers as separate types

Draws on the F# tip. The shape is "a thunk evaluated at most once": `lazy`, a function-local `static`, a memoized promise. It is pure only while the thunk succeeds. When it fails, the cache has to choose between remembering the failure, which makes it a referentially transparent value, and retrying, which makes it a side effect with a cache in front.

Same probe in each language: a loader that fails on the first call and succeeds on the second, accessed twice.

| Language | Memoized form | Load calls | Second access | What it costs |
| --- | --- | --- | --- | --- |
| F# | `lazy (load ())` | 1 | same exception object | permanent failure; `PublicationOnly` retries but lets threads race the factory |
| Rust | `LazyLock::new(load)` | 1 | panics (poisoned, unrecoverable) | permanent; no `into_inner` recovery on stable |
| Rust | `OnceLock::get_or_init(load)` | 2 | `"connection=prod"` | retries; the closure is passed at each call site, not once at the declaration |
| C++ | `static const auto config = load();` | 2 | `"connection=prod"` | retries; the standard requires a throwing initializer to be attempted again |
| TypeScript | `cached ??= load()` (a promise) | 1 | same rejection | permanent; retrying means clearing `cached` in a `.catch`, by hand |

The C++ row was run on Linux (GCC 14.2, Debian 13, `-std=c++20`): 2 load calls, second access `"connection=prod"`. The Rust, F# and TypeScript rows are language semantics, the same on Linux and macOS. As a separate confirmation, all five rows were run on macOS on 2026-10-13: rustc 1.95.0, Apple clang 21 `-std=c++20`, Node 22.17.1, .NET 8.0.8.

The asymmetry worth noticing is Rust's. `LazyLock` and `OnceLock` are the same machinery, and the only difference is *where the closure lives*. Bind the computation to the declaration and you get a value, which can only be poisoned. Pass it at the call site and you get a procedure, which can be tried again. F# and TypeScript give you the value form by default; C++ gives you only the procedure form, with no way to ask for a remembered failure except by catching and storing it yourself. The immutable, declaration-bound form is the one that pins a transient error forever.

The open thread: if a cached failure is the honest, pure answer, and a retry is the practical one, where should the retry policy live? Inside the cell, at the call site, or in a supervisor that throws the whole cell away?

# The security angle: an id that rounds is an authorization bug, and the type checker blesses it

Draws on the TypeScript tip, Mode B: the tip showed the rounding as a correctness problem; the question here is what it does to an access check. The direction is "the language does not prevent it".

The insecure sample is ordinary code that passes review:

```typescript
type DocumentRequest = { document_id: number };

// Looks like a standard ownership check. `db` and `Forbidden` stand for your own layer.
async function load_document(body: string, caller_id: bigint): Promise<string> {
    const request: DocumentRequest = JSON.parse(body);         // id above 2^53 is rounded here
    const row = await db.documents.findById(request.document_id); // reads the neighbour's row
    if (row.owner_id !== caller_id) throw new Forbidden();     // compares against that neighbour
    return row.content;
}
```

Two things go wrong depending on which side rounds. If the request id rounds and the stored owner id does not, the check fails closed and a legitimate user is refused, which is an outage, not a leak. If both ids pass through a double, for example the owner id was itself loaded through `JSON.parse` from another service, two distinct ids can compare equal and the check passes for the wrong principal. That second case is the authorization bypass, and it needs no attacker skill beyond choosing an id next to someone else's. Classes: CWE-681 (incorrect conversion between numeric types) leading to CWE-639 (authorization bypass through a user-controlled key).

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | every JSON number becomes a double; ids above 2^53 collide | nothing; `number` is the declared type and is satisfied | ids as strings on the wire, or `context.source` into `BigInt` (Node 22+) |
| Rust (`serde_json`) | an id larger than `u64`, or parsed via `f64` by choice | parses into `u64` exactly; out-of-range is an error | do not deserialize ids into `f64` or `serde_json::Value::as_f64` |
| F# / C# (`System.Text.Json`) | an `Int64` property read from a number above `long.MaxValue` | throws `JsonException` instead of rounding | catch it as a 400, not a 500 |
| C++ (nlohmann::json) | `get<double>()` on an id field | stores integers as `int64_t` / `uint64_t` exactly | request the integer type, never `double` |
| Go (side note) | `json.Unmarshal` into `interface{}` makes `float64` | rounds, same as JavaScript | `Decoder.UseNumber()` or a typed struct field |

The Rust, .NET, C++ and Go rows are from library documentation and were not run today; only the TypeScript row was measured. The baseline for this class is Rust, because `serde_json` makes the exact parse the default, so the TypeScript row reads as a choice the runtime made rather than something inherent to JSON. RFC 8259 section 6 warns that integers outside the IEEE 754 double range may not interoperate.

The open thread: which of your services compares an id that came through a JSON number on *both* sides of the check, and has any test ever used two ids that differ only above bit 53?
