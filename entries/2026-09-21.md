## Rust: HashMap::capacity() is a computed number, and it moves without any allocator call

*Stdlib and ecosystem gems*

**Did you know**

`Vec::capacity()` reports the length of a real allocation, so reading it tells
you something about memory. `HashMap::capacity()` does not: it is derived from
the bucket count times the maximum load factor, so it changes as entries are
removed even though hashbrown never gives the buckets back. Removing 9,995 of
10,000 entries reports a capacity drop from 14,336 to roughly 10,400 while the
table still owns every byte it ever allocated. `clear()` is the tell, because it
empties the map and reports the original 14,336 unchanged.

**Show me**

```rust
use std::collections::HashMap;

fn main() {
    let mk = || -> HashMap<u32, u32> { (0..10_000).map(|i| (i, i)).collect() };

    let mut a = mk();
    let full = a.capacity();                 // 14336
    a.retain(|&k, _| k < 5);
    // Capacity "dropped" to ~10.5k, but no realloc happened: retain rehashes
    // in place and leaves tombstones. The number moved; the footprint did not.
    println!("retain -> len {} cap {} (from {})", a.len(), a.capacity(), full);

    let mut c = mk();
    c.clear();
    // The honest reading: clear() removes every entry and capacity is untouched.
    println!("clear  -> len {} cap {}", c.len(), c.capacity());

    let mut d = mk();
    d.retain(|&k, _| k < 5);
    d.shrink_to_fit();                       // the only thing that calls the allocator
    println!("shrink -> len {} cap {}", d.len(), d.capacity());
}
```

Measured with rustc 1.95.0, `-O`: `retain` 14336 -> 10559, `remove` in a loop
14336 -> 10340 (the two differ only in tombstone accounting, not in bytes held),
`clear` 14336 -> 14336, and `shrink_to_fit` 14336 -> 7.

**Why it matters**

A long-lived cache that fills to a peak and then retains a small working set
holds its peak footprint for the life of the process, and `capacity()` will not
tell you, because the number you read drifts downward while RSS does not. No
profiler flags it as a leak: the map is legitimately alive. `Vec` is the
contrast that makes the trap, since there `retain` genuinely leaves capacity at
10,000 and the number means what you assumed.

**Chew on this**

Which of your long-lived maps has a peak that is much larger than its steady
state, and what would you actually measure to find out, given that
`capacity()` cannot answer it? If you added a `shrink_to_fit` after the
eviction pass, what would the rehash cost you on the request that happens to
trigger it?

## C++: One defaulted move constructor decides whether your type works with map::operator[]

*Idioms and antipatterns*

**Did you know**

Declaring a move constructor implicitly deletes copy assignment. `std::map`
splits its API along exactly that line: `try_emplace`, `emplace`, and `insert`
only ever *construct* a mapped value, while `operator[]`-then-assign and
`insert_or_assign` *assign* to an existing one. So a type with a defaulted move
constructor lives happily in a `map` until someone writes `m[k] = v`, and the
diagnostic points into `<map>` rather than at your class. C++11 onward for the
rule of five part; `try_emplace` and `insert_or_assign` are C++17, available in
libstdc++ 7, libc++ 4, and MSVC 19.11 onward.

**Show me**

```cpp
#include <map>
#include <string>
#include <type_traits>

struct Config {
    std::string name;
    Config(const char* n) : name(n) {}
    Config(Config&&) noexcept = default;   // this one line deletes copy-assign
    Config(const Config&) = default;
};

static_assert(std::is_copy_constructible_v<Config>);    // passes
static_assert(!std::is_copy_assignable_v<Config>);      // also passes
static_assert(!std::is_move_assignable_v<Config>);      // and this

int main() {
    std::map<int, Config> m;
    m.try_emplace(1, "alpha");        // OK: constructs in place, never assigns
    m.emplace(2, "beta");             // OK
    m.insert({3, Config("gamma")});   // OK: move-constructs into the node

    // Each of these fails to compile, and the error is reported inside <map>:
    //   m[1] = Config("x");                  // needs copy/move assignment
    //   m.insert_or_assign(1, Config("x"));  // same
    return m.size() == 3 ? 0 : 1;
}
```

Checked with Apple clang 21.0.0 (`-std=c++20`) against libc++. The failing form
reports `object of type 'Config' cannot be assigned because its copy assignment
operator is implicitly deleted`, sourced to `map:1234`, at `__iter->second =
std::forward<_Vp>(__v);`.

**Why it matters**

The rule-of-five consequence is well known in the abstract; what bites is that
the container decides which half of it you need, and the two halves look
interchangeable at the call site. A refactor that swaps `try_emplace` for the
more familiar `m[k] = v` turns a compiling type into an uncompilable one with no
change to the type at all, and the error blames the standard library.

Worth noting what this tip is *not*: the common claim that `emplace`
eagerly constructs a value and discards it on key collision did not reproduce
here. With an instrumented type, libc++ printed no constructor call for either
`emplace` or `try_emplace` on an existing key, because it compares the key
first when the key type permits. That optimization is permitted, not required,
so the difference is a quality-of-implementation matter rather than a guarantee.

**Chew on this**

In your own codebase, which mapped types would stop compiling if a colleague
replaced a `try_emplace` with `operator[]` and an assignment, and would your CI
catch it in a translation unit that nobody rebuilds often? If a type is
constructible but not assignable on purpose, is the `map` API the right place
for that invariant to be enforced, or should the value type say so itself?

## F#: Structural hashing reads the first 19 elements of an array, and equality reads all of them

*Perf and memory model*

**Did you know**

F#'s generic structural hash does not walk a whole array. It reads a bounded
prefix, measured here as indices 0 through 18, and ignores everything after,
while structural equality compares the array in full. The hash contract survives
(equal values still hash equally) but the converse fails loudly: two records
whose arrays differ only past index 18 collide in every hash-based container,
then pay a full-length comparison to be told apart. Verified on FSharp.Core
8.0.0.0 / .NET 8.0.8.

**Show me**

```fsharp
type Key = { Data: int[] }

// Which indices actually move the hash? Change one slot at a time and look.
let n = 64
let mk i v = { Data = Array.init n (fun j -> if j = i then v else j) }
let affects i = hash (mk i 999) <> hash (mk i 1000)
printfn "%A" ([ 0 .. n - 1 ] |> List.filter affects)
// [0; 1; 2; ...; 18]  -- 19 of 64. Indices 19..63 are invisible to the hash.

// Equality is not bounded, so these are correctly unequal but identically hashed.
let a = { Data = Array.init 100 (fun j -> if j = 99 then 1 else j) }
let b = { Data = Array.init 100 (fun j -> if j = 99 then 2 else j) }
printfn "equal: %b   same hash: %b" (a = b) (hash a = hash b)
// equal: false   same hash: true
```

The cost, on 2,000 keys of length 64 in a `Dictionary<Key,int>`:

```
differ at index 5  (hash spreads)   insert   0.3 ms   lookup   0.8 ms
differ at index 40 (all collide)    insert 113.6 ms   lookup  92.6 ms
```

Same key count, same array length, same container. Moving the distinguishing
element from index 5 to index 40 costs roughly 380x on insert, because every
insert degrades to a linear scan of one bucket with a full 64-element comparison
at each step.

**Why it matters**

Prefixed keys are ordinary, not adversarial: timestamps, zero-padded account
numbers, tenant-prefixed identifiers, and fixed protocol headers all share long
leading runs. Key a cache or a dedup set on one of those and the container
silently stops being a hash table. It is also the reachable-without-an-attacker
form of an algorithmic complexity attack (CWE-407), since anyone who chooses
your key layout chooses your data structure's asymptotics.

**Chew on this**

Which of your dictionary or `HashSet` keys wrap an array, a `byte[]`, or a
record containing one, and where does the first differing element actually sit
in real production data rather than in your test fixtures? If you moved the
distinguishing field to the front of the key, would that be a correctness-neutral
change, or does something downstream depend on the current ordering?

## TypeScript: The 10x is the Go rewrite, not the parallelism, and --checkers bought 13%

*New discoveries and currently popular patterns*

**Did you know**

TypeScript 7.0 shipped in August 2026 on a native Go compiler, and the headline
number is real but widely misattributed. The speedup comes from the rewrite
itself, not from the new `--checkers` parallelism flag. On the same 120-file
project measured here, 7.0.2 against 6.0.3 was 594 ms -> 194 ms, a 3x win with
`--checkers` left at its default. Varying `--checkers` from 1 to 8 on that same
project moved it 215 ms -> 188 ms, about 13%.

**Show me**

```bash
# Same project, same tsconfig, 120 files of mapped/conditional types.
$ tsc --version && npx tsc --version
Version 6.0.3
Version 7.0.2

$ time tsc -p .          # TypeScript 6.0.3
594 ms
$ time npx tsc -p .      # TypeScript 7.0.2, default checkers
194 ms                   # ~3x, and this is where the win actually comes from

# Now hold the compiler fixed at 7.0.2 and vary only the parallelism:
checkers=1     215 ms
checkers=2     194 ms
checkers=4     189 ms
checkers=8     188 ms    # 13% total, not 8x
```

Diagnostic *ordering* was stable across all four checker counts: errors came
back sorted by filename every time, so the release notes' caution about
order-dependent results did not manifest as scrambled output here.

**Why it matters**

If you are budgeting a 7.0 migration, the gain is in upgrading and needs no
tuning, whereas `--checkers` is a knob worth roughly a tenth on a project this
size and is not where the money is. Per-file checking is not the bottleneck at
120 files; the parallel win needs a large program with genuinely independent
modules, which is also the case the published 8-12x benchmarks measure. The flag
being cheap to try is exactly why it is worth measuring on your own repo instead
of assuming either number transfers.

**Chew on this**

On your largest project, does `--checkers` beat 13%, and if it does, what does
that tell you about how coupled your module graph is? Given that 7.0 has no
stable programmatic API until 7.1, which of your build steps actually embed
`typescript` as a library rather than shelling out to `tsc`, and do you know
without grepping?

**Sources**

- https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/
- https://www.infoq.com/news/2026/08/typescript-7-released/
- https://github.com/microsoft/typescript-go

**Verified**

Timings are from a single host (Apple silicon, Node 22.17.1) on a synthetic
120-file project, so treat the magnitudes as indicative rather than as
benchmarks. The published 8-12x figures are Microsoft's, on much larger real
codebases, and were not reproduced here.

# The security angle: a bounded hash is an unbounded comparison

Drawing on today's F# tip, and on the Rust one for the part nobody bills.

F#'s prefix-bounded structural hash is the clearest case, because the defect has
no insecure-looking code in it at all. This is ordinary, reviewable F#:

```fsharp
// Dedup incoming records by their raw payload. Looks like a cache.
type Envelope = { Payload: byte[] }
let seen = System.Collections.Generic.HashSet<Envelope>()
let accept (e: Envelope) = seen.Add e   // false if already seen
```

Nothing here is wrong on its face. But `Payload` is attacker-shaped data, the
hash reads only its first 19 bytes, and every message sharing a 19-byte prefix
lands in one bucket and costs a full-length comparison per existing entry. A
protocol with a fixed header supplies that prefix for free, no attacker needed;
an attacker who notices supplies it deliberately and turns the dedup set into a
quadratic allocator. That is CWE-407, and the fix is to key on something
uniformly distributed (a cryptographic digest of the payload, or a
`[<CustomEquality>]` implementation that hashes the whole array) rather than to
validate anything.

Rust's `retain` case is the same shape with the timing inverted: safe Rust, no
`unsafe`, no leak by any definition the language cares about, and a process
whose memory ceiling is set by its worst historical minute. Sustained unbounded
growth is a denial of service whether or not it is reachable on purpose.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| F# | Prefix-bounded hash turns a `HashSet`/`Map` into a linear scan (CWE-407) | Nothing. The hash contract is satisfied and the code compiles clean | Choose the key. Digest the payload or write `CustomEquality` that reads all of it |
| Rust | `HashMap` holds its peak footprint after eviction | Defaults to SipHash, so flooding the *hash* is already off the table | Bound the map, or `shrink_to_fit` on the eviction path. `capacity()` will not warn you |
| C++ | `std::hash<int>` is the identity function, `unordered_map` has no flooding resistance | Nothing, by design, for speed | Supply your own hash for any map keyed by untrusted values |
| TypeScript | Faster checks mean more CI runs trusting the same types, none of which exist at runtime | Nothing at runtime, in any version | Every boundary still needs a parse, and 7.0 did not change that |

Rust is the control here specifically because it already fixed the famous
version of this bug: `HashMap` uses SipHash by default precisely because hash
flooding is an attack. Which makes the F# result the interesting one, since the
collision arrives through the hash *function's own bound* rather than through a
weak algorithm, and no amount of choosing a better hash algorithm addresses it.

Which of your hash keys is a wrapper around a buffer whose leading bytes you do
not control?

# FAQ

**Does the F# prefix bound apply to lists and strings too, or only arrays?**
Today's measurement covers arrays specifically, including `int[][]`, where
nesting still hashed structurally and equally. `string` hashing goes through
.NET's own implementation rather than FSharp.Core's array path, so it is a
different mechanism and was not measured here.

**Would `[<CustomEquality>]` fix the F# case without changing my key type?**
It is the intended escape hatch, and it lets you hash the full array. Note the
tradeoff you are buying: an unbounded hash is O(n) per lookup by construction,
which is why FSharp.Core bounded it in the first place. A fixed-size digest
computed once at construction avoids both problems.

**Is `--checkers` on by default in TypeScript 7.0?**
The default is not 1: running with no flag matched `--checkers 2` at 194 ms in
the numbers above, and `--checkers 1` was measurably slower at 215 ms. So you
get some parallelism without asking.

**Does the C++ split apply to `unordered_map` as well?**
Yes, it has the same `try_emplace` / `insert_or_assign` pair with the same
construct-versus-assign requirements. `std::vector` has no equivalent, since
every insertion there needs move-assignability anyway to shift elements.

**Does Rust's `Vec::retain` have the same invisible-retention problem?**
It retains the allocation exactly as `HashMap` does, but `capacity()` reports it
honestly (10,000 before and after in the measurement above), so the number you
read is not lying to you. That is the whole distinction the Rust tip turns on.
