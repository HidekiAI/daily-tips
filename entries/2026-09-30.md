# Daily Tips: 2026-09-30

## Rust: `Arc::make_mut` with only `Weak` refs left moves the value to a new allocation, and every `Weak` now reads as dead

*Perf and memory model*

**Did you know**

`Arc::make_mut` has three outcomes, not two. Unique with no `Weak`: it mutates in place. Another strong `Arc` exists: it clones `T`. But strong count 1 with any `Weak` outstanding takes a third path: it does not clone `T`, it *moves* it into a fresh allocation and disassociates the old one, so every `Weak::upgrade()` returns `None` from then on. The value is alive and being mutated; every observer holding a `Weak` believes it was dropped. `Rc::make_mut` does the same. Stable since Rust 1.4.

**Show me**

```rust
// rustc 1.95.0, --edition 2024, -O. Printed values are from that run.
use std::sync::{Arc, Weak};

fn addr<T>(a: &Arc<T>) -> usize { Arc::as_ptr(a) as *const u8 as usize }

fn main() {
    let mut c = Arc::new(vec![0u8; 1 << 20]);   // 1 MiB payload
    let w: Weak<Vec<u8>> = Arc::downgrade(&c);  // e.g. a cache or observer
    let (alloc0, buf0) = (addr(&c), c.as_ptr() as usize);

    Arc::make_mut(&mut c)[0] = 3;               // strong == 1, weak == 1

    println!("same Arc alloc: {}", addr(&c) == alloc0);            // false: new control block
    println!("same Vec buffer: {}", c.as_ptr() as usize == buf0);  // true: T was moved, not cloned
    println!("weak sees: {:?}", w.upgrade().map(|v| v[0]));         // None: "dropped"
    println!("strong={} weak={}", Arc::strong_count(&c), Arc::weak_count(&c)); // 1 0

    // For contrast, with a second strong Arc the same call deep-copies the 1 MiB,
    // and the other Arc keeps the old value. Only the no-other-refs case is in place.
}
```

**Why it matters**

The cheap path is the right one for performance (a 24-byte move of the `Vec` header instead of a 1 MiB clone), which is exactly why it surprises: a `Weak`-keyed registry, a subscriber list, or a parent pointer in a tree loses track of the node the moment someone copy-on-writes it, with no error anywhere. C++ has no `make_mut` in std at all, and cannot write one safely: `shared_ptr::unique()` was deprecated in C++17 and removed in C++20 because `use_count()` is only approximate under concurrent `weak_ptr::lock()`. F#'s `{ r with X = 1 }` and TypeScript's spread never ask the question: they always allocate, because a tracing GC has no refcount to check, and so they never cut an observer loose either.

**Chew on this**

Where in your code does a `Weak` stand for "still the same logical object", and where does it only mean "this exact allocation"? If a writer copy-on-writes the node, which of those two contracts did your observers actually sign up for?

**Sources**

- https://doc.rust-lang.org/std/sync/struct.Arc.html#method.make_mut
- https://doc.rust-lang.org/std/rc/struct.Rc.html#method.make_mut
- https://en.cppreference.com/w/cpp/memory/shared_ptr/unique

**Verified**

## C++: `resize_and_overwrite` skips the zero-fill `resize` does, about 10x on a reused 1 MiB buffer, and the size you return is a promise

*Stdlib and ecosystem gems*

**Did you know**

`std::string::resize_and_overwrite(n, op)` (C++23, P1072R10) grows the string to `n` without value-initializing the new characters, hands `op` a `char*` and `n`, and truncates to whatever size `op` returns. That removes the zero-fill `resize(n)` pays before a `read()`/`recv()`/C API writes over it. Support: libstdc++ 12, libc++ 14, MSVC STL 19.31; feature-test macro `__cpp_lib_string_resize_and_overwrite` is `202110L`. The contract is strict: UB if `op` throws, if it returns a size outside `[0, n]`, or if any character in `[p, p + r)` is still indeterminate.

**Show me**

```cpp
// clang++ -std=c++23 -O2; Apple clang 21 and Homebrew clang 23.1.1, both libc++.
#include <cstring>
#include <string>

// Stands in for recv()/read(): writes some bytes, returns how many.
std::size_t fill(char* dst, std::size_t cap) {
    std::size_t n = cap / 16;
    std::memset(dst, 'x', n);
    return n;
}

void old_way(std::string& buf, std::size_t cap) {
    buf.clear();
    buf.resize(cap);                    // zeroes all cap bytes, every call
    buf.resize(fill(buf.data(), cap));  // then throws most of them away
}

void new_way(std::string& buf, std::size_t cap) {
    buf.resize_and_overwrite(cap, [](char* p, std::size_t n) {
        return fill(p, n);  // must not throw; must return <= n; must not touch buf
    });
}
// Measured, 1 MiB reused buffer, 2000 calls, best of two runs:
//   old_way 9.1 us/call   new_way 0.8-1.1 us/call   (same on both compilers)
```

**Why it matters**

Every network read loop that stages bytes in a `std::string` pays a memset proportional to the buffer, not to the bytes received, and with a 1 MiB buffer and 64 KiB reads that is most of the call. Rust's equivalent, `Vec::spare_capacity_mut`, hands out `&mut [MaybeUninit<u8>]` and makes you call `unsafe { set_len(n) }` to claim the bytes, so the promise `op`'s return value makes silently in C++ is an `unsafe` block you can grep for. .NET's `string.Create(length, state, SpanAction)` gives the same callback shape, but the span arrives zeroed (measured: an untouched span yields eight `\0`), so it saves a copy, not the zeroing.

**Chew on this**

Which of your buffers are sized to "the most we could receive" and then zero-filled on every request? And if a callback like `op` ever returns the offered size instead of the written size, what would be in the tail of that string on your platform?

## F#: `dict` finds an array key and `Dictionary()` does not, and wrapping the key in a tuple breaks it where a record does not

*Idioms and antipatterns*

**Did you know**

F#'s own collection functions (`dict`, `readOnlyDict`, `Map`, `Set`, `List.distinct`, `Seq.groupBy`, `HashIdentity.Structural`) use F# generic equality, which compares arrays by content. A BCL constructor like `Dictionary<_,_>()` or `HashSet<_>()` uses `EqualityComparer<T>.Default`, which compares arrays by reference. The trap deepens with composite keys: an F# record holding an array works as a `Dictionary` key, because the compiler generates a structural `Equals`/`GetHashCode`, but a tuple holding the same array does not, because `System.Tuple.Equals` compares its items with the .NET default comparer. And `(a, 1) = (b, 1)` is `true` while `(a, 1).Equals((b, 1))` is `false`.

**Show me**

```fsharp
// dotnet fsi, .NET 8.0.8, FSharp.Core 8.0.0.0. Results printed by that run.
open System.Collections.Generic
type R = { Key: int[] }
let a, b = [| 1; 2 |], [| 1; 2 |]          // equal contents, different objects

(dict [ a, "x" ]).ContainsKey b             // true   F# generic equality
(Dictionary<int[], string>(dict [ a, "x" ])).ContainsKey b  // false  copying drops the comparer
Set.contains b (set [ a ])                  // true
(HashSet<int[]>([ a ])).Contains b          // false

let dt = Dictionary<int[] * int, string>()
dt.[(a, 1)] <- "x"
dt.ContainsKey((b, 1))                      // false  System.Tuple.Equals, by reference inside
let dr = Dictionary<R, string>()
dr.[{ Key = a }] <- "x"
dr.ContainsKey { Key = b }                  // true   compiler-generated structural Equals

// The fix keeps the BCL type and picks the comparer explicitly:
let fixedD = Dictionary<int[], string>(HashIdentity.Structural)  // ContainsKey b -> true
```

**Why it matters**

Moving a lookup from `dict` to a mutable `Dictionary` for performance is a routine refactor, and it silently turns every hit on an array or tuple-of-array key into a miss: no exception, just a cache that never hits or a dedup that never dedups. Rust has no such split: `Vec<u8>`, `[u8; 4]`, and tuples hash by content through `derive(Hash, Eq)`, so a `HashMap` key means the same thing everywhere. C++ goes the other way: `std::unordered_map<std::vector<int>, V>` does not compile at all without a user-supplied hash, so the choice is forced into view. TypeScript's `Map` is reference-only for every object, which is at least uniform.

**Chew on this**

Which of your hot-path `Dictionary` instances started life as a `dict` or a `Map`, and did the comparer come along? And is a record-wrapping-an-array key a design you would keep, knowing that it works only because of generated code a tuple does not get?

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-hashidentity.html
- https://learn.microsoft.com/dotnet/api/system.tuple-2.equals
- https://learn.microsoft.com/dotnet/api/system.collections.generic.equalitycomparer-1.default

## TypeScript: `filter(x => x !== undefined)` narrows the array and `filter(x => !!x)` does not, because an inferred predicate has to be an "if and only if"

*Type system deep cuts*

**Did you know**

Since TypeScript 5.5, a function whose body returns a boolean can get an *inferred* type predicate, so `xs.filter(x => x !== undefined)` on `(number | undefined)[]` finally returns `number[]`. The inference only fires when the `false` branch also narrows: returning `false` must prove the value is *not* the narrowed type. `!!x` fails that test because `0` is falsy, so `false` does not mean `undefined`; `filter(Boolean)`, `s => s` on `(string | null)[]`, and `x => x !== undefined && x > 0` all stay wide for the same reason. An explicit `(x): x is number` predicate skips the proof entirely, so a wrong one compiles.

**Show me**

```ts
// tsc --strict --noEmit, identical results on TypeScript 6.0.3 and 7.0.2.
declare const xs: (number | undefined)[];

const a = xs.filter(x => x !== undefined);        // number[]
const b = xs.filter(x => !!x);                    // (number | undefined)[]  0 is falsy
const c = xs.filter(Boolean);                     // (number | undefined)[]
const d = xs.filter(x => x !== undefined && x > 0); // (number | undefined)[]
                                                  //   false could mean "was 0"

function isDef(x: number | undefined) { return x !== undefined; }
const e: number[] = xs.filter(isDef);             // OK: named functions infer too

// Hand-written predicates are trusted, not checked:
const liar: number[] = xs.filter((x): x is number => x !== 0);  // compiles;
//   undefined is still in the array at runtime
```

**Why it matters**

The "iff" rule is what keeps the inference sound, and it is also why the most common idiom, `filter(Boolean)`, never benefited: the fix is to write the comparison you mean, not to add a `!`. Rust's `filter` never changes the element type; changing it is a different function, `filter_map` or `flatten`, so the type change is visible at the call. The dangerous version is the explicit predicate: it is an `as` cast wearing a function signature, and the compiler checks nothing in its body.

**Chew on this**

How many `(x): x is T =>` predicates in your code were written before 5.5 and could now be deleted in favor of an inferred one? And for the ones that remain, what would it take to check that the body really proves what the signature claims?

**Sources**

- https://devblogs.microsoft.com/typescript/announcing-typescript-5-5/#inferred-type-predicates
- https://www.typescriptlang.org/docs/handbook/2/narrowing.html#using-type-predicates

# The functional angle: only TypeScript lets `filter` change the element type, so only TypeScript has to prove an "if and only if"

Draws on the TypeScript tip. The shape: drop the missing values from a list of optionals and end up with a list of the values. Every language can do it; they disagree on whether a *filter* is allowed to do it.

```rust
let kept: Vec<Option<i32>> = xs.iter().copied().filter(|x| x.is_some()).collect(); // type unchanged
let got:  Vec<i32>         = xs.iter().copied().flatten().collect();               // [0, 3]
```

```cpp
auto got = xs | std::views::filter([](auto& o) { return o.has_value(); })
              | std::views::transform([](auto& o) { return *o; });  // *o unchecked, trusts the filter
```

```fsharp
List.filter Option.isSome xs   // [Some 0; Some 3]  still options
List.choose id xs              // [0; 3]
```

| Language | Functional form | What it costs |
| --- | --- | --- |
| F# | `List.choose` | nothing extra: filter-and-unwrap is one function, so there is no predicate to trust (the baseline because `choose` is the idiomatic spelling) |
| Rust | `filter_map` / `flatten` | nothing extra; `filter` cannot change the type, so the change is always a different, named adaptor |
| C++ | `views::filter` then `views::transform(deref)` | two adaptors and an unchecked `*o` whose safety lives in the other lambda; no `choose` in std |
| TypeScript | `filter` with an inferred predicate | one function that sometimes changes the type: only when the predicate is an iff, and a hand-written predicate is trusted without a check |

The asymmetry: F# and Rust made "refine the type" a constructor-driven operation (`Some v` is the proof), so the question never arises. TypeScript made it predicate-driven, which is the only way a structural type system can express it, and paid for that with an inference rule readers have to learn. C++ pays in a different coin: the proof and its use sit in two lambdas that can drift apart.

Left hanging: in your own pipelines, where does "this value is present" get proved, and how far away is the line that relies on it?

# The security angle: a buffer you did not zero holds the previous request, and only Rust makes reading it a type error

Draws on the C++ tip, Mode B: `resize_and_overwrite` is fine used this way, but is it *secure*? It runs in the direction C++ does **not** prevent. Class: CWE-226 (Sensitive Information in Resource Not Removed Before Reuse), with CWE-908 (Use of Uninitialized Resource) as the mechanism.

```cpp
// Looks like a correct read loop. The callback returns the size it hoped for,
// not the size it wrote. The standard calls this UB; libc++ on this Mac
// returned the previous request's bytes.
std::string buf;  // reused across requests
buf.resize_and_overwrite(64, [](char* p, std::size_t) {
    std::memcpy(p, "token=HUNTER2", 13); return std::size_t{13}; });   // request 1
buf.resize_and_overwrite(64, [](char* p, std::size_t) {
    std::memcpy(p, "ok\n", 3); return std::size_t{13}; });            // request 2: wrote 3
// buf == "ok\nen=HUNTER2"   <- measured, Apple clang 21 -O2
```

```cpp
// What was meant: return what was written, and nothing else. (sketch, not compiled; needs <unistd.h>)
buf.resize_and_overwrite(64, [&](char* p, std::size_t n) {
    ssize_t got = ::read(fd, p, n);
    return got < 0 ? std::size_t{0} : static_cast<std::size_t>(got); });
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | claiming spare capacity you did not write | `spare_capacity_mut` yields `MaybeUninit<u8>`; `set_len` is `unsafe` | audit every `unsafe { set_len(..) }` against the byte count actually written |
| C++ | `op` returns more than it wrote | nothing; UB by the standard, stale bytes in practice | return the written count, never the offered one; treat `op` as security-relevant code |
| C# / F# | same callback shape via `string.Create` | the span arrives zeroed (measured), so the worst case is `\0` padding | nothing for disclosure; still check the length you produce |
| TypeScript | `Buffer.allocUnsafe` sent before it is fully written | documented as possibly holding old data; not measured leaking today | use `Buffer.alloc` on any path whose bytes leave the process, or `fill` before use |

The control is Rust: it is the only row where the uninitialized state has a *type*, so reading it is a compile error rather than a code-review finding. C++ offers the same performance with the promise moved into a return value nobody checks.

Left hanging: which of your reused buffers can leave the process, and does the length that leaves come from the bytes you wrote or from the size you asked for?

# FAQ

**Does `Arc::make_mut` count a `Weak` held by another thread the same way?** Yes. The check is on the counts, not on who holds them; the doc's disassociation rule applies to any outstanding `Weak`.

**Is there a `resize_and_overwrite` for `std::vector`?** Not in C++23. P1072 covered `basic_string` only; a vector needs a custom allocator that default-initializes instead of value-initializing.

**Does the inferred predicate survive `.filter(...).map(...)`?** Yes: the narrowed element type flows into the next call, which is most of the benefit.
