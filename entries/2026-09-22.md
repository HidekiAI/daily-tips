# Daily Tips: 2026-09-22

## Rust: Box<LocalType> is local for coherence and Rc<LocalType> is not

*Type system deep cuts*

**Did you know**

The orphan rule is usually explained as "one of the types has to be local", but
`Box<Local>` counts as local and `Rc<Local>` does not, and nothing in the error
message tells you why. The reference says it outright: "for the purposes of
coherence, fundamental types are special. The `T` in `Box<T>` is not considered
covered, and `Box<LocalType>` is considered local." Fundamentality is the
unstable `#[fundamental]` attribute, carried by exactly four things in std:
`&T`, `&mut T`, `Box<T>` (alloc/src/boxed.rs:228) and `Pin<T>`
(core/src/pin.rs:1088). `Rc`, `Arc`, `Vec` and `Option` do not have it, so a
foreign trait implemented through them is E0117. The attribute is
`rustc`-internal, so you cannot add it to your own smart pointer.

**Show me**

```rust
use std::rc::Rc;
use std::sync::Arc;
use std::pin::Pin;

struct Local(u32);

// std::ops::Add is foreign and u32 is foreign, so the ONLY thing making these
// legal is that the wrapper is #[fundamental] and therefore transparent to
// the coherence check.
impl std::ops::Add<u32> for &Local        { type Output = u32; fn add(self, r: u32) -> u32 { r } }
impl std::ops::Add<u32> for &mut Local    { type Output = u32; fn add(self, r: u32) -> u32 { r } }
impl std::ops::Add<u32> for Box<Local>    { type Output = u32; fn add(self, r: u32) -> u32 { r } }
impl std::ops::Add<u32> for Pin<Box<Local>> { type Output = u32; fn add(self, r: u32) -> u32 { r } }

// Identical shape, non-fundamental wrapper, rejected:
//   impl std::ops::Add<u32> for Rc<Local>     -> error[E0117]
//   impl std::ops::Add<u32> for Arc<Local>    -> error[E0117]
//   impl std::ops::Add<u32> for Vec<Local>    -> error[E0117]
//   impl std::ops::Add<u32> for Option<Local> -> error[E0117]
// The note reads "`Rc` is not defined in the current crate", which is true of
// Box as well and is therefore not the actual reason.

// The documented way out is a local newtype, not a cleverer impl:
struct MyArc(Arc<Local>);
impl std::ops::Add<u32> for MyArc { type Output = u32; fn add(self, r: u32) -> u32 { self.0.0 + r } }
```

MEASURED, each case compiled on its own with `rustc --edition 2021
--crate-type lib` on rustc 1.95.0: `&Local`, `&mut Local`, `Box<Local>` and
`Pin<Box<Local>>` accepted; `Rc<Local>`, `Arc<Local>`, `Vec<Local>` and
`Option<Local>` all E0117. The newtype version compiles. A *local* trait for a
foreign type (`impl MyTrait for Rc<u32>`) is fine and always was, by the first
clause of the rule.

**Why it matters**

This is the rule that decides whether a wrapper type in your public API can be
extended by your users. Return `Box<Handle>` from a builder and a downstream
crate can `impl serde::Serialize for Box<Handle>`; return `Arc<Handle>` and they
cannot, and their only recourse is a newtype that breaks every deref site. The
choice looks like a refcounting decision and is also a coherence decision, made
permanently at the moment you publish the signature.

No other language in this rotation has this rule, which is the interesting half.
C++ has no coherence check at all: two translation units may specialize the same
template differently and the standard calls that an ODR violation, which is
ill-formed-no-diagnostic-required, so you get a link-time coin flip rather than
an error. C# and F# extension members are resolved by what is in `using` /
`open` scope at the call site, so two libraries extending the same type is an
ambiguity you fix per file, not a conflict the compiler forbids. TypeScript's
declaration merging is a deliberate extension point, so a third party is
*supposed* to reopen your interface. Rust is alone in paying for global
uniqueness up front, and `#[fundamental]` is the list of exceptions it was
willing to hard-code.

**Chew on this**

Which of your public types hand out `Arc<T>` where the caller might reasonably
want to implement a foreign trait on it, and would exposing `T` alongside the
`Arc` actually help them? And since `#[fundamental]` is closed to your crate,
what does that imply about a smart pointer you wrote yourself as a drop-in for
`Arc` - which of the two rules is it silently on the wrong side of?

**Sources**

- https://doc.rust-lang.org/reference/items/implementations.html
- https://rust-lang.github.io/rfcs/2451-re-rebalancing-coherence.html
- https://doc.rust-lang.org/error_codes/E0117.html

**Verified**

All eight impls and the newtype workaround compiled or failed as stated on
rustc 1.95.0 (aarch64-apple-darwin). The `#[fundamental]` line numbers are from
this toolchain's vendored source under `rustc --print sysroot`; `&T` and
`&mut T` fundamentality is built into the compiler rather than spelled in
library source, so that pair rests on the reference plus the measured result.
The C++, C#/F# and TypeScript comparison above rests on documentation only:
nothing about ODR violations, extension-member resolution or declaration
merging was compiled here.

- [2026-09-15](2026-09-15.md) - Rust, "A trait object's elided lifetime comes
  from the containing type, not the use site". Same shape of surprise: the rule
  reads a property off the wrapper, and the diagnostic points at the payload.

## C++: GCC 16 made C++20 the default, so [=] capturing this now warns in code you never touched

*New discoveries and currently popular patterns*

**Did you know**

GCC 16.1 shipped 2026-04-30 with this in its changes page: "GCC 16 changes the
default language version for C++ compilation from -std=gnu++17 to -std=gnu++20.
If your code relies on older versions of the C++ standard, you will need to
either add -std= to your build flags, or port your code." One consequence lands
on every codebase that writes lambdas inside member functions. C++20 deprecated
`[=]` implicitly capturing `this`, and the resulting diagnostic is **on by
default** - no `-Wall`, no `-Wextra`, no `-Wdeprecated` required. So a build
that was silent under GCC 15 now warns, on a line nobody edited, because the
default standard moved underneath it.

**Show me**

```cpp
#include <functional>

struct Widget {
    int n = 7;
    std::function<int()> make() {
        // [=] reads as "capture everything by value". For a member it does not:
        // n is not a variable, it is this->n, so what gets captured is the bare
        // `this` pointer. The lambda now outlives whatever `this` pointed at.
        return [=] { return n; };
        // [=, this]  -> same meaning, spelled out, and silent (C++20 added it)
        // [*this]    -> captures a COPY of the object, and is what [=] implies
    }
};

int main() {
    std::function<int()> f;
    { Widget w; f = w.make(); }   // w dies here; f still holds its address
    return f();                   // reads through a dangling this
}
```

MEASURED on Apple clang 21.0.0 (clang-2100.3.34.2, arm64-apple-darwin25.6.0):

| Flags | Result |
| --- | --- |
| `-std=c++17 -Wall -Wextra -Wdeprecated` | silent |
| `-std=c++20`, no warning flags at all | `warning: implicit capture of 'this' with a capture default of '=' is deprecated [-Wdeprecated-this-capture]` |
| `-std=c++23`, no warning flags | same warning |
| `-std=c++20`, rewritten as `[=, this]` | silent |
| `-std=c++20`, rewritten as `[*this]` | silent |

Run under `-fsanitize=address`: `ERROR: AddressSanitizer: stack-use-after-scope
... READ of size 4 ... SUMMARY: stack-use-after-scope cap.cpp:7 in
Widget::make()::'lambda'()::operator()() const`. The warning is pointing at a
real use-after-free, not a style preference.

**Why it matters**

The upgrade is the event, not the code. A team that moves to GCC 16 without
pinning `-std=` gets C++20 semantics across the whole tree at once: `u8"..."`
becomes `const char8_t*` and stops converting to `const char*`, `concept` and
`requires` stop being usable as identifiers, `operator!=` starts being
synthesized from `operator==` and can make a hand-written `!=` ambiguous, and
the `[=]` deprecation fires wherever a saved lambda touches a member. Pinning
the old standard makes the build green again and also switches the
`[=]`-captures-`this` warning back off, which is the one item on that list you
probably wanted to keep.

**Chew on this**

Does your build pin `-std=` explicitly, or inherit whatever the compiler
defaults to - and if you moved to GCC 16 tomorrow, would the new warnings reach
anyone, or land in a log nobody reads because the build still exits zero? And
given that `[=]` inside a member function has always captured `this` by pointer,
what made that worth deprecating in 2020 rather than at any point in the
previous eight years?

**Sources**

- https://gcc.gnu.org/gcc-16/changes.html
- https://gcc.gnu.org/gcc-16/porting_to.html
- https://en.cppreference.com/w/cpp/language/lambda
- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2018/p0806r2.html

**Verified**

The five flag combinations, the ASan report and the `u8"hi"` -> `const char*`
error (clean at `-std=c++17`, `error: cannot initialize a variable of type
'const char *' with an lvalue of type 'const char8_t[3]'` at `-std=c++20`) were
all run here on Apple clang 21.0.0. No GCC is installed on this host, so the
default-standard switch itself and the `operator!=` ambiguity are quoted from
gcc.gnu.org, not reproduced. Deprecation state is standard-mandated (P0806R2,
C++20), so clang and GCC agree on the *rule*; whether GCC spells the warning
`-Wdeprecated-this-capture` was not confirmed.

**Related**

- [2026-08-28](2026-08-28.md) - C++, "GCC 16 quietly turns on zero-init for
  locals under -std=c++26 (P2795 erroneous behavior)". The same release, the
  same mechanism: a standard-version knob rewriting the meaning of code you did

## F#: ValueOption has been in FSharp.Core since 4.5, and Some on an int costs 24 bytes without it

*Stdlib and ecosystem gems*

**Did you know**

`Option<'T>` in FSharp.Core is an ordinary reference-type discriminated union,
so every `Some x` over a value type allocates a heap object: measured at 24
bytes per element on .NET 8, being a 16-byte object header plus a 4-byte payload
padded to 8. `None` is the one free case, because FSharp.Core represents it as
`null`. The fix has shipped in the standard library since FSharp.Core 4.5 and
almost nobody reaches for it: `ValueOption<'T>`, spelled `ValueSome` / `ValueNone`
and abbreviated `voption`, is a `[<Struct>]` union and allocates zero. Both
report `sizeof` 8 on this host, which tells you nothing, because for the
reference option that 8 is the pointer and not the payload.

**Show me**

```fsharp
open System
open System.Runtime.CompilerServices

// NoInlining is load-bearing for the MEASUREMENT, not for the behavior.
// Without it the F# optimizer fuses construct-with-match and elides the
// allocation outright, so a naive benchmark reports 0 bytes for both and
// "proves" there is no cost. This was actually observed; see Verified.
[<MethodImpl(MethodImplOptions.NoInlining)>]
let mkOption (i: int) : int option = if i % 2 = 0 then Some i else Some (i + 1)

[<MethodImpl(MethodImplOptions.NoInlining)>]
let mkVOption (i: int) : int voption = if i % 2 = 0 then ValueSome i else ValueSome (i + 1)

let measure name (f: unit -> int) =
    f () |> ignore                                   // warm the JIT first
    GC.Collect()
    let before = GC.GetAllocatedBytesForCurrentThread()
    f () |> ignore
    printfn "%-26s %9d bytes" name (GC.GetAllocatedBytesForCurrentThread() - before)

measure "Some i  (int option)" (fun () ->
    let mutable s = 0
    for i in 1 .. 1_000_000 do
        match mkOption i with Some v -> s <- s + (v &&& 1) | None -> ()
    s)                                               // 24000000 bytes, 24 each

measure "ValueSome i (int voption)" (fun () ->
    let mutable s = 0
    for i in 1 .. 1_000_000 do
        match mkVOption i with ValueSome v -> s <- s + (v &&& 1) | ValueNone -> ()
    s)                                               // 0 bytes

printfn "None is represented as null: %b" (isNull (box (None: int option)))   // true
```

MEASURED: `24000000` bytes for `Some` (24 per element), `0` for `ValueSome`,
and `None is represented as null: true`. Run with `dotnet fsi`, .NET SDK
8.0.401, runtime 8.0.8, FSharp.Core 8.0.0.0.

**Why it matters**

`option` is the return type of every lookup, parse and partial function in
idiomatic F#, so a request handler threading a few options per field over a
collection allocates steadily in the gen0 nursery for no semantic gain.
Survivable in a batch job; visible as GC pressure in a service at steady state.
The comparison is what makes this F#-specific rather than general: Rust's
`Option<u32>` is 8 bytes on the stack and `Option<&T>` is niche-optimized to a
single pointer with no tag at all, while C++'s `std::optional<int>` is a payload
plus a `bool`, inline. F# is the only one of the three whose *default* option
type reaches for the heap, which is a strange place for the FP-native language
to charge the most.

**Chew on this**

Which of your hot paths return `option` over a primitive or a struct, and would
`voption` actually survive the trip, given it does not interoperate with
`Option.map` and friends without a rewrite? And since the optimizer erased the
allocation entirely once inlining was allowed, how would you find out whether
your real code gets that optimization or pays the 24 bytes?

**Sources**

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-core-fsharpvalueoption-1.html
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-core-fsharpoption-1.html
- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/prim-types.fs
- https://learn.microsoft.com/en-us/dotnet/api/system.gc.getallocatedbytesforcurrentthread

**Verified**

Measured twice, on 2026-09-21 and again today, with `dotnet fsi` on .NET SDK
8.0.401, runtime 8.0.8, FSharp.Core 8.0.0.0. The 24-byte figure is this runtime
on this host, not a language guarantee; the object header size is an
implementation detail of CoreCLR on 64-bit. The methodology note is real: the
first attempt, without `NoInlining`, reported 0 bytes for **both** cases because
the optimizer never allocated.

**Related**

- [2026-09-21](2026-09-21.md) - F#, "Structural hashing reads the first 19
  elements of an array, and equality reads all of them". The other half of what
  FSharp.Core's defaults cost you: that one is time per comparison, this one is
  bytes per value.
- [2026-09-17](2026-09-17.md) - C++, "std::deque gives you one heap block per
  element once sizeof(T) reaches 512". The same surprise from the container
  side: a per-element allocation hiding behind an abstraction that reads as flat.

## TypeScript: Node blanks your types out with spaces rather than deleting them, and Node 26 removed the escape hatch for everything else

*Idioms and antipatterns*

**Did you know**

Node's type stripping does not remove type annotations, it overwrites them with
whitespace. That is why a stack trace from a `.ts` file run directly points at
the right line *and column* with no source map, and why Node does not generate
one. The same design choice is what makes any TypeScript construct needing real
code generation unsupportable: `enum`, `namespace` with runtime content,
parameter properties and import aliases raise
`ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`. Node 26.0.0 removed
`--experimental-transform-types`, the flag that used to compile those, so the
gap is now permanent rather than opt-in. Type stripping itself went stable in
v25.2.0 and v24.12.0, and it performs no type checking whatsoever.

**Show me**

```ts
// strip.ts, run as: node strip.ts
const a: number       = 1;
interface Gone { x: string }
type Also = { y: number };
function f(v: Map<string, number>): void { throw new Error("here"); }
f(new Map());
```

MEASURED OUTPUT. Node prints the offending source line back with the types
blanked, and the column in the trace lands on the real `throw`:

```
strip.ts:4
function f(v                     )       { throw new Error("here"); }
Error: here
    at f (/.../strip.ts:4:50)
```

```ts
// Neither of these can be erased, because both need emitted runtime code.
enum Color { Red, Green }                       // ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX
class C { constructor(private x: number) {} }   // ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX

// tsc catches both at authoring time, but only with the flag on:
//   tsc --noEmit --strict                       -> clean, no diagnostic
//   tsc --noEmit --strict --erasableSyntaxOnly  -> TS1294 on each
```

MEASURED: both raised `SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]`, with
messages "TypeScript enum is not supported in strip-only mode" and "TypeScript
parameter property is not supported in strip-only mode". `tsc` emitted
`error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.`
for each, and emitted nothing without the flag.

**Why it matters**

Dropping the build step is the whole appeal, and it quietly relocates two
guarantees. There is no type check left in the pipeline unless you still run
`tsc` somewhere, so `node app.ts` will happily execute code that does not
typecheck. And the unsupported-syntax failure is a *startup crash* in whatever
environment first runs the file without a transpiler, which makes it a
deploy-time discovery unless `erasableSyntaxOnly` (TypeScript 5.8 and later) is
on in the config that your editor and your CI both read. That is the antipattern
in one line: the `enum` your teammate adds is legal TypeScript, passes `tsc`, and
takes the service down on boot.

**Chew on this**

If your service runs `.ts` directly, what in your pipeline still fails the build
on a type error, and would you notice today if that step were silently skipped?
Given that the erasure is positional, what does that imply about the one thing a
type annotation can still change about the emitted JavaScript?

**Sources**

- https://nodejs.org/api/typescript.html
- https://nodejs.org/api/errors.html#err_unsupported_typescript_syntax
- https://www.typescriptlang.org/tsconfig/#erasableSyntaxOnly
- https://github.com/nodejs/node/blob/main/doc/api/typescript.md

**Verified**

The whitespace-blanking trace, the two `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`
failures and the TS1294 pair were run here on Node 22.17.1 (with
`--experimental-strip-types`, which that version still requires) and tsc 6.0.3.
The Node 26.0.0 removal of `--experimental-transform-types` and the
v25.2.0 / v24.12.0 stabilization are quoted from the nodejs.org history table,
not reproduced, since this host runs Node 22.

**Related**

- [2026-09-18](2026-09-18.md) - TypeScript, "A gap of 1024 turns your array into
  a hash table, and the type still says number[]". The same divergence between
  what the annotation claims and what the runtime does with it.

# The functional angle: all four languages let a closure outlive what it captured, and only one of them lets it dangle

Draws on today's C++ tip, which is entirely about what a capture list actually
stores, and on the F# tip, which is about what wrapping a value costs. The shape
is the smallest interesting closure there is: build one over a local, return it,
call it after the local is gone.

C++ is the baseline here, not because it is the odd one out but because it is
the only one of the four where the *capture mode is written down by the
programmer* and can therefore be written down wrongly.

```cpp
// C++: [=] over a member captures `this` by pointer, not the member by value.
struct Widget { int n = 7; std::function<int()> make() { return [=] { return n; }; } };
// ASan: stack-use-after-scope, READ of size 4, in the lambda's operator()
```

```rust
// Rust: the borrow checker refuses before you can run it. Note that the
// diagnostic names `w.n`, not `w` -- edition 2021 captures disjoint fields.
fn make() -> Box<dyn Fn() -> u32> {
    let w = Widget { n: 7 };
    Box::new(|| w.n)        // error[E0373]: closure may outlive the current
}                           // function, but it borrows `w.n`
// Box::new(move || w.n)    // compiles, prints 7: the closure OWNS w
```

```fsharp
// F#: no capture syntax exists, and no lifetime error is possible. The CLR
// lifts `w` into a heap display class, so the closure cannot outlive it.
let make () : unit -> int =
    let w = { n = 7 }
    fun () -> w.n
printfn "%d" (make () ())        // 7
```

```ts
// TS/JS: captures the BINDING, not the value. Nothing dangles, but the closure
// sees writes that happened after it was built.
function make() { let n = 7; const f = () => n; n = 99; return f; }
make()();                        // 99, not 7
// And the loop case, which is the same fact wearing a hat:
for (let i = 0; i < 3; i++) withLet.push(() => i);   // [0, 1, 2]
for (var j = 0; j < 3; j++) withVar.push(() => j);   // [3, 3, 3]
```

| Language | What "capture" stores | Measured | What it costs |
| --- | --- | --- | --- |
| C++ | whatever the capture list says; `[=]` over a member stores `this`, a raw pointer | ASan `stack-use-after-scope` at the call | correctness. `[=, this]` or `[*this]` are silent; a deprecation warning is the only guard, and only since C++20 |
| Rust | the fields actually used, by the weakest mode that works; `move` forces ownership | `error[E0373]` naming `w.n` | nothing at runtime. You pay by having to decide `move` or not, and the decision is in the type |
| F# | a compiler-generated heap object holding the captured values | 24 bytes per iteration for a record capture; ~0 for a bare `int`, because escape analysis erased it | an allocation per closure, in principle. In practice the optimizer often takes it back, which makes it unpredictable rather than free |
| TypeScript | a reference to the enclosing binding, per `let` iteration or once per `var` | `99` instead of `7`; `[3,3,3]` for `var` | nothing dangles, and nothing is a snapshot either. Immutability is the only way to make a capture mean what it looks like |

The asymmetry worth keeping is not "Rust is safe". It is that **C++ is the only
one of the four that asks you to name the capture mode, and the shorthand
everybody types names the wrong one.** `[=]` is spelled as a by-value default
and behaves as by-pointer for the members you most want to read. Rust removed
the question by inferring the mode and putting the failure in the type system;
F# and TypeScript removed it by making the environment reachable forever.

Immutability outranks purity here, and TypeScript is where you can see it: its
closure is not wrong so much as *not a snapshot*, and the only fix that makes
`() => n` mean 7 forever is never writing to `n`. F# gets that for free by
default and needed `let mutable` only to hold the benchmark's sink, which is the
measurement's problem rather than the shape's.

Left hanging: `[*this]` copies the whole object, which is the honest
by-value capture and also a copy constructor call you did not write. On a type
with a `vector` member, in a lambda built per request, which of the two bugs
would you rather have - and how would you notice the second one?

# The security angle: every guard in today's four tips is a compile-time guard, and three of the four have an off switch

Mode B, interrogating all four of today's tips at once, and it runs in the
"what does it still let through" direction. Each tip is about a rule the
compiler enforces. The question none of them asked is what happens to the rule
at runtime, and who can turn it off before then.

Rust's orphan rule is the control for this section, because it is the only one
of the four with no flag, no standard-version dependency and no runtime
component: coherence is checked on every build, an `#[fundamental]` you cannot
write means you cannot widen it, and there is nothing left to enforce once the
binary exists. That makes the other three legible as degrees of erosion.

**C++: the guard is a warning, and the standard version chooses whether it
fires.** The dangling capture from today's tip is CWE-416, and it is real -
ASan reported `stack-use-after-scope` on it. But:

```cpp
struct Session { std::string token; std::function<bool()> authz() { return [=] { return !token.empty(); } }; };
// A per-request authorization callback, capturing `this` by pointer. If the
// Session is pooled, reset, or destroyed while a queued callback still holds
// it, the check reads freed memory and answers from whatever is there now.
```

Compiled at `-std=c++17`: silent, at every warning level tried. At
`-std=c++20`: one deprecation warning, on by default - which `-std=c++17`,
`-Wno-deprecated-this-capture`, or `-Wno-error` each switch back off. A
diagnostic that a build flag can retire is not a guarantee, and the flag that
retires it is the same one a team reaches for to make a GCC 16 upgrade go green.

**TypeScript: the guard is gone at runtime by design, and the tool that
enforces it is optional.** Today's tip is the mechanism: annotations are
overwritten with spaces, and `node app.ts` type-checks nothing. So this passes:

```ts
// The annotation is the ONLY thing asserting shape here. Under `node app.ts`
// it is whitespace, and `role` is whatever the request body said.
const claims = JSON.parse(body) as { sub: string; role: "admin" | "user" };
if (claims.role === "admin") grantEverything(claims.sub);
```

CWE-704 (incorrect type conversion) composed with CWE-20. The `as` is a grant of
trust with no code behind it, and unlike a bad cast in C++ there is not even a
runtime representation to disagree with. The fix is a decode step that exists at
runtime - `Schema.decodeUnknownSync` in Effect, or any real parser - and the
thing to check is whether `tsc` still runs anywhere in your pipeline at all.

**F#: `None` is literally `null`, so the non-nullness is a compile-time story
that stops at the CLR boundary.** This one came out of today's F# measurement
rather than its headline:

```fsharp
printfn "%b" (isNull (box (None: int option)))               // true
printfn "%b" (box (null: obj) :?> int option |> Option.isNone) // true
```

MEASURED, both true. A `null` handed across from C#, VB, or any reflection or
deserialization path unboxes cleanly to `None` - which is benign for an option,
and is exactly why the opposite direction bites: a plain `string` parameter from
a .NET library is nullable and F# will let you use it as though it were not.
CWE-476. F# 9's nullable reference types make that checkable, and only when the
flag is on.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | nothing here. Coherence is unconditional and has no runtime half | rejects the impl on every build; `#[fundamental]` is closed to your crate | choosing `Box` over `Arc` in a public signature, which is a permanent coherence decision, not a security one |

# FAQ

**Does the `#[fundamental]` rule apply to `dyn Trait` or to slices?**

Different mechanism. `&dyn Trait` and `&[Local]` are references, so the `&` is
doing the work. A bare `[Local]` or `dyn MyTrait` is not wrapped in anything
fundamental, so the ordinary orphan clauses decide. Not measured today.

**Is `-Wdeprecated-this-capture` an error anywhere by default?**

No. It is a warning in clang 21 at `-std=c++20` and later, and P0806R2 deprecated
the construct rather than removing it, so no conforming compiler may reject it.
Making it fail is `-Werror=deprecated-this-capture`, which you have to ask for.

**Does `voption` work with `Option.map`, `Option.bind`, and the rest?**

No. `ValueOption` has its own module (`ValueOption.map`, `ValueOption.bind`),
and the two do not interconvert implicitly. That is most of the reason it stays
unused despite being eight years old.

**If Node strips types with whitespace, can a type annotation ever change the
emitted JavaScript?**

Under strip-only mode, only by being unsupported syntax and refusing to run.
That is the whole point of `erasableSyntaxOnly`: it makes "legal TypeScript" and
"erasable TypeScript" the same set, so your editor rejects what Node would.

**Which `-std=` does Apple clang 21 default to?**

Not established today. Every C++ measurement above passed `-std=` explicitly, so
none of the results depend on the answer - and that is the tip's advice applied
to its own evidence.
