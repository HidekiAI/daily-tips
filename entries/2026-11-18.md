## Rust: clone_from reuses the buffers that a = b.clone() throws away, and derive(Clone) never writes it, so a derived struct allocated 10,200 times where a hand-written one allocated 0

*Perf and memory model*

**Did you know**

`Clone::clone_from` has a default body of `*self = source.clone()`, and `Vec` and `String` override it to copy into the allocation the destination already owns. Measured on rustc 1.100.0 with a counting global allocator: refreshing a 1,000-element `Vec<u64>` 100 times cost 100 allocations as `target = source.clone()` and 0 as `target.clone_from(&source)`; for a `Vec<String>` of 100 names it was 10,100 against 0, because the `Vec` override calls `clone_from` on every `String` inside it. `#[derive(Clone)]` writes only `clone`, though, so a struct holding those same two vectors keeps the default `clone_from` and allocated 10,200 times over 100 refreshes, while a hand-written `clone_from` that forwards field by field allocated 0.

**Show me**

```rust
// Rust 1.100.0, edition 2024. Counts came from a counting #[global_allocator].
#[derive(Clone)]
pub struct DerivedSnapshot {
    pub names: Vec<String>,
    pub scores: Vec<u64>,
}

pub struct HandSnapshot {
    pub names: Vec<String>,
    pub scores: Vec<u64>,
}

impl Clone for HandSnapshot {
    fn clone(&self) -> Self {
        HandSnapshot { names: self.names.clone(), scores: self.scores.clone() }
    }
    // The derive never writes this method, so DerivedSnapshot keeps the default
    // body, *self = source.clone(): fresh buffers in, old buffers freed.
    fn clone_from(&mut self, source: &Self) {
        self.names.clone_from(&source.names); // reuses the Vec and each String in it
        self.scores.clone_from(&source.scores); // reuses the Vec<u64> buffer
    }
}

// 100 names and 1,000 scores, refreshed 100 times:
pub fn refresh(derived_target: &mut DerivedSnapshot, derived_source: &DerivedSnapshot,
               hand_target: &mut HandSnapshot, hand_source: &HandSnapshot) {
    derived_target.clone_from(derived_source); // 10,200 allocations over the 100 rounds
    hand_target.clone_from(hand_source); // 0 allocations over the 100 rounds
}
```

**Why it matters**

The usual long-running-server shape is a snapshot refreshed on a timer (a routing table, a config, a leaderboard), and both ways people write it, `current = latest.clone()` and `current.clone_from(&latest)` on a derived type, pay one allocation per vector and per string on every refresh. C++ gets this for free in the opposite direction: a defaulted copy assignment forwards to each member, so `target = source` on the same struct of `std::vector<std::string>` and `std::vector<unsigned long>` allocated 0 times over 100 rounds on GCC 16.2.0 and Debian clang 19.1.7, while `target = Snapshot(source)` allocated 10,200, the exact Rust figure. In Rust the reuse is opt-in per type and the derive opts out; in C++ it is the default and only a temporary opts out. F# and TypeScript have no in-place counterpart at all: an immutable record copy or an object spread is always a new allocation.

**Chew on this**

Which of your refreshed structs derive `Clone` today, and how many `String` fields does each one hold? And if something else still borrows or shares the old snapshot, is reusing its buffer what you want, or is the fresh allocation the point?

**Sources**

- https://doc.rust-lang.org/std/clone/trait.Clone.html#method.clone_from
- https://doc.rust-lang.org/std/clone/trait.Clone.html#derivable

**Gotchas**

- `clone()` copies the length, not the capacity: a `Vec<u64>` with capacity 4,096 and one element cloned to capacity 1.
- `clone_from` from a shorter source keeps the destination capacity: after copying a 10-element source into a 4,096-element `Vec<u64>`, capacity stayed 4,096 with length 10, so a snapshot that once grew large keeps that memory.
- `clone_from` from a longer source still allocates: growing a 10-element `Vec<u64>` to 1,000 took 1 allocation.
- Clippy 0.1.100 has a lint for the assignment form, `assigning_clones` ("assigning the result of `Clone::clone()` may be inefficient"), and it is not on by default: it fired only with `-W clippy::assigning_clones`.

## C++: C++26 std::indirect is a heap box with value semantics, so == compares the values and const reaches through, and a moved-from one segfaulted with _GLIBCXX_ASSERTIONS on

*New discoveries and currently popular patterns*

**Did you know**

P3019R14, voted into C++26, adds `std::indirect<T>` and `std::polymorphic<T>` to `<memory>`: an owning heap pointer that behaves like the value it holds. A copy is a deep copy, `==` compares the owned values (true for two separate `Widget{{1, 2, 3}}` boxes, where two `std::unique_ptr` to equal widgets compare false), and const propagates, so `frozen->cells.push_back(7)` on a `const std::indirect<Widget>` is a compile error while the same line through a `const std::unique_ptr<Widget>` compiles. The only empty state is moved-from, which `valueless_after_move()` reports and `operator*` does not check: dereferencing it segfaulted (exit 139) at `-O0` with `-D_GLIBCXX_ASSERTIONS` and at `-O2` without. Support state, checked here: GCC 16 libstdc++ only (16.2.0, library stamped 20260807, `__cpp_lib_indirect` and `__cpp_lib_polymorphic` both `202502`, and only under `-std=c++26`); Debian clang 19.1.7 rejects it with both libstdc++ 14 and libc++ 19, and cppreference lists Clang libc++ and the MSVC STL as not yet shipping it.

**Show me**

```cpp
// C++26 (-std=c++26), GCC 16.2.0. Not in Clang libc++ or the MSVC STL yet.
#include <cstdio>
#include <memory>
#include <utility>
#include <vector>

struct Widget {
    std::vector<int> cells;
    bool operator==(const Widget&) const = default;
};

int main() {
    std::indirect<Widget> original{Widget{{1, 2, 3}}};
    std::indirect<Widget> copied = original; // deep copy: a second heap Widget
    copied->cells.push_back(4); // original still has 3 cells

    std::indirect<Widget> same_value{Widget{{1, 2, 3}}};
    bool equal = (original == same_value); // true: compares Widgets, not addresses

    const std::indirect<Widget> frozen{Widget{}};
    // frozen->cells.push_back(7); // error: const reaches the Widget
    const std::unique_ptr<Widget> pointer = std::make_unique<Widget>();
    pointer->cells.push_back(7); // compiles: const stops at the pointer

    std::indirect<Widget> moved_to = std::move(original);
    if (original.valueless_after_move()) { // the only empty state, and only you check it
        std::puts("original is valueless");
    }
    // original->cells.size(); // UB: segfaulted (exit 139), _GLIBCXX_ASSERTIONS or not
    std::printf("%zu %zu %d\n", copied->cells.size(), moved_to->cells.size(), equal);
}
```

It printed `original is valueless` and `4 3 1` on GCC 16.2.0.

**Why it matters**

The pimpl idiom and the big-payload value object are where this lands: a `std::unique_ptr` member deletes the implicit copy constructor, leaks mutability through `const` member functions, and makes `operator==` compare addresses, and `std::indirect` fixes all three with no hand-written special members. The price is that every copy is an allocation plus a deep copy, with no sharing. Rust has had this type all along: `Box<T>` clones deeply, `==` on two boxes compares contents, a shared reference to a `Box<T>` gives only shared access to the `T`, and the moved-from state cannot be touched at all, because using a moved value is compile error E0382 instead of a runtime flag. In F# a record already has structural equality and immutability by default, and TypeScript has no counterpart: an object is a reference and `===` is identity.

**Chew on this**

Which of your classes delete their copy constructor only because a `std::unique_ptr` member forced it? And on the day a moved-from `std::indirect` reaches a logging call in an error path, which line of yours is the one that checks `valueless_after_move()`?

- https://en.cppreference.com/w/cpp/memory/indirect/operator*
- https://en.cppreference.com/w/cpp/compiler_support/26

**Verified**

The libc++ and MSVC STL support state rests on the cppreference table; only GCC 16.2.0 and Debian clang 19.1.7 were run.

**Gotchas**

- `sizeof(std::indirect<Widget>)` is 8 on libstdc++, the same as `std::unique_ptr<Widget>`, and `sizeof(std::polymorphic<Shape>)` is 8 too, not a two-pointer type.
- On GCC 16 with `-std=c++23` the error is `'indirect' is not a member of 'std'`; the type needs `-std=c++26` (or `c++2c`).
- `std::polymorphic<Shape>` copies the derived object, not the base: a copy of one holding a `Square` of side 2.0 still reported area 4.0.
- `_GLIBCXX_ASSERTIONS` does not cover a valueless `std::indirect`: the run ended in a segfault, not an assertion message, and cppreference notes the operator "does not check" for that state.

## F#: Option.defaultValue runs its fallback even on Some, so defaultValue (failwith "PORT is required") throws when the port is set

*Idioms and antipatterns*

**Did you know**

F# evaluates arguments before the call, and `Option.defaultValue` is an ordinary function, so its fallback runs before it ever looks at the option. Measured with `dotnet fsi` on F# 10 (SDK 10.0.404, FSharp.Core assembly 10.1.0.0, .NET 10.0.15): `Some 9000 |> Option.defaultValue (load_default_port ())` called `load_default_port` once, `Option.defaultValue (failwith "PORT is required")` threw on `Some 9000`, and a cache read written as `Map.tryFind |> Option.defaultValue (compute_score ...)` recomputed on all 1,000 of 1,000 hits. `Option.defaultWith` takes the function itself and called it 0 times. Being `inline` does not change this: FSharp.Core defines it as `let inline defaultValue value option = match option with None -> value | Some v -> v`, and the argument is still evaluated first.

**Show me**

```fsharp
// F# 10, .NET 10.0.15 (SDK 10.0.404). Run with: dotnet fsi show.fsx
let mutable mut_load_calls = 0
let load_default_port () =
    mut_load_calls <- mut_load_calls + 1
    8080

let configured_port : int option = Some 9000

// Eager: load_default_port () runs before defaultValue looks at the Some.
let port_value = configured_port |> Option.defaultValue (load_default_port ()) // 1 call

// Lazy: defaultWith takes the function itself and calls it only on None.
let port_with = configured_port |> Option.defaultWith load_default_port // 0 more calls

// Reads like a guard and throws on every call, Some 9000 included.
let read_required_port () =
    configured_port |> Option.defaultValue (failwith "PORT is required")

// A cache that saves nothing: compute_score runs on every one of 1,000 hits.
let mutable mut_compute_calls = 0
let compute_score (player: string) =
    mut_compute_calls <- mut_compute_calls + 1
    player.Length * 10
let score_cache = Map.ofList [ ("ada", 30) ]
for _ in 1 .. 1000 do
    score_cache |> Map.tryFind "ada" |> Option.defaultValue (compute_score "ada") |> ignore

printfn "port %d %d, load calls %d, compute calls %d" port_value port_with mut_load_calls mut_compute_calls
```

It printed `port 9000 9000, load calls 1, compute calls 1000`.

**Why it matters**

The pipeline reads like a lazy fallback, so the cost hides in plain sight: a cache whose miss path is a database read does that read on every hit, and a "required setting" guard written with `failwith` takes the service down at startup even when the setting is present. The same split exists everywhere, spelled differently: Rust has `unwrap_or` (eager) and `unwrap_or_else` (lazy), C++ has only the eager `value_or` plus a C++23 `or_else` that returns another `optional`, and TypeScript `??` is an operator, so its right side runs only when the left is `null` or `undefined`.

**Chew on this**

Where in your code does a fallback have a side effect, a log line, a metric, a lookup, that now fires on the happy path too? And would anyone reviewing `defaultValue (load ())` against `defaultWith load` notice the difference?

**Sources**

- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/option.fs
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/options

**Verified**

Run in the Ubuntu 24.04 based `mcr.microsoft.com/dotnet/sdk:10.0` image, since there is no Debian .NET SDK image.

**Gotchas**

- `defaultArg`, the older spelling, is just as eager: `defaultArg (Some 9000) (load_default_port ())` made 1 call.
- `Option.orElse (Some (load_default_port ()))` is eager too: 1 call on `Some 9000`.
- `Result.defaultValue` has the same shape: `Ok 5 |> Result.defaultValue (load_default_port ())` made 1 call.
- A `lazy` value passed as `Option.defaultWith lazy_default.Force` ran 0 times on `Some`.

## TypeScript: A spread of Partial<T> types an explicit undefined as the default it erased, so require_mfa true became undefined under --strict, and only exactOptionalPropertyTypes refuses it

*Type system deep cuts*

**Did you know**

Under `--strict`, an optional property `require_mfa?: boolean` also accepts an explicit `undefined`, and tsc types `{ ...defaults, ...overrides }` as if an optional key is either missing or holds a `boolean`. At runtime a key that is present with the value `undefined` overwrites the default. Measured on tsc 7.0.2 and Node 26.13.1: `merge_config({ port: 9000, require_mfa: read_flag({}) })` compiled with exit 0, the result was typed `boolean`, and it printed `undefined`. `--exactOptionalPropertyTypes` (TypeScript 4.4 and later, not part of `--strict`) makes the same call fail with TS2379, "not assignable to parameter of type `Partial<ServerConfig>` with `exactOptionalPropertyTypes: true`".

**Show me**

```ts
// TypeScript 7.0.2, --strict. Node 26.13.1 runs the file directly.
interface ServerConfig {
    port: number
    require_mfa: boolean
}
const defaults: ServerConfig = { port: 8080, require_mfa: true }

function merge_config(overrides: Partial<ServerConfig>): ServerConfig {
    // Typed ServerConfig: tsc treats an optional key as missing or a boolean.
    return { ...defaults, ...overrides }
}

// A form reader that writes every key, present in the form or not.
function read_flag(form: Record<string, string>): boolean | undefined {
    return form["require_mfa"] === undefined ? undefined : form["require_mfa"] === "on"
}

const merged = merge_config({ port: 9000, require_mfa: read_flag({}) })
// --strict: accepted, exit 0. --exactOptionalPropertyTypes: TS2379 on that call.
const mfa_flag: boolean = merged.require_mfa // the type says boolean
console.log(mfa_flag) // prints undefined: the true default is gone
```

**Why it matters**

Settings merges are where this lives: defaults in code, overrides from a form, a query string or a mapper that writes every key whether the input had it or not, and the merged object then gates behaviour with a type that promises a `boolean`. The secure default is the one that disappears, and nothing in the type says so. Rust struct update syntax cannot express it, because a `bool` field has no absent value and an override has to be an `Option<bool>` that someone resolves; F# `{ defaults with ... }` is the same, every unnamed field keeps its default. C++ designated initializers fail the other way: a field you leave out is reset rather than kept.

**Chew on this**

How many of your `Partial<...>` parameters are filled by code that copies every key, present or not? And if you turned on `exactOptionalPropertyTypes` tomorrow, would you fix the call sites, or add `| undefined` to the types until it went quiet?

**Sources**

- https://www.typescriptlang.org/tsconfig/#exactOptionalPropertyTypes
- https://www.typescriptlang.org/docs/handbook/utility-types.html#partialtype

**Gotchas**

- `"require_mfa" in overrides` is `true` for an explicit `undefined`, so an `in` check for "was it set?" agrees with the bug.
- `Object.assign({}, defaults, overrides)` behaves the same: `require_mfa` came out `undefined`.
- With the flag on, writing the overrides with `as Partial<ServerConfig>` still compiled: the flag checks assignments, and a type assertion goes around it.
- Declaring the overrides as `?: T | undefined` on purpose changes nothing under `--strict` (the spread still returns `ServerConfig` with exit 0); only with `--exactOptionalPropertyTypes` does tsc report TS2322 on the return. Without the flag, tsc cannot tell the two declarations apart.

# The functional angle: a default is either a value or a function, and only the function form waits to see whether it is needed

Draws on the F# tip, with TypeScript `??` from the TypeScript tip as the odd one out. All four languages are strict, so a fallback written as a value is computed before the call; laziness has to be spelled as a function, and three of the four make the eager spelling the shorter one.

Rust has the same pair as F#, and the counting closure shows the one asymmetry worth noticing: the lazy form takes `FnOnce`, so a closure that counts its own calls has to be passed as `&mut`, while the eager form just calls it.

```rust
// Rust 1.100.0, edition 2024
fn main() {
    let mut mut_load_calls = 0;
    let mut mut_fn_load_default_port = || {
        mut_load_calls += 1;
        8080
    };
    let configured_port: Option<u16> = Some(9000);
    let eager_port = configured_port.unwrap_or(mut_fn_load_default_port()); // runs the closure
    let lazy_port = configured_port.unwrap_or_else(&mut mut_fn_load_default_port); // does not
    println!("unwrap_or {eager_port}, unwrap_or_else {lazy_port}, load calls {mut_load_calls}");
}
```

C++ has no lazy `value_or`. The nearest is the C++23 monadic `or_else`, which takes a function but returns another `std::optional`, so the lazy version is one dereference longer:

```cpp
// C++23 (-std=c++23), GCC 16.2.0 and Debian clang 19.1.7
#include <cstdio>
#include <optional>

int load_calls = 0;
int load_default_port() {
    ++load_calls;
    return 8080;
}

int main() {
    const std::optional<int> const_configured_port = 9000;
    const int const_eager_port = const_configured_port.value_or(load_default_port()); // runs it
    const std::optional<int> const_lazy_port = const_configured_port.or_else(
        [] { return std::optional<int>{load_default_port()}; }); // does not
    std::printf("value_or %d, or_else %d, load calls %d\n", const_eager_port, *const_lazy_port, load_calls);
}
```

| Language | Eager form | Lazy form | Fallback calls with a value present (eager / lazy) |
| --- | --- | --- | --- |
| F# | `Option.defaultValue x` | `Option.defaultWith f` | 1 / 0 |
| Rust | `unwrap_or(x)` | `unwrap_or_else(f)` | 1 / 0 |
| C++ | `value_or(x)` | `or_else(f)` (C++23), returns `optional` | 1 / 0, GCC 16.2.0 and Debian clang 19.1.7 |
| TypeScript | none built in | `a ?? b`, an operator | not applicable / 0 |

TypeScript is the only one where the short spelling is the lazy one, because `??` is syntax rather than a function, so its right side is never an argument. Nothing in the other three warns by default: Rust Clippy 0.1.100 has `or_fun_call` for `unwrap_or(f())`, and it fired only with `-W clippy::or_fun_call`.

If the lazy form is always at least as correct, what is it about a closure in a hot path that still makes the eager spelling the one people reach for?

# The security angle: an absent field that arrives as undefined switches a secure default off, and the type still says it is on

Draws on the TypeScript tip and runs in the "the language does not stop it" direction. Rust is the control for this class, because its type for the merged config has no way to hold "absent" in a `bool`. The class is CWE-636, not failing securely: when the input is missing, the check falls back to the permissive branch.

The insecure TypeScript version looks like ordinary settings code and compiles under `--strict`:

```ts
// TypeScript 7.0.2, --strict: compiles with no error.
interface ServerConfig {
    port: number
    require_mfa: boolean
}
const defaults: ServerConfig = { port: 8080, require_mfa: true }
const merge_config = (overrides: Partial<ServerConfig>): ServerConfig => ({ ...defaults, ...overrides })

function login_steps(config: ServerConfig): string[] {
    // Reads as "MFA unless someone turned it off". An absent form field turns it off.
    return config.require_mfa ? ["password", "totp"] : ["password"]
}

const request_body: { require_mfa?: string } = {}
const config = merge_config({
    require_mfa: request_body.require_mfa === undefined ? undefined : request_body.require_mfa === "on",
})
console.log(login_steps(config)) // [ 'password' ]: MFA is off

// Fails closed: only an explicit false turns MFA off, so undefined keeps it on.
const fn_requires_mfa = (merged: ServerConfig): boolean => merged.require_mfa !== false
console.log(fn_requires_mfa(config)) // true
```

It printed `[ 'password' ]` (no TOTP step) and then `true` for the fail-closed check. The Rust shape cannot reach the first result without someone writing the wrong default on purpose, because the override is an `Option<bool>` and the merge has to say what `None` means:

```rust
#[derive(Clone, Debug)]
struct ServerConfig {
    port: u16,
    require_mfa: bool,
}

struct Overrides {
    port: Option<u16>,
    require_mfa: Option<bool>,
}

fn merge_config(defaults: &ServerConfig, overrides: &Overrides) -> ServerConfig {
    ServerConfig {
        port: overrides.port.unwrap_or(defaults.port),
        require_mfa: overrides.require_mfa.unwrap_or(defaults.require_mfa),
    }
}

fn main() {
    let defaults = ServerConfig { port: 8080, require_mfa: true };
    let merged = merge_config(&defaults, &Overrides { port: Some(9000), require_mfa: None });
    println!("{merged:?}");
}
```

The Rust version printed `ServerConfig { port: 9000, require_mfa: true }`.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | an explicit `undefined` in a `Partial` override erases `require_mfa: true`, still typed `boolean` | nothing under `--strict`; TS2379 with `--exactOptionalPropertyTypes`; an `as` cast goes around even that | turn the flag on, no casts on overrides, and gate with `!== false` so a missing value fails closed |
| Rust | an `Option<bool>` override arrives as `None` | a `bool` field cannot be absent, so the merge must resolve `None` explicitly (`unwrap_or(defaults.require_mfa)` kept `true`) | decide once, in the merge, what `None` means |
| F# | a `{ defaults with ... }` update from a `bool option` override | unnamed fields keep their values, and a `bool` has no `undefined` | the same `None` decision as Rust; not measured today |
| C++ | a designated initializer that leaves the flag out | a left-out field is reset, not kept ([the 2026-10-27 tip](2026-10-27-extra-10-of-12.md)) | name every security field, or give it a `true` default member initializer; not measured today |

Which of your access checks read a flag that came through a merge, and what does each one do on the day that flag arrives missing?
