# Daily Tips special, part 1 of 4: timestamps, or how Jan 31 plus one month becomes four different days

_Special edition, written 2026-10-21 beside that day's entry. One topic across all four languages instead of the rotation: instants, calendar dates, wall-clock readings, and the arithmetic between them. [Part 2](2026-10-21-extra-2-of-4.md) covers cron schedules, epoch rollovers, ISO 8601 durations and zone IDs, and migrating to JS `Temporal`; [part 3](2026-10-21-extra-3-of-4.md) covers 32-bit millisecond counters, timer delay limits and two-digit years; [part 4](2026-10-22-extra-4-of-4.md) covers zone names, abbreviations and DST flags, RFC 3339 parsing, the `TZ` variable and JWT clock leeway._

**The thesis of this special: an instant, a calendar date and a wall-clock reading are three different things, and every bug below passes one where another was meant.** As in the rounding special, none of these functions is broken. .NET `AddMonths`, JS `setUTCMonth`, C++ `months{1}` and Rust `jiff` `1.month()` each do exactly what their documentation says. The bug is the gap between that and what the caller assumed "one month" meant.

Every value below was printed by the snippet beside it: rustc 1.95.0 with `jiff` 0.2.38 and `chrono` 0.4.45, Apple clang 21 (libc++) and GCC 14.4.0 (libstdc++, Debian 13 container, tzdata 2026c), F# 8 on .NET 8.0.8 (Arm64), Node 22.17.1 with tsc 6.0.3. Local-time examples ran with `TZ=America/Chicago`.

**"Jan 31, 2026 plus one month":**

| Library | `+1 month` | `+1 month` twice | `+2 months` |
| --- | --- | --- | --- |
| Rust `jiff` / `chrono` | 2026-02-28 (clamp) | 2026-03-28 | 2026-03-31 |
| C++ `year_month_day + months{1}` | **2026-02-31**, `ok()` is false | 2026-03-31 | 2026-03-31 |
| C++ `sys_days + months{1}` | **2026-03-02 10:29:06** | n/a | n/a |
| .NET `AddMonths` | 2026-02-28 (clamp) | 2026-03-28 | 2026-03-31 |
| JS `setUTCMonth(m + 1)` | **2026-03-03** (overflow) | n/a | n/a |

**A wall time that does not exist (2026-03-08 02:30) and one that exists twice (2026-11-01 01:30), America/Chicago:**

| Library | Gap 02:30 | Overlap 01:30 |
| --- | --- | --- |
| Rust `jiff` `to_zoned` | 03:30 CDT, silently (`unambiguous()` is `Err`) | 01:30 CDT (06:30Z, the first one) |
| C++ `time_zone::to_sys` (GCC 14) | throws `nonexistent_local_time`; `choose::earliest` gives **03:00** CDT | throws `ambiguous_local_time` |
| .NET `TimeZoneInfo.ConvertTimeToUtc` | throws `ArgumentException` | 01:30 **CST** (07:30Z, the second one) |
| JS `new Date("...T02:30")` | 03:30 CDT, silently | 01:30 CDT (06:30Z, the first one) |

Four libraries, three answers for the gap, two for the overlap, and only two of them tell you a choice was made.

## Rust: std has two clocks and no calendar, and in `jiff` one day is not 24 hours

_Stdlib and ecosystem gems_

**Did you know**

`std::time` has exactly two clocks and no calendar at all. `SystemTime` is the wall clock, so `duration_since` returns a `Result`: the earlier reading can be later, and `now.duration_since(now + 5s)` is `Err(SystemTimeError(5s))`. `Instant` is monotonic, and since Rust 1.60 a reversed `duration_since` saturates to `0ns` instead of panicking. Months, days and time zones live in crates. In `jiff` 0.2.38, `1.day()` is a calendar day and `24.hours()` is 24 hours, so across the 23-hour spring-forward day they land an hour apart.

**A caveat that belongs on every Rust crate claim:** Rust and its ecosystem are still moving fast. `jiff` is pre-1.0 (0.2.38 measured here) and `chrono` has sat at 0.4.x for years, so by the time you read this either may have changed its API, been superseded, or become the legacy choice. Treat the crate names as "what was current on 2026-10-21" and check crates.io before you adopt one.

**Show me**

```rust
// Cargo.toml: jiff = "0.2.38" (measured version; pre-1.0, so check what it is today)
use jiff::{civil::date, tz::TimeZone, ToSpan};
use std::time::{Duration, Instant, SystemTime};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // std has two clocks and no calendar. SystemTime is the wall clock, so going
    // "backwards" is a real outcome (NTP step, manual set) and the API says so.
    let now = SystemTime::now();
    let later = now + Duration::from_secs(5);
    assert!(now.duration_since(later).is_err()); // Err(SystemTimeError(5s))

    // Instant is monotonic; a reversed subtraction saturates to zero (it panicked before 1.60).
    let started = Instant::now();
    assert_eq!(started.duration_since(Instant::now()), Duration::ZERO);

    // Calendar units live in crates. In jiff, days are calendar days and hours are hours:
    let chicago = TimeZone::get("America/Chicago")?;
    let saturday_noon = date(2026, 3, 7).at(12, 0, 0, 0).to_zoned(chicago.clone())?;
    let next_day = saturday_noon.checked_add(1.day())?;   // 2026-03-08T12:00:00-05:00
    let plus_24h = saturday_noon.checked_add(24.hours())?; // 2026-03-08T13:00:00-05:00
    assert_ne!(next_day, plus_24h); // the 23-hour DST day makes them differ

    // Months clamp, so two single steps are not one double step.
    let jan_31 = date(2026, 1, 31);
    assert_eq!(jan_31.checked_add(1.month())?.checked_add(1.month())?, date(2026, 3, 28));
    assert_eq!(jan_31.checked_add(2.months())?, date(2026, 3, 31));

    // A nonexistent local time is resolved silently unless you ask for strictness.
    let in_gap = date(2026, 3, 8).at(2, 30, 0, 0);
    assert_eq!(in_gap.to_zoned(chicago.clone())?.to_string(), "2026-03-08T03:30:00-05:00[America/Chicago]");
    assert!(chicago.to_ambiguous_zoned(in_gap).unambiguous().is_err());
    println!("ok");
    Ok(())
}
```

**Why it matters**

A retry deadline computed as `SystemTime::now() + timeout` and checked against `SystemTime::now()` stretches or collapses when NTP steps the clock; the same code on `Instant` cannot. A "run at noon every day" scheduler that adds `24.hours()` drifts to 13:00 after spring-forward, and one that adds `1.day()` does not. Rust is the only one of the four whose std refuses to pretend it has a calendar: C++20 put one in `<chrono>`, .NET has had `DateTime` since 1.0, and JS has `Date` (and `Temporal` from Node 26). Whether that absence is a virtue depends on whether your crate choice outlives the code.

**Chew on this**

Which of your timeouts is computed from `SystemTime`, and what happens to it the day a VM resumes with its clock an hour stale? When your scheduler says "daily", does it mean every 86,400 seconds or every calendar day, and which one did your users assume?

**Verified**

**Gotchas**

- `Duration::from_secs_f64(1e-10)` is `0ns`: sub-nanosecond values truncate to zero without error.
- `chrono::TimeDelta::days(1).num_seconds()` is always 86400. `chrono`'s duration has no calendar day; only `jiff::Span` distinguishes `1.day()` from `24.hours()`.
- `jiff`'s `1.month().total(Unit::Second)` is an `Err` ("requires that a relative reference time be given"): a month has no length until you say which month.
- Leap years disagree across crates: `chrono` `NaiveDate(2024-02-29).with_year(2025)` is `None`, while `jiff` and .NET clamp a year add to Feb 28.
- `jiff::civil::Date::new(2026, 2, 30)` is an `Err` ("must be in range `1..=28`"), yet `to_zoned` on a nonexistent wall time succeeds silently. Strict for dates, lenient for gaps.
- Leap seconds: `chrono` parses `"2016-12-31T23:59:60Z"` and keeps `23:59:60`; `jiff` parses it as `23:59:59`.
- `chrono::DateTime::from_timestamp_millis(1761000000)` is `1970-01-21T09:10:00Z`. Only the method name carries the unit; a seconds value fed to it is a valid January 1970.
- `format("%Y")` on 2024-12-30 prints `2024`, `format("%G-W%V")` prints `2025-W01`. `%G` is the ISO week-year.

## C++: `2026y/January/31 + months{1}` is a valid object holding an invalid date, and `sys_days + months{1}` lands at 10:29:06

_Idioms and antipatterns_

**Did you know**

C++20 `<chrono>` calendar arithmetic does not clamp and does not overflow: `year_month_day + months{1}` keeps the day field, producing `2026-02-31` with `ok() == false`. Because it carries the 31 forward, adding another month gives `2026-03-31`, so in C++ (+1)+(+1) equals +2, the only one of the four where that holds. The caller resolves Feb 31 in one line: `/ last` clamps, `sys_days{...}` rolls to 2026-03-03. The trap is that `months{1}` is also a plain duration of 2,629,746 s (the average Gregorian month, 30.436875 days), so `sys_days{jan_31} + months{1}` compiles and gives `2026-03-02 10:29:06`. The calendar types are C++20 (P0355R7) and work in Apple clang 21. Time zones and the leap-second clocks from the same paper do not: Apple's libc++ ships with `_LIBCPP_HAS_TIME_ZONE_DATABASE 0`, so `locate_zone` and `utc_clock` are undeclared. cppreference lists P0355R7 as complete in GCC 14 and MSVC 19.29, partial in libc++ 19.

**Show me**

```cpp
#include <cassert>
#include <chrono>
#include <iostream>
using namespace std::chrono;

int main() {
    year_month_day jan_31 = 2026y / January / 31;

    // Calendar arithmetic on a year_month_day keeps the day field as-is:
    year_month_day feb_31 = jan_31 + months{1};
    assert(!feb_31.ok());                          // "2026-02-31 is not a valid date"
    assert(feb_31 + months{1} == 2026y / March / 31); // so +1 +1 == +2, unlike every clamp

    // Deciding what Feb 31 means is the caller's job, and both answers are one line:
    year_month_day clamped = feb_31.year() / feb_31.month() / last; // 2026-02-28
    year_month_day rolled = year_month_day{sys_days{feb_31}};      // 2026-03-03
    assert(clamped == 2026y / February / 28 && rolled == 2026y / March / 3);

    // The trap: months{1} is also a duration, the average Gregorian month,
    // so adding it to a time_point compiles and lands mid-morning.
    sys_seconds instant_plus_month = sys_days{jan_31} + months{1};
    std::cout << instant_plus_month << "\n";      // 2026-03-02 10:29:06
    static_assert(duration_cast<seconds>(months{1}).count() == 2'629'746);

    // system_clock can jump; steady_clock cannot. high_resolution_clock is
    // whichever the library picked (steady here on libc++, not guaranteed).
    static_assert(steady_clock::is_steady && !system_clock::is_steady);
}
```

**Why it matters**

"Bill again in one month" written as `next_bill = last_bill + months{1}` on a `sys_seconds` compiles cleanly and moves every billing time by 10 h 29 min 6 s per cycle, so the drift only shows up after a few months of production. On the calendar type the same line yields an invalid date that streams as text and compares unequal to everything valid, which fails loudly the first time someone checks `ok()` and silently if nobody does. .NET and Rust `jiff` clamp and lose the 31st forever; JS overflows into March; C++ keeps the information and makes the decision your problem.

**Chew on this**

Where in your code does a `months` or `years` duration touch a `time_point` rather than a `year_month_day`, and would a reviewer see the difference? If you need "same day next month" for the 31st, is clamping or rolling the rule your business actually wrote down?

- https://en.cppreference.com/w/cpp/chrono/year_month_day/operator_arith_2
- https://en.cppreference.com/w/cpp/chrono/duration (`std::chrono::months`, `years`)
- https://en.cppreference.com/w/cpp/chrono/high_resolution_clock
- https://en.cppreference.com/w/cpp/compiler_support/20 (P0355R7 row)

**Verified**

Compiled and run with Apple clang 21 and GCC 14.4.0 (`-std=c++20 -Wall -Wextra`, both clean, same output). Not checked on MSVC; its support row is from cppreference.

**Gotchas**

- `years{1}` is 31,556,952 s (365.2425 days), so `sys_days + years{1}` drifts too, by 5 h 49 min 12 s from a 365-day year.
- `2024y/February/29 + years{1}` is `2025-02-29` with `ok()` false; .NET and Rust `jiff` would give Feb 28.
- Streaming an invalid date does not throw: it prints `2026-02-31 is not a valid date`, which a log line will happily record as data.
- `high_resolution_clock` is `steady_clock` on libc++ but `system_clock` on libstdc++ 14 (measured with `is_same_v`), so on Linux it can go backwards. Use `steady_clock` for durations.
- `sys_time<nanoseconds>` ends at `2262-04-11 23:47:16.854775807`: signed 64-bit nanoseconds since 1970.
- On a DST gap, `to_sys(gap, choose::earliest)` gives `03:00` CDT (the transition instant), not `03:30` as JS and Rust `jiff` do. Same input, a 30-minute disagreement.
- `utc_clock` is the only std clock that knows leap seconds: across 2016-12-31 it reports a 2 s difference where `sys_clock` reports 1 s, and prints the extra second as `23:59:60` (GCC 14).
- `tai_time - utc_time` does not compile: time points of different clocks cannot be subtracted. `clock_cast` first.

## F#: a UTC noon equals a local noon, because `DateTime` compares ticks and ignores `Kind`

_Idioms and antipatterns_

**Did you know**

.NET has the richest calendar library of the four, and its oldest type still has the sharpest edge: `DateTime` equality and subtraction look only at `Ticks`. The docs say it directly: "Their Kind property values are not considered in the test for equality." So `DateTime(..., Utc) = DateTime(..., Local)` with the same fields is `true` and their difference is `0` hours, although in Chicago they are five hours apart. `DateTimeOffset` carries the offset and compares the instant, so the same pair is unequal. The rest of the library is the reference the others are measured against: `AddMonths` documents its clamp, `DateOnly` and `TimeOnly` split the date from the clock, `TimeZoneInfo.IsInvalidTime` and `IsAmbiguousTime` name the DST cases, and `ISOWeek` does ISO 8601 weeks. Measured on F# 8, FSharp.Core 8.0.0.0, .NET 8.0.8.

**Show me**

```fsharp
open System
open System.Globalization

// Same fields, different Kind: DateTime compares and subtracts the ticks only.
let utc_noon = DateTime(2026, 10, 21, 12, 0, 0, DateTimeKind.Utc)
let local_noon = DateTime(2026, 10, 21, 12, 0, 0, DateTimeKind.Local) // 17:00Z in Chicago
printfn "%b %f" (utc_noon = local_noon) (utc_noon - local_noon).TotalHours // true 0.000000

// DateTimeOffset carries the offset, so the same two readings differ:
printfn "%b" (DateTimeOffset(utc_noon) = DateTimeOffset(local_noon))      // false

// AddMonths clamps to the last day, and a clamp cannot be undone by the next step:
let jan_31 = DateOnly(2026, 1, 31)
printfn "%O %O" (jan_31.AddMonths(1).AddMonths(1)) (jan_31.AddMonths(2))  // 3/28/2026 3/31/2026

// TimeZoneInfo refuses a wall time that never happened, instead of guessing:
let chicago = TimeZoneInfo.FindSystemTimeZoneById "America/Chicago"
let in_gap = DateTime(2026, 3, 8, 2, 30, 0)
printfn "%b" (chicago.IsInvalidTime in_gap)                               // true
let to_utc_checked (zone: TimeZoneInfo) (wall: DateTime) : DateTime option =
    if zone.IsInvalidTime wall || zone.IsAmbiguousTime wall then None
    else Some(TimeZoneInfo.ConvertTimeToUtc(wall, zone))
printfn "%A" (to_utc_checked chicago in_gap)                              // None

// Week numbers: the culture Calendar is not ISO 8601, even with ISO-looking rules.
let new_year_week = DateTime(2024, 12, 30)
let culture_week = CultureInfo.InvariantCulture.Calendar.GetWeekOfYear(new_year_week, CalendarWeekRule.FirstFourDayWeek, DayOfWeek.Monday)
printfn "%d vs %d-W%02d" culture_week (ISOWeek.GetYear new_year_week) (ISOWeek.GetWeekOfYear new_year_week) // 53 vs 2025-W01
```

**Why it matters**

A cache entry stamped `DateTime.UtcNow` and checked against `DateTime.Now` on a host west of UTC compares two numbers in different zones and gets a confident wrong answer, with no `Kind` mismatch reported anywhere. F# structural equality inherits this, so a record holding a `DateTime` can compare equal to one holding a different instant. `DateTimeOffset` closes it for instants and `DateOnly` for dates; the bug lives in code that still passes `DateTime` around because it was the only type in 2002. Rust's `jiff` and C++ `zoned_time` make the zone part of the type; JS `Date` has no Kind at all, because it is always an instant and only its getters are local.

**Chew on this**

How many `DateTime` values in your code base cross a boundary (a database column, a JSON field, a cache key) without anyone knowing which `Kind` they had? If `DateTimeOffset` is strictly more information, what is the one thing it still cannot tell you about a future appointment?

**Gotchas**

- The default `DateTime(y, m, d)` constructor gives `Kind = Unspecified`, and the two conversions read it oppositely: `ToUniversalTime` treats it as local (12:00 becomes 17:00Z) and `ToLocalTime` treats it as UTC (12:00 becomes 07:00-05:00). One value, ten hours apart.
- Subtracting two local midnights across 2026-03-08 gives 24 h; the real day was 23 h (25 h on 2026-11-01). `DateTime` arithmetic is clock-face arithmetic.
- An ambiguous 01:30 on 2026-11-01 converts to `07:30Z` (standard time, the second occurrence). JS and Rust `jiff` pick `06:30Z` (the first).
- `AddYears(1)` on 2024-02-29 gives 2025-02-28; `AddYears(4)` gives 2028-02-29.
- `DateTime.Parse("03/04/2026")` is March 4 under en-US and ja-JP and April 3 under en-GB and de-DE, with no warning.
- `ParseExact("2026-02-30", "yyyy-MM-dd", ...)` throws `FormatException`; V8 accepts the same string as March 2.
- `DateTimeOffset.FromUnixTimeMilliseconds(1761000000)` is `1970-01-21T09:10:00+00:00`, silently; `FromUnixTimeSeconds(1761000000000)` throws `ArgumentOutOfRangeException`. Under-scaling is silent, over-scaling throws.
- `DateTime(2026, 10, 21, 24, 0, 0)` throws: no `24:00`. `TimeOnly(23, 0).AddHours 3.0` is `2:00 AM`, and the day it wrapped (1) only comes back through the `out` overload.
- `DateTime.MaxValue` is `9999-12-31T23:59:59.9999999`: the type ends long before its 64-bit ticks would.

## TypeScript: `new Date("2026-10-31")` is UTC, `"2026-10-31T00:00"` is local, and a comment in parentheses makes it local too

_Idioms and antipatterns_

**Did you know**

The ECMAScript date-time string format reads a date-only string as UTC and a date-time string without an offset as local time, so two spellings of "Halloween midnight" are five hours apart in Chicago. Anything outside that format falls back to an implementation-defined legacy parser, and V8's is generous: it skips parenthesised text, so `"(Halloween) 2026-10-31"` parses, and as a non-ISO string it parses as local. Every field also overflows instead of failing: month 1 is February, `Date.UTC(2026, 1, 30)` and even `new Date("2026-02-30")` are March 2, and Jan 31 plus one `setUTCMonth` is March 3. The site https://jsdate.wtf collects 28 of these; every one quoted below was re-run in Node 22.17.1 rather than copied. `Temporal` fixes most of them and is `undefined` on this host's Node 22; it ships on by default from Node 26 (see Related).

**Show me**

```typescript
// Run with TZ=America/Chicago. Every comment is the printed toISOString().
const iso = (stamp: Date): string => (Number.isNaN(stamp.getTime()) ? "Invalid Date" : stamp.toISOString());

// Date-only ISO is UTC; date-time without an offset is LOCAL; a comment makes it local too.
console.log(iso(new Date("2026-10-31")));              // 2026-10-31T00:00:00.000Z
console.log(iso(new Date("2026-10-31T00:00")));        // 2026-10-31T05:00:00.000Z
console.log(iso(new Date("(Halloween) 2026-10-31")));  // 2026-10-31T05:00:00.000Z

// Months are 0-based and every field overflows instead of failing.
console.log(iso(new Date(Date.UTC(2026, 1, 30))));     // 2026-03-02T00:00:00.000Z (month 1 is Feb)
console.log(iso(new Date("2026-02-30")));              // 2026-03-02T00:00:00.000Z (V8 accepts it)
const jan_31 = new Date(Date.UTC(2026, 0, 31));
jan_31.setUTCMonth(jan_31.getUTCMonth() + 1);          // mutates in place
console.log(iso(jan_31));                              // 2026-03-03T00:00:00.000Z

// The number constructor is milliseconds; a seconds value is silently January 1970.
console.log(iso(new Date(1_761_000_000)));             // 1970-01-21T09:10:00.000Z

// A clamped month add, like .NET and Rust jiff, that never mutates the caller's Date.
const DAY_MS = 86_400_000;
const add_months_clamped = (start: Date, month_count: number): Date => {
    const target_first = new Date(Date.UTC(start.getUTCFullYear(), start.getUTCMonth() + month_count, 1));
    const last_day = new Date(Date.UTC(target_first.getUTCFullYear(), target_first.getUTCMonth() + 1, 0)).getUTCDate();
    target_first.setUTCDate(Math.min(start.getUTCDate(), last_day)); // own fresh Date, safe to mutate
    const time_of_day_ms = ((start.getTime() % DAY_MS) + DAY_MS) % DAY_MS; // % is negative before 1970
    return new Date(target_first.getTime() + time_of_day_ms);
};
console.log(iso(add_months_clamped(new Date(Date.UTC(2026, 0, 31)), 1))); // 2026-02-28T00:00:00.000Z
console.log(typeof (globalThis as { Temporal?: unknown }).Temporal);      // undefined on Node 22
```

**Why it matters**

A date picker that sends `"2026-10-31"` and a server that compares it to `new Date("2026-10-31T00:00")` disagree by the server's UTC offset, so "events on the 31st" silently drops or gains the first or last few hours depending on where the server runs. `Date` never rejects a field, so a form value of February 30 becomes a real March 2 booking instead of a validation error. TypeScript's types see none of this: `new Date(string)` and `new Date(number)` both type-check for any string or number. Rust's `jiff` and .NET `ParseExact` reject Feb 30; C++ represents it and marks it `!ok()`; only JS turns it into a different valid date.

**Chew on this**

Which of your date strings cross the wire without an offset, and do both ends agree on whether that means UTC or local? When `Temporal` lands in your runtime, which `Date` call sites would you migrate first, and how would you find the ones relying on overflow?

- https://tc39.es/ecma262/multipage/numbers-and-dates.html (Date Time String Format, `Date.parse`)

**Gotchas**

- `new Date(2026)` is 2,026 ms after the epoch (`1970-01-01T00:00:02.026Z`); `new Date("2026")` is `2026-01-01T00:00:00.000Z`.
- `new Date(null)` is the epoch; `new Date(undefined)` is Invalid Date.
- Single numbers as strings: `"0"` is 2000-01-01, `"1"` is 2001-01-01, `"12"` is 2001-12-01, `"13"` is Invalid Date, `"32"` through `"49"` are 2032 to 2049, `"50"` is 1950 (jsdate.wtf, re-run).
- `new Date("100")` in Chicago is `0100-01-01T05:50:36.000Z`: before 1883 the zone uses local mean time, an offset of -5:50:36.
- Invalid Date is still a `Date`: `instanceof Date` is true, `getTime()` is `NaN`, and `toISOString()` throws `RangeError: Invalid time value`.
- `new Date(stamp) == new Date(stamp)` is `false` (two objects); compare `getTime()`.
- `getYear()` is 126 for 2026, `getDay()` is the weekday (3 for Wednesday 2026-10-21), and `getDate()` is the day of the month.
- `Date()` without `new` returns a string, not a `Date`.
- Local midnight to local midnight across 2026-03-08 is 23 h. `"2026-03-08T02:30"` (in the gap) becomes 03:30 CDT, and `"2026-11-01T01:30"` (twice) picks the first, CDT.
- `"2026-10-20T24:00:00Z"` parses as the next midnight, `T24:00:01Z` is Invalid Date, and `setUTCHours(26)` quietly rolls to 02:00 the next day: the only way JS accepts a Japanese TV-listing "26:00".
- Microseconds are dropped: `"...12:00:00.123456Z"` becomes `.123Z`.
- `JSON.parse(JSON.stringify({ when: date })).when` is a `string`. JSON has no date type.
- The range ends at `new Date(8.64e15)`, `+275760-09-13T00:00:00.000Z`; one more millisecond is Invalid Date.

# The functional angle: "add a month" is a partial function, and only C++ refuses to make it total

Draws on all four tips. The shape: `add_months: date -> int -> date option`, returning nothing when the target day does not exist, instead of clamping or overflowing.

F# is the baseline here because .NET `AddMonths` is the documented clamp the other libraries copy, so the strict version is a filter on top of it:

```fsharp
// F#
let add_months_strict (start: DateOnly) (month_count: int) : DateOnly option =
    let moved = start.AddMonths month_count
    if moved.Day = start.Day then Some moved else None // AddMonths clamped
// add_months_strict (DateOnly(2026, 1, 31)) 1 -> None; ... 2 -> Some 3/31/2026
```

Rust and `jiff` 0.2.38 are the same shape, with `?` and `then_some` doing the `Option` plumbing:

```rust
// Rust (jiff 0.2.38)
fn add_months_strict(start: Date, month_count: i32) -> Option<Date> {
    let moved = start.checked_add(month_count.months()).ok()?;
    (moved.day() == start.day()).then_some(moved) // jiff clamped
}
```

C++ needs no detection at all, because the invalid value is itself the signal:

```cpp
// C++20
std::optional<year_month_day> add_months_strict(year_month_day start, months count) {
    year_month_day moved = start + count;
    return moved.ok() ? std::optional{moved} : std::nullopt; // the invalid value is the signal
}
```

TypeScript has no immutable date, so the strict version starts with a defensive copy:

```typescript
// TypeScript
const add_months_strict = (start: Date, month_count: number): Date | undefined => {
    const moved = new Date(start.getTime());
    moved.setUTCMonth(moved.getUTCMonth() + month_count);
    return moved.getUTCDate() === start.getUTCDate() ? moved : undefined; // overflowed past month end
};
```

| Language | Built-in month add | Associative? (Jan 31: +1+1 vs +2) | What the strict form costs |
| --- | --- | --- | --- |
| F# / .NET | clamp, total | No: Mar 28 vs Mar 31 | a day comparison after the fact |
| Rust (`jiff`) | clamp, `Result` only for range | No: Mar 28 vs Mar 31 | the same comparison, plus `?` on the range error |
| C++20 | keeps Feb 31, `!ok()` | **Yes**: Mar 31 vs Mar 31 | nothing: `ok()` is the check |
| TypeScript | overflow, mutating | No: Mar 3, then Apr 3 | a copy before every add, since `setUTCMonth` mutates |

The clamp makes the function total and loses information: once Jan 31 has become Feb 28, no later step knows it was ever the 31st. C++ keeps the information by allowing a value that is not a date, which is the only reason its addition stays associative. Immutability is where TypeScript pays: it is the one language here where the strict form needs a copy, because the built-in mutates the caller's object.

Is "a date that is not a date" a type-system failure, or the honest representation of a question the caller has not answered yet?

# The security angle: a "once per day" limit keyed on the caller's date is a limit the caller sets

Mode B on the TypeScript and F# tips, running in the direction the languages do not help: none of the four types can tell a server-chosen "today" from a client-chosen one.

At one instant, 2026-10-21T10:30Z, three calendar dates are current: 2026-10-20 at 22:30 in `Etc/GMT+12`, 2026-10-21 in UTC, and 2026-10-22 at 00:30 in `Pacific/Kiritimati` (UTC+14). A limit keyed on "today in the caller's zone" therefore grants three times at the same moment, and the caller picks the zone:

```typescript
// TypeScript
// INSECURE: the limit key is "today" in a zone the caller sent with the request.
const used_keys = new Set<string>();
const claim_daily_bonus_insecure = (account_id: string, caller_zone: string, now: Date): boolean => {
    const caller_today = new Intl.DateTimeFormat("en-CA", { timeZone: caller_zone }).format(now);
    const limit_key = `${account_id}:${caller_today}`;
    if (used_keys.has(limit_key)) return false;
    used_keys.add(limit_key);
    return true;
};
const same_instant = new Date("2026-10-21T10:30:00Z");
const grants = ["Etc/GMT+12", "UTC", "Pacific/Kiritimati"].map((zone) => claim_daily_bonus_insecure("acct-1", zone, same_instant));
console.log(grants); // [ true, true, true ]: three "days" at one instant

// FIXED: one authority zone, chosen by the server, never by the request.
const AUTHORITY_ZONE = "UTC";
const used_keys_fixed = new Set<string>();
const claim_daily_bonus = (account_id: string, now: Date): boolean => {
    const authority_today = new Intl.DateTimeFormat("en-CA", { timeZone: AUTHORITY_ZONE }).format(now);
    const limit_key = `${account_id}:${authority_today}`;
    if (used_keys_fixed.has(limit_key)) return false;
    used_keys_fixed.add(limit_key);
    return true;
};
console.log([claim_daily_bonus("acct-1", same_instant), claim_daily_bonus("acct-1", same_instant)]); // [ true, false ]
```

The same unit confusion as the seconds-versus-milliseconds Gotchas reaches token expiry. RFC 7519 defines `exp` as a NumericDate in **seconds**; JS hands you milliseconds:

```typescript
// TypeScript
const ONE_HOUR = 3600;                               // the unit is in nobody's name
const issued_ms = Date.UTC(2026, 9, 21, 12);
const exp_written_in_ms = issued_ms + ONE_HOUR;      // meant "one hour from now"
console.log(new Date(exp_written_in_ms * 1000).toISOString()); // +058774-09-23T01:00:00.000Z to a seconds reader
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | "today" derived from a request field; `exp` written in ms | nothing: `Date` and `Intl` take any zone, and both units are `number` | pick the authority zone server-side; name units (`exp_s`) or brand the type |
| F# / .NET | `DateTime.Now` on the server is the server's zone; `Kind` is ignored in comparisons | `DateTimeOffset` and `DateOnly` make the zone and the date explicit | key limits on `DateTimeOffset.UtcNow` or one named `TimeZoneInfo` |
| Rust | the zone is a runtime value passed to `jiff`, same as JS | `Timestamp::from_second` vs `from_millisecond` puts the unit in the name | the same authority-zone rule; a `Duration` newtype for token lifetimes |
| C++ | same request-zone keying, once a tzdb is available | `duration<long, std::milli>` vs `seconds` is a type, so mixing them is a conversion | the bug moves to `time_since_epoch().count()`, where the type is dropped |

C++ is the control for the unit half, since it is the only one where seconds and milliseconds are different types: `count()` is the one place the unit can be lost. No language is a control for the zone half; it is a policy decision none of them can make. Classes: CWE-837 (Improper Enforcement of a Single, Unique Action) and CWE-799 (Improper Control of Interaction Frequency) for the daily limit, CWE-613 (Insufficient Session Expiration) for the token that outlives the sun.

Which of your rate limits, trials or "one per day" rules reads its idea of "today" from anything the client can set, including the device clock?

# FAQ

**Is `Date.now() - start` a safe way to time something?**
No. JS `Date.now()`, Rust `SystemTime`, C++ `system_clock` and .NET `DateTime.UtcNow` read the wall clock, which NTP, an admin or a VM resume can move backwards or forwards. Durations want the monotonic clock: JS `performance.now()`, Rust `Instant`, C++ `steady_clock`, .NET `Stopwatch`. Measured: C++ `steady_clock::is_steady` is true and `system_clock::is_steady` false on both libc++ and libstdc++; .NET `Stopwatch.IsHighResolution` is true on .NET 8 Arm64; Rust's reversed `Instant` subtraction saturates to 0.

**Does Unix time count leap seconds?**
No: every Unix day is 86,400 s, so a leap second is not representable. Measured with C++ `utc_clock` (GCC 14): from 2016-12-31 23:59:59 to 2017-01-01 00:00:00 is 1 s in C++ `sys_clock` and 2 s in C++ `utc_clock`, the extra second prints as `23:59:60`, 27 leap seconds have been inserted since 1970, TAI reads `00:00:37` and GPS `00:00:18` at that midnight. Rust std, .NET and JS `Date` have no leap-second clock. The CGPM decided in 2022 to raise the UT1-UTC tolerance "in, or before, 2035", which ends new leap seconds.

**Is 2038 the only epoch cliff?**
No. Measured: signed 32-bit seconds end at 2038-01-19 03:14:07 UTC and wrap to 1901-12-13 20:45:52; unsigned 32-bit lasts to 2106-02-07 06:28:15 but cannot hold 1969; signed 64-bit nanoseconds (C++ `sys_time<nanoseconds>`) end at 2262-04-11 23:47:16.854775807; .NET `DateTime` at 9999-12-31; JS `Date` at +275760-09-13. The quiet one already happened: on 2001-09-09 Unix seconds went from 9 to 10 digits, and a string sort puts `"1000000000"` before `"999999999"`.

**Does .NET `DateTime.Parse` work out the date format from the string?**
No, from the culture. `"03/04/2026"` is March 4 under en-US and ja-JP, April 3 under en-GB and de-DE. Node always reads US order and calls `"13/04/2026"` Invalid Date. Send ISO 8601 with an offset and parse with an exact format.

**Is week 1 the week that contains January 1?**
Not in ISO 8601: week 1 holds the first Thursday. Measured: 2024-12-30 is 2025-W01, 2027-01-01 is 2026-W53, and 2026 has 53 weeks. A Rust `chrono` format string with `%Y` (calendar year) next to `%V` (ISO week) prints `2024-W01` for a day that is in 2025's week 1; use `%G`.

**Do two programs on one host agree on time zone rules?**
Not necessarily: each runtime may carry its own tz database. Measured: Node 22.17.1 bundles tz data `2025b` (ICU 77.1), while the Debian 13 container's tzdata is `2026c`. A rule change between those versions gives the two programs different local times for the same instant. This is also why a future appointment should be stored as zone ID plus local time, not as a frozen offset.

# Appendix A: Japanese eras and the Chinese calendar, two calendars that need data, not math

_Not part of the tip rotation. Written 2026-10-21 for this special, backing the F# and TypeScript tips. Every value printed by Node 22.17.1 (`Intl`, ICU 77.1) and F# on .NET 8.0.8._

## A.1 Japanese eras change mid-year, and year 1 is a word

The era changes on the emperor's accession, not on January 1. Node `Intl.DateTimeFormat("ja-JP-u-ca-japanese")` prints:

| Gregorian | ja-JP output | en-US era output | .NET `JapaneseCalendar` (era, year) |
| --- | --- | --- | --- |
| 1989-01-07 | Showa 64 (昭和64年1月7日) | 64 Shōwa | 3, 64 |
| 1989-01-08 | Heisei **gannen** (平成元年1月8日) | 1 Heisei | 4, 1 |
| 2019-04-30 | Heisei 31 (平成31年4月30日) | 31 Heisei | 4, 31 |
| 2019-05-01 | Reiwa gannen (令和元年5月1日) | 1 Reiwa | 5, 1 |
| 2026-10-21 | Reiwa 8 (令和8年10月21日) | 8 Reiwa | 5, 8 |

Three facts a parser has to know: Showa 64 lasted seven days; the first year is printed as 元 ("gannen", origin), not as the digit 1, so a parser expecting digits fails on it; and a new era is data, not arithmetic: no library can print one before its era table is updated. .NET exposes eras as plain integers (`Eras` is `[5; 4; 3; 2; 1]`), so era 5 means Reiwa only because a table says so.

## A.2 The Chinese lunisolar calendar has leap months, and .NET numbers them differently

A lunar year has 12 or 13 months, and the 13th is a repeated ("leap") month inserted where astronomy puts it. Lunar year 2025 has a leap sixth month:

| Gregorian | Node `Intl` (ICU, `en-US-u-ca-chinese`) | .NET `ChineseLunisolarCalendar` month |
| --- | --- | --- |
| 2025-07-25 | Sixth Month**bis** 1, 2025 (yi-si) | **7**, `IsLeapMonth` true |
| 2025-08-23 | Seventh Month 1, 2025 | **8** |
| 2026-02-16 | Twelfth Month 29, 2025 | **13** |
| 2026-02-17 | First Month 1, 2026 (bing-wu) | 1 |

The trap is the .NET numbering. In a leap year, .NET `GetMonth` counts months in order, so the leap sixth month is month 7, the real seventh month is month 8, and the twelfth month is month 13. .NET `GetLeapMonth(2025)` returns 7, meaning "the 7th month of the year is the leap one", not "the leap month follows the 7th". Node `Intl` (ICU) names it "Sixth Monthbis" instead. Code that maps a .NET month number to a festival (the Mid-Autumn Festival is the 15th of the eighth month) is off by one for the rest of every leap year.

## A.3 Both have a supported range

.NET `ChineseLunisolarCalendar` covers 1901-02-19 to 2101-01-28 and throws outside it, because the month table is precomputed. Node `Intl` (ICU) and .NET agree on the dates measured here; whether they agree on every leap-month placement across that range was not checked.

## A.4 Back to the tips

Both calendars make the F# tip's point from the other side: .NET `DateTime` is a count of ticks, and every calendar, Gregorian included, is a lookup layered on top of it. Gregorian is the one whose lookup is pure arithmetic, which is why .NET `AddMonths` can exist at all; ask a Chinese-calendar library to "add one month" and the answer depends on whether the year has a leap month.

# Appendix B: Postgres `timestamp` and `timestamptz`, a wall-clock reading and an instant in 8 bytes each

_Not part of the tip rotation. Added 2026-10-22, backing this part's thesis that an instant and a wall-clock reading are different things, and the F# (`Kind`) and TypeScript (local parsing) tips. Every value printed by PostgreSQL 14.24 in `docker run postgres:14`, Node `pg` 8.23.1 on Node 22.17.1, F# with `Npgsql` 10.0.3 on .NET 10.0.13, and Rust `postgres` 0.19.14 with `jiff` 0.2.38 on rustc 1.95.0._

## B.1 Neither type stores a zone

Two rows went in as `'2026-10-22 12:00:00-05'` and `'2026-10-22 12:00:00+09'`, into one column of each type:

| Column | Session `TimeZone = 'UTC'` | Session `TimeZone = 'Asia/Tokyo'` |
| --- | --- | --- |
| `timestamp` | `12:00:00`, `12:00:00` | `12:00:00`, `12:00:00` |
| `timestamptz` | `17:00:00+00`, `03:00:00+00` | `02:00:00+09` (next day), `12:00:00+09` |

`timestamp` keeps the wall-clock reading and **drops the input offset without a word**: two different instants became the same value. `timestamptz` keeps the instant and **drops the input offset too**: it converts to UTC on the way in and to the session zone on the way out. Both are 8 bytes (`pg_column_size`). The name says "with time zone", and no zone is stored. Casting `timestamp` to `timestamptz` reads it in the session zone, so the same row means a different instant per connection.

## B.2 The sign flips between text and interval

```sql
-- SQL, PostgreSQL 14.24, session TimeZone = 'UTC'
SELECT timestamptz '2026-10-22 12:00:00Z' AT TIME ZONE '+05:00';           -- 07:00:00: POSIX sign, UTC-5
SELECT timestamptz '2026-10-22 12:00:00Z' AT TIME ZONE interval '+05:00';  -- 17:00:00: ISO sign, UTC+5
SELECT timestamptz '2026-10-22 12:00:00Z' AT TIME ZONE 'Etc/GMT+5';        -- 07:00:00, as in part 4
```

The same characters give opposite answers depending on whether they are typed as text or as an interval. `AT TIME ZONE` also flips the type itself: `timestamptz AT TIME ZONE` returns `timestamp`, and `timestamp AT TIME ZONE` returns `timestamptz` (`pg_typeof`, measured).

## B.3 What each driver hands you

| Language (driver) | `timestamp` reads as | `timestamptz` reads as | The trap |
| --- | --- | --- | --- |
| Rust (`postgres` 0.19.14, `with-jiff-0_2`) | `jiff::civil::DateTime` | `jiff::Timestamp` | none found: reading either column as the other type, or binding a `Timestamp` to `$1::timestamp`, is an error (`error deserializing column 0`, `error serializing parameter 0`) |
| F# (`Npgsql` 10.0.3) | `DateTime`, `Kind=Unspecified` | `DateTime`, `Kind=Utc` | a typed parameter rejects the wrong `Kind` ("only UTC is supported"), but an untyped `Kind=Local` value is sent as `timestamp`, so `$1::timestamptz` reads it in the session zone: noon in Chicago stored as `12:00:00+00`, five hours off |
| TypeScript (`pg` 8.23.1) | a `Date` read in the **client's** zone: `12:00` is `17:00Z` under `TZ=America/Chicago` and `03:00Z` under `TZ=Asia/Tokyo` | a correct `Date` | writing one `Date` (`12:00Z`) into a `timestamp` column stores `07:00` from Chicago and `21:00` from Tokyo |
| C++ (`libpqxx`) | not measured | not measured | not tested here, so no claim |

Only Rust's types refuse to mix the two. The other two drivers fill the missing zone in from whichever process is running, which is the part 4 `TZ` tip again.

## B.4 Back to the tips

`timestamp` is .NET `DateTime` with `Kind=Unspecified` and JS's `"2026-10-31T00:00"`: a reading with no instant behind it. `timestamptz` is an instant with no zone behind it. Store an instant as `timestamptz`, and store a future local appointment as `timestamp` plus a zone ID column, because neither type can hold both.

# Appendix C: Azure on 2012-02-29, "one year from now" as a date that does not exist

_Not part of the tip rotation. Added 2026-10-22, backing this part's thesis and its Jan 31 + 1 month tips from the year side. A real incident, not folklore: the facts are from Microsoft's own post-mortem and the Wikipedia list in C.4, and every value in C.2 was printed by a real run (F# on .NET 8.0.8, Node 22.17.1, C++20 on Apple clang 21, Rust `jiff` 0.2.38)._

## C.1 What happened

Microsoft's post-mortem, signed by Bill Laing (2012-03-09): the guest agent inside each Azure VM created a transfer certificate, and its date math "set a valid-to date of February 29, 2013, an invalid date", so certificate creation failed. The bug "immediately triggered at 4:00PM PST, February 28th (00:00 UST February 29th)", which is midnight UTC: the leap day arrived in UTC hours before it arrived in Redmond. The host agent waited 25 minutes for each failed VM, and after three consecutive timeouts on a clean VM it assumed the hardware was faulty and marked the server for "Human Investigate (HI)". So one invalid date became a stream of healthy servers taken out of service as broken.

## C.2 "Same day, next year" in each language

| Language | Clamping form | Building the date by hand |
| --- | --- | --- |
| F# / .NET | `DateTime(2012, 2, 29).AddYears(1)` = 2013-02-28 | `DateTime(year + 1, 2, 29)` throws `ArgumentOutOfRangeException` |
| Rust (`jiff`) | `date.checked_add(1.year())` = 2013-02-28 | `Date::new(2013, 2, 29)` is `Err("parameter 'day' for 2013-02 is invalid, must be in range 1..=28")` |
| C++20 | none: `2012y/February/29 + years{1}` has `ok() == false` | converting it through `sys_days` silently gives 2013-03-01 |
| TypeScript (`Date`) | none | `setUTCFullYear(year + 1)` silently gives 2013-03-01 |

The Azure bug was the middle column's hand-built form: keep the month and day, add one to the year. The .NET row shows the failure mode it had: an exception at certificate-creation time, once a year.

## C.3 A second one from the same list

The 30 GB Microsoft Zune froze at midnight on 2008-12-31, day 366 of a leap year. Wikipedia, citing Microsoft's support page, says Microsoft blamed the clock driver's leap-year handling, and that the players fixed themselves after 24 hours. Same shape as Azure: code that runs once a year (or once every four) is code nobody tested.
