# Daily Tips: 2026-08-28

## Rust: `&'a mut T` is covariant in `'a` and invariant in `T`

*Type system deep cuts*

**Did you know**

Shared references are covariant in their referent, so a `&&'static str` is
usable where a `&&'a str` is wanted. Mutable references are not: `&mut T` is
invariant in `T`, and no amount of lifetime bounds will let you shorten through
one. This is not a borrow-checker heuristic, it is a soundness requirement of
the variance rules, and rustc names it outright in the diagnostic.
Stable in every edition; the note text below is from rustc 1.95.0.

**Show me**

```rust
// Covariant. Handing out `&'a &'a str` when you hold `&'a &'static str` only
// ever narrows what the reader is permitted to assume, so this is accepted.
fn shorten_shared<'a>(r: &'a &'static str) -> &'a &'a str { r }

// Invariant. Same shape, one keyword changed, and rustc rejects it:
// fn shorten_mut<'a>(r: &'a mut &'static str) -> &'a mut &'a str { r }
//
//   error: lifetime may not live long enough
//     = note: requirement occurs because of a mutable reference to `&str`
//     = note: mutable references are invariant over their type parameter
//
// Why it has to be rejected: a `&mut` slot is both readable and writable. If
// the signature compiled, the callee could store a short-lived `&'a str` into
// a slot the caller still reads as `&'static str`, and the caller's next read
// is a dangling one. Covariance is safe for reads, contravariance for writes,
// and a `&mut` does both, so it gets neither.
```

**Why it matters**

This is the real reason "just add a lifetime parameter" stops working once a
signature takes `&mut Vec<&str>` or `&mut HashMap<K, &'a V>` instead of `&Vec<...>`.
The fix is almost never more bounds, it is making the borrow shared, or moving
the lifetime out to the caller so both sides agree on one `'a`. The same
mechanism is what `PhantomData<Cell<T>>` exists to impose deliberately.

**Chew on this**

Where in your own code do you take `&mut` on a type that carries a lifetime
parameter, and is the mutability actually load-bearing there, or did it come
along for the ride because the surrounding function was already `&mut self`?
And if you wanted to force invariance on a type of your own, do you know which
of your generic parameters is currently covariant by accident?

**Sources**

- https://doc.rust-lang.org/nomicon/subtyping.html
- https://doc.rust-lang.org/reference/subtyping.html#variance

## C++: `-std=c++26` on GCC 16 quietly turns on zero-init for your locals

*New discoveries and currently popular patterns*

**Did you know**

C++26 adopted P2795R5, which reclassifies reading an uninitialized automatic
variable from undefined behavior to a new category, *erroneous behavior*: the
value is a fixed implementation-defined one, the program is still wrong, but
the compiler may no longer optimize on the assumption that the read cannot
happen. GCC implements this by having `-std=c++26` imply an initialization mode
with no user-visible spelling, described by the implementer as "like
`-ftrivial-auto-var-init=zero` except `__builtin_clear_padding` calls aren't
added". Bumping a build to `-std=c++26` therefore changes your codegen, not just
your parser.

Status, stated precisely: adopted into C++26; implemented in GCC 16.1 (released
2026-04-30) with no flag beyond `-std=c++26`; upstream Clang's C++26 status page
still lists P2795R5 as "No"; MSVC not checked.

**Show me**

```cpp
void handle_request() {
    // Pre-C++26: reading this is UB and the optimizer may assume it never
    // happens. Under -std=c++26 on GCC 16, it is erroneous behavior, and the
    // 64 KiB gets filled on every call.
    unsigned char scratch[64 * 1024];

    // The documented escape hatch: [[indeterminate]] restores the old UB and
    // suppresses the fill. Applies to block-scope automatic variables and to
    // function parameters, and on a parameter it must appear on the FIRST
    // declaration, not just the definition.
    unsigned char fast_path[64 * 1024] [[indeterminate]];

    // Whole-TU override, per the GCC patch notes:
    //   -ftrivial-auto-var-init=uninitialized   // C++23-ish behavior back
    //   -ftrivial-auto-var-init=pattern         // 0xFE fill instead of zero
}
```

The closest analog is Rust deciding this at the type level instead: there is no
uninitialized read to reclassify, because `MaybeUninit<T>` makes the unsafety a
named type you have to call `assume_init` on.

**Why it matters**

A large stack buffer in a per-request hot path is exactly the shape that pays
for this, and the cost arrives via a standard-version flag rather than an
optimization flag, so it will not show up where anyone looks for it. The upside
is real though: the class of "worked in debug, garbage in release" bugs that
came from the optimizer exploiting an uninitialized read is gone by
construction.

**Chew on this**

If you flipped a service to `-std=c++26` tomorrow, which of your hot-path stack
buffers would start getting memset, and would your benchmarks be sensitive
enough to notice a few tens of kilobytes per request? Separately: if
`[[indeterminate]]` is silently ignored as an unknown attribute on a toolchain
that has not implemented P2795, is an escape hatch that fails toward safety on
old compilers and toward speed on new ones the behavior you want in a
cross-compiler build?

**Sources**

- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2024/p2795r5.html
- https://gcc.gnu.org/gcc-16/changes.html
- https://gcc.gnu.org/bugzilla/show_bug.cgi?id=114457
- https://www.mail-archive.com/gcc-patches@gcc.gnu.org/msg383328.html
- https://clang.llvm.org/cxx_status.html

**Verified**

Not compiled. The only local toolchain is Apple clang 21.0.0, which reports
`warning: unknown attribute 'indeterminate' ignored` and defines no
`__cpp_impl_erroneous_behavior`, so the GCC 16 behavior above rests on the
release notes and the quoted patch submission (2025-09-19), not on a run here.

## TypeScript: a throwing `using` disposal replaces your error with a `SuppressedError`

*Stdlib and ecosystem gems*

**Did you know**

When a `using` disposal throws while another exception is already in flight, JS
neither terminates nor swallows: it throws a `SuppressedError` carrying both,
with `.error` set to the disposal failure and `.suppressed` set to the original
one. So the naming is inverted from what you would guess, and every
`catch (e) { if (e instanceof MyDomainError) ... }` upstream silently stops
matching. Requires TypeScript 5.2 or later with `lib` including
`esnext.disposable`. The runtime story matters more: `using` syntax is native
only from Node 24 (V8 13.6), and Node 18.18 and 20.4 onward expose
`Symbol.dispose` but cannot parse the syntax.

**Show me**

```ts
class Tx implements Disposable {
  constructor(private readonly name: string) {}
  [Symbol.dispose](): void { throw new Error(`${this.name}: rollback failed`); }
}

function run(): void {
  using tx = new Tx("tx1");
  void tx;
  throw new Error("business rule violated");   // the error you care about
}

// Actual output, tsc 6.0.3 (target es2022) running on Node 22.17.1:
//   ctor.name      = Error                    <-- not SuppressedError
//   err.name       = SuppressedError
//   err.message    = An error was suppressed during disposal.
//   err.error      = tx1: rollback failed     <-- the CLEANUP failure
//   err.suppressed = business rule violated   <-- your ORIGINAL error
//
// And `e instanceof SuppressedError` in your own code throws
// ReferenceError on Node 22: tsc typechecks it clean, because the global is
// declared in lib.esnext.disposable, but Node 22 has no such global. The
// downleveled __disposeResources helper quietly substitutes a plain Error with
// its `name` patched to "SuppressedError", which is why ctor.name is Error.
```

C++ answers the same question with `std::terminate` when a destructor throws
during unwinding, and Rust aborts on a panic in `Drop` while panicking. JS is
the outlier that keeps running and keeps both errors, which is friendlier and
also the reason the failure is silent.

**Why it matters**

`using` is the natural fit for a transaction, a span, or a pooled connection in
a long-running server, and those are precisely the disposals that can fail. The
moment one does, your error taxonomy at the top of the request handler is
wrong, and on anything below Node 24 you cannot even use `instanceof` to detect
that it happened.

**Chew on this**

In your own handlers, does anything upstream branch on error identity in a way
that a `SuppressedError` wrapper would defeat, and would you rather unwrap
`.suppressed` at the boundary or make disposals structurally incapable of
throwing? And which is the honest default for a rollback that fails: report the
business error the caller asked about, or the cleanup error that may mean the
database is now in an unknown state?

**Sources**

- https://devblogs.microsoft.com/typescript/announcing-typescript-5-2/
- https://github.com/tc39/proposal-explicit-resource-management
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SuppressedError
- https://v8.dev/features/explicit-resource-management

**Verified**

Snippet typechecks clean under `tsc 6.0.3 --strict` and the output above is a
real run on Node 22.17.1. The Node 24 and V8 13.6 native-support claim comes
from the V8 feature writeup, not from a run here; no Node 24 available locally.
