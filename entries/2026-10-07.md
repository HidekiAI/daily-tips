# Daily Tips: 2026-10-07

## Rust: Since 1.99 an exhausted a..=b records how it was drained, and slicing with the leftover can panic

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.99.0 (2026-10-01) rewrote `RangeInclusive`'s iterator so `a..=b` loops get the optimizations `a..b` always had ([#155114](https://github.com/rust-lang/rust/pull/155114), merged 2026-07-09). The price is the drained state. Before, every exhausted range collapsed to `end..=end` with an `exhausted` flag. Now the flag is set only when stepping would overflow; otherwise `start` simply walks past `end`. So the leftover depends on whether you used `next`, a fold, `nth`, or `next_back`. Draining `0..=2` from the back wraps `end` to `usize::MAX`, and indexing a slice with that range now panics where 1.95 returned an empty slice.

**Show me**

```rust
// Rust 1.99.0. Built with 1.95.0, the same file prints different values.
fn main() {
    let rows = [10, 20, 30, 40, 50];

    // Drained three different ways; all three report is_empty() == true.
    let mut by_next = 1..=3usize;
    while by_next.next().is_some() {}
    let mut by_fold = 1..=3usize;
    let _sum: usize = by_fold.by_ref().sum(); // internal iteration: the fold path
    let mut by_back = 0..=2usize;
    while by_back.next_back().is_some() {}

    // 1.95 -> 3..=3 (exhausted) | 3..=3 (exhausted) | 0..=0 (exhausted)
    // 1.99 -> 4..=3 | 3..=3 (exhausted) | 0..=18446744073709551615 (exhausted)
    println!("{:?} | {:?} | {:?}", by_next, by_fold, by_back);

    // is_empty() and contains() honour the flag on both versions...
    assert!(by_back.is_empty() && !by_back.contains(&1));

    // ...but slice indexing reads start/end, and end is now usize::MAX.
    let leftover = std::panic::catch_unwind(|| rows[by_back.clone()].len());
    // 1.95 -> true (empty slice)
    // 1.99 -> false: "range end index 18446744073709551615 out of range for slice of length 5"
    println!("rows[by_back] ok: {}", leftover.is_ok());
}
```

**Why it matters**

The release notes call this "not guaranteed to be stable" and therefore not breaking, and that is fair: no code should index with a drained range. But a parser or pager that keeps one `RangeInclusive` as a cursor, iterates it, then reuses `start()` as "where I stopped" or slices with it, now gets a value that differs by drain method, and in one case a request-path panic. C++ never has the question, because `views::iota` is a value and its iterator is a separate object; the view is untouched by the drain. F#'s `seq { 1 .. 3 }` is re-enumerable and has no observable cursor at all.

**Chew on this**

Where in your code does a range outlive the loop that consumed it? And if `std::range::RangeInclusive` (stable since 1.95, `Copy`, `IntoIterator` but not `Iterator`) is the fix, what does migrating a public API that hands out `ops::RangeInclusive` cost your callers?

**Sources**

- https://github.com/rust-lang/rust/pull/155114
- https://github.com/rust-lang/rust/blob/master/RELEASES.md (Version 1.99.0, Libraries)
- https://doc.rust-lang.org/std/ops/struct.RangeInclusive.html

**Verified**

Ran on rustc 1.95.0 and 1.99.0 side by side; the "1.95" and "1.99" comments are the measured outputs. `nth(5)` on `1..=3` also differs: `3..=3 (exhausted)` on 1.95, `7..=3` on 1.99.

## C++: make_shared puts your object inside the control block, so the last weak_ptr, not the last shared_ptr, frees its bytes

*Perf and memory model*

**Did you know**

`std::make_shared<T>` makes one allocation holding both the reference counts and the `T`. When the last `shared_ptr` goes away, `T`'s destructor runs, but the block cannot be freed while any `weak_ptr` still needs the counts. So `sizeof(T)` bytes stay allocated until the last `weak_ptr` dies. `shared_ptr<T>(new T)` makes two allocations, and releases `T`'s storage at the last strong owner. Only inline storage is pinned: a `std::vector` member frees its heap buffer in the destructor, while a `std::array<char, 65536>` member stays. This holds from C++11 on; measured below with libc++ 22 (Apple clang 21), `-std=c++20`.

**Show me**

```cpp
// C++20 (behaviour is C++11). Counts live heap bytes via a replaced operator new.
#include <array>
#include <cstdio>
#include <cstdlib>
#include <memory>
#include <new>

static std::size_t live_bytes = 0;
void* operator new(std::size_t size) {
    live_bytes += size;
    std::size_t* block = static_cast<std::size_t*>(std::malloc(size + sizeof(std::size_t)));
    if (block == nullptr) throw std::bad_alloc{};
    *block = size;                                   // stash the size for delete
    return block + 1;
}
void operator delete(void* payload) noexcept {
    if (payload == nullptr) return;
    std::size_t* block = static_cast<std::size_t*>(payload) - 1;
    live_bytes -= *block;
    std::free(block);
}
void operator delete(void* payload, std::size_t) noexcept { operator delete(payload); }

struct Frame { std::array<char, 64 * 1024> inline_buffer{}; };  // inside sizeof(Frame)

int main() {
    std::weak_ptr<Frame> observer;
    {
        std::shared_ptr<Frame> owner = std::make_shared<Frame>();
        observer = owner;                            // live=65560: one block
    }
    std::printf("make_shared, owners gone: live=%zu expired=%d\n", live_bytes, observer.expired());
    // -> live=65560 expired=1   (destructor ran, 64 KiB still allocated)
    observer.reset();                                // -> live=0

    std::weak_ptr<Frame> split_observer;
    {
        std::shared_ptr<Frame> owner(new Frame);     // two blocks: Frame, then counts
        split_observer = owner;
    }
    std::printf("shared_ptr(new), owners gone: live=%zu\n", live_bytes);
    // -> live=32   (only the control block is left)
}
```

**Why it matters**

A cache of `weak_ptr`s, an observer list, or a parent link in a tree is exactly where a `weak_ptr` outlives its object, and with `make_shared` each of those entries holds `sizeof(T)` bytes of a dead object. For small `T` it is the right default: one allocation instead of two. Rust has no choice to make here: `Rc::new` and `Arc::new` are always the `make_shared` shape, a `Weak` keeps the whole 64 KiB allocation alive (measured, `rustc` 1.95), and `Rc::from(Box<T>)` copies into a fresh block instead of adopting the box. F# and TypeScript sidestep it: a `WeakReference` or `WeakRef` does not keep its target alive, and the GC reclaims the object as a whole.

**Chew on this**

Which of your `weak_ptr` holders points at a type whose `sizeof` is large because of an inline buffer, a `std::array`, or a fat `small_vector`? And if you switched that site to `shared_ptr(new T)`, would the second allocation cost more than the memory you get back?

**Sources**

- https://en.cppreference.com/w/cpp/memory/shared_ptr/make_shared (Notes)
- https://doc.rust-lang.org/std/rc/struct.Weak.html

## F#: A [<Struct>] single-case union hides its constructor, and Array.zeroCreate still makes one with null inside

*Type system deep cuts*

**Did you know**

`type Email = private Email of string` is the usual F# way to build a validated newtype: only the module can call `Email`, so every value went through `make`. Mark it `[<Struct>]` to skip the heap allocation, and you add a value the module never made. Every .NET value type has a default, and `Array.zeroCreate`, `Unchecked.defaultof`, an unset `[<DefaultValue>]` field, or a `Dictionary.TryGetValue` miss all produce `StructEmail null`. The reference version fails loudly instead: a zeroed slot is a `null` reference, and the first unwrap throws `NullReferenceException`. Measured with F# 8, FSharp.Core 8.0.0, .NET 8.0.8.

**Show me**

```fsharp
module Domain =
    type Email = private Email of string
    [<Struct>]
    type StructEmail = private StructEmail of string
    let make (raw: string) = if raw.Contains "@" then Some (Email raw) else None
    let make_struct (raw: string) = if raw.Contains "@" then ValueSome (StructEmail raw) else ValueNone
    let value (Email raw) = raw
    let value_struct (StructEmail raw) = raw

open Domain
// Neither line calls make or make_struct, and neither needs to: private does not cover these.
let ref_slots : Email[] = Array.zeroCreate 2
let struct_slots : StructEmail[] = Array.zeroCreate 2

try printfn "%s" (value ref_slots.[0])
with error -> printfn "reference: %s" (error.GetType().Name)
// -> reference: NullReferenceException     (loud, at the first use)

printfn "struct holds null: %b" (isNull (value_struct struct_slots.[0]))
// -> struct holds null: true                (quiet, flows on as a "valid" Email)

printfn "%A" (Unchecked.defaultof<StructEmail>)
// -> StructEmail null
```

**Why it matters**

The struct attribute is usually added later, as a perf change ("this newtype allocates on a hot path"), by someone who is not thinking about validation. The change compiles, all tests pass, and the type now has a member that bypasses the smart constructor. Rust does not have this problem: a struct with a private field has no value unless you write one or derive `Default`, and `mem::zeroed` is `unsafe`. C++ is the same: `std::vector<Email>(2)` does not compile without a default constructor. Go is the other extreme: `var forged email.Email` is legal from any package, and the zero value is part of the language by design.

**Chew on this**

Which of your F# newtypes are `[<Struct>]`, and does any code path put one in an array, a dictionary miss, or an out parameter before it is assigned? Would you rather keep the struct and make `null` an accepted state, or pay the 24 bytes a call to make the bypass throw?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/discriminated-unions (Struct Discriminated Unions)
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-arraymodule.html#zeroCreate
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-core-operators-unchecked.html#defaultof

**Verified**

The `dotnet fsi` outputs are measured. The "24 bytes" for a reference single-case union is the usual x64 object size (16-byte header plus one reference), not measured here.

## TypeScript: Array.fromAsync is typed like Promise.all, and a later promise that rejects early kills the process

*Stdlib and ecosystem gems*

**Did you know**

`Array.fromAsync(iterable)` (ES2027 per MDN; TypeScript 6.0.3 declares it only in `lib.esnext.array`) accepts an `Iterable<T | PromiseLike<T>>` and returns `Promise<T[]>`, the same shape as `Promise.all`. It does not behave like `Promise.all`. It awaits the elements one at a time and only attaches a handler to element N once element N-1 has settled. If you pass it promises that have already started, and a later one rejects while an earlier one is still pending, that rejection has no handler. Node's default `--unhandled-rejections=throw` then ends the process. The `try/catch` around the `await` never runs.

**Show me**

```typescript
// TypeScript 6.0.3, lib "esnext", module nodenext. Node 22.17.1.
const settle = (delay_ms: number, label: string, fail: boolean): Promise<string> =>
    new Promise((resolve, reject) =>
        setTimeout(() => (fail ? reject(new Error(label)) : resolve(label)), delay_ms));

async function load_all(collect: "all" | "fromAsync"): Promise<string[]> {
    // Both promises start now, before either API sees them.
    const lookups: Promise<string>[] = [settle(200, "slow ok", false), settle(10, "fast fail", true)];
    // tsc accepts both lines with identical types: Iterable<T | PromiseLike<T>> -> Promise<T[]>.
    return collect === "all" ? Promise.all(lookups) : Array.fromAsync(lookups);
}

const collect = process.argv[2] === "all" ? "all" : "fromAsync";
try {
    console.log(await load_all(collect));
} catch (error) {
    console.log(`caught: ${(error as Error).message}`);
}
// node tip.js all        -> "caught: fast fail", exit 0
// node tip.js fromAsync  -> unhandled rejection "Error: fast fail" at ~10 ms, exit 1;
//                           the catch block never runs
```

**Why it matters**

MDN warns that `fromAsync` is sequential, and shows it as a speed cost: five 100 ms timers from a generator take 500 ms instead of 100 ms. With an array of promises that already started, you do not pay that cost, because the work already runs in parallel. So nothing looks slow. What remains is the crash, and it happens only when a later element fails first. A test with one failure, or with failures in order, will not trigger it. Rust's `futures::future::try_join_all` and Effect's `Effect.all` take un-started work and own the failure handling, so there is nothing for them to leave unhandled. JavaScript is the only language here where a promise starts before anyone holds a handler for it.

**Chew on this**

Is there an `Array.fromAsync(` in your code whose argument is an array of promises, not an async generator? And when an async generator really is the input, what makes `fromAsync` the right tool and `Promise.all` the wrong one?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/fromAsync
- https://github.com/tc39/proposal-array-from-async
- https://nodejs.org/api/cli.html#--unhandled-rejectionsmode

**Verified**

Compiled with `tsc --strict` (lib esnext, @types/node 22) and ran both modes on Node 22.17.1; the exit codes are measured. The Rust and Effect remark is from documentation, not run today.

# The functional angle: Rust's old range is its own cursor, so a drained range is a leftover value you can still read

Draws on the Rust tip, with F#, C++ and TypeScript as the other rows. In functional style, iterating does not change the thing you iterate. Each language reaches that in its own way, and only Rust's `ops::RangeInclusive` does not.

```fsharp
let numbers = seq { 1 .. 3 }
Seq.sum numbers, Seq.sum numbers           // (6, 6): no cursor to observe
```

```cpp
auto numbers = std::views::iota(1, 4);     // the view is a value
auto cursor = numbers.begin();             // the cursor is a separate object
while (cursor != numbers.end()) ++cursor;  // numbers.front() is still 1
```

```typescript
const numbers = inclusive(1, 3);           // a generator: value and cursor in one object
[...numbers].length, [...numbers].length   // 3, 0: drained, and the leftover is hidden
```

```rust
let span: std::range::RangeInclusive<usize> = (1..=3).into(); // Rust 1.95+
let copy_one = span;                       // Copy, because it is not an Iterator
let total: usize = span.into_iter().sum(); // the iterator is a separate RangeInclusiveIter
```

| Language | Functional form | What it costs |
| --- | --- | --- |
| F# | `seq { a .. b }`, `[a .. b]` | each enumeration runs the generator again; there is never a leftover to read |
| C++ | `views::iota` + separate iterator | two objects to keep in sync; the iterator dangles if the view was a temporary |
| TypeScript | none in std; a generator is one-shot | second pass yields 0 elements, and nothing tells you why |
| Rust (`ops::RangeInclusive`) | `.clone()` before every pass | not `Copy`, *because* it is an `Iterator`; the drained value is readable and 1.99 changed it |
| Rust (`range::RangeInclusive`, 1.95+) | `IntoIterator`, `Copy` | a second type, and every API that takes `ops::` ranges needs a conversion |

F# is the baseline here because its `..` is a pure description. Verified with `dotnet fsi`, clang++ `-std=c++20`, tsc 6.0.3 + Node 22, and rustc 1.95 / 1.99. The leftover thread: Rust fixed this by adding a type, not by changing the old one. How many editions does a type stay "legacy" when `a..=b` syntax still produces it?

# The security angle: a private constructor guards the values you build, not the zero value the runtime fills in

Draws on the F# tip, Mode D in reverse: a type built to make an invalid state impossible, and the runtime path that makes it anyway. Direction: what the language does *not* stop.

```fsharp
// Looks like a hardened tenant key. Is a filter that can match null.
[<Struct>]
type TenantId = private TenantId of string
let tenant_filter (TenantId raw) = sprintf "tenant_id = '%s'" raw  // demo only, not a real query

let pending : TenantId[] = Array.zeroCreate 8   // a buffer that "will be filled"
tenant_filter pending.[3]                       // "tenant_id = ''": never validated
```

The defect is not the formatting. It is that `pending.[3]` has type `TenantId`, so every check downstream trusts it. The same shape appears wherever a type has a value no constructor made:

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| F# `[<Struct>]` DU | `zeroCreate` / `defaultof` makes `X null` (measured) | nothing; `private` covers the case constructor only | keep validated newtypes as reference types, or check for null at every sink |
| F# reference DU | zeroed slot is a `null` reference | throws `NullReferenceException` at first unwrap (measured) | the crash is the defence; do not "fix" it with a struct |
| Go | `var forged email.Email` from any package (measured, go 1.24.2) | zero value by design | make the zero value invalid on purpose, and check it at every use |
| TypeScript branded type | `new Array<Email>(2)` holes read as `Email` under `strict` (measured) | `noUncheckedIndexedAccess` makes the read `Email \| undefined` (TS2322) | turn that flag on; it is not part of `strict` |
| Rust | none in safe code | a private field means no value without your function; `mem::zeroed` is `unsafe` | audit `unsafe`, `Default` derives, and `MaybeUninit` |
| C++ | none for `vector<T>(n)` | no default constructor means a compile error (measured) | `std::array<T, N>` and aggregates are the gaps to check |

Rust is the baseline here because it is the only row where safe code cannot write the bad value at all. Class: [CWE-1188](https://cwe.mitre.org/data/definitions/1188.html), insecure default initialization of a resource; the F# and Go rows end in [CWE-20](https://cwe.mitre.org/data/definitions/20.html) once the value reaches a sink. Today's other two tips are the denial-of-service form of the same mistake, a value that looks harmless taking the process down ([CWE-248](https://cwe.mitre.org/data/definitions/248.html)): a drained range used as a slice index, and a promise rejection with no handler.

Which of your "validated" types can reach a sink through a buffer, a dictionary miss, or a deserializer that never called the constructor?
