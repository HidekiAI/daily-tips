## Rust: `as` truncates and saturates, `round` goes away from zero, and `(0.29 * 100.0) as i64` is 28

*Idioms and antipatterns*

**Did you know**

A float-to-int `as` cast rounds toward zero, maps `NaN` to 0, and saturates out-of-range values to the integer's min or max. These are defined results, not undefined behaviour, but they are silent. `f64::round` sends halves away from zero (`2.5 -> 3`, `-2.5 -> -3`), and `round_ties_even` (stable since 1.77) is the banker's rounding F# uses by default. There is no `TryFrom<f64>` for any integer type: `i32::try_from(9.99_f64)` fails with E0277, so std has no checked float-to-int conversion at all.

**Show me**

```rust
fn to_cents_checked(amount: f64) -> Option<i64> {
    let scaled = (amount * 100.0).round(); // round first: 0.29 * 100.0 is 28.999999999999996
    // `as` never fails, so the range check has to be ours. Both bounds are exact in f64.
    let in_range = scaled.is_finite() && scaled >= i64::MIN as f64 && scaled < i64::MAX as f64;
    in_range.then_some(scaled as i64)
}

fn main() {
    // `as` truncates toward zero: 9.99 -> 9, -9.99 -> -9 (floor would give -10).
    assert_eq!(9.99_f64 as i32, 9);
    assert_eq!(-9.99_f64 as i32, -9);
    assert_eq!((-9.99_f64).floor(), -10.0);

    // `as` saturates and maps NaN to 0 (defined behaviour since Rust 1.45).
    assert_eq!(1e10_f64 as i32, i32::MAX);
    assert_eq!(f64::NAN as i32, 0);
    assert_eq!(-1.5_f64 as u32, 0);

    // round() sends halves away from zero; round_ties_even() (1.77) is banker's rounding.
    assert_eq!((2.5_f64).round(), 3.0);
    assert_eq!((-2.5_f64).round(), -3.0);
    assert_eq!((2.5_f64).round_ties_even(), 2.0);

    // The money bug: truncating a scaled float drops a cent.
    let price = 0.29_f64;
    assert_eq!((price * 100.0) as i64, 28);
    assert_eq!(to_cents_checked(price), Some(29));
    assert_eq!(to_cents_checked(f64::NAN), None);
    assert_eq!(to_cents_checked(1e300), None);
    println!("ok");
}
```

**Why it matters**

`(price * 100.0) as i64` reads like "convert dollars to cents", but it means "truncate". 0.29, 0.57, 1.15, 4.35 and 19.99 all lose a cent that way (`28`, `56`, `114`, `434`, `1998`), because each product lands a hair below the integer. Saturation makes a garbage input look like a valid one: a `NaN` fee rate becomes a 0-cent fee, and a negative amount cast to `u64` becomes 0 rather than an error. C++ leaves the same cast undefined, F# and .NET only became saturating on x64 in .NET 9, and TypeScript wraps modulo 2^32.

**Chew on this**

Which of your `as` casts from `f64` sit on a value that came from a request body, and what would you rather happen on `NaN`? Is truncation ever the rule your business actually wrote down?

## C++: `static_cast<int>(1e10)` is undefined behaviour that happens to saturate on Arm64, and only `rint` rounds half to even

*Idioms and antipatterns*

**Did you know**

A floating-to-integral conversion discards the fraction, and "if the truncated value cannot fit into the destination type, the behavior is undefined", even for an unsigned destination. On Apple clang 21 / Arm64 the hardware instruction saturates (`1e10 -> 2147483647`, `NaN -> 0`), so the UB looks like Rust's defined behaviour until the code runs elsewhere. `-fsanitize=float-cast-overflow` reports it at runtime (`1e+10 is outside the range of representable values of type 'int'`), and inside a `constexpr` it is a compile error. For rounding, `std::round` and `std::lround` go away from zero, while `std::rint`, `lrint` and `nearbyint` follow the current rounding mode, which defaults to ties-to-even (`rint(2.5) == 2`). All of these are C++11 `<cmath>` and available everywhere.

**Show me**

```cpp
#include <cassert>
#include <cmath>
#include <cstdint>
#include <optional>

// static_cast<int64_t> on an out-of-range double is undefined behaviour, so the
// range check must run on the double, before the cast.
std::optional<std::int64_t> to_cents_checked(double amount) {
    const double scaled = std::round(amount * 100.0);  // 0.29 * 100.0 is 28.999999999999996
    constexpr double lower = -9223372036854775808.0;   // -2^63, exact
    constexpr double upper = 9223372036854775808.0;    //  2^63, exact; must be excluded
    if (!(scaled >= lower && scaled < upper)) return std::nullopt;  // also rejects NaN
    return static_cast<std::int64_t>(scaled);
}

int main() {
    assert(static_cast<int>(9.99) == 9);     // truncation toward zero
    assert(static_cast<int>(-9.99) == -9);
    assert(std::floor(-9.99) == -10.0);

    assert(std::round(2.5) == 3.0);          // halves away from zero
    assert(std::round(-2.5) == -3.0);
    assert(std::rint(2.5) == 2.0);           // current rounding mode: FE_TONEAREST = ties to even
    assert(std::lround(2.5) == 3);           // the l-variant of round, not of rint

    assert(static_cast<std::int64_t>(0.29 * 100.0) == 28);  // the lost cent
    assert(to_cents_checked(0.29) == 29);
    assert(!to_cents_checked(NAN));
    assert(!to_cents_checked(1e300));
}
```

**Why it matters**

Because the cast is UB, the optimizer may assume the value was in range, and the hardware result differs by target: Arm64's `fcvtzs` saturates, which is what was measured here. The written form of the check matters too: `!(scaled >= lower && scaled < upper)` rejects `NaN`, but the natural `scaled < lower || scaled >= upper` lets `NaN` through to the cast, since every comparison with `NaN` is false. Rust made the same cast defined and saturating. F# and .NET made it saturating on x64 only in .NET 9. TypeScript has no undefined result, only a wrong one.

**Chew on this**

How many of your `static_cast<int>` calls on a `double` have a range check before them, rather than after? Does your CI ever run `-fsanitize=float-cast-overflow` on a build where it could fire?

## F#: `round 2.5` is 2.0, and `Checked.int` is the only checked float-to-int conversion of the four

*Idioms and antipatterns*

**Did you know**

F#'s `round` is `Math.Round`, which "rounds midpoint values to the nearest even number": `round 2.5 = 2.0`, `round 3.5 = 4.0`, `round 0.5 = 0.0`, and the same holds for `decimal` (`round 2.5m = 2`). You need `Math.Round(value, MidpointRounding.AwayFromZero)` to get the Rust or C++ `round` answer. `int` truncates toward zero, and out-of-range handling is the runtime's: saturating on Arm64 (measured, .NET 8) and on x64 from .NET 9, but `int.MinValue` for an out-of-range value on .NET 8 x64. `Checked.int` raises `OverflowException` on `1e10` and on `nan` (measured), which makes it the only checked float-to-int conversion built into any of the four languages.

**Show me**

```fsharp
// F# 8, FSharp.Core 8.0.0, .NET 8.0.8 on Arm64 (dotnet fsi)
// `round` is Math.Round: halves go to the EVEN neighbour, not away from zero.
printfn "%g %g %g" (round 2.5) (round 3.5) (round -2.5)                            // 2 4 -2
printfn "%g" (System.Math.Round(2.5, System.MidpointRounding.AwayFromZero))         // 3

// `int` truncates toward zero, like Rust's `as` and C++'s static_cast.
printfn "%d %d %g" (int 9.99) (int -9.99) (floor -9.99)                             // 9 -9 -10

// Unchecked `int` saturates here (Arm64; x64 too since .NET 9), NaN -> 0.
printfn "%d %d" (int 1e10) (int nan)                                                // 2147483647 0

// Checked.int raises instead: the one checked float-to-int of the four languages.
let to_units_checked (amount: float) : int option =
    try Some (Checked.int amount) with :? System.OverflowException -> None
printfn "%A %A %A" (to_units_checked 9.99) (to_units_checked 1e10) (to_units_checked nan) // Some 9 None None

// The lost cent, and the banker's-rounding twist on an exact half.
printfn "%d %d" (int (0.29 * 100.0)) (int (round (0.29 * 100.0)))                   // 28 29
printfn "%g" (round (2.675 * 100.0))                                                // 268: 267.5 is exact, 268 is even
printfn "%d" (int (round 2.5m))                                                     // 2: decimal rounds to even too
```

**Why it matters**

Port a pricing rule from a Rust or C++ service into F#, keep the word `round`, and every exact half now goes to the even neighbour. Totals drift by a cent on exactly the inputs a test fixture with `x.50` prices would catch, and on nothing else. The .NET 8 to .NET 9 change matters for the cast: the same `int amount` line returned `int.MinValue` on x64 and `int.MaxValue` on Arm64 until .NET 9 made both saturate. A limit check written against one of those results quietly inverts on the other.

**Chew on this**

Do your F# services and your Rust or C++ services agree on which way 0.5 rounds, and has anyone checked rather than assumed? Where would `Checked.int` replace `int` in your code without a measurable cost?

## TypeScript: `Math.round(-2.5)` is -2, `x | 0` wraps modulo 2^32, and `parseInt(0.0000005)` is 5

*Idioms and antipatterns*

**Did you know**

`Math.round` rounds halves toward positive infinity, so `Math.round(2.5)` is 3 but `Math.round(-2.5)` is -2, an answer none of the other three gives with its default `round`. The `| 0` and `~~` truncation idioms go through ToInt32, which wraps modulo 2^32: `1e10 | 0` is 1410065408 and `4294967295.5 | 0` is -1. `parseInt` converts its argument to a string first, and `0.0000005` stringifies as `"5e-7"`, so `parseInt(0.0000005)` is 5. `(1.005).toFixed(2)` is `"1.00"`, because 1.005 is stored as 1.00499999...

**Show me**

```ts
// Node 22.17.1, tsc 6.0.3. All values below were printed by this file.
const halves: number[] = [Math.round(2.5), Math.round(-2.5), Math.round(3.5)]
console.log(halves) // [3, -2, 4]: halves round toward +Infinity, so -2.5 -> -2

// Four ways to "drop the fraction", and they disagree on negatives and on range.
const amount_negative = -9.99
console.log(Math.trunc(amount_negative), Math.floor(amount_negative), amount_negative | 0) // -9 -10 -9

// `| 0` (and `~~`) is ToInt32: modulo 2^32, not saturation.
console.log(1e10 | 0, 2 ** 31 | 0, 4294967295.5 | 0, NaN | 0) // 1410065408 -2147483648 -1 0

// parseInt reads the STRING form of a number, and 0.0000005 prints as "5e-7".
console.log(parseInt(String(0.0000005)), parseInt(String(9.99))) // 5 9

// The lost cent, then the same value through toFixed.
const price = 0.29
console.log(Math.trunc(price * 100), Math.round(price * 100), (1.005).toFixed(2)) // 28 29 "1.00"

const to_cents_checked = (value: number): number | undefined => {
    const scaled = Math.round(value * 100)
    return Number.isSafeInteger(scaled) ? scaled : undefined // rejects NaN, Infinity, > 2^53 - 1
}
console.log(to_cents_checked(price), to_cents_checked(NaN), to_cents_checked(1e300)) // 29 undefined undefined
```

**Why it matters**

`number` is the only numeric type the checker sees, so `x | 0`, `Math.trunc`, `Math.floor` and `parseInt` all type-check identically while giving four different answers for the same negative or out-of-range input. The asymmetric `Math.round` means a refund computed as `-Math.round(charge)` does not equal `Math.round(-charge)` on a half, and the two halves of a ledger stop balancing by a cent. Rust and C++ round symmetrically, and F# rounds to even. Only TypeScript's default depends on the sign.

**Chew on this**

Where in your code does `| 0` or `~~` stand in for `Math.trunc`, and can its input ever reach 2^31? If a negative half and a positive half round differently, which of your totals would notice first?

**Sources**

# The functional angle: none of the four ships a total float-to-int function, so `float -> int option` is always yours to write

Draws on all four tips: each one ended with a `to_cents_checked` or `to_units_checked` written by hand.

Converting a float to an integer is a partial function: `NaN`, the infinities and out-of-range values have no right answer. The functional fix is to make it total by moving the failure into the type, `float -> int option`. No standard library here provides that function. What differs is what each one gives you to build it from:

| Language | Building block | Total form | What it costs |
| --- | --- | --- | --- |
| F# | `Checked.int` raises `OverflowException` | `try Some (Checked.int amount) with :? OverflowException -> None` | an exception on every failure (cost not measured); still no `tryInt` in FSharp.Core |
| Rust | none: `i32::try_from(f64)` does not exist (E0277) | `is_finite()` plus a bounds check, then `then_some(scaled as i64)` | the bounds are yours to get exactly right (`< i64::MAX as f64`, not `<=`) |
| C++ | none, and the unchecked cast is UB | `std::optional` plus a negated `>= && <` check before the cast | the check's form decides whether `NaN` reaches the UB |
| TypeScript | `Number.isSafeInteger` | `Math.round`, then `isSafeInteger ? scaled : undefined` | cheapest of the four; "safe" means below 2^53, not "fits in an int32" |

No row needs mutation: every total form is one expression over the input. F# is the only language with a primitive that refuses, and even it reports refusal through an exception, so the `Option` still comes from a wrapper.

Should the conversion return `None`, or the reason (`NaN`, overflow, negative) it refused?

# The security angle: a conversion that cannot fail can still hand the attacker a zero, a max, or a negative

Draws on all four tips (Mode C, the missing check). The direction is mixed. Rust and TypeScript define a result for every input, which prevents undefined behaviour but not wrong values. C++ prevents nothing. F# prevents it only through `Checked.int`. This is CWE-681 (incorrect conversion between numeric types) and CWE-197 (numeric truncation error), with CWE-190 for the TypeScript wrap.

```ts
// Looks like "whole items only". 4294967295.5 | 0 is -1 (measured),
// so a crafted quantity turns a charge into a credit.
const quantity: number = body.quantity | 0
const total_cents: number = quantity * unit_price_cents
```

```rust
// Looks like "fees are never negative". A NaN rate saturates to 0 and a
// negative amount saturates to 0 (both measured): the fee silently vanishes.
let fee_cents = (amount * rate) as u64;
```

```cpp
// Looks like a limit check. The cast is UB for requested >= 2^31, and
// the result depends on the target; Arm64 gives INT_MAX (measured).
if (static_cast<int>(requested) > daily_limit) reject();
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `NaN` and negatives saturate to 0, huge values to max | defines every result; never UB | `is_finite()` and a sign and range check before the cast |
| C++ | out-of-range cast is UB, result differs by target | nothing at runtime; `constexpr` and UBSan catch it | the check on the `double`, written so `NaN` fails it |
| F# | unchecked `int` differed between x64 and Arm64 before .NET 9 | `Checked.int` raises; .NET 9 saturates everywhere | use `Checked.int` at trust boundaries, or validate first |
| TypeScript | `\| 0` wraps to a negative; `parseInt` reads `5e-7` as 5 | nothing: every result is a valid `number` | `Number.isSafeInteger` plus a sign check on input |

Rust is the control here for what "defined" buys: no undefined behaviour, but the attacker still chooses between 0 and the maximum. C++ is the control for what the optimizer may assume once a check is missing.

Which of your request fields is a float on the wire but a count, a quantity or a cent amount in your code?
