# Daily Tips special: float to integer, four ways to lose a cent

_Special edition, written 2026-10-20 beside that day's entry. One topic across all four languages instead of the rotation: truncating, flooring, ceiling and rounding a float into an integer._

**The thesis of this special: each of these bugs exists because someone misunderstood how the function works.** None of the functions below is broken. `round`, `floor`, `/`, `%` and the casts all do exactly what their documentation says. The bug is the gap between that and what the caller assumed, and every tip, Gotcha and FAQ entry here is one of those gaps.

Every value below was printed by the snippet beside it: rustc 1.95.0, Apple clang 21 (libc++), F# 8 on .NET 8.0.8 (Arm64), Node 22.17.1 with tsc 6.0.3.

| ------- | ------------------------------- | ---------------------------------------- | -------------------------------------------- | ------------------------ |
| `9.99`  | 9                               | 9                                        | 9                                            | 9                        |
| `-9.99` | -9                              | -9                                       | -9                                           | -9                       |
| `1e10`  | 2147483647 (saturates, defined) | 2147483647 here, **undefined behaviour** | 2147483647 here (.NET 8 x64: `int.MinValue`) | 1410065408 (modulo 2^32) |

Truncation (`9.99 -> 9`) is the one thing all four agree on. Rounding a half is where they split three ways: away from zero (Rust, C++ `round`), to even (F#, C++ `rint`), and toward positive infinity (TypeScript).

## Rust: `as` truncates and saturates, `round` goes away from zero, and `(0.29 * 100.0) as i64` is 28

_Idioms and antipatterns_

**Did you know**

A float-to-int `as` cast rounds toward zero, maps `NaN` to 0, and saturates out-of-range values to the integer's min or max. These are defined results, not undefined behaviour, but they are silent. `f64::round` sends halves away from zero (`2.5 -> 3`, `-2.5 -> -3`), and `round_ties_even` (stable since 1.77) is the banker's rounding F# uses by default. There is no `TryFrom<f64>` for any integer type: `i32::try_from(9.99_f64)` fails with E0277, so std has no checked float-to-int conversion at all.

**Show me**

```rust
fn to_cents_checked(amount: f64) -> Option<i64> {
    let scaled = (amount * 100.0).round(); // round first: 0.29 * 100.0 is 28.999999999999996
    // `as` never fails, so the range check has to be ours. Both bounds are exact in f64.
    let in_range = scaled.is_finite() && scaled >= i64::MIN as f64 && scaled < i64::MAX as f64;
    in_range.then_some(scaled as i64)
}

fn main() {
    // `as` truncates toward zero: 9.99 -> 9, -9.99 -> -9 (floor would give -10).
    assert_eq!(9.99_f64 as i32, 9);
    assert_eq!(-9.99_f64 as i32, -9);
    assert_eq!((-9.99_f64).floor(), -10.0);

    // `as` saturates and maps NaN to 0 (defined behaviour since Rust 1.45).
    assert_eq!(1e10_f64 as i32, i32::MAX);
    assert_eq!(f64::NAN as i32, 0);
    assert_eq!(-1.5_f64 as u32, 0);

    // round() sends halves away from zero; round_ties_even() (1.77) is banker's rounding.
    assert_eq!((2.5_f64).round(), 3.0);
    assert_eq!((-2.5_f64).round(), -3.0);
    assert_eq!((2.5_f64).round_ties_even(), 2.0);

    // The money bug: truncating a scaled float drops a cent.
    let price = 0.29_f64;
    assert_eq!((price * 100.0) as i64, 28);
    assert_eq!(to_cents_checked(price), Some(29));
    assert_eq!(to_cents_checked(f64::NAN), None);
    assert_eq!(to_cents_checked(1e300), None);
    println!("ok");
}
```

**Why it matters**

`(price * 100.0) as i64` reads like "convert dollars to cents", but it means "truncate". 0.29, 0.57, 1.15, 4.35 and 19.99 all lose a cent that way (`28`, `56`, `114`, `434`, `1998`), because each product lands a hair below the integer. Saturation makes a garbage input look like a valid one: a `NaN` fee rate becomes a 0-cent fee, and a negative amount cast to `u64` becomes 0 rather than an error. C++ leaves the same cast undefined, F# and .NET only became saturating on x64 in .NET 9, and TypeScript wraps modulo 2^32.

**Chew on this**

Which of your `as` casts from `f64` sit on a value that came from a request body, and what would you rather happen on `NaN`? Is truncation ever the rule your business actually wrote down?

**Sources**

- https://doc.rust-lang.org/reference/expressions/operator-expr.html#numeric-cast
- https://doc.rust-lang.org/std/primitive.f64.html#method.round
- https://doc.rust-lang.org/std/primitive.f64.html#method.round_ties_even

**Verified**

The note that `as` became saturating in Rust 1.45 (undefined before) is recalled; the Reference page states the current rules but not when they changed.

**Gotchas**

- `x as i32` truncates, it does not round: `9.99 as i32` is 9 and `-9.99 as i32` is -9.
- `as` never fails. Out-of-range values saturate (`1e10 as i32` is `i32::MAX`, `1e19 as i64` is `i64::MAX`), `NaN` becomes 0, and a negative float cast to an unsigned type becomes 0.
- Integer-to-integer `as` does not saturate, it wraps: `300_i32 as u8` is 44, `-1_i32 as u32` is 4294967295, `3_000_000_000_u32 as i32` is -1294967296. Float casts and integer casts follow opposite rules.
- `f64::round` returns `f64` (`3.0`), not an integer, so storing it still needs `as`.
- `round` sends halves away from zero, but `format!("{:.0}")` sends them to even: 2.5 rounds to 3 and prints as `2`.
- Banker's rounding is a separate method, `round_ties_even`, and needs Rust 1.77.
- `trunc()` is not `as`: `f64::NAN.trunc()` is still `NaN`, while `f64::NAN as i32` is 0.
- `i32::try_from(f64)` does not exist (E0277), so a checked conversion is always hand-written.
- `-7 / 2` is -3 and `-7 % 2` is -1, not -4 and 1. `div_euclid` gives -4 and `rem_euclid` gives 1.
- `((7 / 2) as f64).ceil()` is 3, because the integer division already ran. `7_u32.div_ceil(2)` is 4.
- `(price * 100.0) as i64` turns 0.29 into 28 cents, yet `((0.1 + 0.2) * 100.0) as i64` is 30, so the classic smoke test passes.
- `format!("{:.2}", 1.005)` prints `1.00`, and `(1.005 * 100.0).round() / 100.0` is 1.
- `(-0.4_f64).round()` is `-0.0`, which prints as `-0`.
- `16_777_217_i32 as f32` is 16777216, and `9_007_199_254_740_993_i64 as f64` is 9007199254740992.

## C++: `static_cast<int>(1e10)` is undefined behaviour that happens to saturate on Arm64, and only `rint` rounds half to even

_Idioms and antipatterns_

**Did you know**

A floating-to-integral conversion discards the fraction, and "if the truncated value cannot fit into the destination type, the behavior is undefined", even for an unsigned destination. On Apple clang 21 / Arm64 the hardware instruction saturates (`1e10 -> 2147483647`, `NaN -> 0`), so the UB looks like Rust's defined behaviour until the code runs elsewhere. `-fsanitize=float-cast-overflow` reports it at runtime (`1e+10 is outside the range of representable values of type 'int'`), and inside a `constexpr` it is a compile error. For rounding, `std::round` and `std::lround` go away from zero, while `std::rint`, `lrint` and `nearbyint` follow the current rounding mode, which defaults to ties-to-even (`rint(2.5) == 2`). All of these are C++11 `<cmath>` and available everywhere.

**Show me**

```cpp
#include <cassert>
#include <cmath>
#include <cstdint>
#include <optional>

// static_cast<int64_t> on an out-of-range double is undefined behaviour, so the
// range check must run on the double, before the cast.
std::optional<std::int64_t> to_cents_checked(double amount) {
    const double scaled = std::round(amount * 100.0);  // 0.29 * 100.0 is 28.999999999999996
    constexpr double lower = -9223372036854775808.0;   // -2^63, exact
    constexpr double upper = 9223372036854775808.0;    //  2^63, exact; must be excluded
    if (!(scaled >= lower && scaled < upper)) return std::nullopt;  // also rejects NaN
    return static_cast<std::int64_t>(scaled);
}

int main() {
    assert(static_cast<int>(9.99) == 9);     // truncation toward zero
    assert(static_cast<int>(-9.99) == -9);
    assert(std::floor(-9.99) == -10.0);

    assert(std::round(2.5) == 3.0);          // halves away from zero
    assert(std::round(-2.5) == -3.0);
    assert(std::rint(2.5) == 2.0);           // current rounding mode: FE_TONEAREST = ties to even
    assert(std::lround(2.5) == 3);           // the l-variant of round, not of rint

    assert(static_cast<std::int64_t>(0.29 * 100.0) == 28);  // the lost cent
    assert(to_cents_checked(0.29) == 29);
    assert(!to_cents_checked(NAN));
    assert(!to_cents_checked(1e300));
}
```

**Why it matters**

Because the cast is UB, the optimizer may assume the value was in range, and the hardware result differs by target: Arm64's `fcvtzs` saturates, which is what was measured here. The written form of the check matters too: `!(scaled >= lower && scaled < upper)` rejects `NaN`, but the natural `scaled < lower || scaled >= upper` lets `NaN` through to the cast, since every comparison with `NaN` is false. Rust made the same cast defined and saturating. F# and .NET made it saturating on x64 only in .NET 9. TypeScript has no undefined result, only a wrong one.

**Chew on this**

How many of your `static_cast<int>` calls on a `double` have a range check before them, rather than after? Does your CI ever run `-fsanitize=float-cast-overflow` on a build where it could fire?

**Sources**

- https://en.cppreference.com/w/cpp/language/implicit_conversion
- https://en.cppreference.com/w/cpp/numeric/math/round
- https://en.cppreference.com/w/cpp/numeric/math/rint

**Verified**

Arm64 only. An x86-64 build was not run, so its result for the out-of-range cast is not measured here.

**Gotchas**

- `static_cast<int>(9.99)` truncates to 9; it does not round.
- An out-of-range or `NaN` double-to-int cast is undefined behaviour, unsigned destinations included. Arm64 happened to saturate (`1e10` to `INT_MAX`, `NaN` to 0, `-1.5` to `unsigned` 0), so it can pass every local test.
- `-fsanitize=float-cast-overflow` reports that cast at runtime, and inside a `constexpr` it is a compile error. Nothing else warns.
- Integer narrowing is a different rule and wraps: `static_cast<unsigned char>(300)` is 44 and `static_cast<unsigned>(-1)` is 4294967295.
- `std::round` returns `double`; `std::lround` and `std::llround` are the ones that return integers.
- `std::round` sends halves away from zero, while `std::rint` and `std::nearbyint` use the current rounding mode, which defaults to ties-to-even (2.5 gives 2).
- `rint` follows `std::fesetround`: under `FE_UPWARD`, `rint(2.1)` is 3 while `std::round(2.1)` stays 2 (built with `-frounding-math`).
- `printf("%.0f", 2.5)` and `std::format("{:.0f}", 2.5)` print `2`, while `std::round(2.5)` is 3.
- `(int)(x + 0.5)` is not rounding: it gives -2 for -2.7.
- `std::ceil(7 / 2)` is 3, because integer division ran first. `(7 + 2 - 1) / 2` is 4.
- `-7 / 2` is -3 and `-7 % 2` is -1, so `n % 2 == 1` misses negative odd numbers.
- `std::lround(NaN)` raises `FE_INVALID` and returned 0 here.
- `std::round(-0.4)` is negative zero, and both `printf("%g")` and `std::cout` print `-0`.
- `std::trunc(NaN)` stays `NaN`; only the cast to an integer is undefined.
- `static_cast<float>(16777217)` is 16777216.

## F#: `round 2.5` is 2.0, and `Checked.int` is the only checked float-to-int conversion of the four

_Idioms and antipatterns_

**Did you know**

F#'s `round` is `Math.Round`, which "rounds midpoint values to the nearest even number": `round 2.5 = 2.0`, `round 3.5 = 4.0`, `round 0.5 = 0.0`, and the same holds for `decimal` (`round 2.5m = 2`). You need `Math.Round(value, MidpointRounding.AwayFromZero)` to get the Rust or C++ `round` answer. `int` truncates toward zero, and out-of-range handling is the runtime's: saturating on Arm64 (measured, .NET 8) and on x64 from .NET 9, but `int.MinValue` for an out-of-range value on .NET 8 x64. `Checked.int` raises `OverflowException` on `1e10` and on `nan` (measured), which makes it the only checked float-to-int conversion built into any of the four languages.

**Show me**

```fsharp
// F# 8, FSharp.Core 8.0.0, .NET 8.0.8 on Arm64 (dotnet fsi)
// `round` is Math.Round: halves go to the EVEN neighbour, not away from zero.
printfn "%g %g %g" (round 2.5) (round 3.5) (round -2.5)                            // 2 4 -2
printfn "%g" (System.Math.Round(2.5, System.MidpointRounding.AwayFromZero))         // 3

// `int` truncates toward zero, like Rust's `as` and C++'s static_cast.
printfn "%d %d %g" (int 9.99) (int -9.99) (floor -9.99)                             // 9 -9 -10

// Unchecked `int` saturates here (Arm64; x64 too since .NET 9), NaN -> 0.
printfn "%d %d" (int 1e10) (int nan)                                                // 2147483647 0

// Checked.int raises instead: the one checked float-to-int of the four languages.
let to_units_checked (amount: float) : int option =
    try Some (Checked.int amount) with :? System.OverflowException -> None
printfn "%A %A %A" (to_units_checked 9.99) (to_units_checked 1e10) (to_units_checked nan) // Some 9 None None

// The lost cent, and the banker's-rounding twist on an exact half.
printfn "%d %d" (int (0.29 * 100.0)) (int (round (0.29 * 100.0)))                   // 28 29
printfn "%g" (round (2.675 * 100.0))                                                // 268: 267.5 is exact, 268 is even
printfn "%d" (int (round 2.5m))                                                     // 2: decimal rounds to even too
```

**Why it matters**

Port a pricing rule from a Rust or C++ service into F#, keep the word `round`, and every exact half now goes to the even neighbour. Totals drift by a cent on exactly the inputs a test fixture with `x.50` prices would catch, and on nothing else. The .NET 8 to .NET 9 change matters for the cast: the same `int amount` line returned `int.MinValue` on x64 and `int.MaxValue` on Arm64 until .NET 9 made both saturate. A limit check written against one of those results quietly inverts on the other.

**Chew on this**

Do your F# services and your Rust or C++ services agree on which way 0.5 rounds, and has anyone checked rather than assumed? Where would `Checked.int` replace `int` in your code without a measurable cost?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.math.round
- https://learn.microsoft.com/en-us/dotnet/core/compatibility/jit/9.0/fp-to-integer

**Verified**

The .NET 8 x64 result (`int.MinValue`) comes from the .NET 9 breaking-change page and was not run here. That F#'s `round` maps to `Math.Round` was observed in its output, not read in FSharp.Core's source.

**Gotchas**

- `round` is ties-to-even, not "round down": 2.5 gives 2, but 3.5 gives 4.
- `round` returns `float`; an integer takes `int (round value)`.
- `int` truncates: `int 9.99` is 9 and `int 3.5` is 3.
- `int "9.99"` throws `FormatException`: on a string, `int` parses instead of truncating. `int (float "9.99")` is 9.
- Unchecked `int` on an out-of-range float saturates on Arm64, and on x64 from .NET 9. On .NET 8 x64 it gave `int.MinValue` (documented, not run here).
- `int nan` is 0, but `truncate nan` is still `nan`.
- `Checked.int` raises `OverflowException` on `1e10` and on `nan`, and `Checked.byte 300` raises too.
- Unchecked integer narrowing wraps: `byte 300` is 44, `uint32 -1` is 4294967295, `int32 3000000000u` is -1294967296.
- `Math.Round(1.005, 2, MidpointRounding.AwayFromZero)` is still 1, because the stored double is below the half.
- `Math.Round(2.675, 2)` is 2.68, but `sprintf "%.2f" 2.675` prints `2.67`.
- `MidpointRounding.ToZero`, `ToNegativeInfinity` and `ToPositiveInfinity` apply to every value, not only halves: `Math.Round(2.1, MidpointRounding.ToPositiveInfinity)` is 3.
- `decimal` and `float32` round to even too: `round 2.5m` is 2 and `round 2.5f` is 2.
- `ceil (float (7 / 2))` is 3, because the integer division ran first.
- `-7 / 2` is -3 and `-7 % 2` is -1.
- `string (round -0.4)` is `"-0"`.
- `float32 16777217` is 16777216.

## TypeScript: `Math.round(-2.5)` is -2, `x | 0` wraps modulo 2^32, and `parseInt(0.0000005)` is 5

_Idioms and antipatterns_

**Did you know**

`Math.round` rounds halves toward positive infinity, so `Math.round(2.5)` is 3 but `Math.round(-2.5)` is -2, an answer none of the other three gives with its default `round`. The `| 0` and `~~` truncation idioms go through ToInt32, which wraps modulo 2^32: `1e10 | 0` is 1410065408 and `4294967295.5 | 0` is -1. `parseInt` converts its argument to a string first, and `0.0000005` stringifies as `"5e-7"`, so `parseInt(0.0000005)` is 5. `(1.005).toFixed(2)` is `"1.00"`, because 1.005 is stored as 1.00499999...

**Show me**

```ts
// Node 22.17.1, tsc 6.0.3. All values below were printed by this file.
const halves: number[] = [Math.round(2.5), Math.round(-2.5), Math.round(3.5)];
console.log(halves); // [3, -2, 4]: halves round toward +Infinity, so -2.5 -> -2

// Four ways to "drop the fraction", and they disagree on negatives and on range.
const amount_negative = -9.99;
console.log(
  Math.trunc(amount_negative),
  Math.floor(amount_negative),
  amount_negative | 0,
); // -9 -10 -9

// `| 0` (and `~~`) is ToInt32: modulo 2^32, not saturation.
console.log(1e10 | 0, (2 ** 31) | 0, 4294967295.5 | 0, NaN | 0); // 1410065408 -2147483648 -1 0

// parseInt reads the STRING form of a number, and 0.0000005 prints as "5e-7".
console.log(parseInt(String(0.0000005)), parseInt(String(9.99))); // 5 9

// The lost cent, then the same value through toFixed.
const price = 0.29;
console.log(
  Math.trunc(price * 100),
  Math.round(price * 100),
  (1.005).toFixed(2),
); // 28 29 "1.00"

const to_cents_checked = (value: number): number | undefined => {
  const scaled = Math.round(value * 100);
  return Number.isSafeInteger(scaled) ? scaled : undefined; // rejects NaN, Infinity, > 2^53 - 1
};
console.log(
  to_cents_checked(price),
  to_cents_checked(NaN),
  to_cents_checked(1e300),
); // 29 undefined undefined
```

**Why it matters**

`number` is the only numeric type the checker sees, so `x | 0`, `Math.trunc`, `Math.floor` and `parseInt` all type-check identically while giving four different answers for the same negative or out-of-range input. The asymmetric `Math.round` means a refund computed as `-Math.round(charge)` does not equal `Math.round(-charge)` on a half, and the two halves of a ledger stop balancing by a cent. Rust and C++ round symmetrically, and F# rounds to even. Only TypeScript's default depends on the sign.

**Chew on this**

Where in your code does `| 0` or `~~` stand in for `Math.trunc`, and can its input ever reach 2^31? If a negative half and a positive half round differently, which of your totals would notice first?

**Sources**

- https://www.typescriptlang.org/docs/handbook/2/everyday-types.html

**Verified**

Every value was measured on Node 22.17.1. The ECMAScript rules behind them (Math.round, ToInt32, parseInt) were not read from the specification here, so they rest on measurement.

**Gotchas**

- `Math.round` rounds halves toward positive infinity: `Math.round(2.5)` is 3 but `Math.round(-2.5)` is -2.
- `toFixed` rounds halves away from zero and returns a string: `(-2.5).toFixed(0)` is `"-3"`, and `'1' + (2.5).toFixed(0)` is `"13"`.
- `(1.005).toFixed(2)` is `"1.00"`, but `Intl.NumberFormat` with two digits prints `1.01`. On 0.125, `toFixed(2)` gives `"0.13"`, while Rust, C++ and F# print `0.12`.
- `Intl.NumberFormat` defaults to half-away-from-zero (2.5 gives 3, -2.5 gives -3); `roundingMode: "halfEven"` changes that.
- `x | 0` and `~~x` are ToInt32, which wraps modulo 2^32: `1e10 | 0` is 1410065408, `2 ** 31 | 0` is -2147483648, and `(2 ** 32 + 5) | 0` is 5.
- `x >>> 0` turns -1.5 into 4294967295.
- `parseInt` parses the string form: `parseInt(0.0000005)` is 5 and `parseInt(1e21)` is 1. tsc rejects a number argument (TS2345), but a value typed `any` passes.
- `Math.round('2.5')` is 3 and `Math.round(null)` and `Math.round('')` are 0, while `Math.round(undefined)` is `NaN`. tsc rejects the string literal (TS2345), but not an `any`.
- `Number.isInteger(1e300)` is true; `Number.isSafeInteger` is the check that means "exact".
- `Math.floor(-7 / 2)` is -4 and `Math.trunc(-7 / 2)` is -3, while Rust, C++ and F# integer division give -3.
- `Math.ceil(7 / 2)` is 4: `/` is always float division, so the integer-division `ceil` bug of the other three cannot happen here.
- `-7 % 2` is -1.
- `Math.floor(x + 0.5)` is not `Math.round`: it gives 1 for `0.49999999999999994`, where `Math.round` gives 0.
- `BigInt(9.99)` throws `RangeError`, and `BigInt(2 ** 53 + 1)` is 9007199254740992 because the number had already rounded.
- `Math.round(-0.4)` is `-0`: `String` gives `"0"`, `console.log` shows `-0`, and `(-0.4).toFixed(0)` is `"-0"`.

# The functional angle: none of the four ships a total float-to-int function, so `float -> int option` is always yours to write

Draws on all four tips: each one ended with a `to_cents_checked` or `to_units_checked` written by hand.

Converting a float to an integer is a partial function: `NaN`, the infinities and out-of-range values have no right answer. The functional fix is to make it total by moving the failure into the type, `float -> int option`. No standard library here provides that function. What differs is what each one gives you to build it from:

| Language   | Building block                                    | Total form                                                         | What it costs                                                                       |
| ---------- | ------------------------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| F#         | `Checked.int` raises `OverflowException`          | `try Some (Checked.int amount) with :? OverflowException -> None`  | an exception on every failure, about 18 microseconds each against 0.01 for a success (measured); still no `tryInt` in FSharp.Core |
| Rust       | none: `i32::try_from(f64)` does not exist (E0277) | `is_finite()` plus a bounds check, then `then_some(scaled as i64)` | the bounds are yours to get exactly right (`< i64::MAX as f64`, not `<=`)           |
| C++        | none, and the unchecked cast is UB                | `std::optional` plus a negated `>= && <` check before the cast     | the check's form decides whether `NaN` reaches the UB                               |
| TypeScript | `Number.isSafeInteger`                            | `Math.round`, then `isSafeInteger ? scaled : undefined`            | cheapest of the four; "safe" means below 2^53, not "fits in an int32"               |

No row needs mutation: every total form is one expression over the input. F# is the only language with a primitive that refuses, and even it reports refusal through an exception, so the `Option` still comes from a wrapper.

Gotchas, all measured:

- Rust's `bool::then_some` evaluates its argument even when the condition is false; only `then(|| ...)` is lazy. The cast in `in_range.then_some(scaled as i64)` therefore always runs, which is harmless only because Rust's `as` is defined on every input. The same eager shape in C++ would run the undefined cast.
- The upper bound has to be `<`, not `<=`: `i64::MAX as f64` is exactly 2^63, one past the largest `i64`, and `9223372036854775808.0_f64 as i64` quietly saturates to `i64::MAX`. With `<=`, that input passes the check and comes back as the wrong value.
- F#'s exception-based `Option` is cheap when inputs are valid and expensive when they are not: about 0.01 microseconds per accepted value against about 18 microseconds per rejected one. A bad batch of input is roughly 1800 times slower, which matters when the bad input is what an attacker sends.
- In C++, an `std::optional<std::int64_t>` holding 0 is truthy: `if (auto cents = to_cents_checked(0.001))` takes the branch with `cents` equal to 0, because the test asks "is there a value", not "is it nonzero".
- TS `Number.isSafeInteger(-0)` is true, so `to_cents_checked(-0.004)` returns `-0` rather than `0` or `undefined`, and the `-0` from the FAQ reaches the ledger.

Should the conversion return `None`, or the reason (`NaN`, overflow, negative) it refused?

# The security angle: a conversion that cannot fail can still hand the attacker a zero, a max, or a negative

Draws on all four tips (Mode C, the missing check). The direction is mixed. Rust and TypeScript define a result for every input, which prevents undefined behaviour but not wrong values. C++ prevents nothing. F# prevents it only through `Checked.int`. This is CWE-681 (incorrect conversion between numeric types) and CWE-197 (numeric truncation error), with CWE-190 for the TypeScript wrap.

```ts
// Looks like "whole items only". 4294967295.5 | 0 is -1 (measured),
// so a crafted quantity turns a charge into a credit.
const quantity: number = body.quantity | 0;
const total_cents: number = quantity * unit_price_cents;
```

```rust
// Looks like "fees are never negative". A NaN rate saturates to 0 and a
// negative amount saturates to 0 (both measured): the fee silently vanishes.
let fee_cents = (amount * rate) as u64;
```

```cpp
// Looks like a limit check. The cast is UB for requested >= 2^31, and
// the result depends on the target; Arm64 gives INT_MAX (measured).
if (static_cast<int>(requested) > daily_limit) reject();
```

| Language   | What goes wrong                                              | What the language does                             | Still on you                                             |
| ---------- | ------------------------------------------------------------ | -------------------------------------------------- | -------------------------------------------------------- |
| Rust       | `NaN` and negatives saturate to 0, huge values to max        | defines every result; never UB                     | `is_finite()` and a sign and range check before the cast |
| C++        | out-of-range cast is UB, result differs by target            | nothing at runtime; `constexpr` and UBSan catch it | the check on the `double`, written so `NaN` fails it     |
| F#         | unchecked `int` differed between x64 and Arm64 before .NET 9 | `Checked.int` raises; .NET 9 saturates everywhere  | use `Checked.int` at trust boundaries, or validate first |
| TypeScript | `\| 0` wraps to a negative; `parseInt` reads `5e-7` as 5     | nothing: every result is a valid `number`          | `Number.isSafeInteger` plus a sign check on input        |

Rust is the control here for what "defined" buys: no undefined behaviour, but the attacker still chooses between 0 and the maximum. C++ is the control for what the optimizer may assume once a check is missing.

Gotchas, all measured:

- Validate the converted value, not the input: `0.5 > 0` is true, but `0.5 | 0` is 0, so a check on the float lets a zero quantity through.
- A saturating cast can turn an out-of-range input into one that passes a limit check: Rust's `-1.0_f64 as u64` is 0, so `(requested as u64) > limit` is false for a negative request.
- JSON can deliver values the schema never mentions: `JSON.parse('{"quantity": 1e400}')` gives `Infinity`, which `| 0` turns into 0, and `{"refund": -0}` arrives as `-0`.
- `parseInt` accepts junk: `parseInt("12abc")` is 12, `parseInt("1e3")` is 1 and `parseInt("0x10")` is 16. `Number("12abc")` is `NaN`, but `Number("")` is 0. Rust refuses all of these: `"12abc".parse::<i32>()` and `"9.99".parse::<i32>()` both return `Err`. This is CWE-20, improper input validation, on top of the conversion classes above.
- F#'s `open Checked` changes every operator in its scope, not only conversions: inside it, `Int32.MaxValue + 1` throws `OverflowException`, while outside it the same expression wraps to -2147483648. That is safer, but a reviewer reading the arithmetic cannot tell which mode applies without looking for the `open`.

Which of your request fields is a float on the wire but a count, a quantity or a cent amount in your code?

# FAQ

Every value here was measured on rustc 1.95.0, Apple clang 21 (libc++), F# 8 with FSharp.Core 8.0.0 on .NET 8.0.8 (`dotnet fsi`), and Node 22.17.1. Each question is a common misreading, and most of them have shipped as bugs.

**Is F#'s `round` rounding down?**

No. It rounds to the nearest whole number, and only an exact half is special: a half goes to the even neighbour. So `round 2.5 = 2` goes down, but `round 3.5 = 4` goes up, `round -2.5 = -2` and `round -3.5 = -4`. Anything that is not exactly a half rounds as you would expect: `round 2.51 = 3`, `round 2.49 = 2`. Rounding down is `floor`.

Gotchas for this answer:

- Ties-to-even applies at every digit count, not only to whole numbers: `Math.Round(0.125, 2)` is 0.12.
- "Rounding down" means toward negative infinity, which is `floor`, not `int`: `floor -2.5` is -3, while `int -2.5` is -2.

**Why would a library default to ties-to-even?**

Rounding every half the same way biases a total. The four halves 0.5 + 1.5 + 2.5 + 3.5 sum to 8. Rounded away from zero first, they sum to 10. Rounded to even, they sum to 8, because two halves went down and two went up. The `Math.Round` documentation shows the same bias using a mean. It is also what the floating-point environment's default mode (`FE_TONEAREST`) does, which is why C++ `std::rint(2.5)` is 2.

Gotchas for this answer:

- Ties-to-even only cancels out when the halves land on odd and even neighbours alike. Prices of 1.50, 3.50, 5.50 and 7.50 all round up under it: the true total is 18, and ties-to-even and away-from-zero both give 20.
- It only decides an exact half, and most decimal halves are not exact in binary, so the rounding mode is often not what decides the result (see "Why does rounding 1.005 to two places give 1.00?").

**Is C# the same?**

Yes. F#'s `round` gave the same result as `Math.Round` on every value measured here, and `Math.Round(2.5)` in C# is that same BCL method. C# itself was not run.

Gotchas for this answer:

- .NET has two float-to-int conversions that disagree. F#'s `int 9.99` truncates to 9, as a C# `(int)` cast does (the C# cast itself was not run). `Convert.ToInt32` rounds to even instead: `Convert.ToInt32(9.99)` is 10, `Convert.ToInt32(2.5)` is 2 and `Convert.ToInt32(3.5)` is 4 (measured from F#, calling the same BCL method).
- `decimal` and `double` format differently: `(8.5m).ToString("C0")` prints `$9`, but `(8.5).ToString("C0")` prints `$8`.

**How do I get Rust's or TypeScript's answer in F#?**

For the Rust and C++ `round` answer, use `Math.Round(value, MidpointRounding.AwayFromZero)`: 2.5 gives 3 and -2.5 gives -3. TypeScript's halves-toward-positive-infinity has no matching mode. The other three `MidpointRounding` members are not tie rules at all, they are directed rounding: `ToZero` truncates, `ToNegativeInfinity` floors and `ToPositiveInfinity` takes the ceiling, so `Math.Round(2.1, MidpointRounding.ToPositiveInfinity)` is 3. The usual stand-in, `floor (value + 0.5)`, matches `Math.round` on halves (3 and -2) but not on `0.49999999999999994`, where F# gives 1 and Node gives 0. The addition itself rounds up to `1.0` before `floor` sees it.

Gotchas for this answer:

- With a digit count, the mode still works on the stored double, and the results are inconsistent: `Math.Round(2.345, 2, MidpointRounding.AwayFromZero)` is 2.35 and `Math.Round(2.675, 2)` is 2.68, but `Math.Round(1.005, 2, MidpointRounding.AwayFromZero)` is 1.
- "TypeScript's answer" depends on which TS call you mean. `Math.round(-2.5)` is -2, but `(-2.5).toFixed(0)` and `Intl.NumberFormat` give -3, which is what `MidpointRounding.AwayFromZero` gives (-3).

**`int 2.5` is also 2. Is that the same rule?**

No, that is a coincidence. `int` truncates toward zero, so `int 3.5 = 3` while `round 3.5 = 4`.

Gotchas for this answer:

- The coincidence also holds for -2.5 (`int -2.5` and `round -2.5` are both -2) and breaks at -3.5: `int -3.5` is -3, while `round -3.5` is -4.
- `decimal` truncates the same way: `int 2.5m` is 2.

**Does `round` return an integer?**

No, in all four it returns a float: Rust `2.5_f64.round()` is `3.0_f64`, and C++ `std::round`, F# `round` and JS `Math.round` return a `double`, a `float` and a `number`. In Rust, C++ and F#, getting an integer still takes a cast, which brings back the cast rules above. C++ also has `std::lround` and `std::llround`, which round to a `long` directly.

Gotchas for this answer:

- Casting the rounded float brings the cast rules back: Rust's `1e10_f64.round() as i32` is `i32::MAX`, saturated.
- In JS, "integer" does not mean "fits in an int": `Number.isInteger(Math.round(1e300))` is true.
- C++ `std::lround(NaN)` raises `FE_INVALID` and returned 0 here.

**Does printing with zero decimals round the same way as `round`?**

Only in F#. Formatting follows its own rule in each language:

| Language   | Format call                               | 0.5 | 2.5 | -2.5 | Same as the language's `round`? |
| ---------- | ----------------------------------------- | --- | --- | ---- | ------------------------------- |
| Rust       | `format!("{:.0}", value)`                 | 0   | 2   | -2   | No: `round` gives 1, 3, -3      |
| C++        | `printf("%.0f")`, `std::format("{:.0f}")` | 0   | 2   | -2   | No: `std::round` gives 1, 3, -3 |
| F#         | `sprintf "%.0f"`, `ToString("F0")`        | 0   | 2   | -2   | Yes, both go to even            |
| TypeScript | `toFixed(0)`                              | 1   | 3   | -3   | No: `Math.round(-2.5)` is -2    |
| TypeScript | `Intl.NumberFormat` (default)             | 1   | 3   | -3   | No, same split as `toFixed`     |

So in Rust and C++, the number a log line prints and the number the code stores differ on every exact half. `Intl.NumberFormat` takes `roundingMode: "halfEven"` (Node 22) to match F#.

Gotchas for this answer:

- Negative zero survives formatting: Rust's `format!("{:.0}", -0.4)` and JS `(-0.4).toFixed(0)` both print `-0`.
- C++ iostreams agree with `printf`, not with `std::round`: `std::cout << std::fixed << std::setprecision(0) << 2.5` prints `2`, and 0.5 prints `0`.

**Why does rounding 1.005 to two places give 1.00?**

It is not the rounding mode. 1.005 has no exact binary form and is stored slightly below 1.005, so `1.005 * 100` is `100.49999999999999`. `(value * 100).round() / 100` gives 1 in all four languages, and `Math.Round(1.005, 2, MidpointRounding.AwayFromZero)` is still 1. The answers do not even agree within one language. In .NET, `Math.Round(2.675, 2)` is 2.68, but `sprintf "%.2f" 2.675` prints `2.67`. In JS, `(1.005).toFixed(2)` is `"1.00"`, but `Intl.NumberFormat` with two digits prints `1.01`. Both pairs are measured; why each library lands where it does was not established here. F#'s `decimal` (the .NET type) is the only exact base-10 type in any of the four standard libraries: `Math.Round(2.675m, 2)` is 2.68 with either midpoint rule.

Gotchas for this answer:

- Scaling only moves the error, it does not remove it: `1.005 * 1000` is `1004.9999999999999`.
- The popular `Number.EPSILON` fix only works sometimes: `Math.round((1.005 + Number.EPSILON) * 100) / 100` is 1.01, and 1000.005 gives 1000.01, but 10.075 gives 10.07.
- Converting a double to an exact type behaves differently by library. F#'s `decimal 2.675` is `2.675`, so `Math.Round(decimal 2.675, 2)` is 2.68, but Java's `new BigDecimal(2.675)` built from the double rounds to 2.67 at two places. Build exact values from literals or strings (`2.675m`, `new BigDecimal("2.675")`), not from a double.

**Does integer division round down?**

No, Rust, C++ and F# truncate toward zero: `-7 / 2` is -3, not -4, and the remainder takes the dividend's sign, so `-7 % 2` is -1. Rust adds `div_euclid` (-4) and `rem_euclid` (1). TypeScript has no integer division, so the port matters: `Math.floor(-7 / 2)` is -4 and `Math.trunc(-7 / 2)` is -3. Translating Rust's `a / b` as `Math.floor(a / b)` changes every negative result.

Gotchas for this answer:

- One division overflows: the smallest integer divided by -1. Rust's `i32::MIN / -1` panics, F#'s `Int32.MinValue / -1` throws `OverflowException`, and C++'s `INT_MIN / -1` is undefined behaviour, which returned -2147483648 on Arm64 (UBSan: "cannot be represented in type 'int'"). In JS, `(-(2 ** 31) / -1) | 0` silently wraps back to -2147483648.
- The remainder takes the dividend's sign, never the divisor's: `7 % -2` is 1 in Rust, F# and JS.

**Why does `n % 2 == 1` say -3 is not odd?**

Because `-3 % 2` is -1 in all four languages, and the naive check returned false for -3 in every one of them. Test `n % 2 != 0` instead, or in Rust use `n.rem_euclid(2) == 1`.

Gotchas for this answer:

- Testing the low bit is safe for negatives, but operator precedence is not. In C++ and JS, `n & 1 == 0` parses as `n & (1 == 0)`, so it is false even for -4. Rust gives true, because its `&` binds tighter than `==`. tsc rejects the JS form (TS2363), clang warns (`-Wparentheses`), and F#'s `-4 &&& 1 = 0` is true.

**Is `(int)(x + 0.5)` a rounding function?**

Only for non-negative inputs. `-2.7 + 0.5` is `-2.2`, which truncates to -2, while every language's `round(-2.7)` gives -3. All four agree: Rust `as i32`, C++ `static_cast<int>`, F# `int` and JS `Math.trunc` all return -2.

Gotchas for this answer:

- It fails for some non-negative inputs too, because the addition itself rounds: `floor(0.49999999999999994 + 0.5)` is 1, and `floor(4503599627370497 + 0.5)` is 4503599627370498 (Rust and JS both). JS `Math.round(4503599627370497)` returns it unchanged.

**Why does a report show "-0"?**

`round(-0.4)` and `ceil(-0.4)` return negative zero. Rust `{}`, C++ `printf("%g")` and `std::cout`, and F# `string` all print `-0`. JS is split: `String`, template literals and `JSON.stringify` print `0`, but `console.log` shows `-0`, and `(-0.4).toFixed(0)` is `"-0"`. Since `-0 == 0` is true in all four, a test comparing numbers passes while the printed report shows the minus sign.

Gotchas for this answer:

- Division tells the two zeros apart: `1 / -0` is `-Infinity` in JS and `-inf` in Rust. `Object.is(-0, 0)` is false.
- JSON drops the sign: `JSON.stringify({ total: -0 })` is `{"total":0}`, while `console.log` shows `-0`.
- The cheapest fix is adding zero: `-0.0 + 0.0` is `0` in Rust, and `-0 + 0` is `0` in JS.

**Is converting an integer to a float safe?**

Not above 2^24 for a 32-bit float or 2^53 for a 64-bit one, where integers start to round. `16777217` becomes `16777216` as `f32`, `float32` or `Math.fround`, and `9007199254740993` becomes `9007199254740992` as `f64`, `double` or `float`. In JS, `2 ** 53 + 1` evaluates to `9007199254740992`. No language warns: it is the reverse of this special's topic, and just as silent.

Gotchas for this answer:

- A round trip does not restore the value: Rust's `9_007_199_254_740_993_i64 as f64 as i64` is 9007199254740992. `i64::MAX as f64 as i64` does come back as `i64::MAX`, but only because the cast saturates.
- C++ hides it in the comparison: `static_cast<double>(LLONG_MAX) == LLONG_MAX` is true, because both sides become 2^63, and casting that double back to `long long` is undefined behaviour (UBSan: outside the range). clang does warn on the conversion (`-Wimplicit-const-int-float-conversion`).
- In JS, `9007199254740993 === 9007199254740992` is true. The TypeScript editor flags such a literal (80008, "too large to be represented accurately as integers") as a suggestion, not a compile error.

**How do I round $9.50 to the nearest dollar so it comes out as $10?**

First decide the rule, because "nearest dollar" says nothing about the half. The usual commercial rule is half away from zero: $9.50 becomes $10, $8.50 becomes $9, and a $9.50 refund (-9.50) becomes -$10. The two traps are that plain `round` in F# returns 10 for 9.50 only because 10 happens to be even (8.50 gives 8), and that `Math.round(-9.5)` in JS is -9. Each language below has a float form (one call or a short lambda) and an integer-cents form, the one to prefer for money. All were measured on 9.50, 8.50, -9.50 and 9.49, giving 10, 9, -10 and 9.

```rust
let round_to_dollar = |amount: f64| -> f64 { amount.round() }; // f64::round is already half away from zero
let cents_to_dollars = |cents: i64| -> i64 { (cents.abs() + 50) / 100 * cents.signum() };
```

```cpp
auto round_to_dollar = [](double amount) { return std::lround(amount); };  // half away from zero, returns long
auto cents_to_dollars = [](std::int64_t cents) {
    const std::int64_t whole = (std::llabs(cents) + 50) / 100;
    return cents < 0 ? -whole : whole;
};
```

```fsharp
// Name the midpoint rule: plain `round` goes to even, so `round 8.50` is 8.
let round_to_dollar = fun (amount: float) -> Math.Round(amount, MidpointRounding.AwayFromZero)
let cents_to_dollars = fun (cents: int64) -> int64 (sign cents) * ((abs cents + 50L) / 100L)
```

```ts
// No single call: Math.round(-9.5) is -9, so mirror the sign around it.
const round_to_dollar = (amount: number): number => Math.sign(amount) * Math.round(Math.abs(amount))
const cents_to_dollars = (cents: bigint): bigint => {
    const whole = ((cents < 0n ? -cents : cents) + 50n) / 100n
    return cents < 0n ? -whole : whole
}
```

The integer forms work by adding half a dollar (50 cents) to the size of the amount and letting `/` truncate, then putting the sign back. That is the `(int)(x + 0.5)` trick from earlier in this FAQ, made safe for negatives by doing it on the absolute value. In F#, `Math.Round(9.50m, MidpointRounding.AwayFromZero)` on a `decimal` also gives 10.

Gotchas for this answer, all measured unless marked:

- F#'s plain `round 9.50` is 10 only because 10 is even: `round 8.50` is 8.
- JS `Math.round(-9.5)` is -9, so a refund comes out a dollar smaller than the charge it reverses.
- Leaving out the `abs` breaks refunds: `(-950 + 50) / 100` is -9, not -10 (measured in Rust and TypeScript; C++ and F# use the same truncating `/`). Rust's `div_euclid` does not rescue it either: it also gives -9, which is JS's half-up rule.
- Round the total or round each line, but decide which: $4.25 + $4.25 + $1.00 is $9.50 and rounds to $10, while rounding each line first gives 4 + 4 + 1 = $9.
- The displayed dollar can disagree with the stored one. In .NET, `(8.5).ToString("C0")` prints `$8`, because double formatting goes to even, while `(8.5m).ToString("C0")` on a `decimal` prints `$9`, matching `Math.Round(8.5, MidpointRounding.AwayFromZero)`. JS `Intl.NumberFormat` with `style: "currency"` and zero digits prints 8.5 as `$9` and -0.4 as `-$0`.
- `NaN` passes through every float form silently: Rust `f64::NAN.round()` is `NaN` (and `as i64` then makes it 0), F# `Math.Round(nan, ...)` is `nan`, and the TS lambda returns `NaN`. F#'s `sign nan` is the exception: it throws `ArithmeticException`.
- `abs` of the smallest integer fails: Rust `i64::MIN.abs()` panics in a debug build (`i64::MIN.unsigned_abs()` works), and F# `abs Int64.MinValue` throws `OverflowException`. In C++, `std::llabs(LLONG_MIN)` is undefined behaviour (documented, not run). TypeScript's `bigint` has no minimum.
- The TS float form returns `-0` for -0.4: `String` prints `0`, but the `Intl` currency format above prints `-$0`.
- C++ `std::lround` returns `long`, which is 32 bits on 64-bit Windows, so amounts past about $2.1 billion need `std::llround` (documented, not measured here).
- Not a gotcha, though it is often assumed to be: 9.50 is exact in binary, unlike 1.005, so the float forms are safe for it when the input really is 9.50. All six computations tried here (0.95 * 10, 9.45 + 0.05, 1.9 * 5, 0.1 * 95, 9 + 0.1 + 0.4, 19 * 0.5) landed exactly on 9.5.

# Appendix A: the Superman III half cent, and a split that never loses one

Not part of the tip rotation. Written 2026-10-20 to back the whole special. The plot summary is from memory; every snippet was compiled and run on the toolchains listed at the top of this entry.

## A.1 The story

In _Superman III_ (1983), Richard Pryor plays Gus Gorman, a payroll programmer who notices that pay calculations produce fractions of a cent that the system simply drops. He has the program send those fractions to an account of his own. Each one is worth nothing, but across every paycheck they add up to a large check, and he gives himself away by turning up for work in an expensive sports car. _Office Space_ (1999) names the film when its characters copy the scheme. The real-world name for it is [salami slicing](https://en.wikipedia.org/wiki/Salami_slicing_tactics); the article's "Financial schemes" section describes diverting rounded-off fractions, and it lists both films.

The scheme only works because of a quieter bug: the books never balanced to begin with. A rounding step that discards a remainder makes money disappear, and nobody notices a cent that was never posted anywhere.

## A.2 The leak, in one line

Split $100.00 three ways in integer cents: `10000 / 3` is 3333, and three of those are 9999. The same thing happens with floats: `Math.round(10000 / 3) * 3` is 9999. One cent is gone, in every language, and nothing reports it.

An uneven three-way split is not the bug. In every language, 10000 cents split three ways can only be 3334 + 3333 + 3333. That is very trivial, common-sense knowledge. The bug is that we tend to rely on just one function, `round`, `floor`, `/` or `%`, and assume it will divide the money correctly or round it up for us. None of them decides who gets the extra cent, and none of them even says that it exists. The fix is not a one-liner, but it is not a module either: it is one small lambda that needs careful authoring, and each of these has to be in it:

1. Money in integer cents (or an exact decimal type), never in a float.
2. The floor share, from `/`.
3. The leftover, from `%`, kept non-negative (A.3 shows why that matters).
4. The leftover handed out one cent at a time, by a rule someone wrote down.

Around the lambda go two more lines of defence: a test that the parts sum to the total, and, wherever a share must be rounded anyway, a named rounding account for the difference (A.4). Drop any one of them and Gus is back in business.

## A.3 A split that never loses a cent, one lambda per language

The fix is to stop rounding each share on its own. Give every share the floor, then hand out the leftover cents (`total % ways`, always fewer than `ways`) one each to the first slots. The parts then sum to the total by construction.

```rust
// div_euclid/rem_euclid keep the remainder non-negative, so refunds (negative totals) split exactly too.
let split_cents = |total_cents: i64, ways: i64| -> Vec<i64> {
    (0..ways)
        .map(|slot| total_cents.div_euclid(ways) + i64::from(slot < total_cents.rem_euclid(ways)))
        .collect()
};
// split_cents(10_000, 3) == [3334, 3333, 3333]; split_cents(-10_000, 3) == [-3333, -3333, -3334]
```

```cpp
// total_cents >= 0 only: C++ % takes the dividend's sign, so a negative total loses a cent.
auto split_cents = [](std::int64_t total_cents, std::int64_t ways) {
    std::vector<std::int64_t> parts;
    for (std::int64_t slot = 0; slot < ways; ++slot)
        parts.push_back(total_cents / ways + (slot < total_cents % ways ? 1 : 0));
    return parts;
};
// split_cents(10'000, 3) == {3334, 3333, 3333}; split_cents(-10'000, 3) sums to -9999
```

```fsharp
// total_cents >= 0 only: F# % takes the dividend's sign, so a negative total loses a cent.
let split_cents = fun (total_cents: int64) (ways: int64) ->
    [ for slot in 0L .. ways - 1L -> total_cents / ways + (if slot < total_cents % ways then 1L else 0L) ]
// split_cents 10_000L 3L = [3334L; 3333L; 3333L]; split_cents -10_000L 3L sums to -9999L
```

```ts
// bigint: a number stops counting cents exactly above 2^53. total_cents >= 0 only, as in C++ and F#.
const split_cents = (total_cents: bigint, ways: bigint): bigint[] =>
  Array.from(
    { length: Number(ways) },
    (_, slot) =>
      total_cents / ways + (BigInt(slot) < total_cents % ways ? 1n : 0n),
  );
// split_cents(10000n, 3n) is [3334n, 3333n, 3333n]; split_cents(-10000n, 3n) sums to -9999n
```

| Language   | The lambda above, total -10000                    | With the two-line fix below             |
| ---------- | ------------------------------------------------- | --------------------------------------- |
| Rust       | sums to -10000 (uses `div_euclid` / `rem_euclid`) | not needed                              |
| C++        | sums to -9999                                     | -3333, -3333, -3334: sums to -10000     |
| F#         | sums to -9999                                     | -3333, -3333, -3334: sums to -10000     |
| TypeScript | sums to -9999n                                    | -3333n, -3333n, -3334n: sums to -10000n |

This is not a ranking, and it does not make one language better than another. All four use the same `/` and `%` rules: they truncate toward zero, and the remainder takes the dividend's sign. Rust's lambda only differs because its standard library happens to include `div_euclid` and `rem_euclid` as named methods. The other three get the same answer from a floor-style remainder, one extra line, measured:

```text
remainder = ((total_cents % ways) + ways) % ways   // C++, F#, TypeScript: never negative
share     = (total_cents - remainder) / ways        // now an exact division
```

Each language also has the stronger tool elsewhere in this special: F#'s `decimal` and `Checked.int`, TypeScript's `bigint` and `Number.isSafeInteger`, C++'s `constexpr` and UBSan catching the out-of-range cast. The lesson is the FAQ's "Does integer division round down?" showing up again inside the fix, which is easy to miss in any of the four.

## A.4 Back to the special

Integer cents, or F#'s `decimal`, end the float half of the problem. The split ends the other half. What is left is a rule for the books: when a computation must round a share, such as interest posted per account, the difference between the exact total and the sum of the rounded parts gets posted to a named rounding account. That turns Gus Gorman's invisible cent into a line an auditor can read.

## A.5 Would any other language have stopped Gus?

No language stops him by itself. Exact arithmetic removes the float half of the problem, but splitting 10000 cents three ways leaves a remainder in any type; only an allocation rule or a rounding account catches it. ## A.6 Gotchas

All measured with the A.3 lambdas unless marked:

- Testing only totals that divide evenly hides the leak: `9000 / 3 * 3` is 9000. Only a total where `total % ways` is not 0, such as 10000, shows the missing cent.
- A negative total (a refund) loses a cent wherever `%` takes the dividend's sign: the C++, F# and TS lambdas sum to -9999 (A.3).
- Zero or negative `ways` returns an empty list in all four lambdas, with no error. The range `0..ways` is empty, so the division never runs and the whole total disappears. A bare `10000 / 0` does fail: F# throws `DivideByZeroException`, TS `bigint` throws `RangeError: Division by zero`, and Rust panics (not run here). In C++ it is undefined behaviour, which returned 0 on Arm64; `-fsanitize=integer-divide-by-zero` reports "division by zero".
- The leftover cent always lands on the first slots, so the same payee gets it every time: 12 monthly splits of $100.00 three ways gave slot 0 twelve extra cents. Fairness over time needs a rotating start, or at least a rule someone wrote down.
- Re-sorting the payee list between runs (by name, by id) moves the extra cent to someone else, so the order is part of the rule.
- Rounding each share can create money as well as lose it: `Math.round(2 / 3) * 3` is 3 in JS, and Rust's `(2.0_f64 / 3.0).round() * 3.0` is also 3, so splitting 2 cents three ways by rounding pays out 3. That is Gus in reverse, and the rounding account in A.4 must accept both signs.
