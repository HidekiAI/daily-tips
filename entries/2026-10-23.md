## Rust: Rust 1.98 put itoa in core, and the &str it hands back borrows the buffer until you are done with it

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.98.0 (2026-08-20) stabilized `<integer>::format_into(&mut core::fmt::NumBuffer<Self>) -> &str`, decimal
formatting with no `Formatter`, no `dyn Write` and no heap. `NumBuffer` is sized from the type's longest decimal: 3
bytes for `u8`, 20 for `u64` and `i64`, 39 for `u128`, 40 for `i128`. On rustc 1.99.1, 20 million `u64`s took 58 ms
through `format_into` and 182 ms through `to_string`. The catch is the return type: the `&str` borrows the buffer, so
you get one live number per buffer.

**Show me**

```rust
// Rust 1.98+ (core::fmt::NumBuffer and format_into stabilized 2026-08-20)
use core::fmt::NumBuffer;

fn csv_line(ids: &[u64]) -> String {
    let mut digits = NumBuffer::<u64>::new(); // 20 bytes on the stack: u64::MAX has 20 digits
    // The lazy shape does not compile: each &str borrows `digits`, and an FnMut
    // closure cannot hand out a borrow of what it captured (no lending iterator in std).
    //     ids.iter().map(|id| id.format_into(&mut digits)).collect::<Vec<&str>>().join(",")
    let capacity = ids.len() * 21; // 20 digits plus a comma per id
    ids.iter().enumerate().fold(String::with_capacity(capacity), |mut line, (position, id)| {
        line.push_str(if position == 0 { "" } else { "," });
        line.push_str(id.format_into(&mut digits)); // the &str dies here, before the next id reuses the buffer
        line
    })
}

fn main() {
    assert_eq!(csv_line(&[7, 18_446_744_073_709_551_615, 0]), "7,18446744073709551615,0");
    let mut signed = NumBuffer::<i64>::new();
    assert_eq!(i64::MIN.format_into(&mut signed), "-9223372036854775808"); // sign fits in the same 20 bytes
    println!("ok");
}
```

**Why it matters**

Log lines, CSV exports, metric names and cache keys format integers on the hot path, and `to_string` allocates every
time. A CSV of 2 million ids took 55 to 78 ms as `map(u64::to_string).collect().join(",")` and 16 ms as the fold above:
one `String` grows, one 20-byte buffer is reused. The fold is the functional form that survives: the accumulator is
moved through it rather than bound `let mut`, and `digits` is `let mut` only because `format_into` takes `&mut`. The
textbook `map` cannot be written at all. C++17's `std::to_chars` is the same idea with the sizing left to you: you pass
a `char*` range, and a range too small comes back as `errc::value_too_large` at runtime, where Rust makes the short
buffer unrepresentable. Go's `strconv.AppendInt` appends to a `[]byte` you own.

**Chew on this**

Which of your hot-path `to_string()` calls would become a `format_into` if the result did not have to outlive the
next number? And where it does have to outlive it, is the allocation the cost, or the `Formatter`?

**Sources**

- https://blog.rust-lang.org/2026/08/20/Rust-1.98.0/
- https://doc.rust-lang.org/stable/core/fmt/struct.NumBuffer.html
- https://en.cppreference.com/w/cpp/utility/to_chars

**Verified**

rustc 1.99.1 in `docker run rust:1-slim-trixie` (Linux arm64 on an Apple M3 Pro); timings are single runs, `-O`. The C++
`to_chars` and Go `strconv.AppendInt` comparisons rest on their documentation and were not compiled.

**Gotchas**

- Two live numbers from one buffer do not compile: `let first = 7u64.format_into(&mut buf); let second =
  8u64.format_into(&mut buf);` and then using `first` is E0499. Each live string needs its own `NumBuffer`.
- The buffer is typed per integer. `NumBuffer::new()` infers its type from the first call, so formatting a `u64`
  into a buffer that already formatted a `u32` is E0308, `expected &mut NumBuffer<u64>`.
- `NonZero<u32>` has no `format_into` (E0599). Call `.get()` first.
- `NumBuffer::new` is a `const fn`, but `format_into` is not: calling it in a `const fn` is E0015.
- Reusing a `String` with `write!(out, "{}", value)` is not the fix it looks like: 175 ms against 182 ms for
  `to_string`. The `Formatter` machinery is most of the cost, not the allocation.
- Decimal only. There is no radix, padding or width parameter; for those you are back to `format!`.

## C++: hardware_destructive_interference_size is 256 on every arm64 compiler here, and 64 already stopped false sharing on an M3

*Perf and memory model*

**Did you know**

`std::hardware_destructive_interference_size` (C++17, P0154R1; libstdc++ since GCC 12, complete in libc++) reports the
compiler's tuning, not the CPU. Apple clang 21, GCC 14.4 and GCC 16.2 all say 256 for arm64, while the M3 Pro running
them reports a 128-byte line (`sysctl hw.cachelinesize`). Measured with four threads hammering adjacent counters, 8-byte
spacing took 1505 ms and 64, 128 and 256-byte spacing all took 97 ms. So every `alignas` on it pays four times the bytes
this machine needs, and GCC 16 changes the number under `-mcpu=neoverse-n1` (to 64) while GCC 14 does not.

**Show me**

```cpp
// C++17 (std::hardware_destructive_interference_size, P0154R1)
#include <atomic>
#include <cstdio>
#include <new>

// The value is a property of the compiler's tuning, not of the machine running it:
// Apple clang 21 arm64 256, GCC 14 and 16 aarch64 256, x86_64 64, GCC 16 -mcpu=neoverse-n1 64.
struct alignas(std::hardware_destructive_interference_size) PaddedCounter {
    std::atomic<long> hits{0};
};

// Pinning your own constant keeps sizeof the same in every translation unit and every -mcpu.
inline constexpr std::size_t SERVICE_CACHE_LINE_BYTES = 128; // measured: 64 already avoided false sharing on an M3 Pro
struct alignas(SERVICE_CACHE_LINE_BYTES) PinnedCounter {
    std::atomic<long> hits{0};
};

int main() {
    std::printf("destructive %zu, sizeof(PaddedCounter[64]) %zu, sizeof(PinnedCounter[64]) %zu\n",
                std::hardware_destructive_interference_size, sizeof(PaddedCounter[64]), sizeof(PinnedCounter[64]));
}
// Apple clang 21 and GCC 16 on arm64: destructive 256, sizeof(PaddedCounter[64]) 16384, sizeof(PinnedCounter[64]) 8192
```

**Why it matters**

A per-core or per-shard counter array padded with the standard constant is 16 KiB for 64 slots on arm64 instead of 4 or
8 KiB, and that is L1 a hot path no longer has. Worse, the constant can differ between two translation units built with
different `-mcpu` flags, which makes `sizeof` of a struct in a shared header disagree across the link: an ODR violation
nothing reports. GCC knows: it emits `-Winterference-size` when the constant is used in a header ("its value can vary
between compiler versions or with different '-mtune' or '-mcpu' flags"). Rust has no std constant at all, and the
crate everyone uses, crossbeam's `CachePadded`, picks 128 for both x86_64 and aarch64; Go's runtime pads to 128 on arm64
and 64 on x86.

**Chew on this**

Which of your padded structs sits in a header that two targets, or two `-mcpu` flags, compile differently? And was the
number in your `alignas` ever measured on the hardware you deploy to, or inherited from a constant that describes a
compiler?

**Sources**

- https://en.cppreference.com/w/cpp/thread/hardware_destructive_interference_size
- https://gcc.gnu.org/gcc-12/changes.html
- https://libcxx.llvm.org/Status/Cxx17.html
- https://github.com/crossbeam-rs/crossbeam/blob/master/crossbeam-utils/src/cache_padded.rs

**Verified**

Apple clang 21.0.0 natively (arm64, plus `--target=x86_64-apple-macos13` for the 64), GCC 14.4.0 and 16.2.0 in
`docker run gcc:14` / `gcc:16` (aarch64). The false-sharing timings are one benchmark on one M3 Pro; MSVC not checked.

**Gotchas**

- The warning is header-only. The same `alignas` in a `.cpp` file compiles silently under `-Wall -Wextra`; moved into a
  header, GCC 16 prints `-Winterference-size` and suggests `--param hardware_destructive_interference_size=256`.
- Apple clang does not read it from a table either: libc++ defines the constant as `__GCC_DESTRUCTIVE_SIZE`, a compiler
  builtin macro, so `clang++ -dM -E` shows the value your build will get.
- `-mcpu` moves it on GCC 16 and not on GCC 14: `-mcpu=neoverse-n1` gives 64 on 16.2 and 256 on 14.4. A compiler
  upgrade can change your struct sizes with no source change.
- `hardware_constructive_interference_size` stayed 64 everywhere measured here; the two constants are not a pair you
  can derive one from the other.
- Padding is not what made the padded version fast compared to a per-thread local: four threads doing a relaxed
  `fetch_add` on padded slots took 97 ms, the same count kept in a local and summed afterwards took 25 to 32 ms (see the
  functional angle below).

## F#: Since F# 9 an active pattern's return type picks its representation, and only the option form allocates

*Type system deep cuts*

**Did you know**

F# 9 (RFC FS-1140) lets a partial active pattern return `bool` or `voption` as well as `option`, and the compiler reads
the return type to decide which it is: a pattern that returns `ValueSome` is a struct pattern with no
`[<return: Struct>]` at all, even though the active patterns page on Microsoft Learn still says that attribute "must be
specified". Measured on F# 10 (SDK 10.0.402, FSharp.Core 10.1.0.0, .NET 10.0.13), a successful match through the
`option` form allocates 24 bytes; the `voption` and `bool` forms allocate nothing. Total patterns like `(|Even|Odd|)`
get none of this: they return a `Choice` and allocate 24 bytes on every match, unit cases included.

**Show me**

```fsharp
// F# 9+ for the voption and bool forms (RFC FS-1140); the option form works on any F#
open System
// option return: a Some is allocated on every successful match
let (|Port|_|) (text: string) =
    match Int32.TryParse text with
    | true, port when port > 0 && port < 65536 -> Some port
    | _ -> None
// voption return: the return type alone makes it a struct pattern, no [<return: Struct>]
let (|PortV|_|) (text: string) =
    match Int32.TryParse text with
    | true, port when port > 0 && port < 65536 -> ValueSome port
    | _ -> ValueNone
// bool return: for a pattern that only answers yes or no
let (|IsPort|_|) (text: string) = text |> (|PortV|_|) |> ValueOption.isSome

let inputs = Array.init 1_000_000 (fun index -> [| "8080"; "443"; "x"; "70000" |].[index % 4])
let fnAllocatedBy (classify: string -> int) =
    let before = GC.GetAllocatedBytesForCurrentThread()
    let total = inputs |> Array.sumBy classify
    GC.GetAllocatedBytesForCurrentThread() - before, total
printfn "option  %A" (fnAllocatedBy (fun text -> match text with Port port -> port | _ -> 0))   // (12000360L, ...)
printfn "voption %A" (fnAllocatedBy (fun text -> match text with PortV port -> port | _ -> 0))  // (32L, ...)
printfn "bool    %A" (fnAllocatedBy (fun text -> match text with IsPort -> 1 | _ -> 0))         // (32L, 500000)
// 500,000 successful matches: 12,000,360 bytes is 24 bytes each; the 32 is the closure
```

**Why it matters**

Active patterns sit in request routing, header parsing and validation, so they run per request, and a `Some` per
match is garbage per request. The fix used to need an attribute most people never learned; now it needs only that the
pattern return `ValueSome`, which also means the representation can change without anyone touching the call sites.
Rust never had the problem: a pattern there is syntax, not a function returning a value, and the nearest analogue, a
`fn parse_port(&str) -> Option<u16>`, returns its `Option` on the stack. C++23 has no user-defined patterns at all, so the
comparison stops there.

**Chew on this**

Which of your active patterns are total, `(|A|B|)`, and run on a hot path where a partial `voption` pattern per case
would do? And if a pattern's return type now decides whether it allocates, who on your team will notice when a
refactor turns a `ValueSome` back into a `Some`?

**Sources**

- https://github.com/fsharp/fslang-design/blob/main/FSharp-9.0/FS-1140-boolean-returning-and-return-type-directed-partial-active-patterns.md
- https://github.com/dotnet/fsharp/pull/16473
- https://learn.microsoft.com/en-us/dotnet/fsharp/whats-new/fsharp-9
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/active-patterns

**Verified**

`dotnet fsi` and a `-c Release` console build in `docker run mcr.microsoft.com/dotnet/sdk:10.0` agree on every number.

**Gotchas**

- The Microsoft Learn page is stale on this point: its "Struct Representations for Partial Active Patterns" section
  says the attribute "must be specified, because the use of a struct return is not inferred from simply changing the
  return type to `ValueOption`". On F# 9 and later it is inferred.
- `--langversion:8.0` (or the .NET 8 SDK) rejects both new forms with FS3350, "Boolean-returning and return-type-directed
  partial active patterns", so a project pinned to an older `LangVersion` keeps the old rule.
- A total pattern cannot opt out: `[<return: Struct>]` on `(|Even|Odd|)` is FS3385, "only allowed on partial active
  pattern definitions". Both unit cases and payload cases measured 24 bytes per match.
- A `bool` pattern binds nothing. `match text with IsPort port -> ...` is FS3868, "This active pattern does not expect
  any arguments".
- `[<return: Struct>]` on a pattern that still returns `Some` is a type error (FS0001, expected `'a voption` but has
  `int option`), so the attribute and the body cannot silently disagree.

## TypeScript: Array.isArray turns a readonly string[] into any[], and the else branch never loses the array

*Idioms and antipatterns*

**Did you know**

`Array.isArray` is declared `isArray(arg: any): arg is any[]`, and a `readonly string[]` is not assignable to `any[]`,
so on `string | readonly string[]` the guard cannot narrow the union the way you expect. On tsc 6.0.3 and 7.0.2 with
`--strict`, the true branch types the value as `any[]` and the false branch leaves it as the whole union. Every element
read in the true branch is `any`, and nobody wrote `any`. The issue, microsoft/TypeScript#17002, has been open since
2017-07-07.

**Show me**

```typescript
// TypeScript, tsc 6.0.3 and 7.0.2, --strict
type Tags = string | readonly string[];

// Leaky: compiles clean, then throws "tag.toFixed is not a function" at runtime.
export const fnTagWidthsLeaky = (tags: Tags): number[] =>
    Array.isArray(tags)
        ? tags.map((tag) => tag.toFixed(2).length) // tag is any: isArray narrowed readonly string[] to any[]
        : [tags.length]; // tags is still Tags here: tags.toUpperCase() would be error TS2339

// Fixed: a guard over the union itself, so both branches narrow and nothing becomes any.
const fnIsTagList = (tags: Tags): tags is readonly string[] => Array.isArray(tags);
export const fnTagWidths = (tags: Tags): number[] =>
    fnIsTagList(tags)
        ? tags.map((tag) => tag.length) // tag: string
        : [tags.toUpperCase().length]; // tags: string
```

**Why it matters**

`string | readonly string[]` is exactly the shape of a config field or query parameter that accepts one value or a
list, and `readonly` is what a careful codebase puts on it. The guard that looks like the idiom quietly switches type
checking off for the list branch, and `noImplicitAny` does not object, because the `any` came from a library
declaration, not from an omitted annotation. A mutable `string | string[]` narrows correctly on both branches, so the
bug appears the day someone adds `readonly`. Rust's `match` on an enum and F#'s `match` on a union narrow by
construction; TypeScript narrows only as far as a declaration's type predicate says, and this one predates
`ReadonlyArray`.

**Chew on this**

How many of your `Array.isArray` calls sit on a union with a `readonly` member, and how would you find them, when the
compiler reports nothing for any of them? Would a lint rule against bare `Array.isArray` catch more than it annoys?

**Sources**

- https://github.com/microsoft/TypeScript/issues/17002
- https://github.com/microsoft/TypeScript/blob/main/src/lib/es5.d.ts
- https://www.typescriptlang.org/docs/handbook/2/narrowing.html#using-type-predicates

**Verified**

tsc 6.0.3 and 7.0.2 (`npm install typescript@7.0.2`), `--strict --target es2022`; the runtime TypeError from Node
22.17.1 with `--experimental-strip-types`.

**Gotchas**

- The else branch is the visible symptom: `tags.toUpperCase()` there is TS2339 ("does not exist on type 'Tags'"),
  which looks like your mistake rather than the guard's.
- An `as const` tuple does not become plain `any[]`: `readonly ["admin", "viewer"] | "guest"` narrows to
  `RoleList & any[]`, an intersection that still lets `any` elements through.
- `JSON.parse` returns `any`, and `Array.isArray` on it gives `any[]`, so `input[0].grants.includes("admin")` compiles
  with no check of `input[0]` at all (see the security angle below).
- A custom guard is only as honest as its body: `(tags: Tags): tags is readonly string[] => true` also compiles. Keep
  the guard a one-line wrapper around `Array.isArray`, and type its parameter as the union, not `unknown`, so it cannot
  be applied to something else.

# The functional angle: a count each thread folds and returns needs no padding at all

Draws on the C++ tip. Padding exists because threads share mutable slots; the functional shape, where each thread
folds its own count and the results are reduced after the join, removes the sharing instead of spacing it out.

```cpp
// C++20: one future per worker, each folding into a local, reduced once at the end
std::vector<std::future<long>> partials(thread_count);
std::ranges::generate(partials, [] {
    return std::async(std::launch::async, [] {
        long hits = 0; // local to this thread: nothing to share, nothing to pad
        for (long step = 0; step < steps; ++step) { hits = hits + 1; asm volatile("" : "+r"(hits)); } // barrier stops the optimizer folding the loop
        return hits;
    });
});
const long total = std::transform_reduce(partials.begin(), partials.end(), 0L, std::plus<>{},
                                         [](std::future<long>& partial) { return partial.get(); });
```

```rust
// Rust: scoped threads, each a fold, summed on join
let total: u64 = thread::scope(|scope| {
    let workers: Vec<_> = (0..4).map(|_| scope.spawn(|| (0..STEPS).fold(0u64, |hits, _| black_box(hits + 1)))).collect();
    workers.into_iter().map(|worker| worker.join().unwrap()).sum()
});
```

```fsharp
// F#: Array.Parallel.init runs the folds, Array.sum reduces
let rec countUp step hits = if step = steps then hits else countUp (step + 1L) (hits + 1L)
let total = Array.Parallel.init 4 (fun _ -> countUp 0L 0L) |> Array.sum
```

| Language | Functional form | Fold, 4 x 50M | Shared adjacent slots, 4 x 50M | What it costs |
| --- | --- | --- | --- | --- |
| F# | `Array.Parallel.init` + `Array.sum` | 13-15 ms | 1960-2144 ms (`Interlocked.Increment`) | nothing extra; it is the idiom, and a tail-recursive `countUp` compiles to a loop |
| Rust | `thread::scope` + `fold` + `sum` | 97-127 ms | 383 ms (`AtomicU64`, relaxed) | a `Vec` of join handles; `black_box` per step inflates the fold here |
| C++ | `std::async` + `transform_reduce` | 25-32 ms | 1505-1581 ms (8-byte spacing), 97 ms padded | a `std::future` per worker, and no fold primitive for "a thread's result" |

The numbers compare a fold with shared slots inside one language, not one language with another: each row used a
different barrier to stop the optimizer deleting the loop. TypeScript has no row: workers share memory only through a
`SharedArrayBuffer`, and that was not measured. The asymmetry worth noticing is mutability: the fold needs no `let mut`
in Rust or `mutable` in F#, while C++ keeps a mutable local because `std::async` hands it a lambda, not a fold, and
`ranges::fold_left` has no parallel overload.

Left hanging: a counter that must be read while the threads are still running, a live metrics gauge, cannot wait for
the join. Where is the line in your services between a count you could fold and one you really must share?

# The security angle: Array.isArray on parsed JSON is a grant of trust, and a string passes an array check by substring

Draws on the TypeScript tip and runs the insecure direction: the language does not prevent this, and the idiom makes
it look checked. `JSON.parse` returns `any`, `Array.isArray` narrows it to `any[]`, and from there every property read
is unchecked. A forged body `[{"grants":"superadmin"}]` passes `grants.includes("admin")`, because `includes` on a
string is a substring test.

```typescript
// TypeScript, tsc 6.0.3 and 7.0.2 --strict, effect 4.0.6
import { Result, Schema } from "effect";

// Insecure: compiles clean, and [{"grants":"superadmin"}] grants admin.
export const fnIsAdminLeaky = (body: string): boolean => {
    const claims = JSON.parse(body); // any from the platform
    return Array.isArray(claims) ? claims[0].grants.includes("admin") : false; // claims: any[], so claims[0] is any
};

// Parsed at the boundary: the schema is the only thing that turns JSON text into a type.
const ClaimsList = Schema.Array(Schema.Struct({ grants: Schema.Array(Schema.String) }));
export const fnIsAdmin = (body: string): boolean => {
    const decoded = Schema.decodeResult(Schema.fromJsonString(ClaimsList))(body);
    return Result.isFailure(decoded)
        ? false // SchemaError: Expected array at [0]["grants"]
        : decoded.success.length === 0
          ? false
          : decoded.success[0].grants.includes("admin"); // grants: readonly string[], so includes is membership
};
// Node 22.17.1: leaky true, parsed false, and a real ["admin"] list still true
```

```rust
// Rust, serde_json 1.0.154: a typed target rejects the string before any code reads it
#[derive(serde::Deserialize)]
struct Claims { grants: Vec<String> }
let parsed: Result<Vec<Claims>, _> = serde_json::from_str(r#"[{"grants":"superadmin"}]"#);
// Err: invalid type: string "superadmin", expected a sequence at line 1 column 23
```

```fsharp
// F#, System.Text.Json on .NET 8: the untyped DOM still fails closed on the wrong kind
let grants = JsonDocument.Parse("""[{"grants":"superadmin"}]""").RootElement[0].GetProperty("grants")
grants.EnumerateArray() // InvalidOperationException: requires an element of type 'Array', but the target element has type 'String'
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | `any` from `JSON.parse`, `any[]` from `Array.isArray`, substring `includes` on a forged string | nothing: no runtime types, and `--strict` accepts the code | decode into a schema at the boundary; never let `Array.isArray` be the only check on wire data |
| Rust | the same bug is possible through untyped `serde_json::Value` and `to_string().contains(...)` | a typed `Deserialize` target rejects the wrong shape with an error | deserialize into a struct, not into `Value`, wherever a decision is made |
| F# | a hand-walked `JsonElement` reads the wrong field | the DOM throws on a kind mismatch instead of coercing | catch the exception as a rejection, and prefer a typed deserializer |
