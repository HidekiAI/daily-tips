# Daily Tips special, part 9 of 14: small bugs that exploded, or a check that read whether the call ran instead of what it found

Not part of the rotation. Part 9 of the fourteen-part special on real incidents: the macOS High Sierra root login flaw, [CVE-2017-13872](https://nvd.nist.gov/vuln/detail/CVE-2017-13872), fixed by Security Update 2017-001 on 29 November 2017. Each tip below is a result type that carries two answers, "did the call work" and "what did it find", and a check that reads the first one.

# What happened

**Bug class:** Bohrbug (it fails the same way every time its trigger appears) in this special's classification, condition-triggered: it fired only for account records that took a legacy-password path. The anti-pattern the tips below take from it is checking the status of a verification call instead of its verdict, and then letting the "success" path write.

**The story, in plain words:**

On a Mac, "root" is the all-powerful administrator account, and on these Macs it was disabled. In November 2017, on macOS High Sierra 10.13 and 10.13.1, that stopped mattering: Patrick Wardle of Objective-See wrote that the bug let anybody log into the root account "with a blank, or password of their choosing", and that with screen sharing enabled it could be done remotely. Apple's advisory says macOS Sierra 10.12.6 and earlier were not impacted.

Wardle reports that the bug was first posted, quite innocently, to Apple's own Developer Forums in a post about a user's account-access trouble, and only gained wide attention when Lemi Orhan Ergin posted a tweet about it. On 29 November 2017 Wardle published his analysis of the cause, and Apple released Security Update 2017-001 the same day.

What Wardle found is a password check that did half its job. When someone tries to log in, the `opendirectoryd` daemon looks for stored password hashes on the account. A disabled account like root has none; it only holds a placeholder, `*`. So the code took its old-style (crypt password) branch and called a check function, `od_verify_crypt_password`. That function does two things: it returns a value, and it also writes its verdict into a separate variable, which starts out as 5000, "credentials invalid", and becomes 0 only if the passwords really match.

The code looked only at the returned value, which was non-zero even for a wrong password. It never looked at the verdict variable. It concluded the password was fine and went on to its next step, upgrading the account's stored password to the modern format, using the password the person had just typed. Wardle's summary: the attacker's own chosen password was saved as root's password, and then the login worked. That is why you had to press Enter or click Unlock twice: the first try quietly created the password, the second used it.

Apple's own advisory says only that "a logic error existed in the validation of credentials". After the patch, Wardle compared the old and new binaries and found the new code checks the verdict variable after the call. He also reports that the first patch broke file sharing for some users, and Apple's advisory tells people who moved from 10.13 to 10.13.1 to reboot "to make sure the Security Update is applied properly".

The point for the tips below: a call that reports "I ran" and "what I found" separately is only safe if the code reads the second. Apple's and Wardle's own words follow.

From Apple's "About the security content of Security Update 2017-001" (released November 29, 2017):

```text
Directory Utility
Available for: macOS High Sierra 10.13 and macOS High Sierra 10.13.1
Not impacted: macOS Sierra 10.12.6 and earlier
Impact: An attacker may be able to bypass administrator authentication without
supplying the administrator's password
Description: A logic error existed in the validation of credentials. This was
addressed with improved credential validation.
CVE-2017-13872
```

NVD records the weakness as [CWE-287](https://cwe.mitre.org/data/definitions/287.html), Improper Authentication. Apple does not describe the logic error. The mechanism comes from Patrick Wardle's reverse engineering of `opendirectoryd`, published by Objective-See the same day, "Why <blank> Gets You Root", not from Apple. In his decompilation (quoted with whitespace adjusted), `var_54` is the verdict: it starts as 0x1388, which he identifies as `kODErrorCredentialsInvalid` (5000), and is set to 0 only when the password hashes match:

```text
var_54 = 0x1388;
if ( od_verify_crypt_password (var_70, rax, var_60, &var_54, &var_41) != 0x0) {
    //upgrade password
```

His finding: "only the return value of od_verify_crypt_password is checked....NOT THE RESULT OF THE ACTUAL VERIFICATION!! (i.e. the 'match' variable, var_54)". The branch behind that check is a credential upgrade, logged as "found crypt password in user-record - upgrading to shadowhash or securetoken", so an unread verdict ended in a credential write. His comparison of the patched binary shows Apple's fix now checks `match` after the call. Apple's advisory also told users who had moved from 10.13 to 10.13.1 to reboot "to make sure the Security Update is applied properly".

## Rust: `Result<bool, E>::is_ok()` is `true` for a password that did not match, and Clippy's default lint rewrites `if let Ok(_)` into exactly that

*Idioms and antipatterns*

**Did you know**

A `Result<bool, E>` has three states: the call failed, the call ran and said no, the call ran and said yes. `is_ok()` and `if let Ok(_)` both collapse the last two, so `verify_password(stored, "").is_ok()` is `true` when the verdict is `Ok(false)`, and rustc 1.99.1 gives no warning. Clippy 0.1.99 with no flags at all reports `if let Ok(_) = ...` as "redundant pattern matching" and suggests `.is_ok()`: it treats the two as the same thing, which they are, and neither one reads the bool.

**Show me**

```rust
// rustc 1.99.1, edition 2024, Debian.
#[derive(Debug)]
struct DirectoryError;

// Ok(false) means the lookup ran and the password did not match.
fn verify_password(stored_password_hash: &str, provided_password: &str) -> Result<bool, DirectoryError> {
    Ok(stored_password_hash == provided_password)
}

fn main() {
    let stored_password_hash = "legacy-hash"; // a stored hash the typed password does not match
    if verify_password(stored_password_hash, "").is_ok() {
        println!("is_ok(): upgrading, verdict was false"); // printed
    }
    if let Ok(_) = verify_password(stored_password_hash, "") {
        println!("if let Ok(_): same"); // printed; Clippy suggests is_ok() here
    }
    if matches!(verify_password(stored_password_hash, ""), Ok(true)) {
        println!("never printed"); // naming the value is what reads the verdict
    }
}
```

**Why it matters**

`?` has the same blind spot: `let password_matched = verify_password(...)?;` propagates the error and leaves the verdict in a `bool` that nothing forces you to read. A `bool` in the `Ok` slot is how a "no" gets treated as a success without anyone writing that branch. A `match` that names `Ok(true)` and forgets `Ok(false)` does not compile (`E0004: non-exhaustive patterns: Ok(false) not covered`); only the shortcuts that never name the value, `is_ok()` and `if let Ok(_)`, skip that check.

**Chew on this**

Which of your functions return `Result<bool, _>`, and how many of their callers stop at `is_ok()` or `?`? Would a two-variant enum in place of the `bool` have made the macOS check impossible to write, or only harder?

**Sources**

- https://doc.rust-lang.org/std/result/enum.Result.html#method.is_ok
- https://rust-lang.github.io/rust-clippy/master/index.html#redundant_pattern_matching
- https://objective-see.com/blog/blog_0x24.html

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1; Clippy 0.1.99 was added to a throwaway container with `rustup component add clippy`. With `-W clippy::pedantic` Clippy adds `unnecessary_wraps`, which came from the stub never returning `Err`.

**Gotchas**

- `#[must_use]` on a function returning `bool` warns on a bare call (for `#[must_use] fn hashes_match(stored_password_hash: &str, provided_password: &str) -> bool`: "unused return value of `hashes_match` that must be used"), and `let _ = hashes_match(...)` silences it.
- `matches!(result, Ok(true))` is the cheapest correct check: on `Ok(false)` it is `false`, where `is_ok()` was `true`.

## C++: `if (verify_password(provided_password))` on a `std::expected<bool, E>` tests that the call ran, and no compiler warns that the verdict was `false`

*Stdlib and ecosystem gems*

**Did you know**

`std::expected<bool, E>` (C++23) and `std::optional<bool>` (C++17) both convert to `bool` in a condition, and that conversion means `has_value()`, not the stored value. So `if (verify_password(""))` takes the branch when the verifier returned `false`. GCC 16.2 and Debian clang 19.1.7 compile it with no warning under `-Wall -Wextra`, and clang's `-Weverything` adds nothing about it either. The out-parameter shape from the macOS code is just as quiet: `int verify_match_code = 5000;` passed as `&verify_match_code`, a check of only the return value, and `verify_match_code` still 5000 afterwards, with no diagnostic. `std::expected` ships in libstdc++ 12, libc++ 16 and MSVC 19.33 onward.

**Show me**

```cpp
// C++23, g++ 16.2 and clang++ 19.1.7, Debian.
#include <cstdio>
#include <expected>
#include <optional>
#include <string_view>

constexpr int CREDENTIALS_INVALID = 5000; // kODErrorCredentialsInvalid

// The C shape: status in the return value, verdict in an out-parameter.
[[nodiscard]] int verify_crypt_password(const char* const const_stored_password_hash, const char* const const_provided_password, int* verify_match_code) { // mutable: verify_match_code is an out-parameter
    if (std::string_view(const_stored_password_hash) == const_provided_password) *verify_match_code = 0;
    return 1; // "the call did something"
}

// The C++23 shape: the error channel says the call ran, the bool is the verdict.
std::expected<bool, int> verify_password(const char* const const_provided_password) { return std::string_view("legacy-hash") == const_provided_password; }

int main() {
    int verify_match_code = CREDENTIALS_INVALID; // mutable: written through its address
    if (verify_crypt_password("legacy-hash", "guess", &verify_match_code) != 0) std::puts("status checked, verify_match_code never read"); // printed
    if (verify_password("")) std::puts("if() tested has_value(); the verdict was false");        // printed
    if (verify_password("") == true) std::puts("never printed");     // comparing with true reads the value
    std::printf("verify_match_code=%d\n", verify_match_code);                                 // verify_match_code=5000
}
```

**Why it matters**

`[[nodiscard]]` makes discarding the status a warning, so the status gets checked. That is the shape the macOS code had: status checked, out-parameter never read. Nothing marks the out-parameter, and nothing marks the `bool` inside an `expected`, as the part that must be read. Both shapes look correct to a reviewer who sees a checked return value.

**Chew on this**

Where do you return `std::optional<bool>` or `std::expected<bool, E>` today, and does every caller compare the value rather than test the object? What would an enum `verdict { matched, mismatched }` cost you at those call sites?

**Sources**

- https://en.cppreference.com/w/cpp/utility/expected/operator_bool
- https://en.cppreference.com/w/cpp/utility/optional/operator_bool
- https://en.cppreference.com/w/cpp/compiler_support/23

**Verified**

GCC 16.2.0 (`gcc:latest`) and Debian clang 19.1.7 (`debian:stable` plus `apt-get install clang`), both Debian, `-std=c++23 -Wall -Wextra`. The library versions for `std::expected` are from the cppreference support table, not tested here.

**Gotchas**

- `verify_password("") == true` is the correct test: `expected<bool, E>` compares its value against `true` and returns `false` when it holds an error, so the branch did not run.
- An `expected<bool, E>` holding an error compared with `true` gave `false`, and compared with `false` also gave `false`: neither comparison mistakes an error for a verdict.

## F#: `Result.isOk (Ok false)` is `true`, and only a match on the values makes the compiler name `Ok (false)` as the case you forgot

*Type system deep cuts*

**Did you know**

F# shares Rust's blind spot: `Result.isOk (verify_password "legacy-hash" "guess")` is `true` when the verdict is `Ok false`, and a `| Ok _ ->` arm takes the mismatch as a success with no warning, even with `--warnon:1182` for unused bindings. The difference is what happens when you match on the values instead. `| Ok true -> ... | Error reason -> ...` gets warning `FS0025`: "the value 'Ok (false)' may indicate a case not covered by the pattern(s)". And if you ignore the warning, the missing case fails closed at runtime with `MatchFailureException` instead of granting anything. Measured on .NET SDK 10.0.403, FSharp.Core 10.1.0.0, .NET 10.0.14.

**Show me**

```fsharp
// F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14.
let verify_password (stored_password_hash: string) (provided_password: string) : Result<bool, string> =
    Ok (stored_password_hash = provided_password)

printfn "%b" (Result.isOk (verify_password "legacy-hash" "guess"))   // true, the password did not match

match verify_password "legacy-hash" "guess" with
| Ok _ -> printfn "Ok _: upgrading, verdict ignored"  // runs, and no warning
| Error error_reason -> printfn "error %s" error_reason

let access_decision =
    match verify_password "legacy-hash" "guess" with                 // FS0025: 'Ok (false)' may indicate a case not covered
    | Ok true -> "grant"
    | Error error_reason -> "refuse: " + error_reason
// running it: MatchFailureException, so the missing case refuses instead of granting
```

**Why it matters**

The exhaustiveness check only counts what the patterns name. `Ok _` names nothing inside the `Ok`, so it is complete and silent; `Ok true` names the verdict, so the compiler can see that `Ok false` is missing. Writing the values out is what turns the macOS mistake into a warning.

**Chew on this**

How many of your matches on a `Result<bool, _>` use `Ok _` or `Result.isOk`? If `FS0025` were an error in your build, which of those would you rewrite first?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/pattern-matching
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-core-resultmodule.html

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0`, which is Ubuntu 24.04 rather than Debian.

**Gotchas**

- A .NET out-parameter becomes a tuple element in F#: `let parse_succeeded, parsed_port_number = Int32.TryParse "80x"` gives `false, 0`, and `let parse_succeeded, _ = ...` discards the second element with no warning.
- An out-parameter written in F# itself (`verify_match_code: byref<int>`) keeps the C shape: checking only the return value left `verify_match_code` at 5000 with no warning.

## TypeScript: TS2801 catches an un-awaited `Promise<boolean>` in a condition, and says nothing when the code reads `.ok` instead of `.matched`

*Idioms and antipatterns*

**Did you know**

The TypeScript version of the macOS mistake has two forms. An `async` verifier used without `await`, as in `if (verify_password("legacy-hash", provided_password))`, tests the Promise object, which is always truthy. tsc 7.0.2 rejects that with `TS2801: This condition will always return true since this 'Promise<boolean>' is always defined.`, in an `if`, through a variable, and on the left of `&&`. The other form is a synchronous result object `{ ok: true, matched: false }`: `if (result.ok)` compiles with no diagnostic and runs the branch, because `ok` is a real `true`. Measured on Node 26.13.0.

**Show me**

```ts
// TypeScript, tsc 7.0.2 --strict, Node 26.13.0.
type VerifyResult = { ok: true; matched: boolean } | { ok: false; reason: string }

async function verify_password(stored_password_hash: string, provided_password: string): Promise<boolean> {
    return stored_password_hash === provided_password
}
function verify_password_sync(stored_password_hash: string, provided_password: string): VerifyResult {
    return { ok: true, matched: stored_password_hash === provided_password }
}

async function login(provided_password: string): Promise<void> {
    if (verify_password("legacy-hash", provided_password)) console.log("upgrading")          // TS2801
    const const_pending_verdict_promise = verify_password("legacy-hash", provided_password)
    if (const_pending_verdict_promise) console.log("upgrading")                                 // TS2801
    if (verify_password_sync("legacy-hash", provided_password).ok) console.log("upgrading, matched was false") // no error; runs
    if (await verify_password("legacy-hash", provided_password)) console.log("never printed")
}
void login("")
```

**Why it matters**

TS2801 covers the shape the compiler can recognise, an object that is never falsy. A result object with an `ok` flag is a shape the compiler cannot judge: `ok` is a legitimate boolean, and nothing in the type says that `matched` is the field the caller has to read.

**Chew on this**

Which of your result types carry both an `ok` and a verdict field, and could either one be renamed so that reading the wrong one looks wrong? Do any of your tsconfigs turn `strictNullChecks` off?

**Sources**

- https://www.typescriptlang.org/tsconfig/#strictNullChecks
- https://github.com/microsoft/TypeScript/blob/main/src/compiler/diagnosticMessages.json (TS2801)

**Verified**

Run in `node:lts-trixie` (Debian), Node 26.13.0, tsc 7.0.2 via `npx`. The emitted JavaScript was run too, and printed every branch marked as running.

**Gotchas**

- TS2801 depends on `strictNullChecks`: with `--strict --strictNullChecks false`, all three Promise conditions compiled (exit 0) and every branch ran. tsc 7.0.2 with no flags at all reported them, so the risk is a tsconfig that opts out.
- `const const_grant_label = verify_password("legacy-hash", provided_password) && "grant"` is reported too (TS2801 on the `&&`), and without the check it evaluated to `"grant"`.

# The functional angle: bind the verdict into the error channel, and "the call worked" starts to mean "it matched"

Draws on all four tips. Each language already has the operation that removes the third state: a bind that turns `Ok(false)` into an error. After it, `is_ok()`, `?`, `if (const_require_match_result)` and a failed effect all mean the same thing as "matched".

```rust
// Rust: and_then moves Ok(false) into the error channel.
#[derive(Debug)]
enum LoginError { Directory, Mismatch }
fn verify_password(stored_password_hash: &str, provided_password: &str) -> Result<bool, LoginError> {
    if stored_password_hash.is_empty() { Err(LoginError::Directory) } else { Ok(stored_password_hash == provided_password) }
}
fn require_match(stored_password_hash: &str, provided_password: &str) -> Result<(), LoginError> {
    verify_password(stored_password_hash, provided_password)
        .and_then(|password_matched| if password_matched { Ok(()) } else { Err(LoginError::Mismatch) })
}
fn main() {
    println!("{:?} {}", require_match("legacy-hash", "guess"), require_match("legacy-hash", "guess").is_ok()); // Err(Mismatch) false
}
```

```fsharp
// F#: Result.bind.
type LoginError = Directory | Mismatch
let verify_password (stored_password_hash: string) (provided_password: string) : Result<bool, LoginError> =
    if stored_password_hash = "" then Error Directory else Ok (stored_password_hash = provided_password)
let require_match (stored_password_hash: string) (provided_password: string) : Result<unit, LoginError> =
    verify_password stored_password_hash provided_password
    |> Result.bind (fun password_matched -> if password_matched then Ok () else Error Mismatch)
printfn "%A %b" (require_match "legacy-hash" "guess") (Result.isOk (require_match "legacy-hash" "guess"))   // Error Mismatch false
```

```cpp
// C++23: std::expected::and_then.
#include <cstdio>
#include <expected>
#include <string_view>
enum class LoginError { Directory, Mismatch };
std::expected<bool, LoginError> verify_password(const std::string_view const_stored_password_hash, const std::string_view const_provided_password) {
    if (const_stored_password_hash.empty()) return std::unexpected(LoginError::Directory);
    return const_stored_password_hash == const_provided_password;
}
std::expected<void, LoginError> require_match(const std::string_view const_stored_password_hash, const std::string_view const_provided_password) {
    return verify_password(const_stored_password_hash, const_provided_password).and_then([](const bool const_password_matched) -> std::expected<void, LoginError> {
        if (const_password_matched) return {};
        return std::unexpected(LoginError::Mismatch);
    });
}
int main() {
    const std::expected<void, LoginError> const_require_match_result = require_match("legacy-hash", "guess");
    std::printf("%s\n", const_require_match_result ? "matched" : "refused"); // refused: if() now tests the verdict too
}
```

```ts
// TypeScript, effect 4.1.2: filterOrFail turns "ran, but false" into a typed failure.
import { Effect } from "effect"
class Mismatch { readonly _tag = "Mismatch" }
const const_verify_password = (stored_password_hash: string, provided_password: string): Effect.Effect<boolean> =>
    Effect.succeed(stored_password_hash === provided_password)
const const_require_match = (stored_password_hash: string, provided_password: string): Effect.Effect<boolean, Mismatch> =>
    const_verify_password(stored_password_hash, provided_password).pipe(Effect.filterOrFail((password_matched) => password_matched, () => new Mismatch()))
const const_require_match_result = Effect.runSync(Effect.result(const_require_match("legacy-hash", "guess")))
console.log(const_require_match_result._tag) // Failure
```

Each was run: Rust on rustc 1.99.1, F# on .NET SDK 10.0.403, C++ on GCC 16.2 (`-std=c++23 -Wall -Wextra`, no warnings), TypeScript on Node 26.13.0 with tsc 7.0.2 `--strict` and effect 4.1.2, with the outputs in the comments.

| Language | Bind that removes `Ok(false)` | What it costs |
| --- | --- | --- |
| F# | `Result.bind` | one closure; the error type gains a `Mismatch` case |
| Rust | `Result::and_then` | one closure; every caller's error type must hold `Mismatch` |
| C++ | `std::expected::and_then` (C++23) | the lambda's return type must be spelled out, as `-> std::expected<void, LoginError>` above; `and_then` needs libstdc++ 13, libc++ 17 or MSVC 19.36, a later release than `std::expected` itself |
| TypeScript | effect's `Effect.filterOrFail` | a dependency; in effect 4.1.2 the result runner is `Effect.result` (there is no `Effect.either`) |

F# is the baseline because `Result.bind` is the ordinary way F# sequences these steps. The cost is the same in all four: the mismatch becomes a named error, so every caller up the chain has to handle a case it could previously ignore.

Where in your code does a `bool` verdict travel two or more calls before anything reads it?

# The security angle: a verification that does not match must not reach a write

Draws on all four tips, and runs in the direction of what the languages let through: none of them stopped a check of "the call ran" from standing in for "the password matched". The macOS code went one step further. Its success branch was an upgrade that saved the caller's password, so the unread verdict became a write. This is the missing-check sample, shown once as written and once with the check.

```rust
// Rust. Looks like a migration helper: old "crypt:" records are re-hashed on first login.
use std::collections::HashMap;
fn verify_crypt(stored_password_record: &str, provided_password: &str) -> Result<bool, String> { Ok(stored_password_record == format!("crypt:{provided_password}")) }
fn rehash(provided_password: &str) -> String { format!("shadow:{provided_password}") }

fn login_insecure(password_record_by_user_name: &mut HashMap<String, String>, user_name: &str, provided_password: &str) -> bool {
    let stored_password_record = password_record_by_user_name.get(user_name).cloned().unwrap_or_default();
    if stored_password_record.starts_with("shadow:") { return stored_password_record == rehash(provided_password); }
    if verify_crypt(&stored_password_record, provided_password).is_ok() {               // checks that the call ran, not the verdict
        password_record_by_user_name.insert(user_name.to_string(), rehash(provided_password)); // and the upgrade writes the caller's password
        return true;
    }
    false
}

fn login(password_record_by_user_name: &mut HashMap<String, String>, user_name: &str, provided_password: &str) -> bool {
    let stored_password_record = password_record_by_user_name.get(user_name).cloned().unwrap_or_default();
    if stored_password_record.starts_with("shadow:") { return stored_password_record == rehash(provided_password); }
    match verify_crypt(&stored_password_record, provided_password) {
        Ok(true) => { password_record_by_user_name.insert(user_name.to_string(), rehash(provided_password)); true }
        Ok(false) | Err(_) => false,                            // no write unless the old password matched
    }
}

fn main() {
    let mut mut_password_record_by_user_name: HashMap<String, String> = HashMap::from([("legacy_user".to_string(), "crypt:old-secret".to_string())]);
    println!("{} {:?}", login_insecure(&mut mut_password_record_by_user_name, "legacy_user", "guess"), mut_password_record_by_user_name.get("legacy_user")); // true Some("shadow:guess")
    let mut mut_fixed_password_record_by_user_name: HashMap<String, String> = HashMap::from([("legacy_user".to_string(), "crypt:old-secret".to_string())]);
    println!("{} {:?}", login(&mut mut_fixed_password_record_by_user_name, "legacy_user", "guess"), mut_fixed_password_record_by_user_name.get("legacy_user")); // false Some("crypt:old-secret")
}
```

The insecure version logs in with a wrong password and replaces the stored record with that password's hash. The fixed version refuses and leaves the record alone. The classes, in this part's classification: [CWE-253](https://cwe.mitre.org/data/definitions/253.html), Incorrect Check of Function Return Value, for reading the status instead of the verdict, and [CWE-636](https://cwe.mitre.org/data/definitions/636.html), Not Failing Securely, for a failed check that ends in a write. NVD records [CWE-287](https://cwe.mitre.org/data/definitions/287.html).

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `is_ok()` on `Ok(false)` | `E0004` (an error) once a `match` names `Ok(true)`; Clippy's default lint suggests `is_ok()` for `if let Ok(_)` | match the values, or bind the mismatch into `Err` |
| C++ | `if (expected<bool, E>)` tests `has_value()` | nothing, even with clang `-Weverything` | compare with `true`, or `and_then` into an error |
| F# | `Result.isOk` and `Ok _` accept `Ok false` | `FS0025` when the match names `Ok true`; `MatchFailureException` at runtime | name the values in the match |
| TypeScript | an un-awaited Promise, or `.ok` read instead of `.matched` | TS2801 for the Promise, nothing for `.ok` | keep `strictNullChecks`; one field per result, or a union per verdict |

F# is the baseline because once the patterns name the values its compiler warns (`FS0025`) and its runtime refuses (`MatchFailureException`); Rust goes further and makes the same missing case a compile error (`E0004`), while the C++ and TypeScript shapes measured above (`if (expected)`, reading `.ok`) get no check at all. The Rust sample ran on rustc 1.99.1; each row's behaviour was measured in the tips above.

Which of your "first login" or migration paths write a credential, and what exactly do they check before the write?
