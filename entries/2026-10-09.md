## Rust: `let _ = owned` moves nothing and `let _ = lock()` unlocks on the same line, and rustc only catches the std lock

*Idioms and antipatterns*

**Did you know**

`_` is not a binding, it is a pattern that matches without binding. So `let _ = owned;` against a *place* expression does not move `owned`: the value stays usable and drops at the end of scope. Against a *temporary*, `let _ = shared.lock().unwrap();` drops the guard at the end of the same statement, while `let _guard = ...` holds it to the end of the block. Edition 2021 adds a third case: inside a `move` closure, `let _ = payload;` is not a use, so the closure captures nothing and is 0 bytes.

**Show me**

```rust
use std::sync::Mutex;

fn main() {
    let shared = Mutex::new(0_u32);

    // Temporary bound to `_`: dropped at the semicolon. rustc 1.95 rejects this
    // line with the deny-by-default lint `let_underscore_lock`, so this demo
    // needs the allow to compile at all.
    #[allow(let_underscore_lock)]
    let _ = shared.lock().unwrap();
    println!("{}", shared.try_lock().is_ok()); // true: nothing held

    // A real binding, even one that starts with `_`, lives to the closing brace.
    let _guard = shared.lock().unwrap();
    println!("{}", shared.try_lock().is_ok()); // false: still held
    drop(_guard);

    // `_` on a place expression: no move, no drop.
    let owned = String::from("still mine");
    let _ = owned;
    println!("{owned}"); // compiles

    // Edition 2021 disjoint captures: `let _ = payload` is not a use, so the
    // move closure captures nothing. Edition 2018 moves `payload` in, and the
    // println below fails with E0382.
    let payload = vec![0_u8; 1024];
    let ignores_payload = move || {
        let _ = payload;
    };
    println!("{}", std::mem::size_of_val(&ignores_payload)); // 0
    println!("{}", payload.len()); // 1024: never moved
}
```

**Why it matters**

The lint only knows the std guard types. It sees through `let _ = shared.lock();` (the `Result`) and catches `RwLock` guards too, but a hand-rolled guard, a pool checkout, or a third-party lock guard dropped with `let _ =` compiles with no warning at all. That was tested here with a custom `Drop` guard. C++ is the mirror image: there `_` has always been an ordinary name, so `auto _ = std::lock_guard(m);` holds the lock to the end of scope. The same spelling means the opposite lifetime.

**Chew on this**

Which of your RAII types (a span, a pool lease, a transaction) would `let _ =` turn into a no-op, and would anything in your test suite notice? And if the `let _ = payload` closure is 0 bytes, what does a code reviewer think that closure is keeping alive?

**Sources**

- https://doc.rust-lang.org/rustc/lints/listing/deny-by-default.html#let-underscore-lock
- https://doc.rust-lang.org/edition-guide/rust-2021/disjoint-capture-in-closures.html

## C++: `size_t` and `uint64_t` are the same type on Linux and Windows and different on macOS, so `std::max(v.size(), u64)` compiles on two of three

*Type system deep cuts*

**Did you know**

All three 64-bit platforms make both types 64 bits wide, but each ABI picks which *keyword* sits under each typedef. Linux (LP64) makes both `unsigned long`. Windows (LLP64) makes both `unsigned long long`. macOS (also LP64) makes `size_t` `unsigned long` and `uint64_t` `unsigned long long`. Template argument deduction needs an exact type match, so any function template that deduces one `T` from both arguments works on Linux and Windows and fails on macOS. `std::max`, `std::min` and `std::clamp` are the usual examples. This is true in every C++ standard since C++11, because it is an ABI fact and not a language feature.

**Show me**

```cpp
// Header-free, so it compiles for any -target. These builtins are exactly what
// <cstddef> and <cstdint> typedef size_t and uint64_t to.
using size_type = __SIZE_TYPE__;
using u64 = __UINT64_TYPE__;

// Same shape as std::max: one T, deduced from BOTH arguments.
template <class T>
const T& max_of(const T& left, const T& right) { return left < right ? right : left; }

size_type pick(size_type length, u64 floor) {
    return max_of(length, floor);
}

// clang++ -std=c++20 -fsyntax-only -target <triple>:
//   x86_64-linux-gnu        OK     (both unsigned long)
//   x86_64-pc-windows-msvc  OK     (both unsigned long long)
//   arm64-apple-darwin      error: deduced conflicting types for parameter 'T'
//                          ('unsigned long' vs. 'unsigned long long')
//
// The real header version fails the same way on macOS:
//   std::max(rows.size(), std::uint64_t{1})   -> no matching function for call to 'max'
// Fix that states intent and is portable: std::max<std::uint64_t>(rows.size(), floor)
```

**Why it matters**

A Linux-only CI passes, then a developer's Mac build fails, or the other way round. The same split breaks overload sets and template specializations: `encode(std::int64_t)` plus `encode(long long)` is two overloads on Linux and a redefinition on macOS and Windows. Rust never has this problem, because `usize` and `u64` are distinct types on every target, so `max(rows.len(), floor_u64)` fails everywhere and you fix it once. Go is the same: `go vet` reports `mismatched types int and uint64` for `max(len(rows), floor)` on every platform. F# uses `unativeint` versus `uint64`, also distinct everywhere.

**Chew on this**

Where in your code is `uint64_t` really just "an unsigned 64-bit count", and where is it a wire-format type that should never meet `size_t` without a cast you can see? If the answer is "it depends on the call site", does your build matrix compile on the one platform that would tell you?

**Sources**

- https://en.cppreference.com/w/cpp/language/types (data models: LP64, LLP64)
- https://en.cppreference.com/w/cpp/types/integer
- https://en.cppreference.com/w/cpp/algorithm/max

**Verified**

The Linux and Windows results come from `clang++ -target` with the compiler's predefined macros and no target sysroot. The full-header `std::max` failure was compiled on the host (macOS) only.

## F#: `Set.intersect` walked its first argument, so `intersect huge tiny` was 18,000x slower than `intersect tiny huge` until FSharp.Core 10.1.300, and the fix kept the first set's elements

*New discoveries and currently popular patterns*

**Did you know**

Until May 2026, `Set.intersect a b` walked every node of `a` and looked each one up in `b`, so its cost was O(|a| log |b|) and the argument order decided the speed. PR dotnet/fsharp#19292 (merged 2026-03-02, shipped in FSharp.Core 10.1.300 on NuGet 2026-05-12, and in the .NET 11 previews) compares the two tree heights and walks the shorter tree. The PR adds a step that is easy to miss. When the second set is the one walked, the code fetches the matching element *from the first set* with a new `tryGet`, because the result has always held the first argument's instances. The new unit tests check this with `Object.ReferenceEquals`. That only matters when two elements compare equal but are different objects, which is exactly what `[<CustomComparison>]` on an id field gives you.

**Show me**

```fsharp
// Elements compare by id only, so a "huge" and a "tiny" instance can be equal.
[<CustomEquality; CustomComparison>]
type Tagged =
    { id: int; origin: string }
    override this.Equals(other) =
        match other with
        | :? Tagged as tagged -> this.id = tagged.id
        | _ -> false
    override this.GetHashCode() = this.id
    interface System.IComparable with
        member this.CompareTo(other) = compare this.id (other :?> Tagged).id

let huge = Set.ofSeq (seq { for id in 1 .. 1_000_000 -> { id = id; origin = "huge" } })
let tiny = Set.ofList [ for id in 1 .. 10 -> { id = id; origin = "tiny" } ]

let common = Set.intersect huge tiny
printfn "%s" (Seq.head common).origin   // "huge" on both versions: first argument wins

// Measured, net8.0 console app, 5000 calls each (20 for the 8.0.400 slow case):
//                            FSharp.Core 8.0.400   FSharp.Core 10.1.300
//   Set.intersect huge tiny     ~55 ms/call           ~0.006 ms/call
//   Set.intersect tiny huge     ~0.003 ms/call        ~0.004 ms/call
```

**Why it matters**

The FSharp.Core you run is the one in your package reference, not the one the SDK brings. `dotnet fsi` on SDK 8.0.401 still uses FSharp.Core 8.0.0.0 and still has the slow path, so a script and a service can disagree. And anyone who "fixed" the old slowness by swapping the arguments also changed which instances they get back, without noticing. The siblings each answer the identity question differently. Rust's `BTreeSet::intersection` is fast either way round, but it yields the *smaller* set's elements whichever set is the receiver (measured, rustc 1.95 `-O`). C++ `std::set_intersection` copies from the first range and is a linear merge, about 5 ms for either order when the matches sit at the far end.

**Chew on this**

If your set elements carry data that the comparison ignores (a timestamp, a source, a version), which set's copy should an intersection return, and has any code of yours been relying on the answer without saying so? Did someone on your team swap arguments for speed, and did that change which copy you get?

**Sources**

- https://github.com/dotnet/fsharp/pull/19292
- https://github.com/dotnet/fsharp/issues/19139
- https://github.com/dotnet/core/blob/main/release-notes/11.0/preview/preview2/fsharp.md
- https://www.nuget.org/packages/FSharp.Core/10.1.300

**Verified**

Timings and origins measured on .NET 8.0.8 runtime (SDK 8.0.401), with FSharp.Core pinned through `DisableImplicitFSharpCoreReference`. FSharp.Core 11 previews were not run here. They contain the same commit, which sits on `main`.

**Related**

## TypeScript: a string built with `+=` is a 52-byte-per-piece tree until something reads one character, and that read copies all of it

*Perf and memory model*

**Did you know**

V8 does not copy on `+=`. It allocates a `ConsString` node that points at the two halves, so a loop of a million appends builds a lopsided binary tree, a rope. Reading `.length` is free. The first operation that needs contiguous characters (`charCodeAt`, indexing, a regex, `JSON.parse`) "flattens" it: it copies every character into one flat buffer, and the million tree nodes become garbage. Measured on Node 22.17.1: 3,000,000 characters cost 53.4 MiB of heap as a rope and 2.9 MiB once flat. The first `charCodeAt` took about 2.5 to 3.7 ms, and the second about 0.03 ms.

**Show me**

```typescript
// Measured as plain JS: node --expose-gc rope.mjs (types shown for reading only)
const heap_mib = (): number => { gc!(); gc!(); return process.memoryUsage().heapUsed / 1048576; };

const piece_count = 1_000_000;
const baseline = heap_mib();
let log_line = "";
for (let index = 0; index < piece_count; index += 1) {
    log_line += "ab" + (index % 10);           // each += is a new ConsString node, no copy
}
console.log(heap_mib() - baseline);            // ~53.4 MiB: 1M nodes + 1M 3-char leaves

log_line.length;                               // free: the node caches the total length
log_line.charCodeAt(piece_count);              // ~3 ms: flattens, copies all 3M chars once
console.log(heap_mib() - baseline);            // ~2.9 MiB: one flat one-byte string
```

**Why it matters**

A service that builds a big response or log line with `+=` holds about 18x the memory until something flattens it. The flatten cost then lands on whichever request does the first read, not on the loop that built the string, so a profiler blames the wrong line. Rust's `String` and C++'s `std::string` are always contiguous and pay for this up front with amortized doubling. .NET `string` copies on every `+`. .NET's `StringBuilder` is the closest cousin: it is a linked list of chunks, and its docs warn that indexing it walks that list. So iterating a large chunky builder by index is O(n^2).

**Chew on this**

Where in your hot paths is a string built piece by piece and then handed to something that indexes it, and which request pays for the flatten? If you switched to an array of pieces and `join`, would you be removing the rope, or just moving the copy somewhere else?

**Sources**

- https://github.com/v8/v8/blob/main/src/objects/string.h (ConsString, flattening)
- https://learn.microsoft.com/en-us/dotnet/api/system.text.stringbuilder.chars

**Verified**

The heap and time numbers come from two runs of the `.mjs` form on Node 22.17.1 with `--expose-gc`. The cutoff below which V8 builds a flat string instead of a ConsString comes from the earlier sliced-string entry, not from today's run.

# The functional angle: what a closure captures is decided by a different authority in each language, and only Rust's is the language spec

Draws on the Rust tip (`let _ = payload` in a `move` closure). The question is what a closure holds when its body names a variable but does nothing with it.

```rust
// Rust, edition 2021: language-defined. `let _ = place` is not a use.
let payload = vec![0_u8; 1024];
let ignores_payload = move || { let _ = payload; };
assert_eq!(std::mem::size_of_val(&ignores_payload), 0);
```

```cpp
// C++20: language-defined via odr-use. sizeof is unevaluated, (void)x is not.
std::vector<unsigned char> payload(1024);
auto names_unevaluated = [=] { return sizeof(payload); };  // sizeof(lambda) == 1
auto discards_payload  = [=] { (void)payload; };           // sizeof(lambda) == 24, and a 1 KiB deep copy
```

```fsharp
// F# 8: decided by the optimizer, not the language.
let makeClosure () =
    let local = Array.zeroCreate<byte> 1024
    fun () -> let _ = local in ()
// closure fields via reflection:  --optimize-  [| "local:Byte[]" |]   --optimize+  [||]
```

| Language | Who decides | `let _ = x` / `(void)x` in the body | What it costs |
| --- | --- | --- | --- |
| F# | the optimizer | captured in Debug, dropped in Release | Debug and Release keep different objects alive. A leak you find in Debug may not exist in production, and the reverse |
| Rust | the language (RFC 2229, edition 2021) | not captured; 0-byte closure | nothing, but edition 2018 code captures and moves the whole variable |
| C++ | the language (odr-use) | `(void)x` captures, deep copy under `[=]`; `sizeof(x)` does not | a "harmless" `(void)payload;` to silence a warning copies a vector into every lambda |
| TypeScript | V8, per scope | irrelevant: the context is shared by every closure in the scope | measured on [2026-10-02](2026-10-02.md): a closure that never names a buffer keeps it alive when a sibling closure does |

Immutability does not change any row. Each language captures the same thing whether the variable is mutable or not, so the cost comes from the capture rule, not from mutation.

Left hanging: if a capture list is the part of a closure's type that you cannot see, should your code review treat every closure that outlives its scope as a resource that needs an owner?

# The security angle: `_` ends a lock's life on the line it was taken in exactly one of four languages, and that one only warns for its own std types

Draws on the Rust tip, Mode B: the tip taught when `let _` drops, so is that safe? The direction is mixed. Rust prevents the common case and still allows the general one.

```rust
// Looks like "take the lock, ignore the guard". It is "take it and release it".
// rustc 1.95 rejects this for std::sync guards (let_underscore_lock)...
let _ = accounts.lock().unwrap();
debit(&accounts_view, amount);   // runs with no lock held

// ...but not for a custom guard: compiles silently, and the lease is already returned.
let _ = pool.checkout();
```

```cpp
// C++, three spellings, three lifetimes (Apple clang 21, -std=c++2c, run):
std::lock_guard<std::mutex>{table_lock};          // temporary: unlocked on this line. Warns (libc++ nodiscard)
std::unique_lock<std::mutex>(table_lock);         // declares a NEW unlocked unique_lock named table_lock!
                                                  // -Wvexing-parse warns; the mutex is never touched
auto _ = std::lock_guard(table_lock);             // held to the end of scope. C++26 P2169 only adds
                                                  // permission to declare a second `_` in the same scope
```

```fsharp
let _ = acquire ()   // F#: evaluated and discarded, and Dispose is NEVER called. No warning
use _ = acquire ()   // disposed at the end of scope
```

```typescript
const _ = acquire();  // TS: never disposed
using _ = acquire();  // TS 5.2+: disposed at the closing brace (tested on tsc 6.0.3, Node 22.17.1)
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust (the baseline here, because only Rust drops on `_`) | `let _ = guard()` drops at once: a critical section with no lock (CWE-667) | deny-by-default lint for std `Mutex`/`RwLock` guards, including through the `Result` | custom guards, pool leases and third-party guards: grep for `let _ =` on anything with `Drop` |
| C++ | `T(m);` declares a variable; `T{m};` is a temporary | `-Wvexing-parse`, and libc++ marks lock constructors `[[nodiscard]]` | treat both warnings as errors; prefer `std::scoped_lock lock{m};` with a real name |
| F# | `let _ =` on an `IDisposable` leaks it: no dispose ever | nothing for object expressions or factory functions | use `use` for every disposable; `let _ =` on an acquire function deserves a review comment |
| TypeScript | `const` instead of `using` leaks the resource | nothing: `using` is opt-in | lint rules or review for `Disposable`-returning calls not bound with `using` |

The same pattern on a verification call is CWE-252 (unchecked return value). `let _ = verify_signature(...)` silences `#[must_use]` on purpose, and no lint will argue with it.

Left hanging: in your codebase, does `_` mean "I do not care about this value" or "I do not care about this value's *lifetime*", and have the two meanings ever met in the same line?

Sources: https://cwe.mitre.org/data/definitions/667.html, https://cwe.mitre.org/data/definitions/252.html, https://wg21.link/p2169, https://doc.rust-lang.org/rustc/lints/listing/deny-by-default.html#let-underscore-lock, https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-2.html

# FAQ

**Does the Rust `let _` rule change in edition 2024?** No. Edition 2024 changed temporary scope for `if let` and tail expressions, not the wildcard pattern.

**Does `let _: () = expr;` behave like `let _ = expr;`?** Yes. The type ascription does not create a binding, so a temporary still drops at the semicolon.

**Which other std templates deduce one `T` from two arguments?** `std::min`, `std::max`, `std::clamp`, and `std::minmax`. `std::ranges::max` has the same requirement.

**Is FSharp.Core 10.1.300 usable from a .NET 8 app?** Yes. It targets netstandard2.1 and ran here on the .NET 8.0.8 runtime. Set `DisableImplicitFSharpCoreReference` and add an explicit `PackageReference`.

**Does `Array.join` avoid the V8 rope?** It builds a flat string in one go, so there are no ConsString nodes. The full copy still happens once, at the `join`.
