# Daily Tips: 2026-09-15

## Rust: A trait object's elided lifetime comes from the containing type, not the use site

*Type system deep cuts*

**Did you know**

When you write `dyn Trait` with no explicit lifetime, the compiler does not
infer one from context. It reads the bounds declared on the generic parameter of
the *containing* type. `Box<T>` and `Rc<T>` declare `T: ?Sized` with no lifetime
bound, so the default is `'static`. `&'a T` and `Ref<'a, T>` require `T: 'a`, so
the default there is `'a`. Two bounds means no default at all and a hard error
(E0228). This is why `Box<dyn Trait>` in a struct suddenly demands `+ 'a` while
`&dyn Trait` in the same struct never does.

**Show me**

```rust
use std::fmt::Debug;
use std::rc::Rc;

// Box<T> has no lifetime parameter, so `dyn Debug` defaults to 'static here.
// Drop the `+ 'a` and rustc rejects it: "'a must outlive 'static".
fn boxed<'a>(r: &'a str) -> Box<dyn Debug + 'a> { Box::new(r) }
fn shared<'a>(r: &'a str) -> Rc<dyn Debug + 'a> { Rc::new(r) }

// &'x T implies T: 'x, so `&dyn Debug` already elides to `&'x (dyn Debug + 'x)`.
// Nothing to annotate. Same signature shape, opposite default.
fn borrowed<'a>(r: &'a &'a str) -> &'a dyn Debug { r }

// A user type inherits whatever default its own bound implies.
struct Wrap<'a, T: ?Sized + 'a>(&'a T);
fn wrapped<'a>(r: &'a &'a str) -> Wrap<'a, dyn Debug> { Wrap(r) }

// The INNERMOST object sets the bound, so wrapping in a reference changes
// nothing. rustc prints the type it actually wants, which settles the argument:
//   expected `&'a Box<(dyn Debug + 'static)>`
fn inner<'a>(r: &'a str) -> &'a Box<dyn Debug> { todo!() }
```

**Why it matters**

This is the mechanism behind the `Box<dyn Error>` lifetime fights that look
arbitrary. Once you know the default is read off the container, you can predict
which of your type-erased fields will need `+ 'a` before you compile, and you
stop reaching for `'static` (and therefore for `String` clones and `Arc`) just
to make a signature typecheck.

**Chew on this**

Look at the `Box<dyn _>` fields in your own types: how many are `'static` by
accident rather than by design, and what did you clone to satisfy them? And if
you have a container of your own that stores `T: ?Sized`, what default did you
accidentally publish to your callers by choosing to bound it by `'a` or not?

**Sources**

- https://doc.rust-lang.org/reference/lifetime-elision.html#default-trait-object-lifetimes
- https://doc.rust-lang.org/error_codes/E0228.html

## C++: C++26 standardized library hardening, and your libc++ still ships it switched off

*New discoveries and currently popular patterns*

**Did you know**

C++26 was technically finalized at the March 2026 Croydon meeting, and one of
the four headline features is a hardened standard library (P3471R4): `operator[]`,
`front`, `back`, `pop_back`, `subspan`, and the `optional`/`expected` accessors
all gain checked preconditions that must terminate on violation. The catch is
one sentence in the paper: "It is implementation-defined whether the
implementation is a hardened implementation." So conformance does not mean your
build is checked. Verified locally on Apple clang 21 / libc++: the default is
unhardened at `-O0` and at `-O2`, and an out-of-bounds `v[7]` prints a garbage
`0` and exits 0.

**Show me**

```cpp
#include <vector>
#include <cstdio>
int main() {
    std::vector<int> v{1, 2, 3};
    std::size_t i = 7;
    std::printf("%d\n", v[i]);   // hardened precondition: i < size()
}
```

```text
# Apple clang 21, libc++, measured 2026-09-15:
clang++ -std=c++23 -O2 hard.cpp                     -> prints 0,  exit 0   (!)
  -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST  -> exit 133, NO output
  -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_DEBUG -> message, exit 134
  -D_LIBCPP_ASSERTION_SEMANTIC=..._OBSERVE              -> hard #error, experimental
# fast mode traps on a single instruction, which is why it is silent:
#   vector.h:414: libc++ Hardening assertion __n < size() failed   <- DEBUG only
```

**Why it matters**

Fast mode is the production mode (Google reports ~0.3% cost across hundreds of
millions of lines, 1000+ bugs found), but it trades a wrong answer for a bare
`SIGTRAP` with nothing on stderr. In a server's logs that is indistinguishable
from a hardware fault or a debugger breakpoint, and you will not know which
container it was. That is a deliberate tradeoff, not an oversight: the check has
to be one instruction to be free.

**Chew on this**

Do you know, without checking, which hardening mode your production toolchain
was configured with? Your vendor chose it at libc++ build time and nothing in
your own build files records it. And if you turn fast mode on tomorrow, is a
silent trap in a request handler an improvement over reading one stale int, or
have you just converted a corrupt response into an outage?

The same off-by-one has three personalities worth holding side by side. Rust
panics on `v[7]` unconditionally, with an index, a length, and a backtrace, and
you pay for that bounds check on every access you did not write as an iterator.
C++ gives you a wrong answer by default and a mute trap when you opt in. In
Node, `arr[7]` is `undefined`, which arithmetics into `NaN` and surfaces three
call frames away as something that looks nothing like an index bug. Only one of
the three tells you what happened, and it is the one that charged you for it up
front.

**Sources**

- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3471r4.html
- https://libcxx.llvm.org/Hardening.html
- https://herbsutter.com/2026/03/29/c26-is-done-trip-report-march-2026-iso-c-standards-meeting-london-croydon-uk/
- https://gcc.gnu.org/onlinedocs/libstdc++/manual/using_macros.html

**Verified**

Compiled and run on Apple clang 21.0.0 / libc++ (arm64-darwin), all four rows of
the table above measured, not recalled. No GCC on this machine: the libstdc++
side rests on documentation only, and `_GLIBCXX_ASSERTIONS` is the nearest
equivalent macro rather than a confirmed P3471 implementation. Reports that GCC
15 and MSVC 19.44 partially implement P3471R4 came from secondary commentary and
could not be checked against a primary support table (cppreference returned 403).

## TypeScript: `void` in return position is the type system's one deliberate hole

*Idioms and antipatterns*

**Did you know**

A function type that returns `void` will accept a function returning absolutely
anything, and the handbook says so outright: a contextual function type with a
`void` return type, "when implemented, can return any other value, but it will
be ignored." That is not a soundness bug, it is there so `src.forEach(el =>
dst.push(el))` typechecks when `push` returns a number. It also means every
`async` callback you hand to a `void`-returning parameter is waved through under
`--strict`, floating promise and all. The hole is narrow: `const x: void = 1` is
still TS2322.

**Show me**

```ts
type Handler = (id: string) => void;

const save = async (id: string): Promise<void> => { throw new Error("db down"); };

const h: Handler = save;          // clean under --strict. Promise, erased to void.
const run = (ids: string[]) => ids.forEach(save);   // same hole, via forEach

const observed = h("a");          // typed `void`. You cannot .catch() what you
                                  // cannot see, and tsc will stop you trying.

// The defense is in the handbook's own exception: "when a LITERAL function
// definition has a void return type, that function must not return anything."
// Annotate the literal instead of the variable and async becomes unwritable:
const ok: Handler = async (id: string): void => {};
// TS1064: The return type of an async function or method must be the global
//         Promise<T> type. Did you mean to write 'Promise<void>'?
```

**Why it matters**

Measured just now on Node 22: `["a","b"].forEach(save)` throws out of the
microtask queue and kills the process with exit 1, after `forEach` has already
returned successfully. Nothing awaited it, nothing could have caught it, and the
stack trace reads `at Array.forEach`. On a long-running server that is a whole
process gone, taking every in-flight request with it, because a type annotation
was placed on the variable rather than on the function.

**Chew on this**

Grep your own callback-taking signatures for `=> void`. How many of them are
called in a place that could actually await the result, and how many of those
would you rather have declared `=> Promise<void> | void` and handled? And for
the ones that genuinely cannot await: is throwing the right contract for a
callback nobody is listening to, or should it be returning a result you are
forced to look at?

**Sources**

- https://www.typescriptlang.org/docs/handbook/2/functions.html#return-type-void
- https://nodejs.org/api/cli.html#--unhandled-rejectionsmode

# Appendix A: how `&'a` and `'static` actually work

Not part of the tip rotation. Added 2026-09-15 on request, after the Rust tip
above. Appendix A covers the Rust mechanism; Appendix B answers "does C++ have
an equivalent" and is where the two of them stop lining up.

Every snippet in both was compiled and run locally, and every diagnostic is
quoted from the compiler rather than recalled: rustc 1.95.0 for Appendix A,
Apple clang 21.0.0 / libc++ (arm64-darwin) for Appendix B.

## A.1 A lifetime is a region of code, not a duration

`'a` is not wall-clock time and not a scope. It is a *set of program points*
over which a borrow must stay valid, and rustc derives it from where the
reference is **last used**.

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];        // borrow's region starts
println!("{first}");      // LAST USE -> region ends here
v.push(4);                // legal: `first` is still in scope, region is closed
println!("{v:?}");        // [1, 2, 3, 4]
```

Move the `println!("{first}")` below the `push` and the identical code is
rejected with E0502, because the region now spans the mutation. Nothing about
the data changed, only the region.

Why the name misleads a C++ reader: in C++ you reason about object *extent*, and
the iterator dangles when the vector reallocates. Rust is not tracking extent.
It is solving a constraint system over code regions at compile time, and the
question is never "is this pointer still good" but "does the region I need
outlive the region I have".

## A.2 The caller picks `'a`, never the function

`'a` is an input parameter, exactly like `T`. The body cannot choose it; the
signature only states a relationship that callers must satisfy.

```rust
// Contract: "the returned borrow is valid wherever BOTH inputs are."
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

let long = String::from("aaaa");
{
    let short = String::from("bb");
    let picked = longest(&long, &short);  // 'a := short's region (the shorter)
    println!("inside: {picked}");         // last use inside it -> compiles
}
```

Hoist that last use past the closing brace and you get E0597, `short does not
live long enough`. The function did not change; the caller's demanded region
did. Note the cost: `<'a>` generates no code and adds no runtime overhead. It is
a proof obligation. C++ has no type-system equivalent, so the same guarantee
lives in a doc comment.

## A.3 `'static` as a reference lifetime

`&'static T` means the region is the whole program. Three honest sources:

```rust
static TABLE: [u8; 3] = [1, 2, 3];

let lit: &'static str = "in the binary";                   // 1. literal, .rodata
let item: &'static [u8] = &TABLE;                          // 2. a `static` item
let leaked: &'static str = Box::leak(s.into_boxed_str());  // 3. deliberate leak
```

`'static` is a *subtype* of every other lifetime, so it coerces downward only:

```rust
fn takes_any<'a>(s: &'a str) -> usize { s.len() }
fn needs_static(s: &'static str) -> usize { s.len() }

takes_any(lit);        // 'static -> 'a  : fine, subtyping
takes_any(&owned);     // short 'a       : fine
needs_static(lit);     // exact          : fine
needs_static(&owned);  // 'a -> 'static  : REJECTED
```

Source 3 is a `new` you never `delete`, made explicit: memory traded for a
lifetime. C++ has all three of these storage flavours and, as B.1 shows, almost
no way to say so in a type.

## A.4 `T: 'static` is a different claim, and this is the whole game

When `'static` is a bound on a *type* rather than on a reference, it does not
mean "lives forever". It means: **T contains no borrow that could dangle,
therefore a T may be held for as long as anyone likes.** Owned data satisfies it
trivially.

```rust
fn hold_forever<T: 'static>(x: T) -> T { x }

let s = String::from("built at runtime");
let s = hold_forever(s);   // ACCEPTED. String: 'static holds.
println!("{s}");           // ...and s drops at the end of main, as normal
```

A heap `String` created at runtime and destroyed milliseconds later satisfies
`T: 'static`, because the bound is about what is *inside* the type. What fails
is a type that does carry a borrow:

```rust
let local = String::from("x");
hold_forever(&local);
// error[E0597]: `local` does not live long enough
//   argument requires that `local` is borrowed for `'static`
```

Two hats, one spelling, and nearly every "why does this need `'static`?!"
is someone reading the second as the first:

| Form | Reads as |
| --- | --- |
| `&'static T` | this **reference** is valid for the whole program |
| `T: 'static` | this **type** holds no references, so you may keep it indefinitely |

Mnemonic that sticks: `T: 'static` means *"T is not borrowing from anything"*.
The diagnostic above even preserves the distinction, complaining that `local`
must be *borrowed for* `'static` rather than that the type is wrong.

## A.5 Back to the tip

`Box<dyn Debug>` desugars to `Box<dyn Debug + 'static>`, and by A.4 that bound
reads: the erased concrete type holds no borrows. It says nothing about the box
being immortal.

```rust
fn erase<T: Debug + 'static>(x: T) -> Box<dyn Debug> { Box::new(x) }

let s = String::from("owned, so 'static holds");
let b = erase(s);      // fine
println!("{b:?}");     // and `b` drops right here. Not immortal.
```

Type erasure discards the concrete type, so the compiler loses the ability to
check any borrow that type was holding. `+ 'static` is the safe default it
picks: *if I cannot see inside, I demand there is nothing borrowed inside.*
Writing `Box<dyn Debug + 'a>` instead promises "there IS a borrow in there, good
for at least `'a`", which it can still verify at the construction site.

Which is why the two halves of the tip behave oppositely. `Box<T>` has no
lifetime parameter, so it has no `'a` to offer and falls back to `'static`.
`&'a T` already requires `T: 'a` in its own declaration, so a tighter default is
sitting right there.

The C++ mirror is `std::function<void()>`, which is `Box<dyn FnMut()>` with the
bound not loosened but *absent*. Capture a reference to a local, outlive the
local, and nothing anywhere diagnoses it. The honest framing is not "C++ picks a
looser default" but "C++ has no vocabulary in which that default could be
stated", which is what Appendix B works through. Rust's default is the strict
one, which is why it shouts about `'static` when you were only trying to store a
callback.

- https://doc.rust-lang.org/reference/trait-bounds.html#lifetime-bounds
- https://doc.rust-lang.org/reference/subtyping.html
- https://doc.rust-lang.org/nomicon/lifetimes.html
- https://doc.rust-lang.org/std/boxed/struct.Box.html#method.leak
- https://doc.rust-lang.org/error_codes/E0597.html

# Appendix B: does C++ have an equivalent to `'static`?

The two hats from A.4 come apart completely. `&'static T` has a partial C++
equivalent. `T: 'static` has none, and that gap is the interesting part.

## B.1 Hat 1: `&'static T`, a reference valid for the whole program

C++ has all the *storage* and almost no way to name it *in a type*.

| Rust | C++ | Expressible in the type? |
| --- | --- | --- |
| `&'static T` from a literal | string literal (static storage duration) | No. `const char*` says nothing |
| `&'static T` from a `static` item | global, `static` local, `static` member, `constinit` | No |
| `Box::leak` | a `new` you never `delete` | No |
| `&'static T` as a checked constraint | C++20 reference NTTP | **Yes**, and enforced |

That last row is the one real equivalent, and it is narrow. A reference used as
a non-type template parameter must name an object with static storage duration,
and the compiler enforces it:

```cpp
template <const int& R> struct Holder { int get() const { return R; } };
static const int GLOBAL = 7;

Holder<GLOBAL> ok;              // accepted

const int local = 9;
Holder<local> bad;
// error: non-type template argument is not a constant expression
// note:  reference to 'local' is not a constant expression
```

So that genuinely is `&'static` checked at compile time. But it only works as a
template parameter. You cannot pass such a reference as a function argument or
store it in a struct field, and the moment the reference becomes a runtime value
C++ forgets everything about where it points.

## B.2 Hat 2: `T: 'static`, this type holds no borrows

No equivalent. Not in the language, not in `<type_traits>`, not in any standard
annotation. You cannot ask a type whether it stores a borrow:

```cpp
struct HoldsABorrow { std::string_view sv; };           // borrows
struct HoldsARef    { std::reference_wrapper<int> r; }; // borrows
struct Owns         { int n; };                         // does not
```

```text
HoldsABorrow   trivially_copyable=1  is_reference=0  is_pointer=0
HoldsARef      trivially_copyable=1  is_reference=0  is_pointer=0
Owns           trivially_copyable=1  is_reference=0  is_pointer=0
```

Identical, measured. Every trait in the standard library is blind to the
distinction, because C++ tracks *shape* (is this a pointer, is this trivially
copyable) and never *provenance* (does this borrow from something that might die
first). `std::string_view` and `std::span` are precisely `&'a [T]` with the `'a`
deleted, and `std::reference_wrapper` launders a reference into a value that no
trait flags.

This is why the `Box<dyn Debug>` default from A.5 has no C++ analogue to compare
against. Rust's `+ 'static` is a bound the compiler can *verify* on an erased
type. In C++ the bound is not looser, it is unsayable.

## B.3 The nearest thing C++ does have: `[[clang::lifetimebound]]`

Closest mechanism to `&'a`. Non-standard, but shipping and useful:

```cpp
const std::string& pick(const std::string& a [[clang::lifetimebound]],
                        const std::string& b) { return a; }

const std::string& leak() {
    return pick(std::string("temp"), std::string("other"));
}
// warning: returning reference to local temporary object [-Wreturn-stack-address]
```

Control test matters here, because it is easy to credit this to general compiler
analysis. Identical code with the attribute removed produces **no lifetime
warning at all**, only `-Wunused-parameter`. The attribute is doing all of the
work.

But note its reach. It expresses "the return borrows from *this* parameter": one
relationship, checked by a local heuristic inside one function body. It is `'a`
for a single pattern. There is no `[[clang::static]]` counterpart, nothing that
propagates through a struct field, and nothing that survives type erasure.
Clang's experimental lifetime-safety work and the C++26 profiles discussion aim
at this gap; neither is something to rely on today.

## B.4 Summary

| Rust concept | C++ status |
| --- | --- |
| static storage duration | Has it, cannot name it in a type |
| `&'static T` as a constraint | Only via C++20 reference NTTP, template params only |
| `&'a T` relationship | `[[clang::lifetimebound]]`, one param, one function, Clang-only |
| `T: 'static` bound | Nothing. No trait, no syntax, no annotation |
| `dyn Trait + 'static` default | `std::function` with the bound absent, not defaulted |
