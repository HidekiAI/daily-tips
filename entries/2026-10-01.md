## Rust: `String::from_utf8_lossy_owned` keeps your buffer only when nothing needed replacing, and one stray byte frees it

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.99.0 (released 2026-10-01) stabilized `String::from_utf8_lossy_owned(Vec<u8>) -> String` and `FromUtf8Error::into_utf8_lossy`. The name says "owned", and on valid input it is: the `Vec` becomes the `String`, same pointer, same capacity. On input with even one invalid byte it is not: the 1.99.0 source calls `from_utf8_lossy(&v)`, takes the `Cow::Owned` it returns, and drops your `Vec`. A 4096-byte recycled read buffer comes back as a fresh 32-byte `String`, and the big allocation is gone.

**Show me**

```rust
// rustc 1.99.0, --edition 2024, -O. Printed values are from that run.
fn main() {
    // A recycled read buffer: big capacity, small payload.
    let mut clean: Vec<u8> = Vec::with_capacity(4096);
    clean.extend_from_slice(b"GET /index.html");
    let clean_ptr = clean.as_ptr();
    let text = String::from_utf8_lossy_owned(clean);
    println!("clean: same buffer {}, capacity {}", text.as_ptr() == clean_ptr, text.capacity());
    // clean: same buffer true, capacity 4096   <- the Vec became the String

    let mut dirty: Vec<u8> = Vec::with_capacity(4096);
    dirty.extend_from_slice(b"GET /index\xFF.html"); // one stray byte
    let dirty_ptr = dirty.as_ptr();
    let text = String::from_utf8_lossy_owned(dirty);
    println!("dirty: same buffer {}, capacity {}", text.as_ptr() == dirty_ptr, text.capacity());
    // dirty: same buffer false, capacity 32    <- a new String, the 4096-byte buffer freed

    // FromUtf8Error::into_utf8_lossy (also 1.99) takes the same fork: it copies
    // the valid prefix into a fresh Vec sized to the input, then appends.
    let retry: Vec<u8> = b"GET /index\xFF.html".to_vec();
    let repaired = String::from_utf8(retry).unwrap_or_else(|error| error.into_utf8_lossy());
    println!("{}", repaired.contains(char::REPLACEMENT_CHARACTER)); // true
}
```

**Why it matters**

A read loop that recycles one big buffer per connection and decodes it with `from_utf8_lossy_owned` gets the reuse it expects on every clean request and a free-plus-malloc on every dirty one, so the allocation profile depends on what clients send. Replacing in place cannot work in general: U+FFFD is 3 bytes and the invalid byte it replaces may be 1, so the output can be longer than the input. .NET's `Encoding.UTF8.GetString` and TypeScript's `TextDecoder.decode` never had the choice to make: UTF-16 output means a new string every time, clean or not. C++ has no lossy decoder in std at all since `<codecvt>` was deprecated in C++17.

**Chew on this**

Which of your decode sites assume the clean path's cost? If a client can choose to send one bad byte per request, what does that do to the buffer pool you sized from your benchmarks?

## C++: `unordered_map::reserve(n)` is one allocation, and the `n` inserts after it are `n` more

*Perf and memory model*

**Did you know**

`reserve(n)` on `std::unordered_map` allocates the bucket array and nothing else. Every insert after it still allocates a node: measured on libc++, `reserve(1000)` is one 8072-byte allocation, and the 1000 inserts that follow are 1000 more, 24 bytes each for `<int, int>` (32 after macOS malloc rounding). This is not a libc++ choice. Since C++11 the standard guarantees that rehashing invalidates iterators but never pointers or references to elements, and C++17's `extract` hands out a node you can move between maps; both rule out open addressing, so every conforming `unordered_map` is node-based.

**Show me**

```cpp
// clang++ -std=c++20 -O2; Apple clang 21 and Homebrew clang 23.1.1, both libc++.
#include <cstdio>
#include <cstdlib>
#include <new>
#include <unordered_map>

static std::size_t alloc_count = 0;
void* operator new(std::size_t size) {           // count every heap allocation
    ++alloc_count;
    if (void* block = std::malloc(size)) return block;
    throw std::bad_alloc{};
}
void operator delete(void* block) noexcept { std::free(block); }
void operator delete(void* block, std::size_t) noexcept { std::free(block); }

int main() {
    std::unordered_map<int, int> table;
    table.reserve(1000);                          // 1 allocation: the bucket array (1009 buckets)
    std::size_t after_reserve = alloc_count;
    for (int key = 0; key < 1000; ++key) table.emplace(key, key);
    std::printf("inserts after reserve: %zu allocations\n", alloc_count - after_reserve);
    // inserts after reserve: 1000 allocations   <- one 24-byte node each (32 after malloc rounding)

    int* stable = &table.at(7);
    table.rehash(100000);                         // buckets move, nodes do not
    std::printf("reference survives rehash: %d\n", stable == &table.at(7));  // 1
    // That guarantee is the reason for the nodes: the standard promises it.
}
```

**Why it matters**

On a hot path, a "pre-sized" map still costs one malloc and one free per entry, plus a pointer chase per lookup into memory scattered across the heap. Rust's `HashMap::with_capacity(1000)` followed by 1000 inserts made **0** allocations here, because SwissTable stores entries inline and buys that by moving them on resize: a `&V` into a Rust map cannot outlive the next insert, which the borrow checker enforces. .NET's `Dictionary<int,int>(1000)` keeps entries in one array as well (3456 bytes allocated across 1000 inserts in `dotnet fsi`, not per entry). C++ gets the same layout only outside std: `boost::unordered_flat_map` (Boost 1.81) or `absl::flat_hash_map`, which drop the reference-stability guarantee to get it.

**Chew on this**

Does any code of yours actually hold a pointer into an `unordered_map` across an insert? If not, what is the reference-stability guarantee buying you, and who would notice if you gave it up?

## F#: a unit of measure is gone at runtime, and FS1240 only warns when you write the unit in the type test yourself

*Type system deep cuts*

**Did you know**

`float<meter>` and `float<second>` compile to the same `System.Double`, so a type test cannot tell them apart. Write `:? float<second>` against a boxed meter and the compiler warns FS1240, "This type test or downcast will ignore the unit-of-measure 'second'", then matches anyway. Move the same test behind a type parameter (`:? 'T` called with `'T = float<second>`), or let a serializer do it, and there is no warning at all: meters go in, seconds come out. Checked on F# 8 / FSharp.Core 8.0 / .NET 8.0.8; units have been erased since they shipped in F# 2.0.

**Show me**

```fsharp
// dotnet fsi, SDK 8.0.401: F# 8, FSharp.Core 8.0, .NET 8.0.8. Output is from that run.
[<Measure>] type meter
[<Measure>] type second

let distance: float<meter> = 5.0<meter>

// Written out, the compiler warns FS1240: "This type test or downcast will
// ignore the unit-of-measure 'second'". It still matches.
match box distance with
| :? float<second> as elapsed -> printfn "seconds: %g" (float elapsed)   // seconds: 5
| _ -> printfn "not seconds"

// The same test behind a type parameter: no warning, same answer.
let try_as<'T> (boxed: obj) : 'T option =
    match boxed with
    | :? 'T as value -> Some value
    | _ -> None

printfn "%A" (try_as<float<second>> (box distance))     // Some 5.0
printfn "%b" (typeof<float<meter>> = typeof<float>)      // true: one runtime type

// A serializer is generic code too: meters out, seconds in, no diagnostic.
let json = System.Text.Json.JsonSerializer.Serialize distance
let elapsed = System.Text.Json.JsonSerializer.Deserialize<float<second>> json
printfn "%s -> %g s" json (float elapsed)                // 5 -> 5 s

// A [<Struct>] single-case union survives erasure: a float is not a Meters.
[<Struct>] type Meters = Meters of float
printfn "%b" (match box 5.0 with :? Meters -> true | _ -> false)  // false
```

**Why it matters**

Units protect arithmetic inside one compilation, and nothing at the edges: a cache of `obj`, a `Dictionary<string, obj>` of settings, a JSON payload, or a generic `try_as` helper all launder a unit away silently. TypeScript's branded types (`number & { __brand: "meter" }`) are the exact twin, erased at runtime and forgeable by anything that produces a `number`. Rust's `struct Meters(f64)` and a C++ `struct Meters { double value; }` are real types at zero runtime cost, so a boxed `dyn Any` holding `Meters` will not downcast to `Seconds`; F#'s `[<Struct>]` single-case union is the same trade, at the price of `Meters value` wrapping and unwrapping you do not pay with units.

**Chew on this**

Where does a unit-annotated value in your code cross into `obj`, a generic, or a serializer? On the far side, what is the first line that would have caught a meter arriving where a second was expected?

## TypeScript: `structuredClone` is typed `(value: T) => T`, and a class instance comes back without its class

*Stdlib and ecosystem gems*

**Did you know**

Both `lib.dom.d.ts` (TypeScript 6.0.3) and `@types/node` 22 declare `structuredClone<T>(value: T): T`. The runtime clones own data properties only: the prototype is dropped, so a `Session` comes back as a plain object whose methods are `undefined` while the type still says `Session`. It handles `Date`, `Map`, `Set`, cycles, and typed arrays, which is why it replaced `JSON.parse(JSON.stringify(...))`; it throws `DataCloneError` on functions; and none of this reaches the type checker. Global in Node 17+.

**Show me**

```typescript
// tsc 6.0.3 --strict --lib es2022,dom; Node 22.17.1. Output is from that run.
class Session {
    constructor(public user: string, public expires: Date) {}
    is_expired(now: Date): boolean { return now >= this.expires; }
}

const original = new Session("ada", new Date("2026-10-01T12:00:00Z"));
const copy: Session = structuredClone(original);  // lib.dom: structuredClone<T>(value: T): T

console.log(copy instanceof Session);           // false: the prototype was not cloned
console.log(copy.expires instanceof Date);      // true: Date, Map, Set, RegExp do survive
console.log(Object.keys(copy));                 // [ 'user', 'expires' ]: own data only
console.log(typeof copy.is_expired);            // undefined, typed as a method
try {
    copy.is_expired(new Date());                // compiles cleanly
} catch (error) {
    console.log((error as Error).message);      // copy.is_expired is not a function
}

// Functions are the one case it refuses loudly: DataCloneError at runtime,
// and still no compile error, because T = { on_done: () => number } is accepted.
try { structuredClone({ on_done: () => 1 }); } catch (error) { console.log((error as Error).name); }
```

**Why it matters**

A cloned domain object passes every compile-time check and fails at the first method call, often far from the clone, and `instanceof` guards downstream quietly take their `false` branch. Rust's `Clone` is opt-in per type and returns the real type, so cloning a type without `Clone` does not compile; C++'s copy constructor is the same contract by convention. F# records rarely need cloning at all, since `{ r with ... }` shares what did not change. TypeScript's honest signature would be "the structured-serializable subset of `T`", which the type system can almost express and the lib chose not to.

**Chew on this**

Which of your `structuredClone` calls take a class instance, or an object that contains one three levels down? What would a signature look like that rejected those at compile time, and what would it cost the callers that pass plain data?

- https://nodejs.org/api/globals.html#structuredclonevalue-options

# The functional angle: returning the input untouched when nothing changed is free only where identity is visible

Draws on the Rust tip, with F# and C++ as rows. The shape: a transformation that usually changes nothing, and whether it can hand back the original instead of a copy.

```rust
// from_utf8_lossy(&[u8]) -> Cow<str>: Borrowed when clean, Owned when it replaced something.
// from_utf8_lossy_owned(Vec<u8>) is that Cow with the Borrowed arm turned back into your Vec.
```

```fsharp
let original = "hello world"
obj.ReferenceEquals(original.Replace("zzz", "y"), original)    // true: nothing matched, same instance
let words = [ "a"; "b" ]
obj.ReferenceEquals(List.filter (fun _ -> true) words, words)  // false: always a new list
```

| Language | Functional form | What it costs |
| --- | --- | --- |
| F# / .NET | `String.Replace` returns `this` on no match (measured); `List.filter` keeping everything still copies (measured) | sharing is free under a GC, but each function decides; the type does not tell you which you got |
| Rust | `Cow<'a, str>` | the "maybe unchanged" outcome is in the type, so the caller sees it and pays a lifetime for it |
| C++ | none in std | `std::string` copy-on-write was removed: C++11's rules for `operator[]` and invalidation forced libstdc++ off its COW string in GCC 5 (documentation, not run) |
| TypeScript | none needed for strings | strings have no observable identity, so "same instance" is not a question; arrays always copy |

The asymmetry: F# gets sharing for free from immutability and a GC, but cannot say in a type whether it happened. Rust says it in the type and makes you carry a lifetime for the borrowed arm. C++ tried implicit sharing and the standard took it away.

Left hanging: in your hot paths, which "transform" calls usually return their input unchanged, and are you paying for a copy each time anyway?

# The security angle: lossy decoding is many-to-one, so two different names can become one key

Draws on the Rust tip, Mode B: `from_utf8_lossy_owned` is fine for a log line, but is it secure as an identifier? It runs in the direction no language here prevents. Class: CWE-180 (Validate Before Canonicalize), with CWE-176 (Improper Handling of Unicode Encoding) as the mechanism.

```rust
// rustc 1.99.0. Looks like a sensible ownership index for uploaded files.
use std::collections::HashMap;

fn record_owner(owners: &mut HashMap<String, &'static str>, raw_name: &[u8], user: &'static str) {
    let key = String::from_utf8_lossy_owned(raw_name.to_vec()); // many-to-one
    owners.insert(key, user);                                   // last writer wins
}

fn main() {
    let mut owners: HashMap<String, &'static str> = HashMap::new();
    record_owner(&mut owners, b"report\xFF.pdf", "alice");
    record_owner(&mut owners, b"report\xFE.pdf", "bob"); // a different file on disk
    println!("{} entries, owner {:?}", owners.len(), owners.values().next()); // 1 entries, owner Some("bob")
}
```

```rust
// What was meant: key on the bytes the filesystem uses; decode lossily only for display.
fn record_owner(owners: &mut HashMap<Vec<u8>, &'static str>, raw_name: &[u8], user: &'static str) {
    owners.insert(raw_name.to_vec(), user); // 2 entries for the same two names (measured)
}
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | distinct byte strings collide after lossy decode (measured) | `from_utf8` returns `Result`; lossy is opt-in, by name | never key, compare, or authorize on a lossy-decoded value |
| C# / F# | same collision (measured) | `Encoding.UTF8.GetString` is lossy **by default** | use `UTF8Encoding(false, true)` to throw `DecoderFallbackException` (measured) |
| TypeScript | same collision via `TextDecoder` and `Buffer.toString` (measured) | lossy by default | `new TextDecoder("utf-8", { fatal: true })` throws `TypeError` (measured) |
| Go | `string(bytes)` keeps invalid bytes, so no collision (measured) | no decode happens | `strings.ToValidUTF8` reintroduces the collision (measured) |

The control is Rust, because it is the only row where the strict decode is the default and the lossy one is the function with the longer name. In .NET and TypeScript the dangerous form is the one you get by not choosing.

Left hanging: which of your map keys, cache keys, or permission checks are built from bytes that went through a decoder, and does that decoder replace or reject?
