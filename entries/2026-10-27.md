## Rust: `vec![0; n]` is a calloc in every build, and `with_capacity` plus `resize(n, 0)` is one only when the optimizer says so

*Perf and memory model*

**Did you know**

`vec![0u8; n]` does not write a single zero. std's `IsZero` specialization notices that the element is all-zero bits and asks the allocator for zeroed memory (`alloc_zeroed`, which is `calloc` under glibc), and fresh pages from the kernel are already zero, so a 1 GiB vector costs 0 MiB of resident memory until you write to it. `Vec::with_capacity(n)` followed by `resize(n, 0)` builds the same bytes as malloc plus a zero fill: with `-O` LLVM rewrites that pair into `calloc` and it also costs 0 MiB, but at `opt-level=0` it costs the full 1024 MiB. One is a library guarantee, the other is the optimizer's opinion.

**Show me**

```rust
// Linux only: resident memory comes from /proc/self/statm (second field, in 4 KiB pages).
fn resident_mib() -> u64 {
    let statm = std::fs::read_to_string("/proc/self/statm").unwrap();
    let resident_pages: u64 = statm.split_whitespace().nth(1).unwrap().parse().unwrap();
    resident_pages * 4 / 1024
}

fn main() {
    const ONE_GIB: usize = 1 << 30;

    let before = resident_mib();
    // 0u8 is all-zero bits, so std's IsZero specialization asks the allocator
    // for zeroed memory (alloc_zeroed, which is calloc under glibc).
    let zeroed = std::hint::black_box(vec![0u8; ONE_GIB]);
    println!("vec![0u8; n]           +{} MiB", resident_mib().saturating_sub(before));

    let before = resident_mib();
    // The same bytes, built as malloc + a zero fill. std makes no promise here:
    // only the optimizer's malloc+memset -> calloc rewrite rescues it.
    let mut resized = Vec::with_capacity(ONE_GIB);
    resized.resize(ONE_GIB, 0u8);
    let resized = std::hint::black_box(resized);
    println!("with_capacity + resize +{} MiB", resident_mib().saturating_sub(before));

    let before = resident_mib();
    // -0.0 compares equal to 0.0, but its bits are not zero, so no calloc.
    let negative_zero = std::hint::black_box(vec![-0.0f64; ONE_GIB / 8]);
    println!("vec![-0.0f64; n]       +{} MiB", resident_mib().saturating_sub(before));

    drop((zeroed, resized, negative_zero));
}
// rustc 1.99.1 -O:           +0, +0, +1024 MiB
// rustc 1.99.1 opt-level=0:  +0, +1024, +1024 MiB
```

**Why it matters**

A server that pre-sizes a large buffer (a bitmap, a histogram, a ring of slots) pays for it at startup only if the zeros are written by hand, and that cost moves between debug and release builds, so a container memory limit tuned on a release build can kill the debug build in CI. C++ has no specialization of this kind: `std::vector<char>(1 GiB)` cost the full 1024 MiB under g++ 14.2 at both `-O0` and `-O2`, because libstdc++ writes its zeros and GCC did not rewrite them into a `calloc`. F# `Array.zeroCreate` and TypeScript `new Uint8Array(n)` hand the zeroing to the runtime (.NET's GC, V8's allocator), which has its own rules: not measured here.

**Chew on this**

Which of your large buffers is zeroed by a `resize`, a `collect` or a loop rather than by `vec![0; n]`, and has anyone ever measured it in the build profile your tests run in? If a buffer costs 0 MiB until written, what does your memory dashboard actually tell you about the next request that touches it?

**Gotchas**

- `vec![-0.0f64; n]` costs the full 1024 MiB in both builds: `IsZero` for floats tests `to_bits() == 0`, and `-0.0` has its sign bit set even though `-0.0 == 0.0`.
- A zeroed `#[derive(Clone, Copy)]` struct is not `IsZero`: `vec![Pixel { red: 0, green: 0, blue: 0, alpha: 0 }; n]` cost 1024 MiB at `opt-level=0` and 0 MiB with `-O`. Tuples and arrays of zeros, `[0u8; 4]` and `(0u32, 0u32)`, are covered (0 MiB in both builds).
- `iter::repeat(0u8).take(n).collect::<Vec<u8>>()` behaves like `resize`: 0 MiB with `-O`, 1024 MiB at `opt-level=0`.
- Reading every page of a `vec![0u8; n]` does not raise RSS either (measured +0 MiB; the kernel maps a shared zero page). Writing one byte per page raised it by 1023 MiB, so the bill arrives at the first write, not the first read.
- `vec![None::<Box<u64>>; n]` is covered too: `Option<Box<T>>` is `IsZero` because `None` is guaranteed to be the null pointer (0 MiB in both builds).

## C++: An empty `optional` is less than every value, so an unset ceiling rejects everything and an unset floor lets everything through

*Idioms and antipatterns*

**Did you know**

`std::optional<T>` compares directly against a plain `T`, and an empty optional is defined to be less than every value: `opt < value` is `opt.has_value() ? *opt < value : true`, and `value < opt` is `opt.has_value() ? value < *opt : false`. So an unset `std::optional<int>` is less than `INT_MIN`; it behaves like minus infinity. As a ceiling (`max < size`) it rejects every request, as a floor (`build < min`) it lets every request through, and in neither case did anyone decide that. The relational operators are C++17; in C++20 they are synthesized from `operator<=>`, with the same result. g++ 14.2 with `-Wall -Wextra` and Apple clang 21 with `-Weverything` warn about none of it.

**Show me**

```cpp
// C++17 for the comparisons, C++23 for optional::transform (GCC 12+, Clang 17+ with libc++).
#include <cstdio>
#include <optional>

struct UploadPolicy {
    std::optional<int> max_body_kib;       // unset: nobody configured a ceiling
    std::optional<int> min_client_build;   // unset: nobody configured a floor
};

int main() {
    UploadPolicy policy;                   // nothing configured
    constexpr int body_kib = 64;
    constexpr int client_build = 1;        // an ancient client

    // Ceiling: an unset maximum compares below every size, so every upload is "too big".
    bool too_big = policy.max_body_kib < body_kib;           // empty < value: true
    // Floor: an unset minimum compares below every build, so every client is "new enough".
    bool too_old = client_build < policy.min_client_build;   // value < empty: false
    std::printf("too_big %d, too_old %d\n", too_big, too_old);  // too_big 1, too_old 0

    // nullopt sorts below every int, INT_MIN included.
    std::printf("empty < INT_MIN: %d\n", policy.max_body_kib < -2147483647 - 1);  // 1

    // Say what "unset" means instead of letting operator< decide.
    bool allowed = policy.max_body_kib.has_value()
        ? body_kib <= *policy.max_body_kib
        : true;                            // unset ceiling: no limit
    // C++23 spelling of the same decision.
    bool allowed_23 = policy.max_body_kib
        .transform([](int ceiling_kib) { return body_kib <= ceiling_kib; })
        .value_or(true);
    std::printf("allowed %d, allowed_23 %d\n", allowed, allowed_23);  // allowed 1, allowed_23 1
}
```

**Why it matters**

The comparison against a plain value is the convenience that makes `optional` drop into code written for `int`, and the same convenience turns a forgotten config key into minus infinity, which is the right default for no limit you will ever configure. Rust orders `None` below every `Some` too (`None < Some(i32::MIN)` is `true`, measured), but `timeout < 30000` does not compile there, so you have to write `Some(30000)` and the comparison is in plain sight. F# agrees with both (`None < Some 30000` is `true`). C#'s lifted operators go the other way: `int? null < 30000` and `null >= 30000` are both `False`, so every check involving an unset value fails. In TypeScript, strict mode rejects `config.timeout_ms < 30000` (TS18048), but once something casts it away, `undefined < 30000` and `undefined >= 30000` are both `false`, while `null < 30000` is `true` because `null` converts to 0.

**Chew on this**

Where in your code does an `optional` limit, threshold or deadline meet a plain number through `<`, and is it a ceiling or a floor? If you banned the mixed comparison tomorrow, what would each call site have to say about "unset"?

- https://eel.is/c++draft/optional.comp.with.t

**Verified**

**Gotchas**

- `policy.max_body_kib < std::nullopt` is `false` and `std::nullopt < policy.max_body_kib` is `has_value()`: comparing against `nullopt` asks "is it engaged", not "is it small".
- `optional == value` is honest: an empty `optional<int>` `== 0` is `false`, measured. Only the ordering operators pick a side.
- An empty `optional<std::string>` is less than `""` (measured `1`), so a sort by an optional name puts the unset rows before the empty strings.
- `if (flag)` on a `std::optional<bool>` holding `false` takes the branch (measured `1`): the conversion asks "is there a value", not "is it true".
- `(opt <=> 5) < 0` is `true` for an empty `opt` in C++20: the three-way form keeps the same ordering, so moving to `<=>` fixes nothing.

## F#: FSharp.Core 11's `Task.parallelLimit` takes factories, not tasks, because a `Task` you can hand it is already running

*New discoveries and currently popular patterns*

**Did you know**

FSharp.Core 11 (shipping with the .NET 11 SDK, merged on 2026-09-08 and in the RC 2 release notes) adds `Async.parallelLimit` and `Task.parallelLimit`, which run work with at most N in flight and return results in input order. The `Task` version's input is `seq<CancellationToken -> Task<'T>>`, not `seq<Task<'T>>`: a .NET `Task` starts when it is created, so a limiter that received tasks would have nothing left to limit. Wrap tasks that are already started back into factories, `fun _ -> running`, and it still compiles: six 100 ms jobs then peak at 6 in flight instead of 2.

**Show me**

```fsharp
// F# 11, FSharp.Core 11.0.0, .NET 11 SDK 11.0.100-rc.3. Run with: dotnet fsi tip.fsx
open System.Threading
open System.Threading.Tasks

let peak_gate = obj ()
let mutable in_flight = 0
let mutable peak = 0

let fetch_report (report_id: int) (ct: CancellationToken) : Task<int> =
    task {
        let running = Interlocked.Increment &in_flight
        lock peak_gate (fun () -> peak <- max peak running)
        do! Task.Delay(100, ct)
        Interlocked.Decrement &in_flight |> ignore
        return report_id
    }

// Partially applied: CancellationToken -> Task<int>. Nothing has started.
let factories = [ for report_id in 1..6 -> fetch_report report_id ]
let from_factories = (Task.parallelLimit 2 CancellationToken.None factories).Result
printfn "factories:   peak %d" peak            // 2

peak <- 0
// Applying the token builds a Task, and a Task is already running.
let started = [ for report_id in 1..6 -> fetch_report report_id CancellationToken.None ]
// Compiles fine, and the limiter has nothing left to limit.
let rewrapped = [ for running in started -> fun (_: CancellationToken) -> running ]
let from_started = (Task.parallelLimit 2 CancellationToken.None rewrapped).Result
printfn "pre-started: peak %d" peak            // 6
```

**Why it matters**

The usual reason to cap concurrency is a downstream limit: a connection pool, a rate-limited API, a database that falls over at 50 parallel queries. A list of tasks has already blown through that limit before the limiter is even called, and the code reads exactly like the correct version. Partial application is what makes the correct version cheap in F#: `fetch_report report_id` is already the factory, no lambda needed. The `Async` version cannot hit this at all, because an `Async<'T>` is a description that runs only when started. C#'s `Parallel.ForEachAsync` makes the same choice the other way round: it takes the source items and a body delegate, so it never sees a started task either.

**Chew on this**

Where in your code does a list of tasks get built in one place and throttled in another, and could anyone tell from the throttling site whether the tasks had already started? If `Task.parallelLimit` stops starting new work after the first failure, what happens to the in-flight sibling that was halfway through a write?

Run in the `mcr.microsoft.com/dotnet/sdk:11.0` image (11.0.100-rc.3.26522.148), which is Ubuntu 26.04, not Debian. .NET 11 is still a release candidate, so the API can still change before GA.

**Gotchas**

- `Async.Parallel(computations, maxDegreeOfParallelism = 2)` has existed since FSharp.Core 4.7 and peaked at 2 in flight, the same as `Async.parallelLimit 2` (315 ms against 321 ms for six 100 ms jobs). The new function is the curried, pipeline-friendly spelling, not a new capability for `Async`.
- The new thing is the `Task` side: `Task.parallelLimit` and `Task.parallelDoLimit` sit in a `Task` module that SDK 10.0.402 does not have at all (`Task.parallelLimit` there is FS0039, "not defined").
- When one factory fails, `Task.parallelLimit` stops starting the rest: with job 2 failing immediately, only 1 of the other 5 jobs had started, and still only 1 after another 500 ms.
- No `--langversion:preview` is needed: these are FSharp.Core functions, not language features, so they work under the default F# 11.
- Results come back in input order (`[|1; 4; 9; 16; 25; 36|]` in every run), whatever order the jobs finish in.

## TypeScript: `Object.groupBy` returns a null-prototype object typed as `Partial<Record>`, so `.hasOwnProperty` throws and tsc says nothing

*Stdlib and ecosystem gems*

**Did you know**

`Object.groupBy` (ES2024, TypeScript 5.4+ with `lib` set to `es2024` or `esnext`) builds its result with a null prototype, so nothing from `Object.prototype` is behind it: `"toString" in by_region` is `false`, `by_region.hasOwnProperty("eu")` throws `TypeError: ... is not a function`, and a template literal around it throws `Cannot convert object to primitive value`. TypeScript types the result as `Partial<Record<string, Order[]>>`, an ordinary object type with every `Object` member, so tsc 7.0.2 under `--strict` accepts both lines that throw.

**Show me**

```ts
// TypeScript 5.4+ (lib es2024 or esnext), Node 21+. Checked: tsc 7.0.2 --strict, Node 22.23.4.
type Order = { region: string; cents: number };
const orders: Order[] = [
    { region: "eu", cents: 1200 },
    { region: "us", cents: 800 },
];

// Typed Partial<Record<string, Order[]>>, but built on a null prototype.
const by_region = Object.groupBy(orders, (order) => order.region);

console.log("toString" in by_region);            // false: no Object.prototype behind it
console.log(Object.hasOwn(by_region, "eu"));     // true: the static form works

try {
    console.log(by_region.hasOwnProperty("eu")); // tsc: fine. Node: TypeError
} catch (error) {
    console.log(error instanceof TypeError);     // true: "hasOwnProperty is not a function"
}
try {
    console.log(`${by_region}`);                 // tsc: fine. Node: TypeError
} catch (error) {
    console.log(error instanceof TypeError);     // true: "Cannot convert object to primitive value"
}

// Map.groupBy has none of this: a Map has no prototype keys to collide with.
const by_region_map = Map.groupBy(orders, (order) => order.region);
console.log(by_region_map.get("eu")?.length);    // 1
```

**Why it matters**

The null prototype is deliberate and it is the good part: a group key of `"constructor"` or `"toString"` is just a group (measured: the `"constructor"` key held its 1 order), never an inherited method. The cost is that code written for ordinary objects (a logger that calls `String(value)`, a lodash-era `obj.hasOwnProperty(key)` check) now throws at runtime, on a line the type checker approved. Rust's `HashMap`, C++'s `std::unordered_map` and F#'s `Map` and `dict` never had this split, since keys and methods live in different namespaces there; JavaScript's plain object is the one structure where your data and its methods share one namespace, which is why `groupBy` had to opt out of the prototype.

**Chew on this**

Which of your helpers take "any object" and quietly assume it inherits from `Object.prototype`, and would any test you have ever pass one of these? If your group keys came from user input, would you rather have `Object.groupBy`'s namespace or `Map.groupBy`'s?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/groupBy
- https://tc39.es/ecma262/#sec-object.groupby
- https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-4.html

**Gotchas**

- With TypeScript 5.4 and `--lib es2022`, `Object.groupBy` is TS2339 ("does not exist on type 'ObjectConstructor'"): the declaration ships only in `es2024`/`esnext`.
- `Object.hasOwn(by_region, "eu")` works (measured `true`): use the static form, which never looks anything up on the object itself.
- Every key is optional in the type (`Partial<...>`), so `by_region["eu"]` is `Order[] | undefined`, even for a key you know is present.
- `JSON.stringify` and `Object.entries` are fine: they do not need the prototype. `String(...)`, `+ ""` and a template literal are not.

# The functional angle: you can only schedule a description, and half of these languages hand you a receipt

Draws on the F# tip (`Task.parallelLimit`), with the same question asked of Rust, C++ and TypeScript. The functional shape is "a computation as a value you can pass around before it runs". Whether a language's default async value is that, or a handle to work already in progress, decides whether a limiter, a retry or a timeout can wrap it after the fact.

```fsharp
// F#: Async is a description; Task is a receipt.
let cold = [ for report_id in 1..6 -> async { return report_id } ]        // nothing runs yet
let hot = [ for report_id in 1..6 -> task { return report_id } ]          // all six already ran
```

```rust
// Rust: an async fn call builds an inert future; nothing runs until it is polled.
let pending: Vec<_> = (1..=6).map(work).collect();   // measured: started 0
```

```ts
// TypeScript: a Promise starts on creation; an Effect is a description.
const promises = job_ids.map(work);                                         // measured: started 6
const effects = job_ids.map((job_id) => Effect.promise(() => work(job_id))); // measured: started 0
await Effect.runPromise(Effect.all(effects, { concurrency: 2 }));           // peak 2, 315 ms
```

```cpp
// C++: std::async picks hot or cold by launch policy, per call.
std::async(std::launch::async, work, job_id);     // measured: 6 of 6 started before any get()
std::async(std::launch::deferred, work, job_id);  // measured: 0 of 6 started
```

| Language | Cold form (a description) | Hot form (a receipt) | Pre-started work under a limit of 2 |
| --- | --- | --- | --- |
| F# | `Async<'T>`, or a `CancellationToken -> Task<'T>` factory | `Task<'T>` | peak 6 (`Task.parallelLimit`, rewrapped tasks) |
| Rust | every `Future`: an `async fn` call does nothing until polled | none in std; `tokio::spawn` is the opt-in hot form | not measured (the limiter would need a runtime crate) |
| C++ | `std::launch::deferred`, a coroutine with `suspend_always` | `std::launch::async` | not measured (std ships no limiter) |
| TypeScript | an Effect 4.0.6 `Effect` | `Promise` | peak 6 (`Effect.all` with `concurrency: 2` over started promises) |

Rust is the only one of the four where cold is the default and there is no hot value in std at all, so "already running" is something you opt into with a runtime's `spawn`. F# and TypeScript ship both, with the hot one as the everyday type, which is exactly why `Task.parallelLimit` had to ask for factories and why Effect wraps a promise in a thunk. C++ makes it a per-call flag, and the default policy (`async | deferred`) leaves the choice to the implementation.

If cold is what makes work schedulable, what is the cost of the cold default that F# and TypeScript programmers keep avoiding, and is Rust paying it somewhere you have not looked?

# The security angle: a null prototype protects the groups until you copy them into `{}`

Draws on the TypeScript tip (`Object.groupBy`) and the C++ tip (`optional` ordering); Mode B, asking whether each one is secure as well as convenient. The TypeScript tip runs in the safe direction (the language API closed a hole), the C++ one in the unsafe direction (the language API opened one).

**TypeScript (Node 22.23.4): `Object.groupBy` keeps `"__proto__"` as a data key, `Object.assign` does not.** When the grouping key comes from user input, a group named `"__proto__"` is an own property of the null-prototype result, measured. Copying that result into a fresh `{}` with `Object.assign`, or with a `for ... of` loop that assigns `copy[key] = value`, goes through the `__proto__` setter instead of defining a key, so the copy has no own `"__proto__"` key and its prototype becomes that group's array:

```ts
// TypeScript: looks like a harmless copy before handing the groups to a template.
type Row = { group: string; admin: boolean };
declare const rows: Row[];                                   // group comes from a request
const grouped = Object.groupBy(rows, (row) => row.group);   // safe: "__proto__" is an own key
const copied = Object.assign({}, grouped);                  // not safe: assignment uses the setter
// Measured, with one row whose group is "__proto__": copied has no own "__proto__",
// Array.isArray(Object.getPrototypeOf(copied)) is true, copied.length is 1,
// and copied[0].admin reads true through the prototype.
const kept = { ...grouped };   // measured: spread defines an own "__proto__" key; prototype stays Object.prototype
```

**C++ (g++ 14.2): an unset floor fails open.** The dangerous half of the C++ tip is the floor: `client_build < policy.min_client_build` is `false` when the minimum is unset, so a "reject clients older than the minimum" check accepts every client, the oldest included (measured `too_old 0` for build 1). An unset ceiling fails closed instead, which is an outage rather than a hole. Neither default was chosen by whoever wrote the check: the comparison operator chose it.

```cpp
// C++17: looks like a version gate; with the floor unset it admits everything.
if (client_build < policy.min_client_build) { return reject_upgrade_required(); }
// Decide it out loud: an unset floor admits all, and says so.
bool too_old = policy.min_client_build.has_value() ? client_build < *policy.min_client_build : false;
```

**Rust (rustc 1.99.1): a calloc'd buffer moves the out-of-memory point.** `vec![0u8; attacker_len]` succeeds at 0 MiB resident, so a size taken from a request header passes an allocation that a memory check at that moment would not notice, and the cost lands later, on whichever write first touches the pages.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | a user-chosen `"__proto__"` key re-parents a copy (CWE-1321) | `Object.groupBy` and object spread define own keys | never `Object.assign` or `copy[key] =` user-keyed data into `{}`; use `Map.groupBy`, spread, or a `Map` |
| C++ | an unset optional floor admits every value; an unset ceiling rejects every value (CWE-697) | defines the order, warns about nothing (g++ `-Wall -Wextra`, clang `-Weverything`) | decide "unset" explicitly: `has_value() ? ... : ...` or `transform(...).value_or(...)` |
| Rust | a request-sized zeroed buffer allocates without resident cost (CWE-789) | nothing to catch: the lazy allocation is the optimization working | cap the length before `vec!`, not after the first write |
| F# | none of the three in today's tips | `Map` and `dict` keep keys apart from members | nothing, this one is handled |

TypeScript is the baseline for the first row because it is the only one of the four whose plain object mixes data keys with the object's own machinery. C++ is the baseline for the second because the comparison is defined, so nothing will ever flag it.

# FAQ

**Is `vec![0; n]` free for a `#[derive(Clone)]` struct of zeros?**
No. `IsZero` covers integers, floats with zero bits, `bool`, `char`, `Option<Box<T>>`, and arrays and tuples of those, but not user structs. A zeroed four-byte `Pixel` cost 1024 MiB at `opt-level=0` and 0 MiB with `-O`, so you are back to the optimizer deciding.

**Does C++20's `<=>` change how an empty `optional` sorts?**
No. The relational operators are synthesized from `operator<=>`, and `(empty <=> 5) < 0` is `true`, measured. The ordering was the same in C++17.

**Does Rust's `Option` really order like C++'s?**
Yes, measured: `None < Some(i32::MIN)` is `true`. The difference is that Rust has no implicit comparison with a plain `i32`, so `timeout < 30000` is a compile error and you have to write the `Some`.

**Is `Async.parallelLimit` faster than `Async.Parallel` with `maxDegreeOfParallelism`?**
Not measurably: 321 ms against 315 ms for six 100 ms jobs at a limit of 2, both peaking at 2. It is the curried form that fits a `|>` pipeline.

**Does `Map.groupBy` have the `hasOwnProperty` problem?**
No. A `Map` has `get`, `has` and `size` as methods and its keys in a separate store, so a key can never shadow a method and the result inherits from `Map.prototype` normally.
