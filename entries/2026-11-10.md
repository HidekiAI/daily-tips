## Rust: A closure that returns a borrow of its `&str` argument does not compile, and leaving out the annotation makes it compile with one lifetime for every call

*Type system deep cuts*

**Did you know**

A `fn` item with an elided signature, `fn first_word(text: &str) -> &str`, is higher-ranked: it is `for<'a> fn(&'a str) -> &'a str`, so every call gets its own lifetime. A closure does not get that. Annotate the parameter as `&str` and the input becomes higher-ranked while the return type gets a separate inferred lifetime, so `|text: &str| text.split(' ').next().unwrap_or("")` is rejected with "lifetime may not live long enough". Drop the annotation and it compiles, but with a single lifetime for all calls, so the second call can fail with E0597 far from the closure. The `for<'a>` closure binder that would state the signature is still unstable on rustc 1.99.1 (E0658, issue #97362).

**Show me**

```rust
// rustc 1.99.1, edition 2024, Debian 13.7
fn first_word_fn(text: &str) -> &str {           // a fn item: for<'a> fn(&'a str) -> &'a str
    text.split(' ').next().unwrap_or("")
}

// Stable workaround: say the higher-ranked bound where the closure is created.
fn fn_constrain<F>(closure: F) -> F
where
    F: for<'a> Fn(&'a str) -> &'a str,
{
    closure
}

fn main() {
    // error: lifetime may not live long enough
    //   "returning this value requires that `'1` must outlive `'2`"
    // let first_word = |text: &str| text.split(' ').next().unwrap_or("");

    // Compiles, but `text` gets ONE inferred lifetime shared by every call:
    // let first_word = |text| -> &str { let text: &str = text; text.split(' ').next().unwrap_or("") };
    // ...then a second call on a shorter-lived String is E0597 "does not live long enough".

    let first_word = fn_constrain(|text: &str| text.split(' ').next().unwrap_or(""));
    let line_one = String::from("alpha beta");
    let word_one = first_word(&line_one);
    {
        let line_two = String::from("gamma delta");
        println!("{}", first_word(&line_two));   // gamma: its own lifetime
    }
    println!("{word_one} {}", first_word_fn(&line_one)); // alpha alpha
}
```

**Why it matters**

The closure you write inline in a handler is fine because the call it is passed to supplies the bound. The one you hoist into a `let` to reuse breaks, and the "fix" of removing the annotation moves the error to a later call site that looks unrelated. The C++ lambda that returns its `const&` argument has the mirror-image problem: it compiles and silently returns a copy (see the functional angle below).

**Chew on this**

Which of your helper closures exist only because they were hoisted out of an iterator chain, and would a nested `fn` say what the closure cannot?

**Sources**

- https://rust-lang.github.io/rfcs/3216-closure-lifetime-binder.html ("lifetimes will be inferred as either some local region (via an inference variable), or a higher-ranked lifetime")
- https://github.com/rust-lang/rust/issues/97362
- https://doc.rust-lang.org/reference/lifetime-elision.html

**Gotchas**

- Adding `-> &str` to the annotated closure does not help: `|text: &str| -> &str { ... }` gives the same "lifetime may not live long enough".
- The problem needs a returned borrow. `|text: &str| text.len()` compiles and is used freely, which is why the rule feels arbitrary.
- `#![feature(closure_lifetime_binder)]` is nightly only; on stable `for<'a> |text: &'a str| -> &'a str { ... }` is E0658 with "consider removing `for<...>`".
- The unannotated closure's error lands on the call site, as E0597 on the `String` you passed, not on the closure.

**Related**

- [2026-09-15](2026-09-15.md) - Rust, "A trait object's elided lifetime comes from the containing type, not the use site". Another elision rule that differs by where the type is written.
- [2026-10-27](2026-10-27-extra-5-of-12.md) - Rust, "A closure auto-derefs its argument and a point-free path does not". The other way closures and `fn` items differ at a call.

## C++: libstdc++ makes `shared_ptr` reference counts atomic only after the process's first thread, and never switches back

*Perf and memory model*

**Did you know**

libstdc++'s reference count update goes through `__gnu_cxx::__is_single_threaded()`, which returns glibc's `__libc_single_threaded` (`ext/atomicity.h`). While it is true, a `shared_ptr` copy is a plain load, add and store. `pthread_create` sets it to false, and glibc's manual says the current implementation never sets it back, even after you join the last thread. One `std::thread([]{}).join()` at startup took a copy-and-drop from 4.2 ns to 5.6 ns on GCC 16.2. libc++ has no such switch: its increment is always an atomic with relaxed ordering, and it measured 3.6 ns either way.

**Show me**

```cpp
// C++20, GCC 16.2 and Debian clang 19.1.7, glibc 2.41, Debian 13.7 aarch64
#include <memory>
#include <thread>
#include <sys/single_threaded.h>   // glibc 2.32+: extern char __libc_single_threaded

[[gnu::noinline]] long fn_copy_and_drop(const std::shared_ptr<long>& shared) {
    std::shared_ptr<long> copy = shared;   // +1, then -1 when copy dies
    return *copy;
}

int main(int argc, char**) {
    auto shared = std::make_shared<long>(1);
    if (argc > 1) std::thread([] {}).join();   // one thread, already gone
    // __libc_single_threaded is now 0 for the rest of the process.
    // GCC 16.2 codegen of fn_copy_and_drop:
    //   ldrb w0, [flag]; cbz w0, atomic_path
    //   ldr / add / str               <- single-threaded: plain increment
    //   atomic_path: bl __aarch64_ldadd4_acq_rel
    long checksum = 0;
    for (long step = 0; step < 50'000'000; ++step) checksum += fn_copy_and_drop(shared);
    return checksum == 42;
}
// best of 7 rounds x 50M, separate processes:
//                               no thread   after one joined thread
// GCC 16.2 + libstdc++          4.20 ns     5.55-5.76 ns
// Debian clang 19 + libstdc++   6.12 ns     5.12 ns   (plain path SLOWER)
// Debian clang 19 + libc++      3.59 ns     3.61 ns   (always atomic)
```

**Why it matters**

Every server is multi-threaded within a millisecond of `main`, so a microbenchmark of `shared_ptr` written as a single-threaded test program measures a code path production never runs. It also means a logging library that spawns one background thread changes the cost of every `shared_ptr` copy in the process. Rust makes the same choice visible in the type instead: `Rc` is the non-atomic count and is `!Send`, so it cannot cross into the thread that would make it wrong, and `Arc` is atomic from the first copy.

**Chew on this**

If your service's hot path copies `shared_ptr` per request, what did the benchmark that justified that design have running at the time?

**Sources**

- https://sourceware.org/glibc/manual/latest/html_node/Single_002dThreaded.html ("does not set the `__libc_single_threaded` variable to a true value if a process turns single-threaded again")
- https://gcc.gnu.org/onlinedocs/libstdc++/manual/ext_concurrency.html
- https://doc.rust-lang.org/std/rc/struct.Rc.html

**Verified**

Measured on aarch64 Linux in Docker on Apple silicon; x86-64 not measured, where the atomic path is `lock xadd`. The GCC version that first read `__libc_single_threaded` was not confirmed; the switch is in GCC 16.2's header.

**Gotchas**

- The "fast" single-threaded path is not always faster: under Debian clang 19 with libstdc++ it was 6.1 ns against 5.1 ns for the atomic path. In a position-independent build the flag is read through the GOT on every copy.
- The decrement also checks the flag, and GCC 16.2 adds one more shortcut: an `ldar` of the strong and weak counts together, compared against `0x100000001`, so the last owner skips the atomic decrement.
- Writing to `__libc_single_threaded` yourself is forbidden by glibc's manual, "even if it has joined the last application-created thread".

**Related**

- [2026-11-09](2026-11-09.md) - Rust, "A Relaxed fetch_add is the same lock xadd as SeqCst on x86-64". The instruction this switch is avoiding.
- [2026-10-27](2026-10-27-extra-11-of-12.md) - C++, "atomic<shared_ptr> is how C++20 publishes an immutable snapshot". What the atomic count is protecting.

## F#: `Async.AwaitTask` hands a failed task's error over as `AggregateException`, so `with :? FileNotFoundException` never runs, and F# 11's `Async.Await` is the version that does

*New discoveries and currently popular patterns*

**Did you know**

Inside `async { }`, a task that faulted with `FileNotFoundException` surfaces through `Async.AwaitTask` as an `AggregateException` wrapping it, so a type-test handler for the real exception is skipped and the error escapes. FSharp.Core 11 (F# 11, .NET 11, measured on SDK 11.0.100-rc.3) adds `Async.Await` and `Async.StartTaskImmediate`, which raise the underlying exception, so the same handler matches. Microsoft's "What's new in F# 11" (updated 2026-11-06) says outright that "the older `Async.AwaitTask` retains its exception-wrapping behavior": upgrading changes nothing until you change the call.

**Show me**

```fsharp
// F# 11, FSharp.Core 11.0.0, .NET 11.0.0 (SDK 11.0.100-rc.3, Ubuntu 26.04 image)
open System.IO

let missing_path = "/tmp/no-such-report.csv"

let via_await_task =
    async {
        try
            let! contents = Async.AwaitTask(File.ReadAllTextAsync missing_path)
            return Some contents
        with :? FileNotFoundException -> return None   // never matches
    }

let via_await =
    async {
        try
            let! contents = Async.Await(File.ReadAllTextAsync missing_path)   // F# 11
            return Some contents
        with :? FileNotFoundException -> return None   // matches
    }

let via_start_immediate =
    async {
        try   // F# 11: the factory gets the workflow's cancellation token
            let! contents = Async.StartTaskImmediate(fun cancel -> File.ReadAllTextAsync(missing_path, cancel))
            return Some contents
        with :? FileNotFoundException -> return None   // matches
    }
// Async.RunSynchronously via_await_task      -> AggregateException escapes
//   (inner: FileNotFoundException; same on FSharp.Core 10.1, .NET 10.0.14)
// Async.RunSynchronously via_await           -> None
// Async.RunSynchronously via_start_immediate -> None
```

**Why it matters**

The handler compiles, reads correctly, and passes every test that never produces the error. In production the "file not there yet, return None" branch becomes an unhandled exception, and a retry or fallback written for it never runs. C# never had the problem because `await` unwraps to the first inner exception. Rust's `?` passes the error value through as it is. TypeScript's `await` rethrows the rejection reason as it is.

**Chew on this**

How many `with :? SomeException` arms in your `async` code sit after an `AwaitTask`, and which of them has a test that actually makes that exception happen?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/whats-new/fsharp-11
- https://github.com/dotnet/core/blob/main/release-notes/11.0/preview/rc1/fsharp.md
- https://learn.microsoft.com/en-us/dotnet/api/system.aggregateexception

**Verified**

Measured on the `mcr.microsoft.com/dotnet/sdk:11.0` image, which is Ubuntu 26.04; .NET 11 is at RC3, not GA. The name `Async.Await` is from the Learn page and compiled here; it is FS0039 on FSharp.Core 10.1.

**Gotchas**

- A missing directory raises `DirectoryNotFoundException`, which is not a `FileNotFoundException` (both derive from `IOException`), so even `Async.Await` escaped the handler for `/no/such/report.csv`.
- `async { }` does not bind a `Task` directly: `let! text = File.ReadAllTextAsync path` is FS0193. That is why `AwaitTask` is all over existing code.
- Wrapping in `task { return! ... }` first does not help: `task { ... } |> Async.AwaitTask` still raised `AggregateException`.
- The "fix" of `with _ ->` matches the wrapper, but it also swallows `OperationCanceledException` and every bug the handler was never meant for.

- [2026-10-27](2026-10-27.md) - F#, "FSharp.Core 11's Task.parallelLimit takes factories, not tasks". Why `StartTaskImmediate` takes a factory too.

## TypeScript: `new URL(next_path, base)` turns `/\evil.example` and `/<tab>/evil.example` into another host, and both pass a "starts with one slash" check

*Stdlib and ecosystem gems*

**Did you know**

The WHATWG URL parser behind Node's global `URL` removes every ASCII tab and newline from the input before parsing, and for special schemes (`http`, `https` and others) treats `\` exactly like `/`. So `/\evil.example` and `"/\t/evil.example"` both resolve against `https://app.example.com/dashboard` to `https://evil.example/`, and both pass the usual open-redirect guard `startsWith("/") && !startsWith("//")`. Node 22.1 added `URL.parse(input, base)`, which returns `null` instead of throwing, and checking the resolved `origin` is what closes the hole.

**Show me**

```ts
// Node 26.13.0, TypeScript 7.0.2 --strict --lib es2024,dom
const APP_ORIGIN: string = "https://app.example.com";

// Looks right, and is the common guard:
const fn_looks_local = (next_path: string): boolean =>
    next_path.startsWith("/") && !next_path.startsWith("//");

// new URL(next_path, APP_ORIGIN).host, measured:
//   "/settings"          check true  -> app.example.com
//   "/\\evil.example"    check true  -> evil.example   (\ is / for https)
//   "/\t/evil.example"   check true  -> evil.example   (tab removed first)
//   "//evil.example"     check false -> evil.example
//   "https:evil.example" check false -> app.example.com (same scheme: relative)

// Decide on the parsed result, not the string:
const fn_same_origin_target = (next_path: string): string => {
    const resolved: URL | null = URL.parse(next_path, APP_ORIGIN);   // null, not a throw
    return resolved !== null && resolved.origin === APP_ORIGIN
        ? resolved.pathname + resolved.search
        : "/";
};
// "/settings?tab=keys" -> /settings?tab=keys; every evil.example input -> /
```

**Why it matters**

A `?next=` parameter after login is the classic place for this check, and the browser that follows your `Location` header uses the same WHATWG rules as Node, so the string test and the browser disagree. Rust's `url` crate implements the same standard and agreed with Node on all three inputs; .NET's `Uri` did not, which is the security angle below.

**Chew on this**

Where does your code check a URL as a string and then hand the same string to something that parses it?

**Sources**

- https://url.spec.whatwg.org/#concept-basic-url-parser
- https://nodejs.org/api/url.html#urlparseinput-base
- https://cwe.mitre.org/data/definitions/601.html

**Gotchas**

- `URL.canParse("/x")` is `false`: without a base, a path is not a URL, so `canParse` cannot stand in for "is this a safe relative path".
- `"/%2F/evil.example"` stays on the app host: percent-encoded slashes are not decoded during parsing, so blocking `%2F` buys nothing here.
- Leading spaces are trimmed too: `"  //evil.example"` went to `evil.example`.
- The backslash rule is only for special schemes: against `foo://app.example.com/` the same input stayed in the path as `/\evil.example`.
- `new URL("http://[::1")` throws a `TypeError`; `URL.parse` returns `null`, which is why the snippet uses it at a trust boundary.

# The functional angle: a lambda that returns what it was given is refused in Rust, copied in C++ and shared in TypeScript

Draws on the Rust tip (closure lifetimes), with C++ and TypeScript rows built for it. F# has no row: it has no borrowed return to get wrong, since a lambda returning its argument returns the same reference to a garbage-collected object.

The shape is the identity-like projection: take a view of something, return part of it. Every language infers a lambda's return type, and each infers something different for "the thing I was given".

```rust
// Rust 1.99.1: refused at the definition
let fn_same = |text: &str| text;   // error: lifetime may not live long enough
```

```cpp
// C++20, GCC 16.2: compiles, and the deduced return type decays to a value
auto fn_same_deduced  = [](const tracked_text& text) { return text; };                  // 1 copy
auto fn_same_ref      = [](const tracked_text& text) -> const tracked_text& { return text; }; // 0 copies
auto fn_same_decltype = [](const tracked_text& text) -> decltype(auto) { return (text); };   // 0 copies
```

```ts
// TypeScript: objects are references, so the "same" value is the same object
const fn_same = (text_holder: { body: string }) => text_holder;   // no copy, no lifetime
```

| Language | What the lambda's return is inferred as | What it costs |
| --- | --- | --- |
| Rust | a fresh lifetime unrelated to the argument | a compile error; fixed only by a `for<'a>` bound at creation (stable: a helper `fn`) |
| C++ | a value: `auto` deduction drops `const&` | one copy constructor call per call, measured 1; `-> const T&` or `decltype(auto)` with `(text)` gets 0 |
| TypeScript | the same reference | nothing per call; aliasing instead, so the caller can mutate what it was handed |

The asymmetry is that C++ is the only one of the three that turns the mistake into work rather than an error or an alias, and `-Wall -Wextra` on GCC 16.2 said nothing about the copy. Rust's refusal is the price of the borrow being checked; C++'s copy is the price of it not being. Which one would you rather discover in a profiler?

# The security angle: the code that validates a URL and the browser that follows it must use the same parser

Draws on the TypeScript tip, and runs in the direction where the language does not help: no type system sees a parser differential. Mode C (the missing check) plus a fourth row measured for it.

Two insecure samples, both ordinary-looking:

```ts
// TypeScript, Node 26.13.0: a string test in front of a WHATWG parser
if (next_path.startsWith("/") && !next_path.startsWith("//")) {
    response.redirect(next_path);   // "/\\evil.example" passes and the browser goes to evil.example
}
```

```fsharp
// F#, .NET 11: the .NET parser says "same host", then hands back a path a browser reads as a host
let combined = System.Uri(System.Uri "https://app.example.com/dashboard", "/\\evil.example")
// combined.Host         = "app.example.com"   -> the check passes
// combined.PathAndQuery = "//evil.example"     -> Location: //evil.example -> https://evil.example/
```

The .NET row is the instructive one: `Uri` does not follow the WHATWG rules, converted `\` to `/` inside the path, and kept the host. Validation is correct by its own parser's rules, and the output is a protocol-relative URL by the browser's rules. That is CWE-436, interpretation conflict, delivering CWE-601, open redirect.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | a string prefix check approves `/\evil.example` and `/<tab>/evil.example` | nothing: `URL` is untyped at the boundary, and `string` is `string` | parse with `URL.parse(next_path, origin)` and compare `.origin` |
| Rust | the `url` crate 2.5.8 resolves the same three inputs to `evil.example` | the parser is WHATWG, so it agrees with the browser | the same origin comparison on `Url::join`'s result, never a check on the raw `&str` |
| F# / C# | `Uri` keeps the host and returns the path `//evil.example` | `Uri` follows its own rules, which differ from a browser's | never emit `PathAndQuery` as a `Location` without rejecting a leading `//` |
| C++ | std has no URL type at all | nothing | pick a WHATWG parser; Ada, the C++ library Node itself uses, is one |

The control here is Rust's `url` crate, because it is the one row where the validating parser and the browser agree by construction. Which of your services validates with one parser and redirects, proxies or fetches with another?

# FAQ

**Does C++'s libstdc++ switch also affect `std::atomic` or `std::mutex`?**

No. In C++, `__is_single_threaded()` is used by libstdc++'s internal reference counts (`shared_ptr`, and the dispatch helpers in `ext/atomicity.h`). A `std::atomic<int>::fetch_add` you write is always atomic, single-threaded or not.

**Does F#'s `Async.Catch` see the `AggregateException` or the inner one?**

The wrapper. F#'s `Async.Catch` over the `Async.AwaitTask` workflow returned `Choice2Of2` holding an `AggregateException`, measured on FSharp.Core 11.0.0.

**Is TypeScript's `URL` here Node-only?**

No. JavaScript's `URL` and `URL.parse` are WHATWG APIs, also in browsers and Deno. The measurements are Node 26.13.0.
