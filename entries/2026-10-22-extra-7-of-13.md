**The thesis: "every 100 ms" is a promise no timer can keep through a stall, so each one picks how to break it.** It can burst (fire every missed tick at once), skip (fire once, then return to the original grid), or drift (shift the whole schedule later). Part 2's cron double-fire was one of these choices made by a scheduler. Here the same choice is hidden in an ordinary timer API.

Every row below is the same experiment: a 100 ms periodic timer, a 350 ms stall right after the second tick, and the elapsed milliseconds at each of 8 ticks. Measured on Debian 13 (Docker, arm64) on 2026-10-23 and on macOS on 2026-10-22: every row has the same policy on both, with ticks within about 25 ms of each other. The figures shown are the macOS run, with a few ms of jitter between runs.

## Rust: `tokio::time::interval` defaults to `Burst`, so after a 350 ms stall it fires three ticks in the same millisecond

*Stdlib and ecosystem gems*

**Did you know**

In the Rust `tokio` crate (1.54.1), `interval(period)` uses `MissedTickBehavior::Burst` unless you change it: "ticks as fast as possible until caught up". After a 350 ms stall in a 100 ms interval, three ticks completed at 458 ms, back to back. `Skip` fires one late tick, then returns to the original grid (501, 606, ...). `Delay` restarts the schedule from the late tick, so every later tick moves by the stall. And the first `tick()` completes immediately, at 1 ms, not after one period.

**Show me**

```rust
// Rust: tokio 1.54.1 (features rt, time, macros), rustc 1.99.1 (Debian 13) and 1.95.0 (macOS)
use std::time::Duration;
use tokio::time::{interval, Instant, MissedTickBehavior};

async fn fn_ticks(behavior: MissedTickBehavior) -> Vec<u128> {
    let mut ticker = interval(Duration::from_millis(100));
    ticker.set_missed_tick_behavior(behavior); // the default is Burst
    let start = Instant::now();
    let mut offsets = Vec::new();
    for tick in 0..8 {
        ticker.tick().await; // the FIRST tick completes immediately
        offsets.push(start.elapsed().as_millis());
        if tick == 1 {
            std::thread::sleep(Duration::from_millis(350)); // a stall: GC, a blocking call, swap
        }
    }
    offsets
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    println!("Burst {:?}", fn_ticks(MissedTickBehavior::Burst).await); // one run: [1, 103, 458, 458, 458, 506, 606, 706]
    println!("Delay {:?}", fn_ticks(MissedTickBehavior::Delay).await); // [1, 105, 460, 566, 672, 773, 874, 976]
    println!("Skip  {:?}", fn_ticks(MissedTickBehavior::Skip).await);  // [1, 102, 457, 501, 606, 702, 805, 905]
}
```

**Why it matters**

`Burst` is right for "process every tick's worth of work", and wrong for "poll", "send a heartbeat" or "refill a rate limiter", where three back-to-back ticks are three requests in one millisecond after every pause. The stall that triggers it is usually your own: slow work between ticks, async or blocking. C++'s textbook `sleep_until` loop makes the same choice without naming it. .NET's `PeriodicTimer` made the opposite one. Rust and its crates evolve; this is tokio 1.54.1's documented default.

**Chew on this**

Which of your `interval` loops would rather lose a tick than burst, and which would rather burst than lose one? Did anyone choose, or is it the default?

**Sources**

- https://docs.rs/tokio/1.54.1/tokio/time/enum.MissedTickBehavior.html
- https://docs.rs/tokio/1.54.1/tokio/time/fn.interval.html

**Gotchas**

- The first `tick()` returns at once (1 ms in every run, measured). A loop that "waits, then works" actually works first. `interval_at(Instant::now() + period, period)` starts one period later (103 ms, measured).
- `Skip` is not "skip the late tick": it fires once late (457 ms), then the next tick lands on the original grid (501 ms, measured).
- It is not about blocking. Replacing the blocking `std::thread::sleep` with `tokio::time::sleep(350ms).await` gives the same burst, `[1, 104, 457, 457, 457]` (measured): any delay between `tick()` calls counts, including slow async work.

## C++: there is no standard periodic timer, so the loop you write picks the policy, and the textbook `sleep_until` loop bursts

*Idioms and antipatterns*

**Did you know**

The C++ standard library has `sleep_for` and `sleep_until`, and no periodic timer. So the policy lives in three lines you write. `next += period; sleep_until(next);` keeps a schedule, and after a 350 ms stall it fires three ticks at once (558, 558, 558 ms), exactly like tokio's `Burst`. `sleep_for(period)` after each tick never bursts, and drifts: every delay is added to the rest of the run, so 100 ticks of 10 ms with 4 ms of work take about 1600 ms instead of 1000. Measured on GCC 14.2 and GCC 16.2 (libstdc++, Linux) and Apple clang 21 (libc++, macOS); all behave the same.

**Show me**

```cpp
// C++20: GCC 14.2 and 16.2 (libstdc++) and Apple clang 21 (libc++ 22)
#include <chrono>
#include <cstdio>
#include <thread>
using namespace std::chrono;

template <class Fn> void fn_ticks(const char* label, Fn fn_wait) {
    const auto start = steady_clock::now();
    auto next = start;
    std::printf("%-12s", label);
    for (int tick = 0; tick < 8; ++tick) {
        fn_wait(next);
        std::printf(" %lld", (long long)duration_cast<milliseconds>(steady_clock::now() - start).count());
        if (tick == 1) std::this_thread::sleep_for(350ms);  // a stall
    }
    std::printf("\n");
}

int main() {
    // The textbook loop: keep a schedule. After a stall it fires every missed tick at once.
    fn_ticks("burst", [](steady_clock::time_point& next) { next += 100ms; std::this_thread::sleep_until(next); });
    // Sleep a period after each tick: no burst, but every delay is added for good.
    fn_ticks("drift", [](steady_clock::time_point&) { std::this_thread::sleep_for(100ms); });
    // Keep the schedule, but drop every missed tick except the latest.
    fn_ticks("coalesce", [](steady_clock::time_point& next) {
        next += 100ms;
        const auto now = steady_clock::now();
        while (next + 100ms <= now) next += 100ms;
        std::this_thread::sleep_until(next);
    });
    // one Debian 13 run (GCC 14.2, Docker, arm64):
    // burst     100 200 555 555 555 601 702 801
    // drift     105 208 666 771 874 979 1084 1186
    // coalesce  101 205 556 605 704 800 905 1005
    // one macOS run (a few ms of jitter between runs):
    // burst     105 203 558 558 558 605 705 805
    // drift     102 206 661 765 867 970 1075 1180
    // coalesce  105 205 560 600 705 800 902 1004
}
```

**Why it matters**

Both common loops are "correct", and they fail in opposite directions: the `sleep_until` one floods after a pause, and the `sleep_for` one slowly falls behind wall time (60% over 100 short ticks here). The third loop is the one most periodic jobs want, and it is the one nobody writes first. Rust names the three as `Burst`, `Delay` and `Skip`. C++ makes you discover which one you wrote. Also use `steady_clock`, never `system_clock`, for the `next` variable: a wall-clock step (part 3) would move every deadline.

**Chew on this**

Which loop shape do your C++ pollers and heartbeats use, and what do they do after the process was paused for a second? Would a code reviewer see the policy in the diff?

**Sources**

- https://en.cppreference.com/w/cpp/thread/sleep_until
- https://en.cppreference.com/w/cpp/thread/sleep_for

**Verified**

GCC 14.2 on Debian 13 (Docker, arm64, `-std=c++20 -O2 -Wall -Wextra`, no warnings) and `docker run gcc:16`; as a separate confirmation, Apple clang 21 on macOS. MSVC was not tested.

**Gotchas**

- `sleep_until` with a deadline already in the past returns at once (the burst), and `sleep_for` with zero or a negative duration also returns at once. Neither reports that it was late.
- 100 ticks of `sleep_until(next += 10ms)` with 4 ms of work took 1001 ms, and `sleep_for(10ms)` took 1583 ms on Linux (1577 and 1593 ms on a GCC 14.2 rerun) and 1614 ms on macOS (measured).

## F#: `System.Threading.Timer` runs a slow callback on top of itself, three copies at once, and `PeriodicTimer` cannot

*Idioms and antipatterns*

**Did you know**

`System.Threading.Timer` queues its callback to the thread pool on every period, whether or not the previous call has returned. With a 100 ms period and a 250 ms job, up to three copies of the job ran at the same time, on both .NET 10 (Linux) and .NET 8 (macOS). `PeriodicTimer` (.NET 6+) is the opposite design: one caller awaits `WaitForNextTickAsync`, so the job never overlaps itself. After a 350 ms stall it completes once at once (556 ms) and then returns to the 100 ms grid (601, 701, ...), like tokio's `Skip`. Measured on FSharp.Core 10.1 / .NET 10.0.13 (Linux) and FSharp.Core 8.0 / .NET 8.0.8 (macOS).

**Show me**

```fsharp
// F#: FSharp.Core 10.1 / .NET 10.0.13 (Linux, Docker) and FSharp.Core 8.0 / .NET 8.0.8 (macOS)
open System
open System.Diagnostics
open System.Threading

// System.Threading.Timer fires on schedule whether or not the last callback finished.
let gate = obj ()
let mutable running = 0
let mutable peak = 0
let fn_slow_job (_: obj) =
    lock gate (fun () -> running <- running + 1; peak <- max peak running)
    Thread.Sleep 250                         // the job takes 250 ms, the period is 100 ms
    lock gate (fun () -> running <- running - 1)
let timer = new Timer(TimerCallback fn_slow_job, null, 0, 100)
Thread.Sleep 1000
timer.Dispose()
Thread.Sleep 300
printfn "up to %d copies of the job ran at once" peak  // 3, on both hosts

// PeriodicTimer has one waiter, so it cannot overlap; after a stall it fires once, then realigns.
let periodic = new PeriodicTimer(TimeSpan.FromMilliseconds 100.0)
let clock = Stopwatch.StartNew()
let offsets =
    [ for tick in 0 .. 7 do
        periodic.WaitForNextTickAsync().AsTask().Wait()
        yield clock.ElapsedMilliseconds
        if tick = 1 then Thread.Sleep 350 ]
printfn "%A" offsets  // one run: [102L; 201L; 556L; 601L; 701L; 800L; 900L; 1000L]
```

**Why it matters**

A timer job that is usually fast and sometimes slow (a cleanup that hits a big batch, a sync behind a slow network) becomes a concurrent job exactly when it is slowest. It then races itself on whatever it touches: the same rows, the same file, the same counter. The `lock` in the snippet is there only to count overlaps. Without one, the job's own state is a data race. Rust tokio and JS cannot overlap a timer callback with itself by construction: one is awaited, and the other runs on a single event loop. C++ has no timer to overlap.

**Chew on this**

Which of your `Threading.Timer` (or `System.Timers.Timer`) callbacks could take longer than their period on a bad day, and what do two copies of them do to each other? Would `PeriodicTimer`'s "fire once, then realign" be the behaviour you actually want?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.threading.timer
- https://learn.microsoft.com/en-us/dotnet/api/system.threading.periodictimer

**Gotchas**

- In 1 s the timer called the job 10 times on Linux and 11 on macOS (measured), even though each call took 250 ms: the schedule never slows down for the work.
- `timer.Dispose()` stops new callbacks but does not wait for running ones. The snippet's extra `Thread.Sleep 300` is what lets them finish before `peak` is read.
- A second `WaitForNextTickAsync` while one is pending throws `InvalidOperationException` (measured): the API allows one waiter, which is what makes overlap impossible.

## TypeScript: `setInterval` never bursts and never catches up, so after a stall the whole schedule shifts later

*Stdlib and ecosystem gems*

**Did you know**

Node's `setInterval` re-arms from when each callback actually ran. A 350 ms stall in a 100 ms interval produced one late tick at 552 ms, and every tick after it stayed 350 ms behind the original schedule (653, 754, ...). That is tokio's `Delay` policy, and there is no option to change it. Under steady load it also drifts: 100 ticks of 10 ms with 4 ms of work each took 1141 to 1153 ms, and the hand-rolled "re-arm `setTimeout` after the work" took 1608 to 1622 ms, on Node 22.23.4 (Debian 13, Docker, arm64). As a separate confirmation, on Node 22.17.1 (macOS): 1079 ms and 1501 ms.

**Show me**

```ts
// TypeScript 6.0.3 types, Node 22.23.4 (Linux) and 22.17.1 (macOS)
const start = performance.now()
const fn_elapsed = (): number => Math.round(performance.now() - start)
const fn_stall = (milliseconds: number): void => {
    const until = performance.now() + milliseconds
    while (performance.now() < until) {}    // the event loop is blocked, like a long synchronous call
}

const offsets: number[] = []
let tick = 0
const handle = setInterval(() => {
    offsets.push(fn_elapsed())
    if (tick === 1) fn_stall(350)
    if (++tick === 8) {
        clearInterval(handle)
        console.log(offsets)  // one run: [101, 202, 552, 653, 754, 855, 955, 1057]: no burst, the schedule shifted
    }
}, 100)
```

**Why it matters**

`setInterval` is the safe choice for "poll every 100 ms": after a pause you get one call, not a flood. It is the wrong choice for anything that must line up with wall time, such as "on the minute", a metrics flush every 10 s, or a billing tick, because the error accumulates and never comes back. JS has no burst and no skip option. A schedule that must stay on the grid has to compute the next deadline from the start time, as C++'s coalescing loop does.

**Chew on this**

Which of your intervals are expected to stay aligned to the clock, and how far behind would they be after a week of event-loop stalls? Does anything read the tick count as if it were elapsed time?

**Sources**

- https://nodejs.org/api/timers.html#setintervalcallback-delay-args
- https://developer.mozilla.org/en-US/docs/Web/API/Window/setInterval

**Verified**

`console`, `performance`, `setInterval` and `clearInterval` typed with one-line `declare`s instead of `@types/node`. Run on Node 22.23.4 on Debian 13 (Docker, arm64), and as a separate confirmation on Node 22.17.1 (macOS).

**Gotchas**

- 100 x `setInterval(10)` with 4 ms of work took 1141 to 1153 ms on Linux (about 15% slow; 1079 ms, 8%, on macOS), and 100 x re-armed `setTimeout(10)` took 1608 to 1622 ms (about 61%; 1501 ms, 50%, on macOS) (measured): the hand-rolled form adds the work time to every period.
- The stall delays the tick; it does not cancel it. There is exactly one late call (552 ms), not zero.
- A period over 2^31 - 1 ms fires after 1 ms instead, with a `TimeoutOverflowWarning` (measured for `setInterval(fn, 2 ** 31)`), the same limit as part 3's `setTimeout` tip.

# The functional angle: a schedule is a function from "the last deadline and now" to "the next deadline", and there are exactly three of them

Draws on all four tips. Strip the APIs away and every periodic timer computes `next_deadline(previous, now, period)`. The three policies are three different pure functions:

```text
// Pseudocode for the three policies, then which API implements which (all measured above)
burst(previous, now, period)    = previous + period                                  // may be in the past
delay(previous, now, period)    = now + period                                       // forgets the grid
skip(previous, now, period)     = previous + period * (1 + floor((now - previous) / period))  // next grid point after now
```

| Language | Burst | Skip | Delay (drift) | What choosing costs |
| --- | --- | --- | --- | --- |
| Rust (`tokio`) | `MissedTickBehavior::Burst` (default) | `Skip` | `Delay` | one setter; the default is the one that floods |
| C++ | `sleep_until(next += period)` | the `while` loop in the C++ tip | `sleep_for(period)` | you write the function, and nobody reviewing sees its name |
| F# / .NET | not offered | `PeriodicTimer` | not offered | `Threading.Timer` is none of the three: it does not wait, so it overlaps |
| TypeScript | not offered | not offered | `setInterval` | anything else is hand-written from the start time |

All three are pure: only `now` comes from outside. That makes them easy to test with a fake clock and impossible to test without one, which is why the default is usually discovered in production. No row needs `mut` beyond the stored `next`. The asymmetry is that Rust names all three, and every other row offers one or none.

# The security angle: a timer that bursts after a pause is a burst you scheduled yourself, and one that overlaps is a race you scheduled yourself

Draws on the Rust tip (Mode B: is `Burst` safe on a request path?) and the F# tip (Mode C: the missing "already running" check). In both, the runtime does exactly what it documents.

**Overlapping callbacks (CWE-362, concurrent execution using shared resource with improper synchronization).** The plausible version:

```fsharp
// F#, illustrative and not compiled (load_unpaid_rows, pay and mark_paid stand for your own code).
// Looks like "every 100 ms, pay out what is due". Is "pay out, up to three times at once, when it is slow".
let fn_pay_due (_: obj) =
    let due = load_unpaid_rows ()     // a slow query on a busy day
    for row in due do pay row         // a second copy loads the same rows before the first marks them paid
    mark_paid due
let payout_timer = new Timer(TimerCallback fn_pay_due, null, 0, 100)
```

The fix is not a faster query. It is making overlap impossible (`PeriodicTimer`, or an `Interlocked.CompareExchange` "already running" flag that returns early), and making `pay` idempotent anyway.

**Bursts after a stall (CWE-770, allocation of resources without limits or throttling).** A tokio `interval` driving a heartbeat, a retry or a token-bucket refill sends three in a millisecond after every pause, and every instance stalls together after a deploy or a shared dependency's hiccup. That is a self-made thundering herd (inferred from the measured burst, not from a named incident).

| Language | What goes wrong | What the runtime does | Still on you |
| --- | --- | --- | --- |
| F# / .NET | `Threading.Timer` callbacks overlap (3 at once, measured) | documents it | `PeriodicTimer`, or an "already running" flag; idempotent side effects |
| Rust | `interval` bursts after a stall (measured) | documents `Burst` as the default | `set_missed_tick_behavior(Skip)` for heartbeats and polls |
| C++ | `sleep_until(next += period)` bursts (measured) | nothing; it is your loop | write the coalescing loop, or rate-limit the work itself |
| TypeScript | no burst and no overlap, but drift | the event loop serializes callbacks | do not derive elapsed time from tick counts |

TypeScript is the control for the overlap half: one event loop cannot run a callback on top of itself. Nobody is a control for the burst half, since three of the four can be made to do it.

# FAQ

**Is there an incident appendix for this part?** No. No post-mortem found blames a periodic timer's missed-tick policy or a reentrant timer callback with enough first-hand detail to pass the proof rule. If one turns up, it belongs here.

**Does any of this change with a wall-clock step?** Not for the timers measured here, which all run on monotonic clocks: tokio's `Instant`, C++ `steady_clock` in the snippets, .NET's timers, and Node's timers. A loop that computes its deadline from `system_clock` or `Date.now()` would also jump when the wall clock is stepped (part 3).
