**The thesis of this special: once absence and failure are values, every generic operation treats them as plain data, and plain data has opinions.** It sorts, it gets copied into exceptions, it is a `null` on the runtime underneath, or it stops being an `Effect` when the library changes its mind. None of the four types below is broken. Rust `Result`, C++ `std::expected`, F# `Option` and Effect `Option` each behave exactly as documented. The bug is the generic code that never asked what a "missing" or "failed" value does when it meets `max`, a copy constructor, `ToString` or `yield*`.

## Rust: derive(Ord) puts Ok before Err, so max() over results returns the failure and sort() moves every error to the end

*Idioms and antipatterns*

**Did you know**

`Result` and `Option` derive `PartialOrd` and `Ord`, and a derived enum orders by variant first, in declaration order. `Ok` is declared before `Err` and `None` before `Some`, so every `Err` is greater than every `Ok`, and every `None` is less than every `Some`. `latencies.iter().max()` over a fan-out with one failed shard returns that failure, not the slowest success. The same call over `Option`s does the opposite and silently ignores the gap.

**Show me**

```rust
// rustc 1.99.1, edition 2021. Derived Ord on std's enums: Ok is declared before Err, None before Some.
fn main() {
    // Per-shard latencies from a fan-out; one shard failed to answer.
    let latencies_ms: Vec<Result<u32, String>> =
        vec![Ok(12), Err("shard 3 timed out".to_string()), Ok(48)];

    // "Slowest shard" reads as max(), but every Err sorts above every Ok.
    println!("{:?}", latencies_ms.iter().max()); // Some(Err("shard 3 timed out"))
    println!("{:?}", latencies_ms.iter().min()); // Some(Ok(12))

    let mut sorted = latencies_ms.clone(); // sort() works in place, so this copy has to be mut
    sorted.sort();
    println!("{:?}", sorted); // [Ok(12), Ok(48), Err("shard 3 timed out")]

    // Option is the mirror image: None sorts below every Some.
    let readings: Vec<Option<u32>> = vec![Some(12), None, Some(48)];
    println!("{:?}", readings.iter().max()); // Some(Some(48)): the gap is invisible
    println!("{:?}", readings.iter().min()); // Some(None): the gap wins

    // Say what you mean: drop the failures, then compare the numbers.
    println!("{:?}", latencies_ms.iter().flatten().max()); // Some(48)
}
```

**Why it matters**

A p100 latency gauge built on `max()` reports a timeout message instead of a number, and a dashboard that only plots `Ok` values then shows the healthiest shard as the slowest. With `Option`, `max()` reports a full set of readings even when one sensor is silent, while `min()` reports the silence. C++ makes the same choice for `std::optional` (an empty one is less than every value) but refuses to order `std::expected` at all: `ok_value < failed` is "no match for 'operator<'" on g++ 14.2. F# derives the same order as Rust: `List.max [Ok 12; Error "shard 3 timed out"; Ok 48]` is the `Error`.

**Chew on this**

Which of your aggregates (`max`, `min`, `sort`, a `BTreeMap` key) runs over a type whose "nothing" or "failed" variant you never placed on purpose, and would the declaration order of your own enums survive a reviewer asking why `Err` is the biggest value in the system?

**Sources**

- https://doc.rust-lang.org/std/cmp/trait.PartialOrd.html ("When derived on enums, variants are primarily ordered by their discriminants")
- https://doc.rust-lang.org/std/result/enum.Result.html
- https://doc.rust-lang.org/std/option/enum.Option.html

**Gotchas**

- Two `Err`s compare by their payload: `[Err("a: disk full"), Ok(7), Err("z: timeout")]` has `max` = `Err("z: timeout")`, chosen alphabetically by message, not by severity.
- `flatten()` drops the failures without a trace: `latencies_ms.iter().flatten().max()` is `Some(48)`, and nothing says a shard failed. Count the `Err`s separately if the failure matters.
- `collect::<Result<Vec<_>, _>>()` is not an aggregate over all of them: it stops at the first `Err` and returns it (`Err("shard 3 timed out")`). Part 8 of this special covers folds that stop early.

## C++: std::expected's lvalue value() copies the error into the exception, so a move-only E compiles only as std::move(result).value()

*Stdlib and ecosystem gems*

**Did you know**

`std::expected<T, E>::value()` throws `std::bad_expected_access<E>` when it holds an error, and the exception carries its own `E`. The lvalue overloads build it from `std::as_const(error())`, a copy, so the standard makes them ill-formed when `E` is not copy constructible. An error type that owns a resource (a `unique_ptr`, a file handle, a captured stack) leaves you only `std::move(result).value()`, which moves the payload into the exception and leaves an empty error behind. C++23; `std::expected` ships in GCC 12, Clang 16 and MSVC 19.33, its monadic operations in GCC 13, Clang 17 and MSVC 19.36.

**Show me**

```cpp
// C++23, g++ 14.2 -std=c++23 (libstdc++). std::expected: GCC 12, Clang 16, MSVC 19.33.
#include <cstdio>
#include <expected>
#include <memory>
#include <string>

// The failure owns a resource, so the error type is move-only.
struct read_failure { std::unique_ptr<std::string> detail; };

std::expected<int, read_failure> read_port() {
    return std::unexpected(read_failure{std::make_unique<std::string>("no such key")});
}

int main() {
    auto port_result = read_port();
    // int port_copy = port_result.value();
    //   error: use of deleted function 'read_failure::read_failure(const read_failure&)'
    try {
        int port = std::move(port_result).value(); // rvalue overload: moves E into the exception
        std::printf("port %d\n", port);
    } catch (const std::bad_expected_access<read_failure>& failure) {
        std::printf("caught: %s\n", failure.error().detail->c_str()); // caught: no such key
    }
    // The exception took the payload; the expected still holds an error, now an empty one.
    std::printf("detail is null: %d\n", port_result.error().detail == nullptr); // 1
}
```

**Why it matters**

`.value()` is the bridge from `expected` back to exception-based code, and the bridge charges a copy of the error on every throw: cheap for an `errc`, a heap allocation for a `std::string` message, impossible for a move-only one. The `std::move` workaround is not free either, because any later log line that reads `port_result.error()` sees the moved-from husk. Rust's `Result::unwrap` has the opposite constraint: it needs `E: Debug` so the panic can print the error, never a copy. F# `Result` has no `value()` at all; `match` is the only door out.

**Chew on this**

Does your error type have to be copyable because the code needs copies, or only because one `.value()` call somewhere needs the exception to own one, and which of those two would you rather discover in code review?

**Sources**

- https://en.cppreference.com/w/cpp/utility/expected/value ("If std::is_copy_constructible_v<E> is false, the program is ill-formed")
- https://en.cppreference.com/w/cpp/utility/expected/and_then
- https://en.cppreference.com/w/cpp/compiler_support/23

**Verified**

g++ 14.2 (libstdc++) only; Clang and MSVC not checked, support versions from cppreference.

**Gotchas**

- `and_then` cannot change the error type: a callable returning `std::expected<int, std::string>` from an `expected<int, read_failure>` chain fails libstdc++'s static assertion, "the function passed to std::expected<T, E>::and_then must return a std::expected with the same error_type". `transform_error` is the step that converts it.
- `std::expected` has `==` but no `<`: `ok_value < failed` is "no match for 'operator<'", so it cannot be a `std::set` key or be sorted without a comparator.

## F#: None is a literal null at runtime, so None.ToString() throws and string None prints nothing

*Type system deep cuts*

**Did you know**

FSharp.Core declares `Option<'T>` with `CompilationRepresentationFlags.UseNullAsTrueValue`, so `None` is not an object at all: it is `null`. `isNull (box None)` is `true`, and any instance member that needs an object (`ToString`, `GetHashCode`, `GetType`) throws `NullReferenceException` on it. Members the compiler can turn into static calls, such as `IsNone`, still work, which makes the failure look random. `printf "%A"` special-cases it and prints `None`, while `string None` prints an empty string. Measured on F# 10, FSharp.Core 10.1.0.0, .NET 10.0.13.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, dotnet fsi.
let missing_port : int option = None

printfn "%b" (isNull (box missing_port)) // true: None is compiled as null
printfn "%A" missing_port                // None: printf special-cases it
printfn "[%s]" (string missing_port)     // []: string of a null is ""

let print_member_result (label: string) (member_call: unit -> string) =
    try printfn "%s = %s" label (member_call ())
    with failure -> printfn "%s -> %s" label (failure.GetType().Name)

print_member_result "ToString" (fun () -> missing_port.ToString())                // NullReferenceException
print_member_result "GetHashCode" (fun () -> string (missing_port.GetHashCode())) // NullReferenceException
print_member_result "IsNone" (fun () -> string missing_port.IsNone)               // True: compiled as a static call

// Through an obj-typed .NET API, None reads as a plain null.
let settings = System.Collections.Generic.Dictionary<string, obj>()
settings["port"] <- box missing_port
printfn "%b" (isNull settings["port"]) // true

// ValueOption is a struct, so its "none" is a real value.
let missing_value_port : int voption = ValueNone
printfn "%s" (missing_value_port.ToString()) // ValueNone
```

**Why it matters**

Inside F#, the `null` is invisible and `Option` behaves like a value. The moment it crosses into code that sees `obj` (a logging framework calling `ToString`, a C# library hashing it into a cache, a serializer, a `Dictionary<string, obj>` of settings), `None` and "never set" become the same `null`, and some members crash on it. Rust guarantees the same zero-cost trick for `Option<&T>` and `Option<Box<T>>` (the null pointer is `None`), but there the niche is never visible as a callable object, so nothing can call a method on it. A C++ empty `std::optional` is a real object with a flag inside; nothing about it is a null pointer.

**Chew on this**

Where does an F# `Option` in your service leave F#: a log call, a cache key, an `obj` parameter, a C# interface? And does the code on the far side know that `null` there might mean "a value that was deliberately empty"?

**Sources**

- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/prim-types.fs (`[<CompilationRepresentation(CompilationRepresentationFlags.UseNullAsTrueValue)>]` on `type Option<'T>`)
- https://learn.microsoft.com/dotnet/api/microsoft.fsharp.core.compilationrepresentationflags
- https://learn.microsoft.com/dotnet/fsharp/language-reference/options

**Gotchas**

- `string None` is `""` but `sprintf "%A" None` is `"None"`, so two log lines for the same value disagree depending on which one formatted it.
- `None.IsNone` returns `True` while `None.ToString()` throws: whether a member works depends on how the compiler emits it, not on whether the value is `None`.
- `ValueNone` is not null: `isNull (box ValueNone)` is `false` and `ToString()` returns `"ValueNone"`. Switching to `voption` fixes the crash and changes what an `obj` consumer sees.

## TypeScript: Effect 4 made Option a plain value, so yield* on one dies as a defect, even when it holds Some

*New discoveries and currently popular patterns*

**Did you know**

In Effect 3, `Option` and `Either` were subtypes of `Effect`: `yield* someOption` inside `Effect.gen` returned the value, and a `None` became a typed `NoSuchElementException` in the error channel. Effect 4 reversed that. Its migration guide calls `Option` and `Result` (the new name for `Either`) "plain values, not Effects" that "cannot be yielded directly in `Effect.gen`". tsc rejects the old code, but code that slips past the types (plain JS, an `any`) gets a defect at runtime: `Die("Fiber.runLoop: Not a valid effect: some(\"alice\")")`. The `Some` case dies too, so the happy path breaks, not just the error path. Effect 4.0.6 against 3.22.4.

**Show me**

```typescript
// TypeScript, effect 4.0.6, tsc 7.0.2 --strict, Node 22.23.4.
import { Effect, Exit, Option } from "effect"

const users = new Map<string, string>([["u1", "alice"]])
const find_user = (user_id: string): Option.Option<string> =>
    Option.fromNullishOr(users.get(user_id)) // 3.x name: Option.fromNullable

// Written for Effect 3, where Option was a subtype of Effect:
//   const greet_v3_style = (user_id: string) => Effect.gen(function* () {
//       const name = yield* find_user(user_id)
//       return `hello ${name}`
//   })
// effect 3.22.4:           Success "hello alice"; "u2" -> Fail(NoSuchElementException), a typed error
// effect 4.0.6, tsc:       TS2345 on the Effect.gen call: Property '[TypeId]' is missing in type 'None<string>'
// effect 4.0.6, plain JS:  Die("Fiber.runLoop: Not a valid effect: some(\"alice\")"), a defect even for Some

// Effect 4: convert at the boundary.
const greet = (user_id: string) => Effect.gen(function* () {
    const name = yield* Effect.fromOption(find_user(user_id)) // None -> Fail(NoSuchElementError)
    return `hello ${name}`
})
for (const user_id of ["u1", "u2"]) {
    const exit = Effect.runSyncExit(greet(user_id))
    console.log(user_id, Exit.isSuccess(exit) ? exit.value : String(exit.cause))
}
// u1 hello alice
// u2 Cause([Fail(NoSuchElementError: Effect.fromOption: Option.none)])
```

**Why it matters**

Effect 3's subtyping made absence convert itself into failure silently, at every `yield*`. Effect 4 makes the conversion an explicit call, `Effect.fromOption` or `Effect.fromResult`, which is the same choice Rust makes: `?` on an `Option` inside a function returning `Result` does not compile until you write `.ok_or(...)`. F# never had the subtyping: `Option` and `Result` are unrelated FSharp.Core types, and FSharp.Core ships no computation-expression builder for either, so every conversion is a function you call. The cost of Effect 4's version is the migration. tsc's error lands on the whole `Effect.gen(...)` call rather than on the `yield*` line, so in a long generator it points at the wrong place.

**Chew on this**

In your Effect 3 code, how many `yield*` sites rely on a `None` quietly becoming a failure, and how many of their error handlers match on `NoSuchElementException` by name?

**Sources**

- https://github.com/Effect-TS/effect/blob/main/migration/yieldable.md ("plain values, not Effects", "cannot be yielded directly in `Effect.gen`")
- https://github.com/Effect-TS/effect/blob/main/migration/v3-to-v4.md (`effect/Either` -> `effect/Result`)
- https://github.com/Effect-TS/effect/blob/main/MIGRATION.md

**Gotchas**

- `Result` dies the same way: `yield* Result.succeed(7)` on 4.0.6 is `Die("Fiber.runLoop: Not a valid effect: success(7)")`. `Effect.fromResult(Result.fail("bad port"))` gives `Fail("bad port")`.
- The error class was renamed too: 3.22.4 fails with `NoSuchElementException`, 4.0.6 with `NoSuchElementError`. A `catchTag` on the old name stops matching.
- `Option.fromNullable` is gone in 4.0.6. The constructors are now `fromNullishOr`, `fromNullOr` and `fromUndefinedOr`, one per kind of "missing".
- Operator names moved as well: `Effect.catchAll` from 3.x is `Effect.catch` in 4.0.6.

# The functional angle: all four put "missing" first, so max() hides an absent Option and surfaces a failed Result, and only C++ refuses to order a failure at all

_Draws on the Rust tip, with rows measured for the other three. The functional shape is "absence and failure as ordinary values", and the question is what an ordinary generic operation, `max`, does with them._

F# is the baseline here because comparison is generated for every union, FSharp.Core's included, so its row shows the derived answer with nothing hand-written:

```fsharp
// F# 10, FSharp.Core 10.1.0.0, .NET 10.0.13
let outcomes : Result<int, string> list = [ Ok 12; Error "shard 3 timed out"; Ok 48 ]
printfn "%A" (List.max outcomes)  // Error "shard 3 timed out"
printfn "%A" (List.sort outcomes) // [Ok 12; Ok 48; Error "shard 3 timed out"]
let readings : int option list = [ Some 12; None; Some 48 ]
printfn "%A %A" (List.max readings) (List.min readings) // Some 48 None
```

| Language | Missing vs present | Failed vs succeeded | `max` of [ok 12, failed, ok 48] | What it costs |
| --- | --- | --- | --- | --- |
| F# | `None < Some _` | `Ok _ < Error _` | `Error "shard 3 timed out"` | comparison is generated from the declaration order of the cases; nothing in your code shows the decision |
| Rust | `None < Some(_)` | `Ok(_) < Err(_)` | `Err("shard 3 timed out")` | same as F#, through `derive`; a different order needs a newtype with a hand-written `Ord` |
| C++ | empty `optional` `<` any value | `std::expected` has no `<` (compile error) | does not compile | a comparator you write by hand, which is the one place the decision becomes visible |
| TypeScript (Effect) | `Option.makeOrder(Order.Number)` sorts none first (4.0.6; `Option.getOrder` in 3.22.4) | not measured | no default; you pass an `Order` | nothing is ordered until you choose an `Order`, so the choice is always in the source |

The asymmetry worth keeping: Rust and F# made one decision ("the variant declared first is smaller") and applied it to two types whose meanings point opposite ways. For `Option`, "missing sorts first" makes `max` ignore gaps. For `Result`, the same rule makes `max` report failures. Neither is wrong, and neither was chosen for your aggregate.

Left open: if your codebase had to state one rule for where "nothing" and "failed" sort, would it pick the same rule for both?

# The security angle: an upgrade that turns a typed failure into a defect skips every handler written for the failure

_Draws on the TypeScript tip, Mode B: the tip shows that Effect 4 stopped treating `Option` as an `Effect`; the question is what that does to error handling that was correct on Effect 3. Direction: the library prevented nothing here; the type checker is the only thing that catches it._

The insecure sample is ordinary Effect 3 code: a lookup, and a handler that maps "not found" to a 404.

```typescript
// TypeScript, written for effect 3.x; run as JS on 3.22.4 and 4.0.6, Node 22.23.4
const handle_request = (user_id: string) => Effect.catchAll( // 4.x name: Effect.catch
    Effect.gen(function* () {
        const name = yield* find_user(user_id) // an Option, yielded directly
        return `200 ${name}`
    }),
    () => Effect.succeed("404 not found"))
// effect 3.22.4: u1 -> "200 alice", u2 -> "404 not found"
// effect 4.0.6:  u1 and u2 -> unhandled Die("Fiber.runLoop: Not a valid effect: ..."); the 404 branch never runs
```

`catchAll` (and `catch` in 4.x) only sees typed failures in the `E` channel. On Effect 4 the `yield*` produces a defect instead, so the handler is skipped, and every request, the found ones included, ends as an unhandled defect. That is an availability failure, CWE-755 (Improper Handling of Exceptional Conditions). The fix converts at the boundary, which keeps the failure typed:

```typescript
// TypeScript, effect 4.0.6
const handle_request = (user_id: string) => Effect.catch(
    Effect.gen(function* () {
        const name = yield* Effect.fromOption(find_user(user_id))
        return `200 ${name}`
    }),
    (failure) => Effect.succeed(`404 not found (${failure._tag})`))
// u1 -> "200 alice", u2 -> "404 not found (NoSuchElementError)"
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript (Effect 4) | `yield*` on an `Option` is a defect, so a typed-failure handler never runs (CWE-755) | tsc --strict rejects it (TS2345) | every path the compiler does not see: plain JS, `any`, `@ts-expect-error`; run the "not found" tests after the upgrade |
| F# | `None` crosses into `obj` code as `null`, and `ToString`/`GetHashCode` on it throw (CWE-476) | nothing: inside F# it is a value, outside it is `null` | decide what `null` means at each `obj` boundary, or use `voption` there |
| Rust | an `Err` wins `max()`, so a "worst latency" or "highest privilege" fold returns the failure (CWE-697) | it compiles; the order is documented | filter or `partition` failures before any ordering fold |
| C++ | after `std::move(result).value()` throws, `result.error()` is a moved-from husk (`detail == nullptr`) | nothing; moved-from is a valid state | log from the caught exception's `error()`, never from the original `expected` |

Left open: which of your error handlers would still run if the thing they catch quietly became a different kind of failure?

# FAQ

**Does Rust's `?` turn a `None` into an `Err` when the function returns `Result`?**
No. rustc 1.99.1 rejects it: "the `?` operator can only be used on `Result`s, not `Option`s, in a function that returns `Result`" (E0277). The conversion is `.ok_or(...)?` or `.ok_or_else(...)?`, which is exactly the explicit step Effect 4 now asks for.

**Does C++ `std::optional::value()` have the same copy requirement as `expected::value()`?**
No. `std::bad_optional_access` carries no payload, so `optional<unique_ptr<int>>::value()` on an lvalue compiles and returns the reference (it printed `8080`), and the empty one throws with `what()` = "bad optional access" on libstdc++ 14.2.

**If C# hands F# a `null` where an `int option` was declared, does pattern matching still work?**
Yes, because that `null` is exactly F#'s `None`: `Option.isNone` is `true`, `= None` is `true`, and `match` takes the `None` branch. The crash only comes from instance members like `ToString()`.

**Did Effect 4 remove `Either`?**
It renamed it. The migration guide maps `effect/Either` to `effect/Result`, and 4.0.6 exports `Result` and no `Either`. The constructors are `Result.succeed` and `Result.fail`, and `Effect.fromResult` is the bridge into `Effect.gen`.

# Appendix A: Cloudflare, 2025-11-18, a failure value unwrapped on the request path

_Not part of the tip rotation. Written 2026-10-27; backs the thesis of this part (a failure kept as a value is safe until something unwraps it) and the C++ tip's "bridge out" point. A real incident, quoted from Cloudflare's own postmortem; the reproduction below is illustrative code, run on rustc 1.99.1 (Debian 13.7)._

**Bug class:** Bohrbug, data-triggered: solid once the oversized file arrived, and intermittent only while the database change was half rolled out. Anti-pattern: `unwrap()` on a limit check over internally generated configuration.

## A.1 What happened

Quoted from the postmortem:

- A permissions change was made "at 11:05" on a ClickHouse cluster. The query that builds a bot-management feature file reads `system.columns`, and "the query does not filter for the database name", so the change made it return "a large number of duplicate "feature" rows". The file "doubled in size".
- The proxy that loads the file "preallocate[s] memory for the features" with a limit "set to 200, well above our current use of ~60 features". The bad file had "more than 200 features", "this limit was hit", "resulting in the system panicking": "thread fl2_worker_thread panicked: called Result::unwrap() on an Err value".
- The file "was being generated every five minutes", and "bad data was only generated if the query ran on a part of the cluster which had been updated", so "every five minutes there was a chance of either a good or a bad set of configuration files". Impact began at 11:20 UTC; "as of 17:06 all systems at Cloudflare were functioning as normal".

## A.2 The shape, reproduced

The postmortem shows its code only as an image, so this is the shape rebuilt, not Cloudflare's source. The counts are illustrative (110 columns, chosen so that doubling crosses 200); the postmortem gives only "~60" in use and "more than 200" in the bad file.

```rust
// Rust, rustc 1.99.1. Illustrative reproduction of the shape, not Cloudflare's code.
const FEATURE_LIMIT: usize = 200; // the postmortem's preallocated limit

#[derive(Debug)]
struct TooManyFeatures { found: usize, limit: usize }

// One row per (database, column), as `system.columns` returns them without a database filter.
fn feature_rows(databases: &[&str], columns_per_database: usize) -> Vec<String> {
    databases.iter()
        .flat_map(|database| (0..columns_per_database).map(move |column| format!("{database}.feature_{column}")))
        .collect()
}

fn load_features(rows: &[String]) -> Result<Vec<String>, TooManyFeatures> {
    (rows.len() <= FEATURE_LIMIT)
        .then(|| rows.to_vec())
        .ok_or(TooManyFeatures { found: rows.len(), limit: FEATURE_LIMIT })
}

fn main() {
    let before = feature_rows(&["default"], 110);      // illustrative count
    let after = feature_rows(&["default", "r0"], 110); // same columns, now visible twice
    println!("before: {} rows -> {:?}", before.len(), load_features(&before).map(|loaded| loaded.len()));
    println!("after:  {} rows -> {:?}", after.len(), load_features(&after).map(|loaded| loaded.len()));
    // Keeping the failure a value: fall back to the last good set.
    let last_good = load_features(&before).unwrap_or_default();
    let serving = load_features(&after).unwrap_or_else(|failure| {
        eprintln!("rejected new file: {} features, limit {}", failure.found, failure.limit);
        last_good
    });
    println!("serving {} features", serving.len());
    // The postmortem's shape: unwrap on the request path.
    let features = load_features(&after).unwrap();
    println!("unreachable: {}", features.len());
}
```

Printed:

```text
before: 110 rows -> Ok(110)
after:  220 rows -> Err(TooManyFeatures { found: 220, limit: 200 })
rejected new file: 220 features, limit 200   (stderr)
serving 110 features
thread 'main' (475) panicked at incident.rs:30:42:
called `Result::unwrap()` on an `Err` value: TooManyFeatures { found: 220, limit: 200 }
```

Exit status 101. The limit check itself was correct and returned a well-formed `Err`. Everything turned on the one line that decided what an `Err` meant.

## A.3 Back to the tips

- **Rust:** `Result` made the failure a value, and `unwrap()` turned it back into a crash. `unwrap_or_else` keeping the last good file is the same `Result`, spelled as a decision.
- **C++:** `std::move(result).value()` is the same bridge. It throws `bad_expected_access` where Rust panics, and the C++ tip's copy rule decides what the exception can carry.
- **F#:** there is no `unwrap` on `Result`; `match` is the only way out, so the decision is always written. `Option.get` on a `None` still throws: `ArgumentException: The option value was None (Parameter 'option')`.
- **TypeScript (Effect):** `Effect.runSync` on a failed effect throws; on 4.0.6, `Effect.runSync(Effect.fail("bad port"))` threw the string `"bad port"` itself. Whether a failure stays typed or becomes a defect is exactly the line the security angle above draws.

The postmortem's own remediation names the class: "Hardening ingestion of Cloudflare-generated configuration files in the same way we would for user-generated input".
