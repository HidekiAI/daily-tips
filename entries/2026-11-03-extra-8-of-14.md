# Daily Tips special, part 8 of 14: small bugs that exploded, or a duplicated jump that skipped the signature check

<!-- special-nav -->
**Specials:** [<- previous: small bugs that exploded, part 7 of 14](2026-11-02-extra-7-of-14.md) | [next: small bugs that exploded, part 9 of 14 ->](2026-11-03-extra-9-of-14.md)

Not part of the rotation. Part 8 of the fourteen-part special on real incidents: Apple's "goto fail", [CVE-2014-1266](https://nvd.nist.gov/vuln/detail/CVE-2014-1266), fixed in iOS 7.0.6 and OS X 10.9.2 in February 2014. Each tip below asks the same question of each language's compiler: when a stray line makes the next check unreachable, does it say so, and in which shapes does it stop saying so?

# What happened

**Bug class:** Bohrbug in this special's classification: every connection that reached the code path skipped the check, with no timing involved. The anti-pattern the tips below take from it is a success code inherited from the previous step: the function returned whatever `err` held when it jumped, and the last update had left it at 0.

From Apple's "About the security content of iOS 7.0.6" (CVE-2014-1266):

```text
Impact: An attacker with a privileged network position may capture or modify
data in sessions protected by SSL/TLS
Description: Secure Transport failed to validate the authenticity of the
connection. This issue was addressed by restoring missing validation steps.
```

The code, from Apple's released source, `Security-55471/libsecurity_ssl/lib/sslKeyExchange.c`, function `SSLVerifySignedServerKeyExchange`, lines 625-635:

```c
    if ((err = SSLHashSHA1.update(&hashCtx, &clientRandom)) != 0)
        goto fail;
    if ((err = SSLHashSHA1.update(&hashCtx, &serverRandom)) != 0)
        goto fail;
    if ((err = SSLHashSHA1.update(&hashCtx, &signedParams)) != 0)
        goto fail;
        goto fail;
    if ((err = SSLHashSHA1.final(&hashCtx, &hashOut)) != 0)
        goto fail;

    err = sslRawVerify(ctx,
```

The second `goto fail;` is not guarded by any `if`. It always runs, so `SSLHashSHA1.final` and `sslRawVerify` never do, and `fail:` returns `err`, which the last successful `update` left at 0, meaning success. NVD's summary: the function "does not check the signature in a TLS Server Key Exchange message, which allows man-in-the-middle attackers to spoof SSL servers". The fix in `Security-55471.14` is the deletion of that one line (`diff` of the two releases: `631d630 < goto fail;`).

## Rust: `unreachable_code` flags the statement after a duplicated `return`, and says nothing when the early exit sits behind `if SKIP_SIGNATURE`

*Idioms and antipatterns*

**Did you know**

Rust cannot write goto fail's layout: an `if` body needs braces, so a stray line is never "indented under" the condition. A duplicated early exit still compiles, with only a warning: `return Ok(());` before the signature check gives "warning: unreachable statement", even when the `return` comes out of a `macro_rules!` macro. Put the same exit behind `if true { ... }` or behind `const SKIP_SIGNATURE: bool = true`, and rustc 1.99.1 emits no warning at all, while the function still returns `Ok(())` without checking.

**Show me**

```rust
// rustc 1.99.1, edition 2024, Debian. A Rust port of the C shape above.
#[derive(Debug)]
struct SslError(i32);
fn update_hash() -> Result<(), SslError> { Ok(()) }
fn verify_signature() -> Result<(), SslError> { Err(SslError(-9809)) } // -9809: an arbitrary failure code

fn duplicated_return() -> Result<(), SslError> {
    update_hash()?;
    update_hash()?;
    return Ok(()); // the duplicated line
    verify_signature()?; // warning: unreachable statement
    Ok(())
}

const SKIP_SIGNATURE: bool = true; // a debug switch someone left on

fn constant_switch() -> Result<(), SslError> {
    if SKIP_SIGNATURE { return Ok(()); } // no warning
    if true { return Ok(()); }           // no warning either
    verify_signature()?;
    Ok(())
}

fn main() {
    println!("{:?} {:?}", duplicated_return(), constant_switch()); // Ok(()) Ok(())
}
```

**Why it matters**

The lint looks for code that follows an expression which never completes (`return`, `panic!`, `loop {}`); a branch on a constant is apparently still treated as having two arms (inferred from the measurement above, not documented), so the check behind it reads as reachable. And it is a warning: `cargo build` succeeds with it, and only `-D warnings` (or `#![deny(unreachable_code)]`) turns the duplicated `return` into an error.

**Chew on this**

Which of your verification functions have a `const` or `cfg!` switch that returns early, and who would notice if it shipped set to `true`? Does your CI build with `-D warnings`, and if it does, what is the first warning you would allow back in?

**Sources**

- https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html#unreachable-code
- https://nvd.nist.gov/vuln/detail/CVE-2014-1266

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1. Clippy is not installed in that image, so whether a Clippy lint catches the constant switch was not checked.

**Gotchas**

- `#![allow(unused)]` at the top of a crate also silences `unreachable_code`, because the lint is part of the `unused` group: the duplicated `return` then compiles with 0 warnings and still prints `Ok(())`.
- `-D warnings` turned the duplicated `return` into `error: unreachable statement`, together with every other warning in the file (here also `field 0 is never read`), so enabling it on an old crate fails on unrelated warnings first.

## C++: `-Wall` catches goto fail only by its indentation; add braces and GCC 16 and Debian clang 19 both go silent

*Idioms and antipatterns*

**Did you know**

Compiled as C or as C++23, the original goto fail layout gets one warning under `-Wall` on both compilers: `-Wmisleading-indentation` ("this 'if' clause does not guard..." on GCC 16.2, "misleading indentation; statement is not part of the previous 'if'" on Debian clang 19.1.7). That warning is about the indentation, not about the dead code. Re-indent the duplicate to the `if`'s own level, as a formatter would, or wrap each `if` body in braces, and `-Wall -Wextra` reports nothing on either compiler. Only clang's `-Wunreachable-code`, which neither `-Wall` nor `-Wextra` enables, still reports "code will never be executed". GCC has no working equivalent.

**Show me**

```cpp
// C++23, g++ 16.2 and clang++ 19.1.7, Debian. The "always use braces" version of goto fail.
#include <cstdio>
static int update_hash() { return 0; }                     // 0 = success, as in OSStatus
static int final_hash() { return 0; }
static int verify_signature() { return -9809; }           // the check that should fail; -9809 is arbitrary

static int verify_server_key_exchange() {
    int inherited_status_code; // mutable: assigned by each step
    if ((inherited_status_code = update_hash()) != 0) {
        goto fail;
    }
    if ((inherited_status_code = update_hash()) != 0) {
        goto fail;
    }
    goto fail;                               // the duplicate: -Wall -Wextra say nothing now
    if ((inherited_status_code = final_hash()) != 0) {         // clang -Wunreachable-code: "code will never be executed"
        goto fail;
    }
    inherited_status_code = verify_signature();
fail:
    return inherited_status_code;                              // still 0, inherited from the second update_hash()
}

int main() { std::printf("verify returned %d\n", verify_server_key_exchange()); } // verify returned 0
```

**Why it matters**

Mandatory braces are a common lesson drawn from goto fail, and they remove the misleading layout. They also remove the only reason `-Wall` noticed. The dead code is still there, and finding it now takes a flag you have to turn on deliberately: clang's `-Wunreachable-code`.

**Chew on this**

Does your build turn on `-Wunreachable-code` anywhere, and on which compiler? If your formatter re-indented a stray line tomorrow, which warning would still fire?

**Sources**

- https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html (`-Wmisleading-indentation`)
- https://clang.llvm.org/docs/DiagnosticsReference.html#wunreachable-code
- https://github.com/apple-oss-distributions/Security/blob/Security-55471/libsecurity_ssl/lib/sslKeyExchange.c

**Verified**

GCC 16.2.0 (`gcc:latest`) and Debian clang 19.1.7 (`debian:stable` plus `apt-get install clang`), both Debian; Apple clang 21 also gives the `-Wunreachable-code` warning. That `-Wunreachable-code` is outside clang's `-Wall` and `-Wextra` was measured, not read from the documentation.

**Gotchas**

- GCC accepts `-Wunreachable-code` without complaint and does nothing with it: `gcc -Q --help=warnings` lists it as `[ignored]`, and the braced file above gives 0 warnings with `-Wall -Wextra -Wunreachable-code`.
- On clang, `-Weverything` reports both the misleading indentation and the dead code; `-Wall -Wextra` reports only the indentation, and only while the layout is misleading.

## F#: `FS0026` flags an arm after `_`, and says nothing when the duplicate hides behind a `when` guard

*Idioms and antipatterns*

**Did you know**

F# has no `goto` and no early `return`, so its version of a stray exit is a `match` arm that catches a case before the real check sees it. An arm placed after `| _ ->`, or a repeated literal pattern such as `| 0 ->` twice, gets warning `FS0026`, "This rule will never be matched". Put the duplicate behind a `when` guard or an active pattern and the compiler gives no warning: two `| matched_status_code when matched_status_code = 0 ->` arms, or two `| SignedOk ->` arms, compile cleanly, and the second one never runs. Measured on .NET SDK 10.0.403, FSharp.Core 10.1.0.0, .NET 10.0.14.

**Show me**

```fsharp
// F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14.
type Step = Hashed | Signed | Verified

let verify_plain (completed_step: Step) : Result<unit, int> =
    match completed_step with
    | Hashed -> Ok ()
    | _ -> Ok ()              // the duplicated line
    | Signed -> Error -9809   // FS0026: This rule will never be matched
    | Verified -> Ok ()       // FS0026 again

let verify_guarded (verify_status_code: int) : Result<unit, int> =
    match verify_status_code with
    | matched_status_code when matched_status_code = 0 -> Ok ()
    | matched_status_code when matched_status_code = 0 -> Error -9809   // never runs, and no warning
    | matched_status_code -> Error matched_status_code

printfn "%A %A" (verify_plain Signed) (verify_guarded 0)   // Ok () Ok ()
```

**Why it matters**

The compiler can prove an arm unreachable only when it can compare the patterns themselves. A guard is an arbitrary expression and an active pattern is a function call, so (inferred from the measurements, not documented) the compiler does not compare them, and an arm that repeats one of them gets no warning. That is the same limit the Rust tip hits with `if SKIP_SIGNATURE`: the checker reasons about shapes, not values.

**Chew on this**

How many of your `match` expressions route verification through `when` guards or active patterns, where a duplicated arm gets no warning? Would `FS0026` as an error break your build today?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/match-expressions
- https://github.com/dotnet/fsharp/blob/main/src/Compiler/FSStrings.resx (`RuleNeverMatched`)

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0`, which is Ubuntu 24.04 rather than Debian; .NET SDK 8.0.401 on macOS gave the same warnings.

**Gotchas**

- `FS0026` is a warning, so the file above runs and prints `Ok () Ok ()`; `dotnet fsi --warnaserror+:26` turns it into `error FS0026` and the script exits 1.
- A duplicated active-pattern arm (`| SignedOk -> Ok ()` then `| SignedOk -> Error -9809`, with `let (|SignedOk|_|) (verify_status_code: int) = if verify_status_code = 0 then Some () else None`) also compiled with no warning, while the same duplicate written as the literal `| 0 ->` got `FS0026`.

## TypeScript: `tsc --strict` reports unreachable code only to the editor, and `allowUnreachableCode: false` catches `if (true)` but not an `as const` flag

*Type system deep cuts*

**Did you know**

With `allowUnreachableCode` left unset, the default, `tsc --strict` exits 0 on a duplicated `return`: the documentation says the default only provides "suggestions as warnings to editors", so a CI build never sees it. Set it to `false` and the same code fails with `TS7027: Unreachable code detected.`, and so does the code after `if (true) return 0`. A switch declared `const SKIP_SIGNATURE = true as const` and used as `if (SKIP_SIGNATURE) return 0` is not reported even then, though its type is the literal `true`. Measured on tsc 7.0.2, Node 26.13.0.

**Show me**

```ts
// TypeScript, tsc 7.0.2 --strict --allowUnreachableCode false, Node 26.13.0.
function verify_signature(): number { return -9809 }
const SKIP_SIGNATURE = true as const // a debug switch someone left on

function duplicated_return(update_status_code: number): number {
    if (update_status_code !== 0) return update_status_code
    return 0 // the duplicated line
    return verify_signature() // TS7027 with the option set to false; nothing by default
}

function literal_true(): number {
    if (true) return 0
    return verify_signature() // TS7027
}

function constant_switch(): number {
    if (SKIP_SIGNATURE) return 0
    return verify_signature() // no error, even with the option set to false
}

console.log(duplicated_return(0), literal_true(), constant_switch()) // 0 0 0
```

**Why it matters**

The check that would have caught goto fail's shape is off in CI unless the tsconfig opts in, and with the option set it reads a literal `true` in the source but not a constant whose type is `true`. The type checker does know the value: after `if (SKIP_SIGNATURE) return 0`, the line `const leftover: never = SKIP_SIGNATURE` compiles, so the flag has narrowed to `never` there. The reachability check does not use that narrowing (both measured, tsc 7.0.2).

**Chew on this**

Does any tsconfig you ship set `allowUnreachableCode` at all? Where in your services does a `const` flag decide whether a check runs?

**Sources**

- https://www.typescriptlang.org/tsconfig/#allowUnreachableCode

**Verified**

Run in `node:lts-trixie` (Debian), Node 26.13.0, tsc 7.0.2 via `npx`. "Editor suggestions only" for the default is from the documentation; the exit code 0 was measured.

**Gotchas**

- Code after a call to a function that returns `never` is reported only when the callee's `never` is written out: after `function abort_handshake(reason: string): never` and after `const abort_arrow: (reason: string) => never = ...`, TS7027 fired; after an un-annotated throwing arrow `const abort_inferred = (reason: string) => { throw new Error(reason) }`, nothing.
- `allowUnreachableCode: true` is not the default either: the documentation says it ignores unreachable code entirely, so even the editor hint goes; `tsc` exited 0 with `true` and with the option unset alike.

# The functional angle: when the checks are a list, a duplicated line repeats a check instead of skipping the next one

Draws on all four tips. In goto fail, copying one line skipped every check after it. When the steps are values in a list and a fold runs them, copying an entry only runs that check twice: the signature check at the end still runs and still refuses.

```fsharp
// F#: List.fold with Result.bind.
let update_hash () : Result<unit, int> = Ok ()
let verify_signature () : Result<unit, int> = Error -9809
let fn_run_all (verification_steps: (unit -> Result<unit, int>) list) : Result<unit, int> =
    verification_steps |> List.fold (fun verdict_so_far check_step -> verdict_so_far |> Result.bind check_step) (Ok ())
printfn "%A" (fn_run_all [ update_hash; update_hash; update_hash; verify_signature ])   // Error -9809
```

```rust
// Rust: try_for_each stops at the first Err.
fn update_hash() -> Result<(), i32> { Ok(()) }
fn verify_signature() -> Result<(), i32> { Err(-9809) }
fn main() {
    let verification_steps: [fn() -> Result<(), i32>; 4] = [update_hash, update_hash, update_hash, verify_signature];
    println!("{:?}", verification_steps.iter().try_for_each(|verification_step| verification_step())); // Err(-9809)
}
```

```cpp
// C++23: std::ranges::fold_left with std::expected::and_then.
#include <algorithm>
#include <array>
#include <cstdio>
#include <expected>
using CheckFn = std::expected<void, int> (*)();
std::expected<void, int> update_hash() { return {}; }
std::expected<void, int> verify_signature() { return std::unexpected(-9809); }
int main() {
    const std::array<CheckFn, 4> const_verification_steps{update_hash, update_hash, update_hash, verify_signature};
    const std::expected<void, int> const_verification_verdict = std::ranges::fold_left(const_verification_steps, std::expected<void, int>{},
        [](const std::expected<void, int> const_verdict_so_far, const CheckFn const_check_step) { return const_verdict_so_far.and_then(const_check_step); });
    std::printf("%s %d\n", const_verification_verdict ? "ok" : "refused", const_verification_verdict ? 0 : const_verification_verdict.error()); // refused -9809
}
```

```ts
// TypeScript: reduce keeps the first failure.
type CheckResult = { ok: true } | { ok: false; status_code: number }
const const_update_hash = (): CheckResult => ({ ok: true })
const const_verify_signature = (): CheckResult => ({ ok: false, status_code: -9809 })
const const_verification_steps: Array<() => CheckResult> = [const_update_hash, const_update_hash, const_update_hash, const_verify_signature]
const const_verification_verdict = const_verification_steps.reduce<CheckResult>((verdict_so_far, verification_step) => (verdict_so_far.ok ? verification_step() : verdict_so_far), { ok: true })
console.log(const_verification_verdict) // { ok: false, status_code: -9809 }
```

Each was run: F# on .NET SDK 10.0.403, Rust on rustc 1.99.1, C++ on GCC 16.2 (`-std=c++23 -Wall -Wextra`, no warnings), TypeScript on Node 26.13.0 (tsc 7.0.2 `--strict`), with the outputs in the comments.

| Language | Sequenced form | What a duplicated entry does | What it costs |
| --- | --- | --- | --- |
| F# | `List.fold` with `Result.bind` | runs that check twice | a list of closures; every check must share one signature |
| Rust | `try_for_each` over `[fn() -> Result<..>; N]` | runs that check twice | function pointers, so checks that capture state need `Box<dyn Fn>` |
| C++ | `ranges::fold_left` with `and_then` | runs that check twice | C++23 for both; the fold visits every entry, `and_then` just skips the call |
| TypeScript | `reduce` over a tagged result | runs that check twice | a result type you write yourself; nothing stops a check from throwing instead |

F# is the baseline because `Result.bind` is how F# sequences these steps by default; the other three opt into it. The fold does not make deleting a check visible: none of the four list types says which checks it must hold, so dropping `verify_signature` is not a type error (inferred, not compiled).

What would your handshake look like if the list of checks were the only place the order of verification was written down?

# The security angle: success has to come from the check, not from the step before it

Draws on all four tips. None of the four compilers rejected a duplicated early exit by default. goto fail returned `err`, and `err` was 0 because the previous step had succeeded. The constructive fix is to make "verified" a value that only the signature check can produce, so a stray early exit has nothing to return.

```rust
// Rust: success is a type only the signature module can build.
mod signature {
    pub struct SignatureVerified(()); // private field: no code outside this module can build one
    pub fn verify(signature_ok: bool) -> Result<SignatureVerified, i32> {
        if signature_ok { Ok(SignatureVerified(())) } else { Err(-9809) }
    }
}
use signature::SignatureVerified;
fn update_hash() -> Result<(), i32> { Ok(()) }
fn verify_server_key_exchange(signature_ok: bool) -> Result<SignatureVerified, i32> {
    update_hash()?;
    return Ok(SignatureVerified(())); // error[E0423]: cannot initialize a tuple struct which contains private fields
    signature::verify(signature_ok)
}
```

The insecure version is every function above whose success value is a plain `0`, `Ok(())` or `true` that any line can produce. The classes, in this part's classification, are [CWE-483](https://cwe.mitre.org/data/definitions/483.html), Incorrect Block Delimitation, and [CWE-561](https://cwe.mitre.org/data/definitions/561.html), Dead Code, for the mechanism, and [CWE-295](https://cwe.mitre.org/data/definitions/295.html), Improper Certificate Validation, which is the weakness NVD records for CVE-2014-1266.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | an early `return Ok(())` skips the check | warns on the statement after it; private fields stop forging a token (E0423) | build with `-D warnings`; return a token type, not `()` |
| C++ | a stray `goto` or `return` skips the check | `-Wall` warns only on misleading indentation; a private constructor plus `friend` stops forging ("is private within this context") | add clang `-Wunreachable-code`; GCC has none |
| F# | an arm catches the case first | `FS0026` for plain patterns; a `private` union case stops forging (FS1093) | guards and active patterns get no warning |
| TypeScript | an early `return` skips the check | nothing by default; TS7027 with the option set to false; a private constructor stops only `new` (TS2673) | add a `#private` field (a forged literal then fails with TS2741); `{} as SignatureVerified` still compiles |

Rust is the baseline here because its privacy rule makes the token unforgeable without any extra discipline; C++ and F# get the same guarantee from a private constructor or union case, and TypeScript's structural typing means a cast still forges one. Each row's error was measured on the toolchains named in the tips above.

Which of your verification functions return a value that any earlier line could also have returned?
