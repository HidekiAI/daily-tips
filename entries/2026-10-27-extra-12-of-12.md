**The thesis of this part: structural equality is two promises, "equal values look equal" and "a value's equality does not change while a collection holds it", and each language checks at most one of them.** A hash set relies on both: equal values must hash the same, and a key's hash must not move after insertion. Rust lets you break the first in safe code (clippy refuses it), and refuses the second. C++ lets a `double` inside a defaulted `<=>` break the ordering a `std::set` depends on. F# records give you the first for free and let a `mutable` field break the second. Effect 4 made plain JavaScript objects structurally equal, inside Effect's own collections only.

Every value below was printed by the snippet beside it, on Linux: a Debian 13.7 container with rustc 1.99.1 (clippy 0.1.99), g++ 14.2.0 and .NET SDK 10.0.402 (runtime 10.0.13, FSharp.Core 10.1.0.0), and the `node:22-trixie` image with Node 22.23.4, and effect 4.0.6 and 3.22.4.

## Rust: Eq on the id with Hash derived on every field compiles, and the HashSet kept two sessions that compare equal

*Idioms and antipatterns*

**Did you know**

`HashSet` and `HashMap` require that `a == b` implies `hash(a) == hash(b)`; the std docs call breaking it a logic error, which is safe but makes the collection's behaviour unspecified. Implementing `PartialEq` by hand on `session_id` alone, while deriving `Hash` over every field, compiled with rustc 1.99.1 and broke it: two sessions with the same id compared equal, `contains` on the refreshed one returned `false`, and inserting it gave a set of 2. `cargo clippy` refused the same code outright, "error: you are deriving `Hash` but have implemented `PartialEq` explicitly", because that lint is deny-by-default.

**Show me**

```rust
// Rust, rustc 1.99.1: Eq compares only the id, Hash is derived over every field.
use std::collections::HashSet;

#[derive(Debug, Hash)]
struct Session { session_id: u64, last_seen_ms: u64 }

impl PartialEq for Session {
    fn eq(&self, other: &Self) -> bool { self.session_id == other.session_id } // "same session"
}
impl Eq for Session {}

fn main() {
    let mut active: HashSet<Session> = HashSet::new(); // insert needs a mutable set
    active.insert(Session { session_id: 7, last_seen_ms: 1_000 });
    let refreshed = Session { session_id: 7, last_seen_ms: 2_000 };
    println!("equal: {}", Session { session_id: 7, last_seen_ms: 1_000 } == refreshed); // true
    println!("contains refreshed: {}", active.contains(&refreshed));                  // false: the hashes differ
    active.insert(refreshed);
    println!("len after inserting an equal session: {}", active.len());              // 2
}
// cargo clippy: error: you are deriving `Hash` but have implemented `PartialEq` explicitly
```

**Why it matters**

"Equal means same id" is the natural rule for an entity, and the derive for `Hash` is the natural one-word addition, so this pair appears in real code more often than either half alone. The result is a set that deduplicates sometimes, depending on which fields happen to match. Rust does protect the other promise: a key cannot be mutated through the set, because iteration hands out `&` references (writing through one is "E0596: cannot borrow `session.tenant` as mutable, as it is behind a `&` reference"), and clippy's `mutable_key_type` warns about keys with interior mutability. F# records derive both halves together, so they cannot disagree; C++ and TypeScript leave both to you.

**Chew on this**

Which of your types implement `PartialEq` by hand, and is `Hash` derived or written next to it in the same way, field for field?

**Sources**

- https://doc.rust-lang.org/std/hash/trait.Hash.html#hash-and-eq ("k1 == k2 -> hash(k1) == hash(k2)")
- https://doc.rust-lang.org/std/collections/struct.HashMap.html (the logic-error paragraph)
- https://rust-lang.github.io/rust-clippy/master/index.html#derived_hash_with_manual_eq

**Gotchas**

- A project that runs only `cargo build` and `cargo test` never sees the clippy error; it is a lint, so it fails only the clippy step.
- The mismatch is safe: no undefined behaviour, just unspecified results (duplicates, missed lookups), which is why rustc does not reject it.
- `HashMap<std::cell::Cell<u8>, u8>` drew clippy's "mutable key type" warning, the lint for the second promise, keys that can change while inside the map.

## C++: a defaulted <=> over a double is a partial ordering, so std::set treated a NaN reading as equal to another and find returned the wrong element

*Idioms and antipatterns*

**Did you know**

`auto operator<=>(const reading&) const = default;` on a struct with a `double` member returns `std::partial_ordering`, because a NaN is unordered with everything. `std::set` uses the synthesized `<` and needs a strict weak ordering; a NaN breaks it, because "neither is less" then no longer means "equivalent" in a consistent way. With `{1, 20}`, `{2, 20}` and `{3, 20}` in the set, inserting `{2, NaN}` returned `inserted=0`, pointing at `{2, 20}`: the set decided the NaN reading was already there. `find({2, NaN})` returned `{2, 20}`. g++ 14.2 compiled it with `-Wall -Wextra` and no warning.

**Show me**

```cpp
// C++20, g++ 14.2 -O2 -Wall -Wextra: no warnings.
#include <compare>
#include <cmath>
#include <cstdio>
#include <set>

struct reading {
    int sensor_id;
    double celsius;
    auto operator<=>(const reading&) const = default; // std::partial_ordering, because of the double
    bool operator==(const reading&) const = default;
};

int main() {
    std::set<reading> readings;
    for (int sensor_id : {3, 1, 2}) readings.insert(reading{sensor_id, 20.0});
    auto [nan_position, nan_inserted] = readings.insert(reading{2, std::nan("")});
    std::printf("insert {2, NaN}: inserted=%d, points at {%d, %g}\n", nan_inserted, nan_position->sensor_id, nan_position->celsius);
    // insert {2, NaN}: inserted=0, points at {2, 20}
    auto [later_position, later_inserted] = readings.insert(reading{2, 21.0});
    std::printf("insert {2, 21}: inserted=%d\n", later_inserted); // inserted=1
    for (const reading& entry : readings) std::printf("  {%d, %g}", entry.sensor_id, entry.celsius);
    // {1, 20}  {2, 20}  {2, 21}  {3, 20}
    auto found = readings.find(reading{2, std::nan("")});
    std::printf("\nfind {2, NaN} returned {%d, %g}\n", found->sensor_id, found->celsius); // {2, 20}
}
```

**Why it matters**

A missing sensor value is often stored as NaN, and a defaulted `<=>` is the C++20 way to make a type sortable in one line, so this is the default path to a broken container rather than an exotic one. The violation is undefined behaviour under the standard (the comparator's requirements are not met), and the observed symptom was the quiet kind: a lost insert and a lookup returning a different reading. The equality operator agreed with IEEE rules (`probe == probe` was `0`), while the set treated the same value as a duplicate of something else. Rust refuses the type outright: `f64` is not `Eq`, `Ord` or `Hash`, so `#[derive(PartialEq, Eq, Hash)]` on a struct holding one is "E0277: the trait bound `f64: Eq` is not satisfied". F# structural comparison handles NaN with its own rules (the 2026-10-14 entry measured them).

**Chew on this**

Which of your types with a defaulted `<=>` hold a floating-point member, and which of them are used as `std::set` or `std::map` keys, or sorted?

**Sources**

- https://en.cppreference.com/w/cpp/language/default_comparisons
- https://en.cppreference.com/w/cpp/utility/compare/partial_ordering
- https://en.cppreference.com/w/cpp/named_req/Compare (strict weak ordering)

**Verified**

g++ 14.2 (libstdc++) only. The symptom of undefined behaviour can differ by library and optimization level.

**Gotchas**

- `std::set` does not need `<=>` to return `std::weak_ordering` at compile time: the synthesized `<` from a `partial_ordering` is accepted, so the mismatch is invisible to the type system.
- `(probe <=> probe) == std::partial_ordering::unordered` was `true`: a NaN reading is unordered even with itself.
- Declaring `std::weak_ordering operator<=>` explicitly and mapping NaN to a fixed position is the usual repair; `std::strong_order` on doubles (C++20) gives a total order that places NaNs.

## F#: a record with a mutable field keeps structural equality, so changing that field after insertion made HashSet.Contains miss the same object

*Idioms and antipatterns*

**Did you know**

F# records get structural equality and hashing over all their fields, and a field marked `mutable` is still one of those fields. Insert `{ session_id = 7; tenant = "acme" }` into a `HashSet` and a `Dictionary`, set `session.tenant <- "globex"`, and the same object is lost: `active.Contains session` was `false`, `owners.ContainsKey session` was `false`, yet a scan by reference found it in the set. Adding it again made `Count` 2, the same object twice. An F# `Set` built after the change found it, because it was built from the current value.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, dotnet fsi.
open System.Collections.Generic

type Session = { session_id: int; mutable tenant: string }

let session = { session_id = 7; tenant = "acme" }
let active = HashSet<Session>()
active.Add session |> ignore
let owners = Dictionary<Session, string>()
owners[session] <- "alice"
session.tenant <- "globex"                       // mutate the key after it was inserted

printfn "HashSet contains the same object: %b" (active.Contains session)            // false
printfn "HashSet count: %d" active.Count                                            // 1
printfn "Dictionary has the same object: %b" (owners.ContainsKey session)           // false
printfn "Set.ofList then contains: %b" (Set.contains session (Set.ofList [ session ])) // true: built after the change
let found = active |> Seq.exists (fun entry -> obj.ReferenceEquals(entry, session))
printfn "but it is in there by reference: %b" found                                 // true
active.Add session |> ignore
printfn "Add it again -> count: %d" active.Count                                    // 2
```

**Why it matters**

The bucket a .NET hash collection files a key under is computed from the key's hash at insertion time, and a `mutable` record field changes that hash afterwards. Nothing in F# connects "this record has a mutable field" to "do not use it as a key": the record type still gets `[<StructuralEquality>]` by default, and the compiler does not warn. A session, a cache entry or a connection record that carries one mutable "last seen" or "tenant" field is exactly the kind of value that also ends up as a dictionary key. Rust cannot express the mutation through a set at all; C++'s `std::set` hands out `const` elements; Effect 4's plain objects have the F# problem, in a stranger form.

**Chew on this**

Which of your F# record types have a `mutable` field, and is any value of those types used as a key in a `Dictionary`, a `HashSet` or a `dict`?

**Sources**

- https://learn.microsoft.com/dotnet/fsharp/language-reference/records (structural equality, mutable fields)
- https://learn.microsoft.com/dotnet/api/system.collections.generic.hashset-1
- https://learn.microsoft.com/dotnet/api/system.object.gethashcode (a key's hash must not change while it is in a collection)

**Gotchas**

- `[<ReferenceEquality>]` on the record type makes equality and hashing by reference: the same mutation then left `Contains` `true`, at the cost of structural comparison.
- An immutable record plus copy-and-update (`{ session with tenant = "globex" }`) produces a new value, and the set keeps the old one, which is at least an honest result.
- The F# `Set` and `Map` are trees ordered by comparison, so they have the same problem if a key is mutated after insertion; the `Set.ofList` line only worked because it was built after the change.

## TypeScript: Effect 4 made plain objects structurally equal inside its own collections, so a native Set kept both copies and a mutated key was found by reference only

*New discoveries and currently popular patterns*

**Did you know**

Effect 3 needed `Data.struct` for value equality; Effect 4 removed it, and its migration guide says "plain objects are structurally equal in v4" (the same for `Data.array` and `Data.tuple`). On effect 4.0.6, `Equal.equals({ tenant: "acme", region: "eu" }, { tenant: "acme", region: "eu" })` was `true` (it was `false` on 3.22.4), and an Effect `HashSet` of the two had size 1. JavaScript's own `Set` and `Map` still compare by reference: the same two objects made a native `Set` of size 2, and `new Map([[first, "kept"]]).get(second)` was `undefined`. Mutating a plain object after inserting it into an Effect `HashSet` gave the strangest result in this part: `HashSet.has(set, session)` on the same object was still `true`, while equal fresh objects with the old *or* the new values were both `false`.

**Show me**

```javascript
// JavaScript, Node 22.23.4, effect 4.0.6.
import { Equal, HashSet, HashMap } from "effect"

const first = { tenant: "acme", region: "eu" }
const second = { tenant: "acme", region: "eu" }
console.log("Equal.equals plain objects:", Equal.equals(first, second), "| ===:", first === second) // true | false
console.log("Equal.equals plain arrays:", Equal.equals([80, 443], [80, 443]))                       // true
console.log("native Set size:", new Set([first, second]).size, "| Effect HashSet size:", HashSet.size(HashSet.make(first, second))) // 2 | 1
console.log("native Map get(second):", new Map([[first, "kept"]]).get(second), "| HashMap get(second):", JSON.stringify(HashMap.get(HashMap.make([first, "kept"]), second)))
// native Map get(second): undefined | HashMap get(second): {"_id":"Option","_tag":"Some","value":"kept"}

// Mutate a key after inserting it into an Effect HashSet.
const session = { session_id: 7, tenant: "acme" }
const active = HashSet.make(session)
session.tenant = "globex"
console.log("after mutation, HashSet.has(same object):", HashSet.has(active, session))                          // true
console.log("after mutation, HashSet.has(fresh {7, globex}):", HashSet.has(active, { session_id: 7, tenant: "globex" })) // false
console.log("after mutation, HashSet.has(fresh {7, acme}):", HashSet.has(active, { session_id: 7, tenant: "acme" }))     // false

// Opting out
const by_reference = Equal.byReference({ tenant: "acme", region: "eu" })
console.log("byReference vs equal plain object:", Equal.equals(by_reference, { tenant: "acme", region: "eu" })) // false
```

**Why it matters**

Effect 4's change makes the FP intuition ("two values with the same fields are the same value") true by default, but only for code that goes through `Equal`, `HashSet` and `HashMap`. The moment the same objects meet a native `Map`, a `Set`, an `Array.includes` or `===`, the old reference semantics are back, with no type-level difference between the two worlds. After a mutation, the key is still found by the exact object and by nothing equal to it, either before or after the change: it hashes as one value and compares as another. Rust and F# give each type one equality, decided at the type; C++ gives one per comparator; JavaScript now has two, chosen by which collection you picked.

**Chew on this**

In your Effect 4 code, which objects travel between Effect's `HashMap` and a native `Map` or `Set`, and does the code on each side know which equality it is getting?

**Sources**

- https://github.com/Effect-TS/effect/blob/main/migration/v3-to-v4.md (`Data.struct` -> "none": "plain objects are structurally equal in v4")
- https://effect.website/docs/trait/equal/
- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/Map#key_equality (SameValueZero)

**Gotchas**

- `Equal.byReference(object)` opts one object out of structural equality: compared with an equal plain object it was `false`.
- On effect 3.22.4, `Equal.equals` on two equal plain objects was `false` and a `HashSet` of them had size 2; code that relied on that (for example, deduplicating by identity) changes behaviour on upgrade without a type error.
- The mutation result suggests the hash was taken at insertion while equality is computed live (inferred from the three `has` results; Effect's source was not read here). Either way, treat keys as immutable.

# The functional angle: mutate a key after inserting it, and see which languages even let you try

_Draws on all four tips. The shape: insert a value into a set keyed by structural equality, then change one of its fields through the reference you kept._

| Language | Attempt | Result |
| --- | --- | --- |
| F# | `session.tenant <- "globex"` on a record in a `HashSet` | compiles; `Contains` on the same object is `false`, and `Add` makes a second entry |
| Rust | change a field through the set's iterator | "E0596: cannot borrow `session.tenant` as mutable, as it is behind a `&` reference"; interior mutability in a key draws clippy's `mutable_key_type` warning |
| C++ | assign a member through a `std::set` element | "no match for 'operator='": set elements are `const` |
| TypeScript (Effect 4) | `session.tenant = "globex"` on an object in an Effect `HashSet` | runs; found by the same reference, not found by any equal value |

F# is the baseline because its records make structural equality the default, so its row is the cleanest view of what the promise costs: equality computed from fields is only as stable as the fields. Rust and C++ protect the promise by refusing the mutation, at compile time; F# and TypeScript keep the mutation legal and put the consequence in the collection. That is the whole series in one table: the functional shape is safe exactly where the language makes the dangerous step impossible to write, not where the shape is merely available.

Left open: if your codebase had one rule for keys, "immutable, or compared by reference", which of your current key types would break it?

# The security angle: a revocation keyed by a mutated value misses its own entry

_Draws on the F# tip, Mode B: the tip shows a `HashSet` that cannot find a key after one of its fields changed. When the set is a revocation or deny list, "cannot find" means "not revoked"._

```fsharp
// F#, .NET 10: sessions are revoked by removing them from the active set
let active = HashSet<Session>()
active.Add session |> ignore
session.tenant <- "globex"     // a tenant move, done in place
active.Remove session          // false (measured), and Count stays 1: the session stays active
```

`active.Contains session` returned `false` after the change, so the matching `Remove` cannot succeed either, and any check that iterates the set still sees the old session. That is a failed revocation: CWE-613 (Insufficient Session Expiration), caused by a key whose hash changed after insertion.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| F# | a mutated record key cannot be removed from a revocation set | allows `mutable` fields on records used as keys | keep key types immutable, or `[<ReferenceEquality>]` |
| TypeScript (Effect 4) | removing by an equal value fails after mutation | allows it; only the same reference still matches | revoke by an immutable id, not by an object |
| Rust | `Eq`/`Hash` mismatch lets a "revoked" twin survive in the set | compiles; clippy errors | run clippy in CI; derive `Hash` and `PartialEq` together |
| C++ | a NaN-bearing key is "already present" and never stored | compiles, no warning | a total order (`std::strong_order`) for floating keys, or keep floats out of keys |

Left open: which of your revocation, deny or rate-limit collections are keyed by a whole object rather than by an immutable identifier?

# FAQ

**Does Rust's `derive(PartialEq, Hash)` together always stay consistent?**
Yes for derives: both walk the same fields in the same order. The measured problem needed one of them written by hand; clippy's deny-by-default lint exists for exactly that pair.

**Does `std::unordered_set` have the NaN problem too?**
Differently: it uses `==` and a hash, and a NaN is not equal to itself, so a NaN key can be inserted repeatedly and never found by value. That variant was not measured here; the measured one is `std::set`.

**Is an F# record with no `mutable` fields always safe as a key?**
Its own fields cannot change, but a field holding a mutable .NET object can: a record with an `int[]` field, inserted and then changed through `rule.ports[0] <- 443`, gave `Contains` `false`. Immutability has to go all the way down.

**What changed between Effect 3 and Effect 4 for equality?**
On 3.22.4 two equal plain objects were not `Equal` and needed `Data.struct`; on 4.0.6 they are `Equal`, `Data.struct` is gone, and `Equal.byReference` is the opt-out.
