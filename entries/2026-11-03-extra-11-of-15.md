# Daily Tips special, part 11 of 15: small bugs that exploded, or 21 fields where the caller supplied 20

<!-- special-nav -->
**Specials:** [<- previous: small bugs that exploded, part 10 of 15](2026-11-03-extra-10-of-15.md) | [next: small bugs that exploded, part 12 of 15 ->](2026-11-03-extra-12-of-15.md)

Not part of the rotation. Part 11 of the fifteen-part special on real incidents: the CrowdStrike Falcon sensor crash of 19 July 2024, caused by [Channel File 291](https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf). Each tip below is two pieces of code that each hold their own count of the same fields, and asks which language notices when the counts differ.

# What happened

**Bug class:** Bohrbug (it fails the same way every time its trigger appears) in this special's classification, data-triggered: CrowdStrike calls the out-of-bounds read "latent", and says the count mismatch "evaded multiple layers of build validation and testing" until content used the 21st field. The anti-pattern the tips below take from it is an index that comes from the content and is never checked against the length the code itself built.

**The story, in plain words:**

CrowdStrike's Falcon sensor is security software that runs on a customer's own Windows machines and watches for attacks. Its detection rules do not ship inside the sensor program. They arrive from the cloud as "Rapid Response Content", in files called Channel Files, and the sensor's Content Interpreter reads them. CrowdStrike says this lets it add detections "without requiring sensor code changes".

In February 2024, sensor version 7.11 added a new kind of rule, a Template Type, to catch attacks that abuse Windows named pipes and other interprocess communication. A Template Type is the blueprint for a rule: it lists the input fields, the pieces of activity data a rule may compare against. This one defined 21 input fields. The sensor code that handed the data to the interpreter supplied only 20 values.

Nobody noticed. The report says the mismatch "evaded multiple layers of build validation and testing", including the first several successful deployments in the field. The reason, "in part", was a wildcard: during testing and in the first rules, the 21st field was set to match anything, so the interpreter never had to look at its value.

On 19 July 2024, two more rules went out, and one of them checked the 21st field for a real value. The next time Windows reported an event of that kind, the sensor evaluated the rule, reached for a 21st value that was not there, read past the end of its input array, and crashed the machine.

The check that should have stopped it had the same blind spot. The Content Validator, which screens new rules before they ship, judged them on the expectation that the sensor would supply 21 inputs. The validator and the sensor disagreed about the count. The sensor also had no bounds check on that read; CrowdStrike lists that as a finding.

Microsoft estimated that the update "affected 8.5 million Windows devices, or less than one percent of all Windows machines". By 29 July, CrowdStrike reported about 99% of Windows sensors online compared to before the update. On 25 July it added a bounds check, and a check that the input array size matches the number of inputs the rules expect.

The point for the tips below: an index that came from the content was never checked against how many values the code actually built. CrowdStrike's own words follow.

From CrowdStrike's "External Technical Root Cause Analysis - Channel File 291" (dated 2024-08-06):

```text
The new IPC Template Type defined 21 input parameter fields, but the integration code that
invoked the Content Interpreter with Channel File 291's Template Instances supplied only 20
input values to match against.
```

The report says the mismatch was missed "in part" because tests and the first Template Instances used a wildcard for the 21st input. On 19 July 2024 a new Template Instance "introduced a non-wildcard matching criterion for the 21st input parameter". The Content Validator "based its assessment on the expectation that the IPC Template Type would be provided with 21 inputs", and on the sensor:

```text
The Content Interpreter expected only 20 values. Therefore, the attempt to access the 21st
value produced an out-of-bounds memory read beyond the end of the input data array and
resulted in a system crash.
```

The report lists "A runtime array bounds check was missing" as a finding, adds that this "is not an arbitrary memory write issue", and describes the fix: bounds checking in the function that retrieves input strings, plus "an additional check that the size of the input array matches the number of inputs expected by the Rapid Response Content", both added on 25 July 2024. Microsoft estimated that the update "affected 8.5 million Windows devices, or less than one percent of all Windows machines".

## Rust: a `const` generic field count turns "21 against 20" into `E0308` wherever both sides share the type, and `<[T; 21]>::try_from` is where it meets the data

*Type system deep cuts*

**Did you know**

When the field count is a const generic parameter, `Interpreter<20>` and `Interpreter<21>` are different types, so a 21-field template handed a 20-input interpreter does not compile: `E0308: mismatched types ... expected `21`, found `20``. That covers components inside one program. Content arrives as data, and the conversion from a slice to an array, `<[&str; 21]>::try_from(supplied_inputs.as_slice())`, returns `Err` when the slice holds 20. Measured on rustc 1.99.1.

**Show me**

```rust
// rustc 1.99.1, edition 2024, Debian. An illustration of the class, not CrowdStrike's code.
use std::convert::TryFrom;

const INPUT_COUNT: usize = 20; // what the integration code builds

struct Interpreter<const FIELD_COUNT: usize> { supplied_inputs: [&'static str; FIELD_COUNT] }

fn run_template(twenty_one_field_interpreter: &Interpreter<21>) -> usize { twenty_one_field_interpreter.supplied_inputs.len() }

fn main() {
    let supplied_inputs: Vec<&'static str> = vec!["pipe"; INPUT_COUNT];

    // The content's template declares 21 fields; the conversion is where the counts meet.
    let as_21_field_template: Result<[&str; 21], _> = <[&str; 21]>::try_from(supplied_inputs.as_slice());
    println!("{}", as_21_field_template.is_err()); // true

    let twenty_input_interpreter = Interpreter::<INPUT_COUNT> { supplied_inputs: <[&str; INPUT_COUNT]>::try_from(supplied_inputs.as_slice()).unwrap() };
    println!("{}", twenty_input_interpreter.supplied_inputs.len()); // 20
    // run_template(&twenty_input_interpreter); // error[E0308]: mismatched types, expected `21`, found `20`
}
```

**Why it matters**

In the CrowdStrike report, 21 and 20 lived in two components, the validator and the integration code, and nothing tied them together. A const generic ties them together at compile time for every component that names the type. The data boundary still needs a runtime check, and `try_from` is a check that cannot be skipped by accident, because its result is a `Result`.

**Chew on this**

Where in your code is the same count written in two places, a schema and a parser, or a producer and a consumer? Which of them would have to change type for a mismatch to stop compiling?

**Sources**

- https://doc.rust-lang.org/reference/items/generics.html#const-generics
- https://doc.rust-lang.org/std/primitive.array.html#impl-TryFrom%3C%26%5BT%5D%3E-for-%5BT;+N%5D

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1. The `E0308` line was measured in a separate file that passes `&Interpreter<20>` to `run_template`; it is commented out above so the snippet runs.

**Gotchas**

- Indexing past the end is a panic, not undefined behaviour: `supplied_inputs[20]` on 20 inputs stopped with "index out of bounds: the len is 20 but the index is 20" and exit code 101. Built with `-C panic=abort`, the same index ended the process (exit 134), so the check belongs before the index, for example `supplied_inputs.get(20)`, which returned `None`.
- A const generic only helps where the count is known at compile time; a count read from the content is a `usize` like any other, and `Interpreter::<{ count_from_content }>` does not compile.

## C++: `std::span::operator[]` past the end returned a garbage size at `-O2`, `-O0` aborted, and `at()` exists only from C++26

*Stdlib and ecosystem gems*

**Did you know**

`std::span` (C++20) has an unchecked `operator[]`. Reading index 20 of a 20-element span at `-O2` on GCC 16.2 did not crash; it returned a `string_view` with a garbage size (281473531918144 in one run), which is the kind of out-of-bounds read the report describes. The same build at `-O0`, or at `-O2` with `-D_GLIBCXX_ASSERTIONS`, aborted with "Assertion '__idx < size()' failed" (exit 134). A checked `span::at()` that throws `std::out_of_range` arrived only in C++26 (P2821R5): `-std=c++23` reports "has no member named 'at'". cppreference lists it in libstdc++ 14 and libc++ 18.

**Show me**

```cpp
// C++26, g++ 16.2, Debian. An illustration of the class, not CrowdStrike's code.
#include <array>
#include <cstdio>
#include <span>
#include <stdexcept>
#include <string_view>

constexpr std::size_t INPUT_COUNT = 20;

std::string_view read_input(const std::span<const std::string_view> const_supplied_inputs, const std::size_t const_field_index) {
    return const_supplied_inputs[const_field_index]; // unchecked
}

int main(const int const_argc, char**) {
    std::array<std::string_view, INPUT_COUNT> supplied_inputs{}; // mutable: fill() writes into it
    supplied_inputs.fill("pipe");
    const std::size_t const_field_index = static_cast<std::size_t>(19 + const_argc); // 20 at runtime, as if from the content
    try { std::printf("at: %zu\n", std::span<const std::string_view>(supplied_inputs).at(const_field_index).size()); }
    catch (const std::out_of_range&) { std::printf("at threw out_of_range\n"); }
    const std::string_view const_input_past_end = read_input(supplied_inputs, const_field_index);
    std::printf("operator[]: size=%zu\n", const_input_past_end.size()); // -O2: garbage; -O0: assertion, exit 134
}
```

**Why it matters**

The release build is the one that ships, and it is the one where the read is silent. A debug build of the same code would have stopped at the assertion, but only if a test ever passed index 20, and the report says the tests used a wildcard for that field.

**Chew on this**

Which of your release builds turn on `_GLIBCXX_ASSERTIONS` or libc++'s hardening mode, and which deliberately do not? Where a `span` is indexed by a number that came from outside the process, who checks it first?

**Sources**

- https://en.cppreference.com/w/cpp/container/span/operator_at
- https://en.cppreference.com/w/cpp/container/span/at
- https://en.cppreference.com/w/cpp/compiler_support/26
- https://gcc.gnu.org/onlinedocs/libstdc++/manual/using_macros.html

**Verified**

GCC 16.2.0 (`gcc:latest`, Debian); exit codes read from the program itself. The libc++ 18 support for `at()` is from the cppreference table, not tested here.

**Gotchas**

- A fixed-extent span refuses the wrong count at compile time: passing a `std::array<std::string_view, 20>` to `std::span<const std::string_view, 21>` failed with "could not convert". The dynamic-extent `std::span<const T>` above accepts any length.
- The debug-build check can be switched off too: libstdc++ defines `_GLIBCXX_ASSERTIONS` "by default when compiling with no optimization" (its manual), and `-D_GLIBCXX_NO_ASSERTIONS` prevents that, so the same `-O0` build then read past the end and exited 0. The [2026-11-03 briefing's security angle](2026-11-03.md) measured the same default for `inplace_vector`.

## F#: `Seq.zip` pairs 21 criteria with 20 inputs as 20 pairs and says nothing, while `Array.zip` refuses

*Idioms and antipatterns*

**Did you know**

Pairing each criterion with its input is the natural functional way to evaluate content, and the zip function decides what happens when the counts differ. `Seq.zip` stops at the shorter side: 21 criteria and 20 inputs give 20 pairs, so the 21st criterion is never evaluated and a check over the pairs passes. `Array.zip` and `List.zip` refuse with `ArgumentException`: "The arrays have different lengths. array1.Length = 21, array2.Length = 20". Measured on .NET SDK 10.0.403, FSharp.Core 10.1.0.0, .NET 10.0.14.

**Show me**

```fsharp
// F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14. An illustration of the class, not CrowdStrike's code.
let supplied_inputs : string array = Array.create 20 "pipe"
let template_criteria : string array = Array.init 21 (fun field_index -> if field_index = 20 then "evil-pipe" else "*")
let fn_criterion_matches_input (criterion: string, input: string) : bool = criterion = "*" || criterion = input

printfn "Seq.zip: %d pairs" (Seq.zip template_criteria supplied_inputs |> Seq.length)            // 20 pairs
printfn "Seq.zip: %b" (Seq.zip template_criteria supplied_inputs |> Seq.forall fn_criterion_matches_input)        // true: field 21 never checked
try printfn "%b" (Array.zip template_criteria supplied_inputs |> Array.forall fn_criterion_matches_input)
with failure -> printfn "Array.zip: %s" failure.Message                         // The arrays have different lengths ...
```

**Why it matters**

The two zips are the same idea with opposite answers to "what if the counts differ". In this incident the extra field crashed the reader; with `Seq.zip` the same mismatch fails the other way, and the criterion that should have been checked is skipped without a sound.

**Chew on this**

Which of your pairwise checks zip two sequences whose lengths are supposed to match, and which zip did you pick? What does that zip do when the lengths differ?

**Sources**

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-seqmodule.html#zip
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-arraymodule.html#zip

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0`, which is Ubuntu 24.04 rather than Debian.

**Gotchas**

- The `*2` functions split the same way: `Seq.forall2` over 21 and 20 returned `true`, and `Array.forall2` threw `ArgumentException`.
- Indexing is checked either way: `supplied_inputs.[20]` threw `IndexOutOfRangeException`, and `Array.tryItem 20 supplied_inputs` returned `None`, so in F# the CrowdStrike read is an exception, never a garbage value.

## TypeScript: a 20-element tuple type refuses `const_supplied_inputs[20]` written as a literal, and accepts `const_supplied_inputs[const_criterion.field_index]` from the content

*Type system deep cuts*

**Did you know**

A tuple type knows its length, so `const_supplied_inputs[20]` on a 20-element tuple is `TS2493: Tuple type 'Inputs20' of length '20' has no element at index '20'`. That check only applies to a literal index. An index read from the content, `const_supplied_inputs[const_criterion.field_index]` with `field_index: number`, is typed `string` under `--strict` with no error, and at runtime it is `undefined`: the next call on it threw "Cannot read properties of undefined (reading 'startsWith')". `noUncheckedIndexedAccess` changes the type to `string | undefined` and turns the assignment into `TS2322`. Measured on tsc 7.0.2, Node 26.13.0.

**Show me**

```ts
// TypeScript, tsc 7.0.2 --strict, Node 26.13.0. An illustration of the class, not CrowdStrike's code.
type Inputs20 = [string, string, string, string, string, string, string, string, string, string,
                 string, string, string, string, string, string, string, string, string, string]
const const_supplied_inputs: Inputs20 = ["pipe", "pipe", "pipe", "pipe", "pipe", "pipe", "pipe", "pipe", "pipe", "pipe",
                         "pipe", "pipe", "pipe", "pipe", "pipe", "pipe", "pipe", "pipe", "pipe", "pipe"]
type Criterion = { field_index: number; pattern: string }
const const_criterion: Criterion = JSON.parse('{"field_index": 20, "pattern": "evil-pipe"}')

// const const_input_at_literal_index = const_supplied_inputs[20]                            // TS2493
const const_input_at_content_index: string = const_supplied_inputs[const_criterion.field_index]   // no error; TS2322 with noUncheckedIndexedAccess
console.log(typeof const_input_at_content_index)                            // undefined
try { console.log(const_input_at_content_index.startsWith(const_criterion.pattern)) }
catch (failure) { console.log("TypeError:", (failure as Error).message) } // Cannot read properties of undefined
```

**Why it matters**

The tuple type is the closest TypeScript gets to Rust's const generic, and it protects only the indexes a programmer writes. Content-driven indexes are a `number`, and a `number` index into a tuple is typed as the union of its elements, here `string`, with `undefined` left out unless the flag puts it back.

**Chew on this**

Does any of your tsconfigs set `noUncheckedIndexedAccess`, and how many errors would it report if you turned it on today? Where does a number from parsed input reach an array index?

**Sources**

- https://www.typescriptlang.org/docs/handbook/2/objects.html#tuple-types
- https://www.typescriptlang.org/tsconfig/#noUncheckedIndexedAccess

**Verified**

Run in `node:lts-trixie` (Debian), Node 26.13.0, tsc 7.0.2 via `npx`; the emitted JavaScript printed `undefined` and the `TypeError`.

**Gotchas**

- `TS2493` fired with and without `noUncheckedIndexedAccess`; the flag adds the second error, on the content index, and does not replace the first.
- `JSON.parse` returns `any`, so `const const_criterion: Criterion = JSON.parse(...)` checks nothing about `field_index`: the annotation is an assertion that the content has the shape, not a parse.

# The functional angle: zip decides what a count mismatch means, and three of the four stop at the shorter side

Draws on the F# tip and extends it to the other three. Evaluating content as "pair every criterion with its input, then check every pair" is the functional shape, and its answer to 21 against 20 is decided by the zip, not by the check.

```rust
// Rust: Iterator::zip stops at the shorter side.
fn main() {
    let supplied_inputs: Vec<&str> = vec!["pipe"; 20];
    let template_criteria: Vec<&str> = (0..21).map(|field_index| if field_index == 20 { "evil-pipe" } else { "*" }).collect();
    let fn_criterion_matches_input = |(criterion, input): (&&str, &&str)| *criterion == "*" || criterion == input;
    let criterion_input_pair_count = template_criteria.iter().zip(supplied_inputs.iter()).count();
    let all_criteria_match = template_criteria.iter().zip(supplied_inputs.iter()).all(fn_criterion_matches_input);
    println!("{criterion_input_pair_count} pairs, all_criteria_match={all_criteria_match}"); // 20 pairs, all_criteria_match=true
}
```

```cpp
// C++23: std::views::zip is as long as the shortest range.
#include <algorithm>
#include <cstdio>
#include <ranges>
#include <string_view>
#include <vector>
int main() {
    const std::vector<std::string_view> const_supplied_inputs(20, "pipe");
    std::vector<std::string_view> template_criteria(21, "*"); // mutable: element 20 is overwritten below
    template_criteria[20] = "evil-pipe";
    const auto const_criterion_input_pairs = std::views::zip(template_criteria, const_supplied_inputs);
    const bool const_all_criteria_match = std::ranges::all_of(const_criterion_input_pairs, [](const auto& const_criterion_input_pair) {
        const auto& [const_criterion, const_input] = const_criterion_input_pair;
        return const_criterion == "*" || const_criterion == const_input;
    });
    std::printf("%zu pairs, all_criteria_match=%d\n", static_cast<std::size_t>(std::ranges::distance(const_criterion_input_pairs)), const_all_criteria_match); // 20 pairs, all_criteria_match=1
}
```

```ts
// TypeScript: no zip in the standard library; the usual map-by-index pairs the 21st criterion with undefined.
const const_supplied_inputs: string[] = Array.from({ length: 20 }, () => "pipe")
const const_template_criteria: string[] = Array.from({ length: 21 }, (_, field_index) => (field_index === 20 ? "evil-pipe" : "*"))
const const_criterion_input_pairs: Array<[string, string]> = const_template_criteria.map((criterion, field_index) => [criterion, const_supplied_inputs[field_index]])
console.log(const_criterion_input_pairs.length, const_criterion_input_pairs[20]) // 21 [ 'evil-pipe', undefined ]
console.log(const_criterion_input_pairs.every(([criterion, input]) => criterion === "*" || criterion === input)) // false
```

The F# version is the tip above. Each was run: Rust on rustc 1.99.1, C++ on GCC 16.2 (`-std=c++23 -Wall -Wextra`, no warnings), TypeScript on Node 26.13.0 (tsc 7.0.2 `--strict`, exit 0), with the outputs in the comments.

| Language | Zip | 21 criteria, 20 inputs | What it costs to refuse |
| --- | --- | --- | --- |
| F# | `Array.zip`, `List.zip` / `Seq.zip` | `ArgumentException` / 20 pairs, check passes | nothing: pick the array or list version |
| Rust | `Iterator::zip` | 20 pairs, `all_criteria_match=true` | a length comparison before the zip: `Iterator::zip` ends when either side runs out, by its documentation |
| C++ | `std::views::zip` (C++23) | 20 pairs, `all_criteria_match=1` | the same length comparison |
| TypeScript | none; `map` by index | 21 pairs, the last with `undefined`, check fails | it fails closed here only because `undefined !== "evil-pipe"`; the type `[string, string]` still lies |

F# is the baseline because it is the only one that ships both answers, a zip that truncates and a zip that refuses, side by side, so the choice is visible in the code.

Which of your zips assume equal lengths, and which line of your code would notice if they were not?

# The security angle: an index from the content is checked once, when the content is loaded, against the length the code builds

Draws on all four tips, and runs in both directions: Rust, F# and TypeScript turn the bad index into a panic, an exception or `undefined`, while C++ reads past the end; none of the four checks the content's index for you. The report's own fix was a bounds check plus a check "that the size of the input array matches the number of inputs expected". This is the missing-check sample, unchecked and then checked at load time.

```cpp
// C++23. The interpreter trusts the content's field index; the fix checks it once, when the content loads.
#include <cstdio>
#include <expected>
#include <span>
#include <string_view>
#include <vector>
struct Criterion { std::size_t field_index; std::string_view pattern; };
enum class LoadError { FieldOutOfRange };

bool criterion_matches_unchecked(const std::span<const std::string_view> const_supplied_inputs, const Criterion& const_criterion) {
    return const_criterion.pattern == "*" || const_supplied_inputs[const_criterion.field_index] == const_criterion.pattern; // no bounds check
}

std::expected<std::vector<Criterion>, LoadError> load_content(std::vector<Criterion> template_criteria, const std::size_t const_input_count) { // template_criteria is mutable: returned by move
    for (const Criterion& const_criterion : template_criteria)
        if (const_criterion.field_index >= const_input_count) return std::unexpected(LoadError::FieldOutOfRange);
    return template_criteria;
}

int main() {
    const std::vector<std::string_view> const_supplied_inputs(20, "pipe");
    const std::vector<Criterion> const_channel_file_criteria{{0, "*"}, {20, "evil-pipe"}}; // field 21 of a 20-input array
    const std::expected<std::vector<Criterion>, LoadError> const_loaded_criteria = load_content(const_channel_file_criteria, const_supplied_inputs.size());
    std::printf("load: %s\n", const_loaded_criteria ? "accepted" : "refused, field out of range"); // refused
    std::printf("unchecked: %d\n", criterion_matches_unchecked(const_supplied_inputs, const_channel_file_criteria[1]));       // reads past the end
}
```

At `-O2` on GCC 16.2 the unchecked call printed `0` and the program exited 0; with `-D_GLIBCXX_ASSERTIONS` it aborted (exit 134); built with `-O1 -fsanitize=address`, AddressSanitizer reported a heap-buffer-overflow, "READ of size 8". The load-time check refused the content before any of that. The classes: [CWE-125](https://cwe.mitre.org/data/definitions/125.html), Out-of-bounds Read, which is the report's own description, [CWE-129](https://cwe.mitre.org/data/definitions/129.html), Improper Validation of Array Index, and [CWE-1284](https://cwe.mitre.org/data/definitions/1284.html), Improper Validation of Specified Quantity in Input, for the 21 that nobody compared with the 20.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | `span[20]` reads past the end | nothing at `-O2`; `_GLIBCXX_ASSERTIONS` aborts; `at()` throws from C++26 | check the content's indexes at load against the input count |
| Rust | `supplied_inputs[20]` | panics ("the len is 20 but the index is 20"); a const generic count is `E0308` between components | check at load, so the index never panics (built with `-C panic=abort` it ended the process, exit 134) |
| F# | `supplied_inputs.[20]`, or `Seq.zip` skipping field 21 | `IndexOutOfRangeException`; `Array.zip` refuses | choose the zip that refuses; check at load |
| TypeScript | `const_supplied_inputs[field_index]` is `undefined` typed as `string` | `TS2493` for literal indexes only | `noUncheckedIndexedAccess`, and parse the content instead of annotating `JSON.parse` |

C++ is the baseline here because it is the only one of the four where the bad index reads memory instead of stopping, which is what the report describes. The remaining rows were measured in the tips above.

Which of your loaders accept content whose indexes or counts refer to something the code builds later, and where is the one place they are compared?
