## Rust: sort_by_key calls the key function once per comparison, not once per element

*Idioms and antipatterns*

**Did you know**

`slice::sort_by_key` does not memoize anything. The closure is invoked from
inside the comparator, so it runs roughly twice per comparison, which the docs
spell out as `O(m * n * log(n))` where the key function is `O(m)`. For 64
strings that is 834 calls to the key extractor, not 64. `sort_by_cached_key`
(stable since 1.34) is the same sort with a decorate-sort-undecorate pass
bolted on: `O(m * n + n * log(n))`, and "the key function is called at most
once per element".

**Show me**

```rust
use std::cell::Cell;

fn main() {
    let words: Vec<String> = (0..64).map(|i| format!("w{:03}", (i * 37) % 64)).collect();

    // Cell, not `let mut`: the closure is FnMut but we want a shared counter it
    // can bump without the closure itself taking a &mut of a local.
    let naive = Cell::new(0usize);
    let mut a = words.clone();
    a.sort_by_key(|s| { naive.set(naive.get() + 1); s.to_lowercase() });

    let cached = Cell::new(0usize);
    let mut b = words.clone();
    b.sort_by_cached_key(|s| { cached.set(cached.get() + 1); s.to_lowercase() });

    assert_eq!(a, b);                       // identical ordering, both stable
    println!("{} vs {}", naive.get(), cached.get());   // 834 vs 64
}
```

The functional form is the interesting part, because `sort_by_cached_key` *is*
the functional form, done in place:

```rust
// What sort_by_cached_key does for you: the Schwartzian transform.
// It stores (K, u32) index pairs rather than moving T around, so the extra
// allocation is sizeof(K) + 4 per element, not sizeof(T) per element.
let mut decorated: Vec<(String, String)> =
    words.into_iter().map(|w| (w.to_lowercase(), w)).collect();
decorated.sort_by(|x, y| x.0.cmp(&y.0));
let sorted: Vec<String> = decorated.into_iter().map(|(_, w)| w).collect();
```

**Why it matters**

The trap is that `sort_by_key(|s| s.to_lowercase())` reads as the clean
functional choice and is the expensive one: on that 64-element slice it
allocated 834 `String`s to sort 64. C++ has the identical hazard and no fix in
the standard library: `std::ranges::sort(v, {}, proj)` invokes the projection
from inside the comparator too, measured at 854 calls on the same input, and
there is no `ranges::sort_cached`, so you hand-roll the decorate pass. JS is
worse still, because `Array.prototype.sort(cmp)` has no key notion at all: the
same 64 strings drove 299 comparisons, and a comparator that lowercases both
sides ran 598 extractions. Rust is the only one of the three where std hands
you the cached variant, and the only one where picking the wrong sibling is a
single missing word.

**Chew on this**

Where in your code does a sort key allocate, parse, or `to_string()` inside the
comparator, and how would you find them all? What is the crossover point for
your `K` where the `(K, u32)` side table costs more than re-extracting, and
does `sort_unstable_by_key` change that answer since it has no cached variant
at all?

## C++: A deducing-this member function's address is a plain function pointer, not a pointer-to-member

*Type system deep cuts*

**Did you know**

C++23's explicit object parameter (P0847, "deducing this") does not just change
how `this` is spelled. It changes the *type* of the function. cppreference is
blunt about it: "A pointer to an explicit object member function is an ordinary
pointer to function, not a pointer to member". So `&Widget::size` stops
satisfying `std::is_member_pointer_v`, `(w.*pf)(...)` stops compiling, and
`std::mem_fn` rejects it outright. `std::invoke` keeps working for both, which
is exactly why library code that went through `std::invoke` survives the
switch and code that spelled `.*` does not. Support: C++23, GCC 14+, Clang 18+,
MSVC 19.32+.

**Show me**

```cpp
#include <cstddef>
#include <type_traits>

struct Widget {
    std::size_t n = 3;
    std::size_t size(this const Widget& self) { return self.n; }  // explicit object param
    std::size_t old_size() const { return n; }                    // implicit object param
};

// The two declarations read almost identically. Their addresses do not.
static_assert(std::is_same_v<decltype(&Widget::size),     std::size_t (*)(const Widget&)>);
static_assert(std::is_same_v<decltype(&Widget::old_size), std::size_t (Widget::*)() const>);
static_assert(!std::is_member_pointer_v<decltype(&Widget::size)>);

// So it drops straight into a C callback slot or a function-pointer table,
// with the receiver demoted to an ordinary first argument.
std::size_t (*fp)(const Widget&) = &Widget::size;
```

The functional payoff, and its price:

```cpp
// Recursive lambda with no std::function indirection and no Y-combinator.
// `self` is the closure object itself, deduced per call site.
auto fact = [](this auto self, int n) -> int { return n <= 1 ? 1 : n * self(n - 1); };
// Price: `this auto self` (by value) copies the closure on every recursive call.
// Write `this auto&& self` when the captures are not free to copy. And because
// the parameter is deduced, the function is a template, so it can never be
// virtual: clang says "an explicit object parameter cannot appear in a virtual
// function", and you cannot overload it against `f() const` either, which is
// diagnosed as "class member cannot be redeclared".
```

**Why it matters**

This is the mechanism behind replacing CRTP, const/non-const getter duplication,
and `std::function`-boxed recursive lambdas, so it will show up in your
codebase whether or not you introduce it. The migration hazard is that a
by-value `this Self self` on a class with expensive members turns every call
into a copy, silently, with no diagnostic, because the signature reads like a
receiver rather than a parameter. Rust reached the same destination from the
opposite direction: `self` has always been an ordinary first parameter there, so
`Button::size` has always coerced to `fn(&Button) -> usize`, and there is no
pointer-to-member concept to lose. See Appendix A.

**Chew on this**

If you replace a const/non-const overload pair with one `this auto&& self`
template, what happens to any code that took the member's address, and would
your build even tell you? And which of your `std::function<...>` members exist
only because a lambda needed to call itself?

- https://en.cppreference.com/w/cpp/language/member_functions#Explicit_object_parameter
- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2021/p0847r7.html
- https://en.cppreference.com/w/cpp/compiler_support/23

**Verified**

Every `static_assert` above, the recursive lambda, and all three rejection
diagnostics were compiled on Apple clang 21.0.0 with `-std=c++23 -Wall -Wextra`;
the error texts quoted are that compiler's actual output. GCC, MSVC, and

## TypeScript: A gap of 1024 turns your array into a hash table, and the type still says number[]

*Perf and memory model*

**Did you know**

V8 decides your array's data structure at write time, from the index you
happen to assign. The threshold is a named constant in the engine,
`JSObject::kMaxGap = 1024`, commented "Maximal gap that can be introduced by
adding an element beyond the current elements length". Write index 1023 into an
empty array and you get a contiguous fast store. Write 1024 and V8 swaps the
backing store for a dictionary: `[] ; a[99999] = 1` costs about 1 KiB, while
filling 0..99999 densely costs about 895 KiB. Past
`kMaxUncheckedFastElementsLength` (5000, or 500 for old-space objects) a second
rule kicks in and every expansion is density-checked, so one-in-8 indices stays
fast and one-in-64 does not, with no gap anywhere near 1024.

**Show me**

```js
// node --allow-natives-syntax --expose-gc
const kind = (a) => (%HasDictionaryElements(a) ? "DICTIONARY" : "fast") +
                    (%HasHoleyElements(a) ? "/holey" : "/packed");

const near = []; near[1023] = 1; console.log(kind(near));   // fast/holey
const over = []; over[1024] = 1; console.log(kind(over));   // DICTIONARY/packed

// The other half: holeyness is one-way and .fill does NOT undo it.
console.log(kind([0, 0, 0]));                       // fast/packed
console.log(kind(new Array(3)));                    // fast/holey
console.log(kind(new Array(3).fill(0)));            // fast/holey  <-- still holey
console.log(kind(Array.from({ length: 3 }, () => 0)));  // fast/packed  <-- the fix

// .map launders it by accident, because map builds a fresh array:
console.log(kind(new Array(3).fill(0).map((_, i) => i)));   // fast/packed
```

```ts
// The TypeScript half of the problem: these have the same type and different
// data structures. There is no annotation, no branded type, and no lint rule
// that distinguishes them, because the distinction is not in the language.
const a: number[] = new Array<number>(1000);   // holey, fast store
const b: number[] = [];                        // packed
declare function widen(xs: number[]): void;    // accepts either, cannot tell
```

**Why it matters**

Long-running Node services build arrays from ids, and an id used as an index is
the canonical way to trip this: one `bucket[userId] = x` with a sparse id space
silently converts a vector into a hash table, and nothing in the type, the
lint, or the review diff records that it happened. Rust and C++ push the same
decision into the type, where it is visible forever: you choose `Vec<T>` or
`HashMap<usize, T>`, `std::vector` or `std::map<size_t, T>`, and the compiler
holds you to it. JS makes the choice for you, per object, from a magic constant,
at the moment of a write.

The honest counterweight: on Node 22 I could not measure the classic
"holey arrays are slower" claim at all. A fully populated 1e6 holey array summed
in 0.723 ms/pass against 0.723 ms for the packed one, and `includes`, `indexOf`,
and `reduce` were within noise. The memory difference is enormous and
reproducible; the speed difference on a plain indexed loop, on this engine
version, was not there.

**Chew on this**

Which of your arrays are indexed by an external id rather than by position, and
what is the largest id your production data has actually produced? If the
representation that decides your memory profile cannot be named in the type
system, where does that invariant live instead, and what fails when someone
changes it?

**Sources**

- https://v8.dev/blog/elements-kinds
- https://github.com/v8/v8/blob/main/src/objects/js-objects.h
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/fill

**Verified**

All elements-kind and memory figures were measured on this host with Node
22.17.1 (`--allow-natives-syntax --expose-gc`), and the "holey forever" claim is
also stated outright by the V8 blog: "Once the array is marked as holey, it
remains holey forever, even if all its elements are present later!". The
`kMaxGap` and `kMaxUncheckedFastElementsLength` values are read from V8's `main`
branch, which is newer than the V8 inside Node 22; the 1024 and 5000 boundaries
were reproduced empirically here, but treat the constants as implementation
detail, not contract. The `%Has...Elements` intrinsics are debug-only and absent
without `--allow-natives-syntax`.

# The functional angle: all four can sort by a derived key, and exactly one decided that means caching it

Drawn from today's Rust tip, which is this problem, and today's C++ tip, whose
projection-based `ranges::sort` carries the identical hazard. F# is here as the
control: the language where this shape is the idiom, to settle whether the cost
belongs to functional style or to the languages charging for it.

The shape is "order these by something derived from each element". Every one of
the four can say it. What differs is whether saying it implies that the derived
value is computed once.

```fsharp
// F# 8, FSharp.Core 8.0.0.0, .NET 8.0.8. Every *By function caches the key,
// including the one that mutates in place. Counted, not assumed:
let words = [ for i in 0 .. 63 -> sprintf "w%03d" ((i * 37) % 64) ]
words |> List.sortBy (fun s -> s.ToLowerInvariant())            // 64 calls
words |> List.toArray |> Array.sortInPlaceBy (fun s -> s.ToLowerInvariant())  // 64
// Drop to a raw comparator and the caching goes with it, because there is no
// longer a key for the library to hold on to:
words |> List.sortWith (fun a b -> compare (a.ToLowerInvariant()) (b.ToLowerInvariant()))  // 900
```

The other three, same input, same key, counted the same way: Rust's
`sort_by_key` 834 and `sort_by_cached_key` 64, C++'s
`ranges::sort(v, {}, proj)` 854, and JS `sort(cmp)` 598.

| Language | The functional form | Key calls, n=64 | What it costs |
| --- | --- | --- | --- |
| F# | `List.sortBy`, `Array.sortInPlaceBy` | 64 | Nothing at the call site. The library caches whether or not you allocate a new list. |
| Rust | `sort_by_cached_key` | 64 | A `(K, u32)` side table per element, and you must know the longer name exists. |
| Rust | `sort_by_key` | 834 | The shorter, more obvious name is the expensive one. |
| C++ | `ranges::sort(v, {}, proj)` | 854 | Not expressible. The projection is a call, not a value, and std has no cached form to reach for. |
| TypeScript | `sort(cmp)` | 598 | Not expressible. There is no key parameter at all, so the comparator extracts twice per comparison. |

So the cost is not the price of functional style. It is a library policy
decision, made once per language, that you inherit. F# decided a key is a value
worth keeping; C++ decided a projection is a call to be repeated; Rust decided
both and made the cheap one longer to type; JS never had the concept.

The mutability angle points the other way from the usual expectation.
`Array.sortInPlaceBy` is the impure, mutating F# function, and it still caches,
so in F# you do not trade purity for the cheap key. Rust does not make you
trade either, but it makes you know a name. The one place today where purity did
buy something is in the TypeScript tip: `.map` builds a fresh array and
therefore silently repairs a holey elements kind, while `.fill` mutates in place
and leaves it holey forever. The version that constructs a new value is the one
that could afford to be correct, and nobody wrote that down as the reason.

If a `*By` function in your codebase takes a closure, do you know whether it
holds the result or re-runs it? And when a language gives you both, as Rust
does, which one did the API author make easier to type?

# FAQ

**Does `sort_unstable_by_key` have a cached variant?**
No. Only the stable `sort_by_cached_key` exists, because the cached version
needs the side table anyway and the stable sort already allocates. If you need
unstable plus an expensive key, hand-roll the decorate pass.

**Is `sort_by_cached_key` always the right default then?**
No, and the docs say why: it allocates `(K, u32)` per element. For a cheap key
such as a field access or an integer cast, `sort_by_key` wins, since you are
paying an allocation to avoid a load.

**Does deducing `this` work on lambdas' `operator()` in all the same ways?**
Yes for the recursion case, which is its most common use. The restrictions are
the same ones: the parameter makes it a template, so no `virtual` (irrelevant
for a lambda) and no overload against a plain `operator()`.

**Will `-Wall` warn me if a `this Self self` copies?**
Not on Apple clang 21 with `-Wall -Wextra`. There is no diagnostic for an
expensive-to-copy explicit object parameter, which is the whole reason it is
worth knowing by hand.

**Does `structuredClone` or `JSON.parse` give me packed arrays?**
`JSON.parse` of a dense JSON array does. But this is engine behavior, not spec,
so verify with `%HasHoleyElements` on your Node version rather than trusting a
blog post, including this one.

**Can I force an array back to packed?**
Not in place through `.fill`. Build a new one: `Array.from(old)`, `old.slice()`,
or `[...old]`. Setting `length = 0` and re-pushing also came back packed on
Node 22, but that depends on the store being discarded and is not something to
rely on.

# Appendix A: does Rust have an equivalent to deducing `this`?

Not part of the tip rotation. Written 2026-09-18 to back today's C++ tip.
Snippets were compiled and run with rustc 1.95.0 and Apple clang 21.0.0 on
aarch64-apple-darwin; nothing below is recalled compiler output.

## A.1 Why the C++ feature name misleads a Rust reader

"Deducing this" sounds like a new kind of receiver. To a Rust reader it is the
*removal* of a special case that Rust never had. In Rust, `self` is written in
the parameter list from the start, so there is no implicit object argument to
deduce, and the receiver is an ordinary first parameter for every purpose
including taking the function's address:

```rust
trait Widget: Sized {
    fn size(&self) -> usize;
    // `Self` is the implementing type, statically. No CRTP, no virtual.
    fn describe(&self) -> String {
        format!("{} of size {}", std::any::type_name::<Self>(), self.size())
    }
}
struct Button;
impl Widget for Button { fn size(&self) -> usize { 7 } }

// This is the line C++ needed P0847 to be able to write:
let f: fn(&Button) -> usize = Button::size;
assert_eq!(f(&Button), 7);
// type_name is prefixed with the crate name, so this printed
// "selfty::Button of size 7" from a file named selfty.rs.
println!("{}", Button.describe());
```

So the C++23 fact from today's tip, that `&Widget::size` is a plain function
pointer, is not a surprise in Rust. It is the only thing that was ever true.

## A.2 What each language can actually express

| Capability | C++23 (`this` param) | Rust | Expressible? |
| --- | --- | --- | --- |
| Receiver is an ordinary parameter | `void f(this Widget&)` | `fn f(&self)` | Both. Rust since 1.0. |
| Address is a plain function pointer | Yes, P0847 changed it | Yes, `Button::size as fn(&Button) -> usize` | Both. |
| Deduce the receiver's *derived* type | `this auto&& self` deduces `Derived` | No inheritance, so nothing to deduce; a trait default method gets `Self` = impl type | Different mechanisms, same job. |
| Receiver by value vs by reference, chosen per call | `this Self self` vs `this Self&& self` | `fn f(self)` vs `fn f(&self)`, fixed at declaration | C++ can deduce it, Rust cannot. |
| Receiver is a smart pointer | Not expressible; you take `std::shared_ptr<T>` as a normal parameter and lose method syntax | `fn spawn(self: Arc<Self>)`, stable for `Box`, `Rc`, `Arc`, `Pin` | Rust only. |
| Arbitrary user smart-pointer receiver | Not expressible | Unstable (`arbitrary_self_types`) | Neither, today. |
| Dynamic dispatch on the receiver | Ordinary `virtual`, but never with `this` param | `&dyn Widget`, but the method must be object-safe | Both, with disjoint restrictions. |
| Recursive lambda without boxing | `[](this auto self, ...)` since C++23 | No. A closure cannot name itself; you need a `fn` item or an explicit fix-point | C++ only, and this is the real win. |

The last two rows are the interesting asymmetry. C++23 bought recursive lambdas
and per-call receiver deduction; Rust has had smart-pointer receivers since 1.0
and still cannot write a self-referential closure.

## A.3 The trap that has no Rust analogue

```cpp
struct Big { std::array<char, 4096> buf; 
    // Reads like a receiver. Is a by-value parameter. Copies 4 KiB per call.
    std::size_t len(this Big self) { return self.buf.size(); }
};
```

Rust cannot produce this accidentally, because `fn len(self)` *consumes*: the
equivalent two-call program is rejected with `error[E0382]: use of moved value`,
and the note names the cause, "`Big::len` takes ownership of the receiver
`self`". The C++ version compiles clean under `-Wall -Wextra`, runs, and is
correct, just 4 KiB of copy per call heavier. That is the shape worth
remembering: Rust turns the mistake into an error, C++ turns it into a cost.

## A.4 Summary

| Question | Answer |
| --- | --- |
| Does Rust have deducing `this`? | It has the destination, not the feature. `self` was always explicit. |
| What did C++23 actually gain? | Receiver-type deduction (CRTP replacement), const/non-const dedup, and recursive lambdas. |
| What does Rust still have that C++ cannot express? | Smart-pointer receivers with method-call syntax. |
| What does C++ have that Rust cannot? | A closure that can call itself without an explicit fix-point. |
| Which mistake is cheaper to make? | C++ by a mile: a by-value explicit object parameter is a silent per-call copy. |
