# Daily Tips: 2026-11-17

## Rust: Rust 1.100 put DropGuard in std, and dismiss is the commit: it hands the value back and frees the closure, which mem::forget leaks

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.100.0, released 2026-11-12, stabilized `core::mem::DropGuard<T, F> where F: FnOnce(T)` (also reachable as `std::mem::DropGuard`). It is the scope guard people used to pull in from a crate: it owns a value, derefs to it, and when dropped hands the value to the closure by value. `DropGuard::dismiss(guard)` is the other exit: it returns the value, never runs the closure, and drops whatever the closure captured. It is an associated function, not a method, so `guard.dismiss()` is E0599.

**Show me**

```rust
// Rust 1.100.0, edition 2024. Shape borrowed from C++ scope guards and Go defer,
// with one difference neither has: the cleanup receives the value it guards.
use std::mem::DropGuard;

fn apply(staged: Vec<String>, fail_at: Option<usize>) -> Result<Vec<String>, String> {
    // The guard owns the rows. Any exit that is not the commit below rolls back.
    let mut mut_pending = DropGuard::new(staged, |left_over: Vec<String>| {
        println!("  rollback ran, {} staged rows discarded", left_over.len());
    });
    mut_pending.push("audit row".to_string()); // DerefMut reaches the Vec inside
    if let Some(step) = fail_at {
        return Err(format!("failed at step {step}")); // guard drops here: rollback
    }
    Ok(DropGuard::dismiss(mut_pending)) // commit: the Vec comes back, closure never runs
    // mut_pending.dismiss() would be E0599: "this is an associated function, not a method"
}

fn main() {
    // prints: ok path: Ok(2)
    println!("ok path: {:?}", apply(vec!["a".into()], None).map(|rows| rows.len()));
    // prints the rollback line, then: err path: Err("failed at step 2")
    println!("err path: {:?}", apply(vec!["a".into()], Some(2)).map(|rows| rows.len()));
}
```

**Why it matters**

Commit-or-rollback, restore-the-old-config and return-to-the-pool are all the same shape, and before 1.100 a hand-written `Drop` had to hold an `Option<T>` so `drop(&mut self)` could `take()` the value out. Here the closure takes `T` by value, and the commit point is one visible call. The C++ standard has no scope guard, so most codebases hand-roll an RAII class; `std::experimental::scope_exit` from the Library Fundamentals TS v3 compiled and ran on GCC 16.2, but it sits outside the standard. Go `defer` runs at function end rather than scope end (a `defer` inside a block ran after the code that followed the block, on Go 1.27.4) and has no cancel, so a commit needs a flag the deferred call checks. F# writes the same thing as an `IDisposable` object expression under `use`, which cannot give the value back.

**Chew on this**

Which of your `Drop` impls exist only to carry an `Option<T>` for `take()`, and would turning them into a `DropGuard` make the commit easier to see in review, or bury it inside a closure nobody reads? Which of your release profiles set `panic = "abort"`, and what are you relying on a guard to undo there?

**Sources**

- https://doc.rust-lang.org/std/mem/struct.DropGuard.html
- https://doc.rust-lang.org/releases.html (Version 1.100.0, 2026-11-12, "Stabilized APIs": `core::mem::DropGuard`)

**Verified**

rustc 1.100.0 in the `rust:1.100` Docker image (Debian). The `rust:1` tag served 1.99.1, which has no `DropGuard`, on the morning of 2026-11-17 and 1.100.0 by the afternoon (observed, not reproducible later), so pin the version. The Go and C++ `scope_exit` remarks were run (Go 1.27.4, GCC 16.2.0); the F# remark rests on documentation and was not run.

**Gotchas**

- `let _ = DropGuard::new(1, |_| println!("ran"))` runs the closure on that same line, and rustc 1.100.0 prints no warning: the lint that catches `let _ = mutex.lock()` knows only the std lock guards.
- `std::mem::forget(guard)` also skips the closure, but leaks what the closure captured. An `Rc` captured by the closure stayed at `strong_count` 2 after `forget`, and went back to 1 after `DropGuard::dismiss`.
- The closure runs during unwinding (the guard printed inside `catch_unwind`), but not on `std::process::exit(0)`, and not at all when built with `-C panic=abort`: that process exited with status 134 and the guard printed nothing.

## C++: std::vector{source} copies and std::vector{source, source} nests, so a generic wrap() that adds an optional layer adds none when T is already an optional

*Type system deep cuts*

**Did you know**

Since C++17 (with the P0702R1 fix), braced class template argument deduction with exactly one argument whose type is a specialization of the same template skips the initializer-list phase and picks the copy deduction candidate. So `std::vector const_copied{const_source}` is a `vector<int>` copy, `std::vector const_nested{const_source, const_source}` is a `vector<vector<int>>`, and `std::vector const_iterators{const_source.begin(), const_source.end()}` is a vector of two iterators. Generic code inherits the rule: `std::optional{value}` inside a template adds a layer for every `T` except an optional, where it quietly copies instead.

**Show me**

```cpp
// C++17 rule, measured with -std=c++20 on GCC 16.2.0 and Debian clang 19.1.7.
#include <optional>
#include <vector>

template <class T>
auto wrap(const T const_value) { return std::optional{const_value}; } // meant: add one layer

template <class T>
auto wrap_explicit(const T const_value) { return std::optional<T>{const_value}; } // always adds one

int main() {
    const std::vector<int> const_source{1, 2, 3};
    const std::vector const_copied{const_source};               // vector<int>, size 3 (copy)
    const std::vector const_nested{const_source, const_source}; // vector<vector<int>>, size 2
    const std::vector const_iterators{const_source.begin(), const_source.end()}; // vector of 2 iterators
    const std::vector const_ranged(const_source.begin(), const_source.end());    // parentheses: vector<int>, size 3

    const std::optional<int> const_missing{};                   // "looked up, nothing there"
    const auto const_wrapped = wrap(const_missing);             // optional<int>, has_value() == false
    const auto const_wrapped_explicit = wrap_explicit(const_missing); // optional<optional<int>>, has_value() == true
    return const_wrapped.has_value() == const_wrapped_explicit.has_value(); // 0: they disagree
}
```

**Why it matters**

`optional<optional<V>>` is the usual way to tell "never looked up" from "looked up, not found" in a negative cache. Build the outer layer with `std::optional{lookup_result}` in a template and every not-found result arrives as never-looked-up, so the cache never answers a miss and every repeat goes back to the backend. Rust and F# cannot do this: `Some(found)` and `Some found` always add exactly one layer, and `Option<Option<V>>` is just a type. TypeScript collapses instead of nesting, and does it in the type itself: with `T` set to `number | undefined`, `T | undefined` is one `undefined`, so there is no second layer to lose in the first place.

**Chew on this**

Where does your generic code write `Template{value}` meaning "wrap this", and does any of its tests instantiate it with a `T` that is already a specialization of that same template?

**Sources**

- https://en.cppreference.com/w/cpp/language/class_template_argument_deduction ("the first phase of list-initialization (considering initializer-list constructors) is omitted if the initializer list consists of a single expression of type ... `U`, where `U` is a specialization of `C`")

**Verified**

GCC 16.2.0 (`gcc:latest`) and Debian clang 19.1.7 on Debian 13.7, both with `-std=c++20 -Wall -Wextra`. MSVC not checked. The P0702R1 paper number comes from the cppreference page. The Rust, F# and TypeScript comparisons were not run today.

**Gotchas**

- Neither compiler warns about any line in the snippet with `-Wall -Wextra`, including the vector of two iterators.
- Parentheses change the answer: `std::vector ranged(first, last)` uses the iterator deduction guide and holds the 3 ints, while the braced form holds 2 iterators.
- `std::tuple boxed{pair_like}` with a `std::tuple<int, int>` argument is a copy (`tuple_size` 2), not a one-element tuple holding a tuple.
- Naming the template argument turns the rule off: `std::optional<T>{value}` with `T = std::optional<int>` nests, and `has_value()` is true.

- [2026-10-05](2026-10-05.md) - C++, "C++26 added span's initializer_list constructor". The same braces-versus-parentheses split, on `std::span`.

## F#: F#'s lock takes a System.Threading.Lock and uses Monitor on it, so it never excludes C#'s lock on the same object

*Stdlib and ecosystem gems*

**Did you know**

.NET 9 added `System.Threading.Lock`, and C# 13 compiles `lock (gate)` on an expression of exactly that type to `gate.EnterScope()`. F#'s `lock` is `Monitor.Enter(lockObject, &lockTaken)` for any reference type, so `lock gate` monitor-locks the `Lock` as if it were a plain `obj`. Inside it, `gate.IsHeldByCurrentThread` is `false`, and F# `lock gate` got in after 55 ms while another thread held the same `Lock` through `EnterScope` until 500 ms. C# warns about that exact conversion (CS9216); F# 10 compiles it without a word.

**Show me**

```fsharp
// F# 10 (SDK 10.0.404), FSharp.Core 10.1.0.0, .NET 10.0.15
open System.Diagnostics
open System.Threading

let gate = Lock() // shared with a C# library that does: lock (gate) { ... }

// What F# lock compiles to: Monitor.Enter on the Lock, treated as a plain object
let held_by_fsharp_lock = lock gate (fun () -> gate.IsHeldByCurrentThread)

// What C# 13 lock (gate) compiles to, written out by hand
let fn_with_gate (action: unit -> unit) : unit =
    let scope = gate.EnterScope() // Lock.Scope is a ref struct: use is FS0193 here
    try action () finally scope.Dispose()

let clock = Stopwatch.StartNew()
let holder = Thread(fun () -> fn_with_gate (fun () -> Thread.Sleep 500))
holder.Start()
Thread.Sleep 50
let entered_at_ms = lock gate (fun () -> clock.ElapsedMilliseconds)
holder.Join()

printfn "held_by_fsharp_lock = %b" held_by_fsharp_lock // false
printfn "entered_at_ms = %d" entered_at_ms // 55 here, not 500
```

**Why it matters**

Since .NET 9 and C# 13 the C# docs recommend locking "a dedicated object instance of the System.Threading.Lock type", so a `private readonly object _sync` turns into a `Lock`, and that change compiles cleanly on both sides of a mixed solution. Every F# caller that wraps work in `lock library.SyncRoot` keeps compiling too, because `lock` accepts any reference type, and from then on the two sides hold two different locks and run the critical section at the same time. Rust cannot express the mismatch: `Mutex<T>` owns the data, so the only way in is the guard of that one mutex. C++ can, but it takes two distinct `std::mutex` objects guarding one structure, which at least looks wrong in review; here it is one object.

**Chew on this**

Which C# types that your F# code locks on switched their sync field to `Lock` during a .NET 9 or 10 upgrade, and what test of yours would ever see two threads inside at once?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/lock ("When the compiler knows that `x` is of the type System.Threading.Lock, it's precisely equivalent to" `using (x.EnterScope())`)
- https://learn.microsoft.com/en-us/dotnet/api/system.threading.lock ("the type of the expression must be precisely `System.Threading.Lock`")
- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/prim-types.fs (`let inline lock (lockObject : 'T when 'T : not struct) ...` calls `System.Threading.Monitor.Enter(lockObject, &lockTaken)`)

**Verified**

Run in `mcr.microsoft.com/dotnet/sdk:10.0`, which is Ubuntu 24.04.5, not Debian. The C# comparison was built and run in the same image. The Rust and C++ comparisons were not run today.

**Gotchas**

- `use scope = gate.EnterScope()` does not compile. Inside a function or a `let` body it is FS0193, "Type constraint mismatch. The type 'Lock.Scope' is not compatible with type 'System.IDisposable'" (with `open System.Threading`; without it the message spells `System.Threading.Lock.Scope`). Written directly at script level it is FS0431 instead, "A byref typed value would be stored here". It is a ref struct with a `Dispose` method, so F# needs the explicit `try ... finally scope.Dispose()`.
- `Monitor.IsEntered gate` is `true` inside F# `lock gate`, so a diagnostic that asks `Monitor` reports the object as locked while the `Lock` itself is free.
- C# has the same hole when the type is lost: `object boxed = gate; lock (boxed)` also gave `IsHeldByCurrentThread = False`, but the build printed warning CS9216, "will use likely unintended monitor-based locking".
- Elapsed times vary between runs (50 ms and 55 ms here); what does not vary is that the F# side entered long before the 500 ms hold ended.

## TypeScript: return promise inside try leaves the try before the promise settles, so catch never sees the rejection and finally closes the connection first

*Idioms and antipatterns*

**Did you know**

In an `async` function, `return fetch_config()` inside `try` hands the caller a promise that has not settled yet, and the `try` block is already over. A rejection then skips the `catch` and goes straight to the caller, and a `finally` runs before the work it was meant to wrap. `return await fetch_config()` settles inside the `try`, so both blocks behave as written. tsc 7.0.2 with `--strict` accepts both forms without a diagnostic.

**Show me**

```ts
// TypeScript 7.0.2 --strict, run on Node v26.13.1
const const_fn_sleep_ms = (delay_ms: number): Promise<void> => new Promise((resolve) => setTimeout(resolve, delay_ms))

async function fetch_config(): Promise<string> {
    await const_fn_sleep_ms(10)
    throw new Error("config service down")
}

async function load_returning_promise(): Promise<string> {
    try {
        return fetch_config() // leaves the try unsettled: the caller sees the rejection
    } catch {
        return "default config" // never runs
    }
}

const const_events: string[] = []

async function write_rows(): Promise<number> {
    await const_fn_sleep_ms(50)
    const_events.push("rows written")
    return 3
}

async function with_connection(): Promise<number> {
    const_events.push("connection opened")
    try {
        return write_rows() // `return await write_rows()` keeps the finally after the work
    } finally {
        const_events.push("connection closed") // runs before the rows are written
    }
}

async function main(): Promise<void> {
    await load_returning_promise().catch((error: Error) => console.log("rejected:", error.message))
    console.log("rows:", await with_connection())
    console.log(const_events.join(" -> ")) // connection opened -> connection closed -> rows written
}

void main()
```

**Why it matters**

The `catch` case at least fails loudly: the caller gets "config service down" instead of the default. The `finally` case does not fail at all. The connection is closed, the lock released or the tracing span ended, and then the work runs against something already torn down, while the function still returns `3`. Rust has no such gap because a future is a type: returning `write_rows()` unawaited from a function that returns `u32` does not compile, and a `?` inside the block only sees an awaited value. JavaScript promises flatten instead, so `Promise<Promise<number>>` never exists and the type checker has nothing to object to. F# `task { }` is closer to Rust: the result leaves through `return!`, which awaits, and the same function written with `return! write_rows ()` inside `try ... finally` logged `connection opened -> rows written -> connection closed`.

**Chew on this**

Which of your `async` functions have a `finally` that releases something, and is every `return` inside its `try` an `await`? Where you use a pool or lock helper that takes a callback, does it await the callback or just return it?

**Sources**

- https://github.com/typescript-eslint/typescript-eslint/blob/main/packages/eslint-plugin/docs/rules/return-await.mdx (a promise returned in a `try` "should be awaited in order to trigger subsequent `catch` or `finally` blocks as expected"; default option `in-try-catch`)

**Verified**

tsc 7.0.2 and Node v26.13.1 in the `node:lts` Docker image (Debian). The F# order ran with `dotnet fsi` in the .NET 10 SDK image (Ubuntu 24.04). The Rust comparison was reasoned from the type rules and not run; the typescript-eslint rule was read in its docs and not run.

**Gotchas**

- The finally-first order still returns the result: `rows: 3` printed after "connection closed", so a test that checks only the return value passes.
- The check lives in typescript-eslint, not in tsc: `@typescript-eslint/return-await`, whose default `in-try-catch` requires the `await` exactly where this tip needs it.

**Related**

- [2026-11-02](2026-11-02-extra-5-of-15.md) - TypeScript, "One thread does not mean one update at a time, because every await is a window". The other direction: an `await` that opens a window, here a missing one that closes the `try` too early.

# The functional angle: cleanup is a function of the guarded value, and only Rust's DropGuard lets the commit hand that value back

Draws on the Rust, F# and TypeScript tips. The C++ tip is about deduction, not cleanup, and stays out.

Each language here wraps a body in "acquire, run, release", and the release is a function. The difference is what that function is given and who decides whether it runs.

```rust
// Rust 1.100.0: the release takes the value; the commit takes the guard and returns the value
let pending = DropGuard::new(staged_rows, |left_over: Vec<String>| roll_back(left_over));
let committed_rows: Vec<String> = DropGuard::dismiss(pending);
```

```fsharp
// F# 10: lock is a higher-order function over any reference type
let new_balance = lock account_gate (fun () -> withdraw account amount)
```

```ts
// TypeScript 7.0.2: the release belongs to the try block, not to the promise
async function with_connection(): Promise<number> {
    try { return await write_rows() } finally { close_connection() }
}
```

| Language | Functional form | What it costs |
| --- | --- | --- |
| F# | `lock gate (fun () -> ...)`, and `use` for `IDisposable` | `lock` is generic over `'T : not struct`, so the wrong primitive type-checks: on a `System.Threading.Lock` it took a `Monitor` (measured). `use` refuses the ref struct `Lock.Scope` outright (FS0193 in a function, FS0431 at script level). |
| Rust | `DropGuard::new(value, FnOnce(T))` plus `DropGuard::dismiss` | Each guard has its own closure type, so a struct that stores one needs a type parameter or a `Box<dyn FnOnce(T)>` (not measured). The cleanup cannot run twice, because `FnOnce` consumes it. |
| C++ | none in the standard; `std::experimental::scope_exit` from the Library Fundamentals TS v3, or a hand-written RAII class | `scope_exit` compiled and ran on GCC 16.2.0, but it is outside the standard, so portable code still writes and reviews its own guard. |
| TypeScript | `try { return await body() } finally { release() }` | The `await` is load-bearing and invisible to the type checker: without it the release ran before the body finished (`connection opened -> connection closed -> rows written`, measured). |

The immutability note runs in Rust's favour here: the tip's `let mut mut_pending` exists only because the snippet pushes a row through `DerefMut`. The commit itself takes the guard by value, so no binding has to change for the decision "keep it" to be made. The TypeScript form decides by control flow, which is exactly where its failure came from; the F# failure came from `lock` accepting any reference type.

The thread to leave hanging: if the release function could see the value and the outcome, what would your own TypeScript `finally` blocks and Rust `Drop` impls do differently on the error path than on the success path?

# The security angle: two guards that compile, pass review and guard nothing

Draws on the F# and TypeScript tips, plus the Rust guard's abort case. Direction: what the language does not prevent. The control for this class is Rust's `Mutex<T>`, where the data is reachable only through the guard of one specific lock, so "locked the wrong thing" cannot be written.

**F#: a lock that excludes nobody** (CWE-667, improper locking; CWE-362, race condition). This looks like every other `lock` in the codebase:

```fsharp
// F# 10, illustrative and not run (the mechanism is measured in the F# tip).
// account.SyncRoot is a System.Threading.Lock owned by a C# library,
// whose own methods do: lock (SyncRoot) { ... }
let withdraw (account: Account) (amount: decimal) =
    lock account.SyncRoot (fun () ->
        // WRONG: this is Monitor.Enter on the Lock object, so the C# side,
        // which uses Lock.EnterScope, can be inside its own critical section now
        if account.Balance >= amount then account.Balance <- account.Balance - amount)
```

The fix is to enter it the way C# does, `let scope = account.SyncRoot.EnterScope()` with `try ... finally scope.Dispose()`, or to keep the shared sync object an `obj` until every caller is ported.

**TypeScript: a release before the work** (CWE-672, operation on a resource after expiration or release):

```ts
// TypeScript 7.0.2, illustrative and not run (the order is measured in the TypeScript tip).
// Reads like "always close the audit log".
async function append_audit(entry: AuditEntry): Promise<void> {
    const const_audit_log = await open_audit_log()
    try {
        return const_audit_log.write(entry) // WRONG: write runs after close; its failure skips any catch
    } finally {
        await const_audit_log.close()
    }
}
```

Whether the late write throws, is dropped, or lands in a file that was meant to be sealed depends on the library, which is the problem: the code no longer says.

**Rust: a guard that never runs.** `DropGuard` is unwind-based. Under `-C panic=abort` the process exited with status 134 and the guard printed nothing, and `std::process::exit` skipped it too (closest class CWE-459, incomplete cleanup). A guard that wipes a key buffer or rolls back a half-written file is a convenience on the unwind path, not a guarantee.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| F# | `lock` on a `Lock` takes a `Monitor` and excludes nothing that used `EnterScope` | Nothing: no warning (measured) | Grep for `lock` on any field whose C# type is `Lock`, and enter it with `EnterScope` |
| C# | `lock` on a `Lock` converted to `object` does the same | Warning CS9216 (measured) | Make CS9216 an error |
| TypeScript | A `finally` runs before the returned promise settles | Nothing in tsc 7.0.2 `--strict` (measured) | Run `@typescript-eslint/return-await` in CI |
| Rust | A guard is skipped by `panic = "abort"`, `process::exit` and `mem::forget`, and `let _ =` runs it on the same line, before the work it should wrap | Runs it on every unwind and every normal scope exit | Do not make a guard the only thing between a crash and a leaked secret or a half-written state |

The thread to leave hanging: which of your locks is shared with code in another language, and who checked that both sides mean the same primitive?

# FAQ

**Does a Rust `DropGuard` run its closure where it is moved to, not where it was created?**

Yes. In Rust 1.100.0, a guard passed by value into a `consume` function ran its closure when `consume` returned, so "guard ran" printed before "back in main". The cleanup belongs to whoever owns the guard last, not to the scope that created it.

**Is F#'s `lock` wrong for every object?**

No. On a plain `obj` it is the same `Monitor` lock it has always been, so two F# callers on the same `Lock` object take the same `Monitor` (ordinary `Monitor` behaviour, not measured today). The mismatch appears only when the other side enters the `Lock` through `EnterScope`, which is what C# 13 `lock (gate)` compiles to when `gate` is typed `Lock`.

**Is C++'s `std::make_optional` a safe way to add the layer?**

Yes. In C++, `std::make_optional(const_missing)` returned an `optional<optional<int>>` with `has_value()` true on GCC 16.2.0, because it is a function template that decays its argument, not a deduction from braces.

**Does TypeScript's `await using` close the gap that `finally` leaves?**

No. A TypeScript `await using` resource whose dispose logs "connection closed", in a function that ends with `return write_rows()`, logged `connection opened -> connection closed -> rows written` on Node v26.13.1. Disposal runs when the block exits, and returning the promise exits it before the work is done, exactly as with `finally`.
