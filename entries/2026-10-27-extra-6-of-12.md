**The thesis of this part: each language has one word in a signature that people read as "no side effects", and none of the four words means that.** Rust's `const fn` means "can run at compile time". C++'s `[[gnu::pure]]` is a promise the optimizer trusts and nobody checks. F#'s `seq<string>` means "computed later", and later can mean "every time" or "after the file was closed". Effect's `Effect<A>` describes an effect, but the arguments you pass to build it run immediately. Every row below compiled clean; the difference shows up only when you count how often the effect ran.

Every value below was printed by the snippet beside it, on Linux: a Debian 13.7 container with rustc 1.99.1, g++ 14.2.0 and .NET SDK 10.0.402 (runtime 10.0.13, FSharp.Core 10.1.0.0, Release build), the `gcc:16` image with g++ 16.2.0, and the `node:22-trixie` image with Node 22.23.4, tsc 7.0.2 and effect 4.0.6.

| Language | The word read as "pure" | What actually ran |
| --- | --- | --- |

| TypeScript | `Effect<A>` | `Effect.succeed(issue_token())` issued its token once, at construction |

## Rust: const fn means "can run at compile time", not "has no effects", and at runtime one changed a static mut with no warning

*Type system deep cuts*

**Did you know**

Rust 1.83 lifted two `const fn` limits: mutable references are allowed "inside the computation of a constant", and const contexts may now reference statics. So a `const fn record_request(request_count: &mut u32)` both computed a constant (`START` is 2) and, called at runtime, incremented a live counter. A `const fn` that writes a `static mut` inside `unsafe` compiled with no warning in edition 2021 or 2024 and returned 1, then 2. The compile-time check still exists, but only on the compile-time path: using that function in a `const` is "E0080: constant accesses mutable global memory", and a `println!` inside any `const fn` is E0015.

**Show me**

```rust
// rustc 1.99.1, edition 2024. &mut and references to statics in const fn: Rust 1.83.
static mut AUDIT_EVENTS: u32 = 0;

// const fn: callable at compile time. Not "pure": it may mutate through &mut...
const fn record_request(request_count: &mut u32) -> u32 {
    *request_count += 1;
    *request_count
}

// ...and, at runtime, through a static mut.
const fn bump_audit() -> u32 {
    unsafe { AUDIT_EVENTS += 1; AUDIT_EVENTS } // no warning in edition 2021 or 2024
}

const START: u32 = {
    let mut counter = 0; // a mutable local inside the constant's own computation
    record_request(&mut counter);
    record_request(&mut counter)
};

fn main() {
    let mut live_counter: u32 = 0; // record_request needs a &mut
    println!("{START} {} {}", record_request(&mut live_counter), record_request(&mut live_counter)); // 2 1 2
    println!("{} {}", bump_audit(), bump_audit()); // 1 2: a const fn changing global state
    // const AT_COMPILE_TIME: u32 = bump_audit(); // E0080: constant accesses mutable global memory
    // A println! inside a const fn is E0015: cannot call non-const function `std::io::_print`
}
```

**Why it matters**

`const fn` is often read as Rust's purity marker because it forbids I/O and allocation. What it guarantees is narrower: the function *can* be evaluated at compile time, and when it is, the evaluator rejects anything it cannot replay. At runtime a `const fn` is an ordinary function, and since 1.83 its signature can take `&mut`, so "const" in the name says nothing about whether calling it twice gives the same answer. C++'s `constexpr` has the same split between "may run at compile time" and "is pure". F# and TypeScript have no such keyword at all.

**Chew on this**

**Sources**

- https://blog.rust-lang.org/2024/11/28/Rust-1.83.0/ ("mutable references and pointers can only be used inside the computation of a constant")
- https://doc.rust-lang.org/reference/const_eval.html
- https://doc.rust-lang.org/error_codes/E0015.html

**Gotchas**

- The 1.83 release notes add that "reading the value of a mutable or interior mutable static is still not permitted in const contexts", which is the E0080 above. The rule constrains the compile-time evaluation, not the function.
- `Cell::set` is not callable from a `const fn` yet ("E0658: cannot call conditionally-const method `Cell::<u32>::set`"), so interior mutability through `&Cell` is the one route still closed; `&mut` and `static mut` are open.
- The `unsafe` block is the only marker on `bump_audit`; the signature `const fn bump_audit() -> u32` looks like a constant getter.

## C++: [[gnu::pure]] is a promise the optimizer trusts and nobody checks, so a function that lies ran 3 times at -O0 and once at -O2

*Perf and memory model*

**Did you know**

GCC's `pure` attribute is for "functions that have no observable effects on the state of the program other than to return a value", and `const` is stricter: the return value is also "not affected by changes to the observable state". The compiler uses the promise to merge repeated calls with the same arguments, and it never checks it. A `[[gnu::pure]]` function that increments an audit counter, called three times in one expression, incremented it 3 times at `-O0` and once at `-O1` and `-O2`, on g++ 14.2 and g++ 16.2, with no warning under `-Wall -Wextra`. With `[[gnu::const]]` the count was 1 even at `-O0`.

**Show me**

```cpp
// C++20 with GNU attributes, g++ 14.2 and 16.2, -Wall -Wextra: no warnings.
#include <cstdio>

int audit_calls = 0;

// Declared pure: "no observable effects ... other than to return a value". It writes anyway.
[[gnu::pure]] [[gnu::noinline]] int quota_for(int tenant_id) {
    ++audit_calls; // the lie: a side effect the attribute promises does not exist
    return tenant_id * 100;
}

int main() {
    int total = quota_for(7) + quota_for(7) + quota_for(7); // three calls in the source
    std::printf("total=%d audit_calls=%d\n", total, audit_calls);
    // -O0: total=2100 audit_calls=3
    // -O2: total=2100 audit_calls=1
    // with [[gnu::const]] instead: audit_calls=1 at -O0 as well
}
```

**Why it matters**

The attribute is a performance tool, and it works: a lookup marked `pure` stops being recomputed in a loop. The cost of lying is that the program's behaviour depends on the optimization level, which is the worst kind of difference between a debug build and production: the debug build is the one where it works. Rust has no attribute that lets you promise purity to the optimizer; `const fn` is checked by the compile-time evaluator instead. F# and TypeScript have no equivalent promise to break.

**Chew on this**

Which functions in your code carry `pure` or `const` attributes (often through a macro such as `__attribute_pure__` in a header you did not write), and has anyone added logging, metrics or caching to one of them since?

**Sources**

- https://gcc.gnu.org/onlinedocs/gcc/Common-Attributes.html (the `pure` and `const` function attributes)
- https://clang.llvm.org/docs/AttributeReference.html#pure
- https://en.cppreference.com/w/cpp/language/attributes

**Verified**

g++ 14.2 and 16.2 only; Clang, which also accepts `[[gnu::pure]]`, was not run.

**Gotchas**

- `-O0` is not a safe harbour: with `[[gnu::const]]` the three calls already became one at `-O0`.
- `[[gnu::noinline]]` is what exposes it: with that attribute removed, `-O2` printed `audit_calls=3`, because the inlined body showed the optimizer the write. So the bug also appears and disappears with inlining decisions.
- The return value was right in every build (`total=2100`); only the side effect varied, so a test that checks results alone passes everywhere.

## F#: a function returning seq<string> runs its effect later, so `use` closed the file before the first line was read

*Idioms and antipatterns*

**Did you know**

`seq<'T>` in a return type says "computed on enumeration", and that moves every effect inside it to the caller's loop. A function that opens a `StreamReader` with `use` and returns a `Seq.unfold` over it disposes the reader when the *function* returns, so enumerating the result threw `ObjectDisposedException: Cannot read from a closed TextReader`. Moving the `use` inside `seq { }` disposes it when *enumeration* ends, and fixes that, but now the file is opened on every enumeration: the same sequence read the file twice, and after the file was deleted, enumerating it again threw `FileNotFoundException`. Both functions have the same signature, `string -> seq<string>`.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, Release build.
open System.IO

let config_path = Path.Combine(Path.GetTempPath(), "ports.txt")
File.WriteAllLines(config_path, [| "80"; "443"; "8080" |])

// Looks like "open, read lines, close". The use disposes when the FUNCTION returns.
let read_ports_eager_dispose (path: string) : seq<string> =
    use reader = new StreamReader(path)
    Seq.unfold (fun (open_reader: StreamReader) ->
        match open_reader.ReadLine() with
        | null -> None
        | line -> Some(line, open_reader)) reader

// The use inside the seq builder disposes when ENUMERATION ends.
let read_ports_in_seq (path: string) : seq<string> =
    seq {
        use reader = new StreamReader(path)
        let mutable line = reader.ReadLine() // a loop cursor inside the builder
        while not (isNull line) do
            yield line
            line <- reader.ReadLine()
    }

try List.ofSeq (read_ports_eager_dispose config_path) |> ignore
with failure -> printfn "%s" (failure.GetType().Name)    // ObjectDisposedException

let ports = read_ports_in_seq config_path
printfn "%A" (List.ofSeq ports)                           // ["80"; "443"; "8080"]
printfn "%A" (List.ofSeq ports)                           // ["80"; "443"; "8080"]: the file was read again
File.Delete config_path
try List.ofSeq ports |> ignore
with failure -> printfn "%s" (failure.GetType().Name)    // FileNotFoundException
```

**Why it matters**

F# has no effect type, so `seq` is where effects most often hide in an otherwise functional codebase: a query, a file read, an HTTP page fetch, all returned as a sequence that looks like data. The first version fails loudly. The second one works and quietly repeats the effect on every enumeration, whether that is a `Seq.length` followed by a `Seq.iter` or a retry. Rust's iterators borrow their source, so returning an iterator that borrows a reader owned by the function is a borrow error rather than a runtime one ("E0597: `reader` does not live long enough" on rustc 1.99.1). TypeScript generators have the same "runs on iteration" behaviour, and part 7 of this special measures it.

**Chew on this**

Which of your functions return `seq<'T>` over a resource, and do their callers enumerate the result once, or once per `Seq.length`, `Seq.isEmpty` and `Seq.iter` they call on it?

**Sources**

- https://learn.microsoft.com/dotnet/fsharp/language-reference/sequences
- https://learn.microsoft.com/dotnet/fsharp/language-reference/resource-management-the-use-keyword
- https://learn.microsoft.com/dotnet/api/system.objectdisposedexception

**Gotchas**

- `Seq.cache` (or `List.ofSeq` once, at the boundary) turns "every enumeration" into "the first enumeration"; it does not move the effect back to the call.
- The eager-dispose bug only fires if the caller enumerates; code that returns the sequence and never reads it never sees an error.
- A `let mutable` inside `seq { }` compiles and works, and drew no FS3180 here; the builder compiles the body into an enumerator object (from the F# docs on sequence expressions; the generated code was not inspected).

## TypeScript: Effect.succeed(issue_token()) evaluates its argument once, at construction, so every run returns the same token

*Idioms and antipatterns*

**Did you know**

An `Effect` is a description that runs when you run it, but JavaScript evaluates function arguments before the call, Effect's constructors included. `Effect.succeed(issue_token())` called `issue_token` while the program was being built (the counter was 1 before anything ran), and both runs returned `tok-1`. `Effect.sync(() => issue_token())` defers the call into the effect, so each run issued a new token (`tok-2`, `tok-3`). A throwing argument throws at construction, outside Effect's error channel entirely: `Effect.succeed(parse_quota("ten"))` threw a plain `Error: bad quota ten` from a `try` around the constructor. `Effect.try(() => parse_quota("ten"))` keeps it typed, as a `Fail(UnknownError: ...)`.

**Show me**

```typescript
// TypeScript, effect 4.0.6, tsc 7.0.2 --strict, Node 22.23.4.
import { Effect } from "effect"

let token_requests = 0
const issue_token = (): string => { token_requests += 1; return `tok-${token_requests}` }

const eager = Effect.succeed(issue_token())      // the argument is evaluated here, once
const deferred = Effect.sync(() => issue_token()) // the thunk runs on every run
console.log(token_requests)                        // 1: before anything ran
console.log(Effect.runSync(eager), Effect.runSync(eager))       // tok-1 tok-1
console.log(Effect.runSync(deferred), Effect.runSync(deferred)) // tok-2 tok-3

// A throwing argument throws while the program is being built, outside any Effect error channel.
const parse_quota = (text: string): number => {
    const parsed = Number.parseInt(text, 10)
    return Number.isNaN(parsed) ? (() => { throw new Error(`bad quota ${text}`) })() : parsed
}
try { Effect.succeed(parse_quota("ten")) } catch (thrown) { console.log(String(thrown)) } // Error: bad quota ten
console.log(String(Effect.runSyncExit(Effect.try(() => parse_quota("ten")))).slice(0, 60))
// Failure(Cause([Fail(UnknownError: An error occurred in Effec...
```

**Why it matters**

The type of `eager` and `deferred` is the same, `Effect<string>`, and the difference is invisible at every use site: `Effect.retry`, `Effect.repeat` and every rerun of a stored program replay the first one's result. `Effect.succeed` is right for a value you already have; anything that reads a clock, a counter, a random source or the network belongs in `Effect.sync`, `Effect.try` or `Effect.promise`. Rust has the same argument-evaluation order, but no lazy effect type in std to be surprised by; F#'s `async { }` puts its whole body inside the deferral, so there is no argument to evaluate early (a `task { }` starts at once instead; see [2026-10-06](2026-10-06.md)).

**Chew on this**

Search your Effect code for `Effect.succeed(` followed by a function call: which of those calls read something that changes between runs?

**Sources**

- https://effect.website/docs/getting-started/creating-effects/
- https://github.com/Effect-TS/effect/blob/main/MIGRATION.md
- https://tc39.es/ecma262/#sec-runtime-semantics-argumentlistevaluation

**Gotchas**

- `Effect.fail(build_error())` has the same shape: two runs failed with the identical `Error` object (`===` was `true` on 3.22.4 and 4.0.6), built once at construction.
- Effect 4 names the wrapped exception `UnknownError` (the exit printed `Fail(UnknownError: An error occurred in Effect.try ...)`); Effect 3.22.4 tagged it `UnknownException`, so matching on the old tag stops working after the upgrade.
- `Effect.sync` assumes the thunk does not throw: a throwing thunk gave `Failure(Cause([Die(Error: boom)]))`, a defect, not a typed failure (also `Die` on 3.22.4). Use `Effect.try` when the call can fail.

# The functional angle: count how often the effect ran, because none of the four signatures will tell you

_Draws on all four tips. The shape: something that looks like a value or a pure function, with an effect inside, evaluated more than once._

| Language | Construct | Effect count when used twice | What the signature says |
| --- | --- | --- | --- |
| F# | `seq { use reader ... }` read twice | the file was opened 2 times | `seq<string>`: nothing about when or how often |
| Rust | `const fn bump_audit()` called twice at runtime | 2 writes to a `static mut` | `const fn () -> u32`: nothing about `static mut` |
| C++ | `[[gnu::pure]]` function called 3 times | 3 at `-O0`, 1 at `-O2` | an attribute the compiler trusts and does not check |
| TypeScript | `Effect.succeed(issue_token())` run twice | 1, at construction | `Effect<string>`, identical to the `Effect.sync` version that ran 2 |

F# is the baseline because it has no effect marker at all, so its row shows the default: the effect runs whenever the value is consumed, and only reading the body tells you how often. The other three each added a word that looks like an answer, and in every case the measured count disagreed with what the word suggests to a reader.

Left open: if your team had to annotate effects in one of these four languages tomorrow, would you trust the annotation more than a test that counts calls?

# The security angle: the effect that ran fewer times than written

_Draws on the C++ and TypeScript tips, Mode B: both tips show an effect running fewer times than the source suggests. When that effect is an audit record or a nonce, "fewer" is a security defect. Direction: neither language prevents it._

```cpp
// C++, g++ 14.2 -O2: a permission check that also writes the audit trail
[[gnu::pure]] [[gnu::noinline]] int quota_for(int tenant_id) { ++audit_calls; return tenant_id * 100; }
int total = quota_for(7) + quota_for(7) + quota_for(7); // -O0: audit_calls=3; -O2: audit_calls=1
```

```typescript
// TypeScript, effect 4.0.6: a per-request nonce built with succeed
const with_nonce = Effect.succeed(randomUUID())
Effect.runSync(with_nonce) === Effect.runSync(with_nonce) // true: the same nonce for every run
const with_nonce_per_run = Effect.sync(() => randomUUID())
Effect.runSync(with_nonce_per_run) === Effect.runSync(with_nonce_per_run) // false
```

The first is CWE-778 (Insufficient Logging): two of three audited calls left no record in the optimized build, which is the build that runs in production. The second is CWE-323 (Reusing a Nonce, Key Pair in Encryption) when the value is a nonce, or a replayable token when it is an idempotency or CSRF value: every retry and every rerun of the stored program reused the first value.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | an audited call marked `pure` is merged away (CWE-778) | trusts the attribute; no warning | never put logging, metrics or counters behind `pure`/`const` |
| TypeScript | a nonce or token built with `Effect.succeed` is reused (CWE-323) | evaluates arguments eagerly, as JavaScript always does | build anything random or time-based with `Effect.sync` |
| Rust | a `const fn` can write global state at runtime | allows it inside `unsafe` | treat `const fn` as "compile-time capable", not as an audit-free guarantee |
| F# | a `seq` over a resource repeats its effect per enumeration | runs it whenever enumerated | materialize once (`List.ofSeq`) when the effect must happen exactly once |

Left open: which of your security-relevant effects (audit writes, nonce generation, rate-limit increments) would you notice running fewer times than written?

# FAQ

**Does GCC warn when a function marked `[[gnu::pure]]` writes a global?**
No: g++ 14.2 and 16.2 printed no warning with `-Wall -Wextra` for the snippet above. The attribute is taken on trust.

**Does building at `-O0` make the GNU purity attributes harmless?**
Not for `[[gnu::const]]`: the three calls were merged into one at `-O0` too. Only `[[gnu::pure]]` kept all three at `-O0`.

**Is `Effect.succeed` wrong to use?**
No. It is the constructor for a value that already exists, and the measured behaviour is exactly that: the value is captured once. The trap is passing it a call that reads changing state.

**Does `seq { use ... }` keep the file open between enumerations?**
No. It opens the file when enumeration starts and disposes it when enumeration ends, which is why the second enumeration read the file again and the third failed with `FileNotFoundException` after the file was deleted.
