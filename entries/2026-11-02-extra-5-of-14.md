# Daily Tips special, part 5 of 14: small bugs that exploded, or a second message that arrived while the first was still being handled

<!-- special-nav -->
**Specials:** [<- previous: small bugs that exploded, part 4 of 14](2026-11-02-extra-4-of-14.md) | [next: small bugs that exploded, part 6 of 14 ->](2026-11-02-extra-6-of-14.md)

Not part of the rotation. Part 5 of the fourteen-part special on real incidents: the [AT&T long-distance network slowdown](https://catless.ncl.ac.uk/Risks/9/63/) of 1990-01-15. Each tip below is a second event that arrives while an update is half done, and what the language does about it.

# What happened

**Bug class:** Bohrbug (it fails the same way every time its trigger appears) in this special's classification: AT&T describes it as reproducible once two call attempts arrive inside the vulnerable window. The anti-pattern is state that is inconsistent for a moment, reachable by the next message.

**The story, in plain words:**

On Monday, 15 January 1990, at about 2:30 p.m. Eastern time, one of AT&T's 4ESS long-distance switches in New York City noticed a minor hardware problem and ran its normal fault-recovery routine. That meant pausing new calls for four to six seconds, a routine maintenance step that AT&T says is normally invisible to callers.

Messages went out automatically to the switches connected to it, asking them not to send it new calls for the moment, and each of them made a note in its programs that New York was out of service. When New York was ready again, it sent out its first call attempts, and the other switches started updating that note.

Each switch has a processor, called a Direct Link Node (DLN), that holds this status and connects the switch to the signalling network that carries the call messages (CCS7). Updating the note left it vulnerable for several seconds because of a software flaw. If two call attempts from New York arrived within one hundredth of a second of each other in that window, some of its data was damaged, and it was taken out of service to restart.

The DLN is duplicated, so its mate took over. But a second pair of closely spaced messages from New York hit the mate in its own vulnerable window, and it went out of service too, leaving the switch cut off from the signalling network. The failure cascaded as the same thing happened in other switches. It kept going because the failures were random and the traffic kept supplying the triggers.

The twist is where the flaw came from. It was in every 4ESS switch in the network, put there by a software update in mid-December, intended to make the switches reach a backup signalling network faster when the main one had problems. AT&T says the software had been rigorously tested in laboratories, and that "the unique combination of events that led to this problem couldn't be predicted". The usual recovery procedures did not work: "we knew very early on we had a problem we'd never seen before".

The network was stabilized by suspending signalling traffic on backup links, to cut the load of messages, and at 11:30 p.m. Eastern the last link was cleared. On Tuesday, AT&T took the update out of the switches and went back to the previous program, then found the flaw and reproduced it in the laboratory. AT&T notes that Monday's calling volume was not unusual, less than a normal Monday in fact.

The point for the tips below: for a moment the data was half updated, the next message arrived in that moment, and the backup, running the same code, fell into the same gap. AT&T's own words follow.

From AT&T's "Technical background on AT&T's network slowdown, January 15, 1990", reprinted in RISKS Digest 9.63 from TELECOM Digest (28 January 1990; dashes normalized to ASCII):

```text
As the result of a software flaw, this DLN processor was left vulnerable to
disruption for several seconds. During this vulnerable time, the receipt of two
call attempts from the New York switch -- within an interval of 1/100th of a
second -- caused some data to become damaged. The DLN processor was then taken
out of service to be reinitialized.
```

```text
Since the DLN processor is duplicated, its mate took over the traffic load.
However, a second couplet of closely spaced new call messages from the New York
4ESS switch hit the mate processor during the vulnerable period, causing it to
be removed from service and temporarily isolating the switch from the CCS7
signaling network.
```

The flaw "was inadvertently introduced into all the 4ESS switches in the AT&T network as part of a mid-December software update", so every switch carried it and the effect "cascaded through the network". The often-told version, a C `break` inside an `if` inside a `switch` that left the `switch` instead of the `if`, comes from a forwarded email from a DEC address dated 19 January 1990, quoted secondhand in [RISKS Digest 9.69](https://catless.ncl.ac.uk/Risks/9/69/). AT&T's report does not mention it, so this part does not rest on it.

## Rust: `RefCell` turns a second update during the window into a refusal or a panic, never into damaged data

*Stdlib and ecosystem gems*

**Did you know**

`RefCell<T>` tracks its one mutable borrow at runtime, so a second `borrow_mut` while the first is still alive is refused: `try_borrow_mut` returns `Err`, and `borrow_mut` panics with "RefCell already borrowed". That is the AT&T window turned into an error: the second call attempt cannot reach the half-updated map at all. The cost is that a re-entrant path the design did not foresee now crashes the handler instead of corrupting it. Measured on rustc 1.99.1.

**Show me**

```rust
// rustc 1.99.1, Debian.
use std::cell::RefCell;
use std::collections::HashMap;

fn main() {
    let switch_status_by_name: RefCell<HashMap<&str, bool>> = RefCell::new(HashMap::new());

    let mut mut_update_window_borrow = switch_status_by_name.borrow_mut(); // the update window opens
    mut_update_window_borrow.insert("new-york", true);

    // A second call attempt arrives while the window is open.
    println!("{}", switch_status_by_name.try_borrow_mut().is_err()); // true: refused, nothing damaged
    // switch_status_by_name.borrow_mut() here panics with "RefCell already borrowed".

    drop(mut_update_window_borrow); // the window closes
    println!("{}", switch_status_by_name.try_borrow_mut().is_ok()); // true
}
```

**Why it matters**

A refused update is a design decision you can see and handle: queue the message, drop it, or retry. Damaged data is a decision nobody made. The trade is availability: a panic in a handler is a crash of that handler, which in a duplicated pair can repeat the AT&T outcome (inferred: two halves running the same code fail the same way).

**Chew on this**

Which of your `RefCell` or `Mutex` borrows are held across a call that can deliver another message? If a borrow failure meant "try again in a moment", where would you put the retry?

**Sources**

- https://doc.rust-lang.org/std/cell/struct.RefCell.html#method.try_borrow_mut
- https://doc.rust-lang.org/std/sync/struct.Mutex.html#method.lock

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1.

**Gotchas**

- `std::sync::Mutex` is not re-entrant either: a second `try_lock` from the thread that already holds it returned `WouldBlock`. The docs say a second `lock` from the same thread "will not return" and "might panic or deadlock".
- The refusal happens only while the first borrow is alive: after `drop(mut_update_window_borrow)`, `try_borrow_mut` succeeded. A borrow that ends before an `await` or a callback no longer protects what happens there.

## C++: `std::recursive_mutex` lets the second call attempt in while the invariant is broken, and the state looks right again afterwards

*Idioms and antipatterns*

**Did you know**

A `std::recursive_mutex` lets the thread that holds it lock it again, which is the usual fix for "my handler calls itself and deadlocks". The second entry then runs in the middle of the first one's update: in the measured program the nested call saw `size 2 count 1`, an invariant that never holds between updates. When the outer call finished, the state read `size 2 count 2`, so any check made after the update passes. Measured on Debian clang 19.1.7 and GCC 16.2 in Docker (C++20); Apple clang 21 gave the same output.

**Show me**

```cpp
// C++20, Debian clang 19.1.7 and GCC 16.2 (Docker): same output.
#include <cstdio>
#include <mutex>
#include <string>
#include <vector>

struct LinkStatus {
    std::vector<std::string> in_service_switch_names;
    std::size_t in_service_count = 0;  // invariant: in_service_count == in_service_switch_names.size()
};
std::recursive_mutex link_status_lock;  // mutable: locking changes it
LinkStatus shared_link_status;  // mutable: updated in place

void on_call_attempt(const std::string& const_switch_name, const bool const_should_deliver_nested) {
    const std::lock_guard<std::recursive_mutex> const_link_status_guard(link_status_lock);  // the same thread may enter again
    shared_link_status.in_service_switch_names.push_back(const_switch_name);                   // invariant broken here...
    if (const_should_deliver_nested) on_call_attempt(const_switch_name, false);    // ...when the second attempt arrives
    shared_link_status.in_service_count += 1;                                          // ...and restored here
    std::printf("%s: size %zu count %zu\n", const_should_deliver_nested ? "outer" : "inner",
                shared_link_status.in_service_switch_names.size(), shared_link_status.in_service_count);
}

int main() { on_call_attempt("new-york", true); }
// inner: size 2 count 1   <- the nested call ran on a broken invariant
// outer: size 2 count 2   <- and the state looks right again afterwards
```

**Why it matters**

A recursive mutex protects against other threads, not against your own call stack, and re-entry from your own stack is exactly the second message arriving mid-update. Rust's `RefCell` and `Mutex` refuse the same re-entry, as the Rust tip measured. In C++ the choice between deadlock (`std::mutex`) and a silent broken invariant (`std::recursive_mutex`) is the programmer's, and neither one reports it.

**Chew on this**

Where in your code is a `recursive_mutex` hiding a call path that re-enters an update? If each such path had to be written as "queue this until the current update is done", how many would you find you never meant to allow?

**Sources**

- https://en.cppreference.com/w/cpp/thread/recursive_mutex
- https://en.cppreference.com/w/cpp/thread/mutex/lock

**Verified**

Compiled with `-std=c++20 -Wall -Wextra` on Debian clang 19.1.7 (`debian-clang:trixie`, libstdc++) and GCC 16.2.0 (`gcc:latest`), both in Docker; no warnings, same output. Additionally checked on macOS (Apple clang 21.0.0, arm64): same output.

**Gotchas**

- Neither compiler warned about the re-entrant call: with `-Wall -Wextra` both compiled the program silently.
- The final state is consistent, so an assertion placed after `on_call_attempt` returns would pass; only an assertion inside the nested call sees `count 1` against `size 2`.

## F#: a `Dictionary` written from 8 threads threw only after losing most of 1,600,008 entries, and not always the same exception

*Stdlib and ecosystem gems*

**Did you know**

.NET's `Dictionary` is not safe for concurrent writes, and on .NET 10 it detects some of them: 8 threads writing 200,001 keys each threw in all 34 runs, but not always the same exception. 21 runs ended with `InvalidOperationException`, whose message says "A concurrent update was performed on this collection and corrupted its state"; 8 with an `ArgumentException` ("Destination array was not long enough" or "Source array was not long enough"), and 5 with an `IndexOutOfRangeException`. In the ten runs whose count was recorded, it held between 24 and 200,341 entries, out of 1,600,008. A `ConcurrentDictionary` given the same writes held all 1,600,008. Measured with SDK 10.0.403 on .NET 10.0.14.

**Show me**

```fsharp
// SDK 10.0.403 (F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14).
open System.Collections.Concurrent
open System.Collections.Generic
open System.Threading.Tasks

let fn_fill_from_8_threads (write_switch_key: int -> unit) : string =
    let writer_tasks =
        [| for writer_index in 0 .. 7 ->
            Task.Run(fun () -> for key_offset in 0 .. 200000 do write_switch_key (writer_index * 1000000 + key_offset)) |]
    try Task.WaitAll writer_tasks; "no exception"
    with wait_failure -> wait_failure.InnerException.GetType().Name

let switch_status_by_key = Dictionary<int, bool>()
let fill_exception_name_text = fn_fill_from_8_threads (fun switch_key -> switch_status_by_key.[switch_key] <- true)
printfn "Dictionary: %s, Count %d of %d" fill_exception_name_text switch_status_by_key.Count (8 * 200001)
// Dictionary: InvalidOperationException, Count 882 of 1600008 (other runs: ArgumentException or IndexOutOfRangeException, Count 24 to 200341)

let concurrent_status_by_key = ConcurrentDictionary<int, bool>()
printfn "ConcurrentDictionary: %s, Count %d" (fn_fill_from_8_threads (fun switch_key -> concurrent_status_by_key.[switch_key] <- true)) concurrent_status_by_key.Count
// ConcurrentDictionary: no exception, Count 1600008
```

**Why it matters**

The exception is a detector, not a guard: it fires after the damage, which is the AT&T order of events ("caused some data to become damaged. The DLN processor was then taken out of service"). F#'s own answer to a shared status map is usually to stop sharing it: a `MailboxProcessor` given 1,000 posts processed them one at a time in a separate run, so the second message waits instead of arriving mid-update. The C++ tip above showed the same window opened by one thread re-entering itself.

**Chew on this**

Which of your F# services share a mutable .NET collection between threads because it looked read-mostly? If that collection threw tomorrow, would the exception tell you which write lost which entry?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.dictionary-2#thread-safety
- https://learn.microsoft.com/en-us/dotnet/api/system.collections.concurrent.concurrentdictionary-2

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0` (Ubuntu 24.04, not Debian), 34 runs of the `Dictionary` case; every run threw, and both the exception type and the surviving count varied.

**Gotchas**

- The count left behind is not stable: from 24 to 200,341 in the ten runs whose count was recorded, so a test that checks for "some loss" or a particular number is checking luck.
- The exception type is not stable either: a `catch` for `InvalidOperationException` alone missed 13 of 34 runs, which threw `ArgumentException` or `IndexOutOfRangeException`.
- The documentation leaves concurrent writes to your own synchronization; the exception is a check the runtime happened to make here, so code must not rely on it firing.

## TypeScript: one thread does not mean one update at a time, because every `await` is a window the next message walks into

*Idioms and antipatterns*

**Did you know**

Node runs your code on one thread, but an `async` function gives the event loop back at every `await`, so another call can run in the middle of an update. A status update that pushes a switch, awaits, then increments a count left `size 1 count 0` visible to a second call attempt 1 ms later, inside the 10 ms window. Chaining updates through one promise serializes them: each one finished on a consistent state (`size 1 count 1`, then `size 2 count 2`). Measured on Node 26.13.0.

**Show me**

```ts
// TypeScript, Node 26.13.0 (LTS, strips types natively), tsc 7.0.2 --strict.
const const_link_status: { in_service_switch_names: string[]; in_service_count: number } = { in_service_switch_names: [], in_service_count: 0 } // invariant: in_service_count === in_service_switch_names.length
const const_fn_sleep_ms = (delay_ms: number): Promise<void> => new Promise((resolve) => setTimeout(resolve, delay_ms))

const const_fn_on_call_attempt = async (switch_name: string): Promise<void> => {
    const_link_status.in_service_switch_names.push(switch_name) // invariant broken...
    await const_fn_sleep_ms(10)               // the update window: the event loop runs other work here
    const_link_status.in_service_count += 1                   // ...restored
}

const const_first_call_attempt_update = const_fn_on_call_attempt("new-york-1")
await const_fn_sleep_ms(1) // a second call attempt within 1/100 s
console.log(const_link_status.in_service_switch_names.length, const_link_status.in_service_count) // 1 0: the second arrival sees a half-done update
await Promise.all([const_first_call_attempt_update, const_fn_on_call_attempt("new-york-2")])
console.log(const_link_status.in_service_switch_names.length, const_link_status.in_service_count) // 2 2
```

**Why it matters**

"JavaScript has no data races" is true of memory and false of invariants: the window between two statements of one async function is as open as AT&T's few seconds. Rust's `RefCell` refuses the second entry and F#'s `MailboxProcessor` queues it, as measured above; TypeScript does neither unless you build the queue.

**Chew on this**

Which of your async handlers update two related pieces of state with an `await` between them? If you moved every such `await` to the end of the handler, which ones could not move?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/await
- https://nodejs.org/en/learn/asynchronous-work/event-loop-timers-and-nexttick

**Verified**

Run on Node 26.13.0, the current LTS (`node:lts-trixie`, Debian), and type-checked with tsc 7.0.2 `--strict` and `@types/node` 26.6.6. The serialized version was run separately with the same timings.

**Gotchas**

- Serializing the updates does not hide the intermediate state from an observer: with the promise-chain queue, a read 1 ms into the first update still saw `size 1 count 0`. The queue protects the next update, not the next reader.
- `Promise.all([const_first_call_attempt_update, const_fn_on_call_attempt(...)])` does not serialize anything: it starts the second update immediately and only waits for both at the end.

# The functional angle: an update that is one value replacing another has no window

Draws on all four tips. Every window above exists because the update is two steps on shared state. The functional form builds the new state as a value and publishes it in one step, so there is no moment when `in_service_count` and `in_service_switch_names` disagree.

```fsharp
// F#: an immutable record and a function that returns the next one.
type LinkStatus = { in_service_switch_names: string list; in_service_count: int }
let fn_with_call_attempt (previous_link_status: LinkStatus) (switch_name: string) : LinkStatus =
    { in_service_switch_names = switch_name :: previous_link_status.in_service_switch_names; in_service_count = previous_link_status.in_service_count + 1 }
let current_link_status = fn_with_call_attempt { in_service_switch_names = []; in_service_count = 0 } "new-york"
printfn "%A" current_link_status
```

```rust
// Rust: build the next link status as a value, then replace the shared one in one assignment under the lock.
use std::sync::{Arc, Mutex};
#[derive(Clone, Debug)]
struct LinkStatus { in_service_switch_names: Vec<String>, in_service_count: usize }
fn with_call_attempt(previous_link_status: &LinkStatus, switch_name: &str) -> LinkStatus {
    let mut mut_next_in_service_switch_names = previous_link_status.in_service_switch_names.clone(); // the copy is local until it is complete
    mut_next_in_service_switch_names.push(switch_name.to_string());
    LinkStatus { in_service_switch_names: mut_next_in_service_switch_names, in_service_count: previous_link_status.in_service_count + 1 }
}
fn main() {
    let shared_link_status = Arc::new(Mutex::new(LinkStatus { in_service_switch_names: Vec::new(), in_service_count: 0 }));
    let next_link_status = with_call_attempt(&shared_link_status.lock().unwrap(), "new-york");
    *shared_link_status.lock().unwrap() = next_link_status; // one assignment: readers see the old value or the new one
    println!("{:?}", shared_link_status.lock().unwrap());
}
```

```cpp
// C++20: publish an immutable snapshot through std::atomic<std::shared_ptr<T>>.
#include <atomic>
#include <cstdio>
#include <memory>
#include <string>
#include <vector>
struct LinkStatus { std::vector<std::string> in_service_switch_names; std::size_t in_service_count = 0; };
std::atomic<std::shared_ptr<const LinkStatus>> shared_link_status_snapshot{std::make_shared<const LinkStatus>()};  // mutable: store() publishes into it
std::shared_ptr<const LinkStatus> with_call_attempt(const LinkStatus& const_previous_link_status, const std::string& const_switch_name) {
    LinkStatus next_link_status = const_previous_link_status;          // a private copy, invisible until published; mutable: filled in, then moved
    next_link_status.in_service_switch_names.push_back(const_switch_name);
    next_link_status.in_service_count += 1;
    return std::make_shared<const LinkStatus>(std::move(next_link_status));
}
int main() {
    shared_link_status_snapshot.store(with_call_attempt(*shared_link_status_snapshot.load(), "new-york"));  // one store: readers see old or new
    const std::shared_ptr<const LinkStatus> const_observed_link_status = shared_link_status_snapshot.load();
    std::printf("size %zu count %zu lock_free %d\n", const_observed_link_status->in_service_switch_names.size(), const_observed_link_status->in_service_count, shared_link_status_snapshot.is_lock_free());
}
```

```ts
// TypeScript: build the next state, then replace the reference once.
type LinkStatus = { readonly in_service_switch_names: readonly string[]; readonly in_service_count: number }
let current_link_status: LinkStatus = { in_service_switch_names: [], in_service_count: 0 } // mutable: replaced by one assignment below
const const_fn_with_call_attempt = (previous_link_status: LinkStatus, switch_name: string): LinkStatus =>
    ({ in_service_switch_names: [...previous_link_status.in_service_switch_names, switch_name], in_service_count: previous_link_status.in_service_count + 1 })
current_link_status = const_fn_with_call_attempt(current_link_status, "new-york") // any reader sees the old value or the new one, never half
```

| Language | Two-step update window | Functional form, run here | What it still needs |
| --- | --- | --- | --- |
| F# | open on a shared mutable collection | an immutable record and a function returning the next one: printed as a record with `in_service_switch_names = ["new-york"]` and `in_service_count = 1` | one owner, such as a `MailboxProcessor`, that applies updates in order |
| Rust | refused at runtime by `RefCell` or `Mutex` | build the next value, then one assignment under the `Mutex`: `LinkStatus { in_service_switch_names: ["new-york"], in_service_count: 1 }` | the lock around the assignment |
| C++ | open: `recursive_mutex` admits re-entry | `std::atomic<std::shared_ptr<const T>>` store of a private copy: `size 1 count 1` on GCC 16.2 and Debian clang 19.1.7 (`is_lock_free()` 0) | a standard library that has it: libstdc++ (GCC 16.2 and Debian clang 19.1.7 default) accepted it; Debian clang 19.1.7 with `-stdlib=libc++` rejected `std::atomic<std::shared_ptr>` (error "_Atomic cannot be applied to type ... which is not trivially copyable"), as did Apple clang 21 libc++ (static assertion) |
| TypeScript | open at every `await` | spread into a new object, assign once | the assignment after the last `await`, not before it |

F# is the baseline here because its default data types are already the functional form; the window opens when F# code shares mutable state, such as a .NET collection, a `ref` cell or a captured `mutable`. All four snippets were run: F# on .NET 10.0.403, Rust on rustc 1.99.1, C++ on GCC 16.2.0 and Debian clang 19.1.7 (Docker), TypeScript on Node 26.13.0.

AT&T's report says the flaw was in all the switches and that the duplicated mate was hit during the same vulnerable period; this part infers that the mate failed the same way because it ran the same code. A pure update function shares that property: two replicas fed the same messages fail identically.

Which of your redundant pairs would survive a bug in the code they share?

# The security angle: the window is where a check and its action disagree

Draws on the TypeScript and C++ tips, with Rust and F# as controls. Runs in both directions: Rust refuses the second entry and F#'s agent queues it; C++ and TypeScript leave the window open by default.

```ts
// TypeScript. Looks like a balance check. The await between check and debit is the window.
const const_bank_account = { balance_cents: 100 }
const WITHDRAWAL_CENTS = 100
const const_fn_sleep_ms = (delay_ms: number): Promise<void> => new Promise((resolve) => setTimeout(resolve, delay_ms))
const const_fn_withdraw = async (amount_cents: number): Promise<boolean> => {
    if (const_bank_account.balance_cents < amount_cents) return false
    await const_fn_sleep_ms(10)                    // e.g. a fraud-check call
    const_bank_account.balance_cents -= amount_cents
    return true
}
console.log(await Promise.all([const_fn_withdraw(WITHDRAWAL_CENTS), const_fn_withdraw(WITHDRAWAL_CENTS)]), const_bank_account.balance_cents) // [ true, true ] -100
```

The class is [CWE-367](https://cwe.mitre.org/data/definitions/367.html), time-of-check time-of-use race condition: both withdrawals passed the check before either debited.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | an `await` between check and act lets a second request pass the same check | nothing: one thread, many interleavings | do the check and the act with no `await` between, or serialize per account |
| C++ | a re-entrant or concurrent path runs between check and act | `std::mutex` blocks other threads, `recursive_mutex` admits re-entry | hold one lock across check and act, without re-entry |
| Rust | the same two-step update | `RefCell` and `Mutex` refuse a second borrow during the first | keep the borrow across check and act |
| F# | the same, on shared mutable state | `MailboxProcessor` applies one message at a time | route both requests through one agent |

TypeScript is the baseline because the window there is created by an ordinary `await`, which code review rarely reads as a concurrency boundary. The [2026-09-24 entry](2026-09-24.md#the-security-angle-adding-concurrency-to-effectall-turns-an-authorization-check-into-a-race-with-the-action-it-guards) met the same check-then-act race through `Effect.all` concurrency. The sample was run on Node 26.13.0.

Which of your handlers check a limit, await something, and then act on the limit they checked?
