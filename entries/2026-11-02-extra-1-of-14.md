Not part of the rotation. A fourteen-part special, one real incident per part, each mechanism measured in Rust, C++, F# and TypeScript. Each incident is quoted from a primary source. Part 1 is [Mars Climate Orbiter](https://llis.nasa.gov/llis_lib/pdf/1009464main1_0641-mr.pdf), lost on 1999-09-23.

# What happened

**Bug class:** Bohrbug, fired on every thruster event; the anti-pattern is a unit that lives only in an interface document, never in the data.

From the Mars Climate Orbiter Mishap Investigation Board Phase I Report (1999-11-10):

```text
The MCO MIB has determined that the root cause for the loss of the MCO spacecraft was
the failure to use metric units in the coding of a ground software file, "Small Forces,"
used in trajectory models.
```

```text
The data in the AMD file was required to be in metric units per existing software
interface documentation, and the trajectory modelers assumed the data was provided in
metric units per the requirements.
```

```text
it was discovered that the small forces deltaV's reported by the spacecraft engineers
for use in orbit determination solutions was low by a factor of 4.45 (1 pound force=4.45
Newtons) because the impulse bit data contained in the AMD file was delivered in lb-sec
instead of the specified and expected units of Newton-sec.
```

The report also says these momentum-desaturation events "occurred 10-14 times more often than was expected" during the "9-month journey", so (inferred) the per-event error was added many times over. At Mars the trajectory was "approximately 170 kilometers lower than planned", and after-the-fact estimates gave what the report calls an initial periapsis of 57 km, "judged too low for spacecraft survival".

In the report's words, the file was "delivered in lb-sec instead of the specified and expected units of Newton-sec": the defect was in what the numbers meant, not in the file's shape. The four tips below are four ways a unit falls off a number in today's languages.

## Rust: `uom` stores every quantity in SI and serializes a bare number, so a file written in pound-force seconds reads back as newton seconds without a complaint

*Stdlib and ecosystem gems*

**Did you know**

The `uom` crate (0.37.0) makes `Force * Time` a `Momentum` and refuses to add it to a `Length`, but it does this by storing every quantity in SI base units. Its serde support writes that SI value as a plain JSON number: one pound-force second becomes `{"impulse":4.448222}`. Reading `{"impulse":1.0}` from a tool that meant pound-force seconds gives 1 N*s, with no error, because the file never said which unit it was in.

**Show me**

```rust
// rustc 1.99.1, uom 0.37.0 (features = ["serde"]), serde_json 1.
use serde::{Deserialize, Serialize};
use uom::si::f64::{Force, Momentum, Time};
use uom::si::force::pound_force;
use uom::si::momentum::kilogram_meter_per_second;
use uom::si::time::second;

#[derive(Serialize, Deserialize)]
struct AmdRecord {
    impulse: Momentum, // N*s and kg*m/s are the same dimension
}

fn main() {
    let thruster_impulse_from_pound_sec: Momentum = Force::new::<pound_force>(1.0) * Time::new::<second>(1.0);
    println!("{}", thruster_impulse_from_pound_sec.get::<kilogram_meter_per_second>()); // 4.448222

    // On the wire the unit is gone: SI is implied, not written.
    let amd_file_json = serde_json::to_string(&AmdRecord { impulse: thruster_impulse_from_pound_sec }).unwrap();
    println!("{amd_file_json}"); // {"impulse":4.448222}

    // A file from a tool that meant lbf*s parses happily as N*s.
    let legacy_amd_file_json = r#"{"impulse":1.0}"#;
    let loaded_amd_record: AmdRecord = serde_json::from_str(legacy_amd_file_json).unwrap();
    println!("{}", loaded_amd_record.impulse.get::<kilogram_meter_per_second>()); // 1
}
```

**Why it matters**

Inside one Rust program `uom` closes the Mars Climate Orbiter bug completely: you cannot build a `Momentum` from a bare `f64` without naming its unit. The file is where it reopens, and the file is where the bug happened. C++ and TypeScript have no general quantity-and-unit library in their standard libraries (C++ has `std::chrono`, for time only).

**Chew on this**

Which of your file formats or APIs carry a quantity whose unit is written only in a document? If you put the unit in the data (`{"impulse": {"value": 1.0, "unit": "lbf*s"}}`), who on the other side would actually read that field?

**Sources**

- https://docs.rs/uom/0.37.0/uom/
- https://docs.rs/uom/0.37.0/src/uom/si/force.rs.html
- https://llis.nasa.gov/llis_lib/pdf/1009464main1_0641-mr.pdf
- https://www.nist.gov/pml/special-publication-811/nist-guide-si-appendix-b-conversion-factors/nist-guide-si-appendix-b8

**Verified**

Run in `rust:1-trixie` (Debian): rustc 1.99.1, uom 0.37.0, serde_json 1. Every printed value above came from that run.

**Gotchas**

- `uom`'s pound-force is the 7-digit factor `4.448_222_E0` (`src/si/force.rs:45`), the same value NIST SP 811 prints without marking it exact. The product of the defined pound mass and standard gravity is 4.4482216152605, so 1 lbf*s reads back as 4.4482220000000: a relative error of 8.6e-8, or 0.385 N*s per million lbf*s.
- `.value` is public and always in SI base units: for 1 lbf*s it is 4.448222, not 1.0. Code that reads `.value` instead of `.get::<unit>()` skips the conversion `uom` exists to do.
- `uom` has no `pound_force_second` unit for momentum. The obvious-looking `pound_foot_per_second` is a different quantity (1 lb*ft/s is 0.138 N*s), so the lbf*s value has to be built as `Force * Time`.

## C++: a strong unit type with an `operator double()` refuses `=` and still converts into another unit through parentheses

*Idioms and antipatterns*

**Did you know**

Wrapping a `double` in `struct NewtonSeconds` is the usual C++ defense against unit mix-ups, and adding `operator double()` "for printing" is the usual way it fails. Copy-initialization (`const PoundForceSeconds const_copied_impulse = const_measured_impulse_n_s;`) and an implicit argument are refused, because they would need two user-defined conversions. Direct-initialization, a functional cast, and a braced argument need only one, so all three compile and silently read newton seconds as pound-force seconds. Measured on C++20 with Debian clang 19.1.7 and GCC 16.2 (Docker); additionally checked on macOS (Apple clang 21.0.0), same result.

**Show me**

```cpp
// C++20. Debian clang 19.1.7 and GCC 16.2, -Wall -Wextra: no diagnostic on the
// lines marked "compiles".
#include <cstdio>

struct NewtonSeconds {
    double value_n_s;
    operator double() const { return value_n_s; }  // added "for printing"
};

struct PoundForceSeconds {
    double value_lbf_s;
    PoundForceSeconds(const double const_raw_lbf_s) : value_lbf_s(const_raw_lbf_s) {}
};

void apply_burn(const PoundForceSeconds const_burn_impulse) { std::printf("%.2f lbf*s\n", const_burn_impulse.value_lbf_s); }

int main() {
    const NewtonSeconds const_measured_impulse_n_s{4.45};

    // const PoundForceSeconds const_copied_impulse = const_measured_impulse_n_s;  // error: two user-defined conversions
    // apply_burn(const_measured_impulse_n_s);                   // error: same rule for an argument

    const PoundForceSeconds const_direct_initialized_impulse(const_measured_impulse_n_s);      // compiles: N*s read as lbf*s
    apply_burn(PoundForceSeconds(const_measured_impulse_n_s)); // compiles
    apply_burn({const_measured_impulse_n_s});                    // compiles
    const double const_sum_as_plain_double = const_measured_impulse_n_s + 1.0;             // compiles: the unit is gone

    // Fix: `explicit operator double()` rejects all four lines above.
    // `explicit PoundForceSeconds(double)` rejects only apply_burn({const_measured_impulse_n_s}).
    std::printf("%.2f %.2f\n", const_direct_initialized_impulse.value_lbf_s, const_sum_as_plain_double);
}
```

**Why it matters**

The refused lines are the ones a reviewer tries first, so the type looks safe in review, while the accepted lines are the ones real code writes. Rust has no implicit by-value conversion to another struct: `From` and `Into` are called explicitly, and `Deref` coercion only applies to references.

**Chew on this**

How many of your strong types have a conversion operator or a `get()` that hands back the raw number, and how many call sites use it to build another strong type? If you made every one of them `explicit`, which call sites would you find you never meant to write?

**Sources**

- https://en.cppreference.com/w/cpp/language/cast_operator
- https://en.cppreference.com/w/cpp/language/copy_initialization
- https://en.cppreference.com/w/cpp/language/direct_initialization

**Verified**

Compiled with Debian clang 19.1.7 (`debian-clang:trixie`) and GCC 16.2.0 (`gcc:latest`), both in Docker on Debian aarch64, C++20, `-Wall -Wextra`. Every accepted and refused line above was run on both. Additionally checked on macOS (Apple clang 21.0.0): same results.

**Gotchas**

- `explicit` on the constructor is the fix most people reach for, and it is not enough: it refused only `apply_burn({const_measured_impulse_n_s})`. `PoundForceSeconds(const_measured_impulse_n_s)` and `const PoundForceSeconds const_direct_initialized_impulse(const_measured_impulse_n_s)` still compiled, because direct-initialization may call an explicit constructor.
- `explicit operator double()` blocks arithmetic too: `const_measured_impulse_n_s + 1.0` became an error on both compilers.
- `-Wall -Wextra` warned about none of the four accepted lines on either compiler.

## F#: units of measure stop at the file, so a writer in `float<lbf s>` and a reader in `float<N s>` agree on `{"impulse":1}`

*Type system deep cuts*

**Did you know**

F# rejects `1.0<N s> + 1.0<lbf s>` at compile time (FS0001: "The unit of measure 'lbf s' does not match the unit of measure 'N s'"). It cannot do anything once the value leaves the program, because units are erased: `typeof<float<N s>>` and `typeof<float<lbf s>>` are both `System.Double`. Two programs that both name a field `impulse`, one in pound-force seconds and one in newton seconds, write and read `{"impulse":1}` with no error. That is the Mars Climate Orbiter file in two type declarations.

**Show me**

```fsharp
// SDK 10.0.403 (F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14), System.Text.Json.
open System.Text.Json

[<Measure>] type N
[<Measure>] type lbf
[<Measure>] type s

module GroundSoftware =       // the writer: thruster data in pound-force seconds
    type AmdRecord = { impulse: float<lbf s> }

module Navigation =           // the reader: the interface spec says newton seconds
    type AmdRecord = { impulse: float<N s> }

let amd_file_json : string = JsonSerializer.Serialize({ GroundSoftware.AmdRecord.impulse = 1.0<lbf s> })
let loaded_navigation_record : Navigation.AmdRecord = JsonSerializer.Deserialize<Navigation.AmdRecord>(amd_file_json)

printfn "%s -> %f N s" amd_file_json (float loaded_navigation_record.impulse)          // {"impulse":1} -> 1.000000 N s
printfn "%b" (typeof<float<N s>> = typeof<float<lbf s>>)       // true: both System.Double
```

**Why it matters**

F# is the one language here with units in the type system out of the box, and the measurement shows exactly where that protection ends. A reflection-based serializer cannot write a unit it cannot see, so the contract falls back to a document, as it did in 1999. C++ has no standard units type to compare with. Rust's `uom` behaves the same way at the boundary, though it at least converts to SI before writing.

**Chew on this**

Where does a `float<_>` in your code first become a plain number: a serializer, a database column, a log line? Would a test that reads a file written by the other side, rather than one your own code wrote, have caught a mismatch?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/units-of-measure
- https://llis.nasa.gov/llis_lib/pdf/1009464main1_0641-mr.pdf

**Verified**

Run in `mcr.microsoft.com/dotnet/sdk:10.0` (Ubuntu 24.04, not Debian).

**Gotchas**

- Serializing and deserializing the same `Navigation.AmdRecord` round-trips the value exactly, so a round-trip test inside one program passes.
- `LanguagePrimitives.FloatWithMeasure 1.0` gives a `float<N s>` from any `float`, and `float x` strips the unit. Both compile without a warning, so every boundary has a one-word escape hatch.

**Related**

- [2026-10-01](2026-10-01.md) - F#, "A unit of measure is gone at runtime". Today's tip is the same erasure, met at a file boundary instead of a type test.

## TypeScript: a branded number loses its brand at the first `+`, and the cast you add to restore it also accepts a pound-force value

*Type system deep cuts*

**Did you know**

The usual TypeScript unit type is a brand, `number & { readonly [const_unit_tag]: "N*s" }`. It catches the direct mix-up (TS2322 on assigning a `PoundForceSeconds` to a `NewtonSeconds`). But `+` on two branded numbers returns a plain `number`, so every sum needs a cast back. That cast cannot see what went into the sum: `(const_burn_impulse_n_s + const_thruster_impulse_lbf_s) as NewtonSeconds` adds newton seconds to pound-force seconds and compiles under `--strict`, and `JSON.parse` returns `any`, which is assignable to the brand with no cast at all.

**Show me**

```ts
// TypeScript, tsc 7.0.2 --strict.
declare const const_unit_tag: unique symbol
type NewtonSeconds = number & { readonly [const_unit_tag]: "N*s" }
type PoundForceSeconds = number & { readonly [const_unit_tag]: "lbf*s" }

const const_fn_newton_seconds = (raw_n_s: number): NewtonSeconds => raw_n_s as NewtonSeconds
const const_fn_pound_force_seconds = (raw_lbf_s: number): PoundForceSeconds => raw_lbf_s as PoundForceSeconds

const const_burn_impulse_n_s: NewtonSeconds = const_fn_newton_seconds(4.45)
const const_thruster_impulse_lbf_s: PoundForceSeconds = const_fn_pound_force_seconds(1)

// const const_wrong_unit_impulse_n_s: NewtonSeconds = const_thruster_impulse_lbf_s             // TS2322: the brand works here
// const const_mixed_sum_n_s: NewtonSeconds = const_burn_impulse_n_s + const_burn_impulse_n_s   // TS2322: + returns plain number

// So the sum gets a cast, and the cast cannot tell what went into it:
const const_summed_impulse_n_s: NewtonSeconds = (const_burn_impulse_n_s + const_thruster_impulse_lbf_s) as NewtonSeconds // compiles
const const_parsed_impulse_n_s: NewtonSeconds = JSON.parse("1.0")                          // compiles: any

console.log(const_summed_impulse_n_s, const_parsed_impulse_n_s)
```

**Why it matters**

A brand protects assignments, and unit bugs happen in arithmetic. Once a codebase has `as NewtonSeconds` after every sum, the brand is asserted by the programmer rather than checked by the compiler, which is the "assumed the data was provided in metric units" sentence from the board report, in types. F# units of measure check the arithmetic itself, where `1.0<N s> + 1.0<lbf s>` is FS0001. Rust's `uom` refuses `Momentum + Length`.

**Chew on this**

Where do your branded types get their brand back after arithmetic: a cast at each call site, or a function that does the math? If it is a function, what stops someone from adding two different brands before calling it?

**Sources**

- https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions
- https://www.typescriptlang.org/docs/handbook/2/objects.html#intersection-types

**Verified**

Run on Node 26.13.0, the current LTS (`node:lts-trixie`, Debian), and type-checked with tsc 7.0.2.

**Gotchas**

- A direct cast between two brands is refused: `const_thruster_impulse_lbf_s as NewtonSeconds` is TS2352, "neither type sufficiently overlaps". Going through `number` is not: `const_thruster_impulse_lbf_s as number as NewtonSeconds` compiles.
- `Math.max(const_burn_impulse_n_s, const_thruster_impulse_lbf_s) as NewtonSeconds` compiles too. Any function typed `(...values: number[]) => number` strips the brand from its inputs and accepts any mix of units.
- A branded `PoundForceSeconds` is still assignable to plain `number`, so passing it to any untyped helper drops the unit with no cast.

# The functional angle: the unit belongs to the operation, not to the number

Draws on all four tips. In two of the four (C++, TypeScript) `+` does not know about units, and in F# and Rust `uom` the check stops at the file. The functional move is to make the sum a function, so the unit check happens once, at its parameters.

```fsharp
// F#: the unit is checked in the arithmetic, so the function adds nothing.
let add_impulse (first_impulse: float<N s>) (second_impulse: float<N s>) : float<N s> = first_impulse + second_impulse
// add_impulse 4.45<N s> 1.0<lbf s>   // FS0001
```

```rust
// Rust, uom 0.37.0: the dimension is checked; N*s and lbf*s are both Momentum.
fn add_impulse(first_impulse: Momentum, second_impulse: Momentum) -> Momentum {
    first_impulse + second_impulse
}
// add_impulse(burn, Length::new::<meter>(1.0))   // E0308 mismatched types
```

```cpp
// C++20: a stricter variant of the types above, plain aggregates with no conversion operator.
NewtonSeconds add_impulse(const NewtonSeconds const_first_impulse, const NewtonSeconds const_second_impulse) {
    return {const_first_impulse.value_n_s + const_second_impulse.value_n_s};
}
// add_impulse(NewtonSeconds{4.45}, PoundForceSeconds{1.0});   // clang: no matching function; GCC: could not convert
```

```ts
// TypeScript: the one cast moves inside the one function that does the math.
const const_fn_add_impulse = (first_impulse: NewtonSeconds, second_impulse: NewtonSeconds): NewtonSeconds =>
    (first_impulse + second_impulse) as NewtonSeconds
// const_fn_add_impulse(const_burn_impulse_n_s, const_thruster_impulse_lbf_s)   // TS2345
```

All four refuse the mixed call (F# on SDK 10.0.403, rustc 1.99.1, Debian clang 19.1.7 and GCC 16.2, tsc 7.0.2). The difference is what refuses a mixed `+` written outside the function.

| Language | Where the unit is checked | What `+` across units does | What it costs |
| --- | --- | --- | --- |
| F# | in the type of every arithmetic expression | FS0001 at compile time | nothing at runtime: erased to `System.Double` |
| Rust (`uom`) | in the quantity type, dimension by dimension | `Momentum + Length` does not compile; lbf and N both become SI first | a dependency, and SI-only storage |
| C++ | only where you write a wrapper | compiles through `operator double()` | one `explicit` keyword, if you know which one |
| TypeScript | only on assignment, via a brand | returns plain `number`; the cast back accepts anything | a cast per sum, each one unchecked |

The F# row is the baseline because it is the only one where checking arithmetic is the default rather than a library or a discipline. It is also the row that showed the limit most plainly: checked arithmetic ends at the first serializer.

If arithmetic on two quantities had to go through a function you wrote, `add_impulse : float<N s> -> float<N s> -> float<N s>`, which of your current `+` signs would refuse to become one?

# The security angle: trust the file's unit only when the file states it

Draws on all four tips. Inside one program the languages do prevent the mix: F# with FS0001, Rust `uom` by refusing `Momentum + Length`, TypeScript with TS2322 on a bare assignment. Across a boundary none of them can, because none of the file formats carry a unit.

```ts
// TypeScript. Looks like a config loader. The unit lives in a comment.
type Config = { max_upload_bytes: number }           // bytes, per the README
const const_upload_config = JSON.parse('{"max_upload_bytes": 50}') as Config
// The operator wrote 50 meaning megabytes; the code reads 50 bytes. Nothing
// in the file or the type can tell the two apart.
```

The class is [CWE-1287](https://cwe.mitre.org/data/definitions/1287.html) (improper validation of specified type of input): the value parses, so nothing checks what it means.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `uom` serde writes and reads a bare SI number | nothing at the file: `{"impulse":1.0}` reads as 1 N*s | put the unit in the format, or validate the range |
| C++ | a strong type with `operator double()` converts to another unit | refuses `=`, accepts `T(x)` | make the conversion `explicit` |
| F# | units erased to `System.Double` | nothing at the file: both sides read `{"impulse":1}` | test against a file written by the other side |
| TypeScript | `JSON.parse` returns `any` | assigns it to the brand with no cast | parse into the brand with a range check |

Rust is the baseline for this class: its in-program check is as strong as F#'s, and it still accepted the wrong file, which isolates the failure to the boundary rather than the language.

Which of your configuration values is a quantity whose unit is only in the documentation, and what happens if someone writes it in the other unit?
