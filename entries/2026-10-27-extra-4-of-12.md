**The thesis of this part: a closure's capture is a contract with two clauses, how a value gets in and what the body may do with it, and each language lets you write one clause while the other is decided for you.** Rust's `move` decides how values get in, and the body decides whether the closure is `Fn` or `FnOnce`. C++'s capture list decides how values get in, and the missing `mutable` silently decides that `std::move` inside the body copies. F# lets you capture a `let mutable` and decides for you that it becomes a heap cell. JavaScript captures bindings, never values, and the loop decides which binding you got.

Every value below was printed by the snippet beside it, on Linux: a Debian 13.7 container with rustc 1.99.1 (clippy 0.1.99), g++ 14.2.0 and .NET SDK 10.0.402 (runtime 10.0.13, FSharp.Core 10.1.0.0), the `gcc:16` image with g++ 16.2.0, the `node:22-trixie` image with Node 22.23.4 and tsc 7.0.2, and the `golang:1-trixie` image with Go 1.27.3 for the appendix.

## Rust: move decides how values get into a closure, not how often it can run, and a moved Copy counter never changes outside

*Idioms and antipatterns*

**Did you know**

`move` and `FnOnce` are independent. `move` says the closure takes ownership of what it captures; whether it can be called more than once is inferred from the body. `move || names.len()` is `Fn` and was called twice. `move || names.into_iter().count()` is `FnOnce`, and passing it where `Fn` is required is E0525, "closure is `FnOnce` because it moves the variable `names_again` out of its environment". And for a `Copy` type, `move` copies: a `move` closure that increments a captured `u32` counter returned 1 and 2, while the counter outside stayed 0, with no warning from rustc or from clippy's pedantic and nursery groups.

**Show me**

```rust
// rustc 1.99.1, edition 2021.
fn call_twice<F: Fn() -> usize>(callback: F) -> usize { callback() + callback() }

fn main() {
    let names: Vec<String> = vec!["eu".into(), "us".into()];
    // move says HOW names gets in; the body decides the trait. This one only reads: Fn.
    let count_names = move || names.len();
    println!("{}", call_twice(count_names)); // 4

    // let consume = move || names_again.into_iter().count();
    // call_twice(consume)  // E0525: expected a closure that implements the `Fn` trait,
    //                      // but this closure only implements `FnOnce`

    // A Copy value is copied in: the closure counts on its own copy.
    let mut request_count: u32 = 0; // the closure below needs a mut capture to increment
    let mut record_request = move || { request_count += 1; request_count };
    println!("inside: {} {}", record_request(), record_request()); // inside: 1 2
    println!("outside: {request_count}"); // outside: 0, and no warning anywhere
}
```

**Why it matters**

The trait is inferred from the body, so a one-line edit inside a callback (an `into_iter()`, a `drop`, returning a captured `String`) turns `Fn` into `FnOnce`, and the error appears at whichever call site required `Fn`, possibly in another module. The `Copy` case is quieter: `move` is often added to satisfy a `'static` bound for a thread or a task, and any counter or flag of a `Copy` type silently forks. Without `move`, the same counter closure borrows `request_count` mutably and the outside read printed 2. C++'s `[count]() mutable` forks the same way (outside stayed 0, while `[&count]` gave 2). F# and TypeScript have no by-value capture of a mutable at all, so the outside variable saw both increments.

**Chew on this**

Which of your `move` closures were written to satisfy `'static` rather than to transfer ownership, and is any of them holding a private copy of a counter, a flag or a config value that the rest of the code still updates?

**Sources**

- https://doc.rust-lang.org/reference/types/closure.html (capture modes; "call traits and coercions")
- https://doc.rust-lang.org/std/ops/trait.FnOnce.html
- https://doc.rust-lang.org/error_codes/E0525.html

**Gotchas**

- Adding `move` never makes a closure `FnOnce` by itself; moving a captured value *out* in the body does. The diagnostic points at the moving expression ("closure is `FnOnce` because it moves the variable ... out of its environment").
- A borrowing closure that mutates (`|| request_count += 1`) holds a mutable borrow until its last use, so reading the counter between two calls does not compile; after the last call it reads 2.
- `[u8; 32]` is `Copy`, so a `move` closure over a key array copies the key; the security angle below measures it.

## C++: std::move of an init-capture inside a lambda without `mutable` is a copy, and neither g++ 14 nor g++ 16 says a word

*Idioms and antipatterns*

**Did you know**

A lambda's `operator()` is `const` unless the lambda is declared `mutable`. Inside it, every by-copy capture, init-captures included, is a `const` member, so `std::move(batch)` produces a `const payload&&`, which cannot bind to the move constructor and quietly binds to the copy constructor instead. `[batch = std::move(batch)]() { consume(std::move(batch)); }` moves the payload *into* the lambda and then copies it *out*: copies=1, moves=0. Adding `mutable` gives copies=0, moves=1. g++ 14.2 and g++ 16.2 with `-Wall -Wextra` printed no warning. C++14 for init-capture; the rule is the same in every standard since.

**Show me**

```cpp
// C++20, g++ 14.2 and g++ 16.2 (-std=c++26), -Wall -Wextra: no warnings.
#include <cstdio>
#include <utility>
#include <vector>

// A payload that counts its copies and moves.
struct payload {
    std::vector<int> rows;
    static inline int copies = 0, moves = 0;
    payload(std::vector<int> initial) : rows(std::move(initial)) {}
    payload(const payload& other) : rows(other.rows) { ++copies; }
    payload(payload&& other) noexcept : rows(std::move(other.rows)) { ++moves; }
};
void consume(payload sink) { std::printf("consumed %zu rows\n", sink.rows.size()); }

int main() {
    payload batch{std::vector<int>(1000, 7)};
    auto send = [batch = std::move(batch)]() { consume(std::move(batch)); }; // operator() is const
    payload::copies = payload::moves = 0;
    send();
    std::printf("non-mutable: copies=%d moves=%d\n", payload::copies, payload::moves); // copies=1 moves=0

    payload other_batch{std::vector<int>(1000, 7)};
    auto send_mutable = [other_batch = std::move(other_batch)]() mutable { consume(std::move(other_batch)); };
    payload::copies = payload::moves = 0;
    send_mutable();
    std::printf("mutable:     copies=%d moves=%d\n", payload::copies, payload::moves); // copies=0 moves=1
}
```

**Why it matters**

The init-capture `[batch = std::move(batch)]` is the idiom for handing ownership to a callback, a task or a thread, and the body almost always wants to pass it on. Without `mutable`, the code reads as two moves and performs one move and one full copy of whatever the payload owns: a request body, a vector of rows, a token. Rust cannot express this bug: a `move` closure that moves its capture out becomes `FnOnce`, and the compiler holds you to calling it once. F# and TypeScript capture references to heap objects, so there is no copy to make.

**Chew on this**

How many of your lambdas take ownership with an init-capture and then `std::move` the capture onward, and which of them is called more than once, so that `mutable` would make the second call see a moved-from value?

**Sources**

- https://en.cppreference.com/w/cpp/language/lambda (the function-call operator is const-qualified unless `mutable` is used)
- https://en.cppreference.com/w/cpp/utility/move
- https://clang.llvm.org/extra/clang-tidy/checks/performance/move-const-arg.html

**Verified**

g++ 14.2 and 16.2 only. clang-tidy's `performance-move-const-arg` is cited from its documentation and was not run.

**Gotchas**

- `mutable` fixes the move, and changes what a second call sees: after the first call, the captured `std::string` in the `mutable` version held 0 bytes, so calling it again would send an empty token.
- Without `mutable`, the capture keeps its contents after the "move": the non-mutable lambda's captured 64-byte `std::string` still held 64 bytes after `consume(std::move(...))`.
- The same `const&&`-binds-to-copy rule applies to any `const` object, not only lambda captures; the lambda case is just the one where the `const` is invisible in the source.

## F#: a closure can capture a `let mutable`, and F# quietly moves it into a heap ref cell; FS3180, off by default, is the only sign

*Perf and memory model*

**Did you know**

F# accepts a closure that captures a `let mutable` local, and the docs say what happens: values marked `mutable` "may be automatically promoted to `'a ref` if captured by a closure, including forms that create closures, such as `seq` builders". The promotion is a heap allocation, and the only diagnostic is warning 3180, which is off by default. With `--warnon:3180`, `dotnet fsi` flagged the counter captured by a returned closure ("The mutable local 'request_count' is implicitly allocated as a reference cell because it has been captured by a closure") and did not flag a `List.iter` lambda or a lambda called locally, so the optimizer decides which captures cost an allocation.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, dotnet fsi --warnon:3180.
let make_counter () =
    let mutable request_count = 0 // FS3180 here: promoted to a ref cell
    fun () ->
        request_count <- request_count + 1
        request_count

let next_request = make_counter ()
printfn "returned closure: %d %d" (next_request ()) (next_request ()) // returned closure: 1 2

let total_rows (batches: int list) =
    let mutable rows_seen = 0 // no FS3180: this capture did not need a ref cell
    batches |> List.iter (fun batch_size -> rows_seen <- rows_seen + batch_size)
    rows_seen

printfn "List.iter closure: %d" (total_rows [ 3; 4 ]) // List.iter closure: 7
```

**Why it matters**

The language that makes immutability the default also makes the escape hatch cheap to write: one `let mutable` and a lambda, and the code compiles into a heap-allocated shared cell. On a hot path that is an allocation per call of `make_counter`, invisible in the source. It also changes the semantics in a way that matters for laziness: a `seq` that captures a mutable reads it when enumerated, not when built (`seq { yield page_size }` followed by `page_size <- 50` enumerated as `[50]`). Rust forbids the shared-mutable capture outright unless you ask for `Rc<Cell<_>>`, C++ makes you pick `[&]` or `[=]`, and JavaScript always shares the binding, so only F# changes representation behind your back.

**Chew on this**

If you turned on `--warnon:3180` across your solution today, how many warnings would it print, and how many of those sit inside code you consider a hot path?

**Sources**

- https://learn.microsoft.com/dotnet/fsharp/language-reference/values/ ("may be automatically promoted to `'a ref` if captured by a closure ... enable warning 3180")
- https://learn.microsoft.com/dotnet/fsharp/language-reference/compiler-options (`--warnon`)
- https://learn.microsoft.com/dotnet/fsharp/language-reference/reference-cells

**Gotchas**

- FS3180 is about locals. A `let mutable` at the top level of a script is a static field, so `seq { yield page_size }` over it drew no FS3180 at all, yet still read the later value `[50]`.
- Whether a capture allocates depends on the optimizer: the locally called lambda and the `List.iter` lambda drew no FS3180, the returned closure did. Measure in a Release build before assuming either way.
- An explicit `ref` cell (`let request_count = ref 0`, then `request_count.Value <- ...`) gave the same result, 2, and says the allocation out loud.

## TypeScript: for (let ...) gives every iteration a fresh binding, but a closure made in the loop header keeps the first one forever

*Type system deep cuts*

**Did you know**

JavaScript closures capture bindings, not values. `for (let attempt = 0; ...)` creates a new binding for each iteration and copies the previous value into it before running the update expression, which is why closures created in the loop body see 0, 1 and 2. A closure created in the loop *header*, in the initializer, is made before the first copy, so it is bound to the initial binding, and it read 0 on every iteration. With `var` there is one binding for the whole loop, and every closure read 3. A closure also sees later writes to its own iteration's binding: assigning `attempt += 10` after creating the closure made it read 10.

**Show me**

```typescript
// TypeScript, tsc 7.0.2 --strict, Node 22.23.4.
const from_body: Array<() => number> = []
for (let attempt = 0; attempt < 3; attempt++) from_body.push(() => attempt)
console.log(from_body.map((read_attempt) => read_attempt())) // [ 0, 1, 2 ]

const from_header: Array<() => number> = []
for (let attempt = 0, read_first = () => attempt; attempt < 3; attempt++) {
    from_header.push(read_first) // read_first was created in the header
}
console.log(from_header.map((read_attempt) => read_attempt())) // [ 0, 0, 0 ]

const from_var: Array<() => number> = []
for (var shared_attempt = 0; shared_attempt < 3; shared_attempt++) from_var.push(() => shared_attempt)
console.log(from_var.map((read_attempt) => read_attempt())) // [ 3, 3, 3 ]

const late: Array<() => number> = []
for (let attempt = 0; attempt < 2; attempt++) { late.push(() => attempt); attempt += 10 }
console.log(late.map((read_attempt) => read_attempt())) // [ 10 ]: the closure sees the later write
```

**Why it matters**

The per-iteration copy is what makes `for (let ...)` safe for callbacks, retries and timers, and it is a copy of a binding, not a snapshot of a value: anything written to that iteration's binding later, by the loop body or by another closure, is what every closure from that iteration reads. The header case is rare, and it is the one place the fresh-binding rule does not reach. Go had the `var` behaviour for `for` loops until Go 1.22 (Appendix A is what it cost), Rust and F# loops bind a new immutable value per iteration, and a C++ lambda chooses value or reference in its capture list.

**Chew on this**

In your retry and polling loops, does any callback read a loop variable that a later statement in the same iteration modifies, and does it want the value at creation or the value at call time?

**Sources**

- https://tc39.es/ecma262/#sec-createperiterationenvironment
- https://tc39.es/ecma262/#sec-forbodyevaluation
- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Statements/for

**Gotchas**

- `for (const item of items)` also gets a fresh binding per iteration, so it has the body behaviour; `const` just forbids the later write that the last example made.
- tsc 7.0.2 no longer accepts `--target es5`, the target that used to rewrite `let` loops into renamed `var`s and helper functions: it reports "TS5108: Option 'target=ES5' has been removed".
- Closures in the header are legal and type-check without any diagnostic; nothing in tsc or Node warns that `read_first` sees only the first binding.

# The functional angle: does the outside see what the closure did? Two of five capture forms say no, and neither warns

_Draws on all four tips. The shape: a counter declared outside, a closure that increments it twice, then a read from the outside. Every row ran._

| Language | Capture form | Outside after two calls | What it costs |
| --- | --- | --- | --- |
| F# | captured `let mutable` | 2 | a heap `ref` cell when the optimizer cannot avoid it; FS3180 if enabled |
| Rust | borrowing closure `\|\| count += 1` | 2 | a mutable borrow that blocks every other use until the closure's last call |
| Rust | `move` over a `Copy` counter | 0 | nothing, and no lint: the closure owns a private copy |
| C++ | `[count]() mutable` | 0 | nothing; `mutable` only lets the copy change |
| C++ | `[&count]` | 2 | a reference that dangles if the lambda outlives `count` |
| TypeScript | any closure | 2 | the binding lives as long as the closure (the 2026-10-02 leak) |

F# is the baseline because it is the one language here whose default is immutable values and which still accepts the mutable capture, so its row shows what sharing costs when the language does it for you: an allocation. Rust and C++ make you choose and price the choice in the type (`FnMut`, a borrow, a reference); JavaScript never offers the copy. The two "0" rows are the asymmetry worth remembering: both are by-value captures of a mutable thing, and both compile clean.

Left open: when a closure needs a counter that the outside also reads, which of these shapes would you accept in code review without asking a question?

# The security angle: "move" a secret into a closure, and you may have made a second copy

_Draws on the Rust and C++ tips, Mode B: the tips show that `move` can copy. The question is what that does to key material and tokens, which the code intends to exist in exactly one place. Direction: neither language prevents it._

```rust
// Rust, rustc 1.99.1: [u8; 32] is Copy, so move copies the key into the closure
let session_key: [u8; 32] = [7; 32];
let sign = move |message: &str| message.len() as u8 ^ session_key[0];
println!("{}", sign("hello"));   // 2
println!("{}", session_key[0]);  // 7: the original is still there, so zeroizing one copy leaves the other
```

```cpp
// C++20, g++ 14.2: the capture keeps its bytes after the "move"
std::string api_token(64, 'k');
auto send = [api_token = std::move(api_token)]() {
    consume(std::move(api_token));                                      // copies
    std::printf("capture still holds %zu bytes\n", api_token.size());  // 64
};
```

Both look like ownership transfer, and both leave sensitive bytes in a second location: CWE-316 (Cleartext Storage of Sensitive Information in Memory). A wipe-on-drop wrapper such as Rust `zeroize` or a C++ type that clears itself in its destructor only clears the copy it owns.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `move` of a `Copy` key array leaves the original on the stack | nothing; `Copy` is a promise that duplication is fine | wrap secrets in a non-`Copy` type (a struct without `Copy`, or `zeroize::Zeroizing`), so `move` really moves |
| C++ | `std::move` of a capture in a non-`mutable` lambda copies the token | nothing; no g++ warning | `mutable` on lambdas that move their captures, and a self-clearing type for secrets |
| F# | not applicable in this form: captured values are references to the same heap object | | .NET strings are immutable, so a token held in one cannot be wiped in place (from the .NET docs; not measured here) |
| TypeScript | not applicable in this form: closures share the binding | | JS strings are immutable and cannot be wiped; keep secrets in a `Uint8Array` and `fill(0)` it |

Left open: which of your secret-holding types is `Copy`, `Clone` or copyable in C++, and is that because something needed it or because a derive put it there?

# FAQ

**Does `move` in Rust make a closure `'static`?**
No. It makes the closure own its captures, which is what lets it be `'static` when every captured value is itself `'static` (an owned `Vec<String>` is; a `&str` borrowed from a local is not). `move` is the means, the bound is checked separately.

**Is `mutable` on a C++ lambda just about modifying captures?**
It is the switch that removes `const` from `operator()`, so it also decides whether `std::move(capture)` moves or copies, measured above as copies=1 versus moves=1.

**Is a captured F# `let mutable` shared with the outside or copied into the closure?**
Shared: the promotion to a `ref` cell is what makes it shared. A module-level `let mutable request_count` incremented twice by a closure read 2 from the outside, the same as TypeScript and unlike Rust's `move` or C++'s `[count]`.

**Does `for (const x of xs)` in JavaScript share one binding like `var`?**
No: it creates a fresh binding per iteration, like `for (let ...)`. Only `var`, and a closure created in a `for (let ...)` header, see a single binding.

# Appendix A: Let's Encrypt, 2020-02-29, a loop variable reused across iterations rechecked one domain N times

_Not part of the tip rotation. Written 2026-10-27; backs the TypeScript tip (a per-iteration binding versus one shared binding) and the thesis (the language decides what you captured). A real incident, quoted from Let's Encrypt's incident report and the Go team's blog; the reproduction is illustrative code, run on Go 1.27.3 (`golang:1-trixie`). Go appears here as a side note, as the language the incident happened in._

**Bug class:** Bohrbug, data-triggered: solid whenever an order needed more than one domain rechecked, and present from 2019-07-25 until it was found. Anti-pattern: keeping a pointer to (or a closure over) a loop variable that the loop reuses on every iteration.

## A.1 What happened

Quoted from Let's Encrypt's "2020.02.29 CAA Rechecking Bug" report:

- Boulder rechecks CAA records before issuance when a domain was validated more than 8 hours earlier. When a request had several such domains, it "would pick one domain name and check it N times", so the others were never rechecked.
- It was confirmed 2020-02-29 at 03:08 UTC, issuance was halted at 03:10, and a fix was deployed at 05:22. The bug was likely introduced on 2019-07-25.
- About 2.6% of active certificates were affected, "totalling approximately 3 million certificates"; 1,706,505 that had been replaced were revoked.

The Go team's 2023 post on the Go 1.22 loop change names it "a publicly documented issue at Lets Encrypt": a loop variable was kept past its iteration, and "the accidental capture of the loop variable was spread across multiple functions and much more difficult to notice".

## A.2 The shape, reproduced

```go
// Go: the shape of the Boulder bug, rebuilt (not Let's Encrypt's code).
package main

import (
	"fmt"
	"sort"
)

type authorization struct{ domain string }

func main() {
	pending := map[string]authorization{"a.example": {"a.example"}, "b.example": {"b.example"}, "c.example": {"c.example"}}
	to_recheck := []*authorization{}
	for _, authz := range pending { // authz is the loop variable
		to_recheck = append(to_recheck, &authz) // a pointer to it, kept past this iteration
	}
	checked := []string{}
	for _, authz := range to_recheck {
		checked = append(checked, authz.domain)
	}
	sort.Strings(checked)
	fmt.Println(len(to_recheck), "rechecks:", checked)
}
```

The same file, with only the `go` line in `go.mod` changed, run four times each:

| `go.mod` says | Loop variable | Output (all four runs) |
| --- | --- | --- |
| `go 1.21` | one per loop | `3 rechecks: [c.example c.example c.example]` |
| `go 1.22` | one per iteration | `3 rechecks: [a.example b.example c.example]` |

Under the old semantics the program does exactly what the report describes: three rechecks, all of one domain. `go vet` printed nothing for either version.

## A.3 Back to the tips

- **TypeScript:** `var` in a `for` loop is Go-before-1.22: one binding, every closure reads the last value (`[3, 3, 3]`). `let` is Go 1.22 (`[0, 1, 2]`), except for a closure created in the header.
- **Rust:** the same code does not compile. A reference to the loop variable cannot outlive the iteration, so pushing `&authz` into an outer vector is a borrow error (rustc 1.99.1: "E0597: `authz` does not live long enough"). That is the strongest version of "the language decides what you captured".
- **C++:** `for (auto authz : pending)` copies per iteration, and taking `&authz` into an outer vector leaves dangling pointers; `for (auto& authz : pending)` points into the map, which is what was meant.
- **F#:** `for authz in pending do` binds a fresh immutable value per iteration, and there is no address-of to keep.
