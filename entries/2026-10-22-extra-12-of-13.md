This part: recurrence rules. [Part 13](2026-10-22-extra-13-of-13.md) covers which day a week starts on._

**The thesis: a recurrence is a rule, not a date plus a step, and the rule decides what happens to a day that does not exist.** RFC 5545 (iCalendar) says a monthly event on the 31st skips the months without one. Date arithmetic clamps it to the last day instead. Arithmetic from the previous occurrence drifts it to the 28th forever. All three are "monthly from Jan 31".

| "Monthly, starting 2026-01-31" | Six occurrences |
| --- | --- |
| RFC 5545 (`rrule` crate, Ical.Net, npm `rrule`) | 01-31, 03-31, 05-31, 07-31, 08-31, 10-31: **skips** Feb, Apr, Jun, Sep |
| RFC 5545 with `BYMONTHDAY=-1` | 01-31, 02-28, 03-31, 04-30, 05-31, 06-30: **the last day** |
| Add *n* months to the anchor (Rust `jiff`, .NET `AddMonths`) | 01-31, 02-28, 03-31, 04-30, 05-31, 06-30: **clamps** |
| Add 1 month to the previous occurrence (.NET `AddMonths`) | 01-31, 02-28, 03-28, 04-28, 05-28, 06-28: **drifts** |
| C++20 `year_month_day + months{n}` | 01-31, then 02-31 **not `ok()`**, and so on |

All values measured on 2026-10-22.

## Rust: the `rrule` crate follows RFC 5545 and skips months without a 31st, so six monthly occurrences take ten months

*Stdlib and ecosystem gems*

**Did you know**

The Rust `rrule` crate (0.14.0) implements RFC 5545 recurrence rules. `FREQ=MONTHLY` starting 2026-01-31 produces Jan 31, Mar 31, May 31, Jul 31, Aug 31 and Oct 31: months without a 31st are skipped, because the RFC says an invalid date is ignored rather than moved. `BYMONTHDAY=-1` means "the last day of each month" and does what most people meant. A yearly rule starting on Feb 29 fires only in 2024, 2028 and 2032. Rust `jiff`'s date arithmetic gives the clamped schedule instead (Feb 28, Apr 30), from the same words.

**Show me**

```rust
// Rust: rrule 0.14.0 (RFC 5545) and jiff 0.2.38, rustc 1.95.0
use jiff::{civil::date, ToSpan};
use rrule::RRuleSet;

fn main() {
    let fn_days = |rule: &str| -> Vec<String> {
        let set: RRuleSet = rule.parse().unwrap();
        set.all(6).dates.iter().map(|occurrence| occurrence.format("%m-%d").to_string()).collect()
    };
    // RFC 5545: a date that does not exist is skipped, not moved.
    println!("{:?}", fn_days("DTSTART:20260131T090000Z\nRRULE:FREQ=MONTHLY;COUNT=6"));
    // ["01-31", "03-31", "05-31", "07-31", "08-31", "10-31"]: six occurrences take ten months
    println!("{:?}", fn_days("DTSTART:20260131T090000Z\nRRULE:FREQ=MONTHLY;BYMONTHDAY=-1;COUNT=6"));
    // ["01-31", "02-28", "03-31", "04-30", "05-31", "06-30"]: -1 means "the last day"
    println!("{:?}", fn_days("DTSTART:20240229T090000Z\nRRULE:FREQ=YEARLY;COUNT=3"));
    // ["02-29", "02-29", "02-29"]: in 2024, 2028 and 2032

    // The same words, "monthly from Jan 31", with date arithmetic: it clamps instead of skipping.
    let anchor = date(2026, 1, 31);
    let clamped: Vec<String> = (0..6).map(|step| anchor.checked_add(step.months()).unwrap().strftime("%m-%d").to_string()).collect();
    println!("{clamped:?}"); // ["01-31", "02-28", "03-31", "04-30", "05-31", "06-30"]
}
```

**Why it matters**

"Bill monthly on the customer's signup day" is the classic case. Store it as an RRULE and a customer who signed up on the 31st is billed seven times a year. Compute it with date arithmetic and they are billed twelve times, on days that move. Neither is wrong. They are different products, and the choice is usually made by whichever library someone imported. Ical.Net and npm `rrule` agree with this crate (F# and TypeScript tips). C++ has no RRULE in std, but it has "last" as a type.

**Chew on this**

Which of your recurring events are stored as a rule and which as "a date plus a period"? For a customer on the 31st, which months should they hear from you in, and which library currently decides?

**Sources**

- https://www.rfc-editor.org/rfc/rfc5545#section-3.3.10 (the RECUR value type: "Recurrence rules may generate recurrence instances with an invalid date (e.g., February 30) or nonexistent local time ... Such recurrence instances MUST be ignored and MUST NOT be counted as part of the recurrence set.")
- https://docs.rs/rrule/0.14.0/rrule/

**Gotchas**

- `FREQ=MONTHLY` with no `BYMONTHDAY` takes the day from `DTSTART`, so it skips exactly like `BYMONTHDAY=31` (measured).
- `DTSTART;TZID=America/Chicago:20261031T090000` with `FREQ=DAILY` stays at 09:00 local across the fall-back night: 09:00 CDT, then 09:00 CST (measured).
- Rust and its crates evolve: this is `rrule` 0.14.0, which depends on Rust `chrono` and `chrono-tz` for its dates and zones.

## C++: "the last Friday" and "the last day" are types in `<chrono>`, and "the fifth Friday" of February rolls silently into March

*Type system deep cuts*

**Did you know**

C++20's calendar types can express recurrence anchors that other standard libraries cannot. `2026y/February/Friday[last]` is 2026-02-27. `year_month_day_last` stays "the last day" when you add months: Jan, then Feb 28, then Apr 30. `2026y/January/31 + months{1}` keeps the 31st and is not `ok()`. The trap is the indexed form. February 2026 has no fifth Friday, so `2026y/February/Friday[5]` is not `ok()`, and converting it through `sys_days` silently gives **2026-03-06**, a Friday in the wrong month. Measured on Apple clang 21 (libc++) and GCC 16.2 (libstdc++).

**Show me**

```cpp
// C++20: Apple clang 21 (libc++ 22) and GCC 16.2 (libstdc++)
#include <chrono>
#include <cstdio>
using namespace std::chrono;

static void fn_print(year_month_day date) {
    std::printf("%d-%02u-%02u%s\n", (int)date.year(), (unsigned)date.month(), (unsigned)date.day(), date.ok() ? "" : " (not ok)");
}

int main() {
    // "Last Friday" and "last day" are types in std, not computations:
    fn_print(year_month_day{2026y/February/Friday[last]});     // 2026-02-27
    const year_month_day_last month_end = 2026y/January/last;
    fn_print(year_month_day{month_end + months{1}});            // 2026-02-28: still "last"
    fn_print(year_month_day{month_end + months{3}});            // 2026-04-30

    // "The 31st" plus months keeps the 31st, valid or not:
    fn_print(2026y/January/31 + months{1});                     // 2026-02-31 (not ok)

    // "The fifth Friday" does not exist in February 2026, and sys_days moves it into March:
    const year_month_weekday fifth_friday = 2026y/February/Friday[5];
    std::printf("ok() = %d\n", (int)fifth_friday.ok());        // 0
    fn_print(year_month_day{sys_days{fifth_friday}});           // 2026-03-06
}
```

**Why it matters**

"Every month on the fifth Friday" (a payroll extra, a maintenance window) is a real rule that exists in only four or five months a year. In C++ the type knows: `ok()` is false. Code that skips the check and converts anyway gets March 6 scheduled as February's fifth Friday, and then March's own fifth Friday too if March has one. RFC 5545 libraries skip the month, which is the rule most people meant (Rust and F# tips).

**Chew on this**

Where your C++ code builds a `year_month_weekday` or a day like the 31st, does anything check `ok()` before converting to `sys_days`? Which of your recurrences are really "last", spelled as a number?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/year_month_weekday
- https://en.cppreference.com/w/cpp/chrono/year_month_day_last
- https://en.cppreference.com/w/cpp/chrono/weekday_last

**Verified**

Apple clang 21 on this host and `docker run gcc:16`, with identical output. MSVC not tested.

**Gotchas**

- `year_month_day_last` has no day to go wrong: `2026y/January/last + months{3}` is 2026-04-30 (measured), the only std type in the four languages that means "last" by construction.
- The months without a 31st in the first half of 2026 are Feb, Apr and Jun: `2026y/month/31` was not `ok()` for exactly those (measured).
- `weekday_indexed` accepts index 1 to 5. Index 5 is `ok()` as an index, and only the `year_month_weekday` built from it is not.

## F#: Ical.Net, `AddMonths` from the anchor and `AddMonths` from the last occurrence give three "monthly from Jan 31" schedules

*Idioms and antipatterns*

**Did you know**

There is no recurrence in the .NET base library, so a "monthly" schedule is built one of three ways, and they disagree. Ical.Net (5.0, RFC 5545) skips months without a 31st: 01-31, 03-31, 05-31, ... `start.AddMonths step` from the anchor clamps and returns to the 31st when it can: 01-31, 02-28, 03-31, 04-30. `previous.AddMonths 1` from the last occurrence clamps once and then **stays on the 28th forever**: 01-31, 02-28, 03-28, 04-28. Measured on FSharp.Core 8.0 / .NET 8.0.8.

**Show me**

```fsharp
// F#: Ical.Net 5.0 on FSharp.Core 8.0 / .NET 8.0.8
#r "nuget: Ical.Net"
open System
open Ical.Net
open Ical.Net.CalendarComponents
open Ical.Net.DataTypes

// Three ways to say "monthly, starting Jan 31":
let start = DateTime(2026, 1, 31, 9, 0, 0)

// 1. RFC 5545, through Ical.Net: months without a 31st are skipped.
let meeting = CalendarEvent(DtStart = CalDateTime(start, "America/Chicago"), DtEnd = CalDateTime(start.AddHours 1.0, "America/Chicago"))
meeting.RecurrenceRule <- RecurrencePattern "FREQ=MONTHLY;COUNT=6"
let calendar = Calendar()
calendar.Events.Add meeting
let skipped = calendar.GetOccurrences(CalDateTime(start, "America/Chicago")) |> Seq.map (fun occurrence -> occurrence.Period.StartTime.Value.ToString "MM-dd") |> List.ofSeq
printfn "%A" skipped   // ["01-31"; "03-31"; "05-31"; "07-31"; "08-31"; "10-31"]

// 2. AddMonths from the anchor: clamps, and returns to the 31st when it can.
printfn "%A" [ for step in 0 .. 5 -> (start.AddMonths step).ToString "MM-dd" ]  // ["01-31"; "02-28"; "03-31"; "04-30"; "05-31"; "06-30"]

// 3. AddMonths from the previous occurrence: clamps once, then stays on the 28th forever.
let drifted = List.scan (fun (previous: DateTime) _ -> previous.AddMonths 1) start [ 1 .. 5 ]
printfn "%A" (drifted |> List.map (fun occurrence -> occurrence.ToString "MM-dd")) // ["01-31"; "02-28"; "03-28"; "04-28"; "05-28"; "06-28"]
```

**Why it matters**

The drifting version is the natural shape of a scheduler that stores "next run" and updates it after each run. It is also the one that is wrong in a way nobody chose: one short February moves every later occurrence three days early, forever. Part 10's F# tip measured the same `AddMonths` round trip losing three days. Storing the anchor and the step count, or the RRULE itself, keeps the schedule recomputable.

**Chew on this**

Does your scheduler store the next occurrence, or the rule and the anchor it came from? If a customer moved from the 31st to the 28th after one February, would anyone notice?

**Sources**

- https://github.com/ical-org/ical.net
- https://learn.microsoft.com/en-us/dotnet/api/system.datetime.addmonths
- https://www.rfc-editor.org/rfc/rfc5545#section-3.3.10

**Gotchas**

- `CalendarEvent.RecurrenceRules.Add` compiles with warning FS0044 in Ical.Net 5.0: "Use RecurrenceRule instead. Support for multiple recurrence rules will be removed in a future version." (measured). The snippet uses `RecurrenceRule`.
- `FREQ=DAILY` from 09:00 America/Chicago gave 09:00 -05:00 and then 09:00 -06:00 across the fall-back night (measured): the rule keeps local time.
- The occurrences are `CalDateTime` values, not `DateTime`, so the zone travels with them until you convert.

## TypeScript: npm `rrule` with `tzid` returns different instants depending on the server's `TZ`

*Stdlib and ecosystem gems*

**Did you know**

The npm `rrule` package (2.8.1) skips the 31st the RFC 5545 way, like the Rust crate and Ical.Net. Its time zones are the trap. Its README says "Returned "UTC" dates are always meant to be interpreted as dates in your local timezone." Measured: the same rule, "daily at 09:00 in America/Chicago" with `tzid`, prints 9:00 AM Chicago when the Node process runs with `TZ=UTC`, 4:00 AM and then 3:00 AM with `TZ=America/Chicago`, and 6:00 PM with `TZ=Asia/Tokyo`. And the package is CommonJS, so `import { RRule } from "rrule"` fails under Node's ESM loader.

**Show me**

```ts
// TypeScript 6.0.3 types, rrule 2.8.1 (npm), Node 22.17.1
import rrule_package from "rrule"            // CommonJS: `import { RRule } from "rrule"` fails under Node ESM
const { RRule } = rrule_package

// "Every day at 09:00 in Chicago", across the night Chicago falls back (2026-11-01).
const daily = new RRule({
    freq: RRule.DAILY,
    dtstart: new Date(Date.UTC(2026, 9, 31, 9, 0)), // rrule reads these UTC fields as Chicago wall time
    tzid: "America/Chicago",
    count: 3,
})
const fn_in_chicago = (occurrence: Date): string =>
    occurrence.toLocaleString("en-US", { timeZone: "America/Chicago", hour: "numeric", minute: "2-digit" })
console.log(process.env.TZ, daily.all().map(fn_in_chicago))
// TZ=UTC:             [ '9:00 AM', '9:00 AM', '9:00 AM' ]
// TZ=America/Chicago: [ '4:00 AM', '3:00 AM', '3:00 AM' ]
// TZ=Asia/Tokyo:      [ '6:00 PM', '6:00 PM', '6:00 PM' ]
// Same code, same rule: the instants depend on the SERVER's zone.
```

**Why it matters**

Recurring jobs are computed on servers, and servers run with whatever `TZ` the image set (part 4's TypeScript tip). The schedule is right on a UTC container and wrong by five hours on a developer's Chicago laptop, so the tests pass where they are written and the bug appears where they are not. Rust `rrule` and Ical.Net take the zone from the rule, not the process. With npm `rrule`, pin `TZ=UTC` for the process, or convert the results with the README's rules.

**Chew on this**

What `TZ` does each process that expands your recurrences run with, and is it the same in tests? If you moved recurrence expansion to the browser, whose time zone would it use?

**Sources**

- https://github.com/jkbrzt/rrule (the "Timezone support" section)
- https://www.rfc-editor.org/rfc/rfc5545#section-3.3.10

**Verified**

`rrule` and `process` typed with one-line `declare`s instead of their type packages. Run on Node 22.17.1 three times, with `TZ=UTC`, `TZ=America/Chicago` and `TZ=Asia/Tokyo`.

**Gotchas**

- Without `tzid`, a `dtstart` of 14:00Z stays 14:00Z every day, so in Chicago it is 9:00 AM before fall-back and 8:00 AM after (measured).
- `daily.toString()` prints `DTSTART;TZID=America/Chicago:20261031T090000 | RRULE:FREQ=DAILY;COUNT=3` (measured, newline shown as `|`): the stored rule is correct, and only the expansion depends on the host.
- The README recommends building `dtstart` with `Date.UTC(...)` or its `datetime()` helper: the UTC fields are read as wall-clock fields, which is why the snippet's `Date.UTC(2026, 9, 31, 9, 0)` means 09:00 Chicago.

# The functional angle: a recurrence is a lazy stream generated by a rule, and "skip, clamp or drift" is the rule's choice for impossible days

Draws on all four tips. A recurrence is `iterate(next, start)` filtered by validity. The three schedules come from three `next` functions:

```text
// RFC 5545:            occurrence(n) = anchor with month + n, KEPT only if that date exists      -> skip
// anchor arithmetic:   occurrence(n) = add(anchor, n months), clamped                            -> clamp
// previous arithmetic: occurrence(n) = add(occurrence(n - 1), 1 month), clamped                  -> drift
// The first two are functions of n; the third is a fold, so one clamp is inherited by every later value.
```

| Language | Skip (RFC 5545) | Clamp (from the anchor) | Drift (from the previous) | What it costs |
| --- | --- | --- | --- | --- |
| Rust | `rrule` crate | `jiff` `checked_add(n.months())` | a fold over `checked_add(1.month())` | a crate for the rule; std has none |
| C++ | none in std | none: `+ months{n}` refuses (`!ok()`) | none | you choose, after `ok()` tells you |
| F# / .NET | Ical.Net | `anchor.AddMonths n` | `previous.AddMonths 1` | the drift is the shape a scheduler naturally has |
| TypeScript | npm `rrule` | Temporal `anchor.add({ months: n })` | `previous.add({ months: 1 })` | the rule package's zone handling depends on the host |

Only the drifting version needs state. The asymmetry: the two stateless versions are functions of `n` and can be recomputed or tested for any occurrence directly, while the stateful one can only be tested by replaying the whole history.

Which of your schedules is a function of the occurrence number, and which is a fold that cannot be recomputed?

# The security angle: a scheduler that depends on the host's zone runs jobs at hours nobody approved

Draws on the TypeScript tip (Mode B: the rule is right, but is its expansion?). The library documents the behaviour. The gap is between the documentation and the deployment.

**Jobs at unintended times (CWE-1188, insecure default, where a library's default depends on the environment; closest class).** A maintenance window, a key rotation or a "send at 09:00 local" campaign expanded on a host whose `TZ` differs from the one it was tested on runs hours early or late. A window that should be quiet traffic hours lands in peak hours, and a rotation lands while the on-call person is asleep:

```ts
// TypeScript, illustrative (it reuses the TypeScript tip's measured behaviour).
// Looks like "rotate keys daily at 02:00 Chicago". On a TZ=Asia/Tokyo host it is 11:00 Chicago.
const rotation = new RRule({ freq: RRule.DAILY, dtstart: new Date(Date.UTC(2026, 9, 31, 2, 0)), tzid: "America/Chicago" })
```

| Language | What goes wrong | What the library does | Still on you |
| --- | --- | --- | --- |
| TypeScript (npm `rrule`) | expansion depends on the process `TZ` (measured) | documents it in the README | pin `TZ=UTC` for the scheduler, and test under a second `TZ` |
| Rust (`rrule` crate) | none measured: the zone comes from `DTSTART;TZID` | follows the rule | keep the zone in the rule |
| F# / .NET (Ical.Net) | none measured: `CalDateTime` carries the zone | follows the rule | same |
| C++ | no std recurrence | | whatever you build inherits your `zoned_time` choices |

The Rust crate and Ical.Net are the control: the rule carries its zone, and the host's zone is not an input.

Which of your scheduled jobs would move if the scheduler's container image changed its `TZ`?

# FAQ

**Is there an incident appendix for this part?** No. Recurrence bugs are common in issue trackers, but none found has a public post-mortem with first-hand detail of an outage.

**Which schedule is right for "monthly on the 31st"?** The one your users expect, which is usually `BYMONTHDAY=-1` ("the last day") for billing and the skipping rule for events that only make sense on that date. Whatever you pick, store the rule and the anchor, not the next occurrence.
