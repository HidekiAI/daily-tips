## Rust: slice::chunk_by compares neighbours, not the group's first element, so a tolerance window drifts

*Stdlib and ecosystem gems*

**Did you know**

`slice::chunk_by` (stable since 1.77) calls its predicate on every pair of consecutive elements, `slice[0]` with `slice[1]`, then `slice[1]` with `slice[2]`, and nothing else. It never sees the first element of the chunk it is building. So a predicate written as a tolerance, `later - earlier <= 3`, does not mean "within 3 of the group": it means "each step is within 3", and a chunk can span any distance in small steps. Measured below: a "3 ms burst" that spans 8 ms.

**Show me**

```rust
fn main() {
    let latencies_ms = [10, 12, 14, 16, 18, 40, 41];

    // Intent: "readings within 3 ms of each other form one burst".
    // chunk_by only ever sees (slice[k], slice[k + 1]), never the burst's first reading.
    let bursts: Vec<&[i32]> = latencies_ms
        .chunk_by(|earlier, later| later - earlier <= 3)
        .collect();
    println!("{bursts:?}"); // [[10, 12, 14, 16, 18], [40, 41]]

    // The first burst spans 8 ms: every step was <= 3, so the tolerance drifted.
    let spans_ms: Vec<i32> = bursts
        .iter()
        .map(|burst| burst[burst.len() - 1] - burst[0])
        .collect();
    println!("{spans_ms:?}"); // [8, 1]

    // Equality is the case where drift cannot happen, but adjacency still rules:
    // unsorted input gives one chunk per run, not one per key (unlike a GROUP BY).
    let statuses = ["ok", "ok", "err", "ok"];
    let runs: Vec<&[&str]> = statuses.chunk_by(|earlier, later| earlier == later).collect();
    println!("{runs:?}"); // [["ok", "ok"], ["err"], ["ok"]]
}
```

**Why it matters**

Bucketing latencies, timestamps or prices into windows is the usual reason to reach for this, and the drift is silent: the output still looks like plausible groups. It is also zero-allocation and slice-only, which is the price of looking at two elements: no state means no anchor. C++23's `views::chunk_by` has the same adjacent-pair contract and the same drift.

**Chew on this**

Which of your "group nearby values" code is really "group values reachable in small steps", and would anyone notice if the input got denser? If you need the anchor, is that still a `chunk_by`, or is it a fold that carries the group start?

## C++: A `<=` comparator lets std::sort read past your vector, and only from 17 elements (libstdc++) or 24 (libc++)

*Idioms and antipatterns*

**Did you know**

`std::sort` requires a strict weak ordering, and `<=` is not one: `comp(a, a)` must be false. The partition step of both libstdc++ and libc++ uses that guarantee as its loop sentinel, scanning "while `comp(*it, pivot)`" with no bounds check. With `<=` and equal keys the scan never stops on its own. Measured with GCC 14.2 / libstdc++ on Debian 13, C++20, `-O2`: 16 equal keys sort fine; from 17 AddressSanitizer reports a heap-buffer-overflow read, silent without it up to 32; from 33 most sizes end in SIGSEGV or a glibc heap-corruption abort (`free(): invalid pointer`, `malloc(): invalid next size`), so the scan's swaps write out of bounds too, while some sizes (49 to 64, 113 to 128, 241 to 256) still exit 0. Below 17 libstdc++ runs a guarded insertion sort (`_S_threshold = 16`). As a separate confirmation, on macOS with Apple clang 21 / libc++ 22 (`_LIBCPP_VERSION` 220106), C++20, `-O2`: 23 equal keys sort fine, 24 or more end in SIGSEGV or SIGBUS, and when the neighbouring memory happens to compare "less" the sort hangs instead. Below 24 libc++ runs a guarded insertion sort. Those cutoffs are why unit tests with a handful of rows pass.

**Show me**

```cpp
#include <algorithm>
#include <cstdio>
#include <cstdlib>
#include <vector>

struct Job { int priority; int id; };

int main(int argc, char** argv) {
    const int job_count = argc > 1 ? std::atoi(argv[1]) : 24;
    std::vector<Job> jobs;
    for (int job_id = 0; job_id < job_count; ++job_id) jobs.push_back({5, job_id});  // a quiet day: all priority 5

    // Reads like "lower priority first, ties allowed". It is not a strict weak ordering:
    // by_priority(job, job) is true, and the unguarded partition relies on it being false
    // to stop scanning. Below 17 elements (libstdc++) or 24 (libc++) a guarded insertion sort
    // runs, so tests pass.
    const auto by_priority = [](const Job& left, const Job& right) { return left.priority <= right.priority; };
    std::sort(jobs.begin(), jobs.end(), by_priority);

    // The fix is the operator, not the algorithm: '<' is irreflexive, so equal keys compare false both ways.
    std::sort(jobs.begin(), jobs.end(), [](const Job& left, const Job& right) { return left.priority < right.priority; });
    std::printf("sorted %zu jobs\n", jobs.size());
}
```

**Why it matters**

"All rows have the same priority" is exactly what production data looks like on a quiet day, and exactly what a 5-row test fixture is not. The failure is undefined behavior in the standard's terms and an out-of-bounds read in practice, plus out-of-bounds writes on libstdc++. On libc++, hardening `fast` turns it into a trap at the first bad step; only `debug` names the comparator, and it fires even at 5 elements because it tests `comp(a, a)` directly. On libstdc++ `_GLIBCXX_ASSERTIONS` does not catch it, and `_GLIBCXX_DEBUG` names the comparator at 5 elements.

**Chew on this**

How many comparators in your codebase are lambdas nobody tested with all-equal keys? Would you rather a release build trap on a bad comparator, or keep the cycles and trust review?

## F#: Seq.groupBy reads the whole input before it yields one group, and does it again on every enumeration

*Perf and memory model*

**Did you know**

`Seq.groupBy` returns a `seq`, so it looks lazy, and building it does run nothing. But the first `MoveNext` drains the entire source into buckets before yielding the first group, and each new enumeration does it all again. Measured on FSharp.Core 8.0.400 / .NET 8.0.8 (`dotnet fsi --optimize+`): one `Seq.head` over a million lines reads all million and allocates about 16.6 MB; a second `Seq.head` reads another million. FSharp.Core has no adjacent-run grouping at all (checked 8.0.400, 10.1.301 and 11.0.101-rc1), so there is no streaming alternative in the box.

**Show me**

```fsharp
// FSharp.Core 8.0.400, .NET 8.0.8, dotnet fsi
let mutable lines_read = 0 // a counter is the honest way to watch a seq; the shape forces the mutable
let access_log = seq { for line_number in 1 .. 1_000_000 do lines_read <- lines_read + 1; yield line_number }

let by_shard = access_log |> Seq.groupBy (fun line_number -> line_number % 3)
printfn "built: read %d" lines_read                       // 0: nothing has run yet

let first_shard = by_shard |> Seq.head
printfn "first group: read %d" lines_read                 // 1000000: the whole input, for one group

by_shard |> Seq.head |> ignore
printfn "again: read %d" lines_read                       // 2000000: re-enumeration re-reads AND re-buckets

let allocated_before = System.GC.GetAllocatedBytesForCurrentThread()
by_shard |> Seq.head |> ignore
printfn "allocated %d bytes for one Seq.head" (System.GC.GetAllocatedBytesForCurrentThread() - allocated_before)

// Seq.cache stops the re-read, not the buffering: the first group still needs every line.
lines_read <- 0
let cached_shards = by_shard |> Seq.cache
cached_shards |> Seq.head |> ignore
cached_shards |> Seq.head |> ignore
printfn "cached, twice: read %d" lines_read               // 1000000
```

**Why it matters**

`lines |> Seq.groupBy key |> Seq.iter handle` over a large file holds the whole file in memory, and passing `by_shard` to two consumers reads the file twice. On an infinite source (`Seq.initInfinite`, a socket) it builds fine and hangs on first use. The docs state this in a remark, not in the type.

**Chew on this**

Where do you pass a `seq` produced by `groupBy`, `sortBy` or `rev` to more than one consumer? If the input is already sorted by key, what do you write instead, given FSharp.Core will not hand you a run-based group?

## TypeScript: Temporal's valueOf throws, its types say never, and tsc still accepts `a < b`

*New discoveries and currently popular patterns*

**Did you know**

Temporal is on by default in Node 26 (released 2026-05-05, V8 14.6) and reached TC39 Stage 4 in March 2026. Every Temporal value's `valueOf` throws a `TypeError` on purpose, so the `Date` habits `a < b`, `a - b` and `Math.max(a, b)` throw at runtime. TypeScript ships `lib.esnext.temporal.d.ts` (6.0.3 and 7.0.2) with `valueOf(): never`, yet `tsc --strict` only rejects the arithmetic (TS2362). Relational operators on two objects are allowed, so `a < b` compiles and throws.

**Show me**

```typescript
declare const console: { log(...items: unknown[]): void };

const deployed_at: Temporal.Instant = Temporal.Instant.from("2026-10-20T09:00:00Z");
const rolled_back_at: Temporal.Instant = Temporal.Instant.from("2026-10-20T09:05:00Z");

// lib.esnext.temporal declares valueOf(): never, and tsc still accepts both of these.
const fnRolledBackLater = (): boolean => deployed_at < rolled_back_at;
const fnSortByLessThan = (events: Temporal.Instant[]): Temporal.Instant[] =>
    events.sort((left, right) => (left < right ? -1 : 1));   // the Date-era habit, ported

// Only arithmetic is rejected: TS2362 on `deployed_at - rolled_back_at`.

try { console.log(fnRolledBackLater()); } catch (error) { console.log((error as Error).message); }
try { fnSortByLessThan([rolled_back_at, deployed_at]); } catch (error) { console.log("sort:", (error as Error).name); }

// What works: a comparator the API ships, and an equals() that is not ===.
console.log([rolled_back_at, deployed_at].sort(Temporal.Instant.compare).map(String));
console.log(Temporal.Instant.from(deployed_at.toString()) === deployed_at, Temporal.Instant.from(deployed_at.toString()).equals(deployed_at));
```

```text
Do not use Temporal.Instant.prototype.valueOf; use Temporal.Instant.prototype.compare for comparison.
sort: TypeError
[ '2026-10-20T09:00:00Z', '2026-10-20T09:05:00Z' ]
false true
```

**Why it matters**

A `Date` to `Temporal` migration is mostly a find-and-replace on types, and the compiler will tell you about every subtraction. It will not tell you about the sort comparators and range checks, which are exactly the lines that run per request. The throw is the good outcome: the API refuses to give you a wrong answer, and the type system just does not say so ahead of time.

**Chew on this**

How many `<` and `>` comparisons on dates does your service have, and how would you find them once the type is no longer `Date`? Is a lint rule against relational operators on objects worth its false positives?

# The functional angle: grouping comes in two shapes, and only the adjacent one can stream

Draws on the Rust and F# tips; C++ and TypeScript rows added as comparisons.

"Group by" is two different functions. The **run** shape looks at neighbours and yields as it goes, but needs sorted input and can drift (Rust tip). The **bucket** shape is a real GROUP BY, but must see every element before yielding the first group (F# tip). No language here gives you both from one call.

```rust
// Run shape: lazy, zero-alloc, slice-only.
let runs = sorted_keys.chunk_by(|earlier, later| earlier == later);
// Bucket shape: std has no groupBy, so it is a HashMap fold, and the fold needs `mut`.
let buckets = keys.iter().fold(HashMap::new(), |mut buckets_so_far, key| { buckets_so_far.entry(*key).or_insert_with(Vec::new).push(*key); buckets_so_far });
```

```fsharp
// Bucket shape is the only one shipped; a run shape is a hand-written seq { } with state.
let buckets = keys |> Seq.groupBy id   // eager on first MoveNext, re-run per enumeration
```

| Language | Run shape (adjacent) | Bucket shape (hash) | What it costs |
| --- | --- | --- | --- |
| F# | not in FSharp.Core (8, 10, 11 checked) | `Seq/List/Array.groupBy` | bucket buffers all input, 16.6 MB per pass over 1M ints; `Seq` re-runs it per consumer |
| Rust | `slice::chunk_by` (1.77) | no std function | run is free but slice-only; bucket is a `HashMap` fold with a `mut` accumulator |
| C++ | `views::chunk_by` (C++23, libstdc++ 14 and libc++ 22 checked) | no std function | run is lazy and drifts the same way; bucket is a hand-rolled `unordered_map` loop |
| TypeScript | no std function | `Map.groupBy` / `Object.groupBy` (ES2024) | bucket drains the iterable (1M pulled for 3 groups, Node 26); run is hand-written |

The asymmetry worth noticing: Rust's bucket shape is the one place the immutability rule bends, because the accumulator is the data structure. F# hides the same mutation inside `groupBy`, which is why its version is a one-liner and also why it is eager.

Left hanging: if your input arrives sorted by key (a log by timestamp, a DB cursor with `ORDER BY`), which of your groupings are paying the bucket shape's memory for a run shape's problem?

# The security angle: one bad comparator, four personalities, and only one of them reads memory it does not own

Draws on the C++ tip (Mode B, then across languages). Direction: what each language does when the comparator breaks its contract. Class: CWE-125 (out-of-bounds read), from CWE-697 (incorrect comparison).

The same comparator in each language, all-equal keys, measured on Debian 13 (Docker, arm64; TypeScript as JS on Node 22.23.4, F# with `Array.sortInPlaceWith`), then on macOS as a separate confirmation:

```text
C++ (libstdc++ 14) [](auto& left, auto& right) { return left <= right; }     n>=17: OOB read (ASan); n>=33: mostly SIGSEGV / heap-corruption abort
Rust 1.99.1        |left, right| if left <= right { Less } else { Greater }    n up to 100000: returns, no panic
F# (.NET 10.0.402) fun left right -> if left <= right then -1 else 1         n=17 and up: ArgumentException
TypeScript (V8)    (left, right) => (left <= right ? -1 : 1)                 n up to 100000: returns, no error

macOS:
C++ (libc++ 22)   [](auto& left, auto& right) { return left <= right; }     n>=24: SIGSEGV / SIGBUS / hang
Rust 1.95         |left, right| if left <= right { Less } else { Greater }    n up to 100000: returns, no panic
F# (.NET 8.0.8)   fun left right -> if left <= right then -1 else 1         n=23 and up: ArgumentException
TypeScript (V8)   (left, right) => (left <= right ? -1 : 1)                 n up to 100000: returns, no error
```

The insecure sample is ordinary-looking code: a `<=` in a sort comparator, which passes review because it reads as "ties allowed". In C++ it becomes an unbounded scan driven by whatever memory sits next to your vector. Where data from outside decides how many equal keys arrive, the input decides whether the process crashes.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | unguarded partition scans past `begin()`/`end()` | nothing by default; libstdc++ `_GLIBCXX_DEBUG` and libc++ hardening `debug` name the comparator, libc++ `fast` traps, `_GLIBCXX_ASSERTIONS` does not catch it | use `<`, test with all-equal keys at n >= 33 (libstdc++) and n >= 24 (libc++), or n >= 17 under ASan; ship libc++ hardening `fast` in release |
| Rust | order is unspecified | stays memory-safe; result is a permutation, may panic (documented) | a panic on a request path is still a denial of service |
| F# / C# | .NET detects `compare(a, a) != 0` | throws `ArgumentException` "IComparer.Compare() method returns inconsistent results" | catch it or fix it; the throw is loud but it is per request |
| TypeScript | order is implementation-defined | no error, a permutation | nothing tells you; wrong order ships silently |

Rust is the control here: it shows the bug can be confined to "wrong order" with no memory consequence, so C++'s outcome is a choice of the implementation, not a law of sorting.

Left hanging: which of your sorts run over data whose duplicate count an outside caller controls?
