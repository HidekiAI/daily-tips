# Daily Tips special, part 15 of 15: random numbers, or the test that could only fail if you told it how, and the seed that says where

<!-- special-nav -->
**Specials:** [<- previous: random numbers, part 14 of 15](2026-11-04-extra-14-of-15.md) | (last special)

Not part of the rotation. The last part is about the thing the rest of the special needed: a way to run code that depends on randomness, fail, and run it again with the same result. A seed is only useful if you can find it after the failure, and a random test is only useful if the random inputs can reach the edge where the bug lives.

# What happened

**Bug class:** an integer overflow in a midpoint calculation, hidden for years because no test and no machine had an array big enough to reach it (CWE-190, integer overflow or wraparound). The same line sits in countless other programs. The reason it matters here is what it takes to find it with random tests.

**The story, in plain words:**

In 2006 Joshua Bloch, a software engineer at Google, published a short post with an alarming title: "Extra, Extra - Read All About It: Nearly All Binary Searches and Mergesorts are Broken". He remembered a lecture from his student years in which Jon Bentley, author of the book Programming Pearls, had asked every student to write a binary search and then dissected one of their implementations in front of the class. "Of course it was broken, as were most of our implementations." The key lesson was to carefully consider the invariants.

Then, in 2006, Bloch learned that the binary search which Bentley had proved correct in that book, and then tested, contained a bug. He told the story of how he found it: "The version of binary search that I wrote for the JDK contained the same bug. It was reported to Sun recently when it broke someone's program, after lying in wait for nine years or so."

The bug was one line, in Java and C alike: `int mid = (low + high) / 2;`. If `low + high` is larger than the biggest 32-bit integer, the sum "overflows to a negative value, and the value stays negative when divided by two". In Java that threw an array exception; in C it went out of bounds with unpredictable results. It needed an array of about a billion elements, which was "inconceivable back in the '80s" and "common these days at Google and other places".

A person, a proof and a test suite had all passed this line for two decades. A random test that draws small numbers passes it as well. The point of this part is the combination: a property test generates inputs, so it can find a bug no one thought of, but only if its generator can produce the inputs where the bug lives, and only if the seed that produced the failing input is printed so that the failure can be repeated.

The quotes, from Bloch's post (2 June 2006):

- "Of course it was broken, as were most of our implementations."
- "The version of binary search that I wrote for the JDK contained the same bug. It was reported to Sun recently when it broke someone's program, after lying in wait for nine years or so."
- "The sum overflows to a negative value, and the value stays negative when divided by two."
- "It is not sufficient merely to prove a program correct; you have to test it too. Moreover, to be really certain that a program is correct, you have to test it for all possible input values, but this is seldom feasible."

The measurements below test a naive midpoint with random tests in four languages and show what each tool prints so the failure can be replayed.

## Rust: proptest found a failing midpoint, saved it to a regression file, and on the next run failed with `successes: 0` before generating anything new

*Stdlib and ecosystem gems*

**Did you know**

`proptest` writes a failing case to `proptest-regressions/lib.txt` as a line starting `cc` and a hash, and replays it before any new random input on later runs. On rustc 1.99.1 the first run failed with "midpoint of 329956977 and 1817526671 came out as -1073741824" (`wrapping_add` of two positive numbers goes negative) and saved `cc bb912743...`; the second run failed with the same input and `successes: 0`, which means it failed before drawing a single new case. The regression file is meant to be committed to version control.

**Show me**

```rust
// proptest 1.x, rustc 1.99.1: the midpoint of two integers computed the naive way wraps around
pub fn midpoint_naive(low: i32, high: i32) -> i32 {
    low.wrapping_add(high) / 2
}

#[cfg(test)]
mod tests {
    use super::*;
    use proptest::prelude::*;

    proptest! {
        #[test]
        fn midpoint_stays_between_the_ends(low in any::<i32>(), high in any::<i32>()) {
            prop_assume!(low <= high);
            let middle: i32 = midpoint_naive(low, high);
            prop_assert!(low <= middle && middle <= high, "midpoint of {} and {} came out as {}", low, high, middle);
        }
    }
}
```

Output on the first run: the failure message above, `minimal failing input: low = 329956977, high = 1817526671`, `successes: 2`, and `proptest: Saving this and future failures in .../proptest-regressions/lib.txt`. Second run: the same input with `successes: 0`. (A fresh project gave a different pair, 291822398 and 1855661250, with `successes: 3`, and the same replay.) (`Cargo.toml` needs `proptest = "1"` under `[dev-dependencies]`.)

**Why it matters**

The saved line is the seed made durable: a failure in CI becomes a file in the repository, and the fix has a test that was failing yesterday. The shrinker did not reduce this input to a minimal pair here (it stopped at ten-digit numbers), which is a property of how this one failed.

**Chew on this**

Is your regression file committed? When a randomized test fails in CI, can someone replay it on their laptop in one command?

**Sources**

- https://altsysrq.github.io/proptest-book/proptest/failure-persistence.html
- https://research.google/blog/extra-extra-read-all-about-it-nearly-all-binary-searches-and-mergesorts-are-broken/

**Verified**

rustc 1.99.1, proptest 1.x from crates.io, `cargo test --release`, two runs. I did not read the book page in this session; the file behavior is measured.

**Gotchas**

- `prop_assume!(low <= high)` discards half of all draws; one global reject was reported.
- `wrapping_add` stands in for a language where overflow wraps; in debug builds plain `+` would panic instead.

## C++: Catch2 prints `Randomness seeded to: 1453372891`, and `--rng-seed 12345` replays the identical failing inputs

*Idioms and antipatterns*

**Did you know**

Catch2 v3 (3.7.1) seeds its random generators from the clock and prints the seed at the top of every run, as "Randomness seeded to: N". Run with `--rng-seed 12345` twice, it drew the same inputs: both runs failed on `low 1525746417 high 2070382655 middle -349419112`. Without the flag, a run printed a different seed and a different failing pair (`low 1101301505 high 2127393722`). Catch2 does not shrink a failing input; it reports the one it drew.

**Show me**

```cpp
// Catch2 v3, clang 19.1.7: random inputs, a seed printed at the top, and --rng-seed to replay
#include <catch2/catch_test_macros.hpp>
#include <catch2/generators/catch_generators.hpp>
#include <catch2/generators/catch_generators_adapters.hpp>
#include <catch2/generators/catch_generators_random.hpp>
#include <cstdint>
#include <limits>

std::int32_t midpoint_naive(std::int32_t low, std::int32_t high) {
    return static_cast<std::int32_t>(static_cast<std::uint32_t>(low) + static_cast<std::uint32_t>(high)) / 2; // wraps instead of undefined behavior
}

TEST_CASE("midpoint stays between the ends") {
    const std::int32_t first = GENERATE(take(200, random(std::numeric_limits<std::int32_t>::min(), std::numeric_limits<std::int32_t>::max())));
    const std::int32_t second = GENERATE(take(200, random(std::numeric_limits<std::int32_t>::min(), std::numeric_limits<std::int32_t>::max())));
    const std::int32_t low = first < second ? first : second;
    const std::int32_t high = first < second ? second : first;
    const std::int32_t middle = midpoint_naive(low, high);
    INFO("low " << low << " high " << high << " middle " << middle);
    REQUIRE((low <= middle && middle <= high));
}
```

Output of the first run (random seed): `Randomness seeded to: 1453372891` and a failure line `low 1101301505 high 2127393722 middle -533136034`. With `--rng-seed 12345`: `Randomness seeded to: 12345` and the same failing line every time. Build: `clang++ -std=c++20 -O1 midpoint.cpp -o t -lCatch2Main -lCatch2`.

**Why it matters**

Printing the seed is the whole replay contract: the value in the log is the value that reproduces. A test runner that does not print it makes every random failure an anecdote. And a failing input without shrinking is large and noisy, which is why property-based libraries (the Rust, F# and TypeScript tips here) add it.

**Chew on this**

Which of your test runners print the seed? If a nightly random test fails, is the seed in the first screen of the log?

**Sources**

- https://github.com/catchorg/Catch2/blob/devel/docs/command-line.md (`--rng-seed`)
- https://github.com/catchorg/Catch2/blob/devel/docs/generators.md

**Verified**

clang 19.1.7, Catch2 3.7.1, `-O1`, one build, three runs. The pair of seeds is from runs on this machine.

**Gotchas**

- The sum uses unsigned arithmetic so that the overflow wraps instead of being undefined behavior (Bloch's own C fix is the same cast).
- 200 x 200 combinations are drawn; most of them fail because random 32-bit pairs usually overflow.

## F#: FsCheck's default `int` generator produced values no larger than 50 in 1,000 samples, so the overflow property passed, and a full-range generator falsified it after 26 tests with a replay seed

*Idioms and antipatterns*

**Did you know**

FsCheck 3.3.2 sizes its generators: an `int` is drawn from a range that grows with the test size. In 1,000 samples from the default generator the largest absolute value was 50, against 2,147,483,647 for `Int32.MaxValue`. The property "the midpoint of low and high lies between them" therefore passed 1,000 tests with the default generator, on a midpoint that is broken for large values. With a generator over the whole `int` range the property was falsified after 26 tests, and the message carried the replay seed.

**Show me**

```fsharp
#r "nuget: FsCheck, 3.3.2"
open System
open FsCheck
open FsCheck.FSharp

let midpoint_naive (low: int) (high: int) : int = (low + high) / 2 // int arithmetic wraps in F# unless checked
let property_holds (low: int) (high: int) : bool = low > high || (let middle = midpoint_naive low high in low <= middle && middle <= high)

// what does the default int generator actually produce?
let default_samples: int list = Gen.sample 1000 (ArbMap.defaults |> ArbMap.generate<int> |> Gen.map id) |> Seq.toList
printfn "default int generator, 1000 samples: largest absolute value %d (Int32.MaxValue is %d)" (default_samples |> List.map abs |> List.max) Int32.MaxValue

let fn_message (check: unit -> unit) : string =
    try check (); "passed"
    with ex -> ex.Message.Replace("\n", " | ")
let default_config: Config = Config.QuickThrowOnFailure.WithMaxTest(1000)
printfn "default generator: %s" (fn_message (fun () -> Check.One(default_config, property_holds)))

let full_range: Arbitrary<int> = Gen.choose (Int32.MinValue, Int32.MaxValue) |> Arb.fromGen
let full_range_property: Property = Prop.forAll full_range (fun low -> Prop.forAll full_range (fun high -> property_holds low high))
printfn "full-range generator: %s" (fn_message (fun () -> Check.One(default_config, full_range_property)))
```

Output: `default int generator, 1000 samples: largest absolute value 50 (Int32.MaxValue is 2147483647)`, `Ok, passed 1000 tests.`, `default generator: passed`, and `full-range generator: Falsifiable, after 26 tests (0 shrinks) (8494244333304146880,6236104288816468067). ... Replay directly at failing step with (10501515186402166946,1827627429144135449,4). | Original: | -2136254736 | -999676811`. The seeds differ on every run; a second run falsified the property after 6 tests.

**Why it matters**

A passing property test with a narrow generator is a false assurance, the same shape as part 2's modulo bias: the test cannot fail because it cannot reach the failure. Bloch's overflow lives at the edge of the type's range, and the default generator does not go there. The tool still did the replay half right: the message carries the seed.

**Chew on this**

What range does your default generator cover? When did you last look at a histogram of what your property tests actually generate?

**Sources**

- https://fscheck.github.io/FsCheck/
- https://research.google/blog/extra-extra-read-all-about-it-nearly-all-binary-searches-and-mergesorts-are-broken/

**Verified**

.NET SDK 10.0, `dotnet fsi` with the `FsCheck 3.3.2` NuGet package. The "largest absolute value 50" is from my sample of 1,000 draws through `Gen.sample`, whose default size parameter may differ from what `Check.One` uses inside a run; the observation that the property passed 1,000 default tests is measured separately and stands on its own. FsCheck did not shrink the failing pair here (0 shrinks).

**Gotchas**

- F# `int` arithmetic is unchecked, so `(low + high) / 2` wraps silently; `Checked` operators would throw and be found immediately.
- The failing pair in the message is the original; shrinking depends on the generator being built with shrinkers (mine used `Arb.fromGen`, which has none).

## TypeScript: fast-check failed after 30 runs with seed 895575536 and the counterexample `[29, 2147483619]`, and replaying with that seed gave the identical counterexample

*Idioms and antipatterns*

**Did you know**

fast-check 4.10.2 on Node 26 failed the midpoint property after 30 runs, reduced it in 28 shrinks to `[29, 2147483619]` (a small number and a number just under the top of the 32-bit range, whose sum wraps), and printed its seed, 895575536. Run again with `{ seed: 895575536 }` it failed the same way with the same counterexample. Unlike the F# default, `fc.integer()` is full-range by default and mixes in edge values, so it reached the failure in 30 runs. The tool shrank to a pair that shows the bug at a glance: 29 plus 2,147,483,619 is 2,147,483,648, one past the maximum.

**Show me**

```ts
// fast-check, Node 26: a property that fails, a seed that replays it
import fc from "fast-check"

const const_fn_midpoint_naive = (low: number, high: number): number => (low + high) >> 1 // int32 arithmetic wraps
const const_fn_property = (low: number, high: number): boolean => low > high || (const_fn_midpoint_naive(low, high) >= low && const_fn_midpoint_naive(low, high) <= high)
const const_fn_run = (label: string, parameters: fc.Parameters<[number, number]>): { seed: number; counterexample: string } => {
    const details = fc.check(fc.property(fc.integer(), fc.integer(), const_fn_property), { ...parameters, numRuns: 1000 })
    console.log(label, details.failed ? `failed after ${details.numRuns} runs, ${details.numShrinks} shrinks, seed ${details.seed}, counterexample ${JSON.stringify(details.counterexample)}` : "passed")
    return { seed: details.seed, counterexample: JSON.stringify(details.counterexample) }
}
const first = const_fn_run("run 1 (random seed):", {})
const second = const_fn_run("run 2 (same seed): ", { seed: first.seed })
console.log("same counterexample on replay:", first.counterexample === second.counterexample)
```

Output: `run 1 (random seed): failed after 30 runs, 28 shrinks, seed 895575536, counterexample [29,2147483619]`, `run 2 (same seed):  failed after 30 runs, 28 shrinks, seed 895575536, counterexample [29,2147483619]` and `same counterexample on replay: true`. The seed and counterexample change from run to run: a second session gave `failed after 6 runs, 35 shrinks, seed -1771731926, counterexample [-1190364985,-957118664]`, where both numbers are negative and the sum wraps past the minimum, and replayed identically.

**Why it matters**

This is the full contract: random inputs find what nobody wrote a case for, shrinking reduces the finding to something a person can read, and the seed lets anyone reproduce it. The generator reached the edge by design, and the example shows that the three features have to come as a set.

**Chew on this**

When a property test in your project fails, does the log give you a seed and a small counterexample, or a large random input and a shrug?

**Sources**

- https://fast-check.dev/docs/core-blocks/runners/ (the `seed` parameter)
- https://research.google/blog/extra-extra-read-all-about-it-nearly-all-binary-searches-and-mergesorts-are-broken/

**Verified**

Node v26.13.0 in the `node:lts` image with fast-check 4.10.2 from npm, one session of two runs. I did not read the fast-check documentation in this session; the replay is measured.

**Gotchas**

- `>> 1` makes the JavaScript sum an int32, which wraps like the C and Java in Bloch's post; plain `/ 2` on doubles would not overflow.

# The functional angle: a random test is a pure function of its seed

Draws on all four tips. A property test is `run(seed, property) -> Pass | Fail(counterexample)`. Given the seed, it is a pure function, and everything useful (replay, regression files, shrinking) follows from treating the seed as the one input that carries the randomness.

```fsharp
// F#: a replayable random test is a function of its seed, with no hidden state
let fn_find_counterexample (seed: int) (property: int -> int -> bool) : (int * int) option =
    let rng: System.Random = System.Random(seed)
    Seq.init 1000 (fun _ -> rng.Next(), rng.Next()) |> Seq.tryFind (fun (low, high) -> not (property low high))
printfn "%A %A" (fn_find_counterexample 7 (fun low high -> low <= high)) (fn_find_counterexample 7 (fun low high -> low <= high))
```

This sample ran and printed the same pair twice (equal inputs, equal result).

| Language | What prints the seed | What replays it | Shrinks |
| --- | --- | --- | --- |
| Rust (proptest) | a `cc` line in a file | the file, automatically | yes (stopped early here) |
| C++ (Catch2) | `Randomness seeded to: N` | `--rng-seed N` | no |
| F# (FsCheck) | `(a,b)` and a step seed in the message | `Replay` in the config | not with `Arb.fromGen` |
| TypeScript (fast-check) | `seed` in the result | `{ seed }` | yes (28 shrinks) |

TypeScript is the baseline because it was the only one of four that gave seed, small counterexample and edge-reaching generator in one run. Which of the four would you want in the log at three in the morning?

# The security angle: a recorded seed is a recorded secret

Draws on all four tips. Mode B (what the test tooling does not prevent). Bug classes: CWE-190 for the midpoint, CWE-337 and CWE-532 (information exposure through log files) for the seed.

```ts
// TypeScript: a test seed in a CI log is harmless; a production seed in a log is a credential
console.log("seed", seed)   // fine in a test; never in a service that derives a key from the seed
```

This is a comment-level sample. The special's thread is that a seed is state; a test seed is state worth printing, and a production seed is state worth hiding. Two things cross the line: a test harness left enabled in production (part 1), and a replayable generator used for a secret (part 4). The shared rule is to keep seeds out of anything an attacker reads, and keep test generators out of anything an attacker uses.

| Language | A test-time seed is | A production-time seed is |
| --- | --- | --- |
| Rust | in `proptest-regressions` | never logged; `rand::rng()` seeds from the OS |
| C++ | the first line of Catch2's output | `random_device`, not logged |
| F# | in the FsCheck message | `RandomNumberGenerator` has none to log |
| TypeScript | in the fast-check result | `crypto.getRandomValues` has none to log |

Rust is the baseline because its saved seeds sit in a file that is meant to be committed, which is the clearest picture of "state worth keeping" in a test directory. What in your repository would be a problem if it were a secret and is not treated like one?

# FAQ

**Does the midpoint bug from Bloch's story, in Java and C, need a big array?**
In Bloch's account it needed an array of about a billion elements for binary search; the probes here feed the midpoint two numbers directly, which is why they fail at once.

**Why does the default generator of F#'s FsCheck never overflow?**
It sizes values by a growing parameter. In my sample the largest value was 50; a property that needs large values needs a generator that produces them.

**Is a replayable test enough?**
Replayable means the same failure on demand. It does not mean the failure is in the code under test: a test can also fail because of the generator, so the seed should be logged with the library versions.

# What this special measured

Fifteen parts, each with a story from a source I could read and a measurement in Rust, C++, F# and TypeScript. The recurring facts: a seed fixes the engine and almost nothing above it (part 1); mapping a random number to a range is where bias and boundary values enter (parts 2, 3, 8, 9); generators fail by their seed (4), their API choice (5), their sharing across threads and processes (6, 7), their state being recoverable (10), their audit (11, 12), their birth (13) and their fit to what people expect (14); and the way to live with all of it is to make the seed an explicit, recorded input (15).

Sources that refused automated access were retried slowly, at most three times each, and then left alone. Where an archive copy existed I used it and said so, and this led to appendices on Betable (part 2), Enigma and Pokemon Emerald (part 4), Venona and Tunny (part 8), the NES (part 9), Minecraft (part 10), slot machines and clinical trials (part 11), and Dual EC and Crypto AG (part 12). One item is still unread: SIGSALY (part 5, Appendix A), whose NSA pages refused every request. If you find the NSA brochure on it, the appendix says what I would like to know.
