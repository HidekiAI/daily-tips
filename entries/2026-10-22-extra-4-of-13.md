## Rust: `jsonwebtoken` accepts a token 60 seconds after `exp`, never checks `nbf`, and treats a millisecond `exp` as valid until the year 58778

*Stdlib and ecosystem gems*

**Did you know**

In the Rust `jsonwebtoken` crate (11.1.0), `Validation::default()` sets `leeway = 60`, `validate_exp = true` and `validate_nbf = false`. A token whose `exp` passed 59 seconds ago is accepted, and one with an `nbf` an hour in the future is accepted too. Nothing checks the unit of `exp`. A JS issuer that writes `Date.now()` (milliseconds) produces a token that, read as seconds, expires in the year 58778. Measured, not just read from the source.

**Show me**

```rust
// Rust: jsonwebtoken 11.1.0 (feature rust_crypto), serde_json 1, rustc 1.95.0
use jsonwebtoken::{decode, encode, DecodingKey, EncodingKey, Header, Validation};
use serde_json::{json, Value};
use std::time::{SystemTime, UNIX_EPOCH};

fn main() {
    let secret = b"demo-secret-not-for-production";
    let now_secs = SystemTime::now().duration_since(UNIX_EPOCH).unwrap().as_secs();
    let fn_verdict = |claims: Value, rules: &Validation| {
        let token = encode(&Header::default(), &claims, &EncodingKey::from_secret(secret)).unwrap();
        match decode::<Value>(&token, &DecodingKey::from_secret(secret), rules) {
            Ok(_) => "ACCEPTED".to_string(),
            Err(error) => format!("rejected: {error}"),
        }
    };

    // Validation::default(): leeway = 60 s, validate_exp = true, validate_nbf = false
    let defaults = Validation::default();
    println!("{}", fn_verdict(json!({ "sub": "alice", "exp": now_secs - 59 }), &defaults)); // ACCEPTED
    println!("{}", fn_verdict(json!({ "sub": "alice", "exp": now_secs - 61 }), &defaults)); // rejected: ExpiredSignature
    // A JS issuer that wrote Date.now() (milliseconds) into exp:
    println!("{}", fn_verdict(json!({ "sub": "alice", "exp": now_secs * 1000 }), &defaults)); // ACCEPTED
    // Not valid for another hour, and nobody looks:
    let not_yet = json!({ "sub": "alice", "exp": now_secs + 7200, "nbf": now_secs + 3600 });
    println!("{}", fn_verdict(not_yet.clone(), &defaults)); // ACCEPTED

    let mut strict = Validation::default();
    strict.leeway = 0;
    strict.validate_nbf = true;
    println!("{}", fn_verdict(not_yet, &strict)); // rejected: ImmatureSignature
    println!("{}", fn_verdict(json!({ "sub": "alice", "exp": now_secs * 1000 }), &strict)); // ACCEPTED: no rule checks the unit
}
```

**Why it matters**

Leeway exists because issuer and verifier clocks disagree, and 60 s is a reasonable tolerance. It is also one minute in which a revoked or logged-out token still works, on top of whatever lifetime the issuer chose. The default differs in every language (table above): 60 s in Rust, 300 s in .NET, 0 in npm `jsonwebtoken` and C++ `jwt-cpp`. A token that passes a 0-second verifier in Node can be accepted for five extra minutes by a .NET service reading the same claims. Rust and its crates evolve, and these defaults are a crate's choice, not the language's: versions measured are named.

**Chew on this**

What lifetime do your tokens have, and what is it once each verifier's leeway is added? If an issuer started writing milliseconds tomorrow, which of your services would notice first, and how?

**Sources**

- https://docs.rs/jsonwebtoken/11.1.0/jsonwebtoken/struct.Validation.html
- https://datatracker.ietf.org/doc/html/rfc7519#section-4.1.4
- https://github.com/Keats/jsonwebtoken

**Gotchas**

- An `exp` sent as a string (`"1792700000"`) is rejected with `Missing required claim: exp` (measured). The claim is present, but the error says it is missing, which misleads whoever reads the log.
- A floating-point `exp` (`now + 300.5`) is accepted (measured). RFC 7519 allows a fractional NumericDate.
- `strict.leeway = 0` plus `validate_nbf = true` fixes skew and `nbf`, but still accepts the millisecond `exp` (measured). Only an explicit upper bound you write yourself (`exp <= now + max_lifetime`) catches it.
- Leeway applies to `nbf` too, in the other direction: with the default 60, a token becomes valid up to a minute early once `validate_nbf` is on (read from the source: `nbf > now + leeway`).

## C++: `sys_info::save` is -60 min for Europe/Dublin in January, so `save != 0min` calls an Irish winter "DST"

*Idioms and antipatterns*

**Did you know**

In C++20 `std::chrono`, `sys_info::save` is "the DST offset". For `Europe/Dublin` in January it is **-60 min**, and in July it is 0. Irish law defines summer time (IST, Irish Standard Time) as the standard and winter GMT as the deviation, and tzdata models that with a negative saving. So `get_info(t).save != 0min`, the obvious "is DST in effect?", answers yes in a Dublin January. Measured with libstdc++ in GCC 14 and GCC 16.2, both reading Debian 13's tzdata 2026c. Apple's libc++ has no tzdb at all (`_LIBCPP_HAS_TIME_ZONE_DATABASE 0`), so on a Mac this code does not compile.

**Show me**

```cpp
// C++20 std::chrono tzdb: GCC 14.x and 16.2 (libstdc++), tzdata 2026c on Debian 13
#include <chrono>
#include <cstdio>
#include <string>
using namespace std::chrono;

int main() {
    const sys_seconds january = sys_days{2026y/January/15} + 12h;

    // "Is DST in effect?" written the obvious way:
    auto fn_is_dst = [&](const char* name) { return locate_zone(name)->get_info(january).save != 0min; };
    std::printf("London DST in January: %d\n", fn_is_dst("Europe/London"));  // 0
    std::printf("Dublin DST in January: %d\n", fn_is_dst("Europe/Dublin"));  // 1: save is -60min
    // Irish law makes summer (IST, Irish Standard Time) the standard time,
    // so tzdata models winter GMT as a negative saving.

    // The sign of an Etc zone is POSIX-style: GMT+5 is FIVE HOURS BEHIND UTC.
    sys_info gmt_plus_5 = locate_zone("Etc/GMT+5")->get_info(january);
    std::printf("Etc/GMT+5 offset: %ld min\n", (long)duration_cast<minutes>(gmt_plus_5.offset).count()); // -300

    // An abbreviation is a label, not a key: count the zones that answer to "CST".
    int answering_cst = 0;
    for (const time_zone& zone : get_tzdb().zones)
        if (zone.get_info(january).abbrev == "CST") ++answering_cst;
    std::printf("zones abbreviated CST: %d\n", answering_cst);  // 29: Chicago, Shanghai, Havana...
}
```

**Why it matters**

"Is it DST?" drives display strings ("CDT" vs "CST"), billing for "summer rates", and a lot of hand-written offset arithmetic. The `offset` field is always right: Dublin is +00:00 in January and +01:00 in July. The `save` field is a policy label, and Ireland's policy is the inverse of the UK's next door. The same question gets a different answer by OS. Debian 13's tzdata marks Dublin's **winter** as `isdst=1`, while macOS and Ubuntu 24.04 (tzdata 2026e) mark its **summer** as `isdst=1` (measured with `zdump`). Rust `jiff` on macOS reads the OS data and says `Dst::No` in January. .NET normalizes on both macOS and Ubuntu: `IsDaylightSavingTime` is false in January and true in July.

**Chew on this**

Where does your code branch on "is DST" rather than on the offset itself, and what does that branch do for Dublin? If your servers run Debian and your laptops run macOS, which answer do your tests see?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/sys_info
- https://github.com/eggert/tz/blob/main/europe (the Europe/Dublin "Vanguard" and "Rearguard" sections)
- https://github.com/eggert/tz/blob/main/etcetera ("Be consistent with POSIX TZ settings in the Zone names, even though this is the opposite of what many people expect.")

**Verified**

Run in `docker run gcc:14` and `docker run gcc:16` (Debian 13, tzdata 2026c). Not runnable on this host's Apple clang, which has no tzdb. MSVC not tested.

**Gotchas**

- `Etc/GMT+5` is UTC**-5**, and its abbreviation is `-05` (measured). tzdata keeps the POSIX sign in `Etc/` names, where positive means west.
- `"CST"` is the January abbreviation of 29 zones in tzdata 2026c, including `America/Chicago` (-06), `Asia/Shanghai` (+08) and `America/Havana` (-05) (measured). Anything that maps an abbreviation back to a zone is guessing.
- Dublin's summer abbreviation `IST` is also the abbreviation of `Asia/Kolkata` (+05:30) and `Asia/Jerusalem` (+02:00 in January), measured.
- tzdata ships Dublin in two forms: "vanguard" with the negative saving, and "rearguard" for parsers that cannot handle it. Which one your OS ships decides the `isdst` flag, not the zone's actual offsets (inferred from the `zdump` results above).

## F#: `DateTimeOffset.Parse` turns RFC 3339's "offset unknown" into +00:00, and a missing offset into the server's own zone

*Stdlib and ecosystem gems*

**Did you know**

RFC 3339 (section 4.3) gives `-00:00` a meaning: "the time in UTC is known, the local offset is not". .NET's `DateTimeOffset.Parse` reads it as `+00:00`, so the "unknown" is lost. A string with no offset at all gets the **server's** offset (`-05:00` under `TZ=America/Chicago`), and an exact format with `K` does the same, because `K` also matches "no offset". Nine fractional digits are rounded to seven (`.123456789` becomes `.1234568`). A leap second `23:59:60`, which RFC 3339 allows, fails. So do ISO 8601's week dates and basic format. Measured identically on FSharp.Core 8.0 / .NET 8.0.8 and FSharp.Core 10.1 / .NET 10.0.13.

**Show me**

```fsharp
// F#: DateTimeOffset parsing, FSharp.Core 8.0 / .NET 8.0.8 and FSharp.Core 10.1 / .NET 10.0.13
open System
open System.Globalization

let fn_parse (text: string) =
    match DateTimeOffset.TryParse(text, CultureInfo.InvariantCulture, DateTimeStyles.None) with
    | true, value -> value.ToString("o")
    | false, _ -> "FAILED"

// Run with TZ=America/Chicago (CDT, -05:00 on this date)
printfn "%s" (fn_parse "2026-10-22T12:00:00-00:00")      // +00:00: "offset unknown" became "offset zero"
printfn "%s" (fn_parse "2026-10-22T12:00:00")            // -05:00: no offset became the SERVER's offset
printfn "%s" (fn_parse "2026-10-22T12:00:00.123456789Z") // .1234568: 9 digits rounded to 7
printfn "%s" (fn_parse "2026-10-22T23:59:60Z")           // FAILED: RFC 3339 allows :60
printfn "%s" (fn_parse "2026-W43-4T12:00:00Z")           // FAILED: an ISO 8601 week date
printfn "%s" (fn_parse "20261022T120000Z")               // FAILED: ISO 8601 basic format

// An exact format does not rescue the missing offset: K also matches "nothing".
let fn_parse_exact (format: string) (text: string) =
    match DateTimeOffset.TryParseExact(text, format, CultureInfo.InvariantCulture, DateTimeStyles.None) with
    | true, value -> value.ToString("o")
    | false, _ -> "FAILED"
printfn "%s" (fn_parse_exact "yyyy-MM-dd'T'HH:mm:ss.FFFFFFFK" "2026-10-22T12:00:00")   // -05:00 again
printfn "%s" (fn_parse_exact "yyyy-MM-dd'T'HH:mm:ss.FFFFFFFzzz" "2026-10-22T12:00:00") // FAILED
printfn "%s" (fn_parse_exact "yyyy-MM-dd'T'HH:mm:ss.FFFFFFFzzz" "2026-10-22T12:00:00Z") // FAILED: zzz refuses Z
```

**Why it matters**

"ISO 8601" in an API spec usually means "whatever the producer's library emits", and .NET's parser is a profile of ISO 8601, not all of it. The dangerous line is the one that parses: a payload missing its offset is read in the server's zone, so the same request means different instants on a Chicago host and a UTC container. No exception is thrown and no log line is written. Rust `jiff` refuses the same string ("failed to find offset component, which is required for parsing a timestamp"). JS `Date` does what .NET does and reads it as local. C++ `chrono::parse` cannot even read the common `Z` form with `%Ez` (all measured in the functional angle below).

**Chew on this**

Which of your inbound timestamps would still parse if the producer dropped the offset tomorrow, and in which zone would your service read them? Is there a single format string that accepts exactly what your API documents, and nothing else?

**Sources**

- https://datatracker.ietf.org/doc/html/rfc3339#section-4.3
- https://learn.microsoft.com/en-us/dotnet/standard/base-types/custom-date-and-time-format-strings#KSpecifier
- https://learn.microsoft.com/en-us/dotnet/api/system.datetimeoffset.parse

**Gotchas**

- `"o"` on a `DateTime` with `Kind = Unspecified` prints `2026-10-22T12:00:00.0000000` with no offset (measured). That string is not valid RFC 3339, and the next parser reads it in its own local zone.
- `DateTime.Parse` of a `-00:00` string returns `Kind = Local` (measured): it converted the instant to the server's zone and dropped the offset.
- Parse is lenient where RFC 3339 is lenient, too: lowercase `t`/`z` and a space instead of `T` all parse (measured). The exact format with `'T'` rejects all three.
- `zzz` needs a numeric offset and refuses `Z`, and `K` accepts both and also "nothing". Neither one, used alone, matches exactly "RFC 3339, offset required".

## TypeScript: Node reads `process.env.TZ` live and never validates it, so a typo is silent UTC, `UTC-5` is five hours east, and a `string` comes back `undefined`

*Idioms and antipatterns*

**Did you know**

Assigning `process.env.TZ` inside a running Node process changes the zone of every `Date` and every default `Intl` formatter immediately. A misspelled zone raises no error and falls back to UTC. `Intl.DateTimeFormat().resolvedOptions().timeZone`, which TypeScript types as `string`, then returns `undefined`. `TZ=UTC-5` is a POSIX TZ string, where positive means west, so it puts the process five hours **east** of UTC. `TZ=CST` labels the time "Central Standard Time" and computes it as UTC. All measured on Node 22.17.1 and Node 26.12.1.

**Show me**

```ts
// TypeScript 6.0.3 types, run on Node 22.17.1 (host TZ America/Chicago) and Node 26.12.1
const instant = new Date("2026-10-22T17:00:00Z")
const fn_show = (): string =>
    `${instant.toString().slice(16)} | Intl zone: ${Intl.DateTimeFormat().resolvedOptions().timeZone}`

console.log(fn_show())          // 12:00:00 GMT-0500 (Central Daylight Time) | Intl zone: America/Chicago
process.env.TZ = "Asia/Tokyo"   // read live: every Date in the process moves at once
console.log(fn_show())          // 02:00:00 GMT+0900 (Japan Standard Time) | Intl zone: Asia/Tokyo
process.env.TZ = "Asia/Tokio"   // a typo: no error, silently UTC
console.log(fn_show())          // 17:00:00 GMT+0000 (GMT) | Intl zone: undefined
process.env.TZ = "UTC-5"        // POSIX sign: this means five hours EAST of UTC
console.log(fn_show())          // 22:00:00 GMT+0500 (GMT+05:00) | Intl zone: undefined
process.env.TZ = "CST"          // labelled Chicago, computed as UTC
console.log(fn_show())          // 17:00:00 GMT+0000 (Central Standard Time) | Intl zone: America/Chicago

process.env.TZ = "Asia/Tokio"
const zone: string = Intl.DateTimeFormat().resolvedOptions().timeZone  // tsc: string
try { console.log(zone.toUpperCase()) }
catch (error) { console.log((error as Error).message) }  // Cannot read properties of undefined
```

**Why it matters**

`TZ` is set by Dockerfiles, Helm charts and CI runners, nearly always by hand, and nothing checks it at startup. A typo in one deployment makes its logs and its "today" UTC while every other deployment stays local, with no error anywhere. `TZ=CST` is worse: the logs say "Central Standard Time" next to a UTC clock reading, so anyone reading them is off by five or six hours. .NET does not read a changed `TZ` at all until `TimeZoneInfo.ClearCachedData()` is called (measured: `TimeZoneInfo.Local.Id` stayed `America/Chicago` until then). Node is the only one of the four where a single assignment moves the whole process.

**Chew on this**

What does each of your services print for `resolvedOptions().timeZone` right now, and would you notice if one said `undefined`? Which library in your dependency tree might be assigning `process.env.TZ` at import time?

**Sources**

- https://nodejs.org/api/cli.html#tz
- https://tc39.es/ecma402/#sec-intl.datetimeformat.prototype.resolvedoptions
- https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html (the POSIX `TZ` format and its sign)

**Verified**

`console` and `process` typed with one-line `declare`s instead of `@types/node`. Node 22 runs on the host, and Node 26 in `docker run node:26`.

**Gotchas**

- `TZ=""` gives `Etc/Unknown` as the zone, not `undefined` and not UTC by name, while the clock reads UTC (measured).
- `TZ=EST5EDT` gives `America/New_York` on Node 22 and `EST5EDT` on Node 26 (measured). The bundled ICU differs between versions.
- `TZ=":America/Chicago"`, the POSIX leading-colon form, works (measured).
- The `node:26` image with `TZ` unset is UTC (`/etc/localtime -> Etc/UTC`, measured), so a container and a laptop running the same code disagree by default.

# The functional angle: a timestamp parser is a partial function, and each language picked a different domain

Draws on the F# tip (`DateTimeOffset.Parse`), with Rust `jiff`, JS `Date` and C++ `std::chrono::parse` as peer rows. The same 11 strings went through each one. A `parse: string -> instant option` is only as good as the set of strings it maps to `Some`, and the interesting failures are the strings that map to `Some` of the wrong instant.

```text
// Every value below was printed by a real run (TZ=America/Chicago for the "no offset" column)
// .NET 8 and .NET 10: DateTimeOffset.TryParse, invariant culture
// Rust jiff 0.2.38:   "...".parse::<jiff::Timestamp>()
// JS Node 22.17.1:    new Date("...")
// C++ GCC 16.2:       std::chrono::parse("%FT%T%Ez") and parse("%FT%TZ")
```

| Input | F# / .NET | Rust `jiff` | JS `Date` | C++ `%FT%T%Ez` |
| --- | --- | --- | --- | --- |
| `...T12:00:00Z` | ok | ok | ok | FAILED (needs `%FT%TZ`, which then refuses `+05:00`) |
| `...T12:00:00` (no offset) | server zone, -05:00 | ERR "offset component required" | server zone, 17:00Z | FAILED |
| `...T12:00:00-00:00` | +00:00, "unknown" lost | 12:00Z | 12:00Z | 12:00Z |
| `.123456789Z` (9 digits) | rounded to `.1234568` | kept, all 9 | truncated to `.123` | FAILED (`%FT%TZ` keeps 9) |
| `...T23:59:60Z` | FAILED | clamped to `23:59:59` | Invalid Date | FAILED |
| `20261022T120000Z` (basic) | FAILED | ok | Invalid Date | FAILED |

| Language | Functional form | What it costs |
| --- | --- | --- |
| Rust | `str::parse::<Timestamp>`, a `Result` | the only one that refuses a missing offset; it silently clamps `:60` |
| F# | `TryParse` returning `bool * DateTimeOffset`, matched | total on far too much: a missing offset is filled in from the machine |
| TypeScript | `new Date(text)`, `NaN` as the failure value | the same machine-zone guess, millisecond precision, and the failure is not in the type |
| C++ | `parse` into a stream, `fail()` as the failure | the format string IS the domain: one string cannot accept both `Z` and `+05:00` |

None of the four is pure. The "no offset" row reads the process environment, which makes the parse depend on where it ran. Only Rust's domain excludes it.

Which of these columns is your API's contract, and which one is your parser's?

# The security angle: a token's lifetime is the issuer's number plus a verifier's default, and the defaults disagree by five minutes

Draws on the Rust tip (Mode A across libraries: what each JWT library does by default) and the TypeScript tip (Mode B: is a silent `TZ` fallback only cosmetic?). Here the language prevents nothing. Every default below is a library's choice.

**Leeway and missing checks (CWE-613, insufficient session expiration).** The insecure sample is ordinary code:

```ts
// TypeScript, npm jsonwebtoken 9.0.3: looks like "issue a 15-minute token". Is a token that never expires.
const token = jwt.sign({ sub: "alice", exp: Date.now() + 15 * 60 * 1000 }, secret) // exp in MILLISECONDS
jwt.verify(token, secret)  // ACCEPTED, and it stays accepted until the year 58778
```

```rust
// Rust, jsonwebtoken 11.1.0: looks like "validate the token". Leaves nbf unchecked and exp 60 s soft.
let claims = decode::<Value>(&token, &key, &Validation::default())?;
```

| Language (library, version) | What goes wrong | What the library does | Still on you |
| --- | --- | --- | --- |
| Rust (`jsonwebtoken` 11.1.0) | `exp` + 60 s accepted; `nbf` ignored; ms `exp` accepted (measured) | requires `exp` by default | set `leeway` and `validate_nbf` on purpose; bound `exp - now` yourself |
| TypeScript (npm `jsonwebtoken` 9.0.3) | no `exp` at all is accepted; ms `exp` accepted (measured) | 0 s tolerance; checks `nbf` (measured) | require `exp` (`maxAge` or your own check) and bound it |
| F# / C# (`Microsoft.IdentityModel.Tokens` 8.23) | `exp` + 5 min accepted (`DefaultClockSkew = 00:05:00`, measured) | the 5-minute skew is the documented default | set `ClockSkew` to what your clocks actually need |
| C++ (`jwt-cpp`, header read) | nothing by default here: `default_leeway{0}` | checks `exp`, `iat`, `nbf` when present | not compiled here; check your vendored version's verifier |

There is no control row: these are library policies, and the type systems see only an integer. The only fix that works in all four is the one no library ships: reject any `exp` further in the future than your maximum token lifetime, which catches the millisecond mistake and a forged far-future token alike.

**A silent `TZ` fallback is a log-integrity problem (closest class: CWE-778, insufficient logging; no advisory, the failure is a configuration one).** A service whose `TZ` is mistyped logs in UTC with no error, and `TZ=CST` logs a UTC clock under a "Central Standard Time" label. Incident timelines built from two such services disagree by hours, and the label tells the investigator the wrong one is right.

Which of your verifiers would accept a token your issuer considers expired, and for how long?

# FAQ

**Is `Etc/GMT+5` a tzdata bug?** No. It is deliberate and documented in the tzdata `etcetera` file: "Be consistent with POSIX TZ settings in the Zone names, even though this is the opposite of what many people expect." C++ tzdb, .NET `TimeZoneInfo`, Rust `jiff` and Node all agree it is -05:00 (measured). The same POSIX sign is why Node's `TZ=UTC-5` is +05:00.

**Is RFC 3339 the same as ISO 8601?** No. RFC 3339 is a profile of ISO 8601 that adds things ISO 8601 does not have: `-00:00` as "offset unknown" (section 4.3), a space allowed in place of `T`, and lowercase `t`/`z`. It also drops much of ISO 8601: week dates, ordinal dates, the basic format without separators, and times without seconds. .NET accepts part of both and all of neither (measured above).

**Does .NET pick up a changed `TZ` like Node does?** Not until you ask. After `Environment.SetEnvironmentVariable("TZ", "Asia/Tokyo")`, `TimeZoneInfo.Local.Id` stayed `America/Chicago`. After `TimeZoneInfo.ClearCachedData()` it became `Asia/Tokyo` (measured, .NET 8.0.8).

**Why does Dublin report `isdst=1` in winter on Debian but in summer on macOS?** tzdata publishes Dublin with a negative saving in its main ("vanguard") data, plus a "rearguard" form for parsers that cannot handle negative DST. Debian 13's tzdata 2026c behaves like the first, and macOS and Ubuntu 24.04's tzdata 2026e like the second (measured with `zdump -v`). The offsets are identical in both: only the flag moves.

# Appendix A: Turkey 2014-2016, a government changes the rule and the phones keep the old one

_Not part of the tip rotation. Added 2026-10-22, backing this part's thesis that the offset is data and the label is not. A real incident, not folklore: the account below is quoted from the tzdata source file itself, where the maintainers record why each rule changed, plus the tz mailing list and Wikipedia (A.5). The transitions in A.2 were printed by `zdump -v Europe/Istanbul` on macOS and on Debian 13 (tzdata 2026c), which agree line for line._

**Bug class:** Not a code bug: stale data. The code applied its rule table correctly; the table predated the rule. Root-cause anti-pattern: trusting a rule table shipped with the device for a rule that changes at short notice.

## A.1 What happened, in tzdata's own words

- **2014, a moved spring-forward.** "The DST for Turkey has been changed for this year because of the Turkish Local election" (Faruk Pasin, 2014-02-14): clocks would move forward on March 31 instead of March 30. A traveller who landed in Istanbul on March 31 reported that "NOBODY (even the airlines) respected this timezone DST change delay". Paul Eggert, the tz maintainer: "The press reported massive confusion, as election officials obeyed the rule change but cell phones (and airline baggage systems) did not."
- **2015, a moved fall-back.** "Turkey delays winter time to 8th of November 04:00" (announced 2015-09-29). Devices with old tzdata fell back on October 25 anyway. The file quotes BBC News (2015-10-25): "Confused Turks are asking 'what's the time?' after automatic clocks defied a government decision." On the tz list, Eggert wrote that his Android phone still had the old Istanbul rules while his Fedora and Ubuntu desktops had the new ones.
- **2016, no fall-back at all.** Turkey stayed on UTC+3 permanently. Eggert (2016-09-07): "The change is permanent, so this is the new standard time in Turkey. It takes effect today, which is not much notice."

## A.2 What tzdata records now

```text
# zdump -v Europe/Istanbul, both hosts, excerpt
Mon Mar 31 01:00:00 2014 UT = Mon Mar 31 04:00:00 2014 EEST isdst=1 gmtoff=10800   <- moved a day for the election
Sun Nov  8 01:00:00 2015 UT = Sun Nov  8 03:00:00 2015 EET  isdst=0 gmtoff=7200    <- moved two weeks
Tue Sep  6 21:00:00 2016 UT = Wed Sep  7 00:00:00 2016 +03  isdst=0 gmtoff=10800   <- label change only
```

The 2016 line is this part's thesis in one row. The offset stays at 10800 seconds before and after. Only the abbreviation (`EEST` to `+03`) and the DST flag (1 to 0) change. A program that keys on `isdst` or the abbreviation sees a transition at midnight on 2016-09-07. A program that keys on the offset sees nothing, which is correct.

## A.3 Why the phones were wrong

This section is inference from the sources, not a quote. A phone that syncs from the network or NTP keeps the instant right. What was stale was its rules, because tzdata ships inside each OS and each runtime (part 1's tzdata tip), and an update has to reach every device before the date it covers. Turkey announced the 2015 change about four weeks ahead (2015-09-29 for 2015-10-25), and the 2016 one took effect the day the tz list heard of it. Wherever the offset came from a local rule table instead of from the network, the clock showed the old rule.

## A.4 Back to the tips

The C++ tip's `save != 0min` and the TypeScript tip's `TZ` both trust a label. Turkey shows the label changing while the offset does not (2016), and the offset changing on a date only a fresh rule table knows (2014, 2015). Store instants. Resolve a zone ID with the newest tzdata you can ship. Treat abbreviations and DST flags as display text.
