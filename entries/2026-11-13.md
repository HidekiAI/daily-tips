## Rust: A child with a piped stdout that writes 65,537 bytes hangs `wait()` forever, and 65,536 bytes does not

*Stdlib and ecosystem gems*

**Did you know**

`Child::wait` closes the child stdin before it waits, which the docs say is to avoid a deadlock, and does nothing about a piped stdout. A Linux pipe holds 64 KiB, so a child that writes more than that blocks in `write()` while the parent blocks in `waitpid()`. Measured on rustc 1.99.1 in Debian 13.7 (kernel 7.0.14): a child writing 65,536 bytes exited and `wait()` returned, and at 65,537 bytes `wait()` was still blocked after 2 seconds. `wait_with_output()` drains both pipes and returned all 1,048,576 bytes.

**Show me**

```rust
use std::process::{Command, Stdio};

fn main() {
    let report_job = Command::new("head")
        .args(["-c", "65537", "/dev/zero"]) // one byte past the 64 KiB Linux pipe buffer
        .stdout(Stdio::piped())
        .spawn()
        .expect("spawn head");

    // mut_report_job.wait() here hangs: the child is blocked in write(),
    // the parent in waitpid(). (wait() takes &mut self, hence the mut_ name.)

    // Fix: wait_with_output() drains stdout and stderr together, so neither
    // pipe can fill up, and only then reaps the child.
    let report_output = report_job.wait_with_output().expect("collect child output");
    println!("{} bytes, {}", report_output.stdout.len(), report_output.status);
}
```

The snippet printed `65537 bytes, exit status: 0`. Call `wait()` instead of `wait_with_output()` and it never prints at all.

**Why it matters**

A sidecar call (a dump tool, a converter, a health-check script) passes every test with small output, then hangs a request worker the first time its output passes 64 KiB: no error, no timeout, no log line. The siblings split three ways. .NET documents the same deadlock for `Process.WaitForExit` before `StandardOutput.ReadToEnd`. Node refuses instead of hanging: `execFileSync` returned 1,048,576 bytes and threw `ENOBUFS` at 1,048,577, its default `maxBuffer`. The C++ standard library can start a command only through `std::system`, with no way to read its output, so the behaviour is whatever `popen` or the library you picked does.

**Chew on this**

Which of your spawned commands writes output whose size you do not control, and what bounds the wait: the pipe buffer, a timeout, or nothing? If you read stdout and stderr yourself, in which order, and what happens when the child fills the other one first?

**Sources**

- https://doc.rust-lang.org/std/process/struct.Child.html#method.wait
- https://doc.rust-lang.org/std/process/struct.Child.html#method.wait_with_output
- https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.standardoutput

**Verified**

The Node row ran on Node 26.13.1 in Debian 13.7. The .NET row and the C++ remark rest on documentation alone and were not run.

**Gotchas**

- Dropping the stdout handle before `wait()` does not hang, it kills: the child got `SIGPIPE` and `wait()` returned `ExitStatus(unix_wait_status(13))`, so `status.success()` is false although the child did nothing wrong.
- 65,536 is the pipe capacity of this kernel, not a Rust constant. `/proc/sys/fs/pipe-max-size` read 1,048,576 here, which is how far an unprivileged process may raise one pipe, so the same binary can hang at a different size on another host.

## C++: `for (const std::pair<std::string, T>& entry : map)` copies every element, because the map holds `pair<const std::string, T>`

*Idioms and antipatterns*

**Did you know**

The `value_type` of `std::map<K, T>` is `std::pair<const K, T>`. Spell the loop variable as `const std::pair<K, T>&` and the types no longer match, so the compiler converts each element into a temporary pair and binds the reference to that. Measured with `-std=c++20 -O2` on GCC 16.2.0 and Debian clang 19.1.7 (Debian 13.7): 3 copies for 3 entries, and `&const_entry.second` was not the address of the value in the map. Both compilers flag it with `-Wrange-loop-construct`, but only under `-Wall`, and with no warning flags both are silent; the conversion rule is C++11, and structured bindings, the cleanest fix, are C++17.

**Show me**

```cpp
// C++20. GCC 16.2.0 and Debian clang 19.1.7 printed the same three lines.
#include <cstdio>
#include <map>
#include <string>
#include <utility>

static int copy_count = 0;
struct Tracked {
    const int const_amount;
    Tracked(const int const_start_amount) : const_amount(const_start_amount) {}
    Tracked(const Tracked& const_other) : const_amount(const_other.const_amount) { ++copy_count; } // count every copy
};

int main() {
    std::map<std::string, Tracked> balances;
    balances.emplace("alice-account-0001", 10);
    balances.emplace("bob-account-0002", 20);
    balances.emplace("carol-account-0003", 30);

    // The map stores std::pair<const std::string, Tracked>. This names a pair
    // without the const, so every iteration converts into a temporary and the
    // reference binds to that copy, not to the element.
    for (const std::pair<std::string, Tracked>& const_entry : balances) { (void)const_entry; }
    std::printf("pair<string, Tracked>:       %d copies\n", copy_count); // 3

    copy_count = 0;
    for (const std::pair<const std::string, Tracked>& const_entry : balances) { (void)const_entry; }
    std::printf("pair<const string, Tracked>: %d copies\n", copy_count); // 0

    copy_count = 0;
    for (const auto& [const_name, const_value] : balances) { (void)const_name; (void)const_value; } // C++17
    std::printf("structured binding:          %d copies\n", copy_count); // 0
}
```

**Why it matters**

In a hot loop over a map with string keys, every iteration copies the key and the value, and each copied key longer than the small-string buffer allocates: 3 allocations for the three 18-character keys above, on both compilers. A pointer or reference taken to `const_entry.second` inside the loop points into the temporary, which dies at the end of the iteration: a dangling reference once anyone uses it (closest class `CWE-825`, expired pointer dereference). Rust cannot express the mistake: `for (name, value) in &balances` yields `(&String, &Tracked)` borrows, and binding one to an owned `(String, Tracked)` is E0308, a type error rather than a conversion. F# and C# iterate a `Dictionary` as `KeyValuePair` structs, which are copied by value every step by design, though for reference-typed keys and values the copy is two references, not two objects.

**Chew on this**

How many of your range-for loops spell out the element type instead of `auto`, and would each one still compile if the container held a slightly different type? Which of your build targets compile hot paths without `-Wall`?

**Sources**

- https://en.cppreference.com/w/cpp/container/map
- https://en.cppreference.com/w/cpp/language/range-for

**Verified**

The allocation count was measured on GCC 16.2.0 and Debian clang 19.1.7 by counting `operator new` calls, and the Rust E0308 on rustc 1.100.0. The F# and C# `KeyValuePair` remark rests on documentation alone and was not run.

**Gotchas**

- The bug survives only in the const form. A non-const `std::pair<std::string, int>&` does not compile on GCC 16.2.0: "cannot bind non-const lvalue reference ... to an rvalue", so the form people write for reading is exactly the form that copies.
- `const std::map<std::string, Tracked>::value_type&`, `const auto&` and `const auto& [const_name, const_value]` all measured 0 copies, so naming the type through the container is as safe as `auto`.
- The diagnostic names the fix: both compilers suggest `const std::pair<const std::basic_string<char>, Tracked>&`, or a non-reference type "to make the copy explicit".

- [2026-09-03](2026-09-03.md) - C++, "Range-for over a temporary's subobject was a use-after-free until C++23". The other way a range-for reference ends up bound to something that dies early.

## F#: F# refuses `=` on a record with a function field, and accepts it on one with an interface field, which then compares by reference

*Type system deep cuts*

**Did you know**

A record is structurally equal only as deep as its fields can be. A function-typed field makes the record fail the `equality` constraint, and the FS0001 error lands on the line that compares, not on the type. An interface-typed field passes, because every .NET type satisfies `equality` unless it carries `[<NoEquality>]`, so the record compiles and `=` falls back to the field's `Object.Equals`: reference identity for a class. Measured on F# 10 (the SDK default), FSharp.Core 10.1.0, .NET 10.0.15: two records with equal names and two separately built loggers compared `false`, had different hashes, and `List.distinct` kept both.

**Show me**

```fsharp
type ILogger = abstract write: string -> unit
type ConsoleLogger(prefix: string) =
    interface ILogger with
        member _.write message = printfn "%s%s" prefix message

// Compiles: ILogger meets the equality constraint, as every .NET type does
// unless it carries [<NoEquality>]. The record then compares logger with
// Object.Equals, which for a class is reference identity.
type Handler = { name: string; logger: ILogger }

let first_handler = { name = "audit"; logger = ConsoleLogger "> " }
let second_handler = { name = "audit"; logger = ConsoleLogger "> " }
let shared_logger = ConsoleLogger "> "

printfn "%b" (first_handler = second_handler) // false: two loggers
printfn "%b" ({ first_handler with logger = shared_logger } = { second_handler with logger = shared_logger }) // true
printfn "%d" (List.distinct [ first_handler; second_handler ] |> List.length) // 2

// A function field is refused, and FS0001 lands on the line that compares,
// not on the type declaration:
// type Job = { name: string; run: unit -> unit }
// let job_check (left: Job) (right: Job) = left = right   // FS0001 here
```

**Why it matters**

A config or handler record used as a dedupe key or cache key quietly stops deduping the day someone adds a dependency field (a logger, a clock, an HTTP client): no compile error, because interfaces pass the constraint. Rust refuses at the declaration instead: `#[derive(PartialEq)]` on a struct holding `Box<dyn Logger>` failed with E0369, "binary operation `==` cannot be applied to type `Box<dyn Logger>`". C++20 behaves like F#: a defaulted `operator==` over a `std::shared_ptr<Logger>` member compiled cleanly under `-Wall -Wextra` on GCC 16.2.0 and compared the pointers, `0` for two loggers and `1` for a shared one. TypeScript never pretended: `===` is reference identity on every object.

**Chew on this**

Which of your records mix data with dependencies, and which code compares or hashes them? If `[<NoEquality>]` went on them today, which call sites would stop compiling, and is each of those a bug you already have?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/generics/constraints
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/records

**Verified**

Run with `dotnet fsi` from the .NET 10 SDK image, which is Ubuntu 24.04, not Debian.

**Gotchas**

- `[<NoEquality; NoComparison>]` turns the silent case into the loud one: `left = right` on such a record failed with FS0001 "because it has the 'NoEquality' attribute".
- Comparison is stricter than equality. The same interface record that accepts `=` was refused by `Set.ofList` with FS0001 "does not support the 'comparison' constraint", so `Set` and `Map` catch the problem while `List.distinct` and `=` do not.
- Sharing one logger instance makes the records equal again (`true` above), so a test that builds fixtures from one shared dependency passes while production, which builds one per request, does not.

- [2026-10-14](2026-10-14.md) - F#, "= says two NaN records differ and .Equals says they match". Another place where record equality is only as good as its fields.
- [2026-10-27](2026-10-27-extra-12-of-12.md) - F#, "A record with a mutable field keeps structural equality". Another way a record compiles with `=` and still misleads a `HashSet`.

## TypeScript: Every `Promise.race` against one long-lived pending promise leaves 256 bytes on it, so a million calls held 244 MiB on Node 26.13.1

*Perf and memory model*

**Did you know**

`Promise.race` subscribes to each input with `.then`, and a promise that never settles keeps every reaction it was ever given. Race each job against one process-wide shutdown promise and every iteration adds to that promise. Measured on Node 26.13.1 (V8 14.6) with `--expose-gc`: a million races grew the heap by about 244 MiB after collection (244.2 and 244.1 MiB in two runs), 256 bytes per race, while racing a fresh pending promise each time grew it by about 0 MiB. The Node issue was closed in 2017 as spec-conforming behaviour, and a 2026 comment on it says Node 26.5.0 fixed the larger part of the leak; the 256 bytes per race is what was still measured on 26.13.1.

**Show me**

```typescript
// Lives as long as the process and settles only at shutdown.
const const_shutdown_signal: Promise<void> = new Promise<void>(() => {});

async function next_job(): Promise<number> { return 1; }

async function worker_loop(job_limit: number): Promise<number> {
    let processed_count = 0;
    while (processed_count < job_limit) {
        // Looks stateless. Each call subscribes to const_shutdown_signal with .then,
        // and a pending promise keeps every subscription it ever received:
        // 256 bytes per call on Node 26.13.1, until const_shutdown_signal settles.
        const const_job_id_or_shutdown: number | void = await Promise.race([const_shutdown_signal, next_job()]);
        if (const_job_id_or_shutdown === undefined) break;
        processed_count += 1;
    }
    return processed_count;
}

// The measured alternative: race against a promise made for this iteration
// (about 0 MiB retained over a million races), and have the one shutdown handler
// settle whichever promise is current.
void worker_loop(3).then((processed_count: number) => console.log(processed_count));
```

**Why it matters**

A worker loop, a stream reader or a per-connection handler that races each read against a shutdown or close promise grows for as long as the process runs, and the heap snapshot shows promise reactions, not anything you allocated. `tsc --strict` has nothing to say: the types are correct. .NET is the nearest sibling, since a `Task` also keeps a continuation list, so `Task.WhenAny` against one forever-pending task is the same shape; whether .NET removes those continuations was not measured here. Rust and C++ do not share the shape: a Rust future is polled rather than subscribed to, and C++ `std::future` has no race combinator at all.

**Chew on this**

Which promises in your service live as long as the process or the connection, and what calls `.then`, `race` or `await` on them per request? At 256 bytes a request, how many requests does your service handle between restarts?

**Sources**

- https://github.com/nodejs/node/issues/17469

**Verified**

The heap numbers are from Node 26.13.1 in Debian 13.7; the snippet type-checked with `tsc --strict` 7.0.2. The .NET, Rust and C++ remarks were not run, and the Node 26.5.0 partial fix rests on the issue comment alone.

**Gotchas**

- An `async` function that returns the long-lived promise adopts it and never settles: raced against a 200 ms timer it was "still pending after 200 ms", and a top-level `await` on one made Node exit with code 13 and "Detected unsettled top-level await".
- The retention belongs to the long-lived promise, not to the loop: once nothing holds the pending promise, its reactions go with it, which is why the fresh-promise-per-iteration run measured about 0 MiB.

**Related**

- [2026-11-09](2026-11-09.md) - TypeScript, "Promise.race([]) never settles". The other way a race over a promise that never settles costs you, there by hanging, here by growing.

# The functional angle: structural equality stops at the first field that has none, and only Rust refuses at the declaration

Draws on the F# tip. One shape in four languages: a value type whose equality is derived from its fields, with one field that is a behaviour rather than data.

```rust
// Rust: refused where the type is declared
trait Logger { fn write(&self, message: &str); }
#[derive(PartialEq)]
struct Handler { name: String, logger: Box<dyn Logger> } // E0369 on rustc 1.99.1
```

```cpp
// C++20: compiles silently and compares the pointers
struct Handler {
    const std::string const_name;
    const std::shared_ptr<Logger> const_logger;
    bool operator==(const Handler&) const = default; // no warning under -Wall -Wextra
};
```

| Language | Derived equality | Measured | What it costs |
| --- | --- | --- | --- |
| F# | record `=` | `false` for two loggers, `true` for one shared | silent reference fallback on an interface field; `[<NoEquality>]` moves the error to every comparison site |
| Rust | `#[derive(PartialEq)]` | E0369 at the derive | you write `PartialEq` by hand and decide what the logger means for equality, once, at the type |
| C++20 | `operator== = default` | `0` for two loggers, `1` for one shared | silent pointer comparison, the F# behaviour; the opt-out is `= delete` or a hand-written `operator==`, not an attribute |
| TypeScript | none; `===` | not measured, true by definition | every object is reference-compared, so a deep equal is a library decision and so is its treatment of functions |

The asymmetry worth noticing: F# and C++ both decided that "this field has some equality" is good enough, and both picked reference identity as that equality. Rust is the only one that asks whether the field type has the equality you meant.

Left hanging: when a value carries a dependency, is the dependency part of the value at all, or should the type that gets compared never have held it?

# The security angle: waiting on something an outsider controls, a child's pipe or a promise's lifetime, turns input size or count into a denial of service

Draws on the Rust and TypeScript tips (Mode B), and runs in the "does not prevent" direction: neither language stops either bug, and both pass every test with small inputs.

```rust
// Rust: looks like a thin wrapper around a converter, and hangs the worker
// as soon as the converted output passes 64 KiB, which the uploader controls.
fn convert_upload(upload_path: &std::path::Path) -> std::io::Result<std::process::ExitStatus> {
    let mut mut_converter = std::process::Command::new("convert-tool")
        .arg(upload_path)
        .stdout(std::process::Stdio::piped()) // piped, never read
        .spawn()?;
    mut_converter.wait() // closest class CWE-833 (deadlock), on a full pipe instead of a lock
}
```

```typescript
// TypeScript: one connection-lifetime promise, raced once per message.
// Each message leaves 256 bytes on `closed` until the client disconnects,
// so a client that never disconnects and sends forever grows the heap forever.
async function serve_connection(closed: Promise<void>, fn_read_message: () => Promise<string>): Promise<void> {
    for (;;) {
        const const_message: string | void = await Promise.race([closed, fn_read_message()]); // CWE-401
        if (const_message === undefined) return;
    }
}
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `wait()` with an unread piped stdout hangs at 65,537 bytes | closes stdin before waiting, nothing for stdout | `wait_with_output()`, or `Stdio::null()` when you do not need the output, plus a timeout around the whole call |
| JavaScript (Node.js `execFileSync`) | output past 1 MiB | refuses with `ENOBUFS` at 1,048,577 bytes, measured | handle the error; do not raise `maxBuffer` to whatever an uploader can produce |
| .NET | `WaitForExit` before `ReadToEnd` deadlocks, per its docs | documents it, does not prevent it | read the stream first, then wait; not run here |
| TypeScript promises | 256 bytes per race on a promise that never settles | spec-conforming, so nothing | a promise per iteration, or bounded lifetimes for anything raced in a loop |

Control: JavaScript, through Node.js `execFileSync`, is the baseline for the process half, because it is the only one of the four that turns unbounded child output into an error by default (`CWE-400` handled by refusing).

Left hanging: which of your request paths run a child process or race a long-lived promise on input whose size or duration someone outside your service chooses?
