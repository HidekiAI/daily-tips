## Rust: impl Future hides the type but not Send, so one Rc held across an await breaks a caller you never touched

*Type system deep cuts*

**Did you know**

A return-position `impl Trait` hides everything about the concrete type except its auto traits. `Send`, `Sync`, `Unpin` and `UnwindSafe` leak through, and the caller sees them. So two functions with the same signature, `fn handler() -> impl Future<Output = usize>`, can differ in whether they are `Send`. If you hold an `Rc` across an `.await` inside one of them, every caller that needs `Send` (`tokio::spawn`, a `Send` bound of your own) stops compiling, and the error points at the caller.

**Show me**

```rust
// Rust, edition 2021 (2024 behaves the same here). rustc 1.99.1.
use std::future::Future;
use std::rc::Rc;

async fn tick() {}

// The public signature never mentions Send.
pub fn handler_v1() -> impl Future<Output = usize> {
    async {
        let hits: usize = 1;
        tick().await;
        hits
    }
}

// Same signature. A private Rc held across an await changes what callers may do.
pub fn handler_v2() -> impl Future<Output = usize> {
    async {
        let hits: Rc<usize> = Rc::new(1);
        tick().await;
        *hits
    }
}

// Stands in for tokio::spawn, which requires Send.
fn require_send<T: Send>(_future: T) {}

fn main() {
    require_send(handler_v1()); // compiles: the hidden type is Send, and that leaks
    require_send(handler_v2()); // error: "future cannot be sent between threads safely"
}
```

**Why it matters**

Auto-trait leakage is why `impl Future` is usable at all in a work-stealing runtime: nobody has to write `+ Send` on every async helper. The price is that the hidden type's auto traits are part of your API, so a change to a private body can break the build of a crate downstream. RFC 1522 says it outright: removing an auto trait "has to be considered a silent breaking change". `Box<dyn Future + Send>` does not leak anything: you get only what you wrote, and you must write it. C++ has no counterpart, because a returned `auto` is the concrete type, fully visible. F# and TypeScript have no auto traits.

**Chew on this**

Which of your public async helpers are `Send` only by accident of what their bodies happen to hold today? Would you rather write `+ Send` on the signature and own the promise, or let it leak and find out from someone else's build?

**Sources**

- https://rust-lang.github.io/rfcs/1522-conservative-impl-trait.html (section "OIBIT transparency")
- https://blog.rust-lang.org/2023/12/21/async-fn-rpit-in-traits/
- https://github.com/rust-lang/rust/issues/109417 (return type notation, still unstable)

**Gotchas**

- The error lands on the caller (`leak.rs:28`, the `require_send(handler_v2())` line). A note then points into the body at the `.await` on line 19, "with `hits` maybe used later". The function whose body changed reports nothing.
- `async fn` in a trait does not leak. A generic caller, `fn spawn_generic<H: Handler + Send + Sync>(handler: &H) { require_send(handler.handle()) }`, fails with E0277 "`impl Future<Output = usize>` cannot be sent between threads safely". That happens even though the only impl is `Send`, and the same call on the concrete type compiles. rustc's help says `Send` has to become part of the method's guarantees, so the trait author must decide, either with `-> impl Future<Output = usize> + Send` or with the `trait-variant` crate.
- The caller-side fix, `where H::handle(..): Send`, is return type notation, and on rustc 1.99.1 it is still E0658 "return type notation is experimental".
- The leak runs through type checking, so two functions in one crate that each check the other's `Send` form a cycle. `fn first() -> impl Sized { require_send(second()); 1u8 }` next to its mirror gives E0391 "cycle detected when computing type of opaque `first::{opaque#0}`".

- [2026-10-05](2026-10-05.md) - Rust, "In edition 2024 a returned impl Trait borrows every argument". The same opaque type: that tip was about the lifetimes it captures, this one is about the auto traits it leaks.

## C++: C++26 reflection sees only what the calling code may access, so a generic serializer drops private fields without a word

*New discoveries and currently popular patterns*

**Did you know**

GCC 16 ships P2996R13, "Reflection for C++26" (GCC 16.1, April 2026; measured here on 16.2.0). You switch it on with `-std=c++26 -freflection`. `-std=c++26` alone does not turn it on. Every member query takes an `access_context`. With `access_context::current()` you get only the members accessible from the point of the call. Inside a free function template, that means the public ones. `unchecked()` returns everything. Nothing warns you that the two results differ.

Support state: GCC 16.1 onward with `-freflection`. Bloomberg's `clang-p2996` fork is the experimental reference implementation. I did not check upstream Clang 23.1 (August 2026, "partial C++26") or MSVC for P2996.

**Show me**

```cpp
// C++26, g++ 16.2.0: g++ -std=c++26 -freflection refl.cpp
#include <meta>
#include <print>
#include <string_view>

class Account {
public:
    int id = 7;
    std::string_view owner = "ops";
private:
    long balance_cents = 12345;   // the field an audit log needs
    friend void dump_as_friend(const Account&);
};

template <typename T>
void dump(const T& value) {
    // current(): only what is accessible from HERE, a free function template.
    constexpr auto ctx = std::meta::access_context::current();
    // template for is an expansion statement (also C++26): one loop body per member.
    template for (constexpr std::meta::info member :
                  std::define_static_array(std::meta::nonstatic_data_members_of(^^T, ctx))) {
        std::println("  {} = {}", std::meta::identifier_of(member), value.[:member:]);
    }
}

void dump_as_friend(const Account&) {
    constexpr auto ctx = std::meta::access_context::current();
    constexpr auto count = std::meta::nonstatic_data_members_of(^^Account, ctx).size();
    std::println("  friend sees {} members", count);      // prints 3
}

int main() {
    constexpr auto everything = std::meta::access_context::unchecked();
    constexpr auto all_count = std::meta::nonstatic_data_members_of(^^Account, everything).size();
    std::println("unchecked sees {} members", all_count); // prints 3
    dump(Account{});                                      // prints id and owner only
    dump_as_friend(Account{});
}
```

**Why it matters**

The first thing everyone writes with reflection is a generic `to_json`, `operator<<` or audit dump. Written the way the paper's examples are, with `current()`, it compiles. It runs, and it leaves out every private field. The output still looks complete, because nothing marks the gap. That is the conservative default, and it is the right one. Rust's `serde` derive runs inside the type's own module, so it sees private fields and you opt them out with `#[serde(skip)]`. C++ reflection starts from the opposite end, and you opt in with `unchecked()` or friendship.

**Chew on this**

When a reflected serializer grows a field list, who should decide which fields go out: the type, by friendship or an annotation, or the serializer, by picking an access context? Which of those would you want to find in a code review a year from now?

**Sources**

- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p2996r13.html
- https://gcc.gnu.org/gcc-16/changes.html ("P2996R13, Reflection (PR120775, enabled by `-std=c++26 -freflection`)")
- https://isocpp.org/blog/2026/04/gcc-16.1

**Verified**

The member counts and outputs were measured on g++ 16.2.0 (Debian-based `gcc:16` image). I could not read the paper's library wording for `access_context`: the fetched copy was cut off before that section. So the filtering rule rests on GCC's behaviour, not on quoted standard text.

**Gotchas**

- Without `-freflection`, g++ 16.2 rejects the file with "'std::meta' has not been declared". `-std=c++26` alone is not enough.
- `std::println("{}", nonstatic_data_members_of(^^Account, everything).size())` is an error: "consteval-only expressions are only allowed in a constant-evaluated context". Bind the count to a `constexpr` first, as `all_count` does.
- Access is checked from where you call, not from what you name. The same `current()` call inside a `friend` function sees all 3 members, so one friend declaration changes what a generic dump prints.
- `-Wall -Wextra` gave no diagnostic about the dropped field. The only warning was an unused parameter.

- [2026-10-26](2026-10-26.md) - C++, "GCC 16 ships C++26 contracts, and -std=c++26 alone compiles them but does not link". The same release, and again `-std=c++26` is not the whole story: contracts compile and then fail to link, and reflection does not compile at all.

## F#: InlineIfLambda changed nothing for a one-line lambda and saved 27% on a five-line one, and in Debug it does nothing at all

*Perf and memory model*

**Did you know**

`inline` copies a higher-order function's body into the caller, but it does not promise to inline the lambda you pass in. On FSharp.Core 10.1 and .NET 10, a one-line lambda was inlined either way. A five-line lambda was not. The compiler turned it into a static method (`map_value@3`) and called it once per element: no allocation, but 202 ms against 148 ms with `[<InlineIfLambda>]` on the parameter. A Debug build turns off inlining entirely. There, both versions allocate a 24-byte closure on every call, and the attribute does nothing.

**Show me**

```fsharp
// F# (LangVersion latest), FSharp.Core 10.1.0.0, .NET 10.0.13, Release build.
// The two helpers differ only by the attribute on map_value.
let inline sum_with (map_value: int -> int64) (count: int) : int64 =
    let mutable total = 0L
    for index in 0 .. count - 1 do
        total <- total + map_value index
    total

let inline sum_with_inlined ([<InlineIfLambda>] map_value: int -> int64) (count: int) : int64 =
    let mutable total = 0L
    for index in 0 .. count - 1 do
        total <- total + map_value index
    total

// One line: both compile to the same 32 bytes of IL, lambda inlined.
let plain (offset: int64) (count: int) = sum_with (fun index -> int64 index + offset) count

// Five lines: without the attribute, the body is lifted to a static method map_value@3
// (91 bytes of IL) and called per element; with it, the caller grows to 184 bytes.
let plain_big (offset: int64) (count: int) = sum_with (fun index ->
    let widened = int64 index
    let mixed = (widened * 31L + offset) ^^^ (widened >>> 3)
    let folded = if mixed % 7L = 0L then mixed / 7L else mixed * 3L
    let clamped = if folded > 1_000_000L then folded - 1_000_000L else folded + offset
    (clamped ^^^ (clamped <<< 5)) + (if clamped % 2L = 0L then offset else -offset)) count
// inlined_big is the same lambda passed to sum_with_inlined.
// 1M calls x 100 elements, after warm-up:
//   Release  plain_big 202 ms   inlined_big 148 ms   both 0.0 bytes/call
//   Debug    every variant ~220-270 ms, 24.0 bytes/call
```

**Why it matters**

A helper library of `inline` combinators (`iter_range`, `sum_by`, a parser's `many`) is where people reach for this attribute, and where the result is hardest to predict. Short lambdas are free with or without it. Longer ones pay a call per element, and that call blocks the optimizer from seeing across the loop. Nothing allocates, so an allocation profiler shows nothing either. Rust's `impl Fn` parameter and a C++ template parameter both give the compiler the lambda's type, and so its body, at every call site. F# passes a plain function value, and the attribute is how you ask for the same treatment.

**Chew on this**

If your benchmark only runs in Release and your profiler only counts allocations, which of your `inline` helpers would you ever catch paying a call per element? Is a 184-byte caller a better trade than a 35-byte one plus a call in your hottest loop?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/functions/inline-functions
- https://github.com/fsharp/fslang-design/blob/main/FSharp-6.0/FS-1098-inline-if-lambda.md

**Verified**

The IL sizes come from `MethodBody.GetILAsByteArray().Length` via reflection over the Release assembly, not from a disassembler. The "static method" description rests on the type listing: there is no closure class and there is a `map_value@3` method on `Program`. Measured on Debian (`debian-test`, SDK 10.0.402).

**Gotchas**

- Put the attribute on a function that is not `inline` and you get error FS3519, "The 'InlineIfLambda' attribute may only be used on parameters of inlined functions of methods whose type is a function or F# delegate type". It is an error, not a hint.
- The first Release round took 215 ms and later rounds took 58 ms, because of tiered JIT. A single-shot timing measures the JIT, not the lambda.
- Turning off the JIT's object stack allocation (`DOTNET_JitObjectStackAllocation=0`) changed nothing. The 0 bytes in Release are the F# compiler's work (lambda lifting), not .NET 10's escape analysis.

## TypeScript: RegExp.escape turns "foo" into "\x66oo", and that first hex escape is what keeps it safe to paste anywhere

*Stdlib and ecosystem gems*

**Did you know**

`RegExp.escape` (ES2025, present in Node 26.13 and absent in Node 22.23, declared in TypeScript's `es2025` lib) escapes more than the usual regex metacharacters. A leading digit or ASCII letter becomes `\xNN`, so `"foo"` becomes `"\\x66oo"`. Punctuators such as `-`, `@`, `,` and space also become `\xNN`. The leading escape exists because your string might land right after `\0` or `\c` in a larger pattern. The `\x2d` for `-` exists because it might land inside `[...]`, where a hand-rolled escape lets `"a-z"` become a range.

**Show me**

```typescript
// TypeScript 7.0.2 with --lib es2025; Node 26.13.0 (Debian-based node:26 image).
console.log(RegExp.escape("foo"));              // \x66oo
console.log(RegExp.escape("1+1"));              // \x31\+1
console.log(RegExp.escape("user@example.com")); // \x75ser\x40example\.com
console.log(RegExp.escape("x-y"));              // \x78\x2dy

// The escape most codebases carry, copied from the old MDN recipe.
const fn_hand_escape = (text: string): string => text.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");

// A user-supplied set of allowed characters, pasted into a character class.
const allowed_input = "a-z";
console.log(new RegExp("[" + fn_hand_escape(allowed_input) + "]").test("b")); // true: a range
console.log(new RegExp("[" + RegExp.escape(allowed_input) + "]").test("b"));  // false: three literals

// Pasted right after an escape in a bigger pattern.
const user_id = "1";
try { new RegExp("\\0" + fn_hand_escape(user_id), "u"); }
catch (error) { console.log((error as Error).message); } // Invalid regular expression: /\01/u: Invalid decimal escape
console.log(new RegExp("\\0" + RegExp.escape(user_id), "u").test("\u00001"));  // true
```

**Why it matters**

Every server that builds a regex from a search box, a tenant prefix or an allow-list carries a hand-rolled escape. Those escapes were written for one place, the middle of a pattern, and they break at the edges: inside a class, right after another escape, under the `u` or `v` flag. The standard one is meant to be safe wherever you paste it, and the price is output nobody can read. Rust's `regex::escape` and .NET's `Regex.Escape` are the same idea with smaller character sets. The security angle below measures what .NET's leaves out.

**Chew on this**

Where in your code does a user string become part of a regex, and do you know which of the three places it lands: the middle, a character class, or right after another escape? If the answer differs per call site, is one escape function even the right abstraction?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/RegExp/escape
- https://tc39.es/ecma262/#sec-regexp.escape
- https://github.com/tc39/proposal-regex-escaping
- https://learn.microsoft.com/en-us/dotnet/api/system.text.regularexpressions.regex.escape

**Gotchas**

- The types and the runtime disagree. tsc 7.0.2 with `--lib es2025` compiles `RegExp.escape(...)`, but on Node 22.23.4 `typeof RegExp.escape` is `undefined`, so the call throws a TypeError. With `--lib es2024` you get TS2550, which suggests `es2025`.
- The output is meant for a regex, not for people. A snapshot test of a generated `pattern.source` changes from `foo` to `\x66oo` when you switch to it.
- A lone surrogate does not throw. `RegExp.escape("\uD800")` returns `"\\ud800"`, unlike `encodeURIComponent`, which throws URIError on the same input (measured, Node 26).
- `_` is not escaped (`"_id"` stays `"_id"`). Non-ASCII letters are not escaped either (`"été"` comes back unchanged). Only ASCII letters and digits get the leading `\x`, and only in first position.

# The functional angle: passing a function is free only where the compiler can see its body, and each language decides that differently

Draws on the F# tip (InlineIfLambda) and, as a comparison, on the same loop written in Rust, C++ and TypeScript. Same shape in all four: a sum over 100 elements, with a captured offset, called 1M times.

```rust
// Rust: impl Fn makes the closure's type part of the call, so its body is known
fn sum_generic<F: Fn(usize) -> i64>(map_value: F, count: usize) -> i64 {
    (0..count).map(|index| map_value(index)).sum()
}
// &dyn Fn erases the type: one indirect call per element
fn sum_dyn(map_value: &dyn Fn(usize) -> i64, count: usize) -> i64 {
    (0..count).map(|index| map_value(index)).sum()
}
```

```cpp
// C++20: template parameter versus type-erased std::function
template <typename F> long long sum_template(F map_value, int count);
long long sum_function(const std::function<long long(int)>& map_value, int count);
```

| Language | Functional form | 1M x 100, ms | What it costs |
| --- | --- | --- | --- |
| F# | `inline` HOF, 5-line lambda, no attribute | 202 | a call per element to a lifted static method; no allocation |
| F# | same, `[<InlineIfLambda>]` | 148 | caller IL grows from 35 to 184 bytes |
| Rust | `impl Fn` generic | 0 | nothing: the optimizer computed the whole loop in closed form |
| Rust | `&dyn Fn` | 85-87 | an indirect call per element, nothing to optimize across |
| C++ | template parameter | 30 | an instantiation per lambda type |
| C++ | `std::function` (callee `noinline`) | 85-87 | type erasure plus an indirect call |
| TypeScript | callback `(index) => index + offset` | 77-79 | whatever V8's inliner decides; not controllable from source |
| TypeScript | loop written by hand | 40-55 | no abstraction at all |

Measured on Debian (`debian-test`): rustc 1.99.1 `-O`, g++ 14.2 `-O2`, Node 22.23.4, .NET 10.0.13. The Rust 0 ms is not a per-call cost. It shows what becomes possible once the body is visible.

The pattern: Rust and C++ make "the compiler can see the body" a property of the type, so you choose it in the signature. F# makes it a property of the parameter, and it is off unless the lambda is small. TypeScript leaves it to a JIT you cannot steer. None of them needs `mut` to express the functional form. The cost is visibility, not mutation.

What none of these measurements settles: when the body is visible, so is every change to it. That is true of a Rust generic, a C++ template and an F# `inline` helper alike. Which of your library's combinators would you be willing to see recompiled into every caller?

# The security angle: an escape function is a promise about where its output gets pasted, and .NET's does not cover a character class

Draws on the TypeScript tip (Mode B: is the escape we just praised secure everywhere?) and on F#/.NET's `Regex.Escape` as the contrast. Direction: the language-level fix exists in JavaScript and is missing in .NET.

The insecure sample. It looks like a reasonable allow-list check and would pass review:

```fsharp
// F# / .NET 10: "only let these characters through", set per tenant
open System.Text.RegularExpressions
let fn_is_allowed (tenant_chars: string) (input: string) : bool =
    Regex.IsMatch(input, "^[" + Regex.Escape tenant_chars + "]+$")

fn_is_allowed "a-z" "b"   // true: Regex.Escape "a-z" is "a-z", a range inside [...]
```

Measured: `Regex.Escape "a-z"` returns `"a-z"`, and `Regex.Escape "a]b"` returns `"a]b"`. .NET escapes a minimal set (`\ * + ? | { [ ( ) ^ $ . #` and white space), which is enough for the middle of a pattern but not for a character class. A tenant configured with `0-9a-f` gets what they meant. A tenant whose list is `+-/` gets `\+-/`, which is still the range `+` to `/`: measured, `,` and `.` both pass. Close a `]` early and the rest of the string becomes pattern.

The fix is to escape for the place the string lands. In a class, escape `-`, `]`, `\` and `^` yourself, or skip the regex and test the characters against a `HashSet<char>`:

```fsharp
// F#: no regex at all, so there is nothing to escape
let fn_is_allowed_set (tenant_chars: string) (input: string) : bool =
    let allowed = System.Collections.Generic.HashSet<char>(tenant_chars)
    input |> Seq.forall allowed.Contains
```

The C++ tip carries a related leak, in the other direction. A reflected `to_json` that someone switches to `access_context::unchecked()` "so it shows everything" now writes `balance_cents`, and every future private field, into whatever the JSON reaches: a log line, an API response (CWE-532, CWE-200).

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | hand-rolled escape lets `a-z` become a range in `[...]`; `\0`+`1` fails under `/u` | `RegExp.escape` escapes `-` as `\x2d` and the leading digit or letter as `\xNN` (measured, Node 26) | Node 22 has none: a polyfill or a hard Node 24+ floor |
| F# / .NET | `Regex.Escape` leaves `-` and `]` alone (measured, .NET 10; see the `Regex.Escape` docs) | nothing for character classes | escape class characters yourself, or do not build a class from input |
| Rust | same question for `regex::escape` | not checked here | test it in a class before you trust it |
| C++ | `std::regex` has no escape function | nothing | write one, and decide where its output may go |
| C++ | `unchecked()` serializer exports private fields | `current()` is the conservative default (measured, g++ 16.2) | review every `unchecked()` like a cast |

Classes: CWE-625 (permissive regular expression), CWE-185 (incorrect regular expression), CWE-532 and CWE-200 for the reflection leak.

Which of your regexes is built from a string an operator or a tenant can edit, and do you know whether that string ever lands inside square brackets?
