## Rust: BTreeMap::range panics on reversed bounds and on an excluded pair, but only when the map is not empty

*Stdlib and ecosystem gems*

**Did you know**

`BTreeMap::range` and `BTreeSet::range` return an iterator, not a `Result`, and they panic in two cases: the start bound is greater than the end bound, and both bounds are `Excluded` with the same key. The second case is the odd one, because `(Included(20), Excluded(20))` is accepted and simply empty, and so is `10..10`. Only the bound-pair shape `(Excluded(k), Excluded(k))` is refused, with "range start and end are equal and excluded in BTreeMap". The panic is the same in debug and release. Measured on rustc 1.95.0 (macOS) and rustc 1.99.1 (Debian 13); the behaviour is documented on `BTreeMap::range`.

**Show me**

```rust
use std::collections::BTreeMap;
use std::ops::Bound::{Excluded, Included};

fn main() {
    let deadlines: BTreeMap<u32, &str> = [(10, "a"), (20, "b"), (30, "c")].into();

    // Fine: half-open and empty.
    println!("{}", deadlines.range(10..10).count()); // 0
    // Fine: Included then Excluded on the same key is empty, not an error.
    println!("{}", deadlines.range((Included(20), Excluded(20))).count()); // 0
    // Fine: a single-key closed range.
    println!("{}", deadlines.range((Included(20), Included(20))).count()); // 1

    // Panics: "range start is greater than range end in BTreeMap".
    let from_query: u32 = 30;
    let to_query: u32 = 10;
    let _ = deadlines.range(from_query..to_query).count();

    // Panics: "range start and end are equal and excluded in BTreeMap".
    let _ = deadlines.range((Excluded(20), Excluded(20))).count();

    // A sorted slice has the non-panicking shape: .get(range) returns an Option.
    let sorted: Vec<u32> = vec![10, 20, 30];
    let from: usize = sorted.partition_point(|&key| key < 30);
    let until: usize = sorted.partition_point(|&key| key < 10);
    println!("{:?}", sorted.get(from..until)); // None
}
```

Comparison, C++ (compiled with g++ 14.2 and Apple clang 21): a `std::map` range is two iterators, `lower_bound(30)` and `lower_bound(10)`, and nothing checks that the second one is reachable from the first. A loop `for (it = from; it != until; ++it)` reaches `end()` without ever meeting `until`; my probe stopped at `end()` (it recorded `met_until=0` after 1 step) because the real loop would step past it, which is undefined behaviour. F# and TypeScript do neither: `[|10; 20; 30|].[2..0]` is `[||]` and `[10, 20, 30].slice(2, 0)` is `[]`.

**Why it matters**

Any range endpoint that came from a request, a config file or a join is a bound you did not choose, and `range(from..to)` reads like a lookup. A reversed pair takes the thread down with a panic, and with `-C panic=abort` the process exits with status 134. The check you need is one line (`if from > to`), and it has to cover the `(Excluded, Excluded)` shape too if your bounds are `Bound` values.

**Chew on this**

Which of your `range` calls take bounds that a caller, not you, picked? And would you rather the standard library returned an empty iterator for a reversed pair, as F# and TypeScript do, or refused it, as Rust does and C++ leaves unchecked?

**Sources**

- https://doc.rust-lang.org/std/collections/struct.BTreeMap.html#method.range
- https://doc.rust-lang.org/std/collections/struct.BTreeSet.html#method.range
- https://en.cppreference.com/w/cpp/container/map/lower_bound

**Verified**

Snippet compiled and run: rustc 1.95.0 (macOS) and rustc 1.99.1 (Debian 13, `debian-test`), identical output, also with `-O`. The C++ iterator walk is a measured stand-in; the undefined step past `end()` is from the C++ iterator-range requirement, not executed.

**Gotchas**

- `range(10..10)` and `(Included(20), Excluded(20))` both return an empty iterator; only reversed bounds and `(Excluded(k), Excluded(k))` panic.
- The panic is data-dependent: on an empty map the same reversed or excluded-equal bounds returned an empty iterator, and on a map with 1 or 2 entries they panicked.
- `BTreeSet::range` panics the same way, with "in BTreeSet" in the message.
- `Vec::get(from..until)` on a sorted slice with `from > until` returns `None`, where indexing `&sorted[from..until]` would panic.

## C++: decltype(auto) returns a reference when you wrap the name in parentheses

*Type system deep cuts*

**Did you know**

With `decltype(auto)` the return type is `decltype` of the return expression, and `decltype` treats `x` and `(x)` differently: `decltype(x)` is the declared type of the entity, while `decltype((x))` is an lvalue reference to it. So `return session.hits;` returns `int` by value and `return (session.hits);` returns `int&`. The same pair of parentheses on a local returns a reference to a variable that is gone. Language requirement: C++14 for `decltype(auto)` (the `is_same_v` assertions below need C++17). Checked with g++ 14.2 on Debian 13 and Apple clang 21; the minimum-compiler versions are not confirmed here.

**Show me**

```cpp
#include <string>
#include <type_traits>
#include <utility>

struct Session { std::string user; int hits = 0; };

// decltype(name) is the declared type, int. decltype((name)) is int&.
decltype(auto) hits_plain(Session& session) { return session.hits; }
decltype(auto) hits_paren(Session& session) { return (session.hits); }

// One pair of parentheses added in a refactor, on a local.
decltype(auto) label_plain() { std::string label = "alpha"; return label; }
decltype(auto) label_paren() { std::string label = "alpha"; return (label); }

static_assert(std::is_same_v<decltype(hits_plain(std::declval<Session&>())), int>);
static_assert(std::is_same_v<decltype(hits_paren(std::declval<Session&>())), int&>);
static_assert(std::is_same_v<decltype(label_plain()), std::string>);
static_assert(std::is_same_v<decltype(label_paren()), std::string&>);

int main() {
    Session session{"ada", 1};
    hits_paren(session) = 99;                  // legal: writes through into session
    const std::string& shown = label_paren();  // compiles; reads a dead stack slot
    return static_cast<int>(shown.size());
}
```

All four `static_assert`s hold on both compilers. Comparison, Rust: the same mistake is a compile error, because a function returning `&String` to a local fails borrow checking (E0515).

**Why it matters**

Return-type deduction hides the one-token difference between a copy and a reference, in a place a reviewer reads as formatting. In a forwarding wrapper, `decltype(auto)` is exactly what you want when the callee returns a reference; the parentheses are what turns a harmless by-value accessor into a view of storage the function does not own.

**Chew on this**

Where in your codebase is `decltype(auto)` used on a function whose body returns an expression in parentheses, and was the parenthesis typed on purpose? Would you rather a deduced return type never be allowed to become a reference to a local, as Rust enforces?

**Sources**

- https://en.cppreference.com/w/cpp/language/decltype
- https://en.cppreference.com/w/cpp/language/function#Return_type_deduction
- https://eel.is/c++draft/dcl.type.decltype

**Verified**

g++ 14.2.0 (Debian 13) and Apple clang 21.0.0 both compile the snippet; both warn on `label_paren` (`-Wreturn-local-addr` and `-Wreturn-stack-address`). Run under AddressSanitizer on g++ 14.2 (aarch64), reading `shown.size()` ended in a SEGV inside `std::string::size()`; the unsanitized macOS build printed a length of 0. Minimum-compiler versions for `decltype(auto)` were not confirmed against the support table.

**Gotchas**

- `decltype(session.hits)` without parentheses is `int`, not `int&`: unparenthesized member access is exempt from the lvalue rule (measured through `hits_plain`).
- The warning is not a guarantee. A local reached through an alias, `Session& alias = local; return (alias.hits);`, was silent in g++ 14.2 at `-O0` and `-Wall -Wextra`, flagged by g++ at `-O2` ("function returns address of local variable"), and flagged by Apple clang 21.
- Unsanitized, the dangling read did not crash on macOS; it returned a size of 0. A passing run says nothing.

## F#: F# 11 makes two delegates built from the same method equal, so -= on an event finally finds them

*New discoveries and currently popular patterns*

**Did you know**

F# 11 (shipped with .NET 11 RC1 in September 2026, on SDK 11.0.100-rc.3 here) changed how `EventHandler(counter.Bump)` compiles: the delegate now points directly at the method, with no generated closure class, per language release notes entry "Direct delegate construction" (dotnet/fsharp PR 19993). The visible effects are three. Two delegates built from the same method and the same target compare equal, so `Delegate.Remove` and `-=` on an event now match them. The delegate's `Target` is your object rather than a hidden closure. And a `null` receiver now fails at construction (`ArgumentException` for a non-virtual method) instead of when the delegate is first called. Final .NET 11 is expected in November, so treat the details as release-candidate behaviour.

**Show me**

```fsharp
open System

type Counter() =
    // Curried member: the shape the direct form takes. A tupled member
    // (sender: obj, args: EventArgs) does not typecheck here (FS0001).
    member this.Bump (sender: obj) (args: EventArgs) = ()

let fn_make_direct (counter: Counter) = EventHandler(counter.Bump)
let fn_make_lambda (counter: Counter) = EventHandler(fun sender args -> counter.Bump sender args)

// Subscribe a handler plus one other, then remove "the same" handler built a second time.
let fn_handlers_left (subscribed: EventHandler) (to_remove: EventHandler) : int =
    let combined = Delegate.Combine(subscribed, EventHandler(fun _ _ -> ())) :?> EventHandler
    (Delegate.Remove(combined, to_remove) :?> EventHandler).GetInvocationList().Length

let counter = Counter()
let direct_first, direct_second = fn_make_direct counter, fn_make_direct counter
let lambda_first, lambda_second = fn_make_lambda counter, fn_make_lambda counter

printfn "direct equal=%b target=%s" (direct_first.Equals direct_second) (direct_first.Target.GetType().Name)
printfn "lambda equal=%b target=%s" (lambda_first.Equals lambda_second) (lambda_first.Target.GetType().Name)
printfn "left after one remove: direct=%d lambda=%d"
    (fn_handlers_left direct_first direct_second) (fn_handlers_left lambda_first lambda_second)
```

Measured output, `LangVersion` 11.0 against 10.0, same SDK:

| LangVersion | direct equal | direct Target | handlers left (direct) | handlers left (lambda) | `fn_make_direct` on a null receiver |
| --- | --- | --- | --- | --- | --- |
| 10.0 | false | closure `fn_make_direct@6` | 2 | 2 | constructed |
| 11.0 | true | `Counter` | 1 | 2 | `ArgumentException` |

Comparison, C#: `+=` and `-=` with a method group have always compared by method and target, which is why `button.Click -= Handler` works there. F# 11 closes that gap for the method-group form only; the lambda form stays a fresh closure in both languages and never compares equal.

**Why it matters**

A long-running service that subscribes and unsubscribes handlers (a connection that reconnects, a per-request scope on a shared event) leaks every handler whose `-=` silently matched nothing, and the leak holds the subscriber alive. Before F# 11 the F# spelling of `-=` with a method group was a no-op; after it, the same source unsubscribes. The behaviour follows `LangVersion`, not the runtime: on SDK 11 with `LangVersion` 10.0 the old closure comes back.

**Chew on this**

Which of your F# event subscriptions rely on a later `-=` or `RemoveHandler`, and do any of them pass a lambda? And if upgrading the compiler turns a leak into a working unsubscribe, which of your handlers was quietly depending on being subscribed forever?

**Sources**

- https://github.com/dotnet/fsharp/blob/main/docs/release-notes/.Language/11.0.md
- https://github.com/dotnet/fsharp/pull/19993
- https://www.infoq.com/news/2026/09/dotnet-11-rc-1-release/

**Verified**

Built and run as a project: SDK 11.0.100-rc.3.26522.148 (`mcr.microsoft.com/dotnet/nightly/sdk:11.0`, Ubuntu 26.04, not Debian), `net11.0`, FSharp.Core 11.0.0.0, once with `LangVersion` 10.0 and once with 11.0. The 10.0 row was also reproduced on the Debian `debian-test` container, SDK 10.0.402, FSharp.Core 10.1.0.0. The C# statement about method-group `-=` is from documentation and was not run. The PR page itself was not fetched; the behaviour description comes from the language release notes and was confirmed by the run.

**Gotchas**

- The direct form needs a curried member; with a tupled member `EventHandler(counter.Bump)` is FS0001 ("expected obj, but is a tuple").
- Wrapping the call in a lambda, `fun sender args -> counter.Bump sender args`, is still a closure: `equal=false`, two handlers left after the remove, on both language versions.
- `dotnet fsi` with a top-level `let counter` reported `equal=true` even without F# 11 semantics, because the closure was a single shared instance; a project build with a counter passed in is what shows the difference.

## TypeScript: delete turns a per-request object into a dictionary, and TS2790 is what nudges you into it

*Perf and memory model*

**Did you know**

In V8, `delete obj.key` moves the object out of fast (hidden-class) mode into dictionary mode, including when the deleted key is the last one added. Assigning `undefined` keeps it fast. TypeScript pushes you toward the slow form: with `strict`, `delete context.user_id` on a required property is TS2790 ("The operand of a 'delete' operator must be optional"), so the usual fix is to make the field optional and then delete it. Measured on Node 22.17.1 (V8 12.4) and Node 22.23.4, tsc 7.0.2.

**Show me**

```ts
// Run with: node --allow-natives-syntax (a V8 debugging flag, test only)
declare function HasFastProperties(target: object): boolean; // stands for %HasFastProperties

interface RequestContext {
    request_id: string;
    user_id?: number; // optional only so that `delete` type-checks
    tenant: string;
    trace_token: string;
}

const fn_make_context = (): RequestContext =>
    ({ request_id: "r1", user_id: 7, tenant: "acme", trace_token: "t" });

const untouched = fn_make_context();                    // fast: true
const set_undefined = fn_make_context();
set_undefined.user_id = undefined;                      // fast: true
const delete_middle = fn_make_context();
delete delete_middle.user_id;                           // fast: false
const delete_last = fn_make_context();
delete delete_last.trace_token;                         // error TS2790 if made required; fast: false
```

The `%HasFastProperties` run printed `untouched true, setUndefined true, deleteMiddle false, deleteLast false`. Reading a property in a hot loop (200,000 objects, 20 reads each) took 13 to 26 ms untouched, 10 to 24 ms after `= undefined`, and 45 to 65 ms (macOS) or 37 to 45 ms (Debian) after `delete`: about 2x to 4x, with run-to-run noise and a narrower gap on the second pass.

Comparison, Rust and F#: neither can remove a field from a value. A Rust struct field is fixed by the type, and an F# record copy `{ context with user_id = None }` builds a new record of the same shape, so the optional-field-and-delete move does not exist there. C++ has the same shape guarantee for a struct.

**Why it matters**

A request context or a session bag that gets `delete`d on every request is on every handler's read path, and each read now does a hash lookup rather than an offset load. The type-checker's complaint steers you toward making a required field optional just to satisfy `delete`, which is the shape-changing move.

**Chew on this**

Which objects on your hot path are built once and then have keys deleted? And would a `Map`, or a new object without the key, or an explicit `undefined`, change what the rest of your code means by "this key is absent"?

**Sources**

- https://v8.dev/blog/fast-properties
- https://www.typescriptlang.org/tsconfig/#strict

**Verified**

Node 22.17.1 (V8 12.4.254.21-node.27, macOS arm64) and Node 22.23.4 (V8 12.4.254.21-node.57, Debian 13 arm64) with `--allow-natives-syntax`; tsc 7.0.2 `--strict` on both hosts gave TS2790 for the required property and accepted the optional one. Not run on Node 26. The snippet above is written for TypeScript with the V8 intrinsic stood in by a declared function; the measurement itself ran as plain JavaScript.

**Gotchas**

- `delete` of the last-added key is still dictionary mode here (`deleteLast false`) on V8 12.4, though one might expect the last-added key to stay fast.
- `= undefined` is not equivalent: `"user_id" in obj` stays `true`, `Object.keys` still lists it, and `JSON.stringify` drops it (measured: `{"tenant":"x"}`, `true`, `user_id,tenant`), while after `delete` the key is gone from all three.
- The gap is a few times, not orders of magnitude, and shrank on the second timed pass; a cold, one-off object will not show it.

# The functional angle: only a .NET delegate has function equality, and F# 11 just fixed which ones

Draws on the F# tip (delegate equality) with a shared thread to the TypeScript tip's event-handler habit. Skip this section if you read neither.

The shape: "is this the same function I registered earlier?", the question `-=`, `removeEventListener` and `unsubscribe` all ask. Four languages answer it differently, and the F# row is the baseline here for a concrete reason: it is the only one of the four where the answer changed this autumn.

```rust
// Rust
fn main() {
    let first = |value: i32| value + 1;
    let second = |value: i32| value + 1;
    // first == second  -> error[E0369]: binary operation `==` cannot be applied to type `{closure}`
    fn plain(value: i32) -> i32 { value + 1 }
    let pointer_one: fn(i32) -> i32 = plain;
    let pointer_two: fn(i32) -> i32 = plain;
    // compiles with a warning ("function pointer comparisons do not produce meaningful results")
    println!("{}", pointer_one == pointer_two);
}
```

```typescript
// TypeScript: bind() builds a new function every call, so the second one is a stranger.
class Panel { count = 0; on_click(): void { this.count++; } }
const panel = new Panel();
const target = new EventTarget();
target.addEventListener("x", panel.on_click.bind(panel));
target.removeEventListener("x", panel.on_click.bind(panel)); // matches nothing
target.dispatchEvent(new Event("x"));
console.log(panel.count); // 1: the handler was never removed
```

```fsharp
// F#: a function value is not comparable at all, a delegate (F# 11, method group) is.
let first = fun (value: int) -> value + 1
let second = fun (value: int) -> value + 1
// printfn "%b" (first = second)  -> error FS0001: 'int -> int' does not support the 'equality' constraint
```

```cpp
// C++
std::function<int(int)> first, second;
// first == second;  // error: no match for 'operator==' (g++ 14.2); deleted operator (Apple clang 21)
// Only `first == nullptr` is defined.
```

| Language | Functional form | What it costs |
| --- | --- | --- |
| F# | function value `=` | rejected at compile time (FS0001); a delegate from a method group is equal in F# 11, a lambda delegate never is |
| Rust | closure `==` | rejected at compile time (E0369); a `fn` pointer compares, but rustc warns that the result is not meaningful |
| C++ | `std::function ==` | no `operator==` at all, only against `nullptr`; two lambdas are two different types anyway |
| TypeScript | `===` on a function | identity only; every `bind` or arrow wrapper is a new, unmatchable function (measured: the count stayed 1) |

The asymmetry worth leading with: three of the four refuse the question outright and one answers it wrongly without warning. A compile error is the cheap failure; TypeScript's silent no-op is the expensive one, and it is the same silent no-op that F# 10 and earlier gave for `-=`. Every row stays unresolved on the remedy: a returned unsubscribe handle, a token, a registration object, or keeping the original function in a variable.

What would you register handlers with, if the only equality you could trust were the one you made yourself?

# The security angle: the bound you did not choose is a denial of service in Rust and a read past the end in C++

Draws on the Rust tip (`range` panics) and the C++ tip (`decltype(auto)` returning `T&`), Mode B: ask whether what each tip taught is *secure*, not just correct. Direction: each language does something here, and each leaves a residue.

An insecure sample, ordinary-looking, from a handler that reads a time window out of a query string:

```rust
// Rust: looks like a read. There is no Result in sight, and from > to is a panic.
fn count_in_window(ledger: &std::collections::BTreeMap<u32, String>, from: u32, to: u32) -> usize {
    ledger.range(from..to).count()
}
```

With `?from=30&to=10` this panics; compiled with `panic = "abort"` the process exits with status 134 (measured), so one request takes the whole service down. Class: CWE-248, Uncaught Exception, and an availability problem rather than memory unsafety. The same line in a thread-per-request server with unwinding is a lost thread; the language does not tell you which one you have built.

```cpp
// C++: two iterators and no relation check between them.
auto from_it = ledger.lower_bound(from_key);
auto to_it = ledger.lower_bound(to_key);          // to_key < from_key: to_it is behind from_it
for (auto it = from_it; it != to_it; ++it) { }    // walks to end() without meeting to_it, then past it
```

Class: CWE-125, Out-of-bounds Read (the standard makes a reversed range undefined behaviour). The `decltype(auto)` tip adds CWE-562, Return of Stack Variable Address: `return (label);` hands back a reference into a frame that is gone, and an ASan run on g++ 14.2 ended in a SEGV inside `std::string::size()`.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | reversed or excluded-equal `range` bounds panic | memory safe: panic, not corruption | check `from <= to` before the call; decide panic strategy per binary |
| C++ | reversed iterator pair is walked as a range | nothing: undefined behaviour | validate the pair; `-Wreturn-local-addr` catches only direct cases (g++ at `-O0` missed the aliased one) |
| F# | reversed slice `arr.[2..0]` | returns `[||]`, no panic | decide whether empty is the right answer for your caller |
| TypeScript | `slice(2, 0)` | returns `[]` | same: a reversed pair silently becomes "no data" |

Baseline per class: Rust for memory safety (its failure is a controlled stop, not a wild read), and F# or TypeScript for what "forgiving" costs, since an empty result can hide that the caller swapped two parameters. Advisories for the class: https://rustsec.org/advisories/ for panic-on-input denial-of-service entries, and https://cwe.mitre.org/data/definitions/248.html, https://cwe.mitre.org/data/definitions/125.html, https://cwe.mitre.org/data/definitions/562.html.

Which of your range-shaped inputs come from a caller, and what does each of your services do when the answer is a panic?

# FAQ

**Does `BTreeMap::range` panic on an empty map?** No, and that is the trap: reversed bounds and `(Excluded(k), Excluded(k))` panicked with 1 or 2 entries and did not panic with 0 (measured on rustc 1.95.0 and 1.99.1), so a test that runs against an empty map passes a bound pair that production data will reject.

**Is `decltype(auto)` the same as `auto&&`?** No. `auto&&` always yields a reference parameter or return; `decltype(auto)` yields exactly the type of the expression, so a plain `return x;` gives a value.

**Does the F# 11 direct form work for an event I own?** For a method group passed to a delegate constructor, as measured here. It was not tested against `[<CLIEvent>]` publishers or the `evt.AddHandler` helpers.

**Do I need `--allow-natives-syntax` to see dictionary mode in production?** No, it is only for the check;.
