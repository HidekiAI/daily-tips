## Rust: Rust 1.99 lets you define a C variadic, and next_arg::<f32>() will not compile because C already turned your float into a double

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.99.0 (released 2026-10-01) stabilized *defining* C variadic functions: `unsafe extern "C" fn sum(count: c_int, args: ...)`. Before, Rust could only call them. The `...` parameter is a `core::ffi::VaList`, which is already started on entry. `Clone` is `va_copy` and `Drop` is `va_end`. The read is `next_arg::<T>()`, bounded by `T: VaArgSafe`, and that trait is implemented only for types that survive C's default argument promotions: `c_int`, `c_uint`, the longs, `c_double`, `usize`/`isize` and raw pointers. `f32`, `i8`, `i16`, `u8` and `u16` are refused at compile time, because no C caller can ever pass one. `VaArgSafe` itself is still unstable, so you cannot implement it for your own types.

**Show me**

```rust
// rustc 1.99.0, edition 2024.
use std::ffi::{c_double, c_int, VaList};

// A C-callable variadic defined in Rust. Safety contract: the caller passes
// at least `count` variadic arguments, each a C double.
unsafe extern "C" fn sum_doubles(count: c_int, args: ...) -> c_double {
    // `args` is a VaList, already va_start'ed. Dropping it is va_end, so
    // the C++ "forgot va_end" bug cannot be written here.
    unsafe { sum_from(count, args) }
}

unsafe fn sum_from(count: c_int, mut args: VaList<'_>) -> c_double {
    let mut total: c_double = 0.0;
    for _ in 0..count {
        // A C caller that passed a float sent a double. Read f64.
        total += unsafe { args.next_arg::<c_double>() };
        // args.next_arg::<f32>()
        //   error[E0277]: the trait bound `f32: VaArgSafe` is not satisfied
    }
    total
}

fn main() {
    let reading: f32 = 1.5;
    // From Rust there is no implicit promotion: sum_doubles(1, reading)
    //   error[E0617]: can't pass `f32` to variadic function
    //   help: cast the value to `c_double`
    let total = unsafe { sum_doubles(2, reading as f64, 2.25f64) };
    println!("total = {total}");   // total = 3.75
}

// The C++ spelling of the same read compiles:
//   float first = va_arg(args, float);
// clang 21 warns by default (-Wvarargs: "this va_arg has undefined behavior
// because arguments will be promoted to 'double'"), and the program printed
// 0.000000 at -O0 and 1.500000 at -O2 on arm64.
```

**Why it matters**

This is the piece that lets a Rust library replace a C library whose ABI exports `...` functions without a C shim in between. The promotion rule is where C and C++ variadics go wrong silently: C++ accepts the `float` read and the result depends on the optimization level, while Rust turns both halves of the mistake into a compile error, on the read (`E0277`) and on the call (`E0617`). The part Rust still cannot check is the count: `next_arg` is `unsafe` because nothing tells the callee how many arguments the caller really sent.

**Chew on this**

The safety contract "at least `count` arguments of type `c_double`" now lives in a doc comment on a Rust function. Is there any type you could write that carries it, or does `...` mark the exact line where the type system has to stop? And if the callee is Rust but every caller is still C, whose code review owns that contract?

## C++: A pmr::vector growing inside a monotonic_buffer_resource keeps every buffer it outgrew

*Perf and memory model*

**Did you know**

`std::pmr::monotonic_buffer_resource::do_deallocate` does nothing (C++17; libstdc++ 9.1, libc++ 16, MSVC 19.13, Apple Clang 15). A vector that grows inside one still hands its old buffer back on every reallocation. The arena just ignores it, so every buffer the vector outgrew stays allocated until the arena is destroyed. On top of that, the arena grows its own upstream chunks geometrically. Measured on this host's libc++: pushing 1,000,000 `int`s without `reserve` left 16,382 KiB live upstream for a 4,096 KiB final buffer, about 4x. With `reserve` it held 3,906 KiB, exactly the payload.

**Show me**

```cpp
// C++17 <memory_resource>; measured with Apple clang 21 / libc++, -O2.
#include <cstddef>
#include <cstdio>
#include <memory_resource>
#include <vector>

// Upstream that counts the bytes the arena is currently holding.
struct counting_resource : std::pmr::memory_resource {
    std::size_t live_bytes = 0;
    void* do_allocate(std::size_t bytes, std::size_t align) override {
        live_bytes += bytes;
        return std::pmr::new_delete_resource()->allocate(bytes, align);
    }
    void do_deallocate(void* block, std::size_t bytes, std::size_t align) override {
        live_bytes -= bytes;   // only ever reached when the arena itself dies
        std::pmr::new_delete_resource()->deallocate(block, bytes, align);
    }
    bool do_is_equal(const memory_resource& other) const noexcept override {
        return this == &other;
    }
};

int main() {
    counting_resource upstream;
    std::pmr::monotonic_buffer_resource arena{&upstream};
    std::pmr::vector<int> values{&arena};
    for (int index = 0; index < 1'000'000; ++index)
        values.push_back(index);   // each regrowth "frees" into a no-op
    std::printf("payload %zu KiB, held %zu KiB\n",
                values.capacity() * sizeof(int) / 1024,
                upstream.live_bytes / 1024);
    // grown:    payload 4096 KiB, held 16382 KiB
    // reserved: payload 3906 KiB, held  3906 KiB
}
```

**Why it matters**

A per-request arena is the textbook server use of `monotonic_buffer_resource`, and it is fast precisely because it never frees. That same property turns every regrowth inside it into retained garbage proportional to how the container grew: `vector` growth, `string` appends, `unordered_map` rehashes. The arena is still correct, but its peak is a multiple of the data. Rust has the same shape outside std, since `Vec` takes no allocator parameter on stable; in `bumpalo` (3.20) "there is no general way to deallocate individual objects", and its `collections::Vec` lives in the arena. .NET has no user arena for managed objects at all, so in F# or C# the GC owns this decision.

**Chew on this**

Which containers in your per-request arenas have a size you only learn by growing them? And when the arena's lifetime is a long-lived connection rather than one request, is it still an arena, or a leak with a destructor?

**Sources**

- https://en.cppreference.com/w/cpp/memory/monotonic_buffer_resource/do_deallocate
- https://en.cppreference.com/w/cpp/compiler_support/17 (P0220R1 row)
- https://docs.rs/bumpalo/latest/bumpalo/

**Verified**

## F#: F# rejects seq<string> :> seq<obj>, and the CLR accepts the same conversion at runtime

*Type system deep cuts*

**Did you know**

`IEnumerable<out T>` is covariant in .NET, so C# assigns an `IEnumerable<string>` to an `IEnumerable<object>` with no cast. F#'s coercion rules never consult variance. `names :> seq<obj>` fails with FS0193. A let-bound function parameter, a flexible `#seq<obj>` parameter and a static method argument all fail with FS0001. Yet `(box names) :?> seq<obj>` succeeds, because a downcast is checked by the CLR, and the CLR does honor `out T`. `seq<int>` fails both ways, because variance applies only to reference types. Checked on F# 8, FSharp.Core 8.0.0.0, .NET 8.0.8. The language suggestion (#162) was closed in 2023, and a maintainer still answered "Not yet." in April 2025.

**Show me**

```fsharp
// F# 8, FSharp.Core 8.0.0.0, .NET 8.0.8 (dotnet fsi).
let names : seq<string> = [ "ada"; "grace" ]

// let as_objects : seq<obj> = names :> seq<obj>
//   error FS0193: Type constraint mismatch. The type 'string seq'
//   is not compatible with type 'obj seq'
// let count_all (items: #seq<obj>) = ...; count_all names
//   error FS0001: The type 'obj' does not match the type 'string'

// The same conversion as a runtime downcast: the CLR honors `out T`.
let as_objects = (box names) :?> seq<obj>
printfn "runtime cast: %A" (Seq.toList as_objects)       // ["ada"; "grace"]

// Variance is a reference-type rule: seq<int> is never a seq<obj>.
let counts : seq<int> = [ 1; 2 ]
printfn "%b" ((box counts) :? seq<obj>)                   // false

// The idiomatic route: a new enumerator that checks every element.
let wrapped : seq<obj> = Seq.cast names

// C#, same runtime, compiles with no cast at all:
//   IEnumerable<object> objects = names;
```

**Why it matters**

A C# library that returns `IEnumerable<Order>` to an API that takes `IEnumerable<object>` works in C# and needs a conversion in F#. The usual fix, `Seq.cast`, wraps the enumerator and checks each element on every enumeration. The `box ... :?>` form costs one runtime check, and the result is the same object, not a wrapper. The rest of the comparison is a spectrum: Rust has variance only through lifetimes, TypeScript makes arrays covariant (unsoundly) and methods bivariant, and C# follows the CLR's `in`/`out` annotations exactly.

**Chew on this**

F# refuses a conversion that its own runtime proves safe. Is that conservative or wrong, and what would F# have to give up in type inference to accept it? Where in your code does a `Seq.cast` exist only to satisfy the compiler, and does anything depend on the extra wrapper it creates?

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/casting-and-conversions
- https://github.com/fsharp/fslang-suggestions/issues/162

## TypeScript: Iterator.prototype.take(2) closes your generator, so the rest of it is gone

*Stdlib and ecosystem gems*

**Did you know**

The ES2025 iterator helpers (spec section 27.1.4.11) say that when `take`'s count reaches 0, it calls `IteratorClose` on the iterator underneath. For a generator that means `return()`: its `finally` runs and it is finished. So `[...source.take(2)]` followed by `[...source]` gives you `[]`, not the rest. Rust's `take` consumes its iterator by value, and `by_ref()` lends it out so the rest survives. JavaScript has no `by_ref`. The equivalent is to hand `take` an iterator with no `return` method, because `IteratorClose` has nothing to call. On the type side, tsc 6.0.3 needs `lib: es2025` (or `esnext`). Under `es2024`, `take` does not exist (TS2339) and `Iterator` is type-only (TS2693). Node 22.17.1 runs it.

**Show me**

```typescript
// tsc 6.0.3 --strict --lib es2025,dom; Node 22.17.1.
function* read_batches(): Generator<number, void, undefined> {
    try {
        for (let batch = 1; batch <= 6; batch++) yield batch;
    } finally {
        console.log("generator closed");   // runs when take() hits its limit
    }
}

const source = read_batches();
const head: number[] = [...source.take(2)];   // [1, 2], then "generator closed"
const rest: number[] = [...source];           // [] : take() called source.return()

// The JS spelling of Rust's by_ref(): an iterator with no return() method,
// so IteratorClose has nothing to call and the generator stays open.
const kept = read_batches();
const borrowed: Iterator<number> = { next: () => kept.next() };
const kept_head: number[] = [...Iterator.from(borrowed).take(2)];   // [1, 2]
const kept_rest: number[] = [...kept];                              // [3, 4, 5, 6]

// Rust, for comparison:
//   let head: Vec<i32> = batches.by_ref().take(2).collect();   // lends
//   let rest: Vec<i32> = batches.collect();                    // [3, 4, 5, 6]
```

**Why it matters**

A generator that wraps a cursor, a file handle or a paginated API usually releases it in `finally`. `take` triggering that is right for cleanup. It is wrong when you meant "read the header, then stream the body", and it fails quietly: the second loop sees an empty iterator, not an error. `for...of` with `break` closes the same way, so a refactor from a `break` loop to `take` keeps the behavior. A refactor from a hand-written `next()` loop to `take` changes it.

**Chew on this**

JavaScript decided that a partial read closes by default; Rust decided that it lends only when you ask. Which default would you pick for an iterator that owns a database cursor, and would you pick the same one for an iterator that owns nothing? Which of your generators hold a resource in `finally` today, and does every consumer of them actually mean to close it?

# The functional angle: taking a prefix of a lazy sequence decides who owns the rest, and four languages give four answers

Draws on the TypeScript tip (`take` closes) and the F# tip only for its baseline row. The functional claim is "`take n` is a pure prefix". That holds only when the source is a value. When the source is a stateful iterator, `take` has to decide what happens to the elements it did not take. Each row was run on a source of `1..6`, taking 2 and then reading the rest.

```fsharp
let numbers = seq { try (for step in 1 .. 6 do yield step) finally printfn "finally ran" }
numbers |> Seq.take 2 |> Seq.toList   // [1; 2], "finally ran"
numbers |> Seq.take 2 |> Seq.toList   // [1; 2] again: a seq is a recipe, every read restarts
```

```rust
let mut batches = 1..=6;
let head: Vec<i32> = batches.by_ref().take(2).collect();   // [1, 2]
let rest: Vec<i32> = batches.collect();                    // [3, 4, 5, 6]
```

```cpp
std::istringstream input{"1 2 3 4 5 6"};
auto batches = std::views::istream<int>(input);
for (int batch : batches | std::views::take(2)) {}   // 1 2
for (int batch : batches) {}                          // 4 5 6 : 3 is gone
```

```typescript
const source = read_batches();
[...source.take(2)];   // [1, 2], generator closed
[...source];           // []
```

| Language | Prefix form | Rest after taking 2 | What it costs |
| --- | --- | --- | --- |
| F# | `Seq.take 2` | the sequence restarts at 1 | the baseline here, since a `seq` is a value and the purity is real: there is no "rest" to own. Continuing needs a hand-held `IEnumerator`, and `Seq.take` disposes its own one |
| Rust | `by_ref().take(2)` | `[3, 4, 5, 6]` | opt-in: plain `take` consumes the iterator by value, so you must ask to keep it |
| C++ | `views::take(2)` over `views::istream` | `4 5 6`, element 3 lost | nothing closes, but the view reads ahead: the iterator's last `++` pulls 3 into the view's cache, and the next `begin()` reads again and overwrites it |
| TypeScript | `iterator.take(2)` | `[]` | closes by spec; lending needs a wrapper with no `return()` |

The C++ row is the one to remember: no error, no close, just one element that nobody received. That is the cost of the view caching a lookahead value it does not own.

Rust is the only row that can lend without allocating or wrapping, and it pays for that with `&mut` in the signature, which is exactly what makes the borrow visible. So which of these is the "functional" answer: F#'s restart, which is pure because it refuses to share state, or Rust's lend, which shares state and says so in the type?

# The security angle: C's `...` is the only calling convention here where the callee guesses how many arguments it got

Draws on the Rust tip, and runs in the insecure direction: Rust 1.99 checks the *type* of each variadic read, but nothing in any language checks the *count* or the *format* across a C `...` boundary. This is Mode B: the tip taught how to read a `VaList` safely; is the function that reads it secure?

The insecure sample is a log wrapper, which looks harmless and passes review:

```cpp
// Looks like a convenience wrapper. With no format attribute, the compiler
// cannot tell that `format` is a printf format string.
void log_line(const char* format, ...) {
    va_list args; va_start(args, format);
    std::vfprintf(stderr, format, args);   // reads as many args as the format names
    va_end(args);
}
void handle(const char* request_path) {
    log_line(request_path);   // attacker-chosen format string. No diagnostic by default.
}
```

The check is one attribute, plus a literal format at every call site:

```cpp
__attribute__((format(printf, 1, 2)))
void log_checked(const char* format, ...);
// log_checked(request_path);   -> warning: format string is not a string literal
//                                  (potentially insecure) [-Wformat-security], on by default
log_checked("%s", request_path);   // the request path is data, never a format
```

A Rust port does not inherit that attribute. `unsafe extern "C" fn log_line(format: *const c_char, args: ...)` gets no format checking at all, and `next_arg` trusts the format exactly as `va_arg` did. Rust's improvement is narrower than it looks: every read is `unsafe` and visibly so, and a `f32` read cannot be written.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | the callee reads more arguments than were passed, or reads them as the wrong type (CWE-134, CWE-686) | `-Wformat-security` and `-Wvarargs`, but only for functions declared with `format(printf, ...)` | the attribute on every printf-style wrapper; `-Wformat-nonliteral` to find the wrappers that lack it |
| Rust 1.99 | the same over-read, now in Rust code | the type of each read is checked (`VaArgSafe`), and every read is `unsafe` | keep `...` at the FFI edge only, and convert to a slice or a typed struct on the first line |
| TypeScript | not expressible: a rest parameter is an array, so the count travels with the arguments | `args.length` is always correct | nothing for the count; the element types are still unchecked at runtime |
| F# / C# | not expressible in safe code: `ParamArray` / `params` is an array | the length is in the value | nothing for the count |

Rust is the control for this class because it is the only row with both kinds of variadic: `...` at the C boundary, and slices everywhere else. The fix is the difference between them. Where in your codebase does a format string or an argument count cross a C boundary, and who chose the string?

Sources: https://cwe.mitre.org/data/definitions/134.html, https://cwe.mitre.org/data/definitions/686.html, https://clang.llvm.org/docs/AttributeReference.html#format
