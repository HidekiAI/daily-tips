## Rust: Backtrace::capture() is free when disabled, and the real cost of a captured one lands at Display, not at capture

*Perf and memory model*

**Did you know**

`std::backtrace::Backtrace` (stable since 1.65) has two constructors. `capture()` reads `RUST_BACKTRACE` / `RUST_LIB_BACKTRACE` once, memoizes the answer in an atomic for the rest of the process, and when neither is set returns `Disabled` without walking a single frame: 1000 calls measured 15 us total. `force_capture()` always walks, but lazily: it records raw instruction pointers (about 5 us per call at depth 20) and defers symbolization until the backtrace is formatted, which measured about 100 us per call. So the expensive part of a backtrace is not the error path, it is the log line.

**Show me**

```rust
use std::backtrace::Backtrace;
use std::time::Instant;

// A recursive frame chain so the walk has something to walk.
#[inline(never)]
fn deep(n: u32) -> Backtrace {
    if n == 0 { Backtrace::force_capture() } else { deep(n - 1) }
}

fn main() {
    // Env unset: capture() returns Disabled. No frames walked at all.
    let t = Instant::now();
    for _ in 0..1000 { let _ = std::hint::black_box(Backtrace::capture()); }
    println!("capture() x1000, env unset: {:?}", t.elapsed());          // ~15 us

    // force_capture() walks, but stores unresolved frames only.
    let t = Instant::now();
    for _ in 0..1000 { let _ = std::hint::black_box(deep(20)); }
    println!("force_capture() x1000:      {:?}", t.elapsed());          // ~5 ms

    // Display forces symbolization: this is where the time goes.
    let t = Instant::now();
    for _ in 0..100 { std::hint::black_box(deep(20).to_string()); }
    println!("force_capture()+to_string x100: {:?}", t.elapsed());      // ~10 ms

    // The env decision was memoized by the first capture() above,
    // so this changes nothing for the rest of the process.
    unsafe { std::env::set_var("RUST_BACKTRACE", "1") };
    println!("after set_var: {:?}", Backtrace::capture().status());      // Disabled
}
```

**Why it matters**

`anyhow` and `thiserror`'s `#[backtrace]` build on `capture()`, so a container that does not carry `RUST_BACKTRACE` logs empty backtraces with no warning, and setting it from a config file after startup is too late. The other way round, the budget question is how often you *print* them: an error type that captures cheaply but gets `{:?}`-logged on every retry pays roughly 20x the capture cost each time. C++23's `std::stacktrace` specifies no resolution timing at all, and Go's `runtime.Callers` / `CallersFrames` split is the same two-phase design made explicit in the API.

**Chew on this**

Which of your error types capture a backtrace, and is the variable present in the environment the service actually boots with, as opposed to the shell you tested in? If you wanted backtraces only above a severity threshold, where would that decision have to live, given `capture()` asks the environment exactly once?

**Sources**

- https://doc.rust-lang.org/std/backtrace/struct.Backtrace.html
- https://doc.rust-lang.org/std/backtrace/index.html#environment-variables

**Verified**

rustc 1.95.0, `--edition 2024 -O`, macOS; timings are one run on one host, magnitudes only.

## C++: libc++ ships ranges::fold_left but withholds __cpp_lib_ranges_fold, so a feature-test guard hides the fix for accumulate's init trap

*Stdlib and ecosystem gems*

**Did you know**

`std::accumulate(first, last, T init)` takes its accumulator type from `init` alone, so a literal `0` over `vector<double>` sums in `int` and truncates at every step. C++23's `std::ranges::fold_left` (P2322R6) deduces the result from `f(init, *it)` and fixes it. The gem-within-the-gem: Apple clang 21's libc++ (`_LIBCPP_VERSION` 220106) implements `fold_left` and `fold_left_with_iter` and they work, but it lacks `fold_right`, `fold_right_last`, `fold_left_first` and `fold_left_first_with_iter`, so it does not define `__cpp_lib_ranges_fold` at all. Support per cppreference: libstdc++ 13, MSVC 19.35, libc++ partial from 18 and complete in 23.

**Show me**

```cpp
#include <algorithm>
#include <functional>
#include <numeric>
#include <print>
#include <vector>

int main() {
    std::vector<double> v{1.5, 2.5, 3.25};   // true sum: 7.25

    // T deduced from the literal 0 -> int. Each step truncates: 1, 3, 6.
    auto bad = std::accumulate(v.begin(), v.end(), 0);

    // Result type is decltype(plus{}(0, 1.5)) -> double. Same seed, right answer.
    auto good = std::ranges::fold_left(v, 0, std::plus{});

    static_assert(std::is_same_v<decltype(bad), int>);
    static_assert(std::is_same_v<decltype(good), double>);
    std::println("accumulate = {}, fold_left = {}", bad, good);   // 6, 7.25

    // Guarding with #ifdef __cpp_lib_ranges_fold would compile the fallback
    // on this libc++, even though the line above works: the macro is all-or-
    // nothing across the six fold algorithms, and four are missing.
}
```

**Why it matters**

The literal `0` is what everyone types and the result is a plausible number, so it survives review and any test that only checks the sum is positive. The macro trap compounds it: a careful team that writes `#ifdef __cpp_lib_ranges_fold` to adopt the fix portably silently keeps the broken path on every macOS build until libc++ 23. Rust rejects the same seed mismatch (`fold(0, |a, b| a + b)` over `f64` is E0277) and F# rejects `List.fold (+) 0 [1.5]` as FS0001; C++ is the only one that answers wrongly and keeps going.

**Chew on this**

Where in your code is an accumulator's width decided by a literal rather than a named type, and which of those totals feeds a comparison rather than a display? If a feature-test macro is all-or-nothing over a paper, what should a portability guard test instead when you need only one algorithm out of six?

**Sources**

- https://en.cppreference.com/w/cpp/algorithm/ranges/fold_left
- https://en.cppreference.com/w/cpp/compiler_support/23
- https://libcxx.llvm.org/Status/Cxx23.html
- https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2322r6.html

**Verified**

Apple clang 21.0.0, libc++ 220106, `-std=c++23`: 6 vs 7.25 measured; each of the six fold algorithms probed with `-fsyntax-only`. libstdc++ and MSVC support states rest on cppreference; neither toolchain is installed here.

## F#: use outside a seq expression disposes before the first element is read

*Idioms and antipatterns*

**Did you know**

A `seq { }` is a recipe, not a result. If the resource is bound with `use` in the enclosing function and the function returns a `seq` that reads from it, the function returns first, `use` disposes the resource, and enumeration later throws `ObjectDisposedException`. Move the `use` inside the `seq { }` and the compiler turns it into a `try/finally` inside the generated enumerator, so disposal runs when enumeration finishes (or when the consumer's `for` exits early). F# 8, FSharp.Core 8.0.0, .NET 8.0.8.

**Show me**

```fsharp
open System.IO

File.WriteAllLines("demo.txt", [| "a"; "b"; "c" |])

// Looks like every other "open, read, close" helper. Compiles clean.
let linesBad (path: string) : seq<string> =
    use r = new StreamReader(path)          // disposed when linesBad returns...
    seq { while not r.EndOfStream do yield r.ReadLine() }   // ...read later

// use inside the seq: disposal moves into the enumerator's finally block.
let linesGood (path: string) : seq<string> =
    seq {
        use r = new StreamReader(path)
        while not r.EndOfStream do yield r.ReadLine()
    }

try linesBad "demo.txt" |> Seq.toList |> printfn "%A"
with e -> printfn "bad: %s" (e.GetType().Name)          // ObjectDisposedException
linesGood "demo.txt" |> Seq.toList |> printfn "%A"      // ["a"; "b"; "c"]
```

**Why it matters**

In a service this is a helper returning `seq<Row>` over a `DbDataReader` or a `Stream`, and it fails only when the caller enumerates, often in another module or after a `Seq.map` pipeline, so the stack trace points nowhere near the `use`. The same shape gets three verdicts elsewhere: Rust refuses to return an iterator borrowing a local (E0515), C++ compiles `return local | views::filter(...)` with no warning at `-Wall -Wextra` and dangles, and TypeScript's `using` outside a returned generator disposes early exactly like F#, throwing at the first `next()`.

**Chew on this**

Which of your functions return `seq<_>` while holding a disposable in a binding outside the expression, and would a test that calls `Seq.toList` at the call site even notice? Once `use` is inside, who owns disposal if the consumer takes `Seq.head` and never finishes, and does your consumer guarantee it?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/sequences
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/resource-management-the-use-keyword

**Verified**

`dotnet fsi` (SDK 8.0.401); Rust row on rustc 1.95.0, C++ row on Apple clang 21 `-std=c++23 -Wall -Wextra`, TS row on tsc 6.0.3 downlevelled to es2022 and run on Node 22.17.1.

## TypeScript: a never-returning arrow function narrows nothing, and the error lands on the line after it

*Type system deep cuts*

**Did you know**

Control flow analysis only honors `asserts x is T` and `: never` signatures when every name in the call target is declared with an explicit type annotation. `const fail = (m: string): never => { throw ... }` annotates the arrow's return, not the `const`, so it does not qualify. For an assertion function TS says so (TS2775). For a `never` function it says nothing at the call: the narrowing silently does not happen, and the error appears on whatever line relied on it. A `function` declaration, or a `const` with a full type annotation, works. Behavior since TS 3.7; measured on tsc 6.0.3.

**Show me**

```ts
// Looks identical in intent. Only the declaration form differs.
const fail = (msg: string): never => { throw new Error(msg); };
function fail2(msg: string): never { throw new Error(msg); }

function a(x: string | undefined): string {
  if (x === undefined) fail("missing");   // no diagnostic here...
  return x;   // ...error TS2322 here: 'string | undefined' not assignable
}

function b(x: string | undefined): string {
  if (x === undefined) fail2("missing");
  return x;   // fine: fail2 is a declaration, so CFA treats it as an exit
}

// The assertion-signature version at least names the cause:
const assertIsString = (x: unknown): asserts x is string => {
  if (typeof x !== "string") throw new TypeError("not a string");
};
declare const v: unknown;
assertIsString(v);   // error TS2775: Assertions require every name in the
                     // call target to be declared with an explicit type annotation.
```

**Why it matters**

The rule exists because CFA runs while types are still being inferred; resolving an inferred `const`'s type to discover it is an assertion would be circular. The practical cost is in codebases that standardize on arrow-function `const`s: the invariant helper everyone calls quietly does not narrow, the reported error points at the wrong line, and the reflexive fix is `x!` or `as string`, which turns a type-checked guard into an unchecked one. Rust and F# have no flow-sensitive narrowing to lose; Rust's `-> !` diverges regardless of how the function is bound, which is the property TS only grants to annotated names.

**Chew on this**

How many `const x = (...): never =>` helpers does your codebase have, and how many `!` sit on the lines right after their calls? If an assertion helper is imported through a re-export or a destructured namespace, which of those forms still counts as "declared with an explicit type annotation"?

**Sources**

- https://github.com/microsoft/TypeScript/pull/33622
- https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html#assertion-functions

**Verified**

tsc 6.0.3 `--noEmit --strict`: TS2322 on `a`, clean on `b`, TS2775 on the arrow assertion, and both the `function` form and the fully annotated `const` form narrow.

# The functional angle: three of these four languages decide a fold's accumulator type from the fold, and only C++ lets the seed decide it

Draws on the C++ tip. Same shape everywhere: a left fold with an explicit seed.

F# is the baseline here because `List.fold` is generic in `'State` and `'T` separately and inference must unify `'State` with the folder's result, so a mismatch is a type error by construction.

```fsharp
let xs = [1.5; 2.5; 3.25]
let bad  = List.fold (+) 0   xs   // error FS0001: 'float' does not match 'int'
let good = List.fold (+) 0.0 xs   // 7.25
```

```rust
let v: Vec<f64> = vec![1.5, 2.5, 3.25];
let bad  = v.iter().fold(0,   |a, b| a + b);  // error[E0277]: cannot add `&f64` to `{integer}`
let good = v.iter().fold(0.0, |a, b| a + b);  // 7.25
```

```cpp
auto bad  = std::accumulate(v.begin(), v.end(), 0);   // 6, silently, T == int
auto good = std::ranges::fold_left(v, 0, std::plus{}); // 7.25, even with the int seed
```

```ts
const s: string[] = ["a", "b"];
const bad = s.reduce((a, b) => a + b, 0);   // error TS2769: No overload matches
// number[] with seed 0 is fine: there is no integer type to truncate into.
```

| Language | Where the accumulator type comes from | Seed/element mismatch |
| --- | --- | --- |
| F# | `'State`, unified with the folder's result | FS0001 at compile time |
| Rust | closure's inferred parameter and return | E0277 at compile time |
| TypeScript | `U` on `reduce<U>`, bound by the seed | TS2769; no integer type exists |
| C++ `accumulate` | `T`, from `init` alone | none; 6 instead of 7.25 |
| C++ `ranges::fold_left` | `decay_t<invoke_result_t<F&, T, range_reference_t<R>>>` | none needed: result widens to `double` |

C++23 did not add a check; it moved the accumulator's type from the seed to the folder, which is what the other three always did. `std::reduce` is the other std answer and the thread left hanging: it may reorder, so it needs an associativity that `double` addition does not have, and the fastest of the three std folds is the one whose preconditions your data violates.

# The security angle: the seed you typed is the integer width your quota check runs in

Mode B, interrogating the C++ tip. It treated `0` as a correctness bug; the same mechanism is a bounds-check bypass, because an accumulated total is usually the left side of a comparison against a limit. C++ is the control: it is the only one of the four where the overflow is undefined behavior.

```cpp
// Sums a resumable upload's chunk sizes and enforces a quota.
// The elements are uint64_t. The accumulator is not.
bool under_quota(const std::vector<std::uint64_t>& chunks, std::uint64_t quota) {
    auto total = std::accumulate(chunks.begin(), chunks.end(), 0);   // T == int
    return static_cast<std::uint64_t>(total) <= quota;               // widens a wrong value
}
```

Measured on 2026-09-21 (Apple clang 21, `-O0` and `-O2`): four chunks of 1,073,741,849 bytes (4,294,967,396 total) against a 4,000,000,000-byte quota returns **true**. The `static_cast` looks like diligence and is the laundering step. CWE-197 composed with CWE-190.

F# holds the surprise, a split inside one library: `List.sum [Int32.MaxValue; 1]` throws `OverflowException` (FSharp.Core implements `sum` with `Checked.(+)`), while `List.fold (+) 0` over the same list wraps to -2147483648. Measured on 2026-09-21.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | seed literal fixes a 32-bit accumulator; signed overflow is UB | nothing at default warnings | name the type (`std::uint64_t{0}`) or use `fold_left`; `-fsanitize=signed-integer-overflow` in CI. CWE-190 |
| Rust | `i32` folds wrap in release, panic in debug | release wraps by defined rule, never UB | `try_fold` + `checked_add`, or `overflow-checks = true` in the release profile |
| F# | `fold (+) 0` wraps, `sum` throws | `sum`/`sumBy` use `Checked.(+)` | know which you called, and whether `OverflowException` becomes a 500 |
| TypeScript | past 2^53 a total loses low bits, and a self-check computed the same way agrees | nothing; `number` is a double | `BigInt` for byte counts and money. CWE-681 |

Which of your quota, limit and length checks compute their left-hand side by accumulating, and what is the declared width of that accumulator versus the width of what it accumulates?

# FAQ

**Does `RUST_BACKTRACE=0` count as "set"?** It is read, and `0` means disabled; the memoization applies either way.

**Is `std::stacktrace` lazy like Rust's?** The C++23 standard does not say; it is implementation-defined and was not measured here.

**Does `Seq.cache` fix the F# case?** No. It caches elements already read; the reader is still disposed before the first one.

**Does `satisfies` or an `as const` make an arrow `never` helper qualify?** The rule wants an explicit type annotation on the declared name; the fully annotated `const f: (m: string) => never = ...` form was verified to work.
