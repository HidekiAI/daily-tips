**The thesis of this part: a persistent data structure makes "a new version with one change" cheap by sharing everything else with the old version, and sharing is a contract between versions that each language enforces differently.** Rust's std has no persistent collections, so copy-on-write with `Arc` copied a million elements on the first write, while the `im` crate updated one tree path in about 300 ns. .NET's `ImmutableList` shares structure as an AVL tree, so one `Add` cost 1,032 bytes, and building it one `Add` at a time cost 17 times the allocation of its builder. C++ has nothing persistent in std, and its standard way to publish an immutable snapshot, `atomic<shared_ptr>`, is not lock-free on libstdc++. Immer in TypeScript shares the untouched parts of the tree with your original, and then freezes them, so the original changes behaviour too.

Every value below was printed by the snippet beside it, on Linux aarch64 containers: a Debian 13.7 container with rustc 1.99.1 (`im` 15.1.0), g++ 14.2.0 and .NET SDK 10.0.402 (runtime 10.0.13, FSharp.Core 10.1.0.0, Release builds), the `gcc:16` image with g++ 16.2.0, and the `node:22-trixie` image with Node 22.23.4 and immer 11.2.9. ## Rust: std has no persistent collections, so copy-on-write with Arc cloned a million elements on the first write, and im::Vector updated one path

*Stdlib and ecosystem gems*

**Did you know**

The std way to share an immutable `Vec` and occasionally produce a new version is `Arc<Vec<T>>` with `Arc::make_mut`. While a reader holds the old version, `make_mut` cannot share anything: it cloned all 1,000,000 elements before writing one (0.5 to 1.4 ms across runs), and `Arc::ptr_eq` confirmed the reader kept the old buffer. The next `make_mut`, with the writer now the only owner, wrote in place in 41 to 84 ns. The `im` crate's persistent vector is a tree: `clone()` is O(1), and `update(0, 42)` copied one path and shared the rest, in 291 to 458 ns, while the reader's clone still saw the old value.

**Show me**

```rust
// Rust, rustc 1.99.1 --release, im 15.1.0 (cargo add im).
use std::sync::Arc;
use std::time::Instant;

fn main() {
    let item_count: usize = 1_000_000;
    let snapshot: Arc<Vec<u64>> = Arc::new((0..item_count as u64).collect());

    // A reader holds the current version; a writer wants a new version with one element changed.
    let reader_view = Arc::clone(&snapshot);
    let mut writer_copy = Arc::clone(&snapshot); // make_mut needs &mut
    let started = Instant::now();
    Arc::make_mut(&mut writer_copy)[0] = 42; // shared, so make_mut clones all 1,000,000 elements first
    println!("Arc::make_mut while shared: {:?}, same buffer: {}", started.elapsed(), Arc::ptr_eq(&reader_view, &writer_copy));

    let started = Instant::now();
    Arc::make_mut(&mut writer_copy)[1] = 43; // unique now, so this one writes in place
    println!("Arc::make_mut when unique:   {:?}", started.elapsed());

    let persistent: im::Vector<u64> = (0..item_count as u64).collect();
    let reader_version = persistent.clone(); // O(1): shares the tree
    let started = Instant::now();
    let updated = persistent.update(0, 42); // copies one path of the tree
    println!("im::Vector::update:          {:?}, reader still sees {}", started.elapsed(), reader_version[0]);
    println!("updated[0] = {}, len = {}", updated[0], updated.len());
}
// Arc::make_mut while shared: 529.5us .. 1.38ms, same buffer: false
// Arc::make_mut when unique:   41ns .. 84ns
// im::Vector::update:          291ns .. 458ns, reader still sees 0
```

**Why it matters**

`Arc` plus `make_mut` is persistence by full copy: correct, simple, and priced at O(n) per version whenever anyone still holds the previous one, which is the whole point of having versions. For a config or a route table republished occasionally, that is fine; for a structure updated per request while readers hold it, the cost is a full clone per request. F# ships persistent collections in FSharp.Core and .NET in System.Collections.Immutable; C++ ships none; JavaScript gets structural sharing from libraries such as Immer or Effect.

**Chew on this**

Which of your `Arc<Vec<_>>` or `Arc<HashMap<_, _>>` values are updated while readers hold them, and how large are they at the point where `make_mut` clones?

**Sources**

- https://doc.rust-lang.org/std/sync/struct.Arc.html#method.make_mut
- https://docs.rs/im/15.1.0/im/struct.Vector.html
- https://doc.rust-lang.org/std/sync/struct.Arc.html#method.ptr_eq

**Verified**

Timings are single runs in a container, repeated three times; `im` was compiled from crates.io, not audited.

**Gotchas**

- `make_mut` clones only while the value is shared; once the clone exists, the writer owns it and later writes are in place, so the cost hits the first write of each version.
- Weak references count too: the 2026-09-30 entry measured what `make_mut` does when only `Weak` pointers remain.
- `im::Vector` indexing walks a tree, so random access costs more than `Vec` indexing (from the crate's documentation; not measured here); the trade is cheap versions for slower reads.

## C++: atomic<shared_ptr> is how C++20 publishes an immutable snapshot, and on libstdc++ it is not lock-free, yet it still beat a mutex 2.5x

*Stdlib and ecosystem gems*

**Did you know**

C++ has no persistent containers in std; the idiomatic substitute is an immutable snapshot, `std::shared_ptr<const T>`, replaced wholesale by a writer and read by many readers. C++20 standardized the publication step as `std::atomic<std::shared_ptr<T>>` (`__cpp_lib_atomic_shared_ptr` 201711 in g++ 14.2). On libstdc++, `is_lock_free()` and `is_always_lock_free` were both `0` on g++ 14.2 and g++ 16.2: the implementation uses an internal lock. It was still faster than the obvious alternative: four reader threads doing 2 million loads each took 103 to 122 ms, against 274 to 308 ms for copying a `shared_ptr` out from under a `std::mutex`. A reader that loaded the old snapshot kept seeing 2 routes after the writer stored a version with 3.

**Show me**

```cpp
// C++20, g++ 14.2 -O2 (g++ 16.2: same results), Linux aarch64.
#include <atomic>
#include <cstdio>
#include <memory>
#include <vector>

using route_table = std::vector<int>;

int main() {
    std::atomic<std::shared_ptr<const route_table>> current{std::make_shared<const route_table>(route_table{80, 443})};
    std::printf("is_lock_free: %d\n", current.is_lock_free());                                          // 0
    std::printf("__cpp_lib_atomic_shared_ptr: %ld\n", (long)__cpp_lib_atomic_shared_ptr);             // 201711
    std::printf("is_always_lock_free: %d\n", std::atomic<std::shared_ptr<const route_table>>::is_always_lock_free); // 0
    auto snapshot = current.load();                       // readers hold an immutable version
    current.store(std::make_shared<const route_table>(route_table{80, 443, 8080})); // writer publishes a new one
    std::printf("reader still sees %zu routes, new version has %zu\n", snapshot->size(), current.load()->size()); // 2, 3
    std::printf("sizeof atomic<shared_ptr>: %zu, sizeof shared_ptr: %zu\n", sizeof(current), sizeof(snapshot));    // 16, 16
}
// 4 readers x 2M loads each, 12 cores: atomic<shared_ptr> 103-122 ms, std::mutex + shared_ptr copy 274-308 ms
```

**Why it matters**

The snapshot pattern is C++'s answer to persistence: never mutate a published value, replace it. `atomic<shared_ptr>` makes the replacement race-free without every reader taking a mutex, but "atomic" is not "lock-free", which matters in a signal handler, a real-time thread, or anywhere a reader must never wait. The new version is a full copy of the data (170 to 504 us for a million elements, warm), because std has no structure that shares the unchanged parts. Rust's `Arc` swap has the same full-copy cost and no std atomic swap at all (the `arc-swap` crate fills that gap; not measured here); F# and .NET persistent collections share structure, so a new version is cheap and only the reference needs publishing.

**Chew on this**

Which of your threads read a published snapshot, and is any of them on a path where waiting on even a short internal lock is not acceptable?

**Sources**

- https://en.cppreference.com/w/cpp/memory/shared_ptr/atomic2
- https://en.cppreference.com/w/cpp/atomic/atomic/is_lock_free
- https://gcc.gnu.org/onlinedocs/libstdc++/manual/status.html#status.iso.2020

**Verified**

libstdc++ on aarch64 only; libc++, MSVC and x86_64 were not checked, and lock-freedom is platform-dependent. Timings are single runs repeated four times.

**Gotchas**

- `sizeof(std::atomic<std::shared_ptr<T>>)` was 16, the same as `shared_ptr`, so the lock lives inside the existing pointer storage rather than in a separate mutex object (inferred from the size; the libstdc++ source was not read here).
- The reader's snapshot is a real `shared_ptr`, so the old version stays alive until the last reader drops it; a slow reader pins old versions in memory.
- The first full copy took 8.7 ms against 170 to 504 us afterwards: page faults on fresh memory, which a benchmark that starts timing on the first copy measures instead of the copy.

## F#: ImmutableList is an AVL tree, so one Add to 100,000 items cost 1,032 bytes, and 100,000 Adds cost 17 times what its builder did

*Perf and memory model*

**Did you know**

`System.Collections.Immutable.ImmutableList<T>` is a balanced tree, not an array: every `Add` copies the path from the root to the new leaf and shares the rest. One `Add` to a 100,000-item list allocated 1,032 bytes, which is cheap for a new version. Building the list with 100,000 `Add` calls allocated 82.5 MB in 45 ms, while `ImmutableList.CreateBuilder` did the same in 4.8 MB and 11 ms. F#'s own `Map.add` loop cost about the same as the `ImmutableList` loop (85.7 MB), and consing onto an F# `list` cost 6.4 MB in 2.8 ms. Reading is where the tree shows: indexing all 100,000 positions took 3.5 ms, against effectively nothing for an array.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, Release build.
open System.Collections.Immutable

let measure (label: string) (run: unit -> int) =
    run () |> ignore
    let before_bytes = System.GC.GetAllocatedBytesForCurrentThread()
    let watch = System.Diagnostics.Stopwatch.StartNew()
    let result = run ()
    printfn "%-40s %8.1f ms %12d bytes  (%d)" label watch.Elapsed.TotalMilliseconds (System.GC.GetAllocatedBytesForCurrentThread() - before_bytes) result

let item_count = 100_000
measure "ImmutableList.Add x100k" (fun () -> (Seq.fold (fun (list: ImmutableList<int>) item -> list.Add item) ImmutableList<int>.Empty (seq { 1 .. item_count })).Count)
measure "ImmutableList builder x100k" (fun () -> let builder = ImmutableList.CreateBuilder<int>() in (for item in 1 .. item_count do builder.Add item); builder.ToImmutable().Count)
measure "F# list cons x100k" (fun () -> List.length (List.fold (fun tail item -> item :: tail) [] [ 1 .. item_count ]))
measure "F# Map.add x100k" (fun () -> Map.count (Seq.fold (fun table item -> Map.add item item table) Map.empty (seq { 1 .. item_count })))
let filled = ImmutableList.CreateRange(seq { 1 .. item_count })
let fs_array = [| 1 .. item_count |]
measure "ImmutableList indexer, every index" (fun () -> let mutable total = 0 in (for index in 0 .. item_count - 1 do total <- total + filled[index]); total % 1000)
measure "array indexer, every index" (fun () -> let mutable total = 0 in (for index in 0 .. item_count - 1 do total <- total + fs_array[index]); total % 1000)
let shared_base = ImmutableList.CreateRange(seq { 1 .. item_count })
measure "one Add to a 100k ImmutableList" (fun () -> (shared_base.Add 0).Count)
// ImmutableList.Add x100k                 45.3 ms     82524256 bytes
// ImmutableList builder x100k             10.9 ms      4800280 bytes
// F# list cons x100k                       2.8 ms      6400232 bytes
// F# Map.add x100k                        45.5 ms     85706448 bytes
// ImmutableList indexer, every index       3.5 ms          192 bytes
// array indexer, every index               0.0 ms          192 bytes
// one Add to a 100k ImmutableList          0.0 ms         1032 bytes
```

**Why it matters**

A persistent structure is priced per version: cheap when you keep old versions around, expensive when you were only ever going to keep the last one. Building a collection with repeated `Add` pays the "new version" price 100,000 times and throws 99,999 versions away; the builder (or `ImmutableList.CreateRange`) is the mutable construction phase the type is designed to have. The `ImmutableList` name also suggests `List<T>`, whose indexer is O(1); this one is O(log n). Rust's `im::Vector` makes the same trade, a C++ snapshot copies everything, and an F# `list` is the cheapest of all for cons, because it only ever shares a tail.

**Chew on this**

Where your code builds an immutable collection in a loop, is any intermediate version ever read by anyone, and if not, what is the builder costing you by not being used?

**Sources**

- https://learn.microsoft.com/dotnet/api/system.collections.immutable.immutablelist-1
- https://learn.microsoft.com/dotnet/api/system.collections.immutable.immutablelist.createbuilder
- https://learn.microsoft.com/dotnet/standard/collections/thread-safe/immutable-collections (the "Builders" section)

**Gotchas**

- `ImmutableArray<T>` is the array-backed sibling: O(1) indexing, but every `Add` copies the whole array; pick by whether you index or version more.
- F#'s `Map.add` in a loop allocated about as much as `ImmutableList.Add` (85.7 MB): it is also a balanced tree with path copying.
- The `let mutable total` in the indexing loops is a local accumulator for the benchmark, not part of either data structure.

## TypeScript: Immer shares the untouched part of the tree with your original and then freezes it, so writing to the original's other branch threw

*Idioms and antipatterns*

**Did you know**

Immer's `produce` gives you persistent updates on plain objects: the new version shares every subtree you did not touch with the base (`raised.globex === tenants.globex` was `true`). By default it also deep-freezes the result, and because the untouched subtrees *are* the original's objects, freezing the result freezes parts of the original. After one `produce` that changed only `acme`, writing `tenants.globex.limits.max_upload_mb` in an ES module threw "TypeError: Cannot assign to read only property 'max_upload_mb'", while writing `tenants.acme.limits.max_upload_mb` (the branch Immer had copied) still worked. In a sloppy-mode CommonJS script the same write was silently ignored, and `setAutoFreeze(false)` left the original unfrozen.

**Show me**

```javascript
// JavaScript (ESM is strict mode), Node 22.23.4, immer 11.2.9.
import { produce } from "immer"

const tenants = { acme: { limits: { max_upload_mb: 10 } }, globex: { limits: { max_upload_mb: 20 } } }
const raised = produce(tenants, (draft) => { draft.acme.limits.max_upload_mb = 50 })
console.log("acme changed:", raised.acme.limits.max_upload_mb, "| original:", tenants.acme.limits.max_upload_mb) // 50 | 10
console.log("untouched globex shared:", raised.globex === tenants.globex)                                     // true
console.log("result frozen:", Object.isFrozen(raised), "| shared globex frozen:", Object.isFrozen(tenants.globex), "| original root frozen:", Object.isFrozen(tenants))
// result frozen: true | shared globex frozen: true | original root frozen: false
try { tenants.globex.limits.max_upload_mb = 99; console.log("wrote original globex:", tenants.globex.limits.max_upload_mb) }
catch (thrown) { console.log("writing the ORIGINAL globex threw:", thrown.constructor.name, thrown.message) }
// writing the ORIGINAL globex threw: TypeError Cannot assign to read only property 'max_upload_mb' of object '#<Object>'
try { tenants.acme.limits.max_upload_mb = 99; console.log("wrote original acme:", tenants.acme.limits.max_upload_mb) }
catch (thrown) { console.log("writing original acme threw:", thrown.constructor.name) }
// wrote original acme: 99
```

**Why it matters**

Structural sharing is what makes Immer cheap, and auto-freeze is what keeps the sharing safe: a shared subtree must never change, so Immer makes sure it cannot. The surprise is that "the result is frozen" includes objects you still think of as your own mutable input, and which branches are affected depends on which ones the recipe happened not to touch, so the same write to the original works or throws depending on an unrelated update. In sloppy-mode code it does neither: the write just does not happen. Rust's `im` and .NET's immutable collections share structure through types that have no mutating methods at all; C++ snapshots copy, so there is nothing shared to freeze.

**Chew on this**

After you pass an object to `produce`, does any code still mutate the original, and would it be in strict mode (an exception) or sloppy mode (a silent no-op)?

**Sources**

- https://immerjs.github.io/immer/freezing
- https://immerjs.github.io/immer/api#setautofreeze
- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/Object/freeze

**Gotchas**

- Only the shared branches freeze: the copied `acme` branch of the original stayed writable, so the behaviour of the original depends on what the recipe changed.
- The original's root was not frozen (`Object.isFrozen(tenants)` was `false`), because the root itself was copied; only shared children are.
- Every ES module is strict, so the same line that silently failed in a `.cjs` script threw in an `.mjs` one.

# The functional angle: a persistent structure is cheap per version and expensive per element, and only F# ships one where you need it

_Draws on all four tips. The shape: produce a new version with one change while old versions are still readable, and price the new version._

| Language | Persistent form | Cost of one new version | Cost of building it element by element | Shipped where |
| --- | --- | --- | --- | --- |
| F# | `list`, `Map`, `ImmutableList` | 1,032 bytes for one `ImmutableList.Add` to 100,000 | 82.5 MB per 100,000 `Add`s (builder: 4.8 MB) | FSharp.Core and .NET |
| Rust | `im::Vector` | 291 to 458 ns for one `update` of 1,000,000 | not measured | a crate; std has none |
| Rust | `Arc<Vec>` + `make_mut` | 0.5 to 1.4 ms (a full clone) while shared | in place when unique | std |
| C++ | `atomic<shared_ptr<const vector>>` snapshot | 170 to 504 us (a full copy) of 1,000,000 | not applicable | std, but no sharing |
| TypeScript | Immer `produce` | copies only the changed path; shared parts frozen | not measured | a library |

F# is the baseline because its default collections are persistent, so the row shows the shape's real price: very cheap versions, and a large bill if you use versions where you only wanted construction. The other rows show what each language does without that default: Rust and C++ fall back to whole copies, and TypeScript adds sharing through a library that has to freeze objects to keep the sharing honest.

Left open: for the structure in your service that is read by many and changed by few, is your cost per change a path or the whole thing, and which would you have guessed?

# The security angle: an immutable snapshot is a promise that a revocation will not reach you

_Draws on the C++ tip, Mode B: the tip shows a reader keeping the old snapshot after the writer publishes a new one. When the snapshot is an access list, "keeps the old version" means "keeps a revoked permission"._

```cpp
// C++20, g++ 14.2: the reader loaded the route table before the writer changed it
auto snapshot = current.load();                 // a request handler takes the current ACL / route table
current.store(std::make_shared<const route_table>(route_table{80, 443, 8080})); // an operator publishes a change
snapshot->size();                               // 2: the handler keeps deciding with the old version
```

This is by design, and it is a TOCTOU window (CWE-367) as long as the reader holds the snapshot: a long request, a streaming connection or a cached handle can keep making decisions with a permission that was revoked minutes ago. The Immer case is the quieter version: in sloppy-mode code, a write meant to revoke something in the original after a `produce` was silently ignored (the value stayed 20).

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | a reader's `shared_ptr` snapshot keeps a revoked entry alive | keeps the old version alive by design | bound how long a snapshot may be held, or re-load before security decisions |
| Rust | an `Arc` clone held by a task keeps the old version | same as C++ | same: re-read the `Arc` per decision on long-lived tasks |
| F# / .NET | a captured `ImmutableList` or `Map` is an old version forever | same; versions never change | hold the reference that is republished, not the value |
| TypeScript | a revoking write to an Immer-frozen original is ignored in sloppy mode | strict mode throws; sloppy mode does nothing | run in strict mode (ES modules are), and never mutate a `produce` base |

Left open: how long can a request in your service keep the permission set it loaded at its start, and what is the longest-running request you have?

# FAQ

**Is `std::atomic<std::shared_ptr>` lock-free anywhere?**
`is_always_lock_free` was `false` on libstdc++ (g++ 14.2 and 16.2) on aarch64; other standard libraries and architectures may differ, which is why both `is_lock_free()` and the compile-time constant exist. Only libstdc++ on aarch64 was measured here.

**Does Immer freeze anything if `setAutoFreeze(false)` is called?**
No: with auto-freeze off, the shared `globex` subtree of the original was not frozen after `produce`. The sharing still happens; only the protection is gone.

**Is an F# `list` persistent too?**
Yes, for its one cheap operation: consing onto the front shares the whole tail, which is why building 100,000 elements by cons allocated 6.4 MB, close to one small node per element. Appending at the end copies the list.

**Does `im::Vector` replace `Vec` in Rust?**
It trades faster versions for slower element access (it is a tree; the access cost was not measured here). For data that is versioned more than it is indexed it is the better fit; for hot loops over elements, `Vec` stays faster.
