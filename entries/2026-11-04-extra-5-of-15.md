# Daily Tips special, part 5 of 15: random numbers, or the generator that was fast and the key that paid for it

<!-- special-nav -->
**Specials:** [<- previous: random numbers, part 4 of 15](2026-11-04-extra-4-of-15.md) | [next: random numbers, part 6 of 15 ->](2026-11-04-extra-6-of-15.md)

Not part of the rotation. Part 4 showed a good generator fed a bad seed. This part is about the generator itself: most standard libraries ship a fast one and a secure one, the fast one is the easy name to type, and the choice is usually made by whoever types first. The measurements here also correct a belief: the secure generator is not always the slow one.

# What happened

**Bug class:** a security-sensitive value produced by a generator that was not initialized with enough entropy; the API gave the caller no way to see it (CWE-331, insufficient entropy, in the PRNG family).

**The story, in plain words:**

On 11 August 2013 the Bitcoin project published an alert titled "Android Security Vulnerability". It said that "a component of Android responsible for generating secure random numbers contains critical weaknesses, that render all Android wallets generated to date vulnerable to theft". Every wallet app that made its own private keys on an Android phone was affected, and the alert named several of them. The fix it described was not a patch to a program but a move of money: key rotation, "generating a new address with a repaired random number generator and then sending all the money in your wallet back to yourself".

Three days later the Android security team explained what had gone wrong, in a blog post by an Android security engineer. They had been investigating "the root cause of the compromise of a bitcoin transaction". The cause was that applications using the Java Cryptography Architecture (JCA) for key generation, signing or random numbers "may not receive cryptographically strong values on Android devices due to improper initialization of the underlying PRNG". Code that went through Android's HTTP and `java.net` classes was fine, because those classes seeded the generator from `/dev/urandom`. Code that called `SecureRandom` directly was not. The name said secure. The state behind it had never been filled from the operating system.

Two details make the story useful for the rest of this part. First, the post's advice to developers was to initialize the generator explicitly with entropy from `/dev/urandom` or `/dev/random`, and it said apps running only on Android 4.4 (KitKat) or later "do not need to take any special action to work around this bug": the fix went into the platform. Second, the researchers who notified Google were from ETRI and Korea University, and the post thanks them by name. The compromise was found by looking at what was on the blockchain, not at the code.

The quotes:

- "We recently learned that a component of Android responsible for generating secure random numbers contains critical weaknesses, that render all Android wallets generated to date vulnerable to theft." (Bitcoin alert, 11 August 2013)
- "applications which use the Java Cryptography Architecture (JCA) for key generation, signing, or random number generation may not receive cryptographically strong values on Android devices due to improper initialization of the underlying PRNG." (Android Developers Blog, "Some SecureRandom Thoughts", 14 August 2013)
- "Applications that establish TLS/SSL connections using the HttpClient and java.net classes are not affected as those classes do seed the OpenSSL PRNG with values from /dev/urandom." (same)
- "Applications which run exclusively on Android KitKat (4.4) or above do not need to take any special action to work around this bug." (same)

This part measures what each language does to stop a fast generator from being used for a key, and what the secure one really costs.

## Rust: `SmallRng` is not `CryptoRng`, so passing it to a key function fails at compile time, and the secure `StdRng` ran at about 1,300 MB/s against `SmallRng`'s 9,100

*Type system deep cuts*

**Did you know**

rand 0.9 marks cryptographically secure generators with the trait `CryptoRng`. A function that takes `&mut impl CryptoRng` accepts `StdRng` and refuses `SmallRng` at compile time: error E0277, "the trait bound `SmallRng: CryptoRng` is not satisfied". Throughput on an Apple M3 Pro, 256 MiB each, release build: `SmallRng` 9,034 MB/s, `StdRng` 1,240, `rand::rng()` 1,302 and the operating system's `OsRng` 262 (a second run gave 9,126, 1,321, 1,236 and 265). The secure ones are slower, by roughly a factor of 7 to 34, and still over a thousand megabytes a second for the userspace ones.

**Show me**

```rust
// rand 0.9.5, rustc 1.99.1, release build; Cargo.toml: rand = { version = "0.9", features = ["small_rng"] }
use rand::rngs::{OsRng, SmallRng, StdRng};
use rand::{CryptoRng, RngCore, SeedableRng, TryRngCore};
use std::time::Instant;

const TOTAL_BYTES: usize = 256 * 1024 * 1024;

fn fn_megabytes_per_second(label: &str, mut_rng: &mut impl RngCore) {
    let mut mut_buffer: Vec<u8> = vec![0; 1024 * 1024];
    let start: Instant = Instant::now();
    for _ in 0..(TOTAL_BYTES / mut_buffer.len()) {
        mut_rng.fill_bytes(&mut mut_buffer);
    }
    let seconds: f64 = start.elapsed().as_secs_f64();
    println!("{:<12} {:>9.0} MB/s", label, (TOTAL_BYTES as f64 / 1e6) / seconds);
}

fn fn_make_session_key(mut_rng: &mut impl CryptoRng) -> u64 {
    mut_rng.next_u64()
}

fn main() {
    fn_megabytes_per_second("SmallRng", &mut SmallRng::seed_from_u64(1));
    fn_megabytes_per_second("StdRng", &mut StdRng::seed_from_u64(1));
    fn_megabytes_per_second("rand::rng()", &mut rand::rng());
    fn_megabytes_per_second("OsRng", &mut OsRng.unwrap_err());
    println!("session key from StdRng: {}", fn_make_session_key(&mut StdRng::seed_from_u64(1)));
    // println!("{}", fn_make_session_key(&mut SmallRng::seed_from_u64(1))); // does not compile: SmallRng is not CryptoRng
}
```

Output: four throughput lines in the order above, then `session key from StdRng: 17971643333364160609`. Uncommenting the last line gives `error[E0277]: the trait bound 'SmallRng: CryptoRng' is not satisfied`.

**Why it matters**

The Android failure was a secure-looking name over an unseeded state, which a type bound cannot catch. What it can catch is the other half: a fast generator passed to a function that makes a key. `CryptoRng` is a marker, so the check costs nothing at run time. Note what the bound does not say. `StdRng::seed_from_u64(1)` satisfies `CryptoRng` and is a terrible key source (part 4): the trait certifies the algorithm, not the seed.

**Chew on this**

Which of your functions that create secrets accept a plain `RngCore`, so a fast generator could be passed without an error? Is the seed visible in the type at all?

**Sources**

- https://docs.rs/rand/latest/rand/trait.CryptoRng.html
- https://docs.rs/rand/latest/rand/rngs/struct.SmallRng.html

**Verified**

rustc 1.99.1, rand 0.9.5, release build, native on an Apple M3 Pro (arm64 macOS); the compile error is the compiler's text from a build with the last line uncommented. That `rand::rng()` is a ChaCha-based generator reseeded from the operating system is the crate documentation, not something I checked.

**Gotchas**

- The throughput numbers are one run each on a laptop. The ratio is the claim, not the megabytes.
- `OsRng` in rand 0.9 needs `TryRngCore::unwrap_err` to be used as an `RngCore`; it can fail, which the infallible `rand::rng()` hides.

## C++: `std::random_device` took about 21 ns a word on libstdc++ and 264 to 288 ns on libc++, against 1.2 to 1.3 and 2.8 to 3.0 for `mt19937`, and the standard has no secure generator at all

*Idioms and antipatterns*

**Did you know**

The C++ standard library has `std::mt19937`, `std::random_device` and a few cousins. None is specified to be cryptographically secure: `random_device` may be deterministic, which is why it has an `entropy()` function (part 4 measured it at 32 here). Cost per 32-bit word on an Apple M3 Pro in Linux containers, `-O2`: GCC 16.2 (libstdc++) `mt19937` 1.26 ns and `random_device` 21.2 ns; Debian clang 19.1.7 with libc++ `mt19937` 2.80 ns and `random_device` 263.5 ns. The two libraries disagree by about 12 times on what the device costs. A second run gave 1.21 and 22.0 ns on libstdc++ and 2.98 and 288 ns on libc++.

**Show me**

```cpp
// g++ -std=c++23 -O2 cost.cpp          (GCC 16.2)
// clang++ -std=c++23 -stdlib=libc++ -O2 cost.cpp   (Debian clang 19.1.7)
#include <chrono>
#include <cstdint>
#include <iostream>
#include <random>

template <typename Generator>
double fn_nanoseconds_per_word(Generator& generator, std::uint64_t word_count) {
    const auto start = std::chrono::steady_clock::now();
    std::uint64_t checksum = 0;
    for (std::uint64_t word_index = 0; word_index < word_count; ++word_index) checksum += generator();
    const auto stop = std::chrono::steady_clock::now();
    if (checksum == 42) std::cout << ""; // keep the loop from being removed
    return std::chrono::duration<double, std::nano>(stop - start).count() / static_cast<double>(word_count);
}

int main() {
    constexpr std::uint64_t ENGINE_WORD_COUNT = 50000000;
    constexpr std::uint64_t DEVICE_WORD_COUNT = 2000000; // the device is slower, so fewer words
    std::mt19937 engine(1);
    std::random_device entropy_source;
    std::cout << "mt19937       " << fn_nanoseconds_per_word(engine, ENGINE_WORD_COUNT) << " ns/word\n";
    std::cout << "random_device " << fn_nanoseconds_per_word(entropy_source, DEVICE_WORD_COUNT) << " ns/word\n";
}
```

Output (one run): GCC 16.2 prints about `1.26` and `21.2`; libc++ prints about `2.80` and `263.5`.

**Why it matters**

A program that wants secrets has no portable standard answer: `random_device` is "a source of non-deterministic bits if available", and its cost depends on how the library reads the operating system. The cost gap is what pushes people to seed `mt19937` from one `random_device` call and keep going, which is part 4's 32-bit seed. In a hot loop the 10 to 100 times difference is real; for a handful of keys per request it is not.

**Chew on this**

How often does your code ask for secrets, per request or per second? Is the slow generator actually in a hot path, or was "random_device is slow" a belief?

**Sources**

- https://eel.is/c++draft/rand.device
- https://eel.is/c++draft/rand.eng.mers

**Verified**

GCC 16.2.0 and Debian clang 19.1.7 with libc++, `-O2`, Linux containers on Apple M3 Pro hardware. The claim that the standard specifies no cryptographically secure generator is from the draft's text as I read it, not something a program can show.

**Gotchas**

- `random_device` produced words one call at a time here; an API that reads a block would change the numbers.
- I did not test MSVC, where `random_device` is documented to use the system's cryptographic API.

## F#: `RandomNumberGenerator.Fill` ran at 9,300 to 10,400 MB/s on .NET 10, level with `Random.Shared` and thirty times faster than `Random(1).NextBytes` at about 310

*Stdlib and ecosystem gems*

**Did you know**

On .NET 10 the cryptographic `RandomNumberGenerator.Fill` reached 10,437 MB/s on a 1 MiB buffer, `Random.Shared.NextBytes` 9,376 MB/s, and a seeded `Random(1).NextBytes` only 310 MB/s. A second run gave 9,339, 10,198 and 319: the first two swap places, so treat them as level. The seeded `Random` is the legacy algorithm from part 1, and filling bytes through it is slow; the fast, unseeded `Random.Shared` and the secure generator are an order of magnitude faster. The fast default is not the cheap one, and the secure generator is not the expensive one.

**Show me**

```fsharp
// .NET 10.0.14, dotnet fsi --optimize+
open System
open System.Diagnostics
open System.Security.Cryptography

let total_bytes: int = 256 * 1024 * 1024
let buffer: byte[] = Array.zeroCreate (1024 * 1024)
let fn_megabytes_per_second (label: string) (fn_fill: byte[] -> unit) : unit =
    let stopwatch: Stopwatch = Stopwatch.StartNew()
    for _ in 1 .. total_bytes / buffer.Length do
        fn_fill buffer
    printfn "%-28s %8.0f MB/s" label (float total_bytes / 1e6 / stopwatch.Elapsed.TotalSeconds)

let seeded_random: Random = Random(1)
fn_megabytes_per_second "Random(1).NextBytes" (fun target -> seeded_random.NextBytes target)
fn_megabytes_per_second "Random.Shared.NextBytes" (fun target -> Random.Shared.NextBytes target)
fn_megabytes_per_second "RandomNumberGenerator.Fill" (fun target -> RandomNumberGenerator.Fill(Span<byte>(target)))
```

Output (one run): `Random(1).NextBytes 310 MB/s`, `Random.Shared.NextBytes 9376 MB/s`, `RandomNumberGenerator.Fill 10437 MB/s`.

**Why it matters**

"Use the cryptographic one because it is safer" and "use `Random` because it is faster" are both slogans, and the numbers say the second is false for bulk bytes in .NET 10. Per-call costs differ from per-byte costs: this measures 1 MiB fills, not a million calls for one byte each, where the system call or lock would dominate. The seeded legacy `Random` is the slow one, which is the cost of the compatibility choice in part 1.

**Chew on this**

Was the last time you chose `Random` over `RandomNumberGenerator` a measurement or a habit? Which cost would you measure first: bytes per second or calls per second?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.randomnumbergenerator
- https://learn.microsoft.com/en-us/dotnet/api/system.random.shared

**Verified**

.NET SDK 10.0 image (Ubuntu, aarch64 container on Apple M3 Pro), `dotnet fsi --optimize+`. One run each. Throughput for one-byte calls was not measured.

**Gotchas**

- `dotnet fsi` without `--optimize+` can distort a tight loop; the numbers above are optimized.
- `Random.Shared` needs no lock in the common case; the docs say it is thread-safe and I did not measure contention.

## TypeScript: `crypto.getRandomValues` filled bytes at about 8,500 MB/s on Node 26, forty-five times a byte-at-a-time `Math.random` loop at about 190 MB/s

*Stdlib and ecosystem gems*

**Did you know**

In Node 26.13, filling a 64 KiB buffer from `crypto.getRandomValues` ran at 8,639 MB/s and `crypto.randomFillSync` at 9,446 (a second run: 8,411 and 9,461). Filling the same buffer with `Math.random() * 256` byte by byte ran at 191 MB/s. `Math.random` produces one double per call, so building bytes from it is the slow way and the insecure way at once. Web Crypto's `getRandomValues` accepts at most 65,536 bytes per call.

**Show me**

```ts
// Node 26.13.0: save as cost.mts, run with node cost.mts (types are stripped)
import { randomFillSync } from "node:crypto"

const const_total_bytes: number = 256 * 1024 * 1024
const const_buffer: Uint8Array = new Uint8Array(65536) // getRandomValues allows at most 65536 bytes per call

const const_fn_megabytes_per_second = (label: string, fn_fill: (target: Uint8Array) => void): void => {
    const start: number = performance.now()
    for (let chunk_index: number = 0; chunk_index < const_total_bytes / const_buffer.length; chunk_index++) fn_fill(const_buffer)
    console.log(label.padEnd(30), Math.round(const_total_bytes / 1e6 / ((performance.now() - start) / 1000)), "MB/s")
}

const_fn_megabytes_per_second("Math.random bytes", (target) => { for (let byte_index = 0; byte_index < target.length; byte_index++) target[byte_index] = Math.random() * 256 })
const_fn_megabytes_per_second("crypto.getRandomValues", (target) => { crypto.getRandomValues(target) })
const_fn_megabytes_per_second("crypto.randomFillSync", (target) => { randomFillSync(target) })
```

Output (one run): `Math.random bytes 191 MB/s`, `crypto.getRandomValues 8639 MB/s`, `crypto.randomFillSync 9446 MB/s`.

**Why it matters**

The usual argument for `Math.random` in a token generator is speed, and for bulk bytes it does not hold. The remaining cost of `crypto` is the per-call overhead for tiny requests, which this probe does not measure. And `Math.random` cannot be made safe by being called more: it is predictable from its outputs (part 10).

**Chew on this**

How many random bytes does your service request per second, and in how many calls? If both numbers are small, what was the speed argument for?

**Sources**

- https://nodejs.org/api/crypto.html#cryptogetrandomvaluestypedarray
- https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues

**Verified**

Node v26.13.0 in the `node:lts` image (aarch64 container on Apple M3 Pro), one run. The 65,536-byte limit is the documented Web Crypto quota, not something I exceeded.

**Gotchas**

- A tight `Math.random` byte loop is not the best a `Math.random` user could do; the claim is about the idiom, not the floor.
- `crypto.randomInt` and `randomUUID` have their own costs; I did not measure them.

# The functional angle: the secure and the fast generator are the same function with a different environment, and the type should say which

Draws on the Rust tip and the Android story. A function that makes a key takes a generator as a parameter (an effect passed in, not reached for). That makes the choice visible at the call site and testable, but only if the type says which kind it needs. Only Rust did.

```rust
// Rust: the capability is in the signature
fn fn_make_session_key(mut_rng: &mut impl CryptoRng) -> u64 { mut_rng.next_u64() }
```

| Language | Does the signature distinguish secure from fast? | Measured throughput of the secure option | What the call site must do |
| --- | --- | --- | --- |
| Rust | yes: `CryptoRng` is a bound, a compile error otherwise | `StdRng` 1,240 MB/s, `OsRng` 262 | pass a `CryptoRng`; the seed is still unchecked |
| C++ | no; `random_device` and `mt19937` are both just callables | `random_device` 21 or 264 ns/word | name the source in review |
| F# | no; `RandomNumberGenerator` is a different class, not a type bound | 10,437 MB/s | choose the class |
| TypeScript | no; `crypto` and `Math.random` are different functions | 8,639 MB/s | choose the function |

Rust is the baseline here because it is the only row whose compiler can refuse a mistake. Is a marker trait the right shape, or only the first step of one that says where the seed came from too?

# The security angle: a name that says "secure" does not say the state was filled

Draws on the Android story and the Rust tip. Mode B (what the language does not prevent). Bug classes: CWE-331 (Insufficient Entropy), CWE-338 (Use of Cryptographically Weak PRNG) and CWE-337.

```rust
// Rust: the bound passes, the seed is a constant: the compiler certifies the algorithm, not the entropy
let mut mut_rng = StdRng::seed_from_u64(0);
let _key: u64 = fn_make_session_key(&mut mut_rng); // compiles
```

The Android post's own advice is the discipline: initialize explicitly from `/dev/urandom` or `/dev/random`, or let the platform do it, and re-generate keys that were made before the fix.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | a `CryptoRng` seeded from a constant (measured to compile) | the bound blocks `SmallRng` | take `rand::rng()` or `OsRng`, never `seed_from_u64` |
| C++ | nothing marks a generator as secure | nothing | pick a vetted library or the OS |
| F# | `Random` is used where `RandomNumberGenerator` was meant | different class, same method names | grep for `Random(` in key code |
| TypeScript | `Math.random` where `crypto` was meant | nothing | a lint rule against `Math.random` in key code |

TypeScript is the baseline because nothing in the type system or the library separates the two, and the cost argument does not hold either. If the platform fixes your generator in a later release, as Android did in 4.4, how will you know which keys were made before?

# FAQ

**Does `SecureRandom` on Android still have this problem?**
The post says applications running only on Android 4.4 or later need no special action. I did not check later versions.

**Is `rand::rng()` secure?**
Per the rand documentation it is a ChaCha-based generator seeded from the operating system. I did not verify that beyond the throughput number.

**Why is `OsRng` slower than `StdRng` in Rust?**
Not measured. A plausible cause is a system call per fill, but I did not check.
