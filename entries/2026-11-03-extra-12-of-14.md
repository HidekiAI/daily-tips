Not part of the rotation. Part 12 of the fourteen-part special on real incidents: the [Windows 10 October 2018 Update](https://blogs.windows.com/windowsexperience/2018/10/09/updated-version-of-windows-10-october-2018-update-released-to-windows-insiders/), version 1809, which Microsoft paused after it deleted users' files. Each tip below is a delete call that either refuses a folder with something in it or removes everything, and asks which one your cleanup code actually calls.

# What happened

**Bug class:** Bohrbug in this special's classification, configuration-triggered: Microsoft ties it to Known Folder Redirection set up before the update, with files left in the old location. The anti-pattern the tips below take from it is a cleanup whose name and intent say "empty folders" while its delete call does not require the folder to be empty. Microsoft does not say which call it used; this is the class the tips illustrate.

From Microsoft's "Updated version of Windows 10 October 2018 Update released to Windows Insiders" (John Cable, Windows Experience Blog, 9 October 2018):

```text
In previous feedback from the Windows 10 April 2018 Update, users with KFR reported an
extra, empty copy of Known Folders on their device. Based on feedback from users, we
introduced code in the October 2018 Update to remove these empty, duplicate known folders.
That change, combined with another change to the update construction sequence, resulted in
the deletion of the original "old" folder locations and their content, leaving only the new
"active" folder intact.
```

KFR is Known Folder Redirection, moving Documents, Pictures and the like to a new location. Microsoft says the loss "occurred if Known Folder Redirection (KFR) had been previously enabled, but files remain in the original "old" folder location vs being moved to the new, redirected location", and that "the reports of actual data loss are few (one one-hundredth of one percent of version 1809 installs), any data loss is serious". The fixed release keeps "the 'original' old folder location and its contents" intact. Microsoft does not publish the code, so every snippet below is an illustration of the class, not Windows code, and every one was run on Linux.

## Rust: `fs::remove_dir` is the emptiness check, done by the kernel in the same call, and a separate check followed by `remove_dir_all` deletes whatever arrived in between

*Stdlib and ecosystem gems*

**Did you know**

`std::fs::remove_dir` removes a directory only if it is empty; on a directory with a file in it, it returned `Err` with kind `DirectoryNotEmpty` (stable since Rust 1.83.0) and the file survived. `remove_dir_all` removes the directory and everything in it. The common "safe" version, check that the folder looks empty and then call `remove_dir_all`, has a window: in a deterministic run where a file was written between the check and the delete, the check said empty and `remove_dir_all` deleted the new file. `remove_dir` in the same sequence refused, because the kernel decides emptiness at the moment of the delete. Measured on rustc 1.99.1, Debian.

**Show me**

```rust
// rustc 1.99.1, edition 2024, Debian. An illustration of the class, not Windows code.
use std::fs;
use std::path::Path;

fn is_empty_dir(dir_path: &Path) -> std::io::Result<bool> { Ok(fs::read_dir(dir_path)?.next().is_none()) }

fn main() -> std::io::Result<()> {
    for uses_remove_dir_all in [true, false] {
        let duplicate_known_folder = Path::new("/tmp/probe/duplicate_documents");
        fs::create_dir_all(duplicate_known_folder)?;
        let looked_empty = is_empty_dir(duplicate_known_folder)?;          // 1. the cleanup checks: empty
        fs::write(duplicate_known_folder.join("draft.txt"), b"saved")?;      // 2. the user saves a file
        let delete_io_result = if uses_remove_dir_all { fs::remove_dir_all(duplicate_known_folder) } else { fs::remove_dir(duplicate_known_folder) };
        println!("remove_dir_all={uses_remove_dir_all} looked_empty={looked_empty} delete={:?} draft_survived={}",
            delete_io_result.map_err(|io_error| io_error.kind()), duplicate_known_folder.join("draft.txt").exists());
        let _ = fs::remove_dir_all(duplicate_known_folder); // probe cleanup only
    }
    Ok(())
}
// remove_dir_all=true looked_empty=true delete=Ok(()) draft_survived=false
// remove_dir_all=false looked_empty=true delete=Err(DirectoryNotEmpty) draft_survived=true
```

**Why it matters**

A cleanup that is only ever meant to remove empty folders does not need a check at all: `remove_dir` is the check, and it cannot be out of date. Reaching for `remove_dir_all` in case of hidden files is what turns an emptiness rule into a recursive delete. The 1809 explanation has the same shape, an intent ("remove these empty, duplicate known folders") and an outcome ("and their content"), though Microsoft does not publish the mechanism between them.

**Chew on this**

Which of your cleanup jobs call `remove_dir_all` on a path that is supposed to be empty already? If one of them met a folder with a file in it, would you rather it stopped or carried on?

**Sources**

- https://doc.rust-lang.org/std/fs/fn.remove_dir.html
- https://doc.rust-lang.org/std/fs/fn.remove_dir_all.html
- https://doc.rust-lang.org/std/io/enum.ErrorKind.html#variant.DirectoryNotEmpty

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1. The two output lines in the comments are the program's output. The interleaving is forced by running the write between the check and the delete, not by timing.

**Gotchas**

- `remove_dir_all` itself once had a check-then-act window of this kind: [CVE-2022-21658](https://blog.rust-lang.org/2022/01/20/cve-2022-21658/), "vulnerable to a race condition enabling symlink following ([CWE-363](https://cwe.mitre.org/data/definitions/363.html))", affected Rust 1.0.0 through 1.58.0 and was fixed in 1.58.1. From the advisory, not reproduced here.
- `fs::remove_dir` on a path that does not exist is an `Err` too, of kind `NotFound`, so a cleanup that treats every `Err` as "not empty" will log a missing folder as a full one; the functional angle below separates the two.

## C++: `std::filesystem::remove` returns `false` both when the folder was not there and when it refused a full one, and only the `error_code` tells them apart

*Stdlib and ecosystem gems*

**Did you know**

`std::filesystem::remove` (C++17) deletes a file or an empty directory and returns whether it deleted anything. On a directory holding a file it returned `false` and set the `error_code` to "Directory not empty"; on a path that did not exist it also returned `false`, with the `error_code` clear ("Success"). A caller that tests only the `bool` cannot tell "nothing to clean" from "refused, there are files in here". `remove_all` deletes recursively and returns a count: 2 for a folder holding one file, and 0 for a missing path. Measured on GCC 16.2 and clang 22.1.8, both with libstdc++, on Debian.

**Show me**

```cpp
// C++17, g++ 16.2 and clang++ 22.1.8, Debian. An illustration of the class, not Windows code.
#include <cstdio>
#include <filesystem>
#include <fstream>
#include <system_error>
namespace fs = std::filesystem;

int main() {
    const fs::path old_documents_dir = "/tmp/probe/old_documents";
    fs::create_directories(old_documents_dir);
    std::ofstream(old_documents_dir / "thesis.docx") << "five years of work";

    std::error_code full_remove_error;
    const bool full_was_removed = fs::remove(old_documents_dir, full_remove_error);
    std::printf("full folder: removed=%d error_set=%d\n", full_was_removed, static_cast<bool>(full_remove_error)); // 0 1

    std::error_code missing_remove_error;
    const bool missing_was_removed = fs::remove("/tmp/probe/never_existed", missing_remove_error);
    std::printf("missing: removed=%d error_set=%d\n", missing_was_removed, static_cast<bool>(missing_remove_error)); // 0 0

    const std::uintmax_t removed_entry_count = fs::remove_all(old_documents_dir);
    std::printf("remove_all removed %ju entries\n", removed_entry_count);                         // 2: the folder and the thesis
}
```

**Why it matters**

`if (!fs::remove(folder_path)) fs::remove_all(folder_path);` reads like "fall back if the simple delete did not work", and the simple delete did not work precisely because the folder had content. The `bool` is the wrong signal to branch on; the `error_code` is the one that says why.

**Chew on this**

Where does your code call `remove` and look only at its return value? What does each of those callers do when the answer is `false` because the folder still holds files?

**Sources**

- https://en.cppreference.com/w/cpp/filesystem/remove
- https://en.cppreference.com/w/cpp/filesystem/is_empty

**Verified**

GCC 16.2.0 (`gcc:latest`) and Debian clang 22.1.8 (`silkeh/clang:latest`, using libstdc++), both Debian, `-std=c++17` and `-std=c++23` with `-Wall -Wextra`, no warnings. The output values in the comments come from those runs; libc++ and MSVC were not tested.

**Gotchas**

- The throwing overload reports the reason in its message: `fs::remove(old_documents_dir)` without an `error_code` threw `filesystem error: cannot remove: Directory not empty [/tmp/probe/old_documents]`.
- `fs::is_empty` is a separate call with the same window as the Rust tip's `read_dir` check: it returned 0 on the full folder, and any file created after it returns is not part of its answer.

## F#: `Directory.Delete(path, true)` puts the destructive mode in a bare `true`, and computing it from an emptiness check rebuilds the 1809 shape

*Idioms and antipatterns*

**Did you know**

.NET's `Directory.Delete(path)` refuses a directory with content: it threw `IOException` "Directory not empty : '/tmp/probe/old_documents'" and the file survived. The overload `Directory.Delete(path, true)` deletes recursively, and the only thing at the call site that says so is a bare `true`. F# lets the call name it, `Directory.Delete(path, recursive = true)`, which compiled and behaved the same. Naming the flag also makes the dangerous version visible: `Directory.Delete(folder_path, recursive = looked_empty)` is "delete recursively because it looked empty", and with a file written after the check it deleted the file. Measured on .NET SDK 10.0.403, FSharp.Core 10.1.0.0, .NET 10.0.14.

**Show me**

```fsharp
// F# 10, .NET 10.0.14. An illustration of the class, not Windows code.
open System.IO

let duplicate_known_folder = "/tmp/probe/duplicate_documents"
Directory.CreateDirectory duplicate_known_folder |> ignore
let looked_empty = Seq.isEmpty (Directory.EnumerateFileSystemEntries duplicate_known_folder)   // 1. the check: empty
File.WriteAllText(Path.Combine(duplicate_known_folder, "draft.txt"), "saved")                    // 2. the user saves a file

Directory.Delete(duplicate_known_folder, recursive = looked_empty)                               // 3. recursive, because it looked empty
printfn "looked_empty=%b draft_survived=%b" looked_empty (File.Exists(Path.Combine(duplicate_known_folder, "draft.txt")))
// looked_empty=true draft_survived=false
```

**Why it matters**

A named argument does not make the call safer, but it makes it readable in review: `recursive = true` on a folder that is meant to be empty is a question a reviewer can ask, and `true` alone is not. The safe form for an "empty folders only" cleanup is the overload without the flag, which refuses on its own.

**Chew on this**

How many `Delete(..., true)` calls in your .NET code would you be able to explain to a reviewer without opening the method? Which of them decide the flag at runtime?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.io.directory.delete
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/members/methods#named-arguments

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0`, which is Ubuntu 24.04 rather than Debian.

**Gotchas**

- .NET has no exception type of its own for "not empty": the refusal is a plain `IOException`, the base class of `DirectoryNotFoundException`. With the `IOException` arm written first, F# warned `FS0026: This rule will never be matched` on the `DirectoryNotFoundException` arm, and a missing folder came back as `KeptNotEmpty`.
- `Directory.Delete(duplicate_known_folder, recursive = true)` with nothing inside removed the folder as well, so a recursive delete gives no sign afterwards whether there was anything in it.

## TypeScript: Node's `fs.rmSync(dir, { recursive: true, force: true })` is the usual cleanup line, and `force` also hides "there was nothing to delete"

*Stdlib and ecosystem gems*

**Did you know**

Node 26 has three directory deletes. `fs.rmdirSync(dir)` refuses a directory with content (`ENOTEMPTY`), `fs.rmSync(dir)` without options refuses any directory (`ERR_FS_EISDIR`), and `fs.rmSync(dir, { recursive: true, force: true })`, the line most cleanup code copies, deletes everything. The `force` half has a second effect: on a path that did not exist, `rmSync` with `recursive` alone threw `ENOENT`, and with `force: true` it returned without a word. The old `fs.rmdirSync(dir, { recursive: true })` is gone: Node 26.13.0 rejected it with `ERR_INVALID_ARG_VALUE`, and current `@types/node` already reports `TS2554: Expected 1 arguments, but got 2`.

**Show me**

```ts
// TypeScript, tsc 7.0.2 --strict --types node with @types/node, Node 26.13.0, Debian. An illustration of the class, not Windows code.
import * as fs from "node:fs"
import * as path from "node:path"

const duplicate_known_folder = "/tmp/probe/duplicate_documents"
for (const uses_recursive_rm of [true, false]) {
    fs.mkdirSync(duplicate_known_folder, { recursive: true })
    const looked_empty = fs.readdirSync(duplicate_known_folder).length === 0      // 1. the cleanup checks: empty
    fs.writeFileSync(path.join(duplicate_known_folder, "draft.txt"), "saved")    // 2. the user saves a file
    let delete_error_code = "none"
    try { uses_recursive_rm ? fs.rmSync(duplicate_known_folder, { recursive: true, force: true }) : fs.rmdirSync(duplicate_known_folder) }
    catch (delete_failure) { delete_error_code = String((delete_failure as NodeJS.ErrnoException).code) }
    console.log(`recursive_rm=${uses_recursive_rm} looked_empty=${looked_empty} error=${delete_error_code} draft_survived=${fs.existsSync(path.join(duplicate_known_folder, "draft.txt"))}`)
    fs.rmSync(duplicate_known_folder, { recursive: true, force: true }) // probe cleanup only
}
// recursive_rm=true looked_empty=true error=none draft_survived=false
// recursive_rm=false looked_empty=true error=ENOTEMPTY draft_survived=true
```

**Why it matters**

`{ recursive: true, force: true }` is two decisions in one literal: delete the contents, and do not complain about anything. A cleanup meant for empty folders wants neither, and `rmdirSync` already says no to the first and reports the second.

**Chew on this**

Which of your scripts call `rmSync` with `force: true`, and which of them would you want to hear from if the path was missing? Where is the folder they delete created, and by whom?

**Sources**

- https://nodejs.org/api/fs.html#fsrmsyncpath-options
- https://nodejs.org/api/fs.html#fsrmdirsyncpath-options

**Verified**

Run in `node:lts-trixie` (Debian), Node 26.13.0, tsc 7.0.2 with `@types/node` from npm and `--types node` (tsc 7 includes no `@types` by default; without it the file fails with TS2591); the two output lines in the comments are the program's output.

**Gotchas**

- `rmSync` with `recursive` but without `force` is the version that still reports a missing path: on `/tmp/probe/never_existed` it threw `ENOENT`, which is the signal `force: true` throws away.
- The two calls also disagree about files: `rmdirSync` on a plain file threw `ENOTDIR`, while `rmSync` on the same file deleted it, so a cleanup that switches from one to the other changes what a wrong path costs.

# The functional angle: a delete that returns which of three things happened, instead of a `bool` or an exception that means two of them

Draws on all four tips. Each language's non-recursive delete already knows the three outcomes, removed, refused because not empty, and not there; the tips show each API folding two of them together. The functional form maps them into one sum type, so the caller has to name each.

```rust
// Rust: remove_dir's io::ErrorKind mapped to an enum.
use std::{fs, io, path::Path};
#[derive(Debug)]
enum FolderRemoval { Removed, KeptNotEmpty, AlreadyGone, Failed(io::ErrorKind) }
fn remove_if_empty(folder_path: &Path) -> FolderRemoval {
    match fs::remove_dir(folder_path) {
        Ok(()) => FolderRemoval::Removed,
        Err(io_error) => match io_error.kind() {
            io::ErrorKind::DirectoryNotEmpty => FolderRemoval::KeptNotEmpty,
            io::ErrorKind::NotFound => FolderRemoval::AlreadyGone,
            unmapped_error_kind => FolderRemoval::Failed(unmapped_error_kind),
        },
    }
}
fn main() -> io::Result<()> {
    let old_documents_dir = Path::new("/tmp/probe/old_documents");
    fs::create_dir_all(old_documents_dir)?;
    fs::write(old_documents_dir.join("thesis.docx"), b"five years of work")?;
    println!("{:?} {:?}", remove_if_empty(old_documents_dir), remove_if_empty(Path::new("/tmp/probe/never_existed"))); // KeptNotEmpty AlreadyGone
    Ok(())
}
```

```cpp
// C++17: std::filesystem::remove plus its error_code, mapped to an enum.
#include <cstdio>
#include <filesystem>
#include <fstream>
#include <system_error>
namespace fs = std::filesystem;
enum class FolderRemoval { Removed, KeptNotEmpty, AlreadyGone, Failed };
FolderRemoval remove_if_empty(const fs::path& folder_path) {
    std::error_code remove_error;
    const bool was_removed = fs::remove(folder_path, remove_error);
    if (was_removed) return FolderRemoval::Removed;
    if (!remove_error) return FolderRemoval::AlreadyGone;                       // false with no error: nothing was there
    if (remove_error == std::errc::directory_not_empty) return FolderRemoval::KeptNotEmpty;
    return FolderRemoval::Failed;
}
int main() {
    const fs::path old_documents_dir = "/tmp/probe/old_documents";
    fs::create_directories(old_documents_dir);
    std::ofstream(old_documents_dir / "thesis.docx") << "five years of work";
    std::printf("%d %d\n", static_cast<int>(remove_if_empty(old_documents_dir)), static_cast<int>(remove_if_empty("/tmp/probe/never_existed"))); // 1 2
}
```

```fsharp
// F#: the same three outcomes as a union, from .NET's exceptions.
open System.IO
type FolderRemoval = Removed | KeptNotEmpty | AlreadyGone
let remove_if_empty (folder_path: string) : FolderRemoval =
    try Directory.Delete folder_path; Removed
    with
    | :? DirectoryNotFoundException -> AlreadyGone
    | :? IOException -> KeptNotEmpty      // .NET raises a plain IOException for "Directory not empty"
let old_documents_dir = "/tmp/probe/old_documents"
Directory.CreateDirectory old_documents_dir |> ignore
File.WriteAllText(Path.Combine(old_documents_dir, "thesis.docx"), "five years of work")
printfn "%A %A" (remove_if_empty old_documents_dir) (remove_if_empty "/tmp/probe/never_existed")   // KeptNotEmpty AlreadyGone
```

```ts
// TypeScript (Node): rmdirSync's error codes mapped to a union.
import * as fs from "node:fs"
import * as path from "node:path"
type FolderRemoval = "removed" | "kept_not_empty" | "already_gone" | "failed"
const fn_folder_removal_from_code = (error_code: string | undefined): FolderRemoval =>
    error_code === "ENOTEMPTY" ? "kept_not_empty" : error_code === "ENOENT" ? "already_gone" : "failed"
const remove_if_empty = (folder_path: string): FolderRemoval => {
    try { fs.rmdirSync(folder_path); return "removed" }
    catch (rmdir_failure) { return fn_folder_removal_from_code((rmdir_failure as NodeJS.ErrnoException).code) }
}
const old_documents_dir = "/tmp/probe/old_documents"
fs.mkdirSync(old_documents_dir, { recursive: true })
fs.writeFileSync(path.join(old_documents_dir, "thesis.docx"), "five years of work")
console.log(remove_if_empty(old_documents_dir), remove_if_empty("/tmp/probe/never_existed")) // kept_not_empty already_gone
```

Each was run on Debian (F# on the Ubuntu SDK image): Rust on rustc 1.99.1 (one warning, that `Failed`'s field is never read), C++ on GCC 16.2 (`-std=c++17 -Wall -Wextra`, no warnings), F# on .NET SDK 10.0.403, TypeScript on Node 26.13.0 with tsc 7.0.2 `--strict`, with the outputs in the comments.

| Language | Non-recursive delete | What it folds together | What the sum type costs |
| --- | --- | --- | --- |
| F# | `Directory.Delete` | "not empty" is a plain `IOException`, the base class of "not found" | arm order matters: with `IOException` first, `FS0026` warned and "missing" came back as `KeptNotEmpty` |
| Rust | `fs::remove_dir` | nothing: `ErrorKind` separates `DirectoryNotEmpty` and `NotFound` | a nested match; `DirectoryNotEmpty` needs Rust 1.83 or later |
| C++ | `fs::remove` | missing and refused are both `false` | reading the `error_code`, and the rule that a clear one after `false` means "missing" |
| TypeScript | `fs.rmdirSync` | nothing in the codes, `ENOTEMPTY` against `ENOENT`, but they are strings | a cast to `NodeJS.ErrnoException` and string comparisons |

F# is the baseline because a union is how F# returns several outcomes by default, which isolates the real cost here: .NET's exceptions do not carry the distinction, so the F# row has to recover it from the exception's type and order.

# The security angle: check-then-delete is a time-of-check to time-of-use window, and the non-recursive delete closes it by not having a check

Draws on all four tips, and runs in both directions: every language offers a delete that refuses atomically, and every language also offers the recursive one that the tips caught deleting a file written after the check. The data-loss version is what 1809 did; the security version is a privileged cleaner deleting what an attacker arranged to be there, which is the class of Rust's CVE-2022-21658. This is the missing-check sample in its most common form, a shell-style cleanup in TypeScript:

```ts
// TypeScript (Node). Looks like a careful cleanup: it checks before it deletes.
import * as fs from "node:fs"
const fn_remove_if_empty_insecure = (folder_path: string): void => {
    if (fs.readdirSync(folder_path).length === 0) {          // the check
        fs.rmSync(folder_path, { recursive: true, force: true }) // the use: deletes whatever is there now
    }
}
const fn_remove_if_empty = (folder_path: string): void => {
    fs.rmdirSync(folder_path)                                // no separate check: the kernel refuses a non-empty folder (ENOTEMPTY)
}
export { fn_remove_if_empty_insecure, fn_remove_if_empty }
```

The TypeScript tip measured what the first one does when a file is written between the two lines: `draft_survived=false`; the second refused with `ENOTEMPTY` and the draft survived. The classes: [CWE-367](https://cwe.mitre.org/data/definitions/367.html), Time-of-check Time-of-use (TOCTOU) Race Condition, for the window, and [CWE-363](https://cwe.mitre.org/data/definitions/363.html), Race Condition Enabling Link Following, which is how the Rust advisory classifies the symlink form.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `read_dir` check, then `remove_dir_all` | `remove_dir` refuses atomically; `remove_dir_all` has guarded symlinks since 1.58.1 | call `remove_dir` when the folder should be empty |
| C++ | `is_empty`, then `remove_all`: on GCC 16.2 the file written in between was deleted (`draft_survived=0`), and `remove` refused it ("Directory not empty") | `remove` refuses a non-empty directory | read the `error_code`, not the `bool` |
| F# | `recursive = looked_empty` | `Directory.Delete(path)` refuses with `IOException` | keep the flag a literal, never computed |
| TypeScript | `readdirSync` check, then `rmSync({ recursive, force })` | `rmdirSync` refuses with `ENOTEMPTY` | drop `force` unless "missing" really is fine |

Rust is the baseline here because its own standard library shipped this class and published the fix, which makes the failure concrete rather than hypothetical. The sample above compiles under tsc 7.0.2 `--strict --types node` with `@types/node`; its behaviour is the one the TypeScript tip measured.

Which of your cleaners run with more privilege than the user who can write into the folder they clean?
