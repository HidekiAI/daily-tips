**The thesis of this part: a fold cannot stop, so every language moves the stop somewhere else, and where it lands decides whether the stop condition can see the running total.** "Add up request sizes until the budget is exceeded" is a fold whose exit depends on its own accumulator. Rust puts the exit inside the fold (`try_fold`), so the condition sees the total. F# puts the running totals in a lazy stream (`Seq.scan`) and cuts that. C++ puts the exit in front of the fold (`take_while`), where it sees only elements, so the total has to be smuggled into the predicate's mutable state. Effect 4 removed its fold-while, and its own migration guide replaces it with a mutable accumulator.

## Rust: try_fold stops at the first None and leaves the iterator just past it, while sum::<Option<u8>> stops at None but not at overflow

*Idioms and antipatterns*

**Did you know**

`fold` always reads everything, but `try_fold` stops as soon as its closure returns `None`, `Err` or `ControlFlow::Break`, and the iterator is left positioned right after the element that stopped it. `try_fold(0u8, |sum, size| sum.checked_add(*size))` over `[100, 100, 100, 7, 8, 9]` returned `None` after three elements, and the next `next()` gave `Some(7)`. `ControlFlow::Break(300)` carried the crossing total out. `sum::<Option<u8>>()` also short-circuits, but only on `None`; it adds with `+`, so three `Some(100)`s panicked in a debug build ("attempt to add with overflow", from `iter/traits/accum.rs`) and returned `Some(44)` in a release build.

**Show me**

```rust
// rustc 1.99.1, edition 2021. Debug build unless noted.
use std::ops::ControlFlow;

fn main() {
    let request_sizes: Vec<u8> = vec![100, 100, 100, 7, 8, 9];

    // try_fold stops at the first None and leaves the iterator just past it.
    let mut remaining = request_sizes.iter();
    let total = remaining.try_fold(0u8, |sum, size| sum.checked_add(*size));
    println!("{total:?}, next = {:?}", remaining.next()); // None, next = Some(7)

    // ControlFlow carries a value out of the stop.
    let crossed = request_sizes.iter().try_fold(0u32, |sum, size| {
        let next_sum = sum + u32::from(*size);
        if next_sum > 250 { ControlFlow::Break(next_sum) } else { ControlFlow::Continue(next_sum) }
    });
    println!("{crossed:?}"); // Break(300)

    // sum::<Option<_>> also stops at the first None, but it adds with +:
    let all_present: Option<u8> = request_sizes[..3].iter().map(|size| Some(*size)).sum();
    println!("{all_present:?}");
    // debug:   panicked at .../iter/traits/accum.rs: attempt to add with overflow
    // release: Some(44), because 300 wrapped around in a u8
}
```

**Why it matters**

`try_fold` is the one shape in this part where the stop is inside the fold, so the condition is free to look at the accumulator, and no mutable state outside the closure is needed. It also explains `sum::<Option<_>>`: that is a `try_fold` whose step is `+`, so "short-circuits on `None`" says nothing about overflow, which is a separate debug/release split. The leftover position matters when the iterator is reused (`by_ref()`, a `&mut` iterator, a parser): the element that stopped the fold has been consumed. A C++ `take_while` cannot see the total at all; F#'s `Seq.scan` sees it because the totals become the stream.

**Chew on this**

Where your code sums `Option`s or `Result`s with `sum()` or `product()`, which numeric type is inside, and what is the largest input a release build would quietly wrap?

- https://doc.rust-lang.org/std/ops/enum.ControlFlow.html
- https://doc.rust-lang.org/std/iter/trait.Sum.html (the `impl Sum<Option<U>> for Option<T>`)

**Gotchas**

- `fold` with an `Option` accumulator (`total.and_then(|sum| sum.checked_add(size))`) gives the same `None` but read all 6 elements instead of 3.
- `ControlFlow` needs no `?`-able type at all, so `try_fold` also works with a plain accumulator and an explicit `Break`.
- The release `Some(44)` is overflow wrapping, not a library choice: build with `-C overflow-checks=on` (or `[profile.release] overflow-checks = true`) to get the debug panic in release too.

## C++: ranges::fold_left cannot stop, so the budget moves into a stateful take_while, and the second pass over the same view kept nothing

*Idioms and antipatterns*

**Did you know**

C++23's `ranges::fold_left` has no early exit: over the six request sizes it returned 324, reading all of them. The ranges way to stop is `views::take_while` in front of the fold, but `take_while` tests elements, not the accumulator, so "stop when the total exceeds 250" needs the predicate to keep its own running total in a captured variable. That gave the right answer once (200). Folding the same view a second time gave 0, because the captured total was still 300 from the first pass. The standard requires the predicate to be `regular_invocable`, meaning equality-preserving, which a stateful predicate is not, and nothing diagnoses it.

**Show me**

```cpp
// C++23 (ranges::fold_left), g++ 14.2 -std=c++23 and g++ 16.2 -std=c++26: same output.
#include <algorithm>
#include <cstdio>
#include <functional>
#include <ranges>
#include <vector>

int main() {
    std::vector<int> request_sizes{100, 100, 100, 7, 8, 9};
    std::printf("%d\n", std::ranges::fold_left(request_sizes, 0, std::plus<>{})); // 324: no way to stop

    // The stop has to go in front of the fold, and take_while sees elements, not the total,
    // so the running total moves into the predicate's own state:
    int running_total = 0;
    auto under_budget = request_sizes | std::views::take_while([&running_total](int size) {
        running_total += size;
        return running_total <= 250;
    });
    std::printf("%d\n", std::ranges::fold_left(under_budget, 0, std::plus<>{})); // 200
    std::printf("%d\n", std::ranges::fold_left(under_budget, 0, std::plus<>{})); // 0: same view, state never reset
}
```

**Why it matters**

Views are meant to be traversed any number of times, and algorithms are allowed to call a predicate more than once per element, which is exactly why the standard asks for equality-preserving predicates. A stateful `take_while` works in the test that walks it once, and breaks the moment the view is walked again: a retry, a `ranges::distance` before the loop, a debug print. The direct C++ answer is still the plain loop with a `break`, which is what `fold_left` cannot express. Rust's `try_fold` and F#'s `Seq.scan` both keep the total in the fold's own state, so a second run starts from the seed again.

**Chew on this**

Which of your range predicates capture something by reference and change it, and how many times does each of those views get walked between creation and destruction?

**Sources**

- https://en.cppreference.com/w/cpp/algorithm/ranges/fold_left
- https://en.cppreference.com/w/cpp/ranges/take_while_view
- https://en.cppreference.com/w/cpp/concepts/invocable (`regular_invocable` and equality preservation)

**Verified**

g++ 14.2 and 16.2 (libstdc++) only.

**Gotchas**

- Resetting the captured total by hand before each pass makes it work again (`ranges::distance` then reported 2 elements kept, with 3 predicate calls), which is the fragility in one line.
- The predicate was called 3 times on the first fold (two passing elements plus the one that stopped it) and once on the second, whose first call already saw a total over 250.
- C++23 also added `ranges::fold_left_with_iter`, which returns where the fold ended; it still read all 6 elements (total 324, iterator at the end).

## F#: Seq.fold cannot stop, so a guard still read all 6 elements, while Seq.scan plus takeWhile stopped after 3

*Perf and memory model*

**Did you know**

`Seq.fold` and `List.fold` have no early exit; a guard in the folder (`if total > 250 then total else total + size`) produces the right total and still reads every element (6 of 6). `Seq.scan` turns the fold inside out: it yields every intermediate total lazily, starting with the seed, so the stop can be an ordinary `Seq.takeWhile` or `Seq.tryFind` on the totals. `Seq.scan (+) 0 |> Seq.takeWhile (fun total -> total <= 250) |> Seq.last` returned 200 after reading 3 elements, and `Seq.tryFind (fun total -> total > 250)` returned `Some 300`, also after 3. `List.scan` is eager and computed all seven totals.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, dotnet fsi.
let mutable evaluations = 0 // counts how many elements the source produced
let request_sizes : seq<int> = seq {
    for size in [ 100; 100; 100; 7; 8; 9 ] do
        evaluations <- evaluations + 1
        yield size }

// A fold cannot stop; a guard keeps the total but every element is still read.
let guarded = Seq.fold (fun total size -> if total > 250 then total else total + size) 0 request_sizes
printfn "Seq.fold with a guard: %d, evaluations %d" guarded evaluations // 300, 6

// scan emits the running totals lazily, so the stop can test the total itself.
evaluations <- 0
let within_budget = request_sizes |> Seq.scan (+) 0 |> Seq.takeWhile (fun total -> total <= 250) |> Seq.last
printfn "Seq.scan, takeWhile, last: %d, evaluations %d" within_budget evaluations // 200, 3

evaluations <- 0
let first_over = request_sizes |> Seq.scan (+) 0 |> Seq.tryFind (fun total -> total > 250)
printfn "Seq.scan, tryFind: %A, evaluations %d" first_over evaluations // Some 300, 3

printfn "%A" (List.scan (+) 0 [ 100; 100; 100; 7; 8; 9 ]) // [0; 100; 200; 300; 307; 315; 324]: eager, all of it
```

**Why it matters**

`scan` is the functional answer that needs no mutable state and no exception: the accumulator becomes data, and every stopping tool that works on data works on it. It is lazy only on `seq`; the same pipeline written with `List.scan` builds every total first, and the stop happens after the work. The other F# idiom, raising an exception from the folder to break out, also stopped after 3 elements here, and it puts control flow into exception handling. Rust's `try_fold` gets the same result without an intermediate stream; C++ and Effect 4 both end up with a mutable accumulator outside the fold.

**Chew on this**

**Gotchas**

- `Seq.scan` yields the seed first, so `Seq.scan (+) 0` over an empty input is `[0]`, and `Seq.last` on it is `0`, not an exception.
- `takeWhile` on the totals returns the last total that passed (200); `tryFind` returns the first that failed (300). Pick by which number the caller needs.
- The `Seq.fold` guard version returned 300, not 200: the guard stops adding after the total crosses, but the crossing element was already added.

## TypeScript: Effect 4 removed Stream.runFoldWhile and made fold seeds thunks, so a v3-style seed fails only when the stream runs

*New discoveries and currently popular patterns*

**Did you know**

Effect 3's `Stream.runFoldWhile(stream, 0, (total) => total <= 250, add)` stopped pulling after 3 elements and returned 300. Effect 4.0.6 has no `runFoldWhile`; the migration guide lists its replacement as "none" and says to "emulate with Stream.runForEachWhile and a mutable accumulator". The functional route that still works is `Stream.scan` plus `Stream.takeWhile`, which returned 200 after 3 pulls. The other change is in the signatures: v4's `runFold` and `scan` take the seed as a thunk, `() => 0`. tsc 7.0.2 rejects a plain `0` (TS2345, "not assignable to parameter of type 'LazyArg<number>'"), but from plain JavaScript the stream builds fine and fails only when run: `TypeError: initial is not a function`.

**Show me**

```javascript
// JavaScript (the TS types aside), effect 4.0.6 and 3.22.4, Node 22.23.4.
import { Effect, Option, Stream } from "effect"

const request_sizes = [100, 100, 100, 7, 8, 9]
let pulls = 0
const counted = Stream.fromIterable(request_sizes).pipe(Stream.tap(() => Effect.sync(() => { pulls += 1 })))

// effect 3.22.4: Stream.runFoldWhile(counted, 0, (total) => total <= 250, add) -> 300, pulls 3
// effect 4.0.6: runFoldWhile is gone ("Replacement: none" in the migration guide).

// Running totals, cut at the budget. In v4 the seed is a thunk:
const within_budget = Stream.runLast(counted.pipe(
    Stream.scan(() => 0, (total, size) => total + size),
    Stream.takeWhile((total) => total <= 250)))
console.log(Option.getOrNull(Effect.runSync(within_budget)), "pulls", pulls) // 200 pulls 3

// A v3-style plain seed: TS2345 under tsc; from plain JS it fails only when the stream runs.
const plain_seed = counted.pipe(Stream.scan(0, (total, size) => total + size)) // builds fine: the stream is lazy
try { Effect.runSync(Stream.runLast(plain_seed)) }
catch (thrown) { console.log(String(thrown)) } // TypeError: initial is not a function
```

**Why it matters**

The thunk seed is there for a reason the guide spells out: it "is evaluated for each stream run", so mutable initial state is not shared between runs, which is exactly the bug the C++ tip measured. The cost is the migration: plain-JS call sites, `any`-typed wrappers and tests that build streams without running them all pass until the first real run. The guide's own `runForEachWhile` emulation (measured: 300 after 3 pulls, and 300 again on a rerun, because the accumulator is created inside `Effect.suspend`) is correct, and it is the one place in this part where a library's recommended replacement is a mutable variable. Plain arrays have the same gap: `reduce` read all 6 elements, and `some` with an outer running total stopped after 3.

**Chew on this**

In your Effect code, which stream folds or scans are built in one module and run in another, so that a seed-signature change would surface far from the line that has to change?

**Sources**

- https://github.com/Effect-TS/effect/blob/main/migration/v3-to-v4.md (`Stream.runFoldWhile`: "Replacement: none"; `Stream.scan`: "Wrap the initial state in a thunk")
- https://effect.website/docs/stream/consuming-streams/
- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/Array/some

**Gotchas**

- Passing a v4-style thunk to v3's `runFold` does not fail: it folds onto the function, and the string concatenation produced `"() => 0100100100789"`.
- `Iterator.prototype.reduce` (ES2025) has no early exit either: it read all 6 elements of a generator.
- `runFoldWhile` in v3 returned 300 (it adds the crossing element, then stops), while `scan` + `takeWhile` returns 200 (the last total that passed). The two are not drop-in replacements for each other.

# The functional angle: the stop needs the accumulator, and only two of the four can give it one without a mutable variable

_Draws on all four tips. The shape: a fold whose exit depends on its own running total. The question per language is where the total lives when the stop is tested._

| Language | Form | Where the running total lives | Mutable state needed? | Second run |
| --- | --- | --- | --- | --- |
| F# | `Seq.scan (+) 0 \|> Seq.takeWhile ...` | in the stream itself, as elements | no | starts from the seed again |
| Rust | `try_fold(0u8, \|sum, size\| sum.checked_add(*size))` | in the fold's accumulator | no | starts from the seed again |
| C++ | `views::take_while` with a captured `running_total` | in a variable outside the view | yes, and it must be reset by hand | kept 0 without a reset |
| TypeScript (Effect 4) | `Stream.runForEachWhile` with a `let` accumulator (the guide's emulation) | in a `let` inside `Effect.suspend` | yes, scoped per run | 300 again, because `suspend` re-creates it |

F# is the baseline because `scan` is the textbook functional answer and costs nothing extra on a lazy `seq`, so its row shows the shape at its cleanest: the accumulator is data. Rust reaches the same place by letting the fold itself return early. The other two rows are the asymmetry the FP lens warns about: the functional form needed a mutable variable in C++ and in Effect 4, and the only difference between the safe and the broken version is where that variable is created.

Left open: when a library removes a functional combinator and documents a mutable replacement, do you adopt the replacement, or write the combinator yourself on top of `scan`?

# The security angle: a quota check that sums Options passes 300 bytes as under 250 in a release build

_Draws on the Rust tip, Mode C: the missing check. `sum::<Option<u8>>()` short-circuits on `None`, which makes it look like a safe "sum if all present". The check it does not make is overflow, and the release build wraps._

```rust
// Rust, rustc 1.99.1
fn is_within_quota(chunk_sizes: &[u8]) -> bool {
    let total: Option<u8> = chunk_sizes.iter().map(|size| Some(*size)).sum();
    total.is_some_and(|sum| sum <= 250)
}
fn is_within_quota_checked(chunk_sizes: &[u8]) -> bool {
    chunk_sizes.iter().try_fold(0u8, |sum, size| sum.checked_add(*size)).is_some_and(|sum| sum <= 250)
}
// [100, 100, 100]: release: is_within_quota = true (300 wrapped to 44), is_within_quota_checked = false
//                  debug:   is_within_quota panics "attempt to add with overflow"
```

The same function is a denial of service in debug and an authorization bypass in release: CWE-190 (Integer Overflow or Wraparound) feeding CWE-863 (Incorrect Authorization). The `u8` makes it easy to show; the same wrap happens to a `u32` byte count at 4 GiB.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `sum::<Option<u8>>` wraps in release and passes the quota check | panics in debug, wraps in release by default | `try_fold` with `checked_add`, or `overflow-checks = true` in the release profile |
| C++ | `fold_left` over `uint8_t` with `std::plus<>` | unsigned wrap is defined; signed overflow is undefined | accumulate in a wider type, or check before adding |
| F# | `byte` arithmetic wraps by default: `100uy + 100uy + 100uy` and `List.fold (+) 0uy` gave 44 | but `List.sum` and `Seq.sum` over the same bytes threw `OverflowException` | do not rely on which one you got: `open Checked`, or sum into a wider type |
| TypeScript | `reduce` over numbers | no wrap below 2^53, so this shape is safe; above it, precision loss | `BigInt` or a range check for byte counts near 2^53 |

Left open: which of your quota, limit or budget checks sum into a type whose maximum a client can reach, and does the release build check overflow?

# FAQ

**Does Rust have a `fold_while`?**
Not in std. `try_fold` with `ControlFlow` is the std form (`ControlFlow::Break(300)` above); the `itertools` crate has a `fold_while` with its own `FoldWhile` type (from its documentation; not compiled here).

**Is a stateful `take_while` predicate undefined behaviour in C++?**
It violates a semantic requirement of the concept (`regular_invocable`: equality-preserving), which the standard does not diagnose. What was measured is the observable effect: the second fold over the same view returned 0.

**Does F#'s `Seq.scan` read one element too many?**
No. With the budget crossed on the third element, `takeWhile` stopped after reading 3 elements, the same as Rust's `try_fold` and C++'s `take_while`; the third element has to be read to know the budget was crossed.

**Did Effect 4 remove `runFold` too?**
No, only the `While` and scoped variants. `Stream.runFold(stream, () => 0, add)` still exists, read all 6 elements and returned 324; its seed is now a thunk.
