# Daily Tips: 2026-09-01

## Rust: algebraic_add is -ffast-math scoped to one call, not one build

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.98.0 (2026-08-20) stabilized `algebraic_add`, `algebraic_sub`,
`algebraic_mul`, `algebraic_div`, and `algebraic_rem` on `f16`, `f32`, `f64`,
and `f128`. Ordinarily rustc will not reassociate a float expression at all: it
only rewrites float math when the result is bitwise identical, because IEEE
addition is not associative. These methods waive that guarantee at the call
site. The docs decline to enumerate what the compiler may do, saying only that
it is "similar to the kind of optimization you would see with the `-ffast-math`
option in other languages" -- so `a + b + c + d` may be evaluated as
`(a + b) + (c + d)`. Results are non-deterministic. They are never undefined
behavior.

**Show me**

```rust
// Requires Rust 1.98.0 (stable 2026-08-20). Earlier toolchains reject this
// as unstable feature `float_algebraic` (tracking issue #136469).

/// Strict IEEE: rustc must emit a serial dependency chain, one add per
/// element, because reassociating would change the result bits.
fn sum_strict(xs: &[f64]) -> f64 {
    xs.iter().fold(0.0, |acc, &x| acc + x)
}

/// Same arithmetic, reassociation permitted. The adds may be split into
/// independent partial sums and folded at the end -- the shape a hand-written
/// SIMD horizontal sum has, without the unsafe intrinsics.
fn sum_algebraic(xs: &[f64]) -> f64 {
    xs.iter().fold(0.0, |acc, &x| acc.algebraic_add(x))
}

// Note what did NOT change: NaN and infinity still behave. Unlike C's
// -ffast-math, nothing here implies -ffinite-math-only, so `x.is_nan()`
// elsewhere in the crate cannot be folded to `false` as a side effect.
```

**Why it matters**

On a long-running aggregation loop the strict version is latency-bound on the
FP add chain (roughly 3-4 cycles per element on current x86-64 and AArch64);
the algebraic version lets the vectorizer break the chain into independent
accumulators. The real win is blast radius. C and C++ expose this as
`-ffast-math`, a translation-unit flag that also enables
`-ffinite-math-only`, which is what makes `std::isnan` quietly fold to false
and leaks across inlining and LTO into code that never asked for it. Rust made
the same optimization opt-in per operation, and nothing outside the call is
weakened. JS and TypeScript have no such lever at all: V8 never reassociates
float arithmetic, so on the server side you simply eat the dependency chain.

**Chew on this**

Where in your hot loops is left-to-right evaluation order actually load-bearing
(a Kahan or Neumaier compensated sum depends on it entirely) versus merely
incidental? And if you swapped in `algebraic_add`, would your existing tests
notice -- do they assert a tolerance, or do they assert bit equality on a
golden value?

**Sources**

- https://blog.rust-lang.org/2026/08/20/Rust-1.98.0/
- https://doc.rust-lang.org/std/primitive.f64.html#method.algebraic_add
- https://github.com/rust-lang/rust/issues/136469

**Verified**

Claim rests on the 1.98.0 release announcement and std docs. The snippet was
not compiled: this machine has rustc 1.95.0, which rejects `algebraic_add` with
`E0658 use of unstable library feature 'float_algebraic'` -- consistent with,
but not proof of, stabilization in 1.98.

## C++: [[no_unique_address]] eats your member's tail padding, but only when the member is not trivially copyable

*Perf and memory model*

**Did you know**

C++20, P0840R2. GCC 9 onward, Clang 9 onward. MSVC ignores the standard
spelling entirely even in C++20 mode and provides `[[msvc::no_unique_address]]`
instead, from 19.28 (VS 2019 16.9). Everyone reaches for it to collapse an
empty stateless member -- an allocator, a comparator -- to zero bytes. The
other half of cppreference's wording is the interesting one: "If the member is
not empty, any tail padding in it may be also reused to store other data
members." On the Itanium ABI that reuse fires only when the member type is
*not* trivially copyable, because the ABI has to keep
`memcpy(dst, src, sizeof(T))` safe for the types where you are allowed to do
it.

**Show me**

```cpp
// C++20. Compiled and run with Apple Clang 21 (arm64, Itanium-family ABI).
struct PodPad { int a; char b; };              // sizeof 8, 3 tail padding bytes
struct NonPod { int a; char b; ~NonPod() {} }; // same layout, NOT trivially copyable

struct HostPod { [[no_unique_address]] PodPad p; char c; };
struct HostNp  { [[no_unique_address]] NonPod p; char c; };

// Measured, both members annotated identically:
//   sizeof(HostPod) == 12   attribute had NO effect
//   sizeof(HostNp)  ==  8   c placed at offset 5, inside p's tail padding
//
// Only the destructor differs. Declaring it makes NonPod non-trivially-copyable,
// which is exactly the permission the ABI was waiting for.
// (The empty-member case works on both: an empty member drops 8 -> 4.)
```

**Why it matters**

That is 33 percent off a struct you may be holding a few million of, bought
with an attribute and no code change. The trap is that `c` now lives *inside*
`p`, so `std::memset(&h.p, 0, sizeof(NonPod))` or a hand-rolled bulk copy of
the subobject silently overwrites the neighbor. What makes this survivable is
that the ABI only overlaps types you were never permitted to `memcpy` in the
first place, so the corruption only appears in code that was already undefined.
Rust's default `repr(Rust)` reorders fields and packs niches without being
asked, but never overlaps two live fields' storage; C++ makes you ask, then
declines when it cannot prove safety; and neither one tells you which of the
two it decided to do.

**Chew on this**

In your hottest aggregate, how many members carry tail padding, and how many of
those are non-trivially-copyable -- that is, how much free space is already
sitting there? And if a member's tail padding is now occupied by a sibling,
what is your `static_assert(std::is_trivially_copyable_v<...>)` actually
protecting, given it passes on precisely the types where the optimization does
nothing?

**Sources**

- https://en.cppreference.com/w/cpp/language/attributes/no_unique_address
- https://en.cppreference.com/w/cpp/compiler_support/20
- https://wg21.link/p0840

**Verified**

Compiled and run with Apple Clang 21.0.0 (arm64-apple-darwin25). Note that
`/usr/bin/g++` on macOS is Apple Clang, so the identical numbers from both
commands are one implementation, not two. Real GCC was not available here; the
GCC 9 support figure and the MSVC behavior come from cppreference, not from a
local build.

## TypeScript: strictFunctionTypes does not apply to methods, and that is deliberate

*Type system deep cuts*

**Did you know**

`strictFunctionTypes` makes function parameters contravariant. It exempts
anything written with method syntax. `{ handle(a: Animal): void }` and
`{ handle: (a: Animal) => void }` are indistinguishable at runtime and are
checked by different rules: the first is bivariant, so a handler that narrows
its parameter is accepted; the second is not. This is a documented, intentional
soundness hole. The handbook's reason: "Methods are excluded specifically to
ensure generic classes and interfaces (such as `Array<T>`) continue to mostly
relate covariantly."

**Show me**

```ts
// Verified with tsc 6.0.3 under --strict.
interface Animal { name: string }
interface Dog extends Animal { bark(): void }

interface MethodSink { handle(a: Animal): void }    // method syntax  -> bivariant
interface PropSink   { handle: (a: Animal) => void } // property syntax -> checked

const dogOnly = (d: Dog) => d.bark()

const m: MethodSink = { handle: dogOnly }  // accepted, no diagnostic
const p: PropSink   = { handle: dogOnly }  // TS2322: Property 'bark' is missing
                                           //   in type 'Animal' but required in 'Dog'

m.handle({ name: "cat" })   // type-checks. Throws at runtime: bark is not a function.
```

**Why it matters**

Handler registries, plugin interfaces, and event maps are almost always written
with method shorthand, because that is the shorthand. Every one of them accepts
a callback that narrows its argument, and nothing at the call site enforces the
narrowing. Changing one line -- shorthand to an explicit function-typed
property -- turns on the check you assumed `strict` already gave you. The same
mistake in the sibling languages is not available to make: Rust has no
subtyping on function arguments beyond lifetimes, so it is a compile error you
cannot opt out of, and in C++ an override that narrows a parameter type is not
an override at all but a hiding overload, which `override` diagnoses. C# is the
closer cousin -- delegate parameter types are invariant, so the assignment is
simply rejected. TypeScript is the only one here that knows the rule and
suspends it for ergonomics.

**Chew on this**

How many interfaces in your codebase use method shorthand for what is really a
callback slot rather than a method someone will call on an instance? And of
those, which ones already have an implementation that narrows the parameter --
and how would you find out, given the compiler will not tell you?

**Sources**

- https://www.typescriptlang.org/tsconfig/#strictFunctionTypes
- https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-6.html
