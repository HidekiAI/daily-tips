## Rust: Since 1.92, load_setting()?; with nothing naming T is an error, and in edition 2024 T falls back to ! instead of ()

*Type system deep cuts*

**Did you know**

When nothing constrains a type variable except a diverging expression, such as the `return` hidden inside `?`, rustc picks a fallback type. Up to edition 2021 that fallback is `()`. In edition 2024 it is `!`. So `load_setting()?;`, where `fn load_setting<T: Default>()`, used to compile with `T = ()`. In edition 2024 it asks for `!: Default`, which does not exist. Since Rust 1.92 (2025-12-11) the lint `dependency_on_unit_never_type_fallback` is deny-by-default, so the same line is now an error in edition 2021 as well.

**Show me**

```rust
// Rust: never-type fallback, measured on rustc 1.95.0 and 1.99.0
fn load_setting<T: Default>() -> Result<T, String> {
    Ok(T::default())
}

fn warm_cache() -> Result<(), String> {
    // Nothing names T here: the value is thrown away. The only other type
    // in play is the `return` hidden inside `?`, which has type `!`.
    // Edition 2021 used to pick T = () and compile.
    //   1.92+, edition 2021: error, `dependency_on_unit_never_type_fallback`
    //   edition 2024:        error[E0277]: `!: Default` is not satisfied
    // load_setting()?;

    // Say the type, and both editions agree:
    load_setting::<()>()?;
    let _: u32 = load_setting()?;
    Ok(())
}

fn main() {
    println!("{:?}", warm_cache());
}
```

**Why it matters**

The lines this breaks are the ones whose result nobody reads: warm-ups, "does it parse" checks, a fire-and-forget fetch. In edition 2021 those quietly ran the generic function at `T = ()`, which is a type nobody chose. C++ refuses to guess at all (`couldn't deduce template parameter`). TypeScript guesses `unknown` (measured: `loadSetting()` infers `unknown`, TS2322 at first use). F# guesses `obj` without a word (measured: `System.Object` under `dotnet fsi`). Rust is the only one of the four that changed its guess between editions.

**Chew on this**

Which of your discarded `?` calls were running at `T = ()` without anyone choosing it? When you name the type to fix the error, is `()` the type you actually meant?

**Sources**

- https://doc.rust-lang.org/edition-guide/rust-2024/never-type-fallback.html
- https://blog.rust-lang.org/2025/12/11/Rust-1.92.0/
- https://github.com/rust-lang/rust/issues/148922

**Gotchas**

- `let _ = load_setting()?;` does not name the type. It fails exactly like the bare call in both editions (measured). `let _: u32 = ...` does name it.
- `#[allow(dependency_on_unit_never_type_fallback)]` in edition 2021 brings back `T = ()` and prints `Ok(())` (measured). The same `allow` in edition 2024 does nothing, because there the error is E0277, not a lint.
- The deny lint fires only when the crate itself is built. A dependency on edition 2021 that trips it still compiles, and Cargo reports a warning (1.92 release notes).
- `unsafe { std::mem::zeroed() }` with an inferred type has its own deny-by-default sibling, `never_type_fallback_flowing_into_unsafe`, also since 1.92.

## C++: C++26 optional<T&> rebinds on assignment where T& writes through, and value_or still hands you a copy

*New discoveries and currently popular patterns*

**Did you know**

`std::optional<T&>` (P2988R12, voted into C++26 in June 2025) is now in libstdc++ with GCC 16 (16.1 released 2026-04-30, still marked experimental under `-std=c++26`) and in libc++ 22, which Apple clang 21 ships. Before C++26 it was ill-formed (GCC 16 with `-std=c++23` fails with "may not have reference type"). Its assignment **rebinds**: `target = backup` points it at `backup` and leaves the old referent alone, the opposite of a plain `T&`. Its `value_or` returns `T` by value, so asking for "the referenced object or a fallback" copies whichever it picks. Constructing one from a temporary is deleted, so the `const T&` lifetime-extension trick does not compile. Feature test: `__cpp_lib_optional >= 202506L`. MSVC STL status: not checked.

**Show me**

```cpp
// C++26 std::optional<T&>: GCC 16.2 (libstdc++) and Apple clang 21 (libc++ 22)
#include <cassert>
#include <optional>
#include <string>

struct Config {
    std::string region = "us-east";
    static inline int copies = 0;
    Config() = default;
    Config(const Config& other) : region(other.region) { ++copies; }
};

int main() {
    int primary = 1, backup = 2;

    int& plain = primary;
    plain = backup;                 // a T& assigns THROUGH: primary is now 2
    assert(primary == 2);

    primary = 1;
    std::optional<int&> target = primary;
    target = backup;                // optional<T&> REBINDS: primary untouched
    assert(primary == 1 && &*target == &backup);
    *target = 20;                   // writing through it needs the *
    assert(backup == 20);

    Config live, fallback;
    std::optional<Config&> found = live;
    auto&& chosen = found.value_or(fallback);  // returns Config, not Config&
    assert(&chosen != &live && Config::copies == 1);

    // Binding to a temporary is deleted, unlike const T& lifetime extension:
    // std::optional<const std::string&> name = std::string("bob"); // error

    static_assert(sizeof(std::optional<int&>) == sizeof(int*));
}
```

**Why it matters**

This is the type a lookup returns: "the cached `Config` if there is one", without a pointer and without a copy. That promise holds until `value_or`, which is the one-liner everyone reaches for and which copies the whole object. Rust's `Option<&T>` is the same shape and also rebinds, but `unwrap_or(&fallback)` gives back a `&T` (measured, `std::ptr::eq` holds). The 8-byte, trivially copyable layout matches Rust's niche-optimized `Option<&T>` (measured on both compilers).

**Chew on this**

Where you return `T*` today to mean "maybe a reference", would `optional<T&>` make a caller's `= other` do something different from what the code beside it expects? Which of your lookups would switch to `value_or` and start copying without anyone seeing it in review?

**Sources**

- https://wg21.link/p2988r12
- https://en.cppreference.com/w/cpp/utility/optional
- https://gcc.gnu.org/gcc-16/changes.html
- https://libcxx.llvm.org/ReleaseNotes/22.html

**Verified**

GCC 16.2.0 in `docker run gcc:16` (Debian 13), and Apple clang 21 with libc++ 22.1 (`_LIBCPP_VERSION 220106`) on macOS. Both agree on every line. Rerun on GCC 16.2 with `-std=c++26 -Wall -Wextra`: every assert passes, no warnings. GCC 14.2, Debian 13's own `g++`, rejects the snippet under `-std=c++26` ("may not have reference type"), as expected before GCC 16. MSVC was not tested.

**Gotchas**

- `operator==` compares the referenced values, not the addresses: two `optional<int&>` bound to two different ints that both hold 5 compare equal (measured).
- `return local;` into an `optional<const T&>` does not compile, because the implicit move makes `local` an rvalue and the temporary constructor is deleted (measured, both compilers). Wrapping it first, `std::optional<const T&> found = local; return found;`, compiles with no warning and dangles.
- An `optional<Session&>` into a `std::vector` dangles after the vector reallocates, with no warning at `-Wall -Wextra` on either compiler. ASan reports `heap-use-after-free` (measured).
- `*target = 20` writes through. `target = 20` does not compile on either compiler (measured: "no viable overloaded '='").
- Both libraries make it trivially copyable (measured), but the P2988R12 wording does not require that. P3836 ("Make optional<T&> trivially copyable") proposes to require it, so do not rely on it for `memcpy` across implementations yet.

## F#: [<Struct>] on a record makes generic = allocate 64 bytes a compare, and the reference record it replaced allocated none

*Perf and memory model*

**Did you know**

Inside a generic function that is not `inline`, `=` on a `'T` goes through FSharp.Core's generic equality. For a `[<Struct>]` record that path boxes, and a 16-byte struct record costs 64 bytes per comparison. The same record without `[<Struct>]` costs 0 bytes, because it is already on the heap. `Array.distinct` over the struct costs 112 bytes per element against 8 for the class. Measured identically on FSharp.Core 8.0 / .NET 8.0.8 and FSharp.Core 10.1 / .NET 10.0.13, with and without `--optimize`. The 2024 compiler fix removed the box only at call sites where the type is known.

**Show me**

```fsharp
// F#: generic = on a [<Struct>] record, FSharp.Core 8.0 / .NET 8 and FSharp.Core 10.1 / .NET 10
open System

[<Struct>]
type Money = { cents: int64; currency: int }     // 16 bytes, "no allocation"
type MoneyRef = { cents: int64; currency: int }  // the class it replaced

// Not inline, so 'T is only known at runtime: = goes through FSharp.Core's
// generic equality, which boxes a struct on every call.
let count_matches (target: 'T) (items: 'T[]) =
    items |> Array.sumBy (fun item -> if item = target then 1 else 0)

let bytes_per_item (work: unit -> int) =
    work () |> ignore                             // warm up the JIT
    let before = GC.GetAllocatedBytesForCurrentThread()
    work () |> ignore
    float (GC.GetAllocatedBytesForCurrentThread() - before) / 1_000_000.0

let structs = Array.init 1_000_000 (fun index -> ({ cents = int64 (index % 10); currency = 840 } : Money))
let classes = Array.init 1_000_000 (fun index -> ({ cents = int64 (index % 10); currency = 840 } : MoneyRef))

printfn "struct, generic:  %.0f B" (bytes_per_item (fun () -> count_matches structs.[3] structs))  // 64
printfn "class, generic:   %.0f B" (bytes_per_item (fun () -> count_matches classes.[3] classes))  // 0
printfn "struct, concrete: %.0f B" (bytes_per_item (fun () ->
    structs |> Array.sumBy (fun item -> if item = structs.[3] then 1 else 0)))                 // 0
printfn "Array.distinct:   %.0f B" (bytes_per_item (fun () -> (Array.distinct structs).Length))  // 112
```

**Why it matters**

`[<Struct>]` is the annotation people add to remove allocation, and in generic code it moves the allocation from construction to every comparison. A dedupe, a `List.contains` (72 bytes per call over a ten-item list, measured) or a generic cache keyed by the record now produces garbage per element. Rust and C++ monomorphize generics, so the same comparison inside a generic function compiles to a direct call with no box. TypeScript has no value types to box. The cost is specific to the .NET generic path F# routes `=` through.

**Chew on this**

Which of your `[<Struct>]` types were made structs to save allocations, and then handed to a generic helper? Would you have measured the allocation before the change and after it, or only before?

**Sources**

- https://devblogs.microsoft.com/dotnet/fsharp-developer-stories-how-weve-finally-fixed-a-9yearold-performance-issue/
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/structs
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/records

**Verified**

All numbers are measured with `GC.GetAllocatedBytesForCurrentThread` under `dotnet fsi` (SDK 8.0.401, and `mcr.microsoft.com/dotnet/sdk:10.0`). Which FSharp.Core function does the boxing is inferred from the 2024 post, not read from source.

**Gotchas**

- Marking the helper `inline` brings the struct back to 0 bytes (measured), because `'T` becomes concrete at each call site. That copies the helper's body into every caller.
- `int`, `DateTime` and struct tuples in the same generic helper allocate 0 bytes (measured). FSharp.Core fast-paths them. The F# struct record and the struct union do not (struct union: 48 bytes, measured).
- `Dictionary<Money, _>` with either the default comparer or `HashIdentity.Structural` allocates 0 bytes per lookup (measured). The boxing is in `=`, not in hashing.
- The 2024 fix is real: `item = structs.[3]` at the concrete type is 0 bytes (measured). The fix just does not reach code that is generic over `'T`.

## TypeScript: Set.prototype.intersection walks whichever set is smaller, so the result's order and the methods it calls depend on sizes

*Stdlib and ecosystem gems*

**Did you know**

The ES2025 Set methods (`union`, `intersection`, `difference`, `symmetricDifference`, `isSubsetOf`, `isSupersetOf`, `isDisjointFrom`) are in Node 22 and typed in TypeScript under `lib: es2025`. `intersection` iterates whichever side is smaller: it calls `has` on the argument for each of the receiver's elements, or it walks the argument's `keys()` and asks the receiver. So the result follows the smaller set's order, and the same receiver gives `['a', 'b']` or `['b', 'a']` depending only on the argument's size. The argument does not have to be a `Set`. It has to be a "set-like" with `size`, `has` and `keys`, so a `Map` works and an array does not.

**Show me**

```ts
// TypeScript 6.0.3 types (lib es2025), run on Node 22.17.1
const receiver = new Set(["b", "a", "q"])

// The spec iterates whichever side is SMALLER, so the result takes that side's order.
const fewer = new Set(["a", "b"])            // size 2 < 3: walks fewer.keys()
const more = new Set(["a", "b", "x", "y"])   // size 4 >= 3: walks receiver
console.log([...receiver.intersection(fewer)]) // [ 'a', 'b' ]
console.log([...receiver.intersection(more)])  // [ 'b', 'a' ]

// The argument is a "set-like": size, has and keys. An array is not one.
// receiver.union(["x"])                     // tsc: TS2345, missing has, size
// at runtime with a cast: TypeError: The .size property is NaN
const via_map = receiver.union(new Map([["k", 1]]))  // a Map is set-like
console.log([...via_map])                     // [ 'b', 'a', 'q', 'k' ]

// Which of has() or keys() it calls depends on size, never on your intent.
const calls: string[] = []
const fn_spy_like = (size: number) => ({
    size,
    has: (key: string) => { calls.push(`has(${key})`); return true },
    keys: () => { calls.push("keys()"); return ["a"][Symbol.iterator]() },
})
receiver.intersection(fn_spy_like(1))
receiver.intersection(fn_spy_like(10))
console.log(calls.join(" "))                 // keys() has(b) has(a) has(q)
```

**Why it matters**

These methods replace the `[...a].filter(item => b.has(item))` everyone writes, and that one-liner always kept `a`'s order. A snapshot test, a paginated response or a "first match wins" built on the new method changes its output when the other set grows past the receiver. Rust's `HashSet::intersection` makes the same size-based choice (measured below), while F#'s `Set.intersect` and C++'s `std::set_intersection` return sorted output, so order there is not in question.

**Chew on this**

Which of your hand-written intersections would you replace with the built-in, and does anything downstream read the order? If you pass your own set-like, are its `has` and its `keys` guaranteed to agree?

**Gotchas**

- With `lib: es2024` the methods do not exist at all: TS2550, "Try changing the 'lib' compiler option to 'es2025' or later" (measured on tsc 6.0.3).
- `isSubsetOf` returns `false` without calling anything when the receiver is larger than the argument (measured: no `has` or `keys` call). Only `size` is read.

# The functional angle: intersection is a filter over one side, and Rust and TypeScript choose the side by size

Draws on the TypeScript tip (`Set.prototype.intersection`), with Rust, F# and C++ as peer rows.

The shape is `filter (fun item -> other.contains item) one_side`. The open question is which side gets filtered, and therefore whose elements come back. With plain values that is invisible. With a type whose equality looks only at a key, the side shows up in the data:

```rust
// Rust: HashSet::intersection, Tagged compares by `key` only (rustc 1.95.0)
// receiver has 3 elements tagged "receiver"; the argument's are tagged "argument"
receiver.intersection(&tiny_1) // element for "a" comes from: argument
receiver.intersection(&big_5)  // element for "a" comes from: receiver
```

```fsharp
// F#: Set.intersect with the same key-only comparison (FSharp.Core 8.0 and 10.1)
Set.intersect small large  // element comes from: small
Set.intersect large small  // element comes from: large
```

| Language | Functional form | Whose elements come back | What it costs |
| --- | --- | --- | --- |
| F# | `Set.intersect first second` | always the first argument's, measured | nothing to learn; sorted output, so order is fixed too |
| C++ | `std::ranges::set_intersection(first, second, out, by_key)` | always the first range's, documented and measured | both inputs must already be sorted by the same comparator |
| Rust | `a.intersection(&b)` on `HashSet` | the smaller set's, measured | an argument that grows flips the provenance; iteration order is random anyway |
| TypeScript | `a.intersection(b)` | the smaller set's order; values are SameValueZero, so provenance is invisible for a real `Set` | a custom set-like's `has` and `keys` both have to be right, because either may be the one used |

No row needs `mut`. The asymmetry is that the two hash-based libraries made the optimization part of the semantics, and the two sorted ones did not need to.

If your equality compares only a key, which side's payload did your code assume it was getting back?

# The security angle: a set-like whose has and keys disagree makes your allow-list check depend on the list's length

Draws on the TypeScript tip (Mode B: the size-based choice is fine for correctness, but is it secure?) and on the C++ tip (Mode C: the dangling the temporary-guard does not catch). In the TypeScript case the language prevents nothing. In the C++ case the library prevents the temporary, and nothing prevents the rest.

**Size picks the code path (CWE-697, incorrect comparison; CWE-863 when it gates access).** A set-like with a case-insensitive `has` and exact-case `keys` looks harmless. Measured on Node 22.17.1:

```ts
// TypeScript: looks like "case-insensitive membership". Is two different predicates.
const members = new Set(["Alice", "Bob", "Carol"])
const fn_case_insensitive = (names: string[]) => ({
    size: names.length,
    has: (name: string) => names.includes(name.toLowerCase()),
    keys: () => names[Symbol.iterator](),
})
members.intersection(fn_case_insensitive(["alice", "dave", "erin"])) // { 'Alice' }: walks members, uses has()
members.intersection(fn_case_insensitive(["alice", "dave"]))         // {}: walks keys(), asks members.has("alice")
members.isDisjointFrom(fn_case_insensitive(["alice"]))               // true: "nobody on the deny list"
members.isDisjointFrom(fn_case_insensitive(["alice", "p", "q", "r"])) // false
```

A deny-list check written as `isDisjointFrom` passes while the deny list is short and starts failing when someone adds unrelated entries. No test with one fixed list size sees it.

**Dangling through a rebindable reference (CWE-416, use after free).** `std::optional<T&>` refuses a temporary, so it looks lifetime-safe. It is not. A reference to `sessions[0]` held across `sessions.emplace_back()` reads freed memory, and neither GCC 16.2 nor clang 21 warns at `-Wall -Wextra`. ASan reports `heap-use-after-free` on both (measured).

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | the set method uses `has` or `keys` depending on size | nothing; the set-like protocol trusts both | make `keys()` yield exactly what `has()` accepts, or normalize before building a real `Set` |
| Rust | `HashSet::intersection` provenance flips by size | nothing for provenance; `Eq` and `Hash` must agree, which is a documented contract | do not let `Eq` ignore fields a caller will read |
| C++ | `optional<T&>` outlives its referent | deletes construction from a temporary only | the same rules as a raw `T&`: no reference across a reallocation |
| F# | none of the above for `Set.intersect` | sorted, first-argument provenance | nothing for this one |

Rust is the control row for the memory half: holding `&sessions[0]` across a `push` is a borrow error there. Nobody is a control row for the set-like half, since it is a protocol, not a type.

Which of your allow or deny checks takes its list from configuration whose size you do not control?
