**The thesis of this part: treat `None` as an empty collection and `Some` as a collection of one, and a nested select over optional lookups stops at the first missing one for free, but the same view drops errors without a word.** It is the SQL intuition: a lookup that finds nothing is an empty row set, and joining against an empty row set yields nothing, without a special case. Rust and C++26 make the option itself iterable, F# makes you convert it, and JavaScript's `flatMap` uses an array of zero or one as the option. All four stopped after the first lookup when it came back empty. The cost is on the other side: the moment a `Result` is viewed as zero or one items, an error becomes an empty row, and an empty row looks the same as nothing to do.

## Rust: rustc warns when you loop over an Option, and says nothing when .flatten() over Results throws every error away

*Idioms and antipatterns*

**Did you know**

`Option` and `Result` implement `IntoIterator` with zero or one items, which is what makes `extend(maybe_port)` and `flat_map` over lookups work. rustc has a warn-by-default lint for the most visible use, `for_loops_over_fallibles`: "for loop over an `Option`. This is more readably written as an `if let` statement". The same zero-or-one view applied to a batch of `Result`s, `replies.iter().flatten()`, drops every `Err` and keeps the `Ok` values, and neither rustc nor clippy at `-W clippy::pedantic -W clippy::nursery` says anything.

**Show me**

```rust
// rustc 1.99.1, edition 2021; clippy 0.1.99.
fn main() {
    let maybe_port: Option<u16> = Some(8080);
    // Option and Result implement IntoIterator, and rustc comments on it:
    for port in maybe_port { println!("{port}"); } // warning: for loop over an `Option` (for_loops_over_fallibles)

    // ...but says nothing when the same "0 or 1 items" view throws an error away.
    let replies: Vec<Result<u16, String>> = vec![Ok(80), Err("shard 2: bad port".to_string()), Ok(443)];
    let ports: Vec<u16> = replies.iter().flatten().copied().collect();
    println!("{ports:?}"); // [80, 443]: no rustc warning, nothing from clippy pedantic or nursery

    // Keeping both halves: partition by is_ok, then take the errors out of the failed side.
    let (succeeded, failed): (Vec<_>, Vec<_>) = replies.into_iter().partition(Result::is_ok);
    let failures: Vec<String> = failed.into_iter().filter_map(Result::err).collect();
    println!("{} ok, failures: {failures:?}", succeeded.len()); // 2 ok, failures: ["shard 2: bad port"]

    // The 0-or-1 view is exact: size_hint is (1, Some(1)) or (0, Some(0)), so extend reserves exactly.
    let mut listen_ports: Vec<u16> = vec![22]; // extend appends in place, so this Vec has to be mut
    listen_ports.extend(maybe_port);
    println!("{listen_ports:?}"); // [22, 8080]
}
```

**Why it matters**

The lint and the silence point the wrong way round. A `for` over an `Option` is merely unidiomatic; `.flatten()` over a fan-out's replies is a decision to treat failure as "no data", and it compiles to the same three characters whether you meant it or not. `filter_map(Result::ok)` says it more loudly, and `partition` keeps both halves. C++26 has no `Result` range to flatten (`std::expected` is not a range), F# makes the drop explicit with `Result.toOption`, and TypeScript's `flatMap` drops whatever the callback maps to `[]`.

**Chew on this**

In your fan-out code, which `.flatten()` or `filter_map(Result::ok)` was written because an error really means "skip this one", and which was written because the types lined up?

**Sources**

- https://doc.rust-lang.org/std/option/enum.Option.html#impl-IntoIterator-for-Option%3CT%3E
- https://doc.rust-lang.org/std/result/enum.Result.html#impl-IntoIterator-for-Result%3CT,+E%3E
- https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html#for-loops-over-fallibles

**Gotchas**

- The lint fires on `for` over a `Result` too ("for loop over a `Result`"), with the same `if let` advice, and a `for` over an `Err` runs zero times without any other sign.
- `.flatten()` on an iterator of `&Result<T, E>` yields `&T`, which is why the snippet needs `.copied()`; `filter_map(|row| row.as_ref().ok())` yields the same `[80, 443]`.
- `size_hint` on the option's iterator is exact, `(1, Some(1))` for `Some` and `(0, Some(0))` for `None`, so `extend` with an option never over-reserves.

## C++: C++26 made std::optional a range of zero or one, so nested range-for is a nested select, and begin() on a temporary dangles

*New discoveries and currently popular patterns*

**Did you know**

P3168, adopted for C++26, gives `std::optional` `begin()` and `end()`: an empty optional is a range of zero elements, an engaged one a range of one, and it is even a `contiguous_range`. That makes a nested range-for over optional lookups a nested select that stops at the first empty one, and `views::join` over a `vector<optional<int>>` drops the empties. The feature-test macro is `__cpp_lib_optional_range_support` (202406 in GCC 16.2). cppreference lists libstdc++ 16, libc++ 22 (partial), and no MSVC STL version yet; g++ 14 rejects `for (int port : optional)` with "no matching function for call to 'begin'".

**Show me**

```cpp
// C++26 (P3168, std::optional range support), g++ 16.2 -std=c++26 (gcc:16 image). Not in g++ 14.
#include <cstdio>
#include <map>
#include <optional>
#include <ranges>
#include <string>
#include <vector>

std::map<std::string, std::string> region_of{{"u1", "eu"}};
std::map<std::string, int> port_of{{"eu", 8080}};

std::optional<std::string> find_region(const std::string& user_id) {
    auto found = region_of.find(user_id);
    return found == region_of.end() ? std::nullopt : std::optional{found->second};
}
std::optional<int> find_port(const std::string& region) {
    auto found = port_of.find(region);
    return found == port_of.end() ? std::nullopt : std::optional{found->second};
}

int main() {
    // An optional is now a range of 0 or 1 elements, so nested range-for is a nested select
    // that stops at the first empty lookup: u2 never calls find_port.
    for (const char* user_id : {"u1", "u2"})
        for (const std::string& region : find_region(user_id))
            for (int port : find_port(region))
                std::printf("%s -> %s:%d\n", user_id, region.c_str(), port); // u1 -> eu:8080

    // A vector of optionals flattens with views::join, dropping the empty ones.
    std::vector<std::optional<int>> readings{12, std::nullopt, 48};
    for (int reading : readings | std::views::join) std::printf("%d ", reading); // 12 48
    std::printf("\n");

    // The iterator points into the optional, so a temporary's begin() dangles, with no warning:
    // auto stale = find_port("eu").begin();  // -O0 printed 8080; ASan: stack-use-after-scope
}
```

**Why it matters**

Before C++26 the same nested lookup was either an `if` ladder or C++23's `and_then` chain, and both made you spell out how to stop. The range form reads like the query and composes with every range adaptor. The range-for itself is safe, because the temporary optional in its initializer lives for the whole loop. Holding an iterator past the statement is not: the iterator points into the optional's own storage, which is destroyed at the semicolon. Rust's `Option::iter()` borrows the option, so the same line is a borrow-checker error. F# options are not enumerable at all, and a JS array of zero or one is a heap object that outlives any reference to it.

**Chew on this**

Where your code now has an `if (auto region = find_region(...))` ladder three levels deep, would the range-for version be clearer to the next reader, or just newer?

**Sources**

- https://wg21.link/P3168R2 ("Give std::optional Range Support")
- https://en.cppreference.com/w/cpp/utility/optional
- https://en.cppreference.com/w/cpp/compiler_support/26

**Verified**

g++ 16.2 (libstdc++) only; libc++ 22's "partial" support and MSVC not checked.

**Gotchas**

- The iterator type is `std::optional<int>::iterator`, not `int*`: `int* first = maybe_port.begin();` is "cannot convert 'std::optional<int>::iterator' to 'int*'", even though the range is contiguous.
- `std::ranges::size` works and answers 0 or 1.
- The dangling `begin()` gets no warning at `-O0` with `-Wall -Wextra`. At `-O2` the same build warns "dangling pointer to an unnamed temporary may be used [-Wdangling-pointer=]", because that warning needs the optimizer's analysis. Appendix A has the measurements.

## F#: option is not a sequence, so `for` over one is FS0693, and the nested-`for` workaround allocated four times what List.choose did

*Perf and memory model*

**Did you know**

F#'s `'T option` does not implement `IEnumerable`, so `[ for port in Some 8080 -> port ]` is FS0693: "The type 'int option' is not a type whose values can be enumerated with this syntax". FSharp.Core offers `Option.toList` and `Option.toArray` (there is no `Option.toSeq`), and the nested-select shape works through them, stopping after the first empty lookup like the other three. The price is allocation. Over a million inputs, two-thirds of them `Some`, a Release build allocated 21.3 bytes per input for `List.choose id` (the result list and nothing else), 42.7 for `List.collect Option.toList`, and 82.7 for a nested `for` over `Option.toList` in a list expression.

**Show me**

```fsharp
// F# 10 (FSharp.Core 10.1.0.0), .NET 10.0.13, Release build; bytes from GC.GetAllocatedBytesForCurrentThread.
let readings : int option list = List.init 1_000_000 (fun index -> if index % 3 = 0 then None else Some index)

// [ for port in Some 8080 -> port ] does not compile: FS0693, 'int option' is not a type whose values
// can be enumerated. FSharp.Core has Option.toList and Option.toArray, but no Option.toSeq.

let measure_bytes (label: string) (run: unit -> int list) =
    run () |> ignore // warm up
    let before = System.GC.GetAllocatedBytesForCurrentThread()
    let kept = run ()
    let after = System.GC.GetAllocatedBytesForCurrentThread()
    printfn "%-30s %d kept, %.1f bytes per input" label (List.length kept) (float (after - before) / 1e6)

measure_bytes "List.choose id" (fun () -> List.choose id readings)                        // 666666 kept, 21.3
measure_bytes "List.collect Option.toList" (fun () -> List.collect Option.toList readings) // 666666 kept, 42.7
measure_bytes "nested for over Option.toList" (fun () ->
    [ for reading in readings do for value in Option.toList reading -> value ])             // 666666 kept, 82.7
```

**Why it matters**

In F# the zero-or-one view is a conversion you pay for, not a property of the type. `List.choose` is the function built for exactly this shape and allocates only its output: 666,666 list cells at 32 bytes each is the 21.3 MB measured. Every `Option.toList` is a fresh one-element list, and the list expression's nested `for` doubled that again. Rust's `Option::into_iter` and C++26's optional range are views over the option itself and allocate nothing; JavaScript's `[value]` is a heap array per element, the same shape as `Option.toList`. For the nested lookup itself, `Option.bind` is the allocation-free spelling: `find_region user_id |> Option.bind find_port` made one lookup for a missing user and two for a known one.

**Chew on this**

Which of your F# pipelines turn options into lists only so that a `for` or a `List.collect` will accept them, and would `choose` or `bind` say the same thing without the lists?

**Sources**

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-core-optionmodule.html
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-listmodule.html#choose
- https://learn.microsoft.com/dotnet/api/system.gc.getallocatedbytesforcurrentthread

**Gotchas**

- FSharp.Core's `Option` conversions are `ofNullable`, `ofObj`, `ofValueOption`, `toArray`, `toList`, `toNullable`, `toObj` and `toValueOption`. No `toSeq`: `Option.toSeq` is FS0039, "not defined".
- `Seq.collect Option.toArray |> List.ofSeq` allocated 42.7 bytes per input, the same as `List.collect Option.toList`, and `List.collect (Option.toArray >> List.ofArray)` allocated 64.0.
- `Map [ "u1", "eu" ]` in a script now draws "info FS3886: This list expression contains a single tuple element. Did you mean to use ';' instead of ','" on .NET SDK 10.0.402. It is informational only, and `Map [ ("u1", "eu") ]` silences it.

## TypeScript: flatMap is JavaScript's option of zero or one, and it keeps a bare value as if bracketed and an undefined as a hole

*Idioms and antipatterns*

**Did you know**

`Array.prototype.flatMap` is JavaScript's zero-or-one collection: the callback returns `[]` to drop an element and `[value]` to keep it. It flattens exactly one level, and a return value that is not an array is kept as-is. So a forgotten bracket on the keep side changes nothing (`[80, 443]` either way), and an `undefined` in place of the `[]` on the drop side is kept as a hole: `[80, undefined, 443, undefined]`. tsc infers that result as `(number | undefined)[]` and reports nothing until the array meets an annotation that says `number[]`.

**Show me**

```typescript
// TypeScript, tsc 7.0.2 --strict, Node 22.23.4, effect 4.0.6.
import { Array as EffectArray, Option } from "effect"

const ports_text: ReadonlyArray<string> = ["80", "eighty", "443", ""]
const parse_port = (text: string): number => Number.parseInt(text, 10)

// flatMap is JavaScript's 0-or-1 collection: [] drops an element, [value] keeps it.
const kept = ports_text.flatMap((text) => Number.isInteger(parse_port(text)) ? [parse_port(text)] : [])
console.log(kept) // [ 80, 443 ]

// A bare value is kept as if bracketed, so a forgotten bracket changes nothing...
const unbracketed = ports_text.flatMap((text) => Number.isInteger(parse_port(text)) ? parse_port(text) : [])
console.log(unbracketed) // [ 80, 443 ], typed number[]

// ...and undefined instead of [] is kept too. tsc types it (number | undefined)[] and says nothing
// until the result meets an annotation.
const forgot_empty = ports_text.flatMap((text) => Number.isInteger(parse_port(text)) ? [parse_port(text)] : undefined)
console.log(forgot_empty) // [ 80, undefined, 443, undefined ]
// const checked: number[] = forgot_empty  // TS2322: '(number | undefined)[]' is not assignable to type 'number[]'

// Effect names the shape: an array of Options, keep the Somes.
const somes = EffectArray.getSomes(ports_text.map((text) => Option.liftPredicate(parse_port(text), Number.isInteger)))
console.log(somes) // [ 80, 443 ]
```

**Why it matters**

`flatMap` with brackets is the idiom JavaScript has for "map and filter in one pass", and it is also how a nested lookup reads: `find_region(user_id).flatMap((region) => find_port(region).map(...))` made one lookup for a missing user and two for a known one. The rule that makes the idiom forgiving, non-arrays are kept, is also what makes the drop side fragile: only an array means "this many items", so anything else, `undefined` and `null` included, means "keep it". Rust's `flat_map` requires an `IntoIterator`, so returning a bare value or `()` does not compile, and C++ `views::join` over optionals has no "bare value" case at all. Effect's `Array.getSomes` over `Option`s makes the drop explicit in the type.

**Chew on this**

Which `flatMap` callbacks in your code return a value from a branch that someone may later shorten to `&&` or `?.`, and what would that branch return then?

**Sources**

- https://tc39.es/ecma262/#sec-array.prototype.flatmap
- https://developer.mozilla.org/docs/Web/JavaScript/Reference/Global_Objects/Array/flatMap
- https://effect-ts.github.io/effect/effect/Array.ts.html

**Gotchas**

- It flattens one level only: `flatMap((text) => [[text.length]])` gave `[[2],[6],[3],[0]]`, an array of arrays.
- A string is not spread: `["ab"].flatMap((text) => text)` is `["ab"]`, not `["a","b"]`, because only arrays are flattened.
- `Option.liftPredicate(value, predicate)` is Effect's one-call "Some if it passes"; `Number.isInteger` rejected the `NaN` from `"eighty"` and `""`.

# The functional angle: the nested select stops at the first empty lookup in all four, and only F# charges for the shape

_Draws on all four tips. The shape: three optional lookups (user to region to port), written as a nested select, where an empty result at any level ends the query. Each row counted its lookups._

```rust
// Rust, rustc 1.99.1: two spellings of the same nested select
let endpoint = find_region(user_id).and_then(|region| find_port(region).map(|port| format!("{region}:{port}")));
let endpoints: Vec<String> = find_region(user_id).into_iter()
    .flat_map(|region| find_port(region).into_iter().map(move |port| format!("{region}:{port}")))
    .collect();
```

| Language | Nested-select form | Lookups, known user / missing user | What it costs |
| --- | --- | --- | --- |
| F# | `find_region user_id \|> Option.bind find_port`, or `[ for region in Option.toList .. do for port in Option.toList .. -> .. ]` | 2 / 1 (both forms) | `bind` is free; the collection form allocates a list per option (82.7 bytes per input in the tip's loop) |
| Rust | `and_then`, or `into_iter().flat_map(..)` | 2 / 1 (both forms) | nothing: the option's iterator is a view; the `flat_map` form needs `move` on the inner closure (without it: E0373, "closure may outlive the current function") |
| C++26 | nested range-for over `optional` | 2 / 1 | nothing at runtime; needs GCC 16, and an iterator kept past the statement dangles |
| TypeScript | `[]`/`[value]` arrays with nested `flatMap` | 2 / 1 | a heap array per lookup, plus the hole when a branch returns `undefined` |

F# is the baseline because it is the one language here where the shape has a dedicated function (`Option.bind`) and the collection view is a conversion. That makes the cost visible: the collection view is not free in general, it is free only where the language made the option itself the iterator.

Left open: when a query over optional lookups grows a fourth level, which reads better to you, the chain (`and_then`, `bind`) or the nested `for`, and does the answer change when the levels start returning lists instead of options?

# The security angle: when every check fails, the zero-or-one view leaves an empty list, and "all of nothing" is true

_Draws on the Rust tip, Mode C: the missing check. The view that drops an `Err` as "no item" turns a policy service outage into a vacuous success. Direction: none of the four languages prevents it._

```rust
// Rust, rustc 1.99.1: "allow if every applicable policy allows"
let permission_checks: Vec<Result<bool, String>> =
    vec![Err("policy service timeout".into()), Err("policy service timeout".into())];
let allowed = permission_checks.iter().flatten().all(|allowed| *allowed);
println!("{allowed}"); // true: both checks failed, flatten dropped them, and all() of nothing is true
```

The same three steps in the other two languages that have them gave the same answer:

```fsharp
// F#, .NET 10: Result.toOption + List.choose drops the errors, List.forall of an empty list is true
checks |> List.choose Result.toOption |> List.forall id // true
```

```typescript
// TypeScript (run as JS, Node 22.23.4): flatMap to [] for a failed check, every() of an empty array is true
checks.flatMap((check) => check.ok ? [check.allowed] : []).every((allowed) => allowed) // true
```

This is CWE-636, Not Failing Securely ('Failing Open'): an outage of the thing that says no is read as "nobody said no". The fix is not a different combinator; it is refusing to drop the errors before the decision: `permission_checks.iter().all(|check| matches!(check, Ok(true)))` treats an `Err` as a denial, and returned `false` for the two timeouts.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `flatten()` then `all()` over failed checks is `true` | compiles silently; no lint for `flatten` over `Result` | decide on the `Result` (`matches!(check, Ok(true))`), never after flattening |
| F# | `List.choose Result.toOption` then `List.forall` is `true` | nothing; `toOption` is the explicit drop | same; the explicit name does not make the decision for you |
| TypeScript | `flatMap(.. ? [value] : [])` then `every` is `true` | nothing | an empty input to an authorization `every` should be a denial |
| C++26 | the range form has no `Result` to flatten (`std::expected` is not a range) | the shape cannot be written with std types alone | a hand-written filter over `expected` reintroduces it |

Left open: which of your "all of these must pass" checks would return true if the list of checks came back empty?

# FAQ

**Is C++26's optional range available on every compiler that has C++26 mode?**
No. cppreference lists libstdc++ 16, libc++ 22 as partial, and no MSVC STL version. The feature-test macro `__cpp_lib_optional_range_support` (202406 in GCC 16.2) is the portable check.

**Does `Option::iter()` in Rust allocate, like F#'s `Option.toList`?**
No. It is a view that borrows the option; its `size_hint` is exactly `(1, Some(1))` or `(0, Some(0))`, and `extend` with it appended `8080` to `[22]` with no intermediate collection.

**Does Effect's `Array.getSomes` keep the input order?**
Yes: `["80", "eighty", "443", ""]` mapped through `Option.liftPredicate` and `getSomes` gave `[80, 443]`, in input order.

**Why did rustc warn about `for` over an `Option` but not about `flatten()`?**
The lint `for_loops_over_fallibles` targets the loop syntax only, and its advice is a style one ("more readably written as an `if let`"). Dropping errors with `flatten()` is a meaning choice, and no lint in rustc or in clippy's pedantic and nursery groups flagged it here.

# Appendix A: a dangling optional iterator that reads the right value at every optimization level

_Not part of the tip rotation. Written 2026-10-27; backs the C++ tip's last line. A concept appendix about a bug pattern, not a documented incident (none tied to this thesis turned up). Snippets run on g++ 16.2 (`gcc:16` image), output quoted._

**Bug class:** a latent bug that hides from ordinary testing: deterministic undefined behaviour (CWE-562, Return of Stack Variable Address, in spirit; the storage is a temporary's) that printed the correct value at `-O0` and at `-O2`. Only the optimized build warned, and only AddressSanitizer reported it. Anti-pattern: keeping an iterator into a temporary vocabulary type past the full-expression.

## A.1 The program

```cpp
// C++26, g++ 16.2. A dangling iterator into a temporary std::optional.
#include <cstdio>
#include <optional>
#include <string>
std::optional<std::string> find_region() { return std::string{"eu-west-1"}; }
int noise(int seed) { volatile char scratch[64]; for (int offset = 0; offset < 64; ++offset) scratch[offset] = static_cast<char>('A' + (seed + offset) % 26); return scratch[0]; }
int main() {
    auto stale = find_region().begin(); // the optional dies at the end of this statement
    noise(3);                            // reuse the stack the temporary lived in
    std::printf("[%s]\n", stale->c_str());
}
```

## A.2 What each build said

| Build | Warnings (`-Wall -Wextra`) | Output |
| --- | --- | --- |
| `-O0` | 0 | `[eu-west-1]` |
| `-O2` | 1: "dangling pointer to an unnamed temporary may be used [-Wdangling-pointer=]" | `[eu-west-1]` |
| `-fsanitize=address` | | "AddressSanitizer: stack-use-after-scope" |

The value survived because nothing reused that exact stack slot before the read, even with `noise()` writing 64 bytes in between. That is the trap: a test that checks the output passes, the debug build is silent, and the one diagnostic depends on the optimizer's flow analysis, so it can appear or disappear when unrelated code changes what gets inlined.

## A.3 Back to the tip

- **C++:** iterate in the range-for's own initializer, where the temporary lives for the whole loop; never store `begin()` of a returned optional. Run the test suite under ASan once.
- **Rust:** `find_region().iter()` held past the statement is a borrow-checker error, so the shape cannot compile: rustc 1.99.1 reported "E0716: temporary value dropped while borrowed".
- **F# and TypeScript:** the zero-or-one collections there (`Option.toList`, a `[value]` array) are heap objects, so an iterator over them cannot outlive its storage.
