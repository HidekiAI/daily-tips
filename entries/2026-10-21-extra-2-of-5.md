## Rust: the `cron` crate skips 02:30 on spring-forward and runs 01:30 twice on fall-back, and `croner` does neither

_Stdlib and ecosystem gems_

**Did you know**

Two popular cron crates disagree on every hard case. Given a `chrono-tz` zone, `cron` 0.17.0 skips a fixed-time job whose wall time does not exist (its `schedule.rs` handles `LocalResult::None` with `continue`) and fires both occurrences of a repeated wall time. `croner` 4.0.2 documents Vixie-cron behaviour instead: the skipped job runs at the first valid time after the gap, and a fixed-time job runs once in the repeated hour. They also read a pattern that restricts both day-of-month and day-of-week oppositely: `croner` follows the Vixie OR rule ("13th or any Friday"), `cron` requires both ("Friday the 13th"). `cron` also takes a seconds field first and rejects the classic five-field `30 2 * * *`.

**A caveat that belongs on every Rust crate claim:** Rust and its ecosystem are still moving fast. `cron` is pre-1.0 (0.17.0), `croner` is on its fourth major version (4.0.2), and `chrono` has sat at 0.4.x for years. By the time you read this, either crate may have changed its DST rules, been superseded, or become the legacy choice. Treat the behaviour below as "measured on 2026-10-21" and re-run it against the version you actually depend on.

**Show me**

```rust
// Cargo.toml (measured versions; check what they are today):
// cron = "0.17.0", croner = "4.0.2", chrono = "0.4.45", chrono-tz = "0.10.4"
use chrono::{DateTime, TimeZone};
use chrono_tz::{America::Chicago, Tz};
use std::str::FromStr;

fn main() {
    // Next three runs of each schedule after a start time, as RFC 3339 strings.
    let fn_croner_runs = |pattern: &str, start: DateTime<Tz>| -> Vec<String> {
        let schedule = croner::Cron::from_str(pattern).expect("croner pattern");
        schedule.iter_after(start).take(3).map(|run| run.to_rfc3339()).collect()
    };
    let fn_cron_runs = |pattern: &str, start: DateTime<Tz>| -> Vec<String> {
        let schedule = cron::Schedule::from_str(pattern).expect("cron pattern"); // seconds field first
        schedule.after(&start).take(3).map(|run| run.to_rfc3339()).collect()
    };
    let before_spring = Chicago.with_ymd_and_hms(2026, 3, 7, 0, 0, 0).unwrap();
    let before_fall = Chicago.with_ymd_and_hms(2026, 10, 31, 0, 0, 0).unwrap();

    // "Every day at 02:30" across spring-forward: croner runs at 03:00, cron skips the day.
    assert_eq!(fn_croner_runs("30 2 * * *", before_spring)[1], "2026-03-08T03:00:00-05:00");
    assert_eq!(fn_cron_runs("0 30 2 * * *", before_spring)[1], "2026-03-09T02:30:00-05:00");

    // "Every day at 01:30" across fall-back: croner runs once, cron runs twice.
    assert_eq!(fn_croner_runs("30 1 * * *", before_fall)[2], "2026-11-02T01:30:00-06:00");
    assert_eq!(fn_cron_runs("0 30 1 * * *", before_fall)[1..], ["2026-11-01T01:30:00-05:00", "2026-11-01T01:30:00-06:00"]);

    // Day-of-month plus day-of-week: croner reads OR (Vixie cron), cron reads AND.
    let new_year = Chicago.with_ymd_and_hms(2026, 1, 1, 0, 0, 0).unwrap();
    assert_eq!(fn_croner_runs("0 0 13 * FRI", new_year)[0], "2026-01-02T00:00:00-06:00"); // any Friday
    assert_eq!(fn_cron_runs("0 0 0 13 * FRI", new_year)[0], "2026-02-13T00:00:00-06:00"); // Friday the 13th
    println!("ok");
}
```

**Why it matters**

A nightly billing or backup job written as `0 30 1 * * *` with the `cron` crate in a DST zone charges or backs up twice on the first Sunday of November and, at 02:30, not at all in March. Swapping to `croner` changes both answers without changing a character of the pattern. The simplest defence is to schedule in UTC, where neither case exists; the durable one is an idempotency key (see the security angle). None of the other three ships a cron parser in its standard library: C++ and .NET leave it to libraries (.NET users reach for Cronos, NCrontab or Quartz.NET), and Node to packages like `node-cron` and `croner`'s own JS original.

**Chew on this**

**Sources**

- https://docs.rs/cron/0.17.0/cron/
- https://docs.rs/croner/4.0.2/croner/ (README, "Daylight Saving Time (DST) Handling")
- https://manpages.debian.org/trixie/cron/crontab.5.en.html
- https://man7.org/linux/man-pages/man5/crontab.5.html

**Verified**

Crate behaviour measured on the versions above. The .NET and Node scheduler libraries are named, not measured.

**Gotchas**

- `cron` 0.17.0 rejects `"30 2 * * *"` (five fields): its first field is seconds, so the same job is `"0 30 2 * * *"`. `croner` accepts both five and six fields.
- With `"0 */30 * * * *"` across the fall-back hour, `cron`'s iterator yields 06:00Z, 07:00Z, 06:30Z, 07:30Z: it runs the wall clock's two passes interleaved, so the instants go backwards (see the functional angle). `croner` documents that it runs the whole first pass, then the second.
- Wildcard and step jobs (`*/30`) run in both passes of the repeated hour in both crates, and in Debian cron, which applies its DST rule only to fixed-time jobs.
- `croner` `"0 0 29 2 *"` next fires on 2028-02-29, then 2032-02-29. A leap-day job runs once every four years and nobody notices it never ran.
- `croner` `"0 0 31 * *"` skips February, April, June, September and November entirely: no clamp to the last day.
- Debian's `cron` ignores `TZ=` and `CRON_TZ=` for scheduling: its crontab(5) says the variable affects "only the commands executed in the crontab, not the execution of the crontab tasks themselves". Fedora's `cronie` does honour `CRON_TZ`. Same line, two behaviours.

## C++: every epoch is `sys_days{origin} + duration<Rep>`, and `duration<uint32_t>` wraps NTP back to 1900 with no warning

_Type system deep cuts_

**Did you know**

`std::chrono` can describe any wire epoch as an origin plus a duration type, so the constants everyone hard-codes become derivations: `sys_days{1970y/January/1} - sys_days{1900y/January/1}` is NTP's 2,208,988,800 s, and the same subtraction in 100 ns ticks from 1601 is Windows FILETIME's 116,444,736,000,000,000. The `Rep` you pick also decides when the epoch ends. A `duration<std::uint32_t>` modelling NTP's 32-bit seconds field last holds 2036-02-07 06:28:15; one more second wraps to 1900-01-01, and `ntp_seconds{5} - ntp_seconds{10}` is 4,294,967,291. Unsigned wrap is defined behaviour, so neither `-Wall -Wextra -Wconversion -Wsign-conversion` nor `-fsanitize=undefined` says anything. The calendar types and these duration types are C++20 and work on Apple clang 21 and GCC 14; `gps_clock`, used in the Gotchas, is in GCC 14's libstdc++ but not in Apple's libc++.

**Show me**

```cpp
#include <chrono>
#include <cstdint>
#include <iostream>
#include <limits>
using namespace std::chrono;

// Every wire epoch is an origin plus a duration. The rep type decides when it ends.
using ntp_seconds = duration<std::uint32_t>;                                 // NTP era field
using filetime_ticks = duration<std::int64_t, std::ratio<1, 10'000'000>>;   // 100 ns
constexpr sys_days NTP_EPOCH = 1900y / January / 1;
constexpr sys_days GPS_EPOCH = 1980y / January / 6;
constexpr sys_days FILETIME_EPOCH = 1601y / January / 1;

int main() {
    // The offsets everybody hard-codes, derived instead of typed:
    std::cout << duration_cast<seconds>(sys_days{1970y / January / 1} - NTP_EPOCH).count() << "\n";     // 2208988800
    std::cout << duration_cast<filetime_ticks>(sys_days{1970y / January / 1} - FILETIME_EPOCH).count() << "\n"; // 116444736000000000

    // An unsigned rep wraps with no diagnostic, under -Wall -Wextra, on both compilers.
    ntp_seconds last_of_era0{std::numeric_limits<std::uint32_t>::max()};
    std::cout << (NTP_EPOCH + seconds{last_of_era0.count()}) << "\n";          // 2036-02-07 06:28:15
    ntp_seconds one_later = last_of_era0 + ntp_seconds{1};
    std::cout << (NTP_EPOCH + seconds{one_later.count()}) << "\n";            // 1900-01-01 00:00:00
    std::cout << (ntp_seconds{5} - ntp_seconds{10}).count() << "\n";         // 4294967291, not -5

    // GPS broadcasts the week number in 10 bits, so it rolls every 1024 weeks.
    for (int rollover : {1, 2, 3})
        std::cout << (GPS_EPOCH + weeks{1024 * rollover}) << "\n";            // 1999-08-22 2019-04-07 2038-11-21

    // A signed 64-bit count of 100 ns ticks from 1601 lasts until year 30828.
    std::cout << year_month_day{floor<days>(sys_time<filetime_ticks>{FILETIME_EPOCH} + filetime_ticks::max())} << "\n"; // 30828-09-14
}
```

**Why it matters**

A server that subtracts two NTP-era timestamps to compute a clock offset gets 4,294,967,291 s instead of -5 s the moment the operands arrive out of order, and in 2036 gets a 136-year jump from timestamps that are one second apart. RFC 5905 solves the rollover with an era number outside the 32-bit field; code that copied only the field into a `uint32_t` did not get the era. The chrono type at least puts the width in the type name, which is where a reviewer can see it. Rust's `u32` panics on overflow in debug builds and wraps in release, .NET's `uint` wraps unless the code is `checked`, and JS numbers never wrap at 2^32 at all unless a bitwise operator is involved (`>>> 0`).

**Chew on this**

Which wire formats in your system store time in 32 bits, and which side of 2036 or 2038 does each one fail on? When you parse a FILETIME or an NTP timestamp, is the epoch offset a named constant derived from two dates, or a literal someone pasted?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/duration
- https://en.cppreference.com/w/cpp/chrono/gps_clock
- https://www.rfc-editor.org/rfc/rfc5905 (NTP era and timestamp formats)
- https://en.wikipedia.org/wiki/GPS_week_number_rollover

**Verified**

Compiled clean and run on Apple clang 21 and GCC 14.4.0 (`-std=c++20 -Wall -Wextra`, plus `-Wconversion -Wsign-conversion` on clang: zero warnings). `gps_clock` conversions ran on GCC 14 only.

**Gotchas**

- The GPS rollover dates the arithmetic prints (1999-08-22, 2019-04-07) are GPS midnights. In UTC, which is what the news reported, they were 1999-08-21 23:59:47 and 2019-04-06 23:59:42 (GCC 14 `clock_cast<utc_clock>`), because GPS time does not insert leap seconds.
- The 13-bit modernised GPS week field rolls on 2137-01-06 (`GPS_EPOCH + weeks{8192}`).
- clang's `-fsanitize=unsigned-integer-overflow` (not part of `undefined`, since the wrap is defined) does flag the NTP wrap, but also flags libc++'s own `year_month_day` internals (`11 + 4294967287` in `year_month_day.h`), so it is noisy.
- `duration<std::int32_t>::max()` from 1970 is `2038-01-19 03:14:07`: Y2038 is the same mechanism with a signed `Rep`.
- There is no `sys_minutes` alias in std (clang: "use of undeclared identifier"). The aliases are `sys_days` and `sys_seconds`; anything else is `sys_time<minutes>`.
- NTP's era 0 and unsigned 32-bit Unix time end at the same clock time, 06:28:15 on February 7 (2036 and 2106): both are 2^32 s after their epoch, and 1900 to 1970 and 2036 to 2106 contain the same number of leap days.

## F#: `XmlConvert.ToTimeSpan "P1M"` is 30 days, so Jan 31 plus "P1M" is March 2

_Stdlib and ecosystem gems_

**Did you know**

`TimeSpan` is a count of ticks with no calendar part, so it cannot hold "one month". .NET's only ISO 8601 duration parser, `XmlConvert.ToTimeSpan` (from the XML Schema `xs:duration` type), converts anyway: `P1M` becomes 30 days and `P1Y` 365 days, with no warning. `DateTime(2026, 1, 31) + XmlConvert.ToTimeSpan "P1M"` is therefore 2026-03-02, while `AddMonths(1)` is 2026-02-28. `TimeSpan.Parse` is not ISO 8601 at all (`"P1D"` throws `FormatException`), and `XmlConvert` rejects the valid ISO week duration `"P1W"`. The time zone side has the same shape: since .NET 6, `TimeZoneInfo.TryConvertIanaIdToWindowsId` maps IANA IDs to Windows IDs, many to one, and the reverse needs a region. Measured on F# 8, FSharp.Core 8.0.0.0, .NET 8.0.8.

**Show me**

```fsharp
open System
open System.Xml

// TimeSpan has no months, so the ISO 8601 parser silently picks a length for one:
let one_month = XmlConvert.ToTimeSpan "P1M"
printfn "%O %O" one_month (XmlConvert.ToTimeSpan "P1Y")                     // 30.00:00:00 365.00:00:00
printfn "%s" ((DateTime(2026, 1, 31) + one_month).ToString "yyyy-MM-dd")   // 2026-03-02, not Feb 28
printfn "%s" ((DateTime(2026, 1, 31)).AddMonths(1).ToString "yyyy-MM-dd")  // 2026-02-28

// TimeSpan.Parse is not ISO 8601 at all, and XmlConvert rejects a valid ISO week:
let fn_try_parse (parse: string -> TimeSpan) (text: string) : string =
    try (parse text).ToString() with error -> error.GetType().Name
printfn "%s %s" (fn_try_parse TimeSpan.Parse "P1D") (fn_try_parse XmlConvert.ToTimeSpan "P1W") // FormatException FormatException

// Keep the calendar part and the clock part apart, the way ISO 8601 does:
type CalendarSpan = { months: int; days: int; clock: TimeSpan }
let add_span (start: DateTimeOffset) (span: CalendarSpan) : DateTimeOffset =
    start.AddMonths(span.months).AddDays(float span.days) + span.clock     // months first, like Temporal
let jan_31 = DateTimeOffset(2026, 1, 31, 9, 0, 0, TimeSpan.Zero)
printfn "%O" (add_span jan_31 { months = 1; days = 0; clock = TimeSpan.Zero }) // 2/28/2026 9:00:00 AM +00:00

// Zone IDs: IANA to Windows is many-to-one, so the round trip needs a region.
let fn_windows_id (iana: string) : string =
    match TimeZoneInfo.TryConvertIanaIdToWindowsId iana with
    | true, windows -> windows
    | _ -> "(none)"
printfn "%s | %s" (fn_windows_id "America/Chicago") (fn_windows_id "Europe/Kyiv")  // Central Standard Time | FLE Standard Time
let fn_iana_id (windows: string) (region: string) : string =
    match TimeZoneInfo.TryConvertWindowsIdToIanaId(windows, region) with
    | true, iana -> iana
    | _ -> "(none)"
printfn "%s %s" (fn_iana_id "Central Standard Time" "001") (fn_iana_id "Central Standard Time" "MX") // America/Chicago America/Matamoros
```

**Why it matters**

A subscription service that stores its plan length as the ISO string `"P1M"` and applies it with `XmlConvert` bills every 30 days, about 12.2 charges a year on a monthly plan, and the billing day walks backwards through the calendar, which a test covering a single cycle never shows. Zone IDs fail the same way at a boundary: a Windows ID is not a zone, it is a family of them, so a value stored as `"Central Standard Time"` comes back as `America/Chicago`, `America/Matamoros` or `America/Winnipeg` depending on the region you pass. Rust's `jiff::Span` and JS `Temporal.Duration` keep months as months; C++ `months{1}` is the average month (part 1), which is the same mistake made with more precision.

**Chew on this**

Where does your system store a period ("monthly", "P1M", "30") and which type turns it back into a date? If you stored a Windows zone ID last year, which IANA zone do you get for it today?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.xml.xmlconvert.totimespan
- https://learn.microsoft.com/en-us/dotnet/api/system.timezoneinfo.tryconvertianaidtowindowsid
- https://learn.microsoft.com/en-us/dotnet/api/system.datetime.fromoadate
- https://learn.microsoft.com/en-us/troubleshoot/microsoft-365-apps/excel/wrongly-assumes-1900-is-leap-year

**Verified**

The ".NET 6" for the zone ID conversion API is recalled, not checked; everything else ran on .NET 8.0.8.

**Gotchas**

- `America/Chicago` maps to `"Central Standard Time"` although it observes daylight time (`SupportsDaylightSavingTime` is true). `Europe/London` maps to `"GMT Standard Time"`, and both `Europe/Kyiv` and the old name `Europe/Kiev` map to `"FLE Standard Time"`.
- On macOS and Linux, `FindSystemTimeZoneById "Central Standard Time"` works (the Windows ID is converted), and so does the renamed `"Europe/Kiev"`.
- `TimeSpan.Parse "24:00"` and `"36:00"` throw `OverflowException`; a day-and-a-half is `"1.12:00"`. `XmlConvert.ToString` writes 36 hours as `P1DT12H`, so the round trip changes the spelling.
- `DateTime.FromFileTimeUtc 0L` is 1601-01-01 UTC, but `FromFileTime 0L` (local) in Chicago is `1600-12-31T18:09:00-05:51`: before 1883 the zone uses local mean time.
- `DateTime.FromOADate` counts days from 1899-12-30, so serial 60 is 1900-02-28 in .NET; Excel's 1900 date system shows serial 60 as the nonexistent 1900-02-29, a bug Microsoft keeps for Lotus 1-2-3 compatibility. Same number, one day apart before March 1900.
- Negative OLE Automation dates are not monotonic: `FromOADate -1.5` is 1899-12-29 12:00, which is later than `-1.0` (1899-12-29 00:00), and `-0.5` equals `0.5` (1899-12-30 12:00). Sorting serials numerically mis-sorts them.
- `ParseExact("13:00 PM", "HH:mm tt", en-US)` succeeds and returns 13:00: with `HH` the `PM` is ignored. With `hh` it throws.
- `DateTime(1582, 10, 10)` is valid (a Sunday) although that date never happened in Catholic Europe: `DateTime` is proleptic Gregorian. `DateTime(1752, 9, 3, JulianCalendar())` gives 1752-09-14, the British cutover.

## TypeScript: `Temporal` turns every `Date` guess into an option, and its defaults still guess

_New discoveries and currently popular patterns_

**Did you know**

`Temporal` (TC39 Stage 4 in March 2026, on by default in Node 26, released 2026-05-05) splits `Date` into types that cannot be confused (`Instant`, `ZonedDateTime`, `PlainDate`, `PlainDateTime`, `Duration`), makes months 1-based and values immutable, and turns each silent `Date` decision into a named option: `overflow: "reject"`, `disambiguation: "reject"`, `relativeTo`. The defaults still choose for you, and choose like the libraries in part 1: `add({ months: 1 })` clamps Jan 31 to Feb 28, a DST gap resolves to 03:30, and a property bag `{ month: 2, day: 30 }` clamps while the string `"2026-02-30"` throws. It also does not invert: Jan 31 plus one month is Feb 28, but `until` reports Jan 31 to Feb 28 as `P28D`. Measured on Node 26.12.1 (V8 14.6, tz data 2026e) and type-checked with tsc 6.0.3 `lib.esnext`; this host's Node 22 has no `Temporal`.

**Show me**

```typescript
// Node 26 (Temporal on by default). Each comment is the printed value.
const fn_attempt = (thunk: () => unknown): string => {
    try { return String(thunk()); } catch (error) { return (error as Error).name; }
};
const jan_31 = Temporal.PlainDate.from("2026-01-31");

// Months are 1-based and the default still clamps, like .NET and jiff:
console.log(String(jan_31.add({ months: 1 })));                                        // 2026-02-28
console.log(fn_attempt(() => jan_31.add({ months: 1 }, { overflow: "reject" })));    // RangeError

// add() and until() are not inverses: one month forward, but "P28D" back.
console.log(String(jan_31.until("2026-02-28", { largestUnit: "months" })));            // P28D

// A string is strict, a property bag clamps by default: two answers for Feb 30.
console.log(fn_attempt(() => Temporal.PlainDate.from("2026-02-30")));                  // RangeError
console.log(String(Temporal.PlainDate.from({ year: 2026, month: 2, day: 30 })));       // 2026-02-28

// Calendar fields are applied largest first: months, then days.
console.log(String(Temporal.PlainDate.from("2026-01-30").add({ months: 1, days: 1 }))); // 2026-03-01

// Durations: P1D equals PT24H until you say which day it is.
const one_day = Temporal.Duration.from("P1D");
console.log(Temporal.Duration.compare(one_day, Temporal.Duration.from("PT24H")));      // 0
console.log(one_day.total({ unit: "hours", relativeTo: "2026-03-08T00:00[America/Chicago]" })); // 23
console.log(fn_attempt(() => Temporal.Duration.from("P1M").total("days")));          // RangeError

// Every DST choice is an option, and only "reject" makes you handle it.
console.log(String(Temporal.ZonedDateTime.from("2026-03-08T02:30[America/Chicago]")));  // 2026-03-08T03:30:00-05:00[America/Chicago]
console.log(fn_attempt(() => Temporal.ZonedDateTime.from("2026-03-08T02:30[America/Chicago]", { disambiguation: "reject" }))); // RangeError

// Migrating: Date -> Instant is lossless; the seconds-vs-ms trap survives it.
console.log(String(new Date("2026-10-21T12:00Z").toTemporalInstant()));                // 2026-10-21T12:00:00Z
console.log(String(Temporal.Instant.fromEpochMilliseconds(1_761_000_000)));            // 1970-01-21T09:10:00Z
```

**Why it matters**

Migrating `Date` code to `Temporal` removes the parse and mutation traps from part 1, but a straight port keeps every default decision: the month clamp, the DST shift, and the 24-hour day when no `relativeTo` is given. The migration is the moment to decide which of those your domain wants and write the option down, because after it the code looks correct to every reviewer. `Temporal` is the only API of the four where each of those choices has a name at the call site; Rust's `jiff` is the closest (strictness is a different method, `unambiguous()`), while .NET and C++ express them as different functions or types rather than options.

**Chew on this**

If you ported your `Date` code to `Temporal` tomorrow, which calls would you mark `overflow: "reject"`, and who decides what Feb 30 means for a user-entered date? Is a clamp ever the right default for a value a human typed?

**Gotchas**

- `Temporal.Instant.from("2026-10-21T12:00")` throws: an `Instant` string needs an offset or `Z`. `PlainDate.from("2026-10-21T23:30Z")` also throws ("UTC designator is not valid"), so a `Z` string cannot silently become a local date.
- A string whose offset disagrees with its zone (`"2026-07-01T12:00-06:00[America/Chicago]"`, which is -05:00 in July) throws by default; `{ offset: "ignore" }` keeps the wall time and recomputes the offset.
- `disambiguation: "earlier"` on the 02:30 gap gives 01:30 CST, half an hour before the gap starts, not 02:00. "Earlier" shifts by the gap's length.
- `startOfDay()` is not always 00:00: `America/Sao_Paulo` on 2018-11-04 starts at 01:00, because DST skipped midnight. `hoursInDay` for Chicago on 2026-03-08 is 23.
- `PlainTime.from("24:00")` throws, although `new Date("...T24:00:00Z")` accepts it (part 1).
- A leap second string `"2016-12-31T23:59:60Z"` parses as `23:59:59Z`, the same as Rust `jiff`.
- `PlainDate.from("2024-12-30")` has `yearOfWeek` 2025 and `weekOfYear` 1: the ISO week-year is a separate field.
- Two equal `PlainDate`s are not `===`; use `equals` or `PlainDate.compare`.
- Node 22's iterator helpers include `take`, `drop`, `filter` and `map` but no `takeWhile`, and Node 26 does not add one either.

# The functional angle: a schedule is a lazy infinite sequence, and `take_while` is only correct if it is sorted

Draws on the Rust tip, with the other three written against the same data. The shape: "every run before the deadline" over a lazy, possibly infinite schedule. Rust `take_while` (F# `Seq.takeWhile`, C++ `views::take_while`) is the natural fold for that, because it stops at the first run past the deadline instead of searching forever. It also silently assumes the sequence is sorted.

The Rust `cron` crate's every-30-minutes iterator across the fall-back hour yields 06:00Z, 07:00Z, 06:30Z, 07:30Z. With a 07:00Z deadline:

```rust
// Rust (cron 0.17.0, chrono-tz 0.10.4)
let schedule = cron::Schedule::from_str("0 */30 * * * *").unwrap();
let start = Chicago.with_ymd_and_hms(2026, 11, 1, 0, 50, 0).unwrap();
let deadline = Utc.with_ymd_and_hms(2026, 11, 1, 7, 0, 0).unwrap(); // 01:00 CST
let by_take_while: Vec<_> = schedule.after(&start).take_while(|run| *run < deadline).collect();
let by_filter: Vec<_> = schedule.after(&start).take(4).filter(|run| *run < deadline).collect();
println!("{} vs {}", by_take_while.len(), by_filter.len()); // 1 vs 2
```

F# is the baseline since F# `Seq.takeWhile` is the same lazy combinator in the language where laziness is idiomatic:

```fsharp
// F#
let runs = [ 6, 0; 7, 0; 6, 30; 7, 30 ] |> Seq.map (fun (hour, minute) -> DateTimeOffset(2026, 11, 1, hour, minute, 0, TimeSpan.Zero))
let deadline = DateTimeOffset(2026, 11, 1, 7, 0, 0, TimeSpan.Zero)
printfn "%d vs %d" (runs |> Seq.takeWhile (fun run -> run < deadline) |> Seq.length) (runs |> Seq.filter (fun run -> run < deadline) |> Seq.length) // 1 vs 2
```

C++20 ranges, same answer:

```cpp
// C++20
auto fn_before_deadline = [deadline](sys_time<minutes> run) { return run < deadline; };
std::cout << std::ranges::distance(runs | std::views::take_while(fn_before_deadline)) << " vs "
          << std::ranges::distance(runs | std::views::filter(fn_before_deadline)) << "\n"; // 1 vs 2
```

TypeScript has iterator helpers but no `takeWhile`, so it is a hand-written generator:

```typescript
// TypeScript
const take_while = function* <T>(source: Iterable<T>, keep: (item: T) => boolean): Generator<T> {
    for (const item of source) { if (!keep(item)) return; yield item; }
};
console.log([...take_while(runs, (run) => run < deadline)].length, runs.filter((run) => run < deadline).length); // 1 2
```

| Language | Lazy "runs before deadline" | Result on the fall-back sequence | What it costs |
| --- | --- | --- | --- |
| F# | `Seq.takeWhile` | 1 of 2 runs | nothing to write; the sortedness assumption is invisible |
| Rust | `Iterator::take_while` | 1 of 2 runs | same; `filter` needs a `take(n)` bound or it never ends |
| C++20 | `views::take_while` | 1 of 2 runs | same, plus the lambda's capture |
| TypeScript | no std `takeWhile`; a generator | 1 of 2 runs | a generator function of your own |

The four agree, which is the point: the bug is not in any combinator, it is in the sequence's contract. `filter` is correct on unsorted input but, over an infinite lazy source (Rust iterators, F# `Seq`, C++ views), never terminates; TypeScript's `Array.prototype.filter` is eager and cannot take an infinite source at all. `take_while` terminates but is only correct on sorted input. A schedule iterator that is "sorted by wall clock" is not sorted by instant across a fall-back hour, and Rust `croner` documents that it chose instant order precisely so that a forward search never goes backwards.

What would it take for a type to say "this iterator is sorted", and would you trust a library that claimed it?

# The security angle: a job that fires twice is a replay you scheduled yourself

Mode C on the Rust tip, running in the direction the languages do not help: "run at 01:30 daily" is a request for at-most-once, and no scheduler type in any of the four can express that. Leave out the idempotency check and the fall-back day performs the action twice:

```rust
// Rust (cron 0.17.0, chrono-tz 0.10.4)
let schedule = cron::Schedule::from_str("0 30 1 * * *").unwrap(); // "charge subscriptions daily at 01:30"
let start = Chicago.with_ymd_and_hms(2026, 10, 31, 12, 0, 0).unwrap();
let fires: Vec<DateTime<Tz>> = schedule.after(&start).take(3).collect();

// INSECURE: one charge per fire. The fall-back day fires twice, so it charges twice.
let charges_insecure = fires.len();

// FIXED: an idempotency key on the scheduled LOCAL date, recorded before charging.
let mut charged_dates: HashSet<chrono::NaiveDate> = HashSet::new(); // a DB unique constraint in real code
let charges_fixed = fires.iter().filter(|fire| charged_dates.insert(fire.date_naive())).count();
println!("{charges_insecure} fires, {charges_fixed} charges"); // 3 fires, 2 charges
```

The opposite failure is a job that silently never runs. Debian's `run-parts`, which runs `/etc/cron.daily`, skips any file name outside `^[a-zA-Z0-9_-]+$`: measured in a Debian 13 container, `backup.sh`, `bad~` and `with space` were skipped and only `backup` and `good_name` would run. A certificate-renewal or log-pruning script saved as `renew-certs.sh` is a security control that is installed, executable and dead.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `cron` fires 01:30 twice, skips 02:30 | nothing: the iterator is a plain `Iterator` | an idempotency key per (job, scheduled date), enforced by the database |
| C++ | a hand-rolled scheduler over `zoned_time` | `to_sys` throws on gaps and overlaps unless you pass `choose` | choosing `earliest` or `latest` deliberately, and the same idempotency key |
| F# / .NET | Cronos/Quartz schedules in a DST zone | `TimeZoneInfo.IsAmbiguousTime` and `IsInvalidTime` name the cases | checking them, or scheduling in UTC |
| TypeScript | `node-cron`-style libraries in a DST zone | `Temporal`'s `disambiguation: "reject"` forces a decision when used | using it; JS `Date` resolves both cases silently |

C++ is the control here because it is the only one whose `std::chrono` conversion refuses both DST cases by default (`nonexistent_local_time`, `ambiguous_local_time`, measured in part 1). Class: CWE-837 (Improper Enforcement of a Single, Unique Action) for the double run. The skipped job has no CWE that fits cleanly; it is a configuration failure that looks like success.

Which of your scheduled jobs moves money, sends a message, or revokes access, and what stops it from doing so twice on 2026-11-01?

# FAQ

**Is 12 AM noon?**
No: on a 12-hour clock 12 AM is midnight and 12 PM is noon. Measured in Node: en-US `hour12: true` prints `12:00 AM` / `12:00 PM` (cycle `h12`), `hourCycle: "h11"` prints `0:00 AM` / `0:00 PM`, and `h24` prints midnight as `24:00`. The same Node `Intl` `hour12: true` resolves to `h11` for ja-JP (midnight is "gozen 0:00") and `h12` for en-US, so the hour cycle is locale data. .NET parses `12:00 AM` as 00:00 and `12:00 PM` as 12:00; a hand-rolled `hour + 12` for PM turns 12 PM into 24.

**Does `cron.daily` run my `backup.sh`?**
Not on Debian: `run-parts` skips names containing a dot (and `~`, spaces), so `backup.sh` never runs and nothing reports it. Name it `backup`, or check with `run-parts --test /etc/cron.daily`, which lists what would run.

**Does `TZ=Asia/Tokyo` at the top of a crontab change when the jobs run?**
Depends on the daemon. Debian's `cron` uses it only for the commands' environment; the schedule stays in the daemon's zone. Fedora's `cronie` reads `CRON_TZ` for the schedule. systemd timers take the zone in the `OnCalendar=` expression itself: systemd.time(7) accepts `UTC` or an IANA zone name there (read from the man page, not run).

**Is Unix time affected by the Julian-to-Gregorian switch?**
No. Unix time, .NET `DateTime`, JS `Date` and C++ `sys_days` all use the proleptic Gregorian calendar, extending today's rules backwards forever. Historical records do not: `cal 9 1752` on macOS jumps from Wednesday the 2nd to Thursday the 14th (the British cutover), and .NET's `JulianCalendar` maps Julian 1752-09-03 to Gregorian 1752-09-14. A birth date from 1700s England stored in any of these types is off by 11 days unless someone converted it.

**Is GPS time the same as UTC?**
No: GPS time does not insert leap seconds, so it runs 18 s ahead of UTC since 2017 (part 1, C++ `gps_clock` on GCC 14). That is why the GPS week rollovers fell at GPS midnight on 1999-08-22 and 2019-04-07 but are reported as 1999-08-21 and 2019-04-06 UTC. Honda and Acura navigation units built 2004 to 2012 showed 2002 instead of 2022 in January 2022, an overflow of the same GPS epoch (per Wikipedia's GPS week rollover article, not measured).

**Is `P1D` the same as `PT24H`?**
Only when nothing says which day. JS `Temporal.Duration.compare` returns 0 for them without `relativeTo`, in JS `Temporal` `P1D` totals 23 hours relative to 2026-03-08 in Chicago, and Rust `jiff` keeps them distinct in arithmetic (part 1). .NET cannot tell them apart at all: `XmlConvert.ToTimeSpan "P1D"` and `"PT24H"` are both one `TimeSpan` day.

# Appendix A: Cloudflare DNS on 2017-01-01, a leap second that made a round trip take negative time

_Not part of the tip rotation. Added 2026-10-22, backing this part's thesis that every epoch is a number someone chose: UTC chose to insert a second, and the wall clock went backwards to fit it. A real incident, not folklore: the facts are from Cloudflare's own post-mortem, the Go design document it prompted, and Wikipedia, all in A.5. Every value in A.3 was printed by a real run (Go 1.24.2, Rust 1.95.0, C++20 on Apple clang 21, F# on .NET 8.0.8, Node 22.17.1)._

## A.1 What happened

A leap second was inserted at the end of 2016-12-31. Cloudflare's post-mortem timeline: "2017-01-01 00:00 UTC Impact starts", "2017-01-01 06:45 UTC Impact ends", and "at peak approximately 0.2% of DNS queries to Cloudflare were affected". The resolver measured upstream round-trip times as `rtt := time.Now().Sub(start)`, and the post notes that "`rtt` could be negative if time.Now() was earlier than `start`", which is what a wall clock does when a second is repeated. The negative value reached `rand.Int63n`, which "promptly panics if its argument is negative".

## A.2 What it changed

Go then had no monotonic clock in `time.Now()`. Russ Cox's design document for Go's monotonic time (proposal 12914) opens with it: "A Go program measuring a negative elapsed time during a leap second caused CloudFlare's recent DNS outage." Since Go 1.9, `time.Now()` carries a monotonic reading as well, and `Sub` uses it. The Go `time` docs: "The canonical way to strip a monotonic clock reading is to use t = t.Round(0)", and after that, subtraction is wall-clock again.

```go
// Go 1.24.2, measured: the panic, recovered
rtt := time.Duration(-5 * time.Millisecond) // what Sub returned across the repeated second
rand.Int63n(int64(rtt))                     // panic: invalid argument to Int63n
```

## A.3 What a backwards wall clock gives you in each language

| Language | Wall-clock "later minus earlier" when the clock stepped back 5 ms | The monotonic alternative |
| --- | --- | --- |
| Rust | `SystemTime::duration_since` returns `Err("second time provided was later than self")`: it cannot go negative silently | `Instant`; `duration_since` saturates to `0ns` |
| C++ | `system_clock` difference is `-5 ms`, a valid signed `duration` | `steady_clock` (`is_steady` is 1; `system_clock::is_steady` is 0) |
| F# / .NET | `DateTime` difference is `-00:00:00.0050000` | `Stopwatch` |
| TypeScript | `Date` difference is `-5` | `performance.now()` |

Rust is the only one whose wall-clock API makes the negative case a value you have to handle. In the other three, a negative duration is a number like any other until something downstream refuses it, as `Int63n` did.

## A.4 Back to the tips

Part 2's cron tip ran a job twice when the wall clock repeated an hour. Here the wall clock repeated one second, and a measurement went negative. The same rule covers both: schedules belong on the wall clock, and durations belong on a monotonic one.
