## Rust: Path::join with an absolute name throws the base away, and starts_with(root) still passes /srv/uploads/../etc/passwd

*Idioms and antipatterns*

**Did you know**

`upload_root.join(client_name)` reads like "put this file under the root", but when `client_name` is absolute the result is just `client_name`: `Path::new("/srv/uploads").join("/etc/passwd")` is `/etc/passwd`. The guard people add next, `joined.starts_with(upload_root)`, catches that case and misses the other one, because `starts_with` is lexical and component-wise: `/srv/uploads/../etc/passwd` starts with `/srv/uploads`, so it returns `true`. Nothing in `std::path` resolves `..` without touching the disk (`std::path::absolute` keeps it on purpose), so the dependable check is to accept only `Component::Normal` parts before joining.

**Show me**

```rust
use std::path::{Component, Path, PathBuf};

// Looks like "put the uploaded file under the root". It is not.
fn resolve_upload(upload_root: &Path, client_name: &str) -> PathBuf {
    upload_root.join(client_name) // an absolute client_name replaces upload_root
}

// Accept only plain names: no root, no "..", no ".".
fn join_inside(upload_root: &Path, client_name: &str) -> Option<PathBuf> {
    let client_path = Path::new(client_name);
    client_path
        .components()
        .all(|component| matches!(component, Component::Normal(_)))
        .then(|| upload_root.join(client_path))
}

fn main() {
    let upload_root = Path::new("/srv/uploads");
    for client_name in ["report.pdf", "/etc/passwd", "../etc/passwd"] {
        let joined = resolve_upload(upload_root, client_name);
        // The usual guard is lexical: starts_with never resolves ".."
        let guard_passes = joined.starts_with(upload_root);
        println!(
            "{client_name:>13} -> {:<27} guard {guard_passes:<5} join_inside {:?}",
            joined.display(),
            join_inside(upload_root, client_name)
        );
    }
}
```

Output on rustc 1.100.0:

```text
   report.pdf -> /srv/uploads/report.pdf     guard true  join_inside Some("/srv/uploads/report.pdf")
  /etc/passwd -> /etc/passwd                 guard false join_inside None
../etc/passwd -> /srv/uploads/../etc/passwd  guard true  join_inside None
```

**Why it matters**

Every service that stores an upload, reads a template, or serves a static file by a name from a request builds a path this way. The absolute-name case is the one people test, the guard catches it, and the `..` case walks straight past the same guard. C++ `std::filesystem::path::operator/` has exactly the same replace rule; Node.js `path.join` does the opposite and glues `/etc/passwd` under the root, but then normalizes `../etc/passwd` into `/srv/etc/passwd`, outside it.

**Chew on this**

Where in your services does a path from a request, a config file, or a database row meet `join` or `push`, and which of those sites would accept a name with a `..` in the middle? Would rejecting everything but `Component::Normal` break a client you cannot change?

**Sources**

- https://doc.rust-lang.org/std/path/struct.Path.html#method.join
- https://doc.rust-lang.org/std/path/struct.PathBuf.html#method.push
- https://doc.rust-lang.org/std/path/struct.Path.html#method.starts_with
- https://doc.rust-lang.org/std/path/fn.absolute.html

**Gotchas**

- `PathBuf::push("/tmp/x")` on `/srv/uploads` also replaces: the buffer becomes `/tmp/x` (measured).
- `Path::starts_with` compares whole components: `Path::new("/srv/uploads2/x").starts_with("/srv/uploads")` is `false`, while the same strings with `str::starts_with` give `true`.
- `std::path::absolute("/srv/uploads/../etc/passwd")` returns it unchanged; only `fs::canonicalize` resolves `..`, and it fails when the file does not exist yet, which is every new upload.
- `components()` drops an interior `.` but keeps `..` as `ParentDir`: `/srv/./uploads/../etc` gives `[RootDir, Normal("srv"), Normal("uploads"), ParentDir, Normal("etc")]`.
- The empty name passes `join_inside`: `""` has no components, so `all` is vacuously true and the result is `Some("/srv/uploads/")`, the root directory itself. Reject empty names separately.

## C++: operator<< prints a uint8_t as a character and std::format prints it as a number, so moving a log line to std::format turns A into 65

*Stdlib and ecosystem gems*

**Did you know**

`std::uint8_t` and `std::int8_t` are `unsigned char` and `signed char` on GCC, Clang and MSVC, and `std::ostream` has dedicated overloads for both that insert a character. So `std::cout << retry_count` with the value 65 prints `A`, and an `int8_t` of -1 writes the raw byte `0xff` into your log. C++20 `std::format` went the other way: its character formatter covers only `char` and `wchar_t`, so the same two values print as `65` and `-1`. Rewriting a log line from `<<` to `std::format` (or C++23 `std::print`) silently changes what every 8-bit field prints. `std::format` needs C++20 and is listed on cppreference for GCC libstdc++ 13, Clang libc++ 17 (partial from 14), and MSVC 19.29.

**Show me**

```cpp
// C++20 for std::format
#include <cstdint>
#include <format>
#include <iostream>
#include <sstream>

int main() {
    std::uint8_t retry_count = 65;      // uint8_t is unsigned char on every compiler here
    std::int8_t temperature_delta = -1; // and int8_t is signed char

    // << picks the character overload: prints "A 65"
    std::cout << "ostream: " << retry_count << " " << +retry_count << "\n";
    // std::format treats both as integers: prints "65 A -1"
    std::cout << std::format("format:  {} {:c} {}\n", retry_count, retry_count, temperature_delta);

    std::ostringstream log_line;
    log_line << "delta=" << temperature_delta; // writes the raw byte 0xff, not "-1"
    std::cout << "log bytes: " << log_line.str().size() << "\n"; // 7

    std::istringstream config_input("42");
    std::uint8_t parsed_retries = 0;
    config_input >> parsed_retries; // reads one character, the 4
    std::cout << std::format("parsed: {}\n", parsed_retries); // 52
}
```

Output, identical on g++ 16.2.0 and Debian clang 19.1.7 (libstdc++), `-std=c++20` and `-std=c++23`:

```text
ostream: A 65
format:  65 A -1
log bytes: 7
parsed: 52
```

**Why it matters**

Protocol fields, status codes, retry counts and sensor deltas are exactly the values people store in 8-bit types, and they are exactly what ends up in a log line. With `<<` a zero byte writes a NUL into a text log and a reading of 10 writes a newline; with `std::format` the same field reads as a number, so a log parser or a dashboard built on the old output breaks on the day of the refactor. Rust has no such split: `u8` and `i8` always `Display` as numbers, and a character needs an explicit `as char`.

**Chew on this**

Which of your structs carry a `uint8_t` that is logged with `<<` today, and does anything downstream (a grep, a log parser, an alert rule) depend on the character it prints? When the line moves to `std::format`, who notices first?

**Sources**

- https://en.cppreference.com/w/cpp/io/basic_ostream/operator_ltlt2
- https://en.cppreference.com/w/cpp/utility/format/formatter
- https://en.cppreference.com/w/cpp/compiler_support/20

**Gotchas**

- Reading goes wrong too: `std::istringstream("42") >> parsed_retries` into a `uint8_t` reads one character, so the value is 52 (the code of `4`), not 42, and the stream reports success.
- Unary plus is the usual `<<` fix: `+retry_count` promotes to `int` and prints `65`.
- `std::format("{:c}", retry_count)` prints `A` and `std::format("{:d}", char{65})` prints `65`: the presentation type overrides the default in both directions.
- `std::to_string(retry_count)` prints `65`, because it promotes to `int`; only the stream overloads treat it as a character.
- `std::byte` is not formattable at all: `std::formattable<std::byte, char>` is `false` in C++23 on both compilers here, so it needs `std::to_integer<int>` first.

## F#: Seq.cache held 47.6 MB for a million short strings, read them back no faster than regenerating them, and keeps the source open if you stop early

*Perf and memory model*

**Did you know**

`Seq.cache` stores every element it has produced for as long as the cached sequence is reachable, so it is a growing buffer, not a memo of "the computation". On .NET 11 (FSharp.Core 11.0, F# 11), one pass over a million `string row` values left 47,585,232 bytes on the heap, against 3,136 bytes for the uncached sequence. It also costs per element: summing 10 million `int64` took 175 ms as a plain `seq`, 394 ms on the first pass through the cache and 187 ms on the second, so for a cheap source the cached replay was slower than recomputing. And a cache read only part of the way never finishes its source, so a `finally` or `use` inside it does not run.

**Show me**

```fsharp
// F# 11, FSharp.Core 11, .NET 11: dotnet fsi show.fsx
open System

let heap_bytes () =
    GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect()
    GC.GetTotalMemory(true)

let before_cache = heap_bytes ()
// Looks like "remember the source so a second pass is cheap"
let cached_rows = Seq.cache (seq { for row in 1 .. 1_000_000 -> string row })
cached_rows |> Seq.length |> ignore
printfn "held by the cache: %d bytes" (heap_bytes () - before_cache)
GC.KeepAlive cached_rows

// A cache read only part of the way never finishes its source
let audit_rows = seq { try yield! [ 1; 2; 3; 4 ] finally printfn "source closed" }
let cached_audit = Seq.cache audit_rows
cached_audit |> Seq.take 2 |> Seq.toList |> printfn "cached take 2: %A" // no "source closed"
audit_rows |> Seq.take 2 |> Seq.toList |> printfn "plain take 2: %A"   // "source closed" first
```

Output (dotnet fsi, SDK 11.0 image):

```text
held by the cache: 47585232 bytes
cached take 2: [1; 2]
source closed
plain take 2: [1; 2]
```

**Why it matters**

The usual reason to reach for `Seq.cache` is to stop a lazy `seq` re-running its work on every enumeration. It does that, but the price is the whole materialized sequence pinned for the cached value's lifetime, plus a slower first pass, and in a long-running service a cached value stored in a module-level `let` or a long-lived object is never released. `Array.ofSeq` gives the same "evaluate once" with a flat array (the 10-million sum over an array took 4 ms) and makes the memory cost visible in the type. Rust has no `Seq.cache` in `std`; the nearest shapes are `collect::<Vec<_>>()`, which is the array choice, and `Peekable`, which buffers a single element.

**Chew on this**

Which `Seq.cache` calls in your code wrap a sequence that is read once, or read only part of the way? If a cached sequence wraps a file or a database reader, what keeps that handle open between the first `take` and the end of the process?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/sequences

**Verified**

The SDK 11.0 image is Ubuntu 26.04 (no Debian .NET image), and the timings come from `dotnet fsi`, not a Release build.

**Gotchas**

- The source does run only once: two `Seq.sum` calls ran a counting source twice as a plain `seq` and once through `Seq.cache`.
- Partial reads leak the source: after `Seq.take 2` on the cached sequence, its `finally` ran only when a later full read reached the end; `Seq.take 2` on the plain sequence ran it at once.

## TypeScript: Node 26.12.1 made TLS refuse 0x7f.0.0.1 as a host name, which 26.12.0 matched against a *.0.0.1 certificate while the socket dialled 127.0.0.1

*New discoveries and currently popular patterns*

**Did you know**

Node.js 26.12.1, a security release of 2026-10-21 (now in 26.13.x LTS "Lithium"), lists "tls: reject non-canonical IP addresses" under CVE-2026-106069 and CVE-2026-106072 ([release notes](https://github.com/nodejs/node/releases/tag/v26.12.1)). The gap it closes: `net.isIP("0x7f.0.0.1")` is `0`, so `tls.checkServerIdentity` treated that spelling as a DNS name and matched it against DNS altnames, while `dns.lookup` resolves the same string to `127.0.0.1`. On Node 26.12.0 a certificate for `DNS:*.0.0.1` was accepted for `0x7f.0.0.1` and `0177.0.0.1`; on 26.13.1 every non-canonical spelling (`127.1`, `0x7f.0.0.1`, `0177.0.0.1`, `127.000.000.001`, `2130706433`) fails with `ERR_TLS_CERT_ALTNAME_INVALID` and the reason "Host is a non-canonical IP address".

**Show me**

```typescript
// TypeScript, run directly with Node 26 type stripping: node identity.ts
import { checkServerIdentity, type PeerCertificate } from "node:tls";
import { isIP } from "node:net";
import { lookup } from "node:dns/promises";

// Only the two fields checkServerIdentity reads. The cast is the test fixture, not production code.
const wildcard_cert = { subject: {}, subjectaltname: "DNS:*.0.0.1" } as PeerCertificate;

for (const target_host of ["0x7f.0.0.1", "0177.0.0.1", "127.0.0.1"]) {
    // Returns the error instead of throwing it: a custom callback that drops it accepts everything.
    const identity_error: Error | undefined = checkServerIdentity(target_host, wildcard_cert);
    const { address: dialed_address } = await lookup(target_host);
    console.log(target_host, "isIP=" + isIP(target_host), "dials", dialed_address, "->", identity_error?.message ?? "ACCEPTED");
}
```

Node 26.12.0, then Node 26.13.1 (both run with `node identity.ts`; type-checked with tsc 7.0.2 and @types/node 26.6.6 under `--strict`):

```text

127.0.0.1 isIP=4 dials 127.0.0.1 -> Hostname/IP does not match certificate's altnames: IP: 127.0.0.1 is not in the cert's list:
```

**Why it matters**

Server code passes host strings from config and from callers straight into `https.request({ hostname })`, `tls.connect({ host })` and webhook dispatchers. If an attacker can choose that string, an inet_aton-style spelling made the identity check and the address you actually connected to disagree, which is the kind of mismatch that turns an SSRF filter or a pinned-certificate rule into a formality. Rust's `rustls` takes a typed `ServerName`, so the string has to be parsed into an IP or a DNS name before any check runs; the Node.js API takes a bare `string`, and the TypeScript types cannot tell the two apart.

**Chew on this**

Which of your outbound calls take a host from somewhere other than a hard-coded constant, and is it a `URL` object or a raw `hostname` string by the time it reaches Node? Which of your containers still run a Node image older than 26.12.1, 24.x or 22.x patch included?

**Sources**

- https://github.com/nodejs/node/releases/tag/v26.12.1
- https://nodejs.org/api/tls.html#tlscheckserveridentityhostname-cert

**Verified**

The nodejs.org API page was not fetched (outside the allowed hosts); the two CVE ids are quoted from the release page, which says nothing about which Node 24 and 22 releases carry the fix. The Rust `rustls` comparison rests on its documentation and was not compiled here.

**Gotchas**

- `new URL("https://0x7f.0.0.1/").hostname` is already `127.0.0.1`: the WHATWG URL parser canonicalizes all four spellings tried (`0x7f.0.0.1`, `0177.0.0.1`, `127.1`, `2130706433`), so code that goes through `fetch(url)` or a `URL` never handed the odd spelling to TLS; raw `hostname` options did.
- `checkServerIdentity` returns its error instead of throwing it (`Error | undefined`), so a custom `checkServerIdentity` callback that calls it and forgets to return the result accepts every certificate.
- With a certificate that holds only IP altnames, 26.12.0 already rejected these spellings, with the misleading reason "Cert does not contain a DNS name"; the accepted case needs a DNS altname that matches the spelling, such as a wildcard.
- `::ffff:127.0.0.1` is canonical IPv6 (`isIP` gives `6`), so it is checked as an IP and does not match a certificate listing `127.0.0.1`, on both versions.

# The functional angle: "evaluate once" is a type in Rust and a call in F#, and only the call can hide what it keeps

This draws on the F# tip (`Seq.cache`) and, for the comparison, on the lazy sequences of the other three languages. It runs one shape: a lazy pipeline that two consumers need to read.

In F#, laziness and replay are the same type: a `seq<'T>` can be enumerated any number of times, and each enumeration re-runs the source. `Seq.cache` changes that without changing the type, so the reader of a `seq<string>` cannot tell whether it re-runs the work or holds 47.6 MB.

```fsharp
// F#: both have the type seq<string>
let rows_recomputed = seq { for row in 1 .. 1_000_000 -> string row }
let rows_kept = Seq.cache rows_recomputed // one call, same type, now a buffer
```

In Rust the choice cannot hide, because an `Iterator` is consumed by the first pass (`sum` and `count` take `self` by value), so a second reader needs either a new iterator or a collection, and the collection is a different type:

```rust
// Rust: the second consumer forces the decision into the types
let rows_kept: Vec<String> = (1..=1_000_000).map(|row| row.to_string()).collect();
let total_length: usize = rows_kept.iter().map(String::len).sum();
```

| Language | "Evaluate once" form | What it costs |
| --- | --- | --- |
| F# | `Seq.cache` (same `seq` type) or `Array.ofSeq` | measured: 47,585,232 bytes kept for 1M rows; first pass 394 ms against 175 ms uncached; replay 187 ms against 4 ms for an array |
| Rust | `collect::<Vec<_>>()` | a `Vec` in the signature; an iterator cannot be replayed at all, so there is no hidden middle ground (not measured today) |
| C++ | `std::ranges::to<std::vector>()` (C++23) | a view re-runs its adaptors on every iteration, as the [2026-10-27 C++ tip](2026-10-27-extra-7-of-12.md) measured; the vector is the only cache in std (not measured today) |
| TypeScript | `Array.from(generator)` | a generator is single-use like a Rust iterator, but silently: the second loop sees nothing instead of failing to compile ([2026-10-27 TypeScript tip](2026-10-27-extra-7-of-12.md)) |

The asymmetry worth noticing: F# is the only one of the four where "replayable" is the default and "kept in memory" is invisible in the type. The thread left open: if a function in your code returns `seq<'T>`, does its signature tell the caller whether iterating twice costs time or costs memory?

# The security angle: the string you checked is not the string you used

This draws on the Rust tip and the TypeScript tip, and it runs in the insecure direction: both are cases where a check passed on one reading of a string while the operation used another. In the Rust tip the check is lexical and the file system resolves `..`; in the TypeScript tip the certificate check read `0x7f.0.0.1` as a DNS name and the resolver read it as `127.0.0.1`. The class is CWE-22 (path traversal) and CWE-41 (improper resolution of path equivalence) for the first, and CWE-297 (certificate with host mismatch) for the second.

The C++ version of the path half, measured with Debian clang 19.1.7:

```cpp
// C++20: looks like the Rust guard, has the same hole
const std::filesystem::path upload_root = "/srv/uploads";
const std::filesystem::path joined = upload_root / client_name;
// "/etc/passwd"   -> /etc/passwd                  (operator/ replaces, like Rust join)
// "../etc/passwd" -> /srv/uploads/../etc/passwd   (lexically_normal(): /srv/etc/passwd)
```

And the TypeScript version on Node.js, measured on Node.js 26.13.1, which fails the other way round:

```typescript
// TypeScript on Node.js: path.join never replaces, it normalizes
path.join("/srv/uploads", "/etc/passwd");   // "/srv/uploads/etc/passwd"
path.join("/srv/uploads", "../etc/passwd"); // "/srv/etc/passwd", outside the root
path.resolve("/srv/uploads", "/etc/passwd"); // "/etc/passwd", like Rust join
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `join` with an absolute name replaces the root; `starts_with` passes `..` | nothing in `std::path` resolves `..` without the disk; `Component` makes the parts inspectable | accept only `Component::Normal` parts, and reject the empty name |
| C++ | `operator/` replaces on an absolute name; `..` survives the join | `lexically_normal` resolves `..` on the string, without the disk | compare after normalizing, and still reject symlinks if the tree has any |
| TypeScript (Node.js) | `path.join` normalizes `..` out of the root; before 26.12.1, TLS matched an inet_aton spelling as a DNS name | since 26.12.1, non-canonical IP spellings fail `checkServerIdentity`; `URL` canonicalizes them | check the normalized result is under the root; pass hosts as a `URL`, and run 26.12.1 or later |
| F# (.NET) | `Path.Combine` follows the same replace rule as Rust `join` (documentation, not measured today) | `Path.GetFullPath` resolves `..` on the string | same as C++: normalize, then compare with an ordinal, case-aware prefix check |

The control here is Rust, because it is the one language where the dependable fix is a pure function over parsed components rather than a string comparison. The thread to take home: where else in your code does a validator and the call that follows it parse the same input twice, with two different parsers?
