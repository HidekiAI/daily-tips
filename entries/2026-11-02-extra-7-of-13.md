Not part of the rotation. Part 7 of the thirteen-part special on real incidents: the [PHE delayed reporting of COVID-19 cases](https://www.gov.uk/government/news/phe-statement-on-delayed-reporting-of-covid-19-cases) in England, 25 September to 2 October 2020. Each tip below is a write or a load that takes less than it was given and still reports success.

# What happened

**Bug class:** Bohrbug in this special's classification (inferred: PHE gives a file-size limit and cases "not included"; it does not say how the data was cut or what the load reported). The anti-pattern the tips below take from it is a bounded load whose only signal of truncation is a number nobody reads.

From "PHE statement on delayed reporting of COVID-19 cases" (Public Health England, published 4 October 2020, updated 5 October 2020):

```text
A technical issue was identified overnight on Friday 2 October in the data load
process that transfers COVID-19 positive lab results into reporting dashboards.
After rapid investigation, we have identified that 15,841 cases between 25 September
and 2 October were not included in the reported daily COVID-19 cases.
```

```text
The technical issue was caused by the fact that some files containing positive test
results exceeded the maximum file size that takes these data files and loads then
into central systems. A rapid mitigation has been put in place that splits large files ...
```

PHE adds that "over 75% (11,968)" of the cases fell in the last few days, and that all of them were passed to contact tracing "by 1am on 3 October". PHE's statement does not name the tool or the limit. The widely repeated detail, a legacy Excel `.xls` file and its row limit, comes from press reports, not from PHE, so this part uses 65,536 rows only as the illustrative limit.

## Rust: `Write::write` may take only part of its input and report it only in the returned count, and `write_all` is the call that refuses

*Stdlib and ecosystem gems*

**Did you know**

`std::io::Write::write` is allowed to write fewer bytes than it was given and still return `Ok`: writing 20 bytes into an 8-byte slice returned `Ok(8)`. The truncation is reported only by that number, so code that discards it has the shape of the press-reported PHE bug. `write_all`, and the `write!` macro built on it, treats "could not take everything" as an error, `WriteZero`. Measured on rustc 1.99.1.

**Show me**

```rust
// rustc 1.99.1, Debian.
use std::io::Write;

fn main() {
    let lab_result_bytes: &[u8] = b"case-1,case-2,case-3"; // 20 bytes
    let mut central_loader_buffer = [0u8; 8];                 // the loader's fixed limit

    // write() is allowed to take only part of the input, and says so only in its return value.
    let accepted_byte_count = (&mut central_loader_buffer[..]).write(lab_result_bytes).unwrap();
    println!("{accepted_byte_count} of {}", lab_result_bytes.len()); // 8 of 20, and the call returned Ok

    // write_all() treats "could not take it all" as an error.
    let mut strict_loader_buffer = [0u8; 8];
    println!("{:?}", (&mut strict_loader_buffer[..]).write_all(lab_result_bytes).map_err(|write_failure| write_failure.kind())); // Err(WriteZero)
}
```

**Why it matters**

A short write is normal for sockets and pipes, which is why `write` returns a count; every caller that wants all of it must loop or use `write_all`. Code that calls `write` once and checks only for `Err` treats a partial write as a full one. `#[must_use]` on `io::Result` makes ignoring the `Result` a warning, but `let _ = writer.write(...)?` and an unread count are both silent.

**Chew on this**

Which of your writers call `write` rather than `write_all`, and does each caller read the returned count? Which of your buffers are fixed-size because a limit was chosen once and never revisited?

**Sources**

- https://doc.rust-lang.org/std/io/trait.Write.html#tymethod.write
- https://doc.rust-lang.org/std/io/trait.Write.html#method.write_all

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1. The `#[must_use]` remark is from the documentation of `Result` and was not compiled today.

**Gotchas**

- `write!(cursor, "case-{},positive", 15841)` into an 8-byte slice returned `Err(WriteZero)`: the formatting macro uses `write_all`, so it refuses where a bare `write` would have cut.
- An `&mut [u8]` writer advances the slice past what it wrote: writing 3 bytes and then 5 into an 8-byte buffer filled it as `abcdefgh` and left 0 bytes, so a third `write` takes nothing and returns `Ok(0)`.

## C++: `snprintf` cuts a row to fit and returns the length it wanted, and neither compiler warns when only the data is too long

*Idioms and antipatterns*

**Did you know**

`snprintf` never writes past the buffer: given a 30-byte row and a 16-byte buffer it stored `"case-15841,posi"` (15 bytes plus the terminator) and returned 30, the length it needed. The return value is the only sign of the cut. GCC's `-Wformat-truncation` and clang's "will always be truncated" warning fire only when the format text itself is too long; with `"%s"` of runtime data, both compilers reported 0 warnings at `-O2 -Wall -Wextra`. Measured on Debian clang 19.1.7 and GCC 16.2 in Docker (C++20); Apple clang 21 gave the same result.

**Show me**

```cpp
// C++20, Debian clang 19.1.7 and GCC 16.2 (Docker): same output, no warnings.
#include <cstdio>
#include <cstring>

int main(int argument_count, char** arguments) {
    char lab_row_buffer[16];  // the loader's fixed limit
    const char* lab_row = argument_count > 1 ? arguments[1] : "case-15841,positive,2020-10-02";

    // snprintf never overruns the buffer: it cuts the row, and returns the length it wanted.
    int needed_byte_count = std::snprintf(lab_row_buffer, sizeof lab_row_buffer, "%s", lab_row);
    std::printf("\"%s\" kept %zu, needed %d\n", lab_row_buffer, std::strlen(lab_row_buffer), needed_byte_count);
    // "case-15841,posi" kept 15, needed 30: the only sign of the cut is needed_byte_count >= sizeof lab_row_buffer
}
```

**Why it matters**

`snprintf` replaced `sprintf` because it cannot overflow, and that safety is exactly what makes truncation quiet: the program stays well-defined and the data is simply shorter. Rust's `write` has the same contract, as the Rust tip showed, but Rust's formatting macros refuse instead of cutting.

**Chew on this**

How many of your `snprintf` calls compare the return value with the buffer size? If a cut row had to be an error, which of your log lines, keys or file names would start failing?

**Sources**

- https://en.cppreference.com/w/cpp/io/c/fprintf
- https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html#index-Wformat-truncation

**Verified**

Compiled with `-std=c++20 -Wall -Wextra -O2` on Debian clang 19.1.7 (`debian-clang:trixie`) and GCC 16.2.0 (`gcc:latest`), both in Docker. Additionally checked on macOS (Apple clang 21.0.0, arm64): same output and warnings. The warning cases were a separate probe with a constant format string longer than the buffer.

**Gotchas**

- With a constant format whose fixed text alone overflows (`"case-%d,positive,%s"` into 16 bytes), both compilers warned, which makes the warning look like coverage. It stops the moment the overflowing part comes from data.
- A negative return means an error occurred, not a truncation, so cppreference's complete-output test is "nonnegative and less than `buf_size`": `needed_byte_count >= 0 && needed_byte_count < size`.

## F#: `Seq.truncate 65536` keeps the first 65,536 rows of 70,000 without a word, and `Seq.take` is the version that refuses

*Stdlib and ecosystem gems*

**Did you know**

F# has two ways to take the first n elements, and they disagree about too-short and too-long input. `Seq.truncate 65536` on 70,000 rows returned 65,536 and dropped 4,464 with no error, the shape of the press-reported PHE load in one call. `Seq.take` with more than the sequence holds threw `InvalidOperationException`. `List.truncate` and `Array.truncate` behave like `Seq.truncate`. Measured on .NET 10.0.403.

**Show me**

```fsharp
// SDK 10.0.403 (F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14).
// 70,000 lab rows arrive; the old file format holds 65,536 (the limit the press reported).
let lab_row_numbers = Seq.init 70000 id

let loaded_row_list = lab_row_numbers |> Seq.truncate 65536 |> Seq.toList
printfn "%d rows loaded, %d dropped, no error" loaded_row_list.Length (70000 - loaded_row_list.Length)   // 65536 rows loaded, 4464 dropped

// Seq.take is the version that refuses when it cannot deliver what was asked.
printfn "%s" (try string (lab_row_numbers |> Seq.take 70001 |> Seq.length) with take_failure -> take_failure.GetType().Name) // InvalidOperationException
```

**Why it matters**

The names read alike in review, and `truncate` is usually picked because it "never throws". That is the right choice for a preview and the wrong one for a load whose job is to carry every row. The C++ tip above has the same split between a call that cuts and a check nobody wrote.

**Chew on this**

Where in your pipelines is a `truncate`, `Take` or `LIMIT` that was meant as a safety cap, and would anyone notice the day real data passed it? Should a cap that is hit be a log line, a metric, or a failure?

**Sources**

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-seqmodule.html#truncate
- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-collections-seqmodule.html#take

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0` (Ubuntu 24.04, not Debian).

**Gotchas**

- `Seq.take` refuses only when the sequence is consumed: building `lab_row_numbers |> Seq.take 70001` raised nothing, and the `InvalidOperationException` came at `Seq.length`. A pipeline that is never fully enumerated never reports it.
- `Seq.take 65536` on 70,000 rows also returned 65,536 without error: `take` refuses too few elements, not too many, so it does not detect the PHE case either. Only a length check against the source does.

## TypeScript: `TextEncoder.encodeInto` fills what fits and reports the rest only in its result object

*Stdlib and ecosystem gems*

**Did you know**

`TextEncoder.encodeInto(text, buffer)` writes as much of the text as fits and returns `{ read, written }`; encoding 20 characters into an 8-byte `Uint8Array` returned `{ read: 8, written: 8 }`, with no exception. The 12 characters that did not fit are reported only as the gap between `read` and the text's length. A wrapper that throws when `read < source_text.length` turns the silent cut into an error. Measured on Node 26.13.0.

**Show me**

```ts
// TypeScript, Node 26.13.0 (LTS, strips types natively), tsc 7.0.2 --strict.
const lab_result_text = "case-1,case-2,case-3"        // 20 characters
const central_loader_buffer = new Uint8Array(8)          // the loader's fixed limit

// encodeInto fills what fits and reports the rest only in its result object.
const encode_into_counts = new TextEncoder().encodeInto(lab_result_text, central_loader_buffer)
console.log(encode_into_counts, lab_result_text.length)          // { read: 8, written: 8 } 20

// The check that turns a silent cut into an error.
const fn_encode_all = (source_text: string, destination_bytes: Uint8Array): number => {
    const { read, written } = new TextEncoder().encodeInto(source_text, destination_bytes)
    if (read < source_text.length) throw new RangeError(`only ${read} of ${source_text.length} characters fit`)
    return written
}
try { fn_encode_all(lab_result_text, new Uint8Array(8)) } catch (encode_failure) { console.log((encode_failure as Error).message) } // only 8 of 20 characters fit
```

**Why it matters**

`encodeInto` exists so you can encode into a preallocated buffer without a copy, the kind of fixed limit a loader has, often chosen for the same reason. The type of the result says nothing about whether it was complete: `{ read: number; written: number }` is the same type for a full and a partial write.

**Chew on this**

Which of your fixed-size buffers or batch limits were sized for last year's volume? Where would a partial encode be noticed, by a length check, a checksum, or a user?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/API/TextEncoder/encodeInto
- https://nodejs.org/api/util.html#textencoderencodeintosrc-dest

**Verified**

Run on Node 26.13.0, the current LTS (`node:lts-trixie`, Debian), and type-checked with tsc 7.0.2 `--strict`.

**Gotchas**

- Assigning a smaller `length` to an array drops the tail with no error: `rows.length = 2` on four rows left `[ 'a', 'b' ]`.
- `read` counts UTF-16 code units of the source and `written` counts bytes of the destination: for `"caf\u00e9-\u{1F600}"` (length 7) everything fit with `read` 7 and `written` 10, so compare `read` with `source_text.length`, never `written`.

# The functional angle: a bounded load is total only if "did not fit" is one of its results

Draws on all four tips. Each tip's truncating call returns a value that looks complete; the functional form makes the partial case a different value, so the caller cannot forget to look.

```fsharp
// F#: a load that either takes every row or says how many did not fit.
let fn_load_all (row_limit: int) (lab_row_numbers: int list) : Result<int list, int> =
    if lab_row_numbers.Length <= row_limit then Ok lab_row_numbers else Error (lab_row_numbers.Length - row_limit)
printfn "%A" (fn_load_all 65536 (List.init 70000 id) |> Result.map List.length)   // Error 4464
```

```rust
// Rust: the same shape, Err carries the number of rows that would be lost.
const XLS_ROW_LIMIT: usize = 65_536; // rows an .xls worksheet holds
fn load_all(row_limit: usize, lab_row_numbers: &[u32]) -> Result<&[u32], usize> {
    if lab_row_numbers.len() <= row_limit { Ok(lab_row_numbers) } else { Err(lab_row_numbers.len() - row_limit) }
}
fn main() {
    let lab_row_numbers: Vec<u32> = (0..70_000).collect();
    println!("{:?}", load_all(XLS_ROW_LIMIT, &lab_row_numbers).map(|loaded_row_slice| loaded_row_slice.len())); // Err(4464)
}
```

```cpp
// C++23: snprintf's return value turned into a result type.
#include <cstdio>
#include <expected>
#include <string>
std::expected<std::string, int> format_row(const char* lab_row, std::size_t row_buffer_size) {
    std::string formatted_row_buffer(row_buffer_size, '\0');
    int needed_byte_count = std::snprintf(formatted_row_buffer.data(), row_buffer_size, "%s", lab_row);
    if (needed_byte_count < 0 || static_cast<std::size_t>(needed_byte_count) >= row_buffer_size) return std::unexpected(needed_byte_count);
    formatted_row_buffer.resize(static_cast<std::size_t>(needed_byte_count));
    return formatted_row_buffer;
}
int main() {
    constexpr std::size_t ROW_BUFFER_BYTES = 16;
    std::expected<std::string, int> row_format_attempt = format_row("case-15841,positive,2020-10-02", ROW_BUFFER_BYTES);
    std::printf("%s %d\n", row_format_attempt.has_value() ? "ok" : "refused, needed", row_format_attempt.has_value() ? 0 : row_format_attempt.error()); // refused, needed 30
}
```

```ts
// TypeScript: a tagged result instead of a silently shortened array.
type LoadResult = { ok: true; lab_row_numbers: number[] } | { ok: false; dropped: number }
const XLS_ROW_LIMIT = 65536 // rows an .xls worksheet holds
const fn_load_all = (row_limit: number, lab_row_numbers: number[]): LoadResult =>
    lab_row_numbers.length <= row_limit ? { ok: true, lab_row_numbers } : { ok: false, dropped: lab_row_numbers.length - row_limit }
const lab_rows_load_outcome = fn_load_all(XLS_ROW_LIMIT, Array.from({ length: 70000 }, (_, row_index) => row_index))
console.log(lab_rows_load_outcome.ok ? lab_rows_load_outcome.lab_row_numbers.length : `refused, ${lab_rows_load_outcome.dropped} rows would be dropped`) // refused, 4464 rows would be dropped
```

Each was run: F# on .NET 10.0.403, Rust on rustc 1.99.1, C++ on GCC 16.2 and Debian clang 19.1.7 (`-std=c++23`, no warnings), TypeScript on Node 26.13.0 (tsc 7.0.2 `--strict` clean), with the outputs in the comments.

The shape is the same as [part 6's lookup](2026-11-02-extra-6-of-13.md#the-functional-angle-a-lookup-is-a-partial-function-and-the-default-is-a-decision-made-far-from-the-data): a partial operation made total by giving the failure its own result.

| Language | Call that cuts quietly | Where the cut is reported | Total form |
| --- | --- | --- | --- |
| F# | `Seq.truncate`, `List.truncate` | nowhere | `Result<_, int>` carrying the rows dropped |
| Rust | `Write::write` | the returned byte count | `write_all`, or a `Result` like the one above |
| C++ | `snprintf` | the return value, if compared | `std::expected` built from the return value |
| TypeScript | `encodeInto`, `array.length = n` | `read` in the result object | a tagged result |

F# is the baseline here because it ships both a cutting and a refusing version side by side (`truncate` and `take`), and even the refusing one does not detect too much input.

Which of your pipeline stages would you change first if every cap had to return how much it dropped?

# The security angle: a truncated value is a different value

Draws on the C++ and TypeScript tips, with Rust and F# as controls. Runs in both directions: Rust's `write_all` and F#'s `Seq.take` refuse some truncations, and none of the four stops a truncated value from being used as if it were whole.

```ts
// TypeScript. Looks like a fixed-width user field. Two different users become one key.
const fn_fixed_width_key = (user_name: string): string => {
    const fixed_width_field_bytes = new Uint8Array(8)
    const { written } = new TextEncoder().encodeInto(user_name, fixed_width_field_bytes)
    return new TextDecoder().decode(fixed_width_field_bytes.subarray(0, written))
}
console.log(fn_fixed_width_key("operator-alice"), fn_fixed_width_key("operator-bob")) // operator operator
```

The class is [CWE-222](https://cwe.mitre.org/data/definitions/222.html), truncation of security-relevant information: the cut key no longer identifies its user, and any check keyed on it treats `operator-alice` and `operator-bob` as one.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | `encodeInto` cuts a key to the buffer | reports `read` and `written` | compare `read` with the input length |
| C++ | `snprintf` cuts a key to the buffer | returns the needed length | compare it with the buffer size |
| Rust | `write` cuts into a fixed slice | `write_all` refuses | use `write_all` for keys |
| F# | `Seq.truncate` drops the tail | `Seq.take` refuses too few, not too many | check the length against the source |

TypeScript is the baseline because its encoder reports the cut in a field whose type is identical for complete and partial results. The sample was run on Node 26.13.0.

Which of your identifiers are stored in a fixed-width field, and what happens when two of them share a prefix that fills it?
