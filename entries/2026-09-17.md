# Daily Tips: 2026-09-17

## Rust: Nightly's borrow checker went flow-sensitive, and NLL's most-hit false positive is gone

*New discoveries and currently popular patterns*

**Did you know**

On 2026-08-04 the project enabled Polonius Alpha as the default borrow checker
on nightly, with stabilization aimed at before the end of 2026. The one thing it
adds over NLL is flow-sensitive checking of outlives relationships, which means
the canonical `get_mut_or_default` shape finally compiles. NLL's analysis is
flow-insensitive: a borrow returned from one `match` arm is treated as live for
the whole function, including the arm that provably does not hold it. If a crate
of yours breaks on nightly, `-Zpolonius=off` puts the old checker back.

**Show me**

```rust
use std::collections::HashMap;
use std::hash::Hash;

// Verbatim from the announcement post. Rejected by NLL, accepted by Polonius Alpha.
fn get_mut_or_default<'r, K: Hash + Eq + Copy, V: Default>(
    map: &'r mut HashMap<K, V>,
    key: K,
) -> &'r mut V {
    match map.get_mut(&key) {
        Some(value) => value,      // this arm's borrow is what NLL propagates
        None => {
            map.insert(key, V::default()); // <- NLL: "second mutable borrow occurs here"
            map.get_mut(&key).unwrap()
        }
    }
}

// The smaller demonstration of the same defect: a reborrow that only one
// branch returns.
fn reborrow(a: &mut u8) -> &mut u8 {
    let b = &mut *a;
    if true { b } else { a }   // NLL: `*a` borrowed twice; Polonius Alpha: fine
}
```

Actual stable output here (rustc 1.95.0, edition 2024), which is the diagnostic
you have been trained to route around for eight years:

```text
error[E0499]: cannot borrow `*map` as mutable more than once at a time
   |
 4 |   fn get_mut_or_default<'r, K: Hash + Eq + Copy, V: Default>(
   |                         -- lifetime `'r` defined here
 8 |       match map.get_mut(&key) {
   |       -     --- first mutable borrow occurs here
 9 | |         Some(value) => value,
11 | |             map.insert(key, V::default());
   | |             ^^^ second mutable borrow occurs here
14 | |     }
   | |_____- returning this value requires that `*map` is borrowed for `'r`
```

**Why it matters**

Every workaround for this pattern costs something real in a service: a
`contains_key` pre-check pays a second hash and probe on the hot path, and the
`Entry` API pays an owned key even on the overwhelmingly common hit. The
functional shape, one `match` over one lookup, was always the correct code; the
rejection was an artifact of the analysis, and C++ has no analysis to be an
artifact of. Note the honest limit: Polonius Alpha is a subset of the 2018
formulation, and the loop-carried `Option<Box<X>>` reassignment case still fails
on both.

**Chew on this**

Which of your `&mut self` methods have a `contains_key`-then-`get_mut` double
lookup, or an `Entry` call that clones a key, purely to get past E0499? If those
functions compile unchanged on nightly today, what does that tell you about how
much of your API shape is the domain and how much is the 2018 solver?

**Sources**

- https://blog.rust-lang.org/2026/08/04/enabling-polonius-alpha-on-nightly/
- https://blog.rust-lang.org/2022/08/05/nll-by-default/

**Verified**

Rejection confirmed locally on stable rustc 1.95.0 (aarch64-apple-darwin,
edition 2024); the error text above is that run's real output, lightly trimmed.
Acceptance under Polonius Alpha rests on the announcement post alone: no nightly
toolchain is installed on this host, so it was not run.

## C++: std::deque gives you one heap block per element once sizeof(T) reaches 512

*Perf and memory model*

**Did you know**

The standard says nothing about `std::deque`'s block size, and the two Linux
implementations disagree by 8x. libstdc++ hardcodes `_GLIBCXX_DEQUE_BUF_SIZE`
at 512 *bytes*, so a block holds `512 / sizeof(T)` elements and clamps to **1**
once `sizeof(T) >= 512`: your deque becomes a linked list with a malloc per
`push_back`. libc++ computes `sizeof(T) < 256 ? 4096 / sizeof(T) : 16`, so it
never drops below 16 per block. Worse, libstdc++'s default constructor calls
`_M_initialize_map(0)`, which allocates the map *and* one node: an empty
`std::deque<int>` already owns two allocations, about 576 bytes on LP64, where
`std::vector` owns none. All of this is C++98-era and unfixable, because the
header says out loud that changing the constant "breaks the binary
compatibility".

**Show me**

```cpp
// Counting allocator via replaced operator new. Measured with Apple clang 21
// (libc++, _LIBCPP_VERSION 220106), -std=c++20 -O2.
static std::size_t g_count = 0, g_bytes = 0;
void* operator new(std::size_t n) { ++g_count; g_bytes += n; return std::malloc(n); }

using Big = std::array<double, 64>;              // exactly 512 bytes

std::deque<int> d;                               // libc++  : 0 allocs, 0 bytes
                                                 // libstdc++: 2 allocs, ~576 bytes
d.push_back(1);                                  // libc++  : 2 allocs, 4104 bytes

std::deque<Big> big;
for (int i = 0; i < 64; ++i) big.push_back(Big{});
// libc++  : 9 allocs, 41080 bytes   (16 elements per 8 KiB block)
// libstdc++: 64 node allocs + map growth, because __deque_buf_size(512) == 1

// Rust's equivalent declines the guarantee that forces the block map:
//   let mut q: VecDeque<[f64; 64]> = VecDeque::new();  // no allocation at all
//   q.push_back([0.0; 64]);                            // one ring buffer, doubling
// VecDeque is contiguous-ish and reallocates, so &mut q[0] cannot survive a push.
// deque's block map exists precisely to keep references valid across push_back.
```

**Why it matters**

`std::deque<T>` is the reflex choice for a work queue, and a queue of 512-byte
jobs on libstdc++ costs one allocator round trip per enqueue plus a cache miss
per traversal step, while the same code on libc++ amortizes 16 to a block. The
empty-deque allocation is the quieter bug: a `unordered_map<Key, std::deque<Job>>`
with a hundred thousand idle keys is ~55 MiB of nothing on libstdc++ and zero on
libc++. The container you chose for its reference-stability guarantee is billing
you for that guarantee on every push, which is the trade Rust's `VecDeque`
simply refuses to make.

**Chew on this**

Which of your `std::deque` uses actually depend on references surviving a
`push_back`, and which just wanted a queue? For the ones that only wanted a
queue, what is the block-size arithmetic for your real element type on the
standard library your production containers link against, not the one on your
laptop?

- https://en.cppreference.com/w/cpp/container/deque
- https://doc.rust-lang.org/std/collections/struct.VecDeque.html

**Verified**

The libc++ numbers are from a local run (Apple clang 21, libc++ 220106). The

`_Deque_base() { _M_initialize_map(0); }`), not measured: no GCC or libstdc++ on
this host. MSVC's STL was not checked at all.

## TypeScript: Channel's type parameters do not type publish, and subscribers get your object by reference

*Stdlib and ecosystem gems*

**Did you know**

`node:diagnostics_channel` is the instrumentation hook you can leave switched on
in production: `channel.hasSubscribers` is a property read, so a publish site
costs nothing measurable when nothing is listening, and `tracingChannel()` gives
you `start`, `end`, `asyncStart`, `asyncEnd` and `error` subchannels for one
operation. Two things the ergonomics hide. `@types/node` declares
`class Channel<StoreType = unknown, ContextType = StoreType>`, but the method is
`publish(message: unknown): void` and `ChannelListener = (message: unknown, name:
string | symbol) => void`, so those parameters type the tracing *store*, not your
payload: `dc.channel(name)` returns a plain `Channel` and your payload type is
erased on the way in and unknown on the way out. And publish does not clone, so
a subscriber holds your live object.

**Show me**

```ts
import dc from 'node:diagnostics_channel';

const ch = dc.channel('app:order');
ch.hasSubscribers;                      // false -> the publish below is ~free

dc.subscribe('app:order', (msg, name) => {
  // msg is `unknown` no matter what you published. Cast it and you own the risk.
  const order = msg as { total: number };
  order.total = 0;                      // this is the PUBLISHER's object
});

const order = { id: 'A1', total: 4200 };
ch.publish(order);
console.log(order);                     // { id: 'A1', total: 0 } -- measured, not hypothetical

// readonly does not help: it is assignability-only, erased at runtime, and the
// subscriber never sees your type anyway.
const publishRO = (o: Readonly<typeof order>) => ch.publish(o);  // widens to unknown

// Rust's tracing crate cannot express this failure: a Subscriber receives
// &Event, and &T has no mutating method to reach for. C++'s equivalent hook
// would hand you a const& and let a const_cast through, i.e. TypeScript's
// situation with an extra keyword to type.
```

**Why it matters**

An observability hook that can silently rewrite domain state is a very bad
failure mode to debug, because the mutation is attributed to whichever
third-party APM subscriber you installed last, not to your code. The cheap
discipline is to publish a fresh literal at the call site rather than the object
you are still using, and to wrap `channel()` in a typed publisher of your own so
the `unknown` boundary is crossed exactly once. Immutability is the property you
want here and the type system will not give it to you, so the object graph has
to.

**Chew on this**

Where in your service do you hand a live domain object to a callback you do not
own, on the assumption that a listener only listens? If the only thing standing
between an APM agent and your order total is that nobody has written that line
yet, is that a guarantee or a coincidence?

**Sources**

- https://nodejs.org/api/diagnostics_channel.html
- https://github.com/DefinitelyTyped/DefinitelyTyped/blob/master/types/node/diagnostics_channel.d.ts

**Verified**

The mutation, `hasSubscribers`, and the `tracing:app:db:start` / `:end`
subchannel names were run on Node v22.17.1. The signatures are quoted from the
current `@types/node` `diagnostics_channel.d.ts`; no `tsc` run, because
`@types/node` is not installed on this host.

# FAQ

**Why not just use the `Entry` API for `get_mut_or_default`?**
You often should, and it compiles today. It also takes the key by value, so a
`String` or a `Vec<u8>` key is cloned on every call including the hit path, and
`or_insert_with` runs after the lookup has already committed to an insert
position. The `match` version is the one that pays nothing on a hit.

**Does Polonius Alpha change any diagnostics?**
The announcement says no diagnostic changes have been seen yet, which is part of
why they want nightly testing. Compile time is strictly equal or greater than
NLL; the measured regressions across the 10,000 most-downloaded crates were rare
and small.

**Can I raise libstdc++'s deque block size for my build?**
Technically `-D_GLIBCXX_DEQUE_BUF_SIZE=4096` compiles, and the header explicitly
warns that it breaks binary compatibility, so any translation unit or shared
library disagreeing with you has a different `std::deque` layout. It is an ODR
violation waiting for a link.

**Is `hasSubscribers` worth checking if I am already publishing?**
Only to skip *building* the message. `publish` on a channel with no subscribers
already short-circuits; the guard exists so you do not serialize a payload
nobody will read.
