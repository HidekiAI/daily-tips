Not part of the rotation. Part 13 of the fourteen-part special on real incidents: the retransmission behaviour of the Solaris 2.3 and 2.4 TCP, measured in Vern Paxson's [Automated Packet Trace Analysis of TCP Implementations](http://conferences.sigcomm.org/sigcomm/1997/papers/p054.pdf) (SIGCOMM 1997). Each tip below is a timeout: a number fixed once, a number that stops adapting, or a retry that the far end pays for, and asks what your own timeouts learn from.

# What happened

**Bug class:** Bohrbug in this special's classification, path-triggered: Paxson writes that "For a connection with a longer RTT, the TCP is guaranteed to retransmit its first packet, whether needed or not." The anti-pattern the tips below take from it is a timeout that is reset to its first guess instead of learning from the delays it measures.

From Paxson, section 8.6, "Solaris 2.3/2.4 TCP":

```text
Dawson et al. identified that Solaris uses an atypically low initial value of about
300 msec for its retransmission timeout (RTO) [DJM97], ... This value, coupled with
difficulties in adapting the timer to higher RTTs, leads to the broken retransmission
behavior. For a connection with a longer RTT, the TCP is guaranteed to retransmit its
first packet, whether needed or not.
```

```text
While the RTO does indeed double on multiple timeouts, it is restored to its erroneously
small value immediately upon an acknowledgement for a retransmitted packet, so it never
has much opportunity to adapt.
```

His example connection ran from California to the Netherlands with a round-trip time of "about 680 msec, above that of 200 msec for the initial Solaris retransmit timer" (the same section gives about 300 msec a paragraph earlier), and "The Solaris TCP sends almost as many retransmissions as new packets, yet each retransmission is completely unnecessary!" He also notes that "it is difficult to find unambiguous RTT timings, which are required in order to adapt the timer", citing Karn and Partridge [KP87], whose rule [RFC 6298](https://www.rfc-editor.org/rfc/rfc6298) now makes mandatory ("TCP MUST use Karn's algorithm"): the acknowledgement of a packet sent twice does not say which copy it answers. Every snippet below is an illustration of the class, not Solaris code.

## Rust: `set_read_timeout(Some(Duration::ZERO))` is an error, because one layer down a zero timeout means "never time out"

*Stdlib and ecosystem gems*

**Did you know**

`TcpStream::set_read_timeout` takes an `Option<Duration>`, and passing `Some(Duration::ZERO)` returned `Err` with kind `InvalidInput` and the message "cannot set a 0 duration timeout"; the documentation says "An Err is returned if the zero Duration is passed to this method." The reason is the socket option underneath. Measured in C on the same Debian image, `SO_RCVTIMEO` set to 300 ms made `recv` fail with `EAGAIN` after 308 ms, and set to 0 it blocked until a 2-second alarm killed the probe. Rust spells "no timeout" as `None`, so a zero can never silently become "wait forever". Measured on rustc 1.99.1.

**Show me**

```rust
// rustc 1.99.1, edition 2024, Debian.
use std::net::{TcpListener, TcpStream};
use std::time::Duration;

fn main() -> std::io::Result<()> {
    let local_listener = TcpListener::bind("127.0.0.1:0")?;
    let client_stream = TcpStream::connect(local_listener.local_addr()?)?;

    let zero_timeout_io_result = client_stream.set_read_timeout(Some(Duration::ZERO));
    println!("{:?}", zero_timeout_io_result.map_err(|io_error| io_error.to_string())); // Err("cannot set a 0 duration timeout")

    client_stream.set_read_timeout(Some(Duration::from_millis(300)))?;
    println!("{:?}", client_stream.read_timeout()?); // Some(300ms)

    client_stream.set_read_timeout(None)?;            // "no timeout" has its own spelling
    println!("{:?}", client_stream.read_timeout()?); // None
    Ok(())
}
```

**Why it matters**

A timeout read from configuration is the usual way a zero arrives: an unset field, a parse that defaulted, a unit conversion that rounded 300 microseconds down. In C that zero turns a timeout into an unbounded wait; Rust turns it into an error at the call. Neither one adapts: a socket timeout is a number fixed until someone sets another, which is the Solaris problem in its simplest form.

**Chew on this**

Where do your socket or HTTP timeouts come from, and what happens to each one if its configuration value is missing? Which of them were chosen once and never measured against the latency they guard?

**Sources**

- https://doc.rust-lang.org/std/net/struct.TcpStream.html#method.set_read_timeout
- https://man7.org/linux/man-pages/man7/socket.7.html (`SO_RCVTIMEO`)

**Verified**

Rust run in `rust:1-trixie`, the C `SO_RCVTIMEO` probe in `gcc:latest` (GCC 16.2), both Debian.

**Gotchas**

- `TcpStream::connect_timeout` refuses a zero `Duration` with the same `InvalidInput` and the same message, so both directions of "time out immediately" have to be written another way.
- `Duration::from_micros(300).as_millis()` is a typical way a zero is produced; converting a timeout to milliseconds for a C API without a minimum of 1 recreates the C behaviour the Rust check exists to stop.

## C++: a smoothed round-trip time kept in `std::chrono::milliseconds` stops learning 7 ms short, because `/ 8` truncates

*Perf and memory model*

**Did you know**

The standard round-trip smoothing is `smoothed += (sample - smoothed) / 8`. Kept in `std::chrono::milliseconds`, whose count is an integer, the division drops any error below 8 ms, so the estimate stops moving before it reaches the truth: from 300 ms toward a steady 680 ms it stopped at 673 ms after 200 samples, and from 1000 ms it stopped at 687 ms. The same loop in `std::chrono::duration<double, std::milli>` reached 680.000. [Paxson](http://conferences.sigcomm.org/sigcomm/1997/papers/p054.pdf) cites an earlier finding of a related class on a different stack: Brakmo and Peterson found Net/3 TCP had "inaccuracies computing the retransmission timeout (RTO) due to details of the integer arithmetic". C++11 chrono, measured on GCC 16.2.

**Show me**

```cpp
// C++20, g++ 16.2, Debian. An illustration of the class, not Solaris code.
#include <chrono>
#include <cstdio>

int main() {
    using namespace std::chrono;
    const milliseconds const_measured_rtt_ms{680};                    // California to the Netherlands, per Paxson
    milliseconds smoothed_rtt_ms{300};                          // mutable: += in the loop; the initial guess, integer milliseconds
    duration<double, std::milli> smoothed_rtt_double_ms{300.0}; // mutable: += in the loop; the same guess in floating point
    for (int sample_index = 0; sample_index < 200; ++sample_index) { // mutable: loop counter
        smoothed_rtt_ms += (const_measured_rtt_ms - smoothed_rtt_ms) / 8;                                  // alpha = 1/8
        smoothed_rtt_double_ms += (duration<double, std::milli>(const_measured_rtt_ms) - smoothed_rtt_double_ms) / 8.0;
    }
    std::printf("integer ms: %lld, double ms: %.3f\n",
                static_cast<long long>(smoothed_rtt_ms.count()), smoothed_rtt_double_ms.count()); // 673, 680.000
}
```

**Why it matters**

An estimator that stops 7 ms short sounds harmless, and here it is. The point is the shape: integer arithmetic gives every estimator a dead zone in which new samples change nothing, and a timer that needs a larger error than the path will ever produce never moves at all.

**Chew on this**

Which of your moving averages or rate estimates are kept in an integer type, and how large is the dead zone of each? Would you notice an estimate that had stopped moving, or only one that moved wrongly?

**Sources**

- http://conferences.sigcomm.org/sigcomm/1997/papers/p054.pdf (section 2, on Brakmo and Peterson's Net/3 findings)
- https://www.rfc-editor.org/rfc/rfc6298 (the smoothing formulas, alpha = 1/8, beta = 1/4)
- https://en.cppreference.com/w/cpp/chrono/duration/operator_arith4

**Verified**

GCC 16.2.0 (`gcc:latest`, Debian), `-std=c++20 -Wall -Wextra`, no warnings.

**Gotchas**

- Integer division in C++ truncates toward zero, so the dead zone is on both sides of the truth: the estimate stops below it when it comes from below (673) and above it when it comes from above (687), never at 680.
- `-Wall -Wextra` say nothing about the division: dividing a `milliseconds` by `8` is an ordinary integer `duration` operation, and the result type is still `milliseconds`.

## F#: `HttpClient.Timeout` is one number for the client's whole life, 100 seconds by default, and it cannot be changed after the first request

*Stdlib and ecosystem gems*

**Did you know**

.NET's `HttpClient.Timeout` defaults to 00:01:40, and it is a property of the client, not of a request. After the client has started a request, setting it threw `InvalidOperationException`: "This instance has already started one or more requests. Properties can only be modified before sending the first request." A request that failed immediately, to a closed port, already counts as started. So a long-lived client, which Microsoft's guidance recommends ("Use a static or singleton HttpClient instance with PooledConnectionLifetime set"), has a timeout fixed at construction and no way to learn: if the server's latency changes, the client's idea of "too slow" does not. Measured on .NET SDK 10.0.403, FSharp.Core 10.1.0.0, .NET 10.0.14.

**Show me**

```fsharp
// F# 10, .NET 10.0.14.
open System
open System.Net.Http

let fixed_timeout_client = new HttpClient()
printfn "default Timeout: %O" fixed_timeout_client.Timeout                     // 00:01:40

try (fixed_timeout_client.GetAsync "http://127.0.0.1:9/").Wait()               // a closed port: fails at once
with request_failure -> printfn "first request failed: %s" (request_failure.InnerException.GetType().Name) // HttpRequestException

try fixed_timeout_client.Timeout <- TimeSpan.FromMilliseconds 680.0
with change_failure -> printfn "%s" change_failure.Message
// This instance has already started one or more requests. Properties can only be modified before sending the first request.
```

**Why it matters**

The 1997 bug was a timer that went back to its first guess; this API never leaves its first guess. That is usually the right default for a client shared across a process, but it means any per-call or adaptive timeout has to be built on top, with a `CancellationToken` per request, rather than by adjusting the client.

**Chew on this**

Is any of your `HttpClient` timeouts the 100-second default because nobody set it? For the clients you did set, what latency was the number chosen against, and when?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclient.timeout
- https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0`, which is Ubuntu 24.04 rather than Debian. The request went to port 9 on the container's own loopback, where nothing listens.

**Gotchas**

- A per-request deadline still works after the client is locked: on the same client, a `CancellationTokenSource` of 300 ms cancelled a request to a server that never answered after 357 ms, and one of 680 ms after 684 ms, each with `TaskCanceledException`, while `Timeout` stayed 00:01:40.
- `request_failure.InnerException` is where the real error was: `.Wait()` wraps it in an `AggregateException`, so the outer exception's type says nothing about the network.

## TypeScript: a 300 ms client timeout against a 680 ms server gave up three times, and the server still did all three requests

*Idioms and antipatterns*

**Did you know**

Against a local Node server that answers after 680 ms, a client that waits 300 ms and retries timed out on every attempt, and the server received 3 requests for 3 attempts, the Solaris pattern of work done and thrown away. How the client gives up changes what the client does, not what the server does: with `Promise.race([fetch(...), sleep(300)])` all three fetches kept running and completed after the client had moved on (3 completed, 0 used); with `fetch(url, { signal: AbortSignal.timeout(300) })` the client cancelled each one, and the server had still received all three. A timeout of 1360 ms got the answer with 1 request. Measured on Node 26.13.0.

**Show me**

```ts
// TypeScript (compiled with tsc 7.0.2 --strict --types node), Node 26.13.0, Debian. An illustration, not Solaris code.
import * as http from "node:http"
import type { AddressInfo } from "node:net"

const SERVER_DELAY_MS = 680
const CLIENT_TIMEOUT_MS = 300
let received_request_count = 0 // mutable: counted in the handlers
let completed_after_timeout_count = 0 // mutable: counted in the handlers
const const_slow_server = http.createServer((_request, response) => { received_request_count += 1; setTimeout(() => response.end("ok"), SERVER_DELAY_MS) })
await new Promise<void>((resolve) => const_slow_server.listen(0, "127.0.0.1", resolve))
const const_server_url = `http://127.0.0.1:${(const_slow_server.address() as AddressInfo).port}/`
const const_fn_wait_ms = (delay_ms: number): Promise<void> => new Promise((resolve) => setTimeout(resolve, delay_ms))

for (let attempt_index = 0; attempt_index < 3; attempt_index += 1) { // mutable: loop counter
    const const_response_text_promise = fetch(const_server_url).then((response) => response.text())
        .then((body_text) => { completed_after_timeout_count += 1; return body_text })
    console.log(await Promise.race([const_response_text_promise, const_fn_wait_ms(CLIENT_TIMEOUT_MS).then(() => "timed_out")]))      // timed_out, three times
}
await const_fn_wait_ms(SERVER_DELAY_MS + 120)
console.log("server received", received_request_count, "completed after the client gave up", completed_after_timeout_count) // 3 3
const_slow_server.close()
```

**Why it matters**

A timeout shorter than the real latency does not make anything faster: every attempt is full work for the far end and none of it is used. The race version also leaves each abandoned fetch running: all three completed after the client had given up. What that costs the client in sockets and memory was not measured.

**Chew on this**

Which of your clients time out with `Promise.race` and never cancel the request they abandoned? For the ones that do cancel, does the server you call notice the cancellation, or finish the work anyway?

**Sources**

- https://nodejs.org/api/globals.html#fetch
- https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static

**Verified**

Run in `node:lts-trixie` (Debian), Node 26.13.0; the `AbortSignal.timeout` and 1360 ms runs used the same server in a separate probe. The snippet compiles with tsc 7.0.2 `--strict --types node` and `@types/node`.

**Gotchas**

- `AbortSignal.timeout` rejects with an error named `TimeoutError`, not `AbortError`: the three aborted attempts each came back as `TimeoutError`, so code that checks for `AbortError` alone treats a timeout as an unknown failure.
- Retrying with a doubling timeout, 300 ms then 600 ms then 1200 ms, succeeded on the third attempt, after the server had received 3 requests; a fixed 300 ms over 5 attempts gave up after 5, so a cap without backoff only changes how many requests the server wastes.

# The functional angle: a retransmission timer is a fold over packets, and the Solaris bug is one arm that returns the initial state

Draws on all four tips. A timer that learns is a pure step function, `next_state = send_packet(state)`, folded over the packets of a connection. Paxson's description pins down the shape of the Solaris arm: on a timeout the RTO doubles, and on the acknowledgement that follows it is "restored to its erroneously small value", which the model represents as its first guess. The model below runs 10 packets over a 680 ms path with a 300 ms first guess, once with that reset and once with RFC 6298's rules: keep the backed-off timer, take no sample from a retransmitted packet (Karn), and smooth clean samples with alpha 1/8 and beta 1/4. It leaves out RFC 6298's 1-second minimum RTO and its clock-granularity term (the RFC writes `RTO <- SRTT + max (G, K*RTTVAR)` with K = 4).

```rust
// Rust: the timer folded over 10 packets.
const PATH_RTT_MS: f64 = 680.0;
const INITIAL_RTO_MS: f64 = 300.0;
#[derive(Clone, Copy, Debug)]
struct TimerState { rto_ms: f64, smoothed_rtt_ms: Option<f64>, rtt_variance_ms: f64, retransmission_count: u32 }
fn send_packet(timer_state: TimerState, resets_on_ambiguous_ack: bool) -> TimerState {
    if PATH_RTT_MS > timer_state.rto_ms {
        // the timer fires first: retransmit, double the RTO; the ack that follows is ambiguous (Karn), so no sample
        let backed_off_rto_ms = if resets_on_ambiguous_ack { INITIAL_RTO_MS } else { timer_state.rto_ms * 2.0 };
        TimerState { rto_ms: backed_off_rto_ms, retransmission_count: timer_state.retransmission_count + 1, ..timer_state }
    } else {
        // a clean sample: RFC 6298 smoothing, alpha 1/8 and beta 1/4
        let (smoothed_rtt_ms, rtt_variance_ms) = match timer_state.smoothed_rtt_ms {
            None => (PATH_RTT_MS, PATH_RTT_MS / 2.0),
            Some(previous_srtt_ms) => (0.875 * previous_srtt_ms + 0.125 * PATH_RTT_MS,
                                       0.75 * timer_state.rtt_variance_ms + 0.25 * (previous_srtt_ms - PATH_RTT_MS).abs()),
        };
        TimerState { rto_ms: smoothed_rtt_ms + 4.0 * rtt_variance_ms, smoothed_rtt_ms: Some(smoothed_rtt_ms), rtt_variance_ms, ..timer_state }
    }
}
fn main() {
    let initial_state = TimerState { rto_ms: INITIAL_RTO_MS, smoothed_rtt_ms: None, rtt_variance_ms: 0.0, retransmission_count: 0 };
    for resets_on_ambiguous_ack in [true, false] {
        let final_state = (0..10).fold(initial_state, |timer_state, _packet_index| send_packet(timer_state, resets_on_ambiguous_ack));
        println!("resets={resets_on_ambiguous_ack} retransmitted {} of 10, final RTO {:.0} ms", final_state.retransmission_count, final_state.rto_ms);
    }
}
// resets=true retransmitted 10 of 10, final RTO 300 ms
// resets=false retransmitted 2 of 10, final RTO 862 ms
```

// F#: the same timer as a record folded with List.fold.
let PATH_RTT_MS = 680.0
let INITIAL_RTO_MS = 300.0
type TimerState = { rto_ms: float; smoothed_rtt_ms: float option; rtt_variance_ms: float; retransmission_count: int }
let send_packet (resets_on_ambiguous_ack: bool) (timer_state: TimerState) : TimerState =

        { timer_state with rto_ms = (if resets_on_ambiguous_ack then INITIAL_RTO_MS else timer_state.rto_ms * 2.0)
                           retransmission_count = timer_state.retransmission_count + 1 }
    else
        let smoothed_rtt_ms, rtt_variance_ms =
            match timer_state.smoothed_rtt_ms with
            | None -> PATH_RTT_MS, PATH_RTT_MS / 2.0
            | Some previous_srtt_ms -> 0.875 * previous_srtt_ms + 0.125 * PATH_RTT_MS, 0.75 * timer_state.rtt_variance_ms + 0.25 * abs (previous_srtt_ms - PATH_RTT_MS)

let initial_state = { rto_ms = INITIAL_RTO_MS; smoothed_rtt_ms = None; rtt_variance_ms = 0.0; retransmission_count = 0 }
for resets_on_ambiguous_ack in [ true; false ] do

```cpp
// C++23: the same timer with std::ranges::fold_left; doubles, not integer milliseconds.
#include <algorithm>
#include <cmath>
#include <cstdio>
#include <optional>
#include <ranges>
constexpr double PATH_RTT_MS = 680.0;
constexpr double INITIAL_RTO_MS = 300.0;
struct TimerState { double rto_ms; std::optional<double> smoothed_rtt_ms; double rtt_variance_ms; int retransmission_count; };
TimerState send_packet(TimerState timer_state, const bool const_resets_on_ambiguous_ack) { // timer_state is mutable: updated in place on the retransmit path
    if (PATH_RTT_MS > timer_state.rto_ms) {
        timer_state.rto_ms = const_resets_on_ambiguous_ack ? INITIAL_RTO_MS : timer_state.rto_ms * 2.0;
        timer_state.retransmission_count += 1;
        return timer_state;
    }
    const double const_smoothed_rtt_ms = timer_state.smoothed_rtt_ms ? 0.875 * *timer_state.smoothed_rtt_ms + 0.125 * PATH_RTT_MS : PATH_RTT_MS;
    const double const_rtt_variance_ms = timer_state.smoothed_rtt_ms
        ? 0.75 * timer_state.rtt_variance_ms + 0.25 * std::fabs(*timer_state.smoothed_rtt_ms - PATH_RTT_MS) : PATH_RTT_MS / 2.0;
    return {const_smoothed_rtt_ms + 4.0 * const_rtt_variance_ms, const_smoothed_rtt_ms, const_rtt_variance_ms, timer_state.retransmission_count};
}
int main() {
    for (const bool const_resets_on_ambiguous_ack : {true, false}) {
        const TimerState const_final_state = std::ranges::fold_left(std::views::iota(0, 10), TimerState{INITIAL_RTO_MS, std::nullopt, 0.0, 0},
            [const_resets_on_ambiguous_ack](const TimerState const_timer_state, int) { return send_packet(const_timer_state, const_resets_on_ambiguous_ack); });
        std::printf("resets=%d retransmitted %d of 10, final RTO %.0f ms\n", const_resets_on_ambiguous_ack, const_final_state.retransmission_count, const_final_state.rto_ms);
    }
}
```

```ts
// TypeScript: the same timer reduced over 10 packets; every field written out, no object spread.
const PATH_RTT_MS = 680
const INITIAL_RTO_MS = 300
type TimerState = { rto_ms: number; smoothed_rtt_ms: number | undefined; rtt_variance_ms: number; retransmission_count: number }
const const_fn_smoothed_state = (timer_state: TimerState, previous_srtt_ms: number): TimerState => {
    const const_smoothed_rtt_ms = 0.875 * previous_srtt_ms + 0.125 * PATH_RTT_MS
    const const_rtt_variance_ms = 0.75 * timer_state.rtt_variance_ms + 0.25 * Math.abs(previous_srtt_ms - PATH_RTT_MS)
    return { rto_ms: const_smoothed_rtt_ms + 4 * const_rtt_variance_ms, smoothed_rtt_ms: const_smoothed_rtt_ms, rtt_variance_ms: const_rtt_variance_ms, retransmission_count: timer_state.retransmission_count }
}
const const_send_packet = (timer_state: TimerState, resets_on_ambiguous_ack: boolean): TimerState =>
    PATH_RTT_MS > timer_state.rto_ms
        ? { rto_ms: resets_on_ambiguous_ack ? INITIAL_RTO_MS : timer_state.rto_ms * 2, smoothed_rtt_ms: timer_state.smoothed_rtt_ms,
            rtt_variance_ms: timer_state.rtt_variance_ms, retransmission_count: timer_state.retransmission_count + 1 }
        : timer_state.smoothed_rtt_ms === undefined
          ? { rto_ms: PATH_RTT_MS + 4 * (PATH_RTT_MS / 2), smoothed_rtt_ms: PATH_RTT_MS, rtt_variance_ms: PATH_RTT_MS / 2,
              retransmission_count: timer_state.retransmission_count }
          : const_fn_smoothed_state(timer_state, timer_state.smoothed_rtt_ms)
const const_initial_state: TimerState = { rto_ms: INITIAL_RTO_MS, smoothed_rtt_ms: undefined, rtt_variance_ms: 0, retransmission_count: 0 }
for (const const_resets_on_ambiguous_ack of [true, false]) {
    const const_final_state = Array.from({ length: 10 }).reduce<TimerState>((timer_state) => const_send_packet(timer_state, const_resets_on_ambiguous_ack), const_initial_state)
    console.log(`resets=${const_resets_on_ambiguous_ack} retransmitted ${const_final_state.retransmission_count} of 10, final RTO ${const_final_state.rto_ms.toFixed(0)} ms`)
}
```

All four printed the same two lines (shown under the Rust block): Rust on rustc 1.99.1, F# on .NET SDK 10.0.403, C++ on GCC 16.2 (`-std=c++23 -Wall -Wextra`, no warnings), TypeScript on Node 26.13.0 with tsc 7.0.2 `--strict`.

| Language | State update | Reset arm (Solaris shape) | What the shape costs |
| --- | --- | --- | --- |
| F# | `{ timer_state with ... }` | 10 of 10 retransmitted, RTO 300 ms | nothing extra: copy-and-update is the default |
| Rust | `TimerState { ..timer_state }` with `Copy` | the same | `TimerState` is `Copy` only because the loop folds the same `initial_state` twice; without it, rustc refused with E0382 (use of moved value), and the closure itself needs no `Copy` |
| C++ | a by-value parameter, mutated and returned | the same | the "pure" step mutates its own copy; nothing stops a reference parameter instead |
| TypeScript | a fresh object literal per step | the same | every field written out by hand, to keep a misspelt key from adding a property |

F# is the baseline because a record update is its normal way to return a new state, so the F# row shows the shape at no cost and the other rows show what each language charges for it.

Which of your adaptive values, a timeout, a rate limit, a batch size, has an arm that sends it back to its first guess?

# The security angle: a retry that does not back off is load you send to someone else

Draws on the TypeScript tip. Nothing in any of the four languages stops a loop from retrying a slow call as fast as its timeout allows. Paxson's Solaris connections cost the network bandwidth; a retry loop costs the server a request per attempt, and many clients running the same loop can become a self-inflicted denial of service (inferred: only one client was measured). This is the missing-check sample, fixed and then doubling:

```ts
// TypeScript (Node). Looks like a careful client: it has a timeout and a retry limit.
const const_fn_attempt = (server_url: string, timeout_ms: number): Promise<string> =>
    fetch(server_url, { signal: AbortSignal.timeout(timeout_ms) }).then((response) => response.text())
        .catch((fetch_failure: Error) => fetch_failure.name)

const INITIAL_TIMEOUT_MS = 300

const const_fn_retry_fixed = async (server_url: string, attempt_limit: number): Promise<string> => {
    for (let attempt_index = 0; attempt_index < attempt_limit; attempt_index += 1) // mutable: loop counter
        if ((await const_fn_attempt(server_url, INITIAL_TIMEOUT_MS)) === "ok") return "ok"            // the same 300 ms every time
    return "gave_up"
}
const const_fn_retry_backoff = async (server_url: string, attempt_limit: number): Promise<string> => {
    for (let attempt_index = 0; attempt_index < attempt_limit; attempt_index += 1) // mutable: loop counter
        if ((await const_fn_attempt(server_url, INITIAL_TIMEOUT_MS * 2 ** attempt_index)) === "ok") return "ok" // 300, 600, 1200 ...
    return "gave_up"
}
export { const_fn_retry_fixed, const_fn_retry_backoff }
```

Against the 680 ms server with 5 attempts allowed, the fixed version gave up and the server received 5 requests; the doubling version succeeded on the third attempt, after 3. The class is [CWE-400](https://cwe.mitre.org/data/definitions/400.html), Uncontrolled Resource Consumption, here caused by the client rather than suffered by it.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | a fixed timeout retried in a loop | `AbortSignal.timeout` cancels the client side only | back off and cap the attempts |
| Rust | the same loop with `set_read_timeout` | refuses a zero timeout | the same backoff; std has no retry policy |
| C++ | an integer timer that stops adapting | nothing | keep estimates in floating point (measured above), or work out the integer form's dead zone |
| F# | a client-wide timeout fixed at construction | refuses changes after the first request | a per-request `CancellationToken` for anything adaptive |

TypeScript is the baseline because its sample ran against a real server and the request counts above are measured, not modelled.

How many requests does each of your clients send to a server that has slowed down, and would the server's operators call that a retry or an attack?
