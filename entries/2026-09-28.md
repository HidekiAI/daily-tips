## Rust: `extract_if` keeps every element it never reached, so `.take(n)` removes n and leaves the rest

*Stdlib and ecosystem gems*

**Did you know**

`Vec::extract_if(range, pred)` (stable since 1.87) and `HashMap::extract_if(pred)` (1.88) remove and yield matching elements in one pass. The pass is only as long as your consumption, though. If the iterator is dropped early, from `.take(n)`, a `break`, or never being iterated at all, every element it has not yet visited **stays**. `drain` does the opposite: drop it early and the whole range is still gone. The predicate also gets `&mut T` (`&K, &mut V` for the map), and a mutation sticks even on the elements you keep. So one call can filter, partition, and update in place.

**Show me**

```rust
use std::collections::HashMap;

fn main() {
    // Stop early: only the elements actually visited get the chance to leave.
    let mut v: Vec<u32> = (1..=10).collect();
    let first_two: Vec<u32> = v.extract_if(.., |j| *j % 2 == 0).take(2).collect();
    // first_two=[2, 4]  v=[1, 3, 5, 6, 7, 8, 9, 10]   (6, 8, 10 survive)

    // drain is eager about removal: take(2) still empties the range.
    let mut d: Vec<u32> = (1..=10).collect();
    let got: Vec<u32> = d.drain(..).take(2).collect();
    // got=[1, 2]  d=[]

    // The range narrows the scan (a partition of only the tail).
    let mut r: Vec<u32> = (1..=10).collect();
    let tail_evens: Vec<u32> = r.extract_if(5.., |j| *j % 2 == 0).collect();
    // tail_evens=[6, 8, 10]  r=[1, 2, 3, 4, 5, 7, 9]

    // HashMap: the predicate takes &mut V, so "decay then evict" is one pass.
    // The decrement persists on the entries that were KEPT.
    let mut ttl: HashMap<u32, u32> = (1..=6).map(|k| (k, k * 10)).collect();
    let expired: HashMap<u32, u32> =
        ttl.extract_if(|_, t| { *t -= 5; *t < 30 }).collect();
    // expired={1: 5, 2: 15, 3: 25}  ttl={4: 35, 5: 45, 6: 55}
    println!("{first_two:?} {v:?} {got:?} {d:?} {tail_evens:?} {r:?} {} {}", expired.len(), ttl.len());
}
```

**Why it matters**

`extract_if` replaces the "collect indices, then `swap_remove` in reverse" dance and the clone-then-`retain` pair, and it backshifts in bulk rather than calling `remove` per hit. But its removal is lazy in a way `drain`'s is not, so "extract the first N" is a correct batching idiom and "extract, then bail on error" silently leaves the tail untouched. In C++ the nearest shape is `std::erase_if` (C++20), which is eager and yields nothing. F#'s `List.partition` gives both halves but builds two new lists. TypeScript has no in-place filter at all.

**Chew on this**

Where in your services does a `retain` exist only because you also needed the removed elements, and would the lazy half of `extract_if` make that code more correct or less? If a predicate mutates *and* can panic halfway through, what state is the collection in, and would your caller know?

**Sources**

- https://doc.rust-lang.org/std/collections/struct.HashMap.html#method.extract_if

## C++: `optional::value_or` builds its fallback every call and copies the value it already has

*Idioms and antipatterns*

**Did you know**

`opt.value_or(make_default())` is an ordinary function call, so `make_default()` runs even when `opt` is engaged. And `value_or` returns `T` by value, never `const T&`, so on an engaged `const optional<std::string>&` it copies the string you only wanted to read. C++23's monadic `or_else` makes the fallback lazy but still returns `optional<T>` by value, so it copies too. Standard: `value_or` is C++17; `or_else` is C++23 (P0798R8), in libstdc++ 12, libc++ 14 and MSVC STL 19.32.

**Show me**

```cpp
// clang++ -std=c++23 -O2 (Apple clang 21, libc++ 22)
#include <cstdio>
#include <optional>
#include <string>

static int loads = 0, copies = 0;

struct Blob {
    std::string data;
    explicit Blob(std::string d) : data(std::move(d)) {}
    Blob(const Blob& o) : data(o.data) { ++copies; }   // count every copy
    Blob(Blob&&) noexcept = default;
};

Blob load_default() { ++loads; return Blob{std::string(4096, 'x')}; }

const std::optional<Blob>& cached() {
    static const std::optional<Blob> c{Blob{"hit"}};  // always engaged
    return c;
}

int main() {
    // Engaged, yet: loads=1 copies=1. The 4 KiB default was built and thrown away.
    const Blob& a = cached().value_or(load_default());

    loads = copies = 0;
    // C++23: loads=0, but copies=1. or_else returns optional<T> by value.
    std::optional<Blob> b =
        cached().or_else([] { return std::optional<Blob>{load_default()}; });

    loads = copies = 0;
    // The only zero-cost read: loads=0 copies=0.
    const Blob& c = *cached();
    std::printf("%zu %zu %zu\n", a.data.size(), b->data.size(), c.data.size());
}
```

**Why it matters**

On a hot path, `cfg.value_or(std::string{})` is an allocation per call even when the value is present, and `value_or(expensive())` hides a fallback computation in what reads like a cheap default. Rust has the same eager trap in `unwrap_or(f())` and lints it (clippy `or_fun_call`), and it gets the read without a copy through `as_ref()`. TypeScript's `??` never has the trap, because it is an operator and short-circuits. F# splits the two explicitly, `Option.defaultValue` (eager) against `Option.defaultWith` (lazy).

**Chew on this**

How many of your `value_or` calls have an argument that allocates or does I/O, and would a grep for `value_or(` followed by `(` tell you? When the honest answer is "I want a reference to the value or to a static default", is there a standard C++ shape for that at all before C++26?

- https://en.cppreference.com/w/cpp/compiler_support/23

## F#: a function returning `int * int` costs 24 bytes a call, and the tuple from `TryParse` is free only at the call site

*Perf and memory model*

**Did you know**

F# tuples are `System.Tuple`, a heap object, so a non-`inline` function returning `a, b` allocates 24 bytes per call even when the caller destructures it immediately. The pattern `match Int32.TryParse s with | true, v -> ...` looks like the same tuple, but the compiler rewrites the `out` parameter at the call site and allocates nothing. Wrap that same match in your own `tryParse : string -> bool * int` and the tuple becomes real: 24 bytes. `struct (a, b)` or `inline` both get it to zero. Measured on F# 8, FSharp.Core 8.0.0, .NET 8.0.8.

**Show me**

```fsharp
// dotnet fsi --optimize+   (F# 8, FSharp.Core 8.0.0, .NET 8.0.8)
open System

let divRem (a: int) (b: int) : int * int = (a / b, a % b)
let divRemS (a: int) (b: int) : struct (int * int) = struct (a / b, a % b)
let inline divRemI (a: int) (b: int) : int * int = (a / b, a % b)
let tryParse (s: string) : bool * int =
    match Int32.TryParse s with
    | true, v -> (true, v)
    | _ -> (false, 0)

// Bytes per call, from GC.GetAllocatedBytesForCurrentThread over 1,000,000 calls:
//   let q, r = divRem i 7                 -> 24.0  (System.Tuple<int,int>)
//   let struct (q, r) = divRemS i 7       ->  0.0  (ValueTuple, returned in registers)
//   let q, r = divRemI i 7                ->  0.0  (inlined, tuple never built)
//   let ok, v = tryParse "42"             -> 24.0  (your function returns a real tuple)
//   match Int32.TryParse "42" with ...    ->  0.0  (out param, no tuple exists)
let measure (f: unit -> int) : float =
    f () |> ignore
    let before: int64 = GC.GetAllocatedBytesForCurrentThread()
    f () |> ignore
    float (GC.GetAllocatedBytesForCurrentThread() - before) / 1_000_000.0
```

**Why it matters**

"Return a tuple" is the idiomatic F# answer to multiple results, and it is the idiom Rust and C++ get for free: a Rust `(i32, i32)` and a C++ `std::pair<int, int>` are plain values with no allocation to elide. In F# it is an allocation per call on any parse, lookup, or `divRem` helper in a hot loop, and the GC pressure never shows up in a profile as the tuple. TypeScript is closer to F# here: returning `[q, r]` builds an array, and whether V8 escape-analyzes it away is up to the JIT.

**Chew on this**

Which of your hot helpers return a tuple that callers destructure on the next line, and would switching one to `struct` change its public signature enough to matter? If .NET's newer escape analysis starts stack-allocating these after inlining, does `struct` stop being worth the syntax?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/tuples
- https://learn.microsoft.com/en-us/dotnet/api/system.gc.getallocatedbytesforcurrentthread

**Verified**

Measured in `dotnet fsi --optimize+` on .NET 8 only; a compiled Release build and .NET 9/10 were not measured.

## TypeScript: `Math.sumPrecise` is ES2026 and shipped in Chrome 147, but TypeScript 7.0.2 still has no declaration and Node 26 hides it behind a V8 flag

*New discoveries and currently popular patterns*

**Did you know**

`Math.sumPrecise(iterable)` reached TC39 Stage 4 on 2025-07-28 (ES2026) and shipped in Chrome 147 in April 2026. It sums as if in exact arithmetic and rounds once, so `[1e20, 1, -1e20]` gives `1` where `reduce` gives `0`, and it rejects non-numbers with a `TypeError`. As of today, TypeScript 7.0.2's `lib.esnext.d.ts` has no declaration (issue #63427, open since 2026-04-23), and Node 26.10 ships V8 14.6, one release short, with the method behind `--js-sum-precise`. Also: `Math.sumPrecise([])` is `-0`, not `0`.

**Show me**

```ts
// tsc 7.0.2 --strict --lib esnext. Without this block: TS2339.
declare global {
    interface Math {
        sumPrecise(items: Iterable<number>): number;
    }
}

const xs: number[] = [1e20, 1, -1e20];

// The fold everyone writes: one rounding per step, left to right.
const naive: number = xs.reduce((acc, x) => acc + x, 0);          // 0

// The declaration above is a promise to the compiler, not a runtime fact.
const precise: number | undefined =
    typeof Math.sumPrecise === "function" ? Math.sumPrecise(xs) : undefined;

// node 26.10.0                      -> 0 undefined
// node 26.10.0 --js-sum-precise     -> 0 1
// Also measured with the flag:
//   [0.1, 0.2, 0.3]: reduce 0.6000000000000001, sumPrecise 0.6
//   [MAX, MAX, -MAX]: reduce Infinity, sumPrecise 1.7976931348623157e+308
//   sumPrecise([]) is -0;  sumPrecise([1, "2"]) throws TypeError
console.log(naive, precise);
export {};
```

**Why it matters**

Money totals, metrics rollups, and averages over large arrays are exactly where `reduce((a, b) => a + b, 0)` drifts, and it also overflows to `Infinity` on intermediates the final answer would not need. The fix is now in the language but not yet in your server runtime or your type definitions, so a `declare global` shim plus a runtime check is the honest state. Rust's `f64` `Sum` and C++'s `std::reduce` are both plain rounding-per-step sums; neither std ships a compensated sum.

**Chew on this**

Once Node ships this unflagged, which of your `reduce` sums would change their output, and which of those outputs are persisted where a changed last digit is a diff someone will investigate? Is a `declare global` shim that lies until the runtime catches up better or worse than no declaration at all?

**Sources**

- https://github.com/tc39/proposal-math-sum
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Math/sumPrecise
- https://chromestatus.com/feature/4790090146643968
- https://github.com/microsoft/TypeScript/issues/63427

# The functional angle: the additive identity of floating point is -0, and only two of the folds you write know it

Draws on the TypeScript tip (`Math.sumPrecise([])` is `-0`), with a measured row from each other language. The shape: sum a sequence of `f64`, starting from the fold's identity element. For `+` on IEEE-754, that element is `-0.0`, because `-0.0 + x == x` for every `x`, including `x = -0.0`. `+0.0 + -0.0` is `+0.0`, so starting from `+0` changes the result for an all-negative-zero input.

```rust
let s: f64 = [-0.0f64].iter().sum();                 // -0.0: std's Sum folds from -0.0
let f: f64 = [-0.0f64].iter().fold(0.0, |a, b| a + b); // +0.0: your fold does not
```

```cpp
std::accumulate(v.begin(), v.end(), 0.0);   // +0.0 for {-0.0}: your init
std::reduce(v.begin(), v.end());            // +0.0 for {-0.0}: init is T{}, which is +0.0
```

```fsharp
List.sum [-0.0]            // +0.0: GenericZero is +0.0
List.fold (+) 0.0 [-0.0]   // +0.0
```

```ts
[-0].reduce((a, b) => a + b, 0);   // +0
Math.sumPrecise([-0]);             // -0 (and [] gives -0 too)
```

| Language | Functional form | Sign for `[-0.0]` | What it costs |
| --- | --- | --- | --- |
| F# | `List.sum` | +0 | the baseline, since it is the idiomatic `sum`; `GenericZero` picks +0, so the identity law is broken by the stdlib itself |
| Rust | `Iterator::sum` / `fold(0.0, ..)` | -0 / +0 | std gets it right (`core/src/iter/traits/accum.rs` folds from `-0.0`); the hand-written fold, which is what most people write, does not |
| C++ | `accumulate(.., 0.0)` / `reduce` | +0 / +0 | no std sum knows; `reduce` also may reorder, so it is not even the same rounding |
| TypeScript | `reduce(.., 0)` / `sumPrecise` | +0 / -0 | the new builtin is the only precise sum in any of the four stdlibs, and the runtime lag is the cost |

The asymmetry worth noticing: none of these needs `mut`, and every one is a "pure" fold. The bug is in the identity element, not in the style. A fold is only lawful if its seed is the operator's identity, and three of four standard libraries chose the seed that reads nicest instead.

Left hanging: does any code of yours branch on the sign of zero (`1 / x`, `Math.sign`, `atan2`, a serializer that writes `-0`), and if so, which of your sums feed it?

# The security angle: a discarded filter is a revocation that never ran

Draws on the Rust tip, and runs in the direction the language does **not** prevent. `extract_if` removes nothing until consumed. A bare statement at least warns; `let _ =` silences the warning and still removes nothing. The same omission, a filter whose result is dropped, compiles in all four languages, and in one of them without a word. Class: CWE-252 (Unchecked Return Value), with CWE-613 (Insufficient Session Expiration) as the consequence when the collection holds sessions or grants.

```rust
// Looks like "evict expired sessions". Removes nothing, and warns about nothing.
let _ = sessions.extract_if(|_, exp| *exp < now);
// sessions.len() is unchanged. Without the `let _ =`, rustc 1.95 warns:
//   unused `ExtractIf` that must be used ... iterators are lazy
```

```rust
// What was meant: retain for discard-only, or consume the iterator.
sessions.retain(|_, exp| *exp >= now);
```

```ts
// tsc 7.0.2 --strict: exit 0, no diagnostic. filter returns a NEW array.
sessions.filter((s) => s.exp >= now);
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | `let _ = map.extract_if(..)` removes nothing | `#[must_use]` warns on the bare statement; `let _` opts out silently | grep for `let _ =` on iterator-returning calls; prefer `retain` when the removed items are not needed |
| C++ | `std::remove_if` without `erase` leaves `size()` unchanged | libc++ marks it `[[nodiscard]]`; clang warns with `-Wall` | use `std::erase_if` (C++20); do not rely on the warning under GCC or MSVC without checking |
| F# | `List.filter pred xs` on its own line inside a function | FS0020 warning on any discarded non-unit value, `let _ =` silences it | treat FS0020 as an error (`--warnaserror:20`) |
| TypeScript | `arr.filter(pred)` as a statement | nothing: tsc has no unused-result check | a lint rule for unused expressions, or keep grants in a structure whose only mutator is the revoke function |

The control here is F#: it warns on *any* discarded value, not only on types marked `must_use`, so the omission is a warning by default everywhere. Rust and C++ protect only the APIs someone annotated, and every language here, F# included, lets `let _ =` or its cousin turn the warning into silence.

Left hanging: in your revocation and cleanup paths, is the thing that removes a grant a function whose return value can be ignored, and which of your reviewers would read `let _ =` as intentional?

# FAQ

**Does `extract_if` on `Vec` need the range argument?** Yes. The stable signature takes `range` and `filter`; pass `..` for the whole vector. The unstable `drain_filter` it replaced took only the predicate.

**Does `HashMap::extract_if` visit in a stable order?** No. It follows the table's iteration order, so a `.take(n)` removes an arbitrary n matching entries, not the "first" n.

**Is `std::optional<T&>` the fix for the `value_or` copy?** It is in C++26 (P2988). Support on this host was not checked, so treat it as not yet usable.

**Does F#'s `[<Struct>]` attribute on a function make its tuple return struct?** No. The struct-ness is in the type: write `struct (a, b)` in the body and `struct (int * int)` in the signature.

**Can I polyfill `Math.sumPrecise` today?** Yes: core-js 3.50 ships one (`core-js/actual/math/sum-precise`). Its speed against `reduce` was not measured.
