# Daily Tips special, part 6 of 6: timestamps, or every hop rounds, and nobody agrees which way

_Special edition, written 2026-10-22. Part 6 of the timestamps special: [part 1](2026-10-21-extra-1-of-6.md) covered month arithmetic, DST and parsing, [part 2](2026-10-21-extra-2-of-6.md) cron, epochs, durations and `Temporal`, [part 3](2026-10-21-extra-3-of-6.md) 32-bit counters, timer limits and two-digit years, [part 4](2026-10-22-extra-4-of-6.md) zone names, abbreviations, RFC 3339 and JWT leeway, and [part 5](2026-10-22-extra-5-of-6.md) equality, ordering and sorting. This part: precision. How fine a clock really ticks, what each type can hold, and what is lost at every boundary between them._

**The thesis: a timestamp's precision belongs to whoever produced it last.** The type says nanoseconds, the OS delivers microseconds, the wire format keeps milliseconds, and a float keeps a few hundred nanoseconds. Each hop rounds, and below zero they do not even agree on the direction.

| | Rust | C++ | F# / .NET | TypeScript / JS |
| --- | --- | --- | --- | --- |
| Wall-clock type's unit | 1 ns (`SystemTime`) | 1 us on libc++, 1 ns on libstdc++ | 100 ns tick | 1 ms (`Date`) |

## Rust: `SystemTime` holds nanoseconds and macOS fills in only microseconds, and `as_secs_f64` of today's time already loses 72 ns

*Perf and memory model*

**Did you know**

`std::time::SystemTime` stores nanoseconds on every platform, but the OS decides how many of them are real. On macOS all 20 of 20 readings were whole microseconds. On Linux none were. Converting a current timestamp to `f64` seconds keeps only about 238 ns of precision, because neighbouring `f64` values near 1.79e9 are 2^-22 s apart, and the round trip measured 72 ns lost. `as_secs_f32` is worse: the next `f32` after today's timestamp is 128 seconds away.

**Show me**

```rust
// Rust: std only, rustc 1.95.0 on macOS (Apple Silicon) and rustc 1.99.1 on Linux (Docker)
use std::time::{Duration, SystemTime, UNIX_EPOCH};

fn main() {
    // The type holds nanoseconds; the OS decides how many of them are real.
    let whole_micros = (0..20)
        .map(|_| SystemTime::now().duration_since(UNIX_EPOCH).unwrap().subsec_nanos())
        .filter(|nanos| nanos % 1000 == 0)
        .count();
    println!("{whole_micros}/20 readings are whole microseconds"); // macOS: 20/20, Linux: 0/20

    // f64 seconds since 1970 cannot hold nanoseconds any more.
    let stamp = Duration::new(1_792_693_394, 123_456_789);
    let as_float = stamp.as_secs_f64();
    let spacing = f64::from_bits(as_float.to_bits() + 1) - as_float;
    println!("{:.0} ns between neighbouring f64 values", spacing * 1e9); // 238
    println!("{} ns lost on the round trip",
        stamp.as_nanos() - Duration::from_secs_f64(as_float).as_nanos()); // 72
    let as_single = stamp.as_secs_f32();
    println!("{as_single}, next f32 is {} s away",
        f32::from_bits(as_single.to_bits() + 1) - as_single); // 1792693400, 128 s away
}
```

**Why it matters**

Two things go wrong in practice. A test that asserts nanosecond-distinct timestamps passes on a Linux CI runner and fails on a developer's Mac. And a metrics pipeline that ships "seconds since the epoch" as a float (a common JSON and Prometheus habit) has already rounded every sample to about a quarter of a microsecond, and to two minutes if anyone picks `f32`. C++ hides the same platform split inside the clock's type (C++ tip below), and JS never had sub-millisecond wall time to lose.

**Chew on this**

Where do your services turn a `Duration` or a `SystemTime` into a float, and does anything downstream subtract two of them? What resolution do your tests assume the clock has, and on which OS were they written?

**Sources**

- https://doc.rust-lang.org/std/time/struct.SystemTime.html (the "Platform-specific behavior" table)
- https://doc.rust-lang.org/std/time/struct.Duration.html#method.as_secs_f64

**Gotchas**

- `Instant` on both hosts stepped in 41 to 42 ns increments (measured), so the monotonic clock is not nanosecond-grained either.
- `UNIX_EPOCH - 1.5 s` cannot be represented as a `Duration` since the epoch: `duration_since` returns `Err`, and the error's `.duration()` gives the 1.5 s back (measured).
- `Duration::as_millis` returns `u128` and truncates; there is no rounding variant (measured: `...394123` for `.123456789`).

## C++: `system_clock` counts microseconds on libc++ and nanoseconds on libstdc++, so `.count()` changes meaning by 1000x and libstdc++'s clock ends in 2262

*Stdlib and ecosystem gems*

**Did you know**

The standard fixes `system_clock`'s epoch (C++20: Unix time) but not its tick. Apple clang 21 with libc++ 22 ticks in microseconds (`period` = 1/1000000). GCC 16.2 with libstdc++ ticks in nanoseconds (1/1000000000). So `system_clock::now().time_since_epoch().count()` is a 16-digit number on one compiler and a 19-digit number on the other, for the same instant. The range differs with it: a signed 64-bit count of nanoseconds runs out in 2262, while microseconds last about 292,277 years. Even `high_resolution_clock` is a different clock: an alias of `steady_clock` on libc++, of `system_clock` on libstdc++.

**Show me**

```cpp
// C++20: Apple clang 21 (libc++ 22) and GCC 16.2 (libstdc++)
#include <chrono>
#include <cstdio>
using namespace std::chrono;

int main() {
    // The unit of system_clock is the library's choice, not the standard's.
    std::printf("system_clock tick: 1/%lld s\n", (long long)system_clock::period::den);
    // libc++: 1/1000000 (microseconds)   libstdc++: 1/1000000000 (nanoseconds)

    // So the raw count is a different number for the same instant:
    long long wire_value = system_clock::now().time_since_epoch().count(); // 16 or 19 digits
    std::printf("now().count() = %lld\n", wire_value);

    // Say the unit at the boundary, and say which way to round:
    microseconds before_epoch{-500};
    std::printf("duration_cast: %lld ms\n", (long long)duration_cast<milliseconds>(before_epoch).count()); // 0: toward zero
    std::printf("floor:         %lld ms\n", (long long)floor<milliseconds>(before_epoch).count());         // -1
    std::printf("micros on the wire: %lld\n", (long long)duration_cast<microseconds>(system_clock::now().time_since_epoch()).count());
}
```

**Why it matters**

`.count()` is how a `time_point` leaves the type system: into a database column, a protobuf `int64`, a log line. Write it on Linux, read it on a Mac (or the reverse), and every timestamp is off by a factor of 1000, which lands in 1970 or about 57,000 years from now with no error. The fix is the one C++ makes possible: `duration_cast` to a named unit at the boundary, and use `floor` when the value can be before 1970. Rust's `Duration` and .NET's `DateTime` fix the unit in the type instead (nanoseconds and 100 ns ticks), and JS `Date` is always milliseconds.

**Chew on this**

Which of your binary formats store a raw `.count()`, and which compiler wrote the data you have today? If a value can be negative, which rounding did your conversion pick, and did anyone choose it?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/system_clock
- https://en.cppreference.com/w/cpp/chrono/duration/duration_cast
- https://en.cppreference.com/w/cpp/chrono/duration/floor

**Verified**

Apple clang 21 on this host and `docker run gcc:16`. MSVC was not tested.

**Gotchas**

- `duration_cast<milliseconds>(-500us)` is 0 and `floor` is -1 (measured on both). `round` is also 0 here, because it rounds half to even.
- The libc++ microsecond `system_clock` reaches about 292,277 years either side of 1970, while the libstdc++ nanosecond one ends in 2262 (measured from `time_point::max()`).
- `steady_clock` is nanoseconds on both libraries. On this Mac its epoch is boot time: 14.11 days, against `uptime`'s 14 days 2:36 (measured).

## F#: `DateTime.UtcNow` returns the same value for 98% of back-to-back calls on macOS, so an id built from it repeats

*Idioms and antipatterns*

**Did you know**

A .NET tick is 100 ns, but the clock behind `DateTime.UtcNow` decides how often it moves. On macOS every reading was a whole microsecond (20 of 20), and 98275 of 100000 consecutive pairs were identical. On Linux, 80823 pairs were. An order id built as `$"order-{DateTime.UtcNow.Ticks}"` gave 132 and 155 distinct values out of 1000 in two macOS runs, and 979 on Linux. Measured on FSharp.Core 8.0 / .NET 8.0.8 (macOS) and FSharp.Core 10.1 / .NET 10.0.13 (Linux).

**Show me**

```fsharp
// F#: FSharp.Core 8.0 / .NET 8.0.8 (macOS) and FSharp.Core 10.1 / .NET 10.0.13 (Linux, Docker)
open System

// How often do two back-to-back readings come out identical?
let fn_equal_readings () =
    let readings = Array.init 100_001 (fun _ -> DateTime.UtcNow)
    readings |> Array.pairwise |> Array.filter (fun (earlier, later) -> earlier = later) |> Array.length
printfn "%d of 100000 consecutive UtcNow pairs are equal" (fn_equal_readings ())
// macOS: ~98000 (the clock moves in whole microseconds); Linux: ~81000

// The tick is 100 ns, but on macOS only every tenth tick is ever produced:
let whole_micros = [ for _ in 1 .. 20 -> DateTime.UtcNow.Ticks ] |> List.filter (fun ticks -> ticks % 10L = 0L)
printfn "%d of 20 readings are whole microseconds" whole_micros.Length // macOS 20, Linux a handful (5 in one run)

// So "a new order id from the clock" repeats:
let fn_order_id () = $"order-{DateTime.UtcNow.Ticks}"
let ids = Array.init 1000 (fun _ -> fn_order_id ())
printfn "%d distinct ids out of 1000" (ids |> Array.distinct |> Array.length) // macOS 132 and 155 in two runs, Linux 979
```

**Why it matters**

"The timestamp is unique enough" is an assumption about the clock's resolution and the code's speed at the same time. Both change: a faster CPU, a tighter loop, or moving from Linux to a Mac developer box turns a rare duplicate into a common one. A primary key fails on insert. A dedupe or a file name collides silently. Linux's numbers are better only because its clock is finer, and 979 of 1000 is still not unique. The same rates show up in Rust, C++ and JS (the table at the top), so no language makes the clock an id.

**Chew on this**

Which of your ids, file names or cache keys contain a timestamp and nothing else to break ties? If two arrive in the same tick, which one wins, and would you know?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.datetime.utcnow
- https://learn.microsoft.com/en-us/dotnet/api/system.datetime.ticks

**Gotchas**

- `DateTimeOffset.ToUnixTimeMilliseconds` rounds toward negative infinity: 1969-12-31T23:59:59.9995Z gives -1, and 1970-01-01T00:00:00.0005Z gives 0 (measured on both).
- A 7-digit `"o"` round trip through `ToUnixTimeMilliseconds` drops the last four digits: `.1234567` comes back as `.1230000` (measured).
- `Stopwatch` is the .NET clock for intervals. It is not a source of ids either; it only measures.

## TypeScript: a microsecond `updated_at` read into a `Date` never matches again, so optimistic concurrency refuses every save

*Idioms and antipatterns*

**Did you know**

Postgres `timestamptz` keeps microseconds. node-postgres (`pg` 8.23.1) hands it to you as a JS `Date`, which keeps milliseconds. So the `.887211` you read becomes `.887`. Send that `Date` back as the optimistic-concurrency token in `WHERE updated_at = $2`, and it matches **0 rows**: the save looks exactly like "someone else changed this row" every time. The same token kept as the database's own text matches 1 row. Measured with PostgreSQL 14.24 and Node 22.17.1.

**Show me**

```ts
// TypeScript 6.0.3 types, node-postgres (pg) 8.23.1, Node 22.17.1, PostgreSQL 14.24
import pg from "pg"

const client = new pg.Client({ host: "localhost", port: 55432, user: "postgres", password: "tips", database: "postgres" })
await client.connect()
await client.query("create temp table invoices (id int primary key, total_cents int, updated_at timestamptz not null default clock_timestamp())")
await client.query("insert into invoices (id, total_cents) values (1, 5000)")

const { rows: [invoice] } = await client.query("select id, updated_at, updated_at::text as exact from invoices where id = 1")
console.log(invoice.exact)                     // 2026-10-22 18:27:09.887211+00  (microseconds)
console.log(invoice.updated_at.toISOString())  // 2026-10-22T18:27:09.887Z       (a Date keeps milliseconds)

// Optimistic concurrency: save only if nobody changed the row since we read it.
const fn_save = (token: unknown) => client.query(
    "update invoices set total_cents = 4500, updated_at = clock_timestamp() where id = $1 and updated_at = $2::timestamptz",
    [invoice.id, token])
console.log((await fn_save(invoice.updated_at)).rowCount) // 0: "someone else changed it", every time
console.log((await fn_save(invoice.exact)).rowCount)      // 1: the token kept as text
await client.end()
```

**Why it matters**

What happens next depends on how the caller reads `rowCount: 0`. Code that shows "conflict, please reload" annoys every user on every save. Code that retries loops forever. Code that ignores `rowCount` silently drops the update, which is a lost write. The same mismatch happens with any server-side timestamp finer than milliseconds: Postgres and Rust `SystemTime` on Linux, Go `time.Time`, .NET ticks. An integer `version` column avoids the problem, because nothing rounds an integer.

**Chew on this**

Which of your tables use `updated_at` as the concurrency token, and what does your client do with `rowCount: 0`? If you keep the timestamp, where does it stop being text and start being a `Date`?

**Sources**

- https://node-postgres.com/features/types
- https://www.postgresql.org/docs/14/datatype-datetime.html
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date

**Verified**

Run against `docker run postgres:14`. `pg` typed with a one-line `declare module` instead of `@types/pg`. The printed timestamps are from one run, and later runs print later times.

**Gotchas**

- `JSON.stringify({ updated_at: date })` gives `"2026-10-22T12:00:00.123Z"`, three digits (measured). An API that serializes the `Date` has already dropped the microseconds before the client sees them.
- `Date.parse("1969-12-31T23:59:59.9995Z")` is -1, and `"1970-01-01T00:00:00.0005Z"` is 0 (measured): JS truncates fractions toward negative infinity, like .NET.
- `performance.now()` has sub-millisecond digits (`17.345417`), but it is a monotonic clock since process start, not a wall-clock timestamp.

# The functional angle: converting to a coarser unit is a function with a rounding mode, and below zero the libraries disagree

Draws on the C++ and F# tips, with Rust `jiff` and JS as peer rows. `to_millis: micros -> millis` looks total and obvious. It is a choice between truncating toward zero and flooring toward negative infinity, and the two only differ for values before 1970.

```text
// -500 microseconds (1969-12-31T23:59:59.9995Z) converted to milliseconds, measured
// Rust jiff 0.2.38: Timestamp::from_microsecond(-500)?.as_millisecond()   ->  0
// C++20:            duration_cast<milliseconds>(-500us)                   ->  0
// C++20:            floor<milliseconds>(-500us)                           -> -1
// F# / .NET:        ToUnixTimeMilliseconds()                              -> -1
// JS:               Date.parse("1969-12-31T23:59:59.9995Z")               -> -1
```

| Language | Function | Rounds | What it costs |
| --- | --- | --- | --- |
| Rust | `jiff` `as_millisecond` | toward zero | a pre-1970 instant moves later, into the next millisecond |
| C++ | `duration_cast` / `floor` / `round` | toward zero / down / half-even | the only one that names all three; the default spelling is the truncating one |
| F# / .NET | `ToUnixTimeMilliseconds` | down | consistent with the calendar: 23:59:59.9995 stays in 1969 |
| TypeScript | `Date.parse` | down | the same; and `Math.trunc` vs `Math.floor` at your own call sites decides the rest |

Truncation toward zero is not monotonic in the useful sense: -0.5 ms and +0.5 ms both become 0, so two distinct instants a millisecond apart collapse into one, and the one before 1970 now sorts as if it were in 1970. Flooring keeps the order. No row needs `mut`; the asymmetry is that only C++ makes you see that a choice exists.

Which of your unit conversions can receive a negative value, and which rounding did its library choose for you?

# The security angle: a timestamp is not a nonce, and the clock says so 98% of the time

Draws on the F# tip (Mode B: a clock-derived id works until it does not, but is it safe?) and the table at the top. The language prevents nothing here. Every runtime measured hands back duplicate readings most of the time.

**Duplicate identifiers (CWE-694, use of multiple resources with duplicate identifier; CWE-330 when the value is meant to be unguessable).** An id, a nonce, an idempotency key or a temp-file name made from the clock alone:

```ts
// TypeScript: looks like "a unique key per request". Is the same key for every request in that millisecond.
const idempotency_key = `pay-${Date.now()}`  // 99995 of 100000 back-to-back Date.now() readings were equal (measured)
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | `Date.now()` repeats for a whole millisecond | nothing | `crypto.randomUUID()`, or a counter beside the time |
| F# / .NET | `UtcNow.Ticks` repeats for a microsecond on macOS | nothing | `Guid.NewGuid()`, or a database sequence |
| Rust | `SystemTime::now()` repeats (97884 / 65388 of 100000) | nothing | a `uuid` or an atomic counter; never `SystemTime` alone |
| C++ | `system_clock::now()` repeats (96381 / 65751 of 100000) | nothing | the same |

A clock value is also predictable to anyone who knows roughly when the request was made, which is why a token derived from it fails CWE-330 even when it happens to be unique. There is no control row: no runtime here treats a time as unique, and none should.

Which of your keys would collide if two requests arrived in the same microsecond, and which would be guessable if someone knew the second?

# FAQ

**Is "epoch time" always 1970-01-01?** For Unix time, yes: 1970-01-01T00:00:00Z, and C++20 specifies that `system_clock` measures Unix time. But "epoch" just means the instant a counter starts from, and others are in daily use: NTP counts from 1900-01-01, GPS from 1980-01-06, Windows `FILETIME` from 1601-01-01, and .NET `DateTime.Ticks` from 0001-01-01 (part 2 measured these). A monotonic clock's epoch is unspecified: on this Mac, `steady_clock` counted 14.11 days, matching `uptime` (measured), so its epoch is boot time. A number without its epoch is not a timestamp.

**Is there an incident appendix for this part?** The clearest precision incident is the Patriot clock, already in [part 3's Appendix A](2026-10-21-extra-3-of-6.md): a tick count multiplied by an inexact 0.1, exactly the "every hop rounds" thesis. No second incident with a primary source was found, so this part has none of its own.
