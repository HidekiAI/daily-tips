# Daily Tips: 2026-09-24

## Rust: Rust 1.97 made v0 symbol mangling the default, and your binaries were already mostly v0 before it

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.97.0 (2026-07-09) switched stable rustc to the Rust-specific v0 symbol mangling scheme; legacy mangling is now nightly-only and slated for removal. v0 encodes generic arguments in the symbol itself, so `parse::<u32>` and `parse::<i64>` get readable, distinct names instead of the same path plus two opaque hashes. The part that surprised me: on rustc 1.95, *before* the switch, a hello-world binary already carried 591 v0 symbols and 8 legacy ones, because only your own crate used legacy; the prebuilt std in it was already v0. And Apple's `c++filt` demangles the legacy names but returns a v0 name unchanged.

**Show me**

```rust
// m.rs -- one generic function, two instantiations.
#[inline(never)]
pub fn parse<T: std::str::FromStr>(s: &str) -> Option<T> { s.parse().ok() }

fn main() {
    println!("{:?} {:?}", parse::<u32>("7"), parse::<i64>("-3"));
}

// rustc m.rs ; nm m | grep 1m5parse          (legacy, the pre-1.97 default)
//   __ZN1m5parse17h2220b8792a91c5e7E         <- which one is u32? only the hash knows
//   __ZN1m5parse17hc987b2c661b980b7E
//
// rustc -C symbol-mangling-version=v0 m.rs   (the 1.97+ default)
//   __RINvCskK7mfDs1mzF_1m5parsemEB2_        <- 'm' = u32
//   __RINvCskK7mfDs1mzF_1m5parsexEB2_        <- 'x' = i64
//
// echo <symbol> | c++filt   (Apple, CommandLineTools)
//   legacy -> m::main::h4009bc0cd8b193aa
//   v0     -> printed back unchanged
```

**Why it matters**

Anything in your pipeline that symbolizes Rust frames without Rust's own demangler (an old `perf`, a vendor profiler agent, a crash-report service, a `c++filt` step in a script) now shows `_R...` noise for your code where it used to show paths, and it already did for std frames. Rust's own backtraces use `rustc-demangle`, which handles both, so the break shows up only in the tools that sit outside Rust. C++ never had this split, since Itanium mangling is the one scheme every tool speaks; Go writes readable names straight into its symbol table, generics included (`main.Parse[go.shape.uint32]`, measured on Go 1.24.2).

**Chew on this**

Which of your profiling, crash-reporting, or log-symbolization tools demangle with their own code rather than calling a Rust-aware demangler, and when did you last see one of their flame graphs for a 1.97+ build? If a symbol now carries the type arguments, what does that do to your symbol-size budget for heavily generic code?

**Sources**

- https://blog.rust-lang.org/2026/07/09/Rust-1.97.0/
- https://doc.rust-lang.org/rustc/symbol-mangling/v0.html

**Verified**

rustc 1.95.0 with `-C symbol-mangling-version=v0` standing in for the 1.97 default; `-C symbol-mangling-version=legacy` already required `-Z unstable-options` on 1.95. No 1.97 toolchain was run. Apple `c++filt` from CommandLineTools.

**Related**

- [2026-09-23](2026-09-23.md) - Rust, "Backtrace::capture() is free when disabled, and the real cost of a captured one lands at Display". Symbolization was yesterday's cost; today is what it produces.

## C++: libc++'s std::function keeps a capture inline only if it is 16 bytes and nothrow-copyable, so a missing noexcept costs a heap allocation

*Perf and memory model*

**Did you know**

`std::function` (C++11) is allowed a small-buffer optimization but the standard fixes neither its size nor its conditions. In libc++ (Apple clang 21, `_LIBCPP_VERSION` 220106) the object is 32 bytes and the buffer is `3 * sizeof(void*)`, but that buffer also holds the type-erased wrapper's vtable pointer, so a lambda fits only up to 16 bytes of capture. The second condition is in `__functional/function.h`: `is_nothrow_copy_constructible`. An 8-byte capture whose type has a user-written copy constructor without `noexcept` goes to the heap. C++23's `move_only_function` is not in this libc++ (`__cpp_lib_move_only_function` undefined).

**Show me**

```cpp
#include <functional>
#include <cstdio>
#include <cstdlib>
#include <new>

static int g_allocs = 0;   // count every global operator new
void* operator new(std::size_t n) { ++g_allocs; return std::malloc(n); }
void operator delete(void* p) noexcept { std::free(p); }
void operator delete(void* p, std::size_t) noexcept { std::free(p); }

struct Plain { long a = 1; };                                   // implicit copy: noexcept
struct Handwritten { long a = 1; Handwritten() = default;
                     Handwritten(const Handwritten& o) : a(o.a) {} };  // not noexcept

int main() {
    int before = g_allocs;
    { Plain p; std::function<long()> f = [p] { return p.a; }; }
    std::printf("8-byte capture, implicit copy:    %d alloc\n", g_allocs - before);  // 0

    before = g_allocs;
    { Handwritten h; std::function<long()> f = [h] { return h.a; }; }
    std::printf("8-byte capture, handwritten copy: %d alloc\n", g_allocs - before);  // 1
}
// Size sweep with std::array<char, N> captures: 8 and 16 bytes -> 0 allocs,
// 17, 24, 25 and 32 bytes -> 1 alloc each.
```

**Why it matters**

A callback table, a retry policy, or a per-request continuation stored as `std::function` allocates on construction and on every copy once it crosses either line, and nothing at the call site shows which side it is on. Rust makes the choice explicit instead: `Box<dyn Fn>` always allocates for a capturing closure (measured: 1 allocation for a 4-byte capture) and never for a non-capturing one, because the closure is zero-sized; `impl Fn` never allocates. libstdc++ and MSVC use different buffer sizes and conditions, so a threshold measured on one standard library does not carry to another.

**Chew on this**

Which of your `std::function` members capture a type whose copy constructor you wrote by hand, and would anyone have thought to mark it `noexcept`? If you switched the hot ones to a template parameter or a `function_ref`, what would you give up at the API boundary, and who is holding the callable long enough to need ownership?

**Sources**

- https://en.cppreference.com/w/cpp/utility/functional/function
- https://github.com/llvm/llvm-project/blob/main/libcxx/include/__functional/function.h
- https://en.cppreference.com/w/cpp/utility/functional/move_only_function

**Verified**

Apple clang 21.0.0, libc++ 220106, `-std=c++23 -O2`, allocations counted by replacing `operator new`; the `is_nothrow_copy_constructible` condition read from the shipped header. libstdc++ and MSVC thresholds were not measured; no toolchain for either here.

**Related**

- [2026-09-17](2026-09-17.md) - C++, "std::deque gives you one heap block per element once sizeof(T) reaches 512". Another size threshold in the library that quietly decides your allocation count.
- [2026-09-22](2026-09-22.md) - C++, "GCC 16 made C++20 the default, so [=] capturing this now warns". Same lambda capture list, seen from its lifetime side instead of its size.

## F#: a record expression takes the most recently declared type with those labels, so adding a record changes what existing code builds

*Type system deep cuts*

**Did you know**

When two record types share labels, an unannotated record expression `{ Id = 1; Name = "a" }` is inferred as whichever of them was declared *most recently* at that point, and so is an unannotated function parameter accessed as `x.Name`. The consequence: adding a new record type with overlapping labels retypes existing, unchanged code below it. Code that used to build a `User` now builds a `Tenant`, and a helper that used to take a `User` now demands a `Tenant`. Documented behavior; measured on F# 8, FSharp.Core 8.0.0, .NET 8.0.8.

**Show me**

```fsharp
type User = { Id: int; Name: string }
let mk () = { Id = 1; Name = "a" }            // User: the only candidate so far

type Tenant = { Id: int; Name: string }        // someone adds this later
let mk2 () = { Id = 1; Name = "a" }            // identical text, now a Tenant

let describe x = sprintf "%d:%s" x.Id x.Name   // x inferred as Tenant, the latest

printfn "%s %s" ((mk ()).GetType().Name) ((mk2 ()).GetType().Name)   // User Tenant
printfn "%s" (describe (mk2 ()))               // 1:a
// describe (mk ())                            // error FS0001: expected 'Tenant'
//                                             //   but here has type 'User'

// Pinning it: annotate the parameter, or qualify one label.
let describeUser (x: User) = sprintf "%d:%s" x.Id x.Name
let mk3 () = { User.Id = 1; Name = "a" }       // User, whatever is declared later
```

**Why it matters**

In a service where DTOs and domain records share `Id` / `Name` / `CreatedAt`, the break shows up as an FS0001 in a file nobody touched, or worse, as a helper that silently changed which type it accepts while every call site still compiles because they all moved together. Rust cannot have this problem because a struct literal names its type (`User { id, name }`); TypeScript has the opposite property, since structurally the two types are the same type and nothing needs resolving; C# records are nominal and constructed by name.

**Chew on this**

Which of your record types share two or more labels, and how many unannotated `x.Label` functions sit below the later one in compile order? When the second type was added, did the resulting compile errors get fixed by annotating the helper, or by reordering the declarations until they went away?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/records

**Verified**

`dotnet fsi` (SDK 8.0.401): `User Tenant`, `1:a`, and the FS0001 on the commented line, all measured.

## TypeScript: Effect.all is sequential unless you say otherwise, and by default it stops starting effects at the first failure

*Stdlib and ecosystem gems*

**Did you know**

`Effect.all` looks like `Promise.all` and does the opposite by default: with no `concurrency` option it runs the effects one after another. Three 200 ms tasks took 607 ms through `Effect.all`, 214 ms with `{ concurrency: "unbounded" }`, 405 ms with `{ concurrency: 2 }`, and 202 ms through `Promise.all`. Its default failure mode is also short-circuiting in the sequential sense: when the first effect fails, the other two are never started. With `{ mode: "either" }` all three run. Measured on effect 3.22.2, Node 22.17.1.

**Show me**

```ts
import { Effect } from "effect";

const task = (n: number) =>
  Effect.promise(() => new Promise<number>((r) => setTimeout(() => r(n), 200)));

// Default: sequential. 3 x 200 ms = ~600 ms.
Effect.all([task(1), task(2), task(3)]);

// What Promise.all does, stated explicitly: ~200 ms.
Effect.all([task(1), task(2), task(3)], { concurrency: "unbounded" });

// A bound, which Promise.all cannot express at all: ~400 ms for 3 tasks.
Effect.all([task(1), task(2), task(3)], { concurrency: 2 });

// "inherit" takes the bound from Effect.withConcurrency on an enclosing
// effect, and falls back to "unbounded" when none is set.
Effect.all([task(1), task(2), task(3)], { concurrency: "inherit" });

// Default mode: first failure ends it. Measured: 1 of 3 effects ever started.
// { mode: "either" } runs all 3 and returns an Either per slot.
```

**Why it matters**

A handler ported from `Promise.all` to `Effect.all` keeps its types and its results and triples its latency, and no test that checks the returned values notices. The upside is that the default is the safe one: unbounded fan-out against a database pool is how `Promise.all` takes down a dependency, and Effect makes that a visible choice at the call site. Rust's `futures::join_all` is concurrent and unbounded, and a bound needs `buffer_unordered`; C++ has no standard equivalent at all.

**Chew on this**

Which of your `Effect.all` calls were written expecting `Promise.all` timing, and which ones are fanning out against something that has a connection limit? If an enclosing effect sets `withConcurrency`, which of your inner calls would pick it up through `"inherit"`, and which would ignore it because they never passed the option?

**Sources**

- https://effect.website/docs/concurrency/basic-concurrency/

**Verified**

effect 3.22.2 on Node 22.17.1, timings from `Date.now()` around `Effect.runPromise`, one run. `"inherit"` semantics rest on the documentation; not measured. The `futures::join_all` claim rests on documentation.

# The functional angle: every language here type-erases a closure, and only C++ lets a copy constructor's noexcept decide whether that allocates

Draws on the C++ tip. The shape is the same in all four: take a closure, forget its concrete type, store it behind one uniform callable type.

```rust
let x = 7;
let f: Box<dyn Fn() -> i32> = Box::new(move || x);   // 1 allocation once it captures
let g: Box<dyn Fn() -> i32> = Box::new(|| 1);        // 0: a non-capturing closure is zero-sized
fn take(h: impl Fn() -> i32) -> i32 { h() }          // no erasure, no allocation, one copy of code per closure
```

```cpp
std::function<long()> f = [p = Plain{}] { return p.a; };        // 0: fits 16 bytes, nothrow copy
std::function<long()> g = [h = Handwritten{}] { return h.a; };  // 1: same size, copy ctor not noexcept
```

```fsharp
let make (i: int) = fun () -> i + 1                          // 24 bytes: an FSharpFunc subclass instance
let asDelegate (i: int) = System.Func<int>(fun () -> i + 1)  // 88 bytes: closure plus delegate
```

```ts
const make = (i: number) => () => i + 1;   // a heap-allocated closure object in V8; not measured here
```

| Language | Erased form | Allocation, measured | What it costs |
| --- | --- | --- | --- |
| F# | `unit -> int` closure / `Func<int>` | 24 B / 88 B per capturing closure | always a GC object; crossing into a .NET delegate nearly quadruples it |
| Rust | `Box<dyn Fn>` / `impl Fn` | 1 alloc capturing, 0 non-capturing / none | erasure is opt-in and priced at the type; `impl Fn` pays in code size instead |
| C++ | `std::function` | 0 up to 16 B with nothrow copy, else 1 | the price depends on a property of the captured type that the call site never shows |
| TypeScript | any function value | not measured | every closure is a heap object; there is no unboxed form to choose |

F# is the baseline because the functional form is its default, and it still charges for the capturing closure every time: the cost is intrinsic to erasing a closure, not to any one language. What sets C++ apart is not the price but where the decision comes from. Rust and F# price the type you chose; C++ prices the captured type's copy constructor. Left hanging: which of your .NET interop boundaries converts an F# closure into a delegate on every request?

# The security angle: adding concurrency to Effect.all turns an authorization check into a race with the action it guards

Mode B, interrogating the Effect tip. Its latency fix, `concurrency: "unbounded"`, is right for independent reads and wrong wherever one slot is meant to gate another. This runs in the direction the language does *not* prevent: nothing in the types says slot 0 must finish before slot 1 starts.

```ts
// Looks like a harmless latency fix on a handler that "checks, then acts".
const authorize = Effect.promise(() => sleep(50)).pipe(Effect.zipRight(Effect.fail("forbidden")));
const deleteRecord = Effect.promise(async () => { await sleep(10); deleted = true; });

Effect.all([authorize, deleteRecord]);                               // Left, deleted = false
Effect.all([authorize, deleteRecord], { concurrency: "unbounded" }); // Left, deleted = true
```

Measured on effect 3.22.2, Node 22.17.1: both calls return the `forbidden` failure, so the handler reports a refusal, but with `unbounded` the delete had already committed 40 ms before the check failed. The sequential default was the only thing enforcing the order. CWE-696 (incorrect behavior order) leading to CWE-862 (missing authorization).

F# measured the same way: `Async.Parallel [authorize; deleteRecord]` threw `forbidden` with `deleted = true` (`dotnet fsi`, .NET 8.0.8).

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript / Effect | a `concurrency` option lets the action start before the check fails | sequential by default, so the unsafe form needs an explicit option | sequence the check (`Effect.zipRight`, `Effect.gen`) instead of listing it beside the action. CWE-696 |
| F# | `Async.Parallel` starts every child at once | nothing; there is no sequential default to fall back on | `let!` the check before the action; keep `Async.Parallel` for independent reads |
| Rust | `join!` / `try_join!` poll both futures, so the action can finish first | nothing; `try_join!` stops only once it observes the error (documentation, not measured) | `check().await?` before `act().await`; never both in one join |
| C++ | two `std::async` tasks race the same way | no std combinator at all; the race is hand-built (documentation, not measured) | call `.get()` on the check before launching the action |

TypeScript is the baseline for this class: it is the only row where the safe order is the default and the race needs an opt-in, which is exactly why a latency fix can remove the safeguard without anyone deciding to. Left hanging: which of your parallel combinators list a check and an action side by side, and would your tests see anything but the correct error?

# FAQ

**Can I still get legacy mangling on stable Rust after 1.97?** No; per the release post it is nightly-only and planned for removal. On 1.95 the `legacy` value already required `-Z unstable-options`.

**Does marking the lambda itself `noexcept` help the libc++ case?** No. The check is on the closure type's copy constructor, which follows the captured members' copy constructors.

**Does the F# rule apply across files?** It follows declaration order as the compiler sees it, which in a project is file order, so a record added in an earlier file affects later files that open its module. Reasoned from the ordering rule, not measured in a multi-file project.

**Does `Effect.forEach` share `Effect.all`'s default?** It takes the same `concurrency` option; its default was not measured here.
