# Daily Tips special, part 6 of 15: random numbers, or the generator that shared one state and stopped being random

<!-- special-nav -->
**Specials:** [<- previous: random numbers, part 5 of 15](2026-11-04-extra-5-of-15.md) | [next: random numbers, part 7 of 15 ->](2026-11-04-extra-7-of-15.md)

Not part of the rotation. Earlier parts treated a generator as a function from a seed to a stream. This part has several threads asking the same generator for numbers. A generator is mutable state, and mutable state shared between threads is where "random" turns into "zero", "repeated" or "the same in every worker".

# What happened

**Bug class:** a data race on generator state, found as a Heisenbug: it appears only under load, after hours, and not under a debugger (Heisenbug, CWE-362).

**The story, in plain words:**

A team had written a service that needed random numbers, and had made one `System.Random` object and shared it between its threads. It worked. After about a day, it stopped. From then on `Next()` returned only zero.

They had read the documentation, which says the class is not thread safe. They had understood that to mean that two threads in a race might sometimes get the same random number. They had not understood it to mean that the generator would be broken for good. They asked on an internal Microsoft mailing list, and a Microsoft engineer shared the question and answer on a blog.

The answer was short. "As you note, and as we say in the docs, the class is not threadsafe. That means anything can happen. In this case it looks like the seed is getting corrupted." The fix was a lock around every call, with a pointer to `RandomNumberGenerator` for anything touching security or privacy. The seeded generator keeps its state in an array and indexes (as I understand its algorithm; I did not read the code), so two threads updating that state at once can corrupt it. Today's documentation says the same in one sentence: "If you don't ensure that the Random object is accessed in a thread-safe way, calls to methods that return random numbers return 0."

The quotes:

- "We have created a System.Random object and shared it among multithreads. After calling m_random.Next() for awhile (eg. 1 day), it stops generate any random but only return zero." (the question, on a Microsoft blog whose comments are dated October 2006)
- "As you note, and as we say in the docs, the class is not threadsafe. That means anything can happen. In this case it looks like the seed is getting corrupted." (the answer)
- "Random objects are not thread safe. If your app calls Random methods from multiple threads, you must use a synchronization object to ensure that only one thread can access the random number generator at a time." (current .NET documentation, "Thread safety")

The measurements below reproduce the zeros in a few seconds, and show the other three languages' version of the same mistake.

## Rust: `rand::rng()` cannot be moved to another thread, and four workers seeded with 42 each draw `572990626`

*Type system deep cuts*

**Did you know**

`rand::rng()` returns a `ThreadRng`, which holds an `Rc` and is not `Send`: moving it into `thread::spawn` fails to compile with E0277, "`Rc<UnsafeCell<ReseedingRng<...>>>` cannot be sent between threads safely". The compiler refuses the thing .NET's documentation merely warns about. What it cannot refuse is the same seed in every thread: four workers each calling `StdRng::seed_from_u64(42)` printed `[572990626, 572990626, 572990626, 572990626]`, four copies of one stream. Seeding with `42 + worker_index` gave four different values, and `rand::rng()` called inside each thread gave four different values.

**Show me**

```rust
// rand 0.9.5, rustc 1.99.1
use rand::rngs::StdRng;
use rand::{RngCore, SeedableRng};
use std::thread;

fn main() {
    let first_values: Vec<u32> = (0..4)
        .map(|_| thread::spawn(|| StdRng::seed_from_u64(42).next_u32())) // the same seed in every worker
        .map(|handle| handle.join().unwrap())
        .collect();
    println!("four workers, seed 42 each: {:?}", first_values);

    let distinct_values: Vec<u32> = (0..4u64)
        .map(|worker_index| thread::spawn(move || StdRng::seed_from_u64(42 + worker_index).next_u32()))
        .map(|handle| handle.join().unwrap())
        .collect();
    println!("four workers, seed 42 + worker index: {:?}", distinct_values);

    let thread_local_values: Vec<u32> = (0..4)
        .map(|_| thread::spawn(|| rand::rng().next_u32())) // each thread gets its own OS-seeded generator
        .map(|handle| handle.join().unwrap())
        .collect();
    println!("four workers, rand::rng(): {:?}", thread_local_values);

    // let mut_rng = rand::rng();
    // thread::spawn(move || { let mut mut_moved = mut_rng; mut_moved.next_u32() }); // does not compile: ThreadRng is not Send
}
```

Output: `four workers, seed 42 each: [572990626, 572990626, 572990626, 572990626]`, then `four workers, seed 42 + worker index: [572990626, 3968477430, 1973064695, 2899840862]`, then four different values from `rand::rng()` (they change every run). Uncommenting the last two lines gives `error[E0277]: Rc<UnsafeCell<ReseedingRng<rand_chacha::chacha::ChaCha12Core, OsRng>>> cannot be sent between threads safely`.

**Why it matters**

The compile error closes the shared-state failure: no `Send` generator can be handed to two threads without a lock. The per-worker seed is the remaining hole, and the type system says nothing about it. Seeding with `base + index` gives different streams, but they are adjacent seeds, not independent ones, and the rand book lists the options: `rng()` in each worker, a master generator to seed a custom one per worker, or a single master seed with a stream number per work unit, and warns not to clone generators for workers (I read the book, I did not run these).

**Chew on this**

Is the seed of each of your workers derived from one parent in a way you could write down? If a worker restarts, does it get its own stream again or repeat its first one?

**Sources**

- https://docs.rs/rand/latest/rand/fn.rng.html
- https://rust-random.github.io/book/guide-parallel.html

**Verified**

rustc 1.99.1, rand 0.9.5. The E0277 text is the compiler's output from a build with the last two lines uncommented. The parallel-seeding advice is from the rand book, which I did not run.

**Gotchas**

- `StdRng` itself is `Send`, so one can be moved to a thread; two threads sharing one needs a `Mutex`, and then it is as slow as a lock.
- `rand::rng()` reseeds from the operating system periodically; that is its documentation, not my measurement.

## C++: four threads sharing one `std::mt19937` with no lock drew a different total every run, and ThreadSanitizer on GCC 16.2 reported the data race on every run

*Idioms and antipatterns*

**Did you know**

If four threads each take 100,000 draws from one shared `mt19937` seeded with 42, the sum of all 400,000 values should be the same every run whatever order the threads interleave, because the engine emits one fixed sequence and each draw is consumed once. It is not: on GCC 16.2 the three runs gave `859625108963803`, `861527258666509` and `859004342400979`, and the single-threaded sum of the first 400,000 draws is `859719340311805`. On libc++ the three runs were `860415186728992`, `857930231954373` and `858300065275431`. Draws were duplicated or skipped. Under `-fsanitize=thread` GCC reported the data race 14 times at the draw line in one run and 8 times in another.

**Show me**

```cpp
// g++ -std=c++23 -O2 -pthread shared.cpp
// clang++ -std=c++23 -stdlib=libc++ -O2 -pthread shared.cpp
// race report (GCC): g++ -std=c++23 -O1 -g -fsanitize=thread -pthread shared.cpp && ./a.out
#include <cstdint>
#include <iostream>
#include <random>
#include <thread>
#include <vector>

int main() {
    constexpr int THREAD_COUNT = 4;
    constexpr int DRAWS_PER_THREAD = 100000;
    std::mt19937 shared_engine(42); // one engine, no lock
    std::vector<std::uint64_t> sums(THREAD_COUNT, 0);
    std::vector<std::thread> workers;
    for (int thread_index = 0; thread_index < THREAD_COUNT; ++thread_index) {
        workers.emplace_back([&, thread_index] {
            for (int draw = 0; draw < DRAWS_PER_THREAD; ++draw) sums[thread_index] += shared_engine(); // data race
        });
    }
    for (std::thread& worker : workers) worker.join();
    std::uint64_t total = 0;
    for (std::uint64_t sum : sums) total += sum;
    std::cout << "sum of all draws: " << total << "\n";

    std::mt19937 serial_engine(42); // the same 400000 draws, one thread
    std::uint64_t serial_total = 0;
    for (int draw = 0; draw < THREAD_COUNT * DRAWS_PER_THREAD; ++draw) serial_total += serial_engine();
    std::cout << "serial sum of the first 400000 draws: " << serial_total << "\n";
}
```

Output: a first line that changes on every run and a second line that does not, `859719340311805`. The first TSan run printed `WARNING: ThreadSanitizer: data race` 14 times with `SUMMARY: ThreadSanitizer: data race /w/shared.cpp:15 in operator()`.

**Why it matters**

The invariant (the multiset of consumed draws) is checkable without being able to see the race. A sum, a count of distinct values or a checksum of the consumed stream turns "I do not trust it" into a test. The standard says concurrent calls on one engine are a data race and therefore undefined behavior, so what you see here is one of the legal outcomes and on another build it could be a crash.

**Chew on this**

Which of your generators is a global or a static captured by threads? Can you state an invariant of its output that a test could check?

**Sources**

- https://eel.is/c++draft/res.on.data.races
- https://eel.is/c++draft/rand.req.eng

**Verified**

GCC 16.2.0 with `-O2` and with `-fsanitize=thread`, clang 19.1.7 with libc++ at `-O2`, three runs each. ThreadSanitizer on clang could not be linked in that image (the runtime was missing), so the report counts are GCC's only. The standard citations are from the draft, not run.

**Gotchas**

- The fix is a `thread_local` engine seeded per thread, not a mutex around a shared one; a mutex fixes the race and keeps the contention.
- The totals differ by well under one percent, so the corruption is invisible to a glance at the numbers.

## F#: eight threads sharing one `Random(42)` produced zeros, 4,442 in one run and 10.7 million of 16 million in another, and a shared `Random()` and `Random.Shared` produced none

*Idioms and antipatterns*

**Did you know**

The question that opened this part reproduces on .NET 10 in seconds. Eight threads each took 2 million draws from one shared `Random(42)`. A uniform `Next()` returns 0 about once in 2^31 draws, so seven thousandths of a zero was expected for 16 million. One run returned 4,442 zeros and the next run 10,683,847, two thirds of everything drawn. A shared `Random()` (no seed) returned none, and so did `Random.Shared`. The seeded generator is the legacy algorithm from part 1, which keeps its state in an array, and that array is what the race damages.

**Show me**

```fsharp
// .NET 10.0.14, dotnet fsi --optimize+
open System
open System.Threading

let thread_count: int = 8
let draws_per_thread: int = 2000000

let fn_count_zeros (label: string) (fn_next: unit -> int) : unit =
    let zero_counts: int[] = Array.zeroCreate thread_count
    let threads: Thread[] =
        Array.init thread_count (fun thread_index ->
            Thread((fun () ->
                for _ in 1 .. draws_per_thread do
                    if fn_next () = 0 then zero_counts.[thread_index] <- zero_counts.[thread_index] + 1), 1024 * 1024))
    threads |> Array.iter (fun worker -> worker.Start())
    threads |> Array.iter (fun worker -> worker.Join())
    printfn "%-22s zeros out of %d draws: %d" label (thread_count * draws_per_thread) (Array.sum zero_counts)

let shared_seeded: Random = Random(42)
fn_count_zeros "shared Random(42)" (fun () -> shared_seeded.Next())
let shared_default: Random = Random()
fn_count_zeros "shared Random()" (fun () -> shared_default.Next())
fn_count_zeros "Random.Shared" (fun () -> Random.Shared.Next())
```

Output (the first run; the second printed 10683847): `shared Random(42) zeros out of 16000000 draws: 4442`, `shared Random() zeros out of 16000000 draws: 0`, `Random.Shared zeros out of 16000000 draws: 0`. The count varies enormously per run; "not zero" does not.

**Why it matters**

The seeded `Random` is the one people use in tests and replays (part 1), so the corruption shows up exactly where the code was thought to be deterministic. A shared `Random()` did not corrupt in this run, which is an implementation fact about the unseeded generator that the documentation does not promise: the docs say only that `Random` is not thread safe. `Random.Shared` is documented as thread-safe.

**Chew on this**

Is there a `Random(seed)` in a static field anywhere in your code? Did anyone write that "not thread safe" means "wrong sometimes" or "wrong forever"?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.random (the "Thread safety" section)
- https://learn.microsoft.com/en-us/archive/blogs/brada/random-next-always-return-0

**Verified**

.NET SDK 10.0, `dotnet fsi --optimize+`, one run. That a shared unseeded `Random()` is safe in practice is what this run shows, not a guarantee. That `Random.Shared` is thread-safe is the documentation.

**Gotchas**

- The race is probabilistic; fewer threads or fewer draws may print zero zeros.
- The array-and-indexes explanation of the legacy generator is the shape of the algorithm as I understand it (a subtractive generator); I did not read the code for this part.

## TypeScript: four Node workers' first `Math.random()` all differ by default, and all equal `0.6159659788862542` under `--random-seed=42`

*Stdlib and ecosystem gems*

**Did you know**

JavaScript has no shared-state race on `Math.random`: each worker thread has its own generator. In Node 26.13 four workers printed four different first values by default (`0.4285 0.1020 0.9757 0.7577` in the run below). Under `node --random-seed=42` all four printed `0.6159659788862542`, the same value as the main thread, so every thread replays the same stream. Part 1 measured one worker; this is four.

**Show me**

```ts
// Node 26.13.0: save as workers.mts, run with node workers.mts and with node --random-seed=42 workers.mts
import { Worker, isMainThread, parentPort } from "node:worker_threads"

const const_worker_count: number = 4
if (isMainThread) {
    const const_first_values: Promise<number>[] = Array.from({ length: const_worker_count }, () =>
        new Promise<number>((resolve) => {
            const worker: Worker = new Worker(new URL(import.meta.url))
            worker.once("message", (first_value: number) => { resolve(first_value); void worker.terminate() })
        }))
    console.log("main thread  :", Math.random())
    console.log("four workers :", (await Promise.all(const_first_values)).join(" "))
} else {
    parentPort?.postMessage(Math.random())
}
```

Output without the flag: `main thread  : 0.4727642179098738` and four different values. With `--random-seed=42`: `main thread  : 0.6159659788862542` and `four workers : 0.6159659788862542 0.6159659788862542 0.6159659788862542 0.6159659788862542`.

**Why it matters**

The language removes the data race by giving each thread its own state, and trades it for the same-seed problem from Rust: if the seed is chosen globally, every worker gets the same one. A test run that passes `--random-seed` to make a flaky test reproducible also makes four workers do identical "random" work, and the failure that reproduced in one thread may not in four.

**Chew on this**

If a seed flag made your tests reproducible, how many of your workers did it also make identical? Does anything in your pool check that workers differ?

**Sources**

- https://nodejs.org/api/worker_threads.html
- https://nodejs.org/api/cli.html (V8 options)

**Verified**

Node v26.13.0 in the `node:lts` image, one run each. The flag's effect on workers is measured; that each worker has its own generator by default follows from the four different values, not from reading V8.

**Gotchas**

- `--random-seed` is refused in `NODE_OPTIONS` (part 1), so the flag must be on the command line, and workers inherit it as shown.
- The default values differ per run; the equality under the flag is the claim.

# The functional angle: share nothing, and make the stream a value passed in

Draws on all four tips. The race exists because a generator is hidden mutable state. The three languages' answers differ in who removes the mutation: the type system (Rust), a fresh object per thread (TypeScript) or a lock (everything else).

```rust
// Rust: pass the generator explicitly and split it, so no two workers share state
use rand::{rngs::StdRng, Rng, SeedableRng};
fn fn_worker_streams(mut_parent: &mut StdRng, worker_count: usize) -> Vec<StdRng> {
    (0..worker_count).map(|_| StdRng::from_rng(&mut *mut_parent)).collect()
}
```

| Language | How shared mutable state is stopped | Measured result of ignoring it |
| --- | --- | --- |
| Rust | `ThreadRng` is `!Send`, a compile error | 4 identical streams when the same seed is passed to each worker |
| C++ | nothing; a data race is undefined behavior | total differs every run, 8 to 14 TSan reports on GCC |
| F# | documentation only ("not thread safe") | 4,442 and 10.7 million zeros in 16 million draws (two runs, seeded) |
| TypeScript | each worker has its own generator | all 4 workers identical under `--random-seed` |

C++ is the baseline for this angle because the standard states the rule and the language does not enforce it. Which of these four would your code review catch first?

# The security angle: duplicated randomness is a repeated nonce

Draws on all four tips. Mode B (what the language does not prevent). Bug classes: CWE-362 (race condition), CWE-330 and CWE-323 (reusing a nonce or key).

```ts
// TypeScript: workers that each derive an identifier from the same seeded stream produce the same identifier
// node --random-seed=42 server.mjs   (every worker thread: Math.random() === 0.6159659788862542 first)
```

A generator shared without a lock, or a stream replayed in every worker, hands the same value to two requests. For an identifier that is a collision. For a nonce or an initialization vector it is the failure part 8 measures.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| Rust | every worker gets seed 42 (measured) | refuses to share `ThreadRng` | derive worker seeds from a parent |
| C++ | duplicated and skipped draws (measured) | nothing | `thread_local` engines, seeded apart |
| F# | zeros from a shared seeded `Random` (measured) | `Random.Shared` is thread-safe (documentation) | one instance per thread, or the shared one |
| TypeScript | identical streams under a seed flag (measured) | refuses the flag in `NODE_OPTIONS` | no seed flag outside tests |

F# is the baseline: the failure there is silent and permanent, which is the worst combination for a security property. What would tell you, in production, that your generator had started returning zero?

# FAQ

**Why a sum as the C++ check?**
The sum of a fixed set of 400,000 values does not depend on the order they are consumed in, so any difference means a value was repeated or lost.

**Does a lock around .NET's `System.Random` (the story and the F# tip) fix it?**
It fixes the corruption, as the Microsoft answer says. It adds contention; per-thread instances avoid that.

**Is Rust's `rand::rng()` safe to call from every thread?**
Each call returns the calling thread's own generator (documentation), and it is not `Send`, so the compiler stops it crossing threads.
