# Daily Tips special, part 4 of 14: small bugs that exploded, or an event that happened before anyone was listening

Not part of the rotation. Part 4 of the fourteen-part special on real incidents: [Mars Polar Lander](https://ntrs.nasa.gov/api/citations/20000032458/downloads/20000032458.pdf), lost on landing in December 1999. Each tip below is a mechanism that keeps an event from before the listener started, or drops it, and the language decides which.

# What happened

**Bug class:** Bohrbug, in this special's classification: the NASA report calls it the most probable cause, the JPL board cites compelling evidence, and tests showed the leg-deploy transient was almost certain to reach the software. The anti-pattern is a latched event that the code which enables listening never clears.

From the NASA Mars Program Independent Assessment Team Report (2000-03-14):

```text
The most probable cause of the MPL failure is premature shutdown of the lander
engines due to spurious signals generated at lander leg deployment during descent.
```

The report puts leg deployment at "Entry +257 seconds" and says "Initial sensor interrogation is at an altitude of 40 meters", and that the failure "resulted from inadequate checks and balances that permitted an incomplete systems test and allowed a significant software design flaw to go undetected."

From the testimony of John Casani, Chairman of the JPL Special Review Board, before the House Science Committee (headed April 13, 2000; SpaceNews page dated April 12, 2000):

```text
The software logic accepts this transient signal as a valid touchdown event if it
persists for two consecutive readings of the sensor.
```

```text
The software - intended to ignore touchdown indications prior to the enabling of the
touchdown sensing logic - was not properly implemented, and the spurious touchdown
indication was retained. The touchdown sensing logic is enabled at 40 meters altitude,
and the software would have issued a descent engine thrust termination at this time in
response to a (spurious) touchdown indication.
```

The testimony gives about 13 m/s at 40 m and an impact of "approximately 22 meters per second (the nominal touchdown velocity is 2.4 meters per second)". Recomputed with Mars gravity at 3.71 m/s^2: `sqrt(13^2 + 2 * 3.71 * 40)` is 21.58 m/s, which matches. The JPL board's own report (JPL D-18709) could not be fetched here, so the software detail rests on its chairman's testimony. The lander sent no entry, descent or landing telemetry, so no flight data confirms the scenario. The tips use 1500 m as an example altitude for the leg-deploy reading; the sources give only "Entry +257 seconds".

## Rust: an `mpsc` channel keeps every event sent before you start receiving, so the first touchdown you read can be the leg-deploy transient

*Stdlib and ecosystem gems*

**Did you know**

`std::sync::mpsc::channel` buffers without limit, so a value sent while nobody was receiving is still the first thing `try_recv` returns, however long ago it was sent. A descent loop that starts reading at 40 m therefore reads the leg-deploy reading first (1500 m in the example). Enabling the listener has to discard what arrived before it, for example `try_iter().count()` to drain the queue, which measured 1 stale reading and then `Err(Empty)`. Measured on rustc 1.99.1.

**Show me**

```rust
// rustc 1.99.1, Debian.
use std::sync::mpsc;

fn main() {
    const LEG_DEPLOY_TRANSIENT_ALTITUDE_M: u32 = 1500; // the spurious reading the legs produce
    let (touchdown_sensor_sender, descent_loop_receiver) = mpsc::channel::<u32>(); // altitude in m at each touchdown reading

    touchdown_sensor_sender.send(LEG_DEPLOY_TRANSIENT_ALTITUDE_M).unwrap(); // leg-deploy transient, long before sensing is enabled

    // At 40 m the descent loop starts listening, and the queue still holds the transient.
    println!("{:?}", descent_loop_receiver.try_recv()); // Ok(1500): read as touchdown

    // Enabling has to discard what arrived while nobody was listening.
    touchdown_sensor_sender.send(LEG_DEPLOY_TRANSIENT_ALTITUDE_M).unwrap();
    let stale_reading_count = descent_loop_receiver.try_iter().count();
    println!("{stale_reading_count} {:?}", descent_loop_receiver.try_recv()); // 1 Err(Empty)
}
```

**Why it matters**

Any service that starts a consumer after its producer, a health checker after a config watcher or a worker after its queue fills, sees the backlog as current. Keeping messages is the point of a channel, so the bug is not the channel; it is an enable step that treats "first message after I started" as "first message after the condition I care about".

**Chew on this**

Which of your consumers start after their producer, and what does the first message they read mean? If a reading carried the time it was taken, would your enable step compare it, or just take the next one?

**Sources**

- https://doc.rust-lang.org/std/sync/mpsc/fn.channel.html
- https://doc.rust-lang.org/std/sync/mpsc/struct.Receiver.html#method.try_iter

**Verified**

Run in `rust:1-trixie` (Debian), rustc 1.99.1.

**Gotchas**

- A rendezvous channel cannot hold the transient: `sync_channel(0).try_send(1500)` with no receiver waiting returned `Err(Full)`.
- A bounded channel still can: `sync_channel(1)` accepted the first `try_send` and refused only the second, so the one transient that matters is kept.
- Draining with `try_iter()` takes only what is queued at that moment: a reading sent after the drain (1400) was still what the next `try_recv` returned.

## C++: the predicate form of `condition_variable::wait` is a latch, so a flag set before you wait counts as the event you were waiting for

*Idioms and antipatterns*

**Did you know**

A `notify_one` with no thread waiting is lost, which is why the standard advice is to wait with a predicate: `sensor_signal.wait_for(descent_loop_lock, timeout, [&] { return is_touchdown_flagged; })` checks the flag first and returns at once if it is already true. That is exactly what turns a flag set during leg deployment into a touchdown at 40 m: the predicate wait returned `true` after 0 us, with no new notify. The plain `wait_for` without a predicate timed out after 205 ms instead, because its notify had been lost. Measured on Debian clang 19.1.7 and GCC 16.2 (C++20, Docker); additionally checked on macOS (Apple clang 21.0.0).

**Show me**

```cpp
// C++20, Debian clang 19.1.7 and GCC 16.2: same output.
#include <chrono>
#include <condition_variable>
#include <cstdio>
#include <mutex>

int main() {
    std::mutex sensor_mutex;
    std::condition_variable sensor_signal;
    bool is_touchdown_flagged = false;

    {   // leg deployment: the sensor sets the flag and notifies, and nobody is waiting yet
        std::lock_guard<std::mutex> sensor_lock_guard(sensor_mutex);
        is_touchdown_flagged = true;
    }
    sensor_signal.notify_one();  // lost: there is no waiter

    // At 40 m the descent loop waits. The predicate form checks the flag first.
    std::unique_lock<std::mutex> descent_loop_lock(sensor_mutex);
    bool has_landed = sensor_signal.wait_for(descent_loop_lock, std::chrono::milliseconds(200),
                                         [&] { return is_touchdown_flagged; });
    std::printf("%d\n", has_landed);  // 1: the transient counts as touchdown

    // The enable step must clear the flag before it starts waiting.
    is_touchdown_flagged = false;
    has_landed = sensor_signal.wait_for(descent_loop_lock, std::chrono::milliseconds(200),
                                    [&] { return is_touchdown_flagged; });
    std::printf("%d\n", has_landed);  // 0: timed out, nothing new happened
}
```

**Why it matters**

The predicate exists to stop lost wakeups and spurious wakeups, and it is the right default. It also means the flag is state, not an event: whatever set it, whenever, satisfies the wait. Rust's `mpsc` keeps a queued value the same way, as the Rust tip measured; the difference is that the channel keeps every reading and the flag keeps only "some reading happened".

**Chew on this**

Which of your condition-variable flags are set by more than one kind of event, and which waits care about only one of them? Where in your code is the step that clears a flag, and does it run before the wait it is meant to protect?

**Sources**

- https://en.cppreference.com/w/cpp/thread/condition_variable/wait_for
- https://en.cppreference.com/w/cpp/thread/condition_variable/notify_one

**Verified**

Compiled with `-std=c++20 -Wall -Wextra` on Debian clang 19.1.7 (`debian-clang:trixie`, libstdc++ and also `-stdlib=libc++`) and GCC 16.2.0 (`gcc:latest`), both in Docker on Debian aarch64; additionally checked on macOS (Apple clang 21.0.0). The timings came from a separate probe with `steady_clock` (re-measured on Linux: GCC 16.2 0 us and 205 ms, Debian clang 19.1.7 0 us and 203 ms).

**Gotchas**

- A predicate that clears the flag, `[&] { return std::exchange(is_touchdown_flagged, false); }`, consumes it: the first wait returned 1 and a second wait on the same flag returned 0, so two waiters see one event between them.

## F#: `Event` drops a trigger that nobody heard, and `MailboxProcessor` keeps a post sent before it started

*Stdlib and ecosystem gems*

**Did you know**

F# ships both policies side by side. `Event<int>().Trigger 1500` with no subscriber is gone: a handler added afterwards heard nothing. A `MailboxProcessor` posted to before `Start` keeps the message in its queue (`CurrentQueueLength` was 1), and its first `Receive` returned 1500. Measured on .NET 10.0.403.

**Show me**

```fsharp
// SDK 10.0.403 (F# 10, FSharp.Core 10.1.0.0, .NET 10.0.14).
// Event: a Trigger with no subscriber is gone.
let touchdown_sensor_event = Event<int>()
touchdown_sensor_event.Trigger 1500                                    // leg-deploy transient, nobody subscribed
let heard_altitudes_m = ResizeArray<int>()
touchdown_sensor_event.Publish.Add heard_altitudes_m.Add
printfn "Event heard: %A" (List.ofSeq heard_altitudes_m)           // []

// MailboxProcessor: a Post before Start waits in the queue.
let descent_agent =
    new MailboxProcessor<int>(fun descent_inbox -> async {
        let! first_received_altitude_m = descent_inbox.Receive()
        printfn "agent read touchdown at %d m" first_received_altitude_m })   // 1500
descent_agent.Post 1500                                // posted before the agent starts
printfn "queued before Start: %d" descent_agent.CurrentQueueLength   // 1
descent_agent.Start()
System.Threading.Thread.Sleep 200
```

**Why it matters**

Switching a component from events to an agent, or back, silently flips whether early signals count. The MPL code needed the drop behaviour for readings before 40 m and the keep behaviour for readings after it; neither primitive gives both, so the enable step has to supply the boundary. The Rust and C++ tips above show the keeping side in two more forms.

**Chew on this**

Which of your F# components would behave differently if an `Event` became a `MailboxProcessor` or the reverse? When an agent starts, does any of your code look at `CurrentQueueLength` before it trusts the first message?

**Sources**

- https://fsharp.github.io/fsharp-core-docs/reference/fsharp-control-fsharpmailboxprocessor-1.html
- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/members/events

**Verified**

Run with `dotnet fsi` in `mcr.microsoft.com/dotnet/sdk:10.0` (Ubuntu 24.04, not Debian).

**Gotchas**

- Two posts before `Start` gave `CurrentQueueLength` 2: the queue keeps all of them, not just the latest.

## TypeScript: a resolved `Promise` answers every later `await` at once, so a touchdown promise resolved by the transient lands the descent loop at 40 m

*Idioms and antipatterns*

**Did you know**

A `Promise` resolves once and remembers: awaiting it later returns the stored value immediately, so it behaves as a latch. A touchdown promise resolved by the leg-deploy transient makes the descent loop's `await touchdown` at 40 m return 1500 at once. A Node `EventEmitter` is the opposite: an `emit` with no listener is gone, and a listener added afterwards timed out. Measured on Node 26.13.0.

**Show me**

```ts
// TypeScript, Node 26.13.0 (LTS, strips types natively), tsc 7.0.2 --strict.
import { EventEmitter } from "node:events"

const fn_timeout_after_ms = (delay_ms: number): Promise<"timeout"> =>
    new Promise((resolve) => setTimeout(() => resolve("timeout"), delay_ms))

const LEG_DEPLOY_TRANSIENT_ALTITUDE_M = 1500 // the spurious reading the legs produce

// A Promise is a latch: once resolved, every later await gets the value at once.
let fn_report_touchdown: (altitude_m: number) => void = () => {}
const touchdown_latch: Promise<number> = new Promise((resolve) => { fn_report_touchdown = resolve })
fn_report_touchdown(LEG_DEPLOY_TRANSIENT_ALTITUDE_M) // leg-deploy transient

// An EventEmitter is not: an emit with no listener is gone.
const touchdown_emitter = new EventEmitter()
touchdown_emitter.emit("touchdown", LEG_DEPLOY_TRANSIENT_ALTITUDE_M)
const fn_next_touchdown = (): Promise<number> => new Promise((resolve) => touchdown_emitter.once("touchdown", resolve))

// At 40 m the descent loop starts listening.
console.log(await Promise.race([touchdown_latch, fn_timeout_after_ms(100)]))          // 1500: read as touchdown
console.log(await Promise.race([fn_next_touchdown(), fn_timeout_after_ms(100)])) // timeout
```

**Why it matters**

Promises are the usual way to say "wait until X happens", and the latch behaviour is usually what you want. It is wrong for a condition that only counts after an enable step, because nothing in the type says when the promise resolved. A type check cannot help: `Promise<number>` is the same type whether it resolved a second ago or at 1500 m.

**Chew on this**

Which of your long-lived promises stand for "the first time X happened", and which are awaited by code that means "X happened after I started waiting"? Where would you put the timestamp that tells the two apart?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise
- https://nodejs.org/api/events.html#emitteremiteventname-args

**Verified**

Run on Node 26.13.0, the current LTS (`node:lts-trixie`, Debian), and type-checked with tsc 7.0.2 `--strict` and `@types/node` 26.6.6.

**Gotchas**

- `events.once(touchdown_emitter, "touchdown")`, Node's promise-returning helper, drops the early emit too: it timed out after an `emit` that came first.
- `AbortSignal` is a latch with a non-latching listener: after `abort()`, `signal.aborted` was `true`, but an `"abort"` listener added afterwards never ran.

# The functional angle: an event is a value with a time, and dropping the time is what lets an old one look new

Draws on all four tips. Every mechanism above passes the reading on without the moment it was taken, so the listener cannot tell "before I was enabled" from "after". The functional fix is to carry the time, or an epoch, in the value, and filter on it.

```rust
// Rust, edition 2021 or later: tag each reading with the epoch it belongs to, and drop older epochs.
#[derive(Clone, Copy)]
struct Reading { epoch: u32, altitude_m: u32 }

fn first_touchdown_altitude_m(readings: impl Iterator<Item = Reading>, enabled_epoch: u32) -> Option<u32> {
    readings.filter(|reading| reading.epoch >= enabled_epoch).map(|reading| reading.altitude_m).next()
}
// first_touchdown_altitude_m([Reading { epoch: 0, altitude_m: 1500 }, Reading { epoch: 1, altitude_m: 0 }].into_iter(), 1) == Some(0)
```

```ts
// TypeScript: the same filter over timestamped readings.
type Reading = { taken_at_ms: number; altitude_m: number }
const fn_first_touchdown_altitude_m = (readings: Reading[], enabled_at_ms: number): number | undefined =>
    readings.find((reading) => reading.taken_at_ms >= enabled_at_ms)?.altitude_m
```

| Language | Keeps the early event | Drops it | What carries the time |
| --- | --- | --- | --- |
| Rust | `mpsc::channel`, `sync_channel(1)` | `sync_channel(0)` | nothing; add an epoch to the message |
| C++ | a predicate `wait` on a flag | a plain `wait` (the notify is lost) | nothing; the flag is a bool |
| F# | `MailboxProcessor` | `Event` | nothing; add it to the message type |
| TypeScript | `Promise`, `AbortSignal.aborted` | `EventEmitter`, `events.once` | nothing; resolve with a timestamped value |

F# is the baseline here because it is the one row that ships both policies in its own core library, which shows the choice is about the mechanism, not the language. In every row the fix is the same shape: a value that carries when it happened, filtered against when listening began.

The snippets in this section were run: the Rust `first_touchdown_altitude_m` returned `Some(0)` for the commented input, and the TypeScript version returned the same for the equivalent array on Node 26.13.0.

Which of your messages, flags or promises would you have to change to carry the moment they were produced?

# The security angle: a stale grant that arrives first is a grant

Draws on the C++ and TypeScript tips, with Rust and F# as controls. Runs in both directions: every language here lets you build an enable step that discards early events, and none of them does it for you.

```ts
// TypeScript. Looks like "wait until the user is approved". The approval is from an earlier session.
const fn_load_cached_approval = (): Promise<string> => Promise.resolve("alice") // resolved at last login
const unlocked_user_ids: string[] = []
const fn_unlock = (user_id: string): void => { unlocked_user_ids.push(user_id) }
const cached_approval_promise: Promise<string> = fn_load_cached_approval()
async function fn_open_vault(user_id: string): Promise<void> {
    const approved_user_id = await cached_approval_promise // returns at once with the stale value
    if (approved_user_id === user_id) fn_unlock(user_id)
}
await fn_open_vault("alice")
console.log("unlocked without a new approval:", unlocked_user_ids)
// unlocked without a new approval: [ 'alice' ]
```

The class is [CWE-1464](https://cwe.mitre.org/data/definitions/1464.html), improper session invalidation: a cached approval from a session that should have ended still answers a later check.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | a resolved promise answers every later await | nothing: a promise has no age | resolve with a timestamp or session id and check it |
| C++ | a predicate wait accepts a flag set before it | prevents lost wakeups, which is the latch | clear the flag at the boundary |
| Rust | a channel delivers messages from before the receiver started | nothing | drain, or tag messages with an epoch |
| F# | a `MailboxProcessor` processes posts from before `Start` | nothing | the same |

TypeScript is the baseline because its latch is the most common way to express "wait until approved" in application code. The sample was run on Node 26.13.0 and type-checked with tsc 7.0.2 `--strict`.

Which of your "wait until allowed" steps could be satisfied by a permission granted before the current request began?
