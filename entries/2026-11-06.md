## Rust: VecDeque::retain_back(3) keeps the last three, truncate(3) keeps the first three, and the name was changed after its FCP had closed

*New discoveries and currently popular patterns*

**Did you know**

Rust 1.99.0 (2026-10-01) stabilized `VecDeque::retain_back(len)`: it keeps the last `len` elements and drops the front, the mirror image of `truncate(len)`. It spent a year unstable as `truncate_front` (tracking issue #140667). The libs-api FCP closed on 2026-05-08 and the rename landed in the stabilization PR, merged 2026-07-09; one reviewer then wrote that it "feels like the name change was snuck in hastily post-FCP". It is the "keep the newest N log lines" call that ring buffers used to write as a `pop_front` loop.

**Show me**

```rust
use std::collections::VecDeque;

fn main() {
    let log_lines: VecDeque<u32> = (1..=6).collect();

    let mut mut_newest = log_lines.clone();
    mut_newest.retain_back(3); // keeps the BACK: [4, 5, 6]
    let mut mut_oldest = log_lines.clone();
    mut_oldest.truncate(3); // keeps the FRONT: [1, 2, 3]
    println!("{mut_newest:?} {mut_oldest:?}");

    // A length that is too long is a no-op, not a panic.
    let mut mut_short_log: VecDeque<u32> = (1..=2).collect();
    mut_short_log.retain_back(1_000);
    println!("{mut_short_log:?}"); // [1, 2]

    // The pre-1.99 one-liner for the same trim, and why it is not the same.
    const KEEP_COUNT: usize = 1_000;
    let drain_end: usize = mut_short_log.len() - KEEP_COUNT; // 2 - 1000: debug panics here
    mut_short_log.drain(..drain_end); // release: drain_end wrapped to 18446744073709550618
}
```

Measured on rustc 1.99.1, Debian 13.7: on 10 million `u64` keeping 1,000, `retain_back` took 41 ns and `drain(..len - 1000)` was just as fast, while a `while len > 1000 { pop_front() }` loop took about 10 ms. So the new call buys clarity and a safe short-input case, not speed over `drain`.

C++ comparison: `std::deque` has no "keep the last N". The usual `erase(begin(), end() - KEEP)` on a deque shorter than `KEEP` is undefined behavior, and with g++ 16.2 `-O2` a 2-element deque came back reporting `size() == 3`. Only `-D_GLIBCXX_DEBUG` stopped it, with an assertion in `safe_iterator.h`. TypeScript's `log.slice(-KEEP)` clamps a short input the way `retain_back` does, but has its own edge: `slice(-0)` returns the whole array.

**Why it matters**

Bounded buffers (recent requests, a metrics window, an audit tail) are trimmed on every insert, and the trim is the line nobody tests with a short buffer. `retain_back` has no subtraction you can get wrong. The cost is one more name to read correctly: it shares a prefix with `retain`, which takes a predicate.

**Chew on this**

Where does your code trim a buffer with `len() - n`? What does it do on the first few calls after a restart, when the buffer is still shorter than `n`?

**Sources**

- https://doc.rust-lang.org/std/collections/struct.VecDeque.html#method.retain_back
- https://blog.rust-lang.org/2026/10/01/Rust-1.99.0/
- https://github.com/rust-lang/rust/issues/140667 (tracking issue, as `truncate_front`)
- https://github.com/rust-lang/rust/pull/151379 (stabilization and rename)
- https://en.cppreference.com/w/cpp/container/deque/erase

**Gotchas**

- `retain_back` is not in the `retain` family. `retain(f)` takes a predicate and `retain_back(n)` takes a count. Josh Triplett made the same objection in the PR on 2026-04-28: the family "generally involves a predicate".
- `retain_back` drops the removed elements front first: on `1..=6` with `retain_back(3)` the drop log read `drop1 drop2 drop3`. `truncate(3)` drops `4 5 6`.
- It never reallocates or moves the survivors. A wrapped deque with slices `([1, 2, 3], [4, 5, 6, 7, 8])` became `([5, 6, 7, 8], [])` after `retain_back(4)`, still with capacity 8. The capacity stays, so call `shrink_to_fit` if you want the memory back.
- It is O(1) only for element types with no drop glue. On 1 million `String`s keeping 1,000 it took about 8.5 ms, because every removed `String` is freed.
- The old `drain(..len - n)` trim fails differently by build: debug panics with `attempt to subtract with overflow`, and release, on a 10-element deque, panics with `range end index 18446744073709550626 out of range for slice of length 10`.

## C++: { sensor.reading } -> std::integral is false for an int member, because the constraint sees int&, and the overload it guarded is skipped without a word

*Type system deep cuts*

**Did you know**

In a C++20 compound requirement, `{ expression } -> concept` does not test the expression's declared type. It tests `decltype((expression))`, with the double parentheses, and for a data member that is an lvalue, so a reference. A `struct Sensor { int reading; }` fails `{ sensor.reading } -> std::integral` and `-> std::same_as<int>`, because `std::integral<int&>` is false. GCC 16.2, Debian clang 19.1.7 and Apple clang 21 agree, under `-std=c++20` and `-std=c++26`, with no warning under `-Wall -Wextra -Wpedantic`.

**Show me**

```cpp
#include <concepts>
#include <iostream>
#include <string>
#include <type_traits>

struct Sensor { int reading; };

// Meant: "T has an integral data member called reading".
// Checked: std::integral<decltype((sensor.reading))>, which is std::integral<int&>.
template <class T>
concept has_integral_reading = requires(T sensor) { { sensor.reading } -> std::integral; };

// Fixed: strip the reference the parentheses added before asking.
template <class T>
concept has_integral_reading_fixed =
    requires(T sensor) { requires std::integral<std::remove_cvref_t<decltype(sensor.reading)>>; };

template <class T> std::string encode(const T&) { return "generic path"; }
template <has_integral_reading T> std::string encode(const T& sensor) { return "integer path " + std::to_string(sensor.reading); }

template <class T> std::string encode_fixed(const T&) { return "generic path"; }
template <has_integral_reading_fixed T> std::string encode_fixed(const T& sensor) { return "integer path " + std::to_string(sensor.reading); }

int main() {
    const Sensor boiler{ 42 };
    std::cout << encode(boiler) << '\n';       // generic path: the constrained overload never matched
    std::cout << encode_fixed(boiler) << '\n'; // integer path 42
    static_assert(std::same_as<decltype(boiler.reading), int>);          // the declared type
    static_assert(std::same_as<decltype((boiler.reading)), const int&>); // what the requirement sees
}
```

Rust comparison: a trait cannot name a field at all, so the same intent becomes a getter `fn reading(&self) -> i32`, and an impl that returns `&i32` instead is an E0308 at the impl rather than a quiet miss. F#'s SRTP constraint `(^T : (member reading : int) sensor)` accepts a record field `reading: int` directly (checked with `dotnet fsi`, .NET SDK 8.0.401), because a record field is a property and a property has no value category. TypeScript's `T extends { reading: number }` has no reference types to trip over.

**Why it matters**

A concept that guards a fast path or a serializer overload fails closed into the generic overload, and that one compiles too. Nothing breaks: the integer path just never runs, and the only symptom is a slower or differently formatted result.

**Chew on this**

Which of your concepts constrain a data member or a `*it` with `same_as` or a category concept like `integral`? If one of them is false today, which overload has been doing the work instead?

**Sources**

- https://en.cppreference.com/w/cpp/language/requires.html (compound requirements: "`decltype((expression))` must satisfy the constraint")
- https://eel.is/c++draft/expr.prim.req.compound
- https://en.cppreference.com/w/cpp/language/decltype.html

**Gotchas**

- `-> std::convertible_to<int>` passed on the same member (`convertible_to<int&, int>` is true), which is why most examples use it and never meet this.
- Getters behave differently from members: `{ sensor.current_reading() } -> std::same_as<int>` is true for `int current_reading() const`, a prvalue. It is false for `const int& reading_ref() const`.
- The parameter's constness leaks in: with `requires(const T sensor)` the member is `const int&`, so a constraint written for `int&` turns false once someone adds `const`.
- `std::same_as<decltype(T::reading), int>` (no parentheses, no object) is true, so the same check gives opposite answers depending on how it is spelled.

**Related**

- [2026-09-02](2026-09-02.md) - C++, "Two textually identical requires clauses are two different constraints". Another way a concept quietly fails to mean what it says.

## F#: A record in an interpolated string costs about 20 KB and 20 microseconds, because its ToString is sprintf "%+A", and %A skips your override

*Perf and memory model*

**Did you know**

F# records and unions come with a generated `ToString` that is `sprintf "%+A"`: a reflection walk over every field that lays out the value as indented text. On .NET 10.0.14 with FSharp.Core 10.1.0.0, one three-field record cost about 22 microseconds and 20 KB of allocation per call, whether reached as `string r`, `r.ToString()`, `$"{r}"`, `%O` or `String.Format`. A hand-written override of the same text cost 400 ns and 744 B. And `%A` does not call that override: it walks the record again.

**Show me**

```fsharp
open System
open System.Diagnostics

type Reading = { sensor_id: int; celsius: float; site: string }

type ReadingWithOverride =
    { sensor_id: int; celsius: float; site: string }
    override this.ToString () = $"sensor {this.sensor_id} {this.celsius} C at {this.site}"

// Average time and allocation of one call, after a warm-up.
let fn_cost_of (fn_format: unit -> string) : string =
    for _ in 1 .. 2_000 do fn_format () |> ignore
    let call_count = 200_000
    let bytes_before: int64 = GC.GetAllocatedBytesForCurrentThread ()
    let stopwatch = Stopwatch.StartNew ()
    for _ in 1 .. call_count do fn_format () |> ignore
    let bytes_per_call: int64 = (GC.GetAllocatedBytesForCurrentThread () - bytes_before) / int64 call_count
    $"%.0f{stopwatch.Elapsed.TotalNanoseconds / float call_count} ns, {bytes_per_call} B"

let plain: Reading = { sensor_id = 7; celsius = 21.5; site = "boiler-room" }
let custom: ReadingWithOverride = { sensor_id = 7; celsius = 21.5; site = "boiler-room" }

printfn "%s" (fn_cost_of (fun () -> $"reading {plain}"))   // 22335 ns, 20664 B: the generated sprintf "%+A"
printfn "%s" (fn_cost_of (fun () -> $"reading {custom}"))  // 400 ns, 744 B: the override
printfn "%s" (fn_cost_of (fun () -> sprintf "%A" custom))  // 19321 ns, 20157 B: %A skips the override
printfn "%s" (fn_cost_of (fun () -> $"{plain.sensor_id} {plain.celsius} {plain.site}"))  // 263 ns, 416 B
printfn "%s" (string plain)  // three lines, not one
```

Rust comparison: `#[derive(Debug)]` writes the formatting code at compile time, and `format!("{:?}", reading)` on the same three fields took 124 ns (rustc 1.99.1). C++ has no default at all: `std::format` needs a `formatter` specialization you write. TypeScript's `${reading}` prints `[object Object]`, and `JSON.stringify` took 59 ns on Node 26.13.0.

**Why it matters**

The expensive call hides in the cheapest-looking line: a log statement or an exception message with a record in a hole. At 20 KB a call, logging one record per request at 10,000 requests a second allocates about 200 MB a second of garbage, before the logger is even reached.

**Chew on this**

Which of your log lines, exception messages or metrics labels format a record or a union without naming its fields? Does your logger format the message even when the level is switched off?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/plaintext-formatting ("By default, F# record and union types override the implementation of `ToString` with an implementation that uses `sprintf "%+A"`.")
- https://github.com/dotnet/fsharp/blob/main/src/FSharp.Core/printf.fs
- https://learn.microsoft.com/en-us/dotnet/api/system.gc.getallocatedbytesforcurrentthread

**Verified**

Run with `dotnet fsi --optimize+` in the `mcr.microsoft.com/dotnet/sdk:10.0` image (SDK 10.0.403), which is Ubuntu 24.04.5, not Debian. Without `--optimize+` the numbers moved by at most about 7%.

**Gotchas**

- A union is no cheaper: `string (Reading (7, 21.5))` on a two-field union case cost 26.8 microseconds and 23.6 KB.
- Not every F# value pays this. `string [1; 2; 3]` cost 125 ns and 312 B, and `string 42` cost 5 ns and nothing, because lists and primitives have their own `ToString`.
- From two fields up, the default text spans several lines, `{ sensor_id = 7\n  celsius = 21.5\n  site = "boiler-room" }`, so one log call writes three lines. A one-field record stays on one line: `{ only_id = 1 }`.
- `%A` stops at 100 list elements: a record holding `[1 .. 150]` printed `... 98; 99; 100; ...] }`.
- `[<StructuredFormatDisplay>]` together with a `ToString` override is how the docs make `%A` and `%O` agree. On a public record the override alone fixes `string`, `$"{r}"` and `%O`, but not `%A`; on a record with a `private` representation `%A` does use it.

## TypeScript: slice(0, 5) can cut an emoji in half, and then encodeURIComponent throws, TextEncoder writes U+FFFD, and JSON keeps the half

*Stdlib and ecosystem gems*

**Did you know**

`slice` counts UTF-16 code units, so a cut that lands inside an emoji leaves half of a surrogate pair. The standard library then disagrees about what that half is. `encodeURIComponent` throws `URIError: URI malformed`, `TextEncoder` and `Buffer.from` silently write `EF BF BD` (U+FFFD), and `JSON.stringify` escapes it as `\ud83d`, which `JSON.parse` returns unchanged. ES2024's `isWellFormed()` detects the half, `toWellFormed()` replaces it, and `Intl.Segmenter` with `granularity: "grapheme"` is the cut that never makes one. Measured on Node 26.13.0 and tsc 7.0.2.

**Show me**

```typescript
// A display name cut to fit a 5-unit column, the way most code does it.
const display_name: string = "Ana \u{1F469}\u{1F3FD}‍\u{1F4BB} Silva"; // woman technologist, medium skin tone
const COLUMN_UNITS = 5;

const cut_by_slice: string = display_name.slice(0, COLUMN_UNITS); // "Ana \ud83d": half of a surrogate pair
console.log(cut_by_slice.isWellFormed()); // false (ES2024)

// Three consumers, three different reactions to the same half character.
const fn_try_encode_uri = (text: string): string => {
    try { return encodeURIComponent(text); } catch (err) { return `threw ${err instanceof Error ? err.name : typeof err}`; }
};
console.log(fn_try_encode_uri(cut_by_slice)); // threw URIError
console.log(Buffer.from(new TextEncoder().encode(cut_by_slice)).toString("hex")); // ...efbfbd: U+FFFD, silently
console.log(JSON.stringify(cut_by_slice)); // "Ana \ud83d": escaped, and JSON.parse gives it back unchanged

// The stdlib cut that never splits what a reader sees as one character.
const grapheme_segmenter = new Intl.Segmenter("en", { granularity: "grapheme" });
const fn_cut_on_grapheme = (text: string, max_units: number): string =>
    Array.from(grapheme_segmenter.segment(text), (piece) => piece.segment)
        .reduce(
            (kept: { text: string; full: boolean }, grapheme: string) =>
                kept.full || kept.text.length + grapheme.length > max_units
                    ? { text: kept.text, full: true }
                    : { text: kept.text + grapheme, full: false },
            { text: "", full: false },
        ).text;
console.log(JSON.stringify(fn_cut_on_grapheme(display_name, COLUMN_UNITS))); // "Ana "
const WITH_EMOJI_UNITS = 11; // "Ana " is 4 units, the emoji 7
console.log(JSON.stringify(fn_cut_on_grapheme(display_name, WITH_EMOJI_UNITS))); // "Ana " plus the whole emoji
```

Rust comparison: `&display_name[..5]` on a `str` panics with "end byte index 5 is not a char boundary; it is inside '👩' (bytes 4..8 of string)" instead of producing half a character (rustc 1.99.1), and `str::floor_char_boundary` (stable since 1.91) finds a safe cut. Neither knows about graphemes; that needs the `unicode-segmentation` crate. C++ `std::string::substr` counts bytes and happily returns a broken UTF-8 sequence, with no check in the standard library at all. .NET strings are UTF-16 like JavaScript's, so `Substring` in F# splits the same pair.

**Why it matters**

The column limit is applied to a name, a title or a preview, which are exactly the fields people decorate with emoji. One cut then fails three ways on three paths: a redirect URL builder throws, the database row stores a replacement character, and the JSON cache keeps the broken half and passes it on to whoever decodes it next.

**Chew on this**

Is your length limit in code units, code points, bytes or graphemes, and does the database column count the same thing? Which of your encoders is the first to see a string after it was cut?

**Sources**

- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/isWellFormed
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter
- https://tc39.es/ecma262/#sec-encodeuricomponent-uricomponent (throws `URIError` on a lone surrogate)
- https://github.com/tc39/proposal-well-formed-stringify (why `JSON.stringify` escapes it)
- https://encoding.spec.whatwg.org/#utf-8-encoder (TextEncoder takes a USVString, so the half becomes U+FFFD)

**Gotchas**

- `[...text]` and `Array.from(text)` keep surrogate pairs together but still split the emoji: a 6-code-point cut gave `"Ana 👩🏽"`, a woman with a skin tone and no laptop, and `isWellFormed()` says `true`.
- `isWellFormed()` does not catch a lost accent: `"José".slice(0, 4)` is `"Jose"`, well-formed, with the accent gone.
- `tsc --target es2022` rejects `isWellFormed` with TS2550 and asks for `lib` `es2024` or later; the method has been in Node since 20.
- The grapheme cut costs: about 1,540 ns per call against 40 ns for `slice` plus `toWellFormed`, on this 17-unit string.
- `display_name.length` is 17, it is 14 code points, and `Intl.Segmenter` counts 11 graphemes. A "max 15 characters" rule accepts or refuses it depending on which one you meant.

# The functional angle: a value that prints itself is a reflection walk in F#, generated code in Rust, a compile error in C++, and [object Object] in TypeScript

Draws on the F# tip, with the same three-field reading measured in the other three languages. In a functional style a record is plain data, and plain data is expected to print, compare and hash itself from its definition alone. All four languages agree on that expectation for equality; for printing, they disagree about when the work is done.

```fsharp
// F#: free, and done at runtime by reflection on every call
type Reading = { sensor_id: int; celsius: float; site: string }
let boiler: Reading = { sensor_id = 7; celsius = 21.5; site = "boiler-room" }
let line: string = $"reading {boiler}"
```

```rust
// Rust: opt-in, and written out at compile time by the derive macro
#[derive(Debug)]
struct Reading { sensor_id: i32, celsius: f64, site: String }
// format!("{:?}", reading) -> Reading { sensor_id: 7, celsius: 21.5, site: "boiler-room" }
```

```cpp
// C++23: nothing to derive. std::format("{}", Sensor{ 42 }) fails with
// "std::formatter must be specialized for each type being formatted" (g++ 16.2).
```

```typescript
// TypeScript: `${reading}` is "[object Object]"; JSON.stringify(reading) walks own enumerable properties.
```

| Language | Free printing form | Per call, same three fields | What it costs |
| --- | --- | --- | --- |
| F# | generated `ToString` = `sprintf "%+A"` | 22,335 ns, 20,664 B | runtime reflection every call; multi-line output |
| Rust | `#[derive(Debug)]`, `{:?}` | 124 ns | one line of opt-in per type; code size per type |
| C++ | none | not expressible without writing a `formatter` | all of it is yours |
| TypeScript | `JSON.stringify` | 59 ns | only own enumerable data; `${r}` prints nothing useful |

The asymmetry worth noticing is not speed but timing. Rust's derive and a hand-written F# override both decide the text once, at compile time, while F#'s default decides it again on every call. C++26 reflection could move C++ into the first group without a hand-written formatter, and was not measured here.

Which of your types print themselves today only because nobody wrote down what they should print?

# The security angle: a record's free ToString writes every field into your log, private fields and newlines included

Draws on the F# tip, and runs in the direction where the language does not protect you: `private` on a record's representation hides the fields from code, and not from the formatter. Two classes apply: CWE-532 (sensitive information in a log file) and CWE-117 (log output not neutralized).

```fsharp
// F#: looks like encapsulation, logs like a dump.
type ApiKey = private { owner: string; secret: string }
module ApiKey =
    let create (owner: string) (secret: string) : ApiKey = { owner = owner; secret = secret }

type Upload = { file_name: string; size_bytes: int64 }

let issued: ApiKey = ApiKey.create "ops" "sk-live-123"
printfn "issued key %O" issued // { owner = "ops"\n  secret = "sk-live-123" }

let uploaded: Upload = { file_name = "report.pdf\nINFO admin login ok"; size_bytes = 512L }
printfn "upload %O" uploaded   // the file name's newline starts a new, forged log line
```

The fix is to say what a log may see, in the type itself:

```fsharp
// F#: the override wins for %O, string, $"{r}", and here also for %A,
// because %A does not look inside a private representation.
type ApiKeyRedacted =
    private { owner: string; secret: string }
    override this.ToString () = $"ApiKey(owner={this.owner}, secret=<redacted>)"
// printfn "%O" and printfn "%A" both print: ApiKey(owner=ops, secret=<redacted>)
```

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| F# | default `ToString` prints a private `secret` and a raw newline | nothing; `%+A` reveals private structure by design | override `ToString` on every type that holds a secret or user text |
| Rust | `#[derive(Debug)]` printed `secret: "sk-live-123"` | `{:?}` escapes the newline (`"a\nFAKE LOG LINE"`); `{}` on the field does not | a manual `Debug` impl, or a wrapper type that redacts |
| TypeScript | `JSON.stringify` prints every own enumerable field | a `#secret` class field was left out; `\n` escaped | keep secrets in `#private` fields or out of loggable objects |
| C++ | nothing is printed you did not write | no default formatter exists | the `operator<<` or `formatter` you write is the whole policy |
