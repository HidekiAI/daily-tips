**The thesis: "the same time" has three meanings, and each library picked some of them for `==` and others for `<`.** Same instant. Same instant and same zone. Same wall-clock reading. The bugs below live where `==` uses one meaning and `<`, a hash set or a string sort uses another.

| Same instant (17:00Z), UTC vs Chicago | `==` | ordering | hash set of the two |
| --- | --- | --- | --- |
| Rust `jiff` `Zoned` | true | `Equal` | 1 element |
| C++ `zoned_time` | **false** | no `operator<` at all | `std::set` does not compile |
| F# / .NET `DateTimeOffset` | true (`EqualsExact`: false) | `compare` = 0 | 1 element, the first one inserted |
| TypeScript `Temporal.ZonedDateTime` | `equals`: **false** | `compare` = 0 | `Set` size 2 (references) |

Sorting the strings `12:00:00Z`, `12:00:00.5Z`, `11:59:59+00:00` and `07:30:00-05:00` (all 2026-10-22) puts them in the same wrong order in all four languages: `07:30-05:00` first, although at 12:30Z it is the latest. All values measured on 2026-10-22.

## Rust: `civil::DateTime` orders by the wall clock, so across the fall-back hour a refund sorts before the payment it refunds

*Idioms and antipatterns*

**Did you know**

In the Rust `jiff` crate (0.2.38), `Zoned` compares by instant, and `civil::DateTime` compares by wall-clock reading. On the night Chicago falls back (2026-11-01, 02:00 CDT becomes 01:00 CST), 01:00 to 01:59 happens twice. A payment at 01:45 CDT happens before a refund at 01:15 CST. As instants that is 06:45Z < 07:15Z, but as wall-clock readings 01:15 < 01:45. Sort a ledger by `.datetime()` and the refund comes first. In the other direction, two `Zoned` values in different zones are **equal** when the instant is, because `jiff` keeps `Eq` consistent with `Ord`.

**Show me**

```rust
// Rust: jiff 0.2.38, rustc 1.95.0. America/Chicago falls back at 02:00 CDT on 2026-11-01.
use jiff::Zoned;

fn main() {
    // 01:00-01:59 happens twice that night. The payment is in the first pass,
    // the refund thirty minutes later in the second.
    let payment: Zoned = "2026-11-01T01:45:00-05:00[America/Chicago]".parse().unwrap(); // CDT
    let refund: Zoned = "2026-11-01T01:15:00-06:00[America/Chicago]".parse().unwrap(); // CST
    println!("{} < {}", payment.timestamp(), refund.timestamp()); // 06:45Z < 07:15Z

    println!("{}", payment < refund);                       // true: Zoned orders by instant
    println!("{}", payment.datetime() < refund.datetime()); // false: civil::DateTime orders by wall clock

    let mut ledger = vec![("payment", payment.datetime()), ("refund", refund.datetime())];
    ledger.sort_by_key(|(_, wall)| *wall);
    println!("{:?}", ledger.iter().map(|(label, _)| *label).collect::<Vec<_>>()); // ["refund", "payment"]

    // And the other direction: two Zoned in different zones are EQUAL when the instant is.
    let in_utc: Zoned = "2026-11-01T06:45:00+00:00[UTC]".parse().unwrap();
    println!("{}", payment == in_utc);                      // true, by design (Eq agrees with Ord)
}
```

**Why it matters**

Event logs, ledgers and audit trails are often stored as local wall-clock time "because that is what the user saw". One night a year, that order is wrong for an hour. The `jiff` docs state the design: "`Zoned` comparisons only consider the precise instant in time. The civil datetime or even the time zone are completely ignored", because "`Eq` and `Ord` trait implementations must be consistent in Rust". Temporal made the opposite choice for `equals` (TypeScript tip below). C++ refused to pick one for `<` at all.

**Chew on this**

Which of your tables store a local `timestamp` and are ever sorted, and what happens to their order on the first Sunday of November? If two `Zoned` values are equal but print different zones, which one does your `HashSet` keep, and does anything read its zone?

**Sources**

- https://docs.rs/jiff/0.2.38/jiff/struct.Zoned.html (the "Comparisons" section)
- https://docs.rs/jiff/0.2.38/jiff/civil/struct.DateTime.html
- https://doc.rust-lang.org/std/cmp/trait.Ord.html (the consistency requirement between `Ord` and `PartialEq`)

**Gotchas**

- A `HashSet<Zoned>` of 12:00-05:00 Chicago and 17:00Z UTC holds 1 element (measured), and printing it shows whichever zone survived.
- The ambiguous reading `2026-11-01T01:30:00` resolved with `.compatible()` picks the **first** pass, `-05:00` (measured), so it is not a tie-breaker you can lean on for ordering.
- Rust and its crates evolve: this is `jiff` 0.2.38's documented design. Rust `chrono`'s `DateTime<Tz>` is a different crate with its own rules, not measured here.

## C++: `zoned_time ==` compares the zone too, and there is no `<`, so `std::set<zoned_time>` does not compile

*Type system deep cuts*

**Did you know**

C++20's `std::chrono::zoned_time` defines `operator==` as "same time zone **and** same instant". The same instant in UTC and in Chicago compares unequal. It defines no `operator<` and no `<=>`, so `std::set<zoned_time<seconds>>` fails at its first insert ("no match for 'operator<'"), and `std::ranges::sort(events)` does not compile either. You have to say which order you mean: `std::ranges::sort(events, {}, &zoned_time<seconds>::get_sys_time)`. Measured with GCC 14 and GCC 16.2 (libstdc++). Apple's libc++ has no tzdb, so this cannot be built on a Mac.

**Show me**

```cpp
// C++20 std::chrono tzdb: GCC 16.2 (libstdc++), tzdata 2026c on Debian 13
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <format>
#include <set>
#include <vector>
using namespace std::chrono;

int main() {
    const sys_seconds instant = sys_days{2026y/October/22} + 17h;
    zoned_time<seconds> in_utc{"UTC", instant};
    zoned_time<seconds> in_chicago{"America/Chicago", instant};

    std::printf("%d\n", (int)(in_utc.get_sys_time() == in_chicago.get_sys_time())); // 1: same instant
    std::printf("%d\n", (int)(in_utc == in_chicago));  // 0: == also compares the zone pointer

    // No operator< exists, so these do not compile:
    //   in_utc < in_chicago;                       // no match for 'operator<'
    //   std::set<zoned_time<seconds>> seen;        // fails at the first insert, inside std::less
    //   std::ranges::sort(events);                 // same reason

    // Say which order you mean, with a projection:
    std::vector<zoned_time<seconds>> events{{"America/Chicago", instant + 30min}, in_utc, {"Asia/Tokyo", instant - 1h}};
    std::ranges::sort(events, {}, &zoned_time<seconds>::get_sys_time);
    for (const auto& event : events) std::printf("%s\n", std::format("{:%FT%T%z %Z}", event).c_str());
    // 2026-10-23T01:00:00+0900 JST, 2026-10-22T17:00:00+0000 UTC, 2026-10-22T12:30:00-0500 CDT
}
```

**Why it matters**

This is the one library of the four that cannot be wrong by default. "Is this the same event?" and "which came first?" are different questions, and `zoned_time` makes you answer the second one out loud at every sort. The cost is the first compile error, and the C++ wrapper that someone writes to make it go away: a `<` that compares `get_local_time()` brings back the Rust tip's fall-back bug.

**Chew on this**

If you wrote the missing `operator<` for `zoned_time`, would it compare instants, local times, or zones first? Would the `==` you already have agree with it?

**Sources**

- https://en.cppreference.com/w/cpp/chrono/zoned_time/operator_cmp
- https://eel.is/c++draft/time.zone.zonedtime.nonmembers

**Verified**

`docker run gcc:14` and `docker run gcc:16` (Debian 13, tzdata 2026c). Not buildable on this host's Apple clang (no tzdb). MSVC not tested.

**Gotchas**

- Two `zoned_time` values with the same zone and the same instant are equal, and `locate_zone("America/Chicago")` returns the same pointer each time (both measured).
- `std::ranges::sort(events)` fails with "no match for call to '(const std::ranges::__sort_fn)'" (measured), which does not mention `operator<` at all.
- `sys_time` and `local_time` have `<`; only the pairing in `zoned_time` lacks it. Comparing `get_local_time()` is legal, and wrong across fall-back.

## F#: `DateTimeOffset` equality ignores the offset, so a `Dictionary` keyed by it keeps the first key and the last value

*Stdlib and ecosystem gems*

**Did you know**

`.NET` `DateTimeOffset`'s `=`, `Equals`, `GetHashCode` and `CompareTo` all use the instant only: 17:00+00:00 and 12:00-05:00 are equal, hash the same and compare as 0. `EqualsExact` is the method that also checks the offset. So every collection keyed by it merges the two. `Set.ofList` and `List.distinct` keep whichever came first. A `Dictionary` written by two services keeps the **first** key and the **last** value, so the stored entry says `-05:00` next to text written by the UTC service. Measured identically on FSharp.Core 8.0 / .NET 8.0.8 and FSharp.Core 10.1 / .NET 10.0.13.

**Show me**

```fsharp
// F#: DateTimeOffset equality, FSharp.Core 8.0 / .NET 8.0.8 and FSharp.Core 10.1 / .NET 10.0.13
open System
open System.Collections.Generic

let in_utc = DateTimeOffset(2026, 10, 22, 17, 0, 0, TimeSpan.Zero)
let in_chicago = DateTimeOffset(2026, 10, 22, 12, 0, 0, TimeSpan.FromHours -5.0)

printfn "%b" (in_utc = in_chicago)           // true: = compares the instant only
printfn "%b" (in_utc.EqualsExact in_chicago) // false: instant AND offset
printfn "%d" (compare in_utc in_chicago)     // 0

// Every collection keyed by it merges the two, and keeps whichever arrived first:
printfn "%s" ((Set.ofList [ in_chicago; in_utc ] |> Seq.head).ToString "o")  // ...T12:00:00.0000000-05:00
printfn "%s" ((Set.ofList [ in_utc; in_chicago ] |> Seq.head).ToString "o")  // ...T17:00:00.0000000+00:00

// A Dictionary keeps the FIRST key and the LAST value:
let audit = Dictionary<DateTimeOffset, string>()
audit.[in_chicago] <- "written by the Chicago service"
audit.[in_utc] <- "written by the UTC service"
for entry in audit do printfn "%s -> %s" (entry.Key.ToString "o") entry.Value
// 2026-10-22T12:00:00.0000000-05:00 -> written by the UTC service
```

**Why it matters**

The offset is the part of `DateTimeOffset` that says where an event was recorded, and it is the part every equality-based operation throws away. A dedupe, a `groupBy` or a cache keyed by it reports one event with one offset chosen by arrival order, which differs between runs. F# usually makes equality structural, so a reader expects all fields compared. `DateTimeOffset` is a .NET struct with its own `Equals`, and F#'s `=` defers to it. C++ `zoned_time` compares the zone, and Rust `jiff` agrees with .NET.

**Chew on this**

Where do you key a collection by `DateTimeOffset` and later read the key's `Offset`? If two services record the same instant from different zones, which one should win, and does your code decide or does arrival order?

**Sources**

- https://learn.microsoft.com/en-us/dotnet/api/system.datetimeoffset.equals
- https://learn.microsoft.com/en-us/dotnet/api/system.datetimeoffset.equalsexact

**Gotchas**

- `in_utc.GetHashCode() = in_chicago.GetHashCode()` is true (measured), so the merge is consistent, not a hash accident.
- `List.groupBy id [ in_chicago; in_utc ]` gives 1 group (measured).
- `DateTimeOffset(DateTime(2026, 10, 22, 12, 0, 0, DateTimeKind.Local))` equals `in_chicago` under `TZ=America/Chicago` (measured): converting a `DateTime` picks up the machine's offset first, so the equality depends on the host.
- `%O` formatting differs between hosts (`12:00:00 PM` on macOS, `12:00:00` in the .NET 10 container), which is why the snippet prints `ToString "o"`.

## TypeScript: `Temporal.ZonedDateTime.equals` says false while `compare` says 0, and a `Set` uses neither

*Stdlib and ecosystem gems*

**Did you know**

`Temporal.ZonedDateTime.compare(in_utc, in_chicago)` is 0 for the same instant, and `in_utc.equals(in_chicago)` is `false`, because `equals` also compares the time zone and the calendar. Even a fixed `-05:00` zone is not equal to `America/Chicago` at the same instant, and switching the calendar to `japanese` makes a value unequal to itself. A `Set` of `ZonedDateTime` uses neither rule: it compares object references, so two copies of one value make size 2. TypeScript 6.0.3 types all of this under `lib: esnext` (`lib.esnext.temporal.d.ts`). Run on Node 26.12.1, since Node 22 has no `Temporal`.

**Show me**

```ts
// TypeScript 6.0.3 (lib esnext, which carries Temporal), run on Node 26.12.1
const in_utc = Temporal.ZonedDateTime.from("2026-10-22T17:00:00+00:00[UTC]")
const in_chicago = Temporal.ZonedDateTime.from("2026-10-22T12:00:00-05:00[America/Chicago]")

console.log(Temporal.ZonedDateTime.compare(in_utc, in_chicago)) // 0: same instant
console.log(in_utc.equals(in_chicago))                          // false: zone differs
console.log(in_utc.toInstant().equals(in_chicago.toInstant()))  // true

// equals also looks at things compare ignores: a fixed offset is not the named zone,
// and a different calendar is a different value.
const fixed_offset = Temporal.ZonedDateTime.from("2026-10-22T12:00:00-05:00[-05:00]")
console.log(in_chicago.equals(fixed_offset))                    // false
console.log(in_utc.equals(in_utc.withCalendar("japanese")))     // false

// A Set uses neither: it compares object references.
console.log(new Set([in_utc, Temporal.ZonedDateTime.from(in_utc)]).size) // 2

// Deduplicate by the key you mean, spelled out:
const fn_by_instant = (stamp: Temporal.ZonedDateTime): string => stamp.toInstant().toString()
const unique = new Map([in_utc, in_chicago].map((stamp) => [fn_by_instant(stamp), stamp]))
console.log(unique.size)                                        // 1
```

**Why it matters**

`equals` and `compare` answer different questions on purpose: "is this the same value, zone and calendar included?" against "which came first?". The trap is code that treats `compare(...) === 0` and `equals` as interchangeable, for example a sorted merge that drops duplicates with `equals`: it keeps both 17:00Z and 12:00-05:00, then a downstream `compare` reports them as one instant. Rust `jiff` documents that it chose the opposite of `equals` because Rust requires `Eq` and `Ord` to agree. C++ has an `==` like `equals` and no `<`.

**Chew on this**

When you replace `Date` with `Temporal` in a dedupe, which of `equals`, `compare` or an instant string should be the key? Would your answer change for a calendar app where the zone is part of the meaning?

**Sources**

- https://tc39.es/proposal-temporal/docs/zoneddatetime.html#equals
- https://tc39.es/proposal-temporal/docs/zoneddatetime.html#compare
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Temporal/ZonedDateTime/equals

**Verified**

**Gotchas**

- `in_utc < in_chicago` throws `TypeError: Do not use Temporal.ZonedDateTime.prototype.valueOf; use Temporal.ZonedDateTime.prototype.compare for comparison.` (measured).
- `Date` is no better for sets: `new Set([new Date(0), new Date(0)]).size` is 2, `new Date(0) === new Date(0)` is false, and `<=` and `>=` are both true (measured).
- `Temporal.Instant.equals` has no zone or calendar to disagree about, so it matches `Instant.compare(...) === 0`.

# The functional angle: equality has to agree with ordering, and only Rust makes it a contract

Draws on all four tips. A sort, a dedupe and a set are three functions built on two relations, `eq` and `lt`. They only compose when "neither is less" means "equal". Rust's `Ord` documentation makes that a requirement: an `Ord` implementation must be consistent with `PartialEq`. That is why `jiff`'s `Zoned` gave up zone-aware equality.

The same strings through a plain string sort, measured in each language:

```text
// Rust Vec::sort, C++ std::ranges::sort, F# List.sort, JS Array.prototype.sort: identical result
2026-10-22T07:30:00-05:00   <- actually 12:30:00Z, the LATEST
2026-10-22T11:59:59+00:00
2026-10-22T12:00:00.5Z      <- '.' (0x2E) sorts before 'Z' (0x5A)
2026-10-22T12:00:00Z
// Sorted by instant (JS Temporal.Instant.compare): 11:59:59Z, 12:00:00Z, 12:00:00.5Z, 07:30:00-05:00
```

| Language | Type | `eq` | `lt` | Agree? | What it costs |
| --- | --- | --- | --- | --- | --- |
| Rust | `jiff::Zoned` | instant | instant | yes, required by `Ord` | zone-aware equality is a hand-written `a == b && a.time_zone() == b.time_zone()` |
| C++ | `zoned_time` | zone and instant | none | nothing to agree with | every sort needs a projection; `std::set` needs a comparator |
| F# | `DateTimeOffset` | instant | instant | yes | the offset is silently dropped by any keyed collection |
| TypeScript | `Temporal.ZonedDateTime` | `equals`: zone, calendar, instant | `compare`: instant | **no** | code must pick per call; `Set` uses references, which is a third relation |
| all four | ISO 8601 strings | bytes | bytes | yes, and both wrong | sort by a parsed key: Rust `sort_by_cached_key`, F# `List.sortBy`, C++ a projection, TS a comparator that parses twice per compare |

No row needs `mut` beyond the sort itself. The asymmetry is that only Rust's type system states the law, and only TypeScript's standard library ships a type that breaks it, on purpose.

Which of your sorts and dedupes over timestamps use two different relations without saying so?

# The security angle: a replay cache keyed by the timestamp string accepts the same instant four times

Draws on the TypeScript tip and the F# tip (Mode B: these equalities are fine for display, but are they safe as keys?). In both, the language prevents nothing. The question is which equality the security check uses.

**Equivalent encodings bypass a string-keyed check (CWE-1289, improper validation of unsafe equivalence in input).** A request-signing scheme that rejects replays by remembering `(nonce, timestamp)` strings looks fine until the timestamp is re-encoded:

```ts
// TypeScript, Node 22.17.1, measured: four strings, one instant
const seen = new Set<string>()
for (const stamp of ["2026-10-22T12:00:00Z", "2026-10-22T12:00:00+00:00", "2026-10-22T12:00:00.000Z", "2026-10-22T07:00:00-05:00"]) {
    if (seen.has(stamp)) continue  // looks like replay protection
    seen.add(stamp)                // accepts all four
}
// seen.size === 4, while new Set([...seen].map(Date.parse)).size === 1
```

The opposite failure is the F# tip's: keying by `DateTimeOffset` merges two different events that share an instant, and the survivor depends on arrival order. One is a replay that gets through, and the other is a real event that gets dropped. Both come from choosing the equality by accident.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| TypeScript | a string key admits every encoding of one instant | nothing; strings are bytes | normalize first (`Temporal.Instant.from(text).toString()`), then key |
| F# / .NET | `DateTimeOffset` keys merge distinct events at one instant | documents it (`EqualsExact` exists) | key by the field that identifies the event, not by its time |
| Rust | `HashSet<Zoned>` merges across zones (measured) | documents it as the `Eq` contract | same: time is rarely an identity |
| C++ | `zoned_time` cannot be a `std::set` key at all | forces you to write the comparator | write one that normalizes to `sys_time` |

C++ is the control for the bypass half: it will not let you key by the value until you say what equal means. Nobody is a control for "time used as an identity", because that is a design choice, not a type.

Which of your replay, idempotency or rate-limit checks use a timestamp as part of the key, and in which encoding?

# FAQ

**Why does `12:00:00.5Z` sort before `12:00:00Z`?** Byte by byte, the two strings agree up to `12:00:00`, then compare `.` (0x2E) with `Z` (0x5A), and `.` is smaller. Fixed-width UTC strings with the same number of fraction digits sort correctly. Anything else needs a parsed key. .NET `String.CompareOrdinal` and the invariant culture both gave the same result (measured).

**Is there an incident appendix for this part?** No. The candidate was the 2018 Verge cryptocurrency timestamp exploit, where blocks with spoofed timestamps were accepted out of order. The accounts found were press reports that disagree on its length and losses, with no first-hand post-mortem, so under this special's rule it stays out.

# Appendix A: Bash compares timestamps as text, and the text order depends on the Bash version and the locale

_Not part of the tip rotation. Added 2026-10-23 to back this part's thesis from the shell side. Every result below was
measured on macOS `/bin/bash` 3.2.57 and on Bash 5.2.37 in `docker run debian:trixie-slim` (with `locales-all` for the
`en_US.UTF-8` rows). Version boundaries are quoted from the Bash 5.2 `NEWS` file._

Bash has no time type. A timestamp is a string, so `==` is string equality, `<` is a string sort, and an hour pulled
out with `date +%H` is a string that arithmetic reads by its own rules. All three of this part's meanings of "the same
time" collapse into the one meaning Bash has: the same bytes.

## A.1 `[[ == ]]` and `[[ < ]]` see text, so the same instant is two different times

```bash
# Bash, any version
utc="2026-10-22T17:00:00Z"; chicago="2026-10-22T12:00:00-05:00"   # the same instant
[[ "$utc" == "$chicago" ]] || echo "different"        # prints different
[[ "$chicago" < "$utc" ]] && echo "chicago first"     # prints chicago first: "12" sorts before "17"
pattern="2026-10-2*"
[[ "$utc" == $pattern ]] && echo "glob match"         # unquoted right side is a pattern, not a string
```

This is the security angle's replay-cache bug in shell form: a dedupe keyed by the string accepts both. And `==` with an
unquoted right side is a glob match, so a stored value containing `*` or `?` matches more than itself.

## A.2 Which order `<` uses depends on the Bash version and the locale

RFC 3339 allows a lowercase `t` separator. Two timestamps, one with each:

| Comparison | macOS Bash 3.2 | Debian Bash 5.2, `C` | Debian Bash 5.2, `en_US.UTF-8` |
| --- | --- | --- | --- |
| `[[ "...T10:00:00Z" < "...t09:00:00Z" ]]` | true: byte order, `T` (0x54) before `t` | true | false: 09:00 first, case is a later collation level |
| `sort`, first line | `t09:00` (macOS `sort` follows the locale) | `T10:00` | `t09:00` |

On the Mac, `[[ < ]]` and `sort` disagree with each other in the same shell. NEWS for bash-4.1: "The < and > operators
to the [[ conditional command now do string comparison according to the current locale if the compatibility level is
greater than 40." Apple ships 3.2, so the same script orders differently on a developer's laptop and on the Linux host.
`LC_ALL=C` makes both byte-ordered, which is correct only for fixed-width UTC strings in one format.

## A.3 A leading zero makes the hour octal, but only in arithmetic

```bash
# Bash, any version
hour=$(date +%H)                       # "08" at 8 a.m.
echo $(( hour + 1 ))                 # error: 08: value too great for base (error token is "08")
[[ "$hour" -lt 9 ]]                    # same error: [[ evaluates -lt arithmetically
[ "$hour" -lt 9 ]                      # true: the test builtin reads 08 as decimal
echo $(( 10#$hour + 1 ))               # 9: the 10# prefix forces base ten
day=010; echo $(( day ))               # 8, silently: date +%j on January 10 is "010"
```

The hour fails by time of day: `00` to `07` and `10` to `23` work, `08` and `09` error. A day of the year from `%j`
is worse: `001` to `007` are right, any day whose digits include an 8 or a 9 (`008`, `019`, `080`) errors, and every
other day from `010` to `077` is silently read as octal (`077` is 63). From `100` on there is no leading zero and it
is right again. `[` and `[[` disagree on the same operator.

## A.4 `EPOCHSECONDS` does not exist on macOS, and arithmetic reads it as 0

```bash
# Bash 5.0+ has EPOCHSECONDS and EPOCHREALTIME; Bash 3.2 has neither
start=$EPOCHSECONDS; run_job; echo "took $(( EPOCHSECONDS - start ))s"
# Bash 5.2: the real duration. Bash 3.2: both expand to "", arithmetic treats "" as 0, prints "took 0s"
```

No error, no warning: an unset variable in `$(( ))` is 0. `date +%s` works on both.

## A.5 `-nt` and `-ot` compare mtimes, and a missing file is always older

| Case | Bash 3.2 (macOS) | Bash 5.2 (Debian) |
| --- | --- | --- |
| equal mtimes, `a -nt b` and `a -ot b` | both false | both false |
| `existing -nt missing` | true | true |
| `missing -ot existing` | true | true |
| written 0.3 s apart, `newer -nt older` | false: whole seconds | true: nanoseconds (bash-4.3 NEWS) |

A `make`-style "rebuild if the source is newer" check is false on a Mac for two writes in the same second, and a typo in
the output path reads as "output is older", so it rebuilds every time instead of failing.

`find -mtime` has the same integer problem, at day scale. POSIX: the age "divided by 86400 (with any remainder
discarded), is n". So `+1` means "more than one whole day", which is 48 hours or more:

| Files aged 23 h, 25 h, 47 h, 49 h | BSD `find` (macOS) | GNU `find` (Debian) |
| --- | --- | --- |
| `-mtime 0` and `-mtime -1` | 23 h | 23 h |
| `-mtime 1` | 25 h, 47 h | 25 h, 47 h |
| `-mtime +1` | 49 h only | 49 h only |
| `-mtime +0`, "older than 24 h" | 25 h, 47 h, 49 h | 25 h, 47 h, 49 h |
| `-mmin -1440` | 23 h | 23 h |
| `-mtime -1h` | accepted (BSD units) | `invalid argument` |

A cleanup job written as `find . -mtime +1 -delete` to "delete what is older than a day" keeps two-day-old files.
`-mtime +0` or `-mmin +1440` says what was meant, and both work on both.

## A.6 Comparing instants: convert to an integer first

```bash
# Bash 3.2+: one comparable integer per instant, on GNU date (Linux) and BSD date (macOS)
to_epoch() {
    if date --version >/dev/null 2>&1; then
        date -u -d "$1" +%s
    else
        # BSD %z reads +0000 and -0500, not Z or -05:00, so rewrite the suffix first
        date -j -u -f '%Y-%m-%dT%H:%M:%S%z' "$(printf '%s' "$1" | sed -E 's/Z$/+0000/; s/([+-][0-9]{2}):([0-9]{2})$/\1\2/')" +%s
    fi
}
# Exit 0 same instant, 1 different, 2 a timestamp did not parse
same_instant() {
    local left right
    left=$(to_epoch "$1") || { echo "rejected: $1" >&2; return 2; }   # an assignment keeps date's exit status
    right=$(to_epoch "$2") || { echo "rejected: $2" >&2; return 2; }
    (( left == right ))
}
same_instant "2026-10-22T17:00:00Z" "2026-10-22T12:00:00-05:00"   # 0 on both hosts (1792688400 each)
same_instant "2026-10-22T25:00:00Z" "not a time"                  # 2 on both hosts
```

GNU `date -d` reads RFC 3339 directly. BSD `date` has no `-d`, and its `-f` with `%z` rejects both `Z` ("Failed
conversion") and `-05:00`, which is why the suffix is rewritten.

The exit-status check is not optional. Without it, two timestamps that fail to parse both come back as `""`, and
`(( "" == "" ))` is `0 == 0`, so they compare as the same instant, on both hosts. Fractional seconds split the hosts:
`17:00:00.250Z` is rejected by BSD `date` and silently truncated to `1792688400` by GNU `date`, so on Linux two
instants 250 ms apart are "the same".

## A.7 The rest of the toolbox: formatting, parsing, setting, and the zone

Same probes, macOS 26.7.1 (BSD `date`) against Debian 13 (GNU coreutils `date`):

| What you ran | macOS | Debian | The trap |
| --- | --- | --- | --- |
| `date +%Y-W%V` on 2024-12-30 | `2024-W01` | `2024-W01` | wrong on both: ISO week 1 there belongs to 2025, which `%G-W%V` prints |
| `date +%Y-W%V` on 2027-01-01 | `2027-W53` | `2027-W53` | wrong on both: `%G-W%V` is `2026-W53` (part 13's week-year bug, in shell) |
| `date +%s%N` | microseconds, padded: `...268508000` | nanoseconds | the last three digits are always `000` on the Mac |
| `date +%3N` | `3N`, literally | `791` | the width flag is GNU-only |
| one month after 2026-01-31 | `-v+1m`: 2026-02-28 (clamps) | `-d '+1 month'`: 2026-03-03 (overflows) | two answers to one question |
| parse a date with no time | `-j -f '%Y-%m-%d'` keeps the current time of day | `-d` gives 00:00:00 | a BSD epoch from a date-only string is off by the time of day |
| `date -s "10/11/2026"` (set) | n/a | sets 2026-10-11 | always month first; a European meaning 10 November sets October 11 |
| `date 102314002026` (set, positional) | `mmddHHMMyy` | `MMDDhhmmCCYY`, 2026-10-23 14:00 | a day-month typo is "illegal time format" on BSD and a valid wrong date when the numbers fit |
| `TZ=America/Chicgo date` (typo) | 17:00 `UTC +0000` | 17:00 `America +0000` | silently UTC on both, and GNU labels it with the misspelled zone's first part |
| `TZ=CST date` | `UTC +0000` | `CST +0000` | GNU prints CST while the offset is zero: the log line lies |
| `jq fromdate` on `...-05:00` | error: only `%Y-%m-%dT%H:%M:%SZ` | (jq not installed) | jq reads UTC `Z` strings only |
| `stat` mtime as epoch | `stat -f %m` | `stat -c %Y` | each flag fails on the other platform |
| `timeout 5 cmd` | not installed | coreutils | macOS has no `timeout` without Homebrew coreutils (`gtimeout`) |
| `sleep infinity` | usage error, exits at once | runs forever | a "keep the container alive" line ends immediately on a Mac |

`date -s` reads the same "date input formats" as `date -d` (the coreutils manual points both at that one
section), which is why the Debian rows above could be checked without
the right to set the clock: in the container `date -s` printed the date it would have set, then failed with
"cannot set date: Operation not permitted". Two read-only tools worth knowing: `zdump -v -c 2026,2027 America/Chicago`
prints the zone's real transitions (`Sun Mar 8 01:59:59 2026 CST` then `03:00:00 2026 CDT`, the same on both hosts),
which is how to check what the tz database says before trusting any arithmetic across a DST change. And `-mmin`,
`-newermt` (GNU) or `-newer reference_file` (both) say what `-mtime` only approximates. The shell that cron runs
these commands in has traps of its own: part 2's [Appendix B](2026-10-21-extra-2-of-13.md).

## A.8 `stat` and `ls`: one mtime, printed in whatever shape the tool and the clock choose

`stat(1)` is the command-line face of the `stat`/`fstat` system calls, and it can print the mtime any way you like,
but with different flags on each platform. `ls -l` prints it the way it likes, and changes shape on its own:

| Same probes | macOS 26.7.1 (BSD) | Debian 13 (GNU coreutils 9.7) |
| --- | --- | --- |
| epoch seconds | `stat -f %m` | `stat -c %Y` |
| with the fraction | `stat -f %Fm`: `1792784307.966325340` | `stat -c %.3Y`: `1792784308.452` |
| as a date | `stat -f %Sm -t '%F %T'` | `stat -c %y`: `2026-10-23 19:38:28.452856000 +0000` |
| full time in `ls` | `ls -lT`, or `ls -l -D '%F %T'` | `ls -l --time-style=full-iso` |
| `ls -l`, a file from 7 months ago | `Mar 23 2026` | `Mar 23 2026` |
| `ls -l`, a file 30 minutes in the future | `Oct 23 2026`: no time of day | `Oct 23 2026`: no time of day |
| `ls -t`, writes 0.3 s apart | newest first, correct | newest first, correct |
| `ls -t`, identical mtimes | by name | by name |

The sixth to eighth columns of `ls -l` are `Mon DD HH:MM` for a recent file and `Mon DD YYYY` otherwise. GNU's
manual says recent means "less than six months old, and is not dated in the future", which is what both hosts did.
The macOS man page says the year appears only "more than 6 months in the past or future", and its own `ls` did
otherwise. So a script that cuts the time out of `ls -l` reads a year as `HH:MM` for any file whose clock ran a
little ahead, such as a file copied from a host with clock skew. Files written in the same minute also printed `14:38` on the
Mac and `19:38` in the container, because `ls` prints local time and the container had no `TZ`. For anything a script reads,
use `stat` with an explicit format, or `ls` with `--time-style`/`-D`, never the default columns.

## A.9 Summary

| Trap | Bash 3.2 (macOS) | Bash 5.2 (Linux) | Fix |
| --- | --- | --- | --- |
| same instant, two zones | `==` false | `==` false | compare `to_epoch` integers |
| two unparseable timestamps | equal (`"" == ""`) | equal | check the conversion's exit status |
| fractional seconds | rejected | truncated, silently | compare at whole seconds only, knowingly |
| `[[ < ]]` order | bytes | locale | `LC_ALL=C`, and only for one fixed-width UTC format |
| `08`, `09` in `$(( ))` or `[[ -lt ]]` | error | error | `10#$hour` |
| `010` from `%j` | 8, silently | 8, silently | `10#$day` |
| `EPOCHSECONDS` | empty, reads as 0 | works | `date +%s` |
| `-nt` resolution | 1 s | 1 ns | do not rely on sub-second ordering |
| `find -mtime +1` | 48 h or more | 48 h or more | `-mtime +0` or `-mmin +1440` |
| `%Y` with `%V` | wrong year at the boundary | wrong year at the boundary | `%G-W%V` |
| a `TZ` typo | silent UTC | silent UTC, wrong label | check `zdump` or the `%z` offset |
| time from `ls -l` columns | `HH:MM` or a year | `HH:MM` or a year | `stat -f` or `stat -c` with a format |
