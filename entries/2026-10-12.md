## Rust: dedup_by hands you the later element first, so a merge written left-to-right sums into the one it deletes

*Stdlib and ecosystem gems*

**Did you know**

`Vec::dedup_by` gives its closure two `&mut` references, and they arrive in the opposite order from the slice: `same_bucket(a, b)` gets the element being tested as `a` and the already-kept element as `b`, and returning `true` removes `a`. Because both are `&mut`, that makes `dedup_by` an in-place run-length merge: fold the duplicate into the survivor and drop it, with no second vector. Name the parameters `first, second` and the merge silently accumulates into the element that is about to be removed. There is a second trap: `a` is compared against the survivor, not against the previous original element, so a "close enough" predicate chains differently from `slice::chunk_by` (stable since 1.77).

**Show me**

```rust
#[derive(Debug)]
struct Hit { path: &'static str, count: u32 }

fn main() {
    let mut hits = vec![
        Hit { path: "/a", count: 1 }, Hit { path: "/a", count: 2 },
        Hit { path: "/a", count: 4 }, Hit { path: "/b", count: 8 },
    ];
    // (candidate, survivor): candidate is LATER in the Vec and is dropped on true.
    hits.dedup_by(|candidate, survivor| {
        if candidate.path != survivor.path { return false; }
        survivor.count += candidate.count; // both are &mut: fold into the keeper
        true
    });
    println!("{hits:?}"); // [Hit { path: "/a", count: 7 }, Hit { path: "/b", count: 8 }]

    // Same closure, parameters named in reading order: the sum goes into the
    // element that dedup_by then deletes. Prints [Hit { path: "/a", count: 1 }].
    let mut wrong = vec![Hit { path: "/a", count: 1 }, Hit { path: "/a", count: 2 }];
    wrong.dedup_by(|first, second| {
        if first.path != second.path { return false; }
        first.count += second.count; // `first` is the later one: this sum is lost
        true
    });
    println!("{wrong:?}");

    // Compared against the survivor: 2 is gone when 3 is tested, so 3 stays.
    let mut readings: Vec<i32> = vec![1, 2, 3, 4];
    readings.dedup_by(|candidate, survivor| candidate.abs_diff(*survivor) <= 1);
    println!("{readings:?}"); // [1, 3]
    // chunk_by compares consecutive ORIGINAL neighbours instead: [[1, 2, 3, 4]]
    let groups: Vec<&[i32]> = [1_i32, 2, 3, 4].chunk_by(|left, right| left.abs_diff(*right) <= 1).collect();
    println!("{groups:?}");
}
```

**Why it matters**

Collapsing adjacent duplicate log lines, merging sorted ranges, or summing per-key counts after a sort are all one `dedup_by` call with zero extra allocation, and that is the idiom. The bug is that the wrong-order version type-checks, runs, and produces a plausible result: the counts are just too low, which in a metrics path is the kind of wrong nobody alerts on. C++ has no `dedup_by` at all: `std::unique` takes a `BinaryPredicate` that the standard forbids from modifying its arguments, so the merge has to be a hand-written loop. F# and TypeScript have no in-place form either and would rebuild the list.

**Chew on this**

Where in your code does a closure take two arguments of the same type, and how would you know if a caller had them the other way round? Is "compare against the survivor" what your dedup predicates actually mean, or did they assume neighbours?

## C++: std::scoped_lock(mutex_); declares a lock over nothing named mutex_, and -Wall -Wextra say nothing

*Idioms and antipatterns*

**Did you know**

Write a lock without a variable name and the declaration grammar wins. `std::unique_lock<std::mutex>(mutex_);` is not a temporary that locks `mutex_`: it declares a new, default-constructed, unlocked `unique_lock` named `mutex_` that shadows the member. `std::scoped_lock(mutex_);` is worse: with CTAD (C++17) it declares a `std::scoped_lock<>` named `mutex_`, a lock over zero mutexes, and Clang 21 and 23 emit no diagnostic under `-Wall -Wextra` for it (only `-Wshadow` notices). The braced form `std::lock_guard<std::mutex>{mutex_};` does lock, then unlocks at the semicolon. All of this is C++17 onward for the CTAD case and every standard for the others; measured with Apple clang 21 and Homebrew clang 23.1.1 on libc++, GCC not available here.

**Show me**

```cpp
#include <mutex>

struct Counter {
    std::mutex mutex_;
    long total_ = 0;

    void add_unique() {
        // Declares unique_lock<std::mutex> mutex_; (default-constructed, owns nothing).
        // Clang: -Wvexing-parse "redundant parentheses around declaration of variable".
        std::unique_lock<std::mutex>(mutex_);
        ++total_;
    }
    void add_scoped() {
        // CTAD from zero arguments: std::scoped_lock<> mutex_; locks nothing.
        // -Wall -Wextra: silent. -Wshadow: "declaration shadows a field".
        std::scoped_lock(mutex_);
        ++total_;
    }
    void add_braced() {
        // A temporary: locks, unlocks at the ';'. libc++ marks the constructor
        // [[nodiscard]], so Clang warns -Wunused-value here.
        std::lock_guard<std::mutex>{mutex_};
        ++total_;
    }
    void add_correct() {
        std::scoped_lock guard(mutex_); // a name is what makes it a lock
        ++total_;
    }
};
// Two threads x 1,000,000 calls each, at -O0:
//   add_unique  1,120,217   add_scoped 1,023,081   add_braced 1,999,997
//   add_correct 2,000,000
// At -O1 all four printed 2,000,000: with no synchronization in the loop the
// optimizer collapsed the increments, so the race hid in the optimized test.
```

**Why it matters**

This is a data race that reviews well: the line says "lock" and the name of the mutex is right there. The optimized-build result is the nasty part, since a stress test at `-O1` reported a perfect count while the code locked nothing. The durable guard is not a warning flag but Clang's thread-safety analysis: annotate `total_` with `guarded_by(mutex_)`, build with `-D_LIBCPP_ENABLE_THREAD_SAFETY_ANNOTATIONS -Wthread-safety`, and all three broken methods are flagged ("writing variable 'total_' requires holding mutex 'mutex_' exclusively") while `add_correct` is not. Rust's version of the same slip is `let _ = mutex.lock()`, which compiles and unlocks on the same line; F#'s `lock obj (fun () -> ...)` takes the critical section as a function, so there is no unnamed-guard form to get wrong.

**Chew on this**

How many of your guard objects would still be correct if a grep for `(mutex` or `{mutex` with no variable name came back non-empty? Would your concurrency tests catch a race that only exists at `-O0`, and what does that say about which build they run against?

## F#: for i in 0L .. n was an IEnumerable loop until F# 9, and LangVersion 8.0 on today's compiler still makes it one

*Perf and memory model*

**Did you know**

Before F# 9, the compiler turned `for ... in start .. finish` into a plain counting loop only when the type was `int32` and the step was a constant `1` or `-1`. `for i in 0L .. n`, `for i in 0u .. n`, and `for i in 0 .. 2 .. n` compiled to an `IEnumerable<_>` with an interface call to `MoveNext` and `Current` for every element. F# 9 (PR #16650, .NET 9 SDK) lowers every built-in integral type and any step to a `while` loop, and builds `[| start .. step .. finish |]` at its exact size. The optimization is tied to the language version: the .NET 10 SDK compiler with `<LangVersion>8.0</LangVersion>` emits the slow form again.

**Show me**

```fsharp
// Same Program.fs, Release build, all run on the .NET 8.0.8 runtime.
// Columns: bytes allocated per call (Stopwatch's 40 B subtracted), time.
//
//                             SDK 8.0.401 (F# 8)   SDK 10.0.301 (F# 10)
// for i in 0 .. n  (20M)       0 B    9 ms          0 B   11 ms
// for i in 0 .. 2 .. n (10M)  96 B   40 ms          0 B    5 ms
// for i in 0L .. n  (20M)     96 B   51 ms          0 B    5 ms
// for i in n .. -1 .. 0        0 B    9 ms          0 B   11 ms  (-1 was always special-cased)
// [| for i in 0 .. 2 .. 1000 -> i * i |]  6432 B    2032 B  (exactly the 501-int array)
//
// SDK 10 compiler + <LangVersion>8.0</LangVersion>:  96 B / 37 ms and 96 B / 47 ms again.

let sum_int64 (count: int64) =
    let mutable total = 0L
    for index in 0L .. count do   // pre-F# 9: an enumerator, one interface call per step
        total <- total + index
    total

let sum_evens (count: int) =
    let mutable total = 0L
    for index in 0 .. 2 .. count do   // a non-1 step: same slow path before F# 9
        total <- total + int64 index
    total
```

**Why it matters**

The 96 bytes are one enumerator per loop, so the garbage is not the cost: the cost is an interface dispatch per element, about 8 to 10 times slower here, in exactly the loops people write when they index into large buffers with `int64` offsets or stride over interleaved data. A service that pins `LangVersion` for a library's sake, or still builds with an older SDK in CI, keeps paying it with nothing in the source to say so. Rust and C++ have no such cliff, since `(0..n).step_by(2)` and a plain `for` with `index += 2` are both ordinary inlined loops, which makes this a compiler-lowering fact about F# rather than a cost of ranges as such.

**Chew on this**

Which of your projects set `LangVersion` explicitly, and does anyone remember why? If a language-version setting can change the generated code of a loop, what else in your hot paths is quietly tied to it?

## TypeScript: getOrInsertComputed searches again after your callback, so a write the callback made to that key is overwritten

*New discoveries and currently popular patterns*

**Did you know**

`Map.prototype.getOrInsertComputed(key, callback)` (the TC39 "upsert" proposal, Stage 4 per its repository) is on by default in Node 26.0 (V8 14.6, released 2026-05-05) and is declared in TypeScript's `lib.esnext.collection.d.ts` (present in tsc 6.0.3; needs `lib: ["esnext"]`). The spec does not insert blindly after the callback returns: step 7 notes "The Map may have been modified during execution of callback", and step 8 searches again, overwriting the value if the key now exists. So a callback that writes its own key loses that write to its return value. The key is also canonicalized first, so a `-0` key reaches the callback as `+0`. With an `async` callback the Map caches the promise synchronously, which makes it a one-line single-flight cache, and that includes caching the rejection.

**Show me**

```typescript
// tsc 6.0.3 --strict --lib esnext,dom; run on Node 26.11.1 (type stripping).
const cache = new Map<string, string>();
const outer = cache.getOrInsertComputed("user:7", (key) => {
    cache.set(key, "written-inside-callback"); // re-entrant write to the same key
    return "returned-by-callback";
});
console.log(outer, cache.get("user:7"), cache.size);
// returned-by-callback returned-by-callback 1   (the inner write is gone)

// Re-entering with OTHER keys is fine: a recursive memo works.
const memo = new Map<number, bigint>();
const fib = (index: number): bigint =>
    index < 2 ? BigInt(index)
              : memo.getOrInsertComputed(index, () => fib(index - 1) + fib(index - 2));
console.log(fib(90), memo.size); // 2880067194370816120n 89

// The promise is stored before it settles, so concurrent callers share it,
// and a rejection is now the cached answer for that key.
const inflight = new Map<string, Promise<string>>();
let loader_calls = 0;
const load = (key: string) => inflight.getOrInsertComputed(key, async () => {
    loader_calls += 1;
    throw new Error("upstream 503");
});
// three sequential awaits of load("cfg") -> three rejections, loader_calls === 1
```

**Why it matters**

The re-search is the sane choice for a hash map in a single-threaded runtime, and the sibling languages show why it had to be decided at all. Rust rejects the re-entrant write at compile time, since `entry(key).or_insert_with(..)` holds `&mut` on the map for the closure's whole life. C++ has no computed form, and a recursive memo through `unordered_map::operator[]` keeps a reference across an insert that may rehash, which is undefined behaviour. .NET's `CollectionsMarshal.GetValueRefOrAddDefault` hands back a `ref` that a re-entrant add invalidates. JavaScript defines it: the outer call wins, silently. Meanwhile `getOrInsert(key, default)` evaluates `default` on every call, hit or miss, the same eager-argument cost as C++'s `optional::value_or`.

**Chew on this**

Which of your caches would you rather have return a stored rejection than retry, and which would you rather not? If a callback's own write is overwritten, what does that mean for a callback that registers itself in the map to break a cycle?

# The functional angle: grouping adjacent runs is a view in Rust and C++23, a mutation in dedup_by, and a hand-written fold in F# and TypeScript

Draws on the Rust tip (`dedup_by` against `chunk_by`), with rows built for the other three languages. The shape: split `[1, 2, 3, 7, 8, 3]` into runs whose neighbours differ by at most 1.

```rust
// Rust: chunk_by borrows the slice; no allocation until you collect.
let runs: Vec<&[i32]> = readings.chunk_by(|left, right| left.abs_diff(*right) <= 1).collect();
```

```cpp
// C++23 views::chunk_by, libc++ in Apple clang 21: prints [ 1 2 3 ][ 7 8 ][ 3 ]
auto close = [](int left, int right) { return left - right <= 1 && right - left <= 1; };
for (auto run : readings | std::views::chunk_by(close)) { /* run is a subrange */ }
```

```fsharp
// F#: FSharp.Core has no adjacent grouping; List.groupBy merges non-adjacent keys.
let runs =
    List.foldBack (fun value runs_so_far ->
        match runs_so_far with
        | (head :: _ as run) :: rest when abs (head - value) <= 1 -> (value :: run) :: rest
        | _ -> [value] :: runs_so_far) readings []
// [[1; 2; 3]; [7; 8]; [3]]
```

```typescript
// TypeScript: Map.groupBy (ES2024) groups by key, not by adjacency:
// [[false, [1, 2, 3, 3]], [true, [7, 8]]]  -- the trailing 3 joined the first run.
```

| Language | Functional form | What it costs |
| --- | --- | --- |
| Rust | `slice::chunk_by` (1.77) | nothing: a borrowed view; `dedup_by` is the in-place, `&mut` alternative that compares against the survivor instead |
| C++ | `views::chunk_by` (C++23; libc++ in Clang 21 has it) | a lazy view, so the lifetime of `readings` is your problem; no in-place merge form, `std::unique` forbids modifying its arguments |
| F# | `List.foldBack` by hand | a new list per run and a pattern to get right; the closest built-in, `List.groupBy`, has the wrong semantics |
| TypeScript | `reduce` by hand | a new array per run; `Map.groupBy` and `Object.groupBy` silently merge non-adjacent runs |

The asymmetry worth noticing is the mutation one. Rust is the only language here whose standard library offers the in-place merge, and it is precisely the `&mut` in `dedup_by`'s signature that makes it both possible and easy to get backwards. Is a run-merge that needs `&mut` to be allocation-free still the functional form, or is `chunk_by` plus a fold the honest version and `dedup_by` the optimization?

# The security angle: a critical section that compiles is not a critical section that holds

Draws on the C++ tip and the TypeScript tip, Mode B: both teach a mechanism that looks like mutual exclusion, so ask whether it is. The C++ tip runs in the "does not prevent" direction; the TypeScript tip runs in both.

The C++ sample, ordinary-looking and wrong (CWE-667, Improper Locking; the outcome is a CWE-362 race):

```cpp
void Account::withdraw(long amount) {
    std::scoped_lock(mutex_);          // declares scoped_lock<> mutex_; locks nothing
    if (balance_ >= amount) balance_ -= amount;  // check-then-act, unprotected
}
```

The TypeScript version has no threads and the same bug, because every `await` is a point where another request runs (CWE-367, time-of-check time-of-use):

```typescript
// Five concurrent callers, measured on Node 26.11.1: the loader ran 5 times.
const get_racy = async (key: string) => {
    if (!racy.has(key)) racy.set(key, await slow_load(key)); // the gap is the await
    return racy.get(key)!;
};
// getOrInsertComputed(key, slow_load) stores the promise first: the loader ran once.
```

And the keyed-collection half of the same tip (CWE-1321): a plain-object multimap keyed by request data, `(by_tag[tag] ??= []).push(id)`, throws `by_tag[tag].push is not a function` for the tags `__proto__` and `constructor`, because `??=` finds the inherited property and never assigns. The `Map` version accepted all three keys. That is a request that crashes the handler, chosen by whoever picks the tag.

| Language | What goes wrong | What the language does | Still on you |
| --- | --- | --- | --- |
| C++ | an unnamed guard declares a variable or a temporary; nothing is locked | nothing by default; `-Wvexing-parse` covers one form, `-Wshadow` another | `guarded_by` annotations plus `-Wthread-safety`, which flagged all three broken forms |
| Rust | `let _ = mutex.lock()` drops the guard on the same line | the guard type makes unprotected access to the data impossible, so the slip shows up as a compile error at the use, not a race | a guard dropped early around a check that spans two locks |
| F# | `lock` on a value type would box and lock a fresh object each time | `lock` requires `'Lock : not struct`; `lock 42 (fun () -> ())` is FS0001 in `dotnet fsi` 8.0.401 | which object is the lock, since any reference will do |
| TypeScript | check-then-act across an `await`; prototype keys in a plain-object map | nothing: no threads, so no locks, and no runtime types | single-flight with `getOrInsertComputed` (and deciding whether a cached rejection is acceptable); `Map` for attacker-chosen keys |

Rust is the baseline for this failure class, because it moves the protection from the lock to the data: the counter is reachable only through the guard. The Rust row rests on the 2026-10-09 entry and was not re-run today. Which of your shared counters, caches, or balances is reachable without going through the thing that is supposed to protect it?
